# Torii საბოლოო წერტილები {#torii-endpoints}

Torii ეს არის HTTP, SSE, და WebSocket შესასვლელი Iroha 3. ეს ემსახურება ორივე.
ლიდერის მიმართულება APIs და ოპერატორის საბოლოო წერტილები.

ამჟამინდელი პროტოკოლის წესებია:

- კანონიკური ბინარული ფორმატი არის **Norito**
- მრავალი საბოლოო წერტილი ასევე მხარს უჭერს JSON როდესაც თქვენ გაგზავნით `Accept: application/json`
- მაჩვენებლები გამოქვეყნებულია Prometheus ფორმატში

ფორმატის დეტალების, შინაარსის მოლაპარაკებების, განლაგების დროშების, სქემა ჰეშების და
Norito RPC ხელმძღვანელობა, იხილეთ [Norito რეფერენცია](/ka/reference/norito.md).

## საერთო საბოლოო წერტილები {#common-endpoints}

| საბოლოო წერტილი | ფორმატირება | მიზანი |
| --- | --- | --- |
| `POST /transaction` | Norito | წარადგინეთ ხელმოწერილი ოპერაცია |
| `POST /query` | Norito | წარადგინეთ ხელმოწერილი გამოკითხვა |
| `GET /events` | WebSocket | გამოწერეთ ღონისძიებების ნაკადები |
| `GET /block/stream` | WebSocket | მიმოქცევაში ჩართული ბლოკები |
| `GET /peers` | JSON | პარტნიორთა სია, რომლებიც გამოქვეყნებულია Torii |
| `GET /health` | JSON | მსუბუქი სიცოცხლის საზღვრის წერტილი |
| `GET /api_version` | JSON | დეფოლტი API ვერსია |
| `GET /status` | JSON | მაღალი დონის სტატუსის შეჯამება ოპერატორებისთვის |
| `GET /metrics` | პრომეთეუსი | Prometheus scrape საწინააღმდეგო წერტილი |
| `GET /schema` | JSON | მონაცემთა მოდელის სქემის გადაღება, რომელსაც ემსახურება კვანძი |
| `GET /openapi` ან `GET /openapi.json` | JSON | OpenAPI დოკუმენტი აქტიური Torii HTTP მარშრუტები |
| `GET /v1/parameters` | JSON | კვანძის პარამეტრების გადაღება |
| `GET /v1/node/capabilities` | JSON | კვანძის შესაძლებლობა და მონაცემთა მოდელის მეტა-მონაცემები |
| `GET /v1/api/versions` | JSON | მხარდაჭერა Torii API ვერსიები |
| `GET /v1/events/sse` | SSE | ღონისძიებების ნაკადი ხანგრძლივი კლიენტებისთვის |
| `GET /v1/time/now` | JSON | კვანძის კედლის საათის სურათი |
| `GET /v1/time/status` | JSON | დროის სინქრონიზაციის სტატუსი |

`/openapi` არის ავტორიტეტული საბოლოო წერტილების სია მიმდინარე კვანძისთვის. ზუსტი
ზედაპირი დამოკიდებულია build მახასიათებლები და runtime კონფიგურაცია, ასე რომ წარმოქმნილი
კლიენტებმა უნდა უპირატესობდნენ პირდაპირი OpenAPI დოკუმენტი ხელით გადაწერილი მარშრუტის სიაზე.
გამოიყენეთ [Torii API კონსოლი](/ka/reference/torii-api-console.md) რომ დატვირთოთ ეს ცოცხალი
დოკუმენტი, ტესტი JSON მარშრუტები, ასლი curl მოთხოვნები, და გენერირებს კლიენტის კოდი
მიმდინარე სქემა.

## სცადე ცოცხალი Taira მარშრუტები {#try-live-taira-routes}

საზოგადოება Taira სატესტო ქსელი ამჟღავნებს იგივე Torii JSON ზედაპირზე ამ აპლიკაციის
კლიენტები იყენებენ მხოლოდ წაკითხვის მიზნით. ეს ბრძანებები არ საჭიროებს გასაღებს:

```bash
TAIRA_ROOT=https://taira.sora.org

curl -fsS "$TAIRA_ROOT/status" \
  | jq '{blocks, txs_approved, txs_rejected, queue_size, peers}'

curl -fsS "$TAIRA_ROOT/openapi.json" \
  | jq -r '.paths | keys[]' \
  | grep '^/v1/' \
  | head -n 20

curl -fsS "$TAIRA_ROOT/v1/node/capabilities" \
  | jq '{abi_version, data_model_version, query: .query.aggregate.supported_resources}'
```

შეეცადეთ რესურსის წაკითხვა დღევანდელი მსოფლიო მდგომარეობის წინააღმდეგ:

```bash
curl -fsS "$TAIRA_ROOT/v1/domains?limit=5" \
  | jq -r '.items[].id'

curl -fsS "$TAIRA_ROOT/v1/assets/definitions?limit=5" \
  | jq -r '.items[] | [.id, .name, .total_quantity] | @tsv'
```

თუ საჯარო ტესტნეტის მარშრუტი ბრუნდება `502`, დროის გამოშვება, ან ანგარიშებს დამაჯერებული
რიგი, განიხილოს ეს როგორც საბოლოო წერტილის ხელმისაწვდომობის საკითხი და შეეცადეთ მოგვიანებით ადრე
თქვენი კლიენტის კოდის დებეგირება.

## აპლიკაცია და SORA რუტის ოჯახები {#app-and-sora-route-families}

როდესაც Torii არის აშენებული აპლიკაციის მიმართულებით ფუნქციების კომპლექსით, ის გამოყოფს დამატებითი JSON
მკვლევართა ოჯახები, SORA მომსახურება, ხიდების ნაკადი, მტკიცებულებები და შენახვა. ეს
ყველა ქსელის პროფილზე ოჯახები არ არის ჩართული.

და აქტივების განსაზღვრა ID. პასუხი არის: `202 Accepted` მქონე `message_id`,
`transaction_hash`, `status`, `pacs002_code`, და გადაჭრილი
ლიდერის/ანგარიშის/აქტივის კონტექსტი.

## Kaigi სხდომები {#kaigi-sessions}

Kaigi უზრუნველყოფს გადახდილი, რეალურ დროში აუდიო/ვიდეო ოთახები SORA Nexus. გამოიყენეთ როდესაც
აპლიკაციისთვის საჭიროა რეგისტრირებული სესიის შექმნა, რესტრის ცვლილებები, რელიე
მანიფესტები, კოდირებული სიგნალი და გამოყენების გაზომვა იმის ნაცვლად, რომ ყველა
კონფერენციები სახელმწიფო გარეთ ჯაჭვი.

რეგისტრირებული ცხოვრების ციკლი არის:

- `CreateKaigi`: შექმნას მოწოდება დომენის ქვეშ და შეინახოს მისი პოლიტიკა,
  გრაფიკი, მეტა მონაცემები და არაკომპანიური რელე მანიფესტი.
- `JoinKaigi` და `LeaveKaigi`: აჟრაიზეთ ზარების სია.
  მონაწილეები იყენებენ ვალდებულებებს, ანულიფიტორებს და სიაში მტკიცებულებებს ნაცვლად
  მონაწილეების ანგარიშის განსაზღვრა IDs პირდაპირ.
- `RecordKaigiUsage`: მიუთითეთ გაზომული ხანგრძლივობა და გაზის მთლიანი რაოდენობა.
- `EndKaigi`: შეწყვიტეთ სესია და ჩაწერეთ ბოლო დროის ბეჭედი.

Torii გამოყოფს რელეების ტელემეტრიას ქვემოთ `/v1/kaigi/relays`,
`/v1/kaigi/relays/{relay_id}`, `/v1/kaigi/relays/health`, და
`/v1/kaigi/relays/events` როდესაც აპლიკაცია API და ტელემეტრიული თვისებები ჩართულია.
სესიის მდგომარეობა ასახულია Kaigi დომენის მოვლენები, როგორიცაა
`KaigiRosterSummary`, `KaigiRelayManifestUpdated`,
`KaigiRelayHealthUpdated`, და `KaigiUsageSummary`.

### CLI მოწევის ტესტირება {#cli-smoke-test}

დავიწყოთ `iroha kaigi` CLI როდესაც გსურთ დაადასტუროთ, რომ Torii საბოლოო წერტილი
მიიღებს Kaigi ტრანზაქციები, სანამ დაკავშირება UI. სწრაფი დაწყების ბრძანება
ქმნის დროებით ოთახს აქტიური წინააღმდეგ Torii საბოლოო წერტილი და ბეჭდვის შემაჯამებელი
ზარის იდენტიფიკატორთან ერთად, შეუერთდით ბრძანებას და SoraNet კედლის მინიშნება:

```bash
iroha kaigi quickstart --auto-join-host --summary-out kaigi-summary.json
```

სკრიპტირებული ნაკადებისათვის, განახორციელეთ ოთახის სიცოცხლის ციკლი მკაფიოდ:

```bash
iroha kaigi create \
  --domain streaming \
  --call-name daily \
  --host <i105-account-id> \
  --privacy-mode transparent \
  --room-policy authenticated

iroha kaigi join --domain streaming --call-name daily --participant <i105-account-id>
iroha kaigi leave --domain streaming --call-name daily --participant <i105-account-id>

iroha kaigi record-usage \
  --domain streaming \
  --call-name daily \
  --duration-ms 120000 \
  --billed-gas 1500

iroha kaigi end --domain streaming --call-name daily
```

გამოყენება `--room-policy public` იმ ოთახებისთვის, რომლებსაც რელეებს შეუძლიათ გამოავლინონ დამთვალიერებლის გარეშე
ბილეთები ან `--room-policy authenticated` როდესაც გასასვლელებს უნდა მოითხოვონ მაყურებელი
ავთენტიფიკაცია. გამოყენება `--privacy-mode zk-roster-v1` მხოლოდ მას შემდეგ, რაც ქსელმა
დასახელება Kaigi საკონფიგურირებული სიის და გამოყენების გადამოწმების გასაღები; სხვაგვარად შეკრებები, ფოთლები,
და კერძო გამოყენების ჩანაწერები არასწორია დეტერმინისტური შემოწმების დროს.

1. დაიწყეთ Iroha კვანძთან ერთად SORA/Kaigi აპლიკაციის მიმართულება APIs ჩართულია ან გამოიყენება
   საჯარო საბოლოო წერტილი, რომელიც აჩვენებს Kaigi ზედაპირები, რომლებიც გჭირდებათ.
2. შეამოწმეთ ძირითადი ხელმისაწვდომობა `/health`, შემდეგ შეამოწმეთ პირდაპირი მარშრუტის ზედაპირი
   მქონე `/openapi` ან `/openapi.json`. ზოგიერთი განთავსება ასევე გამოფენს
   `/v1/health`, მაგრამ `/health` ეს არის პორტატული სიცოცხლის კონტროლი.
3. სამედიცინო მომსახურებისათვის TAIRA, გადაცემის ტელემეტრიული მარშრუტების შემოწმება პირდაპირი შეხვედრის ჩატარებამდე:

   ```bash
   TAIRA=https://taira.sora.org
   curl -fsS "$TAIRA/health"
   curl -fsS "$TAIRA/v1/kaigi/relays"
   curl -fsS "$TAIRA/v1/kaigi/relays/health"
   ```

   ეს შემოწმებები ადასტურებს, რომ Torii და Kaigi რელეების ტელემეტრიის მიღწევა შესაძლებელია.
   არ შექმნას შეხვედრა; `CreateKaigi` და `JoinKaigi` ჯერ კიდევ საჭიროა დაფინანსება
   საფულეები და ხელმოწერილი ტრანზაქციის წარდგენა.
4. გახსნა დემო, წადი **პარამეტრები**, დაყენება Torii URL, და შეუშვით აპლიკაცია ატვირთოს
   ჯაჭვი ID და საბოლოო წერტილიდან ქსელის პრეფექსი.
5. შექმნათ ან აღადგინეთ ორი ადგილობრივი ქაღალდი დემოში. გამოიყენეთ ცალკე აპლიკაციის ფანჯრები,
   პროფილები, ან მანქანები ასე რომ მასპინძელი და სტუმარი აქვს ცალკე ქაღალდის მდგომარეობა.

ტესტირებისთვის Kaigi UI:

1. ფანჯარაში, ღია. **Kaigi**, აირჩიეთ **შეხვედრა დაიწყეთ**, დაასახელოს სათაური,
   და აირჩიე **პირადი მოწვევა** ან **გამჭვირვალე მოწვევა**.
2. შეარჩიეთ **ჩართეთ კამერა და მიკროფონი** ასე რომ, WebRTC ადგილობრივი მედია აქვს.
3. შეარჩიეთ **შექმნას შეხვედრის ბმული**. ცოცხალი საფულე წარადგენს `CreateKaigi`; დასახელება
   აპლიკაცია შემდეგ აჩვენებს `iroha://kaigi/join?call=...&secret=...` მოწვევა და
   `#/kaigi?...` ზვნაგრაჟა.
4. ღია დარჩეთ მასპინძლის ფანჯარა და გაუზიარე მოწვევა სტუმართან.
5. სტუმრების ფანჯარაში, გახსენით მოწვევა ან ჩასმის იგი **შეკრებაზე გაწევრიანება**, გადატრიალება
   ადგილობრივ მედიაში და შეარჩიეთ **შეკრებაზე გაწევრიანება**. ცოცხალი საფულე იღებს
   დაშიფრული მასპინძელი შეთავაზება Torii და წარუდგენს `JoinKaigi` დაშიფვრილი
   პასუხი მეტა მონაცემებზე.
6. მასპინძელმა უნდა ავტომატურად დააყენოს პირველი პასუხი სტრიმინგის ან გამოკითხვის საშუალებით Kaigi
   ზარის სიგნალები. ორივე ფანჯარა უნდა აჩვენოს დაკავშირებული მედია და განახლებული
   კავშირის დეტალები.
7. შეწყვიტეთ სესია მასპინძელიდან, ან გამოიყენეთ CLI `iroha kaigi end` ბრძანება
   იგივე ზარი ID.

კერძო Kaigi დაცული საჭიროებები XOR გადახდის კერძო შესასვლელის საფასური.
demo ანგარიშები, რომ პირადი Kaigi დაცული საჭიროებები XOR, გამოიყენეთ აპლიკაცია
თვითშფარდი მოახდენს და კვლავ ცდილობს შექმნას ან შეუერთდეს ქმედება. თუ მტკიცებულება წარმოქმნა,
კერძო დაფინანსება, ან პირდაპირი სიგნალი არ არის ხელმისაწვდომი, დემო შეიძლება დაეცემა უკან
გამჭვირვალე/მანუალური ნაკადი. ამ შემთხვევაში ღია **მოწინავე სიგნალი**, გადაწერე
ნედლეული შეთავაზება ან პასუხი პაკეტი, და დააჭირეთ იგი მეორე ფანჯარაში.

ავტომატური შემოწმებისათვის დემო რეპოში, გაუშვით:

```bash
npm test -- tests/kaigiView.spec.ts tests/preloadKaigiBridge.spec.ts
npm run e2e:ui
npm run verify
```

ფოკუსირებული Vitest სუიტების საფარი Kaigi შეხვედრის ბმულის შექმნა, კომპაქტური მოწვევა
დატვირთვა, კერძო შექმნა/შეერთება/სრული ხიდის ზარები, თვითგადაკეტების შეტყობინებები, სახელმძღვანელო
ჩავარდნა და პასუხების მიმოხილვა UI ღუმელის გამოცდა მოიცავს: `/kaigi` მარშრუტი
სამუშაო მაგიდის და მობილური ზომის ნახვა პორტები. პირდაპირი მედია ორ საფულეებს შორის ჯერ კიდევ
საჭიროა ორი ფანჯრის სახელმძღვანელო ტესტი, რადგან ბრაუზერის კამერა / მიკროფონის ნებართვა
და პარტნიორული მედიის ნაკადები გარემოსთვის სპეციფიკურია.

ნიმუშების ინტეგრაციის კოდისათვის იხილეთ

## სტატუსი და მაჩვენებლები {#status-and-metrics}

სტატუსისა და მაჩვენებლების ბოლო წერტილები არის პირველი რამ, რომელიც ჩართულია დეშბორდებში:

- `/status` გამოყოფს უმაღლესი დონის თანატოლების, ბლოკების, რიგებისა და კონსენსუსის ველებს
- `/metrics` გამოყოფს Prometheus- ის მაჩვენებლებს, საზომილებს და ჰისტოგრამებს

დაწყებული Nexus-შეამოქმედებული კვანძები, სტატუსის გამოსავალი ასევე მოიცავს ბილიკსა და მონაცემთა სივრცეზე ინფორმირებულს
სექციები. `nexus.enabled = false`, ეს განყოფილებები გამორიცხულია.

## JSON ვ.მ. Norito {#json-vs-norito}

რამდენიმე ოპერატორის საბოლოო წერტილის დაბრუნება Norito გათვალისწინებით. როდესაც ბოლო წერტილი მხარს უჭერს
JSON, გაგზავნა:

```http
Accept: application/json
```

ეს განსაკუთრებით სასარგებლოა:

- `/v1/sumeragi/status`
- `/v1/sumeragi/qc`
- `/v1/sumeragi/commit_qc/{hash}`

როდესაც საბოლოო წერტილი იღებს ან ბრუნდება დაწერილი Norito პირდაპირი გამოყენება
`application/x-norito` როგორც შინაარსის ტიპი ან სასურველი `Accept` ღირებულება. იხილეთ
[Norito](/ka/reference/norito.md#torii-and-norito-rpc) სატრანსპორტო დეტალებისთვის.

საბოლოო წერტილების ხილვადობა დამოკიდებულია ტელემეტრიის პარამეტრებზე.
ხუთი პროფილის დონე:

| `disabled` | არა | არა | არა |
| `operator` | დიახ | არა | არა |
| `extended` | დიახ | დიახ | არა |
| `developer` | დიახ | არა | დიახ |

## CLI მოკლე გზები {#cli-shortcuts}

სააგენტო `iroha` CLI უკვე ამდენი დასასრული აქვს:

```bash
iroha --config ./localnet/client.toml --output-format text ops sumeragi status
iroha --config ./localnet/client.toml --output-format text ops sumeragi phases
iroha --config ./localnet/client.toml ops sumeragi params
iroha --config ./localnet/client.toml --output-format text ops sumeragi telemetry
```
