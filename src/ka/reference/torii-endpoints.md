# Torii საბოლოო წერტილები {#torii-endpoints}

Torii ეს არის HTTP, SSE, და WebSocket შესასვლელი Iroha 3. იგი ემსახურება ორივე ლიდერების მიმართულებით APIs და ოპერატორის საბოლოო წერტილები.

ამჟამინდელი პროტოკოლის წესები არის:

- კანონიკური ორმაგი ფორმატი არის Norito
- ბევრი საბოლოო წერტილი ასევე მხარს უჭერს JSON, როდესაც თქვენ გაგზავნით `Accept: application/json`
- მაჩვენებლები არის გამოქვეყნებული Prometheus ფორმატში

ფორმატის დეტალების, შინაარსის მოლაპარაკებების, განლაგების დროშების, სქემა ჰეშების და Norito RPC სახელმძღვანელოებისათვის იხილეთ [Norito რეფერენცია ](/ka/reference/norito.md).

SSE თხოვნისთვის, რეკლამირება მშობლიური ნაკადი და დამატებით ტიპირებული ჩამოტვირთვა:

```http
Accept: text/event-stream, application/json
```

Torii პირველ რიგში მოლაპარაკებებს აწარმოებს JSON ან Norito წარმოდგენის შესახებ თხოვნის ფენაზე, შემდეგ კი ამტკიცებს მშობლიურ `text/event-stream` პასუხს. შესაბამისად მხოლოდ `text/event-stream`-ის გაგზავნა უარყოფითია `406`; [-სტრიმ-ევენტების რეცეპტი](/ka/cookbook/stream-events.md) იყენებს სრულ სათაურს.

`/openapi` არის სქემაში წარმოდგენილი მარშრუტების ძირითადი გენერირებული ხელშეკრულება, და არა მთლიანი ოპერაციული კვლევის ინვენტარი. მიმდინარე დოკუმენტი გამორიცხავს `/livez` და `/readyz`, ხოლო მისი აღწერა `/health` შეიძლება ჩამორჩეს მზადყოფნის მმართველს. გენერირეთ მარშრუტის კლიენტები ცოცხალი დოკუმენტიდან, მაგრამ შეამოწმეთ სიცოცხლისუნარიანობა და მზადყოფნა პირდაპირ მიმდინარე კვანძისა და ჩაკეტილი მენეჯერების წინააღმდეგ. ზუსტი ზედაპირი კვლავ დამოკიდებულია აშენების მახასიათებლებსა და გამშვებ დროის კონფიგურაციაზე. გამოიყენეთ [Torii API კონსოლი ](/ka/reference/torii-api-console.md) იმ ცოცხალი დოკუმენტის დატვირთვა, ტესტირება JSON მარშრუტები, კოპირება curl მოთხოვნები და გენერირება კლიენტის კოდი დღევანდელი სქემიდან.

## სცადეთ პირდაპირი Taira მარშრუტები {#try-live-taira-routes}

საჯარო Taira ტესტის ქსელი ამჟღავნებს იმავე Torii JSON ზედაპირს, რომელსაც აპლიკაციის კლიენტები მხოლოდ წაკითხვის მიზნით იყენებენ. ეს ბრძანებები არ საჭიროებს გასაღებებს:

```bash
TAIRA_ROOT=https://taira.sora.org

curl -fsS -H 'Accept: application/json' "$TAIRA_ROOT/status" \
  | jq '{blocks, txs_approved, txs_rejected, queue_size, peers}'

curl -fsS "$TAIRA_ROOT/openapi.json" \
  | jq -r '.paths | keys[]' \
  | grep '^/v1/' \
  | head -n 20

curl -fsS -H 'Accept: application/json' \
  "$TAIRA_ROOT/v1/node/capabilities" \
  | jq '{abi_version, data_model_version, query: .query.aggregate.supported_resources}'
```

შეეცადეთ რესურსის წაკითხვა დღევანდელი მსოფლიო მდგომარეობის წინააღმდეგ:

```bash
curl -fsS "$TAIRA_ROOT/v1/domains?limit=5" \
  | jq -r '.items[].id'

curl -fsS "$TAIRA_ROOT/v1/assets/definitions?limit=5" \
  | jq -r '.items[] | [.id, .name, .total_quantity] | @tsv'
```

თუ საჯარო ტესტნეტის მარშრუტი ბრუნდება `502`, დროთა განმავლობაში ან იუწყება გაჯერებული რიგის შესახებ, განიხილეთ ეს როგორც საბოლოო პუნქტის ხელმისაწვდომობის პრობლემა და კიდევ ერთხელ შეეცადეთ მოგვიანებით თქვენი კლიენტის კოდის დებეგირების წინ.

## App და SORA მარშრუტის ოჯახები {#app-and-sora-route-families}

## ანგარიშის ავთენტიფიკაცია, ხილვადობა და Explorer- ის კურსორები {#account-authentication-visibility-and-explorer-cursors}

აპლიკაციის მიმართულების ლიდერის წაკითხვა იყენებს ერთ-ერთ ვარიანტურ კანონიკურ ანგარიშზე ხელმოწერის საზღვარს. ხელმოუწერელი მოთხოვნა იღებს მხოლოდ აქტიურ საჯარო მონაცემთა ბაზებს. ვალიდური ხელმოწერილი მოთხოვნა ემატება დამრევილის მიმდინარე UAID და ზუსტი მონაცემთა ბაზის მარშრუტებს, რომლებიც ამ ანგარიშის `CanReadRestrictedDataspace` ნებართვებით არის დასახელებული. `CanReadAllLedgerData` აძლევს ხილვადობას ყველა მონაცემთა სივრცეში. მხოლოდ `X-Iroha-Account` ან ნებისმიერი არასრულყოფილი ან არასწორად ჩამოყალიბებული ხელმოწერის სათაურის კომპლექტი უზრუნველყოფს `401 Unauthorized`; იგი არ მიუბრუნდება ანონიმურ ხილვადობამდე.

ერთი და იგივე ხილვადობის ობიექტი ფილტრებს ანგარიშს, დომენს, აქტივის განსაზღვრას, აქტივს, NFT, RWA, მფლობელს და Explorer კითხულობს. არარსებული ობიექტი და ობიექტი, რომელიც ზარის ხილული მარშრუტების გარეთ არის მიზანმიმართულად შეუცვლელი. ჩადენილი ტრანზაქციის და ინსტრუქციების ისტორია ნაჩვენებია მხოლოდ მაშინ, როდესაც ყველა მარშრუტის კუთხე რეგისტრირებულია ტრანსაქციაზე. შერეული მონაცემთა სივრცის ტრანზაკცია აქედან გამომდინარე, დამალულია მაშინ, როდესაც ერთ-ერთი მონაწილე კიდეც არ შედის მოწოდებლის სფეროს გარეთ; დაკარგული, მოძველებული ან არასწორად ჩამოყალიბებული მარშრუტის კონტექსტი ჩანს მხოლოდ გლობალური მკითხველი.

Torii იყენებს ამ მასშტაბს მომხმარებლის ფილტრების, გვერდების განლაგების, გათვლის ან პროექციების წინ SSE, WebSocket, ხელშეკრულების მოვლენებისა და განმეორებითი გზებზე. ხანგრძლივი ნაკადები ახდენენ იმავე ავტორიზაციის გადაფასებას, როგორც მთავარ წიგნის ნებართვები იცვლება და დასრულდება ზოგადი ავტორიზაციით ჩავარდნის შემდეგ. აღკვეთილია.

ექვსი მსოფლიო მხარდაჭერილი Explorer კოლექცია იყენებს არაგამჭვირვალე კანონიკური base64url საკვანძო კომპლექტის კურსორებს. გაზუსტებული გვერდის ლიმიტი არის 25, მაქსიმუმი არის 100, ხოლო ერთი გვერდი ინსპექტირებს მაქსიმუმ 512 კანდიდატურ საკვანძიებლებს. თითოეული კურსორი უკავშირდება მის კოლექციას, ფილტრებს, კანონიკურ ბოლო გასაღებას და დამრეკავის ხილულ მარშრუტ-სეტ დიგესტს, ასე რომ ის არ შეიძლება განმეორდეს სხვა გამოკითხვაზე ან მას შემდეგ, რაც დამრევილის ხილვადობა იცვლება.

ბლოკი, ოპერაცია, ბოლო ტრანზაქცია, ინსტრუქცია და უახლესი ინსტრუქციის ისტორია კურსორები დამატებით pin committed snapshot სიმაღლე და ბლოკ hash. პასუხები გამოავლინებს `pagination.limit`, `pagination.snapshot_height`, `pagination.snapshot_hash`, `pagination.next_cursor`, და `pagination.has_more`. სხვა მარშრუტის ან ფილტრების კომპლექტის კურსორი, შეცვლილი ხილვადობის დიგესტი, ან სურათი, რომ კვანძის ვეღარ შეამოწმოს არ დახურულია. ისტორია სკანირება რჩება შიგნით Torii ნებართვა შეკითხვის შესასვლელად, სანამ ბლოკირებული მუშაკი გაიქცევა.

Explorer WebSocket ნაკრებები გამოყოფენ ფილტრირებულ შემაჯამებლებს და აღადგენს ხილვადობას, როდესაც ბაღის ნებართვები იცვლება. მშობლიური `GET /v1/blocks/stream` მარშრუტი განსხვავებულია: ის გამოიყოფა სრული ხელს დაწერილ ბლოკებს, საჭიროებს `CanReadAllLedgerData` ხელის შეხების დროს და იხურება, თუ ეს ნებართვა მოგვიანებით მოიხსნება. არ გამოიყენოთ მშობლიური ნაკადი მონაცემთა სივრცეზე სკოპირებული ექსპლუატორისთვის.

ცოცხალი `GET /v1/sumeragi/status/sse` კონსენსუს-დიაგნოსტიკური ნაკადი ასევე არ არის ანონიმური მონაცემთა სივრცის მიწოდება. იგი მოითხოვს ოპერატორის ხელმოწერის სათაურის კვარტეტს თითოეული კავშირის მცდელობისას. კლიენტები გენერირებენ ახალი ხელმოწერას ზუსტ ნაკადისთვის URI და ავტომატური ტრანსპორტის განმეორებით არ ასრულებენ გადამისამართებას ან იმეორებს ხელმოწერილი მცდელობას.

`pacs.009` წარდგენილებში უნდა იყოს წარმოდგენილი საქმიანი შეტყობინება ID, შეტყობინის განსაზღვრა ID, შექმნის დრო, ბანკთაშორისი ანგარიშსწორების თანხა, ვალუტა, ანგარიშგების თარიღი. ინსტრუქციული აგენტი BICs, და ვალდებული და კრედიტორი IBANs. თუ შეტყობინება მოიცავს `Purp`, ხიდი ამჟამად მხოლოდ ფასიანი ქაღალდების მიზნით დაფინანსებას იღებს: `Purp=SECU`.

`pacs.008` და `pacs.009` წარდგენის საბოლოო წერტილები იღებენ XML ISO კონვერტებს ან ხიდის გამოცდებისას გამოყენებულ ფლატურ მოედნის ფორმატს. არამარჩევნო `SplmtryData` მოედნებს შეუძლიათ მიზნული Iroha ლიდერის ჩაგდება, წყარო და სამიზნე ანგარიში IDs ან მისამართები, და აქტივების განსაზღვრა ID. პასუხი არის `202 Accepted` `message_id`, `transaction_hash`, `status`, `pacs002_code` და გადაჭრილი ლიდერის/ანგარიშის/აქტივის კონტექსტით.

### მონაწილეების ავტორიზაცია და სიცოცხლის ციკლის მფლობელობა {#participant-authorization-and-lifecycle-ownership}

ყველა ჩართული ხიდს აქვს მონაწილეების კატალოგი. თითოეულ მონაწილეს აქვს უნიკალური მონაწილე ID, ერთი ან მეტი ოპერატორის საჯარო გასაღები, ერთი ან რამდენიმე ფინანსური იდენტიფიკატორი, ნებადართული პროფილის ნაკრები და `originator`, `counterparty` ან ორივე როლი . ოპერატორის გასაღები და ფინანსური იდენტიფიკატორები არ შეიძლება ეკუთვნოდეს ერთზე მეტ მონაწილეს. კონფიგურაცია `audit_admin_keys` ცალკე; აუდიტის ადმინის გასაღები ასევე ვერ იქნება მონაწილე მუტაციის გასაღები.

ყველა ISO მარშრუტისთვის საჭიროა ახალი ოპერატორის ხელმოწერა. საწყისი `pacs.008`, `pacs.009`, `sese.023` ან `colr.012` წარდგენისას, დამოწმებული ოპერატორი უნდა ეკუთვნოდეს მონაწილეზე, რომელიც განსაზღვრულია განაცხადის სათაურით `From` ფინანსური იდენტობის მიხედვით . `To` იდენტობა უნდა დაასახელოს სხვა კონფიგურირებული მონაწილე, ხოლო შერჩეული პროფილი უნდა იყოს ნებადართული ორივე მხარისთვის. ხანგრძლივი მიღების მონაცემები ფიქსირებს წარმომადგენელს, საპირისპირო მხარეს, მისაღებ მონაწილეს და ოპერატორის გასაღებად, ასევე ორიგინალურ პროფილსა და ჩაშენებულ ხელმოწერზე პოლიტიკას.

სასიცოცხლო ციკლის ავტორიზაცია გამომდინარეობს ამ შეუცვლელი ჩანაწერისგან და არა დამრეკავის მიერ შერჩეული მნიშვნელობებიდან:

|ცხოვრების ციკლის შეტყობინება |მოთხოვნილი მონაწილე |

|`pacs.002`, `pacs.004`, `sese.024`, `sese.025` |`counterparty` როლის მქონე ორიგინალური საპასუხო მხარე |

ორიგინალური პროფილის და ხელმოწერის პოლიტიკა რჩება ჩაკეტილი მთელი სიცოცხლის ციკლის განმავლობაში, ასე რომ დამრეკავმა არ შეიძლება აირჩიოს უფრო სუსტი პროფილი განახლებისთვის. კოდი `pacs.002` რომელიც რეპრეზენტაცია ანგარიშსწორება (`ACSC`, `ACCP`, `SETT` ან `SETTLED`) შეცვლის ორიგინალურ ჩანაწერს დაფარულად მხოლოდ მაშინ, როდესაც Torii ვალდებულებაშია შეტანილი გარიგების მტკიცებულება.

ნებისმიერ ორიგინალურ მხარეს შეუძლია წაიკითხოს მისი შეტყობინებების ჩანაწერი და წარმოქმნილი საგარეო ყუთის დოკუმენტები. აუდიტის საბოლოო წერტილი მხოლოდ იმ ჩანაწერებს იბრუნებს, რომლებშიც ავთენტიფიცირებული მონაწილე არის წარმომადგენელი ან კონტრაქტორი. დამოუკიდებლად კონფიგურირებული აუდიტის ადმინისტრატორი იღებს გლობალურ მხოლოდ წაკითხული აუდიტის ხედვას და არ შეუძლია შეტყობინებების წარდგენა ან შეცვლა. უცნობი მონაწილეები და შეუკავშირებელი შეტყობინის იდენტიფიკატორები არ გახდება ცნობილი.

## Kaigi სესიები {#kaigi-sessions}

Kaigi უზრუნველყოფს გადახდილ, რეალურ დროში აუდიო / ვიდეო ოთახებს SORA Nexus. გამოიყენეთ მას მაშინ, როდესაც აპლიკაციას სჭირდება წიგნის მხარდაჭერილი სესიის შექმნა, რესტრის ცვლილებები, რელე მანიფესტები, დაშიფრებული სიგნალი და გამოყენების გაზომვა იმის ნაცვლად, რომ ყველა კონფერენციის მდგომარეობა იყოს off-chain.

ლიდერების მიმართული სიცოცხლის ციკლი არის:

- `CreateKaigi`: შექმენით ზარი დომენის ქვეშ და შეინახეთ მისი პოლიტიკა, განრიგი, მეტა მონაცემები და არაკონკრეტული რელე მანიფესტი.
- `JoinKaigi` და `LeaveKaigi`: განახლება მოწოდების სიაში. კერძო რეჟიმში მონაწილეები პირდაპირი ანგარიშის IDs გამოხატვის ნაცვლად იყენებენ ვალდებულებებს, ბათილებლებსა და სიაში მტკიცებულებებს.
- `RecordKaigiUsage`: დაამატეთ გაზომული ხანგრძლივობა და გაზის მთლიანი რაოდენობა.
- `EndKaigi`: შეწყვიტეთ სესია და ჩაწერეთ ბოლო დროის ბეჭედი.

Torii გამოყოფს რელეების ტელემეტრიას ქვემოთ `/v1/kaigi/relays`, `/v1/kaigi/relays/{relay_id}`, `/v1/kaigi/relays/health`, და `/v1/kaigi/relays/events` როდესაც აპლიკაცია API და ტელემეტრიული მახასიათებლები ჩართულია. სესიის მდგომარეობა ასახულია Kaigi დომენის მოვლენები, როგორიცაა `KaigiRosterSummary`, `KaigiRelayManifestUpdated`, `KaigiRelayHealthUpdated`, და `KaigiUsageSummary`.

```bash
  --domain streaming \
  --call-name daily \
  --host <i105-account-id> \
  --privacy-mode transparent \
  --room-policy authenticated

iroha kaigi join --domain streaming --call-name daily --participant <i105-account-id>
iroha kaigi leave --domain streaming --call-name daily --participant <i105-account-id>

iroha kaigi record-usage \
  --domain streaming \
  --call-name daily \
  --duration-ms 120000 \
  --billed-gas 1500

iroha kaigi end --domain streaming --call-name daily
```

გამოიყენეთ `--room-policy public` იმ ოთახებში, სადაც რელეებს შეუძლიათ გამოავლინონ მაყურებლის ბილეთის გარეშე, ან `--room-policy authenticated` როდესაც გასასვლელები უნდა მოითხოვოს მაყურებლის ავთენტიფიკაცია. გამოიყენეთ `--privacy-mode zk-roster-v1` მხოლოდ ქსელში Kaigi სია და გამოყენების შემოწმების გასაღები კონფიგურირებულია; წინააღმდეგ შემთხვევაში, დეტერმინისტური შემოწმების დროს გაერთიანება, ფოთლები და პირადი გამოყენების ჩანაწერები არ მუშაობს.

### ტესტირება JavaScript დემოს საშუალებით {#testing-with-the-javascript-demo}

გამოიყენეთ [soramitsu/iroha-demo-javascript](https://github.com/soramitsu/iroha-demo-javascript) სამუშაო მაგიდის დემო ბოლოდან ბოლომდე საფულის ტესტისთვის. დემო არის ელექტრონული და Vue აპლიკაცია, რომელიც უშუალოდ საუბრობს Torii ადგილობრივი `@iroha/iroha-js` კავშირის მეშვეობით და მოიცავს ბრაუზერის მშობლიური ერთ-ერთი მედიისთვის `/kaigi` მარშრუტს.

გამოიყენეთ დემო [`@iroha/iroha-js`](https://github.com/hyperledger-iroha/iroha/tree/main/javascript/iroha_js) სააგენტოდან Iroha საწყისი რეპროექტორი. დემო პინები SDK მეშვეობით `file:../iroha/javascript/iroha_js`, ასე რომ, შეინახეთ ორივე ჩანთები ამ ძმების განლაგებაში:

```bash
mkdir iroha-wallet-workspace
cd iroha-wallet-workspace
git clone https://github.com/hyperledger-iroha/iroha.git
git clone https://github.com/soramitsu/iroha-demo-javascript.git

cd iroha/javascript/iroha_js
npm install
npm run build:native
npm run build:dist

cd ../../../iroha-demo-javascript
npm install
npm run dev
```

გამოიყენეთ Node.js 20 ან უფრო ახალი და ინსტრუმენტების ჯაჭვი Rust, რათა შეიქმნას მშობლიური `iroha_js_host` მოდული. აღადგინეთ SDK ძმასთან Iroha საფულეში მისი წყაროს შეცვლის შემდეგ; სუფთა პაკეტის განლაგება არ შეიცავს ტვირთის სამუშაო სივრცეს, რომელიც საჭიროა `npm run build:native`.

კონტროლირებადი ტესტისათვის, მიუთითეთ დემო Kaigi-სუნარიანობის Torii საბოლოო წერტილში:

1. დაიწყეთ Iroha კვანძი, სადაც არის ჩართული SORA/Kaigi აპლიკაციის მიმართულება APIs ან გამოიყენეთ საჯარო საბოლოო წერტილი, რომელიც გამოყოფს საჭირო Kaigi ზედაპირებს.
2. შეამოწმეთ ძირითადი ხელმისაწვდომობა `/health`, შემდეგ შეამოწმოთ ცოცხალი მარშრუტის ზედაპირი `/openapi` ან `/openapi.json`. ზოგიერთი განთავსება ასევე გამოხატავს `/v1/health`, მაგრამ `/health` არის გადამტანილი სიცოცხლისუნარიანობის შემოწმება.
3. TAIRA -ისათვის გადაცემის ტელემეტრიული მარშრუტების შემოწმება, სანამ პირდაპირი შეხვედრის ჩატარებას შეეცდებით:

   ```bash
   TAIRA=https://taira.sora.org
   curl -fsS "$TAIRA/health"
   curl -fsS "$TAIRA/v1/kaigi/relays"
   curl -fsS "$TAIRA/v1/kaigi/relays/health"
   ```

აღნიშნული შემოწმებები ადასტურებს, რომ Torii და Kaigi რელიე ტელემეტრიები ხელმისაწვდომია. ისინი არ ქმნიან შეხვედრას; `CreateKaigi` და `JoinKaigi` ჯერ კიდევ საჭიროებენ ფინანსურ საფულეებსა და ხელმოწერილ ტრანზაქციების წარდგენას.
4. გახსენით დემო, გადადით პარამეტრები, დააყენეთ Torii URL და მოდით აპლიკაციას დატვირთოს ჯაჭვი ID და ქსელის პრეფისსი ბოლო წერტილიდან.
5. შექმენით ან აღადგინეთ ორი ადგილობრივი საფულე დემოში. გამოიყენეთ ცალკეული აპლიკაციის ფანჯრები, პროფილები ან მანქანები, რათა მასპინძელს და სტუმარს აქვს ცალკე საფულის მდგომარეობა.

Kaigi UI-ის გამოცდისთვის:

1. მასპინძელი ფანჯარაში გახსენით Kaigi, აირჩიეთ შეხვედრის დაწყება, დაასახელეთ სათაური და აირჩიეთ Private invite ან Transparent invite.
2. აირჩიეთ კამერა და მიკრონი ჩართე, რათა WebRTC ჰქონდეს ადგილობრივ მედიას.
3. აირჩიეთ შეკრების ბმული შექმნა. ცოცხალი საფულე წარადგენს `CreateKaigi`; აპლიკაცია შემდეგ აჩვენებს `iroha://kaigi/join?call=...&secret=...` მოწვევას და `#/kaigi?...` უკან დაბრუნების მარშრუტს.
4. ფანჯარა ღია იყოს და მიწვევა გაუზიაროს სტუმარს.
5. სტუმრების ფანჯარაში, გახსენით მოწვევა ან დააჭირეთ მას შეხვედრაზე შეუერთდით, ჩართეთ ადგილობრივი მედია და აირჩიეთ შეუერთდით შეხვედრას. ცოცხალი საფულე იღებს კოდირებულ მასპინძლის შეთავაზებას Torii-დან და უგზავნის `JoinKaigi` კოდირებული პასუხის მეტადატებით.
6. მასპინძელმა უნდა დააყენოს პირველი პასუხი ავტომატურად სტრიმინგის ან გამოკითხვის გზით Kaigi ზარის სიგნალები. ორივე ფანჯარა უნდა აჩვენოს დაკავშირებული მედია და განახლებული კავშირის დეტალები.
7. სესიის დასრულება მასპინძელიდან, ან გამოიყენეთ ბრძანება CLI `iroha kaigi end` იმავე ზარისთვის ID.

Private Kaigi needs shielded XOR გადაიხადოს კერძო შესასვლელი საფასური. თუ დემო იუწყება, რომ კერძო Kaigi needs shelded XOR, გამოიყენეთ აპლიკაციის შიდა თვითშეფარვის მოთხოვნა და შეეცადეთ შექმნათ ან შეუერთდით ქმედება. თუ მტკიცებულებების გენერაცია, კერძო დაფინანსება ან ცოცხალი სიგნალიზაცია არ არის ხელმისაწვდომი, დემო შეიძლება დაბრუნდეს გამჭვირვალე / სახელმძღვანელო ნაკადზე. ამ შემთხვევაში, გახსენით მოწინავე სიგნალიზაცია, ასახეთ ნედლეული შეთავაზება ან პასუხის პაკეტი და დააჭირეთ მას მეორე ფანჯარში.

ავტომატური შემოწმებისათვის დემოს რეპოში, გაუშვით:

```bash
npm test -- tests/kaigiView.spec.ts tests/preloadKaigiBridge.spec.ts
npm run e2e:ui
npm run verify
```

კონცენტრირებული Vitest სუიტები მოიცავს Kaigi შეხვედრის ბმულების შექმნას, კომპაქტური მოწვევის დატვირთვას, კერძო შექმნა / გაწევრიანება / დასრულების ხიდის ზარებს, თვითშეზღუდვის შეტყობინებებს, სახელმძღვანელო უკან დაბრუნებას და პასუხის მიმოხილვას. UI სიგარეტის ტესტი მოიცავს რუტას `/kaigi` სამუშაო მაგიდაზე და მობილური ზომის სანახავად პორტებზე. ორი საფულეებს შორის პირდაპირი მედია ჯერ კიდევ საჭიროებს ორ ფანჯრის სახელმძღვანელო ტესტს, რადგან ბრაუზერის კამერა / მიკროფონის ნებართვები და პარტნიორული მედიის ნაკადები გარემოსთვის სპეციფიურია.

ნიმუშის ინტეგრაციის კოდისათვის იხილეთ [Embed Kaigi in a JavaScript App](/ka/guide/tutorials/kaigi.md).

## სტატუსი და მაჩვენებლები {#status-and-metrics}

სტატუსისა და მაჩვენებლების ბოლო წერტილები არის პირველი რამ, რომელიც ჩართულია დეშბორდებში:

- `/status` აღმოაჩენს უმაღლესი დონის პარტნიორი, ბლოკი, რიგები და კონსენსუსის ველები
- `/metrics` ამჟღავნებს Prometheus- ის მაჩვენებლებს, მზომილებსა და ჰისტოგრამებს

Nexus-ის შესაძლებლობის მქონე კვანძებზე სტატუსის გამოსავალი ასევე მოიცავს მარშრუტის და მონაცემთა სივრცის შესახებ ინფორმირებულ მონაკვეთებს. როდესაც `nexus.enabled = false`, ეს მონაკვეთები გამორიცხულია.

## JSON vs. Norito {#json-vs-norito}

რამდენიმე ოპერატორის საბოლოო წერტილი ბრუნდება Norito დეფოლტურად. როდესაც საბოლოო პუნქტი მხარს უჭერს JSON, გაგზავნეთ:

```http
Accept: application/json
```

ეს განსაკუთრებით სასარგებლოა:

- `/v1/sumeragi/status`
- `/v1/sumeragi/qc`
- `/v1/sumeragi/commit_qc/{hash}`

როდესაც საბოლოო წერტილი იღებს ან უშუალოდ აგზავნის Norito ტიპს, გამოიყენეთ `application/x-norito` როგორც შინაარსის ტიპი ან სასურველი `Accept` ღირებულება. იხილეთ ტრანსპორტის დეტალები [Norito](/ka/reference/norito.md#torii-and-norito-rpc).
