# Torii API საბოლოო წერტილები {#torii-endpoints}

Torii ეს არის HTTP, SSE, და WebSocket შესასვლელი Iroha 3. ეს ემსახურება როგორც ურთიერთქმედებას ბლოკჩეინი ლეგრი APIs და ოპერატორი API საბოლოო წერტილები.

ამჟამინდელი პროტოკოლის წესები არის:

- კანონიკური ბინარული ფორმატი არის Norito
- ბევრი API საბოლოო წერტილი ასევე მხარს უჭერს JSON, როდესაც თქვენ გამოგზავნით `Accept: application/json`
- მაჩვენებლები არის გამოქვეყნებული Prometheus ფორმატში

ფორმატის დეტალების, შინაარსის მოლაპარაკებების, განლაგების დროშების, სქემა-კრიპტოგრაფიული ჰეშებისა და Norito RPC მითითებებისათვის იხილეთ [რეფერენცია Norito](/ka/reference/norito.md).

|`GET /v1/time/status` |JSON |დროის სინქრონიზაციის სტატუსი |

SSE თხოვნისთვის, რეკლამირება მშობლიური ნაკადი და დამატებით ტიპირებული ჩამოტვირთვა:

```http
Accept: text/event-stream, application/json
```

Torii პირველ რიგში მოლაპარაკებას აწარმოებს JSON ან Norito წარმოდგენის შესახებ თხოვნის ფენაზე, შემდეგ კი ამტკიცებს მშობლიურ `text/event-stream` პასუხს. შესაბამისად მხოლოდ `text/event-stream`-ის გაგზავნა უარყოფითია `406`; [გადაცემების რეცეპტი](/ka/cookbook/stream-events.md) იყენებს სრულ სათაურს.

`/openapi.json` არის სქემაში წარმოდგენილი მარშრუტების გენერირებული ხელშეკრულება, და არა სრული ოპერაციული კვლევის ინვენტარი. მიმდინარე დოკუმენტი გამორიცხავს `/livez` და `/readyz` და მისი აღწერა `/health` შეიძლება დაგვიანდეს მზადყოფნის მმართველს. გენერირება მარშრუტის კლიენტები ცოცხალი დოკუმენტი, მაგრამ დაადასტუროს სიცოცხლისუნარიანობა და მზადყოფნა პირდაპირ მიმდინარე კვანძი და დამაგრებული დამმუშავებლები. ზუსტი ზედაპირი ჯერ კიდევ დამოკიდებულია ნაგებობის მახასიათებლების და შესრულების გარემოს კონფიგურაცია. გამოიყენეთ [კონსოლი Torii API](/ka/reference/torii-api-console.md) იმ ცოცხალი დოკუმენტის დატვირთვა, ტესტირება JSON მარშრუტები, კოპირება curl მოთხოვნები, და გენერირებს კლიენტური კოდი მიმდინარე სქემა.

თითოეული კატალოგის მიერ მხარდაჭერილი OpenAPI ოპერაცია მოიცავს `x-iroha-route-auth` ობიექტს. კატალოგით მხარდაჭერილ MCP ინსტრუმენტებმა გამოავლინეს იგივე კონტრაქტი, როგორც `_meta["iroha/routeAuth"]`. ორივე პროექცია შეიცავს `schemaVersion`, `stableRouteId`, `authentication` და `admission`. შეხედეთ ვერსიას `1` ზუსტი ხელშეკრულების სახით: უარი თქვით დაუჭერელ `schemaVersion`, იმის ნაცვლად, რომ ივარაუდოთ, თუ როგორ უნდა ინტერპრეტირდეს მისი ავთენტიფიცირება ან მიღების ეტიკეტები. მარშრუტის მეტამონაცემები აღწერენ თხოვნის საზღვარს; ის არ შეცვლის ამ საზღვრით მოთხოვნილ სანებართვო პირობებს.

## სცადეთ პირდაპირი Taira მარშრუტები {#try-live-taira-routes}

საჯარო Taira ტესტის ქსელი ამჟღავნებს იმავე Torii JSON ზედაპირს, რომელსაც აპლიკაციის კლიენტები მხოლოდ წაკითხვის მიზნით იყენებენ. აღნიშნულ ბრძანებებს არ მოითხოვს გასაღებები:

```bash
TAIRA_ROOT=https://taira.sora.org

curl -fsS -H 'Accept: application/json' "$TAIRA_ROOT/status" \
  | jq '{blocks, txs_approved, txs_rejected, queue_size, peers}'

curl -fsS "$TAIRA_ROOT/openapi.json" \
  | jq -r '.paths | keys[]' \
  | grep '^/v1/' \
  | head -n 20

curl -fsS -H 'Accept: application/json' \
  "$TAIRA_ROOT/v1/node/capabilities" \
  | jq '{abi_version, data_model_version, query: .query.aggregate.supported_resources}'
```

შეეცადეთ რესურსის წაკითხვა დღევანდელი მსოფლიო მდგომარეობის წინააღმდეგ:

```bash
curl -fsS "$TAIRA_ROOT/v1/domains?limit=5" \
  | jq -r '.items[].id'

curl -fsS "$TAIRA_ROOT/v1/assets/definitions?limit=5" \
  | jq -r '.items[] | [.id, .name, .total_quantity] | @tsv'
```

თუ საჯარო ტესტნეტის მარშრუტი ბრუნდება `502`, დროთა განმავლობაში, ან იუწყება გაჯერებული რიგის შესახებ, განიხილეთ ეს როგორც API საბოლოო წერტილის ხელმისაწვდომობის პრობლემა და კიდევ ერთხელ შეეცადეთ მოგვიანებით თქვენი კლიენტის კოდის დებეგირების წინ.

## აპლიკაცია და SORA მარშრუტის ოჯახები {#app-and-sora-route-families}

როდესაც Torii აშენებულია აპლიკაციის მიმართულებით ფუნქციების კომპლექსით, ის გამოყოფს დამატებით JSON ოჯახებს ექსპლუატორებისთვის, SORA სერვისებს, ხიდის ნაკადებს, მტკიცებულებებს და შენახვას. ეს ოჯახები ყველა ქსელის პროფილისთვის არ არის ჩართული.

`/openapi.json` აღწერს რეგისტრირებულ მარშრუტებს წარმოქმნილ აპლიკაცია-API კატალოგში; იგი ავტორიტეტულია მის შემცველი მითითებებისათვის და არა ყველა მონტაჟებული მარშრუტისათვის პროცესი. კერძოდ, საჯარო ადგილობრივი SoraFS CID და ცნობილი მარშრუტები ამომუშავებული დოკუმენტის გარეთ დამონტაჟებულია და უშუალოდ უნდა იყოს გამოკვლეული.

| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
|`/v1/accounts/*`, `/v1/domains/*`, `/v1/assets/*` |JSON წაკითხვა, შეკითხვის დამხმარეები, ჩართვის დამხმარეები და პორტფელის ან მფლობელის ხედვები |

## ანგარიშის ავთენტიფიკაცია, ხილვადობა და Explorer- ის კურსორები {#account-authentication-visibility-and-explorer-cursors}

### აპლიკაციის ანგარიშის მოთხოვნის პროტოკოლი {#app-account-request-protocol}

აპლიკაციების მიმართული მარშრუტები ან არ იღებენ ავთენტიფიცირების სათაურებს, ერთი პირდაპირი ერთმნიშვნელოვანი მტკიცებულება, ან ერთი მრავალნიშნა მოწმე. თითოეული ავთენტიფირება სათაური უნდა გამოჩნდეს არა უმეტეს ერთხელ.

პირდაპირი დასამტკიცებლად, გააგზავნეთ ოთხივე სათაური ერთად:

- `X-Iroha-Account`: ზუსტი კანონიკური მცირე ასო `0x` ანგარიშის მისამართის hex ან აქტიური კანონიკური ASCII ანგარიშის ალიასი. I105 ტექსტი არ არის უსაფრთხო, როგორც HTTP ველის ღირებულება; გამოიყენეთ ერთიანი პროთოკოლური სტანდარტების hex მართლწერის ამ ანგარიშისთვის.
- `X-Iroha-Signature`: მკაცრი დახურული ბაზა64 ხელმოწერის დატვირთვა.
- `X-Iroha-Timestamp-Ms`: ერთი პროტოკოლური სტანდარტის გარეშე გაფორმებული ათეულიანი Unix დროის ბეჭედი მილისეკონდებში, კონფიგურირებული მიდრეკილების ფანჯრის შიგნით.
- `X-Iroha-Nonce`: 1-დან 256 ბაიტამდე პრინტირებადი ASCII (`0x21`-დან `0x7e`-მდე), რომელიც უნიკალურია გათამაშების ფანჯრის შიგნით.

რეგისტრირებული ერთმხრივი კონტროლერი ამ ზუსტ ბაიტებს აწერს:

```text
iroha.app.request.network.v1\0 || <genesis-derived network_id[32]> ||
<UPPERCASE_METHOD>\n
<exact request path>\n
<canonical query>\n
<lowercase hex SHA-256 of the raw body>\n
<canonical timestamp_ms>\n
<nonce>
```

კანონიკური მოთხოვნის კონსტრუქცია შეისწავლის ნედლეულის მოთხოვნას როგორც `application/x-www-form-urlencoded` (`+` ნიშნავს სივრცეს), პროცენტი-დეკოდებს მის წყვილებს, ასორტირებს მათ `(key, value)` და ფორმას ისევ კოდირებს. პროტოკოლი აღიარებს მაქსიმუმ 64 დეკოდირებული წყვილი და 64 KiB ნედლეულის შეკითხვის ტექსტი. კრიპტოგრაფიული ჰეშის სხეულის ბაიტები ზუსტად ისევე, როგორც გადაცემა. არ შეიყვანოთ გამყოფი ფასი ფიქსირებულ 32-ბაიტიან ქსელურ ID-სა და დიდი წერილების მეთოდს.

V1 ვერიფიკატორი ასევე შეზღუდავს მეთოდის ტოკი 32 ბაიტით, პროცენტული კოდირებული მოთხოვნის გზა 64 KiB და პირდაპირი ანგარიშის იდენტობა 36 KiB სანამ პარსირებას. ანგარიშის ალიასებს აქვთ უფრო მკაცრი სტრუქტურული ლიმიტი სამი სახელების სეგმენტი და მათი გამყოფი. ბინდის გადაჭარბება არ ახდენს აuthentication სანამ ხელმოწერის შემოწმება ან წყარო ზომის განაწილება.

მულტისიგის კონტროლერმა უნდა გამოაგზავნოს `X-Iroha-Witness` როგორც მკაცრი დახურული ბაზა64 კანონიკური Norito და გამორიცხვა `X-Iroha-Signature`, `X-Iroha-Timestamp-Ms`, და `X-Iroha-Nonce`. `X-Iroha-Account` არის ამ ფორმით ნებაყოფლობითი; როდესაც ის არსებობს, იგი უნდა შეესაბამებოდეს მოწმეს `subject_account`. სააგენტო `CanonicalRequestWitnessV1` შეიცავს `schema_version`, `subject_account`, `timestamp_ms`, `nonce`, დასახელება Iroha `Hash` ქსელის ზუსტი მოთხოვნის ბაიტების რაოდენობა სხეულის კრიპტოგრაფიული დიჯესტის საშუალებით, მაგრამ სიახვითობის ველების გარეშე; და არა უმეტეს 64 წევრის ხელმოწერით. თითოეული წევრი ხელს აწერს კანონიკურ, Norito ამავე დატვირთვის კოდირება ხელმოწერების არივის გარეშე. უნდა აკმაყოფილებდეს ანგარიშის ამჟამინდელ მრავალნიშნა პოლიტიკას. კოდირებული მოწმე 1 MiB.

არანაირი ავთენტიფიკაციის სათაურების მიწოდება ანონიმურ წვდომას ირჩევს. ნებისმიერი ნაწილობრივი, შერეული, განმეორებითი, ცუდად ჩამოყალიბებული, მოძველებული ან გადაღებული მტკიცებულებების მიწოდება ვერ ახდენს ავთენტიფაციას; ის არასდროს დაბრუნდება ანონიმური ხილვადობას.

### ოპერატორის მოთხოვნის პროტოკოლი {#operator-request-protocol}

ოპერატორის მიერ ავტორიზებულად აღნიშნული მარშრუტებისათვის საჭიროა ოთხივე სინგლეტონის სათაური:

- `x-iroha-operator-public-key`: კანონიკური Iroha მრავალმხრივი საჯარო გასაღები.
- `x-iroha-operator-timestamp-ms`: ერთიანი პროტოკოლური სტანდარტისათვის ხელმოწერის გარეშე განთავსებული Unix-ის ათეული დროის საფურცელი მილიწამი.
- `x-iroha-operator-nonce`: 1-დან 256 ბაიტამდე პრინტირებადი ASCII, გამონაკლისი იმ გასაღებისათვის განთავსების ფანჯრის შიგნით.
- `x-iroha-operator-signature`: მკაცრი დახურული ბაზა64 ხელმოწერის დატვირთვა.

სათაურის მნიშვნელობები არ უნდა შეიცავდეს მიმდებარე სივრცეებს. ოპერატორის საკვანძო ნიშნები:

```text
iroha.operator.http-request.network.v1\0 || <genesis-derived network_id[32]> ||
<UPPERCASE_METHOD>\n
<exact request path>\n
<canonical query>\n
<lowercase hex SHA-256 of the raw body>\n
<canonical timestamp_ms>\n
<nonce>
```

გზა, შეკითხვა, სხეული, დროის სტამპი და კრიპტოგრაფიული nonce ღირებულების წესები იგივე ერთიანი პროტოკოლი-სტანდარტული წესები გამოიყენება აპლიკაციის პროტოკოლში. გასაღები ასევე უნდა იყოს დაუშვებელია `[torii.operator_signatures]`: ჩამოთვალეთ იგი `allowed_public_keys`-ში, ან მკაფიოდ ჩართეთ `allow_node_key` კვანძის გასაღების გამოყენებისას. რეპლეი-კეშის გაჯერება ვერ დაიხურება `503 Service Unavailable`.

ზუსტი მოთხოვნის ხელმოწერა ყოველთვის სავალდებულოა. როდესაც `[torii.operator_auth].enabled = true`, თითოეული ჩვეულებრივი ოპერატორის მარშრუტი ასევე საჭიროებს ვალიდურ `x-iroha-operator-session`; როდესაც `require_mtls = true`, იგი დამატებით საჭიროებს `x-forwarded-client-cert` საიმედო შესასვლელიდან. არც ერთი ფაქტორი არ შეცვლის მოთხოვნის ხელს.

WebAuthn რეგისტრაციისა და შესვლისას გამოიყენეთ ეს ოთხი JSON API საბოლოო წერტილი:

|მეთოდი და API საბოლოო |მიზანი |
| --------------------------------------------- | ---------------------------------------- |
|`POST /v1/operator/auth/registration/options` |დაიწყეთ WebAuthn სააკრედიტაციო რეგისტრაცია |
|`POST /v1/operator/auth/registration/verify` |შეამოწმეთ და გააგრძელეთ სერთიფიკატები |
|`POST /v1/operator/auth/login/options` |დაიწყეთ WebAuthn ავთენტიფიკაცია |
|`POST /v1/operator/auth/login/verify` |შეამოწმეთ განცხადება და გამოწერეთ სხდომა |

კონფიგურაცია `torii.operator_auth.tokens` სპეციალური საწყისი გამართვა ღირებულებებით. სანამ არსებობს რაიმე საკრედიტაციო ნომერი, გამოგზავნეთ ერთი როგორც `x-iroha-operator-token` პირველი რეგისტრაციის დასაწყისად. ეს ტოკენი არასდროს ავტორიზებს ჩვეულებრივი ოპერატორის მარშრუტს და მოსმენის `x-api-token` მნიშვნელობები არასოდეს გამოიყენება ამ ნაკადისთვის. მას შემდეგ, რაც არსებობს საკრედიტო ქაღალდი, სხვა საკრედიტაციო ქაღალდის დარეგისტრირება მოითხოვს ავთენტიფიცირებულ სესიას. შესვლის შემოწმება უბრუნებს სესიის ტოქენს, რომელიც ყველა ახალი ზუსტი ქსელის ოპერატორის მოთხოვნის ხელმოწერასთან ერთად გაიგზავნება. კრედიტალები რჩება `<torii.data_dir>/operator_auth/operator_webauthn.json`-ში.

ISO 20022 მარშრუტები ორი დამოუკიდებელი შემოწმებას ახორციელებენ. მოთხოვნა ჯერ უნდა გაიაროს ამ ოპერატორის ნებართვის სია და ხელმოწერის პროტოკოლი; შემდეგ ISO მმართველს საჭიროა იგივე გასაღები, რათა დაიკავოს ქვემოთ აღწერილი კონკრეტული მონაწილე ან აუდიტის როლი.

### ბლოკჩეინის რეესტრი ხილვადობა და Explorer კურსორები {#ledger-visibility-and-explorer-cursors}

აპლიკაციების მიმართულებით ბლოკჩეინის რეესტრის მკითხველები იყენებენ ზემოთ ვარიანტური აპლიკაციის ანგარიშის საზღვარს. ხელმოუწერელი მოთხოვნა იღებს მხოლოდ მონაცემთა სივრცეებს, რომლებიც კონფიგურირებულია როგორც საჯარო. ვალიდური ხელმოწერილი მოთხოვნა ემატება მონაცემთა სფეროებს, რომლებიც დაკავშირებულია დამრეკლის მიმდინარე UAID-სთან. თითოეული შეზღუდული მონაცემთა სივრცე, რომელიც დასახელებულია ზუსტი `CanReadRestrictedDataspace { dataspace }` ნებართვით, ან ყველა მარშრუტი, როდესაც ანგარიშს აქვს `CanReadAllLedgerData`.

გამოიყენეთ მარშრუტი, რომელიც შეესაბამება დამრეკლის ავტორიზაციის პრინციპს:

|მეთოდი და API საბოლოო |აuthentication და ხილვადობა |
| ------------------------------------- | --------------------------------------------------------------- |
|`POST /v1/transactions/visible/query` |კანონიკური ანგარიშის ხელმოწერა; გამოიყენება დამრეკავის ხილვადობა |

|`GET /v1/triggers/completed` |ოპერატორის მოთხოვნის ხელმოწერა; კითხულობს კვანძების ადგილობრივ დასრულების ჩანაწერებს |

ერთი და იგივე ხილვადობის ობიექტების ფილტრები ანგარიში, დომენი, აქტივის განსაზღვრა, აქტივი, NFT, RWA, მფლობელი და Explorer კითხულობს. არარსებული ობიექტი და ობიექტი, რომელიც ზარის ხილული მარშრუტების გარეთ არის მიზანმიმართულად შეუცვლელი. საბოლოო ტრანზაქციისა და ინსტრუქციის ისტორია მხოლოდ მაშინ არის ნაჩვენები, როდესაც ტრანზაკციაზე რეგისტრირებული ყველა ფინანსური გადარიცხვის ნაწილი ჩანს. აქედან გამომდინარე, ფარული გადარიცხვის ნაწილი იმ შემთხვევაშიც კი დამალულია, როდესაც ერთ-ერთი მონაწილე საფინანსო ტრანსფერის ნაწილი მრეწველის მოქმედების ფარგლებს გარეთ არის; დაკარგული, გაჩერებული ან არასწორად ჩამოყალიბებული მარშრუტის კონტექსტი ჩანს მხოლოდ გლობალური მკითხველისთვის.

ექვსი მსოფლიო მხარდაჭერილი Explorer კოლექცია იყენებს გაუმჭვირვალე კანონიკური base64url საკვანძო პარამეტრების კურსორებს. დეფოლტური გვერდის ლიმიტი არის 25, მაქსიმალური 100 და ერთი გვერდი ინსპექტირებს მაქსიმალურად 512 კანდიდატურ საკვანჭეს. თითოეული კურსორი უკავშირდება მის კოლექციას, ფილტრებს, ერთიანი პროტოკოლური სტანდარტის ბოლო გასაღებას და დამრეკავის ხილული მარშრუტით განსაზღვრულ კრიპტოგრაფიულ დიჯესტს, ასე რომ ის არ შეიძლება გაითამაშოს სხვა მოთხოვნაზე ან მას შემდეგ, რაც დამრევილის ხილვადობა იცვლება.

ბლოკი, ტრანზაქცია, ბოლო ოპერაცია, ინსტრუქცია და უკანასკნელი ინსტრუქციის ისტორია კურსორები დამატებით პინი საბოლოო წერტილის დროში მონაცემების ხედვის სიმაღლე და ბლოკის კრიპტოგრაფიული hash. პასუხები გამოყოფენ `pagination.limit`, `pagination.snapshot_height`, `pagination.snapshot_hash`, `pagination.next_cursor` და `pagination.has_more`. კურსორი სხვა მარშრუტისთვის ან ფილტრის კომპლექტისთვის, შეცვლილი ხილვადობის კრიპტოგრაფიული დიჯესტი ან დროის მონაცემების ნახვა, რომლის ბმული ვეღარ ახდენს დადასტურებას, ჩაკეტილია. ისტორიის სკანირება რჩება Torii - ის შეკითხვის შესვლის ნებართვის შიგნით, სანამ დაბლოკვის მუშაკი მუშაობს.

Explorer WebSocket ნაკრებები გამოყოფენ ფილტრირებულ შეჯამებებს და აღადგენს ხილვადობას, როდესაც ბლოკჩეინ ლეგჟერის ნებართვები იცვლება. მშობლიური `GET /v1/blocks/stream` მარშრუტი განსხვავდება: იგი გადმოსცემს სრული ხელმოწერილი ბლოკები, მოითხოვს `CanReadAllLedgerData` ხელის შეხების დროს და იხურება, თუ ეს ნებართვა მოგვიანებით მოიხსნება. არ გამოიყენოთ მშობლიური ნაკადი მონაცემთა სივრცეზე სკოპირებული ექსპლუატორისთვის.

## ISO 20022 ხიდი {#iso-20022-bridge}

Torii ამჟღავნებს ISO 20022 ხიდს `/v1/iso20022/*` ქვეშ, როდესაც აპლიკაციის მიმართულებით API და ხიდის შესრულების გარემო არის ჩართული. ხიდი მიზანმიმართულად არის განსაზღვრული: ეს არ არის ზოგადი დანიშნულების ISO 20022 გადარიცხვის კარიბჭე, არამედ მხარდაჭერილი ქვეჯგუფი შერჩეული გადახდის შეტყობინებების გარდაქმნისთვის ხელმოწერილი Iroha ტრანსფერები და მათი ბლოკჩეინის რეესტრის სტატუსის თვალსაზრისით.

დააკონფიგურეთ მდგრადი ადგილობრივი `torii.iso_bridge.store_dir` ნებისმიერი წარდგენის მიღებამდე. კონფიგურაციის ველი ვარიანტია მხოლოდ ისე, რომ კვანძს შეუძლია დაიწყოს მხოლოდ წაკითხვის ან დიაგნოსტიკური გამოყენებისათვის: ყველა ავთენტიფიცირებული ISO წარდგენა საჭიროებს დირექტორს, და დაბრუნება ხელახლა საცდელი `503 Service Unavailable` როდესაც მუდმივი შენახვა არ არის ან ხელახალი დაკვრა-წაშლის ნიშანი ან მდიდარი ჩანაწერი წერა არასწორი.

`pacs.009` შეტყობინებების წარდგენა უნდა შეიცავდეს საქმიანი გზავნილის ID, გზავნილების განსაზღვრის ID, შექმნის დრო, ბანკთაშორისი ფინანსური ოპერაციის ანგარიშსწორების თანხა, ვალუტა. ფინანსური ოპერაციის დაფარვის თარიღი, ინსტრუქციის მიმცემი და ინსტრუქციული აგენტი BICs და ვალდებული და კრედიტორი IBANs. თუ შეტყობინება მოიცავს `Purp`-ს, ხიდმა ამჟამად იღებს მხოლოდ ფასიანი ქაღალდების მიზნით დაფინანსებას: `Purp=SECU`.

სააგენტო `pacs.008` და `pacs.009` წარდგენა API საბოლოო წერტილები მიიღებენ XML ISO მონაცემთა კონტეინერები ან პლასტმასის ფორმატი, რომელიც გამოიყენება ხიდების გამოცდებში. ვარიანტი `SplmtryData` ველებს შეუძლიათ მიზნების დაჭერა. Iroha ბლოკჩეინის რეესტრი, წყარო და სამიზნე ანგარიშების ID ან მისამართები და აქტივების განსაზღვრის ID. პასუხი არის: `202 Accepted` მქონე `message_id`, `transaction_hash`, `status`, `pacs002_code`, და რეზოლუციური ლიდერის / ანგარიშის / აქტივების კონტექსტი.

### მონაწილეების ავტორიზაცია და სიცოცხლის ციკლის მფლობელობა {#participant-authorization-and-lifecycle-ownership}

ყველა ჩართული ხიდს აქვს მონაწილეების კატალოგი. თითოეულ მონაწილეს აქვს უნიკალური მონაწილე ID, ერთი ან რამდენიმე ოპერატორის საჯარო გასაღები, ერთი ან მეტი ფინანსური იდენტიფიკატორი, ნებადართული პროფილის ნაკრები და `originator`, `counterparty` ან ორივე როლი. ოპერატორის გასაღები და ფინანსური იდენტიფიკატორები არ შეიძლება ეკუთვნოდეს ერთზე მეტ მონაწილეს. კონფიგურაცია `audit_admin_keys` ცალკე; აუდიტის ადმინის გასაღები ასევე ვერ იქნება მონაწილე მუტაციის გასაღები.

ყველა ISO მარშრუტისთვის საჭიროა ახალი ოპერატორის ხელმოწერა. საწყისი `pacs.008`, `pacs.009`, `sese.023` ან `colr.012` წარდგენისას, დამოწმებული ოპერატორი უნდა ეკუთვნოდეს მონაწილეზე, რომელიც განსაზღვრულია განაცხადის სათაურით `From` ფინანსური იდენტობის მიხედვით. `To` იდენტობა უნდა გადაიხადოს კონფიგურირებულ მონაწილეს, რომელსაც აქვს `counterparty` როლი, ხოლო შერჩეული პროფილი ორივე მხარისთვის უნდა იყოს ნებადართული. ხანგრძლივი შეღავათის რეგისტრაცია წარმოქმნილის, საპირისპირო მხარის, მიმღებ მონაწილეისა და ოპერატორის გასაღების, ასევე ორიგინალური პროფილისა და ჩაშენებული ხელმოწერის პოლიტიკის რეგისტრაციას.

ორიგინალური პროფილის და ხელმოწერის პოლიტიკა დარჩება ჩაკეტილი მთელი სიცოცხლის ციკლი, ასე რომ დამრეკავმა არ შეიძლება აირჩიოს უფრო სუსტი პროფილი განახლებისთვის. `pacs.002` კოდი, რომელიც წარმოადგენს ფინანსური ოპერაციების გადარიცხვას (`ACSC`, `ACCP`, `SETT`, ან `SETTLED`) შეცვლის თავდაპირველ ანგარიშს დარეგისტრირებულად მხოლოდ მაშინ, როდესაც Torii დაასრულა ოპერაციის მტკიცებულებები.

## Kaigi სესიები {#kaigi-sessions}

Kaigi უზრუნველყოფს გადახდილ, რეალურ დროში აუდიო / ვიდეო ოთახებს SORA Nexus. გამოიყენეთ მას მაშინ, როდესაც აპლიკაციას სჭირდება მხარდაჭერა ბლოკჩეინის რეესტრის სესიის შექმნით, რუსტერის ცვლილებებით, რელიე ტექნიკური მანიფესების, დაშიფრებული სიგნალირებისა და გამოყენების გაზომვის ნაცვლად ყველა კონფერენციის მდგომარეობის გარეშე.

ურთიერთქმედება ბლოკჩეინის რეესტრის სიცოცხლის ციკლი არის:

- `CreateKaigi`: შექმენით ზარი დომენის ქვეშ და შეინახეთ მისი პოლიტიკა, განრიგი, მეტამონაცემები და ავტორიტეტული რელიე ტექნიკური მანიფესტი.
- `JoinKaigi`: განახლება გამოწვევების სია. `zk-roster-v1` რეჟიმში, საჯარო გამოძახების ხედი ასახავს კრიპტოგრაფიულ ვალდებულებას და ნულიფიკატორების რაოდენობას მონაწილე ანგარიშის ID-ების ნაცვლად.
- `LeaveKaigi`: ამოიღეთ მონაწილე გამჭვირვალე ზარიდან. კერძო რეჟიმში წასვლა არის ქსელის გარეთ პირველი გამოშვების პროტოკოლში.
- `RecordKaigiUsage`: მიუთითეთ გაზომული ხანგრძლივობა და გარიგების შესრულების ხარჯების საერთო რაოდენობა.
- `EndKaigi`: დახურეთ სესია და დააფიქსირეთ ბოლო დროის ბეჭედი.

Torii ასახავს შემდეგი აპლიკაციის მიმართულებით წაკითხვები:

|რუტა |ავთენტიფიკაცია |მიზანი |
| ----------------------------------- | --------------------------------------- | ------------------------------------------ |
|`/v1/kaigi/calls/{call_id}` |საზოგადოება |მიმდინარე ზარის ჩანაწერი |
|`/v1/kaigi/calls/{call_id}/signals` |კანონიკური ზუსტი ქსელის ანგარიშის მოთხოვნა |განლაგებული დასკვნითი სიგნალის მეტამონაცემები |
|`/v1/kaigi/calls/{call_id}/events` |კანონიკური ზუსტი ქსელის ანგარიშის მოთხოვნა |სიცოცხლის ციკლის მიწოდება |
|`/v1/kaigi/relays` |ნებადართული სიაში მყოფი ოპერატორის მოთხოვნა |რელე შეჯამება |
|`/v1/kaigi/relays/{relay_id}` |ნებადართული სიაში მყოფი ოპერატორის მოთხოვნა |ერთი რელეის რეგისტრაცია და ჯანმრთელობის დეტალები |
|`/v1/kaigi/relays/health` |ნებადართული სიაში მყოფი ოპერატორის მოთხოვნა |აგრეგატული რელე ჯანმრთელობა |
|`/v1/kaigi/relays/events` |კანონიკური ზუსტი ქსელის ანგარიშის მოთხოვნა |რეგისტრაციისა და ჯანმრთელობის მოვლენების ნაკადი |

აპლიკაცია API უნდა იყოს ჩართული. რელეის შეჯამება და ჯანმრთელობის მარშრუტები არის ოპერატორის ზედაპირები, მიუხედავად იმისა, რომ ისინი მხოლოდ წაკითხვა; ხელმოწერილი არ არის `curl` თხოვნა არ არის დასაშვები ხელმისაწვდომობის სონდი. სესიის მდგომარეობა ასევე ასახულია Kaigi დომენის მოვლენებით, როგორიცაა `KaigiRosterSummary`, `KaigiRelayManifestUpdated`, `KaigiRelayHealthUpdated` და `KaigiUsageSummary`.

### CLI სიგარეტის ტესტი {#cli-smoke-test}

დაიწყეთ `iroha app kaigi` CLI-ით, როდესაც გსურთ დაადასტუროთ, რომ Torii API საბოლოო წერტილი იღებს Kaigi ტრანზაქციებს, სანამ შევაერთებთ UI. სწრაფი დაწყების ბრძანება ქმნის ოთახს კონფიგურირებული API-ის საბოლოო წერტილის წინააღმდეგ და დაბეჭდება მისი ზარის იდენტიფიკატორი და შეუერთდით მეტამონაცემებს:

```bash
iroha app kaigi quickstart \
  --domain kaigi.universal \
  --summary-out kaigi-summary.json
```

სკრიპტირებული ნაკადებისათვის, მართეთ ოთახის სიცოცხლის ციკლი მკაფიოდ:

```bash
iroha app kaigi create \
  --domain kaigi.universal \
  --call-name daily \
  --host <i105-account-id> \
  --privacy-mode transparent \
  --room-policy authenticated

iroha app kaigi join \
  --domain kaigi.universal \
  --call-name daily \
  --participant <i105-account-id>

iroha app kaigi leave \
  --domain kaigi.universal \
  --call-name daily \
  --participant <i105-account-id>

iroha app kaigi record-usage \
  --domain kaigi.universal \
  --call-name daily \
  --duration-ms 120000 \
  --billed-gas 1500

iroha app kaigi end --domain kaigi.universal --call-name daily
```

გამოიყენეთ `--room-policy public` იმ ოთახებში, სადაც რელეებს შეუძლიათ გამოავლინონ მაყურებლის ბილეთის გარეშე, ან `--room-policy authenticated` როდესაც გასასვლელები უნდა მოითხოვოს მაყურებლის ავთენტიფიკაცია. გამოიყენეთ `--privacy-mode zk-roster-v1` მხოლოდ ქსელში Kaigi სია და გამოყენების შემოწმების გასაღები კონფიგურირებულია; წინააღმდეგ შემთხვევაში, დეტერმინისტური შემოწმების დროს გაერთიანება, ფოთლები და პირადი გამოყენების ჩანაწერები არ მუშაობს.

### JavaScript ინტეგრაცია {#javascript-integration}

მიმდინარეობა [Iroha JavaScript დემო](https://github.com/soramitsu/iroha-demo-javascript) ახორციელებს გამჭვირვალე, ავთენტიფიცირებულ ერთ-ერთ შეხვედრის პროფილს. ის არ ასახავს პროტოკოლის `zk-roster-v1` მტკიცებულების ნაკადი. მისი რენდერი ქმნის WebRTC შეთავაზებები და პასუხები, ხოლო პრივილეგირებული ხიდი იყენებს ადგილობრივ [`@iroha/iroha-js`](https://github.com/hyperledger-iroha/iroha/tree/0010c5a70039eac101a4846499ba9ceaf43eb65c/javascript/iroha_js) გადახდა ციტირება, ხელმოწერა, წარდგენა, და ველოდოთ დასრულებული Kaigi ოპერაციები.

იხილეთ [შეყვანა Kaigi JavaScript აპლიკაციაში](/ka/guide/tutorials/kaigi.md) ზუსტი მარშრუტის ავთენტიფიკაციის, მოწვევის ფორმატის, ხიდის საზღვრისა და მიმდინარე დემოტესტირების ბრძანებების შესახებ.

## სტატუსი და მაჩვენებლები {#status-and-metrics}

სტატუსისა და მაჩვენებლების API საბოლოო წერტილები პირველ რიგში დეშბორდებში ჩართულია:

- `/status` გამოყოფს უმაღლესი დონის ქსელის კვანძული, ბლოკის, რიგის და კონსენსუსის ველები
- `/metrics` ამჟღავნებს Prometheus- ის მაჩვენებლებს, მზომილებსა და ჰისტოგრამებს

Nexus-ის შესაძლებლობის მქონე კვანძებზე სტატუსის გამოსავალი ასევე მოიცავს შესრულების ზოლსა და მონაცემთა სივრცეზე ინფორმირებულ განყოფილებებს. როდესაც `nexus.enabled = false`, ეს განყოფილებები გამორიცხულია.

## JSON და Norito: შედარება {#json-vs-norito}

რამდენიმე ოპერატორი API საბოლოო წერტილი აბრუნებს Norito დეფოლტად. როდესაც API-ის საბოლოო წერტილი მხარს უჭერს JSON, გამოგზავნეთ:

```http
Accept: application/json
```

ეს განსაკუთრებით სასარგებლოა:

- `/v1/sumeragi/status`
- `/v1/sumeragi/qc`

როდესაც API საბოლოო წერტილი იღებს ან უშუალოდ აგზავნის Norito-ს, გამოიყენეთ `application/x-norito` როგორც შინაარსის ტიპი ან სასურველი `Accept` ღირებულება. იხილეთ ტრანსპორტის დეტალები [Norito](/ka/reference/norito.md#torii-and-norito-rpc).

## ტელემეტრიის პროფილები {#telemetry-profiles}

API ბოლო წერტილის ხილვადობა დამოკიდებულია კვანძის `telemetry.profile` პარამეტრზე. მიმდინარე კონფიგურაცია გამოყოფს ხუთ პროფილის დონეს:

|პროფილი |`/status` |`/metrics` |შემქმნელთა მარშრუტები |
| ----------- | --------- | ---------- | ---------------- |
|`disabled` |არა.|არა.|არა.|
|`operator` |დიახ.|არა.|არა.|
|`extended` |დიახ.|დიახ.|არა.|
|`developer` |დიახ.|არა.|დიახ.|
|`full` |დიახ.|დიახ.|დიახ.|

`iroha` CLI უკვე მოიცავს ამ API საბოლოო წერტილების ბევრს:

```bash
export IROHA_OPERATOR_KEY_FILE=/run/secrets/iroha/operator.key

iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \

```
