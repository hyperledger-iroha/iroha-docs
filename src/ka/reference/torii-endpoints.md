# Torii საბოლოო წერტილები {#torii-endpoints}

Torii ეს არის HTTP, SSE, და WebSocket შესასვლელი Iroha 3. იგი ემსახურება ორივე ლიდერების მიმართულებით APIs და ოპერატორის საბოლოო წერტილები.

ამჟამინდელი პროტოკოლის წესები არის:

- კანონიკური ბინარული ფორმატი არის Norito
- ბევრი საბოლოო წერტილი ასევე მხარს უჭერს JSON, როდესაც თქვენ გაგზავნით `Accept: application/json`
- მაჩვენებლები არის გამოქვეყნებული Prometheus ფორმატში

ფორმატის დეტალების, შინაარსის მოლაპარაკებების, განლაგების დროშების, სქემა ჰეშების და Norito RPC სახელმძღვანელოებისათვის იხილეთ [Norito რეფერენცია ](/ka/reference/norito.md).

## საერთო დასასრული პუნქტები {#common-endpoints}

|დასასრული |ფორმატი |მიზანი |
| --- | --- | --- |

`/openapi` არის ავტორიტეტული საბოლოო წერტილების სია მიმდინარე კვანძისთვის. ზუსტი ზედაპირი დამოკიდებულია აშენების მახასიათებლებსა და მიმდინარეობის კონფიგურაციაზე, ამიტომ გენერირებულმა კლიენტებმა უნდა ურჩიონ ცოცხალი OpenAPI დოკუმენტი ხელით გადაწერილი მარშრუტის სიაში. გამოიყენეთ [Torii API კონსოლი ](/ka/reference/torii-api-console.md) იმ ცოცხალი დოკუმენტის დატვირთვა, ტესტირება JSON მარშრუტები, კოპირება curl მოთხოვნები, და გენერირებს კლიენტური კოდი მიმდინარე სქემა.

## სცადეთ პირდაპირი Taira მარშრუტები {#try-live-taira-routes}

საჯარო Taira ტესტის ქსელი ამჟღავნებს იმავე Torii JSON ზედაპირს, რომელსაც აპლიკაციის კლიენტები მხოლოდ წაკითხვის მიზნით იყენებენ. აღნიშნულ ბრძანებებს არ მოითხოვს გასაღებები:

```bash
TAIRA_ROOT=https://taira.sora.org

curl -fsS "$TAIRA_ROOT/status" \
  | jq '{blocks, txs_approved, txs_rejected, queue_size, peers}'

curl -fsS "$TAIRA_ROOT/openapi.json" \
  | jq -r '.paths | keys[]' \
  | grep '^/v1/' \
  | head -n 20

curl -fsS "$TAIRA_ROOT/v1/node/capabilities" \
  | jq '{abi_version, data_model_version, query: .query.aggregate.supported_resources}'
```

შეეცადეთ რესურსის წაკითხვა დღევანდელი მსოფლიო მდგომარეობის წინააღმდეგ:

```bash
curl -fsS "$TAIRA_ROOT/v1/domains?limit=5" \
  | jq -r '.items[].id'

curl -fsS "$TAIRA_ROOT/v1/assets/definitions?limit=5" \
  | jq -r '.items[] | [.id, .name, .total_quantity] | @tsv'
```

თუ საჯარო ტესტნეტის მარშრუტი ბრუნდება `502`, დროთა განმავლობაში ან იუწყება გაჯერებული რიგის შესახებ, განიხილეთ ეს როგორც საბოლოო პუნქტის ხელმისაწვდომობის პრობლემა და კიდევ ერთხელ შეეცადეთ მოგვიანებით თქვენი კლიენტის კოდის დებეგირების წინ.

## App და SORA მარშრუტის ოჯახები {#app-and-sora-route-families}

როდესაც Torii აშენებულია აპლიკაციის მიმართულებით ფუნქციების კომპლექსით, ის გამოყოფს დამატებით JSON ოჯახებს ექსპლუატორებისთვის, SORA სერვისებს, ხიდის ნაკადებს, მტკიცებულებებს და შენახვას. ეს ოჯახები ყველა ქსელის პროფილისთვის არ არის ჩართული.

`pacs.009` წარდგენილებში უნდა იყოს წარმოდგენილი საქმიანი შეტყობინება ID, შეტყობინის განსაზღვრა ID, შექმნის დრო, ბანკთაშორისი ანგარიშსწორების თანხა, ვალუტა, ანგარიშგების თარიღი. ინსტრუქციული აგენტი BICs, და ვალდებული და კრედიტორი IBANs. თუ შეტყობინება მოიცავს `Purp`, ხიდი ამჟამად მხოლოდ ფასიანი ქაღალდების მიზნით დაფინანსებას იღებს: `Purp=SECU`.

`pacs.008` და `pacs.009` წარდგენის საბოლოო წერტილები იღებენ XML ISO კონვერტებს ან ხიდის გამოცდებისას გამოყენებულ ფლატურ მოედნის ფორმატს. არამარჩევნო `SplmtryData` მოედნებს შეუძლიათ მიზნული Iroha ლიდერის ჩაგდება, წყარო და სამიზნე ანგარიში IDs ან მისამართები, და აქტივების განსაზღვრა ID. პასუხი არის `202 Accepted` `message_id`, `transaction_hash`, `status`, `pacs002_code` და გადაჭრილი ლიდერის/ანგარიშის/აქტივის კონტექსტით.

## Kaigi სესიები {#kaigi-sessions}

Kaigi უზრუნველყოფს გადახდილ, რეალურ დროში აუდიო / ვიდეო ოთახებს SORA Nexus. გამოიყენეთ მას მაშინ, როდესაც აპლიკაციას სჭირდება წიგნის მხარდაჭერილი სესიის შექმნა, რესტრის ცვლილებები, რელე მანიფესტები, დაშიფრებული სიგნალი და გამოყენების გაზომვა იმის ნაცვლად, რომ ყველა კონფერენციის მდგომარეობა იყოს off-chain.

ლიდერების მიმართული სიცოცხლის ციკლი არის:

- `CreateKaigi`: შექმენით ზარი დომენის ქვეშ და შეინახეთ მისი პოლიტიკა, განრიგი, მეტა მონაცემები და არაკონკრეტული რელე მანიფესტი.
- `JoinKaigi` და `LeaveKaigi`: განახლება მოწოდების სიაში. კერძო რეჟიმში მონაწილეები პირდაპირი ანგარიშის IDs გამოხატვის ნაცვლად იყენებენ ვალდებულებებს, ბათილებლებსა და სიაში მტკიცებულებებს.
- `RecordKaigiUsage`: დაამატეთ გაზომული ხანგრძლივობა და გაზის მთლიანი რაოდენობა.
- `EndKaigi`: შეწყვიტეთ სესია და ჩაწერეთ ბოლო დროის ბეჭედი.

Torii გამოყოფს რელეების ტელემეტრიას ქვემოთ `/v1/kaigi/relays`, `/v1/kaigi/relays/{relay_id}`, `/v1/kaigi/relays/health`, და `/v1/kaigi/relays/events` როდესაც აპლიკაცია API და ტელემეტრიული მახასიათებლები ჩართულია. სესიის მდგომარეობა ასახულია Kaigi დომენის მოვლენები, როგორიცაა `KaigiRosterSummary`, `KaigiRelayManifestUpdated`, `KaigiRelayHealthUpdated`, და `KaigiUsageSummary`.

### CLI სიგარეტის ტესტი {#cli-smoke-test}

დავიწყოთ `iroha kaigi` CLI როდესაც გსურთ შეამოწმოთ, რომ a Torii საბოლოო წერტილი იღებს Kaigi ტრანზაქციები, სანამ დაკავშირება UI. სასწრაფო დაწყების ბრძანება ქმნის დროებით ოთახს აქტიური წინააღმდეგ Torii საბოლოო წერტილი და ბეჭდვის შემაჯამებელი ზარის იდენტიფიკატორით, შეუერთდით ბრძანებას, და SoraNet სროლის მინიშნება:

```bash
iroha kaigi quickstart --auto-join-host --summary-out kaigi-summary.json
```

სკრიპტირებული ნაკადებისათვის, მართეთ ოთახის სიცოცხლის ციკლი მკაფიოდ:

```bash
iroha kaigi create \
  --domain streaming \
  --call-name daily \
  --host <i105-account-id> \
  --privacy-mode transparent \
  --room-policy authenticated

iroha kaigi join --domain streaming --call-name daily --participant <i105-account-id>
iroha kaigi leave --domain streaming --call-name daily --participant <i105-account-id>

iroha kaigi record-usage \
  --domain streaming \
  --call-name daily \
  --duration-ms 120000 \
  --billed-gas 1500

iroha kaigi end --domain streaming --call-name daily
```

გამოიყენეთ `--room-policy public` იმ ოთახებში, სადაც რელეებს შეუძლიათ გამოავლინონ მაყურებლის ბილეთის გარეშე, ან `--room-policy authenticated` როდესაც გასასვლელები უნდა მოითხოვოს მაყურებლის ავთენტიფიკაცია. გამოიყენეთ `--privacy-mode zk-roster-v1` მხოლოდ ქსელში Kaigi სია და გამოყენების შემოწმების გასაღები კონფიგურირებულია; წინააღმდეგ შემთხვევაში, დეტერმინისტური შემოწმების დროს გაერთიანება, ფოთლები და პირადი გამოყენების ჩანაწერები არ მუშაობს.

### ტესტირება JavaScript დემოს საშუალებით {#testing-with-the-javascript-demo}

კონტროლირებადი ტესტისათვის, მიუთითეთ დემო Kaigi-სუნარიანობის Torii საბოლოო წერტილში:

1. დაიწყეთ Iroha კვანძი, სადაც არის ჩართული SORA/Kaigi აპლიკაციის მიმართულება APIs ან გამოიყენეთ საჯარო საბოლოო წერტილი, რომელიც გამოყოფს საჭირო Kaigi ზედაპირებს.
2. შეამოწმეთ ძირითადი ხელმისაწვდომობა `/health`, შემდეგ შეამოწმოთ ცოცხალი მარშრუტის ზედაპირი `/openapi` ან `/openapi.json`. ზოგიერთი განთავსება ასევე გამოხატავს `/v1/health`, მაგრამ `/health` არის გადამტანილი სიცოცხლისუნარიანობის შემოწმება.
3. TAIRA -ისათვის გადაცემის ტელემეტრიული მარშრუტების შემოწმება, სანამ პირდაპირი შეხვედრის ჩატარებას შეეცდებით:

   ```bash
   TAIRA=https://taira.sora.org
   curl -fsS "$TAIRA/health"
   curl -fsS "$TAIRA/v1/kaigi/relays"
   curl -fsS "$TAIRA/v1/kaigi/relays/health"
   ```

აღნიშნული შემოწმებები ადასტურებს, რომ Torii და Kaigi რელიე ტელემეტრიები ხელმისაწვდომია. ისინი არ ქმნიან შეხვედრას; `CreateKaigi` და `JoinKaigi` ჯერ კიდევ საჭიროებენ ფინანსურ საფულეებსა და ხელმოწერილ ტრანზაქციების წარდგენას.
4. გახსენით დემო, გადადით პარამეტრები, დააყენეთ Torii URL და მოდით აპლიკაციამ ჩაიტვირთოს ჯაჭვი ID და ქსელის პრეფიქსი ბოლო წერტილიდან.
5. შექმენით ან აღადგინეთ ორი ადგილობრივი საფულე დემოში. გამოიყენეთ ცალკეული აპლიკაციის ფანჯრები, პროფილები ან მანქანები, რათა მასპინძელს და სტუმარს აქვს ცალკე საფულის მდგომარეობა.

Kaigi UI-ის გამოცდისთვის:

1. მასპინძელი ფანჯარაში გახსენით Kaigi, აირჩიეთ შეხვედრის დაწყება, დაასახელეთ სათაური და აირჩიეთ Private invite ან Transparent invite.
2. აირჩიეთ კამერა და მიკრონი ჩართე, რათა WebRTC ჰქონდეს ადგილობრივ მედიას.
3. აირჩიეთ შეკრების ბმული შექმნა. ცოცხალი საფულე წარადგენს `CreateKaigi`; აპლიკაცია შემდეგ აჩვენებს `iroha://kaigi/join?call=...&secret=...` მოწვევას და `#/kaigi?...` უკან დაბრუნების მარშრუტს.
4. ფანჯარა ღია იყოს და მიწვევა გაუზიაროს სტუმარს.
5. სტუმრების ფანჯარაში, გახსენით მოწვევა ან დააჭირეთ მას შეხვედრაზე შეუერთდით, ჩართეთ ადგილობრივი მედია და აირჩიეთ შეუერთდით შეხვედრას. ცოცხალი საფულე იღებს კოდირებულ მასპინძლის შეთავაზებას Torii-დან და უგზავნის `JoinKaigi` კოდირებული პასუხის მეტადატებით.
6. მასპინძელმა უნდა დააყენოს პირველი პასუხი ავტომატურად სტრიმინგის ან გამოკითხვის გზით Kaigi ზარის სიგნალები. ორივე ფანჯარა უნდა აჩვენოს დაკავშირებული მედია და განახლებული კავშირის დეტალები.
7. სესიის დასრულება მასპინძელიდან, ან გამოიყენეთ ბრძანება CLI `iroha kaigi end` იმავე ზარისთვის ID.

Private Kaigi needs shielded XOR გადაიხადოს კერძო შესასვლელი საფასური. თუ დემო იუწყება, რომ კერძო Kaigi needs shelded XOR, გამოიყენეთ აპლიკაციის შიდა თვითშეფარვის მოთხოვნა და შეეცადეთ შექმნათ ან შეუერთდით ქმედება. თუ მტკიცებულებების გენერაცია, კერძო დაფინანსება ან ცოცხალი სიგნალიზაცია არ არის ხელმისაწვდომი, დემო შეიძლება დაბრუნდეს გამჭვირვალე / სახელმძღვანელო ნაკადზე. ამ შემთხვევაში, გახსენით მოწინავე სიგნალიზაცია, ასახეთ ნედლეული შეთავაზება ან პასუხის პაკეტი და დააჭირეთ მას მეორე ფანჯარში.

ავტომატიზებული შემოწმებისათვის დემო რეპოში, გაუშვით:

```bash
npm test -- tests/kaigiView.spec.ts tests/preloadKaigiBridge.spec.ts
npm run e2e:ui
npm run verify
```

კონცენტრირებული Vitest სუიტები მოიცავს Kaigi შეხვედრის ბმულების შექმნას, კომპაქტური მოწვევის დატვირთვას, კერძო შექმნა / გაწევრიანება / დასრულების ხიდის ზარებს, თვითშეზღუდვის შეტყობინებებს, სახელმძღვანელო უკან დაბრუნებას და პასუხის მიმოხილვას. UI სიგარეტის ტესტი მოიცავს რუტას `/kaigi` სამუშაო მაგიდაზე და მობილური ზომის სანახავად პორტებზე. ორი საფულეებს შორის პირდაპირი მედია ჯერ კიდევ საჭიროებს ორ ფანჯრის სახელმძღვანელო ტესტს, რადგან ბრაუზერის კამერა / მიკროფონის ნებართვები და პარტნიორული მედიის ნაკადები გარემოსთვის სპეციფიურია.

ნიმუშის ინტეგრაციის კოდისათვის იხილეთ [Embed Kaigi in a JavaScript App](/ka/guide/tutorials/kaigi.md).

## სტატუსი და მაჩვენებლები {#status-and-metrics}

სტატუსისა და მაჩვენებლების ბოლო წერტილები არის პირველი რამ, რომელიც ჩართულია დეშბორდებში:

- `/status` აღმოაჩენს უმაღლესი დონის პარტნიორი, ბლოკი, რიგები და კონსენსუსის ველები
- `/metrics` ამჟღავნებს Prometheus- ის მაჩვენებლებს, მზომილებსა და ჰისტოგრამებს

Nexus-ის შესაძლებლობის მქონე კვანძებზე სტატუსის გამოსავალი ასევე მოიცავს მარშრუტის და მონაცემთა სივრცის შესახებ ინფორმირებულ მონაკვეთებს. როდესაც `nexus.enabled = false`, ეს მონაკვეთები გამორიცხულია.

## JSON vs. Norito {#json-vs-norito}

რამდენიმე ოპერატორის საბოლოო წერტილი ბრუნდება Norito დეფოლტურად. როდესაც საბოლოო პუნქტი მხარს უჭერს JSON, გაგზავნეთ:

```http
Accept: application/json
```

ეს განსაკუთრებით სასარგებლოა:

- `/v1/sumeragi/status`
- `/v1/sumeragi/qc`
- `/v1/sumeragi/commit_qc/{hash}`

როდესაც საბოლოო წერტილი იღებს ან უშუალოდ აგზავნის Norito ტიპს, გამოიყენეთ `application/x-norito` როგორც შინაარსის ტიპი ან სასურველი `Accept` ღირებულება. იხილეთ ტრანსპორტის დეტალები [Norito](/ka/reference/norito.md#torii-and-norito-rpc).

## ტელემეტრიის პროფილები {#telemetry-profiles}

საბოლოო წერტილების ხილვადობა დამოკიდებულია კვანძის `telemetry.profile` პარამეტრზე. მიმდინარე კონფიგურაცია ხუთ პროფილის დონეს ხელმისაწვდომს ხდის:

|პროფილი |`/status` |`/metrics` |შემქმნელთა მარშრუტები |
| --- | --- | --- | --- |
|`disabled` |არა |არა |არა |
|`operator` |დიახ |არა |არა |
|`extended` |დიახ |დიახ |არა |
|`developer` |დიახ |არა |დიახ |
|`full` |დიახ |დიახ |დიახ |

## CLI მოკლე გზები {#cli-shortcuts}

`iroha` CLI უკვე მოიცავს ამ საბოლოო წერტილების ბევრს:

```bash
iroha --config ./localnet/client.toml --output-format text ops sumeragi status
iroha --config ./localnet/client.toml --output-format text ops sumeragi phases
iroha --config ./localnet/client.toml ops sumeragi params
iroha --config ./localnet/client.toml --output-format text ops sumeragi telemetry
```
