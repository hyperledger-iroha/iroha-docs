# I105 ანგარიშის მისამართის ფორმატი {#i105-account-address-format}

I105 არის კანონიკური გარე ტექსტის ფორმატი Iroha 3 `AccountId`.

მისი დატვირთვა წარმოადგენს ანგარიშის კონტროლერს.

მისი სენტინელი განსაზღვრავს განკუთვნილ ქსელს ჯაჭვის დისკრიმინანტით.

გამოიყენეთ ის ნებისმიერ ადგილას, სადაც API, ტრანზაქცია, ნებართვა ან მოთხოვნა მოითხოვს კანონიკური ანგარიშის ID.

I105 ანგარიშის იდენტიფიკაცია არის დომენის გარეშე.

ისეთი მნიშვნელობა, როგორიცაა `treasury@payments.universal`, ანგარიშის ალიასია და არა I105 ID-ის ჩაწერის სხვა ფორმა.

I105 ID-ის გამოყვანა ანგარიშს არც არეგისტრირებს და არც აფინანსებს.

::: warning წესები, რომლებიც ხელს უშლის ინტეგრაციის უმეტესობის წარუმატებლობას

- აირჩიეთ ქსელის პროფილი, სანამ კოდირებას ან ადასტურებს მისამართს.
- ინახეთ და შეადარეთ კანონიკური UTF-8 სიგრიფი ზუსტად.
- შეინარჩუნეთ ასოების რეგისტრი და არ გამოიყენოთ `Unicode` ნორმალიზაცია.
- I105 ID-ს არ უნდა ჰქონდეს `@domain` ან `@domain.dataspace` სუფიქსი.
- გამოიყენეთ Iroha SDK ან `iroha tools address`.
- რეგულარული გამოთქმა არ არის I105 ვალიდატორი.

:::

## ლიტერალური ანატომია {#literal-anatomy}

I105 ლიტერალში არის სამი მიმდებარე ნაწილი და არ არსებობს გამყოფი:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

| ნაწილი | დანიშნულება | საკონტროლო ჯამის დაფარვა |
| ---------------- | ------------------------------------------------------------------ | ----------------- |
| ქსელის სენტინელი | ტექსტს აკავშირებს ერთ `u16` ჯაჭვის დისკრიმინანტთან | არ არის დაფარული |
|დატვირთვები |`base-105` კანონიკური ანგარიშის კონტროლერის ბაიტების კოდირება |დაფარული |
| საკონტროლო ჯამი | I105 ანბანით წარმოდგენილი `Bech32m`-ის სტილის ექვსი `5-bit` მნიშვნელობა | N/A |

სასარგებლო დატვირთვა და საკონტროლო ჯამი ანგარიშის კონტროლერს განსაზღვრავს.

სენტინელმა აირჩიოს ქსელის კონტექსტი.

ერთსა და იმავე კონტროლერს აქვს იგივე დატვირთვისა და გადამოწმების რაოდენობა Taira და Minamoto, მაგრამ თითოეული ქსელი იყენებს განსხვავებულ წამყვან სენტინელს.

დეკოდერმა უნდა უზრუნველყოს მოსალოდნელ დისკრიმინანტთან შესაბამისობა.

საკონტროლო ჯამს სენტინელის ჩანაცვლების აღმოჩენა არ შეუძლია.

### ქსელის მცველები {#network-sentinels}

| ქსელი ან კონტექსტი | ჯაჭვის დისკრიმინანტი | Hex | კანონიკური სენტინელი |
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
|Taira საჯარო ტესტის ქსელი |                            `369` |`0x0171` |`test` |
|Minamoto საზოგადოებრივი ქსელი |                            `753` |`0x02f1` |`sora` |
|განვითარების კონტექსტი |                              `0` |`0x0000` |`dev` |
|ნებისმიერი სხვა `u16` ღირებულება |ყველა გარდა `0`, `369` და `753` |        — |`n` პლუს მინიმალური ათეული, მაგალითად `n42` |

დასახელებული მნიშვნელობები ყოველთვის შესაბამის დასახელებულ სენტინელს იყენებს.

ფორმები, როგორიცაა `n00042`, `n369`, `n753` და `n0` არ არის კანონიკური.

ტრანზაქციის ჯაჭვის ID და I105 ჯაჭვური დისკრიმინანტი ცალკე ღირებულებებია.

API საბოლოო წერტილის ან ჯაჭვის ID-ის შერჩევა არ ნიშნავს, რომ პირდაპირ აირჩიოს მისამართი პროფილი.

## ნორმატიული ერთმნიშვნელოვანი მაგალითი {#normative-single-key-example}

ქვემოთ მოცემული სასარგებლო დატვირთვა და Minamoto ფორმა მოდის SDK-ის ჯვარედინით შესაბამისობის მობილურიდან.

Taira ფორმაში გამოიყენება Taira-ის სენტინელი იმავე დატვირთვაზე:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

კანონიკური სასარგებლო დატვირთვა იწყება `02 00 01 20`: სათაური `0x02`, კომპაქტური ერთმნიშვნელოვანი ტეგი `0x00`, `Ed25519` მრგვალი ID `0x01` და 32-ბაიტიანი გასაღების სიგრძე `0x20`.

`multihash` პრეფექსი შეყვანილი მეტამონაცემებია და არ არის გადაწერილი კონტროლერის დატვირთვაში.

## შეიქმნას და შემოწმდეს ID-ები CLI {#create-and-inspect-ids-with-the-cli}

უპირატესობა აქვს საჯარო ქსელისათვის დასახელებული პროფილი:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

I105 შესასვლელის ნორმალიზება და შედარება მისამართ-კოდეკის ქცევის დიაგნოსტიკის დროს:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

შეამოწმეთ აღმოჩენილი ფორმატი, კანონიკური hex და არჩეული ქსელის კონტექსტი JSON-ის სახით:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

ახალი ხაზებით გამოყოფილი ფაილის address-codec-ის სტრუქტურა ისე შეამოწმეთ, რომ პარსინგის შეცდომები ჩუმად არ მიიღოთ:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution CLI ვალიდაციის საზღვარი

`convert`, `normalize` და`audit` ბრძანებები მუშაობენ ქვედა დონის `AccountAddress` კოდეკზე.

ისინი ამოწმებენ სენტინელს, ანბანს, საკონტროლო ჯამს, ბაიტების სიგრძეებს, `CurveId`/გასაღების სტრუქტურას და მისამართის ფენაზე ზუსტ ხელახალ კოდირებას.

ისინი არ წარმოქმნიან `AccountId`.

ისინი თვითონ არ ადასტურებენ ყველა მრავალნიშნა პოლიტიკის სემანტიკას.

ისინი არ ადასტურებენ, რომ სათაურის კლასი შეესაბამება კონტროლერს.

ავტორიზაციამდე ან მუდმივ შენახვამდე გამოიყენეთ `AccountId`-ის მკაცრი ვალიდაცია.

:::

კერძო ქსელისათვის, გამოიყენეთ მისი კონფიგურირებული დისკრიმინანტი მკაფიოდ `--network-prefix`.

არსებული მისამართის მკაფიო კონტექსტებს შორის გარდაქმნისას, ასევე მიაწოდეთ წყარო `--expect-prefix`:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

რე-კოდირება იცვლის მხოლოდ ქსელის კონტექსტს.

ის არ რეგისტრირებს ანგარიშს მიზნობრივ ქსელში ან არ ადასტურებს, რომ იმავე კონტროლერის გამოყენება იქ უნდა მოხდეს.

## კოდირების ალგორითმი {#encoding-algorithm}

კანონიკური კოდერები ასრულებენ შემდეგ ოპერაციებს:

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

ლიდერი ნულოვანი ბაიტები შენარჩუნდება ნულოვან `base-105` ციფრებად.

საკონტროლო ჯამი იყენებს `Bech32` `polymod` გენერატორებს და კონსტანტას `0x2bc830a3`.

მხოლოდ საკონტროლო ჯამისთვის განკუთვნილი HRP არის ASCII სტრიქონი `snx`.

მხოლოდ საკონტროლო ჯამისთვის განკუთვნილი HRP მისამართში არ იბეჭდება.

ექვსი შემოწმების რაოდენობის მნიშვნელობა შედის `0..31` დიაპაზონში და წარმოდგენილია იმავე I105 ანბანის მეშვეობით, რაც დატვირთვის.

### I105 ანბანი {#i105-alphabet}

105 სიმბოლო ინდექსირებულია ზუსტად ამ რიგით.

პირველი რიგითა არის `Bitcoin Base58` ანბანი და შეიცავს ციფრებს `0..57`.

მეორე რიგი შეიცავს ციფრებს `58..104`.

კონკეტენირება რიგები, როდესაც დანერგვის codec.

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

ალიფბეტი `Unicode` -ზე მგრძნობიარეა.

ზუსტი თანმიმდევრულობა იყენებს იაპონურ `compatibility-width` სიმბოლოებს `kana` და კოდპუნქტებს, რომლებიც ნაჩვენებია `ヰ` და `ヱ`.

არ გამოიყენოთ NFC, NFKC, სიგანის გარდაქმნა, ასოების რეგისტრის გათანაბრება ან ვიზუალურად მსგავსი სიმბოლოთი ჩანაცვლება.

ASCII `0`, `O`, `I` და `l` არ არის ანბანის სიმბოლოები.

## კანონიკური ანგარიშის დატვირთვა {#canonical-account-payload}

`base-105` ორგანო კოდირებს ბინარული ანგარიშის დატვირთვას, არა საჯარო გასაღების სტრიქონს და არც Norito JSON ობიექტს:

```text
header:u8 || controller:variable
```

ქვემოთ მოცემული ყველა მრავალბაიტიანი მთელი რიცხვი უნიშნოა და `big-endian` ფორმატშია.

დომენი, მონაცემთა სივრცე, ალიასი, UAID, და ანგარიშის მეტამონაცემების ბაიტები არ არის.

### სათაურის ბაიტი {#header-byte}

|ბიტები |სიგანე |ამჟამინდელი კოდირების გამომუშავება |მნიშვნელობა |
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |მისამართის ფორმატის ვერსია |
| `4..3` |     2 |`0` ცალკე გასაღები, `1` მრავალნიშანი |მისამართების კლასი |
| `2..1` |     2 |                          `1` |ნორმალიზების ვერსიის |
| `0`    |     1 |                          `0` |განკუთვნილი `extension flag` |

ამჟამინდელი V1 კოდერები გამოდის სათაურით `0x02` ერთმნიშვნელოვანი კონტროლორისათვის და `0x0a` მრავალნიშნაობითი კონტროლერისათვის.

მისამართის კლასები `2` და `3` არ არის მინიჭებული.

`extension flag`-ის მნიშვნელობა `1` უარყოფილია.

დაბალი დონის დეკოდერს შეუძლია შეინარჩუნოს ვერსიისა და ნორმალიზაციის ბიტების სხვა მნიშვნელობები და დამოუკიდებლად არ ამოწმებს კლასის შესაბამისობას კონტროლერის ტეგთან.

`AccountId`-ად გარდაქმნა და მისი კანონიკური წარმოდგენის შედარება მიმდინარე V1 კანონიკურობას ადასტურებს.

### ერთმნიშვნელოვანი კონტროლერი {#single-key-controller}

გამოიყენეთ კომპაქტური ფორმა, თუ ნედლი საჯარო გასაღების სასარგებლო დატვირთვა არ აღემატება 255 ბაიტს:

|სფერო |სიგანე |ღირებულება ან მნიშვნელობა |
| ------------ | --------------: | ------------------------ |
|`tag` |1 ბაიტი |`0x00` |
|`curve` |1 ბაიტი |`CurveId` რეესტრის ღირებულება |
| `key_len` | 1 ბაიტი | ნედლი გასაღების სიგრძე |
|`public_key` |`key_len` ბაიტები |ნედლეული საჯარო საკვანძო |

255 ბაიტზე გრძელი გასაღებები გაფართოებულ ფორმას იყენებს:

|სფერო |სიგანე |ღირებულება ან მნიშვნელობა |
| ------------ | --------------: | ---------------------------- |
|`tag` |1 ბაიტი |`0x02` |
|`curve` |1 ბაიტი |`CurveId` რეესტრის ღირებულება |
|`key_len` |2 ბაიტი |ნედლეულის გასაღების სიგრძე, `big-endian` |
|`public_key` |`key_len` ბაიტები |ნედლეული საჯარო საკვანძო |

გაფართოებული კოდირება არ არის კანონიკური გასაღებისთვის, რომელიც შეესაბამება კომპაქტულ ფორმას.

### მულტისიგის კონტროლერი {#multisig-controller}

|სფერო |სიგანე |ღირებულება ან მნიშვნელობა |
| ---------------- | -------: | ------------------------------ |
|`tag` |1 ბაიტი |`0x01` |
|`policy_version` |1 ბაიტი |მიმდინარე ღირებულება `1` |
|`threshold` |2 ბაიტი |სავალდებულო ნებართვის საერთო წონა |
|`member_count` |2 ბაიტი |შემდეგი წევრების რაოდენობა |
|`members` |ცვლადი |განმეორებითი წევრების ჩანაწერები |

თითოეული წევრის ჩანაწერი არის:

|სფერო |სიგანე |მნიშვნელობა |
| ------------ | --------------: | ------------------------ |
|`curve` |1 ბაიტი |`CurveId` რეესტრის ღირებულება |
|`weight` |2 ბაიტი |წევრის დამტკიცების წონა |
| `key_len` | 2 ბაიტი | ნედლი გასაღების სიგრძე |
|`public_key` |`key_len` ბაიტები |ნედლეული საჯარო გასაღები |

მოქმედ პოლიტიკას უნდა ჰყავდეს სულ მცირე ერთი წევრი, ჰქონდეს დადებითი წონები, არ ჰქონდეს დუბლირებული საჯარო გასაღებები, ხოლო ზღვარი უნდა იყოს `1`-დან წევრების წონათა ჯამამდე.

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

კანონიკური კონსტრუქცია ასორტირებს წევრებს ხელმოწერის ალგორითმის სტაბილური სახელწოდებით, ნულოვანი გამყოფი ბაიტით და შემდეგ ნედლეული საჯარო გასაღები ბაიტებით.

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

I105 ლიტერალს არ აქვს ფიქსირებული ხასიათის სიგრძე, რადგან მულტისიგური და პოსტკვანტური კონტროლერები შეიძლება იყოს დიდი.

## მკაცრი AccountId მოწმობა და კანონიკური ფორმის შესრულება. {#strict-accountid-validation-and-canonicality}

SDK-ის მოსალოდნელი ჯაჭვის დისკრიმინანტით კონფიგურაციის შემდეგ, მნიშვნელობა გააანალიზეთ როგორც `AccountId` და დაბრუნებული კანონიკური წარმოდგენა შეადარეთ კიდეებზე ნებადართული ცარიელი სივრცისგან გასუფთავებულ შესატანს.

შედარება არის მნიშვნელოვანი, რადგან პარსერმა შეუძლია ნორმალიზოს `AccountId` კონტროლერის დეკოდებადი მასალა.

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

არასანდო სტრიქონისთვის შესაბამისმა აპლიკაციამ უნდა:

1. სრული მნიშვნელობის გარშემო მხოლოდ ნებადართული სატრანსპორტო ცარიელი სივრცე მოაშორეთ.
2. წაიკითხეთ სენტინელი და მოითხოვეთ მოსალოდნელი ჯაჭვის დისკრიმინანტი.
3. დარჩენილი ყოველი `Unicode` სიმბოლო ზუსტი 105-სიმბოლოიანი ანბანით ასახეთ.
4. გამოყავით საკონტროლო ჯამის ექვსი ციფრი.
5. გადმოიყვანეთ დატვირთვის ციფრები კანონიკურ ბაიტებზე.
6. ამ კანონიკურ ბაიტებზე საკონტროლო ჯამი გადაამოწმეთ.
7. შეამოწმეთ სათაური და კონტროლერი, რომელიც მოითხოვს:
   - სფეროს ზუსტი სიგრძეები
   - მხარდაჭერილი `CurveId`
   - მოქმედი საჯარო გასაღები
   - არ არის შემდგომი ბაიტები
   - მოქმედი მრავალნიშნის პოლიტიკა, სადაც ეს გამოიყენება
8. შექმნას `AccountId`.
9. `AccountId` კანონიკურად წარმოადგინეთ მოსალოდნელი დისკრიმინანტისთვის.
10. მოითხოვეთ `byte-for-byte` ტოლობა კიდეებზე ნებადართული ცარიელი სივრცისგან გასუფთავებულ შესატანთან.

აპლიკაციის მკაფიო საბოლოო ნაბიჯი `render-and-compare` უარყოფს არა მინიმალური ციფრული სენტინელები, არა კანონიკური კონტროლერის განლაგებები, რეორგანიზებული პოლიტიკის მასალა და ნებისმიერი სხვა მართლწერა, რომელიც დეკოდის, მაგრამ არ არის კოდირების მიმდინარე V1 გამოსავალი.

საკონტროლო ჯამის წარმატებული შემოწმება ან დაბალი დონის `AccountAddress`-ის პარსინგი ამ შემოწმებას ვერ ჩაანაცვლებს.

არ მიიღოთ აღნიშნული ღირებულებები ანგარიშის ID-ის მკაცრ ველში:

- ანგარიშის ალიასი, მაგალითად `alice@wonderland.universal`
- I105 ლიტერალი, რომელსაც ბოლოში დამატებული აქვს `@domain` სუფიქსი
- საჯარო გასაღები `multihash`, როგორიცაა `ed0120...`
- კანონიკური დატვირთვის hex, როგორიცაა `0x02000120...`
- არასწორი ჯაჭვის დისკრიმინანტის მისამართი
- რიგები, რომლებიც შეიცვალა დიდი ან მცირე ასოებით, ხასიათის სიგანით, `kana`, დატვირთვით ან ჯამში.

აპლიკაციის საზღვარზე ალიასები ამოხსენით და დაბრუნებული კანონიკური I105 ID შეინარჩუნეთ ავტორიზაციის, ხელმოწერის, ნებართვებისა და აუდიტის ჩანაწერებისთვის.

## API, შენახვისა და გამოფენის წესები {#api-storage-and-display-rules}

- გამოგზავნეთ ზუსტი I105 UTF-8 სტრიკი ანგარიშის ველებში JSON.
- `Percent-encode` ანგარიშის ID სრულად, სანამ ის URL გზაზე განთავსდება.
- არასოდეს გამოიყენოთ ანგარიშის ალიასი I105 ID-ის ნაცვლად.
- შეინახეთ კანონიკური სიგელი, რომელიც დაბრუნებულია კოდექის მიერ `byte-preserving` შედარების სემანტიკით.
- გამოიყენეთ კოლაცია, რომელიც ინარჩუნებს ასოების რეგისტრსა და სიმბოლოს სიგანეს.
- შეინარჩუნეთ ქსელის დისკრიმინანტული ან დასახელებული ქსელის პროფილი ექსპორტირებული ანგარიშების მონაცემებითა და ბეკაპებით.
- გამოიყენეთ მხოლოდ მისამართი ქსელის კონტექსტით.
- აჩვენეთ სრული მისამართი და მიუთითეთ ასლის მოქმედება.
- ყოველ `kana` პერსონაჟს ზუსტად შეინახეთ.
- შეინახეთ სრული მისამართი ხელმისაწვდომი, როდესაც კომპაქტური ეკრანი მოკლეა მისი შუაგული.
- ალიასიდან ხელახლა აგების ნაცვლად გამოიყენეთ შენახული კანონიკური ID.

`AccountId` ჩვენება და JSON კანონიკური გამოყენება I105.

ქვედა დონის `AccountAddress` ჩვენება/JSON წარმოდგენა იყენებს კანონიკური hex შიდა და დებეგინგის კონტექსტებისათვის.

როდესაც გარე ანგარიშის ID არის საჭირო, გამოიძახეთ `AccountAddress`-ის ცხადი I105 ენკოდერი.

ანგარიშის შექმნისა და ანალოგიური რეზოლუციის სამუშაო პროცესებისათვის, განაგრძეთ [ანგარიშები და სათაურები](/ka/cookbook/accounts-and-aliases.md).

ანგარიშის მონაცემთა მოდელი იხილეთ [ანგარიშები](/ka/blockchain/accounts.md).
