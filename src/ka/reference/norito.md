# Norito {#norito}

Norito არის Iroha კანონიკური სერიალიზაციის ფენა. ეს არის გამოყენებული ბაიტის ფორმატი
როცა თანატოლები არიან, SDKs, CLI ინსტრუმენტები, Torii, Kura, და წარმოქმნილი არტეფაქტები უნდა შეთანხმდნენ
ზუსტად იმავე სასარგებლო ტვირთზე.

გამოყენება Norito როდესაც მონაცემები კონსენსუსის ნაწილია, ხელმოწერა, ჰეშინგი, მტკიცებულება;
ან გადასასვლელი SDK ინტერპერატიულობა. გამოყენება JSON როდესაც საბოლოო წერტილი მკაფიოდ გთავაზობთ
ადამიანთა მიერ წაკითხული პროექცია ოპერატორებისთვის, დაშბორდებისთვის ან სწრაფი დებეგირებისათვის.

სასარგებლო ტვირთები.

## სასარგებლო ტვირთის მოდელი {#payload-model}

ყველა მავთულხლართზე ან დისკზე Norito სასარგებლო ტვირთის ჩარჩოში არის სათაური, რომელსაც მოჰყვება
კოდირებული სასარგებლო ტვირთების ბაიტები. უსახური ან შიშველი სასარგებლო დატვირთვები ინტეგრირებულია შიდა
hashing, benchmarks და დამხმარე APIs რომელიც დაუყოვნებლივ შეასრულებს შედეგს
სათაური ტრანსპორტის წინ.

| სათაურის ველი | ზომა | მიზანი |
| --- | ---: | --- |
| მაგია | 4 ბაიტი | ASCII `NRT0`, გამოიყენება უარის თქმის მიზნით,Norito მონაცემები ადრე. |
| მაჟორიტარი | 1 ბაიტი | ფორმატირება ძირითადი ვერსია. მიმდინარე სასარგებლო ტვირთების გამოყენება `0`. |

| სქემა ჰაში | 16 ბაიტი | ტიპის იდენტობა, რომელიც გამოიყენება ტიპირებული დეკოდერების მიერ მოულოდნელი სასარგებლო ტვირთების უარყოფისთვის. |
| კომპრესია | 1 ბაიტი | `0 = None`, `1 = Zstd`. უცნობი ღირებულებები უარყოფავენ. |

| CRC64 | 8 ბაიტი | CRC64-XZ არასაკომპლექტო სასარგებლო ტვირთის შემოწმების თანხა. |
| დროშები | 1 ბაიტი | განლაგების დროშები კომპაქტური სიგრძეებისთვის, შეფუთული თანმიმდევრობებისა და შეფუთულ სტრუქტებზე. |

კაპიტალი 40 ბაიტი. დეკოდერები ადასტურებენ მაგიას, ვერსიას, მხარდაჭერილ დროშას

ტიპირებული ღირებულება.

## განლაგების დროშები {#layout-flags}

Norito შენახავს განლაგების არჩევანს საბოლოო სათაურის ბაიტში.
გამონაბოლქვა `COMPACT_LEN` (`0x02`) კომპაქტური სიგრძის პრეფექციებისათვის.
ფიქსირებული სიგანის სიგრძის პრეფიქსები კვლავ კითხვად რჩება, როდესაც დამრეკელები კოდირებენ
`flags = 0x00`.

| დროშა | ჰექსი | სტატუსი | ეფექტი |
| --- | ---: | --- | --- |
| `PACKED_SEQ` | `0x01` | მხარდაჭერა | კოდირება ცვალებადი ზომის კოლექციები ოფსეტის ცხრილით და თანმიმდევარი მონაცემების ბლოკით. |
| `COMPACT_LEN` | `0x02` | დეფოლტი | გამოიყენება კანონიკური ხელმოუწერელი varints წვრილი სიგრძის პრეფექციებისათვის. |
| `PACKED_STRUCT` | `0x04` | მხარდაჭერა | კოდები წარმოქმნილი სტრუქტები, როგორც შეფუთული საველო სასარგებლო ტვირთები. |
| `VARINT_OFFSETS` | `0x08` | რეზერვებული | უარყოფილი v1; შეფუთული სიხშირის გადანაწილება არის ფიქსირებული სიგანის `u64`. |
| `COMPACT_SEQ_LEN` | `0x10` | რეზერვებული | უარი v1- ში; ზედა დონის სიგრძის სათაურები ფიქსირებული სიგანეა `u64`. |
| `FIELD_BITSET` | `0x20` | მხარდაჭერა მოთხოვნებით | დაამატებს ბიტსეტს შეფუთული სტრუქტებისთვის, ასე რომ მხოლოდ ის ველები, რომლებიც საჭიროებენ მკაფიო ზომებს ატარებენ ზომის პრეფიქსებს. `PACKED_STRUCT` და `COMPACT_LEN`. |

დკოდერები არ ასახელებენ განლაგებას სასარგებლო ტვირთის ფორმიდან,
უმნიშვნელო ვერსია, ან heuristics. უცნობი ან არასწორი კომბინაციების უარყოფა ასე
რომ ყველა თანატოლს სასარგებლო ტვირთის ინტერპრეტაცია ერთნაირად აქვს.

## კოდირების წესები {#encoding-rules}

Norito გამოიყენება დეტერმინისტური განლაგებები საერთო მონაცემთა ფორმებისთვის, რომლებიც გამოჩნდება
დასახელება Iroha მონაცემთა მოდელი:

- რგოლები არის `[len][utf8-bytes]`; `len` შემდეგი: `COMPACT_LEN` როცა ეს შესაძლებელი იქნება.
- გათვალისწინებულია, რომ სარეკლამო მოცულობის შეზღუდვა უნდა იყოს: `COMPACT_LEN` განისაზღვრება, წინააღმდეგ შემთხვევაში
  მუდმივი 8-ბაიტიანი პატარა ენდიანი `u64`.
- სერვისის სიგრძის სათაურები ფიქსირდება 8-ბაიტიანი პატარა ენდიან `u64` v1-ში.
- `Vec<u8>` კოდირებულია როგორც `[len_u64][raw-bytes]` ერთი სიგრძის ნაცვლად ბაიტზე.
- გამოყენება შეფუთული თანმიმდევრობები `(len + 1)` მონოტონიური `u64` შემცირება, რომელსაც მოჰყვება:
  კონკატენირებული ელემენტის სასარგებლო ტვირთები.
- რუკები კოდირება შესვლის რიცხვები ფიქსირებული `u64` და გამოიყენეთ დეტერმინისტური საკვანძო რიგითი.
  `HashMap` ჩანაწერები კოდირებამდე გასაღების მიხედვით არის დარეგულირებული; `BTreeMap` იყენებს თავის
  ბუნებრივი წესრიგი.
- `BigInt` იყენებს მცირე ენდიან ორის დამატების ბაიტებს `u32` ბაიტების სიგრძე
  და 512-ბიტური კაპი.
- `Numeric` კოდირებულია როგორც `(mantissa, scale)`, სადაც mantissa ინახავს
  მთლიანი რიცხვის მნიშვნელობა და მასშტაბი ინახავს ფრაქციონალური ციფრების რაოდენობას.

ეს წესები მნიშვნელოვანია ხელმოწერებისა და ჰაშებისათვის. SDKs რომ ააშენოს იგივე
ლოგიკური ტრანზაქცია უნდა წარმოადგინოს იგივე კანონიკური ბაიტები.

## სქემის ჰაშები {#schema-hashes}

ტიპირებული Norito სასარგებლო ტვირთები ატარებენ 16-ბაიტიანი სქემა hash სათაურში.
hash არის მიღებული სრულად კვალიფიცირებული ტიპის სახელწოდებიდან.
სტრუქტურული სქემის ჰეშინგი იწვევს ჰეშს კანონიკური სქემიდან.

ტიპირებული დეკოდერები უარყოფენ სქემის შეუსაბამობას. ეს იცავს კლიენტებს შემთხვევით
დეკოდირება ვალიდული Norito ჩარჩო როგორც არასწორი ტიპი და არის ჩვეულებრივი გაუმართულობის რეჟიმი
როდესაც SDK ჩარჩოების ბუნდელი დრიფტებს ნოდების მონაცემთა მოდელისგან.

## შეკუმშვა და აჩქარება {#compression-and-acceleration}

Norito მხარს უჭერს მკაფიო და ადაპტიური შეკუმშვა, არ შეცვლის ლოგიკური
სასარგებლო ტვირთი:

| მახასიათებელი | მიზანი |
| --- | --- |
| `to_bytes` | კოდირებული არაკომპრესირებული სათაურის ჩარჩოების სასარგებლო ტვირთით. |
| `to_compressed_bytes` | კოდირება Zstd და ჩანაწერი compression tag სათაურში. |
| `to_bytes_auto` | გამოიყენეთ დეტერმინისტური ჰეურისტიკა იმის დასადგენად, ღირს თუ არა კომპრესია. |
| CRC64 დაჩქარება | პორტატული გამოყენებები CRC64-XZ ყველგან, CLMUL x86-ზე_64 ან PMULL aarch64-ზე, როდესაც ხელმისაწვდომია. |
| GPU CRC64 და შეკვამება | ნორმატიული ლითონი ან CUDA დამხმარეებს შეუძლიათ დააჩქარონ დიდი სასარგებლო ტვირთები, შემდეგ კი უკან დაეცემა CPU გზები. |

აპარატურის დაჩქარება არასდროს ცვლის დეკოდირებულ შინაარსს. CRC და JSON
აჩქარებლები უნდა შეესაბამებოდეს პორტატულ გამოსავალი ბიტ-ბიტს. Zstd ჩარჩო ბაიტები შეიძლება
განსხვავება CPU და GPU კოდერები, მაგრამ დეკოდირებული სასარგებლო ტვირთი და Norito სათაური
მეტა მონაცემები რჩება დეტერმინისტური ვალიდაციისათვის.

## JSON მხარდაჭერა {#json-support}

Norito მოიცავს მშობლიურ JSON დასასრული წერტილების და საჭირო ინსტრუმენტების საფარი JSON
დატოვების გარეშე Norito ტიპის სისტემა.

| JSON მახასიათებელი | გამოყენების შემთხვევა |
| --- | --- |
| `norito::json::{to_json, from_json}` | დეტერმინისტური ტიპი JSON კოდირება/დაკოდირება. |
| ლამაზი და მწერლის დამხმარეები | CLI გამონადენი, მოწყობილობები და სტრიმინგი `std::io` ინტეგრაცია. |
| DOM ღირებულებები | პროგრამული მანიპულაცია Norito ეს არის JSON ღირებულების მოდელი. |
| სწრაფი ტიპირება JSON | სტრუქტურული ზოლის საფუძველზე დამუშავებული დეკოდი/კოდები ცხელი DTO გზები. |
| ნულოვანი ასლის მკითხველი | ტოქნის სკანირება, რომელიც სესხებს სიმბოლოებს შესასვლელიდან, სადაც შესაძლებელია. |
| პირველი ეტაპის აჩქარებლები | ნებაყოფლობით AVX2, NEON, ლითონი, ან CUDA სტრუქტურული ინდექსირება სკალარული დაცემით. |

Iroha კოდი უნდა ურჩევნია `norito::json` დამხმარეები ტიპირებისთვის API სასარგებლო ტვირთების დამატება
მკაფიო `serde_json` საწარმოო გზებისათვის სქემიდან განსხვავებული რისკები და
სასოფლო-სამეურნეო მოქმედება, რომელიც მოსალოდნელია SDKs და Torii ექსტრაქტორები.

## დერევიზური მხარდაჭერა {#derive-support}

Rust მონაცემთა ტიპები, როგორც წესი, იყენებენ დერევიტულ მაკროებს და არა სახელმძღვანელო კოდექის კოდს.
დერევიტური ფენა შეიძლება წარმოქმნას Norito ბინარული კოდეკები, სქემები და JSON დამხმარეები.

საერთო ველის ატრიბუტებია:

| ატრიბუტი | ეფექტი |
| --- | --- |
| `#[norito(rename = "other")]` | იყენებს სტაბილურ სერიალიზებულ სახელს სქემა და JSON შესაბამისობა. |
| `#[norito(skip)]` | ავიცილებს ველს და აავსებს მას `Default` დეკოდირების დროს. |
| `#[norito(default)]` | გამოყენება `Default` როდესაც დეკოდირებული სასარგებლო ტვირთი არ ატარებს ველს. |
| `#[norito(skip_serializing_if = "...")]` | გამორიცხავს ველები JSON როდესაც პროდიკატები შეესაბამება, დეტერმინისტური დეკოდირების დეფოლტების შენარჩუნებისას. |

დერივები ასევე გამოფენს კოდირებული სიგრძის მინიშნებები და ზუსტი სიგრძის გათვლები, როდესაც
კოდერები იყენებენ ამ მითითებებს ბუფერების შესანახად და დამატებითი ასლების თავიდან აცილებისთვის.

## Torii და Norito RPC {#torii-and-norito-rpc}

Torii გამოხატული JSON ბევრი ოპერატორის მარშრუტისთვის, მაგრამ ტიპირებული ბინარული მარშრუტები გამოიყენება
Norito. მოწყობილობის ტიპი Norito HTTP სხეულები არის
`application/x-norito`.

გამოიყენეთ ეს სათაურები, როდესაც საბოლოო წერტილი იღებს ან ბრუნდება დაწერილი Norito:

```http
Content-Type: application/x-norito
Accept: application/x-norito
```

როდესაც საბოლოო წერტილი მხარს უჭერს ორივე წარმოდგენას, კლიენტებს შეუძლიათ გამოაგზავნონ მკაფიო
პრეფერენციების სია:

```http
Accept: application/x-norito, application/json
```

დეკოდირების ჩავარდნა გამოჩნდება როგორც არის დატანილი Torii შეცდომები და ტელემეტრიით გათვლილი.
გავრცელებული მიზეზები მოიცავს არასწორ მაგიას, დაუჭერილ ვერსიას, დაუჭირეს მხარს მახასიათებლებს
დროშა, შედარების არათანაბარი რაოდენობა, დეფორმირებული UTF-8, არასწორი enum tag და სქემა dismatch.

Norito RPC ტრანსპორტი შეირჩევა ტრანსპორტის კონფიგურაციის საშუალებით. ოპერატორი
დაშბორდებმა უნდა გამოიცნონ მოთხოვნის დაგვიანება, ჩავარდნები, აქტიური კავშირები;
რეაგირების ბაიტები და `torii_norito_decode_failures_total` ცალკე JSON
ტრეფიკი.

## საოპერაციო მიმართულებები {#operational-guidance}

- უპირატესობა SDK სამშენებლო და წარმოებული ბმულები ხელნაკეთი Norito ბაიტები.
- შეხედეთ სქემის შეუსაბამობას როგორც ვერსიას ან ჩართულობის პრობლემას და არა გარდამავალი
  ქსელის შეფერხება.
- შენარჩუნება `.nrt`, `.norito`, და გამოხატული არტეფაქტები გათავისუფლების ან ინციდენტის დროს
  ბუნდლი, რომელმაც ისინი შექმნა.
- გამოყენება JSON დაშბორდების პროექციები და სახელმძღვანელო ინსპექტირება, მაგრამ შეინახეთ Norito როგორც
  სიმართლის წყარო ხელმოწერილი, ჰაშირებული ან მუდმივი მონაცემებისთვის.
- ახალი ტიპირების დამატებისას Torii საბოლოო წერტილი, დოკუმენტი თუ ის იღებს JSON,
  Norito, ან ორივე, და გამოავლინოს მხარდაჭერილი შინაარსის ტიპები `/openapi`.
- აჩქარების ჩართვისას, გატარეთ პარიტეტის ტესტები სკალარული გამონადენის მიმართ ადრე
