# Norito {#norito}

Norito არის Iroha-ის კანონიკური სერიალიზაციის ფენა. ეს არის ბაიტების ფორმატი, რომელიც გამოიყენება მაშინ, როდესაც თანატოლებს, SDKs, CLI ინსტრუმენტებს, Torii, Kura და გენერირებულ არტეფაქტებს უნდა შეთანხმდნენ ზუსტად იმავე სასარგებლო ტვირთზე.

გამოიყენეთ Norito, როდესაც მონაცემები შედის კონსენსუსის, ხელმოწერის, ჰეშინგის, მდგრადობის ან SDK-ს ჯვარედინული ინტერპერაბილურობის ნაწილში. გამოიყენეთ JSON, როდესაც საბოლოო წერტილი პირდაპირ გვთავაზობს ადამიანის მიერ წაკითხილ პროექციას ოპერატორებისთვის, დაშბორტებისთვის ან სწრაფი დებეგირებისათვის.

## განლაგების დროშები {#layout-flags}

Norito ინახავს განლაგების არჩევანს საბოლოო სათაურის ბაიტში. შერჩეული v1-ის დამხმარეები გამოყოფენ `COMPACT_LEN` (`0x02`) კომპაქტური ღირებულების სიგრძის პრეფიქსებისთვის. მუდმივი სიღრმის ფსიქიკური სიგრძის წინამდებარეები კვლავ კითხვად რჩება, როდესაც მოუწოდებლები კოდირებენ `flags = 0x00`.

|დროშა |ჰექსი |სტატუსი |ეფექტი |
| --- | ---: | --- | --- |
|`PACKED_SEQ` |`0x01` |მხარდაჭერა |კოდირება ცვლადი ზომის კოლექციები ოფსეტის ცხრილთან და თანმიმდევარი მონაცემთა ბლოკთან ერთად. |
|`COMPACT_LEN` |`0x02` |დეფოლტი |გამოიყენება კანონიკური ხელმოუწერელი varints დიაპაზონის სიგრძის პრეფიქსებისათვის. |
|`PACKED_STRUCT` |`0x04` |მხარდაჭერა |კოდები გამომდინარე-გენერირებული structs როგორც შეფუთული ველის სასარგებლო ტვირთები. |

|`COMPACT_SEQ_LEN` |`0x10` |რეზერვებული |V1- ში უარყოფილია; უმაღლესი დონის რიგის სიგრძის სათაურები არის ფიქსირებული სიგანე `u64`. |
|`FIELD_BITSET` |`0x20` |მხარდაჭერა მოთხოვნებით |დაამატებს ბიტსეტს შეფუთული სტრუქტებისთვის, ასე რომ მხოლოდ ველები, რომლებიც საჭიროებენ მკაფიო ზომებს ატარებენ ზომის პრეფიქსებს. მოითხოვს `PACKED_STRUCT` და `COMPACT_LEN`. |

დროშები არის მკაფიო. დეკოდერები არ განსაზღვრავს განლაგებას სასარგებლო ტვირთის ფორმით, უმნიშვნელო ვერსიით ან ჰეურისტებით. უცნობი ან უვნებელი კომბინაციების უარყოფა ხდება, რათა ყველა თანატოლმა ინტერპრეტაცია გააკეთოს სასარგებლო დატვირთვა ერთნაირად .

## კოდირების წესები {#encoding-rules}

Norito იყენებს დეტერმინისტურ განლაგებებს მონაცემთა საერთო ფორმებისათვის, რომლებიც გამოჩნდება Iroha მონაცემთა მოდელში:

- მავთულხლართები არის `[len][utf8-bytes]`; `len` მოყვება `COMPACT_LEN`, როდესაც ჩართულია.
- როდესაც `COMPACT_LEN` არის განსაზღვრული, თითოეული მნიშვნელობის სიგრძე კომპაქტური ვარინტის გამოყენებით ხდება.
- როდესაც `COMPACT_LEN` არ არსებობს, თითოეული ღირებულების სიგრძე არის 8-ბაიტიანი პატარა ენდიანული `u64`.
- რიგითი სიგრძის სათაურები ფიქსირდება 8-ბაიტიანი მცირე ენდიან `u64` v1.
- `Vec<u8>` კოდირებულია როგორც `[len_u64][raw-bytes]` ერთ სიგრძის ნაცვლად ბაიტზე.
- შეფუთული თანმიმდევრობები იყენებენ `(len + 1)` მონოტონური `u64` კომპენსაციებს, რასაც მოჰყვება კონკატენირებული ელემენტის სასარგებლო ტვირთები.
- რუკაში ჩანაწერების დათვლის კოდირება ფიქსირებულია `u64` და გამოიყენება დეტერმინისტური საკვანძო რეჟიმი. `HashMap` ჩანაწერები განლაგებულია კოდირებამდე გასაღების მიხედვით; `BTreeMap` იყენებს მის ბუნებრივ რეჟიმს.
- `BigInt` იყენებს მცირე ზომის ორმაგი დანამატის ბაიტებს, რომელთა სიგრძე `u32` არის ბაიტი და 512-ბიტიანი საზღვერი.
- `Numeric` კოდირებულია როგორც `(mantissa, scale)`, სადაც mantissa ინახავს მთელი რიცხვის მნიშვნელობას და მასშტაბი ინახავს ფრაქციონალური ციფრების რაოდენობას.

ეს წესები მნიშვნელოვანია ხელმოწერებისა და ჰეშებისათვის. ორი SDKs რომელიც ქმნის ერთსა და იმავე ლოგიკურ ტრანზაქციას, უნდა წარმოადგინოს იგივე კანონიკური ბიტები.

## სქემის ჰაშები {#schema-hashes}

ტიპირებული Norito სასარგებლო დატვირთვები ატარებენ 16-ბაიტიან სქემას ჰეშს სათაურში. დეფოლტური ჰეში არის მიღებული სრულად კვალიფიციური ტიპის სახელისგან. ნაგებობები, რომლებიც ხელს უწყობენ სტრუქტურული სქემის ჰეშინგს, იღებენ ჰეშს კანონიკური სქემიდან.

ტიპირებული დეკოდერები უარყოფენ სქემის შეუსაბამობას. ეს იცავს კლიენტებს, რომ არასწორი Norito ჩარჩოს შეცდომით დეკოდირება არ მოხდეს და არის ჩვეულებრივი უკმარისობის რეჟიმი, როდესაც SDK მოწყობილობის ბუნდი დრიფტობს კვანძების მონაცემთა მოდელისგან.

## შეკუმშვა და დაჩქარება {#compression-and-acceleration}

Norito მხარს უჭერს მკაფიო და ადაპტიური შეკუმშვას, ლოგიკური სასარგებლო ტვირთის შეცვლის გარეშე:

|მახასიათებელი |მიზანი |
| --- | --- |
|`to_bytes` |კოდირებული სათაური, რომელსაც მოჰყვება არასაკომპრესირებული სასარგებლო ტვირთი. |
|`to_compressed_bytes` |კოდირება Zstd და ჩანაწერი compression tag in the header. |
|`to_bytes_auto` |გამოიყენეთ დეტერმინისტური ჰეურისტიკა, რათა გადაწყვიტოთ ღირს თუ არა კომპრესია. |
|CRC64 დაჩქარება |გამოიყენება პორტატული CRC64-XZ ყველგან, CLMUL on x86_64 ან PMULL on aarch64, როდესაც ხელმისაწვდომია |
|GPU CRC64 და შეკუმშვა |ნებაყოფლობითი მეტალის ან CUDA დამხმარე შეიძლება დააჩქაროს დიდი სასარგებლო ტვირთები, შემდეგ კი დაეცემა უკან CPU გზებზე. |

აპარატურის დაჩქარება არასოდეს იცვლის დეკოდირებულ შინაარსს. CRC და JSON აჩქარებლები უნდა შეესაბამებოდეს პორტაბულ გამომავალი ბიტ-ბიტს. Zstd ჩარჩოს ბაიტები შეიძლება განსხვავდებოდეს CPU და GPU კოდირებს შორის, მაგრამ დეკოდებული სასარგებლო ტვირთისა და Norito სათაურის მეტადატანი რჩება დეტერმინისტური მოწმობისთვის.

Norito მოიცავს მშობლიურ JSON დასასრული წერტილების და საჭირო ინსტრუმენტების საფარი JSON დატოვების გარეშე Norito ტიპის სისტემა.

## გამომდინარე მხარდაჭერა {#derive-support}

Rust მონაცემთა ტიპები, როგორც წესი, იყენებენ დერივულ მაკროებს და არა სახელმძღვანელო კოდეკის კოდს. დერივული ფენა შეიძლება წარმოქმნას Norito ორმაგი კოდეკები, სქემები და JSON დამხმარეები.

საერთო ველის ატრიბუტებია:

|ატრიბუტი |ეფექტი |
| --- | --- |
|`#[norito(rename = "other")]` |გამოიყენება სტაბილური სერიალიზებული სახელი სქემა და JSON თავსებადობისთვის. |
|`#[norito(skip)]` |კოდერი გამორიცხავს ველს. დეკოდერი მიაწოდებს მის `Default` მნიშვნელობას. |
|`#[norito(default)]` |გამოიყენება `Default`, როდესაც დეკოდირებული სასარგებლო ტვირთი არ ატარებს მინდორს |
|`#[norito(skip_serializing_if = "...")]` |გამორიცხავს ველებს JSON როდესაც predicate შეესაბამება, ხოლო შენარჩუნების დეტერმინისტური დეკოდირების დეფოლტები. |

დერივები ასევე გამოყოფენ კოდირებული სიგრძის მინიშნებებს და ზუსტი სიგრძის გამოთვლას, სადაც ეს შესაძლებელია. კოდერები იყენებენ ამ მინიშნებებს ბუფერების შესანახად და დამატებითი ასლების თავიდან ასაცილებლად.

## Torii და Norito RPC {#torii-and-norito-rpc}

Torii გამოყოფს JSON მრავალი ოპერატორის მარშრუტისათვის, მაგრამ ტიპირებული ორმაგი მარშრუტები იყენებენ Norito. მიმდინარე ტიპის Norito HTTP სხეულებისათვის მედია ტიპი არის `application/x-norito`.

გამოიყენეთ ეს სათაურები, როდესაც საბოლოო წერტილი იღებს ან იბრუნებს Norito ტიპით:

```http
Content-Type: application/x-norito
Accept: application/x-norito
```

როდესაც საბოლოო წერტილი მხარს უჭერს ორივე წარმოდგენას, კლიენტებს შეუძლიათ გამოაგზავნონ მკაფიო პრეფერენციების სია:

```http
Accept: application/x-norito, application/json
```

დეკოდირების ჩავარდნა გამოჩნდება როგორც Torii ტიპირებული შეცდომები და ითვლება ტელემეტრიით. გავრცელებულ მიზეზებს შორის არიან არასწორი ჯადოსნობა, დაუჭერელი ვერსია, მხარს არ უჭერს მახასიათებლების დროშა, შეამოწმებელი რაოდენობის შეუსაბამობა, არასწორად ჩამოყალიბებული UTF-8, არასწორი enum tag და სქემის შეუსაბამო.

Norito RPC ტრანსპორტი შეირჩევა ტრანსპორტის კონფიგურაციის საშუალებით. ოპერატორის დაშბორდებმა უნდა აკონტროლონ მოთხოვნის დაგვიანება, ჩავარდნები, აქტიური კავშირები, პასუხის ბიტები და `torii_norito_decode_failures_total` ცალკე JSON ტრაფიკიდან.

## საოპერაციო მიმართულებები {#operational-guidance}

- SDK მშენებლები და წარმოქმნილი ბმულები ხელნაკეთი დამზადებული Norito ბიტების ნაცვლად.
- განიხილეთ სქემის შეუსაბამობა როგორც ვერსია ან მოწყობილობის პრობლემა, და არა როგორც გარდამავალი ქსელის უკმარისობა.
- არქივი `.nrt`, `.norito` და მანიფესტური არტეფაქტები გათავისუფლების ან ინციდენტის ბუნდელში, რომელმაც ისინი გამოიწვია.
- გამოიყენეთ Norito როგორც სიმართლის წყარო ხელმოწერილი, ჰაშირებული ან შეჩერებული მონაცემებისთვის. გამოიყენეთ პროექციები JSON დაშბორდებისა და სახელმძღვანელო ინსპექტირებისათვის.
- ახალი ტიპირებული Torii საბოლოო წერტილის დამატებისას, დოკუმენტაცია იმის შესახებ, მიიღებს თუ არა ის JSON, Norito ან ორივე და გამოაქვეყნეთ მხარდაჭერილი შინაარსის ტიპები `/openapi`.
- სანამ აჩქარებელი გააქტიურებთ, შეამოწმეთ პარიტეტის ტესტები სკალარული გამომუშავების წინააღმდეგ. თუ აჩქარო ვერ გამოვა, გამოიყენეთ დეტერმინისტური სკალარული ჩავარდნა. სასარგებლო დატვირთვის სემანტიკა უნდა დარჩეს უცვლელი.
