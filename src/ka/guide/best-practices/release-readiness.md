# მზადყოფნა გათავისუფლებისთვის {#release-readiness}

Iroha აპლიკაციის ან ქსელის ცვლილების ხელშეწყობამდე, დაამტკიცეთ ქცევა ყველაზე პატარა გარემოში, რომელიც შეიძლება გამოავლინოს შესაბამისი რისკი, შემდეგ განზრახ გადაადგილება საერთო ტესტნეტისა და საწარმოო კარიბჭეების საშუალებით.

## ადგილობრივი ქსელის კარიბჭე {#localnet-gate}

- განახორციელეთ ერთჯერადი ადგილობრივი ქსელი იგივე Iroha ტრასით და უახლოესი პრაქტიკული ვალიდატორების რაოდენობით.
- განახორციელეთ ერთეულის ტესტები ტრანზაქციების შემქმნელებისთვის, შეკითხვების პარალიზება, უარყოფის მართვა და კონფიგურაციის დატვირთვა.
- უმცირესი წარმატებული წაკითხვისა და წერის გზების გამოყენება იმავე SDK ან CLI ფორმით, რომელსაც აპლიკაცია მოგვიანებით გამოიყენებს.
- დაფიქსირება მოსალოდნელი ტრანზაქციის კრიპტოგრაფიული ჰეშები, სტატუსები, მოვლენები და მდგომარეობის წაკითხვა ტესტის არტეფექტებში.

იხილეთ [გაშვება Iroha 3](/ka/get-started/launch-iroha.md) და [SDK მასწავლებლები](/ka/guide/tutorials/).

## საერთო ტესტნეტის კარიბჭე {#shared-testnet-gate}

- გამოიყენეთ Taira ან სხვა საერთო ტესტნეტი API საბოლოო წერტილის ქცევისთვის, საფასურებისთვის, ანგარიშის დაფინანსებისათვის, ლატენციისა და ოპერატიული რეპეტიციებისათვის.
- მოქმედ სატესტო ქსელში ჩაწერის ტესტები არჩევითი დატოვეთ, რათა ჩვეულებრივი ტესტები ქსელის ხელმისაწვდომობაზე არ იყოს დამოკიდებული და სატესტო თანხები არ ხარჯოს.
- დააკვირდით კრიპტოგრაფიული ხელმომწერი ფინანსებს, საფასური აქტივების მეტამონაცემებს, ავტორიზაციის ძირითად ნებართვებს და მოსალოდნელი მდგომარეობას თითოეული ცოცხალი ტესტის ტრანზაქციის წარდგენამდე.
- დაველოდოთ ტერმინალის სტატუსს, შემდეგ შეამოწმეთ მიღებული მდგომარეობა მხოლოდ კითხვაზე.

იხილეთ [SORA 3-ზე: Taira და Minamoto](/ka/get-started/sora-nexus-dataspaces.md).

## ძირითადი ქსელი ან საწარმოო კარი {#mainnet-or-production-gate}

- ცალკე გამოიყენეთ საწარმოო ხელმომწერები, თანხები, დომენები და კონფიგურაცია. სატესტო გასაღებები და გამცემზე დაფუძნებული ვარაუდები არ გადაიტანოთ.
- [თავსებადობის მატრიცით](/ka/reference/compatibility-matrix.md) დაადასტურეთ SDK-ებს შორის საჭირო სცენარები. ცალკე დააფიქსირეთ და შეამოწმეთ განთავსების მიერ გამოყენებული CLI-ის, კვანძის ბინარული ფაილის, კონფიგურაციისა და ქსელის გამოშვების ზუსტი ვერსიები.
- მიმოხილვის ნებართვები, საფასურის მხარდაჭერა, განაკვეთების ლიმიტები, მონიტორინგი, სარეზერვო სტატუსი და გადახდის კრიტერიუმები გამოშვების ფანჯრის წინ.
- მოითხოვეთ წერილობითი ტრანზაქციის ან მიგრაციის გეგმა მაღალი გავლენის მქონე წერილებისთვის.

## უკან დაბრუნება და აღდგენა {#rollback-and-recovery}

- განსაზღვრეთ, რომელი ცვლილებები შეიძლება გადაიხადოს კოდის დანერგვის საშუალებით, რომლებიც მოითხოვს ქსელზე ჩატარებულ ტრანზაქციას და რომელიც არ შეიძლება უშუალოდ განმეორდეს.
- ქსელზე არსებული მონაცემთა ცვლილებებისთვის, მომზადება კომპენსაციური ტრანზაქციების ან მიგრაციის სკრიპტები პირველი წარმოების წერამდე.
- ქსელის ცვლილებებისთვის, შეინახეთ წინა ბინარი, კონფიგურაციის ბუნდი, ხელმოწერილი ბლოკჩეინის გენეზისი და ოპერაციული საოპერაციო ინსტრუქცია ხელმისაწვდომია გამოშვების დროს.
- დაადგინეთ გადაწყვეტილების წერტილი განთავსების შეწყვეტისათვის ისეთი ობიექტური სიგნალების საფუძველზე, როგორიცაა უარყოფის მაჩვენებელი, რიგების ზრდა, დაგვიანება ან ქსელის კვანძთა ჯანმრთელობა.

## საბოლოო შეამოწმების სია {#final-checklist}

- კონფიგურაცია არის გარემოს სპეციფიკური და არ შეიცავს მხოლოდ ტესტის საიდუმლოებებს.
- ტრანზაქციის განმეორებითი მცდელობის ქცევა შეუძლებელია ან მკაფიოდ არის შეზღუდული.
- აპლიკაციაში შესაძლებელია განასხვავოს უარყოფის, ვადის ამოწურვის, ვადაგამოშვების და API საბოლოო წერტილის ხელმისაწვდომობის არარსებობა.
- მონიტორინგი მოიცავს გამტარობას, დაგვიანებას, რიგის სიღრმეს, უარყოფას, განხილვის ცვლილებებს და შესაბამის ბიზნეს მოვლენებს.
- ოპერატორებს აქვთ გაშვების წიგნები მოსალოდნელი ჩავარდნის რეჟიმებისთვის.
- უსაფრთხოების მიმოხილვა მოიცავდა საკვანძოების დაცვას, ნებართვებს, ქსელის ექსპოზიციას და ავტომატიზაციის ავტორიზაციის პრინციპს.
