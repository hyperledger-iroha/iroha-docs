# მზადყოფნა გათავისუფლებისთვის {#release-readiness}

Iroha აპლიკაციის ან ქსელის ცვლილების ხელშეწყობამდე, დაამტკიცეთ ქცევა ყველაზე პატარა გარემოში, რომელიც შეიძლება გამოავლინოს შესაბამისი რისკი, შემდეგ განზრახ გადაადგილება საერთო ტესტნეტისა და საწარმოო კარიბჭეების საშუალებით.

## ადგილობრივი ქსელის კარიბჭე {#localnet-gate}

- განახორციელეთ ერთჯერადი ადგილობრივი ქსელი იგივე Iroha ტრასით და უახლოესი პრაქტიკული ვალიდატორების რაოდენობით.
- განახორციელეთ ერთეულის ტესტები ტრანზაქციების შემქმნელებისთვის, შეკითხვების პარალიზება, უარყოფის მართვა და კონფიგურაციის დატვირთვა.
- უმცირესი წარმატებული წაკითხვისა და წერის გზების გამოყენება იმავე SDK ან CLI ფორმით, რომელსაც აპლიკაცია მოგვიანებით გამოიყენებს.
- დაფიქსირება მოსალოდნელი ტრანზაქციის hashes, სტატუსები, მოვლენები და მდგომარეობის წაკითხვა ტესტის არტეფაქტებში.

იხილეთ [გადაშვება Iroha 3](/ka/get-started/launch-iroha.md) და [SDK სახელმძღვანელოები ](/ka/guide/tutorials/).

## საერთო ტესტნეტის კარიბჭე {#shared-testnet-gate}

- გამოიყენეთ Taira ან სხვა საერთო ტესტნეტი საბოლოო წერტილის ქცევისთვის, საფასურებისთვის, ანგარიშის დაფინანსებისათვის, ლატენციისა და ოპერატიული რეპეტიციებისათვის.
- Keep live testnet წერს opt-in, ასე რომ ჩვეულებრივი ტესტირება არ არის დამოკიდებული ქსელის ხელმისაწვდომობაზე ან ხარჯავს testnet ფონდები.
- შეამოწმეთ ხელმომწერის დაფინანსება, საფასური აქტივების მეტა მონაცემები, უფლებამოსილების ნებართვები და მოსალოდნელი მდგომარეობა თითოეული ცოცხალი ტესტის ტრანზაქციის წარდგენის წინ.
- დაველოდოთ ტერმინალის სტატუსს, შემდეგ შეამოწმეთ მიღებული მდგომარეობა მხოლოდ კითხვაზე.

იხილეთ [აწყობა SORA 3: Taira და Minamoto](/ka/get-started/sora-nexus-dataspaces.md).

## ძირითადი ქსელი ან საწარმოო კარი {#mainnet-or-production-gate}

- გამოიყენეთ ცალკეული საწარმოო ხელმოწერები, დაფინანსება, დომენები და კონფიგურაციის გზები. არ გააქტიუროთ ტესტნეტის გასაღები ან საბანქის ვარაუდები.
- დაადასტურეთ საჭირო SDK სცენარები [ თავსებადობის მატრიკით](/ka/reference/compatibility-matrix.md). ცალკე დააჭირეთ და შეამოწმეთ ზუსტი CLI, პარტნიორული ბინარი, კონფიგურაცია და ქსელის გამოშვება, რომელიც გამოიყენება განთავსებისას.
- მიმოხილვის ნებართვები, საფასურის მხარდაჭერა, განაკვეთების ლიმიტები, მონიტორინგი, სარეზერვო სტატუსი და გადახდის კრიტერიუმები გამოშვების ფანჯრის წინ.
- მოითხოვეთ წერილობითი ტრანზაქციის ან მიგრაციის გეგმა მაღალი გავლენის მქონე წერილებისთვის.

## უკან დაბრუნება და აღდგენა {#rollback-and-recovery}

- განსაზღვრეთ, რომელი ცვლილებები შეიძლება გადაიხადოს კოდის დანერგვის საშუალებით, რომლებიც მოითხოვს ქსელზე ჩატარებულ ტრანზაქციას და რომელიც არ შეიძლება უშუალოდ განმეორდეს.
- ქსელზე არსებული მონაცემთა ცვლილებებისთვის, მომზადება კომპენსაციური ტრანზაქციების ან მიგრაციის სკრიპტები პირველი წარმოების წერამდე.
- ქსელის ცვლილებებისთვის, გათავისუფლების დროს ხელმისაწვდომი უნდა იყოს წინა ორმაგი, კონფიგურაციის ბუნდი, ხელმოწერილი გენეზი და ოპერაციული რუნბუქი.
- დაადგინეთ გადაწყვეტილების წერტილი განთავსების შეწყვეტისთვის ობიექტური სიგნალების საფუძველზე, როგორიცაა უარყოფის მაჩვენებელი, რიგის ზრდა, დაგვიანება ან თანატოლთა ჯანმრთელობა.

## საბოლოო შეამოწმების სია {#final-checklist}

- კონფიგურაცია არის გარემოს სპეციფიკური და არ შეიცავს მხოლოდ ტესტის საიდუმლოებებს.
- ტრანზაქციის განმეორებითი მცდელობის ქცევა შეუძლებელია ან მკაფიოდ არის შეზღუდული.
- აპლიკაციას შეუძლია განასხვავოს უარყოფის, ვადის ამოწურვის, ვადაშეზღუდვისა და საბოლოო წერტილების ხელმისაწვდომობის არარსებობა.
- მონიტორინგი მოიცავს გამტარობას, დაგვიანებას, რიგის სიღრმეს, უარყოფას, განხილვის ცვლილებებს და შესაბამისი ბიზნეს მოვლენებს.
- ოპერატორებს აქვთ გაშვების წიგნები მოსალოდნელი ჩავარდნის რეჟიმებისთვის.
- უსაფრთხოების მიმოხილვა მოიცავდა საკვანძო მფარველობას, ნებართვებს, ქსელის ექსპოზიციას და ავტომატიზაციის ორგანოს.
