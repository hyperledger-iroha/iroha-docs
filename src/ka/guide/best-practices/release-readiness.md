# მზადყოფნა გათავისუფლებისთვის {#release-readiness}

წინასაარჩევნო Iroha აპლიკაცია ან ქსელის ცვლილება, დაამტკიცეთ ქცევა
ყველაზე პატარა გარემოში, რომელიც შეიძლება გამოავლინოს შესაბამისი რისკი, შემდეგ გადაადგილება
საერთო სატესტო ქსელის და წარმოების კარიბჭეების საშუალებით მიზანმიმართულად.

## ადგილობრივი ქსელის კარიბჭე {#localnet-gate}

- გაუშვით ერთჯერადი ადგილობრივი ქსელი იმავე Iroha ტრეკი და
  ყველაზე ახლო პრაქტიკული ვალიდატორების რაოდენობა.
- ტესტირების გატარება ტრანზაქციების შემქმნელებისთვის, შეკითხვების ანალიზება, უარყოფა
  მენეჯმენტი და კონფიგურაცია გადატვირთვა.
- წვრთნი ყველაზე პატარა წარმატებული კითხვა და წერა გზები ერთად
  SDK ან CLI ფორმა, რომელსაც აპლიკაცია მოგვიანებით გამოიყენებს.
- დაფიქსირება მოსალოდნელი ტრანზაქციის hashes, სტატუსები, მოვლენები და მდგომარეობა კითხულობს
  საცდელი არტეფაქტები.

იხილეთ [გაშვება Iroha 3](/ka/get-started/launch-iroha.md) და
[SDK მასწავლებლები](/ka/guide/tutorials/).

## საერთო ტესტნეტის კარიბჭე {#shared-testnet-gate}

- გამოყენება Taira ან სხვა საერთო ტესტნეტი საბოლოო პუნქტის ქცევებისთვის, საფასურებისათვის, ანგარიშისთვის
  დაფინანსება, დაგვიანება და ოპერატიული რეპეტიციები.
- Keep live testnet წერს opt-in ასე რომ ჩვეულებრივი ტესტი run არ დამოკიდებულია
  ქსელის ხელმისაწვდომობა ან ტესტნეტის ფონდების ხარჯვა.
- შეამოწმეთ ხელმომწერის დაფინანსება, საფასურის აქტივების მეტა მონაცემები, უფლებამოსილების ნებართვა და
  მოსალოდნელი სტატუსი თითოეული ცოცხალი ტესტის ტრანზაქციის წარდგენის წინ.
- დაველოდოთ ტერმინალურ მდგომარეობას, შემდეგ შეამოწმეთ მიღებული მდგომარეობა
  მხოლოდ წაკითხვის მიზნით.

იხილეთ
[აგრეთვე დაიწყე SORA 3: Taira და Minamoto](/ka/get-started/sora-nexus-dataspaces.md).

## მთავარი ქსელი ან წარმოების კარი {#mainnet-or-production-gate}

- გამოიყენეთ ცალკე წარმოების ხელმოწერები, დაფინანსება, დომენები და კონფიგურაციის გზები. გააკეთეთ
  ტესტნეტის გასაღები ან საფანქნის ვარაუდების ხელშეწყობა არ უნდა მოხდეს.
- დადასტურება SDK, CLI, პერისა და ქსელის თავსებადობა
  [შეთანხმების მატრიცა](/ka/reference/compatibility-matrix.md).
- განხილვის ნებართვები, საფასურის მხარდაჭერა, საფასურების ლიმიტები, მონიტორინგი, სარეზერვო უზრუნველყოფა
  სტატუსი და უკან დაბრუნების კრიტერიუმები გათავისუფლების ფანჯრის წინ.
- მოითხოვეთ წერილობითი ტრანზაქციის ან მიგრაციის გეგმა მაღალი გავლენის მქონე წერილებისთვის.

## უკან დაბრუნება და აღდგენა {#rollback-and-recovery}

- განსაზღვრეთ, თუ რა ცვლილებები შეიძლება მოხდეს კოდის განთავსების შედეგად
  ქსელზე განხორციელებული ტრანზაქცია, რომლის უშუალოდ გაუქმება შეუძლებელია.
- ქსელზე არსებული მონაცემთა ცვლილებისთვის, მომზადება კომპენსაციური ტრანზაქციების ან მიგრაციისათვის
  სცენარები პირველი წარმოების დაწერამდე.
- ქსელის ცვლილებებისთვის, შეინახეთ წინა ბინარული, კონფიგურაციის ბუნდი, გაფორმებული
  გენეზი და ოპერაციული რუნბუქი ხელმისაწვდომია გათავისუფლების დროს.
- განსაზღვრეთ გადაწყვეტილების პუნქტი, რომელიც ობიექტური სიგნალების საფუძველზე გააჩენს გადაწყობის შეწყვეტას.
  ისეთი, როგორიცაა უარყოფის მაჩვენებელი, რიგების ზრდა, დაგვიანება ან თანატოლთა ჯანმრთელობა.

## საბოლოო შეამოწმების სია {#final-checklist}

- კონფიგურაცია გარემოსთვის სპეციფიკური და არ შეიცავს მხოლოდ გამოცდებს
  საიდუმლოები.
- ტრანზაქციის განმეორებითი მცდელობის ქცევა უძლურია ან მკაფიოდ არის შეზღუდული.
- აპლიკაცია შეუძლია განასხვავოს უარყოფა, ვადის ამოწურვა, ვადა და საბოლოო წერტილი
  ხელმისაწვდომობის შეფერხებები.
- მონიტორინგი მოიცავს გამტარობას, დაგვიანებას, რიგის სიღრმეს, უარყოფას, ნახვას
  ცვლილებები და შესაბამისი ბიზნეს მოვლენები.
- ოპერატორებს აქვთ გაშვების წიგნები მოსალოდნელი ჩავარდნის რეჟიმებისთვის.
- უსაფრთხოების გადამოწმება მოიცავდა საკვანძო მფარველობას, ნებართვებს, ქსელის ექსპოზიციას და
  ავტომატიზაციის ორგანო.
