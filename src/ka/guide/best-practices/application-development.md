# აპლიკაციების განვითარება {#application-development}

Iroha აპლიკაციებმა უნდა გააკეთონ ტრანზაქციის ქცევა მკაფიოდ, გააგრძელეთ ხელმოწერა
და გამოიყენეთ კითხვები და მოვლენები გზით, რომელიც ადვილია
წარმოების დროს შეინიშნება.

## მომხმარებლის პარამეტრები {#client-setup}

- შეინახეთ კლიენტის კონფიგურაცია პროგრამის წყარო კოდის გარეთ.
  ჯაჭვი ID, Torii URL, ხელმოწერის ანგარიში და ტრანზაქციის პარამეტრები
  გარემოს სპეციფიკური კონფიგურაცია.
- შენარჩუნება `client.toml` ცალკე ფაილები localnet-ისთვის, Taira, Minamoto, და
  კერძო ქსელები. გადაწერილი სატესტო ქსელის ხელმომწერები არასდროს უნდა გახდნენ ძირითადი ქსელი
  მწერალი.
- განზრახ დაწესებული ოპერაციების ხანგრძლივობა და სტატუსის დრო. ძალიან მოკლე
  სიცოცხლე შეიძლება დასრულდეს ნორმალური ქსელის jitter, ხოლო ძალიან გრძელი
  შეიძლება ორმაგი წარდგენები უფრო რთული იყოს დასაბუთება.
- გამოყენება `nonce = true` მხოლოდ იმ შემთხვევაში, თუ განმეორებითი ოპერაციები უნდა ჰქონდეს განსხვავებული
  ჰაშები. უპატენტო ბიზნეს ოპერაციებისათვის, ინახეთ და განმეორებით გამოიყენეთ
  განაცხადის თხოვნა ID მაშ, შემდგომი მცდელობები თვალსაჩინო იქნება.

იხილეთ [კლიენტის კონფიგურაცია](/ka/guide/configure/client-configuration.md) სამედიცინო
მიმდინარე TOML ველები.

## ოპერაციები {#transactions}

- შექმნას ტრანზაქციები ტიპირებული SDK ინსტრუქციები, სადაც შესაძლებელია, ნაცვლად
  ნედლეული JSON ან ძროხებით დამონტაჟებული სასარგებლო ტვირთები.
- პრეფლიტ-მნიშვნელოვანი წერს მხოლოდ კითხვაზე: ანგარიშის არსებობა,
  აქტივების ბალანსი, ნებართვის მდგომარეობა, საფასური აქტივების ხელმისაწვდომობა და მიზანი
  საგნის მდგომარეობა.
- ჩაწერეთ ტრანზაქციის ჰეში, ავტორიტეტის ანგარიში, ინსტრუქციების შეჯამება და
  მოსალოდნელი სახელმწიფო ცვლილება წარდგენამდე.
- მკურნალობა `Rejected`, `Expired`, და დროის შედეგი განსხვავდება.
  ნიშნავს, რომ კლიენტმა საბოლოო სტატუსი არ დააკვირდა; ეს არ ადასტურებს, რომ
  ქსელმა ტრანზაქცია უგულებელყო.
- წარმატებული დაწერის შემდეგ, შეამოწმეთ მიღებული მდგომარეობა გამოკითხვით ან
  მოვლენების შემოწმების პუნქტი, რომელიც შეესაბამება ბიზნეს ოპერაციას.

ტრანზაქციების მექანიკისთვის იხილეთ [ოპერაციები](/ka/blockchain/transactions.md).

## კითხვები და მოვლენები {#queries-and-events}

- გამოიყენეთ შეკითხვები მიმდინარე მდგომარეობისა და მოვლენების ნაკადებისთვის ცვლილებების ცნობისთვის.
  მოერიდეთ მოვლენების მართვის შეცვლას განმეორებით ფართო კითხვებით.
- გვერდების ფართო iterable queries, როგორიცაა ანგარიში, აქტივი და ბლოკი
  სიები.
- უპირატესობა აქვს ვიწრო ფილტრებს აბონენტებისა და გამომწვევებისთვის. ფართო ფილტრები არის
  სასარგებლო დიაგნოსტიკისთვის, მაგრამ შეიძლება დამატდეს ზედმეტი შესრულება და კლიენტის მხრიდან
  დამუშავება.
- გაითვალისწინეთ, რომ მხოლოდ წაკითხული სიგარეტის კონტროლი განცალკევებულია ხელმოწერილი ტრანზაქციული ტესტებისგან.
  დასასრული პუნქტის ხელმისაწვდომობა უფრო ადვილია დიაგნოზის გაკეთება.

იხილეთ [კითხვები](/ka/blockchain/queries.md), [მოვლენები](/ka/blockchain/events.md), და
[ფილტრები](/ka/blockchain/filters.md).

## სააგენტო დახმარებით განვითარება {#agent-assisted-development}

- ეა ჟვ ოპაგპვნთ ჟოპჲქს. SDK კოდი, და მხოლოდ წაკითხვის ქსელის სტატუსი
  თმამ მათ ტრანზაქციული კოდი დაწერონ.
- შეინახეთ ცოცხალი ქსელის ტესტები opt-in გარემოს დროშის უკან, როგორიცაა
  `TAIRA_LIVE=1`.
- არ ჩაკეცი კერძო გასაღები, ანგარიშის აღდგენის მასალა, API ქაღალდები ან
  ავტორის სათაურები გადაიგზავნა შეტყობინებებში.
- მოითხოვეთ ტრანზაქციის გეგმა, სანამ რომელიმე აგენტი პირდაპირი ტესტნეტს წარადგენს
  გეგმა უნდა დაასახელოს ქსელი, ორგანო, ინსტრუქცია,
  საფასურის აქტივი, ფრენის წინასწარი წაკითხვა, მოსალოდნელი შედეგი და განმეორებითი მცდელობის ქცევა.

სამინისტროში Taira MCP სამუშაო მიმდინარეობა, იხილეთ
[აგრეთვე დაიწყე SORA 3: Taira და Minamoto](/ka/get-started/sora-nexus-dataspaces.md#taira-mcp-for-agents).

## SDK ჰიგიენა {#sdk-hygiene}

- ფანქარი SDK და ორმაგი ვერსიები ერთად გამოყენებით
  [შეთანხმების მატრიცა](/ka/reference/compatibility-matrix.md).
- შეინარჩუნეთ გენერირებული კლიენტის კოდი, ნაწყვეტები და მაგალითები სინქრონიზებულია
  სამუშაო სივრცის გადახედვა.
- დამატება ერთეულის ტესტები ტრანზაქციების კონსტრუქციის კოდისა და ინტეგრაციის ტესტებისათვის
  ყველაზე პატარა წაკითხვის და წერის გზები თქვენი განაცხადი დამოკიდებულია.
