# ვირტუალური კერძო ქსელები {#virtual-private-networks}

<abbr title="Virtual Private Network">VPN</abbr> არის ქსელის კონტროლი, რომელიც ზღუდავს იმას, თუ ვის შეუძლია მიაღწიოს Iroha სერვისებს. ის ყველაზე სასარგებლოა კერძო და კონსორციუმის განთავსებისთვის, სადაც ვალიდატორები, აპლიკაციების უკანასკნელი მხარეები და ოპერატორები უნდა კომუნიკაცია პირადი მისამართებზე ღია ინტერნეტ მარშრუტების ნაცვლად.

VPN არ ჩაანაცვლებს Iroha ქსელის კვანძის გასაღები, ანგარიშის გასაღებები, ნებართვები, ფაირვუალის წესები, მონიტორინგი ან უსაფრთხო გასაღების შენახვა. განიხილეთ იგი როგორც ერთი ფენა  განთავსების საზღვარი: VPN შეამცირებს ქსელის ხელმისაწვდომობას, ხოლო Iroha კონფიგურაცია და მმართველობა წყვეტს რომელი ქსელური პარტნიორები და ანგარიშები არიან ნდობითი.

## როდის გამოიყენოთ VPN {#when-to-use-a-vpn}

გამოიყენეთ VPN როდესაც:

- დამტკიცებლები სხვადასხვა ორგანიზაციების მიერ ან სხვადასხვა ჰოსტინგის გარემოში ფუნქციონირებს
- Torii უნდა იყოს ხელმისაწვდომი მხოლოდ აპლიკაციების ბეკენდი-ების, ოპერატორების ან სანდო კლიენტებისათვის.
- მაჩვენებლები, ლოგები, SSH ან სხვა ადმინისტრაციის API საბოლოო წერტილები უნდა დარჩეს კერძო ოპერატორის ქსელში.
- საცდელი ან ეტაპობრივი ქსელი უნდა ჰგავდეს წარმოების წვდომის კონტროლს, საჯარო API საბოლოო წერტილების გაშუქების გარეშე.

VPN არ არის საჭირო ყველა განთავსებისთვის. საჯარო ქსელებს შეუძლიათ მიზანმიმართულად გამოავლინონ Torii საჯარო კარიბჭის, დატვირთვის ბალანსერის ან რევერსული პროქციის მეშვეობით. ამ შემთხვევაშიც კი, შეინარჩუნეთ ვალიდატორი პიერ-ტა-პიერ მოძრაობისა და ადმინისტრირების ბოლო წერტილები API შეზღუდულ ქსელში ყოველთვის, როდესაც ეს შესაძლებელია.

::: tip

ბრაუზერი VPN იცავს მხოლოდ იმ ბრაუზის ტრაფიკს. იგი არ იცავს `iroha3d`, CLI, SDK, SSH, მეტრიკებს ან სარეზერვო ტრაფიკს, თუ ეს პროცესები არ არის გადაყვანილი იმავე კერძო ქსელში.

:::

## განთავსების ნიმუში {#deployment-pattern}

კერძო ვალიდატორის ქსელისათვის, მიუთითეთ თითოეულ ვალიდატორს სტაბილური VPN მისამართი ან კერძო DNS სახელწოდება. კონფიგურირეთ ქსელური პერები ისე, რომ მათი რეკლამირებული პერ-დან-პერის მისამართები ხელმისაწვდომი იყოს სხვა ვალიდატორიდან ამ ქსელში:

```toml
trusted_peers = [
  "PUBLIC_KEY_1@10.20.0.11:1337",
  "PUBLIC_KEY_2@10.20.0.12:1337",
  "PUBLIC_KEY_3@10.20.0.13:1337",
  "PUBLIC_KEY_4@10.20.0.14:1337",
]

[network]
address = "10.20.0.11:1337"
public_address = "10.20.0.11:1337"

[torii]
address = "10.20.0.11:8080"
```

გამოიყენეთ მიმდინარე ქსელის პარისთვის დანიშნული მისამართი `network.address` და `network.public_address`. თითოეულმა ქსელურმა პარმა უნდა ჩამოთვალოს იგივე საიმედო ქსელის პარების იდენტობა, მაგრამ მისამართებით, რომლებიც ხელმისაწვდომია საკუთარი VPN მარშრუტის ცხრილიდან.

კლიენტის და CLI კონფიგურაციების მიმართულება უნდა მიუთითებდეს Torii API საბოლოო წერტილს, რომლის მიღწევა შესაძლებელია VPN ან კონტროლირებადი შიდა კარიბჭის მეშვეობით:

```toml
torii_url = "http://10.20.0.11:8080"
```

თუ Torii უნდა იყოს ხელმისაწვდომი VPN-ის გარეთ, დააყენეთ იგი სათადარიგო პროქსის ან დატვირთვის ბალანსერის უკან, რომელიც უზრუნველყოფს TLS-ის ავთენტიფიცირებას, განაკვეთების შეზღუდვას და ჩანაწერებს. თავიდან აიცილეთ ნედლი პორტების ან ადმინისტრირების API საბოლოო წერტილების პირდაპირი გამოფენა საზოგადოებრივ ინტერნეტში .

## ცეცხლსასროლი კედლების წესები {#firewall-rules}

გამოიყენეთ ჰოსტისა და ღრუბლის ფაირვუალის წესი მაშინაც კი, როდესაც VPN არის:

|მომსახურება |რეკომენდებული წვდომა |
| --- | --- |
|პორტი "პერ-ტო-პერ"|სხვა ვალიდატორი VPN მხოლოდ მისამართით |
|Torii |აპლიკაციების ბაქტენდები, ოპერატორები ან საიმედო კლიენტები VPN |
|მეტრიკები და ჯანმრთელობის კონტროლი |ოპერატორის ქსელზე მონიტორინგის სისტემები |
|SSH და ადმინისტრაცია |ბასტიონური ჰოსტი, პრივილეგირებული ოპერატორი VPN დიაპაზონი ან მინის დაშლის პროცესი |
|სათადარიგოები და შენახვის რეპლიკა |სათადარიგო სისტემები კერძო ქსელში |

დეფალტის უარყოფის წესები უფრო ადვილია აუდიტირება, ვიდრე ფართო ნებართვის წესები. როდესაც ახალი ქსელის კვანძები შეუერთდებიან ქსელს, განახლება VPN წევრობა, ქსელური ეკრანი ნებართვების სია და Iroha საიმედო ქსელი თანატოლების კონფიგურაცია როგორც ერთი კოორდინირებული ცვლილება.

## ოპერაციული კონტროლის სია {#operational-checklist}

- აირჩიეთ აუდიტირებული და აქტიურად მოთავსებული VPN დანერგვა, როგორიცაა WireGuard, IPsec ან ორგანიზაციის მიერ დამტკიცებული მართული კერძო ქსელი.
- გამოიყენეთ უნიკალური VPN საკრედიტაციო მონაცემები თითოეული მასპინძლისა და ოპერატორისთვის. არ გაიზიაროთ VPN გასაღებები ვალიდატორებს შორის.
- შეინახეთ VPN საკრედიტაციო მონაცემები ცალკე Iroha კერძო გასაღებებიდან და ბლოკჩეინის გენეზის ხელმოწერის მასალა.
- მონიტორინგი VPN ლეტენცია, პაკეტის დაკარგვა, ხელახლა კავშირები და მარშრუტის ცვლილებები. კონსენსუსი მგრძნობიარეა ქსელის არასტაბილურობისთვის.
- შეამოწმეთ ეფექტური MTU. პაკეტის ფრაგმენტაცია შეიძლება გამოიყურებოდეს როგორც ინტერმიტაციული ქსელის პარების ან Torii ჩავარდნის.
- დოკუმენტი, რომლის ფარგლებშიც VPN-ის დიაპაზონები მიაღწევს Torii, მეტრიკებს, SSH და სათადარიგო საბოლოო წერტილებს API.
- VPN სანებართვო მონაცემების ბრუნვა, როდესაც ჰოსტი, ოპერატორის ანგარიში ან ორგანიზაცია ტოვებს ქსელს.
- ავიცილეთ ერთი VPN კარიბჭე, როგორც ერთადერთი მარშრუტი ვალიდატორებს შორის. დაგეგმეთ ზედმეტი კარიბხეები ან საწარმოო ქსელების საიტიდან საიტის მიმართულებები.
- ჩართეთ VPN შეფერხებები ინციდენტის რეაგირების წვრთნებში, რათა ოპერატორებმა იცოდნენ, როდის უნდა განასხვავონ ქსელური პარტიცია Iroha პროცესის შეფერხებით.
