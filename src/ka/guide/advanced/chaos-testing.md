# ქაოსის ტესტირება იზანამი-მთან ერთად {#chaos-testing-with-izanami}

იზანამი არის ქაოსნეტის ორკესტრატორი ზემო ნაკადში Iroha სამუშაო სივრცე.
იწყებს ერთჯერადი ადგილობრივი Iroha კლასტერი, წარუდგენს კონფიგურებადი სამუშაო დატვირთვას;
და ინექციებს ხარვეზებს შერჩეულ თანატოლებში, რათა ოპერატორებმა შეძლონ შეამოწმონ თუ არა
ქსელი განაგრძობს პროგრესს კონტროლირებადი ჩავარდნის დროს.

გამოიყენეთ Izanami წარმოების წინასწარი გამძლეობის შემოწმებისთვის, რეგრესიული რეპროდუქციისთვის,
და კონსენსუსის ატონირება. არ მიუთითოთ მას საწარმოო ქსელზე: ინსტრუმენტი არის
შექმნილია იმისათვის, რომ ჰქონდეს პარები, რომელიც იწყება, მათ შორის პარების განახლება, შენახვა
საფარი, ხელოვნური შეტაკების დაკარგვა და ადგილობრივი CPU ან დისკის წნეხი.

## წინაპირობები {#prerequisites}

იზანამი გაუშვით
[Iroha წყარო რეპოზიტორი](https://github.com/hyperledger-iroha/iroha),
ამ დოკუმენტაციის რეპოზიტორიდან არ არის:

```bash
git clone https://github.com/hyperledger-iroha/iroha.git
cd iroha
cargo build -p izanami
```

ბინარი უნდა იყოს ხაზგასმული ნებადართული შექმნას და მანიპულაცია ქსელური
ჟრამჲპარა. `--allow-net` თითოეული არა-TUI გაშვება ან ჩართვა `allow_net` დაწვრილებით
დასახელება TUI.

```bash
cargo run -p izanami -- --allow-net --peers 4 --faulty 1 --duration 120s
```

ინტერაქტიული გაშვების კონფიგურაციისათვის:

```bash
cargo run -p izanami -- --tui --allow-net
```

იზანამი აგრძელებს. TUI და CLI მომხმარებლის კონფიგურაციის დირექტორის ქვეშ არსებული პარამეტრები, ასე რომ
განახორციელოს წარდგენილი პარამეტრების გადახედვა წინა პროფილის ხელმეორედ გამოყენებამდე.

## საწყისი ხაზის გატარება {#baseline-run}

დაიწყეთ ერთი რეპროდუქციული საწყისი ხაზით, სანამ სერიოზულ ხარვეზებს დაამატებთ:

```bash
cargo run -p izanami -- \
  --allow-net \
  --peers 4 \
  --faulty 1 \
  --duration 5m \
  --target-blocks 100 \
  --progress-interval 15s \
  --progress-timeout 120s \
  --latency-p95-threshold 2s \
  --tps 15 \
  --max-inflight 32 \
  --submitters 1 \
  --seed 42
```

ეს გაშვება წარმატებულია მხოლოდ იმ შემთხვევაში, თუ კლასტერმა მიაღწია მოთხოვნილ ბლოკის მიზანს,
შეზღუდული დროის განმავლობაში პროგრესს განაგრძობს და რჩება პორტალური p95 ქვეშ
ბლოკის ინტერვალის ზღვარი.

დაწერე ბრძანება, შვილო. Iroha დანაშაული, თანატოლების რაოდენობა, არასწორი თანატოლთა რაოდენობა,
სამუშაო დატვირთვის პროფილი, მიზანი TPS, და ლეტენციის ზღვარი ჩანაწერებთან ერთად.
ამ მნიშვნელობებზე, სხვა ოპერატორს არ შეუძლია გაიმეოროს იგივე წარუმატებლობის მოდელი.

## სამუშაო დატვირთვის პროფილი {#workload-profiles}

Izanami-ს აქვს ორი სამუშაო დატვირთვის პროფილი:

| პროფილი  | გამოიყენეთ იგი                                         | შენიშვნები                                  |
| -------- | -------------------------------------------------- | -------------------------------------- |
| `stable` | ხანგრძლივი სარეაბილიტაციო რეჟიმები და განმეორებადი შესრულების შემოწმება | სასურველი რეცეპტები          |
| `chaos`  | დაფარვის საფრთხე                              | შეიცავს განზრახ არასწორ რეცეპტებს |

ჯერ გამოიყენეთ სტაბილური პროფილი:

```bash
cargo run -p izanami -- --allow-net --workload-profile stable --seed 42
```

გადასვლა ქაოსის პროფილისკენ, როდესაც საწყისი ხაზია უკვე გასაგებია:

```bash
cargo run -p izanami -- --allow-net --workload-profile chaos --seed 42
```

კონტრაქტის განთავსების რეცეპტები სტაბილურ მიმდინარეობებში გამორთულია, თუ ეს არ არის ნათლად
დასაშვებია:

```bash
cargo run -p izanami -- \
  --allow-net \
  --workload-profile stable \
  --allow-contract-deploy-in-stable
```

გამოყენება `--nexus` როდესაც გაშვება უნდა გამოიყენოს ჩაშენებული SORA Nexus დეფოლტები
სამუშაო სივრცე ზემოთ.

## შეცდომების კონტროლი {#fault-controls}

როდესაც `--faulty` 0-ზე მეტია, მინიმუმ ერთი სცენარი უნდა იყოს
ჩართულია. შეცდომა ჩართულია გათვალისწინებით ჩართულია, და ბულური დროშები შეიძლება იყოს
შეზღუდული შესაძლებლობის მქონე პირები `=false`.

| შეცდომა                    | CLI დროშა                                   | რა ახორციელებს                          |
| ------------------------ | ------------------------------------------ | ------------------------------------------ |
| გაჩერება და განახლება        | `--fault-enable-crash-restart`             | პარტნიორული პროცესის დაკარგვა და აღდგენა             |
| გაწმენდი შენახვა და განახლება | `--fault-enable-wipe-storage`              | გამოჯანმრთელება დაკარგული ადგილობრივი სახელმწიფოსგან          |
| არასწორი ტრანზაქციის სპამი | `--fault-enable-spam-invalid-transactions` | მიღებისა და უარყოფის გზები              |
| ქსელის ლეტენცია          | `--fault-enable-network-latency`           | ნელი ჭორები და დაგვიანებული კონსენსუსის შეტყობინებები |
| ქსელის პარტიცია        | `--fault-enable-network-partition`         | დროებითი სანდო თანატოლთა იზოლაცია           |
| P2P პაკეტის დაკარგვა          | `--fault-enable-network-packet-loss`       | აპლიკაციის ჩარჩოზე მოძრაობა შემცირდა          |
| CPU სტრესი               | `--fault-enable-cpu-stress`                | ადგილობრივი ვალიდენციის და განრიგების ზეწოლა   |
| დისკის სიმკვრივე          | `--fault-enable-disk-saturation`           | ადგილობრივი შენახვის წნეხი                     |

მხოლოდ პაკეტის დაკარგვის შემთხვევაში:

```bash
cargo run -p izanami -- \
  --allow-net \
  --peers 20 \
  --faulty 5 \
  --duration 800s \
  --fault-window-start 133s \
  --fault-window-end 266s \
  --tps 200 \
  --submitters 20 \
  --max-inflight 512 \
  --fault-enable-crash-restart=false \
  --fault-enable-wipe-storage=false \
  --fault-enable-spam-invalid-transactions=false \
  --fault-enable-network-latency=false \
  --fault-enable-network-partition=false \
  --fault-enable-network-packet-loss=true \
  --fault-enable-cpu-stress=false \
  --fault-enable-disk-saturation=false \
  --fault-network-packet-loss-percent 75 \
  --seed 42
```

გამოყენება `--fault-window-start` და `--fault-window-end` კონტროლირებად
პრეპარატის ჩატარების პერიოდი ინექციური შეფერხებამდე და შემდეგ.
უფრო ადვილია გაირკვეს საწყისი ხმაური და ხარვეზის ეფექტი.

## სცენარის ფორმები {#scenario-shapes}

ზემოთ მიმდინარე Izanami კატალოგი რუკები საერთო blockchain კომუნიკაციის წარუმატებლობა
ფორმები CLI პროფილები. შეგიძლიათ მოდელირდეთ ისინი იმავე დროშებით:

| სცენარი              | ტიპიური ფორმა                                                                                                            |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| მიზნობრივი დატვირთვა         | `--faulty 0`, მაღალი `--tps`, ერთი შემსრულებელი, მაღალი `--max-inflight`                                                         |
| დროებითი შეფერხება     | ჩავარდნა/გადართვა მხოლოდ შეზღუდული ხარვეზის ფანჯრის შიგნით                                                                  |
| პაკეტის დაკარგვა           | მხოლოდ პაკეტის დაკარგვის შესაძლებლობა, ჩვეულებრივ გათვალისწინებული 75%-იანი დანაკლისის მაჩვენებელი                                                          |
| შეჩერება და აღდგენა | გამოიყენეთ დიდი ხარვეზური პარების პოპულაცია ჩავარდნის/გადაშლის დროს                                                                    |
| ლიდერის იზოლაცია      | გამოიყენეთ ზუსტად ერთი ხარვეზიანი თანატოლები მხოლოდ ქსელის პარტიციის ან პაკეტის დაკარგვის ხარვეზებით; Izanami შემდეგნაირად Sumeragi ლიდერი ტელემეტრიის |

ერთი ცვლადი მუდმივად. თუ თქვენ შეცვალეთ თანატოლების რაოდენობა, სამუშაო დატვირთვა
პროფილი, ხარვეზის ფანჯარა და TPS ამავე დროს, შედეგი რთულია
თარგმნა.

## რა უნდა ნახოთ {#what-to-watch}

გატარების დროს, ყურადღება მიაქციეთ იგივე სიგნალებს, რომლებიც გამოიყენება შესრულების ვალიდატაციისთვის:

- ბლოკის სიმაღლის პროგრესი თითოეულ მიმდინარე თანატოლზე
- წარდგენილი, მიღებული, უარყოფილი და დროულად ამოწურული ოპერაციები
- რიგის სიღრმე, რიგის სიმკვრივე და საბოლოო წერტილის უკანა ზეწოლა
- შეხედულების ცვლილებები, აღდგენის გზები, დაკარგული ბლოკები და დაკარგული კვორუმი
  სერტიფიკატები
- RBC ჩარჩო, მოულოდნელი სხდომები და შემცირებული ან დაგვიანებული კონსენსუსის ტრაფიკი
- CPU, მეხსიერება, დისკი და ქსელის saturation მასპინძელი მართავს თანატოლები

ვალიდენციის დადების ანალიზისათვის, ჩართეთ ძირითადი რუკის დებუგის ლოგები:

```bash
RUST_LOG=iroha_core::sumeragi::main_loop=debug \
  cargo run -p izanami -- --allow-net --seed 42
```

თითოეული ბლოკი უნდა გამოიყოს `block validation timings` მქონე `stateless_ms`,
`execution_ms`, და `total_ms`. შეადარეთ ეს დროები p95 ბლოკთან
ინტერვალები, ხედვის ცვლილების მაჩვენებლები და რიგის წნეხი შეცვლის წინ
კონსენსუსის დროები.

## შედეგების ინტერპრეტაცია {#interpreting-results}

გაითვალისწინეთ ჯანსაღი რეჟიმი, როდესაც ყველა შერჩეული თანატოლები განაგრძობენ ბლოკების ჩადენას.
უკანასკნელი არ იზრდება bound გარეშე, და ხარვეზები შეწყვიტოს ახალი აღდგენა გამოწვევა
აქტივობა კონფიგურირებული ფანჯრის დასრულების შემდეგ.

გაშვება ცუდია, როდესაც:

- ბლოკის პროგრესის გაჩერება უფრო ხანგრძლივი, ვიდრე `--progress-timeout`
- თანასწორობის სიმაღლეები განსხვავდება და არ გადახდის
- p95 ლატენცია აღემატება `--latency-p95-threshold`
- რიგები იზრდება დანარჩენი გაშვების შემდეგ, როდესაც გამონაკლისი ფანჯარა დაიხურება
- უარყოფილი ან ვადაგვიანებული ოპერაციები არ განმარტებულია შერჩეული
  სამუშაო დატვირთვა
- პარტნიორული განახლება, შენახვის წაშლა ან პაკეტის დაკარგვის აღდგენა საჭიროებს სახელმძღვანელო
  გაწმენდა

შეცდომის შემდეგ, გაიმეორეთ იგივე მარცვლე და ერთი ნაკლები ხარვეზის ტიპი.
ინარჩუნებს სამუშაო დატვირთვასა და დროის განახლებას, ხოლო შეამცირებს ხარვეზების შეზღუდვას
ზედაპირი.
