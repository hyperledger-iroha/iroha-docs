# შესრულება და მაჩვენებლები {#performance-and-metrics}

Iroha შესრულება დამოკიდებულია სამუშაო დატვირთვაზე, ვალიდატორების ტოპოლოგიაზე, ქსელზე
პირობები და კონსენსუსის პარამეტრები. TPS ამდენად, ნომერი მხოლოდ სასარგებლოა.
როდესაც ის არის დაკავშირებული სტანდარტულ გაშვებასთან მუდმივი კონფიგურაციით.

შესაძლებლობების დაგეგმვისთვის, შედეგი უნდა იყოს ოპერატიული ჩარჩო:

- ქსელმა მიიღო თხოვნილი ტრანზაქციის განაკვეთი
- შეზღუდული ხარჯის ფარგლებში გათვალისწინებული ლატენციის შენარჩუნება
- ტრანზაქციების რიგები შეზღუდული რჩება
- კონსენსუსი არ ეყრდნობა ხედვის განმეორებულ ცვლილებებს ან აღდგენის გზებს

გამოიყენეთ ეს გვერდი, რათა შეაფასოთ არის თუ არა განთავსება მაღალი, საშუალო ან დაბალი
მოცემული კვანძების რაოდენობის შესრულების მდგომარეობა, ქსელის ლეტენციის ზღვარი და სამიზნე
TPS.

## რა უნდა გაზომოთ {#what-to-measure}

დაიწყეთ ოპერატორის ზედაპირებით, რომლებიც გამოფენილია Torii:

```bash
export TORII=http://127.0.0.1:8180

curl -s "$TORII/status" | jq .
curl -s -H 'Accept: application/json' "$TORII/v1/sumeragi/status" | jq .
curl -s "$TORII/v1/sumeragi/phases" | jq .
curl -s "$TORII/v1/sumeragi/rbc" | jq .
curl -s "$TORII/v1/sumeragi/params" | jq .
curl -s "$TORII/metrics" > metrics.prom
```

შეგიძლია იგივე წაკითხვითი ნიმუში შეამოწმე საზოგადოების წინააღმდეგ Taira:

```bash
TAIRA=https://taira.sora.org

curl -fsS "$TAIRA/status" \
  | jq '{blocks, txs_approved, txs_rejected, queue_size, peers}'

curl -fsS "$TAIRA/v1/time/status" \
  | jq '{healthy: .health.healthy, peers, samples_used, rtt_count: .rtt.count}'

curl -fsS "$TAIRA/metrics" \
  | grep -E '^(block_height|queue_size|sumeragi_tx_queue_depth|txs|view_changes)' \
  | head -n 20
```

საზოგადოება Taira სიგნალის სახელების შესასწავლად სასარგებლოა. არ გამოიყენოთ ისინი
როგორც თქვენი საკუთარი განთავსების საწარმოო სიმძლავრის რიცხვები.

იგივე კონსენსუსის სურათები ხელმისაწვდომია CLI:

```bash
iroha --config ./localnet/client.toml --output-format text ops sumeragi status
iroha --config ./localnet/client.toml --output-format text ops sumeragi phases
iroha --config ./localnet/client.toml --output-format text ops sumeragi telemetry
iroha --config ./localnet/client.toml ops sumeragi params
```

ტელემეტრიის ხილვადობა დამოკიდებულია კონფიგურირებული პროფილი. გამოყენება `extended` როდესაც თქვენ
საჭიროება `/metrics`, და გამოყენება `full` ტესტის დროს, როდესაც ასევე საჭიროა დეტალური
Sumeragi ოპერატორის მარშრუტები.

```toml
telemetry_enabled = true
telemetry_profile = "full"
```

## შესრულების ბენდები {#performance-bands}

გამოიყენეთ ეს ზოლები დაკვირვებული გამავლობისთვის სამიზნე გამტარზე `Y` TPS და დაგვიანება
ბიუჯეტი `L` მილისეკონდებში. გაუშვით სამუშაო დატვირთვა საკმარისად დიდხანს, რომ ჩართოთ თბება,
სტაბილური მდგომარეობა და მოსალოდნელი პიკის ტვირთის მინიმუმ ერთი პერიოდი.

| ბენდი | პირობები | მნიშვნელობა |
| --- | --- | --- |
| მაღალი | მიღებული გამტარობა ან მეტია `Y`, p95 commit latency ქვემოთ არის `0.8 * L`, რიგები მუდმივად რჩება 10%-ზე ნაკლები სიმძლავრის, ხოლო ხედვის ცვლილების/აღდგენის მაჩვენებლები ფართოა | განთავსებას აქვს ადგილი მოთხოვნილი სამუშაო დატვირთვისთვის |
| საშუალო | მიღებული გამტარობა ახლოსაა `Y`, p95 commit latency ქვემოთ არის `L`, რიგები სტაბილურია 50%-ზე ნაკლები სიმძლავრის ქვეშ და ნახვის ცვლილებები იშვიათია | ოპერაცია მუშაობს, მაგრამ შეზღუდული ტოლერანტობაა აფეთქებისათვის. |
| დაბალი | მიღებული გამტარობა ქვემოთა `Y`, p95 commit latency აღემატება `L`, რიგები გაიზრდება მიმდინარეობის დროს, ან ხედვის ცვლილების/გამოძრავების მაჩვენებლები მუდმივად იზრდება | მოთხოვნილი სამუშაო დატვირთვა აღემატება მინიმუმ ერთ ღილაკს |

მთავარი წესი არის რიგის მიმართულება. TPS უფრო დიდია, ვიდრე დადებული TPS
და რიგის ზრდა განაგრძობს, განთავსება გადატვირთულია მაშინაც კი, თუ მოკლე ნიმუშები
ჯანსაღად გამოიყურებ.

## კვორუმისა და ნოდების რაოდენობა {#node-count-and-quorum}

მეტი ვალიდატორი აუმჯობესებს ხარვეზების ტოლერანტობას, მაგრამ ზრდის კოორდინაციას, ხელმოწერას,
და ქსელის წარმოების ხარჯები. Sumeragi შესრულება:

- დამტკიცებლის რაოდენობა `n` გამოიყოფა ხარვეზის ბიუჯეტი `f = floor((n - 1) / 3)`
- სამედიცინო `n >= 4`, კომიტეტის კვორუმი `2f + 1`
- სამედიცინო `n <= 3`, ყველა დამტკიცებელი აუცილებელია ვალდებულების მიღებისთვის
- დამკვირვებელი თანატოლები სინქრონიზაციის ბლოკებს, მაგრამ არ კენჭისყრა, წინადადება ან შეკრება

| გამართავებელი | ხარვეზის ბიუჯეტი | კომიტეტის კვორუმი | ქონების განცხადება |
| --- | --- | --- | --- |
| 1 დან 3 | 0 პრაქტიკული offline slack | ყველა ვალიდატორი | სასარგებლო განვითარებისა და მცირე ტესტებისათვის; ნებისმიერი დაკარგული ვალიდატორი შეიძლება შეაჩეროს კომიტეტები |
| 4 | 1 | 3 | ერთი შეცდომის ტოლერანტობის საერთო მინიმუმი |
| 7 | 2 | 5 | უფრო მდგრადი, მეტი ხმის მიცემისა და პროპაგანდის ტრანსპორტი |
| 10 | 3 | 7 | უფრო მაღალი კოორდინაციის ხარჯები; ქსელებისა და კოლექტორების ატონირების მნიშვნელობა მეტია |

"X კვანძების" შეფასებისას, ცალკე ხმის მიცემის დამტკიცებლები დამკვირვებლებიდან. დამატება
დამკვირვებლები, როგორც წესი, ნაკლები ხარჯებია, ვიდრე ვალისატორების დამატება, მაგრამ დამკვირვებელი მაინც მოიხმარს
ბლოკ-ფოქს, ბლოკ სინქრონიზაციას, დისკს და ქსელის ზღვრის სიგანეს.

## ფაქტორები, რომლებიც გავლენას ახდენენ შესრულებაზე {#factors-that-influence-performance}

### სამუშაო დატვირთვის ფორმა {#workload-shape}

იგივე TPS შეიძლება იყოს იაფი ან ძვირადღირებული დამოკიდებულია იმაზე, თუ რა აკეთებს თითოეული ტრანზაქცია.
დოკუმენტი:

- ინსტრუქციების რაოდენობა თითოეული ტრანზაქციაზე
- ხელმოწერების რაოდენობა და ხელმოწერის ალგორითმები
- ტრანზაქციის ბაიტის ზომა და გამორთული სასარგებლო ტვირთის ზომა
- წაკითხვა/წერის მაჩვენებელი
- მეტა მონაცემების ზომა და აქტივების ოპერაციები
- ჭკვიანი კონტრაქტი, გამშვები და IVM განხორციელების ხარჯები
- შეკითხვის დატვირთვა იგივე თანატოლების წინააღმდეგ

მცირე ტრანსფერები არ წარმოადგენს ხელშეკრულებით მძიმე ან მეტა მონაცემებით მძიმე ოპერაციის პროქსია
სამუშაო დატვირთვები.

### კონსენსუსის დრო {#consensus-timing}

Sumeragi დროის კონტროლი ხდება ეფექტური Sumeragi პარამეტრები:

- `block_time_ms`
- `commit_time_ms`
- `min_finality_ms`
- `pacing_factor_bps`
- NPoS ფაზის გათიშვა, როდესაც NPoS რეჟიმი ჩართულია

შეამოწმეთ ისინი:

```bash
iroha --config ./localnet/client.toml ops sumeragi params
curl -s "$TORII/v1/sumeragi/params" | jq .
```

დროის შემცირების მიზანშეწონილი მიზნები შეიძლება გაუმჯობესდეს ლეტენციას მხოლოდ მაშინ, როდესაც ქსელი, შენახვა და
განხორციელების ფენები შეიძლება შეინარჩუნოს. ერთხელ ნახვა ცვლილებები, დაკარგული payload მოძიება, ან
რეპრესია გამოჩნდება, დროის შემცირება ჩვეულებრივ უარყოფს შესრულებას.

### კოლექციონერი Fanout {#collector-fanout}

კოლექტორის პარამეტრები გავლენას ახდენს იმაზე, თუ რამდენად სწრაფად კონვერგენციურ ხმებს აპირებენ:

- `sumeragi.collectors.k` აკონტროლებს, თუ რამდენი კოლექტორი იღებს ხმას სიმაღლეზე
- `sumeragi.collectors.redundant_send_r` დამატებითი ხმის მიცემის კონტროლის შემდეგ
  ადგილობრივი დროის გამოტოვება
- `sumeragi.collectors.parallel_topology_fanout` დამატება topology fanout გვერდით
  კოლექტორები

გაზრდილი ფანოუტი შეიძლება შეამციროს ტაილ ლატენსი უფრო დიდ ან ნაკლებად საიმედო ქსელებში,
მაგრამ ის ასევე ზრდის მოძრაობას. შეადარეთ საერთო ხელმისაწვდომობა და კოლექტორი
ტელემეტრიის გამოყენება დახურულობისა და უკანა წნევის მაჩვენებლებით, სანამ ამ მნიშვნელობებს შეცვლით:

```bash
iroha --config ./localnet/client.toml --output-format text ops sumeragi telemetry
```

### ქსელის პირობები {#network-conditions}

კონსენსუსის შედეგები მგრძნობიარეა:

- RTT ვალიდატორებს შორის
- შეშფოთება და პაკეტის დაკარგვა
- ბლოკის სასარგებლო ტვირთებისთვის ზღვრის სიგანე და RBC ნაჭრები
- რეგიონებს შორის ასიმეტრიული კავშირები
- NAT, firewall, ან რელე ქცევა, რომელიც შეფერხებს თანატოლთა კავშირს

როგორც გეგმური წესი, დააყენეთ ლეტენციის ბიუჯეტი საკმარისად მაღალია, რათა დაფაროს რამდენიმე
დამტკიცებლის ბრუნვა-გადმოგზაურობა და შესრულება და დისკის ჩაბარების დრო. თუ p95 ქსელი RTT არის
უკვე სასურველი p95 კომიტეტის ლატენციის ახლოს, მიზანი არ არის რეალური.

### რიგები და მიღების შეზღუდვები {#queues-and-admission-limits}

შეყვანის და რიგის პარამეტრები განსაზღვრავს, თუ რამდენი ბურუსის ზეწოლა შეიძლება შეიწოვოს თანატოლმა:

- `queue.capacity`
- `queue.capacity_per_user`
- `queue.transaction_time_to_live_ms`
- გენეზის ტრანზაქციის ლიმიტები, როგორიცაა მაქსიმალური ხელმოწერები, ინსტრუქციები, ბაიტები და
  დაშლილი ბაიტები
- p2p რიგის საზღვრები და კონსენსუსული შესვლის ლიმიტები

მაღალი რიგის სიმძლავრე შეიძლება მალოს გადატვირთვა გარკვეული პერიოდის განმავლობაში, მაგრამ ეს არ იზრდება
მდგრადი ხაზი ჯანსაღია; მზარდი ხაზი უკანასკნელია.

### ტექნიკა და შენახვა {#hardware-and-storage}

გაზომეთ ყველა დამტკიცებელი, არა მხოლოდ ლიდერი:

- CPU გაჯერება ვალიდენციის, ხელმოწერის შემოწმების და შესრულების დროს
- მეხსიერების წნეხი რიგებიდან, სურათებიდან და აქტიურიდან RBC სხდომები
- ბლოკის შენახვის და გადაღებების დისკზე დაწერის ლატენცია
- ქსელის გადაცემა/მიღება saturation
- სამუშაო დატვირთვით გამოყენებისას არაკომპეტენტური აპარატურის დაჩქარების პარამეტრები

ყველაზე ნელმა კენჭისყრის ვალისტირებელმა შეიძლება განსაზღვროს ქსელის ტაილ ლატენცია.

## პრომეტეუსის სიგნალები {#prometheus-signals}

მეტრიკული სახელები შეიძლება განსხვავდებოდეს პროფილის შექმნის და მახასიათებლების ნაკრების მიხედვით. `/metrics` დაწვრილებით
ჯერ შენი კვანძი, შემდეგ კი შექმენით დეშბორდები ხელმისაწვდომი სერიების გარშემო.

ჩვეულებრივი სიგნალებია:

| სიგნალი | პრომეტეუსის მაგალითები | რა უნდა უყუროთ |
| --- | --- | --- |
| მიღებული გამტარობა | `sum(rate(txs{type="accepted"}[5m]))` | უნდა შეხვდეს ან გადააჭარბოს მიზანს TPS სტაბილურ მდგომარეობაში |
| უარყოფა | `sum(rate(txs{type="rejected"}[5m]))` | უნდა იყოს განმარტებული სატესტო გეგმით |
| დაწესებული ლეტენცია | `histogram_quantile(0.95, sum(rate(commit_time_ms_bucket[5m])) by (le))` | შეადარეთ p95/p99 და ლეტენციის ბიუჯეტი |
| რიგის სიღრმე | `queue_size`, `sumeragi_tx_queue_depth` | უნდა იყოს შეზღუდული პიკის დატვირთვის დროს |
| რიგის შეჯერება | `sumeragi_tx_queue_saturated` | გაგრძელებული ნულოვანი მნიშვნელობის საშუალო გადატვირთვა |
| ცვლილებების ნახვა | `view_changes`, `sumeragi_view_change_suggest_total`, `sumeragi_view_change_install_total` | მზარდი მნიშვნელობები მიუთითებს დროის, ტოპოლოგიის, სასარგებლო დატვირთვის ან ქსელის პრობლემების შესახებ |
| წაშლილი შეტყობინებები | `dropped_messages`, `sumeragi_consensus_message_handling_total` | დაწევის დროს ჩვეულებრივ ახსნის ლატენციის პიკებს |
| RBC წნეხი | `sumeragi_rbc_store_pressure`, `sumeragi_rbc_backpressure_deferrals_total` | ნულოვანი წნევის წერტილები სასარგებლო ტვირთის აღდგენისა ან შენახვისთვის |
| კომიტეტის კვორუმი | `sumeragi_commit_signatures_counted`, `sumeragi_commit_signatures_required` | გათვლილი ხელმოწერები უნდა მიაღწიონ საჭირო კვორუმს სწრაფად |

როდესაც მეტრიკა არსებობს მხოლოდ `/v1/sumeragi/status`, დააკავეს JSON გადაღება
იგივე ნაგებობები, რაც პრომეთეუსის ნაღდი ნაჭერი.

## შეფასება სამუშაო მიმდინარეობა {#estimation-workflow}

1. განსაზღვრეთ სცენარი:
   - ვალიდატორთა და დამკვირვებლების რაოდენობა
   - კონსენსუსის რეჟიმი
   - მიზანი TPS
   - p95 და p99 ვალდებულებების გათვალისწინების ბიუჯეტები
   - ტრანზაქციების შერწყმა
   - მოსალოდნელი ქსელი RTT, jitter, და ზღვრის სიგანე
2. დაფიქსირება ეფექტური კონფიგურაცია:

   ```bash
   iroha --config ./localnet/client.toml --output-format json ops sumeragi params \
     > artifacts/sumeragi-params.json
   curl -s "$TORII/v1/sumeragi/collectors" \
     > artifacts/sumeragi-collectors.json
   ```

3. გაუშვით სამუშაო დატვირთვა მიზანზე TPS.
4. დაფიქსირება სტატუსი და მაჩვენებლები დასაწყისში, შუა, და დასასრული run.
5. დარეგისტრირება შესრულების ზოლის მაგიდათ.
6. თუ ბენდია საშუალო ან დაბალი, შეცვალეთ ერთი ფაქტორი ერთდროულად და გაიმეორეთ.

## სტანდარტული ანგარიშის შაბლონი {#benchmark-report-template}

გამოაქვეყნეთ შესრულების ნომრები მხოლოდ საკმარის კონტექსტით, რომ მათი რეპროდუქცია მოხდეს:

- Iroha commit, release და feature flags
- ვალიდატორისა და დამკვირვებლის რაოდენობა
- კონსენსუსის რეჟიმი და Sumeragi პარამეტრები
- კოლექტორი `k`, გამორიცხული გადაგზავნა `r`, და ტოპოლოგიის ფანოუტი
- ტელემეტრიის პროფილი
- აპარატურა, შენახვა და OS დეტალი
- ქსელი RTT, jitter, დანაკარგები და ზღვრის სიგანე ვარაუდები
- ტრანზაქციების შერეული და სასარგებლო ტვირთის ზომები
- შემოთავაზებული TPS და გატარების ხანგრძლივობა
- მიღებული/გარიცხული TPS
- p50/p95/p99 კომიტეტის ლეტენცია
- რიგის სიღრმე და სიმკვრივე
- ცვლილებების ნახვა, შეტყობინებები, RBC წნევის და დაკარგული სასარგებლო ტვირთის სათვალეები
- CPU, მეხსიერება, დისკი და ქსელის გამოყენება თითო ვალიდატორზე

ამ დეტალების გარეშე, TPS ნომერი უნდა იყოს ანეკდოტური.
