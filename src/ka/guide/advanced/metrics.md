# შესრულება და მაჩვენებლები {#performance-and-metrics}

Iroha შესრულება დამოკიდებულია სამუშაო დატვირთვაზე, ვალიდატორების ტოპოლოგიაზე, ქსელის პირობებსა და კონსენსუსის პარამეტრებზე. ამდენად ერთიანი TPS ნომერი სასარგებლოა მხოლოდ მაშინ, როდესაც ის არის დაკავშირებული სტანდარტული რეგულირების ჩატარებასთან მუდმივ კონფიგურაციით.

ქონების დაგეგმვისთვის, შედეგი უნდა იყოს ოპერატიული მონაცემთა კონტეინერის სახით:

- ქსელი იღებს მოთხოვნილ ტრანზაქციის განაკვეთს;
- პროტოკოლის განხორციელების ლეტენცია რჩება მიზნობრივი ბიუჯეტის ფარგლებში
- ტრანზაქციების რიგები შეზღუდული რჩება
- კონსენსუსი არ ეყრდნობა ხედვის განმეორებულ ცვლილებებს ან აღდგენის გზებს.

გამოიყენეთ ეს გვერდი იმის შესაფასებლად, არის თუ არა განთავსება მაღალი, საშუალო ან დაბალი შესრულების მდგომარეობაში მოცემული კვანძის რაოდენობისთვის, ქსელის ლეტენციის ზღვარისა და სამიზნე TPS.

## რა უნდა გაზომოთ {#what-to-measure}

დაიწყეთ საჯარო კვანძის წერტილის დროში მონაცემების ხედვით და Prometheus scrape- ით, შემდეგ გამოიყენეთ CLI ოპერატორის მიერ ავტორიზებული კონსენსუსის მდგომარეობისთვის. ოპერატორის გასაღები უნდა იყოს ნებადართული სამიზნე კვანჭით და დატვირთულია მხოლოდ შესრულების გარემოში:

```bash
export TORII=http://127.0.0.1:8180
export OPERATOR_KEY_FILE=./secrets/operator.key

curl -s -H 'Accept: application/json' "$TORII/status" | jq .
curl -s "$TORII/metrics" > metrics.prom

iroha --config ./localnet/client.toml \
  --operator-private-key-file "$OPERATOR_KEY_FILE" \
  --output-format json ops sumeragi status
iroha --config ./localnet/client.toml \
  --operator-private-key-file "$OPERATOR_KEY_FILE" \
  --output-format json ops sumeragi diagnostics
iroha --config ./localnet/client.toml \
  --operator-private-key-file "$OPERATOR_KEY_FILE" \
  --output-format json ops sumeragi qc
iroha --config ./localnet/client.toml \
  --operator-private-key-file "$OPERATOR_KEY_FILE" \
  --output-format json ops sumeragi params
```

საჯარო Taira სასარგებლოა ანონიმური კვანძების სურათების ფორმის შესასწავლად. მისი ოპერატორის დიაგნოსტიკა განზრახ არ არის ხელმისაწვდომი Taira ოპერატორული გასაღების გარეშე:

```bash
TAIRA=https://taira.sora.org

curl -fsS -H 'Accept: application/json' "$TAIRA/status" \
  | jq '{blocks, txs_approved, txs_rejected, queue_size, peers}'

curl -fsS "$TAIRA/v1/time/now" \
  | jq '{now_ms, offset_ms}'
```

არ გამოიყენოთ საჯარო ტესტნეტის დაკვირვებები საკუთარი განთავსებისათვის წარმოების სიმძლავრის რიცხვებად.

ტელემეტრიის ხილვადობა დამოკიდებულია კონფიგურირებულ პროფილზე. `operator` საშუალებას აძლევს სტატუსისა და დიაგნოსტიკური კადრების გადაღებას. `extended` დამატებს `/metrics` და ძვირადღირებული დროების, როდესაც `developer` დაამატებს დეველოპერის მონაცემების პუნქტის დროის ხედვას, როგორიცაა ლიდერი, QC, პარამეტრები და მტკიცებულებები, არ ჩართვის გარეშე `/metrics`. გამოიყენეთ `full` მაშინ, როდესაც ერთ რუნს ორივე კომპლექტი სჭირდება. `telemetry_profile` არის ერთადერთი ტელემეტრიული გადამწყვეტი პირველი გამოშვებისას.

```toml
telemetry_profile = "full"
```

## შედეგიანი ბენდები {#performance-bands}

გამოიყენეთ ეს ზოლები დაკვირვებული გატარებისათვის სამიზნე გამავლობის `Y` TPS და ლატენციის ბიუჯეტის `L` მილიწამებში. გაატარეთ სამუშაო ტვირთი საკმარისად ხანგრძლივად, რომ მოიცავდეს გათბობას, სტაბილურ მდგომარეობას და მინიმუმ ერთ პერიოდს მოსალოდნელი პიკის დატვირთვისას.

|ბენდი |პირობები |მნიშვნელობა |
| --- | --- | --- |
|მაღლა |მიღებული გამტარუნარიანობა არის `Y` ან მეტი, პ95 პროტოკოლის დასრულების ლატენცია ქვემოთ `0.8 * L`, რიგები რჩება 10%-ზე ნაკლები სიმძლავრის და ნახვის ცვლილების/გადადგენის მაჩვენებლები არის ფასიანი |განთავსებას აქვს სივრცე მოთხოვნილი სამუშაო დატვირთვისთვის |
|საშუალო |მიღებული გამტარუნარიანობა ახლოსაა `Y`, p95 პროტოკოლის დასრულების ლეტენცია ქვემოთ `L`, რიგები სტაბილურია 50%-ზე ნაკლები სიმძლავრის და ხედვის ცვლილებები იშვიათია |ოპერაცია მუშაობს, მაგრამ შეზღუდული ტოლერანტობაა.|
|დაბალი |მიღებული გამტარობა არის `Y` ქვემოთ, p95 პროტოკოლის განხორციელების დაგვიანება აღემატება `L`, რიგები იზრდება მიმდინარეობის დროს ან ხედვის ცვლილების/გამოძრავების მაჩვენებლები მუდმივად იმატებს |მოთხოვნილი სამუშაო დატვირთვა აღემატება მინიმუმ ერთ ღილაკს |

მთავარი წესი არის რიგის მიმართულება. თუ წარდგენილი TPS უფრო დიდია, ვიდრე დასრულებული TPS და რიგის ზრდა გრძელდება, განთავსება გადატვირთულია მაშინაც კი, თუ მოკლე ნიმუშები ჯანმრთელი გამოიყურება.

## ნოდების რაოდენობა და კვორუმი {#node-count-and-quorum}

უფრო მეტი ვალიდატორი აუმჯობესებს ხარვეზების ტოლერანტობას, მაგრამ ზრდის კოორდინაციის, ხელმოწერისა და ქსელის გამოშვების ხარჯებს. პირველი გამოსვლის Sumeragi პროტოკოლი მოითხოვს:

- ზუსტი `n = 3f + 1` კენჭისყრის კომიტეტი
- `4 <= n <= 31`, შესაბამისად, მოქმედი ზომები არის 4, 7, 10 და ა.შ.
- კონსენსუსული დასკვნითი კვორუმი `2f + 1`
- სადამკვირვებლო ქსელის კვანძები სინქრონიზებენ ბლოკებს, მაგრამ არ კენჭისყრა, წინადადება ან შეგროვება

|ვალიდატორები |ხარვეზური ბიუჯეტი |კონსენსუსის დასკვნითი კვორუმი |შესაძლებლობების ცნობა |
| --- | --- | --- | --- |
| 4 | 1 | 3 |საერთო მინიმუმი ერთი შეცდომის ტოლერანტობისთვის |
| 7 | 2 | 5 |უფრო მდგრადი, მეტი ხმის მიცემითა და პროპაგანდის ტრანსპორტით |
| 10 | 3 | 7 |უფრო მაღალი საკოორდინაციო ხარჯები; ქსელური და შესასვლელი მოწყობილობა უფრო მნიშვნელოვანია |
| 31 | 10 | 21 |მაქსიმალური პირველი გამოშვების კომიტეტი; საკანონმდებლო შეფასების კოორდინაცია და ხელმოწერის ღირებულება ყურადღებით |

ბლოკჩეინის გენეზისის წარმოება და სტარტაპის ვალიდატირება უარყოფს არასათანადო კომიტეტების ზომებს; არ შეაფასოთ ტოპოლოგია, რომელიც გამოცემაში ვერ აღიარდება.

"X კვანძების" შეფასებისას, გამოყოფენ ხმის მიცემის დამტკიცებლებს დამკვირვებლებისაგან. დამკვირვებლის დამატება ჩვეულებრივ იჯდება ნაკლებად, ვიდრე დამტკიცებლების დამატება, მაგრამ დამკვირვებელი მაინც მოიხმარს ბლოკის ჭორებს, ბლოკის სინქრონიზაციას, დისკსა და ქსელის ზღვრის სიგანეს.

## ფაქტორები, რომლებიც გავლენას ახდენენ შესრულებაზე {#factors-that-influence-performance}

### სამუშაო დატვირთვის ფორმა {#workload-shape}

იგივე TPS შეიძლება იყოს იაფი ან ძვირადღირებული იმის მიხედვით, თუ რა ხდება თითოეული ტრანზაქცია. ჩანაწერი:

- ტრანზაქციაზე ინსტრუქციების რაოდენობა
- ხელმოწერების რაოდენობა და ხელმოწერის ალგორითმები
- ტრანზაქციის ბაიტების ზომა და დეკომპრესირებული დატვირთვის ზომა
- წაკითხვა/წერის მაჩვენებელი
- მეტამონაცემების ზომა და აქტივების ოპერაციები
- ინტელექტუალური ხელშეკრულება, განმახორციელებელი და IVM შესრულების ღირებულება
- შეკითხვის დატვირთვა მიმდინარეობს იგივე ქსელის კვანძების წინააღმდეგ

მცირე გადარიცხვის ოპერაციები არ წარმოადგენს ხელშეკრულებით მძიმე ან მეტამონაცემებით მძიმე სამუშაო დატვირთვების პროქსიას.

### კონსენსუსის კადენცია {#consensus-cadence}

ეფექტური Sumeragi პარამეტრის წერტილ-დროში მონაცემების ნახვა შეიცავს ხელმოწერილი შეუცვლელ ბლოკის კადენციას და საათის დრიფტის ზღვარს:

- `block_cadence_ms`
- `max_clock_drift_ms`

შეამოწმეთ ისინი:

```bash
iroha --config ./localnet/client.toml \
  --operator-private-key-file "$OPERATOR_KEY_FILE" \
  --output-format json ops sumeragi params
```

`block_cadence_ms` ფიქსირდება ხელმოწერილი ბლოკჩეინის გენეზისით და გაყინულია სტარტაპისას; ეს არ არის ცოცხალი ათვისების ღილაკი. შეადარეთ ქსელები სხვადასხვა ხელმოწერილ ბლოკჩეინ გენეზის შემოტანებით მხოლოდ ცალკეული სცენარების სახით. მას შემდეგ, რაც ჩანს ცვლილებები, დაკარგული დატვირთვის მოძიება ან უკანა ზეწოლა გამოჩნდება, უფრო მოკლე კადენცია ჩვეულებრივ ხდის გადატვირთვას უფრო თვალსაჩინო და არა გაზრდის მდგრადი გამავლობა.

### კანდიდატის და მიღების საზღვრები {#candidate-and-ingress-bounds}

კვანძების ადგილობრივი Sumeragi საზღვრები განსაზღვრავს, თუ რამდენი კანდიდატი და აღდგენითი სამუშაო შეიძლება შეინარჩუნოს ვალიდატორს:

- `sumeragi.block.max_transactions`
- `sumeragi.block.max_payload_bytes`
- `sumeragi.block.proposal_queue_scan_multiplier`
- `sumeragi.queues.commands`
- `sumeragi.queues.bodies` და `sumeragi.queues.body_bytes`
- `sumeragi.queues.body_source_bytes`, `sumeragi.queues.chunks`, და `sumeragi.queues.ready_bodies`

ზედმეტად პატარა საზღვრები ქმნის რიგის ან დატვირთვების აღდგენის წნეხს; ზედმეტი ზომის საზღვრებს ზრდიან შენახული მეხსიერება და მუშაობის რაოდენობა, რომელიც ხელმისაწვდომია ბოროტად გამოყენებულ ქსელში პარტნიორი. შეადარეთ დიაგნოსტიკური დროის მონაცემების ნახვა პროცესის მეხსიერებასთან, შეტყობინებების მენეჯმენტთან და დაკარგული სხეულების მაჩვენებლებთან, სანამ ერთჯერადად ერთი ზღვარი შეცვლით:

```bash
iroha --config ./localnet/client.toml \
  --operator-private-key-file "$OPERATOR_KEY_FILE" \
  --output-format json ops sumeragi diagnostics
```

### ქსელის პირობები {#network-conditions}

კონსენსუსის შედეგები მგრძნობიარეა:

- RTT ვალიდატორებს შორის
- შეშფოთება და პაკეტის დაკარგვა
- ბენდის სიგანე ბლოკის დატვირთვებისა და RS16 ხელმოწერილი ნაწილისთვის
- რეგიონებს შორის ასიმეტრიული კავშირები
- NAT, ქსელური ეკრანი ან რელე ქცევა, რომელიც ხელს უწყობს ქსელის კვანძული კავშირგაბმულობის დაგვიანებას

როგორც გეგმური წესი, დააყენეთ ლატენციის ბიუჯეტი საკმარისად მაღალია, რომ დაფაროს რამდენიმე ვალიდატორის ბრუნვა-გასვლა და აღსრულების დრო და დისკის მდგრადობის დრო. თუ p95 ქსელი RTT უკვე ახლოსაა სასურველი p95 პროტოკოლის დასრულების ლატენციასთან, სამიზნე არ არის რეალისტური.

### რიგები და შესვლის შეზღუდვები {#queues-and-admission-limits}

შეყვანის და რიგის პარამეტრები განსაზღვრავს, თუ რამდენი წნეხი შეიძლება შეიწოვოს ქსელის თანასწორმა:

- `queue.capacity`
- `queue.capacity_per_user`
- `queue.max_retained_bytes`
- `queue.transaction_time_to_live_ms`
- ბლოკჩეინის გენეზისი ტრანზაქციის საზღვრები, როგორიცაა მაქსიმალური ხელმოწერები, ინსტრუქციები, ბაიტები და დეკომპრესირებული ბაიტები
- p2p რიგის საზღვრები და კონსენსუსული შესვლის ლიმიტები

მაღალი რიგის სიმძლავრე შეიძლება მალოს გადატვირთვა გარკვეული პერიოდის განმავლობაში, მაგრამ ეს არ ზრდის მდგრად გამტარებას. სტაბილური რიგის ჯანმრთელობაა; მზარდი რიგის მიღმა დარჩენა არის ჩამორჩენილი.

### ტექნიკა და შენახვა {#hardware-and-storage}

გაზომეთ ყველა დამტკიცებელი, და არა მხოლოდ ლიდერი:

- CPU გაჯერება ვალიდაციის, ხელმოწერის შემოწმების და შესრულების დროს
- მეხსიერების წნეხი რიგებიდან, მონაცემთა პუნქტის დროის ნახვა და დატვირთვის აღდგენის ბუფერები
- დისკის დაწერის ლატენცია ბლოკის შენახვისა და მონაცემთა პუნქტის დროში ნახვისთვის
- ქსელის გადაცემა/მიღება saturation
- სამუშაო დატვირთვით გამოყენებისას საბაჟო აჩქარების ფორმატირება

ყველაზე ნელი კენჭისყრის ვალიდატორს შეუძლია განსაზღვროს ქსელის ზურგის ლატენცია.

## პრომეტეუსის სიგნალები {#prometheus-signals}

მეტრიკის სახელები მოდის ჩანახული ტელემეტრიის კატალოგიდან. სერიების ხელმისაწვდომობა და ნიმუშების აღება კვლავ დამოკიდებულია შენობის მახასიათებლებზე და `telemetry_profile`, ამიტომ შეამოწმეთ `/metrics` სამიზნე კვანძზე დასბორდის აშენებამდე .

საერთო სიგნალები მოიცავს:

|სიგნალი |Prometheus-ის მაგალითები |რა უნდა ვუყუროთ?|
| --- | --- | --- |
|მიღებული გამტარობა |`sum(rate(txs{type="accepted"}[5m]))` |უნდა შეხვდეს ან გადააჭარბოს მიზანს TPS სტაბილურ მდგომარეობაში |
|უარყოფა |`sum(rate(txs{type="rejected"}[5m]))` |ეს უნდა იყოს განმარტებული ტესტის გეგმით |
|პროტოკოლის განხორციელების დაგვიანება |`histogram_quantile(0.95, sum(rate(commit_time_ms_bucket[5m])) by (le))` |შეადარეთ p95/p99 და ლეტენციური ბიუჯეტი |
|რიგის სიღრმე |`queue_size`, `sumeragi_tx_queue_depth` |უნდა დარჩეს შეზღუდული მატების პიკის დროს |
|რიგის გაჯერება |`sumeragi_tx_queue_saturated` |მუდმივი ნულოვანი მნიშვნელობის საშუალო გადატვირთვა |
|ნახეთ ცვლილებები |`view_changes`, `sumeragi_view_change_suggest_total`, `sumeragi_view_change_install_total` |მზარდი ღირებულებები მიუთითებს დროის, ტოპოლოგიის, სასარგებლო დატვირთვის ან ქსელის პრობლემების |
|წაშლილი შეტყობინებები |`dropped_messages`, `sumeragi_consensus_message_handling_total` |ტვირთის დროს შემცირება, როგორც წესი, ხსნის ლატენციის მაქსიმუმებს.|
|დატვირთვა და DA აღდგენა | `sumeragi_missing_block_requests`, `sumeragi_missing_block_oldest_ms`, `sumeragi_missing_block_fetch_total`, `sumeragi_da_gate_block_total`, `sumeragi_da_gate_satisfied_total` |მუდმივი მოთხოვნები, ასაკის ზრდა ან განმეორებითი DA კარიბჭეები მიუთითებენ სხეულის ან ნაწილის შეძენის პრობლემებზე |
|კონსენსუსის დასკვნითი კვორუმი |`sumeragi_commit_signatures_counted`, `sumeragi_commit_signatures_required` |გათვლილი ხელმოწერები სასწრაფოდ უნდა მიაღწიონ საჭირო კვორუმს.|

როდესაც მეტრიკა არსებობს მხოლოდ `/v1/sumeragi/status`, დაიჭირეთ JSON წერტილის დროში მონაცემების ნახვა იმავე გაშვებით არტეფაქტებში, როგორც Prometheus-ის scrape.

## შეფასება სამუშაო მიმდინარეობა {#estimation-workflow}

1. განსაზღვრეთ სცენარი:
   - ვალიდატორთა და დამკვირვებლების რაოდენობა
   - კონსენსუსის რეჟიმი
   - მიზანი TPS
   - p95 და p99 პროტოკოლების დასკვნა-გვიანობის ბიუჯეტები
   - ტრანზაქციების შერეული
   - მოსალოდნელი ქსელი RTT, jitter და მაჩვენებელი სიგანე
2. ჩაწერეთ ეფექტური კონფიგურაცია:

   ```bash
   iroha --config ./localnet/client.toml \
     --operator-private-key-file "$OPERATOR_KEY_FILE" \
     --output-format json ops sumeragi params \
     > artifacts/sumeragi-params.json
   iroha --config ./localnet/client.toml \
     --operator-private-key-file "$OPERATOR_KEY_FILE" \
     --output-format json ops sumeragi status \
     > artifacts/sumeragi-status.json
   iroha --config ./localnet/client.toml \
     --operator-private-key-file "$OPERATOR_KEY_FILE" \
     --output-format json ops sumeragi diagnostics \
     > artifacts/sumeragi-diagnostics.json
   ```

3. განახორციელეთ სამუშაო დატვირთვა მიზნზე TPS.
4. დაფიქსირება სტატუსი და მაჩვენებლები დასაწყისში, შუა, და დასასრული მიმდინარეობს.
5. გატარების კლასიფიცირება შესრულების ზოლის მაგიდათ.
6. თუ ბენდია საშუალო ან დაბალი, შეცვალეთ ერთი ფაქტორი ერთდროულად და გაიმეორეთ.

## სტანდარტული ანგარიშის შაბლონი {#benchmark-report-template}

გამოაქვეყნეთ შესრულების ნომრები მხოლოდ საკმარისი კონტექსტით, რომ მათი რეპროდუქცია მოხდეს:

- Iroha პროტოკოლის დასკვნა, გათავისუფლება და მახასიათებლების დროშები
- ვალიდატორისა და დამკვირვებლის რაოდენობა
- კონსენსუსის რეჟიმი, ბლოკის კადენცია და DA განლაგება
- ზუსტი `3f + 1` კომიტეტი, კვორუმი და დამკვირვებლის სია.
- `sumeragi.block`,`sumeragi.queues`, `sumeragi.limits`, ქსელის შესვლის და ტრანზაქციების რიგის საზღვრები
- ტელემეტრიის პროფილი
- აღჭურვილობა, შენახვა და OS დეტალები
- ქსელის RTT, jitter, დანაკლისი და ზღვრის სიგანის ვარაუდები
- ტრანზაქციების შერეული და დატვირთვის ზომები
- შემოთავაზებული TPS და მიმდინარეობის ხანგრძლივობა
- მიღებული/გარღვეული TPS
- p50/p95/p99 პროტოკოლის განხორციელების ლატენცია
- რიგის სიღრმე და სიმკვრივე
- ნახვა ცვლილებები, წასული შეტყობინებები, დაკარგული ბლოკების მოძიება და DA კარიბჭეების მაჩვენებლები
- CPU, მეხსიერება, დისკი და ქსელის გამოყენება თითოეული ვალდიტორის მიხედვით

ამ დეტალების გარეშე, TPS ნომერი უნდა ჩაითვალოს ანეკდოტურად.
