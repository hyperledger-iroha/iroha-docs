# პრობლემების გადაჭრა განთავსების საკითხებში {#troubleshooting-deployment-issues}

ეს განყოფილება გთავაზობთ პრობლემების მოგვარების რჩევებს Iroha 3 დანერგვისთვის. თუ პრობლემა არ არის აღწერილი აქ, დაგვიკავშირდით ტელეგრამზე [](https://t.me/hyperledgeriroha).

## დაიწყეთ შექმნილი არტეფაქტებით. {#start-with-generated-artifacts}

ადგილობრივი და სატესტო დანერგვისთვის, სასურველია Kagami-ის მიერ შექმნილი არტეფაქტები ხელით დაწერილი თანატოლების ფაილების ნაცვლად:

```bash
cargo run --bin kagami -- localnet --peers 4 --out-dir ./localnet
```

გენერირებული დირექტორი შეიცავს პარტნიორთა კონფიგურაციას, გენეზის მასალას, საწყისი სცენარებს და README Iroha 3 მშენებლობის ხაზისთვის.

## პარტნიორი არ იწყება {#peer-does-not-start}

პირველ რიგში, შეამოწმეთ ეს ნივთები:

- `iroha3d --config <path>` პუნქტები პარტნიორის საკუთარ ფაილში TOML.
- `public_key` და `private_key` პარტნიორების კონფიგურაციაში ერთსა და იმავე საკვანძო წყვილს ეკუთვნის.
- `genesis.public_key` შეესაბამება გენეზის ტრანზაქციაზე ხელმოწერისთვის გამოყენებულ გასაღებელს.
- ვალიდატორების თანატოლთა იდენტობა იყენებს BLS-ნორმალურ საკიდებს, ხოლო `trusted_peers_pop` შეიცავს ადგილობრივი გასაღების და სანდო თანატოლების საკუთრების მტკიცებულებების მითითებებს.
- Torii და P2P პორტები ჯერ კიდევ არ არიან დაკავშირებულნი სხვა პროცესით.
- Kura მაღაზიების დირექტორი ერთსა და იმავე ქსელს ეკუთვნის და სხვა ქსელური პროფილისგან არ არის გაფორმებული.

გამოიყენეთ კონფიგურაციის თვალსაზრისი, როდესაც დეიმონი კითხულობს ერთზე მეტ TOML ფენას:

```bash
cargo run -p irohad --bin iroha3d -- --config ./config.toml --trace-config
```

## Docker და კომპოზიტი {#docker-and-compose}

გენერირება შეადგინეთ მიმდინარე Kagami ადგილობრივი ქსელის გამოშვებიდან, ასე რომ ბრძანების ხაზის არგუმენტები და კონფიგურაციის ფაილები შეესაბამებიან ამოღებულ კოდს:

```bash
cargo run --bin kagami -- localnet --peers 4 --out-dir ./localnet
cargo run --bin kagami -- docker --peers 4 --config-dir ./localnet --image hyperledger/iroha:dev --out-file ./docker-compose.yml --force
docker compose -f ./docker-compose.yml up
```

თუ კომპოზიციის განთავსება იწყება და შემდეგ ჩერდება, შეამოწმეთ დეიმონების ლოგები:

- არათანაბარი `chain`
- ერთი თანამოაზრე, რომელიც იყენებს განსხვავებულ გენეზის ტრანზაქციას ან მანიფესტს
- რეკლამირებული P2P მისამართები, რომლებიც მუშაობს მხოლოდ კონტეინერების ქსელში
- ადგილობრივი მოცულობის განმეორებითი გამოყენება გენეზის რეგენერაციის შემდეგ

ახალი გენეზის ტესტირებისას, ამოიღეთ ძველი Kura მოცულობები სადგურის განახლების წინ. ძველი ბლოკების შენახვა ახალ გენეზიასთან ერთად შეცვლის გათამაშებას.

## კუბერნეტები {#kubernetes}

Kubernetes- ისთვის, თითოეული ვალიდატორი განიხილეთ როგორც სახელმწიფოებრივი ინფრასტრუქტურა:

- აძლევს თითოეულ თანატოლს სტაბილური იდენტობის გასაღები და სტაბილურ მუდმივ მოცულობას
- გამოავლინოს P2P მისამართები, რომლებიც სხვა თანატოლებს შეუძლიათ გადაწყვიტონ კლასტერის შიგნით
- სამონტაჟო კონფიგურაცია და genesis ფაილები როგორც შეუცვლელი კონფიგურა განხორციელებისათვის
- ყველა გენეზიის ან ტოპოლოგიის ცვლილების განზრახ განხორციელება, არა როგორც ავტომატური კონფიგურაციის რუკის განახლება

თუ კადრი განმეორებით იწყება, შეადარეთ კადრში წარმოდგენილი კონფიგურაცია მოსალოდნელი [`peer.template.toml`](/ka/reference/peer-config/index.md#template) და შეამოწმეთ, განაახლებს თუ არა პერ ძველი Kura მონაცემები.

## Sora- ს პროფილი {#sora-profile}

Iroha 3 განთავსებები, რომლებიც იყენებენ Nexus, SoraFS ან მრავალგზის ნაკადებს, უნდა დაიწყონ დეიმონი Sora-ს პროფილის ჩართვით:

```bash
cargo run -p irohad --bin iroha3d -- --config ./config.toml --sora
```

გამოიყენეთ იგივე პროფილი მუდმივად ერთი და იმავე ქსელში არსებული ვალიდატორების შორის.
