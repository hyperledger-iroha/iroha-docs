# პრობლემების აღმოფხვრა კონფიგურაციის საკითხებში {#troubleshooting-configuration-issues}

აღნიშნული განყოფილება გთავაზობთ Iroha 3 კონფიგურაციის პრობლემების მოგვარების რჩევებს. დარწმუნდით, რომ თქვენ [შეამოწმე გასაღები.](./overview.md#check-the-keys) პირველ რიგში, რადგან ეს არის ყველაზე გავრცელებული პრობლემების წყარო Iroha.

თუ თქვენთან არსებული პრობლემა აქ არ არის აღწერილი, დაგვიკავშირდით [ტელეგრამი](https://t.me/hyperledgeriroha).

## მოძველებული ბლოკჩეინის გენეზისი Docker Compose დანერგვაზე {#outdated-genesis-on-a-docker-compose-setup}

როდესაც იყენებთ Docker Compose ვერსიას Iroha, თქვენ შეიძლება შეხვდეთ ქსელის ერთ-ერთი პარტნიორის კონტეინერის პრობლემას, რომელიც არ მუშაობს `Failed to deserialize raw genesis block` შეცდომით. ეს ჩვეულებრივ ნიშნავს, რომ ქსელის კვანძი, ხელმოწერილი ბლოკჩეინის გენეზისის ტრანზაქცია და წარმოებული კონფიგურაცია სხვადასხვა Iroha რევიზიების ან პროფილების მიერ იქნა შექმნილი.

ვალიდატორების ჟურნალების სანახავად ნაკრების საქაღალდიდან გაუშვით `python3 poc.py logs`. Docker-ში ერთი და იმავე რევიზიის ბინარული ფაილებით ოთხი ვალიდატორის ასაწყობად და გასაშვებად მიჰყევით სახელმძღვანელოს [გაშვება Iroha 3](/ka/get-started/launch-iroha.md).

იმავე ქსელის ხელახლა გასაშვებად გამოიყენეთ `python3 poc.py down` და შემდეგ `python3 poc.py up`. შეინახეთ `state/` მის ოთხ Docker ტომთან ერთად.

::: info

არ არსებობს საერთო ავტომატური გადაწერის გზა ცოცხალ ქსელში ბლოკჩეინის წარმოქმნის შესაცვლელად. განიხილეთ ეს როგორც კოორდინირებული მიგრაცია: შეინარჩუნეთ ძველი მდგომარეობა, შეიყვანეთ თავსებადი ქსელის კვანძეები და მხოლოდ მას შემდეგ გადაიტანეთ დამტკიცებლები ახალ კონფიგურაციას, რაც ოპერატორები მიგრაციის გეგმაზე შეთანხმდებიან.

:::

## პირადი და საჯარო გასაღების მრავალფუნქციური ფორმატი {#multihash-format-of-private-and-public-keys}

თუ შეხედავთ [კლიენტის კონფიგურაცია](/ka/guide/configure/client-configuration.md), აღნიშნავთ, რომ მის გასაღები მოცემულია [მრავალფუნქციური ფორმატი](https://github.com/multiformats/multihash)-ში.

თუ თქვენ არასდროს მუშაობდით მულტი-ჰეშით ადრე, ბუნებრივია ვივარაუდოთ, რომ მარჯვენა მხარე არ არის ექსადეციმალი საკვანძო ბაიტების წარმოდგენა (ორი სიმბოლო ბიტზე), არამედ ბაიტები, რომლებიც კოდირებულია როგორც: ASCII (ანუ UTF-8), და იწვევს `from_hex` ლიტერატურული სტრიქონის ორივე `public_key` და `private_key` აჟიოტაჟი.

ბუნებრივია იფიქროთ, რომ სტრიქონულ ლიტერალზე `PrivateKey::try_from_str` მხოლოდ სწორ გასაღებს დააბრუნებს და არასწორი სიგრძე — მაგალითად, 32 ბაიტი 64-ის ნაცვლად — შეცდომას გამოიწვევს.

სამწუხაროდ, შეცდომათა შეტყობინებები არ ეხმარება ამ კონკრეტულ ტიპის წარუმატებლობის აღმოფხვრაში.

როგორ დავასწოროთ: გამოიყენეთ `hex_literal`. ეს ასევე შეცვლის უხეში სიმბოლოების სტრიქონს ლამაზ პატარა ცხრილში, რომელიც აშკარად ექვსმეტი რიცხვია.

::: warning

თუნდაც `try_from_str` განხორციელება ვერ შეამოწმებს, არის თუ არა მოცემული სტრიკი მოქმედი `PrivateKey` და გაფრთხილებთ თუ ეს არ არის.

იგი აღმოაჩენს გარკვეულ აშკარა შეცდომებს, მაგალითად, თუ სტრიკი შეიცავს არასწორ სიმბოლოს. თუმცა, ვინაიდან ჩვენ მიზნად ისახავთ მრავალი საკვანძო ფორმატის მხარდაჭერას, ის ბევრი სხვა რამ ვერ გააკეთებს. მას არ შეუძლია გაიგოს, არის თუ არა გასაღები სწორი კერძო გასაღები მოცემული ანგარიშისთვის, თუ თქვენ წარუდგენთ ინსტრუქციას.

:::

ამგვარი ფირფიტური შეცდომები შეიძლება თავიდან იქნას აცილებული, მაგალითად, პირდაპირ დესერიალიზაციის გზით სტრიქონის ლიტერალებიდან ან ახალი საკვანძო წყვილის შექმნით იმ ადგილებში, სადაც ეს აზრი აქვს.
