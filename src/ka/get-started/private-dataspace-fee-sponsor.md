# კერძო მონაცემთა სივრცის საკომისიოს სპონსორობა {#sponsor-fees-for-a-private-data-space}

SORA Nexus საკომისიოს სპონსორის პროგრამას შეუძლია გადაიხადოს კერძო მონაცემთა სივრცეში მარშრუტებული დასაშვები ტრანზაქციების გლობალური შესრულების საკომისიო. მომხმარებელი კვლავ მთელ ტრანზაქციას აწერს ხელს. მისი ტიპიზებული `FeePaymentIntent` ირჩევს ზუსტ სპონსორის პროგრამასა და უცვლელ რევიზიას, საჭიროებისას gas ზღვარს და მაქსიმალურ გადასახადებს.

მონაცემთა სივრცის კატალოგის ჩანაწერი დამოუკიდებლად ხელმოწერილ ფესვს არ ქმნის. დამოუკიდებელ მონაცემთა სივრცის ფესვს თავისი დამტკიცებული საკომისიო ვალუტა და პოლიტიკა აქვს; საჯარო სპონსორის საცავები მის კერძო ფესვის საკომისიოს უფლებამოსილებას ვერ ანიჭებს. სპონსორობის დაგეგმვამდე განსაზღვრეთ შესრულების ფესვი.

## 1. დამტკიცებული საკომისიო პოლიტიკის განსაზღვრა {#_1-establish-the-committed-fee-policy}

ხელმოწერილი გენეზისი განსაზღვრავს ერთ `root_fees_v1` სპეციალურ პარამეტრს, რომელიც `RootFeePolicy`-ს შეიცავს. ის აკავშირებს საკომისიო ვალუტას, საკომისიოს მიმღებს, სპონსორის თანხის დაცული შენახვის ანგარიშს, მოთხოვნების გამონაკლისებსა და ტარიფებს. ყოველი ჩვეულებრივი ბლოკი და ფასის გამოთვლა თავის დაფიქსირებულ დამტკიცებულ პოლიტიკას იყენებს. უფლებამოსილი პოლიტიკის განახლებები მომდევნო ბლოკიდან მოქმედებს.

გლობალური შესრულებისთვის ნატიური საკომისიო წვავს ხელმოწერაში ზუსტად მითითებულ ქსელის XOR ვალუტას. ამ ვალუტას სპონსორის პროგრამის საცავი აწვდის. კვანძის პარამეტრები და ტრანზაქციის მეტამონაცემები გადამხდელს არ ირჩევს და სპონსორობას არ ააქტიურებს.

გამოიყენეთ ქსელის კანონიკური ვალუტისა და ანგარიშის იდენტობები. ფსევდონიმის ამოხსნამ დამტკიცებული ვალუტის, დაცული შენახვის ან საკომისიოს მიმღების იდენტობები არ უნდა გადაამისამართოს.

## 2. სპონსორის პროგრამის შექმნა და დაფინანსება {#_2-create-and-fund-a-sponsor-program}

პროგრამის ID-ს აქვს ფორმა `<canonical-sponsor-account>/<program-name>`. მოამზადეთ იგი მიმდინარე SDK-ისა და მონაცემთა მოდელის ტიპიზებული ინსტრუქციებით:

| ინსტრუქცია | დანიშნულება |
| --- | --- |
| `CreateFeeSponsorProgram` | მომზადებულ მდგომარეობაში პროგრამის შექმნა მისი სავალდებულო თანხის გასატანი ანგარიშით. |
| `StageFeeSponsorProgramRevision` | ერთი უცვლელი დასაშვებობის, ოპერაციებისა და ბიუჯეტის პოლიტიკის განსაზღვრა. |
| `EnrollFeeSponsorBeneficiary` | დასაშვები ბენეფიციარის ჯაჭვში აღრიცხვა. |
| `FundFeeSponsorProgram` | აქტივების დაცულ შენახვაში გადატანა და ზუსტი პროგრამის საცავზე დარიცხვა. |
| `ActivateFeeSponsorProgramRevision` | მომზადებული რევიზიის ყველაზე ადრეული აქტივაციის სიმაღლის დაგეგმვა. |

პროგრამის ადმინისტრირებას სპონსორი ან ზუსტად დელეგირებული მმართველი ანიჭებს უფლებამოსილებას. თანხის გატანას თავად სპონსორი სჭირდება და თანხა მხოლოდ პროგრამაში აღრიცხულ გასატან ანგარიშზე ბრუნდება, როცა პროგრამა შეჩერებულია ან დახურვის პროცესშია.

ყოველი რევიზია განსაზღვრავს:

- აშკარა რეგისტრაციას ან რეგისტრაციას ნებადართულ მარშრუტის ნაგულისხმევ დასაშვებობასთან ერთად;
- დაშვებისა და აკრძალვის წესებს ზუსტი ნატიური ინსტრუქციის გადაცემის ID-ებისთვის ან კონტრაქტის მისამართებისთვის, კოდის ჰეშებისა და შესასვლელი წერტილებისთვის;
- თითო აქტივზე ტრანზაქციის, ბლოკის, პროგრამის ეპოქისა და ბენეფიციარის ეპოქის ზღვრებს;
- რეზერვის ქვედა ზღვარსა და ეპოქის დეტერმინისტულ სიგრძეს.

აკრძალვის წესი დაშვების წესზე პრიორიტეტულია. მონაცემთა სივრცის `fee_sponsor_program_id` მარშრუტის ნაგულისხმევ დასაშვებობას მხოლოდ მაშინ იძლევა, როცა აქტიური რევიზია ამას ნებას რთავს; ტრანზაქციამ მაინც ზუსტი პროგრამა და რევიზია უნდა დაასახელოს. აქტივაცია შეიძლება გადაიდოს, სანამ წინა რევიზიის დარჩენილ გამოყოფებს ვადა არ გაუვა.

სპონსორის საცავის აქტივებმა `Global` ბალანსის პოლიტიკა უნდა გამოიყენოს. მხოლოდ სპონსორის ჩვეულებრივი ანგარიშის დაფინანსება იზოლირებულ პროგრამის საცავს არ აფინანსებს და ერთი პროგრამა მეორის ბალანსს ვერ მოიხმარს.

## 3. ზუსტი ტრანზაქციის ფასის გამოთვლა, ხელმოწერა და გაგზავნა {#_3-quote-sign-and-submit-the-exact-transaction}

SDK ინტეგრაცია ასრულებს შემდეგ ნაბიჯებს:

1. შექმენით ხელმოუწერელი `TransactionPayload` უფლებამოსილი სუბიექტით, შესასრულებელი შიგთავსით, დროის ნიშნულებით, nonce-ით, მეტამონაცემებით, სპონსორის პროგრამის ზუსტი რევიზიითა და საჭირო gas ზღვრით. მაქსიმალური გადასახადები თავდაპირველად შეიძლება ცარიელი იყოს.
2. ანგარიშის ხელმოწერით გაგზავნეთ `POST /v1/fees/quote` მოთხოვნა `{"payload": <payload>}`-ით. მოთხოვნის ხელმომწერი ტრანზაქციის უფლებამოსილი სუბიექტი უნდა იყოს.
3. შეამოწმეთ დაკვირვებული სიმაღლე, ამოხსნილი მონაცემთა სივრცის მარშრუტი, საკომისიოს კომპონენტები, ჩამოჭრის წყარო და სპონსორის ტევადობა. დარწმუნდით, რომ პასუხი არჩეულ გადამხდელს, რევიზიასა და gas ზღვარს ინარჩუნებს.
4. მხოლოდ `payload.fee_payment` შეცვალეთ რეკომენდებული განზრახვით, შემდეგ ხელი მოაწერეთ და გაგზავნეთ ზუსტად ეს დატვირთვა.
5. ტრანზაქციას მიჰყევით მდგომარეობით განსაზღვრულ `Applied` საბოლოო დადასტურებამდე და შეინახეთ მისი ქვითარი, რეალური სპონსორის პროგრამის, რევიზიისა და საკომისიოს ჩათვლით.

ფასის გამოთვლა რეესტრს აკვირდება; ტევადობას არ არეზერვებს. რიგში დაშვება დასაშვებობას ხელახლა ამოწმებს და ხელმოწერილ მაქსიმუმებს არეზერვებს. სპონსორის უარი ტრანზაქციას უარყოფს და მომხმარებლისთვის თანხის დაკისრებაზე არ გადადის.

CLI იგივე საკომისიოს წყაროს აშკარად უთითებს. მაგალითად, მას შემდეგ, რაც პროგრამა ზუსტად ამ აქტივის გადარიცხვას დაუშვებს და ანგარიში დასაშვები იქნება:

```bash
iroha --config ./user.client.toml \
  --fee-payer sponsor \
  --fee-program '<SPONSOR_CANONICAL_I105>/team-payments' \
  --fee-program-revision 1 \
  ledger asset transfer \
  --definition '<ASSET_DEFINITION_BASE58>' \
  --account '<USER_CANONICAL_I105>' \
  --to '<RECIPIENT_CANONICAL_I105>' \
  --quantity 1
```

გამოიყენეთ თქვენი ქსელის აქტიური რევიზია და ზუსტი იდენტიფიკატორები. მომხმარებლის კონფიგურაცია მხოლოდ ამ მომხმარებლის ხელმომწერს შეიცავს; დასაშვები დასპონსორებული ტრანზაქციის გასაგზავნად სპონსორის კერძო გასაღები საჭირო არ არის.

## 4. გადაწყვიტეთ, იხდის თუ არა მომხმარებელი აპლიკაციის საკომისიოს {#_4-decide-whether-the-user-pays-an-application-fee}

სპონსორს შეუძლია გლობალური საკომისიოს დაფარვა ისე, რომ აპლიკაციამ მომხმარებელს არაფერი გადაახდევინოს. თუ აპლიკაცია ლოკალურ ტოკენს იღებს, შესაბამისი გადარიცხვა ან კონტრაქტის წესი აშკარად ჩაწერეთ მომხმარებლის ხელმოწერილ შესასრულებელ შიგთავსში. ყველა ოპერაცია შეიტანეთ სპონსორის რევიზიის პოლიტიკაში და სრული დატვირთვის ფასი შეამოწმეთ. ქსელის საკომისიოს განზრახვიდან აპლიკაციის ტოკენის გადარიცხვას ნუ ივარაუდებთ.

## უარის მიზეზის დიაგნოსტიკა {#diagnose-a-refusal}

გამოიყენეთ კვანძის მიერ დაბრუნებული საკომისიოს სტაბილური კოდი და გამოსწორების დეტალები:

| კოდი | შესამოწმებელი |
| --- | --- |
| `program_not_found` | პროგრამის ზუსტი კანონიკური იდენტობა. |
| `revision_not_active`, `program_not_active` | რევიზიის აქტივაცია და პროგრამის სასიცოცხლო ციკლი. |
| `beneficiary_not_eligible` | რეგისტრაცია ან ნებადართული მარშრუტის ნაგულისხმევი დასაშვებობა. |
| `operation_not_allowed`, `operation_denied` | ყოველი ზუსტი ხელმოწერილი ოპერაცია და აკრძალვის წესი. |
| `invalid_gas_limit`, `signed_limit_exceeded` | gas ზღვარი და ხელმოწერილი მაქსიმუმები ახალ ფასთან შედარებით. |
| `vault_insufficient` | ამ პროგრამის ზუსტი ვალუტის საცავის დაფინანსებული ბალანსი. |
| ბიუჯეტის ამოწურვის კოდები | ტრანზაქციის, ბლოკის, პროგრამის ეპოქისა და ბენეფიციარის ეპოქის ტევადობა. |

ბუნდოვანი გაგზავნის გამოძიებისას შეინახეთ თავდაპირველი ტრანზაქციის ჰეში და საკომისიოს უარის დეტალები. შემცვლელის აგებამდე მისი მდგომარეობა დაადასტურეთ.
