# ოპერაციები {#transactions}

ტრანზაქცია არის ხელმოწერილი თხოვნა, რათა შესრულდეს მუშაობა ბლოკჩეინზე. განსახორციელებელი დატვირთვა შეიძლება იყოს [ინსტრუქციები](./instructions.md) შეკვეთილი თანმიმდევრულობა, ხელშეკრულების ტექნიკური მოწოდება, IVM ბიტკოდი ან დამტკიცებული IVM შესრულება. იხილეთ [ჭკვიანი ხელშეკრულებები](./smart-contracts.md) მიმდინარე ხელშეკარგვის შესრულების მოდელისთვის.

ტრანზაქციები ახორციელებს სახელმწიფოს შეცვლას ან განხორციელებადი სამუშაოს. მხოლოდ წაკითხვის ინსპექტირება იყენებს ხელმოწერილი მოთხოვნებს ან საჯაროდ წაკითხული API საბოლოო წერტილებს და არ ქმნის ტრანზაკციას.

საბოლოო ბლოკში მიღებული ტრანზაქცია ინახება მისი შესრულების შედეგით, მათ შორის განხორციელების უარყოფითი. ბლოკის შესვლამდე უარყოფილი მოთხოვნები, როგორიცაა არასწორი მონაცემთა კონტეინერი ან რიგის მიერ უარი თქმული ტრანზაკცია, არ ინახება ბლოკზე.

პირადი ცხოვრების დაცვის აქტივების მოძრაობის შესახებ იხილეთ [ანონიმური ოპერაციები](./anonymous-transactions.md). ანონიმური ტრანზაქციები საჯარო ანგარიშზე ბალანსის ცვლილებების ნაცვლად იყენებენ დაფარულ აქტივებზე, კრიპტოგრაფიული ვალდებულებების ღირებულებებზე, გაუქმებლებსა და ნულოვანი ცოდნის მტკიცებულებებზე.

დეტერმინისტური მტკიცებულებების შესახებ ცალკეული გამჭვირვალე შესრულების ეფექტი იხილეთ [FastPQ](./fastpq.md). FastPQ იყენებს აღსრულების მოწმეებს ჩვეულებრივი ტრანზაქციის შესრულების შემდეგ და აგებს დეტერმინისტურ მტკიცებულებათა პარტიებს მხარდაჭერილი სახელმწიფო გარდაქმნებისთვის.

## განახორციელეთ ეს სამუშაო პროცესი Taira {#try-it-on-taira}

გამოიყენეთ Explorer-ის მარშრუტები, რათა შეამოწმოთ ბოლო საჯარო Taira ბლოკები და ტრანზაქციების სტატუსი ხელმოწერის ანგარიშით:

```bash
curl -fsS 'https://taira.sora.org/v1/explorer/blocks?page=1&per_page=3' \
  | jq '{pagination, blocks: [.items[] | {height, hash, transactions_total, transactions_rejected}]}'

curl -fsS 'https://taira.sora.org/v1/explorer/transactions?page=1&per_page=5' \
  | jq '{pagination, txs: [.items[] | {hash, block, status, executable}]}'
```

თქვენი აპლიკაციის მიერ წარდგენილი ტრანზაქციის დასაკვალიერებლად, გადაწერეთ `hash` ჩამონათვალიდან და შეამოწმეთ Explorer- ის დეტალური მარშრუტი:

```bash
TX_HASH='<transaction-hash>'

curl -fsS "https://taira.sora.org/v1/explorer/transactions/$TX_HASH" \
  | jq '{hash, block, status, authority, executable}'
```

ტრანზაქციის წარდგენა საჭიროა Norito მონაცემთა კონტეინერის ხელმოწერა, სწორი ჯაჭვის ID, გადასახადის მეტამონაცემები და სატესტო ქსელი-ის მიერ დაფინანსებული Taira ანგარიში.

Taira-ზე საკომისიოს გადამხდელი მაგალითებისთვის [Taira-ზე სატესტო XOR-ის მიღების](/ka/get-started/sora-nexus-dataspaces.md#_4-get-testnet-xor-on-taira) დამხმარე სკრიპტი შეინახეთ როგორც `taira_faucet_claim.py`, შემდეგ კი ხელმომწერის ანგარიში ჯერ საჯარო გამცემიდან დააფინანსეთ:

```bash
export TAIRA_ACCOUNT_ID='<TAIRA_I105_ACCOUNT_ID>'
export TAIRA_FEE_ASSET=6TEAJqbb8oEPmLncoNiMRbLEK6tw

curl -fsS https://taira.sora.org/v1/accounts/faucet/puzzle | jq .
python3 taira_faucet_claim.py "$TAIRA_ACCOUNT_ID"

iroha --config ./taira.client.toml ledger asset get \
  --definition "$TAIRA_FEE_ASSET" \
  --account "$TAIRA_ACCOUNT_ID"
```

თუ ტესტური მონეტების გამცემის პაზლი ან მოთხოვნის მარშრუტი `502` დაბრუნდება, ელოდეთ და კიდევ ერთხელ შეეცადეთ თვითონ ტრანზაქციის დებეგირება.

შემდეგ, ტრანზაქციის წარდგენისას მიაერთეთ Taira საფასურის აქტივის მეტადატატი:

```bash
printf '{"gas_asset_id":"%s"}\n' "$TAIRA_FEE_ASSET" > taira.tx-metadata.json

iroha --config ./taira.client.toml \
  --metadata ./taira.tx-metadata.json \
  ledger transaction ping --msg "faucet-funded taira transaction"
```

## ქსელგარეშე ტრანზაქციები {#offline-transactions}

Iroha აქვს ორი ოფლაინ ტრანზაქციის სამუშაო ნაკადი:

- ქსელგარეშე ხელმოწერა ქმნის ჩვეულებრივი ხელმოწერილი ტრანზაქცია, სანამ ხელმოწერის მოწყობილობა გათიშულია. ტრანზაკცია არ დამუშავდება მანამ, სანამ ონლაინ კლიენტი არ წარუდგენს ხელმოწერილ მონაცემთა კონტეინერს Torii, ასე რომ მას მაინც სჭირდება სწორი ჯაჭვის ID, ავტორიზაციის პრინციპალი, ნებართვები, გადასახადები, და ტრანზაქციის სიცოცხლე.
- კაგემუშა ოფლაინ ფულადი თანხა საფულის თავზე აყენებს, როდესაც ის ონლაინ არის, მხარს უჭერს მიმღებელის მიერ დაწყებულ საფულე-საფულე გადაცემას ორივე საფულის გარეშე ყოფნის დროს და გამოსდის შედეგად მიღებული შენიშვნების მდგომარეობას, როდესაც მიმღებელს ონლაინ ბრუნდება.

Torii ასახავს კაგემუშას სიცოცხლის ციკლს სრულად `/v1/offline/*`:

|მეთოდი და API საბოლოო |მიზანი |
| --- | --- |
|`GET /v1/offline/readiness` |შეაფასეთ Kagemusha მზადყოფნა ერთი `asset_definition_id` |
|`POST /v1/offline/receiver-lineage` |დარეგულირდება აქტიური რეგისტრაციის მტკიცებულების მქონე გვარობა ხელმოწერილი მიმღები მოთხოვნისათვის |
|`POST /v1/offline/top-up` |წარადგინეთ ხელით გაფორმებული ონლაინ-ოფლაინ ოპერაცია |
|`POST /v1/offline/redeem` |წარადგინეთ ოფლაინ გადახდის ოპერაცია. |
|`GET /v1/offline/operations/{operation_id}` |წაიკითხეთ კანონიკური სტატუსი დამატების ან გადახდის |

შეამოწმეთ აქტივის მზადყოფნა ოპერაციის ოფლაინ განხორციელების წინ:

```bash
curl -fsS --get https://taira.sora.org/v1/offline/readiness \
  --data-urlencode 'asset_definition_id=<canonical_asset_definition_id>' \
  | jq '{ready, blockers, artifact_set}'
```

მზადყოფნა აკავშირებს საფულეს აქტიურ ხიდთან ABI 21 და დამოწმებული V4 არტეფაქტის კომპლექტი. გვარის, დამატების და გამოსასყიდის მოთხოვნები გამოიყენება ტიპირებული `application/x-norito` არქივები. აღდგენა და გამოსასყიდი დაბრუნება `202 Accepted` ა `Location` სათაური, რომელიც მიუთითებს ოპერაციის რესურსზე; ჩაშენებული ნულოვანი ოპერაციის ID უზრუნველყოფს idempotency გასაღების.

ტიპიური ნაკადი არის:

1. შეკითხვა მზადყოფნა და შეჩერება, თუ `ready` არის ცრუ ან რომელიმე ბლოკერი გამოიყენება.
2. გამოიყენეთ Swift ან JVM ტიპირებული საფულე, რათა შეიქმნას კანონიკური დამატებითი არქივი, წარადგინოთ იგი და შეინახოთ როგორც შესასვლელი ჩანაწერის მდგომარეობა, ასევე ოპერაციის ID სანამ ოპერაცია მიაღწევს საბოლოო ჯაჭვის მდგომარეობას.
3. საჭიროების შემთხვევაში გადაწყვიტეთ მიმღებელის რეგისტრაციის გვარები, შეადგინეთ და შემოწმეთ თითოეული ქსელის კვანძური გადაცემა ადგილობრივად და გააგრძელეთ კოდირებული ნოტის მდგომარეობა გადაცემის აღიარებამდე.
4. როდესაც მიმღები ონლაინშია, შეიქმნას კანონიკური გამოსყიდვის არქივი, წარუდგინოს იგი და გამოკითხვა მისი ოპერაციული რესურსი საბოლოო.

ბლოკჩეინის რეესტრი ვერ შეამოწმებს კონფლიქტურ ოფლაინ გადაცემას მანამ, სანამ შენიშვნების მდგომარეობა ონლაინ ცხოვრების ციკლის განმავლობაში არ დაბრუნდება. ამდენად ქაღალდის და ოპერატორის პოლიტიკა უნდა ახორციელოს ღირებულების ლიმიტები, ვადის ამოწურვა, მიღებული ემიტენტები, მდგრადი ადგილობრივი შენახვა და შერიგების ფანჯრები.

აქ მოცემულია ახალი გარიგების შექმნის მაგალითი `Grant` ინსტრუქციის გამოყენებით. ამ გარიგებაში, Mouse აძლევს Alice მითითებულ როლს (`role_id`). შეამოწმეთ [სრული მაგალითი](./permissions.md#register-a-new-role).

```rust
let grant_role = Grant::account_role(role_id, alice_id);
let grant_role_tx = TransactionBuilder::new(chain_id, mouse_id)
    .with_instructions([grant_role])
    .sign(mouse_private_key);
```
