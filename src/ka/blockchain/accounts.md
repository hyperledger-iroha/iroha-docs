# ანგარიშები {#accounts}

ანგარიში არის ავტორიტეტი, რომელსაც შეუძლია ხელი მოაწეროს ტრანზაქციებს და საკუთარი ბუღალტრული მდგომარეობა.
ამჟამად Iroha 3 მონაცემთა მოდელი, `AccountId` არის კანონიკური და დომენის გარეშე:
ის არის მიღებული ანგარიშის კონტროლისგან და კოდირებულია კანონიკურად როგორც I105.
ადამიანის მიერ წაკითხული დომენი და მონაცემთა სივრცის კონტექსტი შედის ცალკეულ ანგარიშებზე
ბმულები.

## სტრუქტურა {#structure}

დარეგისტრირებული `Account` შეიცავს:

- `id`: კანონიკური `AccountId`
- `metadata`: ანგარიშის არჩევითი მეტა მონაცემები
- `label`: სტაბილური ალექსანდრე
- `uaid`: ვარიანტური უნივერსალური ანგარიში ID გამოყენებული Nexus ნაკადები
- `opaque_ids`: ანგარიშის მონაცემებთან დაკავშირებული არაგამჭვირვალე იდენტიფიკატორები UAID

ანგარიშის შექმნაში გამოყენებული ტრანზაქციის სასარგებლო ტვირთი არის `NewAccount`. ატარებს
იგივე იდენტობა, მეტა მონაცემები, ეტიკეტი; UAID, და არაგამჭვირვალე ID გამოყენებული ველები
რეგისტრირებული ანგარიში.

`uaid` სრულდება კანონიკური `AccountId`; ნვ დჲ ნაოპაგთ.
როდესაც Nexus სერვისებს სჭირდებათ სტაბილური მომხმარებელი ან ორგანიზაციის მენეჯერი
მონაცემთა სივრცეები, კონფიდენციალურობის შენარჩუნების რეგისტრაცია ან მომსახურების შესაძლებლობების შესწავლა.
runtime ინარჩუნებს ერთი-ერთ UAID-საკონტო ინდექსი, საჭიროებს არაპროკაზმულ იდენტიფიკატორებს
დამაკავშირებელი საიტი UAID, და უარყოფს ორმაგი ან შეჯახების არაპრომანენტულ
იდენტიფიკატორები. იხილეთ
[FHE და UAID](/ka/blockchain/sora-nexus-services.md#fhe-and-uaid) სამინისტრო Nexus
მომსახურების ფენის ნაკადი.

## ანგარიშის კონტროლერები {#account-controllers}

კონტროლერი განსაზღვრავს, თუ როგორ ავტორიზებს ანგარიში ქმედებები.
ნაკადი იყენებს Ed25519 საკვანძო წყვილი, მაგრამ მონაცემთა მოდელი ასევე მხარს უჭერს მდიდარი
კონტროლერები, როგორიცაა მრავალხელმოწერის პოლიტიკა კონტროლერი.

კლიენტის კონფიგურაცია ინახავს ხელმოწერის ავტორიტეტს ცალკე თანატოლებისგან
კონფიგურაცია:

```toml
[account]
public_key = "ed0120..."
private_key = { digest_function = "ed25519", payload = "..." }
```

იხილეთ [კლიენტის კონფიგურაცია](/ka/guide/configure/client-configuration.md) და
[მთავარი თაობა](/ka/guide/security/generating-cryptographic-keys.md) სამინისტრო
ამჟამინდელი საკვანძო ფორმატი.

## სცადე. Taira {#try-it-on-taira}

რამდენიმე კანონიკური ცნობის ჩამონათვალი IDs საზოგადოებისგან Taira სატესტო ქსელი:

```bash
curl -fsS 'https://taira.sora.org/v1/accounts?limit=5' \
  | jq -r '.items[] | [.id, (.primary_alias // "-")] | @tsv'
```

ანგარიშის აქტივების შესამოწმებლად, გადაწერეთ ანგარიში ID პირველი ზარიდან და URL-კოდირება
მანამდე, სანამ გზას არ დაუშვებდი. Python ნაწილის პირველი აკეთებს, რომ
რეგისტრირებული ანგარიში:

```bash
python3 - <<'PY'
import json
import urllib.parse
import urllib.request

root = "https://taira.sora.org"
accounts = json.load(urllib.request.urlopen(f"{root}/v1/accounts?limit=1"))["items"]
account_id = accounts[0]["id"]
encoded = urllib.parse.quote(account_id, safe="")
assets = json.load(
    urllib.request.urlopen(f"{root}/v1/accounts/{encoded}/assets?limit=5")
)

print(json.dumps({"account_id": account_id, "assets": assets["items"]}, indent=2))
PY
```

ეს არის საჯარო წაკითხვები. ანგარიშის შექმნა ან განახლება ხელმოწერილი ოპერაციაა
და მოითხოვს საბანქის ფინანსური Taira განლაგება აღწერილია
[შეხება SORA Nexus მონაცემთა ბაზები](/ka/get-started/sora-nexus-dataspaces.md).

## რეგისტრაცია და ნებართვები {#registration-and-permissions}

ანგარიშები რეგისტრირებულია და არ არის რეგისტრებული გენერიკთან
[`Register` და `Unregister`](/ka/blockchain/instructions.md#un-register)
ინსტრუქციები. აქტიური runtime Validator გადაწყვეტს ვინ შეიძლება შექმნას ანგარიშები
და რა ნებართვის ტოქნები ან როლები საჭიროა.

რეგისტრაციის შემდეგ ანგარიშს შეუძლია:

- ტრანზაქციების გაფორმება
- ქონება
- საკუთარი დომენები
- მიიღოს როლები და ნებართვის ნიშნები
- შენახვის მეტა მონაცემები
- მონაწილეობა მიიღოს ანალოგიურ, რეკეი, აღდგენა და Nexus იდენტობა მიედინება, როდესაც ისინი
  მახასიათებლები ჩართულია

## პრობლემების აღმოფხვრა იდენტობის საკითხებში {#troubleshooting-identity-issues}

თუ ტრანზაქცია მოულოდნელად უარყოფითია, შეამოწმეთ:

- კლიენტის საჯარო გასაღები შეესაბამება ხელმოწერისთვის გამოყენებულ კერძო გასაღებს
- ანგარიში დარეგისტრირდა გენეზის ან ჩაბარებული ოპერაციის შედეგად
- ორგანოს აქვს ინსტრუქციის მიერ მოთხოვნილი ნებართვები
- მკაცრი ანგარიშის ველები იყენებენ კანონიკურ I105 ანგარიში ID, წაკითხული,
  სახელები გადაწყდება აქტიური ანგარიშის ანალიზის საშუალებით
