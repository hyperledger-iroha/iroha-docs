# ანონიმური ტრანზაქციები {#anonymous-transactions}

Iroha-ში ანონიმური ტრანზაქციები კონფიდენციალური აქტივების ოპერაციებზეა აგებული. საჯარო თანხით ანგარიშებს შორის საჯარო გადარიცხვის ჩაწერის ნაცვლად, საფულე ღირებულებას დაფარულ რეესტრში გადააქვს და შემდეგ გაუმჭვირვალე ჩანაწერებს ნულოვანი ცოდნის მტკიცებულებებით ხარჯავს.

საჯარო რეესტრი კონფიდენციალური ოპერაციის ფაქტს მაინც აღრიცხავს. მასში ინახება ვალდებულებები, ნულიფიკატორები, მტკიცებულების ჰეშები და მოვლენები, თუმცა დაფარულ ანგარიშებს შორის მოძრაობისთვის ჩანაწერის მფლობელი, მიმღები და თანხა არ იწერება. ტრანზაქციის ჩვეულებრივ მონაცემთა კონტეინერს წარმდგენი ანგარიში შეიძლება მაინც გაემჟღავნებინა, ამიტომ „ანონიმური“ აქ აქტივის ანონიმურ მოძრაობას ნიშნავს და არა ავტომატურ ანონიმურობას ქსელის ან ანგარიშის დონეზე.

## ძირითადი კომპონენტები {#building-blocks}

|ცნება |რეესტრში წარმოდგენა |
| ------------------ | ------------------------------------------------------------------------------------------------------------------ |
|დაფარული ჩანაწერი |საფულის დახურული ჩანაწერი, რომელიც აქტივს, თანხას, მფლობელის მონაცემებსა და შემთხვევით მნიშვნელობას შეიცავს. |
|კრიპტოგრაფიული ვალდებულება |32-ბაიტიანი საჯარო მნიშვნელობა, რომელიც ჩანაწერს მისი ველების გამჟღავნების გარეშე აკავშირებს. |
|ნულიფიკატორი |ჩანაწერის დახარჯვისას მიღებული 32-ბაიტიანი საჯარო მნიშვნელობა. ორმაგი ხარჯვის თავიდან ასაცილებლად Iroha განმეორებულ ნულიფიკატორს უარყოფს. |
|მერკლის ფესვი |აქტივის ვალდებულებათა ხის უახლესი ფესვი. მტკიცებულებები მისი მეშვეობით აჩვენებს, რომ დახარჯული ჩანაწერები არსებობს. |
|მტკიცებულების დანართი |`ProofAttachment`, რომელიც მტკიცებულების ბაიტებს და ვერიფიკაციის გასაღების მითითებას ან ჩადგმულ ვერიფიკაციის გასაღებს შეიცავს. |
|კონფიდენციალური მოვლენა |რეესტრის მოვლენა, მაგალითად `ConfidentialEvent::Shielded`, `Transferred` ან `Unshielded`. |

ძირითადი ინსტრუქციები:

- `RegisterZkAsset`: აქტივს ZK-ის მხარდამჭერად არეგისტრირებს და გადარიცხვის, დაფარვისა და დაფარვის მოხსნის ვერიფიკაციის გასაღებებს უკავშირებს.
- `Shield`: საჯარო ნაშთს აკლებს თანხას და დაფარული ჩანაწერის ვალდებულებას ამატებს.
- `ZkTransfer`: დაფარულ ჩანაწერებს ხარჯავს და ახალი დაფარული ჩანაწერების ვალდებულებებს ქმნის.
- `Unshield`: დაფარულ ჩანაწერებს ხარჯავს და საჯარო ანგარიშის ნაშთს ზრდის.
- `ScheduleConfidentialPolicyTransition` და `CancelConfidentialPolicyTransition`: აქტივის კონფიდენციალურობის პოლიტიკას მმართველობის მეშვეობით ცვლის.

აქტივის განსაზღვრა ასევე შეიცავს [`AssetConfidentialPolicy`](/ka/reference/data-model-schema.md)-ს. პოლიტიკის რეჟიმი განსაზღვრავს, რომელი ნაკადებია დაშვებული:

|რეჟიმი |მნიშვნელობა |
| ----------------- | ---------------------------------------------------------------- |
|`TransparentOnly` |მიღებულია მხოლოდ ჩვეულებრივი საჯარო ბალანსი და გადარიცხვები. |
|`Convertible` |მომხმარებელს შეუძლია ღირებულება საჯარო ნაშთებსა და დაფარულ ჩანაწერებს შორის გადაიტანოს. |
|`ShieldedOnly` |აქტივის გამოშვება და გადარიცხვა დაფარულ რეესტრში უნდა დარჩეს. |

## როგორ გამოვიყენოთ ისინი {#how-to-use-them}

1. ვალიდატორის კვანძებზე კონფიდენციალური ოპერაციების მხარდაჭერა ჩართეთ. ვალიდატორები უნდა შეთანხმდნენ მტკიცებულების ბეკენდზე, მოქმედ ვერიფიკაციის გასაღებებზე, Poseidon/Pedersen-ის პარამეტრების ID-ებსა და კონფიდენციალურობის წესების ვერსიაზე. კვანძი შეუსაბამო კონფიდენციალური შესაძლებლობების დიჯესტის მქონე კვანძს ან ბლოკს უარყოფს.
2. წრედების მიერ გამოყენებული ვერიფიკაციის გასაღებები და პარამეტრების ნაკრებები გამოაქვეყნეთ ან დაარეგისტრირეთ. საფულეებმა და ოპერატორებმა გასაღებებს `VerifyingKeyId`-ით უნდა მიმართონ, მაგალითად `halo2/ipa:vk_transfer`.
3. აქტივი `RegisterZkAsset`-ით ZK-ის მხარდამჭერად დაარეგისტრირეთ, ან პოლიტიკა `TransparentOnly`-იდან `Convertible`-ზე ან `ShieldedOnly`-ზე გადაიყვანეთ.
4. საჯარო თანხა `Shield`-ით დაფარეთ. ტრანზაქციის წარდგენამდე საფულე მიმღებისთვის ჩანაწერის ვალდებულებასა და დაშიფრულ დატვირთვას ქმნის.
5. კერძო გადარიცხვა `ZkTransfer`-ით შეასრულეთ. საფულე ამტკიცებს, რომ შემავალ ჩანაწერებს ფლობს, შემავალი და გამომავალი თანხები დაბალანსებულია და თითოეული დახარჯული ჩანაწერი ვალდებულებების უახლეს ხეშია დამაგრებული.
6. დაფარვა მხოლოდ მაშინ მოხსენით, როცა აქტივის პოლიტიკა ამის უფლებას იძლევა. `Unshield` საჯარო თანხასა და მიმღების ანგარიშს ამჟღავნებს, დახურული ჩანაწერის ნულიფიკატორს ხარჯავს და შეუძლია დახურული ხურდის გამომავალი შექმნას.
7. აუდიტისთვის ტიპიზებული მოთხოვნებითა და Torii-ის საბოლოო წერტილებით წაიკითხეთ კონფიდენციალური მოვლენები, მტკიცებულების ჩანაწერები, ნულიფიკატორის მდგომარეობა და ანონიმური ესქროს ჩანაწერები.

## CLI მაგალითები {#cli-examples}

ZK CLI ბრძანებები განკუთვნილია ოპერატორის და ტესტირების ნაკადებისთვის. წარმოების საფულეებმა უნდა შექმნან კრიპტოგრაფიული ვალდებულებები, გაშიფრებული დატვირთვები და მტკიცებულებები საფულის/გამოცდის ბიბლიოთეკით, სანამ შედეგად მიღებული ინსტრუქციების წარდგენა მოხდება.

დარეგისტრირება ჰიბრიდული ZK-სუნარიანობის აქტივზე:

```bash
iroha app zk register-asset \
  --asset <asset-definition-id> \
  --allow-shield true \
  --allow-unshield true \
  --vk-transfer halo2/ipa:vk_transfer \
  --vk-unshield halo2/ipa:vk_unshield \
  --vk-shield halo2/ipa:vk_shield
```

შეიქმნას ვერსიით დაშიფვრილი დატვირთვის მონაცემთა კონტეინერი დაცული შენიშვნისთვის:

```bash
iroha app zk envelope \
  --ephemeral-pubkey 0101010101010101010101010101010101010101010101010101010101010101 \
  --nonce-hex 020202020202020202020202020202020202020202020202 \
  --ciphertext-b64 AQIDBA== \
  --print-json \
  --output note-envelope.bin
```

CLI ამზადებს აქტივების პოლიტიკას, საკვანძო რეფერენციების შემოწმებასა და ჩიფრებული ცნობის მონაცემთა კონტეინერს. იგი არ გამოხატავს `shield` ან `unshield` ტრანზაქციის ქვებრძანებებს. შეადგინეთ ეს ინსტრუქციები SDK- ით და წარუდგინეთ ისინი როგორც ჩვეულებრივი ხელმოწერილი ტრანზექცია საფასურის ფასის შეფასებით.

გაუმკლავებელი მტკიცებულების მიმაგრება აქვს ასეთი ფორმა:

```bash
cat > unshield-proof.json <<'JSON'
{
  "backend": "halo2/ipa",
  "proof_b64": "BASE64_PROOF_BYTES",
  "vk_ref": {
    "backend": "halo2/ipa",
    "name": "vk_unshield"
  }
}
JSON
```

## SDK მაგალითი {#sdk-example}

ზუსტი მტკიცებულების ბაიტები მოდის კონფიგურირებული მტკიცებულება ბეკენდი. ტრანზაქციის დატვირთვა მხოლოდ საჭიროებს საჯარო შეყვანები და მტკიცებულება attachment:

```rust
use iroha_data_model::{
    isi::zk::{Unshield, ZkTransfer},
    prelude::{AccountId, AssetDefinitionId, InstructionBox},
    proof::{ProofAttachment, ProofBox, VerifyingKeyId},
};

fn transfer_instruction(
    asset: AssetDefinitionId,
    input_nullifier: [u8; 32],
    output_commitment: [u8; 32],
    anchor_root: [u8; 32],
    proof_bytes: Vec<u8>,
) -> InstructionBox {
    let backend = "halo2/ipa".into();
    let proof = ProofBox::new(backend, proof_bytes);
    let vk = VerifyingKeyId::new("halo2/ipa", "vk_transfer");
    let attachment = ProofAttachment::new_ref("halo2/ipa".into(), proof, vk);

    ZkTransfer::new(
        asset,
        vec![input_nullifier],
        vec![output_commitment],
        attachment,
        Some(anchor_root),
    )
    .into()
}

fn unshield_instruction(
    asset: AssetDefinitionId,
    recipient: AccountId,
    amount: u128,
    input_nullifier: [u8; 32],
    anchor_root: [u8; 32],
    proof_bytes: Vec<u8>,
) -> InstructionBox {
    let backend = "halo2/ipa".into();
    let proof = ProofBox::new(backend, proof_bytes);
    let vk = VerifyingKeyId::new("halo2/ipa", "vk_unshield");
    let attachment = ProofAttachment::new_ref("halo2/ipa".into(), proof, vk);

    Unshield::new(
        asset,
        recipient,
        amount,
        vec![input_nullifier],
        attachment,
        Some(anchor_root),
    )
    .into()
}
```

## ანონიმური აქტივების ესქრო {#anonymous-asset-escrow}

ანონიმური აქტივების ესქრო ესქროში მოთავსებული ღირებულებისთვის იმავე დაფარული გადარიცხვის მექანიზმს იყენებს. მხარეები და ესქროს მდგომარეობა კვლავ ესქროს ჩანაწერში ინახება, ხოლო დაფინანსების, გათავისუფლების, გაუქმებისა და დავის გადაწყვეტის ოპერაციებში გამოიყენება დაფარული ნულიფიკატორები და გამომავალი კრიპტოგრაფიული ვალდებულებები.

ესქროს ISI-ის ქცევისა და მაგალითების დეტალური აღწერისთვის იხილეთ [ადგილობრივი აქტივების ესქრო](/ka/blockchain/escrow.md#anonymous-escrow).

სიცოცხლის ციკლი ასეთია:

1. `OpenAnonymousAssetEscrow` ხარჯავს დაფარულ დაფინანსების ჩანაწერებს და ქმნის ესქროს ერთ ვალდებულებას.
2. `AcceptAnonymousAssetEscrow` მყიდველს აღრიცხავს.
3. `MarkAnonymousEscrowPaymentSent` აღრიცხავს, რომ მყიდველმა გადახდა ქსელის გარეთ გაგზავნა.
4. `ReleaseAnonymousAssetEscrow` ესქროს ვალდებულებას ხარჯავს და მყიდველისთვის გამომავალ ვალდებულებებს ქმნის.
5. თუ გადახდა მონიშნული არ არის, `CancelAnonymousAssetEscrow` ესქროს ვალდებულებას ხარჯავს და ღირებულებას გამყიდველის გამომავალ ვალდებულებებში აბრუნებს.
6. `OpenAnonymousEscrowDispute` და `ResolveAnonymousEscrowDispute` სადავო ესქროებს მტკიცებულების ჰეშებითა და გადამწყვეტის მიერ კონტროლირებული გაყოფით მართავენ.

ესქროს ჩანაწერებისა და მდგომარეობების შესამოწმებლად გამოიყენეთ [კითხვებში](/ka/reference/queries.md#escrow-and-proof-records) ჩამოთვლილი ანონიმური ესქროს მოთხოვნები.

## მათემატიკა {#math}

ქვემოთ მოცემული აღნიშვნები კონფიდენციალური აქტივების ნაკადს აღწერს. დანერგვა აქტივის პოლიტიკასა და ვერიფიკატორის რეესტრში მითითებულ აქტიურ წრედსა და პარამეტრების ID-ებს იყენებს, ამიტომ კლიენტებმა ვალდებულებები, ნულიფიკატორები და მტკიცებულების ბაიტები საფულის ან პროვერის გაუმჭვირვალე გამომავალ მონაცემებად უნდა მიიჩნიონ.

დაფარული ჩანაწერი შეიძლება ასე აღინიშნოს:

$$
n = (\mathsf{asset}, \mathsf{amount}, \mathsf{owner}, \rho)
$$

აქ `owner` მიმღების ნახვის ან ხარჯვის მონაცემებიდან მიიღება, ხოლო `rho` ჩანაწერის შემთხვევითი მნიშვნელობაა.

ჩანაწერის ვალდებულება დამფარავი კრიპტოგრაფიული ვალდებულებაა:

$$
C = \mathsf{Commit}(\mathsf{asset}, \mathsf{amount}, \mathsf{owner}, \rho)
$$

მიმდინარე კონფიდენციალური გადარიცხვის წრედების საჯარო შეყვანებში შედის ჩანაწერის ვალდებულებები, ნულიფიკატორები, Merkle-ის ფესვი, აქტივის ტეგი და ჯაჭვის ტეგი. წრედი ამ ფორმის ვალდებულების კავშირს ამოწმებს:

$$
C = H_c(\mathsf{amount}, \rho, \mathsf{owner\_tag}, \mathsf{asset\_tag})
$$

ჩანაწერის დახარჯვისას საფულე ნულიფიკატორს გამოითვლის:

$$
N = H_n(\mathsf{spend\_key}, \rho, \mathsf{asset\_tag}, \mathsf{chain\_tag})
$$

`N` საჯაროა. ის ჩანაწერს არ ამჟღავნებს, თუმცა ამ ჩანაწერისა და ჯაჭვისთვის უცვლელია, ამიტომ Iroha-ს იმავე ნულიფიკატორით განმეორებითი ხარჯვის უარყოფა შეუძლია.

ვალდებულებების ხე ჩანაწერის არსებობას ადასტურებს. თუ საფულე `C_i` ვალდებულებას ხარჯავს, მტკიცებულება შეიცავს დახურულ Merkle-გზას `C_i`-დან უახლეს საჯარო ფესვამდე:

$$
\mathsf{MerkleRoot}(C_i, \mathsf{path}) = R
$$

დაფარულიდან დაფარულზე გადარიცხვისას მტკიცებულება ღირებულების შენარჩუნებასაც ამოწმებს:

$$
\sum \mathsf{inputs} = \sum \mathsf{outputs}
$$

დაფარვის მოხსნისას საჯარო თანხა პირდაპირ შედის გამოთვლაში:

$$
\sum \mathsf{inputs} = \mathsf{public\_amount} + \sum \mathsf{private\_change}
$$

წარდგენილი მტკიცებულება შეიძლება ასე შეჯამდეს:

$$
\mathsf{Verify}(\mathsf{vk}, \mathsf{public\_inputs}, \pi) = \mathsf{true}
$$

აქ `public_inputs` შეიცავს ვალდებულებებს, ნულიფიკატორებს, ფესვს, აქტივისა და ჯაჭვის ტეგებს და დაფარვის მოხსნის ნებისმიერ საჯარო თანხას. მოწმე შეიცავს ჩანაწერის თანხებს, შემთხვევითობას, ხარჯვის მონაცემებსა და Merkle-გზებს. ვალიდატორები მტკიცებულებას ამოწმებენ, შემდეგ კი რეესტრის მდგომარეობას ცვლიან: ამატებენ გამომავალ ვალდებულებებს და შემავალ ნულიფიკატორებს დახარჯულად ნიშნავენ.

## რა არის საჯარო {#what-is-public}

ანონიმური ტრანზაქციები არ განაპირობებს ყველა შესამჩნეველ ფაქტზე კონფიდენციალურობას. შემდეგი მონაცემები მაინც შეიძლება იყოს საჯარო:

- ტრანზაქციის კრიპტოგრაფიული ჰეში, ბლოკის სიმაღლე და შეკვეთა
- ტრანზაქციის წარმდგენი უფლებამოსილი ანგარიში, თუ აპლიკაცია დახურულ შესასვლელ წერტილს ან რელეიერის სქემას არ იყენებს
- გამოყენებული აქტივის განსაზღვრა
- ნულიფიკატორები და გამოსავალი კრიპტოგრაფიული ვალდებულებები
- მტკიცებულების ჰეშები, ვერიფიკაციის გასაღების მითითებები და სურვილისამებრ მონაცემთა კონტეინერის ჰეშები
- საჯარო თანხა და მიმღებ ანგარიში `Unshield`
- ანონიმური ესქროს გამყიდველი, მყიდველი, მდგომარეობა, დროის ნიშნულები და მტკიცებულების ჰეშები

აპლიკაციები ისე შექმენით, რომ ამ საჯარო მეტამონაცემებმა დასაცავი საქმიანი ურთიერთობა არ გაამჟღავნოს.
