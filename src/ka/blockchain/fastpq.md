# FastPQ {#fastpq}

FastPQ არის Iroha-ს STARK მტკიცებულების გზა შესრულების შერჩეული ეფექტებისთვის. ის არ ცვლის ტრანზაქციების ჩვეულებრივ შესრულებას ან კონსენსუსს. ტრანზაქციები კვლავ ჩვეულებრივად სრულდება ISI-ის, IVM-ისა და Sumeragi-ის გავლით; FastPQ მხარდაჭერილ ეფექტებს შემდგომ ამტკიცებს იმ საწყისი ჩანაწერის საფუძველზე, რომელიც ბლოკის შესრულებამ დააფიქსირა.

ჰოსტის ამჟამინდელ ინტეგრაციას ორი ძირითადი გზა აქვს:

- ფინალიზებული ბლოკების რიცხვითი აქტივების ეფექტები, რომლებსაც კვანძის პროვერის ზოლი ამტკიცებს
- SORA Nexus-ის AXT მტკიცებულების კონვერტები, რომელთა `fastpq_binding` FastPQ ბმას შეიცავს

## გადარიცხვის მოწმის გზა {#transfer-witness-path}

გამჭვირვალე რიცხვითი გადარიცხვები ქმნის გადარიცხვის სტრუქტურირებულ ტრანსკრიპტს, როდესაც ინსტრუქცია ბალანსებს ცვლის. ტრანსკრიპტში იწერება:

- საწყისი ანგარიში, დანიშნულების ანგარიში, აქტივის განსაზღვრება და თანხა
- გამგზავნისა და მიმღების ბალანსები გადარიცხვამდე და გადარიცხვის შემდეგ
- ტრანზაქციის შესვლის წერტილის ჰეში, რომელიც პაკეტის ჰეშად გამოიყენება
- უფლებამოსილების დიჯესტი, რომელიც წარმდგენი ანგარიშიდან არის მიღებული
- Poseidon დიჯესტი ერთდელტიანი ტრანსკრიპტებისთვის
- იშვიათი Merkle-ის ხის განახლების მოწმეები გამგზავნისა და მიმღების ბალანსებისთვის

პაკეტური გადარიცხვები იყენებს ერთ ტრანსკრიპტს რამდენიმე დელტით. ამ შემთხვევაში ერთდელტიანი Poseidon დიჯესტი არ არსებობს.

ბლოკის შესრულება ტრანსკრიპტებს აჯგუფებს იმ შესრულების გამოძახების მიხედვით, რომელმაც ისინი გამოსცა, და ინახავს მათ ბლოკის FastPQ საწყის ჩანაწერთან ერთად. AXT გადარიცხვის დებულებაში გადარიცხვის თითოეული დელტა გადასვლის ორ სტრიქონად იქცევა:

| სტრიქონი | გასაღები | წინა მნიშვნელობა | შემდგომი მნიშვნელობა |
| --------------- | --------------------------------------------------------------------- | ----------------------- | ---------------------- |
| გამგზავნის დებეტი | `FastpqBalanceKeyV1` აქტივის განსაზღვრებისა და საწყისი ანგარიშისთვის | გამგზავნის ბალანსი მანამდე | გამგზავნის ბალანსი შემდეგ |
| მიმღების კრედიტი | `FastpqBalanceKeyV1` აქტივის განსაზღვრებისა და დანიშნულების ანგარიშისთვის | მიმღების ბალანსი მანამდე | მიმღების ბალანსი შემდეგ |

თითოეული გასაღები არის `FastpqBalanceKeyV1`-ის კანონიკური Norito ფრეიმი, რომელსაც `transfer_balance_key` აგებს ტიპიზებული აქტივის განსაზღვრებიდან და დომენის გარეშე ანგარიშიდან. ანგარიშის ალიასები და საჩვენებელი ფორმები არასდროს წარმოადგენს გასაღების მასალას.

## შესრულების ეფექტები {#execution-effects}

პროვერის ზოლი ამტკიცებს შესრულების ეფექტების სრულ დებულებებს. თითოეული დებულება მოიცავს ერთი შესრულების ჩანაწერის ყველა რაოდენობრივ ეფექტს, შესრულების თანმიმდევრობით:

| ეფექტი | განახლებული მნიშვნელობები | წესი |
| -------- | ------------------------------ | ------------------------------------------------------------------- |
| გადარიცხვა | საწყისი და დანიშნულების ბალანსი | თანხა გადაადგილდება ერთი აქტივის ორ ბალანსს შორის |
| ემისია | ბალანსი და მიწოდება | ორივე იზრდება ერთი და იმავე არანულოვანი ოდენობით |
| დაწვა | ბალანსი და მიწოდება | ორივე მცირდება ერთი და იმავე ოდენობით |
| მიმოქცევიდან ამოღება | მიწოდება და სასიცოცხლო ციკლი | მიწოდება ნულად რჩება, ხოლო აქტივის არსებობა ერთიდან ნულად იცვლება |

მიწოდება არასდროს ეცემა ბალანსზე დაბლა. თითოეული გასაღები შედგება `iroha:fastpq:execution-quantity-key:v1` დომენისგან, ერთი NUL ბაიტისგან და `FastpqExecutionQuantityKeyV1` ბალანსის, მიწოდების ან სასიცოცხლო ციკლის გასაღების Norito კოდირებისგან. როლების მინიჭება, როლების გაუქმება და სხვა ოპერაციები არ მტკიცდება.

შესრულების ეფექტებისა და AXT გადარიცხვის დებულებებში მნიშვნელობები არის ზუსტი არაუარყოფითი მთელი ერთეულები აქტივის ათობითი მასშტაბით (`FastpqQuantityUnits`), ამიტომ ისინი `u64`-ით არ შემოიფარგლება. დებულების აგება უარყოფს მასშტაბის შეუსაბამობას, უარყოფით სხვაობას და ნებისმიერ არითმეტიკულ ან დალაგების შეუსაბამობას; ის საჯარო მნიშვნელობას არასდროს ასწორებს.

## საჯარო შეყვანები {#public-inputs}

ყველა FastPQ დებულება შეიცავს საჯარო შეყვანებს, რომლებიც მტკიცებულებას ბლოკსა და შესრულების კონტექსტს უკავშირებს:

| შეყვანა | მნიშვნელობა |
| ------------- | ------------------------------------------------------------------------------------ |
| `dsid` | მონაცემთა სივრცის იდენტიფიკატორი: მისი `u64` მნიშვნელობა უმცროსი ბაიტიდან დაწყებული რიგით, რასაც მოსდევს რვა ნულოვანი ბაიტი |
| `slot` | ბლოკის შექმნის დრო ნანოწამებში, მილიწამის სიზუსტით |
| `old_root` | დებულებით შეხებული გასაღებების იშვიათი Merkle-ის ხის ფესვი დებულებამდე |
| `new_root` | დებულებით შეხებული გასაღებების იშვიათი Merkle-ის ხის ფესვი დებულების შემდეგ |
| `perm_root` | ვალდებულება შემსრულებელი მდგომარეობის როლებისა და ნებართვების ცხრილზე |
| `tx_set_hash` | ვალდებულება ბლოკის ტრანზაქციების გადაცემის ფორმატის წარმოდგენებზე, ბლოკის რიგით |

`old_root` და `new_root` მოიცავს მხოლოდ იმ გასაღებებს, რომლებსაც დებულება ეხება. ისინი არ არის მსოფლიო მდგომარეობის შენახული ფესვი.

`perm_root` არის Iroha-ს 32-ბაიტიანი `Hash`, რომელიც გამოითვლება `fastpq:v1:permission-table:blake2b-256` დომენზე, უმცროსი ბაიტიდან დაწყებული `u64`-ის სახით წარმოდგენილ ჩანაწერების რაოდენობაზე და დალაგებულ ჩანაწერებზე. თითოეული ჩანაწერი შედგება როლის ID-ის ჰეშისგან, ამ როლის ერთ-ერთი ნებართვის ჰეშისგან და ამ ნებართვის ეპოქისგან, რომელიც უმცროსი ბაიტიდან დაწყებული `u64`-ის სახითაა წარმოდგენილი. ცარიელი ცხრილი 32 ნულოვან ბაიტზე ფიქსირდება. ეს მხოლოდ როლებისა და ნებართვების კონტექსტია; ის არ ამტკიცებს ანგარიშის წევრობას ან ავტორიზაციას.

`tx_set_hash` არის Iroha-ს `Hash`, რომელიც გამოითვლება `iroha:axt:ordered-transaction-wire-set:v1` დომენზე, ერთ NUL ბაიტზე, ტრანზაქციების რაოდენობაზე და, ბლოკის რიგით თითოეული ტრანზაქციისთვის, მისი გადაცემის ფორმატის სიგრძესა და გადაცემის ფორმატის სრულ ბაიტებზე. რაოდენობა და სიგრძეები უმცროსი ბაიტიდან დაწყებული `u64` მნიშვნელობებია. ტრანზაქციები არ ლაგდება და მათგან დუბლიკატები არ იშლება, ხოლო ხელმოწერები წინასახეში რჩება.

Iroha-ს `Hash` არის Blake2b-256, რომლის ბოლო ბაიტის უმცროსი ბიტი ერთზეა დაყენებული. დებულება ასევე შეიცავს დალაგების ჰეშს, თავის სრულ კანონიკურ სტრიქონებსა და წყაროს ფაქტებს; მტკიცებულება ყველა მათგანს აკავშირებს.

## მტკიცებულების პროტოკოლი {#proof-protocol}

FastPQ-ის კანონიკური არტეფაქტები ნიღბიანი DEEP მტკიცებულებებია Goldilocks ველზე მე-4 ხარისხის გაფართოებით. მათი ზუსტი მიმართება, ტრანსკრიპტი და მოთხოვნების გეომეტრია განსაზღვრულია დაფიქსირებულ [FastPQ DEEP პროტოკოლის კონტრაქტში](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/specs/fastpq_deep_protocol_contract.md).

გამომძახებლები ირჩევენ ჩვეულებრივ ან AXT დებულებას და რესურსების ლიმიტებს. ისინი არ ირჩევენ სქემებს, შემოწმების გასაღებებს, მოთხოვნების რაოდენობას ან ტრანსკრიპტის შიდა დეტალებს. ჩვეულებრივი მარშრუტია `offline_compact::prove_quantity_ordinary_artifact`; AXT მარშრუტია `offline_compact::prove_quantity_axt_artifact`, რომლის გარსსაც მიბმული პაკეტებისთვის `prove_axt_bound_batch` წარმოადგენს. გამჭვირვალე `Prover`, `Proof` და ხელახალი გაშვების `verify` API არსებობს მხოლოდ ტესტებსა და `dev-tools` აგებებში.

## რას ამოწმებს მტკიცებულება {#what-the-proof-checks}

ნებისმიერ კერძო სამუშაომდე მწარმოებელი ამზადებს საჯარო დებულებას. ის ამოწმებს ანგარიშებს, თანხებს, მნიშვნელობებს, შემთხვევების რაოდენობას, გასაღებების სტაბილურ რიგს და გასაღებების განაწილებას, და უარყოფს დებულებას, რომლის საჯარო ფაქტები ერთმანეთს არ ემთხვევა. შემდეგ დალუქული მიმართება თითოეულ სეგმენტში ამტკიცებს ერთი ეფექტის ან გადარიცხვის ერთი შემთხვევის ორ სრულ 32-დონიან იშვიათი Merkle-ის განახლებას. ნაგულისხმევი ლიმიტები ერთ არტეფაქტში მაქსიმუმ ორ სეგმენტს უშვებს.

თითოეულ ტრასას აქვს 65,536 სტრიქონი. მწარმოებელი აფიქსირებს 301 კერძო სვეტს, ხოლო ვერიფიკატორი დამოუკიდებლად აღადგენს 41 საჯარო სვეტს. ახალი კრიპტოგრაფიული ენტროპია ნიღბავს ტრასის სვეტებს, განაყოფს და დამოუკიდებლად დაფიქსირებულ კომპოზიციურ პოლინომს. განაყოფის მისაღები გაყოფა ზუსტი უნდა იყოს. მწარმოებელი საკუთარ არტეფაქტს დაბრუნებამდე თავად ამოწმებს.

დებულების საჯარო მნიშვნელობები დამალული არ არის. ოპერაციის არსებობა გადაცემის ფორმატში მას დაშვებულად არ აქცევს: მიმართებები მხოლოდ ზემოთ ჩამოთვლილ ეფექტებს აქვს, ხოლო AXT დებულებები მხოლოდ მოწმით დადასტურებულ გადარიცხვებს უშვებს.

## პროვერის ზოლი {#prover-lane}

`iroha3d` კვანძის გაშვებისას, სანამ Torii წარდგენებს მიიღებს, უშვებს ერთ FastPQ პროვერის დამმუშავებელს, თუ Kura `init_mode = "fast"`-ით არ ეშვება. დამმუშავებელი თავის ბექენდს ფონურ რეჟიმში ახდენს ინიციალიზაციას, ამიტომ ინიციალიზაციის წარუმატებლობის შემთხვევაში გაშვება გრძელდება; ასეთ დროს ზოლი გამორთული რჩება.

დამმუშავებელი პერიოდულად ამოწმებს კვანძის ფინალიზებულ მდგომარეობას და Kura-ს საცავს. თითოეული ფინალიზებული ბლოკისთვის ის იღებს ავთენტიფიცირებულ წყაროს, რისთვისაც, თუ წყარო შენახული არ არის, ნატიურ შესრულებას ხელახლა უშვებს, და ბლოკის სრულ დებულებებს სათითაოდ ამტკიცებს ჩვეულებრივი მარშრუტით. გადატვირთვის შემდეგ ის ავთენტიფიცირებულ პრეფიქსს თავიდან აგებს დაფიქსირებული ხელმოწერილი გენეზისიდან. ის თითოეულ არტეფაქტს ინახავს Kura-ს შეზღუდული მოცულობის FastPQ საცავში. შენახული არტეფაქტი მხოლოდ განცხადებაა: შემდეგზე გადასვლამდე მწარმოებელი წყაროს ავთენტიფიკაციას ახდენს და არტეფაქტს ხელახლა ამოწმებს.

მტკიცებულების წარმოება კვანძის ლოკალური პროცესია. ის არ არის ტრანზაქციების დაშვების ან კონსენსუსის კარიბჭე: შესრულება, ფიქსაცია და ფინალურობა მტკიცებულებას არ ელოდება. წარუმატებლობა, რომლის გამეორებაც შესაძლებელია, სამუშაოს მოგვიანებითი მცდელობისთვის ტოვებს, ხოლო თითო პროცესში ერთი მწარმოებელი მუშაობს.

## შემოწმება {#verification}

ვერიფიკატორი არტეფაქტს ამოწმებს იმ მოლოდინებთან შედარებით, რომლებსაც საკუთარი ავთენტიფიცირებული დებულებიდან იღებს და არასდროს — შესამოწმებელი არტეფაქტიდან. ვერიფიკაცია თითოეულ სეგმენტს შეზღუდვების ფარგლებში ერთხელ დეკოდირებს, AIR-ს ერთხელ აფასებს დომენის გარეთა წერტილში, დაფიქსირებულ ფესვებთან მიმართებით ავთენტიფიკაციას უკეთებს ყოველ გახსნილ სტრიქონს, განაყოფის ფოთოლს, FRI ბოჭკოს და სრულ FRI ტერმინალს, და ასრულებს მაქსიმუმ 385 დაკეცვის შემოწმებას. ის არ აგებს კერძო მოწმეს, ტრასას ან სრულ დაბალი ხარისხის გაფართოებას.

წარმატება ადასტურებს თანხვედრას გამომძახებლის მოლოდინებთან. ის არ ანიჭებს შესრულების უფლებამოსილებას, წყაროს ფინალურობას, ხელახალი წარდგენის დაშვებას ან AXT ხარჯვის ავტორიზაციას.

`offline_compact::VerificationLimits`-ის ნაგულისხმევი ლიმიტები, რომლებსაც ჩვეულებრივი მარშრუტიც იყენებს:

| ლიმიტი | ნაგულისხმევი მნიშვნელობა |
| ------------------------------- | ------------: |
| სეგმენტები ერთ არტეფაქტში | 2 |
| არტეფაქტის ბაიტები გადაცემის ფორმატში | 1 MiB |
| შვილობილი მტკიცებულების ფრეიმი | 500,084 ბაიტი |
| დებულების ბაიტები ყველა სეგმენტში ჯამურად | 512 KiB |
| მოთხოვნები ერთ სეგმენტში | 77 |
| მოთხოვნები ყველა სეგმენტში ჯამურად | 154 |

კვანძის ზოლი არტეფაქტის ბაიტებს გადაცემის ფორმატში დამატებით ზღუდავს `zk.fastpq.proof_sidecar_max_bytes`-ით და Kura-ს FastPQ ობიექტის ლიმიტით. დეკოდირებამდე AXT მტკიცებულების ბლობი შეიძლება შეიცავდეს მაქსიმუმ 2 MiB-ს, ხოლო მასში ჩაშენებული FastPQ დატვირთვა — მაქსიმუმ 1 MiB-ს.

## SORA Nexus-ის AXT მტკიცებულების კონვერტები {#sora-nexus-axt-proof-envelopes}

SORA Nexus-ის AXT მტკიცებულების კონვერტები შეიძლება შეიცავდეს `AxtFastpqBinding`-ს. AXT კონვერტების ბლოკური ვალიდაცია, IVM ჰოსტის AXT კონვერტის შემოწმებები და `RegisterVerifiedFeeSponsorVaultAllocation` მოითხოვს კონვერტის `fastpq_binding`-ს, ამოწმებს მას მოსალოდნელ მტკიცებასთან და იძახებს FastPQ ვერიფიკატორს კონვერტსა და მასში ჩაშენებულ მტკიცებულებაზე. ბმის არარსებობა ან წარუმატებელი ვერიფიკაცია ოპერაციას უარყოფს.

ვერიფიკატორი იღებს მხოლოდ მოწმით დადასტურებულ გადარიცხვის მტკიცებებს: `tx_predicate` და `value_conservation`. `authorization` და `compliance` მტკიცების ტიპები ეფექტის გაუმჭვირვალე მატარებლებია გადარიცხვის მიმართების გარეშე, და ვერიფიკაცია მათ უარყოფს. ბლოკის ვალიდაცია ასევე უარყოფს კონვერტებს, რომლებიც დისტანციურ ხარჯვებს შეიცავს, ხოლო IVM ჰოსტი უარყოფს `AXT_VERIFY_DS_PROOF`-ის დამოუკიდებელ დაშვებას. ორივე მიუწვდომელი რჩება მანამ, სანამ ფინალიზებული წყაროს ფესვების, ტრანზაქციების ნაკრებისა და გამცემის ავტორიზაციის ავთენტიფიკაცია შესაძლებელი არ გახდება.

### AXT ბმა {#axt-binding}

SORA Nexus-ის AXT კონვერტებისთვის `AxtFastpqBinding` მტკიცებულების შექმნამდე და ვერიფიკაციამდე კანონიკურ ფორმაში გადადის:

- `parameter`, `source_dataspace`, `source_receipt_id` და `verified_effect_type` მნიშვნელობებს კიდეებიდან ჰარები ეჭრება და ისინი ცარიელი არ უნდა იყოს
- `source_tx_commitment`, `claim_digest`, `witness_commitment` და `policy_commitment` პატარა ასოებში გადადის და უნდა იყოს 32 ბაიტის თექვსმეტობითი კოდირება
- `verifier_id` უნდა იყოს `fastpq`, ხოლო `verifier_version` — `v1`
- `claim_type`-ს კიდეებიდან ჰარები ეჭრება, ის პატარა ასოებში გადადის და უნდა ასახელებდეს ზემოთ მოცემული ოთხი მტკიცების ტიპიდან ერთ-ერთს
- `target_dsids` არ უნდა იყოს ცარიელი და მკაცრად ზრდადი უნდა იყოს
- `remote_spend_intent_commitments` მკაცრად ზრდადი უნდა იყოს და პირველი გამოშვების ლიმიტს არ უნდა აჭარბებდეს

ვერიფიკაცია ზუსტ კანონიკურ ფორმას მოითხოვს; ის გამომძახებლის ნაცვლად ბმას არ ანორმალიზებს.

ბმა უერთდება პაკეტს, რომელიც ბლოკის შესრულებამ უკვე დააფიქსირა; ის გადასვლებს არ ქმნის. პაკეტი უნდა შეიცავდეს მინიმუმ ერთ მდგომარეობის გადასვლას და უნდა ასახელებდეს ბმის პარამეტრების ნაკრებს, `fastpq-state-transition-stark-v1`-ს. მისი `entry_hash` მეტამონაცემი `source_tx_commitment`-ის ტოლი უნდა იყოს, ხოლო მისი საჯარო `dsid` ბმის `source_dsid`-ს უნდა აკოდირებდეს. გადარიცხვის მტკიცება უნდა შეიცავდეს მინიმუმ ერთ გადარიცხვის ტრანსკრიპტს, ხოლო ყოველი ტრანსკრიპტის პაკეტის ჰეში `source_tx_commitment`-ის ტოლი უნდა იყოს.

შემდეგ ბმა პაკეტში მტკიცებულებასთან მიბმულ მეტამონაცემებს წერს: კანონიკურ ბმას, მის ოთხ დიჯესტს, `source_receipt_id`-ს, `target_dsids`-ს, `verified_effect_type`-ს, არაცარიელ `corridor`-ს, არანულოვან მანიფესტის ფესვს, ოფციურ DA ვალდებულებას, ოფციურ არანულოვან დაფიქსირებულ თანხას და ვადის გასვლის სლოტს, სადაც ნული ნიშნავს, რომ ვადა არ იწურება. ბოლოს ის ამატებს ბეჭედს ბმაზე და ბეჭდის გარეშე აღებულ პაკეტზე:

$$
\operatorname{seal} =
\operatorname{Hash}(
\texttt{fastpq:axt:batch-seal:v1}\|
E(\operatorname{binding})\|
E(\operatorname{batch})
)
$$

აქ $E$ არის კანონიკური Norito კოდირება. ბმის შემდეგ პაკეტის, ბმის ან მტკიცებულებასთან მიბმული მნიშვნელობის შეცვლა ვერიფიკაციას წარუმატებელს ხდის. ვერიფიკატორი ასევე ადარებს კონვერტის მონაცემთა სივრცეს, მანიფესტის ფესვს, DA ვალდებულებას, დაფიქსირებულ თანხას და ვადის გასვლას მტკიცებულებასთან მიბმულ მნიშვნელობებს.

ვერიფიცირებული კონვერტი აბრუნებს თავის დამტკიცებულ `old_root`-ს, `new_root`-ს და `tx_set_hash`-ს, ასევე დებულების დიჯესტს. დიჯესტი მოიცავს კონვერტის მონაცემთა სივრცეს უმცროსი ბაიტიდან დაწყებული `u64`-ის სახით, მის მანიფესტის ფესვს, DA ვალდებულებას (თუ ის არსებობს), ბმას და დებულებას:

$$
\operatorname{statement\_digest} =
\operatorname{Hash}(
\texttt{fastpq:axt:statement:v1}\|
\operatorname{le64}(\operatorname{dsid})\|
\operatorname{manifest\_root}\|
\operatorname{da\_commitment}\|
E(\operatorname{binding})\|
E(\operatorname{statement})
)
$$

AXT პაკეტის მანიფესტის დიჯესტი კანონიკური ბმის Norito კოდირებაზე გამოთვლილი SHA-256-ია:

$$
\operatorname{manifest\_digest} =
\operatorname{SHA256}(E(\operatorname{canonical\_binding}))
$$

## პარამეტრების ნაკრებები {#parameter-sets}

პირველ გამოშვებას აქვს ზუსტად ერთი პარამეტრების ნაკრები, `fastpq-state-transition-stark-v1`. პაკეტები და AXT ბმები მას ასახელებენ, ხოლო AXT მტკიცებულების შექმნა ნებისმიერ სხვა სახელს უარყოფს. DEEP პროტოკოლის კონტრაქტი აფიქსირებს გამოშვებული არტეფაქტის გეომეტრიას:

| ელემენტი | მნიშვნელობა |
| -------------------------- | ----------------------------------------------------- |
| ველი | Goldilocks `p = 2^64 - 2^32 + 1`, გაფართოება `u^4 - 7` |
| ტრასის სტრიქონები | 65,536 |
| შეფასების სტრიქონები | 8,388,608 (გაფართოების კოეფიციენტი 128) |
| FRI-ის დაკეცვის არიტეტები | `[16, 16, 8, 8, 4]` |
| მოთხოვნები | 77 განსხვავებული პოზიცია |
| გრაინდინგი | არ გამოიყენება |
| ვალდებულებები და ტრანსკრიპტი | SHA3-256 და SHAKE256 |

საწარმოო კვალიფიკაცია მიუწვდომელია. ამ კონსტრუქციის მართებულობის, დამალვისა და Fiat-Shamir-ის დამოუკიდებელი მიმოხილვები ჯერ არ ჩატარებულა, ხოლო დაფიქსირებული [საწარმოო მზადყოფნის ჩანაწერი](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/specs/fastpq_production_readiness.md) სამუშაოთი ნორმალიზებული უსაფრთხოების შესახებ არანაირ განცხადებას არ აკეთებს.

## კონფიგურაცია {#configuration}

FastPQ კონფიგურაცია განთავსებულია `zk.fastpq` ქვეშ.

```toml
[zk.fastpq]
execution_mode = "cpu"
poseidon_mode = "cpu"
proof_sidecar_queue_cap = 1024
proof_sidecar_max_retries = 16

# Optional telemetry labels.
device_class = "apple-m4"
chip_family = "m4"
gpu_kind = "integrated"

# Optional Metal backend tuning.
metal_queue_fanout = 3
metal_queue_column_threshold = 24
metal_max_in_flight = 5
metal_threadgroup_width = 128
metal_trace = false
metal_debug_enum = false

[zk.fastpq.producer]
poll_interval_ms = 1000
step_timeout_ms = 30000
max_native_steps = 16
max_source_entries = 65536
max_source_statements = 16384
```

ორივე რეჟიმი იღებს მხოლოდ `cpu`-ს ან `gpu`-ს და ნაგულისხმევი მნიშვნელობაა `cpu`. რომელიმე მათგანის `gpu`-ზე დაყენებისას მტკიცებულების ჰეშირებას მოწყობილობა სჭირდება: macOS-ზე Metal, სხვაგან კი CUDA. თუ GPU-ის მხარდაჭერა კომპილაციაში არ არის ჩართული ან მოწყობილობა წინასწარ შემოწმებას ვერ გადის, პროვერის ზოლი გამორთული რჩება; ის CPU-ზე არასდროს გადადის. მოწყობილობა ასრულებს Merkle-ის ფოთლებისა და ქვედა მშობელი კვანძების მასობრივ ჰეშირებას; ტრანსკრიპტი, დალაგებული ზედა ხე და ტრასის არითმეტიკა CPU-ზე რჩება. `poseidon_mode = "gpu"`-ის შემთხვევაში კვანძი ტრანსკრიპტის Poseidon დიჯესტებსაც GPU-ზე პაკეტურად ამუშავებს, თუ ცალკე წინასწარი შემოწმება წარმატებით გაივლის; წინააღმდეგ შემთხვევაში ის მათ CPU-ზე ითვლის.

`proof_sidecar_max_bytes` ზღუდავს კოდირებულ არტეფაქტს, რომელსაც კვანძი ინახავს და ამოწმებს, და ნაგულისხმევად პროვერის მტკიცებულების მაქსიმალური ფრეიმის ტოლია. `producer` ცხრილი ზღუდავს მტკიცებულების შექმნის თითოეულ მცდელობას: მის შემოწმების ინტერვალს, დროის ბიუჯეტს, ნატიური ხელახალი გაშვების ნაბიჯებს (1-დან 64-მდე) და მეხსიერების გამოყოფამდე დაშვებულ წყაროს ჩანაწერებსა და დებულებებს. `metal_queue_fanout` იღებს მნიშვნელობებს 1-დან 4-მდე.

რეჟიმისა და ტელემეტრიის ეტიკეტების პარამეტრები ასევე შეიძლება `iroha3d`-დან გადაიფაროს:

```shell
iroha3d --fastpq-execution-mode gpu
iroha3d --fastpq-poseidon-mode cpu
iroha3d --fastpq-device-class apple-m4
iroha3d --fastpq-chip-family m4
iroha3d --fastpq-gpu-kind integrated
```

`iroha3d` კონფიგურაციის ფაილის წაკითხვისას გარემოს ცვლადებს უგულებელყოფს, ამიტომ ეს მნიშვნელობები TOML-ში ან ზემოთ მოცემული ოფციებით დააყენეთ.

## მაჩვენებლები {#metrics}

ტელემეტრიის ჩართვისას FastPQ ექსპორტს უკეთებს მაჩვენებლებს ბექენდის შერჩევის, მტკიცებულებების შენახვისა და Metal-ის შესრულების გარემოს ქცევის შესახებ:

| მაჩვენებელი | მნიშვნელობა |
| ----------------------------------- | --------------------------------------------------------------------------- |
| `fastpq_execution_mode_total` | მოთხოვნილი და ფაქტობრივად შერჩეული შესრულების რეჟიმი ბექენდისა და მოწყობილობის ეტიკეტების მიხედვით |
| `fastpq_poseidon_pipeline_total` | მოთხოვნილი და ფაქტობრივად შერჩეული Poseidon-ის დამუშავების კონვეიერის გზა |
| `fastpq_gpu_disable_total` | GPU ამაჩქარებლის გამორთვის მოვლენები ამაჩქარებლის, მიზეზისა და მოწყობილობის ეტიკეტების მიხედვით |
| `fastpq_gpu_parity_failure_total` | GPU-ის შედეგების თანხვედრის შერჩევითი შემოწმების წარუმატებლობები ამაჩქარებლის, მიზეზისა და მოწყობილობის ეტიკეტების მიხედვით |
| `fastpq_proof_sidecar_queue_depth` | რიგში მდგომი FastPQ მტკიცებულების თანმხლები დანართები |
| `fastpq_proof_sidecar_events_total` | მტკიცებულების თანმხლები ფაილის შენახვის მოვლენები მოვლენის მიხედვით |
| `fastpq_metal_queue_depth` | Metal-ის რიგის ლიმიტი, ერთდროულად მიმდინარე სამუშაოების მაქსიმალური რაოდენობა, გაგზავნების რაოდენობა და ნიმუშების აღების ფანჯარა |
| `fastpq_metal_queue_ratio` | Metal-ის რიგის დატვირთულობისა და გადაფარვის კოეფიციენტები |
| `fastpq_zero_fill_duration_ms` | ჰოსტის ნულებით შევსების ხანგრძლივობა Metal-ის გაშვებებისთვის |
| `fastpq_zero_fill_bandwidth_gbps` | ნულებით შევსების გამოთვლილი გამტარუნარიანობა |

რეჟიმის, GPU-ის, Metal-ის რიგისა და ნულებით შევსების მაჩვენებლებს სჭირდება `extended` ან `full` ტელემეტრიის პროფილი და ისინი არ ექსპორტდება, როცა Kura `init_mode = "fast"`-ით ეშვება. Metal-ის რიგისა და ნულებით შევსების მაჩვენებლებს ასევე სჭირდება `fastpq-gpu` აგება macOS-ზე.

ზოგადი შესრულების განსაზღვრისთვის, გამოიყენეთ ისინი [შესრულება და მაჩვენებლები](/ka/guide/advanced/metrics.md) -ში ჩამოთვლილი კონსენსუსის და რიგის სიგნალებით.
