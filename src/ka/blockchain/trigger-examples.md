# მოვლენების გამომწვევი მაგალითი {#event-trigger-example}

ეს მაგალითი იყენებს კანონიკური დომენის გარეშე ანგარიში IDs და პროგნოზირებული აქტივი
განმარტებები Iroha 3 მონაცემთა მოდელი.

ვთქვათ, ქსელში არის:

- კანონიკური ანგარიში, რომელსაც აკონტროლებს ალისის გასაღები.
- კანონიკური ანგარიში, რომელსაც გიჟი თოფის გასაღები აკონტროლებს
- აქტივების განსაზღვრა, რომელიც პროგნოზირებულია როგორც `tea` ქვემოთ `wonderland.universal`
- თითოეული ანგარიშის მიერ განთავსებული ამ აქტივის ბალანსი

მიზანია დარეგისტრირდეს გამშვები, რომელიც აკვირდება ალისის ჩაის ბალანსს და
წარადგენს გადარიცხვას Mad Hatter-ის ანგარიშიდან, როდესაც შედარებითი მონაცემების მოვლენა
გამონაბეჭდილი.

## 1. ანგარიშების და აქტივების მომზადება {#_1-prepare-accounts-and-assets}

დარეგისტრირეთ მონაწილე ანგარიშები და აქტივების განსაზღვრა.
მიმდინარე Iroha, ანგარიში IDs მოდის ანგარიშის კონტროლერებისგან, ხოლო პროგნოზირებული
დომენების გამოყენება `domain.dataspace` ფორმა:

```text
domain: wonderland.universal
asset definition projection: tea in wonderland.universal
holder accounts: AccountId(controller=alice_key), AccountId(controller=mad_hatter_key)
```

აქტივის განსაზღვრა კვლავ აქვს კანონიკური არაპროკაზმული მისამართი. შეინახეთ ან გამოკითხეთ ეს
რეგისტრაციის შემდეგ მისამართი და გამოიყენეთ მისი გამამოძრავებელი მოქმედებაში.

## 2. აირჩიეთ გამომწვევი ავტორიტეტი {#_2-choose-the-trigger-authority}

განსაზღვრეთ გამშვები სისტემის ტექნიკური ანგარიში სპეციალურ ანგარიშზე, თუ ეს შესაძლებელია.
განკუთვნილი ანგარიში აშკარად აჩვენებს, თუ რა ნებართვებია საჭირო trigger-ისთვის
აღსრულება და თავიდან აიცილებს გამშვებ ღილაკის დაკავშირებას ოპერატორის პირად ხელმოწერასთან
გასაღები.

ტექნიკური ანგარიში უკვე უნდა არსებობდეს და მას უნდა ჰქონდეს ნებართვა წარადგინოს
ინსტრუქციები გამშვებ აპარატში.

## 3. განსაზღვრეთ შესრულებადი {#_3-define-the-executable}

განხორციელებადი არის ინსტრუქციის თანმიმდევრობა, რომელიც გამშვები აძლევს, როდესაც მოვლენა
ამ მაგალითისთვის, იგი შეიცავს ერთ გადაცემას:

```text
Transfer(
  source = AssetId(tea_definition, mad_hatter_account),
  value = Numeric(1),
  destination = AssetId(tea_definition, alice_account)
)
```

გამოიყენეთ SDK აჟაინური ტიპირებული მშენებლები საბოლოო ტრანზაქციის სასარგებლო ტვირთისთვის.
ძველი ტექსტური მკაცრი კოდირება IDs გაშვების კოდში; ანალიზება ან გამოკითხვა კანონიკური IDs
სანამ აღსრულებადი აწარმოებს.

## 4. განსაზღვრეთ მოვლენების ფილტრი {#_4-define-the-event-filter}

გამოიყენეთ მონაცემთა მოვლენების ფილტრი, რომელიც შეამცირებს მოვლენებს იმ ობიექტზე, რომელსაც თქვენ აინტერესებთ:

```text
EventFilterBox::Data(
  DataEventFilter for asset changes involving
  AssetId(tea_definition, alice_account)
)
```

შეინახეთ ფილტრები ისეთი კონკრეტული, როგორც პრაქტიკული. `AcceptAll` ფილტრი სასარგებლოა
დებეგირება, მაგრამ ეს ყველა შედარებით მოვლენა იხდის ღირებულება გაშვების
შეფასება.

## 5. დარეგისტრირეთ გამშვები {#_5-register-the-trigger}

დარეგისტრირეთ გამშვები ღილაკი:

- სათავსო `TriggerId`
- განხორციელებადი ინსტრუქციის თანმიმდევრულობა
- `Repeats::Indefinitely` ან `Repeats::Exactly(n)`
- ტექნიკური ანგარიში
- მოვლენების ფილტრი
- ავტორიზებული მეტა მონაცემები

ტრიგერის რეგისტრაცია თავისთავად ჩვეულებრივი ოპერაციაა, ამიტომ რეგისტრაციის
ანგარიშს სჭირდება ნებართვა, რომ დარეგისტრირდეს გამოწვევები. ტექნიკურ ანგარიშს უნდა
ტრიგერის შესრულებისათვის საჭირო ნებართვები.

## აღსრულების ბრძანება {#execution-order}

როდესაც ბლოკი შესრულდება:

1. ნორმალური ტრანზაქციის ინსტრუქციები პირველ რიგში ჩატარდება.
2. აღნიშნული ინსტრუქციით წარმოქმნილი მონაცემები შეგროვდება.
3. ჟაჟრთმვნ, კჲთრჲ ფილტრჲ ჟვ ოპაგს ნა ჲეალთრვ ჟრანთ.
4. ბლოკის შესრულების მილსადენში ტრიგერით წარმოქმნილი ეფექტები ხორციელდება
   რაც საშუალებას იძლევა განახორციელოს რეკურსიული გამშვები მოქმედება.

თუ გამშვები აპარატის გამოყენება `Repeats::Exactly(n)`, დარეგისტრირეთ ახალი გამშვები, როდესაც გათვლა
არის ამოწურული და იგივე ქცევაა საჭირო ისევ.
