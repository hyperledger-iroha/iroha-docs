# ჭკვიანი ხელშეკრულებები {#smart-contracts}


Iroha ტრანზაქციები ახორციელებს `Executable` სასარგებლო ტვირთებს. მიმდინარე მონაცემთა მოდელი მხარს უჭერს:

- `Executable::Instructions`: Iroha სპეციალური ინსტრუქციების შედგენილი კომპლექტი
- `Executable::ContractCall`: განთავსებული ხელშეკრულების ინსტანციის გვერდითი რეფერენციული მოწოდება
- `Executable::Ivm`: ბაიტების კოდი Iroha VM
- `Executable::IvmProved`:Iroha VM ბაიტ-კოდი წინასწარ გამოანგარიშებული ინსტრუქციის საფარით და მტკიცებულების ვალდებულებებით

Kotodama არის Iroha ეს არის მაღალი დონის ჭკვიანი ხელშეკრულების ენა. `.ko` წყარო ფაილი კომპილებს დეტერმინისტური IVM ბაიტო კოდი, რომელიც კონვენციულად ინახება როგორც `.to` არტეფაქტი განთავსებისთვის. Kotodama მიზნები IVM მხოლოდ. ის არ არის მიზნად RISC-V ან WebAssembly.

პირველი გამოშვება მხარს უჭერს მხოლოდ ABI ვერსიას 1. syscall და pointer-ABI პოლიტიკა არის ერთი უპირობო V1 ხელშეკრულება, რომელიც ამოქმედდება მიღებითა და შესრულებით; არ არსებობს ალტერნატიული runtime რეჟიმი.

## როდის უნდა გამოიყენოთ ჭკვიანი ხელშეკრულებები {#when-to-use-smart-contracts}

გამოიყენეთ ჩვეულებრივი ინსტრუქციები, როდესაც ოპერაცია შეიძლება პირდაპირ გამოხატული იყოს:

- დარეგისტრირებული ან არარეგისტრირებელი ობიექტები
- მინა, დამწვარი ან გადარიცხული აქტივები
- განახლება მეტა მონაცემები
- ნებართვის მინიჭება ან გაუქმება
- განახორციელოს გამშვები
- ქსელზე პარამეტრების დაყენება

გამოიყენეთ ჭკვიანი ხელშეკრულება მაშინ, როდესაც ტრანზაქციას სჭირდება შეფუთული ლოგიკა, რომელიც უხერხულია სტატიკური ინსტრუქციის თანმიმდევრობით გამოხატვა, ან როდესაც განთავსებული ხელშეკარგულების ინსტანცია უნდა გამოიძახოს რეფერენციით.

## IVM განხორციელებადი {#ivm-executables}

`Executable::Ivm` შეიცავს ნედლს IVM ბაიტკოდი. კვანძები ასრულებენ იმ ბაიტკოდს ჯაჭვისთვის კონფიგურირებული გაშვების დროის ლიმიტების შიგნით. შეინარჩუნეთ ბაიტ-კოდი პატარა და დეტერმინისტური; ხელშეკრულებები არის ტრანზაქციის შესრულების ნაწილი და შესაბამისად, გავლენას ახდენს კონსენსუსზე.

`Executable::IvmProved` განკუთვნილია მტკიცებულების გადამზიდველი ნაკადებისთვის. მასში შედის:

- IVM ბაიტების კოდი
- დეტერმინისტური ინსტრუქციის გადაფარვა
- აღსრულების ღონისძიებების ვალდებულება
- გაზის პოლიტიკის მიმართულებით ვალდებულება

მტკიცებულება უკავშირდება გადაფარვას შესრულებულ ბაიტ-კოდს. მილსადენის პოლიტიკის მიხედვით, ვალიდატორებს შეუძლიათ შემოწმონ მტკიცებულება და განახორციელონ მისი შესრულება დამატებითი უსაფრთხოების შემოწმების სახით.

## განთავსებული ხელშეკრულების ზარები {#deployed-contract-calls}

`Executable::ContractCall` იწვევს განთავსებულ ხელშეკრულების ინსტანციას მისამართით. გამოიყენეთ ეს, როდესაც ხელშეკარგულების კოდი ცალკე არის რეგისტრირებული და ტრანზაქციები უნდა მოიწვიოს იგი რეფერენციის ნაცვლად ყოველ ჯერზე ბაიტების კოდის თანხა.

## ხელშეკრულების სიცოცხლის ციკლი და საკუთრება {#contract-lifecycle-and-ownership}

თითოეული განთავსებული მისამართი ინახავს `ContractLifecycleControlV1` ჩანაწერს, მათ შორის იმ პერიოდში, როდესაც ხელშეკრულება არააქტიურია. ჩანაწერი შეიცავს პირველი განთავსების შეუცვლელ წარმომავლობას, მიმდინარე და მოქმედი მფლობელს, პარლამენტის ნებისმიერ გაუქმებადი დელეგაციას, აქტიურ კოდის ჰეშს, ნულოვანი შედარებისა და გაცვლის რევიზიონს; საგანგებო სიტუაციების შეჩერება. პირდაპირი განთავსება ფიქსირებს განთავსების ანგარიშს. პარლამენტის განთავსებით ფიქსირდება მისი შემოთავაზებელი, წინადადებითი შინაარსი ID და წარმატებული მმართველობის მცდელობა ID.

სიცოცხლის ციკლის მფლობელი არის ან ერთი ანგარიში, ან პარლამენტი. ანგარიშის მფლობელობის ცვლილებები იყენებს ცალკე შეთავაზებას და მიღებას; შეთავაზების მიღება ამტკიცებს პარლამენტის ნებისმიერ დელეგაციას. ანგარიშის მფლობელს შეუძლია პარლამენტის მიერ ხელშეკრულების გააქტიურების ან დეაქტივაციის უფლება მისცეს, შემდეგ კი ამ დელეგაციას გააუქმოს, მაგრამ დელეგაცია არასდროს აძლევს საშუალებას პარლამენტს საკუთრების გადაცემა. პარლამენტის საკუთრებაში არსებული ცვლილებები და პარლამენტის მიღება ხდება დამოწმებული მართვის ეფექტით.

RAW `ActivateContractInstance` და `DeactivateContractInstance` ინსტრუქციები ხელმისაწვდომია მხოლოდ მიმდინარე ანგარიშის მფლობელს. ისინი უნდა შეიცავდნენ რეკორდის ზუსტ `expected_revision`; runtime უარყოფს მოძველებულ ან ნულოვან რევიზიებს. ნედლეული აქტივაცია არ შეიძლება შექმნას სიცოცხლის ციკლის რეკორდი და იგი ვალიდატირებს რეგისტრირებულ არტეფაქტს, მანიფესტსა და ABI სანამ შეიცვლება `active_code_hash`. დეაქტივაცია  გაწმენდა აქტიური კოდის ჰეშის, მაგრამ ინარჩუნებს საკუთრებასა და წარმოშობას. ყოველი წარმატებული გადასვლა სიცოცხლის ციკლის წინ აღწევს რევიზიას და გამოიყოფა სრული პოსტ-სახელმწიფოს.

გააქტიურებას შეუძლია ასევე განახორციელოს ერთი გამოცხადებული სიცოცხლის ციკლის კოკი. პირველი გააქტივება, რომლის მანიფესტში შედის `EntryPointKind::Hajimari` შესასვლელი წერტილი (`hajimari`/`始まり`) ეტაპები `Hajimari`. აქტიური მისამართის რეაბილიტაცია კოდზე, რომლის მანიფესტი შეიცავს `EntryPointKind::Kaizen` შესასვლელ წერტილს (`kaizen`/`改善`) ეტაპები `Kaizen`. ბმული იცვლება დაუყოვნებლივ, მაგრამ ხელშეკრულება მზად არ არის: ყველა `Kotoage` და `View` ზარი უარყოფითია, სანამ ზუსტად განლაგებული კოკი წარმატებას ვერ მიაღწევს. კიდევ ერთი გააქტიურება ასევე უარყოფითი ხდება, სანამ კოკი მოქმედებს

მოითხოვეთ `Executable::ContractCall` დადგენილი კოკი იმავე ხელშეკრულების მისამართზე და ახალი კოდის ჰეშით, ზუსტი `hajimari` ან `kaizen` შესასვლელი პუნქტის გამოყენებით და მისი მანიფესტში განცხადებული არგუმენტები. Runtime უზრუნველყოფს `CanInvokeContractEntrypoint` ნებართვას მისამართისა და სელექტორის მიხედვით; დამრეკველებმა არ უნდა შექმნან ან აძლეონ ეს ნებართვა. მოლოდინში მყოფი მარკერი შეიცავს runtime-გენერირებულ, დეტერმინისტურ `transition_id` და ახალ `code_hash`; `Kaizen` მარკერი ასევე შეიცავს `previous_code_hash`. კლიენტები არ ითვლიან და არ წარუდგენენ `transition_id`. წარმატებული ჰაკი მოხმარებს მარკერს ატომურად, ხოლო წარუმატებელი ჰაკი ტოვებს მას მოლოდინში მოგვიანებით განმეორებითი ცდისთვის.

საგანგებო დონის პარლამენტის წინადადება შეიძლება დააწესოს შეჩერება მაქსიმუმ 3600 ბლოკზე, როდესაც ის აკავშირებს მიმდინარე რევიზიას, კოდის ჰაშს და არა ნულოვან ინციდენტების დიჟესტს. გამოძახებები დაბლოკებულია დაწესების სიმაღლიდან, მაგრამ არ მოიცავს ვადის ამოწურვის სიმაღლეს. მოქმედების ვადა აღადგენს შესრულებას, მაგრამ არ წაშლის შეკავებას. სერტიფიცირებული `CompleteEmergencyHoldRetrospective` ქმედება მოგვიანებით უნდა დააკავშიროს ზუსტი შეკავება IDs და გადაჭრას პლუს ნულოვანი აღმოჩენის ფესვი, სანამ ჩანაწერი გაწმენდილი იქნება; სხვა შეკავება ვერ განხორციელდება იმ პერიოდში, როდესაც ეს რეტროსპექცია რჩება გამოწვეული.

როდესაც აპლიკაცია API არის ჩართული, წაიკითხეთ შენახული მდგომარეობა `GET /v1/gov/contracts/{contract_address}`. მისი `found` ველი ნიშნავს იმას, რომ არსებობს სიცოცხლის ციკლის რეკორდი, არა ის, რომ მისამართს ამჟამად აქვს აქტიური კოდი.

## საოპერაციო მიმართულებები {#operational-guidance}

- კონტრაქტების დეტერმინისტური შენარჩუნება. კონტრაქტის ქცევა არ უნდა იყოს დამოკიდებული ადგილობრივი კედლის საათის დროზე, მასპინძელი ფაილების სისტემის მდგომარეობაზე, ქსელის ზარებზე ან სხვა თანატოლ-ლოკალური შეღწევებზე.
- ტვირთების კომპაქტური შენარჩუნება. დიდი ბაიტო კოდი ზრდის ტრანზაქციის ზომას და ბლოკზე გავრცელების ხარჯებს.
- უპირატესობას ანიჭებს წაკითხული ინსტრუქციები მარტივი რეგისტრაციის ცვლილებებისთვის. ისინი უფრო ადვილია აუდიტირება და უფრო იაფი შესრულება.
- კონტრაქტის განახლება და რეგისტრაციის ნებართვა მაღალი რისკის მქონე ოპერატიული კონტროლის სახით განიხილეთ.
