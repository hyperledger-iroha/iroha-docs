# I105 اکاؤنٹ ایڈریس فارمیٹ {#i105-account-address-format}

I105 Iroha 3 `AccountId` کے لیے بیرونی ٹیکسٹ فارمیٹ ہے۔

اس کا فائدہ مند بوجھ اکاؤنٹ کنٹرولر کی نمائندگی کرتا ہے۔

اس کا سینٹینل ایک سلسلہ امتیاز کے ساتھ ارادہ کردہ نیٹ ورک کی شناخت کرتا ہے.

API، ٹرانزیکشن، اجازت، یا استفسار کے لئے کینیکل اکاؤنٹ ID کی درخواست کرتا ہے جہاں کہیں بھی استعمال کریں.

ایک I105 اکاؤنٹ ID ڈومینلیس ہے۔

ایک قدر جیسے `treasury@payments.universal` اکاؤنٹ کا عرفی نام ہے، I105 ID کی دوسری ہجے نہیں.

I105 ID حاصل کرنا اکاؤنٹ کو رجسٹر یا فنڈ نہیں کرتا ہے۔

::: warning انضمام کی زیادہ تر ناکامیوں کو روکنے والے قواعد

- ایک ایڈریس کوڈ کرنے یا تصدیق کرنے سے پہلے نیٹ ورک پروفائل منتخب کریں۔
- کینونیکل UTF-8 سٹرنگ کو بعینہٖ ذخیرہ کریں اور اسی طرح اس کا موازنہ کریں۔
- حروف کی بڑی/چھوٹی حالت برقرار رکھیں اور `Unicode` نارملائزیشن لاگو نہ کریں۔
- ایک I105 ID میں `@domain` یا `@domain.dataspace` کا ضمیمہ نہیں ہونا چاہئے.
- Iroha SDK یا `iroha tools address` کا استعمال کریں.
- ایک باقاعدہ اظہار I105 کی توثیق نہیں ہے.

:::

## لفظی اناٹومی {#literal-anatomy}

ایک I105 حرف میں تین ملحقہ حصے ہوتے ہیں اور کوئی جداکار نہیں ہوتا:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

|حصہ |مقصد |چیک کی رقم کا احاطہ |
| ---------------- | ------------------------------------------------------------------ | ----------------- |
|نیٹ ورک سینٹل |ٹیکسٹ کو ایک `u16` چین discriminant میں نقشہ جات |احاطہ نہیں |
|مفید بوجھ |`base-105` کینونیکل اکاؤنٹ-کنٹرولر بائٹس کوڈنگ |احاطہ کیا |
| چیک سم | I105 حروفِ تہجی میں دکھائی گئی `Bech32m` طرز کی چھ `5-bit` قدریں | N/A |

پے لوڈ اور چیک سم اکاؤنٹ کنٹرولر کی شناخت کرتے ہیں۔

Sentinel نیٹ ورک کے تناظر کو منتخب کرتا ہے.

ایک ہی کنٹرولر میں Taira اور Minamoto پر ایک ہی پلے لوڈ اور چیکسوم ہوتا ہے، لیکن ہر نیٹ ورک مختلف لیڈر سینٹینل کا استعمال کرتا ہے۔

ایک ڈیکوڈر کو متوقع امتیاز کو نافذ کرنا ہوگا.

چیکسوم Sentinel کی تبدیلی کا پتہ نہیں لگا سکتا ہے.

### نیٹ ورک سینٹینلز {#network-sentinels}

|نیٹ ورک یا تناظر |زنجیروں میں فرق |ہیکس |کینونیکل سینٹینل |
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
|Taira عوامی ٹیسٹ نیٹ ورک |                            `369` |`0x0171` |`test` |
|Minamoto عوامی نیٹ ورک |                            `753` |`0x02f1` |`sora` |
|ترقیاتی تناظر |                              `0` |`0x0000` |`dev` |
|کوئی اور قدر `u16` |`0` ، `369`، اور `753` کے علاوہ سبھی |        — |`n` کے علاوہ کم از کم اعشاریہ، مثال کے طور پر `n42` |

نام زدہ اقدار ہمیشہ اپنا نام زدہ سینٹینل استعمال کرتی ہیں۔

`n00042` ، `n369`، `n753`، اور `n0` جیسے فارم کینیکل نہیں ہیں.

ٹرانزیکشن چین ID اور I105 چین کے فرقہ دار الگ الگ اقدار ہیں۔

ایک اختتامی نقطہ یا سلسلہ ID کا انتخاب ضمنی طور پر ایڈریس پروفائل کو منتخب نہیں کرتا ہے.

## معیاری سنگل کلیدی مثال {#normative-single-key-example}

ذیل میں مفید بوجھ اور Minamoto فارم کراس-SDK تعمیل فکسچر سے آتے ہیں.

Taira فارم ایک ہی مفید بوجھ پر Taira کی سینٹینل لاگو ہوتا ہے:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

کینونیکل مفید بوجھ کے ساتھ شروع ہوتا ہے `02 00 01 20`: سرخی `0x02`, کمپیکٹ سنگل کلیدی ٹیگ `0x00`, `Ed25519` منحنی خطوط ID `0x01`, اور ایک 32 بائٹ کلید کی لمبائی `0x20`.

`multihash` پریفیکس ان پٹ میٹا ڈیٹا ہے اور کنٹرولر کی مفید بوجھ میں کاپی نہیں کیا جاتا ہے.

## CLI کے ساتھ IDs بنائیں اور معائنہ کریں۔ {#create-and-inspect-ids-with-the-cli}

عوامی نیٹ ورک کے لیے نامزد پروفائل کو ترجیح دیں:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

ایڈریس کوڈک رویے کی تشخیص کرتے وقت I105 ان پٹ کو معمول اور موازنہ کریں:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

معلوم شدہ فارمیٹ، کینونیکل ہیکس اور منتخب کردہ نیٹ ورک کے تناظر کو JSON کے طور پر چیک کریں:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

تجزیہ کی ناکامیوں کو خاموشی سے قبول کیے بغیر نئے لائن علیحدہ فائل کے ایڈریس کوڈک ڈھانچے کا آڈٹ کریں:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution CLI توثیق کی حد

`convert` ، `normalize`، اور `audit` کمانڈ کم سطح کے `AccountAddress` کوڈیک پر کام کرتے ہیں.

وہ سینٹینل، الفبا، چیکسوم، بائٹ لمبائی، `CurveId`/کی شکل، اور ایڈریس پرت کی عین مطابق دوبارہ کوڈنگ کی تصدیق کرتے ہیں۔

وہ `AccountId` نہیں بناتے۔

وہ خود ہی تمام ملٹی سگ پالیسی کے معنی کو درست نہیں کرتے ہیں.

وہ ثابت نہیں کرتے کہ ہیڈر کلاس کنٹرولر سے ملتی ہے.

اختیار دہی یا مستقل ذخیرہ کرنے سے پہلے سخت `AccountId` توثیق استعمال کریں۔

:::

ایک نجی نیٹ ورک کے لئے، `--network-prefix` کے ساتھ واضح طور پر اس کی تشکیل شدہ امتیاز کا استعمال کریں.

کسی موجودہ پتے کو واضح سیاقوں کے درمیان تبدیل کرتے وقت، ماخذ کا سابقہ بھی `--expect-prefix` کے ذریعے فراہم کریں:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

ری کوڈنگ صرف نیٹ ورک کے سیاق و سباق کو تبدیل کرتی ہے.

یہ اکاؤنٹ کو ہدف نیٹ ورک پر رجسٹر نہیں کرتا ہے اور نہ ہی اس بات کا ثبوت دیتا ہے کہ اسی کنٹرولر کو وہاں دوبارہ استعمال کیا جانا چاہئے۔

## انکوڈنگ الگورتھم {#encoding-algorithm}

کینونیکل کوڈر ان کارروائیوں کو انجام دیتے ہیں:

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

لیڈنگ صفر بائٹس کو صفر قدر والے `base-105` ہندسوں کے طور پر محفوظ کیا جاتا ہے۔

چیک سم `Bech32` کے `polymod` جنریٹرز اور مستقل `0x2bc830a3` استعمال کرتا ہے۔

صرف چیک سم کے لیے HRP، ASCII سٹرنگ `snx` ہے۔

صرف چیک سم کے لیے HRP ایڈریس میں شامل نہیں کیا جاتا۔

چھ چیک سوم اقدار `0..31` کی حد میں ہیں اور وہی I105 الفبا کے ذریعے پیش کیے جاتے ہیں جو مفید بوجھ کے ساتھ ہے۔

### I105 الفبا {#i105-alphabet}

ان 105 علامتوں کی فہرست اسی ترتیب میں ہے۔

پہلی سطر `Bitcoin Base58` حروف تہجی ہے اور اس میں اعداد `0..57` شامل ہیں۔

دوسری سطر میں `58..104` ہندسوں پر مشتمل ہے۔

کوڈک کو لاگو کرتے وقت قطاروں کو مربوط کریں۔

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

الفبا `Unicode` - حساس ہے.

عین مطابق ترتیب میں `compatibility-width` جاپانی `kana` علامتوں کے علاوہ `ヰ` اور `ヱ` کے لئے دکھائے گئے کوڈ پوائنٹس کا استعمال کیا جاتا ہے۔

NFC، NFKC، چوڑائی کی تبدیلی، کیس فولڈنگ، یا نظر کے مطابق متبادل کا استعمال نہ کریں.

ASCII `0`, `O`, `I`, اور `l` یہ حروف تہجی کی علامتیں نہیں ہیں۔

## کینونیکل اکاؤنٹ کا مفید بوجھ {#canonical-account-payload}

`base-105` جسم ایک بائنری اکاؤنٹ پلے لوڈ کوڈ کرتا ہے، نہ ہی عوامی کلید سٹرنگ اور نہ ہی ایک Norito JSON اعتراض:

```text
header:u8 || controller:variable
```

ذیل میں تمام کثیر بائٹ انٹیجرز غیر دستخط شدہ ہیں اور `big-endian`۔

ڈومین، ڈیٹا اسپیس، عرفات، UAID، اور اکاؤنٹ میٹا ڈیٹا بائٹس موجود نہیں ہیں۔

### ہیڈر بائٹ {#header-byte}

|بٹس |چوڑائی |موجودہ کوڈر آؤٹ پٹ |معنی |
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |ایڈریس فارمیٹ ورژن فیلڈ |
| `4..3` |     2 |`0` ایک ہی کلید، `1` ملٹی سگنل |ایڈریس کلاس |
| `2..1` |     2 |                          `1` |معمول کے ورژن فیلڈ |
| `0` | 1 | `0` | محفوظ `extension flag` |

موجودہ V1 کوڈر ایک واحد کلید کنٹرولر کے لئے ہیڈر `0x02` اور ایک کثیر سگنل کنٹرولر کیلئے `0x0a` جاری کرتے ہیں۔

ایڈریس کلاسز `2` اور `3` تفویض نہیں کی گئی ہیں۔

`extension flag` کا ایک `1` مسترد کیا جاتا ہے.

کم سطح کا ڈیکوڈر دوسرے ورژن اور معمول کے بٹ اقدار کو برقرار رکھ سکتا ہے اور کنٹرولر ٹیگ کے ساتھ کلاس کی آزادانہ طور پر کراس چیک نہیں کرتا ہے۔

`AccountId` میں تبدیل کرنا اور اس کی کینونیکل رینڈرنگ کا موازنہ کرنا موجودہ V1 کینونیکلٹی کو ثابت کرتا ہے۔

### سنگل کلیدی کنٹرولر {#single-key-controller}

جب خام عوامی کلید کا پے لوڈ زیادہ سے زیادہ 255 بائٹس ہو تو کمپیکٹ شکل استعمال کریں:

|فیلڈ |چوڑائی |قدر یا معنی |
| ------------ | --------------: | ------------------------ |
|`tag` |1 بائٹ |`0x00` |
|`curve` |1 بائٹ |`CurveId` رجسٹری کی قیمت |
|`key_len` |1 بائٹ |خام کلید کی لمبائی |
|`public_key` |`key_len` بائٹس |خام عوامی کلید مفید بوجھ |

255 بائٹ سے زیادہ لمبی چابیاں توسیع شدہ فارم کا استعمال کرتی ہیں:

|فیلڈ |چوڑائی |قدر یا معنی |
| ------------ | --------------: | ---------------------------- |
|`tag` |1 بائٹ |`0x02` |
|`curve` |1 بائٹ |`CurveId` رجسٹری کی قیمت |
|`key_len` |2 بائٹس |خام کلید کی لمبائی، `big-endian` |
|`public_key` |`key_len` بائٹس |خام عوامی کلید مفید بوجھ |

جو کلید کمپیکٹ شکل میں سما سکتی ہو، اس کے لیے توسیعی انکوڈنگ کینونیکل نہیں ہے۔

### ملٹی سیگ کنٹرولر {#multisig-controller}

|فیلڈ |چوڑائی |قدر یا معنی |
| ---------------- | -------: | ------------------------------ |
|`tag` |1 بائٹ |`0x01` |
|`policy_version` |1 بائٹ |موجودہ قیمت `1` |
|`threshold` |2 بائٹس |مطلوبہ مجموعی منظوری وزن |
|`member_count` |2 بائٹس |مندرجہ ذیل ممبران کی تعداد |
|`members` |متغیر |بار بار ممبر ریکارڈ |

ہر رکن کا ریکارڈ ہے:

|فیلڈ |چوڑائی |معنی |
| ------------ | --------------: | ------------------------ |
|`curve` |1 بائٹ |`CurveId` رجسٹری کی قیمت |
|`weight` |2 بائٹس |ممبر کی منظوری کا وزن |
|`key_len` |2 بائٹس |خام کلید کی لمبائی |
|`public_key` |`key_len` بائٹس |خام عوامی کلید مفید بوجھ |

ایک درست پالیسی میں کم از کم ایک ممبر، مثبت وزن، کوئی دوہری عوامی چابیاں نہیں، اور `1` سے ممبر وزن کے مجموعہ تک کی حد ہوتی ہے.

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

کینونیکل تشکیل ارکان کو پہلے دستخطی الگورتھم کے مستحکم نام، پھر صفر جداکار بائٹ، اور اس کے بعد خام عوامی کلید کے بائٹس کے لحاظ سے ترتیب دیتی ہے۔

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

ایک I105 حرف کی کوئی مقررہ حروف کی لمبائی نہیں ہے کیونکہ multisig اور پوسٹ کوانٹم کنٹرولرز بڑے ہو سکتے ہیں.

### رجسٹری `CurveId` {#curveid-registry}

آخری کالم میں مطلوبہ اختیاری خصوصیت `Cargo` کا نام دیا گیا ہے۔

ڈیش کا مطلب یہ ہے کہ رجسٹری اندراج بغیر کسی اختیاری ڈیٹا ماڈل خصوصیت کے دستیاب ہے۔

|ID |سگنلنگ الگورتھم |مطلوبہ `Cargo` خصوصیت |
| ---: | -------------------------------------------- | ------------------------ |
|  `1` |`Ed25519` | —                        |
|  `2` |`ML-DSA` | —                        |
|  `3` |`BLS12-381 normal` |`bls` |
|  `4` |`secp256k1` | —                        |
|  `5` |`BLS12-381 small` |`bls` |
| `10` |`GOST R 34.10-2012 256-bit, parameter set A` |`gost` |
| `11` |`GOST R 34.10-2012 256-bit, parameter set B` |`gost` |
| `12` |`GOST R 34.10-2012 256-bit, parameter set C` |`gost` |
| `13` |`GOST R 34.10-2012 512-bit, parameter set A` |`gost` |
| `14` |`GOST R 34.10-2012 512-bit, parameter set B` |`gost` |
| `15` |`SM2` |`sm` |

غیر مختص کردہ IDs اور وصول کرنے والے بلڈ میں غیر فعال الگورتھم کو مسترد کیا جاتا ہے۔

کلیدی فائدہ مند بوجھ کو `CurveId` کے ذریعہ منتخب کردہ الگورتھم کے لئے بھی ساختہ طور پر درست ہونا چاہئے.

## سخت AccountId توثیق اور کینونیکلٹی۔ {#strict-accountid-validation-and-canonicality}

متوقع چین ڈسکرمننٹ کے ساتھ SDK کو کنفیگر کرنے کے بعد، قدر کو `AccountId` کے طور پر پارس کریں اور واپس آنے والی کینونیکل نمائندگی کا موازنہ کناروں کی اجازت یافتہ خالی جگہ ہٹائی ہوئی ان پٹ سے کریں۔

اس کا موازنہ اہم ہے کیونکہ تجزیہ کار `AccountId` کی تعمیر کے دوران ڈیکوڈ کنٹرولر مواد کو معمول پر لا سکتا ہے۔

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

غیر قابل اعتماد سٹرنگ کے ل a ، ایک مطابق درخواست:

1. مکمل قدر کے اردگرد صرف اجازت یافتہ ترسیلی خالی جگہ کو ہٹائیں۔
2. Sentinel پڑھیں اور متوقع سلسلہ discriminant کی ضرورت ہے.
3. ہر باقی `Unicode` علامت کا نقشہ درست 105 علامات الفبا کے ذریعے.
4. چیک سم کے چھ ہندسوں کو الگ کریں۔
5. مفید لوڈ ہندسوں کو واپس canonical بائٹس میں تبدیل کریں.
6. ان کینونیکل بائٹس پر چیک رقم کی تصدیق کریں.
7. ہیڈر اور کنٹرولر کا تجزیہ کریں، جس کی ضرورت ہے:
   - فیلڈ کی درست لمبائی
   - ایک معاون `CurveId`
   - ایک درست عوامی کلید
   - کوئی پیچھے بائٹ نہیں
   - اگر قابل اطلاق ہو تو ایک درست ملٹی سگ پالیسی
8. `AccountId` تعمیر کریں.
9. متوقع ڈسکرمننٹ کے لیے `AccountId` کو کینونیکل صورت میں پیش کریں۔
10. کناروں کی خالی جگہ ہٹائی ہوئی ان پٹ کے ساتھ `byte-for-byte` برابری لازم کریں۔

ایپلی کیشن کا واضح آخری `render-and-compare` مرحلہ غیر کم سے کم عددی سینٹینلز، غیر کینونیکل کنٹرولر لے آؤٹس، دوبارہ ترتیب دیے گئے پالیسی مواد، اور ہر ایسی دوسری املا کو مسترد کرتا ہے جو ڈی کوڈ تو ہو سکتی ہو لیکن انکوڈر کا موجودہ V1 آؤٹ پٹ نہ ہو۔

ایک کامیاب چیک سوٹ یا کم سطح `AccountAddress` تجزیہ اس چیک کی جگہ نہیں لے سکتا.

ان اقدار کو ایک سخت اکاؤنٹ- ID فیلڈ میں قبول نہ کریں:

- اکاؤنٹ کا عرف، مثلاً `alice@wonderland.universal`
- ایک I105 لٹرل جس کے آخر میں `@domain` لاحقہ شامل ہو
- ایک عوامی کلید `multihash` جیسے `ed0120...`
- کینیکل پائل لوڈ ہیکس جیسے `0x02000120...`
- غلط چین ڈسکرمننٹ کے لیے ایڈریس
- بڑی یا چھوٹی حرفوں، حروف کی چوڑائی، `kana`، پے لوڈ، یا چیک سوم کے ساتھ تبدیل شدہ سٹرنگ

درخواست کی حد پر عرفی ناموں کو حل کریں اور اجازت، دستخط، اجازت اور آڈٹ ریکارڈز کے لئے واپسی شدہ کینونیکل I105 ID برقرار رکھیں.

## API، اسٹوریج اور ڈسپلے کے قوانین {#api-storage-and-display-rules}

- JSON اکاؤنٹ کے کھیتوں میں درست I105 UTF-8 تار بھیجیں۔
- `Percent-encode` مکمل اکاؤنٹ ID اس سے پہلے کہ اسے ایک URL راستے کے حصے میں رکھا جائے۔
- کبھی بھی I105 ID کی جگہ اکاؤنٹ کا عرف استعمال نہ کریں۔
- `byte-preserving` موازنہ semantics کے ساتھ کوڈک کی طرف سے واپس کینیکل سٹرنگ ذخیرہ کریں.
- ایسا تقابلی ترتیب نامہ استعمال کریں جو حروف کی بڑی/چھوٹی حالت اور حروف کی چوڑائی برقرار رکھے۔
- برآمد شدہ اکاؤنٹ کے اعداد و شمار اور بیک اپ کے ساتھ سلسلہ امتیاز یا نامزد کردہ نیٹ ورک پروفائل کو برقرار رکھیں.
- ایک ایڈریس کو صرف اس کے نیٹ ورک کے تناظر سے دوبارہ استعمال کریں۔
- مکمل ایڈریس دکھائیں اور اسے نقل کرنے کی سہولت فراہم کریں۔
- ہر `kana` حرف کو بعینہٖ محفوظ رکھیں۔
- جب ایک کمپیکٹ ڈسپلے اس کے وسط کو مختصر کرتا ہے تو مکمل ایڈریس دستیاب رکھیں۔
- ایک عرفی نام سے دوبارہ تعمیر کرنے کے بجائے ذخیرہ شدہ کینونیکل ID کا استعمال کریں۔

`AccountId` ڈسپلے اور JSON کا استعمال کینونیکل I105.

نچلے درجے کی `AccountAddress` ڈسپلے/JSON نمائندگی اندرونی اور ڈیبگنگ کے سیاق و سباق کے لئے کینونیکل ہیکس کا استعمال کرتی ہے۔

جب ایک بیرونی اکاؤنٹ ID کی ضرورت ہو تو صریح `AccountAddress` I105 کوڈر پر کال کریں۔

اکاؤنٹ تخلیق اور مستعار حل کے ورک فلوز کے لئے، [اکاؤنٹس اور مستعار ](/ur/cookbook/accounts-and-aliases.md) کے ساتھ جاری رکھیں.

اکاؤنٹ ڈیٹا ماڈل کے لئے، دیکھیں [اکاؤنٹس ](/ur/blockchain/accounts.md).
