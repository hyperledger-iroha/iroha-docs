# I105 帳戶地址格式 {#i105-account-address-format}

I105 是 Iroha 3 `AccountId` 的規範外部文字格式。

它的有效負載代表了帳戶控制者.

它的監視器會使用鏈區分符識別預期網路.

使用任何一個 API,交易,許可或查詢要求使用 ID 的法規帳戶.

I105 帳戶 ID 是無域名的.

一個值如 `treasury@payments.universal`是一個帳戶別名,而不是 I105 ID 的另一種拼寫.

匯出 I105 ID 不註冊或資助帳戶.

::: warning 防止大多數整合失敗的規則

- 在編碼或驗證地址之前,選擇網路配置檔案.
- 精確儲存並比較規範 UTF-8 字串。
- 保留字母大小寫，且不要套用 `Unicode` 正規化。
- I105 ID 不得帶有 `@domain` 或 `@domain.dataspace` 字尾。
- 使用 Iroha SDK 或 `iroha tools address`.
- 正規表示式不是 I105 驗證器。

:::

## 字面上的解剖學 {#literal-anatomy}

I105 字母有三個相鄰的部分,沒有分離器:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

| 部分             | 用途                                                            | 校驗和涵蓋範圍 |
| ---------------- | ------------------------------------------------------------------ | ----------------- |
| 網路 sentinel | 將文字對映到一個 `u16` 鏈區分符                      | 未涵蓋       |
| 有效載荷          | 規範帳戶控制器位元組的 `base-105` 編碼      | 已涵蓋           |
| 校驗和         | 透過 I105 字母表呈現的六個 `Bech32m` 風格 `5-bit` 值 |N/A |

有效載荷和校驗和識別帳戶控制器。

Sentinel 選擇網路上下文。

同一個控制器在 Taira 和 Minamoto 上具有相同的有效載荷和檢查數量,但每個網路使用不同的領先哨兵.

解碼器必須確保鏈區分符符合預期。

校驗和無法偵測 sentinel 替換。

### 網路哨兵 {#network-sentinels}

| 網路或上下文      |               鏈區分符 |      十六進位 | 規範 sentinel                          |
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
|Taira 公共測試網 |                            `369` |`0x0171`|`test`|
| Minamoto 公共網路 |                            `753` |`0x02f1`|`sora`|
|發展環境|                              `0` |`0x0000`|`dev`|
|任何其他 `u16`值|除了 `0`, `369`和 `753` 之外,所有|        — |`n`加上最小十數,例如 `n42` |

命名的值總是使用他們的名字哨兵.

`n00042`,`n369`, `n753`和 `n0`等形式不屬於規範形式.

交易鏈 ID 和 I105 鏈區分符是單獨的值.

選擇端點或鏈 ID 並不暗示地選擇地址配置檔案.

## 規範單鍵的例子 {#normative-single-key-example}

下面的有效載荷和 Minamoto 表單來自交叉 SDK 合規性測試資料.

Taira 形式適用於同一個實用載荷的 Taira 哨兵:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

規範的有效載荷始於 `02 00 01 20`:標題`0x02`,緊單鍵標籤 `0x00`,曲線 `Ed25519` ID `0x01`和一個32位元組鍵長度 `0x20`.

`multihash`前是輸入後設資料,不復制到控制器的有效載荷中.

## 用 CLI 建立和檢查 IDs {#create-and-inspect-ids-with-the-cli}

對於公共網路,更喜歡一個命名的個人資料:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

在診斷地址碼克行為時,正常化和比較 I105 輸入:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

檢查被檢測到的格式,神經六合和選定的網路文字為 JSON:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

稽核一個新線分隔的檔案的地址編碼結構,而不預設分析故障:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution CLI 驗證邊界

`convert`, `normalize`和`audit`命令在較低階別的 `AccountAddress`編碼中執行.

它們驗證 sentinel、字母表、校驗和、位元組長度、`CurveId`/金鑰結構以及地址層的精確重新編碼。

它們並未實現 `AccountId`.

它們本身並不能驗證所有多標籤的政策語義.

它們無法證明標頭類別與控制器相符。

在授權或持久化之前使用嚴格的 `AccountId` 驗證。

:::

對於私人網路,使用其配置的區分符明確地與 `--network-prefix`.

當將現有地址轉換成明確的文字時,還輸入源為 `--expect-prefix`:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

重新編碼只改變了網路環境.

它不會在目標網路上註冊帳戶,也不證明該控制器應該在這裡重複使用.

## 編碼演算法 {#encoding-algorithm}

標準編碼器執行以下操作:

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

領先零位元組儲存為零值的 `base-105` 數字.

檢查總數使用`Bech32` `polymod`發電機和常量 `0x2bc830a3`.

只有檢查金額的 HRP 為 ASCII 字串 `snx`.

檢查金額僅為 HRP 在地址上不列印.

檢查總值的六個值在 `0..31`範圍內,並透過同樣的 I105 字母表呈現為實用載荷.

### I105 字母 {#i105-alphabet}

這些105個符號是按照這個順序排列的.

第一個行是`Bitcoin Base58`字母,包含 `0..57`數字.

第二行包含 `58..104` 數字.

在執行編碼器時,連線列表.

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

字母是對 `Unicode`敏感.

確切序列使用`compatibility-width`日本 `kana`符號加上`ヰ`和`ヱ`的程式碼點.

不要套用 NFC、NFKC、寬度轉換、大小寫摺疊或相似字元替換。

ASCII `0`,`O`, `I`和 `l`不是字母符號.

## 佳能帳戶實用負載 {#canonical-account-payload}

`base-105`實體編碼了二元帳戶有效載荷,而不是公鑰字串,也不是 Norito JSON 物件:

```text
header:u8 || controller:variable
```

下面的所有多位元組整數是未簽名的,並且`big-endian`.

其中不包含網域、資料空間、別名、UAID 或帳戶中繼資料位元組。

### 標題位元組 {#header-byte}

| 位元   | 寬度 |       目前編碼器輸出 | 含義                      |
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |地址格式版本欄位 |
| `4..3` |     2 |`0`單鍵, `1`多簽名 |地址類|
| `2..1` |     2 |                          `1` |標準化版本欄位|
| `0`    |     1 |                          `0` |預留的 `extension flag`|

目前的 V1 編碼器為單鍵控制器產生標頭 `0x02` 和為多籤控器發放標題`0x0a`.

`2`和 `3`的地址類別未被分配.

`extension flag` 的 `1`被拒絕.

低階解碼器可以儲存其他版本和正常化位元值,並且不會獨立與控制器標籤進行交叉檢查.

轉換為 `AccountId` 並比較其規範呈現可證明目前 V1 的規範性。

### 單鍵控制器 {#single-key-controller}

在公共金鑰的原始有效載荷最多為255位元組時使用緊形式:

| 欄位        |           寬度 | 值或含義         |
| ------------ | --------------: | ------------------------ |
|`tag`|一個位元組|`0x00`|
|`curve`|一個位元組|`CurveId`登記值 |
|`key_len`|1 位元組|原始鍵長度|
|`public_key`|`key_len`位元組 |公共鑰匙的原始有效載荷|

長於255位元組的鍵使用擴充套件形式:

| 欄位        |           寬度 | 值或含義             |
| ------------ | --------------: | ---------------------------- |
|`tag`|1 位元組|`0x02`|
|`curve`|1 位元組|`CurveId`登記值 |
|`key_len`|兩個位元組|原金鑰長度, `big-endian` |
|`public_key`|`key_len`位元組 |公共鑰匙的原始有效載荷|

擴充套件的編碼不是合適於緊形式的鑰匙的標準.

### 多位控制器 {#multisig-controller}

| 欄位            |    寬度 | 值或含義               |
| ---------------- | -------: | ------------------------------ |
|`tag`|1 位元組|`0x01`|
|`policy_version`|1 位元組|目前價值 `1` |
|`threshold`|兩個位元組|所需的總批准重量 |
|`member_count`|兩個位元組|下列成員數量 |
|`members`| 可變 | 重複的成員記錄        |

每個成員的記錄是:

| 欄位        |           寬度 | 含義                  |
| ------------ | --------------: | ------------------------ |
|`curve`|1 位元組|`CurveId`登記值 |
|`weight`|兩個位元組|成員批准權重|
|`key_len`|兩個位元組|原始鍵長度|
|`public_key`|`key_len`位元組 |公共鑰匙的原始有效載荷|

有效策略至少包含一個成員，各權重為正，沒有重複公鑰，且閾值介於 `1` 與成員權重總和之間。

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

根據簽署演算法的穩定名稱,零分離位元組,然後是原始公鑰位元組來排序成員.

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

一個 I105 字母沒有固定的符號長度,因為多籤和後量子控制器可以很大.

### `CurveId` 登錄檔 {#curveid-registry}

在最後一列中,指定所需的可選 `Cargo` 功能.

按表示登錄檔輸入沒有可選的資料模型功能.

|ID|簽字演算法|要求的 `Cargo`特徵|
| ---: | -------------------------------------------- | ------------------------ |
|  `1` |`Ed25519`| —                        |
|  `2` |`ML-DSA`| —                        |
|  `3` |`BLS12-381 normal`|`bls`|
|  `4` |`secp256k1`| —                        |
|  `5` |`BLS12-381 small`|`bls`|
| `10` |`GOST R 34.10-2012 256-bit, parameter set A`|`gost`|
| `11` |`GOST R 34.10-2012 256-bit, parameter set B`|`gost`|
| `12` |`GOST R 34.10-2012 256-bit, parameter set C`|`gost`|
| `13` |`GOST R 34.10-2012 512-bit, parameter set A`|`gost`|
| `14` |`GOST R 34.10-2012 512-bit, parameter set B`|`gost`|
| `15` |`SM2`|`sm`|

不分配的 IDs 和在接收構件中禁用的演算法被拒絕.

關鍵有效載荷也必須對被申報的 `CurveId`所選的演算法具有結構性有效性.

## 嚴格的 AccountId 驗證和規範性 {#strict-accountid-validation-and-canonicality}

在使用預期鏈區分符設定 SDK 後，將輸入解析為 `AccountId`，並將傳回的規範呈現與去除首尾空白後的輸入進行比較。

這種比較是顯著的,因為解析器可以在構建 `AccountId`時正常化可解碼控制器材料.

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

對於不值得信賴的字串,符合要求的應用程式應:

1. 僅刪除整個值周圍允許存在的傳輸空白。
2. 讀取 sentinel，並要求鏈區分符符合預期。
3. 按準確的 105 符號字母表對映其餘每個 `Unicode` 符號。
4. 分離出六個校驗和數字。
5. 將有效載荷數字轉換回規範位元組。
6. 驗證這些規範位元組的校驗和。
7. 解析標頭和控制器，並要求：
   - 精確的欄位長度
   - 受支援的 `CurveId`
   - 有效的公鑰
   - 沒有尾隨位元組
   - 適用時有效的多重簽名策略
8. 建構 `AccountId`。
9. 針對預期的鏈區分符以規範形式呈現 `AccountId`。
10. 要求與去除首尾空白後的輸入 `byte-for-byte` 相等。

該應用程式的明確最終步驟 `render-and-compare` 拒絕了非最小數值哨兵,非規範控制器佈局,重新排序的政策材料以及任何其他解碼但不是編碼器當前輸出的 V1 拼寫.

校驗和成功或低層級 `AccountAddress` 解析不能替代此檢查。

在嚴格的帳戶-ID 欄位中,不要接受這些值:

- `alice@wonderland.universal`這樣的帳戶別名
- 一個 I105 字型,附上一個 `@domain`後音
- 一個公鑰 `multihash`,如`ed0120...`
- 規範有效載荷列表 (如 `0x02000120...`)
- 一個錯誤的鏈分辨器地址
- 大寫或小寫字母、字元寬度、`kana`、有效載荷或校驗和被更改的字串

在應用程式邊界解析別名，並保留傳回的規範 I105 ID，用於授權、簽署、權限和稽核記錄。

### 常見穩定的錯誤程式碼 {#common-stable-error-codes}

|程式碼| 含義                                                             |
| -------------------------------- | ------------------------------------------------------------------- |
|`ERR_UNEXPECTED_NETWORK_PREFIX`|解碼的區分器不符合所需網路.|
|`ERR_CHECKSUM_MISMATCH`|六個檢查總數符號不匹配的有效載荷|
|`ERR_INVALID_I105_CHAR`|一個符號是正確字母之外的.|
|`ERR_MISSING_I105_SENTINEL`|沒有找到規範名字或數字哨兵.|
| `ERR_I105_TOO_SHORT` | 正文無法同時容納有效負載和校驗和 |
|`ERR_INVALID_LENGTH`|一個控制器欄位是縮小的,或者使用非規範長度形式|
|`ERR_UNKNOWN_CURVE`|控制者宣佈未分配或不可使用的 `CurveId` |
|`ERR_INVALID_PUBLIC_KEY`|對於其 `CurveId`所選的演算法來說,關鍵是無效的.|
|`ERR_UNSUPPORTED_ADDRESS_FORMAT`|輸入不是被接受的規範形式 I105 |

## API,儲存和顯示規則 {#api-storage-and-display-rules}

- 在 JSON 帳戶欄位中傳送準確的 I105 UTF-8 字串.
- `Percent-encode`在將其置於 URL 路徑段之前的完整帳戶 ID.
- 切勿以帳戶別名替代 I105 ID。
- 使用 `byte-preserving` 比較語義儲存編解碼器傳回的規範字串。
- 使用保留字母大小寫和字元寬度的定序規則。
- 保持鏈區分或命名的網路配置檔案,並將出口的帳戶資料和備份儲存.
- 僅用其網路背景重新使用地址.
- 顯示完整地址,並提供複製操作.
- 保持每一個 `kana` 字元的精確.
- 如果一個緊的顯示屏縮短中部時,請保持完整地址.
- 使用儲存的規範 ID，而不是根據別名重新建構它。

`AccountId` 的顯示和 JSON 表示使用規範 I105。

較低層級的 `AccountAddress` 顯示/JSON 表示在內部和偵錯情境中使用規範十六進位格式。

如果需要外部帳戶 ID,請呼叫明確的 `AccountAddress` I105 編碼器.

對於建立帳戶和號解決工作流程,繼續使用 [帳戶和名](/zh-hant/cookbook/accounts-and-aliases.md).

對於帳戶資料模型,請見 [帳戶](/zh-hant/blockchain/accounts.md).
