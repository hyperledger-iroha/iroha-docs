# 執行原子私人跨資料空間解決方案 {#run-atomic-private-cross-dataspace-settlement}

`AtomicPrivateSettlementV1`在每一個2到255個 SORA Nexus 資料域中協調一個機密結算段,並在一項全球狀態交易中完成每個結算段.被拒絕,過期或中止的捆綁不適用於任何結算段.透明原生 AMX DvP/PvP 仍然是單獨的協議路徑.

::: warning 發行狀態
此功能受治理、預設停用，且尚未取得生產使用資格。在確切版本通過所有已公布的功能、隱私、容錯、效能、可重現建置、獨立密碼學審查與構件發布關卡之前，請勿將其啟用於真實 CBDC 價值。
:::

## 協議所隱藏的內容 {#what-the-protocol-hides}

每條結算段都使用固定的兩輸入,三輸出私人筆記證明.委員會驗證人員驗證了證明和不透明狀態過渡;他們沒有接收平文部分,資產,金額,備忘錄或業務結果.授權的本地審計員解密了填充的審計囊,檢查了這些內容,並簽署了一份針對目的的單獨批准.預設政策接受由受監管的審計員集中的一個批准.

公共承載交易和收據故意披露:

- 網路和捆綁識別符號
- 參與者資料空間路線和參與者的數量
- 時間和過期的高度
- 穩定的不透明池識別符號,根,取消符,承諾和固定加密文字插槽
- 委員會權限主體和準確的3/4可用性,準備和提交證書
- 支持者,公共網路費用和終端狀態

這就是內容的保密性,而不是流量匿名性. 時間表,參與者數量,資料空間身份和穩定池活動仍然是公開的.只容納一個 CBDC 的資料空間也可以使資產從路線下降,即使沒有字面上的資產識別符釋出.

## 部署要求 {#deployment-requirements}

在啟用之前,運營商需要所有以下條件:

1. 每個參與資料空間的確切四個驗證器,具有不同的 BLS 共識金鑰和擁有證明.
2. 強制性 Sumeragi DA/RBC 可用於每一個高度
3. 一個管理的機密結算池和每一個資料空間中的初始根
4. 一個活躍的 V1 私人筆記功能和單獨的結算證明配置檔案
5. 至少有一個受監管的本地 `PrivateSettlementAuditPolicyV1`,包括不同的審計簽名和混合加密金鑰,一個關鍵時代,高度有效性和批准門
6. 在配置的保留期內,足夠的私人輔助記錄儲存
7. 一個能夠提交最終公共承載交易的中立發起方帳戶

審計員也可以執行驗證器,但必須使用單獨的共識,審計簽名和審計加密金鑰.在監管保留期內保留已停用的解密金鑰,或在停用前完成受治理且經過測試的膠囊重新包裝.

四驗證者許可權集錨定在鏈上狀態中，並非由使用者端提供。在資訊清單的 `authority_context_height`，每個驗證者都從共識狀態解析精確排序的 lane/dataspace 名單和作用中的 lane incarnation，要求解析出的高度相符，並驗證四個 BLS 金鑰及其持有證明。Upload、Prepare 和最終收據准入均使用同一歷史許可權集。

## 設定錄取 {#configure-admission}

所有生產行為都來自節點配置.環境變數不能啟用這個路徑. 傳送的預設是 `enabled = false`;將功能禁用不需要任何定位特定的配置.

管理人員已註冊所需的功能,並以適當的通知選擇了啟用高度後,將每個相關節點都配置一致:

```toml
[nexus.atomic_private_settlement]
enabled = true
activation_height = 500000
minimum_activation_notice_blocks = 7200
proof_profile_version = 1
max_participants = 255
max_expiry_blocks = 7200
audit_timeout_blocks = 1200
prepare_timeout_blocks = 1200
commit_timeout_blocks = 1200
capsule_padding_classes_bytes = [4096, 16384, 65536, 262144]
max_proof_bytes = 8388608
max_capsule_bytes = 1048576
max_carrier_bytes = 4194304
sidecar_retention_blocks = 1000000
sidecar_max_records = 256
sidecar_max_total_bytes = 3221225472
default_min_auditor_approvals = 1
permitted_policy_versions = [1]
```

此範例使用隨軟體提供的 V1 限值，並非效能建議。在選擇運作限值之前，請在目標硬體上測量儲存、證明、膠囊、承載交易和延遲的容量邊界。三個階段的逾時都必須在 `max_expiry_blocks` 範圍內，輔助記錄的保留期至少應涵蓋該到期視窗。

`max_capsule_bytes` 限制整個 `PrivateSettlementAuditCapsuleV1` 的規範 Norito 編碼：AAD、nonce、密文、向量框架、稽核者身分，以及每個已包裝 DEK 資料列。它不是僅針對密文的限制。每個已設定的填補類別都必須能容納至少 `default_min_auditor_approvals` 名稽核者的保守完整膠囊封裝。Torii 還會拒絕 `min_approvals` 低於該治理下限的新准入原則，並拒絕完整規範編碼過大的任何實際膠囊。

`max_carrier_bytes`不僅限於受認證的捆綁,但限制了完全的法規贊助商簽署的交易.計數包括註冊指令框架,交易授權主體和後設資料,費用意圖和簽名.普通的網路交易限制仍然適用於獨立的上限.

除非受治理的功能處於作用中狀態、其狀態高度和啟用高度滿足通知期、編譯後的證明設定檔與 V1 相符，且鏈上集區和稽核記錄均為最新，否則啟用會採用失敗關閉策略。僅啟用設定旗標並不足夠。

## 結算工作流程 {#settlement-workflow}

客戶本地構建證明和加密囊.秘密證人必須留在原生錢包或原生工作者中;不要將它們序列成申請日誌, Python 物件, HTTP 請求或持久的協調記錄.

膠囊和每個稽核者 DEK 包裝的已驗證資料包含精確的狀態錨定委員會摘要和 `authority_context_height`，以及網路、路由/執行個體、套件、結算區段、原則、金鑰 epoch 和明文承諾。已包裝金鑰不能移到其他名單或歷史許可權內容。

對於每條規律的結算段,協調員然後執行這個序列:

1. 將臨時加密材料上傳到全部四個驗證器，並取得規範的精確 3-of-4 可用性憑證。
2. 讓授權稽核者取得並解密其膠囊，重新計算公開繫結，套用本機原則，並提交核准。
3. 在投票之前,每個驗證者獨立檢查和穩定地進行分別測試.在每一個測試的響應者身上,保持可規定的3/4預備證明.
4. 每個結算段都取得 Prepare 憑證後，建立不可變的完整 Prepare 屏障。請求並持久儲存規範的 3-of-4 Commit 憑證。如果協調器重新啟動，請向參與節點查詢其在本機持久儲存的 Prepare 和 Commit 憑證，選擇一份規範且達到等效法定人數要求的憑證，並在繼續之前重新分發；切勿從未經身分驗證的本機快取重建憑證。
5. 讓清單贊助方簽署並提交恰好一個全域承載交易。該承載交易包含一條 `FinalizeAtomicPrivateSettlementV1` 指令和精確、完整、已認證的套件。協調器和 WSV 預檢會測量完整封裝的最終化指令，包括已註冊指令的框架。Torii 和核心的一次性承載交易繫結會對贊助方簽署的精確規範交易執行 `max_carrier_bytes`，其中包括權限、中繼資料、費用意圖和簽章。Torii 會拒絕在其權限內容之前提交的承載交易；若它在到期前仍可能達到最終性的最後准入高度或之後進入，或超出治理規定的到期區間，也會被拒絕。
6. 查詢公開捆綁狀態和回執,直到全球最終完成.處理本地輔助記錄狀態為暫時的,直到它調整了不可改變的全球終端記錄.

Rust 客戶端透過包括`certify_and_upload_private_settlement_legs_v1`,`prepare_private_settlement_bundle_v1`,`commit_private_settlement_bundle_v1`和`submit_private_settlement_bundle_v1`在內的方法來暴露這種流動. 可安全因應重新啟動的協調流程使用 `recover_or_prepare_private_settlement_bundle_v1` 和 `recover_or_commit_private_settlement_bundle_v1`。委員會和審計人員的呼叫要求明確的角色憑證;它們不會重複使用普通帳戶簽字者.

## 安全地轉換審計政策 {#rotate-an-auditor-policy-safely}

使用隱私管理授權的 `RotatePrivateSettlementPoolPolicyV1`指令. 它必須指定當前的確切治理測試,保持相同的路線,合併和資產繫結承諾,提升治理修訂一項,使用更新的關鍵時代和不同的政策/治理測驗,並在包含旋轉的區塊上啟用. 池邊界、根、取消器、輸出、重播集和最終收據會被保留. 不要包含在輪換啟用高度觸及相同 route/pool 的收據;該指令會拒絕此邊界.

公共集區投影保留完整的已取代原則修訂譜系。因此，在輪替前最終確定的收據在重新啟動後仍然有效，精確重放該收據仍具有冪等性。該譜系不授權未完成的工作：任何跨越啟用邊界的舊原則套件都會在全域狀態變更前以失敗關閉方式失敗。請保留開啟已儲存膠囊所需的每個舊解密金鑰，或在銷毀前完成受治理且經過測試的膠囊重新包裝。

## Torii 路線家族 {#torii-route-family}

這些路線使用規範的 Norito 請求和響應物件.驗證和限制的響應使用私人 `no-store`快取行為.

|行動|方法和路徑|主體|
| ------------------ | -------------------------------------------------------------------------- | --------------------------- |
|載入結算段|`POST /v1/nexus/private-settlements/legs`|規範帳戶簽名|
|可用性分享|`POST /v1/nexus/private-settlements/legs/availability-shares`|規範帳戶簽名|
|準備投票|`POST /v1/nexus/private-settlements/phases/prepare-votes`|規範帳戶簽名|
|提交投票|`POST /v1/nexus/private-settlements/phases/commit-votes`|規範帳戶簽名|
|持續階段 QC |`POST /v1/nexus/private-settlements/phases/certificates`|規範帳戶簽名|
| 恢復階段 QCs | `GET /v1/nexus/private-settlements/legs/{payload_digest}/phase-certificates` | 公示贊助商 |
|結算段狀況|`GET /v1/nexus/private-settlements/legs/{payload_digest}/status`|規範帳戶簽名|
|委員會證明|`GET /v1/nexus/private-settlements/legs/{payload_digest}/committee-proof`|精確的清單驗證器|
|審計囊|`GET /v1/nexus/private-settlements/legs/{payload_digest}/audit-capsule`|管理審計師|
|審計員的批准|`POST /v1/nexus/private-settlements/legs/{payload_digest}/audit-approvals`|管理審計師|
|提交最終確定/中止|`POST /v1/nexus/private-settlements/bundles`|公示贊助商|
|捆綁狀態|`GET /v1/nexus/private-settlements/bundles/{bundle_id}`|公共|
|收到或取消|`GET /v1/nexus/private-settlements/bundles/{bundle_id}/receipt`|公共|

公共狀態與收據 APIs 只公開有檔案記載的公共欄位。尤其是，一般結算結算段狀態不會揭露核准數量或治理規定的稽核員門檻。受限讀取會刻意把資料缺失、未獲授權及保留期已過這三種情況歸入同一個「不可用」回應類別。 提交路由只接受一項由贊助者直接簽署的最終確定或中止指令。其 `202` 回應只包含捆綁 ID、觀測到的受理高度與承載交易雜湊；這並不表示排入佇列的中止指令已經成為最終結果。SDKs 要求兩個識別碼均為格式規範且校驗和有效的 Norito `Hash` JSON 字面值，且高度必須是精確的 64 位元無號整數；欄位若缺少、多餘、型別錯誤、格式不規範、校驗和無效、為負數、負零、小數或溢位，都會採安全關閉方式拒絕。請使用捆綁狀態或收據取得權威的最終狀態。狀態碼同樣有精確要求：此承載交易受理路由必須回傳 `202`，其他所有私人結算 V1 成功回應則必須回傳 `200`。使用者端會將其他成功的 `2xx` 狀態碼視為契約偏移並予以拒絕，且不會透過使用者端錯誤重現未預期的回應本文。只有當伺服器拒絕碼符合 `[A-Za-z0-9_.:-]{1,128}` 時才會公開該碼，並捨棄回應解析或驗證的原因，以免回應本文或攻擊者選定的 JSON 欄位名稱重新出現在包含原因鏈的日誌中。

## 失敗和恢復 {#failure-and-recovery}

在全球突變之前,缺失或過時的審計批准,不到三個驗證者投票,錯誤的根源或時代,重複廢除,替換的證明或囊,非規範的步驟順序,過期的捆綁和不匹配的退款條款都會失敗.提交證書永遠不會改變私人狀態.

驗證者在確認輔助記錄、暫存差異和階段憑證之前先將其 fsync。重新啟動時，驗證者從規範的持久記錄重建保留項，然後協調不可變的全域收據、中止標記或到期狀態。即使沒有要協調的終結候選項，受監督的協調器也會在同步觀測到的權威高度執行終結保留清理，並在清理出錯時採用失敗關閉策略。只有權威的全域終結記錄才能釋放暫存鎖。重放完全相同的已最終確定收據具有冪等性；衝突重放會確定性失敗。

預訂身份包括完整的路線.池頭使用 `(route, pool_id, epoch, root)`,取消器使用 `(route, pool_id, nullifier)`,輸出使用 `(route, pool_id, commitment)`.在另一條路線上相同的不透明值是獨立的;重啟過程中仍然鎖定了精確路線碰撞.

運營警報應僅使用不透明的捆綁,路線,階段,摘要,高度和理性類欄位.永遠不要將解密囊,帳戶或資產識別器,金額,備忘錄,檢視資料,證明見證者或解析器有效載荷放置在日誌,事件,計量標籤或追蹤範圍中.

## 在實際價值之前的資格 {#qualification-before-real-value}

為了檢視您打算部署的確切構建和配置,儲存包含:

- 抵制性證明,囊,政策,鑰匙轉換,退款和重播案件
- 2, 3, 4, 8 和 16 個資料空間的實際四個驗證器程序,包括驗證器和協調器重啟,認可 5%, 10% 和 20% 的訊息丟失,階段分割槽,恢復以及永續性邊界崩
- 在 Torii, P2P,區塊, Kura,快照,查詢,事件,日誌和遠端測量中進行 canary 和差分洩漏分析
- 每個實際網路參與者的數量至少有5次加熱和30次測量捆綁, p50,p95,p99,信任間隔,資源,流量,證明和回執大小以及透明的 AMX 作為控制.
- 嚴格的工作空間測試,和格式檢查,隨機種子,浸泡,可複製的構建, SBOMs,以及簽署的構件雜湊.
- 兩種正式層次:3/255結算段的計數對稱性檢查和準確的四個驗證器委員會索引 N=2驗證器重點加上全侷限錯誤,紙質主要 N=3 錯誤,N=4 清潔,N=3 過期/複製配置,每個委員會的錯誤預算獨立.
- 獨立審查證明關係,模擬插槽選擇器,資產和囊繫結,退款關係,加密技術和跨資料空間狀態機

將原始證據和清理後的證據、威脅模型、協議論證、限制、commit ID、硬體說明和稽核報告釋出到由 DOI 支援的不可變成品中。僅有儲存庫測試並不能使該功能成為達到生產要求的 CBDC 結算系統。

從最終乾淨的 Iroha 簽出中產生發行版來源清冊，並將其密封到該簽出目錄之外既有的套件根目錄中：

```sh
python3 scripts/private_settlement_source_evidence.py \
  --repository-root . \
  --bundle-root /absolute/path/to/release-bundle
```

產生工具遇到已暫存、未暫存、未追蹤或未合併的檔案，或擷取期間發生任何來源變更時，都會失敗。它會保留原始 commit 物件、規範的 Git 樹狀清冊、精確的二進位檔路徑清單、確定性的來源封印以及 `Cargo.lock`；請將其 JSON 結果中的每一項成品宣告納入最終發行版資訊清單。這不會免除最終 DOI 套件驗證器或任何外部發行閘門的要求。

來源封印可攜，且會採安全關閉方式處理錯誤：產生工具與最終驗證器會解析整個已封存的符號連結圖，因此，任何看似位於根目錄內但會經由另一個連結逸出、形成迴圈、穿越 `.git`，或指向 Windows 樣式目標的連結，都會在建立連結前遭到拒絕。結構化的來源與閘門報告只會從大小受限且穩定的檔案中解析；這些檔案的摘要與長度必須符合發行版資訊清單，而且每種來源承載資料都必須恰好出現一次。

每次原始故障執行和延遲樣本都必須繫結完整的發行版提交、一份結構化且固定的硬體說明的 SHA-256，以及其精確參與者數量設定的 SHA-256。請封存一份涵蓋 N=2,3,4,8,16 的規範設定資訊清單；每個專案都必須參照保留的設定位元組，並斷言每個資料空間恰有四個驗證器、採用 3-of-4 法定人數，且強制使用已簽署的 RS16 DA/RBC。發行版驗證器會拒絕由不同建置、硬體設定檔或網路設定所產生的摘要。每一筆訊息遺失、階段切斷和持久化崩潰記錄還必須指定全域不可重複使用的精確 JSONL 記錄參照；這些參照位於受 SHA-256 約束的已驗證控制器成品和原子性擷取成品中。發行版驗證器會解析這些摘要，並要求各列與執行識別碼、試驗索引和引數、控制器確認或復原結果、連續檢查次數，以及「部分可見性與可支用性觀測均為零」的結果一致。後續版本的 p95/p99 比較也會拒絕硬體、設定或測量要求與候選版本不同的已簽署基準。最終驗證器不會信任分離的基準摘要，而是從封存的原始樣本重新產生所有報告的百分位數、MADs 和確定性信賴區間。它也會重新載入 canary 資訊清單，並獨立重新掃描封存中的每個隱私介面，因此報告無法在重新繫結檔案摘要後掩蓋預先植入的秘密命中。每次僅含秘密資料的執行都必須保留僅擁有者可讀的未過濾回送 pcap、原始 tcpdump 標準錯誤輸出和零丟包統計、規範連線埠資訊清單、已封裝的受限來源封存，以及所有對等節點的原子性觀測。最終驗證器會直接根據這些封存位元組重新執行連線埠繫結的封包切分、來源投影和從基準到終態的原子性檢查，而不是信任已釋出的摘要。

封存還必須包含規範且成對的流量計數資訊清單與差異配對資訊清單，將每個必要隱私介面的精確左右檔案路徑、種類、位元組長度及 SHA-256 摘要繫結在一起。其宣告的根目錄必須只包含成對的封存清冊。對一般介面，驗證器要求完整檔案大小相等，且 JSON 公開形狀相同。含熵的原始 loopback 擷取檔與已封裝的受限來源封存是明確的大小例外；驗證器會改為比較封包鏈路型別、每個封包的長度、受限來源身分，以及固定形狀資料列的長度。每個 Torii 要求/回應、公開/受限 P2P 封包、區塊、查詢、事件、日誌及遙測的流量計數也必須相符。封包形狀變更、相同大小的結構性洩漏、虛假的來源宣告或未配對的檔案，都無法藉由改寫洩漏報告及其雜湊來隱藏。
