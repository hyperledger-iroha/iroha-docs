# 共識 {#consensus}

交易先進入佇列，隨後由 Sumeragi 將其納入區塊提案。驗證節點各自驗證並執行提案，而且只簽署自己能夠重現的狀態轉換。達到所需的驗證節點法定人數、各方對結果達成一致且相符的有效負載可用後，區塊才會提交。

所有 Iroha 3 網路都使用已簽署的 RS16 資料可用性清單和分塊，以及經認證的區塊本體復原機制。資料可用性是共識要求，並非選用的部署功能。

## Sumeragi {#sumeragi}

Sumeragi 是 Iroha 的拜占庭容錯共識引擎。它從佇列中取得交易，讓各驗證節點對同一個有序區塊達成一致，而且只在足夠多的驗證節點重現相同結果並簽署提交憑證後，才最終確認該區塊。

### 提案與提交路徑 {#proposal-and-commit-path}

Sumeragi 每次將帳本向前推進一個區塊高度。每個高度都有一名驗證者擔任目前視圖的提議者。提議者從佇列取出符合條件的交易，建立候選區塊，並向目前的驗證者集合公布提議。閒置的鏈不會產生空區塊。

許可制部署與提名權益證明（NPoS）部署使用同一條 Sumeragi 流水線：

1. 一個驗證節點根據佇列中的交易提出區塊。
2. 各驗證節點在相同的世界狀態上執行交易，以驗證該提案。
3. 各驗證節點交換目前高度與檢視的投票及法定人數憑證。
4. 達到提交法定人數後，各節點提交區塊並更新各自的世界狀態。

驗證節點只簽署能夠在本機重現的資料。投票前，驗證節點會檢查提案是否屬於預期的鏈、高度與檢視；交易簽章和限制是否有效；通道路由與執行器驗證是否具有確定性；以及執行有效負載是否產生預期的狀態轉換。如果本機結果不同，驗證節點會拒絕提案，而不會為其投票。

投票是體積很小的已簽署共識訊息，其中參照了提議區塊、高度、檢視和驗證節點身分。通過驗證的簽章組成 Prepare 與 Commit 法定人數憑證。提交憑證是持久證明，證明已有足夠多的驗證節點針對同一區塊觀察到相同結果。集合 A 的驗證節點通常會將 Prepare 與 Commit 投票傳送給本輪的代理尾端節點，由其彙總恰好所需數量的相同投票並廣播憑證。若憑證逾時仍未形成，集合 B 的驗證節點也會向代理尾端節點投票；作為最後手段，每個驗證節點都會廣播自己的投票，任何驗證節點都可以彙總該憑證。

### 法定人數與觀察節點 {#quorum-and-observers}

首版協定只允許人數恰為 `3f + 1` 的投票委員會，驗證者總數介於 4 到 31。因此，有效人數依序為 4、7、10，直到 31。當 `n = 3f + 1` 時，容許的拜占庭故障數為 `f`，提交法定人數為 `2f + 1`。創世資料產生及啟動驗證會拒絕其他委員會規模。每個 PrepareQC、CommitQC 和 TimeoutCert 都必須恰好包含 `q = n - f` 張等權重驗證者投票；多於此數的簽署者集合會遭到拒絕。

觀察節點可以同步已提交的區塊，但不會提出提案、投票，也不計入提交法定人數。當部署需要本機查詢容量、索引、監控或區域性區塊副本，但不希望增加投票驗證節點數量時，可使用觀察節點。

### 檢視變更與復原 {#view-changes-and-recovery}

檢視表示 Sumeragi 使用特定提議者和時序方案最終確認某一高度的一次嘗試。如果提案、有效負載、投票或提交進度停滯，節拍器可將該高度推進到後續檢視。檢視變更不會重寫已提交的區塊；它會改變驗證節點完成尚未提交高度的方式，並延續已知最高的法定人數證據或提交證據，防止各節點最終確認互相衝突的區塊。

有效負載復原與最終性決策互相獨立。節點可能在取得完整區塊有效負載前收到法定人數憑證或提交憑證。此時，該節點會請求已簽署的 RS16 有效負載分塊或經認證的區塊本體，對照已公布的雜湊驗證復原的位元組，然後才將區塊套用到世界狀態和 Kura。

### 共識模式 {#consensus-modes}

所選模式控制驗證者集合的組成與運作方式。此模式透過 [`consensus_mode`](/zh-hant/reference/genesis.md) 在簽署的創世資料中宣告，並固定於各高度的脈絡中。本機 `[sumeragi]` 設定選擇節點角色、簽署材料的保管方式、安全記錄路徑，以及文件允許的逾時與同步覆寫值。區塊與交易限制、共識模式和節奏則來自簽署的創世資料與已提交狀態。驗證者必須使用相同的簽署創世資料、拓撲、可信對等節點資料，以及生效的 Sumeragi 參數。

| 模式 | 最適用的情境 | 驗證節點集合 | 維運重點 |
| --- | --- | --- | --- |
| 許可制 | 私有網路、聯盟網路和由營運方管理的網路 | 驗證節點來自部署各方議定的可信對等節點拓撲 | 確保所有驗證節點使用相同的已簽署創世設定、可信對等節點、節點金鑰和 Sumeragi 參數 |
| NPoS | 驗證活動遵循提名與權益政策的公開網路，或面向 SORA Nexus 的網路 | 驗證者由 NPoS 設定檔選出，通常隨時期變更，並須具備 BLS 金鑰與持有證明 | 在整個網路中維持權益快照、簽署的時期與選舉輸入、驗證者 PoPs，以及不可變區塊節奏的一致性 |

::: tip 許可制模式

當驗證節點名單是一項明確的維運選擇時，請使用許可制模式。這通常是自行託管 Iroha 網路的起點，因為成員變更屬於有意進行的治理或管理員操作。重要的維運規則是，每個驗證節點都必須對創世設定、可信對等節點、BLS 持有證明和 Sumeragi 參數採用相同檢視。只要有一個節點採用不同的拓撲或已簽署創世設定，網路就可能無法提交區塊。

:::

::: tip NPoS 模式

當部署設定要求由提名與權益狀態決定驗證節點參與資格時，請使用 NPoS 模式。公開 SORA Nexus 部署使用 NPoS；其產生的設定包含啟動時所需的 BLS 驗證節點身分、持有證明、epoch 設定和 Sumeragi NPoS 參數。epoch 變更可以在指定高度替換目前的驗證節點集合，因此營運方既要監控共識健康狀況，也要監控決定下一份名單的權益或提名狀態。

:::

## 多通道共識 {#multilane-consensus}

資料空間為資料、權限、政策與應用程式定義環境，其通道則增加傳播與認證容量。兩類目錄彼此獨立：`nexus.dataspace_catalog` 定義資料空間，`nexus.lane_catalog` 定義通道，而每個通道都參照一個資料空間。多個通道可共用同一資料空間。

對於公共全域執行，通道 `0` 由全域 Sumeragi 實例排序。其他每個處於活動狀態的通道世代都以固定的委員會和共識參數執行同一 Sumeragi 核心的獨立實例。其認證的區塊包含按順序排列的交易批次，這些交易須依據已提交的全域錨點通過准入檢查。通道認證不會修改全域 State。

全域鏈合併各通道接續且連續的已認證區塊。執行合併後的全域區塊時，交易會依標準順序套用，全域 CommitQC 則使該次執行獲得最終性。因此，僅有通道憑證不足以聲稱交易已改變全域狀態。在復原與執行期間，仍會持續檢查通道身分、世代、錨點時效、來源保管，以及連續合併的進度邊界。

已提交的 `sumeragi_lane_policy` 管理固定通道、路由、委員會與自動擴縮。單靠設定目錄不會啟用共識通道。具體的資料空間目標必須解析到已准入且相符的通道；無法使用的私有路由會被拒絕，而不會改以通用工作執行。完整的控制平面批次經由通道 `0` 路由，讓目錄與啟用狀態轉換能夠繼續推進。

獨立簽署的資料空間根是獨立的執行邊界，擁有自己的狀態與本地最終性。登記資料空間目錄項目不會建立這個根。跨根原子性使用獨立的 AMX 協定。對這條路徑的貨幣功能與整體網路資格驗證，在固定版本的候選實作中仍未完成。

請參閱固定版本中的[通道實作](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/crates/iroha_core/src/sumeragi/lanes/mod.rs)、[通道規範](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/specs/sumeragi_lanes.md)、[獨立資料空間規範](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/specs/sumeragi.md)與[資格驗證狀態](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/specs/sumeragi_goals.md)。

## 資料可用性與有效負載復原 {#data-availability-and-payload-recovery}

Sumeragi V1 透過簽署的 RS16 `PayloadManifest` 與 `PayloadChunk` 訊息提供全域負載可用性。領導者將簽署的清單與每個簽署的資料列傳給其他所有委員會成員，以及下一屆委員會的新加入成員。驗證者必須重建標準主體、驗證清單與分片雜湊、持久儲存主體，並完成確定性驗證後，才能投出 Prepare 票。缺少資料列的對等節點會以 `PayloadRequest` 請求這些資料列。當對等節點在收到主體前就得知最終性時，已認證主體復原與區塊同步提供有界的復原路徑。

每個通道實例都有自己經過驗證的可用性與憑證脈絡。全域合併檢查會將其已認證批次與原始負載綁定到預期的世代及錨點。對等節點只有在本機具備相符的全域負載及有效 CommitQC 時，才會套用全域最終性。

請使用經過身分驗證的營運方介面，而不是個別的 RBC 端點：

- `iroha --operator-private-key-file <path> --output-format text ops sumeragi status` 報告權威的高度、檢視、階段、憑證和存活狀態。
- `iroha --operator-private-key-file <path> --output-format text ops sumeragi diagnostics` 回報不具權威性的交易佇列壓力、NPoS 選舉狀態，以及通道治理清單狀態。
- `sumeragi_fetch_requests_total`（`kind="body"` 表示缺失的區塊本體，`kind="sync"` 表示追趕同步）、`sumeragi_view_changes_total`、`sumeragi_round_stage` 和 `sumeragi_dropped_total` 等依實例區分的 Prometheus 序列帶有 `lane` 標籤，可區分區塊本體缺失復原、檢視變更與有界佇列丟棄；詳見[效能與指標](/zh-hant/guide/advanced/metrics.md)。

通道區塊儲存會保留合併與復原所需的已認證批次及來源記錄。其生命週期遵循已提交的通道世代；儲存目錄名稱不會授權建立新的通道或執行根。
