# 共識 {#consensus}

交易先進入佇列，隨後由 Sumeragi 將其納入區塊提案。驗證節點各自驗證並執行提案，而且只簽署自己能夠重現的狀態轉換。達到所需的驗證節點法定人數、各方對結果達成一致且相符的有效負載可用後，區塊才會提交。

所有 Iroha 3 網路都使用已簽署的 RS16 資料可用性清單和分塊，以及經認證的區塊本體復原機制。資料可用性是共識要求，並非選用的部署功能。

## Sumeragi {#sumeragi}

Sumeragi 是 Iroha 的拜占庭容錯共識引擎。它從佇列中取得交易，讓各驗證節點對同一個有序區塊達成一致，而且只在足夠多的驗證節點重現相同結果並簽署提交憑證後，才最終確認該區塊。

### 提案與提交路徑 {#proposal-and-commit-path}

Sumeragi 每次將帳本推進一個區塊高度。在每個高度，目前檢視由一個驗證節點擔任提議者。提議者從佇列中取出符合條件的交易、建構候選區塊，並向目前的驗證節點集合公布提案。

許可制部署與提名權益證明（NPoS）部署使用同一條 Sumeragi 流水線：

1. 一個驗證節點根據佇列中的交易提出區塊。
2. 各驗證節點在相同的世界狀態上執行交易，以驗證該提案。
3. 各驗證節點交換目前高度與檢視的投票及法定人數憑證。
4. 達到提交法定人數後，各節點提交區塊並更新各自的世界狀態。

驗證節點只簽署能夠在本機重現的資料。投票前，驗證節點會檢查提案是否屬於預期的鏈、高度與檢視；交易簽章和限制是否有效；通道路由與執行器驗證是否具有確定性；以及執行有效負載是否產生預期的狀態轉換。如果本機結果不同，驗證節點會拒絕提案，而不會為其投票。

投票是體積很小的已簽署共識訊息，其中參照了提議區塊、高度、檢視和驗證節點身分。通過驗證的簽章組成 Prepare 與 Commit 法定人數憑證。提交憑證是持久證明，證明已有足夠多的驗證節點針對同一區塊觀察到相同結果。每個驗證節點都會將 Prepare 與 Commit 投票傳送給整個委員會；任何驗證節點都可以彙總所需數量的相同投票，並廣播產生的憑證。

### 法定人數與觀察節點 {#quorum-and-observers}

首個版本的協定只接受嚴格為 `3f + 1` 的投票委員會，驗證節點數量為 4 至 31。因此，有效規模為 4、7、10，依此類推，最大為 31。對於 `n = 3f + 1`，拜占庭故障預算為 `f`，提交法定人數為 `2f + 1`。創世設定產生與啟動驗證會拒絕其他委員會規模。

觀察節點可以同步已提交的區塊，但不會提出提案、投票，也不計入提交法定人數。當部署需要本機查詢容量、索引、監控或區域性區塊副本，但不希望增加投票驗證節點數量時，可使用觀察節點。

### 檢視變更與復原 {#view-changes-and-recovery}

檢視表示 Sumeragi 使用特定提議者和時序方案最終確認某一高度的一次嘗試。如果提案、有效負載、投票或提交進度停滯，節拍器可將該高度推進到後續檢視。檢視變更不會重寫已提交的區塊；它會改變驗證節點完成尚未提交高度的方式，並延續已知最高的法定人數證據或提交證據，防止各節點最終確認互相衝突的區塊。

有效負載復原與最終性決策互相獨立。節點可能在取得完整區塊有效負載前收到法定人數憑證或提交憑證。此時，該節點會請求已簽署的 RS16 有效負載分塊或經認證的區塊本體，對照已公布的雜湊驗證復原的位元組，然後才將區塊套用到世界狀態和 Kura。

### 共識模式 {#consensus-modes}

所選模式決定驗證節點集合的組成與運作方式。模式透過已簽署創世設定中的 [`consensus_mode`](/zh-hant/reference/genesis.md) 宣告，並固定到每個高度的上下文中。本機 `[sumeragi]` 設定只能選擇節點角色，以及區塊、佇列、執行階段、儲存和金鑰原則的有限上限；它不能覆寫共識模式或出塊節奏。各驗證節點必須使用相同的已簽署創世設定、拓撲、可信對等節點資料和有效 Sumeragi 參數。

| 模式 | 最適用的情境 | 驗證節點集合 | 維運重點 |
| --- | --- | --- | --- |
| 許可制 | 私有網路、聯盟網路和由營運方管理的網路 | 驗證節點來自部署各方議定的可信對等節點拓撲 | 確保所有驗證節點使用相同的已簽署創世設定、可信對等節點、節點金鑰和 Sumeragi 參數 |
| NPoS | 驗證活動遵循提名和權益原則的公開網路或面向 Nexus 的網路 | 驗證節點由 NPoS 設定選出，通常按 epoch 變更，而且需要 BLS 金鑰和持有證明 | 在整個網路中保持權益快照、已簽署的 epoch 與選舉輸入、驗證節點 PoPs 和不可變出塊節奏一致 |

::: tip 許可制模式

當驗證節點名單是一項明確的維運選擇時，請使用許可制模式。這通常是自行託管 Iroha 網路的起點，因為成員變更屬於有意進行的治理或管理員操作。重要的維運規則是，每個驗證節點都必須對創世設定、可信對等節點、BLS 持有證明和 Sumeragi 參數採用相同檢視。只要有一個節點採用不同的拓撲或已簽署創世設定，網路就可能無法提交區塊。

:::

::: tip NPoS 模式

當部署設定要求由提名與權益狀態決定驗證節點參與資格時，請使用 NPoS 模式。公開 SORA Nexus 部署使用 NPoS；其產生的設定包含啟動時所需的 BLS 驗證節點身分、持有證明、epoch 設定和 Sumeragi NPoS 參數。epoch 變更可以在指定高度替換目前的驗證節點集合，因此營運方既要監控共識健康狀況，也要監控決定下一份名單的權益或提名狀態。

:::

## 多通道共識 {#multilane-consensus}

Iroha 透過 Nexus 通道和資料空間設定實作多通道共識路徑。它不會為每條通道啟動個別的共識執行個體。Sumeragi 仍然最終確認單一的有序區塊流；通道描述該區塊流內交易的路由、排程、計量和儲存方式。

軟體執行環境設定會建構三部分的執行通道狀態：

- `nexus.lane_catalog`：已設定的通道；每條通道都有數值 `LaneId`、別名、資料空間、可見性、儲存設定檔、證明方案和中繼資料。
- `nexus.dataspace_catalog`：已設定的資料空間；每個資料空間都有數值 `DataSpaceId`，以及用於決定中繼委員會規模的容錯值。
- `nexus.routing_policy`：預設通道/資料空間配對，以及可比對帳戶或指令路徑的有序路由規則。

交易進入佇列時，通道路由器會將其解析為 `RoutingDecision { lane_id, dataspace_id }`。在單通道模式下，結果始終是通道 `0` 和通用資料空間。在 Nexus 模式下，已設定的路由器依序套用資料空間範圍規則、結算路由、帳戶規則、明確路由規則，最後套用預設路由。解析出的通道與資料空間必須存在於各自目錄中，而且該通道必須繫結到解析出的資料空間；否則，交易會在進入佇列前遭到拒絕。

佇列將該路由決策與交易雜湊一併儲存，因此後續階段不必再次推斷。建構提案時會以兩種方式使用通道中繼資料：

- 按通道交錯編排交易，避免某條通道只因其交易較早進入佇列而占用整個區塊。
- 套用每條通道的交易執行單元（TEU）上限。會使通道超出設定容量的交易將延後並重新進入佇列；但可接納該通道的第一筆超重交易，以避免活鎖。

準備候選區塊時，Sumeragi 按通道與資料空間彙總提議的有效負載，並衍生通道本機的資料可用性識別碼。記錄的總計包括交易數、分塊數、有效負載位元組數和 TEU。提交後，這些總計會成為透過經身分驗證的 Sumeragi 診斷公開的通道與資料空間承諾快照。如果區塊包含通道結算收據，區塊處理還會建立通道結算承諾和中繼封裝，將區塊標頭、提交憑證、資料可用性承諾雜湊、結算證明和通道有效負載大小繫結在一起。

## 資料可用性與有效負載復原 {#data-availability-and-payload-recovery}

Sumeragi v2 透過已簽署的 RS16 `PayloadManifest` 與 `PayloadChunk` 訊息提供全域有效負載可用性。領導者將已簽署的清單傳送給整個委員會，並先將確定性分塊分發給集合 A。驗證節點只有在重建規範區塊本體、驗證清單與分塊雜湊、持久儲存區塊本體並完成確定性驗證後，才能投出 Prepare 票。如果快速路徑停滯，復原流程會將分塊交付擴展到集合 B。當節點在收到區塊本體前得知最終性時，經認證的區塊本體復原和區塊同步會提供有界的復原路徑。

多通道執行還會為每個通道主題衍生確定性的有效負載所有權雜湊和通道本機 RBC 執行個體雜湊。這些識別碼將通道提案與憑證繫結到全域承載交易；它們並不構成獨立的全域共識工作階段。只有當節點在本機擁有有效的提交憑證與相符的有效負載時，區塊才會最終確認。

請使用經過身分驗證的營運方介面，而不是個別的 RBC 端點：

- `iroha --operator-private-key-file <path> --output-format text ops sumeragi status` 報告權威的高度、檢視、階段、憑證和存活狀態。
- `iroha --operator-private-key-file <path> --output-format text ops sumeragi diagnostics` 報告非權威的佇列、流水線、NPoS、通道與資料空間診斷資訊，包括通道有效負載所有權。
- `sumeragi_missing_block_requests`、`sumeragi_missing_block_oldest_ms`、`sumeragi_missing_block_fetch_total`、`sumeragi_da_gate_block_total` 和 `sumeragi_da_gate_satisfied_total` 等 Prometheus 訊號可區分區塊本體缺失復原、資料可用性閘門和訊息處理；詳見[效能與指標](/zh-hant/guide/advanced/metrics.md)。

Kura 使用衍生的通道設定安排儲存配置。每條通道都會取得 `blocks/lane_000_core` 和 `merge_ledger/lane_000_core_merge.log` 等確定性儲存名稱；通道生命週期變更可以佈建、停用或重新標記這些區段，而不會改變全域區塊順序。
