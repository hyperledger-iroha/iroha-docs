# I105 အကောင့်လိပ်စာပုံစံ {#i105-account-address-format}

I105 တစ်ခုတည်းသော ပရိုတိုကုတ်စံညွှန်း ပြင်ပစာသားပုံစံကို Iroha 3 `AccountId`.

၎င်းရဲ့ အသုံးဝင် ကုန်ကြမ်းက အကောင့်ထိန်းချုပ်သူကို ကိုယ်စားပြုပါတယ်။

၎င်းရဲ့ sentinel ကတော့ ရည်ရွယ်ထားတဲ့ ကွန်ရက်ကို Chain Discriminant နဲ့ သတ်မှတ်ပေးတယ်။

API, ငွေလွှဲပြောင်းမှု, ခွင့်ပြုချက် (သို့) မေးမြန်းချက်တစ်ခုအတွက် တစ်နည်းတည်းသော ပရိုတိုကောစံညွှန်းစာရင်း ID ကိုတောင်းဆိုသည့် နေရာတိုင်းတွင်အသုံးပြုပါ။

I105 အကောင့် ID က Domainless ပါ။

`treasury@payments.universal` ကဲ့သို့သောတန်ဖိုးသည်စာရင်းအမည်မဟုတ်ဘဲ I105 ID ၏ အခြားအက္ခရာမဖြစ်ပါ။

I105 ID ကို ရယူခြင်းသည် စာရင်းကို မှတ်ပုံတင်ခြင်း သို့မဟုတ် ငွေကြေးထောက်ပံ့ခြင်းမရှိပါ။

::: warning ပေါင်းစည်းမှု ကျရှုံးမှု အများစုကို တားဆီးတဲ့ စည်းမျဉ်းများ

- လိပ်စာကို ကုဒ်သွင်းခြင်း သို့မဟုတ် အတည်ပြုခြင်း မပြုမီ ကွန်ရက်ပရိုဖိုင်ကို ရွေးပါ။
- Single protocol-standard UTF-8 string ကို တိကျစွာ သိုလှောင်ပြီး နှိုင်းယှဉ်ပါ။
- စာလုံးအကြီးအသေးကို မပြောင်းဘဲ ထိန်းသိမ်းပြီး `Unicode` normalization ကို မပြုလုပ်ပါနှင့်။
- I105 ID တွင် `@domain` သို့မဟုတ် `@domain.dataspace` နောက်ဆက် မပါရပါ။
- Iroha (သို့) SDK သို့မဟုတ် `iroha tools address` ကို အသုံးပြုပါ။
- regular expression သည် I105 validator မဟုတ်ပါ။

:::

## စာလုံးအရ ခန္ဓာဗေဒ {#literal-anatomy}

I105 စာလုံးမှာ နီးစပ်ရာ အစိတ်အပိုင်း သုံးခုရှိပြီး ခွဲခြမ်းမှုမရှိပါဘူး။

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

| အပိုင်း | ရည်ရွယ်ချက် | checksum လွှမ်းခြုံမှု |
| ---------------- | ------------------------------------------------------------------ | ----------------- |
| ကွန်ရက် sentinel | စာသားကို `u16` chain discriminant တစ်ခုနှင့် ချိတ်ဆက်ပေးသည် | checksum မလွှမ်းခြုံ |
| payload | canonical account-controller bytes များ၏ `base-105` encoding | checksum လွှမ်းခြုံ |
| checksum | I105 alphabet ဖြင့် ဖော်ပြသော `Bech32m` ပုံစံ `5-bit` တန်ဖိုး ခြောက်ခု | N/A |

payload နှင့် checksum တို့က account controller ကို သတ်မှတ်ပေးသည်။

Sentinel က ကွန်ရက် အခြေအနေကို ရွေးချယ်တယ်။

တူညီသော controller ၏ payload နှင့် checksum သည် Taira နှင့် Minamoto နှစ်ခုလုံးတွင် တူညီသော်လည်း ကွန်ရက်တစ်ခုစီတွင် ရှေ့ဆုံး sentinel မတူညီပါ။

decoder သည် မျှော်မှန်းထားသော discriminant ကို မဖြစ်မနေ စစ်ဆေးရမည်။

စစ်ဆေးမှုဂဏန်းက Sentinel အစားထိုးမှုကို ရှာမတွေ့နိုင်ပါ။

### ကွန်ရက်စောင့်တပ်များ {#network-sentinels}

|ကွန်ရက် (သို့) အခြေအနေ|ကွင်းဆက်ခွဲခြားမှု |Hex |Single protocol-standard sentinel ကို|
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
|Taira အများပြည်သူ စစ်ဆေးရေးကွန်ရက် |                            `369` |`0x0171` |`test` |
|Minamoto ပြည်သူ့ကွန်ရက် |                            `753` |`0x02f1` |`sora` |
|ဖွံ့ဖြိုးရေး အခြေအနေ |                              `0` |`0x0000` |`dev` |
|အခြား `u16` တန်ဖိုးများ |`0`, `369` နှင့် `753` မှလွဲ၍ အားလုံး။|        — |`n` + အနိမ့်ဆုံး ဆယ်ဂဏန်း၊ ဥပမာ `n42` |

အမည်ပေးထားတဲ့ တန်ဖိုးတွေဟာ အမြဲတမ်း သူတို့အမည်ပေးထားတဲ့ စောင့်ကြည့်ရေးကို သုံးတယ်။

`n00042`, `n369`, `n753` နှင့် `n0` ကဲ့သို့သော ပုံစံများသည် တစ်မူထူးသော ပရိုတိုကောစံညွှန်းမဟုတ်ပါ။

Transaction Chain ID နဲ့ I105 Chain Discriminant တို့ဟာ သီးခြားတန်ဖိုးတွေပါ။

endpoint သို့မဟုတ် chain ID ကို ရွေးခြင်းက address profile ကို အလိုအလျောက် ရွေးပေးခြင်းမဟုတ်ပါ။

## စည်းမျဉ်းစည်းကမ်းချက် တစ်ခုတည်းသော သော့ဥပမာ {#normative-single-key-example}

အောက်ပါ အသုံးဝင်ဝန်ဆောင်မှုနှင့် Minamoto ပုံစံသည် SDK ကန့်သတ်ချက် လိုက်နာမှု ကိရိယာမှ လာသည်။

Taira ပုံစံသည် တူညီသော payload ပေါ်တွင် Taira sentinel ကို အသုံးပြုသည်:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

တစ်ခုတည်းသော ပရိုတိုကုတ်စံညွှန်း အသုံးဝင်ဝန်ဆောင်မှုသည် `02 00 01 20`: ခေါင်းစဉ် `0x02`, Compact single-key tag `0x00`, `Ed25519` ခေါက်ဆွဲ ID `0x01`, 32 ဘိုက်သော့အလျား `0x20`.

`multihash` ကြိုတင်ကိန်းက input metadata ဖြစ်ပြီး controller payload ထဲမှာ ကူးယူမထားပါ။

## CLI ဖြင့် ID များကို ဖန်တီးပြီး စစ်ဆေးပါ။ {#create-and-inspect-ids-with-the-cli}

အများသုံးကွန်ရက်တစ်ခုအတွက် နာမည်တပ်ထားတဲ့ ပရိုဖိုင်ကို ကြိုက်တယ်။

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

I105 input ကို Address Codec အပြုအမူကို ရှာဖွေနေစဉ် ပုံမှန်လုပ်ပြီး နှိုင်းယှဉ်ကြည့်ပါ။

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

JSON အဖြစ်တွေ့ရှိထားသောပုံစံ၊ Single Protocol Standard Hex နှင့် ရွေးချယ်ထားသည့် ကွန်ရက် အခြေအနေကို စစ်ဆေးပါ။

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

Newline-separated file တစ်ခုရဲ့ address-codec တည်ဆောက်မှုကို ဆိတ်ငြိမ်စွာ analyze failure တွေကို လက်မခံဘဲ စစ်ဆေးပါ။

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution CLI အတည်ပြုနယ်နိမိတ်

`convert`၊ `normalize` နှင့် `audit` command များသည် low-level `AccountAddress` codec ပေါ်တွင် လုပ်ဆောင်သည်။

သူတို့ဟာ sentinel, အက္ခရာ၊ checksum, byte lengths, `CurveId`/key shape နဲ့ exact address layer re-encoding တွေကို စစ်ဆေးတယ်။

၎င်းတို့သည် `AccountId` ကို မဖြစ်ပေါ်စေပါ။

၎င်းတို့တစ်ခုတည်းဖြင့် multisig policy semantics အားလုံးကို အတည်မပြုနိုင်ပါ။

ခေါင်းစဉ်တန်းအစားဟာ ထိန်းချုပ်ရေးကိရိယာနဲ့ ကိုက်ညီတယ်ဆိုတာ သက်သေမပြဘူး။

authorization သို့မဟုတ် persistent storage မပြုမီ တင်းကျပ်သော `AccountId` validation ကို အသုံးပြုပါ။

:::

ပုဂ္ဂလိကွန်ရက်အတွက် `--network-prefix` နဲ့ ရှင်းလင်းစွာ သတ်မှတ်ထားသော ခွဲခြားကိန်းကို အသုံးပြုပါ။

ရှိနေတဲ့လိပ်စာကို ရှင်းလင်းတဲ့ အခြေအနေတွေကြား ပြောင်းတဲ့အခါ အရင်းအမြစ်မှာ `--expect-prefix` ကိုလည်း ထည့်သွင်းပါ။

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

Re-encoding ဟာ ကွန်ရက် အခြေအနေကိုသာ ပြောင်းလဲပေးတယ်။

၎င်းသည် target network ပေါ်တွင် account ကို register မလုပ်သလို တူညီသော controller ကို ထိုနေရာတွင် ပြန်သုံးသင့်ကြောင်းလည်း သက်သေမပြပါ။

## ကုဒ်သွင်းခြင်း အယ်လ်ဂိုရစ်သမ် {#encoding-algorithm}

Single protocol-standard encoders တွေက အောက်ပါ လုပ်ဆောင်ချက်တွေကို လုပ်ပေးပါတယ်။

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

ရှေ့တန်း သုည byte တွေကို သုညတန်ဖိုးရှိတဲ့ `base-105` ဂဏန်းတွေအဖြစ် ထိန်းသိမ်းထားတယ်။

စစ်ဆေးမှုအရေအတွက်မှာ `Bech32` `polymod` ထုတ်ကုန်များနှင့် အမြဲတမ်း `0x2bc830a3` ကို အသုံးပြုပါတယ်။

စစ်ဆေးမှုအရေအတွက်သာ HRP ဆိုသည်မှာ ASCII string `snx` ဖြစ်သည်။

စစ်ဆေးမှုအရေအတွက်သာ HRP ကိုလိပ်စာတွင် ပုံနှိပ်ခြင်းမရှိပါ။

စစ်ဆေးမှုအရေအတွက် ၆ တန်ဖိုးသည် `0..31` ကြားမှာရှိပြီး အသုံးဝင်ဝန်ပိုးနှင့်အတူတူသော I105 အက္ခရာဖြင့် ပြန်ညွှန်းထားသည်။

### I105 အက္ခရာ {#i105-alphabet}

သင်္ကေတ ၁၀၅ ခုကို ဒီတိကျတဲ့ အစဉ်အတိုင်း ညွှန်ပြထားပါတယ်။

ပထမတန်းမှာ `Bitcoin Base58` အက္ခရာဖြစ်ပြီး `0..57` ဂဏန်းတွေပါပါတယ်။

ဒုတိယအတန်းမှာ `58..104` ဂဏန်းတွေရှိပါတယ်။

Codec ကို အကောင်အထည်ဖော်တဲ့အခါ အတန်းတွေကို Concatenate လုပ်ပါ။

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

အက္ခရာက `Unicode` - ထိခိုက်လွယ်ပါတယ်။

တိကျတဲ့ အစဉ်မှာ `compatibility-width` ဂျပန် `kana` သင်္ကေတတွေနဲ့ `ヰ` နဲ့ `ヱ` အတွက် ပြထားတဲ့ ကုဒ်မှတ်တွေ ပါဝင်ပါတယ်။

NFC၊ NFKC၊ width conversion၊ case folding သို့မဟုတ် ရုပ်ဆင်တူသင်္ကေတဖြင့် အစားထိုးခြင်းကို မပြုလုပ်ပါနှင့်။

ASCII `0`, `O`, `I` နှင့် `l` တို့သည် အက္ခရာ သင်္ကေတမဟုတ်ပါ။

## တစ်ခုတည်းသော ပရိုတိုကုတ်စံညွှန်းစာရင်းသုံးစွဲမှု {#canonical-account-payload}

`base-105` ကိုယ်ခန္ဓာသည် ဘိုင်နရီအကောင့် အသုံးဝင်ဝန်ဆောင်မှုကို ကုဒ်သွင်းသည်၊ အများသုံးသော့ကြိုးမဟုတ်၊ Norito JSON အရာဝတ္ထုမဟုတ်ပါ။

```text
header:u8 || controller:variable
```

အောက်ပါ multi-byte integer အားလုံးသည် unsigned ဖြစ်ပြီး `big-endian` ဖြစ်သည်။

Domain, data space, alias, UAID နဲ့ account metadata bytes တွေတော့ မရှိပါဘူး။

### ခေါင်းစဉ် byte {#header-byte}

|အနည်းငယ် |အလျား|လက်ရှိ encoder output ကို |အဓိပ္ပါယ်|
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |Address Format Version ကွင်းများ |
| `4..3` |     2 |`0` key တစ်ခုတည်း၊ `1` multisig |လိပ်စာတန်း |
| `2..1` |     2 |                          `1` |Normalization version ကွင်း |
| `0`    |     1 |                          `0` |ကန့်သတ်ထားသော `extension flag` |

လက်ရှိ V1 encoders များသည် single-key controller အတွက် header `0x02` နှင့် multisig controller အတွက် `0x0a` ကို ထုတ်လွှတ်ပေးသည်။

Address classes `2` နဲ့ `3` တို့ကို မသတ်မှတ်ထားပါ။

`extension flag` ၏ `1` ကို ပယ်ချသည်။

Low-level decoder က အခြား version နဲ့ normalization bit values တွေကို ထိန်းသိမ်းနိုင်ပြီး controller tag နဲ့ class ကို သီးခြား crosscheck မလုပ်ပါဘူး။

`AccountId` ကိုပြောင်းပြီး ၎င်းရဲ့ Single Protocol Standard rendering ကို နှိုင်းယှဉ်လိုက်ရင် Single Protocol Standard Form ကို လက်ရှိ V1 လိုက်နာမှု သက်သေပြပါတယ်။

### Single key controller {#single-key-controller}

raw public-key payload သည် 255 ဘိုက်အထိသာ ရှိပါက compact form ကို အသုံးပြုပါ:

|ကွင်း |အလျား|တန်ဖိုး (သို့) အဓိပ္ပါယ်|
| ------------ | --------------: | ------------------------ |
|`tag` |1 byte |`0x00` |
|`curve` |1 byte |`CurveId` မှတ်ပုံတင်တန်ဖိုး |
|`key_len` |1 byte |Raw key အလျား|
| `public_key` | `key_len` ဘိုက် | raw public-key payload |

255 ဘိုက်ထက်ရှည်သော key များသည် extended form ကို အသုံးပြုသည်:

|ကွင်း |အလျား|တန်ဖိုး (သို့) အဓိပ္ပါယ်|
| ------------ | --------------: | ---------------------------- |
|`tag` |1 byte |`0x02` |
|`curve` |1 byte |`CurveId` မှတ်ပုံတင်တန်ဖိုး |
|`key_len` |2 bytes |ရိုးရိုး key length `big-endian` |
|`public_key` |`key_len` ဘိုက်များ |ရိုးရိုး အများသုံး သော့သုံး ဝန်ဆောင်မှု|

compact form နှင့် ကိုက်ညီသော key အတွက် extended encoding သည် canonical မဟုတ်ပါ။

### Multisig Controller {#multisig-controller}

|ကွင်း |အလျား|တန်ဖိုး (သို့) အဓိပ္ပါယ်|
| ---------------- | -------: | ------------------------------ |
|`tag` |1 byte |`0x01` |
|`policy_version` |1 byte |လက်ရှိတန်ဖိုး `1` |
| `threshold` | 2 ဘိုက် | လိုအပ်သော approval weight စုစုပေါင်း |
|`member_count` |2 bytes |အောက်ပါ အဖွဲ့ဝင်များအရေအတွက် |
|`members` |အပြောင်းအလဲ |အကြိမ်ကြိမ်ဝင်မှတ်တမ်းများ |

အဖွဲ့ဝင်မှတ်တမ်းတိုင်းမှာ:

|ကွင်း |အလျား|အဓိပ္ပါယ်|
| ------------ | --------------: | ------------------------ |
|`curve` |1 byte |`CurveId` မှတ်ပုံတင်တန်ဖိုး |
|`weight` |2 bytes |အဖွဲ့ဝင် ခွင့်ပြုချက် အလေးချိန်|
|`key_len` |2 bytes |Raw key အလျား|
| `public_key` | `key_len` ဘိုက် | raw public-key payload |

မှန်ကန်သော policy တစ်ခုတွင် အနည်းဆုံး member တစ်ဦး၊ သုညထက်ကြီးသော weight များ၊ duplicate public key မရှိခြင်းနှင့် `1` မှ member weight စုစုပေါင်းအထိရှိသည့် threshold တစ်ခု ပါရမည်။

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

Canonical construction သည် member များကို signing algorithm ၏ stable name၊ zero separator byte၊ ထို့နောက် raw public-key bytes အလိုက် စီစဉ်သည်။

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

I105 စာလုံးမှာ fixed character length မရှိပါဘူး။ အကြောင်းက multisig နဲ့ post-quantum controller တွေက ကြီးမားနိုင်လို့ပါ။

Key payload ကလည်း ကြေညာထားတဲ့ `CurveId` က ရွေးချယ်တဲ့ အယ်လ်ဂိုရစ်သမ်အတွက် ဗျူဟာအရ valid ဖြစ်ရပါမယ်။

## AccountId ကို တင်းကျပ်စွာ အတည်ပြုပြီး Single Protocol Standard Form ကို လိုက်နာခြင်း {#strict-accountid-validation-and-canonicality}

SDK ကို ကြိုတင်မျှော်မှန်းထားသော ကွင်းဆက်ခွဲခြားမှုပစ္စည်းဖြင့် သတ်မှတ်ပြီးနောက် `AccountId` သို့ ဆန်းစစ်ပြီး ပြန်လည်ထုတ်ပြန်သည့် တစ်ခုတည်းသော ပရိုတိုကုတ်စံညွှန်း rendering နှင့် trimed input ကို နှိုင်းယှဉ်ပါ။

ဒီနှိုင်းယှဉ်မှုဟာ `AccountId` ကို တည်ဆောက်နေစဉ်မှာ parser က decodable controller ပစ္စည်းကို ပုံမှန်ဖြစ်အောင် လုပ်နိုင်လို့ပါ။

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

မယုံကြည်ရသော string တစ်ခုအတွက် စံနှုန်းနှင့်ကိုက်ညီသော application သည် အောက်ပါတို့ကို လုပ်ဆောင်သင့်သည်:

1. တန်ဖိုးအပြည့်၏ အစနှင့်အဆုံးရှိ ခွင့်ပြုထားသော transport whitespace ကိုသာ trim လုပ်ပါ။
2. Sentinel ကိုဖတ်ပြီး မျှော်မှန်းထားတဲ့ ကွင်းဆက်ခွဲခြားမှုကို တောင်းဆိုပါ။
3. ကျန်နေတဲ့ `Unicode` သင်္ကေတတိုင်းကို ၁၀၅ သင်္ကေတစ်ရဲ့ အက္ခရာအတိအကျကနေ မြေပုံပါ။
4. checksum digit ခြောက်လုံးကို ခွဲထုတ်ပါ။
5. အသုံးဝင်တဲ့ ဝန်ဆောင်မှု ကိန်းဂဏန်းတွေကို Single Protocol Standard byte အဖြစ် ပြန်ပြောင်းပါ။
6. အဲဒီ တစ်ခုတည်းသော ပရိုတိုကုတ်စံညွှန်း ဘိုက်များအတွက် စစ်ဆေးမှုအရေအတွက်ကို စစ်ဆေးပါ။
7. header နှင့် controller ကို parse လုပ်ပြီး အောက်ပါတို့ကို လိုအပ်ပါသည်:
   - တိကျတဲ့ ကွင်းအလျားများ
   - အထောက်အပံ့ပေးထားသော `CurveId`
   - သက်ဝင်သော အများသုံး သော့
   - နောက်ဆက်တွဲ bytes မရှိပါ။
   - မှန်ကန်သော multisig မူဝါဒကို အသုံးပြုပါက
8. `AccountId` ကို တည်ဆောက်ပါ။
9. မျှော်မှန်းထားသော discriminant အတွက် `AccountId` ကို canonical ပုံစံဖြင့် render လုပ်ပါ။
10. trimmed input နှင့် `byte-for-byte` တူညီမှုကို လိုအပ်သည်။

အက်ပ်ရဲ့ ရှင်းလင်းတဲ့ နောက်ဆုံး အဆင့် `render-and-compare` ကတော့ အနည်းဆုံး ကိန်းဂဏန်း စောင့်ကြည့်ရေးကိရိယာတွေ၊ တစ်ခုတည်းသော ပရိုတိုကုတ်စံညွှန်းမဟုတ်တဲ့ ထိန်းချုပ်ရေးကိရိယာတွေရဲ့ စီစဉ်ချက်တွေ၊ ပြန်လည်စီစဉ်ထားတဲ့ မူဝါဒဆိုင်ရာ ပစ္စည်းတွေနဲ့ ကုဒ်တွေကို ဖယ်ရှားပေမဲ့ ကုဒ်ပေးသူရဲ့ လက်ရှိ V1 ထုတ်ပြန်မှု မဟုတ်တဲ့ အခြားအက္ခရာတွေကို ပယ်ချတယ်။

အောင်မြင်တဲ့ checksum (သို့) low-level `AccountAddress` parse ဟာ ဒီစစ်ဆေးမှုကို အစားထိုးလို့မရဘူး။

တင်းကျပ်သော account-ID field တွင် ဤတန်ဖိုးများကို လက်မခံပါနှင့်:

- `alice@wonderland.universal` ကဲ့သို့သော စာရင်းအမည်
- အဆုံးတွင် `@domain` suffix ထည့်ထားသော I105 literal
- အများသုံးသော့ `multihash` အတိုင်း `ed0120...`
- `0x02000120...` ကဲ့သို့သော single protocol-standard payload hex များ
- မှားယွင်းသော ကွင်းဆက်ခွဲခြားမှုအတွက်လိပ်စာ
- စာလုံးအကြီးအသေး၊ character width၊ `kana`၊ payload သို့မဟုတ် checksum ပြောင်းလဲထားသော string

Application boundary မှာ aliases တွေကို ဖြေရှင်းပြီး ခွင့်ပြုချက်၊ လက်မှတ်ထိုးမှု၊ ခွင့်ပြုချက်တွေ နဲ့ စစ်ဆေးရေး မှတ်တမ်းတွေ အတွက် ပြန်ပို့ထားတဲ့ Single Protocol-Standard I105 ID ကို သိမ်းထားပါ။

### Common stable error code များ {#common-stable-error-codes}

|ကုဒ်|အဓိပ္ပါယ်|
| -------------------------------- | ------------------------------------------------------------------- |
|`ERR_UNEXPECTED_NETWORK_PREFIX` |decoded discriminant ကတော့ လိုအပ်တဲ့ network ကို မက်ညီဘူး။ |
|`ERR_CHECKSUM_MISMATCH` |ခြောက်လုံးရဲ့ စစ်ဆေးမှုအရေအတွက် သင်္ကေတတွေဟာ အသုံးဝင်တဲ့ ဝန်ဆောင်မှုကို မက်ညီပါဘူး။|
|`ERR_INVALID_I105_CHAR` |သင်္ကေတတစ်ခုဟာ အက္ခရာအတိအကျရဲ့ ပြင်ပမှာ ရှိတယ်။|
|`ERR_MISSING_I105_SENTINEL` |တစ်ခုတည်းသော ပရိုတိုကုတ်စံညွှန်းနာမည် သို့မဟုတ် ကိန်းဂဏန်း စောင့်ကြည့်ရေးတပ်ကို မတွေ့ရှိခဲ့ပါ။|
|`ERR_I105_TOO_SHORT` |ကိုယ်ခန္ဓာထဲမှာ အသုံးဝင်တဲ့ ဝန်ဆောင်မှုနဲ့ စစ်ဆေးမှု ပမာဏ နှစ်ခုစလုံး မပါနိုင်ဘူး။|
|`ERR_INVALID_LENGTH` |Controller ကွင်းကို ဖြတ်တောက်ထားတယ် (သို့) Single Protocol-standard length form ကိုသုံးတယ်|
|`ERR_UNKNOWN_CURVE` |ထိန်းချုပ်သူက တာဝန်မအပ်တဲ့ (သို့) မရနိုင်တဲ့ `CurveId` ကို ကြေညာပါတယ်။|
| `ERR_INVALID_PUBLIC_KEY` | key သည် ၎င်း၏ `CurveId` ရွေးထားသော algorithm အတွက် မမှန်ကန်ပါ |
|`ERR_UNSUPPORTED_ADDRESS_FORMAT` |input ဟာ လက်ခံထားတဲ့ Single Protocol Standard I105 form မဟုတ်ဘူး။ |

## API၊ သိုလှောင်ခြင်းနှင့် ပြသခြင်းဆိုင်ရာ စည်းမျဉ်းများ {#api-storage-and-display-rules}

- တိကျသော I105 UTF-8 string ကို JSON account field များတွင် ပို့ပါ။
- account ID အပြည့်ကို URL path segment ထဲ မထည့်မီ `Percent-encode` လုပ်ပါ။
- I105 ID အစား account alias ကို မည်သည့်အခါမျှ မသုံးပါနှင့်။
- Codec ကပြန်လာတဲ့ Single Protocol Standard string ကို `byte-preserving` comparison semantics နဲ့ store လုပ်ပါ။
- စာလုံးအကြီးအသေးနှင့် character width ကို ထိန်းသိမ်းသော collation ကို အသုံးပြုပါ။
- Chain discriminant (သို့) နာမည်တပ်ထားတဲ့ network profile ကို Export Account Data နဲ့ Backup တွေနဲ့အတူ သိမ်းထားပါ။
- လိပ်စာကို ၎င်း၏ network context နှင့်သာ ပြန်လည်အသုံးပြုပါ။
- လိပ်စာအပြည့်အစုံကို ပြသပြီး copy action ကို ပေးပါ။
- `kana` စာလုံးတိုင်းကို တိကျစွာ ထိန်းထားပါ။
- အပြည့်အစုံသော လိပ်စာကို အသေးစား display တစ်ခုက အလယ်ကို ဖြတ်တောက်တဲ့အခါမှာ ရယူနိုင်ပါ။
- သိုလှောင်ထားတဲ့ Single Protocol Standard ID ကို alias တစ်ခုကနေ ပြန်တည်ဆောက်တာအစား သုံးပါ။

`AccountId` ပြသခြင်းနှင့် JSON တစ်ခုတည်းသော ပရိုတိုကောလံကို အသုံးပြုပါ။ I105.

အောက်ခြေအဆင့် `AccountAddress` display/JSON ကိုယ်စားပြုချက်သည် အတွင်းပိုင်းနှင့် debugging အခြေအနေများအတွက် single protocol-standard hex ကို အသုံးပြုသည်။

ပြင်ပ account ID လိုအပ်ပါက explicit `AccountAddress` I105 encoder ကို ခေါ်သုံးပါ။

Account creation နှင့် alias resolution workflows များအတွက် [အကောင့်များနှင့် အမည်မဖော်လိုသူများ](/my/cookbook/accounts-and-aliases.md) ကို ဆက်သုံးပါ။

စာရင်း အချက်အလက် ပုံစံအတွက် [အကောင့်များ](/my/blockchain/accounts.md) ကို ကြည့်ပါ။
