# Data Space များအကြား အက်တမ်သဘောရှိသော သီးသန့် ငွေစာရင်းရှင်းလင်းမှု လုပ်ဆောင်ခြင်း {#run-atomic-private-cross-dataspace-settlement}

`AtomicPrivateSettlementV1` သည် SORA Nexus ၏ data space 2 ခုမှ 255 ခုအထိ တစ်ခုစီရှိ လျှို့ဝှက်ငွေစာရင်းရှင်းလင်းမှု အပိုင်းတစ်ခုကို ညှိနှိုင်းပြီး အပိုင်းအားလုံးကို ကမ္ဘာလုံးဆိုင်ရာ အခြေအနေ transaction တစ်ခုတည်းတွင် အပြီးသတ်သည်။ ငြင်းပယ်ခံရ၊ သက်တမ်းကုန် သို့မဟုတ် ဖျက်သိမ်းထားသော အစုသည် မည်သည့်အပိုင်းကိုမျှ အသုံးမချပါ။ ပွင့်လင်းမြင်သာသော Native AMX DvP/PvP သည် သီးခြား protocol လမ်းကြောင်းအဖြစ် ဆက်ရှိသည်။

::: warning လွတ်မြောက်မှုအခြေအနေ
ဤလုပ်ဆောင်ချက်သည် အုပ်ချုပ်မှုဖြင့် ထိန်းချုပ်ထားပြီး မူလအတိုင်း ပိတ်ထားသည်။ Production အသုံးပြုရန် အရည်အချင်းပြည့်မီကြောင်း မသတ်မှတ်ရသေးပါ။ ထိုထုတ်ဝေမှုအတိအကျအတွက် ထုတ်ပြန်ထားသော လုပ်ဆောင်နိုင်မှု၊ ကိုယ်ရေးလုံခြုံမှု၊ ချို့ယွင်းမှု၊ စွမ်းဆောင်ရည်၊ တူညီစွာ ပြန်တည်ဆောက်နိုင်မှု၊ လွတ်လပ်သော စာဝှက်ပညာ ပြန်လည်သုံးသပ်မှုနှင့် artifact ထုတ်ဝေမှုဆိုင်ရာ သတ်မှတ်စစ်ဆေးချက်အားလုံး မအောင်မြင်မချင်း တကယ့် CBDC တန်ဖိုးအတွက် မဖွင့်ပါနှင့်။
:::

## ဒီပရိုတိုကောက ဘာကို ဖုံးကွယ်ထားလဲ။ {#what-the-protocol-hides}

ဘဏ္ဍာရေးလွှဲပြောင်းမှု အစိတ်အပိုင်းတစ်ခုစီမှာ တည်ငြိမ်သော နှစ်ဝင်၊ သုံးထွက် Private-note သက်သေကို အသုံးပြုသည်။ ကော်မတီအတည်ပြုသူများက သက်သေခံချက်နှင့် ပွင့်လင်းမြင်သာမှုမရှိတဲ့ အခြေအနေ ကူးပြောင်းမှုကို စစ်ဆေးကြသည်။ ၎င်းတို့ဟာ ရှင်းလင်းသော စာသားပါတီများ၊ အရင်းအမြစ်များ၊ ငွေကြေးပမာဏများ၊ မှတ်စုများ သို့မဟုတ် စီးပွားရေး ရလဒ်များကို မရရှိပါ။ ခွင့်ပြုထားတဲ့ ဒေသတွင်း စာရင်းစစ်သူက ပိတ်ထားတဲ့ စာရင်းစစ်ဆေးမှုပုဒ်မကို ဖေါ်ထုတ်ပြီး ဒီအထဲမှာ ပါဝင်တာကို စစ်ဆေးပြီး ရည်ရွယ်ချက် သီးခြား အတည်ပြုချက်ကို လက်မှတ်ထိုးပါတယ်။ ပုံမှန် မူဝါဒအရ အုပ်ချုပ်တဲ့ စာရင်းစစ်မှူးစုထံမှ အတည်ပြုချက် တစ်ခုကို လက်ခံတယ်။

အများပြည်သူ ကွန်တိန်နာ ကုန်သွယ်မှုနှင့် ပရိုတိုကော ရလဒ် မှတ်တမ်းမှာ ရည်ရွယ်ချက်ရှိပြီး ဖော်ပြထားပါတယ်-

- ကွန်ရက်နှင့် အစုအဝေး မှတ်သားချက်များ
- ပါဝင်သော data space လမ်းကြောင်းများနှင့် ပါဝင်သူအရေအတွက်
- အချိန်ကာလနှင့် သက်တမ်းကုန်ဆုံးမှု အမြင့်
- တည်ငြိမ်ပြီး အတွင်းအဓိပ္ပာယ် မဖော်ပြသော pool identifier များ၊ root များ၊ nullifier များ၊ commitment များနှင့် ပုံသေ ciphertext slot များ
- ကော်မတီ ခွင့်ပြုချက် မူဝါဒများနှင့် တိကျသော 3-of-4 ရရှိနိုင်မှု, ပြင်ဆင်ခြင်း, နှင့်ပရိုတိုကောအပြီးသတ်သတ်မှတ်ချက်များ
- ပံ့ပိုးသူ၊ အများသုံးကွန်ရက် အခကြေးနဲ့ terminal status

ဤသည် အကြောင်းအရာလျှို့ဝှက်မှုဖြစ်ပြီး အသွားအလာလမ်းကြောင်း အမည်မဖော်နိုင်မှု မဟုတ်ပါ။ အချိန်၊ ပါဝင်သူအရေအတွက်၊ data space ၏ identity နှင့် တည်ငြိမ်သော pool လှုပ်ရှားမှုတို့သည် အများသိဖြစ်နေဆဲဖြစ်သည်။ CBDC တစ်မျိုးတည်းကိုသာ လက်ခံထားသော data space တွင် ပိုင်ဆိုင်မှု identifier အတိအကျကို မထုတ်ပြန်သော်လည်း လမ်းကြောင်းမှ ပိုင်ဆိုင်မှုကို ခန့်မှန်းနိုင်သည်။

## အသုံးချမှု လိုအပ်ချက်များ {#deployment-requirements}

မဖွင့်ခင် operator တွေဟာ အောက်ပါအချက်တွေအားလုံးကို လိုအပ်ပါတယ်။

1. ပါဝင်သော data space တိုင်းအတွက် ကွဲပြားသော BLS consensus ကီးများနှင့် ပိုင်ဆိုင်ကြောင်း သက်သေများပါသော validator လေးခုအတိအကျ
2. လိုအပ်တဲ့ Sumeragi DA/RBC ကို အမြင့်တိုင်းအတွက် လုပ်နိုင်သည်။
3. data space တိုင်းတွင် အုပ်ချုပ်မှုအောက်ရှိ လျှို့ဝှက်ငွေစာရင်းရှင်းလင်းမှု pool နှင့် ကနဦး root
4. ရရှိနိုင်သော မူလ `IrohaIvmPrivateNoteStarkV1` အကောင်အထည်ဖော်မှု၊ commit လုပ်ပြီးသော သီးသန့်ငွေစာရင်းရှင်းလင်းမှု ကန့်သတ်ချက်များနှင့် V1 မူဝါဒ ခွင့်ပြုချက်
5. အနည်းဆုံး စည်းကမ်းထားသော ဒေသခံ `PrivateSettlementAuditPolicyV1` တစ်ခု၊ သီးခြားအော်ဒီတာ လက်မှတ်ထိုးခြင်းနှင့် ဟိုက်ဘရစ်ကုဒ်ရေးရာ သော့များ၊ အဓိကခေတ်ကာလ၊ အမြင့် သက်တမ်းနှင့် ခွင့်ပြုချက် တံခါးကိုပါ ၀ င်သည်။
6. commit လုပ်ပြီးသော ထိန်းသိမ်းမှုကာလအတွက် လုံလောက်သော သီးသန့် sidecar သိုလှောင်မှု
7. နောက်ဆုံး အများပြည်သူ ကွန်တိန်နာ ငွေပေးချေမှုကို တင်ပြနိုင်သော ဘက်လိုက် ပံ့ပိုးရေး အကောင့်

Auditor တစ်ဦးသည် validator ကိုလည်း လည်ပတ်နိုင်သော်လည်း consensus၊ auditor လက်မှတ်ထိုးမှုနှင့် auditor စာဝှက်မှုတို့အတွက် သီးခြားကီးများ သုံးရမည်။ စည်းမျဉ်းအရ ထိန်းသိမ်းရမည့် ကာလအတွင်း အနားပေးထားသော စာဝှက်ဖြည်ကီးများကို ထိန်းသိမ်းပါ။ သို့မဟုတ် ထိုကီးများကို အနားမပေးမီ capsule များကို ကီးအသစ်ဖြင့် ပြန်ထုပ်ပိုးခြင်းအား အုပ်ချုပ်မှုအရ အတည်ပြုပြီး စမ်းသပ်ပါ။

Validator လေးခု၏ authority ကို အခြေအနေတွင် ချည်နှောင်ထားပြီး client က ပေးခြင်းမဟုတ်ပါ။ Manifest ၏ `authority_context_height` တွင် validator တိုင်းသည် consensus အခြေအနေမှ အစဉ်လိုက် lane/data space စာရင်းအတိအကျနှင့် လက်ရှိအသုံးပြုနေသော lane မျိုးဆက်ကို ဖြေရှင်းပြီး ဖြေရှင်းရရှိသော အမြင့်ကိုက်ညီရန် လိုအပ်ကာ BLS ကီးလေးခုနှင့် ပိုင်ဆိုင်ကြောင်း သက်သေများကို စစ်ဆေးသည်။ Upload၊ Prepare နှင့် နောက်ဆုံးပြေစာ လက်ခံမှုတို့အားလုံးသည် တူညီသော သမိုင်း authority ကို သုံးသည်။

## Sidecar ထိန်းသိမ်းမှုကို ပြင်ဆင်သတ်မှတ်ခြင်း {#configure-sidecar-custody}

Commit လုပ်ပြီးသော ကိုယ်ရေးလုံခြုံမှုမူဝါဒက သက်သေ၊ capsule နှင့် သယ်ဆောင် transaction ကန့်သတ်ချက်များ၊ ပါဝင်သူ ကန့်သတ်ချက်များ၊ သက်တမ်းကုန်ဆုံးမှု၊ ထိန်းသိမ်းမှုကာလနှင့် စာရင်းစစ် လိုအပ်ချက်များကို သတ်မှတ်သည်။ လက်ခံခွင့်အတွက် pool မူဝါဒ အုပ်ချုပ်မှု အသိပေးကာလနှင့် လက်ရှိ ချိန်းပေါ် pool နှင့် စာရင်းစစ်မှတ်တမ်းများလည်း လိုအပ်သည်။ Node တွင် ဖွင့်ရန် flag သို့မဟုတ် ဝန်ဆောင်မှု အသက်သွင်းသည့် အမြင့် မရှိပါ။

နိုဒ်ပြင်ဆင်သတ်မှတ်မှုသည် စာဝှက်ထားသော sidecar သိုလှောင်မှု၏ ဒေသတွင်း စွမ်းရည်ကိုသာ ထိန်းချုပ်သည်:

```toml
[nexus.atomic_private_settlement]
sidecar_max_records = 256
sidecar_max_total_bytes = 3221225472
```

ဤတို့သည် ဖြန့်ချိထားသော သိုလှောင်မှု ကန့်သတ်ချက်များဖြစ်သည်။ ဒေသတွင်း စွမ်းရည် မရွေးချယ်မီ ရည်ရွယ်ထားသော ဟာ့ဒ်ဝဲပေါ်တွင် ထိန်းသိမ်းထားသော မှတ်တမ်းများနှင့် စံ byte ပမာဏကို တိုင်းတာပါ။ စွမ်းရည်တစ်ခုတည်းက ငွေစာရင်းရှင်းလင်းမှုကို အသက်မသွင်းသလို commit လုပ်ပြီးသော မှန်ကန်မှုမူဝါဒကိုလည်း မပြောင်းလဲပါ။

Commit လုပ်ပြီးသော capsule ကန့်သတ်ချက်သည် `PrivateSettlementAuditCapsuleV1` ၏ စံ Norito ကုဒ်သွင်းမှု အပြည့်အစုံကို တိုင်းတာသည်။ AAD၊ nonce၊ စာဝှက်ဒေတာ၊ vector frame ဖွဲ့စည်းမှု၊ စာရင်းစစ် identity များနှင့် ဖုံးအုပ်ထားသော DEK အတန်းတိုင်း ပါဝင်သည်။ Commit လုပ်ပြီးသော carrier transaction ကန့်သတ်ချက်သည် sponsor က လက်မှတ်ထိုးထားသော transaction အပြည့်အစုံကို တိုင်းတာပြီး ညွှန်ကြားချက် frame ဖွဲ့စည်းမှု၊ authority၊ metadata၊ အခကြေးငွေရည်ရွယ်ချက်နှင့် လက်မှတ်တို့ ပါဝင်သည်။ ပုံမှန်ကွန်ရက် transaction ကန့်သတ်ချက်များလည်း သက်ရောက်သည်။

## ငွေရေးကြေးရေးလုပ်ငန်းများ ဖြေရှင်းမှု လုပ်ငန်းစဉ် {#settlement-workflow}

ဖောက်သည်က သက်သေခံချက်များနှင့် ကုဒ်သွင်းထားသော ကပ်ဆူလ်များကို ဒေသတွင်းတွင် တည်ဆောက်သည်။ လျှို့ဝှက်သက်သေများသည် ဒေသခံငွေကြေးစာရင်း (သို့) ဒေသခံအလုပ်သမားအတွင်းမှာနေရမည်ဖြစ်ပြီး လျှောက်လွှာမှတ်တမ်းများ၊ Python အရာဝတ္ထုများ, HTTP တောင်းဆိုချက်များ သို့မဟုတ် ရေရှည်တည်တံ့သည့် ညှိနှိုင်းရေး မှတ်တမ်းများသို့ serialize မလုပ်ရပါ။

Capsule နှင့် auditor တစ်ဦးစီအတွက် DEK ထုပ်ပိုးမှု၏ စစ်မှန်ကြောင်းအတည်ပြုဒေတာတွင် အခြေအနေအရ ချည်နှောင်ထားသော ကော်မတီအတိအကျ၏ digest နှင့် `authority_context_height` တို့အပြင် ကွန်ရက်၊ လမ်းကြောင်း/အသက်ဝင်စက်ဝန်း၊ bundle၊ အပိုင်း၊ မူဝါဒ၊ ကီး epoch နှင့် မစာဝှက်ထားသော စာသား၏ ကတိပြုတန်ဖိုးတို့ ပါဝင်သည်။ ထုပ်ပိုးထားသော ကီးကို မတူသော လူစာရင်း သို့မဟုတ် သမိုင်းဝင် လုပ်ပိုင်ခွင့်အခြေအနေသို့ ရွှေ့မသုံးနိုင်ပါ။

အစီရင်ခံစာစံညွှန်း ငွေကြေးလွှဲပြောင်းမှု အစိတ်အပိုင်းတစ်ခုစီအတွက် ညှိနှိုင်းရေးမှူးက ဒီအစဉ်ကို လုပ်ဆောင်သည်။

1. ယာယီ ကုဒ်ဝှက်ထားသော ပစ္စည်းကို validator လေးခုစလုံးသို့ တင်ပြီး လေးခုအနက် သုံးခု အတိအကျပါဝင်သော စံရရှိနိုင်မှု အတည်ပြုလက်မှတ်ကို ရယူပါ။
2. ခွင့်ပြုထားတဲ့ စာရင်းစစ်သူတစ်ဦးက ၎င်းရဲ့ ကပ်ဆူးကိုယူပြီး ဖေါ်ထုတ်ပေးပါ၊ အများပြည်သူ ချုပ်ဆိုချက်တွေကို ပြန်လည် တွက်ချက်၊ ဒေသဆိုင်ရာ မူဝါဒကို လိုက်နာကာ အတည်ပြုချက်ကို တင်ပြပါ။
3. အတည်ပြုသူ ၄ ဦးမှ မဲများကို ပြင်ဆင်ပါ။ အတည်ပြုသူများတိုင်းက မဲမပေးမီ ဒယ်လ်တာကို သီးသန့်စစ်ဆေးပြီး ရေရှည်တည်တံ့စွာ အဆင့်သတ်မှတ်သည်။ အဆင့်သတ်မှတ်သူတိုင်းအတွက် Single Protocol-Standard 3-of-4 Prepare Certificate ကို ဆက်လက်ထားပါ။
4. အပိုင်း (leg) တိုင်းတွင် Prepare အတည်ပြုလက်မှတ် ရရှိပြီးနောက် မပြောင်းလဲနိုင်သော ပြီးပြည့်စုံသည့် Prepare barrier ကို တည်ဆောက်ပါ။ Manifest ပံ့ပိုးသူအား ၎င်းကို `RegisterAtomicPrivateSettlementPrepareV1` ထိန်းချုပ်မှု သယ်ဆောင် transaction တစ်ခုဖြင့် တင်သွင်းစေပြီး အပြီးသတ်အတည်ဖြစ်မှုကို စောင့်ပါ။ Commit မဲပေးသူများသည် ထပ်တူကူးယူထားသော ထို lock ကို စစ်ဆေးကြည့်ရှုသည်။ ထို့နောက် စံ 3-of-4 Commit အတည်ပြုလက်မှတ်များကို တောင်းဆိုပြီး တည်မြဲစွာ သိမ်းဆည်းပါ။ ညှိနှိုင်းသူ ပြန်လည်စတင်ပါက ပါဝင်သူ node များထံမှ ၎င်းတို့၏ ဒေသတွင်း တည်မြဲစွာ သိမ်းထားသော Prepare နှင့် Commit အတည်ပြုလက်မှတ်များကို query လုပ်ပြီး quorum နှင့် ညီမျှသော စံ အတည်ပြုလက်မှတ်တစ်ခုကို ရွေးချယ်ကာ ဆက်မလုပ်မီ ပြန်လည်ဖြန့်ဝေပါ။ အထောက်အထားမစစ်ရသေးသော ဒေသတွင်း cache မှ အတည်ပြုလက်မှတ်ကို ဘယ်တော့မှ ပြန်မတည်ဆောက်ပါနှင့်။
5. Manifest ပံ့ပိုးသူအား ကမ္ဘာလုံးဆိုင်ရာ အပြီးသတ် သယ်ဆောင် transaction ကို လက်မှတ်ထိုးပြီး တင်သွင်းစေပါ။ သယ်ဆောင် transaction တွင် `FinalizeAtomicPrivateSettlementV1` ညွှန်ကြားချက် တစ်ခုနှင့် အတည်ပြုလက်မှတ်ရ bundle အပြည့်အစုံ အတိအကျ ပါဝင်သည်။ ညှိနှိုင်းသူနှင့် WSV ကြိုတင်စစ်ဆေးမှုသည် မှတ်ပုံတင်ထားသော ညွှန်ကြားချက် frame ဖွဲ့စည်းမှု အပါအဝင် box လုပ်ထားသော အပြီးသတ် ညွှန်ကြားချက် အပြည့်အစုံကို တိုင်းတာသည်။ Torii နှင့် core ၏ တစ်ကြိမ်သုံး သယ်ဆောင် transaction ချိတ်ဆက်မှုတို့သည် လုပ်ပိုင်ခွင့်၊ metadata၊ အခကြေးငွေ ရည်ရွယ်ချက်နှင့် လက်မှတ် အပါအဝင် sponsor လက်မှတ်ထိုးထားသော စံ transaction အတိအကျအပေါ် `max_carrier_bytes` ကို ကျင့်သုံးသည်။ Torii သည် သယ်ဆောင် transaction ကို ၎င်း၏ လုပ်ပိုင်ခွင့်ဆိုင်ရာ အခြေအနေ မတိုင်မီ၊ သက်တမ်းကုန်ချိန်အမီ အပြီးသတ်အတည်ဖြစ်နိုင်သော နောက်ဆုံးဝင်ခွင့်အမြင့်တွင် သို့မဟုတ် ၎င်းနောက်ပိုင်း၊ သို့မဟုတ် အုပ်ချုပ်မှုက သတ်မှတ်ထားသော သက်တမ်းကာလကို ကျော်လွန်သည့်အခါ ငြင်းပယ်သည်။
6. ကမ္ဘာလုံးဆိုင်ရာ အပြီးသတ်မှုအထိ အများပြည်သူ ဘန်ဒယ်အခြေအနေနှင့် ပရိုတိုကော ရလဒ်မှတ်တမ်းကို မေးမြန်းပါ။ ဒေသတွင်း အထောက်အပံ့ မှတ်တမ်းအခြေအနေကို မပြောင်းလဲနိုင်တဲ့ ကမ္ဘာလုံးဆိုင်ရာ နောက်ဆုံးမှတ်တမ်းကို ညှိမပေးတဲ့အထိ ယာယီအဖြစ် ဆက်ဆံပါ။

Rust client သည် `certify_and_upload_private_settlement_legs_v1`၊ `prepare_private_settlement_bundle_v1`၊ `register_private_settlement_prepare_and_wait_v1`၊ `commit_private_settlement_bundle_v1` နှင့် `submit_private_settlement_bundle_v1` အပါအဝင် method များဖြင့် ဤလုပ်ငန်းစဉ်ကို ပံ့ပိုးသည်။ ပြန်စတင်ပြီးနောက်လည်း ဘေးကင်းသော ညှိနှိုင်းမှုအတွက် `recover_or_prepare_private_settlement_bundle_v1` နှင့် `recover_or_commit_private_settlement_bundle_v1` ကို သုံးသည်။ ကော်မတီနှင့် စာရင်းစစ်သူ ခေါ်ဆိုမှုများတွင် သက်ဆိုင်ရာ role အတွက် အထောက်အထားများကို အတိအလင်း ပေးရသည်။ ၎င်းတို့သည် သာမန်အကောင့် လက်မှတ်ထိုးသူကို ပြန်မသုံးပါ။

## Auditor Policy ကို လုံခြုံစွာ Rotate လုပ်ပါ။ {#rotate-an-auditor-policy-safely}

Privacy-Governance-authorized `RotatePrivateSettlementPoolPolicyV1` ညွှန်ကြားချက်ကိုအသုံးပြုပါ။ ၎င်းသည်အတိအကျလက်ရှိ အုပ်ချုပ်မှု cryptographic digest တန်ဖိုးကိုဖော်ပြရမည်၊ လမ်းကြောင်းတစ်ခုတည်း၊ ပရိုတိုကုတ်ဒေတာအုပ်စုနှင့် အရင်းအမြစ်ဘောင်သတ်မှတ်သော cryptographic commitment တန်ဖိုးကို ထိန်းထားရမည်။ အုပ်ချုပ်မှု ပြန်လည်သုံးသပ်မှုကို တစ်ဆင့်တိုးမြှင့်ရမည်။ မူဝါဒ/အုပ်ချုပ်မှု အမျိုးမျိုးသော cryptographic digests များကို အသုံးပြုပြီး rotation ကိုပါ ၀ င်သည့် block တွင် activate လုပ်ပါ။ replay set များနှင့် နောက်ဆုံးသတ်မှတ်ထားသော protocol ရလဒ် မှတ်တမ်းများကို သိမ်းဆည်းထားသည်။ rotation ၏ activation အမြင့်တွင်တူညီသော route / pool ကိုထိတွေ့သည့် protocol ရလဒ်မှတ်တမ်းကို မပါ ၀ င်ပါ။ ညွှန်ကြားချက်သည် ထိုနယ်နိမိတ်ကို ငြင်းပယ်သည်။

အများမြင် pool projection သည် အစားထိုးခံရပြီးသော မူဝါဒပြင်ဆင်မှု မျိုးဆက်စဉ် အပြည့်အစုံကို ထိန်းသိမ်းထားသည်။ ထို့ကြောင့် လှည့်ပြောင်းမှု မတိုင်မီ အပြီးသတ်ခဲ့သော ပြေစာသည် ပြန်လည်စတင်ပြီးနောက်တွင်လည်း မှန်ကန်နေဆဲဖြစ်ပြီး ထိုပြေစာကို အတိအကျ ပြန်လည်တင်သွင်းမှုကို အခြေအနေ မပြောင်းလဲဘဲ ငြင်းပယ်သည်။ မျိုးဆက်စဉ်သည် မပြီးဆုံးသေးသော အလုပ်ကို ခွင့်မပြုပါ- အသက်သွင်းမှု နယ်နိမိတ်ကို ဖြတ်ကျော်သော မူဝါဒဟောင်း bundle မည်သည့်တစ်ခုမဆို ကမ္ဘာလုံးဆိုင်ရာ အခြေအနေ မပြောင်းလဲမီ ဘေးကင်းစွာ ပိတ်၍ ကျရှုံးသည်။ သိမ်းဆည်းထားသော capsule များကို ဖွင့်ရန် လိုအပ်သော စာဝှက်ဖြည် key ဟောင်းတိုင်းကို ထိန်းသိမ်းပါ၊ သို့မဟုတ် ၎င်းကို မဖျက်ဆီးမီ အုပ်ချုပ်မှုဖြင့် အတည်ပြုပြီး စမ်းသပ်ထားသော capsule ပြန်ထုပ်ပိုးမှုကို အပြီးသတ်ပါ။

## ကျရှုံးမှုနှင့် ပြန်လည်ထူထောင်ခြင်း {#failure-and-recovery}

Auditor အတည်ပြုချက်များ မရှိခြင်း သို့မဟုတ် ဟောင်းနေခြင်း၊ validator မဲ သုံးမဲမပြည့်ခြင်း၊ အမြစ် သို့မဟုတ် epoch မမှန်ခြင်း၊ nullifier ထပ်နေခြင်း၊ proof သို့မဟုတ် capsule အစားထိုးထားခြင်း၊ အပိုင်းအစဉ် စံမဟုတ်ခြင်း၊ bundle သက်တမ်းကုန်ခြင်းနှင့် ပြန်လည်ပေးလျော်မှု စည်းကမ်းများ မကိုက်ညီခြင်းအားလုံးသည် ကမ္ဘာလုံးဆိုင်ရာ အခြေအနေ မပြောင်းမီ ကျရှုံးသည်။ Commit အသိအမှတ်ပြုလက်မှတ်များသည် သီးသန့်အခြေအနေကို မည်သည့်အခါမျှ မပြောင်းလဲပါ။

Validator များသည် sidecar များ၊ ယာယီထားရှိသော delta များနှင့် အဆင့်အတည်ပြုလက်မှတ်များကို အသိအမှတ်မပြုမီ fsync လုပ်သည်။ ပြန်လည်စတင်ချိန်တွင် ၎င်းတို့သည် စံ တည်မြဲမှတ်တမ်းများမှ ကြိုတင်သိမ်းဆည်းမှုများကို ပြန်လည်တည်ဆောက်ပြီးနောက် မပြောင်းလဲနိုင်သော ကမ္ဘာလုံးဆိုင်ရာ ပြေစာများ၊ abort အမှတ်အသားများ သို့မဟုတ် သက်တမ်းကုန်ဆုံးမှုကို ညှိနှိုင်းသည်။ ကြီးကြပ်ထားသော ညှိနှိုင်းသူ (reconciler) သည် ညှိနှိုင်းရန် နောက်ဆုံးအခြေအနေ ကိုယ်စားလှယ်လောင်း မရှိသည့်အခါတွင်ပင် ထပ်တူကျစွာ တွေ့ရှိရသော တရားဝင်အမြင့်တွင် နောက်ဆုံးအခြေအနေ ထိန်းသိမ်းမှု ဖြတ်တောက်ခြင်းကို လုပ်ဆောင်ပြီး ဖြတ်တောက်မှု အမှားဖြစ်ပါက ဘေးကင်းစွာ ပိတ်၍ ကျရှုံးသည်။ တရားဝင် ကမ္ဘာလုံးဆိုင်ရာ နောက်ဆုံးအခြေအနေ မှတ်တမ်းသာ ယာယီထားရှိသော lock များကို လွှတ်ပေးသည်။ အပြီးသတ်ထားသော ပြေစာကို အတိအကျ ပြန်လည်တင်သွင်းမှုကို အခြေအနေ မပြောင်းလဲဘဲ ငြင်းပယ်သည်။ ကွဲလွဲသော ပြန်လည်တင်သွင်းမှုသည် တစ်သမတ်တည်း ကျရှုံးသည်။

ကြိုတင်သီးသန့်ယူထားမှု၏ အထောက်အထားတွင် လမ်းကြောင်းအပြည့်အစုံ ပါဝင်သည်။ Pool ထိပ်မှတ်များသည် `(route, pool_id, epoch, root)`၊ nullifier များသည် `(route, pool_id, nullifier)`၊ အထွက်များသည် `(route, pool_id, commitment)` ကို သုံးသည်။ အခြားလမ်းကြောင်းပေါ်ရှိ တူညီသော မဖော်ထုတ်နိုင်သည့် တန်ဖိုးများသည် သီးခြားဖြစ်သည်။ လမ်းကြောင်းအတိအကျ တိုက်မိမှုသည် ပြန်စတင်ပြီးနောက်လည်း ပိတ်လှောင်ထားဆဲ ဖြစ်သည်။

လည်ပတ်ရေး သတိပေးချက်များသည် မဖော်ထုတ်နိုင်သည့် bundle၊ လမ်းကြောင်း၊ အဆင့်၊ digest၊ အမြင့်နှင့် အကြောင်းရင်းအတန်း အကွက်များကိုသာ သုံးသင့်သည်။ စာဝှက်ဖြည်ထားသော capsule များ၊ အကောင့် သို့မဟုတ် ပိုင်ဆိုင်မှုအမှတ်အသားများ၊ ပမာဏများ၊ မှတ်စုများ၊ view ဒေတာ၊ proof သက်သေဒေတာများ သို့မဟုတ် parser payload များကို log၊ ဖြစ်ရပ်၊ metric အညွှန်း သို့မဟုတ် tracing span များတွင် မည်သည့်အခါမျှ မထည့်ပါနှင့်။

## အစစ်တန်ဖိုးမတိုင်မီ အရည်အသွေး {#qualification-before-real-value}

သင်ဖြန့်ချိရန် ရည်ရွယ်သော build နှင့် ပြင်ဆင်သတ်မှတ်မှု အတိအကျအတွက် အောက်ပါအချက်များကို ဖုံးလွှမ်းသည့် အထောက်အထားများကို မော်ကွန်းတင်ပါ။

- ပဋိပက္ခသက်သေ၊ ကပ်ဆူလ်၊ မူဝါဒ၊ သော့လှည့်ခြင်း၊ ပြန်လည်ပေးချေခြင်းနှင့် ပြန်လည်ဖြည့်စွက်မှု ကိစ္စများ
- data space 2၊ 3၊ 4၊ 8 နှင့် 16 ခုအတွက် အမှန်တကယ် validator လေးခုပါ process များ၊ validator နှင့် ညှိနှိုင်းသူ ပြန်စတင်မှုများ၊ စစ်မှန်ကြောင်း အတည်ပြုထားသော 5%၊ 10% နှင့် 20% မက်ဆေ့ချ်ပျောက်ဆုံးမှု၊ အဆင့်လိုက် ကွန်ရက်ခွဲပြတ်မှု၊ ပြန်လည်ရယူမှုနှင့် သိမ်းဆည်းရေးနယ်နိမိတ်၌ crash ဖြစ်မှုများအပါအဝင်
- Torii၊ P2P၊ ဘလော့ခ်များ၊ Kura၊ snapshot များ၊ query များ၊ ဖြစ်ရပ်များ၊ log များနှင့် telemetry တစ်လျှောက် canary နှင့် ကွဲပြားမှုနှိုင်းယှဉ် သတင်းအချက်အလက်ပေါက်ကြားမှု စိစစ်ခြင်း
- အနည်းဆုံးအပူချိန်ငါးခုနှင့် real network ပါဝင်သူအရေအတွက်ကို တိုင်းတာမှုသုံးဆယ်စုပေါင်း, p50, p95, p99, ယုံကြည်မှု ကြားကာလများ, အရင်းအမြစ်များ, ယာဉ်မောင်းနှင်မှု၊ သက်သေခံချက်နှင့်ပရိုတိုကောလစ်ရလဒ်မှတ်တမ်းအရွယ်အစားများ, နှင့် ပွင့်လင်းမြင်သာသော AMX ကိုထိန်းချုပ်ခြင်း
- ကျဉ်းမြောင်းတဲ့ လုပ်ငန်းခွင် စမ်းသပ်မှုတွေ၊ ခေါက်ဆွဲနဲ့ ဖွဲ့စည်းချက် စစ်ဆေးမှု၊ ကြုံရာမျိုးစေ့၊ စုပ်ယူခြင်း၊ ပြန်လည်ဖန်တီးလို့ရတဲ့ builds SBOMs နဲ့ လက်မှတ်ထိုးထားတဲ့ artefact cryptographic hashes တွေ
- ပုံစံကျသက်သေပြ အလွှာနှစ်ခုလုံး - အပိုင်း 3/255 ခု၏ အရေအတွက်ညီမျှမှု စစ်ဆေးချက်များနှင့် validator လေးခု အတိအကျပါသော ကော်မတီအလိုက် အညွှန်းသတ်မှတ်သည့် N=2 validator အဓိကစစ်ဆေးမှု၊ ကန့်သတ်ချို့ယွင်းမှု အပြည့်အစုံ၊ စာတမ်းအဓိက N=3 ချို့ယွင်းမှု၊ N=4 ချို့ယွင်းမှုမရှိခြင်းနှင့် N=3 သက်တမ်းကုန်/ပြန်လည်လုပ်ဆောင်မှု ပြင်ဆင်သတ်မှတ်ချက်များ။ ကော်မတီတစ်ခုစီ၏ ချို့ယွင်းမှုဘတ်ဂျက်သည် သီးခြားဖြစ်ရမည်။
- သက်သေဆက်နွှယ်မှု၊ အတု slot ရွေးချယ်သူများ၊ ပိုင်ဆိုင်မှုနှင့် capsule ချည်နှောင်မှုများ၊ ပြန်လည်ပေးချေမှု ဆက်နွှယ်ချက်၊ စာဝှက်နည်းပညာနှင့် data space များအကြား အခြေအနေစက်တို့ကို သီးခြားသုံးသပ်မှု

မူရင်းနှင့် လျှို့ဝှက်အချက်အလက်ဖယ်ရှားထားသော အထောက်အထားများ၊ ခြိမ်းခြောက်မှုပုံစံ၊ protocol မှန်ကန်မှု ရှင်းလင်းချက်၊ ကန့်သတ်ချက်များ၊ commit ID၊ ဟာ့ဒ်ဝဲဖော်ပြချက်နှင့် စာရင်းစစ်အစီရင်ခံစာများကို DOI ဖြင့် အထောက်အထားပြုထားသော မပြောင်းလဲနိုင်သည့် artifact အဖြစ် ထုတ်ဝေပါ။ Repository စမ်းသပ်ချက်များတစ်ခုတည်းက ဤလုပ်ဆောင်ချက်ကို production အသုံးပြုရန် အရည်အချင်းပြည့်မီသော CBDC ငွေရှင်းစနစ်အဖြစ် မဖြစ်စေပါ။

နောက်ဆုံးရှင်းလင်းတဲ့ Iroha checkout ကနေ လွတ်မြောက်မှု အရင်းအမြစ် စာရင်းကို ဖန်တီးပြီး အဲဒီ checkout အပြင်မှာ ရှိပြီးသား bundle root ကို တံဆိပ်ခတ်ပါ။

```sh
python3 scripts/private_settlement_source_evidence.py \
  --repository-root . \
  --bundle-root /absolute/path/to/release-bundle
```

ထုတ်လုပ်သူက ရိုက်ကူးမှုအတွင်းမှာ ပွဲတင်ထားတဲ့၊ ပွဲတင်မထားတဲ့၊ ခြေရာခံမထားတဲ့ (သို့) ပေါင်းစပ်မထားတဲ့ ဖိုင်တွေနဲ့ အရင်းအမြစ်ပြောင်းတာတွေကို ကျရှုံးစေတယ်။ ၎င်းသည် raw source-code revision object ကို ထိန်းသိမ်းထားပြီး single protocol-standard Git tree inventory, တိကျတဲ့ binary path list, deterministic source seal နဲ့ `Cargo.lock`; လက်ရာထုတ်ပြန်ချက်တိုင်းကို ၎င်းရဲ့ JSON နောက်ဆုံးထုတ်ပြန်မှုဆိုင်ရာ အထောက်အထားကို ထုတ်ပေးသည်။ DOI- အစုအဝေး စစ်ဆေးသူ (သို့) ပြင်ပ ထုတ်လွှတ်မှုဂိတ်တစ်ခုခု။

Source တံဆိပ်သည် စနစ်များအကြား သယ်ဆောင်အသုံးပြုနိုင်ပြီး မမှန်လျှင် လက်မခံဘဲ ပိတ်ပင်သည်။ ထုတ်လုပ်သူနှင့် နောက်ဆုံးစစ်ဆေးသူတို့သည် မော်ကွန်းတင်ထားသော symlink ဆက်နွှယ်ပုံတစ်ခုလုံးကို ဖြေရှင်းသည်။ ထို့ကြောင့် root အတွင်းရှိပုံပေါ်သော်လည်း အခြား link မှတစ်ဆင့် အပြင်သို့ ထွက်သော link၊ စက်ဝန်း၊ `.git` ကို ဖြတ်သန်းမှု သို့မဟုတ် Windows ပုံစံ ပစ်မှတ်ကို link မဖန်တီးမီ ပယ်ချသည်။ ဖွဲ့စည်းပုံသတ်မှတ်ထားသော source နှင့် gate အစီရင်ခံစာများကို ထုတ်ဝေမှု manifest နှင့် digest၊ အရှည် ကိုက်ညီသော ကန့်သတ်ထားပြီး တည်ငြိမ်သည့် ဖိုင်များမှသာ parse လုပ်သည်။ Source payload အမျိုးအစားတစ်ခုစီသည် တစ်ကြိမ်အတိအကျသာ ပါရမည်။

ချို့ယွင်းမှုစမ်းသပ်မှု မူရင်း run တိုင်းနှင့် ကြာချိန်နမူနာတိုင်းတွင် ထုတ်ဝေမှု commit အပြည့်အစုံ၊ ဖွဲ့စည်းပုံသတ်မှတ်ထားသော ဟာ့ဒ်ဝဲဖော်ပြချက်တစ်ခု၏ SHA-256 နှင့် ၎င်း၏ ပါဝင်သူအရေအတွက် ပြင်ဆင်သတ်မှတ်မှု အတိအကျ၏ SHA-256 ကို ချည်နှောင်ရမည်။ N=2,3,4,8,16 ကို ဖုံးလွှမ်းသော စံပြင်ဆင်သတ်မှတ်မှု manifest တစ်ခုကို မော်ကွန်းတင်ပါ။ စာရင်းတစ်ခုစီသည် ထိန်းသိမ်းထားသော ပြင်ဆင်သတ်မှတ်မှု byte များကို ရည်ညွှန်းရမည်၊ data space တစ်ခုလျှင် validator လေးခုအတိအကျ၊ လေးခုအနက် သုံးခု၏ မဲပြည့်အရေအတွက်နှင့် မဖြစ်မနေ လက်မှတ်ထိုးထားသော RS16 DA/RBC တို့ကို အတည်ပြုဖော်ပြရမည်။ ထုတ်ဝေမှုစစ်ဆေးသူသည် မတူသော build၊ ဟာ့ဒ်ဝဲ profile သို့မဟုတ် ကွန်ရက်ပြင်ဆင်သတ်မှတ်မှုတွင် ထုတ်လုပ်ထားသော အကျဉ်းချုပ်များကို ငြင်းပယ်သည်။ ပျောက်ဆုံးမှု၊ အဆင့်ခွဲပြတ်မှုနှင့် သိမ်းဆည်းချိန် crash အတန်းတစ်ခုစီသည် SHA-256 ဖြင့် ချည်နှောင်ထားသော စစ်မှန်ကြောင်းအတည်ပြု controller နှင့် အက်တမ်သဘောဖမ်းယူမှု ပစ္စည်းများအတွင်း ကမ္ဘာလုံးဆိုင်ရာ ပြန်သုံးမရသော JSONL မှတ်တမ်းရည်ညွှန်းချက် အတိအကျများကို ထပ်မံအမည်ပေးရမည်။ ထုတ်ဝေမှုစစ်ဆေးသူသည် ထို digest များကို ဖြေရှင်းပြီး အတန်းများသည် run ၏ identity၊ trial အညွှန်းနှင့် parameter များ၊ controller အသိအမှတ်ပြုချက် သို့မဟုတ် ပြန်လည်ရယူမှုရလဒ်၊ ဆက်တိုက်စစ်ဆေးမှု အရေအတွက်နှင့် တစ်စိတ်တစ်ပိုင်းမြင်နိုင်မှု၊ သုံးစွဲနိုင်မှု တွေ့ရှိချက် သုညတို့နှင့် ကိုက်ညီရန် လိုအပ်သည်။ နောက်ထုတ်ဝေမှုများ၏ p95/p99 နှိုင်းယှဉ်မှုများသည်လည်း candidate နှင့် ဟာ့ဒ်ဝဲ၊ ပြင်ဆင်သတ်မှတ်မှု သို့မဟုတ် တိုင်းတာမှုလိုအပ်ချက် မတူသော လက်မှတ်ထိုးထားသည့် အခြေခံမှတ်တမ်းကို ငြင်းပယ်သည်။ နောက်ဆုံးစစ်ဆေးသူသည် သီးခြား benchmark အကျဉ်းချုပ်ကို မယုံကြည်ဘဲ မော်ကွန်းတင်ထားသော မူရင်းနမူနာများမှ အစီရင်ခံထားသည့် percentile များ၊ MADs များနှင့် တစ်သမတ်တည်း ယုံကြည်မှုအပိုင်းအခြားများအားလုံးကို ပြန်တွက်သည်။ ထို့အတူ canary manifest ကို ပြန်ဖတ်ပြီး မော်ကွန်းတင်ထားသော ကိုယ်ရေးလုံခြုံမှုမျက်နှာပြင်တိုင်းကို သီးခြားပြန်စစ်သဖြင့် ဖိုင် digest များ ပြန်ချည်နှောင်ပြီးနောက် အစီရင်ခံစာက ထည့်သွင်းစမ်းသပ်ထားသော လျှို့ဝှက်ချက်တွေ့ရှိမှုကို ဖုံးကွယ်၍ မရပါ။ လျှို့ဝှက်ချက်သီးသန့် run တစ်ခုစီသည် ပိုင်ရှင်သာ ဝင်ရောက်နိုင်သော မစစ်ထုတ်ထားသည့် loopback pcap၊ မူရင်း tcpdump stderr နှင့် packet ပျောက်ဆုံးမှု သုညစာရင်းအင်းများ၊ စံ port manifest၊ ထုပ်ပိုးထားသော ကန့်သတ်ရင်းမြစ် မော်ကွန်းနှင့် peer အားလုံး၏ အက်တမ်သဘောဆိုင်ရာ တွေ့ရှိချက်များကို ထိန်းသိမ်းရမည်။ နောက်ဆုံးစစ်ဆေးသူသည် ထုတ်ပြန်ထားသော အကျဉ်းချုပ်များကို မယုံကြည်ဘဲ ထိုမော်ကွန်း byte များမှ port နှင့် ချည်နှောင်ထားသော packet ခွဲခြားမှု၊ ရင်းမြစ်ဖော်ပြချက်များနှင့် အခြေခံအခြေအနေမှ နောက်ဆုံးအခြေအနေအထိ အက်တမ်သဘော စစ်ဆေးမှုများကို ပြန်လုပ်သည်။

မော်ကွန်းတွင် လိုအပ်သော ကိုယ်ရေးလုံခြုံမှု မျက်နှာပြင်တိုင်းအတွက် ဘယ်နှင့်ညာ ဖိုင်လမ်းကြောင်းအတိအကျ၊ အမျိုးအစား၊ byte အရှည်နှင့် SHA-256 digest တို့ကို ချည်နှောင်သော စံတွဲဖက် traffic အရေအတွက် manifest နှင့် ကွဲပြားမှုနှိုင်းယှဉ် အတွဲ manifest များလည်း ပါဝင်ရမည်။ ၎င်း၏ ကြေညာထားသော root များတွင် တွဲဖက်မော်ကွန်းစာရင်း အတိအကျသာ ပါရမည်။ စစ်ဆေးသူသည် ပုံမှန်မျက်နှာပြင်များအတွက် ဖိုင်တစ်ခုလုံးအရွယ်အစားနှင့် JSON အများမြင်ဖွဲ့စည်းပုံ တူညီရန် လိုအပ်သည်။ ကျပန်းမှုပါဝင်သော loopback ဖမ်းယူမှုအကြမ်းနှင့် ထုပ်ပိုးထားသော ကန့်သတ်ရင်းမြစ် archive သည် အရွယ်အစားစည်းမျဉ်းမှ တိတိကျကျ ခြွင်းချက်ဖြစ်သည်။ ၎င်းတို့အတွက် packet ချိတ်ဆက်မှုအမျိုးအစားနှင့် packet တစ်ခုစီ၏ အရှည်၊ ကန့်သတ်ရင်းမြစ် အထောက်အထားများနှင့် ပုံစံပုံသေ အတန်းအရှည်များကို အစားထိုးနှိုင်းယှဉ်သည်။ Torii တောင်းဆိုမှု/တုံ့ပြန်မှု၊ အများသုံး/ကန့်သတ် P2P packet၊ ဘလော့ခ်၊ query၊ ဖြစ်ရပ်၊ log နှင့် telemetry traffic အရေအတွက်တိုင်းလည်း တူညီရမည်။ Packet ဖွဲ့စည်းပုံပြောင်းလဲမှု၊ အရွယ်အစားတူသော ဖွဲ့စည်းပုံပေါက်ကြားမှု၊ မူလရင်းမြစ်အကြောင်း မမှန်သော အခိုင်အမာပြောဆိုချက် သို့မဟုတ် အတွဲမရှိသော ဖိုင်ကို ပေါက်ကြားမှုအစီရင်ခံစာနှင့် ၎င်း၏ ဟက်ရှ်များ ပြန်ရေးခြင်းဖြင့် ဖုံးကွယ်မရပါ။
