# Atomic Private Data-Cross-Space Settlement ကို Run လုပ်ပါ။ {#run-atomic-private-cross-dataspace-settlement}

`AtomicPrivateSettlementV1` ၂ မှ ၂၅၅ တို့တွင် လျှို့ဝှက် settlement leg တစ်ခုကို ညှိနှိုင်းပေးသည်။ SORA Nexus ဒေတာနေရာတွေရှိပြီး တစ်ကမ္ဘာလုံး နိုင်ငံတကာ ငွေကြေး ဖလှယ်မှု တစ်ခုတည်းရဲ့ ခြေထောက်တိုင်းကို အဆုံးသတ်ပါတယ်။ ပယ်ချခံရတဲ့၊ သက်တမ်းကုန်ဆုံးသွားတဲ့ (သို့) အပိတ်ခံထားရတဲ့ ဘူးတစ်ခုမှာ ခြေထောက်မရှိပါဘူး။ AMX DvP/PvP ကွဲပြားတဲ့ ပရိုတိုကောလမ်းကြောင်းတစ်ခု ဖြစ်နေဆဲပါ။

::: warning Release Status ဒီ feature ကို ထိန်းချုပ်ထားပြီး default အနေနဲ့ disabled လုပ်ထားပါတယ်။
ထုတ်ဝေထားသော functional, privacy, fault, performance, reproducible-build, independent-cryptographic-review နှင့် artefact-publication gates အားလုံးကို တိကျစွာထုတ်ပြန်နိုင်သည်အထိ real CBDC တန်ဖိုးအတွက် မစွမ်းဆောင်ပါ။

## ဒီပရိုတိုကောက ဘာကို ဖုံးကွယ်ထားလဲ။ {#what-the-protocol-hides}

ခြေထောက်တစ်ခုစီမှာ fixed two-input၊ three-output private-note proof ကိုသုံးပါတယ်။ ကော်မတီအတည်ပြုသူတွေက သက်သေခံနဲ့ မရှင်းလင်းတဲ့ အခြေအနေ ကူးပြောင်းမှုကို စစ်ဆေးတယ်။ သူတို့ဟာ plaintext ပါတီတွေ၊ အရင်းအမြစ်တွေ၊ ပမာဏတွေ၊ မှတ်တမ်း (သို့) စီးပွားရေး ရလဒ်တွေကို လက်မခံဘူး။ ခွင့်ပြုထားတဲ့ ဒေသတွင်း စာရင်းစစ်သူက ပိတ်ထားတဲ့ စာရင်းစစ်ဆေးမှုပုဒ်မကို ဖေါ်ထုတ်ပြီး ဒီအထဲမှာ ပါဝင်တာကို စစ်ဆေးပြီး ရည်ရွယ်ချက် သီးခြား အတည်ပြုချက်ကို လက်မှတ်ထိုးပါတယ်။ ပုံမှန် မူဝါဒအရ အုပ်ချုပ်တဲ့ စာရင်းစစ်မှူးစုထံမှ အတည်ပြုချက် တစ်ခုကို လက်ခံတယ်။

အများပြည်သူ သယ်ဆောင်ရေးမှူးနဲ့ လက်မှတ်က ကြံစည်ပြီး ဖော်ပြထားတာက

- ကွန်ရက်နှင့် အစုအဝေး မှတ်သားချက်များ
- ပါဝင်သူ ဒေတာဇုန်လမ်းကြောင်းများနှင့် ပါဝင်သူအရေအတွက်
- အချိန်ကာလနှင့် သက်တမ်းကုန်ဆုံးမှု အမြင့်
- Stable opaque pool identifier များ၊ root များ၊ nullifiers များ၊ commits များနှင့် fixed ciphertext slots များ
- ကော်မတီအာဏာပိုင်များနှင့် တိကျသော 3-of-4 ရရှိနိုင်မှု, ပြင်ဆင်ရန်, နှင့် Commit လက်မှတ်
- ပံ့ပိုးသူ၊ အများသုံးကွန်ရက် အခကြေးနဲ့ terminal status

ဤသည်မှာ ယာဉ်ကြောစီးဆင်းမှု အမည်မဲ့ခြင်းမဟုတ်ဘဲ အကြောင်းအရာ လျှို့ဝှက်ချက်ဖြစ်သည်။ အချိန်ဆွဲခြင်း၊ ပါဝင်သူအရေအတွက်၊ ဒေတာနေရာအသိအမှတ်ပြုမှု၊ တည်ငြိမ်တဲ့စုပေါင်းလုပ်ဆောင်မှုက အများပြည်သူအဖြစ် ကျန်ရှိနေသည်။ တစ်ခုတည်းသော CBDC ကို တည်းခိုထားသည့် ဒေတာဇုန်တစ်ခုသည် စာလုံးဝင်လက်ရှိ asset ID မထုတ်ဝေသော်လည်းလည်း လမ်းကြောင်းမှ asset ကိုဖယ်ရှားနိုင်စေနိုင်ပါတယ်။

## တပ်ဆင်ရန် လိုအပ်ချက်များ {#deployment-requirements}

မဖွင့်ခင် operator တွေဟာ အောက်ပါအချက်တွေအားလုံးကို လိုအပ်ပါတယ်။

1. ပါဝင်တဲ့ ဒေတာနေရာတိုင်းအတွက် အတိအကျ validator လေးခုရှိပြီး ကွဲပြားခြားနားသော BLS သဘောတူညီချက် ခလုတ်များနှင့် ပိုင်ဆိုင်မှု သက်သေခံများရှိသည်။
2. လိုအပ်တဲ့ Sumeragi DA/RBC ကို အမြင့်တိုင်းအတွက် လုပ်နိုင်သည်။
3. စီမံခန့်ခွဲထားသော လျှို့ဝှက် settlement pool နှင့် data space တစ်ခုချင်းစီမှာ မူလ root
4. Active V1 private note capability နှင့် သီးခြား settlement proof profile ကို အသုံးပြုရန်။
5. အနည်းဆုံး စည်းကမ်းထားသော ဒေသခံ `PrivateSettlementAuditPolicyV1` တစ်ခု၊ သီးခြားအော်ဒီတာ လက်မှတ်ထိုးခြင်းနှင့် ဟိုက်ဘရစ်ကုဒ်ရေးရာ သော့များ၊ အဓိကခေတ်ကာလ၊ အမြင့် သက်တမ်းနှင့် ခွင့်ပြုချက် တံခါးကိုပါ ၀ င်သည်။
6. ပြင်ဆင်ထားသော ထိန်းသိမ်းမှုကာလအတွက် လုံလောက်တဲ့ ပုဂ္ဂလိက ဘေးကား သိုလှောင်ခန်း
7. နောက်ဆုံး အများပိုင် သယ်ယူပို့ဆောင်ရေး ကုမ္ပဏီကို တင်ပြနိုင်မယ့် ဘက်မလိုက် ပံ့ပိုးသူ အကောင့်

Auditor သည် validator ကိုလည်းအသုံးပြုနိုင်သော်လည်း သီးခြားသဘောတူညီချက်၊ auditor လက်မှတ်ရေးထိုးခြင်းနှင့် auditor-encryption key များကို အသုံးပြုရမည်ဖြစ်သည်။ စည်းကမ်းချက်အရ ထိန်းသိမ်းထားသည့် ကာလအတွက် အငြိမ်းစား decryption keys များကို သိမ်းဆည်းထားရမည်။ (သို့) မငြိမ်းစားမီ test capsule ကိုထိန်းချုပ်ပြီး ပြန်ထည့်သွင်းရန်။

၄-validator ခွင့်ပြုချက်သည်ဝန်ထမ်းကမပေးဘဲပြည်နယ်တွင်ချိတ်ဆက်ထားသည်။ manifesto ၏ `authority_context_height` တွင် validator တစ်ခုစီသည်အတိအကျစီစဉ်ထားသောလမ်းကြောင်း / ဒေတာနေရာစာရင်းနှင့် Active Lane သရုပ်ဆောင်မှုကိုဖြေရှင်းသည်။ BLS ခလုတ်လေးလုံးနဲ့ ပိုင်ဆိုင်မှု သက်သေခံချက်တွေကို စစ်ဆေးပါတယ်။ Upload, Prepare နဲ့ Final Receipt admits အားလုံးဟာ သမိုင်းဆိုင်ရာ အာဏာတူကို သုံးတယ်။

## Admission ကို Configure လုပ်ပါ။ {#configure-admission}

ထုတ်လုပ်မှုအပြုအမူအားလုံးသည် node ဖွဲ့စည်းချက်မှလာသည်။ ပတ်ဝန်းကျင်ပြောင်းလဲနိုင်သူများက ဤလမ်းကြောင်းကို တက်ကြွမပေးနိုင်ပါ။ ပို့ဆောင်သော default သည် `enabled = false` ဖြစ်သည်၊ feature ကိုပိတ်ထားခြင်းအားဖြင့် settlement-specific ဖွဲ့စည်းမှုတစ်ခုမျှ မလိုပါ။

အုပ်ချုပ်ရေးမှူးက လိုအပ်တဲ့ အရည်အသွေးကို မှတ်တမ်းတင်ပြီးနောက်၊ သင့်တော်သော အသိပေးချက်ဖြင့် တက်ကြွမှု အမြင့်တစ်ခုကို ရွေးချယ်ပြီးနောက်၊ သက်ဆိုင်ရာ node တစ်ခုစီကို စနစ်တကျ ညွှန်ကြားပါ။

```toml
[nexus.atomic_private_settlement]
enabled = true
activation_height = 500000
minimum_activation_notice_blocks = 7200
proof_profile_version = 1
max_participants = 255
max_expiry_blocks = 7200
audit_timeout_blocks = 1200
prepare_timeout_blocks = 1200
commit_timeout_blocks = 1200
capsule_padding_classes_bytes = [4096, 16384, 65536, 262144]
max_proof_bytes = 8388608
max_capsule_bytes = 1048576
max_carrier_bytes = 4194304
sidecar_retention_blocks = 1000000
sidecar_max_records = 256
sidecar_max_total_bytes = 3221225472
default_min_auditor_approvals = 1
permitted_policy_versions = [1]
```

နမူနာမှာ ပို့ဆောင်ထားသော V1 ကန့်သတ်ချက်များကို အသုံးပြုပြီး စွမ်းဆောင်ရည်ဆိုင်ရာ အကြံပြုချက် မဟုတ်ပါ။ စီမံခန့်ခွဲရေး နယ်နိမိတ်တွေကို ရွေးချယ်ဖို့ ရည်ရွယ်တဲ့ Hardware ကို သုံးဆင့် အချိန်ဖြတ်တောက်မှုတွေဟာ `max_expiry_blocks` အတွင်းမှာ တပ်ဆင်ထားရပြီး Sidecar ထိန်းသိမ်းမှုဟာ အနည်းဆုံး သက်တမ်းကုန်ဆုံးတဲ့ ပြတင်းပေါက်ဖြစ်ဖို့လိုပါတယ်။

`max_capsule_bytes` သည် `PrivateSettlementAuditCapsuleV1` တစ်ခုလုံး၏ တရားဝင် Norito ကုဒ်သွင်းခြင်းကို ကန့်သတ်ထားသည် - AAD, nonce, ciphertext, vector framing, auditor identities နှင့် wrapped-DEK စာကြောင်းတစ်ခုစီ။ ဒါဟာ ciphertext အတွက်သာ ကန့်သတ်မှုမဟုတ်ပါ။ ဖွဲ့စည်းထားသော padding class တစ်ခုစီသည် အနည်းဆုံး `default_min_auditor_approvals` စာရင်းစစ်ဆေးသူများအတွက် ထိန်းသိမ်းထားတဲ့ တစ်လုံးလုံး capsule envelope ကိုအံဝင်သင့်သည်။ Torii သည်လည်း အသစ်လက်ခံသည့် မူဝါဒတစ်ခုကိုငြင်းပယ်ပြီး `min_approvals` သည်အုပ်ချုပ်တဲ့ထပ်အောက်ရှိပြီး အသေးစိတ် Canonical ကုဒ်သွင်းမှု အလွန်ကြီးမားသော သက်ဆိုင်ရာ Capsule ကိုငြင်းပယ်သည်။

`max_carrier_bytes` ကော်ပိုရေးရှင်းမှ လက်မှတ်ထိုးထားသော ငွေပေးချေမှုအပြည့်အဝကို ကန့်သတ်ထားသည်မှာ သက်သေခံစာအုပ်တင်မဟုတ်ပေ။ စာရင်းထဲတွင် မှတ်ပုံတင် ညွှန်ကြားချက် ဖွဲ့စည်းပုံ၊ ငွေပေးချေးမှုအာဏာပိုင်နှင့် မီတာဒေတာများ၊ အခွန်ရည်ရွယ်ချက်နှင့် လက်မှတ်ပါ ၀ င်သည်။ သာမန်ကွန်ရက်ငွေပေးချေခြင်း အကန့်အသတ်များသည် လွတ်လပ်သော အထက်နိမိတ်တစ်ခုအဖြစ် ဆက်လက်လုပ်ဆောင်နေဆဲဖြစ်သည်။

Activation ကို မပိတ်နိုင်ဘူးဆိုရင် ထိန်းချုပ်ထားတဲ့ အရည်အသွေးက တက်ကြွနေပြီ၊ ၎င်းရဲ့ အခြေအနေနဲ့ activation heights တွေဟာ ကြေညာချက်ကာလကို ဖြည့်ဆည်းပေးထားပြီး စုစည်းထားတဲ့ proof profile က V1 နဲ့ ကိုက်ညီနေပြီး on-chain pool နဲ့ audit record တွေက လက်ရှိပါ။ configuration flag ကိုသာ enable လုပ်ခြင်းဟာ မလုံလောက်ဘူး။

## ငွေပေးချေမှု လုပ်ငန်းခွင် {#settlement-workflow}

ဖောက်သည်က သက်သေခံချက်များနှင့် ကုဒ်သွင်းထားသော ကပ်ဆူလ်များကို ဒေသတွင်းတွင် တည်ဆောက်သည်။ လျှို့ဝှက်သက်သေများသည် ဒေသခံငွေကြေးစာရင်း (သို့) ဒေသခံအလုပ်သမားအတွင်းမှာနေရမည်ဖြစ်ပြီး လျှောက်လွှာမှတ်တမ်းများ၊ Python အရာဝတ္ထုများ, HTTP တောင်းဆိုချက်များ သို့မဟုတ် ရေရှည်တည်တံ့သည့် ညှိနှိုင်းရေး မှတ်တမ်းများသို့ serialize မလုပ်ရပါ။

ကပ်ဆူလ်နှင့် စာရင်းစစ်သူတစ်ဦးချင်းအတွက် DEK ပုံးတွင် စစ်ဆေးထားသော အချက်အလက်များမှာ တိကျသည့် နိုင်ငံတော်ချိတ်ဆက်ထားသည့် ကော်မတီ၏ အနှစ်သာရနှင့် `authority_context_height` နှင့် ကွန်ရက်တို့ပါဝင်သည်။ လမ်းကြောင်း / သရုပ်ဆောင်မှု, အစုအဝေး, ခြေထောက်, မူဝါဒ, key epoch နှင့် plaintext ကတိပေးချက်။ ပိတ်ထားတဲ့ key ကို အခြားစာရင်းတစ်ခုသို့မဟုတ်သမိုင်းအာဏာပိုင် အခြေအနေကို မပြောင်းနိုင်ပါ။

Canonical leg တစ်ခုစီအတွက် Coordinator က ဒီစဉ်ကို လုပ်ဆောင်တယ်။

1. ယာယီ ကုဒ်သွင်းထားတဲ့ ပစ္စည်းကို validator လေးခုစလုံးမှာ တင်ပြီး Canonical အတိအကျ 3-of-4 အသုံးပြုနိုင်မှုအတည်ပြုချက် ရယူပါ။
2. ခွင့်ပြုထားတဲ့ စာရင်းစစ်သူတစ်ဦးက ၎င်းရဲ့ ကပ်ဆူးကိုယူပြီး ဖေါ်ထုတ်ပေးပါ၊ အများပြည်သူ ချုပ်ဆိုချက်တွေကို ပြန်လည် တွက်ချက်၊ ဒေသဆိုင်ရာ မူဝါဒကို လိုက်နာကာ အတည်ပြုချက်ကို တင်ပြပါ။
3. တောင်းဆိုချက် အတည်ပြုသူ ၄ ဦးမှ မဲများ ပြင်ဆင်ပါ။ အတည်ပြုသူများတိုင်းက မဲမပေးမီ ဒယ်လ်တာကို သီးခြားစစ်ဆေးပြီး ရေရှည် အဆင့်သတ်မှတ်ကြသည်။ အဆင့်သတ်မှတ်ထားသော ဖြေကြားသူတစ်ဦးစီအတွက် တရားဝင် ၃-of-4 Prepare လက်မှတ်ကို ဆက်လက်ရယူပါ။
4. ခြေထောက်တိုင်းမှာ Prepare Certificate ရှိပြီးနောက် မပြောင်းလဲနိုင်တဲ့ Complete Prepare Barrier ကို ဆောက်လုပ်ပါ။ Canonical 3 of 4 Commit Certificate တွေကို တောင်းဆိုပြီး ဆက်လက်တည်ဆောက်လိုက်ပါ။ ညှိနှိုင်းရေးမှူး ပြန်လည်စတင်ပါက ပါဝင်သူ node များထံမှ ၎င်းတို့၏ ဒေသတွင်းတွင် တာရှည်ခံစွာ သိမ်းဆည်းထားသော Prepare နှင့် Commit လက်မှတ်များကို မေးမြန်းရယူပါ၊ တူညီသော quorum ကို ကိုယ်စားပြုသည့် canonical လက်မှတ်တစ်ခုကို ရွေးချယ်ပြီး ဆက်လက်မလုပ်ဆောင်မီ ၎င်းကို ပြန်လည်ဖြန့်ဝေပါ။ စစ်မှန်ကြောင်း အတည်မပြုထားသော ဒေသတွင်း cache မှ လက်မှတ်ကို မည်သည့်အခါမျှ ပြန်လည်တည်ဆောက်ခြင်း မပြုပါနှင့်။
5. ပံ့ပိုးသူရဲ့ လက်မှတ်ကို ထုတ်ပြပြီး ကမ္ဘာလုံးဆိုင်ရာ လေကြောင်းလိုင်းတစ်ခုတည်းကို ပို့ပေးပါ။ လေကြောင်းလိုင္းမှာ တစ်ခုပါဝင်ပါတယ်။ `FinalizeAtomicPrivateSettlementV1` ညွှန်ကြားချက်နှင့် အတိအကျအပြည့်အဝ Certified Bundle ကို. WSV pre-flight တိုင်းတာမှု မှတ်ပုံတင်ညွှန်ကြားချက် ဖွဲ့စည်းခြင်းအပါအဝင် အပြည့်အဝ boxed finalisation ညွှန်ကြားချက်ကို. Torii နျူးကလီးယား single-shot သယ်ဆောင်ရေး binding enforcement ကို `max_carrier_bytes` အာဏာ၊ မီတာဒေတာ၊ အခွန် ရည်ရွယ်ချက်နဲ့ လက်မှတ်အပါအဝင် ပံ့ပိုးသူလက်မှတ်ထိုးထားတဲ့ တိကျတဲ့ Canonical ငွေပေးချေမှုအပေါ်ပါ။ Torii သယ်ဆောင်သူကို ၎င်း၏အာဏာပိုင် အခြေအနေမတိုင်မီ၊ နောက်ဆုံးဝင်ရောက်မှုတွင် (သို့) နောက်ပိုင်းတွင် ပယ်ချသည် သက်တမ်းကုန်ဆုံးချိန် (သို့) သတ်မှတ်ထားတဲ့ သက်တမ်းအလွန်မှာ အပြီးသတ်နိုင်မယ့် အမြင့်ပါ။
6. ကမ္ဘာလုံးဆိုင်ရာ အပြီးသတ်မှုအထိ အများပြည်သူ ဘက်ဒယ်အခြေအနေနဲ့ လက်ခံစာကို မေးမြန်းပါ။ ဒေသတွင်း ဘက်ထရီအခြေအနေကို ပြောင်းလဲမှုမရှိတဲ့ ကမ္ဘာလုံးဆိုင်ရာ terminal မှတ်တမ်းကို ညှိမပေးတဲ့အထိ ယာယီအဖြစ် ဆက်ဆံပါ။

Rust ဖောက်သည်သည်သည် ဤစီးဆင်းမှုကို `certify_and_upload_private_settlement_legs_v1`, `prepare_private_settlement_bundle_v1`, `commit_private_settlement_bundle_v1` နှင့် `submit_private_settlement_bundle_v1` တို့အပါအဝင်နည်းလမ်းများဖြင့် ဖော်ထုတ်သည်။ ပြန်လည်စတင်မှုဘေးကင်းသော ညှိနှိုင်းမှုသည် `recover_or_prepare_private_settlement_bundle_v1` နှင့် `recover_or_commit_private_settlement_bundle_v1` ကို အသုံးပြုသည်။ ကော်မတီနှင့် စာရင်းစစ်သူခေါ်ဆိုမှုများသည် ပွင့်လင်းမြင်သာသော အခန်းကဏ္ဍ မှတ်ပုံတင်ချက်များကိုလိုအပ်ပြီး ပုံမှန်စာရင်း လက်မှတ်ထိုးသူကို ပြန်လည်အသုံးပြုခြင်းမရှိပါ။

## Auditor Policy ကို လုံခြုံစွာ Rotate လုပ်ပါ။ {#rotate-an-auditor-policy-safely}

Privacy-Governance-authorized `RotatePrivateSettlementPoolPolicyV1` ညွှန်ကြားချက်ကို အသုံးပြုပါ။ ၎င်းသည် လက်ရှိအစိုးရစာရင်းကို တိကျစွာ ဖော်ပြရမည်၊ အလားတူ လမ်းကြောင်း၊ စုစုပေါင်းခြင်းနှင့် အရင်းအမြစ်များကို ချုပ်နှောင်ရန် ရည်ရွယ်ချက်ကို ထိန်းသိမ်းရမည်၊ အုပ်ချုပ်ရေး စာရွက်စာတမ်းကို တစ်ကြိမ်တိုးမြှင့်ရမည်၊ ပြတ်သားစွာ အသစ်အဆန်းသော အဓိကခေတ်နှင့် မူဝါဒ/အုပ်ချုပ်ရေးစာရင်းအမျိုးမျိုးကို သုံးရမည်၊ rotation ကိုပါ ၀ င်သော block တွင် activate လုပ်ပါ။ pools နယ်နိမိတ်၊ root များ၊ nullifiers များ၊ output များ၊ replay set များနှင့် နောက်ဆုံးသတ်မှတ်ထားသောလက်မှတ်များကို သိမ်းဆည်းထားသည်။ rotation ၏ activation အမြင့်တွင် ထိုလမ်းကြောင်း / pools ကိုထိတွေ့သည့်လက်မှတ်ကို မပါဝင်ပါနဲ့။ ညွှန်ကြားချက်သည်အဲဒီနယ်နိမိတ်ကိုငြင်းပယ်သည်။

အများပြည်သူအစုပမာဏစီမံကိန်းမှာ မူဝါဒ-ပြင်ဆင်မှု မျိုးရိုးစဉ်တစ်ခုလုံး အစားထိုးထားပြီး ကျန်ရှိနေပါတယ်။ လည်ပတ်ခြင်းမတိုင်မီ နောက်ဆုံးသတ်မှတ်ထားတဲ့ လက်မှတ်ဟာ ပြန်လည်စတင်ပြီးနောက်မှာ သက်ဝင်ဆဲဖြစ်ပြီး ဒီတိကျတဲ့လက်မှတ်ကို ထပ်လောင်းကစားခြင်းဟာ မစွမ်းဆောင်နိုင်ပါ။ မပြီးသေးတဲ့ အလုပ်ကို မျိုးရိုးစဉ်က ခွင့်မပြုဘူး။ တက်ကြွမှု နယ်နိမိတ်ဖြတ်တဲ့ မူဝါဒဟောင်းတစ်ခုခုဟာ ကမ္ဘာလုံးဆိုင်ရာ အခြေအနေပြောင်းလဲခြင်းမတိုင်မီ ပိတ်နိုင်ပါ။ သိုလှောင်ထားသော ကပ်ဆူးတွေကို ဖွင့်ရန်လိုအပ်တဲ့ ရှေးဟောင်း ကုဒ်ဖေါ်ထုတ်ရေး သော့အားလုံးကို ထိန်းသိမ်းပါ၊ (သို့) မဖျက်ဆီးခင် အုပ်ချုပ်ပြီး စမ်းသပ်ထားတဲ့ ကပ်ဆူကို ပြန်လည်ဖြည့်စွက်ပါ။

## ကျရှုံးမှုနှင့် ပြန်လည်ထူထောင်ခြင်း {#failure-and-recovery}

ပျောက်နေတဲ့ (သို့) ခေတ်နောက်ကျတဲ့ စာရင်းစစ်သူ အတည်ပြုချက်တွေ၊ သုံးခုထက်မနည်းသော validator မဲတွေ၊ မှားယွင်းတဲ့ အမြစ်များ (သို့) ကာလများ၊ နှစ်ထပ်အငြင်းပွားမှုတွေ၊ အစားထိုးထားတဲ့ အထောက်အထားများ (သို့မဟုတ်) ကပ်ဆူလ်များ၊ တရားဝင်မဟုတ်တဲ့ ခြေထောက် အစီအစဉ်၊ သက်တမ်းကုန်ဆုံးသွားတဲ့ ဘက်ဒယ်များနဲ့ မညီမျှတဲ့ ပြန်လည်ဖြည့်စွက်ခြင်း စည်းမျဉ်းတွေအားလုံးက ကမ္ဘာလုံးဆိုင်ရာ ဗီဇပြောင်းခြင်းမတိုင်ခင် ကျရှုံးတယ်။ အမိန့်ချမှတ်ချက်တွေဟာ ပုဂ္ဂလိကပြည်နယ်ကို ဘယ်တော့မှ ပြောင်းမသွားဘူး။

Validator တွေဟာ Sidecars, Staged Deltas နဲ့ Phase Certificate တွေကို အသိအမှတ်ပြုမပေးခင် ပြန်လည်စတင်ပြီး Canonical ရေရှည် မှတ်တမ်းတွေကနေ ကန့်သတ်ချက်တွေကို ပြန်တည်ဆောက်ပြီး မပြောင်းလဲနိုင်တဲ့ ကမ္ဘာလုံးဆိုင်ရာ လက်မှတ်တွေ၊ abort markers (သို့) expiration တွေကို ညှိနှိုင်းပါတယ်။ ကြီးကြပ်ခံရတဲ့ reconciller ကလည်း terminal retention cutting ကို synchronously observed authoritative height မှာ ပြုလုပ်တယ်ဆိုရင်တောင် reconciling လုပ်ဖို့ terminal candidate မရှိတဲ့အခါမှာပဲ အချိုးအမှားတစ်ခုကြောင့် ပိတ်နိုင်ခြင်းမရှိပါ။ ခိုင်မာတဲ့ ကမ္ဘာလုံးဆိုင်ရာ terminal record တစ်ခုတည်းက အဆင့်သတ်မှတ်ထားတဲ့ lock တွေကို ထုတ်ပေးတယ်။ တူညီသော နောက်ဆုံးရလက်မှတ်ကို ပြန်လည်ကစားတာဟာ မဖြစ်နိုင်ဘူး၊ ဝိရောဓိရှိတဲ့ ပြန်လည်ကစားမှုက သတ်မှတ်ချက်အရ ကျရှုံးသွားတယ်။

Reservation identity သည်အပြည့်အစုံသောလမ်းကြောင်းကိုပါ ၀ င်သည်။ Pool heads များသည် `(route, pool_id, epoch, root)` ကိုအသုံးပြုကြပြီး nullifiers များက `(route, pool_id, nullifier)` ကိုသုံးကြပြီး outputs များသည် `(route, pool_id, commitment)` ကိုအသုံးပြုကြသည်။ အခြားလမ်းကြောင်းတွင်တူညီသော opaque တန်ဖိုးများသည် လွတ်လပ်သည်။ restart တွင်တိကျသောလမ်းကြောင်း တိုက်မိမှု Lock ဖြစ်နေဆဲဖြစ်သည်။

Operational alerts များတွင် opaque bundle, route, phase, digest, height နှင့် reason-class fields များကိုသာ အသုံးပြုရမည်။ logs, events, metrics labels သို့မဟုတ် tracing span များတွင် ဘယ်တော့မှ decrypted capsules, account or asset identifiers, amounts, memos, view data, proof witnesses, or parser payloads တို့ကို ထည့်မထားပါ။

## အစစ်တန်ဖိုးမတိုင်မီ အရည်အသွေး {#qualification-before-real-value}

သင်ဖြန့်ချိဖို့ရည်ရွယ်တဲ့ တိကျတဲ့ build နဲ့ configuration အတွက် အောက်ပါအချက်အလက်တွေကို ဖုံးအုပ်ထားပါ။

- ပဋိပက္ခသက်သေ၊ ကပ်ဆူလ်၊ မူဝါဒ၊ သော့လှည့်ခြင်း၊ ပြန်လည်ပေးချေခြင်းနှင့် ပြန်လည်ဖြည့်စွက်မှု ကိစ္စများ
- validator နှင့် coordinator ပြန်လည်စတင်ခြင်းအပါအဝင် 2, 3, 4, 8 နှင့် 16 ဒေတာဘေ့စ်များအတွက်စစ်မှန်သော verifier လေး-validator လုပ်ငန်းစဉ်များ၊ စစ်ဆေးထားသော ၅%, ၁၀% နှင့် ၂၀% သတင်းစကားဆုံးရှုံးမှု၊ အဆင့်ပိုင်းခြားခြင်း၊ ပြန်လည်ထူထောင်ခြင်းနှင့် persistence ကန့်သတ်မှု ပျက်စီးမှုများ။
- Torii, P2P, blocks, Kura, snapshots, queries, events, logs, and telemetry အကြားက ကန်နာရီနှင့်ကွဲပြားခြားနားသောသွန်လျှံမှုလေ့လာချက်များ
- အနည်းဆုံးအပူချိန်ငါးခုနှင့် real-network ပါဝင်သူအရေအတွက်ကို တိုင်းတာမှုသုံးဆယ်စုစုပေါင်း, p50, p95, p99, ယုံကြည်မှုအကြားကာလများ, အရင်းအမြစ်များ, ယာဉ်မောင်းနှင်မှု, သက်သေခံနှင့်လက်မှတ်အရွယ်အစားများ, နှင့်ပွင့်လင်းမြင်သာသော AMX ကိုထိန်းချုပ်ခြင်း
- ကျဉ်းမြောင်းတဲ့ အလုပ်ခွင် စမ်းသပ်မှုများ၊ lint နှင့် ဖွဲ့စည်းမှု စစ်ဆေးမှုများ၊ ကြုံရာမျိုးစေ့များ၊ စုပ်ယူခြင်း၊ ပြန်လည်ဖန်တီးနိုင်သော builds များ SBOMs နှင့် လက်မှတ်ထိုးထားသော artefact hashes များ
- တရားဝင် အလွှာ နှစ်ခုစလုံး: ၃/၂၅၅ ခြေထောက်ရေတွက်မှုအချိုးအစား စစ်ဆေးချက်များနှင့် မှန်ကန်သော ၄-validator ကော်မတီစာရင်း N=2 validator-focused အပြည့်အဝသတ်မှတ်ထားသောအမှား၊ စက္ကူ-ပထမဦးဆုံး N=3 မှားယွင်းမှု၊ N=4 clean နှင့် N=3 expiry/replay configurations များ၊ အမှားဘတ်ဂျက်များကိုကော်မတီတစ်ခုစီအတွက် လွတ်လပ်စွာပြုလုပ်သည်။
- အတည်ပြုမှု ဆက်ဆံရေး၊ dummy-slot ရွေးချယ်သူတွေ၊ အရင်းအမြစ်နဲ့ ကပ်ဆူလ် ချည်နှောင်မှု၊ ပြန်လည်ဖြည့်စွက်မှု ဆက်စပ်မှု, လျှို့ဝှက်ဆန်းကြယ်မှုနဲ့ cross-data space state machine တွေကို လွတ်လပ်စွာ စစ်ဆေးပါ။

မူကြမ်းနှင့် သန့်စင်ထားသော အထောက်အထား၊ ခြိမ်းခြောက်မှုမော်ဒယ်၊ ပရိုတိုကောဆွေးနွေးချက်၊ ကန့်သတ်ချက်များ၊ commit ID, hardware သရုပ်ဖော်ချက်နှင့် စစ်ဆေးရေး အစီရင်ခံစာများကို မပြောင်းလဲနိုင်သော DOI ထောက်ပံ့သည့် လက်ရာပစ္စည်းတွင် ထုတ်ဝေပါ။ သိုလှောင်ရုံစမ်းသပ်ခြင်းတစ်ခုတည်းက ဒီ feature ကို ထုတ်လုပ်မှုအရည်အချင်းပြည့်မီတဲ့ CBDC settlement system တစ်ခုသို့ မပြောင်းစေဘူး။

raw fault run နဲ့ latency နမူနာတိုင်းဟာ full release commit ကို SHA-256 ကို ချိတ်ဆက်ပေးရမယ်၊ တစ်ဖွဲ့စည်းထားတဲ့ pinned-hardware သရုပ်ဖော်ချက်ရဲ့ SHA-256 နဲ့ ၎င်းရဲ့ အတိအကျ ပါဝင်သူအရေအတွက် ဖွဲ့စည်းပုံကို ချိတ်ဆက်ရပါမယ်။ N=2,3,4,8,16 ကိုဖုံးအုပ်သော Canonical Configuration Manifesto တစ်ခုကို Archive လုပ်ပါ။ စာရင်းတစ်ခုစီမှာ ထိန်းသိမ်းထားသည့် ဖွဲ့စည်းမှု ဘိုက်များကို ရည်ညွှန်းပြီး ဒေတာနေရာတစ်ခုအတွက် အတည်ပြုသူ ၄ ဦးတိကျစွာ၊ ၃-of-4 quorum နှင့် Mandatory Signed RS16 DA/RBC ကို အာမခံရမည်။ အဆိုပါ release verifier သည်အခြား build၊ hardware profile သို့မဟုတ် network configuration များပေါ်တွင်ထုတ်လုပ်သော summaries ကိုပယ်ဖျက်သည်။ တစ်ဦးချင်းဆုံးရှုံးမှု, phase-cut နှင့် persistence-crash အတန်းတိုင်းသည် SHA-256 -bound အတွင်းမှာကမ္ဘာလုံးအရပြန်လည်အသုံးပြုမည့် တိကျသော JSONL မှတ်တမ်းညွှန်ကြားချက်များကိုလည်းအမည်ပေးရမည်ဖြစ်သည်။ authenticated-controller နဲ့ atomicity-capture artefacts တွေ။ release verifier က ဒီ digests တွေကို ဖြေရှင်းပေးပြီး row တွေဟာ run identification, trial index နဲ့ parameters, controller acknowledgement or recovery result, continuous check count တို့နဲ့ ကိုက်ညီအောင် လုပ်ပေးပါတယ်။ နောက်ပိုင်းထုတ်ဝေမှု p95/p99 နှိုင်းယှဉ်ချက်များသည်လည်း လက်မှတ်ရေးထိုးထားသော အခြေခံအဆင့်ကို ပယ်ချသည်၊ ၎င်း၏ Hardware, Configurations သို့မဟုတ် တိုင်းတာမှုလိုအပ်ချက်များက ပြိုင်ဘက်နှင့် ကွဲပြားသည်။ နောက်ဆုံးစစ်ဆေးသူသည် မှတ်တမ်းတင်ထားသော မူကြမ်းနမူနာများမှ သတင်းထုတ်ပြန်သည့် ရာခိုင်နှုန်းအားလုံး၊ MADs နှင့် သတ်မှတ်ချက်ဆိုင်ရာ ယုံကြည်မှု ကြားကာလများကို သီးခြားချိတ်ဆက်ထားသော စိစစ်ချက်စုဆောင်းချက်အပေါ် မှီခိုခြင်းအစား ပြန်လည်ပြုပြင်သည်။ အလားတူပဲ Canary Manifesto ကို reload လုပ်ပြီး archived privacy မျက်နှာပြင်တိုင်းကို သီးသန့် စကင်လုပ်တယ်၊ ဒီတော့ အစီရင်ခံစာတစ်ခုက file digests တွေ ပြန်လည် ချည်နှောင်ပြီးနောက် ပျိုးထားတဲ့ လျှို့ဝှက် hit ကို ဖိနှိပ်လို့ အများပြည်သူပုံစံများကို ပြန်လည် တွက်ချက်ခြင်းဖြင့် တူညီသည့် အရွယ်အစား တည်ဆောက်မှု လစ်လပ်မှု (သို့) မစုံလင်သော ကွာခြားချက် ဖိုင်ကို ပြန်လည်ရေးသားခြင်းအားဖြင့် ပုန်းကွယ်မရနိုင်ပါ။
