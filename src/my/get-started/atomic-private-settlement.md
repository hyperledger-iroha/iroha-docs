# Atomic Private Cross-Dataspace ဘဏ္ဍာရေး ငွေကြေးငွေပေးချေမှု Settlement ကို Run {#run-atomic-private-cross-dataspace-settlement}

`AtomicPrivateSettlementV1` သည် 2 မှ 255 အထိရှိသော SORA Nexus ဒေတာဘေ့စ်များတွင် လျှို့ဝှက် ငွေကြေးလွှဲပြောင်းမှု အစိတ်အပိုင်းတစ်ခုစီကို ညှိနှိုင်းပြီး ကမ္ဘာ့နိုင်ငံတစ်နိုင်ငံတွင် ငွေကြေး လွှဲပြောင်းမှုအစိတ်အပိုင်းတိုင်းကို အဆုံးသတ်သည်။ ငွေကြေးလွှဲပြောင်းမှုအစိတ်အပိုင်းတစ်ခုမှ ပယ်ချခံရသော၊ သက်တမ်းကုန်ဆုံးသွားသည့် (သို့) ရပ်ဆိုင်းထားသော ဘန်ဒယ်တစ်ခုမှာ အသုံးမပြုပါ။ Transparent Native AMX DvP/PvP သည် သီးခြားပရိုတိုကောလမ်းကြောင်းတစ်ခုဖြစ်နေဆဲဖြစ်သည်။

::: warning လွတ်မြောက်မှုအခြေအနေ
ဤလုပ်ဆောင်ချက်သည် အုပ်ချုပ်မှုဖြင့် ထိန်းချုပ်ထားပြီး မူလအတိုင်း ပိတ်ထားသည်။ Production အသုံးပြုရန် အရည်အချင်းပြည့်မီကြောင်း မသတ်မှတ်ရသေးပါ။ ထိုထုတ်ဝေမှုအတိအကျအတွက် ထုတ်ပြန်ထားသော လုပ်ဆောင်နိုင်မှု၊ ကိုယ်ရေးလုံခြုံမှု၊ ချို့ယွင်းမှု၊ စွမ်းဆောင်ရည်၊ တူညီစွာ ပြန်တည်ဆောက်နိုင်မှု၊ လွတ်လပ်သော စာဝှက်ပညာ ပြန်လည်သုံးသပ်မှုနှင့် artifact ထုတ်ဝေမှုဆိုင်ရာ သတ်မှတ်စစ်ဆေးချက်အားလုံး မအောင်မြင်မချင်း တကယ့် CBDC တန်ဖိုးအတွက် မဖွင့်ပါနှင့်။
:::

## ဒီပရိုတိုကောက ဘာကို ဖုံးကွယ်ထားလဲ။ {#what-the-protocol-hides}

ဘဏ္ဍာရေးလွှဲပြောင်းမှု အစိတ်အပိုင်းတစ်ခုစီမှာ တည်ငြိမ်သော နှစ်ဝင်၊ သုံးထွက် Private-note သက်သေကို အသုံးပြုသည်။ ကော်မတီအတည်ပြုသူများက သက်သေခံချက်နှင့် ပွင့်လင်းမြင်သာမှုမရှိတဲ့ အခြေအနေ ကူးပြောင်းမှုကို စစ်ဆေးကြသည်။ ၎င်းတို့ဟာ ရှင်းလင်းသော စာသားပါတီများ၊ အရင်းအမြစ်များ၊ ငွေကြေးပမာဏများ၊ မှတ်စုများ သို့မဟုတ် စီးပွားရေး ရလဒ်များကို မရရှိပါ။ ခွင့်ပြုထားတဲ့ ဒေသတွင်း စာရင်းစစ်သူက ပိတ်ထားတဲ့ စာရင်းစစ်ဆေးမှုပုဒ်မကို ဖေါ်ထုတ်ပြီး ဒီအထဲမှာ ပါဝင်တာကို စစ်ဆေးပြီး ရည်ရွယ်ချက် သီးခြား အတည်ပြုချက်ကို လက်မှတ်ထိုးပါတယ်။ ပုံမှန် မူဝါဒအရ အုပ်ချုပ်တဲ့ စာရင်းစစ်မှူးစုထံမှ အတည်ပြုချက် တစ်ခုကို လက်ခံတယ်။

အများပြည်သူ ကွန်တိန်နာ ကုန်သွယ်မှုနှင့် ပရိုတိုကော ရလဒ် မှတ်တမ်းမှာ ရည်ရွယ်ချက်ရှိပြီး ဖော်ပြထားပါတယ်-

- ကွန်ရက်နှင့် အစုအဝေး မှတ်သားချက်များ
- ပါဝင်သူ ဒေတာဇုန်လမ်းကြောင်းများနှင့် ပါဝင်သူအရေအတွက်
- အချိန်ကာလနှင့် သက်တမ်းကုန်ဆုံးမှု အမြင့်
- Stable opaque protocol data group identifier များ၊ root များ၊ nullifiers များ၊ cryptographic commitment တန်ဖိုးများနှင့် fixed ciphertext slots များ
- ကော်မတီ ခွင့်ပြုချက် မူဝါဒများနှင့် တိကျသော 3-of-4 ရရှိနိုင်မှု, ပြင်ဆင်ခြင်း, နှင့်ပရိုတိုကောအပြီးသတ်သတ်မှတ်ချက်များ
- ပံ့ပိုးသူ၊ အများသုံးကွန်ရက် အခကြေးနဲ့ terminal status

ဤသည်မှာ ယာဉ်ကြောစီးဆင်းမှု အမည်မဲ့ခြင်းမဟုတ်ဘဲ အကြောင်းအရာ လျှို့ဝှက်ချက်ဖြစ်သည်။ အချိန်ဆွဲခြင်း၊ ပါဝင်သူအရေအတွက်၊ ဒေတာနေရာအသိအမှတ်ပြုမှု၊ တည်ငြိမ်တဲ့စုပေါင်းလုပ်ဆောင်မှုက အများပြည်သူအဖြစ် ကျန်ရှိနေသည်။ တစ်ခုတည်းသော CBDC ကို တည်းခိုထားသည့် ဒေတာဇုန်တစ်ခုသည် စာလုံးဝင်လက်ရှိ asset ID မထုတ်ဝေသော်လည်းလည်း လမ်းကြောင်းမှ asset ကိုဖယ်ရှားနိုင်စေနိုင်ပါတယ်။

## အသုံးချမှု လိုအပ်ချက်များ {#deployment-requirements}

မဖွင့်ခင် operator တွေဟာ အောက်ပါအချက်တွေအားလုံးကို လိုအပ်ပါတယ်။

1. ပါဝင်တဲ့ ဒေတာနေရာတိုင်းအတွက် အတိအကျ validator လေးခုရှိပြီး ကွဲပြားခြားနားသော BLS သဘောတူညီချက် ခလုတ်များနှင့် ပိုင်ဆိုင်မှု သက်သေခံများရှိသည်။
2. လိုအပ်တဲ့ Sumeragi DA/RBC ကို အမြင့်တိုင်းအတွက် လုပ်နိုင်သည်။
3. စီမံခန့်ခွဲထားသော လျှို့ဝှက်ငွေကြေး ငွေချေးမှု ဖြေရှင်းရေး ပရိုတိုကောဒေါင် အချက်အလက် အုပ်စုနှင့် ဒေတာနေရာတိုင်းတွင် မူလ root ကို
4. Active V1 private note capability နှင့် သီးခြားငွေကြေး ငွေပေးချေမှု ဖြေရှင်းမှု သက်သေပြရေး ပရိုဖိုင်
5. အနည်းဆုံး စည်းကမ်းထားသော ဒေသခံ `PrivateSettlementAuditPolicyV1` တစ်ခု၊ သီးခြားအော်ဒီတာ လက်မှတ်ထိုးခြင်းနှင့် ဟိုက်ဘရစ်ကုဒ်ရေးရာ သော့များ၊ အဓိကခေတ်ကာလ၊ အမြင့် သက်တမ်းနှင့် ခွင့်ပြုချက် တံခါးကိုပါ ၀ င်သည်။
6. ပြင်ဆင်ထားသော ထိန်းသိမ်းမှု ကာလအတွက် လုံလောက်တဲ့ ပုဂ္ဂလိက အထောက်အကူ မှတ်တမ်း သိုလှောင်ခြင်း
7. နောက်ဆုံး အများပြည်သူ ကွန်တိန်နာ ငွေပေးချေမှုကို တင်ပြနိုင်သော ဘက်လိုက် ပံ့ပိုးရေး အကောင့်

Auditor တစ်ဦးသည် validator ကိုလည်း လည်ပတ်နိုင်သော်လည်း consensus၊ auditor လက်မှတ်ထိုးမှုနှင့် auditor စာဝှက်မှုတို့အတွက် သီးခြားကီးများ သုံးရမည်။ စည်းမျဉ်းအရ ထိန်းသိမ်းရမည့် ကာလအတွင်း အနားပေးထားသော စာဝှက်ဖြည်ကီးများကို ထိန်းသိမ်းပါ။ သို့မဟုတ် ထိုကီးများကို အနားမပေးမီ capsule များကို ကီးအသစ်ဖြင့် ပြန်ထုပ်ပိုးခြင်းအား အုပ်ချုပ်မှုအရ အတည်ပြုပြီး စမ်းသပ်ပါ။

၄ validator ခွင့်ပြုချက် မူလအချက်အလက်သည် client ကမပေးထားသော state anchored ဖြစ်ပါသည်။ Technical Manifesto `authority_context_height` တွင် validator တစ်ခုချင်းစီကညီညွတ်မှုအခြေအနေမှအတိအကျသတ်မှတ်ထားသော lane / datapace roster နှင့် active execution lane incarnation ကိုဖြေရှင်းသည်။ ဖြေရှင်းသည့်အမြင့်ကိုသင့်တော်စေရန်လိုအပ်သည်။ BLS သော့လေးလုံးနဲ့ ပိုင်ဆိုင်မှု သက်သေခံချက်တွေကို စစ်ဆေးပါတယ်။ Upload, Prepare နဲ့ Final Protocol Result Record admits အားလုံးဟာ သမိုင်းဝင် ခွင့်ပြုချက် မူဝါဒကိုပဲ သုံးတယ်။

## Admission ကို Configure လုပ်ပါ။ {#configure-admission}

ထုတ်လုပ်မှုအပြုအမူအားလုံးသည် node ဖွဲ့စည်းချက်မှလာသည်။ ပတ်ဝန်းကျင်ပြောင်းလဲနိုင်သူများက ဤလမ်းကြောင်းကို တက်ကြွမပေးနိုင်ပါ။ ပို့ဆောင်သော default သည် `enabled = false` ဖြစ်သည်၊ feature ကိုပိတ်ထားခြင်းအားဖြင့် settlement-specific ဖွဲ့စည်းမှုတစ်ခုမျှ မလိုပါ။

အုပ်ချုပ်ရေးမှူးက လိုအပ်တဲ့ အရည်အသွေးကို မှတ်တမ်းတင်ပြီးနောက်၊ သင့်တော်သော အသိပေးချက်ဖြင့် တက်ကြွမှု အမြင့်တစ်ခုကို ရွေးချယ်ပြီးနောက်၊ သက်ဆိုင်ရာ node တစ်ခုစီကို စနစ်တကျ ညွှန်ကြားပါ။

```toml
[nexus.atomic_private_settlement]
enabled = true
activation_height = 500000
minimum_activation_notice_blocks = 7200
proof_profile_version = 1
max_participants = 255
max_expiry_blocks = 7200
audit_timeout_blocks = 1200
prepare_timeout_blocks = 1200
commit_timeout_blocks = 1200
capsule_padding_classes_bytes = [4096, 16384, 65536, 262144]
max_proof_bytes = 8388608
max_capsule_bytes = 1048576
max_carrier_bytes = 4194304
sidecar_retention_blocks = 1000000
sidecar_max_records = 256
sidecar_max_total_bytes = 3221225472
default_min_auditor_approvals = 1
permitted_policy_versions = [1]
```

ဥပမာမှာ သယ်ဆောင်ပို့တဲ့ V1 ကန့်သတ်ချက်တွေကို သုံးပြီး စွမ်းဆောင်ရည်ဆိုင်ရာ အကြံပြုချက်မဟုတ်ပါဘူး။ စီမံခန့်ခွဲမှု နယ်နိမိတ်တွေကို ရွေးချယ်ခင် ရည်ရွယ်ထားတဲ့ Hardware ကို သုံးဆင့် အချိန်ဖြတ်တောက်ချက်တွေဟာ `max_expiry_blocks` အတွင်းမှာ တပ်ဆင်ထားရပြီး အထောက်အကူ မှတ်တမ်း ထိန်းသိမ်းမှုဟာ အနည်းဆုံး သက်တမ်းကုန်ဆုံးတဲ့ ပြတင်းပေါက် ဖြစ်ရပါမယ်။

`max_capsule_bytes` သည် `PrivateSettlementAuditCapsuleV1` တစ်ခုလုံး၏ စံ Norito encoding ကို ကန့်သတ်သည်။ AAD၊ nonce၊ စာဝှက်ဒေတာ၊ vector ဘောင်ဖွဲ့စည်းမှု၊ auditor အထောက်အထားများနှင့် ထုပ်ပိုးထားသော DEK အတန်းတိုင်း ပါဝင်သည်။ စာဝှက်ဒေတာသက်သက်၏ ကန့်သတ်ချက် မဟုတ်ပါ။ ပြင်ဆင်သတ်မှတ်ထားသော ဖြည့်တင်းမှုအတန်းတစ်ခုစီသည် အနည်းဆုံး auditor `default_min_auditor_approvals` ဦးအတွက် သတိထားတွက်ထားသော capsule တစ်ခုလုံး၏ envelope အတွင်း ဆံ့ရမည်။ Torii သည် `min_approvals` က အုပ်ချုပ်မှုသတ်မှတ်ထားသော အနိမ့်ဆုံးအောက် ရှိသည့် အသစ်လက်ခံမည့် မူဝါဒကိုလည်း ငြင်းပယ်ပြီး စံ encoding အပြည့်အစုံ အရွယ်အစားကြီးလွန်းသော capsule မှန်သမျှကို ငြင်းပယ်သည်။

`max_carrier_bytes` က ပရိုတိုကော တစ်ခုတည်းသော စံသတ်မှတ်ချက်အရ ထောက်ခံသူလက်မှတ်ထိုးထားတဲ့ ငွေပေးချေမှု အပြည့်အဝကို ကန့်သတ်ထားပြီး အာမခံစာအုပ်တင်မကပဲ မှတ်ပုံတင်ညွှန်ကြားချက်ကိုပါ ၀ င်ပါတယ်။ ဖွဲ့စည်းပုံ၊ ငွေပေးချေမှု ခွင့်ပြုချက် အရင်းအမြစ်နှင့် မီတာဒေတာများ၊ အခွန် ရည်ရွယ်ချက်နှင့် လက်မှတ်ရေးထိုးခြင်း။ သာမန်ကွန်ရက် ငွေလဲလှယ်မှု ကန့်သတ်ချက်များသည် လွတ်လပ်သော အထက်နိမိတ်တစ်ခုအဖြစ် ဆက်လက်လုပ်ဆောင်သည်။

Activation ကို မပိတ်နိုင်ပါက ထိန်းချုပ်ထားသော အရည်အသွေးသည် တက်ကြွနေမှသာ၊ ၎င်း၏အခြေအနေနှင့် တက်ကြွမှု အမြင့်များသည် ကြေညာချက်ကာလကို ဖြည့်ဆည်းပေးခြင်းမရှိဘဲ၊ စုစည်းထားသည့် သက်သေပြရေး ပရိုဖိုင် V1 နှင့် လက်ရှိ ချိတ်ဆက်ထားတဲ့ ပရိုတိုကောလစ် အချက်အလက်အုပ်စုနှင့် စစ်ဆေးရေး မှတ်တမ်းများ မရှိပါ။ ဖွဲ့စည်းမှု အလံကို သက်ဝင်အောင်လုပ်ခြင်းတစ်ခုတည်းဟာ မလုံလောက်ပါ။

## ငွေရေးကြေးရေးလုပ်ငန်းများ ဖြေရှင်းမှု လုပ်ငန်းစဉ် {#settlement-workflow}

ဖောက်သည်က သက်သေခံချက်များနှင့် ကုဒ်သွင်းထားသော ကပ်ဆူလ်များကို ဒေသတွင်းတွင် တည်ဆောက်သည်။ လျှို့ဝှက်သက်သေများသည် ဒေသခံငွေကြေးစာရင်း (သို့) ဒေသခံအလုပ်သမားအတွင်းမှာနေရမည်ဖြစ်ပြီး လျှောက်လွှာမှတ်တမ်းများ၊ Python အရာဝတ္ထုများ, HTTP တောင်းဆိုချက်များ သို့မဟုတ် ရေရှည်တည်တံ့သည့် ညှိနှိုင်းရေး မှတ်တမ်းများသို့ serialize မလုပ်ရပါ။

Capsule နဲ့ auditor တစ်ခုချင်းအတွက် DEK ပိတ်ထားတဲ့ စစ်ဆေးတဲ့ အချက်အလက်တွေထဲမှာ နိုင်ငံတော်မှာ ခိုင်မာတဲ့ ကော်မတီနဲ့ `authority_context_height` တို့ရဲ့ cryptographic digest value အပါအဝင် network၊ route/incarnation တွေလည်း ပါဝင်ပါတယ်။ ဘက်ဒယ်၊ ငွေကြေးလွှဲပြောင်းမှု အပိုင်း၊ မူဝါဒ၊ သော့ခေတ်နှင့် ရှင်းလင်းသော စာသား cryptographic commitment တန်ဖိုး။ ပိတ်ထားသော သော့ကို အခြားစာရင်းသို့ (သို့) သမိုင်းဝင် ခွင့်ပြုချက် အဓိက အခြေအနေသို့ မပြောင်းနိုင်ပါ။

အစီရင်ခံစာစံညွှန်း ငွေကြေးလွှဲပြောင်းမှု အစိတ်အပိုင်းတစ်ခုစီအတွက် ညှိနှိုင်းရေးမှူးက ဒီအစဉ်ကို လုပ်ဆောင်သည်။

1. ယာယီ ကုဒ်သွင်းထားတဲ့ ပစ္စည်းကို validator လေးခုစလုံးမှာ တင်ပြီး single protocol-standard exact 3-of-4 availability certificate ကို ရယူပါ။
2. ခွင့်ပြုထားတဲ့ စာရင်းစစ်သူတစ်ဦးက ၎င်းရဲ့ ကပ်ဆူးကိုယူပြီး ဖေါ်ထုတ်ပေးပါ၊ အများပြည်သူ ချုပ်ဆိုချက်တွေကို ပြန်လည် တွက်ချက်၊ ဒေသဆိုင်ရာ မူဝါဒကို လိုက်နာကာ အတည်ပြုချက်ကို တင်ပြပါ။
3. အတည်ပြုသူ ၄ ဦးမှ မဲများကို ပြင်ဆင်ပါ။ အတည်ပြုသူများတိုင်းက မဲမပေးမီ ဒယ်လ်တာကို သီးသန့်စစ်ဆေးပြီး ရေရှည်တည်တံ့စွာ အဆင့်သတ်မှတ်သည်။ အဆင့်သတ်မှတ်သူတိုင်းအတွက် Single Protocol-Standard 3-of-4 Prepare Certificate ကို ဆက်လက်ထားပါ။
4. ငွေလွှဲပြောင်းမှု အစိတ်အပိုင်းတိုင်းမှာ Prepare Certificate ရှိပြီးနောက် မပြောင်းလဲနိုင်သော Complete Prepare Barrier ကို တည်ဆောက်ပါ။ Single Protocol-Standard 3-of-4 Protocol Finalisation Certificates တွေကို တောင်းဆိုကာ ဆက်လက်တည်ရှိပါ။ ညှိနှိုင်းရေးမှူးက ပြန်လည်စတင်ပါက ဒေသတွင်း တည်ငြိမ်သော Prepare နှင့် Consensus Finalisation Certificates များအတွက် ပါဝင်သူ node များကို မေးမြန်းပြီး single protocol-standard quorum-equivalent certification ကိုရွေးချယ်ပြီး ဆက်မလုပ်ခင်ပြန်ဖြန့်ချိပါ။ ဘယ်တော့မှ စစ်ဆေးခြင်းမရှိတဲ့ ဒေသတွင်း cache ကနေ Certificate တစ်ခုကို ပြန်လည်တည်ဆောက်ခြင်း။
5. Technical Manifesto Sponsor လက်မှတ်ထိုးပြီး တစ်ကမ္ဘာလုံး container ကုန်သွယ်မှု တစ်ခုကို အတိအကျတင်ပေးပါ။ container transaction မှာ တစ်ခုပါဝင်ပါတယ်။ `FinalizeAtomicPrivateSettlementV1` ညွှန်ကြားချက်နှင့် အတိအကျအပြည့်အဝ Certified Bundle ကို. WSV pre-flight တိုင်းတာမှု မှတ်ပုံတင်ညွှန်ကြားချက် ဖွဲ့စည်းခြင်းအပါအဝင် type-erased အပြီးသတ်ရေး ညွှန်ကြားချက်တစ်ခုလုံး။ Torii နောက်ပြီး ဗဟိုမှာရှိတဲ့ One-Shot Container Transaction ကို ချုပ်ဆိုဖို့ အာဏာပေးတယ်။ `max_carrier_bytes` ပရိုတိုကော တစ်ခုတည်းသော စံနှုန်းဖြင့် ထောက်ခံသူ လက်မှတ်ရေးထိုးထားသည့် ငွေပေးချေမှုအပေါ်၊ ခွင့်ပြုချက် အရင်းအမြစ်၊ မီတာဒေတာ၊ အခွန် ရည်ရွယ်ချက်နဲ့ လက်မှတ်ပါ ၀ င်ပါတယ်။ Torii Container Transaction ကို ခွင့်ပြုချက်ရဲ့ အဓိက အခြေအနေမတိုင်မီမှာ ပယ်ချလိုက်ပါတယ်။ နောက်ဆုံးဝင်ရောက်မှု အမြင့်ချိန်မှာ (သို့) ပြီးဆုံးပြီးနောက်၊ သက်တမ်းကုန်ဆုံးတဲ့အခါမှာ အဆုံးသတ်နိုင်တာ (သို့) သတ်မှတ်ထားတဲ့ သက်တမ်းကုန်လွန်တဲ့ ကာလပါ။
6. ကမ္ဘာလုံးဆိုင်ရာ အပြီးသတ်မှုအထိ အများပြည်သူ ဘန်ဒယ်အခြေအနေနှင့် ပရိုတိုကော ရလဒ်မှတ်တမ်းကို မေးမြန်းပါ။ ဒေသတွင်း အထောက်အပံ့ မှတ်တမ်းအခြေအနေကို မပြောင်းလဲနိုင်တဲ့ ကမ္ဘာလုံးဆိုင်ရာ နောက်ဆုံးမှတ်တမ်းကို ညှိမပေးတဲ့အထိ ယာယီအဖြစ် ဆက်ဆံပါ။

Rust ဖောက်သည်သည်က `certify_and_upload_private_settlement_legs_v1`, `prepare_private_settlement_bundle_v1`, `commit_private_settlement_bundle_v1` နှင့် `submit_private_settlement_bundle_v1` တို့အပါအဝင်နည်းလမ်းများဖြင့် ဤစီးဆင်းမှုကို ဖော်ထုတ်သည်။ Restart-safe ကိုော်ဒင်းရှင်းကို အသုံးပြုခြင်းအားဖြင့် `recover_or_prepare_private_settlement_bundle_v1` နှင့် `recover_or_commit_private_settlement_bundle_v1` တို့ဖြစ်သည်။ ကော်မတီနဲ့ စာရင်းစစ်သူတွေရဲ့ နည်းပညာဖောက်ပြန်ချက်တွေမှာ ကျယ်ပြန့်တဲ့ အခန်းကဏ္ဍ မှတ်ပုံတင်အချက်အလက်တွေ လိုအပ်ပြီး သာမန်စာရင်းအတွက် cryptographic signer ကို ပြန်လည်အသုံးပြုခြင်း မရှိပါဘူး။

## Auditor Policy ကို လုံခြုံစွာ Rotate လုပ်ပါ။ {#rotate-an-auditor-policy-safely}

Privacy-Governance-authorized `RotatePrivateSettlementPoolPolicyV1` ညွှန်ကြားချက်ကိုအသုံးပြုပါ။ ၎င်းသည်အတိအကျလက်ရှိ အုပ်ချုပ်မှု cryptographic digest တန်ဖိုးကိုဖော်ပြရမည်၊ လမ်းကြောင်းတစ်ခုတည်း၊ ပရိုတိုကုတ်ဒေတာအုပ်စုနှင့် အရင်းအမြစ်ဘောင်သတ်မှတ်သော cryptographic commitment တန်ဖိုးကို ထိန်းထားရမည်။ အုပ်ချုပ်မှု ပြန်လည်သုံးသပ်မှုကို တစ်ဆင့်တိုးမြှင့်ရမည်။ မူဝါဒ/အုပ်ချုပ်မှု အမျိုးမျိုးသော cryptographic digests များကို အသုံးပြုပြီး rotation ကိုပါ ၀ င်သည့် block တွင် activate လုပ်ပါ။ replay set များနှင့် နောက်ဆုံးသတ်မှတ်ထားသော protocol ရလဒ် မှတ်တမ်းများကို သိမ်းဆည်းထားသည်။ rotation ၏ activation အမြင့်တွင်တူညီသော route / pool ကိုထိတွေ့သည့် protocol ရလဒ်မှတ်တမ်းကို မပါ ၀ င်ပါ။ ညွှန်ကြားချက်သည် ထိုနယ်နိမိတ်ကို ငြင်းပယ်သည်။

Public Protocol Data Group Projection သည်မူဝါဒ-ပြင်ဆင်မှု မျိုးရိုးစဉ်တစ်ခုလုံးကို အစားထိုးထားသည်။ လည်ပတ်ခြင်းမတိုင်မီ နောက်ဆုံးပြုလုပ်သော ပရိုတိုကောရ် ရလဒ်မှတ်တမ်းသည် ပြန်လည်စတင်ပြီးနောက်မှာ သက်ဝင်ဆဲဖြစ်ပြီး တိကျတဲ့ ပရိုတိုကိုရလဒ်မှတ်တမ်းကိုပြန်လည်ကစားခြင်းသည် မဖြစ်နိုင်သေးပါ။ မပြီးသေးတဲ့ အလုပ်ကို မျိုးရိုးစဉ်က ခွင့်မပြုဘူး။ တက်ကြွမှု နယ်နိမိတ်ဖြတ်တဲ့ မူဝါဒဟောင်းတစ်ခုခုဟာ ကမ္ဘာလုံးဆိုင်ရာ အခြေအနေပြောင်းလဲခြင်းမတိုင်မီ ပိတ်နိုင်ပါ။ သိုလှောင်ထားသော ကပ်ဆူးတွေကို ဖွင့်ရန်လိုအပ်တဲ့ ရှေးဟောင်း ကုဒ်ဖေါ်ထုတ်ရေး သော့အားလုံးကို ထိန်းသိမ်းပါ၊ (သို့) မဖျက်ဆီးခင် အုပ်ချုပ်ပြီး စမ်းသပ်ထားတဲ့ ကပ်ဆူကို ပြန်လည်ဖြည့်စွက်ပါ။

## ကျရှုံးမှုနှင့် ပြန်လည်ထူထောင်ခြင်း {#failure-and-recovery}

မလုံလောက်တဲ့ (သို့) ခေတ်နောက်ကျနေတဲ့ စာရင်းစစ်သူ အတည်ပြုချက်တွေ၊ သုံးခုထက်မနည်းသော validator မဲများ၊ မှားယွင်းတဲ့ အမြစ်တွေ (သို့မဟုတ်) ရာသီဥတုများ၊ duplicate nullifiers, အစားထိုးထားတဲ့ အထောက်အထား (သို့) capsules တွေ၊ တရားဝင်မဟုတ်တဲ့ ငွေကြေး ငွေလွှဲပြောင်းမှု အပိုင်းအခြား၊ သက်တမ်းကုန်ဆုံးနေတဲ့ ဘက်ဒယ်များနဲ့ မညီမျှတဲ့ ပြန်ဆပ်နှုန်း သတ်မှတ်ချက်တွေဟာ ကမ္ဘာလုံးဆိုင်ရာ ဗီဇပြောင်းလဲခြင်းမတိုင်ခင် ကျရှုံးသွားပါတယ်။ သဘောတူညီချက် နောက်ဆုံးသတ်မှတ်ချက်တွေက ဘယ်တော့မှ ပုဂ္ဂလိကပြည်နယ်ကို ပြောင်းလဲတာမဟုတ်ဘူး။

Validator များသည် အကူအညီမှတ်တမ်းများ၊ အဆင့်သတ်မှတ်ထားသော deltas များနှင့်အဆင့်အမှတ်ပြုချက်များကို အသိအမှတ်မပြုမီကတည်းက sync လုပ်သည်။ ပြန်လည်စတင်ခြင်းတွင် single protocol-standard ရေရှည်မှတ်တမ်းများမှ ကန့်သတ်ချက်များကိုပြန်လည်တည်ဆောက်ပြီးနောက် မပြောင်းလဲနိုင်သော ကမ္ဘာ့ပရိုတိုကော ရလဒ် မှတ်တမ်းများ၊ abort markers သို့မဟုတ် သက်တမ်းကုန်ဆုံးမှုများကို ညှိနှိုင်းပေးသည်။ ကြီးကြပ်ခံရတဲ့ reconciller ကလည်း terminal retention cutting ကို synchronously observed authoritative height မှာ ပြုလုပ်တယ်ဆိုရင်တောင် reconciling လုပ်ဖို့ terminal candidate မရှိတဲ့အခါမှာပဲ အချိုးအစားအမှားတစ်ခုကြောင့် ပိတ်မသွားနိုင်ပါ။ ခိုင်မာတဲ့ ကမ္ဘာလုံးဆိုင်ရာ terminal record တစ်ခုတည်းက အဆင့်သတ်မှတ်ထားတဲ့ lock တွေကို ထုတ်လွှတ်တယ်။ တူညီတဲ့ နောက်ဆုံးသတ်မှတ်ထားတဲ့ protocol ရလဒ် မှတ်တမ်းတစ်ခုကို ပြန်လည်ကစားခြင်းဟာ မဖြစ်နိုင်ပါဘူး။ ဝိရောဓိရှိတဲ့ ပြန်လည်ကစားမှုက သတ်မှတ်ချက်အရ ကျရှုံးပါတယ်။

ကြိုတင်သီးသန့်ယူထားမှု၏ အထောက်အထားတွင် လမ်းကြောင်းအပြည့်အစုံ ပါဝင်သည်။ Pool ထိပ်မှတ်များသည် `(route, pool_id, epoch, root)`၊ nullifier များသည် `(route, pool_id, nullifier)`၊ အထွက်များသည် `(route, pool_id, commitment)` ကို သုံးသည်။ အခြားလမ်းကြောင်းပေါ်ရှိ တူညီသော မဖော်ထုတ်နိုင်သည့် တန်ဖိုးများသည် သီးခြားဖြစ်သည်။ လမ်းကြောင်းအတိအကျ တိုက်မိမှုသည် ပြန်စတင်ပြီးနောက်လည်း ပိတ်လှောင်ထားဆဲ ဖြစ်သည်။

လည်ပတ်ရေး သတိပေးချက်များသည် မဖော်ထုတ်နိုင်သည့် bundle၊ လမ်းကြောင်း၊ အဆင့်၊ digest၊ အမြင့်နှင့် အကြောင်းရင်းအတန်း အကွက်များကိုသာ သုံးသင့်သည်။ စာဝှက်ဖြည်ထားသော capsule များ၊ အကောင့် သို့မဟုတ် ပိုင်ဆိုင်မှုအမှတ်အသားများ၊ ပမာဏများ၊ မှတ်စုများ၊ view ဒေတာ၊ proof သက်သေဒေတာများ သို့မဟုတ် parser payload များကို log၊ ဖြစ်ရပ်၊ metric အညွှန်း သို့မဟုတ် tracing span များတွင် မည်သည့်အခါမျှ မထည့်ပါနှင့်။

## အစစ်တန်ဖိုးမတိုင်မီ အရည်အသွေး {#qualification-before-real-value}

သင်ဖြန့်ချိဖို့ရည်ရွယ်တဲ့ တိကျတဲ့ build နဲ့ configuration အတွက် အောက်ပါအချက်အလက်တွေကို ဖုံးအုပ်ထားပါ။

- ပဋိပက္ခသက်သေ၊ ကပ်ဆူလ်၊ မူဝါဒ၊ သော့လှည့်ခြင်း၊ ပြန်လည်ပေးချေခြင်းနှင့် ပြန်လည်ဖြည့်စွက်မှု ကိစ္စများ
- validator နှင့် coordinator ပြန်လည်စတင်ခြင်းအပါအဝင် 2, 3, 4, 8 နှင့် 16 ဒေတာဘေ့စ်များအတွက်စစ်မှန်သော verifier လေး-validator လုပ်ငန်းစဉ်များ၊ စစ်ဆေးထားသော ၅%, ၁၀% နှင့် ၂၀% သတင်းစကားဆုံးရှုံးမှု, အဆင့်ပိုင်းခြားခြင်း၊ ပြန်လည်ထူထောင်ခြင်းနှင့် persistence ကန့်သတ်မှု ပျက်စီးမှု
- Torii၊ P2P၊ ဘလော့ခ်များ၊ Kura၊ snapshot များ၊ query များ၊ ဖြစ်ရပ်များ၊ log များနှင့် telemetry တစ်လျှောက် canary နှင့် ကွဲပြားမှုနှိုင်းယှဉ် သတင်းအချက်အလက်ပေါက်ကြားမှု စိစစ်ခြင်း
- အနည်းဆုံးအပူချိန်ငါးခုနှင့် real network ပါဝင်သူအရေအတွက်ကို တိုင်းတာမှုသုံးဆယ်စုပေါင်း, p50, p95, p99, ယုံကြည်မှု ကြားကာလများ, အရင်းအမြစ်များ, ယာဉ်မောင်းနှင်မှု၊ သက်သေခံချက်နှင့်ပရိုတိုကောလစ်ရလဒ်မှတ်တမ်းအရွယ်အစားများ, နှင့် ပွင့်လင်းမြင်သာသော AMX ကိုထိန်းချုပ်ခြင်း
- ကျဉ်းမြောင်းတဲ့ လုပ်ငန်းခွင် စမ်းသပ်မှုတွေ၊ ခေါက်ဆွဲနဲ့ ဖွဲ့စည်းချက် စစ်ဆေးမှု၊ ကြုံရာမျိုးစေ့၊ စုပ်ယူခြင်း၊ ပြန်လည်ဖန်တီးလို့ရတဲ့ builds SBOMs နဲ့ လက်မှတ်ထိုးထားတဲ့ artefact cryptographic hashes တွေ
- ပုံစံကျသက်သေပြ အလွှာနှစ်ခုလုံး - အပိုင်း 3/255 ခု၏ အရေအတွက်ညီမျှမှု စစ်ဆေးချက်များနှင့် validator လေးခု အတိအကျပါသော ကော်မတီအလိုက် အညွှန်းသတ်မှတ်သည့် N=2 validator အဓိကစစ်ဆေးမှု၊ ကန့်သတ်ချို့ယွင်းမှု အပြည့်အစုံ၊ စာတမ်းအဓိက N=3 ချို့ယွင်းမှု၊ N=4 ချို့ယွင်းမှုမရှိခြင်းနှင့် N=3 သက်တမ်းကုန်/ပြန်လည်လုပ်ဆောင်မှု ပြင်ဆင်သတ်မှတ်ချက်များ။ ကော်မတီတစ်ခုစီ၏ ချို့ယွင်းမှုဘတ်ဂျက်သည် သီးခြားဖြစ်ရမည်။
- အတည်ပြုမှု ဆက်ဆံရေး၊ dummy-slot ရွေးချယ်သူတွေ၊ အရင်းအမြစ်နဲ့ ကပ်ဆူလ် ချည်နှောင်မှု၊ ပြန်လည်ဖြည့်စွက်မှု ဆက်စပ်မှု, လျှို့ဝှက်ဆန်းကြယ်မှုနဲ့ cross-data space state machine တွေကို လွတ်လပ်စွာ စစ်ဆေးပါ။

ရိုးရိုးနှင့် သန့်စင်ထားသော အထောက်အထားများ၊ ခြိမ်းခြောက်မှုပုံစံများ၊ ပရိုတိုကော ဆွေးနွေးချက်များ၊ ကန့်သတ်ချက်များ၊ အရင်းအမြစ်ကုဒ် ပြင်ဆင်ရေး ID များ၊ ဆော့ဝဲ သရုပ်ဖော်ချက်များ နှင့် စစ်ဆေးမှု အစီရင်ခံစာများကို မပြောင်းလဲနိုင်သော DOI ထောက်ပံ့ထားတဲ့ လက်ရာပစ္စည်း။ မှတ်ပုံတင် စမ်းသပ်မှုတစ်ခုတည်းက ဒီ feature ကို ထုတ်လုပ်မှု အရည်အချင်းရှိတဲ့ CBDC ငွေကြေးငွေပေးချေမှု စနစ်အဖြစ် မပြောင်းဘူး။

နောက်ဆုံးရှင်းလင်းတဲ့ Iroha checkout ကနေ လွတ်မြောက်မှု အရင်းအမြစ် စာရင်းကို ဖန်တီးပြီး အဲဒီ checkout အပြင်မှာ ရှိပြီးသား bundle root ကို တံဆိပ်ခတ်ပါ။

```sh
python3 scripts/private_settlement_source_evidence.py \
  --repository-root . \
  --bundle-root /absolute/path/to/release-bundle
```

ထုတ်လုပ်သူက ရိုက်ကူးမှုအတွင်းမှာ ပွဲတင်ထားတဲ့၊ ပွဲတင်မထားတဲ့၊ ခြေရာခံမထားတဲ့ (သို့) ပေါင်းစပ်မထားတဲ့ ဖိုင်တွေနဲ့ အရင်းအမြစ်ပြောင်းတာတွေကို ကျရှုံးစေတယ်။ ၎င်းသည် raw source-code revision object ကို ထိန်းသိမ်းထားပြီး single protocol-standard Git tree inventory, တိကျတဲ့ binary path list, deterministic source seal နဲ့ `Cargo.lock`; လက်ရာထုတ်ပြန်ချက်တိုင်းကို ၎င်းရဲ့ JSON နောက်ဆုံးထုတ်ပြန်မှုဆိုင်ရာ အထောက်အထားကို ထုတ်ပေးသည်။ DOI- အစုအဝေး စစ်ဆေးသူ (သို့) ပြင်ပ ထုတ်လွှတ်မှုဂိတ်တစ်ခုခု။

အရင်းအမြစ် တံဆိပ်ဟာ သယ်ဆောင်နိုင်ပြီး ပိတ်ထားခြင်းမရှိပါ။ ထုတ်လုပ်သူနဲ့ နောက်ဆုံး စစ်ဆေးသူက သိမ်းဆည်းထားတဲ့ symlink graph တစ်ခုလုံးကို ဖြေရှင်းပေးတယ်၊ ဒီတော့ root ထဲမှာ ပေါ်ပေါက်ပေမဲ့ အခြား link တစ်ခု၊ စက်ဝန်းတစ်ခု၊ `.git` ဖြတ်သန်းမှု (သို့) Windows ပုံစံ ရည်မှန်းချက်တစ်ခုကနေ လွတ်မြောက်တဲ့ link ကို link တွေမဖန်တီးခင် ပယ်ချပါတယ်။ Structured source နဲ့ gate reports တွေကို cryptographic digest value နဲ့ length က release technical manifest နဲ့ ကိုက်ညီတဲ့ bounded stable files တွေကနေပဲ parsed လုပ်ထားပြီး source payload အမျိုးအစားတိုင်းဟာ တစ်ကြိမ်သာ ဖြစ်ပေါ်ရပါမယ်။

ချို့ယွင်းမှုစမ်းသပ်မှု အကြမ်းတစ်ကြိမ်စီနှင့် latency နမူနာတစ်ခုစီသည် ထုတ်ဝေမှု commit အပြည့်အစုံ၊ ဖွဲ့စည်းပုံသတ်မှတ်ထားသော ပုံသေသတ်မှတ်ထားသော hardware ဖော်ပြချက်တစ်ခု၏ SHA-256 နှင့် ပါဝင်သူအရေအတွက် ပြင်ဆင်သတ်မှတ်ချက်အတိအကျ၏ SHA-256 တို့ကို ချည်နှောင်ရမည်။ N=2,3,4,8,16 ကို လွှမ်းခြုံသော စံပြင်ဆင်သတ်မှတ်မှု manifest တစ်ခုကို မော်ကွန်းတင်ပါ။ မှတ်တမ်းတစ်ခုစီသည် ထိန်းသိမ်းထားသော ပြင်ဆင်သတ်မှတ်မှု byte များကို ညွှန်းပြီး data space တစ်ခုစီ၌ validator လေးခုအတိအကျ၊ 4 ခုမှ 3 ခု quorum နှင့် မဖြစ်မနေ လက်မှတ်ထိုးထားသော RS16 DA/RBC ရှိကြောင်း အတည်ပြုရမည်။ ထုတ်ဝေမှုစစ်ဆေးသူသည် မတူသော build၊ hardware ပရိုဖိုင် သို့မဟုတ် ကွန်ရက်ပြင်ဆင်သတ်မှတ်မှုဖြင့် ထုတ်ထားသော အနှစ်ချုပ်များကို ငြင်းပယ်သည်။ ဆုံးရှုံးမှု၊ အဆင့်ကြားဖြတ်မှုနှင့် သိမ်းဆည်းမှုအတွင်း crash ဖြစ်မှု အတန်းတစ်ခုစီသည် SHA-256 ဖြင့် ချည်နှောင်ထားသော စစ်မှန်ကြောင်းအတည်ပြု controller နှင့် ခွဲခြားမရမှုဖမ်းယူရေး artifact များအတွင်းရှိ ကမ္ဘာလုံးဆိုင်ရာ ပြန်သုံးမရသည့် JSONL မှတ်တမ်းအတိအကျ ကိုးကားချက်များကိုလည်း အမည်ဖော်ပြရမည်။ ထုတ်ဝေမှုစစ်ဆေးသူသည် ထို digest များကို ဖြေရှင်းပြီး အတန်းများက စမ်းသပ်လုပ်ဆောင်မှု အထောက်အထား၊ စမ်းသပ်ကြိမ်အညွှန်းနှင့် ပါရာမီတာများ၊ controller အသိအမှတ်ပြုချက် သို့မဟုတ် ပြန်လည်ရယူမှုရလဒ်၊ ဆက်တိုက်စစ်ဆေးမှုအရေအတွက်၊ တစ်စိတ်တစ်ပိုင်း မြင်နိုင်မှုနှင့် သုံးစွဲနိုင်မှု တွေ့ရှိချက် သုညတို့နှင့် ကိုက်ညီရန် လိုအပ်သည်။ နောက်ထုတ်ဝေမှုများ၏ p95/p99 နှိုင်းယှဉ်မှုများသည် hardware၊ ပြင်ဆင်သတ်မှတ်မှုများ သို့မဟုတ် တိုင်းတာမှုလိုအပ်ချက်များက candidate နှင့် မတူသော လက်မှတ်ထိုးထားသည့် အခြေခံရလဒ်ကိုလည်း ငြင်းပယ်သည်။ နောက်ဆုံးစစ်ဆေးသူသည် သီးခြား benchmark အနှစ်ချုပ်ကို ယုံကြည်မည့်အစား မော်ကွန်းတင်ထားသော နမူနာအကြမ်းများမှ တင်ပြထားသော percentile အားလုံး၊ MADs နှင့် တစ်သမတ်တည်း ယုံကြည်မှုကြားကာလများကို ပြန်ထုတ်လုပ်သည်။ ထို့အတူ canary manifest ကို ပြန်တင်ယူပြီး မော်ကွန်းတင်ထားသော ကိုယ်ရေးလုံခြုံမှု မျက်နှာပြင်အားလုံးကို သီးခြားပြန်စစ်သဖြင့် အစီရင်ခံစာတစ်ခုသည် ဖိုင် digest များကို ပြန်ချည်နှောင်ကာ ထည့်စိုက်ထားသော လျှို့ဝှက်ချက် တွေ့ရှိမှုကို ဖုံးကွယ်မရပါ။ လျှို့ဝှက်ချက်သီးသန့် စမ်းသပ်မှုတစ်ခုစီသည် ပိုင်ရှင်သာကြည့်နိုင်သော မစစ်ထုတ်ထားသည့် loopback pcap၊ tcpdump ၏ stderr အကြမ်းနှင့် packet မဆုံးရှုံးကြောင်း စာရင်းအင်း၊ စံ port manifest၊ ထုပ်ပိုးထားသော ကန့်သတ်ရင်းမြစ် archive နှင့် peer အားလုံး၏ ခွဲခြားမရမှု တွေ့ရှိချက်များကို ထိန်းသိမ်းရမည်။ နောက်ဆုံးစစ်ဆေးသူသည် ထုတ်ဝေထားသော အနှစ်ချုပ်များကို ယုံကြည်မည့်အစား ထိုမော်ကွန်း byte များမှ port နှင့် ချည်နှောင်ထားသော packet ခွဲမှု၊ ရင်းမြစ်ကိုယ်စားပြုမြင်ကွင်းများနှင့် အခြေခံမှ နောက်ဆုံးအခြေအနေအထိ ခွဲခြားမရမှု စစ်ဆေးချက်များကို ပြန်လုပ်သည်။

မော်ကွန်းတွင် လိုအပ်သော ကိုယ်ရေးလုံခြုံမှု မျက်နှာပြင်တိုင်းအတွက် ဘယ်နှင့်ညာ ဖိုင်လမ်းကြောင်းအတိအကျ၊ အမျိုးအစား၊ byte အရှည်နှင့် SHA-256 digest တို့ကို ချည်နှောင်သော စံတွဲဖက် traffic အရေအတွက် manifest နှင့် ကွဲပြားမှုနှိုင်းယှဉ် အတွဲ manifest များလည်း ပါဝင်ရမည်။ ၎င်း၏ ကြေညာထားသော root များတွင် တွဲဖက်မော်ကွန်းစာရင်း အတိအကျသာ ပါရမည်။ စစ်ဆေးသူသည် ပုံမှန်မျက်နှာပြင်များအတွက် ဖိုင်တစ်ခုလုံးအရွယ်အစားနှင့် JSON အများမြင်ဖွဲ့စည်းပုံ တူညီရန် လိုအပ်သည်။ ကျပန်းမှုပါဝင်သော loopback ဖမ်းယူမှုအကြမ်းနှင့် ထုပ်ပိုးထားသော ကန့်သတ်ရင်းမြစ် archive သည် အရွယ်အစားစည်းမျဉ်းမှ တိတိကျကျ ခြွင်းချက်ဖြစ်သည်။ ၎င်းတို့အတွက် packet ချိတ်ဆက်မှုအမျိုးအစားနှင့် packet တစ်ခုစီ၏ အရှည်၊ ကန့်သတ်ရင်းမြစ် အထောက်အထားများနှင့် ပုံစံပုံသေ အတန်းအရှည်များကို အစားထိုးနှိုင်းယှဉ်သည်။ Torii တောင်းဆိုမှု/တုံ့ပြန်မှု၊ အများသုံး/ကန့်သတ် P2P packet၊ ဘလော့ခ်၊ query၊ ဖြစ်ရပ်၊ log နှင့် telemetry traffic အရေအတွက်တိုင်းလည်း တူညီရမည်။ Packet ဖွဲ့စည်းပုံပြောင်းလဲမှု၊ အရွယ်အစားတူသော ဖွဲ့စည်းပုံပေါက်ကြားမှု၊ မူလရင်းမြစ်အကြောင်း မမှန်သော အခိုင်အမာပြောဆိုချက် သို့မဟုတ် အတွဲမရှိသော ဖိုင်ကို ပေါက်ကြားမှုအစီရင်ခံစာနှင့် ၎င်း၏ ဟက်ရှ်များ ပြန်ရေးခြင်းဖြင့် ဖုံးကွယ်မရပါ။
