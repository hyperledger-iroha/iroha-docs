# သီးသန့် Data Space အတွက် အခကြေးငွေ ပံ့ပိုးပေးခြင်း {#sponsor-fees-for-a-private-data-space}

SORA Nexus အခကြေးငွေ sponsor အစီအစဉ်သည် သီးသန့် data space သို့ လမ်းကြောင်းရွေးချယ်ထားသော အရည်အချင်းပြည့်မီသည့် transaction များ၏ ကမ္ဘာလုံးဆိုင်ရာ လုပ်ဆောင်မှုအခကြေးငွေကို ပေးချေနိုင်သည်။ အသုံးပြုသူသည် transaction အပြည့်အစုံကို လက်မှတ်ထိုးရဆဲဖြစ်သည်။ အမျိုးအစားသတ်မှတ်ထားသော `FeePaymentIntent` သည် sponsor အစီအစဉ်နှင့် မပြောင်းလဲနိုင်သော revision အတိအကျ၊ လိုအပ်သည့်အခါ gas ကန့်သတ်ချက်နှင့် အများဆုံးကောက်ခံပမာဏများကို ရွေးချယ်သည်။

Data space ကတ်တလောက်စာရင်းတစ်ခုသည် သီးခြားလက်မှတ်ထိုးထားသော root ကို မဖန်တီးပါ။ သီးခြား data space root တွင် ကိုယ်ပိုင် commit လုပ်ပြီးသော အခကြေးငွေသုံး ငွေကြေးနှင့် မူဝါဒ ရှိသည်။ အများသုံး sponsor သိုက်များသည် ၎င်း၏ သီးသန့် root အခကြေးငွေများကို ခွင့်မပြုနိုင်ပါ။ ပံ့ပိုးမှုကို မဒီဇိုင်းဆွဲမီ လုပ်ဆောင်မှု root ကို သတ်မှတ်တည်ထောင်ပါ။

## 1. Commit လုပ်ပြီးသော အခကြေးငွေမူဝါဒကို သတ်မှတ်ခြင်း {#_1-establish-the-committed-fee-policy}

လက်မှတ်ထိုးထားသော genesis သည် `RootFeePolicy` ပါဝင်သော `root_fees_v1` စိတ်ကြိုက် parameter တစ်ခုကို သတ်မှတ်သည်။ ၎င်းက အခကြေးငွေသုံး ငွေကြေး၊ အခကြေးငွေလက်ခံဌာန၊ sponsor ထိန်းသိမ်းရေးအကောင့်၊ တောင်းခံမှုကင်းလွတ်ခွင့်များနှင့် နှုန်းထားများကို ချည်နှောင်သည်။ ပုံမှန်ဘလော့ခ်နှင့် quote တစ်ခုစီသည် ၎င်းဖမ်းယူထားသော commit လုပ်ပြီးသည့် မူဝါဒကို သုံးသည်။ နှုန်းထားများ၊ အခကြေးငွေလက်ခံဌာနနှင့် တောင်းခံမှုကင်းလွတ်ခွင့်များသို့ ခွင့်ပြုထားသော ပြောင်းလဲမှုများသည် နောက်ဘလော့ခ်မှ စတင်သက်ရောက်သည်။ အခကြေးငွေသုံး ငွေကြေးနှင့် sponsor ထိန်းသိမ်းရေးအကောင့်ကို ပထမဘလော့ခ်ပြီးနောက် ပြောင်းလဲ၍မရပါ။

ကမ္ဘာလုံးဆိုင်ရာ လုပ်ဆောင်မှုအတွက် မူရင်းအခကြေးငွေသည် လက်မှတ်ထိုးသတ်မှတ်ထားသော ကွန်ရက်၏ XOR ငွေကြေးအတိအကျကို ဖျက်သိမ်းသည်။ Sponsor အစီအစဉ်၏ သိုက်က ထိုငွေကြေးကို ပံ့ပိုးသည်။ နိုဒ်သတ်မှတ်ချက်များနှင့် transaction metadata သည် ပေးချေသူကို မရွေးချယ်သလို ပံ့ပိုးမှုကိုလည်း အသက်မသွင်းပါ။

ကွန်ရက်၏ စံငွေကြေးနှင့် အကောင့် identity များကို သုံးပါ။ Alias ဖြေရှင်းမှုသည် commit လုပ်ပြီးသော ငွေကြေး၊ ထိန်းသိမ်းရေး သို့မဟုတ် လက်ခံဌာန identity များကို အခြားနေရာသို့ မညွှန်းရပါ။

## 2. Sponsor အစီအစဉ်ကို ဖန်တီး၍ ငွေဖြည့်ခြင်း {#_2-create-and-fund-a-sponsor-program}

အစီအစဉ် ID သည် `<canonical-sponsor-account>/<program-name>` ပုံစံရှိသည်။ လက်ရှိ SDK နှင့် ဒေတာမော်ဒယ်က ပေးသော အမျိုးအစားသတ်မှတ်ထားသည့် ညွှန်ကြားချက်များဖြင့် ၎င်းကို ဖန်တီးပြင်ဆင်ပါ:

| ညွှန်ကြားချက် | ရည်ရွယ်ချက် |
| --- | --- |
| `CreateFeeSponsorProgram` | မဖြစ်မနေလိုအပ်သော ထုတ်ပေးရေးအကောင့်နှင့်အတူ အသက်မသွင်းရသေးသော အစီအစဉ်ကို ဖန်တီးသည်။ |
| `StageFeeSponsorProgramRevision` | မပြောင်းလဲနိုင်သော အရည်အချင်း၊ လုပ်ဆောင်ချက်နှင့် ဘတ်ဂျက်မူဝါဒ တစ်ခုကို သတ်မှတ်သည်။ |
| `EnrollFeeSponsorBeneficiary` | အရည်အချင်းပြည့်မီသော အကျိုးခံစားသူကို ချိန်းပေါ် မှတ်တမ်းတင်သည်။ |
| `FundFeeSponsorProgram` | ပိုင်ဆိုင်မှုများကို ထိန်းသိမ်းမှုထဲ လွှဲပြောင်းပြီး အစီအစဉ်သိုက်အတိအကျသို့ စာရင်းတိုးပေးသည်။ |
| `ActivateFeeSponsorProgramRevision` | ပြင်ဆင်ထားသော revision ၏ အစောဆုံးအသက်သွင်းအမြင့်ကို စီစဉ်သတ်မှတ်သည်။ |

Sponsor သို့မဟုတ် တိတိကျကျ လွှဲအပ်ထားသော စီမံခန့်ခွဲသူက အစီအစဉ်စီမံမှုကို ခွင့်ပြုသည်။ ငွေထုတ်ယူမှုတွင် sponsor ကိုယ်တိုင် လိုအပ်ပြီး အစီအစဉ် ရပ်နားထားစဉ် သို့မဟုတ် ပိတ်သိမ်းနေစဉ် မှတ်တမ်းတင်ထားသော ထုတ်ပေးရေးအကောင့်သို့သာ ငွေပြန်ပို့သည်။

Revision တစ်ခုစီက အောက်ပါတို့ကို သတ်မှတ်သည်:

- တိကျသော စာရင်းသွင်းမှု သို့မဟုတ် စာရင်းသွင်းမှုနှင့်အတူ ခွင့်ပြုထားသော ပုံသေလမ်းကြောင်းအလိုက် အရည်အချင်း၊
- မူရင်းညွှန်ကြားချက် ကွန်ရက်ပို့ဆောင်မှုပုံစံ ID အတိအကျများ သို့မဟုတ် စာချုပ်လိပ်စာများ၊ code ဟက်ရှ်များနှင့် ဝင်ပေါက်များအပေါ် ခွင့်ပြု၊ ငြင်းပယ် စည်းမျဉ်းများ၊
- ပိုင်ဆိုင်မှုတစ်မျိုးစီအတွက် transaction၊ ဘလော့ခ်၊ အစီအစဉ် epoch နှင့် အကျိုးခံစားသူ epoch ကန့်သတ်ချက်များ၊
- အရန်ပမာဏ အနည်းဆုံးအဆင့်နှင့် တစ်သမတ်တည်းဖြစ်သော epoch အလျား။

ငြင်းပယ်စည်းမျဉ်းသည် ခွင့်ပြုစည်းမျဉ်းထက် ဦးစားပေးသက်ရောက်သည်။ Data space ၏ `fee_sponsor_program_id` သည် လက်ရှိ revision က ခွင့်ပြုမှသာ ပုံသေလမ်းကြောင်းအလိုက် အရည်အချင်းကို ပေးသည်။ Transaction က အစီအစဉ်နှင့် revision အတိအကျကို အမည်ပေးရဆဲဖြစ်သည်။ ယခင် revision မှ ကျန်ရှိနေသော ခွဲဝေမှုများ သက်တမ်းကုန်သည်အထိ အသက်သွင်းမှုကို ရွှေ့ဆိုင်းနိုင်သည်။

Sponsor သိုက်ရှိ ပိုင်ဆိုင်မှုများသည် `Global` လက်ကျန်မူဝါဒကို သုံးရမည်။ Sponsor ၏ ပုံမှန်အကောင့်ကိုသာ ငွေဖြည့်ခြင်းသည် သီးခြားအစီအစဉ်သိုက်ကို ငွေဖြည့်ခြင်း မဟုတ်ပါ။ အစီအစဉ်တစ်ခုက အခြားအစီအစဉ်၏ လက်ကျန်ကို သုံး၍ မရပါ။

## 3. Transaction အတိအကျ၏ အခကြေးငွေကို တွက်ချက်၍ လက်မှတ်ထိုး၊ တင်သွင်းခြင်း {#_3-quote-sign-and-submit-the-exact-transaction}

SDK ပေါင်းစည်းမှုသည် အောက်ပါအဆင့်များကို လုပ်ဆောင်သည်:

1. Authority၊ လုပ်ဆောင်နိုင်သော code၊ အချိန်မှတ်တမ်းများ၊ nonce၊ metadata၊ sponsor အစီအစဉ် revision အတိအကျနှင့် လိုအပ်သော gas ကန့်သတ်ချက်တို့ပါဝင်သည့် လက်မှတ်မထိုးရသေးသော `TransactionPayload` ကို တည်ဆောက်ပါ။ အများဆုံးကောက်ခံပမာဏများကို အစပိုင်းတွင် အလွတ်ထားနိုင်သည်။
2. `{"payload": <payload>}` ပါဝင်သော `POST /v1/fees/quote` ကို အကောင့်ဖြင့် လက်မှတ်ထိုးပါ။ တောင်းဆိုမှုလက်မှတ်ထိုးသူသည် transaction authority ဖြစ်ရမည်။
3. စောင့်ကြည့်ရရှိသော အမြင့်၊ ဖြေရှင်းရရှိသော data space လမ်းကြောင်း၊ အခကြေးငွေအစိတ်အပိုင်းများ၊ ငွေနုတ်ယူမည့် ရင်းမြစ်နှင့် sponsor စွမ်းရည်ကို စစ်ဆေးပါ။ တုံ့ပြန်ချက်သည် ရွေးထားသော ပေးချေသူ၊ revision နှင့် gas ကန့်သတ်ချက်ကို ထိန်းသိမ်းထားကြောင်း စစ်ဆေးပါ။
4. `payload.fee_payment` တစ်ခုတည်းကို အကြံပြုထားသော ရည်ရွယ်ချက်ဖြင့် အစားထိုးပြီး ထို payload အတိအကျကို လက်မှတ်ထိုးတင်သွင်းပါ။
5. Transaction ကို အခြေအနေဖြင့် ဆုံးဖြတ်ပြီးသော `Applied` အပြီးသတ်အတည်ဖြစ်မှုအထိ ခြေရာခံပြီး အမှန်တကယ်သုံးသော sponsor အစီအစဉ်၊ revision နှင့် ကောက်ခံပမာဏ ပါဝင်သည့် ပြေစာကို ထိန်းသိမ်းပါ။

Quote သည် လယ်ဂျာကို စောင့်ကြည့်ဖတ်ရှုခြင်းသာဖြစ်ပြီး စွမ်းရည်ကို မကြိုတင်သိမ်းယူပါ။ တန်းစီစာရင်းလက်ခံမှုသည် အရည်အချင်းကို ပြန်စစ်ပြီး လက်မှတ်ထိုးထားသော အများဆုံးပမာဏများကို ကြိုတင်သိမ်းယူသည်။ Sponsor ငြင်းပယ်မှုသည် အသုံးပြုသူထံမှ အစားထိုးကောက်ခံခြင်း မပြုဘဲ transaction ကို ငြင်းပယ်သည်။

CLI သည် တူညီသော အခကြေးငွေရင်းမြစ်ကို တိတိကျကျ အမည်ပေးသည်။ ဥပမာ အစီအစဉ်က ဤပိုင်ဆိုင်မှုလွှဲပြောင်းမှုအတိအကျကို ခွင့်ပြုပြီး အကောင့် အရည်အချင်းပြည့်မီပြီးနောက်:

```bash
iroha --config ./user.client.toml \
  --fee-payer sponsor \
  --fee-program '<SPONSOR_CANONICAL_I105>/team-payments' \
  --fee-program-revision 1 \
  ledger asset transfer \
  --definition '<ASSET_DEFINITION_BASE58>' \
  --account '<USER_CANONICAL_I105>' \
  --to '<RECIPIENT_CANONICAL_I105>' \
  --quantity 1
```

သင့်ကွန်ရက်၏ လက်ရှိ revision နှင့် identifier အတိအကျများကို သုံးပါ။ အသုံးပြုသူပြင်ဆင်သတ်မှတ်မှုတွင် ထိုအသုံးပြုသူ၏ လက်မှတ်ထိုးသူသာ ပါဝင်သည်။ အရည်အချင်းပြည့်မီသော ပံ့ပိုးထားသည့် transaction ကို တင်သွင်းရန် sponsor ၏ ကိုယ်ပိုင်ကီး မလိုအပ်ပါ။

## 4. အသုံးပြုသူက အက်ပ်အခကြေးငွေ ပေးမပေး ဆုံးဖြတ်ခြင်း {#_4-decide-whether-the-user-pays-an-application-fee}

အက်ပ်က အသုံးပြုသူထံမှ မည်သည့်အခကြေးငွေမျှ မကောက်ခံစဉ် sponsor က ကမ္ဘာလုံးဆိုင်ရာ အခကြေးငွေများကို ပေးချေနိုင်သည်။ အက်ပ်က ဒေသတွင်း token ကို ကောက်ခံပါက ထိုလွှဲပြောင်းမှု သို့မဟုတ် စာချုပ်စည်းမျဉ်းကို အသုံးပြုသူလက်မှတ်ထိုးထားသော လုပ်ဆောင်နိုင်သည့် code ထဲ တိတိကျကျ ထည့်ရေးပါ။ လုပ်ဆောင်ချက်တိုင်းကို sponsor revision ၏ မူဝါဒတွင် ထည့်ပြီး payload အပြည့်အစုံအတွက် quote ကို စစ်ဆေးပါ။ ကွန်ရက်အခကြေးငွေရည်ရွယ်ချက်မှ အက်ပ် token လွှဲပြောင်းမှုရှိမည်ဟု မယူဆပါနှင့်။

## ငြင်းပယ်မှုကို စစ်ဆေးရှာဖွေခြင်း {#diagnose-a-refusal}

နိုဒ်က ပြန်ပေးသော တည်ငြိမ်သည့် အခကြေးငွေ code နှင့် ဖြေရှင်းနည်း အသေးစိတ်များကို သုံးပါ:

| ကုဒ် | စစ်ဆေးရန် |
| --- | --- |
| `program_not_found` | စံပရိုဂရမ် အထောက်အထား အတိအကျ။ |
| `revision_not_active`၊ `program_not_active` | Revision အသက်သွင်းမှုနှင့် အစီအစဉ်သက်တမ်းစက်ဝန်း။ |
| `beneficiary_not_eligible` | စာရင်းသွင်းမှု သို့မဟုတ် ခွင့်ပြုထားသော ပုံသေလမ်းကြောင်းအလိုက် အရည်အချင်း။ |
| `operation_not_allowed`၊ `operation_denied` | လက်မှတ်ထိုးထားသော လုပ်ဆောင်ချက်အတိအကျတိုင်းနှင့် ငြင်းပယ်စည်းမျဉ်း။ |
| `invalid_gas_limit`၊ `signed_limit_exceeded` | လတ်ဆတ်သော quote နှင့် နှိုင်းယှဉ်သည့် gas ကန့်သတ်ချက်၊ လက်မှတ်ထိုးထားသော အများဆုံးပမာဏများ။ |
| `vault_insufficient` | ဤအစီအစဉ်၏ ငွေကြေးသိုက်အတိအကျတွင် ငွေဖြည့်ထားသော လက်ကျန်။ |
| ဘတ်ဂျက်ကုန်ခန်းမှု code များ | Transaction၊ ဘလော့ခ်၊ အစီအစဉ် epoch နှင့် အကျိုးခံစားသူ epoch စွမ်းရည်။ |

တင်သွင်းမှုရလဒ် မသေချာသောအခါ စစ်ဆေးရန် မူရင်း transaction ဟက်ရှ်နှင့် အခကြေးငွေငြင်းပယ်မှု အသေးစိတ်များကို ထိန်းသိမ်းပါ။ အစားထိုး transaction မတည်ဆောက်မီ ၎င်း၏ အခြေအနေကို အတည်ပြုပါ။
