# ကွန်ရက် ဖြန့်ချိခြင်းအတွက် သော့ချက်များ {#keys-for-network-deployment}

ကွန်ရက်တိုင်းမှာ ဖောက်သည်များ၊ ကွန်ယက်တူညီသူများအတွက် သီးခြားသော အဓိကပစ္စည်းတွေ လိုအပ်တယ်၊ blockchain genesis လက်မှတ်ထိုးခြင်း၊ NPoS သို့မဟုတ် Nexus ပရိုဖိုင်တွေအတွက်တော့ BLS အတည်ပြုသူ လက္ခဏာတွေပါ။

## သော့များ အသုံးပြုရာ {#where-keys-are-used}

- ဖောက်သည် လက်မှတ်ရေးထိုးသော သော့များကို `client.toml` တွင် `[account]` အောက်တွင် သိမ်းထားပါသည်။
- peer တစ်ခုချင်းစီ၏ အထောက်အထားကီးများကို ၎င်း၏ `config.toml` တွင် `public_key` နှင့် `private_key` အဖြစ် သိမ်းထားသည်။
- peer ရှာဖွေမှုသည် `trusted_peers` ထဲရှိ peer တစ်ခုချင်းစီ၏ အများသုံးကီးကို အသုံးပြုသည်။
- NPoS ပရိုဖိုင်များအတွက် BLS သုံး validator များ၏ ကီးပိုင်ဆိုင်ကြောင်းအထောက်အထားများကို `trusted_peers_pop` တွင် သိမ်းထားသည်။
- genesis ကို လက်မှတ်ထိုးရာတွင် peer ပြင်ဆင်သတ်မှတ်မှုရှိ `[genesis].public_key` နှင့် manifest ကို လက်မှတ်ထိုးချိန်၌ ၎င်းနှင့်ကိုက်ညီသော ကိုယ်ပိုင်ကီးကို အသုံးပြုသည်။

ဒေသတွင်း (သို့) စမ်းသပ်မှု ဖြန့်ချိချက်များအတွက် Kagami သည် ဤဖိုင်အားလုံးကို စုပေါင်းထုတ်လုပ်ပါ:

```bash
cargo run --bin kagami -- localnet --peers 4 --out-dir ./localnet
```

ရှိနေတဲ့ ကွန်ရက် (သို့) ပရိုဖိုင်အတွက် guide flow ကိုသုံးပါ။

```bash
cargo run --bin kagami -- wizard
```

## ပုဂ္ဂိုလ်ရေး သော့စုံများ ဖန်တီးခြင်း {#generate-individual-key-pairs}

သီးခြားကီးများ ဖန်တီးရန် `kagami keys` ကို အသုံးပြုပါ။

```bash
cargo run --bin kagami -- keys --algorithm ed25519 \
  --out-dir ./client-key
```

BLS အတည်ပြုပစ္စည်းအတွက် ပိုင်ဆိုင်မှု သက်သေခံစာကို ထည့်သွင်းပါ။

```bash
cargo run --bin kagami -- keys --algorithm bls_normal --pop \
  --out-dir ./validator-key
```

ပြန်လည်ထုတ်လုပ်နိုင်သော ဖွံ့ဖြိုးရေးစမ်းသပ်ဒေတာအတွက် `--seed-hex` ကို ၃၂ ဘိုက်တိတိရှိသော ဆယ့်ခြောက်လီကိန်းပုံစံ လျှို့ဝှက်တန်ဖိုးနှင့်သာ အသုံးပြုပါ။ တကယ့်လုပ်ငန်းသုံး deployment တွင် ၎င်းကို ချန်ထား၍ Kagami က လည်ပတ်စနစ်၏ ကျပန်းတန်ဖိုးများကို အသုံးပြုစေပါ။ ထို့နောက် စာဝှက်မထားသော ကိုယ်ပိုင်ကီးထုတ်ယူဖိုင်ကို အတည်ပြုထားသော ကီးထိန်းသိမ်းရေးနယ်ပယ်သို့ ရွှေ့ပါ။ ဤ command သည် ကိုယ်ပိုင်ကီးများကို မည်သည့်အခါမျှ မဖော်ပြပါ။

## Network peer ကိုညီညွတ်မှု {#peer-consistency}

validator အားလုံးသည် တူညီသော genesis transaction၊ ချိတ်ဆက်ဖွဲ့စည်းပုံ၊ ယုံကြည်ထားသော peer များ၏ အများသုံးကီးများနှင့် validator များ၏ PoPs တို့ကို သဘောတူထားရမည်။ peer ကီးတစ်ခုတည်း ပျောက်နေခြင်း သို့မဟုတ် မကိုက်ညီခြင်းကြောင့် ကွန်ရက် စတင်မရခြင်း သို့မဟုတ် သဘောတူညီချက် မရနိုင်ခြင်း ဖြစ်နိုင်သည်။

Byzantine ချို့ယွင်းမှုများကို ခံနိုင်သော အနည်းဆုံး deployment အတွက် peer အနည်းဆုံးလေးခုကို အသုံးပြုပါ။ peer တစ်ခုချင်းစီတွင် ကိုယ်ပိုင်ကီးတစ်ခုစီ ရှိရမည်ဖြစ်သော်လည်း peer ပြင်ဆင်သတ်မှတ်မှုတိုင်း၌ တူညီသော ယုံကြည်ထားသည့် peer အစုကို ထည့်ထားရမည်။

## ဖောက်သည်စာရင်းများ {#client-accounts}

`client.toml` ထဲက ဖောက်သည်စာရင်းဟာ ချိတ်ဆက်မှုမှာ ရှိပြီးသား ဖြစ်ရပါမယ်။ ဒါကို blockchain Genesis Technical Manifesto သို့မဟုတ် နောက်ပိုင်း ငွေပေးချေမှုဖြင့် မှတ်ပုံတင်နိုင်သည်။ blockchain genesis လက်မှတ်ရေးထိုးတဲ့ ကိုယ်ပိုင်လက္ခဏာကို သက်တမ်းရှည် အက်ပ်အကောင့်အဖြစ် အသုံးပြုခြင်းကနေ ရှောင်ရှားပါ။ blockchain genesis အခွင့်အရေးတွေဟာ blockchain genesis round အတွင်းမှာသာ သက်ရောက်ပြီး ထုတ်လုပ်မှု ဖောက်သည်တွေက သူတို့ကိုယ်ပိုင် အကောင့်တွေနဲ့ အခန်းကဏ္ဍတွေကို သုံးသင့်ပါတယ်။
