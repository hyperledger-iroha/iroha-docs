# ဒေတာပုံစံထုတ်ခြင်း {#data-modeling}

Ledger ဒေတာကို ပိုင်ဆိုင်မှု၊ လွှဲပြောင်းမှု အပြုအမူ၊ ခွင့်ပြုချက် နယ်နိမိတ်များနှင့် မေးမြန်းမှုပုံစံများအနီးတွင် ပုံစံထုတ်သင့်သည်။ စစ်ဆေးနိုင်စွမ်းနှင့် သတ်မှတ်ချက်ဆိုင်ရာ အကောင်အထည်ဖော်မှုကို ထောက်ပံ့နိုင်သော သော့တန်းပေါ်က အသေးဆုံး ကိုယ်စားပြုချက်ကို ရွေးချယ်ပါ။

## ဒိုမီနန်းများနှင့် အကောင့်များ {#domains-and-accounts}

- အုပ်ချုပ်ရေးနှင့် မူဝါဒ နယ်နိမိတ်များကို ကိုယ်စားပြုရန် ဒိုမီနိုင်းများ အသုံးပြုပါ။ အကောင့်များနှင့် အရင်းအမြစ်အမှတ်တံဆိပ်များတွင် ပေါ်လာသောကြောင့် ဒိုမီနာမည်များအား တည်ငြိမ်စွာ ထိန်းသိမ်းပါ။
- သက်ဆိုင်မှုမရှိသော တာဝန်များနှင့်အတူ တစ်ခုတည်းသောအကောင့်ကို အလွန်အကျွံ လွှမ်းမိုးခြင်းကို ရှောင်ရှားပါ။ အသုံးပြုသူများ၊ ဝန်ဆောင်မှုများ၊ trigger များ၊ operator များနှင့် fee sponsor များအတွက် သီးခြားအကောင့်များကိုအသုံးပြုပါ။
- Iroha အမည်တွေဟာ Canonical Parsing နောက်ပိုင်းမှာ Case-sensitive ဖြစ်တယ်။
- အမည်များ၊ ဒိုမီနန်းများနှင့် ဖွဲ့စည်းပုံဖိုင်လမ်းကြောင်းများတွင် စမ်းသပ်မှုနှင့် ထုတ်လုပ်ရေးအသိကို မြင်သာစွာ ခြားနားစေပါ။

[Domains](/my/blockchain/domains.md)၊ [Accounts](/my/blockchain/accounts.md) နှင့် [Naming](/my/reference/naming.md) ကိုကြည့်ပါ။

## အရင်းအမြစ်များနှင့် NFTs {#assets-and-nfts}

- ဖောက်ပြန်နိုင်တဲ့ ငွေကြေးစာရင်းများနဲ့ လွှဲပြောင်းလို့ရတဲ့ ပမာဏအတွက် ကိန်းဂဏန်း အရင်းအမြစ်တွေကို သုံးပါ။
- NFTs သို့မဟုတ် domain-specific objects များကို သီးသန့်ပိုင်ဆိုင်သော မှတ်တမ်းများအတွက် အသုံးပြုပါ။
- Value-bearing state ကို metadata ထဲမှာသာ encoding လုပ်ဖို့ ရှောင်ရှားပါ။ Assets နှင့် NFTs တို့က lifecycle အဖြစ်အပျက်များ၊ transfer semantics များနှင့် metadata မပြုလုပ်တဲ့ ခွင့်ပြုချက် စစ်ဆေးမှုများကို ပေးသည်။
- တိကျမှု၊ ထောက်ပံ့ရေးမူဝါဒ၊ ထုတ်ပြန်သူရဲ့ တာဝန်ရှိမှု၊ အရင်းအမြစ်ကို လျှောက်လွှာများသို့ မတင်ပြခင် မီးရှို့/မင်တာအာဏာပိုင်ကို သတ်မှတ်ပါ။

ကြည့်ပါ။ [ပိုက်ဆံများ](/my/blockchain/assets.md), [NFTs](/my/blockchain/nfts.md), နှင့် [RWAs](/my/blockchain/rwas.md).

## မီတာဒေတာ {#metadata}

- စာရင်းအင်းအရာဝတ္ထုများ၏ အသေးစိတ်လက္ခဏာများအတွက် မီတာဒေတာများကို အသုံးပြုရန်၊ ဥပမာ လိပ်စာများ၊ ပေါင်းစပ်ခြင်း IDs, မူဝါဒ အလံများ, hashes, URIs သို့မဟုတ် အကြောင်းအရာဆိုင်ရာ ရည်ညွှန်းချက်များလိုပါ။
- metadata keys တွေကို တည်ငြိမ်ပြီး မှတ်တမ်းတင်ထားပါ။ ဖောက်သည်တွေ မှီခိုပြီးနောက် key names ကိုပြောင်းတာဟာ ရွှေ့ပြောင်းပြဿနာတစ်ခု ဖန်တီးပါတယ်။
- ကြီးမားတဲ့ စာရွက်စာတမ်းများ၊ မှတ်စုများ၊ ပုဂ္ဂလိက အသုံးပြုသူ ဒေတာများ (သို့မဟုတ်) မြင့်မားသော ချန်ပီယံမှုရှိသည့် အက်ပလီကေးရှင်းအခြေအနေများကို တိုက်ရိုက် metadata များတွင် သိမ်းဆည်းမထားပါ။
- metadata တွေက ကွင်းဆက်ပြင်ပ ဒေတာကို ညွှန်ပြတဲ့အခါ Content hash, URI, SoraFS path, manifest reference, or compact commitment တို့လို စစ်ဆေးလို့ရတဲ့ ရည်ညွှန်းချက်ကို သိမ်းထားပါ။

[Metadata and Ledger Storage Choices](/my/guide/configure/metadata-and-store-assets.md) နှင့် [Metadata](/my/blockchain/metadata.md) ကိုကြည့်ပါ။

## ပုံစံအလိုက် ခွင့်ပြုချက်များ {#permissions-by-model}

- လုပ်ငန်းဆောင်ရွက်မှု အနီးအနားမှာ ဒီဇိုင်းကဏ္ဍများ၊ အကောင်အထည်ဖော်မှု သက်တောင့်သက်သာတွေ မဟုတ်ပါ။ အလုပ်တစ်ခု (သို့) ဝန်ဆောင်မှုတစ်ခုအတွက် နာမည်တပ်ထားတဲ့ ကဏ္ဍကို ကျယ်ပြန့်တဲ့ နည်းပညာ အရည်အသွေးတစ်ခုကြောင့် နာမည်တပ်ထားသည့် ကဏ္ဍထက် စာရင်းစစ်တာ ပိုလွယ်ပါတယ်။
- Workflow ကို ဖြည့်ဆည်းပေးတဲ့ အသေးဆုံး အရာဝတ္ထုကို Scope permission tokens တွေကို ထည့်သွင်းပါ။
- Mining, burning, peer management, executor changes, trigger management နဲ့ metadata mutation တွေအတွက် ခွင့်ပြုချက်တွေကို ထိခိုက်မှုမြင့် ခွင့်ပြုချက်တွေအဖြစ် မှတ်ယူပါ။
- ယာယီ ခွင့်ပြုချက်များအတွက် ရှင်းလင်းစွာ ရုပ်သိမ်းခြင်းနှင့် လည်ပတ်မှု လုပ်ငန်းစဉ်များကို ထည့်သွင်းပါ။

[ခွင့်ပြုချက်များ](/my/blockchain/permissions.md) နှင့် [ခွင့်ပြုချက် လက်မှတ်များ ](/my/reference/permissions.md) ကိုကြည့်ပါ။

## မေးမြန်းပုံ {#query-shape}

- သင့်အက်ပ်လီကေးရှင်းမှာ မကြာခဏလိုအပ်တဲ့ မေးမြန်းချက်တွေကို ထောက်ခံတဲ့ ID တွေနဲ့ metadata သော့တွေကို ရွေးပါ။
- ကျယ်ပြန့်တဲ့ ရလဒ်အစီအစဉ်တွေကို စာမျက်နှာပြုပြင်ပြီး ပုံမှန်လုပ်ဆောင်ချက်တွေအတွက် ကန့်သတ်ချက်မရှိတဲ့ ledger တစ်လွှား စကင်တွေလိုအပ်တဲ့ အသုံးပြုသူ ကြားခံစနစ်တွေကို ရှောင်ပါ။
- critical application behavior အတွက် အသုံးပြုတဲ့ အချိန်တိုင်း ledger ဒေတာနဲ့ ဖြစ်ရပ်တွေကနေ ပြန်လည်တည်ဆောက်နိုင်တဲ့ off-chain index တွေကို ထိန်းထားပါ။
