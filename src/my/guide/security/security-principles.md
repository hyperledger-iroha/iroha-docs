# လုံခြုံရေး မူဝါဒများ {#security-principles}

Iroha blockchain ledger သည် လက်မှတ်ရေးထိုးထားသော ညွှန်ကြားချက်များကို စစ်ဆေးပြီး ခွင့်ပြုချက်များကို အသုံးပြုသည်။ ၎င်းသည် ပုဂ္ဂလိက သော့များ၊ အိမ်ရှင်များ၊ အက်ပ်လီကေးရှင်းများ၊ အော်ပရေတာ အလုပ်ရုံများ သို့မဟုတ် အုပ်ချုပ်မှု လုပ်ငန်းစဉ်များကို လုံခြုံစေခြင်းမရှိပါ။ ဖြန့်ဖြူးမှုက ထိုစနစ်များကို ကာကွယ်ရမည်ဖြစ်သည်။

Iroha ကွန်ရက်ကို ဒီဇိုင်းထုတ်ပြီး လည်ပတ်တဲ့အခါ ဒီအယူအဆတွေကို အသုံးပြုပါ။

## ခွင့်ပြုချက်ပေးသူကို လုံခြုံရေး နယ်နိမိတ်တစ်ခုအဖြစ် ဆက်ဆံပါ။ {#treat-authority-as-a-security-boundary}

- ပုဂ္ဂလိက သော့ကို ထိန်းချုပ်တဲ့ လူတစ်ယောက် (သို့) လုပ်ငန်းစဉ်ဟာ အဲဒီသော့အတွက် တာဝန်ပေးထားတဲ့ ခွင့်ပြုချက် မူပိုင်ရှင်နဲ့ လုပ်ဆောင်နိုင်ပါတယ်။
- ပတ်ဝန်းကျင်နဲ့ လုပ်ငန်းတာဝန်တစ်ခုစီအတွက် သီးခြား ခွင့်ပြုချက် မူဝါဒကို ပေးပါ။
- ထုတ်လုပ်ရေး သော့တွေနဲ့ ပြန်လည်ထူထောင်ရေး သော့တွေကို ပုံမှန် ဖွံ့ဖြိုးတိုးတက်မှုနဲ့ စမ်းသပ်မှု ခွင့်ပြုချက်တွေကနေ ခွဲခြားထားပါ။
- ခွင့်ပြုချက် အရင်းအမြစ်တစ်ခုစီရဲ့ ပိုင်ရှင်ကို မှတ်တမ်းတင်ပါ၊ ၎င်းရဲ့ cryptographic လက်မှတ်ထိုးသူ ဘယ်မှာရှိလဲ၊ ဒါကို ဘယ်လို အစားထိုး (သို့) ရုပ်သိမ်းနိုင်သလဲဆိုတာပါ။

[အများသုံးသော့စာဝှက်ချက်များ](./public-key-cryptography.md) နှင့် [Cryptographic Key ကို သိုလှောင်ခြင်း](./storing-cryptographic-keys.md) ကိုကြည့်ပါ။

## အနည်းဆုံးအခွင့်အရေးကို အသုံးချပါ {#apply-least-privilege}

- Role တစ်ခုအတွက် လိုအပ်တဲ့ Iroha ခွင့်ပြုချက်တွေ၊ host access နဲ့ network access တွေကိုသာ ပေးပါ။
- စီမံခန့်ခွဲမှု၊ ဖြန့်ချိခြင်းနှင့် ပြန်လည်ထူထောင်ရေး ခွင့်ပြုချက် အရင်းအမြစ်မှ ပုံမှန် ငွေကြေးဆိုင်ရာ လက်မှတ်ရေးထိုးမှုကို ခွဲခြားပါ။
- အတည်ပြုသူ အဖွဲ့ဝင်၊ အခွင့်ထူးခံ ခွင့်ပြုချက်များ သို့မဟုတ် တန်ဖိုးမြင့် အရင်းအမြစ်များကို သက်ရောက်နိုင်သော ပြောင်းလဲမှုများအတွက် လွတ်လပ်စွာ ခွင့်ပြုချက်ကို တောင်းဆိုပါ။
- အခန်းကဏ္ဍ ပြောင်းလဲပြီးနောက် ဝင်ရောက်မှုကို ပြန်လည်သုံးသပ်ပြီး မလိုတော့တဲ့ ဝင်ရောက်မှုတွေကို ဖယ်ရှားပါ။

## ကာကွယ်ရေး အလွှာများ အသုံးပြုခြင်း {#use-layers-of-protection}

- Cryptographic signers, applications, operating systems, networks, and physical access ကို ကာကွယ်ပေးပါ။ ထိန်းချုပ်မှုတစ်ခုတည်းကို မမှီခိုပါ။
- Torii, network peer, monitoring နှင့် deployment အတွက်လိုအပ်သော application routes များကိုသာ ဖော်ပြပါ။
- စီမံခန့်ခွဲရေးဝင်ရောက်မှုနှင့် အာရုံခံအချက်အလက်များအတွက် အထောက်အထားရှိပြီး ကုဒ်သွင်းထားတဲ့ လမ်းကြောင်းများကို အသုံးပြုပါ။
- စနစ်တွေကို patched ထားပြီး deployment မသုံးတဲ့ ဝန်ဆောင်မှုတွေကို ပိတ်ထားပါ။
- အရင်းအမြစ် ထိန်းချုပ်မှုမှ လျှို့ဝှက်ချက်တွေ၊ အမိန့်လိုင်းတွေ၊ မှတ်တမ်းတွေ၊ လက်မှတ်တွေ၊ စကားပြောနဲ့ အများသိတဲ့ စာရွက်စာတမ်းတွေကို ရှောင်ရှားပါ။

## အသုံးချမှုများကို ပြန်လည်သုံးသပ်နိုင်အောင် လုပ်ပေးပါ။ {#make-deployments-reviewable}

- ဗားရှင်းထိန်းချုပ်မှုမှာ လျှို့ဝှက်မဟုတ်တဲ့ ဖွဲ့စည်းမှုနဲ့ ဖြန့်ဖြူးခြင်း အလိုအလျောက်ကို ထိန်းထားပါ။
- ဘိုင်နရီများ၊ ဖွဲ့စည်းပုံများ၊ blockchain မျိုးစေ့ရေး ပစ္စည်းများ၊ အတည်ပြုသူ အဖွဲ့ဝင်များ၊ ခွင့်ပြုချက်များနှင့် အများပြည်သူ လမ်းကြောင်းများအတွက် ပြုပြင်ပြောင်းလဲမှုများကို ပြန်လည်လေ့လာပါ။
- ဖြန့်ချိခြင်းမတိုင်မီ ထုတ်ဝေမှု လက်ရာများကို စစ်ဆေးပါ။ ခွင့်ပြုထားသောဗားရှင်းများနှင့် cryptographic hash များကို မှတ်တမ်းတင်ပါ။
- ထုတ်လုပ်မှုမှာ လည်ပတ်မယ့် တိကျတဲ့ binary နဲ့ configuration ပေါင်းစပ်မှုကို စမ်းသပ်ပါ။
- Network ရဲ့ deterministic behaviour ကို ထိန်းထားပါ။ Hardware အရှိန်မြှင့်မှုဟာ peer-visible ရလဒ်တွေကို မပြောင်းလဲစေရ။

## အထောက်အထားကို စောင့်ကြည့်ကာ ထိန်းသိမ်းခြင်း {#monitor-and-preserve-evidence}

- Network peer ကျန်းမာရေး၊ သဘောတူညီမှု တိုးတက်မှု၊ ခွင့်ပြုချက် ပြောင်းလဲခြင်း၊ အခွင့်ထူးခံ ညွှန်ကြားချက်များ၊ စစ်ဆေးမှု ကျရှုံးမှုများနှင့် မမျှော်လင့်ဘဲ ဖွဲ့စည်းပုံပြောင်းလဲမှုများကို စောင့်ကြည့်ပါ။
- ထိခိုက်ခံရတဲ့ အိမ်ရှင်ကို မမှီခိုတဲ့ စနစ်ကို အရေးပါတဲ့ သတိပေးချက်တွေ ပို့ပါ။
- သက်ဆိုင်ရာ logs များ၊ blockchain ledger ကို ရည်ညွှန်းချက်များ၊ Configuration Point-in-Time ဒေတာအမြင်များနှင့် ယုံကြည်စိတ်ချရသော အချိန်တံဆိပ်များဖြင့် ငွေကြေးလုပ်ငန်း cryptographic hashes များကို ထိန်းသိမ်းပါ။
- ပျောက်နေတဲ့ စောင့်ကြည့်မှု ဒေတာကို စုံစမ်းစစ်ဆေးဖို့ လိုအပ်တဲ့ လုပ်ငန်းပြဿနာတစ်ခုအဖြစ် ဆက်ဆံပါ။

## မစတင်မီ ပြန်လည်ထူထောင်ရန် ပြင်ဆင်ပါ {#prepare-recovery-before-launch}

- ဖြစ်ရပ်ကို ဘယ်သူက ကြေညာနိုင်လဲ၊ ဘယ်သူက ပြန်လည်ထူထောင်ရေး လုပ်ဆောင်ချက်တွေကို အတည်ပြုနိုင်လဲဆိုတာ သတ်မှတ်ပါ။
- Backup, Restore, Key Replacement, Permission Revocation နဲ့ Network Peer Recovery လုပ်ငန်းစဉ်တွေကို စမ်းသပ်ပါ။
- စိတ်ချရတဲ့ ထုတ်ပြန်မှု လက်ရာတွေ၊ ဖွဲ့စည်းပုံ၊ blockchain မျိုးဆက်မှတ်တမ်းတွေနဲ့ ဖြစ်စဉ်တစ်ခုအတွင်းမှာ ရယူနိုင်တဲ့ စာရင်းတွေ ထားပါ။
- Read တွေကို Restore နဲ့ Monitoring ကို အရင်ဆုံး Restore လုပ်ပါ။ ပြန်လည်ထူထောင်ထားတဲ့ network နဲ့ dependent applications တွေရဲ့ စစ်ဆေးမှုကို အောင်ပြီးနောက်ပဲ Resume ရေးပေးတာပါ။
- ဖြစ်ရပ်တိုင်းကို စစ်ဆေးပြီး ထိန်းချုပ်မှုတွေ၊ အလိုအလျောက်လုပ်ခြင်းနဲ့ လေ့ကျင့်ခန်းတွေကို မွမ်းမံပါ။

::: warning

blockchain ledger လုပ်ဆောင်ချက်တွေဟာ ပြန်လည်မပြောင်းလဲနိုင်ပါ။ ပြန်လည်ထူထောင်ခြင်း (သို့) အုပ်ချုပ်ရေးလုပ်ငန်းစဉ်တစ်ခု မတင်မီမှာ ကြိုတင်စစ်ဆေးထားတဲ့ လုပ်ငန်းစဉ်တွေနဲ့ လိုအပ်တဲ့ ခွင့်ပြုချက်တွေကို သုံးပါ။

:::
