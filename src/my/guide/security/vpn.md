# Virtual Private Networks များ {#virtual-private-networks}

<abbr title="Virtual Private Network">VPN</abbr> သည် Iroha ဝန်ဆောင်မှုများသို့ မည်သူရောက်ရှိနိုင်သည်ကို ကန့်သတ်သည့်ကွန်ရက်ထိန်းချုပ်မှုတစ်ခုဖြစ်သည်။ validators များ၊ application backends များနှင့် operator များသည်ဖွင့်လှစ်သော အင်တာနက်လမ်းကြောင်းများအစား ပုဂ္ဂလိကလိပ်စာများဖြင့် ဆက်သွယ်သင့်သော သီးသန့်နှင့် ပူးပေါင်းဆောင်ရွက်ချက်များအတွက်အလွန်အသုံးဝင်သည်။

VPN သည် Iroha ၏ peer ကီးများ၊ အကောင့်ကီးများ၊ ခွင့်ပြုချက်များ၊ firewall စည်းမျဉ်းများ၊ စောင့်ကြည့်မှု သို့မဟုတ် လုံခြုံသောကီးသိမ်းဆည်းမှုကို အစားမထိုးပါ။ ၎င်းကို deployment နယ်ပယ်၏ အလွှာတစ်ခုအဖြစ် သတ်မှတ်ပါ။ VPN က ကွန်ရက်ချိတ်ဆက်ရောက်ရှိနိုင်မှုကို ကန့်သတ်ပေးပြီး Iroha ပြင်ဆင်သတ်မှတ်မှုနှင့် အုပ်ချုပ်မှုက မည်သည့် peer နှင့် အကောင့်များကို ယုံကြည်မည်ကို ဆုံးဖြတ်သည်။

## VPN ကို ဘယ်အချိန် အသုံးပြုရမလဲ {#when-to-use-a-vpn}

VPN ကို အသုံးပြုပါ-

- validator တွေကို မတူညီတဲ့ အဖွဲ့အစည်းတွေ (သို့) မတူညီတဲ့ hosting ဝန်းကျင်တွေမှာ လည်ပတ်ပါတယ်။
- Torii ကို အက်ပ် backend များ၊ အော်ပရေတာများ သို့မဟုတ် ယုံကြည်ထားသော client များကသာ ချိတ်ဆက်နိုင်သင့်သည်
- မက်ထရစ်များ၊ မှတ်တမ်းများ၊ SSH, သို့မဟုတ် အခြားစီမံခန့်ခွဲမှု API အပြီးသတ်မှတ်ချက်တွေဟာ ပုဂ္ဂလိက လုပ်ငန်းရှင်တွေရဲ့ ကွန်ရက်မှာ ရှိနေဖို့လိုပါတယ်။
- စမ်းသပ်မှု (သို့) အဆင့်သတ်မှတ်ရေးကွန်ရက်တစ်ခုသည် အများပြည်သူ API အဆုံးအဖြတ်ချက်များကို ဖော်ပြခြင်းမရှိဘဲ ထုတ်လုပ်မှုဝင်ရောက်မှုထိန်းချုပ်မှုများနှင့် ဆင်တူသင့်သည်။

deployment တိုင်းအတွက် VPN မလိုအပ်ပါ။ အများသုံးကွန်ရက်များသည် Torii ကို အများသုံး gateway၊ ဝန်ခွဲစနစ် သို့မဟုတ် ပြန်ပြောင်း proxy မှတစ်ဆင့် တမင်ဖွင့်ပေးနိုင်သည်။ ထိုအခြေအနေတွင်ပင် ဖြစ်နိုင်သမျှ validator များအကြား peer ဆက်သွယ်မှုနှင့် စီမံခန့်ခွဲရေး endpoint များကို ကန့်သတ်ထားသောကွန်ရက်၌ ထားပါ။

::: tip

VPN ရှာဖွေရေးကိရိယာသည် ထိုရှာဖွေရေးခလုတ်မှ ယာဉ်ကြောကိုသာ ကာကွယ်ပေးသည်။ ထိုလုပ်ငန်းစဉ်များကို တစ်ကိုယ်ရေကွန်ရက်တစ်ခုတည်းမှတစ်ဆင့် လမ်းညွှန်မပို့ဘဲ `iroha3d`, CLI, SDK, SSH၊ မက်ထရစ်များသို့မဟုတ် Backup Traffic များကို ကာကွယ်ခြင်းမရှိပါ။

:::

## တပ်ဆင်မှု ပုံစံ {#deployment-pattern}

ပုဂ္ဂလိက validator ချိတ်ဆက်ကွန်ရက်အတွက် validator တိုင်းအား တည်ငြိမ်သော VPN လိပ်စာ သို့မဟုတ် ပုဂ္ဂလိက DNS အမည် ပေးပါ။ အခြား validator များက ထိုကွန်ရက်မှတစ်ဆင့် ၎င်းတို့ကြေညာထားသော peer အချင်းချင်း ဆက်သွယ်ရေးလိပ်စာများသို့ ရောက်ရှိနိုင်အောင် peer များကို ပြင်ဆင်သတ်မှတ်ပါ။

```toml
trusted_peers = [
  "PUBLIC_KEY_1@10.20.0.11:1337",
  "PUBLIC_KEY_2@10.20.0.12:1337",
  "PUBLIC_KEY_3@10.20.0.13:1337",
  "PUBLIC_KEY_4@10.20.0.14:1337",
]

[network]
address = "10.20.0.11:1337"
public_address = "10.20.0.11:1337"

[torii]
address = "10.20.0.11:8080"
```

`network.address` နှင့် `network.public_address` တို့တွင် လက်ရှိကွန်ရက် peer ကိုသတ်မှတ်ထားသောလိပ်စာကို အသုံးပြုပါ။ ကွန်ရက် peer တစ်ခုစီသည် အလားတူ ယုံကြည်မှုရှိသည့် ကွန်ရက် peers အမည်များကို စာရင်းသွင်းသင့်သော်လည်း ၎င်း၏ ကိုယ်ပိုင် VPN လမ်းကြောင်းဇယားမှ ဝင်ရောက်နိုင်သောလိပ်စာများနှင့်အတူ။

Client နှင့် CLI ဖွဲ့စည်းပုံများသည် Torii API အကန့်အသတ်မှတ်ချက်သို့ ညွှန်ပြသင့်ပြီး VPN သို့မဟုတ် ထိန်းချုပ်သော အတွင်းရေးဂိတ်တစ်ခုမှတစ်ဆင့် ရောက်ရှိနိုင်သည်။

```toml
torii_url = "http://10.20.0.11:8080"
```

Torii ကို VPN အပြင်မှာ ရယူနိုင်ရန်ရှိပါက ၎င်းကို TLS၊ စစ်ဆေးခြင်း၊နှုန်းသတ်မှတ်ခြင်းနှင့် မှတ်တမ်းတင်ခြင်းတို့ကိုပေးသော ပြန်လည်အထောက်အပံ့ (သို့မဟုတ်) ဝန်ဆောင်မှု ဟန်ချက်ညီစက်နောက်ကွယ်တွင်ထားပါ။ အရည်အသွေးတူချင်းဆန့်ကျင်ရေးဆိပ်ကမ်းများ သို့မဟုတ် စီမံခန့်ခွဲမှု အဆုံးစွန်များ API ကို အများပြည်သူ အင်တာနက်သို့ တိုက်ရိုက် ဖော်ပြခြင်း ရှောင်ရှားပါ။

## Firewall စည်းမျဉ်းများ {#firewall-rules}

VPN ရှိပါကတောင် host နဲ့ cloud firewall စည်းမျဉ်းတွေကို သုံးပါ။

|ဝန်ဆောင်မှု |အကြံပြုချက်များ|
| --- | --- |
|Peer-to-peer ဆိပ်ကမ်း|အခြားအတည်ပြုသူ VPN အမည်များသာ |
| Torii | အက်ပ် backend များ၊ အော်ပရေတာများ သို့မဟုတ် ယုံကြည်ထားသော client VPN လိပ်စာအပိုင်းအခြားများ |
|မက်ထရစ်များနှင့် ကျန်းမာရေးစစ်ဆေးမှုများ |လုပ်ငန်းရှင်ကွန်ရက်ပေါ်ရှိ စောင့်ကြည့်ရေးစနစ်များ |
|SSH နဲ့ စီမံခန့်ခွဲမှု |Bastion host, privileged operator VPN range သို့မဟုတ် ပြတင်းပေါက်ကွဲခြင်း process |
| အရန်သိမ်းဆည်းမှုနှင့် သိုလှောင်မှုမိတ္တူကူးခြင်း | ပုဂ္ဂလိကကွန်ရက်ပေါ်ရှိ အရန်သိမ်းဆည်းရေးစနစ်များ |

Default-denial စည်းမျဉ်းများကို broad allow စည်းမျဉ်းများထက် စစ်ဆေးရန် ပိုလွယ်ကူသည်။ ကွန်ရက် peer အသစ်တစ်ခုကွန်ရက်သို့ဝင်ရောက်တဲ့အခါ VPN အဖွဲ့ဝင်စာရင်း၊ firewall allow စာရင်းနှင့် Iroha ယုံကြည်စိတ်ချရသော network peer ဖွဲ့စည်းမှုကို ညှိနှိုင်းပြောင်းလဲမှု တစ်ခုအဖြစ် update လုပ်ပါ။

## စီမံခန့်ခွဲမှု စစ်ဆေးစာရင်း {#operational-checklist}

- VPN အကောင်အထည်ဖော်မှုကို စစ်ဆေးပြီး တက်ကြွစွာ ထိန်းသိမ်းထားသော WireGuard, IPsec သို့မဟုတ် အဖွဲ့အစည်းက ခွင့်ပြုသည့် စီမံခန့်ခွဲမှု သီးသန့်ကွန်ရက်ကို ရွေးပါ။
- host နှင့် operator တစ်ခုချင်းအတွက် ထူးခြားသော VPN ခိုင်ခံ့ချက်များကို အသုံးပြုပါ။ validator များအကြား VPN သော့ကိုမမျှဝေပါနဲ့။
- VPN ခွင့်ပြုချက်များကို Iroha ပုဂ္ဂလိက သော့များနှင့် blockchain genesis လက်မှတ်ရေးထိုးမှု ပစ္စည်းများမှ သီးခြားထားပါ။
- VPN နှောင့်နှေးမှု၊ ပက်ကက် ဆုံးရှုံးမှု၊ ပြန်လည်ဆက်သွယ်ခြင်း၊ လမ်းကြောင်းပြောင်းလဲခြင်းများကို စောင့်ကြည့်ပါ။ သဘောတူညီချက်သည် ရေရှည်တည်တံ့သော ကွန်ရက် မတည်ငြိမ်မှုအတွက် ထိခိုက်လွယ်သည်။
- ထိရောက်တဲ့ MTU ကို စမ်းသပ်ပါ။ Package fragmentation ဟာ ကြားဖြတ်ကွန်ရက် peer (သို့) Torii ကျရှုံးမှုလို ထင်ရှားနိုင်ပါတယ်။
- VPN နယ်နိမိတ်များကို peer-to-peer, Torii, metrics, SSH နှင့် backup API အဆုံးမှတ်များသို့ရောက်ရှိခွင့်ပြုထားသောစာရွက်စာတမ်း။
- host, operator account (သို့) အဖွဲ့အစည်းတစ်ခုက ကွန်ရက်မှ ထွက်သွားတဲ့အခါ VPN ခွင့်ပြုချက်များကို လှည့်ပါ။
- validator တွေအကြား တစ်ခုတည်းသောလမ်းကြောင်းအဖြစ် VPN gateway ကို ရှောင်ရှားပါ။ ထုတ်လုပ်ရေးကွန်ရက်များအတွက် redundant gateways သို့မဟုတ် site-to-site routes များကို စီစဉ်ပါ။
- VPN ကျရှုံးမှုများကို incident response drills များတွင် ထည့်သွင်းပါက operator များသည် network partition ကို Iroha process failure မှ ခွဲခြားရန်အချိန်ကိုသိရှိနိုင်သည်။
