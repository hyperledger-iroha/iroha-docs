# လှည့်စားမှု စောင့်ကြည့်ခြင်း {#fraud-monitoring}

Iroha deployment အတွက်လှည့်စားမှု စောင့်ကြည့်ခြင်းသည် ledger ဖြစ်ရပ်များ၊ မေးမြန်းမှုများ၊ ခွင့်ပြုချက်များနှင့် application context တို့ကို အခြေခံ၍ တည်ဆောက်ထားသော လုပ်ဆောင်မှု ထိန်းချုပ်မှုတစ်ခုဖြစ်သည်။ Iroha သည်တင်သွင်းခြင်း၊ လက်ခံခြင်း၊ ပယ်ချခြင်းနှင့် ကျင့်သုံးခြင်းကို မှတ်တမ်းတင်သည်။ သင့်ရဲ့ စောင့်ကြည့်ရေးစနစ်က သင့်စီးပွားရေးလုပ်ငန်းစဉ်အတွက် သံသယရှိတဲ့ ပုံစံတွေကို ဆုံးဖြတ်ပြီး ဒီကိစ္စတွေကို သုံးသပ်သူ (သို့) အလိုအလျောက် တုံ့ပြန်မှု ထိန်းချုပ်မှုဆီ ပို့ပေးတယ်။

လိမ်လည်မှု စောင့်ကြည့်မှုကို validator တွင်ထည့်သွင်းထားသော ဆင်ခြင်တုံတရားအစား သီးခြားဝန်ဆောင်မှုတစ်ခုအဖြစ် ရှုမြင်ပါ။ ဝန်ဆောင်မှုက စာရင်းအင်းလုပ်ဆောင်မှုကို လက်မှတ်ထိုးခြင်း၊ ကွင်းဆက်ပြင်ပ အန္တရာယ် အခြေအနေဖြင့် ချမ်းသာစေခြင်း၊ အထောက်အထားတည်ငြိမ်ခြင်းနှင့် တုံ့ပြန်မှုလုပ်ငန်းများကို ရှင်းလင်းစွာ ခွင့်ပြုချက်များရှိသည့် အကောင့်များမှတစ်ဆင့်သာ တင်ပြသင့်သည်။

## စောင့်ကြည့်မှုပုံစံ {#monitoring-model}

အသုံးဝင်တဲ့ စောင့်ကြည့်မှု ပိုက်လိုင်းမှာ အဆင့် လေးခုရှိပါတယ်။

1. Torii အဖြစ်အပျက်စီးကြောင်းများ၊ မေးမြန်းချက်များနှင့် မက်ထရစ်များမှ စာရင်းအင်းနှင့် လုပ်ငန်းရှင် အချက်ပြမှုများကို စုစည်းပါ။
2. အခင်းဖြစ်စဉ်များကို ဖောက်သည်အခြေအနေ၊ ငွေပေးချေသူ စာရင်းများ၊ လျှောက်လွှာအစည်းအဝေး မှတ်ချက်များ၊ မျှော်မှန်းထားသော အကန့်အသတ်များနှင့် အမှု IDs ကဲ့သို့သော ကွင်းဆက်ပြင်ပ အခြေအနေများဖြင့် ချဲ့ထွင်ပါ။
3. တိကျတဲ့ စည်းမျဉ်းတွေ၊ သုံးသပ်သူတန်းတွေ (သို့) အရဲစွန့်မှတ်ချက်တွေနဲ့ သံသယရှိတဲ့ အပြုအမူကို ရှာဖွေပါ။
4. အော်ပရေတာတွေကို သတိပေးခြင်း၊ အက်ပ်ဘက် အလုပ်ခွင်ကို ရပ်ဆိုင်းခြင်း၊ မလိုလားအပ်တဲ့ ခွင့်ပြုချက်တွေကို ရုပ်သိမ်းခြင်း (သို့) သင့်အုပ်ချုပ်ရေး လုပ်ငန်းစဉ်က ခွင့်ပြုတဲ့အခါ လျော်ကြေးငွေ ငွေလဲလှယ်မှုကို တင်သွင်းခြင်းဖြင့် တုံ့ပြန်ပါ။

မူဝါဒဆုံးဖြတ်ချက်များကို သဘောတူညီမှုမရှိဘဲ ထိန်းသိမ်းပါကသာ အကောင်အထည်ဖော်သူတိုင်းဟာ အလားတူဆုံးဖြတ်ချက်ကို ပြန်လည်ဖြည့်ဆည်းပေးရပါမယ်။ Runtime အတည်ပြုချက်သည် ခွင့်ပြုချက်များနှင့် ငွေကြေးပူးပေါင်းဆောင်ရွက်မှုများ၏ သက်တမ်းကို အာမခံသင့်သည်။ လှည့်စားမှု စောင့်ကြည့်ခြင်းသည် အရဲစွန့်မှုကို ရှင်းလင်းစေရန်၊ အထောက်အထားများကို သိမ်းဆည်းရယူရန်နှင့် လုပ်ငန်းရှင်များကို လျင်မြန်စွာ လုပ်ဆောင်ရန်ကူညီရမည်။

## အချက်ပြမှုများကို စုစည်းရန် {#signals-to-collect}

သေးငယ်တဲ့ subscriptions ကနေစပြီး စုံစမ်းရေးအတွက်သာ ပိုကျယ်ပြန့်တဲ့ stream တွေကို ထည့်ပါ။

|အချက်ပြချက်|အရင်းအမြစ်|အသုံးပြုခြင်း |
| --- | --- | --- |
|ငွေပေးချေမှုအခြေအနေ |ပိုက်လိုင်း ဖြစ်ရပ်များ |ထပ်တလဲလဲ ငြင်းပယ်မှုတွေ၊ ကျရှုံးတဲ့ ခွင့်ပြုချက် ကြိုးပမ်းမှုတွေ နဲ့ ထူးဆန်းတဲ့ တင်ပြမှု ပုံစံတွေကို ရှာဖွေပါ။ |
|Account lifecycle နဲ့ metadata တွေကို |ဒေတာဖြစ်ရပ်များနှင့် အကောင့် မေးမြန်းချက်များ |အကောင့်သစ်များ၊ အမည်မပြောင်းမှုများ၊ ကိုယ်စားလှယ်လက္ခဏာ အသစ်များနှင့် မမျှော်လင့်ဘဲ metadata ကို ပြင်ဆင်ခြင်းများကို ရှာဖွေပါ။ |
|အရင်းအမြစ်စာရင်းများနှင့် ငွေလွှဲပြောင်းမှု |Asset data ဖြစ်ရပ်များနှင့် asset queries များ |တန်ဖိုးမြင့်တဲ့ လှုပ်ရှားမှုတွေ၊ မြန်ဆန်တဲ့ လေထွန်းထွက်မှု၊ ဟန်ချက်ညီတဲ့ ရေစီးဆင်းမှုတွေနဲ့ ထူးဆန်းတဲ့ ဆန့်ကျင်ဘက်တွေကို ရှာဖွေပါ။ |
|အခန်းကဏ္ဍများနှင့် ခွင့်ပြုချက်များ |အခန်းကဏ္ဍနှင့် ခွင့်ပြုချက် မေးမြန်းမှုများ၊ အခန်းကန့် အချက်အလက်များ ဖြစ်ရပ်များ |အခွင့်အရေး တိုးတက်မှုတွေ၊ အရေးပေါ် ထောက်ပံ့မှုတွေ နဲ့ အန္တရာယ်များတဲ့ ဝင်ရောက်ခွင့်တွေ ရှာဖွေပါ။|
|Trigger နှင့် စာချုပ်ပြောင်းလဲမှု |Trigger၊ Contract နဲ့ executor ဖြစ်ရပ်တွေ |အလိုအလျောက် ပြုလုပ်မှု အသစ်တွေ၊ အကောင်အထည်ဖော်ရေး လမ်းကြောင်းတွေ ပြောင်းလဲတာတွေနဲ့ သံသယရှိတဲ့ အဆင့်မြှင့်တင်မှု လှုပ်ရှားမှုတွေ ရှာဖွေပါ။ |
|Configuration နှင့် peer ပြောင်းလဲမှု |Configuration နှင့် peer events များ |Validation, networking သို့မဟုတ် operator ရဲ့ မြင်နိုင်မှုကို သက်ရောက်စေတဲ့ အုပ်ချုပ်မှုအပြောင်းအလဲတွေကို ရှာဖွေပါ။ |
|လုပ်ငန်းရှင် ကျန်းမာရေး |`/metrics` နှင့် Sumeragi အခြေအနေလမ်းကြောင်းများ |node overload၊ queue pressure (သို့) network fault တွေကနေ သံသယရှိတဲ့ user အပြုအမူကို ခွဲခြားပါ။ |

[event filters](/my/blockchain/filters.md) ကို အသုံးပြုပြီး စည်းမျဉ်းတစ်ခုမှာ အကောင့်များ၊ အရင်းအမြစ်များ၊ အခန်းကဏ္ဍများ သို့မဟုတ် ဖွဲ့စည်းပုံပြောင်းလဲမှုများသာ လိုအပ်တဲ့အခါ ဖြစ်စဉ်စီးကြောင်းတစ်ခုလုံးကို စီမံခန့်ခွဲခြင်းကို ရှောင်ရှားပါ။ အကြိမ်ကြိမ် ချိတ်ဆက်နိုင်ရန်အတွက် စီးဆင်းမှုကို စာမျက်နှာဖြည့်ထားသော [quest ](/my/blockchain/queries.md) နှင့် ပေါင်းစပ်၍ မော်နီတာသည် ရပ်တန့်မှုနောက်တွင် ပြန်လည်ထူထောင်နိုင်သည်။

## ရှာဖွေရေး စည်းမျဉ်းများ {#detection-rules}

|အုပ်ချုပ်ရေးမိသားစု|ဥပမာ အခြေအနေ|ပုံမှန် တုံ့ပြန်မှု |
| --- | --- | --- |
|အမြန်နှုန်း |အကောင့်တစ်ခုက မျှော်မှန်းထားတဲ့ ပမာဏ (သို့) ရေတွက်မှုထက်ကို အတိုအကျဉ်းအတွင်း လွှဲပြောင်းပေးတယ်။ |အဲဒီစာရင်းအတွက် ကြိုတင်အသိပေးသူများနှင့် လျှောက်ထားချက်ဘက်မှ ငွေထုတ်ယူမှုများကို ရပ်ဆိုင်း |
|ပျံ့နှံ့ခြင်း |ငွေကြေးက အကောင့်တစ်ခုကနေ အသစ်တွေ့တဲ့ အကောင့်များစွာကို ရွေ့ရှားပါတယ်။|နောက်ထပ် ငွေလွှဲပြောင်းခွင့်မပြုခင် လက်စွဲလက်မှတ်ကို တောင်းဆိုပါ။|
|ဟန်ချက်ညီမှုလျှော့ချခြင်း |Key, alias သို့မဟုတ် metadata ပြောင်းလဲပြီး မကြာမီမှာ account balance ရဲ့ ကြီးမားတဲ့ အစိတ်အပိုင်းတစ်ခု ထွက်သွားတယ်။ |ဖြစ်နိုင်သလောက် အကောင့်သိမ်းယူမှု တိုးမြှင့်ပါ။ |
|အခွင့်အရေး တိုးတက်မှု |အန္တရာယ်များတဲ့ ခွင့်ပြုချက် (သို့) အခန်းကဏ္ဍကို ပြောင်းလဲမှု ပြတင်းပေါက်အပြင်မှာ ပေးအပ်ပါတယ်။|ထောက်ပံ့မှုလုပ်ငန်းရှင်တွေကို သတိပေးပြီး ငွေကြေးထောက်ပံ့မှု လုပ်ငန်းကို ပြန်လည်သုံးသပ်ခြင်း |
|ငြင်းပယ်မှု ပေါက်ကွဲခြင်း |လက်မှတ်ရေးထိုးသူ (သို့) ဖောက်သည်တစ်ဦးက ထပ်တလဲလဲ ပယ်ချထားသော ငွေကြေးမှုများကို ပြုလုပ်သည်။ |ခွင့်ပြုချက် အလွဲသုံးစား၊ ပေါင်းစပ်မှု အမှားများ သို့မဟုတ် စစ်ဆေးမှုများအတွက် စစ်ဆေးပါ။ |
|အလိုအလျောက်ပြောင်းလဲခြင်း |trigger၊ contract သို့မဟုတ် executor နဲ့ဆိုင်တဲ့ အရာဝတ္ထုတစ်ခုက မမျှော်လင့်ဘဲ ပြောင်းလဲနေပါတယ် |အပြောင်းအလဲကို ပြန်လည်သုံးသပ်မချင်း သက်ဆိုင်ရာ လုပ်ငန်းခွင်တွေကို ရပ်တန့်ပါ။ |
|အုပ်ချုပ်မှုဆိုင်ရာ အပြောင်းအလဲများ |Peer, configuration (သို့) runtime အခြေအနေ ပြောင်းလဲမှုတွေဟာ ခွင့်ပြုချက်မရှိဘဲ ဖြစ်ပေါ်ပါတယ်။|အုပ်ချုပ်မှု မှတ်တမ်းနဲ့ ဖြစ်ရပ်ဖြစ်စဉ်ကို နှိုင်းယှဉ်ကြည့်ပါ။ |

စည်းမျဉ်းတွေဟာ သူတို့လိုအပ်တဲ့ အထောက်အထားတွေ၊ သူတို့ အကဲဖြတ်တဲ့ အချိန်ပြတင်းပေါက်၊ သူတို့လုပ်ဆောင်တဲ့ အရေးယူမှုတွေနဲ့ အမှုကို ပိတ်နိုင်မယ့်လူ (သို့) စနစ်အကြောင်း ရှင်းလင်းစွာ ပြောသင့်တယ်။ ဖောက်သည်အန္တရာယ်၊ အရင်းအမြစ်အမျိုးအစား (သို့) အာဏာပိုင်ခွင့်အပေါ် မူတည်တဲ့ နယ်နိမိတ်တွေဟာ သင့်စောင့်ကြည့်ရေး ဝန်ဆောင်မှု ညွှန်ကြားချက်ထဲမှာ ပါဝင်တယ်၊ ad hoc script တွေမှာ မဟုတ်ဘူး။

## တုံ့ပြန်မှု ထိန်းချုပ်ချက်များ {#response-controls}

သတိပေးချက်များ မပြုလုပ်မီ တုံ့ပြန်မှု အစီအစဉ်များကို ပုံစံထုတ်ပါ။ အလွန်ပြင်းထန်တဲ့ လှည့်စားမှုဖြစ်စဉ်တစ်ခုမှာ ရှာဖွေမှုမှ ထိန်းချုပ်ခြင်းအထိ မှတ်တမ်းတင်ထားတဲ့ လမ်းကြောင်းတစ်ခုရှိသင့်ပါတယ်။

- သက်ရောက်မှုရှိသည့် ဒိုမင် (သို့) အရင်းအမြစ် သတ်မှတ်ချက်အတွက် တာဝန်ယူသော လုံခြုံရေး၊ လုပ်ငန်းများနှင့် စီးပွားရေးလုပ်ငန်းရှင်များကို အသိပေးပါ။
- event cursor, block hash, transaction hash, authority, payload, and query snapshot တွေကို ရှာဖွေရေးစည်းမျဉ်းက အသုံးပြုထားတာကို ထိန်းသိမ်းပါ။
- စာရင်းအင်းပြင်မှာရှိတဲ့ application-side လုပ်ဆောင်ချက်တွေကို ရပ်တန့်ပါ၊ ဥပမာ checkout, withdrawal, signing, bridge, or settlement workflows တွေပေါ့။
- Incident Response Plan တွင် အကြောင်းပြချက်မရှိတော့သော အခန်းကဏ္ဍများ (သို့) ခွင့်ပြုချက်များကို ပယ်ဖျက်ခြင်း၊
- နောက်ဆက်တွဲအုပ်ချုပ်ရေးစာရင်းမှ ငွေကြေးများကို Active Governance မူဝါဒနှင့် ခွင့်ပြုချက်ပုံစံများက ခွင့်ပြုသည့်အခါသာ တင်ပြရမည်။
- လက်မှတ်ရေးထိုးသူက သဘောတူညီချက်ချတယ်လို့ အထောက်အထားတွေရှိတဲ့အခါ သော့တွေကို လှည့်ပါ။

စောင့်ကြည့်ရေး ဝန်ဆောင်မှုကို ကျယ်ပြန့်တဲ့ ရေးသားခွင့်ပေးခြင်းကို ရှောင်ရှားပါ။ တုံ့ပြန်မှု လုပ်ဆောင်ချက်တွေအတွက် လိုအပ်တဲ့ ခွင့်ပြုချက် အနည်းငယ်ဆုံးရှိတဲ့ သီးသန့် နည်းပညာအကောင့်ကို သုံးပါ။ လူရဲ့ ခွင့်ပြုချက်ဟာ အရင်းအမြစ်တွေကို ရွေ့ရှားနိုင်တာ၊ ခွင့်ပြုချက်ကို ပြောင်းလဲနိုင်တာ (သို့) validator ကို မျက်နှာမူတဲ့ ဖွဲ့စည်းမှုကို ပြောင်းနိုင်တဲ့ အလုပ်ဖြစ်စဉ်တစ်ခုရဲ့ အစိတ်အပိုင်းအဖြစ် ဆက်ရှိနေသင့်ပါတယ်။

## အထောက်အထားနှင့် ထိန်းသိမ်းခြင်း {#evidence-and-retention}

အတည်ပြုသူ ဒေတာအညွှန်းအုပ်စုမှ သီးခြားခွဲထားသော Append-only စနစ်တစ်ခုတွင် စောင့်ကြည့်မှု အထောက်အထားများကို သိုလှောင်ပါ။ သတိပေးချက်တိုင်းမှာ အောက်ပါအချက်များ ပါဝင်သင့်သည်။

- event stream နာမည်နှင့် cursor
- Block height သို့မဟုတ် block hash ရှိပါက
- ငွေပေးချေမှု hash နှင့် အာဏာ
- သက်ရောက်မှုရှိသည့်စာရင်း၊ ဒိုမင်၊ အရင်းအမြစ်၊ အခန်းကဏ္ဍ၊ trigger သို့မဟုတ် ဖွဲ့စည်းချက် ID
- raw event payload သို့မဟုတ် canonical hash တစ်ခု
- alert ကို ချမ်းသာစေရန် အသုံးပြုသော query snapshots များ
- စည်းမျဉ်းအမည်၊ ဗားရှင်း၊ တံခါးပိတ်ရက်၊ အမှတ်များနှင့် စစ်ဆေးသူ ဆုံးဖြတ်ချက်

ကွန်ရက်၏ ဒေတာအုပ်ချုပ်ရေးမူဝါဒက ရှင်းလင်းစွာ ခွင့်ပြုချက်မပေးပါက ထိခိုက်လွယ်သော စုံစမ်းစစ်ဆေးမှု မှတ်စုများကို အများပြည်သူစာရင်း metadata အဖြစ် မသိုလှောင်ပါနဲ့။ ချိတ်ဆက်မှုအပြင်ဖြစ်ရပ်ကို ချိတ်ဆက်ရန်လိုအပ်ပါက ပုဂ္ဂလိကအချက်အလက်များကို ဖော်ပြခြင်းမရှိသည့် အမှုမှတ်တမ်း၊ လက်မှတ်ထိုးသက်သေခံချက် (သို့မဟုတ်) hash ကတိထားမှုကို ကြိုက်နှစ်သက်ပါ။

## အကောင်အထည်ဖော်မှု စစ်ဆေးစာရင်း {#implementation-checklist}

- `/metrics` နှင့် operator လမ်းကြောင်းများအတွက် လိုအပ်သော telemetry profile ကို enable လုပ်ပါ။
- သင်စောင့်ကြည့်တဲ့ အရာဝတ္ထုတွေအတွက် သေးငယ်တဲ့ စစ်ဆေးမှုတွေနဲ့ Torii ဖြစ်ရပ်စီးကြောင်းတွေကို လက်မှတ်ထိုးပါ။
- Monitor ဟာ အပေါက်တွေမရှိဘဲ ပြန်လည်စတင်နိုင်အောင် Event Cursors တွေကို ဆက်ထားပါ။
- ပုံမှန် အစီအစဉ်တစ်ခုမှာ စာမျက်နှာဖြည့်ထားတဲ့ မေးခွန်းတွေနဲ့ stream တွေကို ညှိပေးပါ။
- Risk threshold တွေကို ထိန်းထားပြီး version controlled configuration မှာ lists ကိုခွင့်ပြုပါ။
- အလိုအလျောက် လုပ်ဆောင်မှု မပြုလုပ်ခင် သမိုင်းဝင် ဘလော့တွေကို စစ်ဆေးတဲ့ သတိပေးချက် စည်းမျဉ်းတွေ။
- တုံ့ပြန်မှု လုပ်ဆောင်ချက်များအတွက် သီးသန့် နည်းပညာစာရင်းများကို အသုံးပြုပါ။
- ပြန်လည်သုံးသပ်မှု အခန်းကဏ္ဍနှင့် ခွင့်ပြုချက် ထောက်ပံ့မှုများကို ထပ်တလဲလဲ ပြက္ခဒိန်တစ်ခုဖြင့် ပြုလုပ်ပါ။
- အလိမ်အညာ စောင့်ကြည့်ရေး သတိပေးချက်များကို ဖြစ်စဉ် တုံ့ပြန်မှု လုပ်ငန်းစဉ်ထဲ ထည့်သွင်းပါ။
