# လှည့်စားမှု စောင့်ကြည့်ခြင်း {#fraud-monitoring}

Iroha ဖြန့်ချိတပ်ဆင်မှု အတွက် လိမ်လည်မှုစောင့်ကြည့်ရေးသည် လယ်ဂျာဖြစ်ရပ်များ၊ query များ၊ ခွင့်ပြုချက်များနှင့် အက်ပ်အသုံးပြုမှုနောက်ခံအပေါ် တည်ဆောက်ထားသော လုပ်ငန်းဆောင်ရွက်မှုဆိုင်ရာ ထိန်းချုပ်မှုဖြစ်သည်။ Iroha က တင်သွင်း၊ လက်ခံ၊ ငြင်းပယ်ပြီး commit လုပ်ခဲ့သည့်အရာများကို မှတ်တမ်းတင်သည်။ သင့်စောင့်ကြည့်ရေးစနစ်က လုပ်ငန်းစဉ်အတွက် မည်သည့်ပုံစံများသည် သံသယဖြစ်ဖွယ်ရှိကြောင်း ဆုံးဖြတ်ပြီး ထိုကိစ္စများကို သုံးသပ်သူများ သို့မဟုတ် အလိုအလျောက်တုံ့ပြန်မှုစနစ်များသို့ ပို့ဆောင်သည်။

လိမ်လည်မှု စောင့်ကြည့်ရေးကို အတည်ပြုသူထဲတွင် ထည့်သွင်းထားသော လော့ဂျစ်အဖြစ် မထားဘဲ သီးခြားဝန်ဆောင်မှုတစ်ခုအဖြစ် သတ်မှတ်ပါ။ ထိုဝန်ဆောင်မှုသည် ဘလော့ခ်ချိန်း စာရင်းလယ်ဂျာ လှုပ်ရှားမှုကို စာရင်းသွင်းနားထောင်ရမည်၊ ကွန်ရက်ပြင်ပ အန္တရာယ်ဆိုင်ရာ အကြောင်းအရာများဖြင့် ဖြည့်စွက်ရမည်၊ အထောက်အထားများကို ရေရှည်သိမ်းဆည်းရမည်၊ ထင်ရှားသော ခွင့်ပြုချက်များရှိသည့် အကောင့်များမှတစ်ဆင့်သာ တုံ့ပြန်ရေး ငွေလွှဲမှုများကို တင်သွင်းရမည်။

## စောင့်ကြည့်မှုပုံစံ {#monitoring-model}

အသုံးဝင်တဲ့ စောင့်ကြည့်ရေး ဆော့ဖ်ဝဲ စီမံခန့်ခွဲမှု အလုပ်ဖြစ်စဉ်မှာ အဆင့် လေးခုရှိပါတယ်။

1. Torii အဖြစ်အပျက်စီးကြောင်းများ၊ မေးမြန်းချက်များနှင့် မက်ထရစ်များမှ blockchain ledger နှင့် operator signal များကို စုစည်းပါ။
2. ဖောက်သည်အခြေအနေ၊ ငွေပေးချေသူ စာရင်းများ၊ လျှောက်လွှာအခမ်းအနား မှတ်သားချက်များ၊ မျှော်မှန်းထားသော ကန့်သတ်ချက်များနှင့် ကိစ္စ ID များလို အဆက်အသွယ်အပြင် အခြေအနေများဖြင့် ဖြစ်ရပ်များကို ချမ်းသာစေပါ။
3. ရလဒ်တူညီစွာထွက်သော စည်းမျဉ်းများ၊ သုံးသပ်သူစောင့်ဆိုင်းတန်းများ သို့မဟုတ် အန္တရာယ်အမှတ်ပေးမှုတို့ဖြင့် သံသယဖြစ်ဖွယ် အပြုအမူကို **ရှာဖွေပါ**။
4. အော်ပရေတာတွေကို သတိပေးခြင်း၊ အက်ပ်ဘက် အလုပ်ခွင်ကို ရပ်ဆိုင်းခြင်း၊ မလိုလားအပ်တဲ့ ခွင့်ပြုချက်တွေကို ရုပ်သိမ်းခြင်း (သို့) သင့်အုပ်ချုပ်ရေး လုပ်ငန်းစဉ်က ခွင့်ပြုတဲ့အခါ လျော်ကြေးငွေ ငွေလဲလှယ်မှုကို တင်သွင်းခြင်းဖြင့် တုံ့ပြန်ပါ။

validator တိုင်းက တူညီသောဆုံးဖြတ်ချက်ကို ပြန်လုပ်ရန် မလိုအပ်လျှင် မူဝါဒဆုံးဖြတ်ချက်များကို သဘောတူညီမှုလုပ်ငန်းစဉ်အပြင်တွင် ထားပါ။ လည်ပတ်ချိန်စစ်ဆေးမှုသည် ခွင့်ပြုချက်များနှင့် transaction မှန်ကန်မှုကို အတည်ပြုရမည်။ လိမ်လည်မှုစောင့်ကြည့်ရေးသည် အန္တရာယ်ကို ရှင်းပြပေးရန်၊ အထောက်အထားကို ထိန်းသိမ်းရန်နှင့် အော်ပရေတာများ လျင်မြန်စွာဆောင်ရွက်နိုင်ရန် ကူညီပေးရမည်။

## အချက်ပြမှုများကို စုစည်းရန် {#signals-to-collect}

သေးငယ်တဲ့ subscriptions ကနေစပြီး စုံစမ်းရေးအတွက်သာ ပိုကျယ်ပြန့်တဲ့ stream တွေကို ထည့်ပါ။

|အချက်ပြချက်|အရင်းအမြစ်|အသုံးပြုခြင်း |
| --- | --- | --- |
|ငွေပေးချေမှုအခြေအနေ |ဆော့ဝဲ စီမံခန့်ခွဲမှု အလုပ်ဖြစ်စဉ်များ |ထပ်တလဲလဲ ငြင်းပယ်မှုတွေ၊ ကျရှုံးတဲ့ ခွင့်ပြုချက် ကြိုးပမ်းမှုတွေ နဲ့ ထူးဆန်းတဲ့ တင်ပြမှု ပုံစံတွေကို ရှာဖွေပါ။ |
|Account lifecycle နဲ့ metadata တွေကို |ဒေတာဖြစ်ရပ်များနှင့် အကောင့် မေးမြန်းချက်များ |အကောင့်သစ်များ၊ အမည်မပြောင်းမှုများ၊ ကိုယ်စားလှယ်လက္ခဏာ အသစ်များနှင့် မမျှော်လင့်ဘဲ metadata ကို ပြင်ဆင်ခြင်းများကို ရှာဖွေပါ။ |
|အရင်းအမြစ်စာရင်းများနှင့် ငွေလွှဲပြောင်းမှု |Asset data ဖြစ်ရပ်များနှင့် asset queries များ |တန်ဖိုးမြင့်တဲ့ လှုပ်ရှားမှုတွေ၊ မြန်ဆန်တဲ့ လေထွန်းထွက်မှု၊ ဟန်ချက်ညီတဲ့ ရေစီးဆင်းမှုတွေနဲ့ ထူးဆန်းတဲ့ ဆန့်ကျင်ဘက်တွေကို ရှာဖွေပါ။ |
|အခန်းကဏ္ဍများနှင့် ခွင့်ပြုချက်များ |အခန်းကဏ္ဍနှင့် ခွင့်ပြုချက် မေးမြန်းမှုများ၊ အခန်းကန့် အချက်အလက်များ ဖြစ်ရပ်များ |အခွင့်အရေး တိုးတက်မှုတွေ၊ အရေးပေါ် ထောက်ပံ့မှုတွေ နဲ့ အန္တရာယ်များတဲ့ ဝင်ရောက်ခွင့်တွေ ရှာဖွေပါ။|
|Trigger နှင့် စာချုပ်ပြောင်းလဲမှု |Trigger၊ Contract နဲ့ executor ဖြစ်ရပ်တွေ |အလိုအလျောက် ပြုလုပ်မှု အသစ်တွေ၊ အကောင်အထည်ဖော်ရေး လမ်းကြောင်းတွေ ပြောင်းလဲတာတွေနဲ့ သံသယရှိတဲ့ အဆင့်မြှင့်တင်မှု လှုပ်ရှားမှုတွေ ရှာဖွေပါ။ |
| ပြင်ဆင်သတ်မှတ်မှုနှင့် peer ပြောင်းလဲမှုများ | ပြင်ဆင်သတ်မှတ်မှုနှင့် peer ဖြစ်ရပ်များ | စစ်ဆေးအတည်ပြုမှု၊ ကွန်ရက်ချိတ်ဆက်မှု သို့မဟုတ် အော်ပရေတာ၏ မြင်နိုင်စွမ်းကို သက်ရောက်သော အုပ်ချုပ်မှုအပြောင်းအလဲများကို ရှာဖွေခြင်း |
|လုပ်ငန်းရှင် ကျန်းမာရေး |`/metrics` နှင့် Sumeragi အခြေအနေလမ်းကြောင်းများ |node overload၊ queue pressure (သို့) network fault တွေကနေ သံသယရှိတဲ့ user အပြုအမူကို ခွဲခြားပါ။ |

စည်းမျဉ်းတစ်ခုက အကောင့်၊ ပိုင်ဆိုင်မှု၊ role သို့မဟုတ် ပြင်ဆင်သတ်မှတ်မှု ပြောင်းလဲမှုများသာ လိုအပ်လျှင် ဖြစ်ရပ် stream တစ်ခုလုံးကို မစစ်ဆေးရစေရန် [ဖြစ်ရပ်စစ်ထုတ်ကိရိယာများ](/my/blockchain/filters.md) ကို အသုံးပြုပါ။ ကာလအလိုက် စာရင်းညှိနှိုင်းရန် stream ကို စာမျက်နှာခွဲထားသော [query များ](/my/blockchain/queries.md) နှင့် ပေါင်းစပ်ပါ။ ထိုသို့ပြုခြင်းဖြင့် ရပ်နားခဲ့ပြီးနောက် စောင့်ကြည့်သူက ပြန်လည်လုပ်ဆောင်နိုင်သည်။

## ရှာဖွေရေး စည်းမျဉ်းများ {#detection-rules}

တူညီတဲ့ စည်းမျဉ်းမိသားစုများမှာ:

|အုပ်ချုပ်ရေးမိသားစု|ဥပမာ အခြေအနေ|ပုံမှန် တုံ့ပြန်မှု |
| --- | --- | --- |
|အမြန်နှုန်း |အကောင့်တစ်ခုက မျှော်မှန်းထားတဲ့ ပမာဏ (သို့) ရေတွက်မှုထက်ကို အတိုအကျဉ်းအတွင်း လွှဲပြောင်းပေးတယ်။ |အဲဒီစာရင်းအတွက် ကြိုတင်အသိပေးသူများနှင့် လျှောက်ထားချက်ဘက်မှ ငွေထုတ်ယူမှုများကို ရပ်ဆိုင်း |
|ပျံ့နှံ့ခြင်း |ငွေကြေးက အကောင့်တစ်ခုကနေ အသစ်တွေ့တဲ့ အကောင့်များစွာကို ရွေ့ရှားပါတယ်။|နောက်ထပ် ငွေလွှဲပြောင်းခွင့်မပြုခင် လက်စွဲလက်မှတ်ကို တောင်းဆိုပါ။|
|ဟန်ချက်ညီမှုလျှော့ချခြင်း |Key, alias သို့မဟုတ် metadata ပြောင်းလဲပြီး မကြာမီမှာ account balance ရဲ့ ကြီးမားတဲ့ အစိတ်အပိုင်းတစ်ခု ထွက်သွားတယ်။ |ဖြစ်နိုင်သလောက် အကောင့်သိမ်းယူမှု တိုးမြှင့်ပါ။ |
|အခွင့်အရေး တိုးတက်မှု |အန္တရာယ်များတဲ့ ခွင့်ပြုချက် (သို့) အခန်းကဏ္ဍကို ပြောင်းလဲမှု ပြတင်းပေါက်အပြင်မှာ ပေးအပ်ပါတယ်။|ထောက်ပံ့မှုလုပ်ငန်းရှင်တွေကို သတိပေးပြီး ငွေကြေးထောက်ပံ့မှု လုပ်ငန်းကို ပြန်လည်သုံးသပ်ခြင်း |
|ထပ်တလဲလဲ ငြင်းပယ်မှု မြင့်တက်လာနေပြီ|Cryptographic လက်မှတ်ရေးထိုးသူ (သို့) ဖောက်သည်တစ်ဦးက ထပ်တလဲလဲ ပယ်ချခံရတဲ့ ငွေပေးချေမှုများကို ပြုလုပ်တယ်။ |ခွင့်ပြုချက် အလွဲသုံးစား၊ ပေါင်းစပ်မှု အမှားများ သို့မဟုတ် စစ်ဆေးမှုများအတွက် စစ်ဆေးပါ။ |
|အလိုအလျောက်ပြောင်းလဲခြင်း |trigger၊ contract သို့မဟုတ် executor နဲ့ဆိုင်တဲ့ အရာဝတ္ထုတစ်ခုက မမျှော်လင့်ဘဲ ပြောင်းလဲနေပါတယ် |အပြောင်းအလဲကို ပြန်လည်သုံးသပ်မချင်း သက်ဆိုင်ရာ လုပ်ငန်းခွင်တွေကို ရပ်တန့်ပါ။ |
|အုပ်ချုပ်မှုဆိုင်ရာ အပြောင်းအလဲများ |Network peer, configuration သို့မဟုတ် software execution environment အခြေအနေ ပြောင်းလဲမှုများကို ခွင့်ပြုချက်မရှိဘဲ ဖြစ်ပေါ်စေပါသည်။ |အုပ်ချုပ်မှု မှတ်တမ်းနဲ့ ဖြစ်ရပ်ဖြစ်စဉ်ကို နှိုင်းယှဉ်ကြည့်ပါ။ |

စည်းမျဉ်းများတွင် လိုအပ်သောအထောက်အထား၊ စစ်ဆေးမည့်အချိန်ကာလ၊ ဆောင်ရွက်မည့်လုပ်ရပ်နှင့် ကိစ္စကို ပိတ်သိမ်းနိုင်သူ သို့မဟုတ် စနစ်တို့ကို ရှင်းလင်းစွာသတ်မှတ်ရမည်။ သုံးစွဲသူအန္တရာယ်၊ ပိုင်ဆိုင်မှုအမျိုးအစား သို့မဟုတ် တရားစီရင်ပိုင်ခွင့်ဒေသအပေါ် မူတည်သော ကန့်သတ်တန်ဖိုးများကို ယာယီ script များထက် စောင့်ကြည့်ရေးဝန်ဆောင်မှု၏ ပြင်ဆင်သတ်မှတ်မှုထဲတွင် ထားပါ။

## တုံ့ပြန်မှု ထိန်းချုပ်ချက်များ {#response-controls}

သတိပေးချက်များ မပြုလုပ်မီ တုံ့ပြန်မှု အစီအစဉ်များကို ပုံစံထုတ်ပါ။ အလွန်ပြင်းထန်တဲ့ လှည့်စားမှုဖြစ်စဉ်တစ်ခုမှာ ရှာဖွေမှုမှ ထိန်းချုပ်ခြင်းအထိ မှတ်တမ်းတင်ထားတဲ့ လမ်းကြောင်းတစ်ခုရှိသင့်ပါတယ်။

- သက်ရောက်မှုရှိသည့် ဒိုမင် (သို့) အရင်းအမြစ် သတ်မှတ်ချက်အတွက် တာဝန်ယူသော လုံခြုံရေး၊ လုပ်ငန်းများနှင့် စီးပွားရေးလုပ်ငန်းရှင်များကို အသိပေးပါ။
- ရှာဖွေစည်းမျဉ်းက အသုံးပြုခဲ့သော ဖြစ်ရပ် cursor၊ ဘလော့ခ်ဟက်ရှ်၊ transaction ဟက်ရှ်၊ authority အကောင့်၊ payload နှင့် query အခြေအနေ snapshot တို့ကို ထိန်းသိမ်းပါ
- blockchain ledger အပြင်မှာရှိတဲ့ application-side လုပ်ဆောင်ချက်တွေကို ရပ်တန့်ပါ။ ဥပမာ checkout, withdrawal, signing, bridge, or financial transaction settlement workflows တွေလိုပေါ့။
- Incident Response Plan တွင် အကြောင်းပြချက်မရှိတော့သော အခန်းကဏ္ဍများ (သို့) ခွင့်ပြုချက်များကို ပယ်ဖျက်ခြင်း၊
- လက်ရှိအုပ်ချုပ်မှုမူဝါဒနှင့် ခွင့်ပြုချက်မော်ဒယ်က ခွင့်ပြုမှသာ နောက်ဆက်တွဲ လယ်ဂျာ transaction များကို တင်သွင်းပါ
- လက်မှတ်ထိုးသူ၏ လုံခြုံရေးပေါက်ကြားကြောင်း အထောက်အထားရှိလျှင် ကီးများကို လဲလှယ်ပါ

စောင့်ကြည့်ရေး ဝန်ဆောင်မှုကို ကျယ်ပြန့်တဲ့ ရေးသားခွင့်ပေးခြင်းကို ရှောင်ရှားပါ။ တုံ့ပြန်မှု လုပ်ဆောင်ချက်များအတွက် လိုအပ်တဲ့ ခွင့်ပြုချက် အနည်းငယ်ဆုံးပါတဲ့ သီးသန့် နည်းပညာ အကောင့်ကို အသုံးပြုပါ။ လူသားရဲ့ ခွင့်ပြုချက်ဟာ အရင်းအမြစ်တွေကို ရွေ့ရှားနိုင်တာ၊ ခွင့်ပြုချက်ကို ပြောင်းနိုင်တာ (သို့) validator ကို မျက်နှာမူတဲ့ ဖွဲ့စည်းမှုကို ပြောင်းလဲနိုင်တဲ့ အလုပ်ဖြစ်စဉ်တစ်ခုလုံးရဲ့ အစိတ်အပိုင်းအဖြစ် ကျန်ရစ်သင့်တယ်။

## အထောက်အထားနှင့် ထိန်းသိမ်းခြင်း {#evidence-and-retention}

အတည်ပြုသူ ဒေတာအညွှန်းအုပ်စုမှ သီးခြားခွဲထားသော Append-only စနစ်တစ်ခုတွင် စောင့်ကြည့်မှု အထောက်အထားများကို သိုလှောင်ပါ။ သတိပေးချက်တိုင်းမှာ အောက်ပါအချက်များ ပါဝင်သင့်သည်။

- event stream နာမည်နှင့် cursor
- Block height (သို့) block cryptographic hash ရှိရင်
- transaction cryptographic hash နှင့် ခွင့်ပြုချက် အရင်းအမြစ်
- သက်ရောက်မှုရှိသော အကောင့်၊ domain၊ ပိုင်ဆိုင်မှု၊ role၊ trigger သို့မဟုတ် ပြင်ဆင်သတ်မှတ်မှု ID
- raw event payload သို့မဟုတ် protocol-standard တစ်ခုတည်းသော cryptographic hash တစ်ခု
- alert ကို ချမ်းသာစေဖို့ အသုံးပြုတဲ့ point-in-time data views တွေကို query လုပ်ပါ။
- စည်းမျဉ်းအမည်၊ ဗားရှင်း၊ တံခါးပိတ်ရက်၊ အမှတ်များနှင့် စစ်ဆေးသူ ဆုံးဖြတ်ချက်

ကွန်ရက်၏ ဒေတာအုပ်ချုပ်မှုမူဝါဒက အတိအလင်း မခွင့်ပြုလျှင် အထိခိုက်မခံသော စုံစမ်းရေးမှတ်စုများကို အများမြင်နိုင်သော လယ်ဂျာ metadata အဖြစ် မသိမ်းပါနှင့်။ ဘလော့ခ်ချိန်းပြင်ပကိစ္စကို ဘလော့ခ်ချိန်းပေါ်ရှိ အခြေအနေနှင့် ချိတ်ရန် လိုအပ်လျှင် ကိုယ်ရေးအချက်အလက်များ မဖော်ထုတ်သော ကိစ္စအမှတ်အသား၊ လက်မှတ်ထိုးအတည်ပြုချက် သို့မဟုတ် ဟက်ရှ်ကတိပြုတန်ဖိုးကို ဦးစားပေးပါ။

## အကောင်အထည်ဖော်မှု စစ်ဆေးစာရင်း {#implementation-checklist}

- `/metrics` နှင့် အော်ပရေတာလမ်းကြောင်းများအတွက် လိုအပ်သော စောင့်ကြည့်တိုင်းတာမှု ပရိုဖိုင်ကို ဖွင့်ပါ။
- သင်စောင့်ကြည့်တဲ့ အရာဝတ္ထုတွေအတွက် သေးငယ်တဲ့ စစ်ဆေးမှုတွေနဲ့ Torii ဖြစ်ရပ်စီးကြောင်းတွေကို လက်မှတ်ထိုးပါ။
- Monitor ဟာ အပေါက်တွေမရှိဘဲ ပြန်လည်စတင်နိုင်အောင် Event Cursors တွေကို ဆက်ထားပါ။
- ပုံမှန်အချိန်ဇယားဖြင့် stream များကို စာမျက်နှာခွဲထားသော query များနှင့် စာရင်းညှိပါ။
- အန္တရာယ်ကန့်သတ်တန်ဖိုးများနှင့် ခွင့်ပြုစာရင်းများကို ဗားရှင်းထိန်းချုပ်ထားသော ပြင်ဆင်သတ်မှတ်မှုထဲတွင် ထားပါ။
- အလိုအလျောက် လုပ်ဆောင်မှု မပြုလုပ်ခင် သမိုင်းဝင် ဘလော့တွေကို စစ်ဆေးတဲ့ သတိပေးချက် စည်းမျဉ်းတွေ။
- တုံ့ပြန်မှု လုပ်ဆောင်ချက်များအတွက် သီးသန့် နည်းပညာစာရင်းများကို အသုံးပြုပါ။
- ပြန်လည်သုံးသပ်မှု အခန်းကဏ္ဍနှင့် ခွင့်ပြုချက် ထောက်ပံ့မှုများကို ထပ်တလဲလဲ ပြက္ခဒိန်တစ်ခုဖြင့် ပြုလုပ်ခြင်း။
- အလိမ်အညာ စောင့်ကြည့်ရေး သတိပေးချက်များကို ဖြစ်စဉ် တုံ့ပြန်မှု လုပ်ငန်းစဉ်ထဲ ထည့်သွင်းပါ။
