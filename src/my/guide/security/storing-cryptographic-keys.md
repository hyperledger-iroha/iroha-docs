# Cryptographic Key ကို သိုလှောင်ခြင်း {#storing-cryptographic-keys}

ပုဂ္ဂလိက သော့ဟာ ၎င်းရဲ့ ခွင့်ပြုချက် မူပိုင်ရှင်ကို အမိန့်ပေးထားတဲ့ လုပ်ဆောင်မှုတိုင်းကို ခွင့်ပြုနိုင်ပါတယ်။ ပုဂ္ဂလိက် သော့ကို ဘယ်တော့မှ မမျှဝေပါနဲ့။ မျိုးစေ့ပစ္စည်း၊ ပြန်လည်ထူထောင်ရေး လျှို့ဝှက်ချက်တွေ၊ ကိုင်ဆောင်သူ လက်မှတ်များနဲ့ တင်ပို့တဲ့ သော့ဖိုင်တွေကိုလည်း တူညီတဲ့ ဂရုစိုက်မှုနဲ့ ကာကွယ်ပါ။

ထုတ်လုပ်မှုကို မစတင်ခင် ထိန်းသိမ်းရေး ဒီဇိုင်းကို ရွေးချယ်ပါ။ ဒီဇိုင်းဟာ အန္တရာယ် တန်ဖိုး၊ အကောင့်ထိန်းချုပ်သူ မူဝါဒနဲ့ ဖြန့်ချိမှု ပြန်လည်ထူထောင်ရေး လုပ်ငန်းစဉ်နဲ့ ကိုက်ညီဖို့လိုပါတယ်။

## စောင့်ရှောက်မှု နယ်နိမိတ်ကို သတ်မှတ်ပါ {#define-the-custody-boundary}

- ခွင့်ပြုချက် အရင်းအမြစ်၊ အများသုံး သော့၊ အယ်လ်ဂိုရစ်သမ်၊ ပတ်ဝန်းကျင်၊ ရည်ရွယ်ချက်၊ ထိန်းသိမ်းသူ၊ သိုလှောင်ရာနေရာ၊ Backup နှင့် အစားထိုးမှု လုပ်ငန်းစဉ်တစ်ခုစီကို စာရင်းသွင်းပါ။
- ဖွံ့ဖြိုးမှု၊ စမ်းသပ်မှု၊ ထုတ်လုပ်မှု၊ ပုံမှန် ငွေကြေးဆောင်ရွက်မှု၊ အုပ်ချုပ်ရေး၊ ဖြန့်ချိခြင်းနဲ့ ပြန်လည်ထူထောင်ရေးအတွက် သီးခြား သော့တွေကို သုံးပါ။
- လူတွေနဲ့ လုပ်ငန်းစဉ်တွေကို သူတို့ရဲ့ အခန်းကဏ္ဍကြောင့် လိုအပ်တဲ့ သော့တွေပဲ ရယူခွင့်ပေးပါ။
- တန်ဖိုးမြင့် သို့မဟုတ် အုပ်ချုပ်မှု လက်မှတ်ရေးထိုးခြင်းအတွက် လွတ်လပ်တဲ့ ခွင့်ပြုချက် လိုအပ်ပါက အရဲစွန့်မှုပုံစံက တောင်းဆိုပါတယ်။
- လက်မှတ်ရေးထိုးသူသည် မည်သည့်ကွန်ရက်နှင့် ခွင့်ပြုချက် မူဝါဒကို အသုံးပြုနိုင်သည်ကို မှတ်တမ်းတင်ပါ။ လက်မှတ်ရေးဆွဲမှု ဝန်ဆောင်မှုသည် ထိုအကန့်အသတ်အပြင် အခြားတောင်းဆိုမှုများအား ပယ်ချရမည်။

## သင့်တော်သော သိုလှောင်နည်းကို ရွေးချယ်ပါ။ {#choose-an-appropriate-storage-method}

ဒေသတွင်းဖွံ့ဖြိုးရေး၊ ထိန်းချုပ်မှု စမ်းသပ်မှုများ သို့မဟုတ် လုံခြုံသော သိမ်းဆည်းမှု လွှဲပြောင်းခြင်းများအတွက် သော့ကို ခွင့်ပြုချက် ကန့်သတ်ထားသည့် ဖိုင်သို့ တင်ပို့နိုင်သည်။ ထောက်ပံ့သော Unix ပလက်ဖောင်းတွင် `kagami` ဖြင့် သော့ညွှန်ကြားစာအုပ်အသစ်တစ်ခု ဖန်တီးပါ။

```bash
cargo run --bin kagami -- keys --algorithm ed25519 --out-dir ./client-key
```

မူရင်း directory ရှိရပါမယ်။ ရည်မှန်းချက်ဟာ အသစ်ဖြစ်သင့်တယ်၊ ဒါမှမဟုတ် လက်ရှိ အသုံးပြုသူပိုင်ဆိုင်နေပြီ ဖြစ်သင့်တယ်။ `0700`, သင်္ကေတဆိုင်ရာ သံယောဇဉ်တွေ ကင်းလွတ်ပြီး အလွတ်ပါ။ Kagami စာရေးသည် `public.key` နှင့် `private.key` mode နဲ့ `0600`; `--pop` စာရေးသူလည်း `pop.hex`. ပလက်ဖောင်းတွေမှာ အမိန့် ပျက်ကွက်တယ်။ Kagami ပိုင်ရှင်တစ်ဦးတည်းရဲ့ ဖိုင်စနစ် စည်းမျဉ်းတွေကို အကောင်အထည်ဖော်လို့မရဘူး။

Private-key ဖိုင်ဟာ ကုဒ်မပါဘဲ တင်ပို့ထားတာပါ။ Source Control, Shared Folders, Logs, Tickets, Chat, and Build artifacts တွေကနေ ပိတ်ထားပါ။ ထုတ်လုပ်ရေးဖိုင်ကို ခွင့်ပြုထားတဲ့ ထိန်းသိမ်းမှု နယ်နိမိတ်ထဲကို တင်သွင်းပြီး ဖြန့်ချိခြင်း လုပ်ငန်းစဉ်အရ တင်ပို့မှုကို ဖယ်ရှားပါ။ ထုတ်လုပ်မှုမှာ ဖွံ့ဖြိုးရေး သော့ကို ပြန်မသုံးပါနဲ့။

ထုတ်လုပ်မှုအတွက် အောက်ပါအတိုင်း စစ်ဆေးထားသော ထိန်းသိမ်းမှု နယ်နိမိတ်ကို ဦးစားပေးပါ။

- Hardware Security Module (သို့) Hardware အားဖြင့်ထောက်ပံ့ထားသော Keystore
- အော်ပရေတာစနစ် (သို့) မိုဘိုင်း keystore
- သီးခြား လက်မှတ်ရေးထိုးမှု ဝန်ဆောင်မှု
- ခွင့်ပြုထားတဲ့ အလုပ်ဝန်ဆောင်မှုအတွက်သာ သော့ကို ထုတ်ပေးတဲ့ လျှို့ဝှက် စီမံခန့်ခွဲသူ

ရွေးချယ်ထားတဲ့ ပေါင်းစပ်မှုက အဲဒီ ဂုဏ်သတ္တိကို ထောက်ပံ့တဲ့အခါ အဓိက ပစ္စည်းတွေကို တင်ပို့လို့မရအောင် ထိန်းထားပါ။ Iroha ခွင့်ပြုချက် မူဝါဒအရ လိုအပ်တဲ့ အယ်လ်ဂိုရစ်သမ်နဲ့ လက်မှတ်ရေးထိုးမှု လုပ်ဆောင်မှုကို ထိန်းသိမ်းရေးစနစ်က ထောက်ပံ့ပေးတယ်ဆိုတာကို အတည်ပြုပါ။

Rest encryption သည် သိမ်းဆည်းထားသော copy ကို ကာကွယ်ပေးသည်။ ခွင့်ပြုချက်မရှိသည့် process သို့မဟုတ် operator တစ်ခုက decrypted byte များရရှိပြီးနောက် key ကိုကာကွယ်မပေးနိုင်ပါ။ host ကိုကြမ်းတမ်းစေခြင်း၊ software execution environment ကို access ကို ကန့်သတ်ခြင်း၊ လက်မှတ်ရေးထိုးခြင်းလုပ်ဆောင်မှုကို စောင့်ကြည့်ခြင်း။

## လက်မှတ်ရေးထိုးခြင်း လုပ်ငန်းခွင်များကို ကာကွယ်ပေးရန် {#protect-signing-workflows}

- နာမည်တပ်ထားသော operator လက္ခဏာများ၊ ခိုင်မာတဲ့ စစ်ဆေးခြင်းနှင့် လက်မှတ်ရေးထိုးစနစ်များကို စစ်ဆေးသုံးစွဲမှု။
- command-line arguments, shell history, environment dumps, process listings, crash reports နဲ့ application logs တွေထဲက raw keys တွေကို ရှောင်ရှားပါ။
- Cryptographic signer ကို လိုအပ်တဲ့ လုပ်ဆောင်ချက်အတွက်သာ ဖွင့်ပါ။ သုံးပြီးနောက် session ကိုပိတ်ထားပါ (သို့) ကုန်ဆုံးပါ
- ခွင့်ပြုချက်မပေးမီ ခွင့်ပြုမှု မူဝါဒ၊ ကွန်ရက်၊ ညွှန်ကြားချက်များ၊ အရင်းအမြစ်များနှင့် အခွန်များကို ပြသပါ။
- အခွင့်ထူးခံ (သို့) တန်ဖိုးမြင့် ငွေပေးချေမှုအတွက် တိကျတဲ့ အတည်ပြုချက် တောင်းဆိုပါ။
- Custom Client Integration က လက်မှတ်ရေးထိုးမှုကို လွှဲပြောင်းနိုင်တဲ့အခါ Browser စာမျက်နှာများနှင့် general-purpose application process များအပြင်မှာ raw private key တွေကို သိမ်းထားပါ။

Plain-text client ဖွဲ့စည်းမှုက ဒေသတွင်းဖွံ့ဖြိုးရေးနဲ့ ထိန်းချုပ်မှု စမ်းသပ်မှုတွေအတွက်သာ သင့်တော်ပါတယ်။ ထုတ်လုပ်မှု ပေါင်းစပ်မှုဟာ ခွင့်ပြုထားတဲ့ ထိန်းသိမ်းမှု နယ်နိမိတ်ကနေ လက်မှတ်တွေ ရယူသင့်တယ်။ Stock Iroha CLI သည် Client ဖွဲ့စည်းချက်မှ ပုဂ္ဂလိက သော့ကိုဖတ်ပြီး ယေဘုယျ ပြင်ပ cryptographic လက်မှတ်ရေးထိုးမှု-ဝန်ဆောင်မှု အကောင့်ပေးခြင်းမရှိပါ။ Custom clients များသည် Transaction payload cryptographic hash ကိုတည်ဆောက်နိုင်ပြီး ပြင်ပ Cryptographic signer ကထုတ်လုပ်သောလက်မှတ်တစ်ခု ချိတ်ဆက်နိုင်သည်။

## Key ကို Back Up လုပ်ပြီး ပြန်ယူပါ {#back-up-and-recover-keys}

- ပြန်လည်ထူထောင်ရေး မူဝါဒက backup လုပ်ဖို့ လိုအပ်တဲ့ သော့တွေပဲ back up လုပ်ပါ။
- Backup တွေကို encrypt လုပ်ပြီး cryptographic signer ကနေ ခွဲခြားထားပါ။
- Live Key နဲ့တူတဲ့ Access နဲ့ approval controls တွေကို Backup ကို သုံးပါ။
- အခွန်ခွဲခြားရန် လိုအပ်ပါက ပြန်လည်သိမ်းယူရေး အချက်အလက်များကို လွတ်လပ်စွာ ထိန်းသိမ်းထားပါ။
- ထုတ်လုပ်ရေးအဓိက ပစ္စည်းတွေကို မဖေါ်ပြဘဲ စမ်းသပ်မှု ပြန်လည်ထူထောင်ခြင်း။
- Backup ဖန်တီးမှု၊ ဝင်ရောက်မှု၊ ပြန်လည်ထူထောင်ခြင်းနဲ့ ဖျက်ဆီးမှုတိုင်းကို မှတ်တမ်းတင်ပြီး စစ်ဆေးပါ။

ဆက်စပ်မှုမရှိတဲ့ wallet mnemonic format က Iroha private key ကို ကိုယ်စားပြုနိုင်တယ်လို့ မယူဆပါနဲ့။ ရွေးချယ်ထားတဲ့ ထိန်းသိမ်းရေးစနစ်က ထောက်ပံ့ပြီး စစ်ဆေးတဲ့ ပြန်လည်ထူထောင်ရေးပုံစံကိုသာ အသုံးပြုပါ။

## Exposed (သို့) Deactivated Key များကို အစားထိုးရန် {#replace-exposed-or-retired-keys}

ဖြစ်ရပ်တစ်ခု မဖြစ်ခင် အစားထိုးဖို့ ပြင်ဆင်ပါ။ လုပ်ငန်းစဉ်က

1. သော့ကို ထုတ်ဖော်ပြောဆိုနိုင်သူ (သို့) ဖျက်သိမ်းထားသော
2. ထိခိုက်ခံရတဲ့ cryptographic signer ကို ဘယ်လို ခွဲခြားထားလဲ။
3. သော့သစ်ကို ဘယ်လို ဖန်တီးပြီး ခွင့်ပြုထားတဲ့ ထိန်းသိမ်းမှုမှာ ထားရှိရမလဲ
4. Account တစ်ခုအတွက် ခွင့်ပြုထားတဲ့ Controller အစားထိုးခြင်း (သို့) လူမှုရေး ပြန်လည်ထူထောင်ခြင်းသည် အစားထိုးမှု Single Protocol-Standard `AccountId` ကို ဖန်တီးပုံနှင့် ချိတ်ဆက်ထားသောနိုင်ငံကို ရွှေ့ပြောင်းပုံ
5. node သို့မဟုတ် network peer အတွက် ခွင့်ပြုထားတဲ့ on-chain consensus key rotation (သို့) disability ကို BLS PoP၊ activation နှင့် overlap policy, local key configuration, `trusted_peers_pop` နဲ့ deployment topology တို့နဲ့ ဘယ်လို ညှိနှိုင်းထားသလဲ
6. အမှီအခိုကင်းတဲ့ ကွန်ပြူတာတွေ၊ အက်ပ်တွေ နဲ့ လုပ်ငန်းရှင်တွေက `AccountId` အသစ်၊ အများသုံး သော့ (သို့) ကွန်ရက်တူညီသူရဲ့ ကိုယ်ပိုင်လက္ခဏာကို ဘယ်လို လက်ခံကြလဲ။
7. သော့ဟောင်းရဲ့ ခွင့်ပြုချက် မူဝါဒကို ဖယ်ရှားပြီး မိတ္တူတွေကို သိမ်းဆည်းထားခြင်း (သို့) ဖျက်ဆီးခြင်း
8. ကွန်ရက်နှင့် မှီခိုသော အက်ပ်များအား နောက်ပိုင်းတွင် ဘယ်လို စစ်ဆေးရမည်နည်း။

::: warning

ကုဒ်သွင်းခြင်း (သို့) စကားဝှက်အသစ်တစ်ခုက ကူးယူထားသော ပုဂ္ဂလိက သော့ကို ပြန်လည်လုံခြုံအောင် မလုပ်နိုင်ပါ။ ထိတွေ့မှု သံသယရှိတဲ့အခါ သော့ကို သုံးတာရပ်ပြီး ခွင့်ပြုထားတဲ့ အစားထိုးခြင်း (သို့မဟုတ်) ရုပ်သိမ်းခြင်း လုပ်ငန်းစဉ်ကို လိုက်နာပါ။

:::
