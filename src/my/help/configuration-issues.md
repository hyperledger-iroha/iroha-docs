# ပြင်ဆင်သတ်မှတ်ချက် ပြဿနာများကို ဖြေရှင်းခြင်း {#troubleshooting-configuration-issues}

ဤအပိုင်းတွင် Iroha 3 ဖွဲ့စည်းမှုအတွက်ပြဿနာဖြေရှင်းရေး အကြံပြုချက်များကို ဖော်ပြထားပါသည်။ [သော့တွေကို စစ်ခဲ့တယ်။](./overview.md#check-the-keys) ကို အရင်ဆုံးစစ်ဆေးရန် သေချာစေပါ၊ ၎င်းသည် Iroha တွင်ဖြစ်ပေါ်သော ပြဿနာများ၏ အများဆုံးရင်းမြစ်ဖြစ်သည်။

သင်တွေ့နေရသော ပြဿနာကို ဤနေရာတွင် မဖော်ပြထားပါက [Telegram](https://t.me/hyperledgeriroha) မှတစ်ဆင့် ကျွန်ုပ်တို့ကို ဆက်သွယ်ပါ။

## Docker Compose setup ပေါ်တွင် ခေတ်နောက်ကျသော blockchain genesis {#outdated-genesis-on-a-docker-compose-setup}

Iroha ၏ Docker Compose ဗားရှင်းကို အသုံးပြုနေစဉ် အဆင့်တူနိုဒ် ကွန်တိန်နာတစ်ခုက `Failed to deserialize raw genesis block` အမှားဖြင့် မအောင်မြင်ခြင်းကို တွေ့နိုင်သည်။ ပုံမှန်အားဖြင့် ၎င်းသည် အဆင့်တူနိုဒ်၊ လက်မှတ်ထိုးထားသော ကနဦးထရန်ဇက်ရှင်နှင့် ဖန်တီးထားသော ပြင်ဆင်သတ်မှတ်ချက်တို့ကို မတူညီသော Iroha ရင်းမြစ်ဗားရှင်းများ သို့မဟုတ် ပရိုဖိုင်များဖြင့် ထုတ်လုပ်ထားခြင်းဟု ဆိုလိုသည်။

အတည်ပြုသူများ၏ မှတ်တမ်းကို ကြည့်ရန် ကိရိယာအစု၏ ဒိုင်ရက်ထရီတွင် `python3 poc.py logs` ကို လုပ်ဆောင်ပါ။ တူညီသော ရင်းမြစ်ဗားရှင်းမှ ဘိုင်နရီဖိုင်များကို တည်ဆောက်ပြီး Docker တွင် အတည်ပြုသူ လေးခုကို စတင်ရန် [လွှတ်တင်ခြင်း Iroha 3](/my/get-started/launch-iroha.md) လမ်းညွှန်ကို လိုက်နာပါ။

တူညီသော ကွန်ရက်ကို ပြန်စရန် `python3 poc.py down` နှင့် `python3 poc.py up` ကို အစဉ်လိုက် လုပ်ဆောင်ပါ။ `state/` ကို ၎င်း၏ Docker သိုလှောင်မှုအတွဲ လေးခုနှင့်အတူ သိမ်းထားပါ။

::: info

လည်ပတ်နေသော ကွန်ရက်တွင် ကနဦးဘလောက်ကို အစားထိုးရန် ယေဘုယျ အလိုအလျောက်ပြန်ရေးလမ်းကြောင်း မရှိပါ။ ၎င်းကို ညှိနှိုင်းထားသော ရွှေ့ပြောင်းမှုအဖြစ် သတ်မှတ်ပါ။ အခြေအနေဟောင်းကို ထိန်းသိမ်းပါ၊ ကိုက်ညီသော အဆင့်တူနိုဒ်များကို စတင်ပြီး အော်ပရေတာများက ရွှေ့ပြောင်းမှုအစီအစဉ်ကို သဘောတူပြီးနောက်မှသာ အတည်ပြုသူများကို ပြင်ဆင်သတ်မှတ်ချက်အသစ်သို့ ရွှေ့ပါ။

:::

## ပုဂ္ဂလိကနှင့် အများပိုင် သော့များ၏ Multi-Hash Format {#multihash-format-of-private-and-public-keys}

[Client ဖွဲ့စည်းမှု](/my/guide/configure/client-configuration.md) ကို ကြည့်လိုက်ရင် အဲဒီမှာရှိတဲ့ သော့တွေကို [multi-hash ဖိုရမ်](https://github.com/multiformats/multihash) မှာ ပေးထားတာကို သတိပြုမိမှာပါ။

multi-hash ကို ယခင်က မသုံးဖူးပါက ညာဘက်ရှိတန်ဖိုးသည် ကီးဘိုက်များကို တစ်ဘိုက်လျှင် သင်္ကေတနှစ်ခုဖြင့် ဖော်ပြသော ဆယ့်ခြောက်အခြေပြု ပုံစံမဟုတ်ဘဲ ASCII သို့မဟုတ် UTF-8 ဖြင့် ကုဒ်ပြောင်းထားသော ဘိုက်များဟု ယူဆကာ `public_key` နှင့် `private_key` နှစ်ခုစလုံးကို ဖန်တီးရာ၌ စာသားကိန်းသေအပေါ် `from_hex` ခေါ်ရန် စဉ်းစားမိခြင်းသည် သဘာဝကျသည်။

`PrivateKey::try_from_str` ကို ကြိုးစာလုံးမှာခေါ်ဆိုခြင်းက မှန်ကန်တဲ့ သော့ကိုသာ ထုတ်ပေးလိမ့်မယ်လို့ ယူဆဖို့လည်း သဘာဝကျပါတယ်။ ဒီတော့ သော့ထဲက ဘိုက်တွေအရေအတွက် မှားယွင်းရင် ဥပမာ 32 bytes vs 64, ဒါကအမှားသတင်းစကားတစ်စောင် ဖြစ်ပေါ်စေပါလိမ့်မယ်။

**ဤယူဆချက်နှစ်ခုစလုံး မှားယွင်းသည်။** ကံမကောင်းစွာဖြင့် ဤကျရှုံးမှုမျိုးကို အကြောင်းရှာဖြေရှင်းရာတွင် အမှားမက်ဆေ့ချ်များက အထောက်အကူမပြုပါ။

ပြင်ဆင်နည်း: `hex_literal` ကိုသုံးပါ။ ဒါကလည်း မိုက်မဲတဲ့ စာလုံးကြိုးကို သိသိသာသာ ခြောက်ဆယ်ကိန်း ဂဏန်းပါတဲ့ လှပတဲ့ စားပွဲလေးတစ်ခုအဖြစ် ပြောင်းပေးပါလိမ့်မယ်။

::: warning

`try_from_str` အကောင်အထည်ဖော်မှုတောင်မှ သတ်မှတ်ထားတဲ့ string တစ်ခုက valid `PrivateKey` ဆိုတာကို စစ်ဆေးလို့မရနိုင်ပြီး မဟုတ်ရင် သတိပေးနိုင်ပါတယ်။

စာသားတန်းထဲတွင် မမှန်သောသင်္ကေတပါခြင်းကဲ့သို့ ထင်ရှားသောအမှားအချို့ကို ၎င်းက ရှာတွေ့နိုင်သည်။ သို့သော် ကီးပုံစံများစွာကို ပံ့ပိုးရန် ရည်ရွယ်ထားသောကြောင့် အခြားအရာများကို များစွာမစစ်ဆေးနိုင်ပါ။ ညွှန်ကြားချက်တစ်ခုကို မတင်သွင်းမချင်း ထိုကီးသည် _ပေးထားသောအကောင့်အတွက်_ _မှန်ကန်သော_ ကိုယ်ပိုင်ကီး ဟုတ်မဟုတ်ကိုလည်း မသိနိုင်ပါ။

:::

ဒီလိုသိမ်မွေ့တဲ့ အမှားတွေကို ရှောင်ရှားနိုင်ပါတယ်။ ဥပမာ string literal တွေကနေ တိုက်ရိုက် deserialising လုပ်ခြင်း (သို့) အဓိပ္ပါယ်ရှိတဲ့ နေရာတွေမှာ သော့စုံအသစ်တစ်ခု ဖန်တီးခြင်းပါ။
