# ငွေပေးချေမှု {#transactions}

ငွေပေးချေမှုသည် blockchain တွင်လုပ်ဆောင်ရန် လက်မှတ်ရေးထိုးထားသောတောင်းဆိုချက်တစ်ခုဖြစ်သည်။ လုပ်ဆောင်နိုင်သည့် အသုံးဝင်ဝန်ပိုးသည် [ညွှန်ကြားချက်](./instructions.md) ၏ အမိန့်ချိထားသောအတန်း၊ စာချုပ်နည်းပညာခေါ်ယူခြင်း, IVM ဘိုက်ကုတ် (သို့မဟုတ်) သက်သေပြထားသော IVM အကောင်အထည်ဖော်မှုဖြစ်နိုင်တယ်။ လက်ရှိစာချုပ် အကောင်အ ထည်ဖော်မှုပုံစံအတွက် [အသိဉာဏ်ရှိတဲ့ စာချုပ်များ](./smart-contracts.md) ကိုကြည့်ပါ။

Transaction များသည် အခြေအနေပြောင်းလဲမှု သို့မဟုတ် executable အလုပ်ကို လုပ်ဆောင်သည်။ ဖတ်ရှုရုံ စစ်ဆေးမှုသည် လက်မှတ်ထိုးထားသော query များ သို့မဟုတ် အများသုံး ဖတ်ရှုမှု endpoint များကို သုံးပြီး transaction မဖန်တီးပါ။

Commit လုပ်ထားသော ဘလော့ခ်ထဲ ဝင်ခွင့်ရသော transaction ကို ၎င်း၏ လုပ်ဆောင်မှုရလဒ်နှင့်အတူ သိမ်းသည်။ လုပ်ဆောင်မှုအတွင်း ငြင်းပယ်ခံရသည့် ရလဒ်လည်း ပါဝင်သည်။ မမှန်သော envelope သို့မဟုတ် တန်းစီစာရင်းက လက်မခံသော transaction ကဲ့သို့ ဘလော့ခ်ဝင်ခွင့် မရမီ ငြင်းပယ်ခံရသည့် တောင်းဆိုမှုများကို ဘလော့ခ်ထဲ မသိမ်းပါ။

ပုဂ္ဂလိကဘဝကို ထိန်းသိမ်းတဲ့ အရင်းအမြစ် လှုပ်ရှားမှုအတွက် [အမည်မသိ ငွေပေးချေမှု](./anonymous-transactions.md) ကိုကြည့်ပါ။ အမည်မဲ့ ငွေကြေးလုပ်ငန်းတွေမှာ အများပိုင်စာရင်းကနေ စာရင်းဆီက ဘားလန်အပြောင်းအစား ကာကွယ်ထားတဲ့ အရင်းအမြတ်မှတ်စုတွေ၊ cryptographic commitment တန်ဖိုးတွေ၊ nullifiers နဲ့ zero knowledge proof တွေ သုံးပါတယ်။

ရွေးချယ်ထားတဲ့ ပွင့်လင်းမြင်သာတဲ့ အကောင်အထည်ဖော်မှု သက်ရောက်မှုအပေါ် သက်သေခံသက်သေများအတွက် [FastPQ](./fastpq.md) ကိုကြည့်ပါ။ FastPQ သည် ပုံမှန် ငွေကြေးဆောင်ရွက်မှု အကောင်အ ထည်ဖော်ပြီးနောက် အကောင်အတာသက်သေများကို စားသုံးပြီး ထောက်ပံ့ state transitions များအတွက် deterministic proof batches တွေကို တည်ဆောက်တယ်။

## Taira တွင် ဤအလုပ်ခွင်ကို run လုပ်ပါ။ {#try-it-on-taira}

လတ်တလော အများပြည်သူ Taira ဘလော့ခ်များနှင့် ငွေပေးချေမှုအခြေအနေများကို လက်မှတ်ရေးထိုးစာရင်းမပါဘဲ စစ်ဆေးရန် Explorer လမ်းကြောင်းများကို အသုံးပြုပါ။

```bash
curl -fsS 'https://taira.sora.org/v1/explorer/blocks?page=1&per_page=3' \
  | jq '{pagination, blocks: [.items[] | {height, hash, transactions_total, transactions_rejected}]}'

curl -fsS 'https://taira.sora.org/v1/explorer/transactions?page=1&per_page=5' \
  | jq '{pagination, txs: [.items[] | {hash, block, status, executable}]}'
```

သင့် app က အရင်က တင်ပြခဲ့တဲ့ ငွေပေးချေမှုကို လိုက်နာဖို့ စာရင်းထဲက `hash` ကို ကူးယူပြီး explorer ရဲ့ အသေးစိတ် လမ်းကြောင်းကို စစ်ဆေးပါ။

```bash
TX_HASH='<transaction-hash>'

curl -fsS "https://taira.sora.org/v1/explorer/transactions/$TX_HASH" \
  | jq '{hash, block, status, authority, executable}'
```

ဤအဆင့်သည်လည်း ဖတ်ရှုမှုသာ ဖြစ်သည်။ Transaction တင်သွင်းရန် လက်မှတ်ထိုးထားသော Norito envelope၊ မှန်ကန်သော ချိန်း ID နှင့် ကွန်ရက် ID၊ အခကြေးငွေပေးသူကို တိတိကျကျ သတ်မှတ်မှုနှင့် faucet မှ ငွေဖြည့်ထားသော Taira အကောင့် လိုအပ်သည်။

Taira တွင် အခကြေးငွေပေးရသော နမူနာများအတွက် [Taira တွင် Testnet XOR ရယူခြင်း](/my/get-started/sora-nexus-dataspaces.md#_4-get-testnet-xor-on-taira) ရှိ ကြိုတင်ပြင်ဆင်သည့် faucet လုပ်ငန်းစဉ်ဖြင့် လက်မှတ်ထိုးသူကို ငွေဖြည့်ပြီး အခကြေးငွေသုံး ပိုင်ဆိုင်မှု၏ လက်ကျန်ကို စစ်ဆေးပါ:

```bash
export TAIRA_ACCOUNT_ID='<TAIRA_I105_ACCOUNT_ID>'
export TAIRA_FEE_ASSET="$(
  curl -fsS https://taira.sora.org/v1/accounts/faucet/policy \
    | jq -er '.asset_definition_id'
)"

iroha --config ./taira.client.toml ledger asset get \
  --definition "$TAIRA_FEE_ASSET" \
  --account "$TAIRA_ACCOUNT_ID"
```

Faucet လမ်းကြောင်းက `502` ပြန်ပေးပါက transaction ကိုယ်တိုင်ကို အမှားမရှာမီ စောင့်ပြီး ပြန်ကြိုးစားပါ။

ထို့နောက် transaction တင်သွင်းချိန်တွင် အခကြေးငွေပေးသူကို ရွေးချယ်ပါ။ `--fee-payer authority` သုံးပါက လက်မှတ်ထိုးသည့် အကောင့်က ပေးချေပြီး CLI သည် လက်မှတ်မထိုးမီ Taira ၏ အခကြေးငွေသုံး ပိုင်ဆိုင်မှုဖြင့် အခကြေးငွေအတိအကျကို တွက်ချက်ဖော်ပြသည်:

```bash
iroha --config ./taira.client.toml \
  --fee-payer authority \
  tx ping --msg "faucet-funded taira transaction"
```

## Offline ငွေပေးချေမှု {#offline-transactions}

Iroha မှာ offline transaction workflows နှစ်ခုရှိပါတယ်-

- **အင်တာနက်မချိတ်ဘဲ လက်မှတ်ထိုးခြင်း** သည် လက်မှတ်ထိုးစက် ချိတ်ဆက်မှုဖြုတ်ထားစဉ် ပုံမှန် လက်မှတ်ထိုးထားသော transaction ကို ဖန်တီးသည်။ အွန်လိုင်း client တစ်ခုက လက်မှတ်ထိုးထားသော envelope ကို Torii သို့ မတင်သွင်းမချင်း transaction ကို မလုပ်ဆောင်သဖြင့် မှန်ကန်သော chain ID၊ authority အကောင့်၊ ခွင့်ပြုချက်များ၊ အခကြေးငွေနှင့် transaction သက်တမ်းတို့ လိုအပ်နေဆဲဖြစ်သည်။
- **Kagemusha အော့ဖ်လိုင်း ငွေသား** သည် စာရင်းသွင်းပြီး ဟာ့ဒ်ဝဲဖြင့် ကာကွယ်ထားသော ပိုက်ဆံအိတ် အွန်လိုင်းရှိချိန်တွင် တန်ဖိုးကို ဖြည့်သွင်းသည်။ ပိုက်ဆံအိတ်နှစ်ခုစလုံး အော့ဖ်လိုင်းရှိစဉ် အချင်းချင်း ငွေပေးချေနိုင်ပြီး ပိုက်ဆံအိတ် အွန်လိုင်းပြန်ရောက်ချိန်တွင် ကျန်တန်ဖိုးကို လယ်ဂျာ အကောင့်သို့ ပြန်ထုတ်ပေးသည်။

Torii တွင် Kagemusha လမ်းကြောင်းတစ်ခုဖြစ်သော `POST /v1/kagemusha/enrollment` ရှိသည်။ ၎င်းက အကောင့်ဖြင့် စစ်မှန်ကြောင်း အတည်ပြုထားသော `application/x-norito` စာရင်းသွင်း frame များကို လက်ခံပြီး cache မသိမ်းရသော သီးသန့်တုံ့ပြန်ချက်များကို ပြန်ပေးသည်။ သက်တမ်းစက်ဝန်း၏ လယ်ဂျာဘက်တွင် `KagemushaWalletLedgerV1` ညွှန်ကြားချက်ပါဝင်သော ပုံမှန် လက်မှတ်ထိုးထားသည့် transaction များကို သုံးသည်:

| လုပ်ဆောင်ချက် | ရည်ရွယ်ချက် |
| --- | --- |
| `Activate` | စာရင်းသွင်းထားသော ပိုက်ဆံအိတ်ကို အသက်သွင်းသည်။ မူရင်းစနစ်၏ ကနဦးစစ်ဆေးမှု မဖြစ်မနေ လိုအပ်သည် |
| `IssueLoad` | ပေးချေသူထံမှ ငွေနုတ်ယူပြီး ပိုက်ဆံအိတ်၏ နောက် Load ကို ခွဲမရသော လုပ်ဆောင်မှုတစ်ခုအဖြစ် မှတ်တမ်းတင်သည် |
| `Unload` | ပြည့်စုံသော Unload တောင်းခံမှုကို ၎င်းနှင့် ချည်နှောင်ထားသော အကောင့်သို့ အများဆုံးတစ်ကြိမ်သာ ပေးချေသည် |
| `ClaimFee` | ပြည့်စုံသော အခကြေးငွေတောင်းခံမှုကို သတ်မှတ်ပြီးသား အကျိုးခံစားသူထံ ပေးချေသည် |
| `Abandon` | အသုံးမပြုရသေးသော စာရင်းသွင်းမှုကို စွန့်လွှတ်သည် |

ပုံမှန် စီးဆင်းမှုက-

1. အမျိုးအစားသတ်မှတ်ထားသော Swift သို့မဟုတ် Android ပိုက်ဆံအိတ်ကို သုံး၍ `/v1/kagemusha/enrollment` မှတစ်ဆင့် စာရင်းသွင်းပြီး အသက်သွင်းပါ။
2. `IssueLoad` transaction ကို တင်သွင်းပါ။ လုပ်ဆောင်မှုက မျှော်မှန်းထားသော နောက် Load အစဉ်နံပါတ်နှင့် သုညမဟုတ်သော တောင်းဆိုမှု ID ကို စစ်ဆေးသောကြောင့် ဟောင်းနေသော သို့မဟုတ် ပြောင်းလဲထားသော ပြန်လည်ကြိုးစားမှုသည် မအောင်မြင်ပါ။ တုံ့ပြန်ချက်ပျောက်ဆုံးပါက နောက်ထပ် Load ကို လက်မှတ်ထိုးမည့်အစား မူရင်း Load ပြေစာကို ဖတ်ရှုပါ။
3. ပိုက်ဆံအိတ်များ အော့ဖ်လိုင်းရှိစဉ် အချင်းချင်း ငွေပေးချေမှုများကို ဒေသတွင်း ဖလှယ်စစ်ဆေးပြီး လွှဲပြောင်းမှုတစ်ခုစီကို အသိအမှတ်မပြုမီ ပိုက်ဆံအိတ် အခြေအနေကို ရေရှည်တည်မြဲစွာ သိမ်းဆည်းပါ။
4. ပိုက်ဆံအိတ် အွန်လိုင်းပြန်ရောက်သောအခါ ၎င်း၏ Unload တောင်းခံမှုကို တင်သွင်းပြီး အပြီးသတ်အတည်ဖြစ်မှုကို စောင့်ပါ။

အွန်လိုင်းသက်တမ်းကာလအတွင်း မှတ်စုအခြေအနေပြန်မလာခင်အထိ blockchain ledger သည်ပဋိပက္ခဖြစ်နေသော offline လွှဲပြောင်းမှုကို သတိပြုနိုင်ခြင်းမရှိပါ။ ထို့ကြောင့် Wallet နှင့် operator မူဝါဒသည်တန်ဖိုးသတ်မှတ်ချက်များ၊ သက်တမ်းကုန်ဆုံးခြင်း၊ လက်ခံထုတ်လွှင့်သူများ၊ ရေရှည် တည်တံ့သည့် ဒေသတွင်း သိုလှောင်မှုနှင့် ညှိနှိုင်းရေး ပြတင်းပေါက်များကို အကောင်အထည်ဖော်သင့်သည်။

`Grant` ညွှန်ကြားချက်ဖြင့် ငွေပေးချေမှု အသစ်တစ်ခု ဖန်တီးခြင်း၏ ဥပမာကို ဖော်ပြပါသည်- ဤလုပ်ငန်းစဉ်တွင် Mouse သည် Alice ကို သတ်မှတ်ထားသော အခန်းကဏ္ဍ (`role_id`) ကို ပေးအပ်နေသည်။ [အပြည့်အစုံ ဥပမာ](./permissions.md#register-a-new-role) ကို စစ်ဆေးပါ။

```rust
let grant_role = Grant::account_role(role_id, alice_id);
let grant_role_tx = TransactionBuilder::new(chain_id, mouse_id)
    .with_instructions([grant_role])
    .sign(mouse_private_key);
```
