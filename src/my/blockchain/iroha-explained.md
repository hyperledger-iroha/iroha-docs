# Iroha ရှင်းပြချက် {#iroha-explained}

Iroha 3 သည်ပထမဦးဆုံးထုတ်ဝေသော Hyperledger Iroha ပလက်ဖောင်းဖြစ်သည်။ အလားတူဗဟိုသည် မိမိဘာသာ တည်းခိုထားသည့်ကွန်ရက်များနှင့် SORA Nexus ဒေတာနေရာများနှင့် multi-lane routing အတွက်လုပ်ဆောင်မှုပုံစံကိုထောက်ခံသည်။

## အခြေခံ အဆောက်အအုံများ {#core-building-blocks}

- **`iroha3d`** သည် peer များကို လည်ပတ်စေသည်။
- Torii က client နဲ့ operator gateway ဖြစ်ပါတယ်
- Sumeragi က သဘောတူညီချက် ကိုင်တွယ်တယ်။
- Norito သည် [Single Protocol Standard ဘိုင်နရီပုံစံ](/my/reference/norito.md) ဖြစ်သည်။
- IVM ကို portable smart contracts နဲ့ byte code တွေကို run လုပ်ပေးတယ်။
- Kotodama သည် အဆင့်မြင့် `.ko` စာချုပ်များကို IVM `.to` ဘိုက်ကုဒ်သို့ စုစည်းသည်။
- Kagami ကီးတွေကို ပြင်ဆင်တယ်၊ ဘလော့ခ်ချ်ကို ဖန်တီးတယ်၊ ပရိုဖိုင်တွေ၊ ဒေသတွင်းကွန်ရက်တွေပေါ့။
- **SORA Nexus ဝန်ဆောင်မှုအလွှာများ** က အက်ပ် hosting၊ ကိုယ်ရေးလုံခြုံမှုဆိုင်ရာ ပို့ဆောင်မှု၊ သိုလှောင်မှုနှင့် အမည်ပေးမှုတို့အတွက် Soracloud၊ Inrou၊ SoraNet၊ SoraFS နှင့် SoraDNS ကို ပေါင်းထည့်ပေးသည်။

## အကောင်အထည်ဖော်မှုပုံစံ {#execution-model}

ကမ္ဘာ့အခြေအနေ ပြောင်းလဲမှုတိုင်းဟာ ငွေကြေးလုပ်ငန်းများမှတဆင့် ဖြစ်ပေါ်နေဆဲပါ။ ငွေကြေး လုပ်ငန်းတွေမှာ ညွှန်ကြားချက် (သို့) IVM ဘိုင်တာကုဒ်ရှိပြီး Torii သည် ဖောက်သည်များက ၎င်းတို့ကို ပေးပို့ခြင်း သို့မဟုတ် ၎င်းတို့၏ သက်ရောက်မှုကို လေ့လာခြင်းအတွက် အဓိကနည်းလမ်းဖြစ်သည်။

- data space များသည် အဖွဲ့အစည်းဆိုင်ရာ ဒေတာ၊ authority၊ မူဝါဒနှင့် အက်ပ်များအတွက် ပတ်ဝန်းကျင်များကို ပေးသည်
- lane များသည် ထိုပတ်ဝန်းကျင်များအတွင်း လမ်းကြောင်းရွေးချယ်မှုနှင့် အတည်ပြုလက်မှတ်ထုတ်ပေးမှု စွမ်းရည်ကို ပေးသည်
- သီးခြားလက်မှတ်ထိုးထားသော data space root သည် ကိုယ်ပိုင် State နှင့် ဒေသတွင်း အပြီးသတ်အတည်ဖြစ်မှုကို ပိုင်ဆိုင်သည်

## Data space များနှင့် လုပ်ဆောင်မှု root များ {#multi-dataspace-architecture}

Data space ကတ်တလောက်စာရင်းတစ်ခုသည် ပတ်ဝန်းကျင်နှင့် ၎င်း၏ identity ကို သတ်မှတ်သည်။ ကတ်တလောက်စာရင်းတစ်ခုတည်းက သီးခြားလုပ်ဆောင်မှု root ကို မတည်ထောင်ပါ။ အများသုံး lane များသည် ကမ္ဘာလုံးဆိုင်ရာ ချိန်းက လုပ်ဆောင်မည့် transaction အစုများကို အတည်ပြုလက်မှတ်ထုတ်ပေးသည်။ သီးခြားလက်မှတ်ထိုးထားသော data space root တွင် ကိုယ်ပိုင် State၊ ကော်မတီနှင့် ဒေသတွင်း အပြီးသတ်အတည်ဖြစ်မှု ရှိသည်။

`DataSpaceCatalog` သည် data space များကို သတ်မှတ်ပြီး `LaneCatalog` သည် lane များကို သတ်မှတ်သည်။ Lane တစ်ခုစီသည် `dataspace_id` မှတစ်ဆင့် data space တစ်ခုအတိအကျကို ရည်ညွှန်းပြီး data space တစ်ခုတွင် lane အများအပြား ပါဝင်နိုင်သည်။ `DataSpaceId` နှင့် `LaneId` သည် သီးခြား identity များဖြစ်ပြီး lane alias က data space နောက်တစ်ခုကို မဖန်တီးပါ။

လုပ်ဆောင်ချိန်တွင် data space ကို ကိန်းဂဏန်း `DataSpaceId` နှင့် ကတ်တလောက် metadata ဖြင့် ကိုယ်စားပြုသည်။ `DataSpaceId::UNIVERSAL` ကို `0` အဖြစ် သီးသန့်ထားပြီး ပုံသေကတ်တလောက်တွင် `universal` data space ပါဝင်သည်။ ပြင်ဆင်သတ်မှတ်ထားသော data space တစ်ခုစီတွင်:

- ထူးခြားတဲ့ ကိန်းဂဏန်း ID
- `universal` သို့မဟုတ် တိတိကျကျ မှတ်ပုံတင်ထားသော အဖွဲ့အစည်းအမည်ကဲ့သို့ တစ်ခုတည်းသာရှိသော alias
- အော်ပရေတာမျက်နှာပြင်အတွက် ရွေးချယ်စရာ သရုပ်ဖော်ချက်
- ရေလွှမ်းမိုးရေးကော်မတီများအတွက် အသုံးပြုသော သုညမဟုတ်သည့် တန်ဖိုး `fault_tolerance`

Lane များသည် ထို data space များနှင့် ချည်နှောင်ထားသော လမ်းကြောင်းရွေးချယ်မှုနှင့် အတည်ပြုလက်မှတ်ထုတ်ပေးမှု အရင်းအမြစ်များဖြစ်သည်။ Lane စာရင်းတစ်ခုတွင် `LaneId`၊ ၎င်းဝန်ဆောင်မှုပေးသော `DataSpaceId`၊ alias၊ မြင်နိုင်မှု (`public` သို့မဟုတ် `restricted`)၊ သိုလှောင်မှုပုံစံ (`full_replica`၊ `commitment_only` သို့မဟုတ် `split_replica`)၊ သက်သေစနစ်နှင့် မဖြစ်မနေမဟုတ်သော အုပ်ချုပ်မှု၊ ငွေစာရင်းရှင်းလင်းမှု၊ အစီအစဉ်ချမှတ်မှု metadata ပါဝင်သည်။ လုပ်ဆောင်မှုစနစ်သည် Kura အပိုင်းအမည်များနှင့် တစ်သမတ်တည်းဖြစ်သော ကီးရှေ့ဆက်များအပါအဝင် lane တစ်ခုစီ၏ သိုလှောင်မှုပုံစံကို ဤကတ်တလောက်မှ ဆင်းသက်တွက်ချက်သည်။

လမ်းညွှန်လမ်းကြောင်းက-

1. ပြင်ဆင်သတ်မှတ်မှုသည် စစ်ဆေးပြီးသော `DataSpaceCatalog`၊ `LaneCatalog` နှင့် `LaneRoutingPolicy` ကို တည်ဆောက်သည်။ SORA Nexus လမ်းကြောင်းရွေးချယ်မှုသည် မဖြစ်မနေ လိုအပ်သည်။ ကမ္ဘာလုံးဆိုင်ရာ root ပေါ်တွင် data space များစွာ၊ lane များစွာ သို့မဟုတ် ပုံသေမဟုတ်သော လမ်းကြောင်းရွေးချယ်မှုသည် SORA Nexus ပရိုဖိုင် (`--sora`) နှင့် NPoS ကို လိုအပ်သည်။ သီးခြားလက်မှတ်ထိုးထားသော data space root တစ်ခုသည် Permissioned မုဒ်ဖြင့် လည်ပတ်သည်။
2. Transaction တန်းစီစာရင်းသည် transaction နှင့် commit လုပ်ပြီးသော အခြေအနေမှ `RoutingPlan` ကို ဖြေရှင်းသည်။ ညှိနှိုင်းသူ သို့မဟုတ် ပါဝင်သူ၏ လမ်းကြောင်းတစ်ခုစီတွင် lane ID နှင့် data space ID ပါဝင်သည်။ Native AMX အစီအစဉ်များသည် ပါဝင်သူအစုအပြည့်အစုံကို ထိန်းသိမ်းသည်။
3. ကမ္ဘာလုံးဆိုင်ရာ လုပ်ဆောင်မှုအတွက် ထိန်းချုပ်ရေးအလွှာ၏ ပြည့်စုံသော အစုများနှင့် data space များအကြား ညှိနှိုင်းသူများသည် lane `0` ကို သုံးသည်။ Universal မဟုတ်သော တိကျသည့် ညွှန်ကြားချက် သို့မဟုတ် စာချုပ်လိပ်စာ ပစ်မှတ်များသည် အကောင့် သို့မဟုတ် ညွှန်ကြားချက် label စည်းမျဉ်းများ မသုံးမီ ကိုက်ညီသော data space နှင့် ကော်မတီရှိသည့် လက်ခံခွင့်ရ ပုံသေ lane ကို ရွေးချယ်သည်။ အခြားအလုပ်များသည် commit လုပ်ပြီးသော တိကျသည့်စည်းမျဉ်းများနှင့် ပုံသေခွဲဝေမှုကို လိုက်နာသည်။ တိကျသော universal ပစ်မှတ်များသည် universal lane များပေါ်တွင် ဆက်ရှိသည်။
4. လမ်းကြောင်းတစ်ခုစီကို ကတ်တလောက်များနှင့် လက်ရှိအသုံးပြုနေသော lane အခြေအနေတို့ဖြင့် စစ်ဆေးသည်။ မသိသော ID များနှင့် lane/data space မကိုက်ညီမှုများကို ငြင်းပယ်သည်။ မရရှိနိုင်သော သီးသန့်ပစ်မှတ်သည် universal လုပ်ဆောင်မှုသို့ ပြောင်းလဲသွား၍ မရပါ။ Data space ပစ်မှတ်အများအပြားက Native AMX အစီအစဉ်ကို ဖြစ်စေနိုင်သည်။ Transaction metadata `amx_policy` ကို `reject_cross_dataspace` အဖြစ် သတ်မှတ်ထားပါက data space များအကြား အစီအစဉ်များကို ငြင်းပယ်သည်။ လမ်းကြောင်းအစီအစဉ်တစ်ခုတည်းက သီးခြား root များအကြား ငွေစာရင်းရှင်းလင်းမှုကို ခွင့်မပြုသလို အပြီးမသတ်ပေးပါ။
5. တယ်လီမီတြီသည် ခွဲဝေသတ်မှတ်မှုကို `/status` lane snapshot (`teu_lane_commit`) တွင် lane တစ်ခုချင်းစီအလိုက် လှုပ်ရှားမှုနှင့် စောင့်ဆိုင်းနေသော အလုပ်များအဖြစ် မြင်နိုင်အောင် ထားရှိသည်။

ထို့ကြောင့် object identifier များ အရေးပါသည်။ Domain များ၏ ID တွင် `payments.universal` ကဲ့သို့ data space alias ပါဝင်သောကြောင့် domain အလိုက် ရေးသားမှုများကို လမ်းကြောင်းရွေးချယ်နိုင်သည်။ အကောင့်များသည် စံပုံစံဖြစ်ပြီး domain မပါဝင်သဖြင့် တူညီသော အကောင့်ကို ၎င်း၏ `AccountId` မပြောင်းဘဲ မတူသော အက်ပ်နယ်ပယ်များနှင့် ချည်နှောင်နိုင်သည်။ ပိုင်ဆိုင်မှု သတ်မှတ်ချက်များတွင် domain/data space ဆိုင်ရာ ဖော်ပြချက် ပါဝင်နိုင်ပြီး ပိုင်ဆိုင်မှုလုပ်ဆောင်ချက်များက မှန်ကန်သော data space လမ်းကြောင်းကို ဆက်ခံနိုင်သည်။

SORA Nexus အစားထိုးသတ်မှတ်ချက်များ မရှိပါက နိုဒ်သည် lane တစ်ခုတည်းနှင့် `universal` data space ကို သုံးသည်။ ပါဝင်ပြီးသား SORA Nexus ၏ profile သည် ၎င်းကို lane သုံးခုပါ ကတ်တလောက်ဖြင့် အစားထိုးသည်။ `core` သည် universal အများသုံး lane၊ `governance` သည် အုပ်ချုပ်မှုအလုပ်များအတွက် ဖြစ်ပြီး `zk` သည် အသိပညာမဖော်ပြသော သက်သေ ပူးတွဲမှုနှင့် စာချုပ်တပ်ဆင်မှု အလုပ်များအတွက် ဖြစ်သည်။

ပါဝင်ပြီးသား lane သုံးခုစလုံးသည် အများသုံးဖြစ်ပြီး တူညီသော `universal` data space ကို ရည်ညွှန်းသည်။ ၎င်းတို့က အလုပ်အမျိုးအစားများကို ခွဲခြားပေးသည်:

| Data space | Lane | ရည်ရွယ်ချက် |
| ------------ | ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `universal` | `core` | ပုံမှန် အများသုံး လယ်ဂျာအလုပ်များနှင့် ပုံသေ လမ်းကြောင်းရွေးချယ်မှု။ |
| `universal` | `governance` | အများသုံး အုပ်ချုပ်မှုနှင့် SORA Parliament အလုပ်များ။ |
| `universal` | `zk` | အများသုံး အသိပညာမဖော်ပြသော သက်သေ ပူးတွဲမှုနှင့် စာချုပ်တပ်ဆင်မှု အလုပ်များ။ |

`DataSpaceId::UNIVERSAL == 0` သည် သီးသန့်ထားသော အခြေခံတန်ဖိုးဖြစ်သည်။ အထက်ပါ `governance` နှင့် `zk` အမည်များသည် သီးခြား data space များ မဟုတ်ဘဲ lane များကို သတ်မှတ်သည်။ အဖွဲ့အစည်းဆိုင်ရာ နယ်နိမိတ်များ မတူပါက data space စာရင်းများကို တိတိကျကျ သတ်မှတ်ရမည်။ သီးခြားလုပ်ဆောင်မှုအတွက် ထပ်မံ၍ သီးခြားစစ်မှန်ကြောင်း အတည်ပြုထားသော root လိုအပ်သည်။

ဤဆက်နွှယ်မှုများကို သတ်မှတ်ထားသော [profile တည်ဆောက်မှုများ](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/crates/iroha_config/src/parameters/actual.rs)၊ [lane အကောင်အထည်ဖော်မှု](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/crates/iroha_core/src/sumeragi/lanes/mod.rs) နှင့် [သီးခြား root စည်းမျဉ်းသတ်မှတ်ချက်](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/specs/sumeragi.md) တို့တွင် သတ်မှတ်ထားသည်။

Sumeragi သည် လက်မှတ်ထိုးထားသော RS16 payload ရရှိနိုင်မှုနှင့် အတည်ပြုလက်မှတ်ရ body ပြန်လည်ရယူမှုကို အမြဲအသုံးပြုသည်။ ဤလမ်းကြောင်းများသည် Iroha 3 သဘောတူညီချက် ပရိုတိုကော၏ အစိတ်အပိုင်းဖြစ်ပြီး ဖြန့်ကျက်မှု ပရိုဖိုင်ဖြင့် ပိတ်၍မရပါ။

Runtime အပြုအမူကို ပြင်ဆင်သတ်မှတ်မှုဖိုင်များနှင့် on-chain ပါရာမီတာများမှ ရယူသည်။ Environment variable များကို production လုပ်ဆောင်ချက်များ ဖွင့်ပိတ်ရန် မသုံးပါ။
