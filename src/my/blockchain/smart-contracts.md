# ပညာရှိ စာချုပ်များ {#smart-contracts}

Iroha ငွေပေးချေမှုတွေမှာ `Executable` အသုံးဝင်ဝန်ဆောင်မှုတွေ လုပ်ဆောင်ပါတယ်။ လက်ရှိ ဒေတာပုံစံက အောက်ပါအချက်တွေကို ထောက်ပံ့တယ်။

- `Executable::Instructions`: Iroha ညွှန်ကြားမှု လုပ်ဆောင်ချက်တွေရဲ့ အစီအစဉ်ချထားသော အစုတစ်ခု
- `Executable::ContractCall`: စေလွှတ်ထားသော စာချုပ်ဖြစ်စဉ်အတွက် ဘေးညွှန်ကြားချက်နည်းပညာခေါ်ဆိုမှု
- `Executable::Ivm`: Iroha VM bytecode
- `Executable::IvmProved`: ကြိုတင်တွက်ချက်ထားတဲ့ ညွှန်ကြားမှု အပေါ်လွှာထားပြီး သက်သေခံတဲ့ cryptographic commitment တန်ဖိုးများပါတဲ့ Iroha VM byte code

Kotodama ရှိသည် Iroha ဒါက အဆင့်မြင့် စမတ်ကုထုံး ဘာသာစကားပါ။ `.ko` source file ကို deterministic သို့ compiles IVM conventionally stored as a byte code ကို `.to` တပ်ဆင်ဖို့ လက်ရာပစ္စည်းပါ။ Kotodama ရည်မှန်းချက်များ IVM ရည်မှန်းချက်မရှိဘူး။ RISC-V ဒါမှမဟုတ် WebAssembly.

ပထမထုတ်ပြန်ချက်သည် ABI ဗားရှင်းကိုသာထောက်ပံ့သည်။ syscall နှင့် pointer-ABI မူဝါဒသည်လက်ခံခြင်းနှင့်လုပ်ဆောင်ခြင်းဖြင့်အကောင်အထည်ဖော်သောစည်းမျဉ်းမဲ့ V1 စာချုပ်တစ်ခုဖြစ်သည်။ အခြားဆော့ဖ်ဝဲ အကောင်အထည် ဖော်မှုပတ်ဝန်းကျင် mode မရှိပါ။

## ပညာရှိ စာချုပ်များကို ဘယ်အချိန် အသုံးပြုရမလဲ။ {#when-to-use-smart-contracts}

Transaction ကို တိုက်ရိုက် ဖော်ပြနိုင်တဲ့အခါ ပုံမှန် ညွှန်ကြားချက်တွေကို အသုံးပြုပါ။

- မှတ်ပုံတင် (သို့) မှတ်ပုံတင်ခြင်းမရှိသော ပစ္စည်းများ
- အရင်းအမြစ်များ ထုတ်ပေးခြင်း၊ ဖျက်ဆီးခြင်း သို့မဟုတ် လွှဲပြောင်းခြင်း
- မီတာဒေတာကို update လုပ်ပါ။
- ခွင့်ပြုချက်များ ပေးအပ်ခြင်း (သို့) ရုပ်သိမ်းခြင်း
- trigger တစ်ခုကို လုပ်ပါ။
- ကွင်းဆက်ပေါ်က parameters ကိုသတ်မှတ်ထားသည်

Transaction မှာ packaged logic လိုတဲ့အခါမှာ Smart Contract ကိုသုံးပြီး Static instruction sequence အဖြစ် ဖော်ပြဖို့ ခက်ခဲတဲ့ (သို့) deployed contract instance ကို reference နဲ့ခေါ်ဖို့လိုတဲ့အခါမှာ သုံးပါ။

## IVM လုပ်ဆောင်နိုင်သော ကိရိယာများ {#ivm-executables}

`Executable::Ivm` သည် raw IVM bytecode ကို သယ်ဆောင်သည်။ node များသည် software execution environment ကန့်သတ်ချက်များအတွင်းတွင် executed လုပ်ကြသည်။ chain အတွက် configured လုပ်ထားသော byte code ကို အသေးစားနှင့် deterministic ထားရှိပါ။ စာချုပ်များသည် ငွေပေးချေမှုအကောင်အထည်ဖော်ခြင်း၏တစ်စိတ်တစ်ပိုင်းဖြစ်ပြီး ထို့ကြောင့် သဘောတူညီမှုကိုသက်ရောက်စေသည်။

`Executable::IvmProved` သည် အတည်ပြုမှု သယ်ဆောင်သည့် စီးဆင်းမှုများအတွက် ရည်ရွယ်ထားပြီး အောက်ပါအချက်များကို သယ်ဆောင်သည်။

- IVM ဘိုင်တာကုဒ်
- deterministic instruction ကို overlay လုပ်ပေးခြင်း
- အကောင်အထည်ဖော်ရေးဖြစ်စဉ်များအတွက် cryptographic commitment value
- ဓာတ်ငွေ့ဆိုင်ရာ မူဝါဒအတွက် cryptographic commitment တန်ဖိုး

Proof က overlay ကို executed bytecode နဲ့ ချိတ်ဆက်ပေးပါတယ်။ software processing workflow policy ကိုအမှီပြုပြီး validator တွေက proof ကို စစ်ဆေးနိုင်ပြီး ထပ်မံ play execution ကို security check တစ်ခုအဖြစ် ထပ်မံလုပ်နိုင်ပါတယ်။

## စေလွှတ်ထားသော စာချုပ်ခေါ်ဆိုချက်များ {#deployed-contract-calls}

`Executable::ContractCall` သည် အသုံးပြုထားသော စာချုပ်ဥပမာကို လိပ်စာဖြင့် ဖေါ်ပြပေးသည်။ စာချုပ်ကုဒ်ကို သီးခြား မှတ်ပုံတင်ထားပြီး ငွေကြေးလုပ်ငန်းများတွင် ဘိုင်တာကုဒ်ကို အမြဲမပါဘဲ ရည်ညွှန်းချက်ဖြင့် ဖေါ်ထုတ်ပေးရန် လိုအပ်ပါသည်။

## စာချုပ်သက်တမ်းနှင့် ပိုင်ဆိုင်မှု {#contract-lifecycle-and-ownership}

စေလွှတ်ထားသောလိပ်စာတိုင်းမှာ `ContractLifecycleControlV1` မှတ်တမ်းကို သိမ်းဆည်းထားသည်၊ စာချုပ်မလုပ်ဆောင်သေးသည့် အချိန်အပါအဝင်။ မှတ်တမ်းတွင် ပထမဦးဆုံး စေလွှမ်းတင်ခြင်း၏ မပြောင်းလဲနိုင်သော မူလနေရာ၊ လက်ရှိနှင့် စောင့်ဆိုင်းနေသော ပိုင်ရှင်၊ ရုပ်သိမ်းနိုင်သော ပါလီမန်ကိုယ်စားလှယ်အဖွဲ့များ၊ တက်ကြွသော ကုဒ် cryptographic hash, သုညမဟုတ်သော နှိုင်းယှဉ်မှုနှင့် လဲလှယ်မှု အပြောင်းအလဲ ပြုပြင်ချက်၊ တိုက်ရိုက်တပ်ဆင်မှုသည် တပ်ဆင်ရေးအကောင့်ကို မှတ်တမ်းတင်သည်။ လွှတ်တော်တပ်ဆင်မှုတစ်ခုသည် အဆိုပြုသူ၊ အဆိုပြုချက်-ဆောင်းပါး ID နှင့် အောင်မြင်သော အုပ်ချုပ်ရေးကြိုးပမ်းမှု ID ကိုမှတ်တမ်းတင်သည်။

သက်တမ်းပတ်လည်ပိုင်ရှင်ဆိုသည်မှာ အကောင့်တစ်ခု (သို့) လွှတ်တော်ဖြစ်သည်။ အကောင့်ပိုင်ဆိုင်မှု ပြောင်းလဲခြင်းများသည် သီးခြားကြော်ငြာနှင့် လက်ခံမှုကို အသုံးပြုသည်။ ကမ်းလှမ်းချက်ကိုလက်ခံခြင်းက လွှတ်တော်ကိုယ်စားလှယ်အဖွဲ့တိုင်းကို ရှင်းလင်းပေးသည်။ စာရင်းပိုင်ရှင်က လွှတ်တော်ကို သဘောတူစာချုပ်ကို တက်ကြွ (သို့) ပိတ်ပင်ခွင့်ပြုပြီး ဒီကိုယ်စားလှယ်လောင်းမှုကို ရုပ်သိမ်းနိုင်ပေမဲ့ ကိုယ်စားလှယ်က ဘယ်တော့မှ လွှတ်တော်ဆီက ပိုင်ဆိုင်မှု လွှဲပြောင်းခွင့်မပေးဘူး။ လွှတ်တော်ပိုင် ပြောင်းလဲမှုနဲ့ လွှတ်တော်လက်ခံမှုဟာ စစ်ဆေးတဲ့ အုပ်ချုပ်ရေး သက်ရောက်မှုတွေကနေ ကျင့်သုံးတာပါ။

အသားအရေ `ActivateContractInstance` နှင့် `DeactivateContractInstance` သင်ကြားချက်များကို ငွေကြေးရင်းနှီးမြှုပ်နှံမှု အကောင့်ပိုင်ရှင်သာ ရရှိနိုင်ပါသည်။ `expected_revision`; မဖြစ်မနေ (သို့) သုည ပြင်ဆင်ချက်များ ပိတ်နိုင်ခြင်းမရှိပါ။ Raw Activation က သက်တမ်းပတ်သတ်မှတ်ချက်နဲ့ မှတ်ပုံတင်ထားတဲ့ လက်ရာ၊ နည်းပညာလက်မှတ်ကို အတည်ပြုပေးပြီး ABI မပြောင်းခင် `active_code_hash`. Deactivation က Active Code ရဲ့ cryptographic hash ကို ရှင်းလင်းပေးပေမဲ့ ပိုင်ဆိုင်မှုနဲ့ provenance ကို ထိန်းသိမ်းထားတယ်။ အောင်မြင်တဲ့ ဘဝ စက်ဝန်း ကူးပြောင်းမှုတိုင်းဟာ ပြန်လည်သုံးသပ်မှုကို တိုးတက်စေပြီး အပြည့်အဝ post-state ကို ထုတ်လွှင့်ပေးပါတယ်။

Activation သည် manifest-declared lifecycle hook တစ်ခုကိုလည်း ဖြစ်ပေါ်စေနိုင်သည်။ ပထမဦးဆုံး Activation သည် Technical Manifesto တွင် `EntryPointKind::Hajimari` ဝင်ရောက်ရေးနေရာ (`hajimari`/`始まり`) အဆင့်များ `Hajimari`. Active Address ကို Technical Manifesto ပါတဲ့ Code ထဲကို ပြန်ထည့်ပေးခြင်း `EntryPointKind::Kaizen` ဝင်ရောက်ရေးနေရာ (`kaizen`/`改善`) အဆင့်များ `Kaizen`. စည်းမျဉ်းစည်းကမ်းတွေ ချက်ချင်း ပြောင်းလဲပေမဲ့ စာချုပ်တော့ မပြီးသေးပါဘူး။ `Kotoage` နှင့် `View` မှန်ကန်တဲ့ အဆင့်သတ်မှတ်ထားတဲ့ ချောင်းချောင်း အောင်မြင်တဲ့အထိ နည်းပညာဆိုင်ရာ တောင်းဆိုချက်ကို ပယ်ချလိုက်ပါတယ်။ ချုပ်ကိုင်ထားတဲ့အချိန်မှာ နောက်ထပ် တက်ကြွမှုတစ်ခုလည်း ပယ်ချခံရတယ်။

စင်ပေါ်က hook ကိုခေါ်ယူပါ `Executable::ContractCall` စာချုပ်လိပ်စာတစ်ခုတည်းနဲ့ ကုဒ်အသစ်ရဲ့ cryptographic hash ကိုသုံးပြီး တိကျတဲ့ `hajimari` ဒါမှမဟုတ် `kaizen` Entry point နှင့် ၎င်း၏ Technical Manifesto တွင် ဖော်ပြထားသော အကြောင်းပြချက်များ။ ဆော့ဖ်ဝဲ အကောင်အထည်ဖော်မှု ပတ်ဝန်းကျင်က Address-and-selector-scoped ကိုပေးသည်။ `CanInvokeContractEntrypoint` ခွင့်ပြုချက်။ တောင်းဆိုနေတဲ့ ဖောက်သည်တွေက ဒီခွင့်ပြုချက်ကို ဖန်တီးခြင်း (သို့) မပေးရဘူး။ pending marker မှာ runtime ပေါ်ပေါက်တဲ့ deterministic ကို ထည့်သွင်းထားပါတယ်။ `transition_id` ပြီးတော့ အသစ် `code_hash`; (က) `Kaizen` marker မှာလည်း ပါဝင်ပါတယ်။ `previous_code_hash`. ဖောက်သည်တွေက တွက်ချက်မလုပ်ဘူး၊ တင်မပေးဘူး။ `transition_id`. အောင်မြင်တဲ့ ချုပ်က အမှတ်တံဆိပ်ကို အက်တမ်နဲ့ စားသုံးပြီး ကျရှုံးနေတဲ့ ချုပ်က နောက်တစ်ကြိမ် ထပ်မံစမ်းသပ်ဖို့ စောင့်ဆိုင်းထားတယ်။

အရေးပေါ်အဆင့် ပါလီမန် အဆိုပြုချက်သည် လက်ရှိ ပြုပြင်ပြောင်းလဲမှု, ကုဒ် cryptographic hash နှင့် သုညမဟုတ်သော incident cryptographic digest တန်ဖိုးကို ချိတ်ဆက်ထားသည့်အခါ အနည်းဆုံး ဘလော့က ၃၆၀၀ ကို ပိတ်ပင်နိုင်သည်။ Technical invocations များအား သတ်မှတ်မှု အမြင့်မှ စ၍ သက်တမ်းကုန်ဆုံးချိန်အထိ ပိတ်ပင်ထားသည်။ Expiry သည် အကောင်အထည်ဖော်မှုကိုပြန်လည်ပြုပြင်ပေးသည်ဆိုသော်လည်း hold ကိုမပယ်ဖျက်ပါ။ သက်သေခံ `CompleteEmergencyHoldRetrospective` လုပ်ဆောင်ချက်တစ်ခုက မှတ်တမ်းရှင်းလင်းခြင်းမတိုင်မီ တိကျသော hold ID များနှင့် cryptographic digest တန်ဖိုးကိုပေါင်းပြီး သုညမဟုတ်သော ရှာဖွေရာ အမြစ်ကို ချိတ်ဆက်ရမည်ဖြစ်ပြီး နောက်တစ်ကြိမ် ထိန်းသိမ်းခြင်းကို မချမှတ်နိုင်ပေ။ နောက်တစ်ခါတွင် ပြန်လည်ကြည့်ရှုမှု ကျန်ရှိနေသည်။

App API ကို activated လုပ်ထားပါက `GET /v1/gov/contracts/{contract_address}` ဖြင့် မှတ်တမ်းတင်ထားသောအခြေအနေကို ဖတ်ပါ။ ၎င်း၏ `found` ကွင်းသည် သက်တမ်းပတ်လည်မှတ်တမ်းတစ်ခုရှိသည်ဟုဆိုလိုပြီးလိပ်စာတွင်လက်ရှိလုပ်ဆောင်နေသည့်ကုဒ်မရှိဟုဆိုသည်။

## လုပ်ငန်းဆိုင်ရာ လမ်းညွှန်ချက်များ {#operational-guidance}

- စာချုပ်များအား သတ်မှတ်မှုရှိစေရန်။ စာချုပ်အပြုအမူသည် ဒေသတွင်းဒေသခံစနစ် နာရီအချိန်၊ အိမ်ရှင်ဖိုင်စနစ်အခြေအနေ၊ ကွန်ရက်တောင်းဆိုချက်များ သို့မဟုတ် အခြား peer-local input များအပေါ် မမှီခိုရပါ။
- အသုံးဝင်ဝန်ဆောင်မှုများကို ညှိထားပါ။ ဘိုင်တကုဒ်ကြီးသည် ငွေချေးမှု အရွယ်အစားကို မြှင့်တင်ပေးပြီး ဘလော့ကာ ပျံ့နှံ့မှု ကုန်ကျစရိတ်ကို မြှင့်တင်ပေးသည်။
- ရိုးရှင်းတဲ့ blockchain ledger အပြောင်းအလဲများအတွက် ရိုက်နှိပ်ထားသော ညွှန်ကြားချက်များကို ဦးစားပေးပါ။ ၎င်းတို့ကို စစ်ဆေးရန် ပိုလွယ်ပြီး အကောင်အထည်ဖော်ရန် စျေးသက်သာသည်။
- စာချုပ်တိုးတက်မှုနဲ့ မှတ်ပုံတင် ခွင့်ပြုချက်တွေကို အရဲစွန့်မှု မြင့်မားတဲ့ လုပ်ငန်း ထိန်းချုပ်မှုတွေအဖြစ် သတ်မှတ်ပေးပါ။
