# ပညာရှိ စာချုပ်များ {#smart-contracts}


Iroha ငွေပေးချေမှုတွေမှာ `Executable` အသုံးဝင်ဝန်ဆောင်မှုတွေ လုပ်ဆောင်ပါတယ်။ လက်ရှိ ဒေတာပုံစံက အောက်ပါအချက်တွေကို ထောက်ပံ့တယ်။

- `Executable::Instructions`: Iroha အထူးညွှန်ကြားချက်များ၏ အစီအစဉ်ချထားသောအစု
- `Executable::ContractCall`: စေလွှတ်ထားသော သဘောတူစာချုပ်ဖြစ်စဉ်အတွက် ဘေးညွှန်ကြားချက်ခေါ်ဆိုမှု
- `Executable::Ivm`: Iroha VM bytecode
- `Executable::IvmProved`: ကြိုတင် တွက်ချက်ထားသော ညွှန်ကြားမှု အပေါ်လွှာနှင့် သက်သေခံတာဝန်များရှိသည့် Iroha VM ဘိုက်ကုဒ်

Kotodama ရှိသည် Iroha ဒါက အဆင့်မြင့် စမတ်ကုထုံး ဘာသာစကားပါ။ `.ko` source file ကို deterministic သို့ compiles IVM conventionally stored as a byte code ကို `.to` တပ်ဆင်ဖို့ လက်ရာပစ္စည်းပါ။ Kotodama ရည်မှန်းချက်များ IVM ရည်မှန်းချက်မရှိဘူး။ RISC-V ဒါမှမဟုတ် WebAssembly.

ပထမထုတ်ပြန်မှုသည် ABI ဗားရှင်းကိုသာထောက်ပံ့သည်။ syscall နှင့် pointer-ABI မူဝါဒသည်လက်ခံခြင်းနှင့်အကောင်အထည်ဖော်ခြင်းဖြင့် အကောင်အထည် ဖော်သော စည်းကမ်းမဲ့ V1 စာချုပ်တစ်ခုဖြစ်သည်။ အစားထိုး runtime mode မရှိပါ။

## ပညာရှိ စာချုပ်များကို ဘယ်အချိန် အသုံးပြုရမလဲ။ {#when-to-use-smart-contracts}

Transaction ကို တိုက်ရိုက် ဖော်ပြနိုင်တဲ့အခါ ပုံမှန် ညွှန်ကြားချက်တွေကို အသုံးပြုပါ။

- မှတ်ပုံတင် (သို့) မှတ်ပုံတင်ခြင်းမရှိသော ပစ္စည်းများ
- မင်တာ၊ လောင်ကျွမ်းခြင်း သို့မဟုတ် လွှဲပြောင်းမှု အရင်းအမြစ်များ
- မီတာဒေတာကို update လုပ်ပါ။
- ခွင့်ပြုချက်များ ပေးအပ်ခြင်း (သို့) ရုပ်သိမ်းခြင်း
- trigger တစ်ခုကို လုပ်ပါ။
- ကွင်းဆက်ပေါ်က parameters ကိုသတ်မှတ်ထားသည်

Transaction မှာ packaged logic လိုတဲ့အခါမှာ Smart Contract ကိုသုံးပြီး Static instruction sequence အဖြစ် ဖော်ပြဖို့ ခက်ခဲတဲ့ (သို့) deployed contract instance ကို reference နဲ့ခေါ်ဖို့လိုတဲ့အခါမှာ သုံးပါ။

## IVM လုပ်ဆောင်နိုင်သော ကိရိယာများ {#ivm-executables}

`Executable::Ivm` သည် raw IVM bytecode ကို သယ်ဆောင်သည်။ node များသည် chain အတွက်သတ်မှတ်ထားသော runtime ကန့်သတ်ချက်များအတွင်းတွင် ထိုbytecode ကိုလုပ်ဆောင်ကြသည်။ bytecode များကိုသေးငယ်ပြီး deterministic ထားရှိပါ။ စာချုပ်များသည် ငွေပေးချေမှု အကောင်အထည်ဖော်ခြင်း၏တစ်စိတ်တစ်ပိုင်းဖြစ်ပြီး ထို့ကြောင့် သဘောတူညီချက်ကိုသက်ရောက်စေသည်။

`Executable::IvmProved` သည် အတည်ပြုမှု သယ်ဆောင်သည့် စီးဆင်းမှုများအတွက် ရည်ရွယ်ထားပြီး အောက်ပါအချက်များကို သယ်ဆောင်သည်။

- IVM ဘိုင်တာကုဒ်
- deterministic instruction ကို overlay လုပ်ပေးခြင်း
- အကောင်အထည်ဖော်မှု-ဖြစ်ရပ်များအတွက် ကတိပေးချက်
- ဓာတ်ငွေ့ဆိုင်ရာ မူဝါဒ ကတိပေးချက်

proof က overlay ကို executed bytecode နဲ့ ချိတ်ဆက်ပေးပါတယ်။ pipeline policy အပေါ် မူတည်ပြီး validators တွေက proof ကို စစ်ဆေးနိုင်ပြီး ထပ်မံ play execution ကို safety check အဖြစ် ထပ်မံလုပ်နိုင်ပါတယ်။

## အသုံးပြုထားသော စာချုပ်ခေါ်ဆိုချက်များ {#deployed-contract-calls}

`Executable::ContractCall` သည် အသုံးပြုထားသော စာချုပ်ဥပမာကို လိပ်စာဖြင့် ခေါ်ယူသည်။ စာချုပ်ကုဒ်ကို သီးခြားမှတ်ပုံတင်တဲ့အခါ ဒါကိုသုံးပြီး ငွေကြေးလုပ်ငန်းများတွင် ဘိုင်တာကုဒ်ကို အမြဲမပါဘဲ ရည်ညွှန်းချက်ဖြင့်ခေါ်ဆိုသင့်ပါတယ်။

## စာချုပ်သက်တမ်းနှင့် ပိုင်ဆိုင်မှု {#contract-lifecycle-and-ownership}

စေလွှတ်ထားသောလိပ်စာတိုင်းမှာ `ContractLifecycleControlV1` မှတ်တမ်းကို သိမ်းဆည်းထားသည်၊ စာချုပ်က မလုပ်ဆောင်သေးသည့် အချိန်အပါအဝင်။ မှတ်တမ်းတွင် ပထမဦးဆုံး စေလွှမ်းတင်မှု မူလနေရာ၊ လက်ရှိနှင့် စောင့်ဆိုင်းနေသည့် ပိုင်ရှင်၊ ရုပ်သိမ်းနိုင်သော လွှတ်တော်ကိုယ်စားလှယ်အဖွဲ့များ၊ တက်ကြွသော ကုဒ် hash၊ သုညမဟုတ်သော နှိုင်းယှဉ်ခြင်းနှင့် လဲလှယ်ခြင်း ပြုပြင်ချက် ပါဝင်သည်။ တိုက်ရိုက်တပ်ဆင်မှုသည် တပ်ဆင်ရေးအကောင့်ကို မှတ်တမ်းတင်သည်။ လွှတ်တော်တပ်ဆင်မှုတစ်ခုသည် အဆိုပြုသူ၊ အဆိုပြုချက်-အကြောင်းအရာ ID နှင့် အောင်မြင်သော အုပ်ချုပ်ရေးကြိုးပမ်းမှုကို မှတ်တမ်းတင်သည် ID.

သက်တမ်းပတ်လည်ပိုင်ရှင်ဆိုသည်မှာ အကောင့်တစ်ခု (သို့) လွှတ်တော်ဖြစ်သည်။ အကောင့်ပိုင်ဆိုင်မှု ပြောင်းလဲခြင်းများသည် သီးခြားကြော်ငြာနှင့် လက်ခံမှုကို အသုံးပြုသည်။ ကမ်းလှမ်းချက်ကိုလက်ခံခြင်းက လွှတ်တော်ကိုယ်စားလှယ်အဖွဲ့တိုင်းကို ရှင်းလင်းပေးသည်။ စာရင်းပိုင်ရှင်က လွှတ်တော်ကို သဘောတူစာချုပ်ကို တက်ကြွ (သို့) ပိတ်ပင်ခွင့်ပြုပြီး ဒီကိုယ်စားလှယ်လောင်းမှုကို ရုပ်သိမ်းနိုင်ပေမဲ့ ကိုယ်စားလှယ်က ဘယ်တော့မှ လွှတ်တော်ဆီက ပိုင်ဆိုင်မှု လွှဲပြောင်းခွင့်မပေးဘူး။ လွှတ်တော်ပိုင် ပြောင်းလဲမှုနဲ့ လွှတ်တော်လက်ခံမှုဟာ စစ်ဆေးတဲ့ အုပ်ချုပ်ရေး သက်ရောက်မှုတွေကနေ ကျင့်သုံးတာပါ။

အသားအရေ `ActivateContractInstance` နှင့် `DeactivateContractInstance` သင်ကြားချက်များကို ငွေကြေးရင်းနှီးမြှုပ်နှံမှု အကောင့်ပိုင်ရှင်သာ ရရှိနိုင်ပါသည်။ `expected_revision`; Runtime က အဟောင်း (သို့) သုည ပြင်ဆင်ချက်တွေကို ပယ်ချတယ်။ Raw activation က ြမန်မာ သက်တမ်းသက်တမ်းမှတ်တမ်းနဲ့ မှတ်ပုံတင်ထားတဲ့ အနုပညာလက်ရာကို အတည်ပြုပေးပြီး ABI မပြောင်းခင် `active_code_hash`. Deactivation က Active Code hash ကို ရှင်းလင်းပေးပေမဲ့ ပိုင်ဆိုင်မှုနဲ့ မူရင်းကို ထိန်းသိမ်းထားတယ်။ အောင်မြင်တဲ့ ဘဝ စက်ဝန်း ကူးပြောင်းမှုတိုင်းဟာ ပြန်လည်သုံးသပ်မှုကို တိုးတက်စေပြီး အပြည့်အဝ post-state ကို ထုတ်လွှင့်ပေးပါတယ်။

Activation သည် manifest-declared lifecycle hook တစ်ခုကိုလည်း stage လုပ်နိုင်သည်။ manifesto တွင် `EntryPointKind::Hajimari` ဝင်ရောက်ရေးနေရာ (`hajimari`/`始まり`) အဆင့်များ `Hajimari`. Active Address ကို Code ထဲကို ပြန်ထည့်လိုက်ပါ `EntryPointKind::Kaizen` ဝင်ရောက်ရေးနေရာ (`kaizen`/`改善`) အဆင့်များ `Kaizen`. စည်းမျဉ်းစည်းကမ်းတွေ ချက်ချင်း ပြောင်းလဲပေမဲ့ စာချုပ်တော့ မပြီးသေးပါဘူး။ `Kotoage` နှင့် `View` call ကို stageed hook အောင်မြင်တဲ့အထိ ပယ်ချလိုက်ပါတယ်။ hook က စောင့်နေတုန်း နောက်ထပ် activation တစ်ခုကိုလည်း ပယ်ချလိုက်တယ်။

`Executable::ContractCall` ကို စာချုပ်အလိပ်စာနှင့် ကုဒ် hash အသစ်တစ်ခုတည်းတွင် `hajimari` (သို့) `kaizen` entry point အတိအကျကို အသုံးပြုပြီး ၎င်း၏ manifest တွင် ဖော်ပြထားသော argument များကို အသုံးပြု၍ အဆင့်သတ်မှတ်ထားသော hook ကိုခေါ်ယူပါ။ Runtime သည် address-and-selector-scoped `CanInvokeContractEntrypoint` ခွင့်ပြုချက်ကိုပေးသည်၊ ဖုန်းခေါ်သူများသည် ထိုခွင့်ပြုချက်ကို ဖန်တီးခြင်း သို့မဟုတ် ပေးအပ်ခြင်းမရှိပါ။ စောင့်ဆိုင်းနေသော marker တွင် runtime-generated, deterministic `transition_id` နှင့် အသစ် `code_hash` ပါရှိသည်။ `Kaizen` marker တွင်လည်း `previous_code_hash` ပါရှိသည်။ ဖောက်သည်များက `transition_id` ကို တွက်ချက်ခြင်း သို့မဟုတ် တင်သွင်းခြင်းမရှိပါ။ အောင်မြင်သော ချောင်းတစ်ခုက အမှတ်တံဆိပ်ကို အက်တမ်အားဖြင့် စားသုံးပြီး ကျရှုံးတဲ့ ချောင်းတစ်ချောင်းက နောက်ပိုင်း ထပ်မံစမ်းသပ်မှုအတွက် စောင့်ဆိုင်းထားသည်။

အရေးပေါ်အဆင့် ပါလီမန် အဆိုတစ်ခုသည် လက်ရှိပြုပြင်ချက်၊ ကုဒ်ဟက်ရှ်နှင့် သုညမဟုတ်သော ဖြစ်စဉ်စာရင်းကို ချိတ်ဆက်ထားပါက အများဆုံး ၃၆၀၀ ဘလော့ကို ပိတ်ပင်နိုင်သည်။ အမိန့်ချမှတ်မှု အမြင့်မှ စ၍ သက်တမ်းကုန်ဆုံးသည့် အမြင့်အထိ ဖုန်းခေါ်ဆိုမှုများပိတ်ပင်ထားသည်။ Expiry သည် အကောင်အထည်ဖော်မှုကို ပြန်လည်ပြုပြင်ပေးသော်လည်း ထိန်းသိမ်းထားခြင်းကို ဖျက်ပစ်ခြင်းမဟုတ်ပါ။ စစ်ဆေးသော `CompleteEmergencyHoldRetrospective` လုပ်ဆောင်ချက်သည် မှတ်တမ်းရှင်းလင်းရန်မတိုင်မီ တိကျတဲ့ ထိန်းချုပ်ထားမှုကို IDs ချည်နှောင်ပြီး အစာခြေခြင်းနှင့်အတူ သုညမဟုတ်သော ရှာဖွေမှု အမြစ်တစ်ခုရှိရမည်။ နောက်တစ်ကြိမ်ထိန်းသိမ်းမှုကို ထပ်မံသတ်မှတ်နိုင်ခြင်းမရှိဘဲ ဒီနောက်ဆက်တွဲစောင့်ကြည့်မှုက ဆက်လက်ရှိနေသည်။

App API ကို activated လုပ်ထားပါက `GET /v1/gov/contracts/{contract_address}` ဖြင့် မှတ်တမ်းတင်ထားသောအခြေအနေကို ဖတ်ပါ။ ၎င်း၏ `found` ကွင်းသည် သက်တမ်းပတ်လည်မှတ်တမ်းတစ်ခုရှိသည်ဟုဆိုလိုပြီးလိပ်စာတွင်လက်ရှိလုပ်ဆောင်နေသည့်ကုဒ်မရှိဟုဆိုသည်။

## လုပ်ငန်းဆိုင်ရာ လမ်းညွှန်ချက်များ {#operational-guidance}

- စာချုပ်များကို သတ်မှတ်ထားပါ။ စာချုပ်အပြုအမူသည် ဒေသတွင်း နံရံနာရီအချိန်၊ အိမ်ရှင်ဖိုင်စနစ်အခြေအနေ၊ ကွန်ရက်ခေါ်ဆိုမှုများ သို့မဟုတ် အခြား peer-local input များအပေါ် မူတည်ခြင်းမရှိရပေ။
- အသုံးဝင်ဝန်ဆောင်မှုများကို ညှိထားပါ။ ဘိုင်တကုဒ်ကြီးသည် ငွေချေးမှု အရွယ်အစားကို မြှင့်တင်ပေးပြီး ဘလော့ကာ ပျံ့နှံ့မှု ကုန်ကျစရိတ်ကို မြှင့်တင်ပေးသည်။
- ရိုးရှင်းတဲ့ Ledger အပြောင်းအလဲတွေအတွက် ရိုက်နှိပ်ထားတဲ့ ညွှန်ကြားချက်တွေကို ကြိုက်တယ်။ ဒါတွေကို စစ်ဆေးဖို့ ပိုလွယ်ပြီး အကောင်အထည်ဖော်ဖို့ စျေးသက်သာပါတယ်။
- စာချုပ်တိုးတက်မှုနဲ့ မှတ်ပုံတင် ခွင့်ပြုချက်တွေကို အရဲစွန့်မှု မြင့်မားတဲ့ လုပ်ငန်း ထိန်းချုပ်မှုတွေအဖြစ် သတ်မှတ်ပေးပါ။
