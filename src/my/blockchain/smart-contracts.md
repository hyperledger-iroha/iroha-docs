# ပညာရှိ စာချုပ်များ {#smart-contracts}

Iroha ငွေပေးချေမှုတွေမှာ `Executable` အသုံးဝင်ဝန်ဆောင်မှုတွေ လုပ်ဆောင်ပါတယ်။ လက်ရှိ ဒေတာပုံစံက အောက်ပါအချက်တွေကို ထောက်ပံ့တယ်။

- `Executable::Instructions`: Iroha အထူးညွှန်ကြားချက်များ၏ အစီအစဉ်ချထားသောအစု
- `Executable::ContractCall`: စေလွှတ်ထားသော သဘောတူစာချုပ်ဖြစ်စဉ်အတွက် ဘေးညွှန်ကြားချက်ခေါ်ဆိုမှု
- `Executable::Ivm`: Iroha VM bytecode
- `Executable::IvmProved`: ကြိုတင် တွက်ချက်ထားသော ညွှန်ကြားမှု အပေါ်လွှာနှင့် သက်သေခံတာဝန်များရှိသည့် Iroha VM ဘိုက်ကုဒ်

Kotodama သည် Iroha ၏ အဆင့်မြင့် စမတ်ကန်ထရိုက် ဘာသာစကားဖြစ်သည်။ `.ko` အရင်းအမြစ်ဖိုင်ကို တိကျသတ်မှတ်ထားသော IVM ဘိုက်ကုဒ်အဖြစ် စုစည်းပြီး တပ်ဆင်ရန်အတွက် `.to` အာတီဖက်အဖြစ် ထုံးစံအတိုင်း သိမ်းဆည်းသည်။ Kotodama သည် IVM ကိုသာ ပစ်မှတ်ထားသည်။ RISC-V သို့မဟုတ် WebAssembly ကို ပစ်မှတ်မထားပါ။

ပထမဆုံး release တွင် ABI version 1 ကိုသာ support လုပ်သည်။ syscall နှင့် pointer-ABI policy ကို contract admission နှင့် execution က အခြေအနေမဲ့ အတည်ပြုအသုံးချသည်။ runtime compatibility toggle မရှိပါ။

## ပညာရှိ စာချုပ်များကို ဘယ်အချိန် အသုံးပြုရမလဲ။ {#when-to-use-smart-contracts}

Transaction ကို တိုက်ရိုက် ဖော်ပြနိုင်တဲ့အခါ ပုံမှန် ညွှန်ကြားချက်တွေကို အသုံးပြုပါ။

- မှတ်ပုံတင် (သို့) မှတ်ပုံတင်ခြင်းမရှိသော ပစ္စည်းများ
- မင်တာ၊ လောင်ကျွမ်းခြင်း သို့မဟုတ် လွှဲပြောင်းမှု အရင်းအမြစ်များ
- မီတာဒေတာကို update လုပ်ပါ။
- ခွင့်ပြုချက်များ ပေးအပ်ခြင်း (သို့) ရုပ်သိမ်းခြင်း
- trigger တစ်ခုကို လုပ်ပါ။
- ကွင်းဆက်ပေါ်က parameters ကိုသတ်မှတ်ထားသည်

Transaction မှာ packaged logic လိုတဲ့အခါမှာ Smart Contract ကိုသုံးပြီး Static instruction sequence အဖြစ် ဖော်ပြဖို့ ခက်ခဲတဲ့ (သို့) deployed contract instance ကို reference နဲ့ခေါ်ဖို့လိုတဲ့အခါမှာ သုံးပါ။

## IVM လုပ်ဆောင်နိုင်သော ကိရိယာများ {#ivm-executables}

`Executable::Ivm` သည် raw IVM bytecode ကို သယ်ဆောင်သည်။ node များသည် chain အတွက်သတ်မှတ်ထားသော runtime ကန့်သတ်ချက်များအတွင်းတွင် ထိုbytecode ကိုလုပ်ဆောင်ကြသည်။ bytecode များကိုသေးငယ်ပြီး deterministic ထားရှိပါ။ စာချုပ်များသည် ငွေပေးချေမှု အကောင်အထည်ဖော်ခြင်း၏တစ်စိတ်တစ်ပိုင်းဖြစ်ပြီး ထို့ကြောင့် သဘောတူညီချက်ကိုသက်ရောက်စေသည်။

`Executable::IvmProved` သည် အတည်ပြုမှု သယ်ဆောင်သည့် စီးဆင်းမှုများအတွက် ရည်ရွယ်ထားပြီး အောက်ပါအချက်များကို သယ်ဆောင်သည်။

- IVM ဘိုင်တာကုဒ်
- deterministic instruction ကို overlay လုပ်ပေးခြင်း
- အကောင်အထည်ဖော်မှု-ဖြစ်ရပ်များအတွက် ကတိပေးချက်
- ဓာတ်ငွေ့ဆိုင်ရာ မူဝါဒ ကတိပေးချက်

proof က overlay ကို executed bytecode နဲ့ ချိတ်ဆက်ပေးပါတယ်။ pipeline policy အပေါ် မူတည်ပြီး validators တွေက proof ကို စစ်ဆေးနိုင်ပြီး ထပ်မံ play execution ကို safety check အဖြစ် ထပ်မံလုပ်နိုင်ပါတယ်။

## အသုံးပြုထားသော စာချုပ်ခေါ်ဆိုချက်များ {#deployed-contract-calls}

`Executable::ContractCall` သည် အသုံးပြုထားသော စာချုပ်ဥပမာကို လိပ်စာဖြင့် ခေါ်ယူသည်။ စာချုပ်ကုဒ်ကို သီးခြားမှတ်ပုံတင်တဲ့အခါ ဒါကိုသုံးပြီး ငွေကြေးလုပ်ငန်းများတွင် ဘိုင်တာကုဒ်ကို အမြဲမပါဘဲ ရည်ညွှန်းချက်ဖြင့်ခေါ်ဆိုသင့်ပါတယ်။

## စာချုပ်သက်တမ်းနှင့် ပိုင်ဆိုင်မှု {#contract-lifecycle-and-ownership}

စေလွှတ်ထားသောလိပ်စာတိုင်းမှာ `ContractLifecycleControlV1` မှတ်တမ်းကို သိမ်းဆည်းထားသည်၊ စာချုပ်က မလုပ်ဆောင်သေးသည့် အချိန်အပါအဝင်။ မှတ်တမ်းတွင် ပထမဦးဆုံး စေလွှမ်းတင်မှု မူလနေရာ၊ လက်ရှိနှင့် စောင့်ဆိုင်းနေသည့် ပိုင်ရှင်၊ ရုပ်သိမ်းနိုင်သော လွှတ်တော်ကိုယ်စားလှယ်အဖွဲ့များ၊ တက်ကြွသော ကုဒ် hash၊ သုညမဟုတ်သော နှိုင်းယှဉ်ခြင်းနှင့် လဲလှယ်ခြင်း ပြုပြင်ချက် ပါဝင်သည်။ တိုက်ရိုက်တပ်ဆင်မှုတစ်ခုက တင်ပြသူအကောင့်ကို ပိုင်ရှင်အဖြစ် သတ်မှတ်ပြီး တပ်ဆင်ခြင်း၏ မူလနေရာအဖြစ် မှတ်တမ်းတင်တယ်။ လွှတ်တော်တပ်ဆင်မှုတစ်ရပ်က ပါလီမန်ကို ပိုင်ဆိုင်သူအဖြစ် သတ်မှတ်ကာ ၎င်းရဲ့ အဆိုပြုသူ၊ အဆိုပြုချက် အကြောင်းအရာ ID ကို မှတ်တမ်းတင်တယ်၊ အောင်မြင်တဲ့ အုပ်ချုပ်ရေးကြိုးပမ်းမှု ID ကို ရင်းမြစ်အဖြစ်သာ သတ်မှတ်ထားတယ်။

ဖွဲ့စည်းထားသော ကာကွယ်ထားတဲ့ နာမည်နေရာများကို လွှတ်တော်တွင် အသုံးပြုနိုင်ရန် ကန့်သတ်ထားသည်။ `CanRegisterSmartContractCode` ပိုင်ဆိုင်မှုသည် လက်ရာပစ္စည်းများအား မှတ်ပုံတင်ခွင့်ပြုသော်လည်း တိုက်ရိုက်မပေးပါ။ ကာကွယ်ထားတဲ့ နာမ်စားနေရာတစ်ခုမှာ ဖြန့်ချိခြင်း (သို့) raw activation လုပ်ပေးခြင်း။ အဲဒီမှာ ပထမဦးဆုံး သက်တမ်း စက်ဝန်း မှတ်တမ်းကို လွှတ်တော်က အသိအမှတ်ပြုတဲ့ ဖြန့်ဖြူးမှုလမ်းကြောင်းကနေ ဖန်တီးဖို့လိုပါတယ်။

သက်တမ်းပတ်လည်ပိုင်ရှင်သည် အကောင့်တစ်ခု (သို့) လွှတ်တော်ဖြစ်သည်။ အကောင့်ပိုင်ဆိုင်မှု ပြောင်းလဲခြင်း `OfferContractOwnership` ကိုအသုံးပြုပြီး စောင့်ဆိုင်းနေသောပိုင်ရှင်၏ `AcceptContractOwnership` ကိုဆက်သွယ်သည်။ လက်ရှိပိုင်ရှင်က `CancelContractOwnershipOffer` နှင့်အတူ လက်မခံသော ကမ်းလှမ်းချက်။ လက်ခံခြင်းသည် ပါလီမန်ကိုယ်စားလှယ်အဖွဲ့တစ်ခုခုကို ရှင်းလင်းစေသည်။ အကောင့်ဖျက်သိမ်းမှုသည် စာချုပ်ပိုင်ရှင်ဖြစ်နေချိန်တွင် ပယ်ချခံရမည်။ (သို့) ကြိုတင်လက်ခံထားရမည့် ကမ်းလှမ္းမှုရှိသူ ဖြစ်နေစဉ်တွင် အကောင့်ဖျက်ခြင်းဖြစ်သည်။

အကောင့်ပိုင်ရှင်က လွှတ်တော်ကို သဘောတူစာချုပ်ကို အဆင့်မြှင့်တင်၊ တက်ကြွ (သို့) ပိတ်ပင်ခွင့်ပြုပြီး ဒီကိုယ်စားလှယ်လောင်းကို ရုပ်သိမ်းနိုင်သည်။ ကိုယ်စားလှယ်က ဘယ်တော့မှ လွှတ်တော်အား မူပိုင်ခွင့်လွှဲပြောင်းခြင်း (သို့) ကိုယ်စားလှယ်အဖွဲ့ကိုယ်၌ကို ပြောင်းလဲခြင်း။ လွှတ်တော်ပိုင်ဆိုင်သည့်မူပိုင်ပြောင်းလဲမှုများနှင့် လွှတ်တော်လက်ခံမှုသည် စစ်ဆေးသော အုပ်ချုပ်ရေးသက်ရောက်မှုများမှတဆင့် ကျင့်သုံးသည်။

အသားအရေ `ActivateContractInstance` နှင့် `DeactivateContractInstance` သင်ကြားချက်များကို ငွေကြေးရင်းနှီးမြှုပ်နှံမှု အကောင့်ပိုင်ရှင်သာ ရရှိနိုင်ပါသည်။ `expected_revision`; မဖြစ်မနေ (သို့) သုည ပြင်ဆင်ချက်များ ပိတ်နိုင်ခြင်းမရှိပါ။ Raw Activation က သက်တမ်းသက်တမ်းမှတ်တမ်းနဲ့ မှတ်ပုံတင်ထားတဲ့ အနုပညာလက်ရာကို အတည်ပြုပေးပြီး ABI မပြောင်းခင် `active_code_hash`. Deactivation က Active Code hash ကို ရှင်းလင်းပေးပေမဲ့ ပိုင်ဆိုင်မှုနဲ့ မူရင်းကို ထိန်းသိမ်းထားတယ်။ အောင်မြင်တဲ့ ဘဝ စက်ဝန်း ကူးပြောင်းမှုတိုင်းဟာ ပြန်လည်သုံးသပ်မှုကို တိုးတက်စေပြီး အပြည့်အဝ post-state ကို ထုတ်လွှင့်ပေးပါတယ်။

အရေးပေါ်အဆင့် ပါလီမန် အဆိုပြုချက်သည် ပါလီမန်၏ အပြည့်အဝကွန်ရက်မှတစ်ဆင့်သာ ရပ်ဆိုင်းနိုင်ပြီး မူလမူဝါဒစုံစမ်းရေးအဖွဲ့ အစည်းအဝေးနေရာများ၏ သုံးပုံနှစ်ပုံထက်မနည်းမှ "အေး" မဲပေးခြင်းဖြင့်ဖြစ်သည်။ ရပ်ဆိုင်းမှုက လက်ရှိ ပြုပြင်ပြောင်းလဲမှု၊ ကုဒ်ဟက်ရှ်နှင့် သုညမဟုတ်သော ဖြစ်စဉ်စာရင်းကို ချိတ်ဆက်ထားပြီး အများဆုံး ၃၆၀၀ ဘလော့ကို ရေရှည်တည်ဆောက်သည်။ ၎င်းသည်ခေါ်ဆိုမှုများကိုရပ်တန့်နိုင်ပြီး လုပ်ဆောင်မှုကို နှိုးဆွပေးခြင်းသာဖြစ်သည်။ ၎င်းကိုတိုးချဲ့ခြင်း သို့မဟုတ်ကုဒ်၊ ပိုင်ဆိုင်မှု၊ လွှဲပြောင်းခြင်းကိုမပြောင်းလဲနိုင်ပါ။ခေါ်ဆိုချက်များနှင့်ညီမျှသောလုပ်ဆောင်မှုများကို သတ်မှတ်မှု အမြင့်မှ စ၍ သက်တမ်းကုန်ဆုံးချိန်အထိ ပိတ်ပင်ထားသည်။ Expiry သည် အလိုအလျောက် အကောင်အထည်ဖော်မှုကို ပြန်လည်ပြုပြင်ပေးသည်၊ ဒါပေမဲ့ ထိန်းသိမ်းထားခြင်းကို ဖျက်ပစ်ခြင်းမဟုတ်ပါ။ အတည်ပြုသော `CompleteEmergencyHoldRetrospective` လုပ်ဆောင်ချက်သည် နောက်ပိုင်းတွင် တိကျတဲ့ ထိန်းချုပ်ထားမှုကို IDs ချည်နှောင်ပြီး မှတ်တမ်းရှင်းလင်းရန်မတိုင်မီ သုညမဟုတ်သည့် ရှာဖွေရာ အမြစ်ကို ပေါင်းစပ်မှုရှိရမည်။ ထိုနောက်ပြန်ကြည့်ခြင်း ပြီးဆုံးသည်အထိ နောက်ထပ်ထိန်းချုပ်မှုကို မချမှတ်နိုင်ပါ။

App API ကို activated လုပ်ထားပါက `GET /v1/gov/contracts/{contract_address}` ဖြင့် မှတ်တမ်းတင်ထားသောအခြေအနေကို ဖတ်ပါ။ ၎င်း၏ `found` ကွင်းသည် သက်တမ်းပတ်လည်မှတ်တမ်းတစ်ခုရှိသည်ဟုဆိုလိုပြီးလိပ်စာတွင်လက်ရှိလုပ်ဆောင်နေသည့်ကုဒ်မရှိဟုဆိုသည်။

## လုပ်ငန်းဆိုင်ရာ လမ်းညွှန်ချက်များ {#operational-guidance}

- စာချုပ်များကို သတ်မှတ်ထားပါ။ စာချုပ်အပြုအမူသည် ဒေသတွင်း နံရံနာရီအချိန်၊ အိမ်ရှင်ဖိုင်စနစ်အခြေအနေ၊ ကွန်ရက်ခေါ်ဆိုမှုများ သို့မဟုတ် အခြား peer-local input များအပေါ် မူတည်ခြင်းမရှိရပေ။
- အသုံးဝင်ဝန်ဆောင်မှုများကို ညှိထားပါ။ ဘိုင်တကုဒ်ကြီးသည် ငွေချေးမှု အရွယ်အစားကို မြှင့်တင်ပေးပြီး ဘလော့ကာ ပျံ့နှံ့မှု ကုန်ကျစရိတ်ကို မြှင့်တင်ပေးသည်။
- ရိုးရှင်းတဲ့ Ledger အပြောင်းအလဲတွေအတွက် ရိုက်နှိပ်ထားတဲ့ ညွှန်ကြားချက်တွေကို ကြိုက်တယ်။ ဒါတွေကို စစ်ဆေးဖို့ ပိုလွယ်ပြီး အကောင်အထည်ဖော်ဖို့ စျေးသက်သာပါတယ်။
- စာချုပ်တိုးတက်မှုနဲ့ မှတ်ပုံတင် ခွင့်ပြုချက်တွေကို အရဲစွန့်မှု မြင့်မားတဲ့ လုပ်ငန်း ထိန်းချုပ်မှုတွေအဖြစ် သတ်မှတ်ပေးပါ။
