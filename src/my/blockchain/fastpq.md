# FastPQ {#fastpq}

FastPQ သည် ရွေးချယ်ထားသော လုပ်ဆောင်မှု သက်ရောက်မှုများအတွက် Iroha ၏ STARK သက်သေလမ်းကြောင်း ဖြစ်သည်။ ၎င်းသည် ပုံမှန် ငွေပေးချေမှု လုပ်ဆောင်ခြင်း သို့မဟုတ် သဘောတူညီမှုစနစ်ကို အစားမထိုးပါ။ ငွေပေးချေမှုများသည် ပုံမှန်အတိုင်း ISI၊ IVM နှင့် Sumeragi မှတစ်ဆင့် ဆက်လက် လုပ်ဆောင်သည်။ FastPQ သည် ဘလော့ခ် လုပ်ဆောင်မှုက မှတ်တမ်းတင်ထားသော မူလရင်းမြစ် မှတ်တမ်းကို အခြေခံ၍ ပံ့ပိုးထားသော သက်ရောက်မှုများကို နောက်ပိုင်းတွင် သက်သေပြသည်။

လက်ရှိ host ပေါင်းစည်းမှုတွင် အဓိကလမ်းကြောင်း နှစ်ခုရှိသည်:

- အပြီးသတ်ထားသော ဘလော့ခ်များ၏ ကိန်းဂဏန်း ပိုင်ဆိုင်မှု သက်ရောက်မှုများ၊ ၎င်းတို့ကို နိုဒ်၏ သက်သေပြသူ lane က သက်သေပြသည်
- `fastpq_binding` တွင် FastPQ ချိတ်ဆက်မှု ပါဝင်သော SORA Nexus AXT သက်သေ envelope များ

## သက်သေခံလမ်းကို လွှဲပြောင်းခြင်း {#transfer-witness-path}

ပွင့်လင်းမြင်သာတဲ့ ကိန်းဂဏန်းလွှဲပြောင်းမှုတွေဟာ ညွှန်ကြားချက်က ဟန်ချက်ညီမှုကို ပြောင်းလဲတဲ့အခါ တည်ဆောက်ထားတဲ့ လွှဲပြောင်းရေး စာသားကို ဖန်တီးပါတယ်။ စာသားလွှဲပြောင်းမှုက မှတ်တမ်းတင်တယ်။

- အရင်းအမြစ်စာရင်း၊ ရည်ရွယ်ချက်စာရင်း၊ ပိုင်ဆိုင်မှု သတ်မှတ်ချက်နှင့် ပမာဏ
- လွှဲပြောင်းခြင်းမတိုင်မီနှင့် နောက်ပိုင်းတွင် ပေးပို့သူနှင့် လက်ခံသူ၏ ငွေကြေးညီမျှမှု
- အစုလိုက်အပြုံလိုက် cryptographic hash အဖြစ် အသုံးပြုသော transaction entry point cryptographic Hash ကို
- ခွင့်ပြုချက်ထုတ်လွှင့်သူစာရင်းမှ ရယူထားသော အဓိက cryptographic digest တန်ဖိုး
- Single-delta transcripts တွေအတွက် Poseidon cryptographic digest value တစ်ခု
- ပေးပို့သူနှင့် လက်ခံသူ၏ လက်ကျန်များအတွက် ကျဲပါးသော Merkle သစ်ပင် ပြင်ဆင်မှု သက်သေဒေတာများ

Batch transfer တွေမှာ delta အမျိုးမျိုးပါတဲ့ transcript တစ်ခုကို သုံးပါတယ်။ ဒီကိစ္စထဲမှာ single-delta Poseidon cryptographic digest value က မရှိပါဘူး။

ဘလော့ခ် လုပ်ဆောင်မှုသည် transcript များကို ၎င်းတို့ကို ထုတ်ပေးခဲ့သော လုပ်ဆောင်မှု ခေါ်ဆိုချက်အလိုက် အုပ်စုဖွဲ့ပြီး ဘလော့ခ်၏ FastPQ မူလရင်းမြစ် မှတ်တမ်းနှင့်အတူ သိမ်းဆည်းထားသည်။ AXT လွှဲပြောင်းမှု ဖော်ပြချက်တစ်ခုတွင် လွှဲပြောင်းမှု delta တစ်ခုစီသည် အကူးအပြောင်း အတန်း နှစ်တန်း ဖြစ်လာသည်:

| အတန်း | ကီး | ယခင်တန်ဖိုး | နောက်တန်ဖိုး |
| --------------- | --------------------------------------------------------------------- | ----------------------- | ---------------------- |
| ပေးပို့သူထံမှ ငွေနုတ်ခြင်း | ပိုင်ဆိုင်မှု သတ်မှတ်ချက်နှင့် မူလအကောင့်အတွက် `FastpqBalanceKeyV1` | မတိုင်မီ ပေးပို့သူ လက်ကျန် | ပြီးနောက် ပေးပို့သူ လက်ကျန် |
| လက်ခံသူထံ ငွေသွင်းခြင်း | ပိုင်ဆိုင်မှု သတ်မှတ်ချက်နှင့် ဦးတည်ရာအကောင့်အတွက် `FastpqBalanceKeyV1` | မတိုင်မီ လက်ခံသူ လက်ကျန် | ပြီးနောက် လက်ခံသူ လက်ကျန် |

ကီးတစ်ခုစီသည် `FastpqBalanceKeyV1` ၏ စံ Norito ဘောင် ဖြစ်ပြီး ၎င်းကို `transfer_balance_key` က အမျိုးအစားသတ်မှတ်ထားသော ပိုင်ဆိုင်မှု သတ်မှတ်ချက်နှင့် ဒိုမိန်းမပါသော အကောင့်မှ တည်ဆောက်သည်။ အကောင့် အမည်ပွားများနှင့် ပြသမှုပုံစံများကို ကီးတည်ဆောက်ရာတွင် ဘယ်သောအခါမျှ အသုံးမပြုပါ။

## လုပ်ဆောင်မှု သက်ရောက်မှုများ {#execution-effects}

သက်သေပြသူ lane သည် ပြည့်စုံသော လုပ်ဆောင်မှု-သက်ရောက်မှု ဖော်ပြချက်များကို သက်သေပြသည်။ ဖော်ပြချက်တစ်ခုစီသည် လုပ်ဆောင်မှု ထည့်သွင်းချက်တစ်ခု၏ ပမာဏဆိုင်ရာ သက်ရောက်မှု အားလုံးကို လုပ်ဆောင်မှု အစီအစဉ်အတိုင်း လွှမ်းခြုံသည်:

| သက်ရောက်မှု | ပြင်ဆင်လိုက်သော တန်ဖိုးများ | စည်းမျဉ်း |
| -------- | ------------------------------ | ------------------------------------------------------------------- |
| လွှဲပြောင်းခြင်း | မူလနှင့် ဦးတည်ရာ လက်ကျန် | ပမာဏသည် ပိုင်ဆိုင်မှုတစ်ခုတည်း၏ လက်ကျန်နှစ်ခုကြားတွင် ရွှေ့ပြောင်းသည် |
| ထုတ်ဝေခြင်း | လက်ကျန်နှင့် စုစုပေါင်းထုတ်ဝေမှု | နှစ်ခုစလုံး သုညမဟုတ်သော တူညီသည့် ပမာဏဖြင့် တိုးသည် |
| မီးရှို့ခြင်း | လက်ကျန်နှင့် စုစုပေါင်းထုတ်ဝေမှု | နှစ်ခုစလုံး တူညီသည့် ပမာဏဖြင့် လျော့သည် |
| ရုပ်သိမ်းခြင်း | စုစုပေါင်းထုတ်ဝေမှုနှင့် သက်တမ်းစက်ဝန်း | စုစုပေါင်းထုတ်ဝေမှု သုညအဖြစ် ဆက်ရှိပြီး ပိုင်ဆိုင်မှု၏ တည်ရှိမှုသည် တစ်မှ သုညသို့ ပြောင်းသည် |

စုစုပေါင်းထုတ်ဝေမှုသည် မည်သည့်လက်ကျန်ထက်မျှ ဘယ်တော့မှ မလျော့ပါ။ ကီးတစ်ခုစီသည် `iroha:fastpq:execution-quantity-key:v1` ဒိုမိန်း၊ NUL ဘိုက်တစ်ခုနှင့် `FastpqExecutionQuantityKeyV1` လက်ကျန်၊ စုစုပေါင်းထုတ်ဝေမှု သို့မဟုတ် သက်တမ်းစက်ဝန်း ကီး၏ Norito ကုဒ်သွင်းချက်တို့ ပေါင်းစပ်ထားခြင်း ဖြစ်သည်။ အခန်းကဏ္ဍ ပေးအပ်ခြင်း၊ အခန်းကဏ္ဍ ပြန်ရုပ်သိမ်းခြင်းနှင့် အခြားလုပ်ဆောင်ချက်များကို သက်သေမပြပါ။

လုပ်ဆောင်မှု-သက်ရောက်မှုနှင့် AXT လွှဲပြောင်းမှု ဖော်ပြချက်များရှိ တန်ဖိုးများသည် ပိုင်ဆိုင်မှု၏ ဒသမစကေးဖြင့် တိကျသော အနုတ်မဟုတ်သည့် ကိန်းပြည့်ယူနစ်များ (`FastpqQuantityUnits`) ဖြစ်သောကြောင့် `u64` ဖြင့် ကန့်သတ်ခြင်း မရှိပါ။ ဖော်ပြချက် တည်ဆောက်မှုသည် စကေးမကိုက်ညီမှု၊ အနုတ်ကွာခြားချက်နှင့် ဂဏန်းသင်္ချာ သို့မဟုတ် အစီအစဉ်ဆိုင်ရာ မကိုက်ညီမှု မည်သည့်အရာကိုမဆို ငြင်းပယ်သည်။ ၎င်းသည် အများမြင်တန်ဖိုးကို ဘယ်တော့မှ ပြုပြင်မပေးပါ။

## ပြည်သူ့ဝင်ငွေများ {#public-inputs}

FastPQ ဖော်ပြချက်တိုင်းတွင် သက်သေကို ဘလော့ခ်နှင့် လုပ်ဆောင်မှု နောက်ခံအခြေအနေတို့နှင့် ချိတ်ဆက်ပေးသော အများမြင် အဝင်ဒေတာများ ပါဝင်သည်:

|ထည့်သွင်းချက်|အဓိပ္ပါယ်|
| ------------- | ------------------------------------------------------------------------------------ |
| `dsid` | ဒေတာနေရာ ခွဲခြားသတ်မှတ်ချက်- ၎င်း၏ `u64` တန်ဖိုးကို little-endian အစီအစဉ်ဖြင့် ရေးပြီး နောက်တွင် သုညဘိုက် ရှစ်ခု ဆက်ထားသည် |
| `slot` | ဘလော့ခ် ဖန်တီးချိန်ကို နာနိုစက္ကန့်ဖြင့် မီလီစက္ကန့် တိကျမှုအထိ ဖော်ပြသည် |
| `old_root` | ဖော်ပြချက် မတိုင်မီ၊ ထိတွေ့ခံရသော ကီးများ၏ ကျဲပါးသော Merkle သစ်ပင် အမြစ် |
| `new_root` | ဖော်ပြချက် ပြီးနောက်၊ ထိတွေ့ခံရသော ကီးများ၏ ကျဲပါးသော Merkle သစ်ပင် အမြစ် |
| `perm_root` | လုပ်ဆောင်နေသည့် အခြေအနေ၏ အခန်းကဏ္ဍ-ခွင့်ပြုချက် ဇယားအပေါ် ကတိပြုတန်ဖိုး |
| `tx_set_hash` | ပို့လွှတ်ပုံစံဖြင့် ကုဒ်သွင်းထားသော ဘလော့ခ်၏ ငွေပေးချေမှုများအပေါ် ဘလော့ခ်အစီအစဉ်အတိုင်း ကတိပြုတန်ဖိုး |

`old_root` နှင့် `new_root` သည် ဖော်ပြချက်က ထိတွေ့သော ကီးများကိုသာ လွှမ်းခြုံသည်။ ၎င်းတို့သည် သိမ်းဆည်းထားသော ကမ္ဘာ့အခြေအနေ၏ အမြစ် မဟုတ်ပါ။

`perm_root` သည် `fastpq:v1:permission-table:blake2b-256` ဒိုမိန်း၊ little-endian `u64` အဖြစ် ဖော်ပြထားသော ထည့်သွင်းချက် အရေအတွက်နှင့် စီထားသော ထည့်သွင်းချက်များအပေါ် တွက်ချက်ထားသည့် Iroha ၏ 32 ဘိုက် `Hash` ဖြစ်သည်။ ထည့်သွင်းချက်တစ်ခုစီတွင် အခန်းကဏ္ဍ ID ၏ ဟက်ရှ်၊ ထိုအခန်းကဏ္ဍ၏ ခွင့်ပြုချက်တစ်ခု၏ ဟက်ရှ်နှင့် ထိုခွင့်ပြုချက်၏ ကာလကို little-endian `u64` အဖြစ် ပါဝင်သည်။ ဗလာဇယားအတွက် ရလဒ်မှာ သုညဘိုက် 32 ခု ဖြစ်သည်။ ဤသည်မှာ အခန်းကဏ္ဍနှင့် ခွင့်ပြုချက်ဆိုင်ရာ နောက်ခံအချက်အလက်သာ ဖြစ်သည်။ ၎င်းသည် အကောင့်အဖွဲ့ဝင်ဖြစ်မှု သို့မဟုတ် ခွင့်ပြုထားမှုကို သက်သေမပြပါ။

`tx_set_hash` သည် `iroha:axt:ordered-transaction-wire-set:v1` ဒိုမိန်း၊ NUL ဘိုက်တစ်ခု၊ ငွေပေးချေမှု အရေအတွက်နှင့် ဘလော့ခ်အစီအစဉ်အတိုင်း ငွေပေးချေမှုတစ်ခုစီအတွက် ၎င်း၏ ပို့လွှတ်ပုံစံ အရှည်နှင့် ပြည့်စုံသော ပို့လွှတ်ပုံစံ ဘိုက်များအပေါ် တွက်ချက်ထားသည့် Iroha ၏ `Hash` ဖြစ်သည်။ အရေအတွက်နှင့် အရှည်များသည် little-endian `u64` တန်ဖိုးများ ဖြစ်သည်။ ငွေပေးချေမှုများကို စီခြင်း သို့မဟုတ် ထပ်နေသည်များကို ဖယ်ရှားခြင်း မပြုဘဲ လက်မှတ်များသည် ဟက်ရှ်၏ မူလထည့်သွင်းဒေတာထဲတွင် ကျန်ရှိနေသည်။

Iroha ၏ `Hash` သည် နောက်ဆုံးဘိုက်၏ အနိမ့်ဆုံးဘစ်ကို တစ်ဟု သတ်မှတ်ထားသော Blake2b-256 ဖြစ်သည်။ ဖော်ပြချက်တွင် အစီအစဉ်ဟက်ရှ်တစ်ခုနှင့် ၎င်း၏ ပြည့်စုံသော စံအတန်းများနှင့် မူလရင်းမြစ် အချက်အလက်များလည်း ပါဝင်သည်။ သက်သေသည် ၎င်းတို့အားလုံးကို ချိတ်ဆက်ထားသည်။

## သက်သေ ပရိုတိုကော {#proof-protocol}

FastPQ ၏ စံ artifact များသည် ဒီဂရီ-၄ တိုးချဲ့မှုပါသော Goldilocks ကွင်းပေါ်ရှိ ဖုံးကွယ်ထားသော DEEP သက်သေများ ဖြစ်သည်။ ၎င်းတို့၏ တိကျသော ဆက်နွယ်ချက်၊ transcript နှင့် query ဂျီဩမေတြီကို ဗားရှင်းပုံသေထားသော [FastPQ DEEP ပရိုတိုကော သတ်မှတ်ချက်](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/specs/fastpq_deep_protocol_contract.md) တွင် သတ်မှတ်ထားသည်။

ခေါ်ဆိုသူများသည် ပုံမှန် သို့မဟုတ် AXT ဖော်ပြချက်နှင့် အရင်းအမြစ် ကန့်သတ်ချက်များကို ရွေးချယ်သည်။ ၎င်းတို့သည် ဆားကစ်များ၊ စစ်ဆေးရေးကီးများ၊ query အရေအတွက် သို့မဟုတ် transcript ၏ အတွင်းပိုင်း အသေးစိတ်များကို မရွေးချယ်ပါ။ ပုံမှန်လမ်းကြောင်းမှာ `offline_compact::prove_quantity_ordinary_artifact` ဖြစ်သည်။ AXT လမ်းကြောင်းမှာ `offline_compact::prove_quantity_axt_artifact` ဖြစ်ပြီး ချိတ်ဆက်ထားသော အစုများအတွက် `prove_axt_bound_batch` က ၎င်းကို အုပ်ထုပ်ခေါ်ယူသည်။ ပွင့်လင်းမြင်သာသော `Prover`၊ `Proof` နှင့် ပြန်လည်လုပ်ဆောင်သည့် `verify` API သည် စမ်းသပ်မှုများနှင့် `dev-tools` တည်ဆောက်မှုများတွင်သာ ရှိသည်။

## သက်သေက စစ်ဆေးသည့်အရာများ {#what-the-proof-checks}

မည်သည့် လျှို့ဝှက်လုပ်ငန်းမဆို မစတင်မီ ထုတ်လုပ်သူသည် အများမြင် ဖော်ပြချက်ကို ပြင်ဆင်သည်။ ၎င်းသည် အကောင့်များ၊ ပမာဏများ၊ တန်ဖိုးများ၊ ဖြစ်ပေါ်မှု အကြိမ်ရေများ၊ တည်ငြိမ်သော ကီးအစီအစဉ်နှင့် ကီးခွဲဝေမှုကို စစ်ဆေးပြီး အများမြင် အချက်အလက်များ အချင်းချင်း မကိုက်ညီသည့် ဖော်ပြချက်ကို ငြင်းပယ်သည်။ ထို့နောက် တံဆိပ်ခတ်ထားသော ဆက်နွယ်ချက်သည် အပိုင်းတစ်ခုစီတွင် သက်ရောက်မှုတစ်ခု သို့မဟုတ် လွှဲပြောင်းမှု ဖြစ်ပေါ်မှုတစ်ခု၏ အဆင့် 32 ဆင့်ပါ ပြည့်စုံသော ကျဲပါးသော Merkle ပြင်ဆင်မှု နှစ်ခုကို သက်သေပြသည်။ မူလကန့်သတ်ချက်များသည် artifact တစ်ခုလျှင် အပိုင်း အများဆုံး နှစ်ခုကိုသာ ခွင့်ပြုသည်။

trace တစ်ခုစီတွင် အတန်း 65,536 တန်း ရှိသည်။ ထုတ်လုပ်သူသည် လျှို့ဝှက်ကော်လံ 301 ခုအတွက် ကတိပြုတန်ဖိုး ထုတ်ပေးပြီး စစ်ဆေးသူသည် အများမြင်ကော်လံ 41 ခုကို သီးခြားလွတ်လပ်စွာ ပြန်လည်တည်ဆောက်သည်။ လတ်ဆတ်သော ခရစ်ပ်တိုဂရပ်ဖစ် အန်ထရိုပီသည် trace ကော်လံများ၊ စားလဒ်နှင့် သီးခြား ကတိပြုထားသော ပေါင်းစပ်ပိုလီနိုမီယယ်ကို ဖုံးကွယ်သည်။ စားလဒ်ရရှိရန် စားခြင်းသည် တိကျရမည်။ ထုတ်လုပ်သူသည် ၎င်း၏ artifact ကို မပြန်ပေးမီ ကိုယ်တိုင် စစ်ဆေးသည်။

အများမြင် ဖော်ပြချက် တန်ဖိုးများကို ဝှက်မထားပါ။ လုပ်ဆောင်ချက်တစ်ခုသည် ပို့လွှတ်ပုံစံတွင် ပါဝင်နေရုံဖြင့် လက်ခံခြင်း မခံရပါ- အထက်တွင် ဖော်ပြထားသော သက်ရောက်မှုများတွင်သာ ဆက်နွယ်ချက်များ ရှိပြီး AXT ဖော်ပြချက်များသည် သက်သေဒေတာဖြင့် ထောက်ခံထားသော လွှဲပြောင်းမှုများကိုသာ လက်ခံသည်။

## Prover စီမံခန့်ခွဲမှုလမ်းကြောင်း {#prover-lane}

Kura ကို `init_mode = "fast"` ဖြင့် မစတင်ပါက `iroha3d` သည် နိုဒ်စတင်ချိန်အတွင်း Torii က တင်သွင်းမှုများကို မလက်ခံမီ FastPQ သက်သေပြသူ နောက်ခံလုပ်ဆောင်သူ တစ်ခုကို စတင်သည်။ ထိုလုပ်ဆောင်သူသည် ၎င်း၏ backend ကို နောက်ခံတွင် စတင်ပြင်ဆင်သောကြောင့် ပြင်ဆင်မှု မအောင်မြင်လျှင်လည်း နိုဒ်စတင်ခြင်းသည် ဆက်လက်ဖြစ်ပေါ်သည်။ ထိုအခါ lane သည် ပိတ်ထားလျက် ကျန်ရှိသည်။

နောက်ခံလုပ်ဆောင်သူသည် နိုဒ်၏ အပြီးသတ်အခြေအနေနှင့် Kura သိုလှောင်မှုကို ပုံမှန် စစ်ဆေးသည်။ အပြီးသတ်ထားသော ဘလော့ခ်တစ်ခုစီအတွက် ၎င်းသည် အထောက်အထားစစ်ဆေးထားသော မူလရင်းမြစ်ကို ရယူသည်။ မူလရင်းမြစ်ကို သိမ်းဆည်းမထားပါက မူရင်း လုပ်ဆောင်မှုကို ပြန်လည်လုပ်ဆောင်၍ ရယူပြီး ဘလော့ခ်၏ ပြည့်စုံသော ဖော်ပြချက်များကို ပုံမှန်လမ်းကြောင်းဖြင့် တစ်ခုပြီးတစ်ခု သက်သေပြသည်။ ပြန်လည်စတင်ပြီးနောက် ၎င်းသည် ပုံသေထားသော လက်မှတ်ထိုး genesis မှ အထောက်အထားစစ်ဆေးထားသော ရှေ့ပိုင်းကို ပြန်လည်တည်ဆောက်သည်။ ၎င်းသည် artifact တစ်ခုစီကို Kura ၏ အရွယ်အစား ကန့်သတ်ထားသော FastPQ သိုလှောင်ရာတွင် သိမ်းဆည်းသည်။ သိမ်းဆည်းထားသော artifact သည် ညွှန်ပြချက်တစ်ခုမျှသာ ဖြစ်သည်- ရှေ့ဆက်မသွားမီ ထုတ်လုပ်သူသည် မူလရင်းမြစ်ကို အထောက်အထားစစ်ဆေးပြီး artifact ကို ထပ်မံစစ်ဆေးသည်။

သက်သေထုတ်လုပ်ခြင်းသည် နိုဒ်အတွင်း၌သာ ဖြစ်သည်။ ၎င်းသည် ငွေပေးချေမှု ဝင်ခွင့် သို့မဟုတ် သဘောတူညီမှုစနစ်၏ အတားအဆီး မဟုတ်ပါ- လုပ်ဆောင်မှု၊ မှတ်တမ်းတင်အတည်ပြုခြင်းနှင့် အပြီးသတ်မှုသည် သက်သေကို မစောင့်ပါ။ ပြန်ကြိုးစားနိုင်သော ချို့ယွင်းမှုတစ်ခုသည် လုပ်ငန်းကို နောက်ထပ်ကြိုးစားမှုအတွက် ချန်ထားပြီး ပရိုဆက်တစ်ခုလျှင် ထုတ်လုပ်သူ တစ်ခုသာ လည်ပတ်သည်။

## စစ်ဆေးခြင်း {#verification}

စစ်ဆေးသူသည် artifact ကို ၎င်း၏ ကိုယ်ပိုင် အထောက်အထားစစ်ဆေးထားသော ဖော်ပြချက်မှ ရယူသည့် မျှော်လင့်ချက်များနှင့် တိုက်စစ်သည်။ စစ်ဆေးခံ artifact မှ ဘယ်တော့မှ မရယူပါ။ စစ်ဆေးမှုသည် အပိုင်းတစ်ခုစီကို ကန့်သတ်ချက်များအောက်တွင် တစ်ကြိမ်သာ ကုဒ်ဖြည်သည်၊ AIR ကို နယ်ပယ်ပြင်ပ အမှတ်တွင် တစ်ကြိမ် အကဲဖြတ်သည်၊ ဖွင့်ထားသော အတန်းတိုင်း၊ စားလဒ် အရွက်တိုင်း၊ FRI အမျှင်တိုင်းနှင့် ပြည့်စုံသော FRI အဆုံးပိုင်းကို ကတိပြုထားသော အမြစ်များနှင့် တိုက်ဆိုင်၍ အထောက်အထားစစ်ဆေးသည်၊ ခေါက်ချိုးစစ်ဆေးမှု အများဆုံး 385 ကြိမ်ကို လုပ်ဆောင်သည်။ ၎င်းသည် လျှို့ဝှက် သက်သေဒေတာ၊ trace သို့မဟုတ် ပြည့်စုံသော ဒီဂရီနိမ့် တိုးချဲ့မှုကို မတည်ဆောက်ပါ။

အောင်မြင်ခြင်းသည် ခေါ်ဆိုသူ၏ မျှော်လင့်ချက်များနှင့် ကိုက်ညီကြောင်းကို အတည်ပြုသည်။ ၎င်းသည် လုပ်ဆောင်မှု လုပ်ပိုင်ခွင့်၊ မူလရင်းမြစ် အပြီးသတ်မှု၊ ပြန်လည်တင်သွင်းမှု ဝင်ခွင့် သို့မဟုတ် AXT သုံးစွဲခွင့် ခွင့်ပြုချက် တစ်ခုမျှ မပေးပါ။

ပုံမှန်လမ်းကြောင်းကလည်း အသုံးပြုသော `offline_compact::VerificationLimits` မှ မူလကန့်သတ်ချက်များ:

|ကန့်သတ်ချက်|အလိုအလျောက်|
| ------------------------------- | ------------: |
| artifact တစ်ခုလျှင် အပိုင်းများ | 2 |
| artifact ၏ ပို့လွှတ်ပုံစံ ဘိုက်များ | 1 MiB |
| အခွဲ သက်သေ ဘောင် | 500,084 ဘိုက် |
| အပိုင်းအားလုံးရှိ ဖော်ပြချက် ဘိုက်များ | 512 KiB |
| အပိုင်းတစ်ခုလျှင် query များ | 77 |
| အပိုင်းအားလုံးရှိ query များ | 154 |

နိုဒ် lane သည် artifact ၏ ပို့လွှတ်ပုံစံ ဘိုက်များကို `zk.fastpq.proof_sidecar_max_bytes` နှင့် Kura ၏ FastPQ အရာဝတ္ထု ကန့်သတ်ချက်ဖြင့် ထပ်မံကန့်သတ်သည်။ ကုဒ်မဖြည်မီ AXT သက်သေ blob တစ်ခုတွင် အများဆုံး 2 MiB နှင့် ၎င်းတွင် ထည့်သွင်းထားသော FastPQ ပါဝင်ဒေတာတွင် အများဆုံး 1 MiB သာ ပါဝင်နိုင်သည်။

## SORA Nexus AXT သက်သေ Envelope များ {#sora-nexus-axt-proof-envelopes}

SORA Nexus AXT သက်သေ envelope များတွင် `AxtFastpqBinding` ကို ထည့်သွင်းနိုင်သည်။ AXT envelope များ၏ ဘလော့ခ်စစ်ဆေးမှု၊ IVM host ၏ AXT envelope စစ်ဆေးမှုများနှင့် `RegisterVerifiedFeeSponsorVaultAllocation` တို့သည် envelope ၏ `fastpq_binding` ကို လိုအပ်ပြီး ၎င်းကို မျှော်မှန်းထားသော ကြေညာချက် (claim) နှင့် တိုက်စစ်ကာ envelope နှင့် ၎င်းတွင် ထည့်သွင်းထားသော သက်သေအပေါ် FastPQ စစ်ဆေးသူကို ခေါ်ဆိုသည်။ ချိတ်ဆက်မှု မရှိခြင်း သို့မဟုတ် စစ်ဆေးမှု မအောင်မြင်ခြင်းသည် လုပ်ဆောင်ချက်ကို ငြင်းပယ်စေသည်။

စစ်ဆေးသူသည် သက်သေဒေတာဖြင့် ထောက်ခံထားသော လွှဲပြောင်းမှု ကြေညာချက်များဖြစ်သည့် `tx_predicate` နှင့် `value_conservation` ကိုသာ လက်ခံသည်။ `authorization` နှင့် `compliance` ကြေညာချက် အမျိုးအစားများသည် လွှဲပြောင်းမှု ဆက်နွယ်ချက် မရှိသော အတွင်းမမြင်ရသည့် သက်ရောက်မှု သယ်ဆောင်သူများ ဖြစ်ပြီး စစ်ဆေးမှုက ၎င်းတို့ကို ငြင်းပယ်သည်။ ဘလော့ခ် အတည်ပြုစစ်ဆေးမှုသည် အဝေးမှ သုံးစွဲမှုများ ပါဝင်သော envelope များကိုလည်း ငြင်းပယ်ပြီး IVM host သည် သီးသန့် `AXT_VERIFY_DS_PROOF` ဝင်ခွင့်ကို ငြင်းပယ်သည်။ အပြီးသတ်ထားသော မူလရင်းမြစ် အမြစ်များ၊ ငွေပေးချေမှု အစုအဝေးနှင့် ထုတ်ပေးသူ၏ ခွင့်ပြုချက်ကို အထောက်အထားစစ်ဆေးနိုင်သည့်အချိန်အထိ နှစ်ခုစလုံးကို အသုံးမပြုနိုင်သေးပါ။

### AXT ချိတ်ဆက်မှု {#axt-binding}

SORA Nexus AXT envelope များအတွက် `AxtFastpqBinding` ကို သက်သေပြခြင်းနှင့် စစ်ဆေးခြင်း မပြုမီ စံပုံစံသို့ ပြောင်းသည်:

- `parameter`၊ `source_dataspace`၊ `source_receipt_id` နှင့် `verified_effect_type` တို့၏ ရှေ့နောက်နေရာလွတ်များကို ဖြုတ်ပြီး ၎င်းတို့ ဗလာ မဖြစ်ရပါ
- `source_tx_commitment`၊ `claim_digest`၊ `witness_commitment` နှင့် `policy_commitment` တို့ကို စာလုံးအသေးသို့ ပြောင်းပြီး ၎င်းတို့သည် 32 ဘိုက်၏ ဆယ့်ခြောက်လီ ကုဒ်သွင်းချက်များ ဖြစ်ရမည်
- `verifier_id` သည် `fastpq` ဖြစ်ရမည်ဖြစ်ပြီး `verifier_version` သည် `v1` ဖြစ်ရမည်
- `claim_type` ၏ ရှေ့နောက်နေရာလွတ်များကို ဖြုတ်ပြီး စာလုံးအသေးသို့ ပြောင်းကာ ၎င်းသည် အထက်ပါ ကြေညာချက် အမျိုးအစား လေးမျိုးအနက် တစ်မျိုးကို ဖော်ပြရမည်
- `target_dsids` သည် ဗလာ မဖြစ်ရဘဲ တင်းကျပ်စွာ ငယ်စဉ်ကြီးလိုက် ဖြစ်ရမည်
- `remote_spend_intent_commitments` သည် တင်းကျပ်စွာ ငယ်စဉ်ကြီးလိုက် ဖြစ်ရမည်ဖြစ်ပြီး ပထမထုတ်ဝေမှု ကန့်သတ်ချက်အတွင်း ရှိရမည်

စစ်ဆေးမှုသည် တိကျသော စံပုံစံကို လိုအပ်သည်။ ၎င်းသည် ခေါ်ဆိုသူကိုယ်စား ချိတ်ဆက်မှုကို ပုံမှန်ပုံစံသို့ ပြောင်းမပေးပါ။

ချိတ်ဆက်မှုသည် ဘလော့ခ် လုပ်ဆောင်မှုက မှတ်တမ်းတင်ပြီးသား အစုတစ်ခုနှင့် တွဲဆက်သည်။ ၎င်းသည် အကူးအပြောင်းများကို မဖန်တီးပါ။ အစုတွင် အခြေအနေ အကူးအပြောင်း အနည်းဆုံး တစ်ခု ပါဝင်ရမည်ဖြစ်ပြီး ချိတ်ဆက်မှု၏ ပါရာမီတာအစု `fastpq-state-transition-stark-v1` ကို ဖော်ပြရမည်။ ၎င်း၏ `entry_hash` မက်တာဒေတာသည် `source_tx_commitment` နှင့် ညီရမည်ဖြစ်ပြီး ၎င်း၏ အများမြင် `dsid` သည် ချိတ်ဆက်မှု၏ `source_dsid` ကို ကုဒ်သွင်းထားရမည်။ လွှဲပြောင်းမှု ကြေညာချက်တွင် လွှဲပြောင်းမှု transcript အနည်းဆုံး တစ်ခု ပါဝင်ရမည်ဖြစ်ပြီး transcript တိုင်း၏ အစုဟက်ရှ်သည် `source_tx_commitment` နှင့် ညီရမည်။

ထို့နောက် ချိတ်ဆက်မှုသည် အစုထဲသို့ သက်သေနှင့် ချည်နှောင်ထားသော မက်တာဒေတာများကို ရေးသွင်းသည်- စံ ချိတ်ဆက်မှု၊ ၎င်း၏ digest လေးခု၊ `source_receipt_id`၊ `target_dsids`၊ `verified_effect_type`၊ ဗလာမဟုတ်သော `corridor`၊ သုညမဟုတ်သော manifest အမြစ်၊ ရွေးချယ်နိုင်သော DA ကတိပြုတန်ဖိုး၊ ရွေးချယ်နိုင်သော သုညမဟုတ်သည့် ကတိပြုထားသော ပမာဏနှင့် သက်တမ်းကုန်ဆုံးမည့် slot တို့ ဖြစ်သည်။ ထို slot တွင် သုညသည် သက်တမ်းကုန်ဆုံးခြင်း မရှိဟု ဆိုလိုသည်။ နောက်ဆုံးတွင် ၎င်းသည် ချိတ်ဆက်မှုနှင့် တံဆိပ်မပါသော အစုအပေါ် တံဆိပ်တစ်ခုကို ထည့်သည်:

$$
\operatorname{seal} =
\operatorname{Hash}(
\texttt{fastpq:axt:batch-seal:v1}\|
E(\operatorname{binding})\|
E(\operatorname{batch})
)
$$

ဤနေရာတွင် $E$ သည် စံ Norito ကုဒ်သွင်းခြင်း ဖြစ်သည်။ ချိတ်ဆက်ပြီးနောက် အစု၊ ချိတ်ဆက်မှု သို့မဟုတ် သက်သေနှင့် ချည်နှောင်ထားသော တန်ဖိုးတစ်ခုခုကို ပြောင်းလဲပါက စစ်ဆေးမှု မအောင်မြင်ပါ။ စစ်ဆေးသူသည် envelope ၏ ဒေတာနေရာ၊ manifest အမြစ်၊ DA ကတိပြုတန်ဖိုး၊ ကတိပြုထားသော ပမာဏနှင့် သက်တမ်းကုန်ဆုံးချိန်ကိုလည်း သက်သေနှင့် ချည်နှောင်ထားသော တန်ဖိုးများနှင့် နှိုင်းယှဉ်သည်။

စစ်ဆေးပြီးသော envelope သည် ၎င်း၏ သက်သေပြထားသော `old_root`၊ `new_root` နှင့် `tx_set_hash` အပြင် ဖော်ပြချက် digest တစ်ခုကို အစီရင်ခံသည်။ digest သည် little-endian `u64` အဖြစ် envelope ၏ ဒေတာနေရာ၊ ၎င်း၏ manifest အမြစ်၊ ရှိပါက DA ကတိပြုတန်ဖိုး၊ ချိတ်ဆက်မှုနှင့် ဖော်ပြချက်တို့ကို လွှမ်းခြုံသည်:

$$
\operatorname{statement\_digest} =
\operatorname{Hash}(
\texttt{fastpq:axt:statement:v1}\|
\operatorname{le64}(\operatorname{dsid})\|
\operatorname{manifest\_root}\|
\operatorname{da\_commitment}\|
E(\operatorname{binding})\|
E(\operatorname{statement})
)
$$

AXT အစု manifest ၏ digest သည် စံ binding ကို Norito ဖြင့် encode လုပ်ထားသည့် ဒေတာပေါ်တွင် တွက်ချက်သော SHA-256 ဖြစ်သည်။

$$
\operatorname{manifest\_digest} =
\operatorname{SHA256}(E(\operatorname{canonical\_binding}))
$$

## Parameters Sets များ {#parameter-sets}

ပထမထုတ်ဝေမှုတွင် ပါရာမီတာအစု တစ်ခုတည်းသာ ရှိပြီး ၎င်းမှာ `fastpq-state-transition-stark-v1` ဖြစ်သည်။ အစုများနှင့် AXT ချိတ်ဆက်မှုများက ၎င်းကို ဖော်ပြပြီး AXT သက်သေပြခြင်းသည် အခြားအမည် မည်သည့်အမည်ကိုမဆို ငြင်းပယ်သည်။ DEEP ပရိုတိုကော သတ်မှတ်ချက်က ထုတ်ဝေထားသော artifact ဂျီဩမေတြီကို ပုံသေသတ်မှတ်သည်:

| အကြောင်းအရာ | တန်ဖိုး |
| -------------------------- | ----------------------------------------------------- |
| ကွင်း | Goldilocks `p = 2^64 - 2^32 + 1`၊ တိုးချဲ့မှု `u^4 - 7` |
| trace အတန်းများ | 65,536 |
| အကဲဖြတ်အတန်းများ | 8,388,608 (တိုးချဲ့မှုအချိုး 128) |
| FRI ခေါက်ချိုးမှု ခွဲဆများ | `[16, 16, 8, 8, 4]` |
| query များ | ကွဲပြားသော နေရာ 77 ခု |
| Grinding | မသုံးပါ |
| ကတိပြုတန်ဖိုးများနှင့် transcript | SHA3-256 နှင့် SHAKE256 |

ထုတ်လုပ်ရေးသုံး အရည်အချင်းသတ်မှတ်ချက် မရရှိနိုင်သေးပါ။ ဤတည်ဆောက်ပုံ၏ မှန်ကန်ခိုင်မာမှု၊ ဝှက်ထားနိုင်မှုနှင့် Fiat-Shamir ဆိုင်ရာ လွတ်လပ်သော ပြန်လည်သုံးသပ်ချက်များ မပြီးသေးဘဲ ဗားရှင်းပုံသေထားသော [ထုတ်လုပ်ရေး အသင့်ဖြစ်မှု မှတ်တမ်း](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/specs/fastpq_production_readiness.md) သည် လုပ်ငန်းပမာဏဖြင့် ချိန်ညှိထားသော လုံခြုံရေး ပြောဆိုချက် တစ်ခုမျှ မပြုလုပ်ပါ။

## ဖွဲ့စည်းပုံ {#configuration}

FastPQ ပြင်ဆင်သတ်မှတ်မှုသည် `zk.fastpq` အောက်တွင် ရှိသည်။

```toml
[zk.fastpq]
execution_mode = "cpu"
poseidon_mode = "cpu"
proof_sidecar_queue_cap = 1024
proof_sidecar_max_retries = 16

# Optional telemetry labels.
device_class = "apple-m4"
chip_family = "m4"
gpu_kind = "integrated"

# Optional Metal backend tuning.
metal_queue_fanout = 3
metal_queue_column_threshold = 24
metal_max_in_flight = 5
metal_threadgroup_width = 128
metal_trace = false
metal_debug_enum = false

[zk.fastpq.producer]
poll_interval_ms = 1000
step_timeout_ms = 30000
max_native_steps = 16
max_source_entries = 65536
max_source_statements = 16384
```

မုဒ်နှစ်ခုစလုံးသည် `cpu` သို့မဟုတ် `gpu` ကိုသာ လက်ခံပြီး မူလတန်ဖိုးမှာ `cpu` ဖြစ်သည်။ ၎င်းတို့အနက် တစ်ခုခုကို `gpu` သို့ သတ်မှတ်ပါက သက်သေ ဟက်ရှ်တွက်ချက်မှုအတွက် စက်ပစ္စည်း လိုအပ်လာသည်- macOS တွင် Metal နှင့် အခြားနေရာများတွင် CUDA ဖြစ်သည်။ GPU ပံ့ပိုးမှုကို ပရိုဂရမ်တည်ဆောက်ရာတွင် ထည့်သွင်းမထားလျှင် သို့မဟုတ် စက်ပစ္စည်းသည် ကြိုတင်စစ်ဆေးမှု မအောင်မြင်လျှင် သက်သေပြသူ lane ကို ပိတ်ထားဆဲ ဖြစ်သည်။ ၎င်းသည် CPU သို့ ဘယ်တော့မှ ပြောင်းမသုံးပါ။ စက်ပစ္စည်းသည် Merkle အရွက်နှင့် အောက်ပိုင်း မိဘ ဟက်ရှ်တွက်ချက်မှုကို အစုလိုက် လုပ်ဆောင်သည်။ transcript၊ အစီအစဉ်ကျ အပေါ်ပိုင်း သစ်ပင်နှင့် trace ဂဏန်းသင်္ချာသည် CPU ပေါ်တွင် ဆက်ရှိသည်။ `poseidon_mode = "gpu"` ဖြင့် သီးခြား ကြိုတင်စစ်ဆေးမှု အောင်မြင်သည့်အခါ နိုဒ်သည် transcript Poseidon digest များကိုလည်း GPU ပေါ်တွင် အစုလိုက် လုပ်ဆောင်သည်။ မဟုတ်ပါက ၎င်းတို့ကို CPU ပေါ်တွင် တွက်ချက်သည်။

`proof_sidecar_max_bytes` သည် နိုဒ်က သိမ်းဆည်းပြီး စစ်ဆေးသည့် ကုဒ်သွင်းထားသော artifact ကို ကန့်သတ်ပြီး ၎င်း၏ မူလတန်ဖိုးမှာ သက်သေပြသူ၏ အများဆုံး သက်သေဘောင် အရွယ်အစား ဖြစ်သည်။ `producer` ဇယားသည် သက်သေပြရန် ကြိုးပမ်းမှုတစ်ခုစီကို ကန့်သတ်သည်- ၎င်း၏ စစ်ဆေးကြားကာလ၊ အချိန်ဘတ်ဂျက်၊ မူရင်း ပြန်လည်လုပ်ဆောင်မှု အဆင့်များ (1 မှ 64 အထိ) နှင့် မှတ်ဉာဏ်ခွဲဝေမှု မပြုမီ လက်ခံသော မူလရင်းမြစ် ထည့်သွင်းချက်များနှင့် ဖော်ပြချက်များ ဖြစ်သည်။ `metal_queue_fanout` သည် 1 မှ 4 အထိ လက်ခံသည်။

မုဒ်နှင့် တယ်လီမီတာ အညွှန်း ဆက်တင်များကို `iroha3d` မှလည်း အစားထိုးသတ်မှတ်နိုင်သည်:

```shell
iroha3d --fastpq-execution-mode gpu
iroha3d --fastpq-poseidon-mode cpu
iroha3d --fastpq-device-class apple-m4
iroha3d --fastpq-chip-family m4
iroha3d --fastpq-gpu-kind integrated
```

`iroha3d` သည် ပြင်ဆင်သတ်မှတ်မှုဖိုင်ကို ဖတ်သည့်အခါ ပတ်ဝန်းကျင် ကိန်းရှင်များကို လျစ်လျူရှုသောကြောင့် ဤတန်ဖိုးများကို TOML တွင် သို့မဟုတ် အထက်ပါ ရွေးချယ်စရာများဖြင့် သတ်မှတ်ပါ။

## မက်ထရစ်များ {#metrics}

တယ်လီမီတာကို ဖွင့်ထားသည့်အခါ FastPQ သည် backend ရွေးချယ်မှု၊ သက်သေ သိမ်းဆည်းမှုနှင့် Metal လုပ်ဆောင်ချိန် ပတ်ဝန်းကျင်၏ အပြုအမူအတွက် မက်ထရစ်များကို ထုတ်ပေးသည်:

|မက်ထရစ် |အဓိပ္ပါယ်|
| ----------------------------------- | --------------------------------------------------------------------------- |
| `fastpq_execution_mode_total` | backend နှင့် စက်အညွှန်းအလိုက် တောင်းဆိုထားသည့် လုပ်ဆောင်မှု mode နှင့် အမှန်တကယ်ရွေးချယ်ထားသည့် mode |
| `fastpq_poseidon_pipeline_total` | တောင်းဆိုထားသည့် Poseidon လုပ်ငန်းစဉ် လမ်းကြောင်းနှင့် အမှန်တကယ်ရွေးချယ်ထားသည့် လမ်းကြောင်း |
| `fastpq_gpu_disable_total` | အရှိန်မြှင့်စက်၊ အကြောင်းရင်းနှင့် စက်အညွှန်းများအလိုက် GPU အရှိန်မြှင့်စက် ပိတ်သိမ်းမှု ဖြစ်ရပ်များ |
| `fastpq_gpu_parity_failure_total` | အရှိန်မြှင့်စက်၊ အကြောင်းရင်းနှင့် စက်အညွှန်းများအလိုက် နမူနာယူစစ်ဆေးထားသော GPU ရလဒ်ကိုက်ညီမှု ချို့ယွင်းချက်များ |
| `fastpq_proof_sidecar_queue_depth` | တန်းစီထားသော FastPQ သက်သေ တွဲဖက်ဖိုင် ပူးတွဲချက်များ |
| `fastpq_proof_sidecar_events_total` | ဖြစ်ရပ်အလိုက် သက်သေ တွဲဖက်ဖိုင် သိမ်းဆည်းမှု ဖြစ်ရပ်များ |
|`fastpq_metal_queue_depth` |သတ္တုတန်းကန့်သတ်ချက်၊ အမြင့်ဆုံး လေယာဉ်ခရီးစဉ်အရေအတွက်၊ ပို့ဆောင်မှုအရေအတွက်နဲ့ နမူနာယူခြင်း ပြတင်းပေါက် |
|`fastpq_metal_queue_ratio` |သံမဏိလိုင်း အလုပ်ရှုပ်ပြီး အပြန်အလှန် ကွဲပြားမှုနှုန်းများ |
|`fastpq_zero_fill_duration_ms` |Metal Run များအတွက် Host သုညဖြည့်ခြင်းသက်တမ်း |
|`fastpq_zero_fill_bandwidth_gbps` |Derived zero-fill bandwidth ကို |

မုဒ်၊ GPU၊ Metal တန်းစီနှင့် သုညဖြည့် မက်ထရစ်များသည် `extended` သို့မဟုတ် `full` တယ်လီမီတာ ပရိုဖိုင် လိုအပ်ပြီး Kura ကို `init_mode = "fast"` ဖြင့် စတင်သည့်အခါ ထုတ်ပေးခြင်း မရှိပါ။ Metal တန်းစီနှင့် သုညဖြည့် မက်ထရစ်များသည် macOS ပေါ်ရှိ `fastpq-gpu` တည်ဆောက်မှုကိုလည်း လိုအပ်သည်။

ယေဘုယျ စွမ်းဆောင်ရည်ခွဲခြားမှုအတွက် [စွမ်းဆောင်ရည်နှင့် မက်ထရစ်များ](/my/guide/advanced/metrics.md) တွင်စာရင်းသွင်းထားသော သဘောတူညီချက်နှင့် တန်းစီအချက်ပြများနှင့်အတူ သုံးပါ။
