# သဘောတူညီချက် {#consensus}

ငွေပေးချေမှုသည် ရှေ့တန်းသို့ ဝင်ပါ Sumeragi အခန်းတစ်ဝိုက်မှာ သူတို့ကို အဆိုပြုတယ်။
အတည်ပြုသူတွေဟာ အဆိုကို လွတ်လပ်စွာ အတည်ပြုပြီး အကောင်အထည်ဖော်ပြီး လက်မှတ်ထိုးတာပါ။
ဘလော့က လိုအပ်တဲ့
validator quorum က ဒီရလဒ်ကို သဘောတူပြီး ကိုက်ညီတဲ့ အသုံးဝင် ဝန်ဆောင်မှု ရှိတယ်။

အားလုံး Iroha 3 ကွန်ရက်တွေက ဒေတာရရှိနိုင်မှုနဲ့ ယုံကြည်မှုရှိတဲ့ ထုတ်လွှင့်လမ်းကြောင်းတွေကို သုံးတယ်။
ဒါတွေဟာ သဘောတူညီမှု လိုအပ်ချက်တွေပါ၊ ရွေးချယ်စရာ တပ်ဆင်ရေး လက္ခဏာတွေ မဟုတ်ဘူး။

## Sumeragi {#sumeragi}

Sumeragi ရှိသည် Iroha ဗစ်ဇာနစ္စ အမှားကို သည်းခံတဲ့ သဘောတူညီချက် အင်ဂျင်ပါ။
အတန်းထဲက ငွေလဲလှယ်မှု, validator peers ကိုတူညီချက်
blocks ကိုပြီးဆုံးဖြတ်ပြီးနောက်သာ blocks ကိုအပြည့်အဝ validators များရှိ
အလားတူ ရလဒ်ကို ပြန်လည်ထုတ်ပြန်ပြီး အမိန့်ချမှတ်ချက် လက်မှတ်ထိုးခဲ့တယ်။

### အဆိုပြုချက်နှင့် အမိန့်ချမှတ်ခြင်းလမ်းကြောင်း {#proposal-and-commit-path}

Sumeragi တချိန်တည်းမှာ တစ်ဘလော့က အမြင့်တစ်ခုနဲ့ ရှေ့ကို ဦးတည်တယ်။ အမြင့်တိုင်းမှာ
လက်ရှိအမြင်အတွက် အဆိုပြုသူအဖြစ် validator တစ်ခုက လုပ်ဆောင်တယ်။ အဆိုပြုသူက drains
ထိပ်တန်းကနေ ဝင်ရောက်ခွင့်ရှိတဲ့ ငွေကြေးပူးပေါင်းမှုတွေ၊ ကိုယ်စားလှယ်လောင်း ဘလော့ကို ဆောက်လုပ်ပြီး ကြေညာတယ်။
Active validator set ကို အဆိုပြုချက်။

အလားတူပဲ Sumeragi ခွင့်ပြုချက်နှင့် အမည်ပေးထားသော နှစ်ခုစလုံးတွင် pipeline ကို အသုံးပြုသည်။
NPoS (Proof of Stake) တပ်ဆင်မှု

1. validator က queued transactions တွေကို တားဆီးဖို့ အကြံပြုတယ်။
2. အတည်ပြုသူများက အဆိုပြုချက်ကို အတည်ပြုခြင်းအားဖြင့်
   ကမ္ဘာတစ်လွှားက အလားတူနိုင်ငံပါ။
3. Validator တွေက လက်ရှိအမြင့်အတွက် မဲတွေနဲ့ quorum certificates တွေကို လဲလှယ်ကြတယ်။
   ပြီးတော့ ရှုခင်းပါ။
4. commit quorum ကို ရယူပြီးတာနဲ့ peers တွေက block လုပ်ပြီး update လုပ်ကြတယ်
   သူတို့ရဲ့ ကမ္ဘာ့အခြေအနေပါ။

အတည်ပြုသူတွေဟာ ဒေသတွင်းမှာ ပြန်လည်ထုတ်လုပ်နိုင်မယ့် အချက်အလက်တွေကိုသာ လက်မှတ်ထိုးကြတယ်။ မဲမပေးခင်
အဆိုပြုချက်ဟာ မျှော်လင့်ထားတဲ့ ကွင်းဆက်၊ အမြင့်နဲ့ ဆက်စပ်နေတာကို အတည်ပြုသူက စစ်ဆေးတယ်။
မြင်ရသည်; ငွေပေးချေမှု လက်မှတ်များနှင့် ကန့်သတ်ချက်များ သက်ဝင်သည်; လမ်းကြောင်းလမ်းညွှန်ခြင်းနှင့်
executor validation က deterministic ဖြစ်ပြီး အသုံးဝင်ဝန်ပိုးကို အကောင်အထည်ဖော်ခြင်းက
Local result ကွဲပြားတယ်ဆိုရင် validator က
အဆိုပြုချက်ကို မဲပေးမယ့်အစား ပယ်ချလိုက်ပါတယ်။

မဲတွေက လက်မှတ်ထိုးထားတဲ့ သဘောတူညီချက် စာတိုလေးတွေပါ၊ အဆိုပြုထားတဲ့ ဘလော့ကို ရည်ညွှန်းတယ်။
အထက်၊ မြင်ကွင်းနဲ့ validator လက္ခဏာကို စုစည်းပါတယ်။
အတည်ပြုချက်စာရင်း သို့မဟုတ် ကော်မတီစာရင်းကို မဲပေးခြင်း။
လုံလောက်တဲ့ validators တွေက တူညီတဲ့ ရလဒ်ကို တူညီတဲ့အတွက် စောင့်ကြည့်ခဲ့တယ်ဆိုတာရဲ့ ရေရှည်တည်တံ့တဲ့ အထောက်အထားပါ။
အတားအဆီးပါ။

### ကော်မတီ၊ စုဆောင်းသူများနှင့် လေ့လာသူများ {#quorum-collectors-and-observers}

မဲပေးသူ အတည်ပြုသူ အရေအတွက် `n` ဘိုင်ဇင်တိန် အမှား ဘတ်ဂျက်ကို သတ်မှတ်တယ်။
အနည်းဆုံး validator လေးခုရှိတဲ့ ကွန်ရက်များအတွက် ဘတ်ဂျက်က `f = floor((n - 1) / 3)`
ကော်မတီချမှတ်ချက်က `2f + 1`. အတည်ပြုသူ ၁ ဦးမှ ၃ ဦးအထိ၊ အတည်ပြုသူများအားလုံး
ကတိပေးချက်အတွက် လိုအပ်ပြီး ဒါက ဖွံ့ဖြိုးတိုးတက်ဖို့ အသုံးဝင်ပေမဲ့ လက်တွေ့မကျဘူး။
အွန်လိုင်းက ချွတ်ယွင်းခြင်း။

Collectors တွေဟာ fanout Optimization ပါ။ validator တစ်ခုချင်းစီကို ပေးပို့မယ့်အစား
အခြားအတည်ပြုသူတိုင်းကို မဲပေးပါ။ Sumeragi အစုလိုက်အပြုံလိုက် စုဆောင်းသူတစ်ဦး (သို့) ပိုမိုရွေးချယ်နိုင်သည်
အစုလိုက်အပြုံလိုက် မဲဆန္ဒရှင်တွေက မဲတွေ စုစည်း၊ ကွမ်ရမ် တိုးတက်မှုကို ထုတ်ပြန်ပြီး
မဲဆန္ဒရှင်များ၏ ပမာဏ
ဖြတ်သန်း `GET /v1/sumeragi/collectors`; ကော်မတီ CLI ဒါက
`ops sumeragi telemetry` snapshot က လက်ရှိ စုဆောင်းသူအရေအတွက်ကို ဖော်ပြပါတယ်။

လေ့လာသူ အဖော်တွေဟာ ကတိပြုထားတဲ့ ဘလော့တွေကို synchronize လုပ်နိုင်ပေမဲ့ သူတို့ အဆိုပြုတာမဟုတ်ဘူး။
မဲဆန္ဒရှင်များအတွက် မဲစုဆောင်းရန် သို့မဟုတ် ကော်မတီကော်မတီကို ရေတွက်ရန်။
deployment အတွက် ဒေသတွင်း query capacity, indexing, monitoring သို့မဟုတ် regional block လိုအပ်ချက်များ
မဲစစ်ဆေးသူ အရေအတွက်ကို တိုးမြှင့်မပေးဘဲ ပြန်လည်ဖန်တီးခြင်း။

### ပြင်ဆင်ချက်များနှင့် ပြန်လည်ထူထောင်မှုများကို ကြည့်ရှုရန် {#view-changes-and-recovery}

ရှုခင်းတစ်ခုက Sumeragi အထူး အဆိုပြုတစ်ယောက်နဲ့ တစ်ချိန်တည်းမှာ အမြင့်ကို အဆုံးသတ်ဖို့ကြိုးပမ်းမှု
အဆိုပြုချက်၊ အသုံးဝင်မှုတင်သွင်းမှု၊ မဲပေးခြင်း (သို့) တိုးတက်မှုလုပ်ဆောင်မှု စတိုင်များရှိလျှင်
နှလုံးခုန်နှုန်းသတ်မှတ်ကိရိယာက အမြင့်ကို နောက်တစ်ကြိမ်မြင်ဖို့ ရွှေ့နိုင်ပါတယ်
ကတိပြုထားတဲ့ ဘလော့က validators တွေက ကတိမချထားတာကို အဆုံးသတ်ဖို့ကြိုးစားပုံကို ပြောင်းလဲစေပါတယ်။
အမြင့်ဆုံးသိတဲ့ ကွမ်ရမ်ကို ဆောင်ရွက်ခြင်း (သို့) သက်သေပြမှုပြုလုပ်ခြင်း
ပဋိပက္ခဖြစ်နေတဲ့ ဘလော့တွေကို အဆုံးသတ်မလုပ်ပါနဲ့။

အသုံးဝင် ဝန်ဆောင်မှု ပြန်လည်ထူထောင်ရေးဟာ နောက်ဆုံး ဆုံးဖြတ်ချက်နဲ့ သီးခြားပါ။
အစုလိုက်အပြုံလိုက် အသုံးဝင်မှု မပြည့်မီခင်မှာ ကော်မတီ (သို့) ကော်မိတ်သက်သေခံစာကို ပေးပါ။
ဖြစ်ရပ်တစ်ခုမှာ peer က ယုံကြည်မှုရှိတဲ့ ထုတ်လွှင့်မှုကို သုံးတယ် (RBC) သို့မဟုတ် ပြန်လည်ထူထောင်ရေးအတွက် sync ကိုပိတ်ပါ။
payload ကို ကြော်ငြာထားတဲ့ hash တွေနဲ့ စစ်ဆေးပြီး ဒီနောက်ပဲ
ကမ္ဘာ့နိုင်ငံကို ပိတ်ဆို့ပြီး Kura.

### သဘောတူညီမှုပုံစံများ {#consensus-modes}

ရွေးချယ်ထားသော mode က validator set ကို ဘယ်လိုဖွဲ့စည်းပြီး လုပ်ဆောင်ပုံကို ထိန်းချုပ်ပါတယ်။
Genesis ထဲမှာ ကြေညာထားတာက [`consensus_mode`](/my/reference/genesis.md)
အတန်းတူပုံစံဖြင့် `sumeragi.consensus_mode`. ဒါကို
ကွန်ရက်တစ်ခုလုံးအခြေအနေ: validator တွေဟာ လက်မှတ်ထိုးထားတဲ့ genesis တစ်ခုတည်း၊ topology တစ်ခုတည်း လိုအပ်တယ်။
ယုံကြည်မှုရှိပြီး ထိရောက်တဲ့ တန်းတူဒေတာ Sumeragi ပြိုင်ဘက်များ။

အကြောင်းက အဖွဲ့ဝင် ပြောင်းလဲမှုဟာ ကြံစည်တဲ့ အုပ်ချုပ်မှု (သို့) စီမံခန့်ခွဲသူဖြစ်လို့ပါ။
အရေးပါတဲ့ လုပ်ငန်းစည်းမျဉ်းက validator တစ်ခုစီဟာ
မျိုးဆက်ကို တူညီတဲ့ ရှုထောင့်၊ ယုံကြည်ရတဲ့ အဖော်တွေ၊ BLS ပိုင်ဆိုင်မှု အထောက်အထားများ၊
Sumeragi ကွဲပြားတဲ့ topology (သို့) လက်မှတ်ထိုးထားတဲ့ genesis ကိုရှိတဲ့ တစ်ကိုယ်တော် peer
ကွန်ရက်က တာဝန်ယူတာ တားဆီးနိုင်တယ်။

## အများပြည်သူ သဘောတူညီချက် {#multilane-consensus}

Iroha multi-line သဘောတူညီချက်လမ်းကြောင်းကို Nexus လမ်းကြောင်းနှင့်
data space ကို configuration. ၎င်းသည် သီးခြားသဘောတူညီချက် instance ကိုမစတင်ပါ။
လမ်းကြောင်းတိုင်းအတွက်ပါ။ Sumeragi အမိန့်ချမှတ်ထားတဲ့ ဘလော့စီးကြောင်း တစ်ခုကို အဆုံးသတ်နေဆဲပါ။
ငွေလဲလှယ်မှု လမ်းညွှန်ခြင်း၊ အစီအစဉ်ချခြင်း၊ မှတ်ပုံတင်ခြင်းနှင့် သိုလှောင်ခြင်း နည်းလမ်းကို ဖော်ပြပါ။
အဲဒီရေစီးကြောင်းထဲမှာပါ။

Runtime Configuration ကတော့ lane state သုံးခုကို တည်ဆောက်ပါတယ်။

- `lane_catalog`: configured lanes တစ်ခုစီမှာ numeric `LaneId`,
  alias, data space, visibility, storage profile, proof scheme နဲ့
  metadata တွေ။
- `dataspace_catalog`: configured data spaces တွေမှာ တစ်ခုချင်းစီဟာ numeric
  `DataSpaceId` နှင့် Relay Committee အတွက် အသုံးပြုသော fault tolerance value ကို
  အတိုင်းအတာတွေ
- `routing_policy`: Default lane/dataspace pair နှင့် ordered routing
  အကောင့်များ (သို့) ညွှန်ကြားချက်လမ်းကြောင်းများကို လိုက်ဖက်အောင် လုပ်နိုင်သော စည်းမျဉ်းများ။

Transaction တစ်ခုဟာ queue ထဲကို ဝင်လာတဲ့အခါ Lane router က ဒါကို
`RoutingDecision { lane_id, dataspace_id }`. Single-lane mode မှာ ဒါက
အမြဲတမ်း Lane `0` ပြီးတော့ စကြာဝဠာဆိုင်ရာ ဒေတာနေရာပါ။ Nexus mode ကို configured ကို
router က data space-scale စည်းမျဉ်းတွေ သုံးတယ်၊ settlement routing၊ account စည်းမျဉ်းတွေ၊
Routing Rules တွေကို ရှင်းလင်းပြီး နောက်ဆုံးတော့ Default Route ကိုပါ။
ပြီးတော့ ဒေတာနေရာဟာ သူတို့ရဲ့ စာရင်းထဲမှာ ရှိဖို့လိုပြီး လမ်းကြောင်းက
ဖြေရှင်းထားသော ဒေတာနေရာ၊ မဟုတ်ရင် ငွေပေးချေမှုသည် မဖြေရှင်းခင် ပယ်ချခံရသည်။
တန်းစီထားတယ်။

queue က transaction hash နဲ့အတူ ဒီ routing ဆုံးဖြတ်ချက်ကို ထိန်းထားပါတယ်
နောက်ပိုင်းအဆင့်များတွင် ထပ်မံဆုံးဖြတ်ရန် မလိုပါ။ အဆိုပြုချက် တည်ဆောက်မှုနောက်
လမ်းကြောင်း metadata ကို နည်းလမ်းနှစ်မျိုးဖြင့်:

- ဒါက လိုင်းတစ်ခုချင်းစီနဲ့ ငွေလဲလှယ်မှုတွေကို အပြန်အလှန် ချိတ်ဆက်ထားတယ်
  ၎င်းရဲ့ ငွေပေးချေမှုတွေဟာ ပထမတန်းမှာ ရှိခဲ့လို့ပါ။
- တစ်လမ်းစီ ရင်းနှီးမြှုပ်နှံမှု အကောင်အထည်ဖော်ရေး ယူနစ် (TEU) ကန့်သတ်ချက်များ
  လမ်းကြောင်းတစ်ခုရဲ့ ညှိနှိုင်းထားတဲ့ စွမ်းအားထက် ပိုများတဲ့လမ်းကြောင်းတွေကို ရွှေ့ဆိုင်းလိုက်ပြီး အဆက်မပြတ်ထားပါ။
  လိုင်းတစ်ခုအတွက် ပထမဆုံး အလေးချိန်အလွန် ကုန်သွယ်မှုကို လက်ခံနိုင်တာထက်
  အသက်ရှင်နေထိုင်မှုကို ရှောင်ရှားဖို့ပါ။

စိတ်ချရတဲ့ ထုတ်လွှင့်မှုအတွင်းမှာ Sumeragi အဆိုပြုတဲ့ အသုံးဝင် ဝန်ဆောင်မှုကို လမ်းကြောင်းအလိုက် စုစည်းပေးတယ်။
မှတ်တမ်းတင်ထားသော စုစုပေါင်းများတွင် ငွေပေးချေမှုအရေအတွက်၊ ထုတ်လွှင့်ခြင်း
chunks, payload bytes နဲ့ TEU. commit လုပ်ပြီးတဲ့အခါ ဒီပေါင်းတွေဟာ lane ဖြစ်လာတယ်။
ဒေတာနေရာဆိုင်ရာ တာဝန်ယူမှု အရှိန်အဟုန်ကို Sumeragi အခြေအနေ။
ဘလော့က လိုင်နို settlement လက်မှတ်တွေပါဝင်ပြီး ဘလော့ processing ကလည်း လိုင်နိုးကို ဖန်တီးပါတယ်။
ဘလော့ခေါင်းကို ချိတ်ဆက်ပေးသော စာရင်းချေမှုတ်ခြင်းဆိုင်ရာ တာဝန်ယူချက်များနှင့် ဆက်လက်တင်ပြသည့် အပုံးများ၊
ကတိပြုချက်ချမှတ်ချက်၊ ဒေတာရရှိနိုင်မှု ကတိပေးချက် hash, ငွေပေးချေမှု သက်သေခံချက်
လမ်းကြောင်း အသုံးဝင် ဝန်ဆောင်မှု အရွယ်အစားပါ။

## စိတ်ချရတဲ့ ထုတ်လွှင့်မှု (RBC) {#reliable-broadcast-rbc}

စိတ်ချရတဲ့ ထုတ်လွှင့်မှု (RBC) ဖြစ်ပါသည်။ Sumeragi အသုံးဝင် ဝန်ဆောင်မှု ပျံ့နှံ့ရေးနှင့် ပြန်လည်ထူထောင်ရေး
ဒါက validators နဲ့ observers တွေကို သူတို့ဆီက block body ကိုရဖို့ ကူညီပေးတယ်
အဆိုပြုချက် (သို့) အမိန့်ချမှတ်စာချုပ်ကို အထူးသဖြင့် `BlockCreated`
သတင်းစာ၊ ဘလော့ကတ်အလိုက် နှိုင်းယှဉ် update (သို့) တိုက်ရိုက် payload လွှဲပြောင်းမှု နောက်ကျသွားတယ် ဒါမှမဟုတ် ပျောက်သွားတယ်

RBC အသုံးဝင် ဝန်ဆောင်မှုအဆင့်မှာ အလုပ်လုပ်ပါတယ်။ အဆိုပြုသူက RBC အစည်းအဝေး
ဘလော့က အမြင့်၊ ကြည့်ရှုမှုနှင့် အသုံးဝင်ဝန်ဆောင်မှု hash ကိုနှိပ်ပြီး အသုံးဝင် ဝန်ဆောင်မှု chunks ကို
Topology ကို commit လုပ်ပါ။ peers တွေက လက်ခံရရှိမှုကို ခြေရာခံပြီး ပြန်လည်ရှာဖွေထားတဲ့ အသုံးဝင်ပစ္စည်းကို အတည်ပြုတယ်။
ကြော်ငြာထားတဲ့ hash နဲ့ Exchange `READY` နှင့် `DELIVER` အချက်ပြချက်များ
Once enough validators have observed the same payload. session တွေကို ကန့်သတ်ထားပါတယ်
မှ TTL, အစိတ်အပိုင်းများ၊ ရောင်ရမ်းခြင်းများ၊ စောင့်ဆိုင်းထားသော သိုလှောင်မှုများနှင့် တည်ငြိမ်စွာ သိုလှောင်ရန် ကန့်သတ်ချက်များ
ပြန်လည်ထူထောင်ရေး ယာဉ်ကြောဟာ အကန့်အသတ်မဲ့ ကြီးထွားလို့မရဘူး။

RBC ကွဲပြားတဲ့ သဘောတူညီမှု ဆုံးဖြတ်ချက်မဟုတ်ဘူး၊
Certificate - ဘလော့က တစ်ပြိုင်နက်မှာ သက်ဝင်တဲ့ ကတိတစ်ခုရှိတဲ့အခါပဲ အဆုံးသတ်နေတုန်းပါ။
Certificate နဲ့ ကိုက်ညီတဲ့ အသုံးဝင် ဝန်ဆောင်မှုကို ဒေသတွင်းမှာ လုပ်ပေးပါ။ RBC အမိန့်ပေး
ရင်းနှီးမြှုပ်နှံမှုဆိုင်ရာ အထောက်အထားများနှင့် အသုံးဝင် ဝန်ဆောင်မှုများ ပြန်လည်ထူထောင်ခြင်း
အမိန့်ချမှတ်ချက်နှင့် ဒေသတွင်း အသုံးဝင်မှုအပြည့်အဝပါ ၀ င်သည်။
payload ကို peer က payload ကို ပြန်ယူနိုင်တယ် RBC ဒါမှမဟုတ် Block Sync နဲ့
ပြီးရင် ကျင့်ပါ။

လုပ်ငန်းအရတော့ RBC ပျောက်နေတဲ့ အသုံးဝင်မှုအတွက် ရောဂါရှာဖွေဖို့ အသုံးဝင်ပါတယ်။
ဒေတာရရှိနိုင်မှု bottlenecks:

- `iroha --output-format text ops sumeragi telemetry` စုစုပေါင်းပြသသည်
  ရယူနိုင်မှု မဲများ၊ လက်ရှိ စုဆောင်းသူအရေအတွက်နှင့် စောင့်ဆိုင်းနေဆဲ RBC အစည်းအဝေးများ။
- `GET /v1/sumeragi/rbc` နှင့် `GET /v1/sumeragi/rbc/sessions` အသေးစိတ် ဖော်ပြပါ
  စုစုပေါင်းပြီး တက်ကြွတဲ့ အစည်းအဝေး အချက်အလက်များ Torii, အစိတ်အပိုင်း တိုးတက်မှုအပါအဝင်၊
  အသင့်ရှိမှု၊ ပို့ဆောင်မှုအခြေအနေနဲ့ လမ်းကြောင်း (သို့) ဒေတာနေရာနောက်ကျနေမှု။
  [Torii အဆုံးသတ်မှတ်ချက်များ](/my/reference/torii-endpoints.md).
- Prometheus အချက်ပြမှုတွေ `sumeragi_rbc_store_pressure`,
  `sumeragi_rbc_backpressure_deferrals_total`, လမ်းကြောင်းတစ်လျှောက် (သို့)
  ဒေတာနေရာတိုင်း RBC backlog gauges များက net loss ကိုခွဲခြားရန်ကူညီပေးသည်, chunk
  ပြန်လည်ထူထောင်ရေးနှင့် သိုလှောင်ရန် ဖိအားကို ကြည့်ပါ။
  [စွမ်းဆောင်ရည်နှင့် မက်ထရစ်များ](/my/guide/advanced/metrics.md).

Kura သိုလှောင်ရေး ပုံစံအတွက် Derived Lane Configuration ကို အသုံးပြုပါတယ်။
