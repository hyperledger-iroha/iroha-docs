# သဘောတူညီချက် {#consensus}

Sumeragi က သူတို့ကို ဘလော့ကထဲမှာ အဆိုပြုမပေးခင်မှာ ငွေကြေးပူးပေါင်းမှုတွေဟာ တန်းစီဝင်ပါတယ်။ အတည်ပြုသူတွေက အဆိုကို လွတ်လပ်စွာ စစ်ဆေးပြီး အကောင်အထည်ဖော်ကာ သူတို့ ပြန်လည်ဖန်တီးနိုင်တဲ့ နိုင်ငံကူးပြောင်းမှုကိုသာ လက်မှတ်ထိုးတယ်။ ဘလော့က ပြီးဆုံးသွားပြီးနောက် လိုအပ်တဲ့ validator quorum က ဒီရလဒ်ကို သဘောတူပြီး ကိုက်ညီတဲ့ အသုံးဝင်ဝန်ဆောင်မှုရှိပြီးနောက်ပါ။

Iroha 3 ကွန်ရက်အားလုံးမှာ RS16 လက်မှတ်ထိုးထားတဲ့ ဒေတာရရှိမှု နည်းပညာ မန်နီစတာများနှင့် အပိုင်းအစများ၊ ဒါ့အပြင် အသိအမှတ်ပြုတဲ့ ကိုယ်ခန္ဓာ ပြန်လည်ထူထောင်ခြင်းများကို အသုံးပြုပါတယ်။ ဒေတာရရှိမှုဟာ သဘောတူညီချက် လိုအပ်ချက်တစ်ခုဖြစ်ပြီး ရွေးချယ်စရာ ဖြန့်ချိရေး လုပ်ဆောင်ချက်မဟုတ်ပါ။

## Sumeragi {#sumeragi}

Sumeragi ဟာ Iroha ရဲ့ Byzantine-fault-tolerant သဘောတူညီချက် အင်ဂျင်ပါ။ ၎င်းဟာ အတန်းကနေ ငွေကြေးကိုယူပြီး validator ကွန်ရက် လုပ်ဖော်ကိုင်ဖက်တွေ အတူတူသဘောတူတယ်။ အမိန့်ချမှတ်ထားတဲ့ ဘလော့က အဲဒီဘလော့ကို လုံလောက်တဲ့ validators တွေဟာ တူညီတဲ့ ရလဒ်ကို ပြန်ထုတ်ပြီး သဘောတူညီမှု နောက်ဆုံးသတ်မှတ်ချက် လက်မှတ်ထိုးပြီးနောက်ပဲ ပြီးဆုံးစေပါတယ်။

### အဆိုပြုချက်နှင့် သဘောတူညီမှု အပြီးသတ်ခြင်း လမ်းကြောင်း {#proposal-and-commit-path}

Sumeragi သည် blockchain ledger ကို တစ်ကြိမ်မှာ ဘလော့ကွတ်တစ်လုံးမြင့်စွာ ရှေ့သို့ ပြသသည်။ အမြင့်တစ်ခုစီတွင် validator တစ်ခုသည်လက်ရှိအမြင်အတွက် အဆိုပြုသူအဖြစ် လုပ်ဆောင်သည်။ အဆိုပြုသူသည်ထောင့်မှသင့်လျော်သော ငွေပေးချေမှုများကိုဖြုတ်ထုတ်ပြီး ကိုယ်စားလှယ်ဘလော့ကိုတည်ဆောက်ကာ အဆိုပြုချက်ကို တက်ကြွတဲ့ validator set သို့ကြေညာသည်။

Sumeragi software processing workflow တစ်ခုတည်းကို ခွင့်ပြုချက်နှင့် NPoS (Nominated Proof-of-Stake) deployments နှစ်ခုစလုံးတွင် အသုံးပြုသည်။

1. validator က queued transaction တွေကို တားဆီးဖို့ အကြံပြုတယ်။
2. အတည်ပြုသူတွေဟာ အလားတူ ကမ္ဘာ့နိုင်ငံကို ဆန့်ကျင်တဲ့ ငွေပေးချေမှုတွေကို အကောင်အထည်ဖော်ရင်း အဆိုပြုချက်ကို အတည်ပြုတယ်။
3. အတည်ပြုသူတွေဟာ လက်ရှိ အမြင့်နဲ့ ရှုထောင့်အတွက် မဲတွေနဲ့ သဘောတူညီချက် ကော်မတီ အထောက်အထားတွေကို လဲလှယ်တယ်။
4. သဘောတူညီချက် နောက်ဆုံးသတ်မှတ်မှု ကော်orum ကိုရောက်ရှိပြီးတာနဲ့ ကွန်ရက် အဖော်တွေဟာ ဘလော့ကို အဆုံးသတ်ပြီး သူတို့ရဲ့ ကမ္ဘာအခြေအနေကို မွမ်းမံတယ်။

အတည်ပြုသူများက ဒေသတွင်းတွင် ပြန်လည်ဖန်တီးနိုင်သော အချက်အလက်များကိုသာ လက်မှတ်ထိုးကြသည်။ မဲမပေးမီ အဆိုပြုချက်သည် မျှော်မှန်းထားသည့် ကွင်းဆက်၊ အမြင့်နှင့် ရှုထောင့်သို့ သက်ဆိုင်ကြောင်း၊ ငွေလဲလှယ်မှုလက်မှတ်များနှင့် အကန့်အသတ်များသည် ပရိုတိုကိုလ်စည်းမျဉ်းများနှင့် ကိုက်ညီကြောင်း၊ စီမံခန့်ခွဲရေးလမ်းကြောင်း လမ်းညွှန်ခြင်းနှင့် အကောင်အထည်ဖော်သူအား အတည်ပြုခြင်းသည် သတ်မှတ်ချက်ဖြစ်သည်ကို အတည်ပြုသူက စစ်ဆေးသည်။ ဒေသတွင်း ရလဒ်က ကွဲပြားတယ်ဆိုရင် validator က အဆိုကို မဲပေးမယ့်အစား ပယ်ချပါတယ်။

မဲပေးခြင်းသည် လက်မှတ်ရေးထိုးထားသော သဘောတူညီချက် စာတိုငယ်များဖြစ်သည်။ အဆိုပြုထားတဲ့ ဘလော့၊ အမြင့်၊ ရှုထောင့်နှင့် အတည်ပြုသူအမည်ကို ရည်ညွှန်းသည်။ စစ်ဆေးထားသောလက်မှတ်များသည် သဘောတူညီမှု ပြင်ဆင်ခြင်းနှင့် နောက်ဆုံးသတ်မှတ်ချက်များကို ဖွဲ့စည်းခဲ့သည်။ သဘောတူညီချက် နောက်ဆုံးသတ်မှတ်ချက်က တူညီတဲ့ block အတွက် validator များအလုံလောက်က တူညီသောရလဒ်ကိုတွေ့ရှိခဲ့ကြောင်း တည်တံ့တဲ့သက်သေပါ။ validator တစ်ခုချင်းစီက ၎င်းရဲ့ အပြည့်အစုံသော ကော်မတီသို့ မဲပေးရန် ပြင်ဆင်ပြီး အဆုံးသတ်မှုအဆင့်တွင် မဲပေးခြင်း။ မည်သည့် validatorမဆို လိုအပ်သော တူညီသော မဲများကို စုစည်းနိုင်ပြီး ရလဒ်ရရှိသော လက်မှတ်ကို ထုတ်လွှင့်နိုင်သည်။

### Quorum နှင့် လေ့လာသူများ {#quorum-and-observers}

ပထမအကြိမ် ထုတ်ပြန်မှု ပရိုတိုကောမှာ မဲပေးသူ ၄ ဦးမှ ၃၁ ဦးအထိ အတိအကျ `3f + 1` ကော်မတီကိုသာ ခွင့်ပြုထားတယ်။ ဒါကြောင့် သက်ဆိုင်ရာ အရွယ်အစားတွေဟာ ၄၊ ၇၊ ၁၀ စသည်တို့ဖြစ်ပြီး ၃၁ အထိပါ။ `n = 3f + 1` အတွက် Byzantine fault ဘတ်ဂျက်က `f` ဖြစ်ပြီး protocol finalisation quorum က `2f + 1` ဖြစ်တယ်။ blockchain genesis generation နဲ့ startup validation တွေဟာ တခြား committee geometry တွေကို ပယ်ချပါတယ်။

Observer network peers တွေက နောက်ဆုံးသတ်မှတ်ထားတဲ့ blocks ကို synchronize လုပ်နိုင်ပေမဲ့ သဘောတူညီချက် အပြီးသတ်ရေး quorum အတွက် အဆိုပြု၊ မဲမပေးတာ (သို့) မရေတွက်တာပါ။ deployment တစ်ခုအတွက် ဒေသတွင်း query capacity, indexing, monitoring လိုတဲ့အခါ လေ့လာသူတွေကို သုံးပါ။ (သို့) မဲအတည်ပြုသူ အရေအတွက်ကို တိုးမြှင့်ခြင်းမရှိဘဲ ဒေသဆိုင်ရာ ဘလော့က ပေါင်းကူးမှုပါ။

### အပြောင်းအလဲများနှင့် ပြန်လည်ထူထောင်ခြင်းများကို ကြည့်ရှုရန် {#view-changes-and-recovery}

အမြင်တစ်ခုသည် Sumeragi မှတစ်ဆင့် အဆိုပြုသူနှင့်အချိန်သတ်မှတ်ချက်တစ်ခုကို အဆုံးသတ်ရန်ကြိုးပမ်းခြင်းဖြစ်သည်။ အဆိုပြုချက်၊ အသုံးဝင်မှုတင်သွင်းမှု၊ မဲပေးခြင်း၊ သို့မဟုတ် သဘောတူညီချက်ပြီးဆုံးဖြတ်ခြင်း၏ တိုးတက်မှုကို ရပ်ဆိုင်းပါက သဘောတူညီမှု နှလုံးခုန်နှုန်းကိရိယာသည် အမြင့်ကို နောက်ပိုင်းအမြင်သို့ ရွှေ့နိုင်သည်။ ရှုထောင့်ပြောင်းလဲမှုက ပြီးဆုံးထားတဲ့ ဘလော့ကို ပြန်ရေးသားခြင်းမဟုတ်ပါ။ ၎င်းသည် validators များသည်အသေးဆုံးသတ်မှတ်မထားသောအမြင့်ကိုပြီးစီးရန်ကြိုးပမ်းပုံကိုပြောင်းလဲစေသည်၊ အမြင့်ဆုံးသိရှိသည့် quorum သို့မဟုတ် သဘောတူညီချက် အဆုံးသတ်မှုသက်သေများကို ဆောင်ရွက်ခြင်းဖြင့်ကွန်ရက် peers များသည်ပဋိပက္ခဖြစ်ပွားနေသော ဘလော့များအား နောက်ဆုံးသတ်မှတ်ခြင်းမရှိပါ။

Payload Recovery သည် အပြီးသတ်မှု ဆုံးဖြတ်ချက်နှင့် ကွဲပြားသည်။ ကွန်ရက် peer တစ်ခုသည် ဘလော့ကအပြည့်အဝ အသုံးဝင်မှုရှိမီ Quorum သို့မဟုတ် Consensus Finalisation Certificate ကိုရယူနိုင်ပါသည်။ ဒီကိစ္စမှာ RS16 အသုံးဝင် ဝန်ဆောင်မှု အပိုင်းတွေ (သို့) အသိအမှတ်ပြုတဲ့ အဖွဲ့အစည်းတစ်ခု လက်မှတ်ထိုးထားတဲ့ ကွန်ရက် နှိုင်းယှဉ်တောင်းဆိုချက်တွေဟာ ကြော်ငြာထားတဲ့ cryptographic hash တွေနဲ့ ပြန်လည်ရှာဖွေထားတဲ့ byte တွေကို စစ်ဆေးပြီး အဲဒီနောက်ပဲ ကမ္ဘာပြည်နယ်နဲ့ Kura ကို ဘလော့က သုံးပါတယ်။

### သဘောတူညီမှုပုံစံများ {#consensus-modes}

::: tip ခွင့်ပြုထားသော mode

validator roster က တိကျတဲ့ လုပ်ဆောင်မှု ရွေးချယ်မှုတစ်ခုဖြစ်တဲ့အခါ ခွင့်ပြုထားသော mode ကိုအသုံးပြုပါ။ ဒါက ကိုယ်တိုင် တည်းခိုထားတဲ့ Iroha ကွန်ရက်တွေအတွက် ပုံမှန်စတင်ချက်ပါ၊ အကြောင်းက အဖွဲ့ဝင် ပြောင်းလဲမှုဟာ ကြံဆထားတဲ့ အုပ်ချုပ်မှု (သို့) စီမံအုပ်ချုပ်ရေး လုပ်ဆောင်ချက်တွေပါ။ အရေးကြီးတဲ့ လုပ်ဆောင်မှု စည်းကမ်းတစ်ခုက validator တစ်ခုစီဟာ blockchain မျိုးဆက်၊ ယုံကြည်ရတဲ့ ကွန်ရက် အဖော်တွေ၊ BLS Proof-of-Possession နဲ့ Sumeragi သတ်မှတ်ချက်တွေကို တူညီတဲ့ ရှုထောင့်နဲ့ လည်ပတ်ဖို့ လိုပါတယ်။ မတူညီတဲ့ topology (သို့) လက်မှတ်ထိုးထားတဲ့ blockchain မျိုးဆက်တစ်ခုနဲ့တူတဲ့ ကွန်ရက်တစ်ချပ်ကွန်ရက်ကို ပြီးဆုံးအောင်တားဆီးနိုင်ပါတယ်။

:::

::: tip NPOS mode ကို

NPoS mode ကိုအသုံးပြုပါ deployment profile က validator ပါ၀င်မှုကို nomination နဲ့ stake state တွေက တွန်းအားပေးမယ်လို့ မျှော်လင့်တဲ့အခါမှာ SORA Nexus NPoS ကိုသုံးပြီး သူတို့ဖန်တီးတဲ့ Profiles တွေမှာ BLS အတည်ပြုသူရဲ့ ကိုယ်ပိုင်လက္ခဏာတွေ၊ ပိုင်ဆိုင်မှု အထောက်အထားတွေ၊ ခေတ်အလိုက် သတ်မှတ်ချက်တွေ၊ Sumeragi Epoch ပြောင်းလဲမှုတွေက သတ်မှတ်ထားတဲ့ အမြင့်တွေမှာ သတ်မှတ်ထားတဲ့ Active Validator ကို အစားထိုးနိုင်ပါတယ်။ ဒီတော့ လုပ်ငန်းရှင်တွေဟာ သဘောတူညီချက်ရဲ့ ကျန်းမာရေးနဲ့ နောက်စာရင်းကို ကျွေးမွေးတဲ့ အခန်းကဏ္ဍ (သို့) အဆိုပြုမှု အခြေအနေ နှစ်ခုစလုံးကို စောင့်ကြည့်ဖို့လိုပါတယ်။

## အများပြည်သူ သဘောတူညီချက် {#multilane-consensus}

Iroha ၏ multi-line consensus path ကို Nexus အကောင်အထည်ဖော်ရေးလမ်းကြောင်းနှင့် ဒေတာနေရာ ညှိနှိုင်းမှုမှတစ်ဆင့် အကောင်အ ထည်ဖော်ထားသည်။ ၎င်းသည် အကောင်အတာလမ်းကြောင်းတစ်ခုစီအတွက် သီးခြား သဘောတူညီချက်ဖြစ်ရပ်ကိုမစတင်ပါ။ Sumeragi သည် ညွှန်ကြားထားသော ဘလော့ခ်စီးကြောင်းတစ်ခုကို အဆုံးသတ်နေဆဲဖြစ်သည်; စီမံခန့်ခွဲမှုလမ်းကြောင်းများသည် ထိုစီးကြောင်းအတွင်းမှာ ငွေလဲလှယ်မှုများဘယ်လို လမ်းညွှန်ခြင်း၊ အစီအစဉ်ချခြင်း၊ မှတ်ပုံတင်ခြင်းနှင့် သိုလှောင်ခြင်းကိုဖော်ပြသည်။

ဆော့ဖ်ဝဲ အကောင်အထည်ဖော်မှု ပတ်ဝန်းကျင် ဖွဲ့စည်းမှုက အကောင်အ ထည်ဖော်ရေးလမ်းကြောင်းအခြေအနေ သုံးခုကို တည်ဆောက်တယ်။

- `nexus.lane_catalog`: ပြဌာန်းထားသော အကောင်အထည်ဖော်မှုလမ်းကြောင်းများ၊ တစ်ခုစီမှာ နံပါတ် `LaneId`၊ အမည်မဖော်လိုသူ၊ ဒေတာနေရာ၊ မြင်နိုင်မှု၊ သိုလှောင်ရေးပရိုဖိုင်း၊ သက်သေပြချက် အစီအစဉ်နှင့် မီတာဒေတာများရှိပါသည်။
- `nexus.dataspace_catalog`: ရေလွှမ်းတင်ကော်မတီအရွယ်အစားအတွက် အသုံးပြုသော ကိန်းဂဏန်း `DataSpaceId` နှင့် အမှားခံနိုင်ရည်တန်ဖိုးရှိ configured data spaces များ။
- `nexus.routing_policy`: အလိုအလျောက်လမ်းကြောင်း/ဒေတာနေရာ နှစ်စုံနှင့် အကောင့်များ (သို့) ညွှန်ကြားချက်လမ်းကြောင်းများနှင့် ကိုက်ညီနိုင်သော လမ်းညွှန်စည်းမျဉ်းများကို စီစဉ်ထားသည်။

Transaction သည် queue ထဲသို့ဝင်သောအခါ, execution lane router က `RoutingDecision { lane_id, dataspace_id }` သို့ဖြေရှင်းသည်။ single-lane mode တွင် ဤသည်မှာ အမြဲတမ်း execution lane `0` နှင့် universal data space ဖြစ်ပါသည်။ Nexus mode မှာ configured router က data space scope စည်းမျဉ်းတွေ၊ ငွေကြေးလုပ်ငန်း settlement routing တွေ၊ account စည်းမျဉ်းတွေ၊ explicit routing စည်းမျဉ်းတွေနဲ့ နောက်ဆုံးတော့ default route တွေကို သုံးပါတယ်။ ပြေလည်တဲ့ အကောင်အထည်ဖော်ရေးလမ်းကြောင်းနှင့် ဒေတာနေရာသည် ၎င်းတို့၏စာရင်းများတွင် တည်ရှိရန်လိုအပ်ပြီး အကောင်အ ထည်ဖော်ရေး လမ်းကြောင်းသည် ပြေလည်သော ဒေတာနေရာနှင့် ချိတ်ဆက်ထားရမည်၊ မဟုတ်ပါက ငွေပေးချေမှုကို အတန်းမတင်မီ ပယ်ချရမယ်။

နောက်ပိုင်းအဆင့်များတွင် ထပ်မံဆုံးဖြတ်ရန်မလိုအောင် စာတန်းသည် transaction cryptographic hash နှင့်အတူဤ routing ဆုံးဖြတ်ချက်ကိုထိန်းသိမ်းထားသည်။ အဆိုပြုချက်တည်ဆောက်မှုဆိုသည်မှာအကောင်အထည်ဖော်လမ်းကြောင်း metadata ကိုနည်းလမ်းနှစ်မျိုးဖြင့်အသုံးပြုသည်။

- ၎င်းဟာ အကောင်အထည်ဖော်ရေးလမ်းကြောင်းဖြင့် ငွေလဲလှယ်မှုများကို ချိတ်ဆက်ထားသည့်ကြောင့် တစ်ခုတည်းသော အကောင်အ ထည်ဖော်ရေး လမ်းကြောင်းတစ်ခုက ဘလော့ကို လွှမ်းမိုးခြင်းမရှိပါ။
- TEU) ကန့်သတ်ချက်များကို သတ်မှတ်ထားသည်။ အကောင်အထည်ဖော်ရေးလမ်းကြောင်း၏ ညှိနှိုင်းနိုင်စွမ်းကို ကျော်လွန်သည့် ငွေကြေးပူးပေါင်းဆောင်ရွက်မှုများကို အချိန်ဆွဲ၍ ပြန်လည်သိမ်းဆည်းပေးခြင်းဖြစ်သည်။

ကိုယ်စားလှယ်လောင်းပြင်ဆင်မှုအတွင်းမှာ Sumeragi က စီမံခန့်ခွဲရေးလမ်းကြောင်းနှင့် ဒေတာနေရာအလိုက် အဆိုပြုထားသော အသုံးဝင်ဝန်ဆောင်မှုကို စုစည်းပြီး လမ်းကြောင်း-ဒေသဆိုင်ရာ ဒေတာရရှိနိုင်မှု ကိုယ်ပိုင်လက္ခဏာများကို ထုတ်ယူသည်။ မှတ်တမ်းတင်ထားတဲ့ စုစုပေါင်းများတွင် ငွေပေးချေမှုအရေအတွက်၊ အပိုင်းအစများ၊ အသုံးဝင် ဝန်ဆောင်မှု ဘိုက်တာများနှင့် TEU တို့ပါဝင်သည်။ protocol ကိုပြီးဆုံးဖြတ်ပြီးနောက်၊ အဲဒီအစုစုပေါင်းတွေဟာ စစ်ဆေးထားတဲ့ Sumeragi ရောဂါစစ်ဆေးမှုတွေကနေ ဖော်ပြတဲ့ အချိန်ကာလ အချက်အလက် အမြင်တွေဖြစ်တဲ့ အကောင်အထည်ဖော်ရေးလမ်းကြောင်းနဲ့ ဒေတာဇုန်ရဲ့ cryptographic commitment value တွေ ဖြစ်လာတယ်။ ဘလော့က execution lane financial transaction settlement protocol ရလဒ်မှတ်တမ်းတွေပါဝင်တယ်ဆိုရင်၊ block processing ကလည်း execution lane finance transaction settment cryptographic commitment values နဲ့ relays တွေကို ဖန်တီးပေးပါတယ်။ Block header ကို ချိတ်ဆက်ပေးသော data containers များ၊ consensus finalisation certificate များ၊ data availability cryptographic hash of the binding value များ၊ financial transaction settlement proof များနှင့် execution lane payload အရွယ်အစားများ။

## ဒေတာရရှိနိုင်မှုနှင့် အသုံးဝင်ဝန်ဆောင်မှု ပြန်လည်ထူထောင်ခြင်း {#data-availability-and-payload-recovery}

Sumeragi v2 သည် လက်မှတ်ရေးထိုးထားသော RS16 `PayloadManifest` နှင့် `PayloadChunk` စာတိုများမှတစ်ဆင့် ကမ္ဘာလုံးဆိုင်ရာ အသုံးဝင်ဝန်ဆောင်မှုရရှိမှုကို ဆောင်ရွက်သည်။ ခေါင်းဆောင်သည် လက်မှတ်ရေးဆွဲထားသော နည်းပညာလက်မှတ်ကို အပြည့်အဝကော်မတီသို့ ပို့ပေးပြီး အစပိုင်းတွင် သတ်မှတ်ချက်အပိုင်းများကို Set A သို့ဖြန့်ဝေသည်။ Validator က Single Protocol Standard Body ကို ပြန်လည်တည်ဆောက်ပြီးနောက်ပဲ Prepare-vote လုပ်နိုင်တယ်၊ Technical Manifesto နဲ့ Chunk cryptographic hash တွေကို validate ပြီးရင် ကိုယ်ခန္ဓာကို ရေရှည် သိုလှောင်ထားတယ်။ အလျင်အမြန်လမ်းကြောင်းသည် ရပ်ဆိုင်းနေပါက ပြန်လည်ထူထောင်ခြင်းသည် အစိတ်အပိုင်းပေးပို့မှုကို Set B သို့တိုးချဲ့သည်။ Certified-body recovery နှင့် block sync သည်အကောင်ကိုလက်ခံမီကွန်ရက် peer တစ်ခုက အဆုံးသတ်မှုသင်ယူတဲ့အခါ ကန့်သတ်ထားတဲ့ပြန်လည်ထူထောင်ရေးလမ်းကြောင်းကိုပေးသည်။

Multilane execution သည်အပြင် execution lane subject တစ်ခုစီအတွက် deterministic payload-ownership cryptographic hash နှင့် lane-local RBC instance cryptographic Hash ကိုရယူသည်။ အဆိုပါ Identities များသည်အကောင်အထည်ဖော်လမ်းကြောင်း အဆိုပြုချက်များနှင့်လက်မှတ်များကိုကမ္ဘာလုံးဆိုင်ရာ container ငွေပေးချေမှုသို့ ချိတ်ဆက်ထားသည်။ ၎င်းတို့သည် သီးခြားကမ္ဘာလုံးဆိုင်ရာသဘောတူညီချက်အစည်းအဝေးမဟုတ်ပါ။ ကွန်ရက် peer တွင်သက်ဝင်သည့် သဘောတူညီချက် နောက်ဆုံးသတ်မှတ်ချက်ရှိပြီး ဒေသတွင်းတွင်သင့်လျော်သော အသုံးဝင်ဝန်ဆောင်မှုရှိလျှင်သာ ဘလော့တစ်ခု အဆုံးသတ်နေဆဲဖြစ်သည်။

သီးခြား RBC API အဆုံးသတ်မှတ်ချက်အစား စစ်ဆေးထားတဲ့ operator မျက်နှာပြင်ကို အသုံးပြုပါ။

- `iroha --operator-private-key-file <path> --output-format text ops sumeragi status` သည် ခိုင်မာသော အမြင့်၊ ရှုခင်း၊ အဆင့်၊ လက်မှတ်များနှင့် သက်တမ်းအခြေအနေကို ဖော်ပြသည်။
- `iroha --operator-private-key-file <path> --output-format text ops sumeragi diagnostics` ကန့်သတ်ချက်မရှိတဲ့ အတန်း၊ ဆော့ဖ်ဝဲ စီမံခန့်ခွဲမှု အလုပ်ဖြစ်စဉ်၊ NPoS၊ အကောင်အထည်ဖော်ရေးလမ်းကြောင်းနှင့် ဒေတာဇုန်ဆိုင်ရာ ရောဂါစစ်ဆေးမှုများ၊ အကောင် အထည်ဖော်ခြင်းလမ်းကြောင်း အသုံးဝင် ဝန်ဆောင်မှု ပိုင်ဆိုင်မှုအပါအဝင်ကို ဖော်ပြသည်။
- Prometheus အချက်ပြမှုတွေလို `sumeragi_missing_block_requests`, `sumeragi_missing_block_oldest_ms`, `sumeragi_missing_block_fetch_total`, `sumeragi_da_gate_block_total`, နှင့် `sumeragi_da_gate_satisfied_total` ပျောက်ဆုံးနေတဲ့ ကိုယ်ခန္ဓာ ပြန်လည်ထူထောင်ရေး၊ ဒေတာရရှိနိုင်မှုဂိတ်များနဲ့ သတင်းအချက်အလက် ကိုင်တွယ်ခြင်းတို့ကို ခွဲခြားထားပါ။ [စွမ်းဆောင်ရည်နှင့် မက်ထရစ်များ](/my/guide/advanced/metrics.md).

Kura သည် storage layout အတွက် derived execution lane configuration ကိုအသုံးပြုသည်။ စီမံခန့်ခွဲမှုလမ်းကြောင်းတစ်ခုစီသည် deterministic storage names များကိုရယူသည်။ ဥပမာ `blocks/lane_000_core` နှင့် `merge_ledger/lane_000_core_merge.log` ။ စီမံခန့်ဲရေးလမ်းကြောင်းသက်တမ်းပတ်လည်ပြောင်းလဲမှုများသည်ကမ္ဘာ့ဘလော့ခ်အစီအစဉ်ကိုမပြောင်းဘဲဤအပိုင်းအစများကို provisioning, decommission သို့မဟုတ် relabel လုပ်နိုင်သည်။
