# သဘောတူညီချက် {#consensus}

Sumeragi က transaction များကို ဘလော့ခ်တစ်ခုတွင် အဆိုမပြုမီ ၎င်းတို့သည် တန်းစီစာရင်းထဲသို့ ဝင်ရောက်သည်။ Validator များသည် အဆိုပြုချက်ကို သီးခြားစီ စစ်ဆေး၍ လုပ်ဆောင်ပြီး မိမိတို့ ပြန်လည်လုပ်ဆောင်ထုတ်ယူနိုင်သော အခြေအနေပြောင်းလဲမှုကိုသာ လက်မှတ်ထိုးသည်။ လိုအပ်သော validator များ၏ quorum က ထိုရလဒ်ကို သဘောတူပြီး ကိုက်ညီသော payload ကို ရရှိနိုင်သည့်အခါ ဘလော့ခ်ကို commit လုပ်သည်။

Iroha 3 ကွန်ရက်အားလုံးမှာ RS16 လက်မှတ်ထိုးထားတဲ့ ဒေတာရရှိမှု နည်းပညာ မန်နီစတာများနှင့် အပိုင်းအစများ၊ ဒါ့အပြင် အသိအမှတ်ပြုတဲ့ ကိုယ်ခန္ဓာ ပြန်လည်ထူထောင်ခြင်းများကို အသုံးပြုပါတယ်။ ဒေတာရရှိမှုဟာ သဘောတူညီချက် လိုအပ်ချက်တစ်ခုဖြစ်ပြီး ရွေးချယ်စရာ ဖြန့်ချိရေး လုပ်ဆောင်ချက်မဟုတ်ပါ။

## Sumeragi {#sumeragi}

Sumeragi သည် Iroha ၏ Byzantine ချို့ယွင်းမှုဒဏ် ခံနိုင်သော consensus အင်ဂျင်ဖြစ်သည်။ ၎င်းသည် တန်းစီစာရင်းမှ transaction များကို ယူကာ validator peer များအား တူညီသော အစီအစဉ်ချထားသည့် ဘလော့ခ်ကို သဘောတူစေသည်။ လုံလောက်သော validator များက တူညီသည့် ရလဒ်ကို ပြန်လည်ထုတ်ယူပြီး commit အတည်ပြုလက်မှတ်ကို လက်မှတ်ထိုးပြီးမှသာ ထိုဘလော့ခ်ကို အပြီးသတ်အတည်ပြုသည်။

### အဆိုပြုချက်နှင့် သဘောတူညီမှု အပြီးသတ်ခြင်း လမ်းကြောင်း {#proposal-and-commit-path}

Sumeragi သည် လယ်ဂျာကို ဘလော့ခ်အမြင့် တစ်ဆင့်စီ ရှေ့သို့ ဆက်လက်လုပ်ဆောင်သည်။ အမြင့်တစ်ခုစီတွင် validator တစ်ခုက လက်ရှိ view ၏ အဆိုပြုသူအဖြစ် ဆောင်ရွက်သည်။ အဆိုပြုသူသည် အရည်အချင်းပြည့်မီသော transaction များကို တန်းစီစာရင်းမှ ထုတ်ယူကာ အဆိုပြုဘလော့ခ်တစ်ခု တည်ဆောက်ပြီး လက်ရှိအသုံးပြုနေသော validator အစုသို့ ကြေညာသည်။ အလုပ်မရှိသော ချိန်းများသည် ဘလော့ခ်အလွတ်များ မထုတ်လုပ်ပါ။

ခွင့်ပြုချက်ဖြင့် ပါဝင်သော deployment နှင့် Nominated Proof-of-Stake (NPoS) deployment နှစ်မျိုးစလုံးတွင် တူညီသော Sumeragi လုပ်ဆောင်မှုအဆင့်ဆင့်ကို အသုံးပြုသည်။

1. Validator တစ်ခုသည် တန်းစီထားသော transaction များမှ ဘလော့ခ်တစ်ခုကို အဆိုပြုသည်။
2. အတည်ပြုသူတွေဟာ အလားတူ ကမ္ဘာ့နိုင်ငံကို ဆန့်ကျင်တဲ့ ငွေပေးချေမှုတွေကို အကောင်အထည်ဖော်ရင်း အဆိုပြုချက်ကို အတည်ပြုတယ်။
3. အတည်ပြုသူတွေဟာ လက်ရှိ အမြင့်နဲ့ ရှုထောင့်အတွက် မဲတွေနဲ့ သဘောတူညီချက် ကော်မတီ အထောက်အထားတွေကို လဲလှယ်တယ်။
4. သဘောတူညီချက် နောက်ဆုံးသတ်မှတ်မှု ကော်orum ကိုရောက်ရှိပြီးတာနဲ့ ကွန်ရက် အဖော်တွေဟာ ဘလော့ကို အဆုံးသတ်ပြီး သူတို့ရဲ့ ကမ္ဘာအခြေအနေကို မွမ်းမံတယ်။

Validator များသည် မိမိတို့ စက်ပေါ်တွင် ပြန်လည်ထုတ်ယူနိုင်သော ဒေတာကိုသာ လက်မှတ်ထိုးသည်။ မဲမပေးမီ validator သည် အဆိုပြုချက်က မျှော်မှန်းထားသော ချိန်း၊ အမြင့်နှင့် view နှင့် ကိုက်ညီကြောင်း၊ transaction လက်မှတ်များနှင့် ကန့်သတ်ချက်များ မှန်ကန်ကြောင်း၊ lane လမ်းကြောင်းရွေးချယ်မှုနှင့် executor စစ်ဆေးမှုတို့က တူညီသော input အတွက် တူညီသော ရလဒ်ပေးကြောင်း၊ payload ကို လုပ်ဆောင်ခြင်းက မျှော်မှန်းထားသော အခြေအနေပြောင်းလဲမှုကို ထုတ်ပေးကြောင်း စစ်ဆေးသည်။ ဒေသတွင်း ရလဒ်က ကွဲပြားလျှင် validator သည် အဆိုပြုချက်ကို မဲပေးမည့်အစား ပယ်ချသည်။

မဲများသည် လက်မှတ်ထိုးထားသော consensus မက်ဆေ့ချ်ငယ်များဖြစ်သည်။ ၎င်းတို့က အဆိုပြုဘလော့ခ်၊ အမြင့်၊ view နှင့် validator ၏ အထောက်အထားကို ရည်ညွှန်းသည်။ စစ်ဆေးပြီးသော လက်မှတ်များက prepare နှင့် commit quorum အတည်ပြုလက်မှတ်များကို ဖွဲ့စည်းသည်။ Commit အတည်ပြုလက်မှတ်သည် လုံလောက်သော validator များက တူညီသော ဘလော့ခ်အတွက် တူညီသည့် ရလဒ်ကို တွေ့ရှိခဲ့ကြောင်း တည်မြဲသော သက်သေဖြစ်သည်။ Validator တစ်ခုစီသည် ၎င်း၏ Prepare နှင့် Commit မဲများကို ကော်မတီတစ်ခုလုံးသို့ ပို့သည်။ မည်သည့် validator မဆို လိုအပ်သော တူညီသည့် မဲများကို စုစည်းပြီး ရလာသော အတည်ပြုလက်မှတ်ကို ထုတ်လွှင့်နိုင်သည်။

### Quorum နှင့် လေ့လာသူများ {#quorum-and-observers}

ပထမထုတ်ဝေမှု protocol သည် validator 4 ခုမှ 31 ခုအတွင်း `3f + 1` အတိအကျရှိသော မဲပေးကော်မတီကိုသာ လက်ခံသည်။ ထို့ကြောင့် မှန်ကန်သော အရွယ်အစားများမှာ 4၊ 7၊ 10 စသည်ဖြင့် 31 အထိ ဖြစ်သည်။ `n = 3f + 1` အတွက် Byzantine ချို့ယွင်းမှု ခံနိုင်ရည်မှာ `f` ဖြစ်ပြီး commit မဲပြည့်အရေအတွက်မှာ `2f + 1` ဖြစ်သည်။ Genesis ထုတ်လုပ်ခြင်းနှင့် စတင်ချိန် စစ်ဆေးခြင်းတို့က အခြားကော်မတီအရွယ်အစားများကို ငြင်းပယ်သည်။ PrepareQC၊ CommitQC နှင့် TimeoutCert တစ်ခုစီတွင် တူညီသော အလေးချိန်ရှိသည့် validator မဲ `q = n - f` အတိအကျ ပါရမည်။ ပိုများသော လက်မှတ်ထိုးသူအစုများကို ငြင်းပယ်သည်။

လေ့လာသူ peer များသည် commit လုပ်ပြီးသော ဘလော့ခ်များကို ထပ်တူပြုနိုင်သော်လည်း အဆိုမပြု၊ မဲမပေးဘဲ commit quorum တွင်လည်း မရေတွက်ပါ။ မဲပေး validator အရေအတွက်ကို မတိုးဘဲ ဒေသတွင်း query စွမ်းရည်၊ အညွှန်းပြုလုပ်မှု၊ စောင့်ကြည့်မှု သို့မဟုတ် ဒေသအလိုက် ဘလော့ခ်မိတ္တူပွားမှု လိုအပ်သော deployment တွင် လေ့လာသူများကို သုံးပါ။

### အပြောင်းအလဲများနှင့် ပြန်လည်ထူထောင်ခြင်းများကို ကြည့်ရှုရန် {#view-changes-and-recovery}

View တစ်ခုသည် သတ်မှတ်ထားသော အဆိုပြုသူနှင့် အချိန်အစီအစဉ်ကို အသုံးပြု၍ အမြင့်တစ်ခုကို အပြီးသတ်ရန် Sumeragi ၏ ကြိုးပမ်းမှုဖြစ်သည်။ အဆိုပြုချက်၊ payload၊ မဲ သို့မဟုတ် commit တိုးတက်မှု ရပ်တန့်လျှင် pacemaker က ထိုအမြင့်ကို နောက် view သို့ ရွှေ့နိုင်သည်။ View ပြောင်းခြင်းသည် commit လုပ်ပြီးသော ဘလော့ခ်ကို ပြန်မရေးပါ။ ၎င်းသည် commit မလုပ်ရသေးသော အမြင့်ကို validator များက အပြီးသတ်ရန် ကြိုးပမ်းပုံကို ပြောင်းလဲပြီး သိရှိထားသည့် အမြင့်ဆုံး quorum သို့မဟုတ် commit သက်သေကို ဆက်သယ်ဆောင်သည်။ ထို့ကြောင့် peer များသည် အချင်းချင်းဆန့်ကျင်သော ဘလော့ခ်များကို အပြီးသတ်အတည်မပြုနိုင်ပါ။

Payload ပြန်လည်ရယူခြင်းသည် အပြီးသတ်အတည်ဖြစ်မှု ဆုံးဖြတ်ချက်နှင့် သီးခြားဖြစ်သည်။ Peer တစ်ခုသည် ဘလော့ခ် payload အပြည့်အစုံ မရရှိမီ quorum သို့မဟုတ် commit အသိအမှတ်ပြုလက်မှတ်ကို ရရှိနိုင်သည်။ ထိုအခါ peer သည် လက်မှတ်ထိုးထားသော RS16 payload အပိုင်းများ သို့မဟုတ် အသိအမှတ်ပြုထားသော body ကို တောင်းခံပြီး ပြန်ရရှိသော byte များကို ကြေညာထားသည့် ဟက်ရှ်များနှင့် တိုက်စစ်သည်။ ထိုစစ်ဆေးမှုအောင်မြင်ပြီးမှသာ ဘလော့ခ်ကို ကမ္ဘာလုံးဆိုင်ရာ အခြေအနေနှင့် Kura တွင် အသုံးချသည်။

### သဘောတူညီမှုပုံစံများ {#consensus-modes}

ရွေးချယ်ထားသော mode သည် validator အစုကို ဖွဲ့စည်းပုံနှင့် လည်ပတ်ပုံကို ထိန်းချုပ်သည်။ ၎င်းကို လက်မှတ်ထိုးထားသော genesis တွင် [`consensus_mode`](/my/reference/genesis.md) ဖြင့် ကြေညာပြီး အမြင့်တစ်ခုစီ၏ context တွင် မပြောင်းလဲနိုင်အောင် သတ်မှတ်ထားသည်။ ဒေသတွင်း `[sumeragi]` ပြင်ဆင်သတ်မှတ်မှုသည် နိုဒ်၏ role၊ လက်မှတ်ထိုးပစ္စည်း ထိန်းသိမ်းမှု၊ ဘေးကင်းရေးမှတ်တမ်း လမ်းကြောင်းများနှင့် မှတ်တမ်းတင်ထားသော အချိန်ကုန်ဆုံးမှု၊ ထပ်တူပြုမှု အစားထိုးတန်ဖိုးများကို ရွေးချယ်သည်။ ဘလော့ခ်နှင့် transaction ကန့်သတ်ချက်များ၊ consensus mode နှင့် အချိန်စည်းချက်တို့သည် လက်မှတ်ထိုးထားသော genesis နှင့် commit လုပ်ပြီးသော အခြေအနေမှ လာသည်။ Validator များတွင် တူညီသော လက်မှတ်ထိုးထားသည့် genesis၊ ကွန်ရက်ချိတ်ဆက်ပုံ၊ ယုံကြည်ရသော peer ဒေတာနှင့် အမှန်တကယ်သက်ရောက်သော Sumeragi parameter များ လိုအပ်သည်။

| မုဒ် | အသင့်တော်ဆုံး အသုံးပြုမှု | Validator အစု | လည်ပတ်ရေး ဦးစားပေးချက် |
| ------------ | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| ခွင့်ပြုချက်ဖြင့် ပါဝင်သောမုဒ် | ပုဂ္ဂလိက၊ အဖွဲ့ပူးပေါင်းနှင့် အော်ပရေတာ စီမံသော ကွန်ရက်များ | Validator များကို deployment က သဘောတူထားသည့် ယုံကြည်ထားသော peer များ၏ ချိတ်ဆက်ဖွဲ့စည်းပုံ မှ ရယူသည် | Validator အားလုံး၌ လက်မှတ်ထိုးထားသော genesis၊ ယုံကြည်ထားသော peer များ၊ peer ကီးများနှင့် Sumeragi ပါရာမီတာများ တူညီစေရန် ထိန်းသိမ်းပါ |
| NPoS | အမည်စာရင်းတင်သွင်းမှုနှင့် stake မူဝါဒအလိုက် စစ်ဆေးသော အများသုံး သို့မဟုတ် SORA Nexus အတွက် ရည်ရွယ်သော ကွန်ရက်များ | Validator များကို ပုံမှန်အားဖြင့် epoch များအလိုက် NPoS ၏ profile ဖြင့် ရွေးချယ်ပြီး BLS ကီးများနှင့် ပိုင်ဆိုင်ကြောင်း သက်သေများ လိုအပ်သည် | Stake snapshot များ၊ လက်မှတ်ထိုးထားသော epoch နှင့် ရွေးချယ်မှု input များ၊ validator များ၏ PoPs နှင့် မပြောင်းလဲသော ဘလော့ခ်အချိန်စည်းချက်တို့ကို ကွန်ရက်တစ်လျှောက် ကိုက်ညီအောင် ထားပါ |

::: tip ခွင့်ပြုထားသော mode

Validator စာရင်းကို လည်ပတ်ရေးအရ တိတိကျကျ ရွေးချယ်ထားသည့်အခါ ခွင့်ပြုချက်ဖြင့် ပါဝင်သောမုဒ်ကို သုံးပါ။ အဖွဲ့ဝင်ပြောင်းလဲမှုများကို အုပ်ချုပ်မှု သို့မဟုတ် စီမံခန့်ခွဲသူက ရည်ရွယ်ချက်ရှိရှိ ဆောင်ရွက်ခြင်းဖြစ်သောကြောင့် ကိုယ်တိုင်လည်ပတ်သော Iroha ကွန်ရက်များအတွက် ဤမုဒ်မှ စတင်လေ့ရှိသည်။ လည်ပတ်ရာတွင် အရေးကြီးသော စည်းမျဉ်းမှာ validator အားလုံးက genesis၊ ယုံကြည်ထားသော peer များ၊ BLS ပိုင်ဆိုင်ကြောင်း အထောက်အထားများနှင့် Sumeragi ပါရာမီတာများကို တူညီစွာ သိရှိအသုံးပြုရခြင်းဖြစ်သည်။ Topology သို့မဟုတ် လက်မှတ်ထိုးထားသော genesis မတူသည့် peer တစ်ခုတည်းကပင် ကွန်ရက်၏ commit လုပ်ဆောင်မှုကို တားဆီးနိုင်သည်။

:::

::: tip NPOS mode ကို

Deployment ပရိုဖိုင်က validator ပါဝင်မှုကို အမည်တင်သွင်းမှုနှင့် stake အခြေအနေအရ ဆောင်ရွက်ရန် မျှော်မှန်းထားလျှင် NPoS မုဒ်ကို သုံးပါ။ အများသုံး SORA Nexus deployment များသည် NPoS ကို သုံးပြီး ထုတ်လုပ်ထားသော ပရိုဖိုင်များတွင် စတင်ချိန်လိုအပ်သည့် validator များ၏ BLS အထောက်အထားများ၊ ပိုင်ဆိုင်ကြောင်း အထောက်အထားများ၊ epoch ဆက်တင်များနှင့် Sumeragi NPoS ပါရာမီတာများ ပါဝင်သည်။ Epoch ပြောင်းလဲမှုများက သတ်မှတ်အမြင့်များတွင် လက်ရှိ validator အစုကို အစားထိုးနိုင်သောကြောင့် အော်ပရေတာများသည် consensus ကျန်းမာရေးနှင့် နောက် validator စာရင်းကို သတ်မှတ်ပေးမည့် stake သို့မဟုတ် အမည်တင်သွင်းမှု အခြေအနေနှစ်ခုလုံးကို စောင့်ကြည့်ရန် လိုအပ်သည်။

## အများပြည်သူ သဘောတူညီချက် {#multilane-consensus}

Data space များသည် ဒေတာ၊ authority၊ မူဝါဒနှင့် အက်ပ်များအတွက် ပတ်ဝန်းကျင်များကို သတ်မှတ်သည်။ ၎င်းတို့၏ lane များက ဖြန့်ဝေမှုနှင့် အတည်ပြုလက်မှတ်ထုတ်ပေးမှု စွမ်းရည်ကို တိုးပေးသည်။ ကတ်တလောက်များမှာ သီးခြားဖြစ်သည်။ `nexus.dataspace_catalog` သည် data space များကို သတ်မှတ်ပြီး `nexus.lane_catalog` သည် data space တစ်ခုစီကို ရည်ညွှန်းသော lane များကို သတ်မှတ်သည်။ Lane အများအပြားသည် data space တစ်ခုတည်းကို မျှဝေနိုင်သည်။

အများသုံး ကမ္ဘာလုံးဆိုင်ရာ လုပ်ဆောင်မှုအတွက် lane `0` ၏ အစဉ်ကို ကမ္ဘာလုံးဆိုင်ရာ Sumeragi instance က သတ်မှတ်သည်။ အခြား လက်ရှိအသုံးပြုနေသော lane မျိုးဆက်တစ်ခုစီသည် သတ်မှတ်ချည်နှောင်ထားသော ကော်မတီနှင့် consensus parameter များဖြင့် တူညီသည့် Sumeragi core ၏ သီးခြား instance ကို လည်ပတ်သည်။ ၎င်း၏ အတည်ပြုလက်မှတ်ရ ဘလော့ခ်တွင် commit လုပ်ပြီးသော ကမ္ဘာလုံးဆိုင်ရာ anchor နှင့် နှိုင်းယှဉ်၍ လက်ခံခွင့်စစ်ဆေးထားသော အစဉ်လိုက် transaction အစု ပါဝင်သည်။ Lane အတည်ပြုလက်မှတ်ထုတ်ပေးမှုသည် ကမ္ဘာလုံးဆိုင်ရာ State ကို မပြောင်းလဲပါ။

ကမ္ဘာလုံးဆိုင်ရာ ချိန်းသည် lane တစ်ခုစီမှ နောက်အစဉ်ဆက် အတည်ပြုလက်မှတ်ရ ဘလော့ခ်များကို ပေါင်းစည်းသည်။ ရလာသော ကမ္ဘာလုံးဆိုင်ရာ ဘလော့ခ်ကို လုပ်ဆောင်သောအခါ transaction များကို စံအစဉ်အတိုင်း အသုံးချပြီး ကမ္ဘာလုံးဆိုင်ရာ CommitQC က ထိုလုပ်ဆောင်မှုကို အပြီးသတ်အတည်ပြုသည်။ ထို့ကြောင့် lane အတည်ပြုလက်မှတ်တစ်ခုတည်းဖြင့် transaction တစ်ခုက ကမ္ဘာလုံးဆိုင်ရာ State ကို ပြောင်းလဲပြီးဟု မဆိုနိုင်ပါ။ ပြန်လည်ရယူမှုနှင့် လုပ်ဆောင်မှုတစ်လျှောက် lane ၏ သတ်မှတ်အမှတ်၊ မျိုးဆက်၊ anchor လတ်ဆတ်မှု၊ မူရင်းဒေတာ ထိန်းသိမ်းမှုနှင့် အစဉ်ဆက် ပေါင်းစည်းမှု နယ်နိမိတ်များကို ဆက်လက်စစ်ဆေးသည်။

Commit လုပ်ပြီးသော `sumeragi_lane_policy` သည် ပုံသေ lane များ၊ လမ်းကြောင်းများ၊ ကော်မတီများနှင့် အလိုအလျောက် စွမ်းရည်ချဲ့ထွင်မှုကို ထိန်းချုပ်သည်။ ပြင်ဆင်သတ်မှတ်မှု ကတ်တလောက်တစ်ခုတည်းက consensus lane ကို အသက်မသွင်းပါ။ တိကျသော data space ပစ်မှတ်များသည် ကိုက်ညီပြီး လက်ခံခွင့်ရထားသော lane သို့ ဖြေရှင်းရမည်။ မရရှိနိုင်သော သီးသန့်လမ်းကြောင်းကို universal အလုပ်အဖြစ် မလုပ်ဆောင်ဘဲ ငြင်းပယ်သည်။ ထိန်းချုပ်ရေးအလွှာ၏ ပြည့်စုံသော အစုများကို lane `0` မှတစ်ဆင့် ပို့ဆောင်သောကြောင့် ကတ်တလောက်နှင့် အသက်သွင်းမှု အပြောင်းအလဲများ ဆက်လက်လုပ်ဆောင်နိုင်သည်။

သီးခြားလက်မှတ်ထိုးထားသော data space root သည် ကိုယ်ပိုင် State နှင့် ဒေသတွင်း အပြီးသတ်အတည်ဖြစ်မှုရှိသော သီးခြားလုပ်ဆောင်မှု နယ်နိမိတ်ဖြစ်သည်။ Data space ကတ်တလောက်စာရင်း မှတ်ပုံတင်ခြင်းက ထို root ကို မဖန်တီးပါ။ Root များအကြား အားလုံးအောင်မြင်မှသာ အတည်ဖြစ်ခြင်းအတွက် သီးခြား AMX protocol ကို သုံးသည်။ သတ်မှတ်ထားသော candidate တွင် ဤလမ်းကြောင်း၏ ငွေကြေးဆိုင်ရာနှင့် ကွန်ရက်တစ်ခုလုံးဆိုင်ရာ အရည်အချင်းစစ် အတည်ပြုမှုများ မပြီးသေးပါ။

သတ်မှတ်ထားသော [lane အကောင်အထည်ဖော်မှု](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/crates/iroha_core/src/sumeragi/lanes/mod.rs)၊ [lane စည်းမျဉ်းသတ်မှတ်ချက်](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/specs/sumeragi_lanes.md)၊ [သီးခြား data space စည်းမျဉ်းသတ်မှတ်ချက်](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/specs/sumeragi.md) နှင့် [အရည်အချင်းစစ် အခြေအနေ](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/specs/sumeragi_goals.md) ကို ကြည့်ပါ။

## ဒေတာရရှိနိုင်မှုနှင့် အသုံးဝင်ဝန်ဆောင်မှု ပြန်လည်ထူထောင်ခြင်း {#data-availability-and-payload-recovery}

Sumeragi V1 သည် လက်မှတ်ထိုးထားသော RS16 `PayloadManifest` နှင့် `PayloadChunk` မက်ဆေ့ချ်များဖြင့် ကမ္ဘာလုံးဆိုင်ရာ payload ရရှိနိုင်မှုကို ဆောင်ရွက်သည်။ ခေါင်းဆောင်သည် လက်မှတ်ထိုးထားသော manifest ကို ကော်မတီတစ်ခုလုံးသို့ ပို့ပြီး အစပိုင်းတွင် တစ်သမတ်တည်းတွက်ချက်ထားသော chunk များကို Set A သို့ ဖြန့်ဝေသည်။ Validator သည် စံ body ကို ပြန်တည်ဆောက်ပြီး manifest နှင့် chunk ဟက်ရှ်များကို စစ်ဆေးကာ body ကို ရေရှည်တည်မြဲစွာ သိမ်းဆည်းပြီး တစ်သမတ်တည်းစစ်ဆေးမှု အပြီးသတ်မှသာ Prepare မဲပေးနိုင်သည်။ အမြန်လမ်းကြောင်း ရပ်တန့်ပါက ပြန်လည်ရယူမှုသည် chunk ပို့ဆောင်မှုကို Set B သို့ ချဲ့ထွင်သည်။ Peer က body မရမီ အပြီးသတ်အတည်ဖြစ်မှုကို သိရှိသွားပါက အတည်ပြုလက်မှတ်ရ body ပြန်လည်ရယူမှုနှင့် ဘလော့ခ်ထပ်တူပြုမှုတို့က ကန့်သတ်ထားသော ပြန်လည်ရယူရေးလမ်းကြောင်းကို ပေးသည်။

Lane instance တစ်ခုစီသည် ကိုယ်ပိုင် စစ်မှန်ကြောင်း အတည်ပြုထားသော ရရှိနိုင်မှုနှင့် အတည်ပြုလက်မှတ် context ကို သုံးသည်။ ကမ္ဘာလုံးဆိုင်ရာ ပေါင်းစည်းမှု စစ်ဆေးချက်များက ၎င်း၏ အတည်ပြုလက်မှတ်ရ အစုနှင့် မူရင်း payload ကို မျှော်မှန်းထားသော မျိုးဆက်၊ anchor တို့နှင့် ချည်နှောင်သည်။ Peer သည် ကိုက်ညီသော ကမ္ဘာလုံးဆိုင်ရာ payload နှင့် မှန်ကန်သော CommitQC ကို ဒေသတွင်း ရရှိထားမှသာ ကမ္ဘာလုံးဆိုင်ရာ အပြီးသတ်အတည်ဖြစ်မှုကို အသုံးချသည်။

သီးခြား RBC API အဆုံးသတ်မှတ်ချက်အစား စစ်ဆေးထားတဲ့ operator မျက်နှာပြင်ကို အသုံးပြုပါ။

- `iroha --operator-private-key-file <path> --output-format text ops sumeragi status` သည် တရားဝင်အခြေအနေကို ဖော်ပြသည့် အမြင့်၊ view၊ အဆင့်၊ အတည်ပြုလက်မှတ်များနှင့် ဆက်လက်တိုးတက်နိုင်မှု အခြေအနေကို အစီရင်ခံသည်။
- `iroha --operator-private-key-file <path> --output-format text ops sumeragi diagnostics` သည် lane payload ပိုင်ဆိုင်မှုအပါအဝင် တန်းစီစာရင်း၊ pipeline၊ NPoS၊ lane နှင့် data space ဆိုင်ရာ အာဏာသက်ရောက်မှုမရှိသော စစ်ဆေးရေးအချက်အလက်များကို ဖော်ပြသည်။
- Prometheus အချက်ပြမှုတွေလို `sumeragi_missing_block_requests`, `sumeragi_missing_block_oldest_ms`, `sumeragi_missing_block_fetch_total`, `sumeragi_da_gate_block_total`, နှင့် `sumeragi_da_gate_satisfied_total` ပျောက်ဆုံးနေတဲ့ ကိုယ်ခန္ဓာ ပြန်လည်ထူထောင်ရေး၊ ဒေတာရရှိနိုင်မှုဂိတ်များနဲ့ သတင်းအချက်အလက် ကိုင်တွယ်ခြင်းတို့ကို ခွဲခြားထားပါ။ [စွမ်းဆောင်ရည်နှင့် မက်ထရစ်များ](/my/guide/advanced/metrics.md).

Lane ဘလော့ခ်သိုလှောင်မှုများသည် ပေါင်းစည်းမှုနှင့် ပြန်လည်ရယူမှုအတွက် လိုအပ်သော အတည်ပြုလက်မှတ်ရ အစုများနှင့် မူရင်းမှတ်တမ်းများကို ထိန်းသိမ်းသည်။ ၎င်းတို့၏ သက်တမ်းစက်ဝန်းသည် commit လုပ်ပြီးသော lane မျိုးဆက်နှင့် ကိုက်ညီရသည်။ သိုလှောင်ရေး directory အမည်တစ်ခုက lane အသစ် သို့မဟုတ် လုပ်ဆောင်မှု root အသစ်ကို ခွင့်မပြုပါ။
