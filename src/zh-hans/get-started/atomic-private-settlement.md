# 运行跨数据空间的原子私有结算 {#run-atomic-private-cross-dataspace-settlement}

`AtomicPrivateSettlementV1` 在 2 至 255 个 SORA Nexus 数据空间中各协调一个保密结算分段，并在一次全局状态事务中使所有分段获得最终性。被拒绝、过期或中止的批包不会应用任何分段。透明的 Native AMX DvP/PvP 仍是独立的协议路径。

::: warning 发布状态
此功能受治理、默认禁用，且尚未达到生产使用标准。在确切版本通过所有已发布的功能、隐私、容错、性能、可复现构建、独立密码学审查和制品发布门槛之前，请勿将其启用于真实 CBDC 价值。
:::

## 协议所隐藏的内容 {#what-the-protocol-hides}

每条结算段都使用固定的两输入,三输出私人笔记证明.委员会验证人员验证了证明和不透明状态过渡;他们没有接收平文部分,资产,金额,备忘录或业务结果.授权的本地审计员解密了填充的审计囊,检查了这些内容,并签署了一份针对目的的单独批准.默认政策接受由受监管的审计员集中的一个批准.

公共承载交易和收据故意披露:

- 网络和捆绑标识符
- 参与者数据空间路由及参与者数量
- 时间和过期的高度
- 稳定的不透明池标识符,根,取消符,承诺和固定加密文本插槽
- 委员会权限主体和准确的3/4可用性,准备和提交证书
- 支持者,公共网络费用和终端状态

这提供内容保密性，而不提供流量匿名性。时序、参与者数量、数据空间身份和稳定池活动仍公开可见。如果数据空间只承载一种 CBDC，即使不公开资产标识符字面量，也可能从路由推断出该资产。

## 部署要求 {#deployment-requirements}

在激活之前,运营商需要所有以下条件:

1. 每个参与数据空间恰好有四个验证者，并各自具备不同的 BLS 共识密钥及持有证明
2. 强制性 Sumeragi DA/RBC 可用于每一个高度
3. 每个数据空间均具备受治理的保密结算池和初始根
4. 可用的原生 `IrohaIvmPrivateNoteStarkV1` 实现、已提交的私有结算限额，以及 V1 策略权限
5. 至少有一个受监管的本地 `PrivateSettlementAuditPolicyV1`,包括不同的审计签名和混合加密密钥,一个关键时代,高度有效性和批准门
6. 足够的私有辅助记录存储空间，以满足已提交的保留期要求
7. 一个能够提交最终公共承载交易的中立发起方账户

审计员也可以运行验证器,但必须使用单独的共识,审计签名和审计加密密钥.在监管保留期内保留已停用的解密密钥,或在停用前完成受治理且经过测试的胶囊重新包装.

四验证者授权集合锚定于状态，并非由客户端提供。在清单的 `authority_context_height`，每个验证者都从共识状态解析准确且有序的执行通道/数据空间成员名单和活跃通道世代，要求解析出的高度匹配，并验证四个 BLS 密钥及持有证明。上传、Prepare 和最终回执准入均使用同一历史授权集合。

## 配置辅助记录保管 {#configure-sidecar-custody}

已提交的隐私策略设定证明、胶囊和承载交易的限额、参与者上限、过期、保留期以及审计者要求。准入还需要池策略的治理通知期，以及当前的链上结算池和审计记录。不存在节点启用标志或服务激活高度。

节点配置仅控制加密辅助记录存储的本地容量：

```toml
[nexus.atomic_private_settlement]
sidecar_max_records = 256
sidecar_max_total_bytes = 3221225472
```

这些是随实现提供的存储上限。选择本地容量之前，应在目标硬件上测量保留记录和规范字节数。容量本身不会激活结算，也不会改变已提交的有效性策略。

已提交的胶囊上限按 `PrivateSettlementAuditCapsuleV1` 的完整规范 Norito 编码计量，包括 AAD、nonce、密文、向量帧结构、审计者身份及每一行包装后的 DEK。已提交的承载交易上限按赞助方签名的完整交易计量，包括指令帧结构、授权主体、元数据、费用意图及签名。普通网络交易限制同样适用。

## 结算工作流程 {#settlement-workflow}

客户本地构建证明和加密囊.秘密证人必须留在原生钱包或原生工作者中;不要将它们串行成申请日志, Python 对象, HTTP 请求或持久的协调记录.

胶囊和每个审计者 DEK 包装的已验证数据包含精确的状态锚定委员会摘要和 `authority_context_height`，以及网络、路由/实例、捆绑、结算段、策略、密钥 epoch 和明文承诺。已包装密钥不能移到其他名单或历史权限上下文。

对于每条规律的结算段,协调员然后执行这个序列:

1. 将临时加密材料上传到全部四个验证器，并取得规范的精确 3-of-4 可用性证书。
2. 让授权审计员获取并解密其胶囊，重新计算公开绑定，应用本地策略，并提交批准。
3. 在投票之前,每个验证者独立检查和稳定地进行分别测试.在每一个测试的响应者身上,保持可规定的3/4预备证明.
4. 每个结算段都取得 Prepare 证书后，构建不可变的完整 Prepare 屏障。让清单赞助方通过一个 `RegisterAtomicPrivateSettlementPrepareV1` 控制承载交易提交该屏障并等待最终性；Commit 投票者会参考这一已复制的锁。然后请求并持久保存规范的 3-of-4 Commit 证书。如果协调器重新启动，请向参与节点查询其在本地持久保存的 Prepare 和 Commit 证书，选择一份规范且达到等效法定人数要求的证书，并在继续之前重新分发；切勿从未经身份验证的本地缓存重建证书。
5. 让清单赞助方签署并提交全局最终化承载交易。该承载交易包含一条 `FinalizeAtomicPrivateSettlementV1` 指令和精确、完整、已认证的捆绑。协调器和 WSV 预检会测量完整封装的最终化指令，包括已注册指令的框架。Torii 和核心的一次性承载交易绑定会对赞助方签署的精确规范交易执行 `max_carrier_bytes`，其中包括权限、元数据、费用意图和签名。Torii 会拒绝在其权限上下文之前提交的承载交易；若它在到期前仍可能达到最终性的最后准入高度或之后进入，或超出治理规定的到期区间，也会被拒绝。
6. 查询公开捆绑状态和回执,直到全球最终完成.处理本地辅助记录状态为暂时的,直到它调整了不可改变的全球终端记录.

Rust 客户端通过 `certify_and_upload_private_settlement_legs_v1`、`prepare_private_settlement_bundle_v1`、`register_private_settlement_prepare_and_wait_v1`、`commit_private_settlement_bundle_v1` 和 `submit_private_settlement_bundle_v1` 等方法提供此流程。可安全应对重新启动的协调流程使用 `recover_or_prepare_private_settlement_bundle_v1` 和 `recover_or_commit_private_settlement_bundle_v1`。委员会和审计者的调用需要明确的角色凭证；它们不会复用普通账户签名者。

## 安全地转换审计政策 {#rotate-an-auditor-policy-safely}

使用隐私管理授权的 `RotatePrivateSettlementPoolPolicyV1`指令. 它必须指定当前的确切治理测试,保持相同的路线,合并和资产绑定承诺,提升治理修订一项,使用更新的关键时代和不同的政策/治理测验,并在包含旋转的区块上激活. 池边界、根、取消器、输出、重播集和最终收据会被保留. 不要包含在轮换激活高度触及相同 route/pool 的收据;该指令会拒绝此边界.

公共池投影保留完整的已取代策略修订谱系。因此，在轮换前最终确定的收据在重启后仍然有效，而对该收据的精确重放会被拒绝，且不会更改状态。该谱系不授权未完成的工作：任何跨越激活边界的旧策略捆绑都会在全局状态更改前以失败关闭方式失败。请保留打开已存储胶囊所需的每个旧解密密钥，或在销毁前完成受治理且经过测试的胶囊重新封装。

## Torii 路线家族 {#torii-route-family}

这些路线使用规范的 Norito 请求和响应对象.验证和限制的响应使用私人 `no-store`缓存行为.

|行动|方法和路径|主体|
| ------------------ | -------------------------------------------------------------------------- | --------------------------- |
|权限上下文|`POST /v1/nexus/private-settlements/context/{height}`|规范账户签名|
|加载结算段|`POST /v1/nexus/private-settlements/legs`|规范账户签名|
|可用性分享|`POST /v1/nexus/private-settlements/legs/availability-shares`|规范账户签名|
|准备投票|`POST /v1/nexus/private-settlements/phases/prepare-votes`|规范账户签名|
|提交投票|`POST /v1/nexus/private-settlements/phases/commit-votes`|规范账户签名|
|持续阶段 QC |`POST /v1/nexus/private-settlements/phases/certificates`|规范账户签名|
| 恢复阶段 QCs | `GET /v1/nexus/private-settlements/legs/{payload_digest}/phase-certificates` | 公示赞助商 |
|结算段状况|`GET /v1/nexus/private-settlements/legs/{payload_digest}/status`|规范账户签名|
|委员会证明|`GET /v1/nexus/private-settlements/legs/{payload_digest}/committee-proof`|精确的清单验证器|
| 审计胶囊 | `POST /v1/nexus/private-settlements/legs/{payload_digest}/audit-capsule` | 经治理授权的审计者 |
|审计员的批准|`POST /v1/nexus/private-settlements/legs/{payload_digest}/audit-approvals`|管理审计师|
|提交承载交易|`POST /v1/nexus/private-settlements/bundles`|清单赞助方|
|捆绑状态|`GET /v1/nexus/private-settlements/bundles/{bundle_id}`|公共|
|收到或取消|`GET /v1/nexus/private-settlements/bundles/{bundle_id}/receipt`|公共|

公开状态和收据 APIs 只披露文档中列明的公开字段。具体而言，普通结算段状态不会披露批准数量或治理规定的审计员阈值。受限读取会有意将材料不存在、无权访问以及保留期已过这三种情况归入同一个“不可用”响应类别。提交路由仅接受一条由赞助方直接签名的 Prepare 锁注册、最终化或中止指令。其 `202` 响应只包含捆绑 ID、观测到的准入高度和承载交易哈希；这并不表示排队等待处理的中止操作已经最终确定。SDKs 要求两个标识符都是规范且带校验和的 Norito `Hash` JSON 字面量，并要求高度是精确的无符号64位整数。字段缺失、多余、类型错误、非规范、校验和无效、负数、负零、小数或溢出时均会以失败关闭方式拒绝。请通过捆绑状态或收据获取权威终态。状态码同样有严格要求：该承载交易准入路由必须返回 `202`，而私有结算 V1 的其他所有成功响应必须返回 `200`。客户端会将其他成功的 `2xx` 状态码视为契约漂移并予以拒绝，同时不会在客户端错误中回显意外的响应正文。只有服务器拒绝代码匹配 `[A-Za-z0-9_.:-]{1,128}` 时才会对外提供；响应解析或验证的错误原因会被丢弃，以免正文内容或攻击者选择的 JSON 字段名重新出现在带原因信息的日志中。

## 失败和恢复 {#failure-and-recovery}

在全球突变之前,缺失或过时的审计批准,不到三个验证者投票,错误的根源或时代,重复废除,替换的证明或囊,非规范的步骤顺序,过期的捆绑和不匹配的退款条款都会失败.提交证书永远不会改变私人状态.

验证者在确认辅助记录、暂存增量和阶段证书之前先将其 fsync。重启时，验证者从规范的持久记录重建预留，然后协调不可变的全局收据、中止标记或到期状态。即使没有要协调的终结候选项，受监督的协调器也会在同步观测到的权威高度执行终结保留清理，并在清理出错时采用失败关闭策略。只有权威的全局终结记录才能释放暂存锁。对已最终确定收据的精确重放会被拒绝，且不会更改状态；冲突重放会确定性失败。

预订身份包括完整的路线.池头使用 `(route, pool_id, epoch, root)`,取消器使用 `(route, pool_id, nullifier)`,输出使用 `(route, pool_id, commitment)`.在另一条路线上相同的不透明值是独立的;重启过程中仍然锁定了精确路线碰撞.

运营警报应仅使用不透明的捆绑,路线,阶段,摘要,高度和理性类字段.永远不要将解密囊,账户或资产识别器,金额,备忘录,查看数据,证明见证者或解析器有效载荷放置在日志,事件,计量标签或追踪范围中.

## 在实际价值之前的资格 {#qualification-before-real-value}

为了查看您打算部署的确切构建和配置,存储包含:

- 抵制性证明,囊,政策,钥匙转换,退款和重播案件
- 针对 2、3、4、8 和 16 个数据空间运行真实进程，每个数据空间包含四个验证者；覆盖验证者和协调者重启、经认证记录的 5%、10% 和 20% 消息丢失、阶段性网络分区、恢复及持久化边界崩溃
- 在 Torii, P2P,区块, Kura,快照,查询,事件,日志和远程测量中进行 canary 和差分泄漏分析
- 每个实际网络参与者的数量至少有5次加热和30次测量捆绑, p50,p95,p99,信任间隔,资源,流量,证明和回执大小以及透明的 AMX 作为控制.
- 严格的工作空间测试,和格式检查,随机种子,浸泡,可复制的构建, SBOMs,以及签署的构件哈希.
- 两种正式层次:3/255结算段的计数对称性检查和准确的四个验证器委员会索引 N=2验证器重点加上全局限错误,纸质主要 N=3 错误,N=4 清洁,N=3 过期/复制配置,每个委员会的错误预算独立.
- 独立审查证明关系、虚拟槽位选择器、资产和胶囊绑定、补偿关系、密码学，以及跨数据空间状态机

将原始证据和清理后的证据、威胁模型、协议论证、限制、commit ID、硬件说明和审计报告发布到由 DOI 支持的不可变工件中。仅有仓库测试并不能使该功能成为达到生产要求的 CBDC 结算系统。

从最终的干净 Iroha 检出中生成发布源文件清单和封印，并将其写入该检出目录之外预先创建的捆绑根目录：

```sh
python3 scripts/private_settlement_source_evidence.py \
  --repository-root . \
  --bundle-root /absolute/path/to/release-bundle
```

如果存在已暂存、未暂存、未跟踪或未合并的文件，或者捕获期间源文件发生任何变化，生成工具都会失败。它会保留原始提交对象、规范的 Git 树清单、精确的二进制文件路径列表、确定性的源文件封印以及 `Cargo.lock`；请将其 JSON 结果中的每一项工件声明都纳入最终发布清单。这不会免除最终 DOI 捆绑验证器或任何外部发布关卡。

源文件封印具有可移植性并采用失败关闭策略：生成工具和最终验证器会解析归档中的整个符号链接图。因此，即使某个链接表面上位于根目录内，只要它通过另一个链接逃逸到外部、形成循环、穿越 `.git`，或使用 Windows 风格的目标，都会在创建链接前被拒绝。结构化的源文件报告和关卡报告只能从有界且稳定的文件中解析，这些文件的摘要和长度必须与发布清单一致；每一种源载荷必须恰好出现一次。

每次原始故障测试运行和每个延迟样本都必须绑定完整的发布 commit、一个结构化固定硬件说明的 SHA-256，以及对应精确参与者数量配置的 SHA-256。应归档一份覆盖 N=2,3,4,8,16 的规范配置清单；各条目必须引用保留的配置字节，并声明每个数据空间恰有四个验证者、采用 3-of-4 法定票数，且强制使用已签名 RS16 DA/RBC。发布验证器拒绝在不同构建、硬件配置或网络配置上生成的汇总。每条消息丢失、阶段切断和持久化崩溃记录还必须指明全局不可复用的精确 JSONL 记录引用，这些记录位于由 SHA-256 绑定的认证控制器及原子性捕获工件中。发布验证器解析这些摘要，并要求记录匹配运行身份、试验索引与参数、控制器确认或恢复结果、连续检查次数，以及部分可见性和部分可花费性观察均为零的结果。后续版本的 p95/p99 比较也拒绝硬件、配置或测量要求与候选版本不同的已签名基线。最终验证器根据归档原始样本重新生成所有报告的百分位数、MADs 和确定性置信区间，而不信任脱离原始数据的基准汇总。它还会重新加载金丝雀测试清单，独立重扫每个归档隐私表面，因此报告不能通过重新绑定文件摘要来掩盖对预埋秘密的检出。每次仅针对秘密的运行都必须保留仅所有者可访问的未过滤环回 pcap、原始 tcpdump stderr 与零丢包统计、规范端口清单、打包的受限源归档，以及所有对等节点的原子性观察。最终验证器直接根据这些归档字节重新执行绑定端口的数据包拆分、源投影，以及从基线到终态的原子性检查，而不信任已发布汇总。

归档还必须包含规范的成对流量计数清单和差异对清单，为每个必需的隐私表面绑定精确的左右文件路径、类型、字节长度和 SHA-256 摘要。清单声明的根必须恰好包含成对的归档清单。对于普通表面，验证器要求整个文件的大小相同，并要求 JSON 的公开结构相同。包含熵的原始环回捕获和已打包的受限源文件归档是明确的大小例外；验证器会改为比较数据包链路类型和每个数据包的长度、受限源文件标识以及固定结构的行长度。所有 Torii 请求/响应、公开/受限 P2P 数据包、区块、查询、事件、日志和遥测的流量计数也必须一致。数据包形状变化、相同大小的结构性泄漏、虚假的来源声明或未配对文件，都不能通过改写泄漏报告及其哈希来隐藏。
