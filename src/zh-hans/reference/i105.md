# I105 账户地址格式 {#i105-account-address-format}

I105 是一个法定外部文本格式 Iroha 3 `AccountId`.

它的有效负载代表了账户控制者.

它的监视器会使用链区分符识别预期网络.

使用任何一个 API,交易,许可或查询要求使用 ID 的法规账户.

I105 账户 ID 是无域名的.

一个值如 `treasury@payments.universal`是一个账户别名,而不是 I105 ID 的另一种拼写.

导出 I105 ID 不注册或资助账户.

::: warning 防止大多数整合失败的规则

- 在编码或验证地址之前,选择网络配置文件.
- 精确存储并比较规范 UTF-8 字符串。
- 保留字母大小写，且不要应用 `Unicode` 规范化。
- I105 ID 不应具有 `@domain`或 `@domain.dataspace`后音.
- 使用 Iroha SDK 或 `iroha tools address`.
- 正则表达式不是 I105 验证器。

:::

## 字面上的解剖学 {#literal-anatomy}

I105 字母有三个相邻的部分,没有分离器:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

| 部分             | 用途                                                            | 校验和覆盖范围 |
| ---------------- | ------------------------------------------------------------------ | ----------------- |
| 网络 sentinel | 将文本映射到一个 `u16` 链区分符                      | 未覆盖       |
| 有效载荷          | 规范账户控制器字节的 `base-105` 编码      | 已覆盖           |
| 校验和         | 通过 I105 字母表呈现的六个 `Bech32m` 风格 `5-bit` 值 |N/A |

有效载荷和校验和标识账户控制器。

Sentinel 选择网络上下文。

同一个控制器在 Taira 和 Minamoto 上具有相同的有效载荷和检查数量,但每个网络使用不同的领先哨兵.

解码器必须确保链区分符符合预期。

校验和无法检测 sentinel 替换。

### 网络哨兵 {#network-sentinels}

| 网络或上下文      |               链区分符 |      十六进制 | 规范 sentinel                          |
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
|Taira 公共测试网 |                            `369` |`0x0171`|`test`|
| Minamoto 公共网络 |                            `753` |`0x02f1`|`sora`|
|发展环境|                              `0` |`0x0000`|`dev`|
|任何其他 `u16`值|除了 `0`, `369`和 `753` 之外,所有|        — |`n`加上最小十数,例如 `n42` |

命名的值总是使用他们的名字哨兵.

`n00042`,`n369`, `n753`和 `n0`等表格不属于法典形式.

交易链 ID 和 I105 链区分符是单独的值.

选择终端点或链 ID 并不暗示地选择地址配置文件.

## 规范单键的例子 {#normative-single-key-example}

下面的有效载荷和 Minamoto 表单来自交叉 SDK 合规性设备.

Taira 表格适用于同一个实用载荷的 Taira 哨兵:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

常规的有效载荷始于 `02 00 01 20`:标题`0x02`,紧单键标签 `0x00`,曲线 `Ed25519` ID `0x01`和一个32字节键长度 `0x20`.

`multihash`前是输入元数据,不复制到控制器的有效载荷中.

## 用 CLI 创建和检查 IDs {#create-and-inspect-ids-with-the-cli}

对于公共网络,更喜欢一个命名的个人资料:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

在诊断地址码克行为时,正常化和比较 I105 输入:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

检查被检测到的格式,神经六合和选定的网络文本为 JSON:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

审核一个新线分隔的文件的地址编码结构,而不默认分析故障:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution CLI 验证边界

`convert`, `normalize`和`audit`命令在较低级别的 `AccountAddress`编码中运行.

它们验证 sentinel、字母表、校验和、字节长度、`CurveId`/密钥结构以及地址层的精确重新编码。

它们并未实现 `AccountId`.

它们本身并不能验证所有多标签的政策语义.

它们无法证明标头类别与控制器匹配。

在授权或持久化之前使用严格的 `AccountId` 验证。

:::

对于私人网络,使用其配置的区分符明确地与 `--network-prefix`.

当将现有地址转换成明确的文本时,还输入源为 `--expect-prefix`:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

重新编码只改变了网络环境.

它不会在目标网络上注册帐户,也不证明该控制器应该在这里重复使用.

## 编码算法 {#encoding-algorithm}

标准编码器执行以下操作:

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

领先零字节保存为零值的 `base-105` 数字.

检查总数使用`Bech32` `polymod`发电机和常量 `0x2bc830a3`.

只有检查金额的 HRP 为 ASCII 字符串 `snx`.

检查金额仅为 HRP 在地址上不打印.

检查总值的六个值在 `0..31`范围内,并通过同样的 I105 字母表格呈现为实用载荷.

### I105 字母 {#i105-alphabet}

这些105个符号是按照这个顺序排列的.

第一个行是`Bitcoin Base58`字母,包含 `0..57`数字.

第二行包含 `58..104` 数字.

在运行编码器时,连接列表.

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

字母是对 `Unicode`敏感.

确切序列使用`compatibility-width`日本 `kana`符号加上`ヰ`和`ヱ`的代码点.

不要应用 NFC、NFKC、宽度转换、大小写折叠或相似字符替换。

ASCII `0`,`O`, `I`和 `l`不是字母符号.

## 佳能账户实用负载 {#canonical-account-payload}

`base-105`实体编码了二元账户有效载荷,而不是公钥字符串,也不是 Norito JSON 对象:

```text
header:u8 || controller:variable
```

下面的所有多字节整数是未签名的,并且`big-endian`.

其中不包含域、数据空间、别名、UAID 或账户元数据字节。

### 标题字节 {#header-byte}

| 位   | 宽度 |       当前编码器输出 | 含义                      |
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |地址格式版本字段 |
| `4..3` |     2 |`0`单键, `1`多签名 |地址类|
| `2..1` |     2 |                          `1` |标准化版本字段|
| `0`    |     1 |                          `0` |预留的 `extension flag`|

目前的 V1 编码器为单键控制器发射标题 `0x02` 和为多签控器发放标题`0x0a`.

`2`和 `3`的地址类别未被分配.

`extension flag` 的 `1`被拒绝.

低级解码器可以保存其他版本和正常化比特值,并且不会独立与控制器标签进行交叉检查.

转换为 `AccountId` 并比较其规范呈现可证明当前 V1 的规范性。

### 单键控制器 {#single-key-controller}

在公共密钥的原始有效载荷最多为255字节时使用紧形式:

| 字段        |           宽度 | 值或含义         |
| ------------ | --------------: | ------------------------ |
|`tag`|一个字节|`0x00`|
|`curve`|一个字节|`CurveId`登记值 |
|`key_len`|1 字节|原始键长度|
|`public_key`|`key_len`字节 |公共钥匙的原始有效载荷|

长于255字节的键使用扩展形式:

| 字段        |           宽度 | 值或含义             |
| ------------ | --------------: | ---------------------------- |
|`tag`|1 字节|`0x02`|
|`curve`|1 字节|`CurveId`登记值 |
|`key_len`|两个字节|原密钥长度, `big-endian` |
|`public_key`|`key_len`字节 |公共钥匙的原始有效载荷|

扩展的编码不是合适于紧形式的钥匙的标准.

### 多位控制器 {#multisig-controller}

| 字段            |    宽度 | 值或含义               |
| ---------------- | -------: | ------------------------------ |
|`tag`|1 字节|`0x01`|
|`policy_version`|1 字节|目前价值 `1` |
|`threshold`|两个字节|所需的总批准重量 |
|`member_count`|两个字节|下列成员数量 |
|`members`| 可变 | 重复的成员记录        |

每个成员的记录是:

| 字段        |           宽度 | 含义                  |
| ------------ | --------------: | ------------------------ |
|`curve`|1 字节|`CurveId`登记值 |
|`weight`|两个字节|成员批准权重|
|`key_len`|两个字节|原始键长度|
|`public_key`|`key_len`字节 |公共钥匙的原始有效载荷|

有效策略至少包含一个成员，各权重为正，没有重复公钥，且阈值介于 `1` 与成员权重总和之间。

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

根据签署算法的稳定名称,零分离字节,然后是原始公钥字节来排序成员.

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

一个 I105 字母没有固定的符号长度,因为多签和后量子控制器可以很大.

### `CurveId` 注册表 {#curveid-registry}

在最后一列中,指定所需的可选 `Cargo` 功能.

按表示注册表输入没有可选的数据模型功能.

|ID|签字算法|要求的 `Cargo`特征|
| ---: | -------------------------------------------- | ------------------------ |
|  `1` |`Ed25519`| —                        |
|  `2` |`ML-DSA`| —                        |
|  `3` |`BLS12-381 normal`|`bls`|
|  `4` |`secp256k1`| —                        |
|  `5` |`BLS12-381 small`|`bls`|
| `10` |`GOST R 34.10-2012 256-bit, parameter set A`|`gost`|
| `11` |`GOST R 34.10-2012 256-bit, parameter set B`|`gost`|
| `12` |`GOST R 34.10-2012 256-bit, parameter set C`|`gost`|
| `13` |`GOST R 34.10-2012 512-bit, parameter set A`|`gost`|
| `14` |`GOST R 34.10-2012 512-bit, parameter set B`|`gost`|
| `15` |`SM2`|`sm`|

不分配的 IDs 和在接收构件中禁用的算法被拒绝.

关键有效载荷也必须对被申报的 `CurveId`所选的算法具有结构性有效性.

## 严格的 AccountId 验证和规范性 {#strict-accountid-validation-and-canonicality}

在使用预期链区分符配置 SDK 后，将输入解析为 `AccountId`，并将返回的规范呈现与去除首尾空白后的输入进行比较。

这种比较是显著的,因为解析器可以在构建 `AccountId`时正常化可解码控制器材料.

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

对于不值得信赖的字符串,符合要求的应用程序应:

1. 仅删除整个值周围允许存在的传输空白。
2. 读取 sentinel，并要求链区分符符合预期。
3. 按准确的 105 符号字母表映射其余每个 `Unicode` 符号。
4. 分离出六个校验和数字。
5. 将有效载荷数字转换回规范字节。
6. 验证这些规范字节的校验和。
7. 解析标头和控制器，并要求：
   - 精确的字段长度
   - 受支持的 `CurveId`
   - 有效的公钥
   - 没有尾随字节
   - 适用时有效的多重签名策略
8. 构建 `AccountId`。
9. 针对预期的链区分符以规范形式呈现 `AccountId`。
10. 要求与去除首尾空白后的输入 `byte-for-byte` 相等。

该应用程序的明确最终步骤 `render-and-compare` 拒绝了非最小数值哨兵,非规范控制器布局,重新排序的政策材料以及任何其他解码但不是编码器当前输出的 V1 拼写.

校验和成功或低层级 `AccountAddress` 解析不能替代此检查。

在严格的账户-ID 字段中,不要接受这些值:

- `alice@wonderland.universal`这样的帐户别名
- 一个 I105 字体,附上一个 `@domain`后音
- 一个公钥 `multihash`,如`ed0120...`
- 常规有效载荷列表 (如 `0x02000120...`)
- 一个错误的链分辨器地址
- 大写或小写字母、字符宽度、`kana`、有效载荷或校验和被更改的字符串

在应用程序边界解析别名，并保留返回的规范 I105 ID，用于授权、签名、权限和审计记录。

|代码| 含义                                                             |
| -------------------------------- | ------------------------------------------------------------------- |
|`ERR_UNEXPECTED_NETWORK_PREFIX`|解码的区分器不符合所需网络.|
|`ERR_CHECKSUM_MISMATCH`|六个检查总数符号不匹配的有效载荷|
|`ERR_INVALID_I105_CHAR`|一个符号是正确字母之外的.|
|`ERR_MISSING_I105_SENTINEL`|没有找到法典名字或数字哨兵.|
|`ERR_I105_TOO_SHORT`|尸体不能包含有效载荷和检查量.|
|`ERR_INVALID_LENGTH`|一个控制器字段是缩小的,或者使用非规范长度形式|
|`ERR_UNKNOWN_CURVE`|控制者宣布未分配或不可使用的 `CurveId` |
|`ERR_INVALID_PUBLIC_KEY`|对于其 `CurveId`所选的算法来说,关键是无效的.|
|`ERR_UNSUPPORTED_ADDRESS_FORMAT`|输入不是被接受的法典形式 I105 |

## API,存储和显示规则 {#api-storage-and-display-rules}

- 在 JSON 账户字段中发送准确的 I105 UTF-8 字符串.
- `Percent-encode`在将其置于 URL 路径段之前的完整账户 ID.
- 切勿用账户别名替代 I105 ID。
- 使用 `byte-preserving` 比较语义存储编解码器返回的规范字符串。
- 使用保留字母大小写和字符宽度的排序规则。
- 保持链区分或命名的网络配置文件,并将出口的帐户数据和备份存储.
- 仅用其网络背景重新使用地址.
- 显示完整地址,并提供复制操作.
- 保持每一个 `kana` 字符的精确.
- 如果一个紧的显示屏缩短中部时,请保持完整地址.
- 使用存储的规范 ID，而不是根据别名重新构建它。

`AccountId` 的显示和 JSON 表示使用规范 I105。

较低层级的 `AccountAddress` 显示/JSON 表示在内部和调试上下文中使用规范十六进制格式。

如果需要外部账户 ID,请电话给明确的 `AccountAddress` I105 编码器.

对于创建帐户和号解决工作流程,继续使用 [账户和名](/zh-hans/cookbook/accounts-and-aliases.md).

对于账户数据模型,请见 [账户](/zh-hans/blockchain/accounts.md).
