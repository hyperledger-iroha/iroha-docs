# 共识 {#consensus}

交易先进入队列，随后由 Sumeragi 将其纳入区块提案。验证节点分别验证并执行提案，并且只签署自己能够重现的状态转换。达到所需的验证节点法定人数、各方对结果达成一致且匹配的有效载荷可用后，区块才会提交。

所有 Iroha 3 网络都使用已签名的 RS16 数据可用性清单和分块，以及经认证的区块体恢复机制。数据可用性是共识要求，并非可选的部署功能。

## Sumeragi {#sumeragi}

Sumeragi 是 Iroha 的拜占庭容错共识引擎。它从队列中取得交易，让各验证节点对同一个有序区块达成一致，并且只在足够多的验证节点重现相同结果并签署提交证书后才最终确认该区块。

### 提案和提交路径 {#proposal-and-commit-path}

Sumeragi 每次将账本推进一个区块高度。在每个高度，当前视图由一个验证节点担任提议者。提议者从队列中取出符合条件的交易、构建候选区块，并向当前验证节点集合公布提案。

许可制部署和提名权益证明（NPoS）部署使用同一条 Sumeragi 流水线：

1. 一个验证节点根据队列中的交易提出区块。
2. 各验证节点在相同的世界状态上执行交易，以验证该提案。
3. 各验证节点交换当前高度和视图的投票及法定人数证书。
4. 达到提交法定人数后，各节点提交区块并更新各自的世界状态。

验证节点只签署能够在本地重现的数据。投票前，验证节点会检查提案是否属于预期的链、高度和视图；交易签名和限制是否有效；通道路由和执行器验证是否具有确定性；以及执行有效载荷是否产生预期的状态转换。如果本地结果不同，验证节点会拒绝提案，而不会为其投票。

投票是体积很小的已签名共识消息，其中引用了提议区块、高度、视图和验证节点身份。通过验证的签名组成 Prepare 和 Commit 法定人数证书。提交证书是持久证明，证明已有足够多的验证节点针对同一区块观察到相同结果。每个验证节点都会将 Prepare 和 Commit 投票发送给整个委员会；任何验证节点都可以聚合所需数量的相同投票，并广播生成的证书。

### 法定人数和观察节点 {#quorum-and-observers}

首个版本的协议只接受严格为 `3f + 1` 的投票委员会，验证节点数量为 4 至 31。因此，有效规模为 4、7、10，依此类推，最大为 31。对于 `n = 3f + 1`，拜占庭故障预算为 `f`，提交法定人数为 `2f + 1`。创世配置生成和启动验证会拒绝其他委员会规模。

观察节点可以同步已提交的区块，但不会提出提案、投票，也不计入提交法定人数。当部署需要本地查询容量、索引、监控或区域性区块副本，但不希望增加投票验证节点数量时，可使用观察节点。

### 视图变更和恢复 {#view-changes-and-recovery}

视图表示 Sumeragi 使用特定提议者和时序方案最终确认某一高度的一次尝试。如果提案、有效载荷、投票或提交进度停滞，节拍器可将该高度推进到后续视图。视图变更不会重写已提交的区块；它会改变验证节点完成尚未提交高度的方式，并延续已知最高的法定人数证据或提交证据，防止各节点最终确认相互冲突的区块。

有效载荷恢复与最终性决策相互独立。节点可能在取得完整区块有效载荷前收到法定人数证书或提交证书。此时，该节点会请求已签名的 RS16 有效载荷分块或经认证的区块体，对照已公布的哈希验证恢复的字节，然后才将区块应用到世界状态和 Kura。

### 共识模式 {#consensus-modes}

所选模式决定验证节点集合的组成和运行方式。模式通过已签名创世配置中的 [`consensus_mode`](/zh-hans/reference/genesis.md) 声明，并固定到每个高度的上下文中。本地 `[sumeragi]` 配置只能选择节点角色，以及区块、队列、运行时、存储和密钥策略的有限上限；它不能覆盖共识模式或出块节奏。各验证节点必须使用相同的已签名创世配置、拓扑、可信对等节点数据和有效 Sumeragi 参数。

| 模式 | 最适用的场景 | 验证节点集合 | 运维重点 |
| --- | --- | --- | --- |
| 许可制 | 私有网络、联盟网络和由运营方管理的网络 | 验证节点来自部署各方商定的可信对等节点拓扑 | 确保所有验证节点使用相同的已签名创世配置、可信对等节点、节点密钥和 Sumeragi 参数 |
| NPoS | 验证活动遵循提名和权益策略的公共网络或面向 Nexus 的网络 | 验证节点由 NPoS 配置选出，通常按 epoch 变更，并且需要 BLS 密钥和持有证明 | 在整个网络中保持权益快照、已签名的 epoch 与选举输入、验证节点 PoPs 和不可变出块节奏一致 |

::: tip 许可制模式

当验证节点名单是一项明确的运维选择时，请使用许可制模式。这通常是自行托管 Iroha 网络的起点，因为成员变更属于有意进行的治理或管理员操作。重要的运维规则是，每个验证节点都必须对创世配置、可信对等节点、BLS 持有证明和 Sumeragi 参数采用相同视图。只要有一个节点采用不同的拓扑或已签名创世配置，网络就可能无法提交区块。

:::

::: tip NPoS 模式

当部署配置要求由提名和权益状态决定验证节点参与资格时，请使用 NPoS 模式。公共 SORA Nexus 部署使用 NPoS；其生成的配置包含启动时所需的 BLS 验证节点身份、持有证明、epoch 设置和 Sumeragi NPoS 参数。epoch 变更可以在指定高度替换当前验证节点集合，因此运营方既要监控共识健康状况，也要监控决定下一份名单的权益或提名状态。

:::

## 多通道共识 {#multilane-consensus}

Iroha 通过 Nexus 通道和数据空间配置实现多通道共识路径。它不会为每条通道启动单独的共识实例。Sumeragi 仍然最终确认单一的有序区块流；通道描述该区块流内交易的路由、调度、计量和存储方式。

软件执行环境配置构建三部分执行通道状态：

- `nexus.lane_catalog`：已配置的通道；每条通道都有数值 `LaneId`、别名、数据空间、可见性、存储配置、证明方案和元数据。
- `nexus.dataspace_catalog`：已配置的数据空间；每个数据空间都有数值 `DataSpaceId`，以及用于确定中继委员会规模的容错值。
- `nexus.routing_policy`：默认通道/数据空间对，以及可匹配账户或指令路径的有序路由规则。

交易进入队列时，通道路由器会将其解析为 `RoutingDecision { lane_id, dataspace_id }`。在单通道模式下，结果始终是通道 `0` 和通用数据空间。在 Nexus 模式下，已配置的路由器依次应用数据空间范围规则、结算路由、账户规则、显式路由规则，最后应用默认路由。解析出的通道和数据空间必须存在于各自目录中，且该通道必须绑定到解析出的数据空间；否则，交易会在入队前被拒绝。

队列将该路由决策与交易哈希一并保存，因此后续阶段无需再次推断。构建提案时会以两种方式使用通道元数据：

- 按通道交错编排交易，避免某条通道仅因其交易较早入队而占据整个区块。
- 应用每条通道的交易执行单元（TEU）上限。会使通道超出配置容量的交易将被延后并重新入队；但可接纳该通道的第一笔超重交易，以避免活锁。

准备候选区块时，Sumeragi 按通道和数据空间聚合提议的有效载荷，并派生通道本地的数据可用性标识。记录的总计包括交易数、分块数、有效载荷字节数和 TEU。提交后，这些总计会成为通过经认证的 Sumeragi 诊断公开的通道和数据空间承诺快照。如果区块包含通道结算收据，区块处理还会创建通道结算承诺和中继封装，将区块头、提交证书、数据可用性承诺哈希、结算证明和通道有效载荷大小绑定在一起。

## 数据可用性和有效载荷恢复 {#data-availability-and-payload-recovery}

Sumeragi v2 通过已签名的 RS16 `PayloadManifest` 和 `PayloadChunk` 消息提供全局有效载荷可用性。领导者将已签名的清单发送给整个委员会，并先将确定性分块分发给集合 A。验证节点只有在重建规范区块体、验证清单和分块哈希、持久保存区块体并完成确定性验证后，才能投出 Prepare 票。如果快速路径停滞，恢复流程会将分块交付扩展到集合 B。当节点在收到区块体前获知最终性时，经认证的区块体恢复和区块同步会提供有界的恢复路径。

多通道执行还会为每个通道主题派生确定性的有效载荷所有权哈希和通道本地 RBC 实例哈希。这些标识将通道提案和证书绑定到全局承载交易；它们并不构成独立的全局共识会话。只有当节点在本地拥有有效的提交证书和匹配的有效载荷时，区块才会最终确认。

请使用经过认证的运营方接口，而不是单独的 RBC 端点：

- `iroha --operator-private-key-file <path> --output-format text ops sumeragi status` 报告权威的高度、视图、阶段、证书和活跃状态。
- `iroha --operator-private-key-file <path> --output-format text ops sumeragi diagnostics` 报告非权威的队列、流水线、NPoS、通道和数据空间诊断信息，包括通道有效载荷所有权。
- `sumeragi_missing_block_requests`、`sumeragi_missing_block_oldest_ms`、`sumeragi_missing_block_fetch_total`、`sumeragi_da_gate_block_total` 和 `sumeragi_da_gate_satisfied_total` 等 Prometheus 信号可区分区块体缺失恢复、数据可用性关卡和消息处理；详见[性能和指标](/zh-hans/guide/advanced/metrics.md)。

Kura 使用派生的通道配置安排存储布局。每条通道都会获得 `blocks/lane_000_core` 和 `merge_ledger/lane_000_core_merge.log` 等确定性存储名称；通道生命周期变更可以预置、停用或重新标记这些分段，而不会改变全局区块顺序。
