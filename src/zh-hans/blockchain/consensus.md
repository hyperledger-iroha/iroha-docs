# 达成共识 {#consensus}

交易进入排队之前 Sumeragi 在一个街区提出.
验证者独立验证和执行提案,然后仅签署
一个区块在要求后承诺
验证人数组同意该结果,并且可获得相应的有效载荷.

所有的 Iroha 3 网络使用数据可用性和可靠的广播路径.
它们是共识要求,而不是可选的部署功能.

## Sumeragi {#sumeragi}

Sumeragi 是 Iroha 需要一点时间,
经验者同行同意相同的订单
只有经过足够的验证器完成了该区块,
复制相同的结果并签署承诺证书.

<img :src="withBase('/sumeragi-round-dataflow.svg')" alt="Sumeragi proposal-to-commit data flow" />

### 建议和承诺途径 {#proposal-and-commit-path}

Sumeragi 在每一个高度上,
一个验证者作为目前观点的提出者.
在排队中进行可接受交易,建立一个候选区,并宣布
积极验证器组的建议.

同样的. Sumeragi 管道使用于允许和指定
证实投资 (NPoS) 的部署:

1. 一个验证者建议阻止排队交易.
2. 验证者通过执行对
   它们是世界上最重要的.
3. 验证者对当前高度进行了投票和定决权证书交换
   和景观.
4. 一旦达成委员会定位数,同行提交封锁和更新
   它们的世界状态.

验证者只签署他们可以本地复制的数据.
验证人检查该提案是否属于预期链,高度和
查看交易签名和限制是否有效;
执行器验证是决定性的;
如果本地结果不同,验证器
否决该提案,而不是投票支持.

投票是签署的小共识信息.
收藏者将这些数据集成到
通过投票,可获得定数证书或承诺证书.
持久性证明,足够的验证者对相同的结果进行了相同的测试
区块.

### 团队,收藏者和观察员 {#quorum-collectors-and-observers}

投票验证人数量 `n` 根据巴塞罗那政府的规定,
有至少四个验证器的网络,预算是 `f = floor((n - 1) / 3)`
委员会决定 `2f + 1`. 对于1至3个验证器,所有验证器
对于发展而言有用,但没有实践性.
在线放松.

而不是每一个验证器都发送了每个
投票给其他验证者, Sumeragi 可以选择一个或多个收藏器
收藏者收集投票,公布定数进展情况,
实际收藏器设置是暴露的
通过 `GET /v1/sumeragi/collectors`; 在 CLI 现在
`ops sumeragi telemetry` 快照报告了当前收藏人数.

观察者同行可以同步承诺的区块,
投票,收集票数,或计数到委员会定位.
部署需要本地查询能力,索引,监测或区域区块
投票验证者数量没有增加.

### 查看变化和恢复 {#view-changes-and-recovery}

一个景象是 Sumeragi 试图与一个特定的提议者完成一项高度
如果提议,有效负载,投票或承诺的进展停滞,
步骤仪可以将高度转移到后面的视图.
它改变了验证者试图完成未承诺的
高度,传递已知的最高定数或提交证据
没有完成冲突的区块.

收回有效载荷与最终决定分开.
在它获得完整的区块有效载荷之前,必须有定数或承诺证书.
在这种情况下,同行使用可靠的广播 (RBC) 或阻同步,以恢复
根据广告的哈希,然后才应用
封锁世界国家和 Kura.

### 共识方式 {#consensus-modes}

选择的模式控制了验证器集的形成和操作方式.
在"创世记"中,通过 [`consensus_mode`](/zh-hans/reference/genesis.md)
在同行配置中,通过 `sumeragi.consensus_mode`. 把它当作
全网络状态:验证者需要相同的签名基因,拓,
值得信赖的同行数据,有效 Sumeragi 参数.

<img :src="withBase('/sumeragi-mode-dataflow.svg')" alt="Sumeragi consensus mode data flow" />

| 模式         | 最适合的                                                                               | 验证器设置                                                                                                      | 运营重点                                                                                          |
| ------------ | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| 允许 | 私人,联盟和运营商管理的网络                                     | 验证器来自部署所同意的可靠同行拓                                            | 保持所有验证器相同的签名基因,可信的同龄人,同龄钥匙, Sumeragi 参数          |
| 公共服务局         | 公共或 Nexus- 认可后续的指名和股权政策 | 验证器由NPoS配置文件选择,通常在不同时期之间,并且需要: BLS 密钥加上所有权证明 | 存储投注快照,时代参数,验证器 PoPs, 和网络中均一致的NPoS阶段时间 |

::: tip 允许的模式

使用授权模式,当验证器列表是明确的操作
这就是自主托管的常见起点. Iroha 网络
因为会员变更是故意的治理或管理者
一个重要的操作规则是,每个验证器必须运行
同样看待创世,可信的同龄人, BLS 持有证据,以及
Sumeragi 一个具有不同的拓或签署的起源的同行
可以阻止网络承诺.

:::

::: tip NPOS模式

使用NPoS模式,当部署配置预期验证器参与时
根据提名和投资状况进行驱动. SORA Nexus 部署
使用NPoS,其生成的个人资料包括: BLS 验证器
身份证,持有证据,时代设置,以及 Sumeragi 公共服务局
时代变化可以取代活跃验证器
设置在定义的高度,因此运营商需要监控共识健康和
投注或提名状态,为下一个名单提供了食物.

:::

## 多边共识 {#multilane-consensus}

Iroha 多线共识路径通过 Nexus 路线和
它不会启动单独的共识实例
在每条车道上. Sumeragi 仍然完成一个订单的区块流;车道
描述交易的路由,安排,会计和存储方式
在河流里.

运行时间配置构建了三条车道状态:

- `lane_catalog`: 设置的车道,每个车道都有数值 `LaneId`,
  密码,数据空间,可见性,存储配置文件,证明方案以及
  其他数据.
- `dataspace_catalog`: 配置的数据空间,每个区域都有数值
  `DataSpaceId` 和继电委员会所使用的故障耐受值
  尺寸.
- `routing_policy`: 默认行径/数据空间对和顺序路由
  可以匹配账户或指令路径的规则.

当一个交易进入队列时,路线路由器将其解决为
`RoutingDecision { lane_id, dataspace_id }`. 在单轨模式下,这是
总是走路 `0` 并且是全球数据空间. Nexus 调节模式,配置
路由器应用数据空间范围规则,结算路由,账户规则
路由规则明确,最后是默认路线.
在它们的目录中必须存在数据空间,
解决的数据空间;否则交易会被拒绝之前
在排队.

排队将这个路由决定与交易哈希保持在一起,
后期阶段不必再推断.
两种方式的车道元数据:

- 交易由一条行径间隔,因此一个行线不会占主导地位
  只是因为它的交易是排队的.
- 它适用于每行业交易执行单元 (TEU) 限额交易
  超过车道配置容量的车道将被推迟和排队,
  除了允许第一次超重行车交易
  为了避免被锁定.

在可靠的广播中, Sumeragi 按车道汇总拟议的有效载荷
记录的总数包括交易数量,广播
块,有效载荷字节,以及 TEU. 在提交后,这些总数变成了车道
数据空间承诺的快照 Sumeragi 如果一个
区块包含车道结算收据,区块处理也创造了车道
结算承诺和连接包裹,绑定区块标题
承诺证书,数据可用性承诺哈希,结算证明,
车道的使用量.

## 可靠的广播 (RBC) {#reliable-broadcast-rbc}

可靠的广播 (RBC) 是 Sumeragi 有效载荷的传播和回收
它帮助验证者和观察员获得属于的块体
特别是在 `BlockCreated`
消息,区块同步更新或直接有效载荷转移延迟或丢失.

RBC 提议者宣布: RBC 一个会议
然后发送有效载荷块到整个
专业人员跟踪部分收件,验证恢复的有效载荷
与广告的哈希和交换 `READY` 并且 `DELIVER` 信号
一旦有足够的验证者观察到相同的有效载荷.
通过 TTL, 零部件,片,悬挂存储和持久存储限量
恢复流量不能无限增长.

RBC 不是单独的共识决定,也不取代承诺
一个区块仍然只有当同行有有效的承诺时完成
证书和当地相应的有效载荷. RBC 提供强制性
预计,可用性证据和有效载荷回收,而承诺的进步由
承诺证书加上本地有效载荷.
随着可用载荷,同行可以通过 RBC 或是区块同步和
然后做出承诺.

在运营方面, RBC 有助于诊断缺失有效载荷和
数据可用性瓶:

- `iroha --output-format text ops sumeragi telemetry` 显示总数
  现有收藏人数,以及未获得的票数 RBC 会议.
- `GET /v1/sumeragi/rbc` 并且 `GET /v1/sumeragi/rbc/sessions` 揭示详细信息
  总和活动会议数据 Torii, 包括部分进展,
  准备性,交付状态以及车道或数据空间后载;见
  [Torii 终点](/zh-hans/reference/torii-endpoints.md).
- 预测信号如: `sumeragi_rbc_store_pressure`,
  `sumeragi_rbc_backpressure_deferrals_total`, 和每条车道或
  每个数据空间 RBC 后载计量有助于分离网络损失,
  恢复和储存压力;见
  [绩效和指标](/zh-hans/guide/advanced/metrics.md).

Kura 使用衍生的车道配置用于存储布局.
收到确定性存储名称,如 `blocks/lane_000_core` 并且
`merge_ledger/lane_000_core_merge.log`; 车道生命周期的变化可能
提供,退休或重新标记这些细分
封锁命令.
