# 共识 {#consensus}

交易先进入队列，随后由 Sumeragi 将其纳入区块提案。验证节点分别验证并执行提案，并且只签署自己能够重现的状态转换。达到所需的验证节点法定人数、各方对结果达成一致且匹配的有效载荷可用后，区块才会提交。

所有 Iroha 3 网络都使用已签名的 RS16 数据可用性清单和分块，以及经认证的区块体恢复机制。数据可用性是共识要求，并非可选的部署功能。

## Sumeragi {#sumeragi}

Sumeragi 是 Iroha 的拜占庭容错共识引擎。它从队列中取得交易，让各验证节点对同一个有序区块达成一致，并且只在足够多的验证节点重现相同结果并签署提交证书后才最终确认该区块。

### 提案和提交路径 {#proposal-and-commit-path}

Sumeragi 每次将区块链账本向前推进一个区块高度。在每个高度上，一个验证者作为当前视图的提议者。提议者从队列中提取符合条件的交易，构建候选区块，并向活跃验证者集合宣布提议。空闲链不会生成空区块。

许可制部署和提名权益证明（NPoS）部署使用同一条 Sumeragi 流水线：

1. 一个验证节点根据队列中的交易提出区块。
2. 各验证节点在相同的世界状态上执行交易，以验证该提案。
3. 各验证节点交换当前高度和视图的投票及法定人数证书。
4. 达到提交法定人数后，各节点提交区块并更新各自的世界状态。

验证节点只签署能够在本地重现的数据。投票前，验证节点会检查提案是否属于预期的链、高度和视图；交易签名和限制是否有效；通道路由和执行器验证是否具有确定性；以及执行有效载荷是否产生预期的状态转换。如果本地结果不同，验证节点会拒绝提案，而不会为其投票。

投票是体积很小的已签名共识消息，其中引用了提议区块、高度、视图和验证节点身份。通过验证的签名组成 Prepare 和 Commit 法定人数证书。提交证书是持久证明，证明已有足够多的验证节点针对同一区块观察到相同结果。每个验证节点都会将 Prepare 和 Commit 投票发送给整个委员会；任何验证节点都可以聚合所需数量的相同投票，并广播生成的证书。

### 法定人数和观察节点 {#quorum-and-observers}

首个版本的协议只接受恰好由 `3f + 1` 个投票验证者组成的委员会，总人数为 4 至 31。因此有效人数为 4、7、10，依此类推，直到 31。对于 `n = 3f + 1`，可容忍的拜占庭故障数为 `f`，提交法定票数为 `2f + 1`。创世生成和启动校验会拒绝其他委员会规模。每份 PrepareQC、CommitQC 和 TimeoutCert 都必须恰好携带 `q = n - f` 张等权验证者选票；超过该人数的签名者集合也会被拒绝。

观察节点可以同步已提交的区块，但不会提出提案、投票，也不计入提交法定人数。当部署需要本地查询容量、索引、监控或区域性区块副本，但不希望增加投票验证节点数量时，可使用观察节点。

### 视图变更和恢复 {#view-changes-and-recovery}

视图表示 Sumeragi 使用特定提议者和时序方案最终确认某一高度的一次尝试。如果提案、有效载荷、投票或提交进度停滞，节拍器可将该高度推进到后续视图。视图变更不会重写已提交的区块；它会改变验证节点完成尚未提交高度的方式，并延续已知最高的法定人数证据或提交证据，防止各节点最终确认相互冲突的区块。

有效载荷恢复与最终性决策相互独立。节点可能在取得完整区块有效载荷前收到法定人数证书或提交证书。此时，该节点会请求已签名的 RS16 有效载荷分块或经认证的区块体，对照已公布的哈希验证恢复的字节，然后才将区块应用到世界状态和 Kura。

### 共识模式 {#consensus-modes}

所选模式决定验证者集合的组成和运作方式。它通过已签名创世配置中的 [`consensus_mode`](/zh-hans/reference/genesis.md) 声明，并固定在每个高度的上下文中。本地 `[sumeragi]` 配置决定节点角色、签名密钥保管、安全记录路径，以及文档规定的超时和同步覆盖项。区块与交易限制、共识模式和节奏来自已签名创世配置及已提交状态。验证者需要相同的已签名创世配置、拓扑、可信对等节点数据和实际生效的 Sumeragi 参数。

| 模式 | 最适用的场景 | 验证节点集合 | 运维重点 |
| --- | --- | --- | --- |
| 许可制 | 私有网络、联盟网络和由运营方管理的网络 | 验证节点来自部署各方商定的可信对等节点拓扑 | 确保所有验证节点使用相同的已签名创世配置、可信对等节点、节点密钥和 Sumeragi 参数 |
| NPoS | 验证活动遵循提名和权益策略的公共网络或面向 SORA Nexus 的网络 | 验证节点由 NPoS 配置选出，通常按 epoch 变更，并且需要 BLS 密钥和持有证明 | 在整个网络中保持权益快照、已签名的 epoch 与选举输入、验证节点 PoPs 和不可变出块节奏一致 |

::: tip 许可制模式

当验证节点名单是一项明确的运维选择时，请使用许可制模式。这通常是自行托管 Iroha 网络的起点，因为成员变更属于有意进行的治理或管理员操作。重要的运维规则是，每个验证节点都必须对创世配置、可信对等节点、BLS 持有证明和 Sumeragi 参数采用相同视图。只要有一个节点采用不同的拓扑或已签名创世配置，网络就可能无法提交区块。

:::

::: tip NPoS 模式

当部署配置要求由提名和权益状态决定验证节点参与资格时，请使用 NPoS 模式。公共 SORA Nexus 部署使用 NPoS；其生成的配置包含启动时所需的 BLS 验证节点身份、持有证明、epoch 设置和 Sumeragi NPoS 参数。epoch 变更可以在指定高度替换当前验证节点集合，因此运营方既要监控共识健康状况，也要监控决定下一份名单的权益或提名状态。

:::

## 多通道共识 {#multilane-consensus}

数据空间为数据、授权、策略和应用提供环境，其执行通道增加传播和认证容量。两个目录彼此独立：`nexus.dataspace_catalog` 定义数据空间；`nexus.lane_catalog` 定义执行通道，每条通道引用一个数据空间。多条执行通道可以共用同一数据空间。

对于公开的全局执行，执行通道 `0` 由全局 Sumeragi 实例排序。其余每个活跃执行通道世代均以固定的委员会和共识参数运行同一 Sumeragi 核心的独立实例。其认证区块包含有序交易批次，批次须依据已提交的全局锚点通过准入检查。执行通道认证不会修改全局 State。

全局链合并各执行通道接下来连续的认证区块。执行生成的全局区块时，这些交易按规范顺序应用，并由全局 CommitQC 确立该执行的最终性。因此，单凭执行通道证书不足以断言交易已改变全局 State。在恢复和执行全过程中，仍须检查执行通道身份、世代、锚点时效、源数据保管和连续合并前沿。

已提交的 `sumeragi_lane_policy` 管理固定执行通道、路由、委员会和自动扩缩容。仅有配置目录不会激活共识执行通道。具体数据空间目标必须解析到已获准且匹配的执行通道；不可用的私有路由会被拒绝，不会改为通用空间工作执行。完整的控制平面批次经执行通道 `0` 路由，以使目录和激活状态变更得以推进。

独立签名的数据空间根构成独立执行边界，拥有自己的 State 和本地最终性。注册数据空间目录条目并不会创建该根。跨根原子性由独立的 AMX 协议实现。在固定版本的候选实现中，该路径的货币级及整网资格验证仍未完成。

请参阅固定版本的[执行通道实现](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/crates/iroha_core/src/sumeragi/lanes/mod.rs)、[执行通道协议约定](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/specs/sumeragi_lanes.md)、[独立数据空间协议约定](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/specs/sumeragi.md)及[资格验证状态](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/specs/sumeragi_goals.md)。

## 数据可用性和有效载荷恢复 {#data-availability-and-payload-recovery}

Sumeragi V1 通过已签名的 RS16 `PayloadManifest` 和 `PayloadChunk` 消息提供全局载荷可用性。领导者将签名清单发送给全体委员会，并首先向集合 A 分发确定性分块。验证者只有在重建规范区块体、验证清单与分块哈希、持久保存区块体并完成确定性校验之后，才能投出 Prepare 票。若快速路径停滞，恢复过程会将分块分发范围扩展到集合 B。当对等节点先得知最终性、后收到区块体时，认证区块体恢复和区块同步提供有界恢复路径。

每个执行通道实例使用自己的经过认证的可用性和证书上下文。全局合并检查将其认证批次和原始载荷绑定到预期世代及锚点。只有匹配的全局载荷和有效的 CommitQC 均已在本地可用时，对等节点才应用全局最终性。

请使用经过认证的运营方接口，而不是单独的 RBC 端点：

- `iroha --operator-private-key-file <path> --output-format text ops sumeragi status` 报告权威的高度、视图、阶段、证书和活跃状态。
- `iroha --operator-private-key-file <path> --output-format text ops sumeragi diagnostics` 报告不作为权威依据的队列、流水线、NPoS、执行通道和数据空间诊断信息，包括执行通道载荷所有权。
- `sumeragi_missing_block_requests`、`sumeragi_missing_block_oldest_ms`、`sumeragi_missing_block_fetch_total`、`sumeragi_da_gate_block_total` 和 `sumeragi_da_gate_satisfied_total` 等 Prometheus 信号可区分区块体缺失恢复、数据可用性关卡和消息处理；详见[性能和指标](/zh-hans/guide/advanced/metrics.md)。

执行通道的区块存储保留合并和恢复所需的认证批次及源记录。其生命周期遵循已提交的执行通道世代；存储目录名称不会授权新的执行通道或执行根。
