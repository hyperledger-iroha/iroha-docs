# I105 Hisobvaraq manzili shakli {#i105-account-address-format}

I105 - Iroha 3 `AccountId` uchun kanonik tashqi matn formatidir.

Uning foydali yuklanishi hisobni nazorat qiluvchi shaxsni ifodalaydi.

Uning sentinelli maqsadli tarmoqni zanjir farqlovchi bilan aniqlaydi.

Uni API, tranzaksiya, ruxsat yoki so'rov ID uchun kanonik hisobni so'ragan har qanday joyda ishlating.

I105 hisob raqami ID domensiz hisoblanadi.

Misol uchun: `treasury@payments.universal` hisobning aliasi bo'lib, uning boshqa sozlanishi emas I105 ID.

I105 ID'ni hosil qilish hisobni ro‘yxatdan o‘tkazmaydi va uni moliyalashtirmaydi.

::: warning Integratsiya muvaffaqiyatsizligining aksariyatini oldini oladigan qoidalar

- Manzilni kodlashdan yoki tasdiqlashdan oldin tarmoq profilini tanlang.
- Kanonik UTF-8 qatorini to'g'ri saqlash va solishtirish.
- Yozuv holatini saqlab qolish va `Unicode` normalizatsiyasini qo'llamaslik.
- I105 ID `@domain` yoki `@domain.dataspace` suffixlariga ega bo'lmasligi kerak.
- Iroha SDK yoki `iroha tools address` raqamidan foydalaning.
- Regex I105 validatori emas.

:::

## Kalomli anatomiya {#literal-anatomy}

I105 matnida uchta qo'shni qism va ajratib bo'lmaydigan qismlar bor:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

| Qism             | Maqsad                                                            | Tekshiruv summasi qamrovi |
| ---------------- | ------------------------------------------------------------------ | ----------------- |
| Tarmoq sentineli | Matnni bitta `u16` zanjir diskriminantiga moslaydi                      | Qamrab olinmagan       |
| Foydali yuk          | Kanonik hisob boshqaruvchisi baytlarining `base-105` kodlanishi      | Qamrab olingan           |
| Tekshiruv summasi         | I105 alifbosi orqali ifodalangan `Bech32m` uslubidagi oltita `5-bit` qiymat |N/A |

Faydali yuk va chek summasi hisobni nazorat qiluvchi shaxsni aniqlaydi.

Sentinel tarmoq kontekstini tanlaydi.

Bir xil boshqaruvchining Taira va Minamoto tarmoqlarida bir xil faydali yuklama va tekshiruv summasi mavjud, ammo har bir tarmoq turlicha etakchi sentineldan foydalanadi.

Dekoder kutilgan diskriminantni majburiy tekshirishi kerak.

Tekshiruv summasi sentinel almashtirilganini aniqlay olmaydi.

### Tarmoq sentinellari {#network-sentinels}

| Tarmoq yoki kontekst      |               Zanjir diskriminanti |      Hex | Kanonik sentinel                          |
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
|Taira ommaviy test tarmog'i|                            `369` |`0x0171` |`test` |
|Minamoto ochiq tarmoqlari |                            `753` |`0x02f1` |`sora` |
|Taraqqiyot konteksti |                              `0` |`0x0000` |`dev` |
|Boshqa har qanday `u16` qiymati |Hammasi `0`, `369` va `753` dan tashqari|        — |`n` qo'shimcha minimal o'nlik, masalan, `n42` |

Nomli qiymatlar uchun har doim ularning nomli sentineli ishlatiladi.

`n00042`, `n369`, `n753` va `n0` kabi shakllar kanonik emas.

Transaksiya zanjirining ID va I105 zanjirning farqlovchi qismlari alohida qiymat hisoblanadi.

Endpoint yoki zanjir ID sini tanlash manzil profilini avtomatik ravishda tanlamaydi.

## Normativ bir kalitli misol {#normative-single-key-example}

Quyidagi foydali yuk va Minamoto shakli SDK-lararo muvofiqlik sinov ma’lumotidan olingan.

Taira shakli ayni shu foydali yukga Taira sentinelini qo‘llaydi:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

Kanonik faydali yuk `02 00 01 20`: sarlavha `0x02`, kompakt bir kalit tag `0x00`, `Ed25519` egri ID `0x01` va 32-baytli kalit uzunligi `0x20` bilan boshlanadi.

`multihash` prefiksi kirish metadatalar hisoblanadi va nazoratchi faydali yukga nusxa ko'rsatilmaydi.

## Yaratish va tekshirish IDs bilan CLI {#create-and-inspect-ids-with-the-cli}

Ommaviy tarmoq uchun nomli profilni afzal koʻrish:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

Manzil-kodek xatti-harakatini tashxislashda I105 kirish qismini normallashtirish va taqqoslash:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

Tanlangan formatni, kanonik hexni va tanlangan tarmoq kontekstini JSON sifatida tekshirish:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

Yangi satrlar bilan ajratilgan faylning manzil-kodek tuzilishini tekshirib ko'rish, tahlil xatolarini xotirjamlik bilan qabul qilmasdan:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution CLI tasdiqlash chegarasi

`convert`, `normalize` va `audit` buyruqlari past darajadagi `AccountAddress` kodekda ishlaydi.

Ular sentinel, alifbo, tekshiruv summasi, bayt uzunliklari, `CurveId`/kalit tuzilishi va manzil qatlamining aynan qayta kodlanishini tekshiradi.

Ular `AccountId` obyektini hosil qilmaydi.

Ular o'z-o'zidan barcha multisig siyosat semantikalarini tasdiqlamaydi.

Ular sarlavha sinfi boshqaruvchiga mos kelishini isbotlamaydi.

Avtorizatsiya yoki doimiy saqlashdan oldin qat’iy `AccountId` tekshiruvidan foydalaning.

:::

Xususiy tarmoq uchun uning konfiguratsiyalangan farqlovchi qismidan `--network-prefix` bilan aniq foydalaning.

Ma'lum manzilni aniq kontekstlar o'rtasida aylantirishda, manbaga `--expect-prefix` bilan ham kiriting:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

Qayta kodlash faqat tarmoq kontekstini o'zgartiradi.

U maqsadli tarmoqdagi hisobni ro'yxatga olmaydi yoki u erda bir xil nazoratchi qayta ishlatilishi kerakligini isbotlamaydi.

## Kodlash algoritmi {#encoding-algorithm}

Kanonik kodlash uskunalari quyidagi operatsiyalarni bajaradi:

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

Avvalgi nol baytlar nol qiymatli `base-105` raqamlar sifatida saqlanadi.

Tekshiruv summasida `Bech32` `polymod` generatorlari va doimiy `0x2bc830a3` ishlatiladi.

Tekshirish summasi HRP faqat ASCII satr `snx` hisoblanadi.

Faqat checksum HRP manzilda bosib chiqarilmaydi.

Olti nazorat summasi qiymatlari `0..31` doirasida bo'lib, foydali yuk bilan bir xil I105 alifbosida ko'rsatilgan.

### I105 alifboshi {#i105-alphabet}

105 ta ramz aynan shu tartibda ko'rsatilgan.

Birinchi qator `Bitcoin Base58` alifbosidir va `0..57` raqamlarini o'z ichiga oladi.

Ikkinchi qatorda `58..104` raqamlari mavjud.

Kodekni amalga oshirayotganda satrlarni qo'shing.

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

Alifbo `Unicode` kod nuqtalarini aynan farqlaydi.

Aniq ketma-ketlik `compatibility-width` formatidagi yapon `kana` belgilaridan hamda `ヰ` va `ヱ` uchun ko‘rsatilgan aynan shu kod nuqtalaridan foydalanadi.

NFC, NFKC, kenglik konvertatsiyasi, registrni birxillashtirish yoki o‘xshash belgi bilan almashtirishni qo‘llamang.

ASCII `0`, `O`, `I` va `l` alifbo belgilari emas.

## Canonik hisobning foydali yuklanishi {#canonical-account-payload}

`base-105` tanasi ochiq kalit satrini yoki Norito JSON obyektini emas, ikkilik hisob foydali yukini kodlaydi:

```text
header:u8 || controller:variable
```

Quyidagi barcha ko'p baytli to'liq sonlar imzolanmagan va `big-endian`.

Domain, ma’lumotlar makoni, alias, UAID va hisob metadata baytlari mavjud emas.

### Sarlavha byti {#header-byte}

|Bitlar |Kenglik |Dastlabki kodlash vositasi |Maʼnosi |
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |Manzil formatidagi versiya maydoni |
| `4..3` |     2 |`0` bitta kalit, `1` ko'p nishonli |Manzil sinflari |
| `2..1` |     2 |                          `1` |Normallashtirish versiyasi maydoni |
| `0`    |     1 |                          `0` | Zaxiralangan `extension flag`    |

Joriy V1 kodlovchilar bir xil kalitli nazoratchi uchun `0x02` va ko'p nishonli boshqaruvchi uchun `0x0a` sarlavhasini chiqarishadi.

Manzil sinflari `2` va `3` bo'yicha belgilanmagan.

`extension flag` qiymati `1` bo‘lsa, u rad etiladi.

Quyi darajadagi dekoder boshqa versiya va normallashtirish bit qiymatlarini saqlab qolishi mumkin, ammo sinfni boshqaruvchi tegi bilan mustaqil ravishda o‘zaro tekshirmaydi.

`AccountId` ga aylantirish va uning kanonik ko‘rinishini taqqoslash joriy V1 kanonikligini tasdiqlaydi.

### Bir xil kalitli nazoratchi {#single-key-controller}

Umumiy kalitning xom fayzli yuklari eng ko'p 255 byt bo'lganda kompakt shakldan foydalanish:

|Maydon |Kenglik |Qiymat yoki ahamiyat |
| ------------ | --------------: | ------------------------ |
|`tag` |          1 bayt |`0x00` |
|`curve` |          1 bayt |`CurveId` ro'yxat qiymati |
|`key_len` |          1 bayt | Xom kalit uzunligi           |
|`public_key` | `key_len` bayt | Ochiq kalitning xom foydali yuki   |

255 bytdan ortiq bo'lgan kalitlar kengaytirilgan shakldan foydalanadi:

|Maydon |Kenglik |Qiymat yoki ahamiyat |
| ------------ | --------------: | ---------------------------- |
|`tag` |          1 bayt |`0x02` |
|`curve` |          1 bayt |`CurveId` ro'yxat qiymati |
|`key_len` |         2 bayt | Xom kalit uzunligi, `big-endian` |
|`public_key` | `key_len` bayt | Ochiq kalitning xom foydali yuki       |

Uzoq kodifikatsiya kompakt shaklga mos keladigan kalit uchun kanonik emas.

### Ko'psig'li boshqaruvchi {#multisig-controller}

|Maydon |Kenglik |Qiymat yoki ahamiyat |
| ---------------- | -------: | ------------------------------ |
|`tag` |   1 bayt |`0x01` |
|`policy_version` |   1 bayt |Joriy qiymat `1` |
|`threshold` |  2 bayt |Talab qilingan umumiy ruxsat etish og ' irligi |
|`member_count` |  2 bayt |Quyidagi aʼzolarning soni |
|`members` |O ' zgaruvchi |Takrorlangan aʼzolar roʻyxatlari |

Har bir a'zo rekordi quyidagilardan iborat:

|Maydon |Kenglik |Maʼnosi |
| ------------ | --------------: | ------------------------ |
|`curve` |          1 bayt |`CurveId` ro'yxat qiymati |
|`weight` |         2 bayt | A’zoning tasdiqlash vazni   |
|`key_len` |         2 bayt | Xom kalit uzunligi           |
|`public_key` | `key_len` bayt | Ochiq kalitning xom foydali yuki   |

Yaroqli siyosatda kamida bitta a’zo, musbat vaznlar va takrorlanmagan ochiq kalitlar bo‘lishi, chegara qiymati esa `1` dan a’zolar vaznlari yig‘indisigacha bo‘lishi kerak.

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

Kanonik tuzilish a’zolarni avval imzolash algoritmining barqaror nomi, keyin nol ajratuvchi bayt va undan so‘ng xom ochiq kalit baytlari bo‘yicha saralaydi.

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

I105 literalda belgilar uzunligi belgilangan emas, chunki multisig va post-quantum boshqaruvchilari katta bo'lishi mumkin.

## Qat’iy AccountId tekshiruvi va kanoniklik {#strict-accountid-validation-and-canonicality}

SDK'ni kutilgan zanjir diskriminanti bilan sozlagach, qiymatni `AccountId` sifatida tahlil qiling va qaytarilgan kanonik ko‘rinishni chetki bo‘shliqlari olib tashlangan kirish bilan taqqoslang.

Taqqoslash muhimdir, chunki parser `AccountId`ni qurishda dekodlash mumkin bo'lgan nazoratchi materialini normallashtirishi mumkin.

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

Ishonchsiz satr uchun talablarga mos ilova quyidagilarni bajarishi kerak:

1. Faqat to‘liq qiymatning boshi va oxiridagi ruxsat etilgan transport bo‘shliqlarini olib tashlang.
2. Sentinelni o‘qing va kutilgan zanjir diskriminantini talab qiling.
3. Qolgan har bir `Unicode` belgisini aniq 105 belgili alifbo bo‘yicha xaritalang.
4. Tekshiruv summasining olti raqamini ajrating.
5. Foydali yuk raqamlarini qayta kanonik baytlarga aylantiring.
6. Shu kanonik baytlar bo‘yicha tekshiruv summasini tekshiring.
7. Sarlavha va boshqaruvchini tahlil qilib, quyidagilarni talab qiling:
   - maydonlarning aniq uzunliklari
   - qo‘llab-quvvatlanadigan `CurveId`
   - yaroqli ochiq kalit
   - oxirida ortiqcha baytlar yo‘qligi
   - tegishli holatda yaroqli multisig siyosati
8. `AccountId` yarating.
9. `AccountId` obyektini kutilgan diskriminant uchun kanonik tarzda ifodalang.
10. Chetki bo‘shliqlari olib tashlangan kirish bilan `byte-for-byte` tenglikni talab qiling.

Talabning aniq oxirgi `render-and-compare` bosqichi minimal bo'lmagan raqamli sentinellarni, kanonik bo'lmagan nazoratchi layoutlarini, qayta tartibga solingan siyosat materialini va kodlash vositasining hozirgi V1 chiqarilishi bo'lmagan har qanday boshqa sozlamalarni rad etadi.

Muvaffaqiyatli checksum yoki past darajadagi `AccountAddress` tahlil ushbu tekshiruvning o'rniga emas.

Ushbu qiymatlarni qat'iy hisob-ID sohasi bo'yicha qabul qilmang:

- `alice@wonderland.universal` kabi hisobning aliasi
- oxiriga `@domain` suffiksi qo‘shilgan I105 literali
- `multihash` kabi ochiq kalitli `ed0120...`
- `0x02000120...` kabi kanonik fayzli yuk hexlari
- noto'g'ri zanjirni ajratish uchun manzil
- katta yoki kichik harflar, belgilar kengligi, `kana`, foydali yuk yoki chek summasi o'zgartirilgan satr

Ilova chegaralarida aliaslarni hal qilish va ruxsatnoma, imzo, ruxsatnomalar va audit yozuvlari uchun qaytarib berilgan kanonik I105 ID ni saqlash.

## API, saqlash va ko'rsatish qoidalari {#api-storage-and-display-rules}

- JSON hisob maydonlarida aynan I105 UTF-8 satrini yuboring.
- `Percent-encode` to'liq hisob raqami ID uni URL yo'nalishidagi segmentga joylashtirishdan oldin.
- Hech qachon I105 ID o‘rniga hisob aliasini ishlatmang.
- Kodek tomonidan qaytarilgan kanonik satrni `byte-preserving` taqqoslash semantikasi bilan saqlang.
- Harf registri va belgi kengligini saqlaydigan kollatsiyadan foydalaning.
- Zanjir diskriminantini yoki nomlangan tarmoq profilini eksport qilingan hisob ma’lumotlari va zaxira nusxalari bilan birga saqlang.
- Manzilni faqat uning tarmoq konteksti bilan qayta ishlating.
- To'liq manzilni ko'rsating va nusxa ko'rsating.
- Har bir `kana` belgisini aynan saqlang.
- Kompakt ekran o'rta qismini qisqartirganida, to'liq manzilni saqlang.
- Uni aliasdan qayta qurishning o'rniga saqlangan kanonik ID dan foydalaning.

`AccountId` ko'rinishi va JSON qo'llanmasi kanonik I105.

Pastki darajadagi `AccountAddress` ko'rsatuv/JSON ifoda ichki va debug kontekstlari uchun kanonik hexdan foydalanadi.

Agar tashqi hisob qaydnomasi ID kerak bo'lsa, aniq `AccountAddress` I105 kodlovchiga murojaat qiling.

Hisoblarni yaratish va aliaslarni hal qilish ish oqimlari uchun [Hisoblar va aliaslar ](/uz/cookbook/accounts-and-aliases.md) bilan davom eting.

Hisobot ma'lumotlari modeli uchun [Hisobotlar](/uz/blockchain/accounts.md)-ni ko'ring.
