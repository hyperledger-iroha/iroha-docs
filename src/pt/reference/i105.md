# Formatos de endereço da conta I105 {#i105-account-address-format}

O I105 é o formato de texto externo canônico para um Iroha 3 `AccountId`.

A sua carga útil representa o controlador da conta.

O seu sentinela identifica a rede prevista com um discriminante de cadeia.

Usá-lo em qualquer lugar que uma API, transação, permissão ou consulta peça uma conta canônica ID.

Uma conta I105 ID é sem domínio.

Um valor como `treasury@payments.universal` é um alias de conta e não outra ortografia do I105 ID.

A dedução de um I105 ID não registra nem financia a conta.

::: warning As regras que prevêem a maior parte das falhas de integração

- Selecione o perfil da rede antes de codificar ou validar um endereço.
- Armazenar e comparar exatamente a cadeia canónica UTF-8.
- Preserve exatamente o uso de maiúsculas e minúsculas e não aplique normalização `Unicode`.
- Um I105 ID não deve ter um sufixo `@domain` ou `@domain.dataspace`.
- Usar um Iroha SDK ou `iroha tools address`.
- Uma expressão regular não é um validador I105.

:::

## Anatomia literal {#literal-anatomy}

Uma letra I105 contém três partes adjacentes e sem separador:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

|Parte |Propósito |Cobertura da soma de cheques |
| ---------------- | ------------------------------------------------------------------ | ----------------- |
|Sentinela de rede |Mapa do texto para um discriminante de cadeia `u16` |Não coberto |
|Carga útil .|`base-105` codificação dos bytes canônicos do controlador de contas |Coberto .|
|Checksum |Seis valores de estilo `Bech32m` `5-bit` representados com o alfabeto I105 |N/A |

A carga útil e a soma de cheques identificam o responsável pelo controlo da conta.

O sentinela seleciona o contexto da rede.

O mesmo controlador tem a mesma carga útil e quantidade de verificação em Taira e Minamoto, mas cada rede utiliza um sentinela principal diferente.

Um decodificador deve impor o discriminante esperado.

A soma de verificação não pode detectar uma substituição do sentinela.

### Sentinelas de rede {#network-sentinels}

|Rede ou contexto |Discriminante de cadeia |Hex |Sentinela canônica .|
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
|Taira rede pública de teste |                            `369` |`0x0171` |`test` |
|Minamoto rede pública |                            `753` |`0x02f1` |`sora` |
|Contexto de desenvolvimento |                              `0` |`0x0000` |`dev` |
|Qualquer outro valor `u16` |Todas, exceto `0`, `369` e `753` |        — |`n` mais um decimal mínimo, por exemplo `n42` |

Os valores nomeados usam sempre o seu sentinela.

Formulários como `n00042`, `n369`, `n753` e `n0` não são canônicos.

A cadeia de transações ID e o elemento discriminante da cadeia I105 são valores separados.

A escolha de um ponto final ou cadeia ID não implica implícitamente a escolha do perfil de endereço.

## Exemplo normativo de chave única {#normative-single-key-example}

A carga útil e o formulário Minamoto abaixo provêm da fixação de conformidade cruzada SDK.

O formulário Taira aplica-se a sentinela do Taira à mesma carga útil:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

A carga útil canónica começa com: `02 00 01 20`: Título `0x02`, Tag compacto de tecla única `0x00`, `Ed25519` Curva ID `0x01`, e um comprimento de chave de 32 bytes `0x20`.

O prefixo `multihash` é um metadados de entrada e não é copiado na carga útil do controlador.

## Criar e inspecionar a IDs com o CLI {#create-and-inspect-ids-with-the-cli}

Preferir um perfil de nome para uma rede pública:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

Normalizar e comparar uma entrada I105 ao diagnosticar o comportamento de endereço-codec:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

Inspectar o formato detectado, o hexágono canônico e o contexto da rede selecionado como JSON:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

Auditar a estrutura de endereço-codec de um arquivo separado por linha nova sem aceitar silenciosamente falhas de análise:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution Limite de validação CLI

Os comandos `convert`, `normalize` e `audit` operam no codec de nível inferior `AccountAddress`.

Verificam a sentinela, o alfabeto, a soma de verificação, os longos bytes, a forma `CurveId`/chave e a recodificação exata da camada de endereços.

Não se materializam em `AccountId`.

Não validam, por si só, todas as semânticas de políticas multisig.

Não provam que a classe de cabeçalhos coincida com o controlador.

Utilize a validação rigorosa `AccountId` antes da autorização ou da persistência.

:::

Para uma rede privada, utilizar explicitamente o seu discriminante configurado com `--network-prefix`.

Ao converter um endereço existente entre contextos explícitos, insira também a fonte com `--expect-prefix`:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

A recodificação altera apenas o contexto da rede.

Não regista a conta na rede-alvo nem demonstra que o mesmo controlador deve ser reutilizado lá.

## Algoritmo de codificação {#encoding-algorithm}

Os codificadores canônicos executam as seguintes operações:

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

Os bytes zero-leading são preservados como dígitos de valor zero `base-105`.

A soma de verificação utiliza os geradores `Bech32` `polymod` e a constante `0x2bc830a3`.

A única soma de verificação HRP é a cadeia ASCII `snx`.

O cheque somente HRP não é impresso no endereço.

Os seis valores de checksum estão na faixa `0..31` e são representados através do mesmo alfabeto I105 que a carga útil.

### Alfabeto I105 {#i105-alphabet}

Os 105 símbolos são indexados nessa ordem exata.

A primeira linha é o `Bitcoin Base58` alfabeto e contém os dígitos `0..57`.

A segunda linha contém os dígitos `58..104`.

Concatenar as linhas ao implementar o codec.

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

O alfabeto é sensível a `Unicode`.

A seqüência exacta utiliza os símbolos japoneses `kana` `compatibility-width` mais os pontos de código indicados para `ヰ` e `ヱ`.

Não aplique NFC, NFKC, conversão de largura, dobramento de maiúsculas/minúsculas ou substituição por caracteres visualmente semelhantes.

ASCII `0`, `O`, `I`, e `l` Não são símbolos do alfabeto.

## Carga útil da conta canónica {#canonical-account-payload}

O corpo `base-105` codifica uma carga útil de conta binária, não uma cadeia de chave pública e não um objeto Norito JSON:

```text
header:u8 || controller:variable
```

Todos os números inteiros de múltiplos bytes abaixo não são assinados e `big-endian`.

Não há domínio, espaço de dados, alias, UAID e bytes de metadados da conta.

### Byte de cabeçalho {#header-byte}

|Bites .|Largura |A saída do codificador de corrente |Que significa ?|
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |Campo de versão em formato de endereço |
| `4..3` |     2 |`0` chave única, `1` múltipla sigla |Classe de endereços |
| `2..1` |     2 |                          `1` |Campo de versão de normalização |
| `0`    |     1 |                          `0` |Reservados `extension flag` |

Os codificadores atuais V1 emitem cabeçalho `0x02` para um controlador de chave única e `0x0a` para um controlador multisig.

As classes de endereços `2` e `3` não são designadas.

Um `extension flag` de `1` é rejeitado.

O decodificador de baixo nível pode preservar outros valores de bits de versão e normalização e não verifica independentemente a classe contra a etiqueta do controlador.

A conversão para um `AccountId` e a comparação da sua tradução canônica provam a canonicalidade atual do V1.

### Controlador de tecla única {#single-key-controller}

Usar a forma compacta quando a carga útil de chave pública é máxima de 255 bytes:

|Campo |Largura |Valor ou significado |
| ------------ | --------------: | ------------------------ |
|`tag` |1 byte |`0x00` |
|`curve` |1 byte |Valor do registo `CurveId` |
|`key_len` |1 byte |Comprimento da chave bruta |
|`public_key` |`key_len` bytes |Carga útil de chaves públicas .|

Chaves com mais de 255 bytes usam a forma alargada:

|Campo |Largura |Valor ou significado |
| ------------ | --------------: | ---------------------------- |
|`tag` |1 byte |`0x02` |
|`curve` |1 byte |Valor do registo `CurveId` |
|`key_len` |2 bytes |Comprimento da chave bruta, `big-endian` |
|`public_key` |`key_len` bytes |Carga útil de chaves públicas .|

Uma codificação estendida não é canônica para uma chave que se encaixa na forma compacta.

### Controlador multisig {#multisig-controller}

|Campo |Largura |Valor ou significado |
| ---------------- | -------: | ------------------------------ |
|`tag` |1 byte |`0x01` |
|`policy_version` |1 byte |Valor atual `1` |
|`threshold` |2 bytes |Peso total de aprovação exigido |
|`member_count` |2 bytes |Número dos seguintes membros |
|`members` |Variavel .|Registros de membros repetidos |

Cada registro do membro é:

|Campo |Largura |Que significa ?|
| ------------ | --------------: | ------------------------ |
|`curve` |1 byte |Valor do registo `CurveId` |
|`weight` |2 bytes |Peso de aprovação do membro |
|`key_len` |2 bytes |Comprimento da chave bruta |
|`public_key` |`key_len` bytes |Carga útil de chaves públicas .|

Uma política válida tem pelo menos um membro, pesos positivos, não há chaves públicas duplicadas e um limiar de `1` através da soma dos pesos dos membros.

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

A construção canônica classifica os membros pelo nome estável do algoritmo de assinatura, um byte separador zero e, em seguida, os bytes crues de chave pública.

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

Um I105 literal não tem comprimento fixo de caracteres, porque os controladores multisig e post-quânticos podem ser grandes.

### Registo `CurveId` {#curveid-registry}

A coluna final indica a função opcional `Cargo` necessária.

Uma pontuação significa que a entrada do registo está disponível sem um modelo de dados opcional.

|ID |Algoritmo de assinatura |Função exigida `Cargo` |
| ---: | -------------------------------------------- | ------------------------ |
|  `1` |`Ed25519` | —                        |
|  `2` |`ML-DSA` | —                        |
|  `3` |`BLS12-381 normal` |`bls` |
|  `4` |`secp256k1` | —                        |
|  `5` |`BLS12-381 small` |`bls` |
| `10` |`GOST R 34.10-2012 256-bit, parameter set A` |`gost` |
| `11` |`GOST R 34.10-2012 256-bit, parameter set B` |`gost` |
| `12` |`GOST R 34.10-2012 256-bit, parameter set C` |`gost` |
| `13` |`GOST R 34.10-2012 512-bit, parameter set A` |`gost` |
| `14` |`GOST R 34.10-2012 512-bit, parameter set B` |`gost` |
| `15` |`SM2` |`sm` |

Os algoritmos não atribuídos IDs e desativados na construção de recepção são rejeitados.

A carga útil da chave deve ser igualmente estruturalmente válida para o algoritmo selecionado pelo `CurveId` declarado.

## Validação e canonicalidade estritas AccountId {#strict-accountid-validation-and-canonicality}

Após a configuração do SDK com o discriminante de cadeia esperado, analise em um `AccountId` e compare a tradução canónica devolvida com a entrada cortada.

A comparação é significativa porque o analisador pode normalizar o material do controlador descodificável ao construir o `AccountId`.

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

Para uma corda não confiável, a aplicação de conformidade deve:

1. Trim só permitiu o transporte de espaços brancos em torno do valor completo.
2. Leia a sentinela e exija o discriminante de cadeia esperado.
3. Mapa de todos os símbolos restantes `Unicode` através do alfabeto exato de 105 símbolos.
4. Separe os seis dígitos da soma de verificação.
5. Converte os dígitos da carga útil de volta para bytes canônicos.
6. Verifique a soma de verificação sobre esses bytes canônicos.
7. Analisar o cabeçalho e o controlador, exigindo:
   - comprimentos exatos de campo
   - um `CurveId` suportado
   - Uma chave pública válida
   - Não há bytes de seguimento
   - Uma política multisig válida, quando aplicável
8. Construir um `AccountId`.
9. Render a `AccountId` canonicamente para o discriminante esperado.
10. Requer a igualdade de `byte-for-byte` com a entrada cortada.

O passo final explícito da aplicação `render-and-compare` rejeita sentinelas numéricas não mínimas, layouts de controladores não-canônicos, material de política reordenado e qualquer outra ortografia que decodifique mas não seja a saída corrente do codificador V1.

Uma soma de verificação bem-sucedida ou uma análise de baixo nível `AccountAddress` não substitui essa verificação.

Não aceitar estes valores num campo estrito de conta- ID:

- um pseudônimo de conta, como `alice@wonderland.universal`
- uma letra I105 com sufixo `@domain` anexado.
- Uma chave pública `multihash`, como `ed0120...`
- Hex de carga útil canônica, tais como `0x02000120...`
- um endereço para o discriminante de cadeia errado
- uma linha com letras maiúsculas ou minúsculas alteradas, largura de caracteres, `kana`, carga útil ou soma de verificação;

Resolver os pseudónimos na fronteira da aplicação e manter o canônico devolvido I105 ID para autorização, assinatura, permissões e registos de auditoria.

### Códigos de erro estável comuns {#common-stable-error-codes}

|Código |Que significa ?|
| -------------------------------- | ------------------------------------------------------------------- |
|`ERR_UNEXPECTED_NETWORK_PREFIX` |O discriminante decodificado não corresponde à rede necessária |
|`ERR_CHECKSUM_MISMATCH` |Os seis símbolos de soma não correspondem à carga útil |
|`ERR_INVALID_I105_CHAR` |Um símbolo está fora do alfabeto exato .|
|`ERR_MISSING_I105_SENTINEL` |Nenhum canônico nome ou sentinela numérica foi encontrado .|
|`ERR_I105_TOO_SHORT` |O corpo não pode conter tanto a carga útil como o checksum .|
|`ERR_INVALID_LENGTH` |Um campo do controlador é truncado ou usa uma forma de comprimento não-canônico |
|`ERR_UNKNOWN_CURVE` |O responsável pelo tratamento declara um `CurveId` não atribuído ou indisponível. |
|`ERR_INVALID_PUBLIC_KEY` |A chave é inválida para o algoritmo selecionado pelo seu `CurveId` |
|`ERR_UNSUPPORTED_ADDRESS_FORMAT` |A entrada não é uma forma canónica I105 aceita |

## API, regras de armazenamento e exibição {#api-storage-and-display-rules}

- Enviar a cadeia exacta I105 UTF-8 nos campos da conta JSON.
- `Percent-encode` a conta completa ID antes de colocá-la em um segmento do caminho URL.
- Nunca use um alias de conta no lugar de um I105 ID.
- Armazenar a cadeia canônica retornada pelo codec com semântica de comparação `byte-preserving`.
- Use uma colação que preserve maiúsculas e minúsculas e a largura dos caracteres.
- Manter o perfil de rede discriminante ou denominado da cadeia com dados e backups de conta exportados.
- Reutilizar um endereço apenas com o seu contexto de rede.
- Mostrar o endereço completo e fornecer uma ação de cópia.
- Preserve exatamente cada caractere `kana`.
- Mantenha o endereço completo disponível quando uma exibição compacta encurtar a parte central.
- Usar o canônico armazenado ID em vez de reconstruí-lo a partir de um alias.

A exibição de `AccountId` e sua representação JSON usam I105 canônico.

A representação de nível inferior `AccountAddress` exibição/JSON usa o hex canônico para contextos internos e de depuração.

Se for necessária uma conta externa ID, ligue-se ao codificador `AccountAddress` I105 explícito.

Para os fluxos de trabalho de criação de contas e resolução de alias, continue com [Contos e aliases ](/pt/cookbook/accounts-and-aliases.md).

Para o modelo de dados da conta, ver [Contos](/pt/blockchain/accounts.md).
