# I105 Formato do Endereço da Conta {#i105-account-address-format}

I105 é o formato de texto externo canônico para um Iroha 3 `AccountId`.

Sua carga representa o controlador da conta.

Seu sentinela identifica a rede pretendida com um discriminante de cadeia.

Use-o em qualquer lugar em que um API, transação, permissão ou consulta solicite um ID de conta canônico.

Um ID de conta I105 não possui domínio.

Um valor como `treasury@payments.universal` é um alias de conta, não outra grafia do ID I105.

Derivar um ID I105 não registra nem financia a conta.

::: warning As regras que evitam a maioria das falhas de integração

- Selecione o perfil de rede antes de codificar ou validar um endereço.
- Armazene e compare a string canônica UTF-8 exatamente.
- Preserve exatamente o uso de maiúsculas e minúsculas e não aplique normalização `Unicode`.
- Um ID I105 não deve ter um sufixo `@domain` ou `@domain.dataspace`.
- Use um Iroha SDK ou `iroha tools address`.
- Uma expressão regular não é um validador I105.

:::

## Anatomia literal {#literal-anatomy}

Um literal I105 tem três partes adjacentes e nenhum separador:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

|Parte|Propósito|Cobertura de checksum|
| ---------------- | ------------------------------------------------------------------ | ----------------- |
|Sentinela de rede|Mapeia o texto para um discriminante de cadeia `u16`|Não coberto|
|Carga útil| `base-105` codificação dos bytes do controlador de conta canônica      |Coberto|
|Soma de verificação|Seis valores `5-bit` no estilo `Bech32m` renderizados com o alfabeto I105|N/A|

A carga útil e o checksum identificam o controlador da conta.

O sentinela seleciona o contexto da rede.

O mesmo controlador tem o mesmo payload e checksum em Taira e Minamoto, mas cada rede usa um sentinela inicial diferente.

Um decodificador deve impor o discriminante esperado.

O checksum não pode detectar uma substituição de sentinela.

### Sentinelas de rede {#network-sentinels}

|Rede ou contexto|Discriminante de cadeia|Hex|Sentinela canônico|
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
| Taira testnet público |                            `369` | `0x0171` | `test`                                      |
|Minamoto rede pública|                            `753` | `0x02f1` | `sora`                                      |
|Contexto de desenvolvimento|                              `0` | `0x0000` | `dev`                                       |
| Qualquer outro valor `u16` |Todos exceto `0`, `369` e `753`|        — | `n` mais decimal mínimo, por exemplo `n42` |

Os valores nomeados sempre usam seu sentinela nomeado.

Formas como `n00042`, `n369`, `n753` e `n0` não são canônicas.

O ID da cadeia de transações e o discriminante da cadeia I105 são valores separados.

Escolher um endpoint API ou ID de cadeia não escolhe implicitamente o perfil de endereço.

## Exemplo normativo de tecla única {#normative-single-key-example}

A carga útil e o formulário Minamoto abaixo vêm do vetor de testes de conformidade entre SDK.

O formulário Taira aplica o sentinela de Taira ao mesmo payload:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

A carga útil canônica começa com `02 00 01 20`: cabeçalho `0x02`, etiqueta compacta de chave única `0x00`, ID da curva `Ed25519` `0x01`, e um comprimento de chave de 32 bytes `0x20`.

O prefixo `multihash` é metadado de entrada e não é copiado para o payload do controlador.

## Crie e inspecione IDs com o CLI {#create-and-inspect-ids-with-the-cli}

Prefira um perfil nomeado para uma rede pública:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

Normalize e compare uma entrada I105 enquanto diagnostica o comportamento do codec de endereço:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

Inspecione o formato detectado, o hex canônico e o contexto de rede selecionado como JSON:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

Audite a estrutura address-codec de um arquivo separado por quebras de linha sem aceitar silenciosamente falhas de análise:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution CLI limite de validação

Os comandos `convert`, `normalize` e `audit` operam no codec de nível mais baixo `AccountAddress`.

Eles verificam o sentinela, alfabeto, soma de verificação, comprimentos de byte, `CurveId`/formato da chave e re-encoding exato da camada de endereço.

Eles não materializam um `AccountId`.

Eles não validam por si mesmos toda a semântica da política multisig.

Eles não provam que a classe do cabeçalho corresponde ao controlador.

Use validação rigorosa `AccountId` antes da autorização ou persistência.

:::

Para uma rede privada, use seu discriminante configurado explicitamente com `--network-prefix`.

Ao converter um endereço existente entre contextos explícitos, também forneça a fonte com `--expect-prefix`:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

A re-codificação altera apenas o contexto da rede.

Não registra a conta na rede de destino nem prova que o mesmo controlador deve ser reutilizado lá.

## Algoritmo de codificação {#encoding-algorithm}

Codificadores canônicos realizam essas operações:

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

Os bytes zero à frente são preservados como dígitos `base-105` com valor zero.

O checksum usa os geradores `Bech32` `polymod` e a constante `0x2bc830a3`.

O HRP apenas de soma de verificação é a string ASCII `snx`.

O HRP apenas com soma de verificação não é impresso no endereço.

Os seis valores de checksum estão no intervalo `0..31` e são exibidos através do mesmo alfabeto I105 que o payload.

### I105 alfabeto {#i105-alphabet}

Os 105 símbolos estão indexados nesta ordem exata.

A primeira linha é o alfabeto `Bitcoin Base58` e contém os dígitos `0..57`.

A segunda linha contém dígitos `58..104`.

Concatenar as linhas ao implementar o codec.

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

O alfabeto é sensível a `Unicode`.

A sequência exata usa `compatibility-width` símbolos japoneses `kana` mais os pontos de código mostrados para `ヰ` e `ヱ`.

Não aplique NFC, NFKC, conversão de largura, dobramento de maiúsculas/minúsculas ou substituição por caracteres visualmente semelhantes.

ASCII `0`, `O`, `I` e `l` não são símbolos alfabéticos.

## Carga útil canônica {#canonical-account-payload}

O corpo `base-105` codifica uma carga útil de conta binária, não uma string de chave pública e não um objeto Norito JSON:

```text
header:u8 || controller:variable
```

Todos os inteiros de múltiplos bytes abaixo são sem sinal e `big-endian`.

O domínio, o espaço de dados, o alias, UAID e os bytes de metadados da conta não estão presentes.

### Byte de cabeçalho {#header-byte}

|Bits|Largura|       Saída atual do codificador |Significado|
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |Campo da versão do formato de endereço|
| `4..3` |     2 | `0` chave única, `1` multisig |Classe de endereço|
| `2..1` |     2 |                          `1` |Campo de versão de normalização|
| `0`    |     1 |                          `0` |Reservado `extension flag`|

Os codificadores atuais V1 emitem o cabeçalho `0x02` para um controlador de chave única e `0x0a` para um controlador multisig.

As classes de endereço `2` e `3` estão não atribuídas.

Um `extension flag` de `1` é rejeitado.

O decodificador de baixo nível pode preservar outros valores de bits de versão e normalização e não verifica independentemente a classe em relação à etiqueta do controlador.

Converter para um `AccountId` e comparar sua representação canônica prova a canonicidade atual de V1.

### Controlador de tecla única {#single-key-controller}

Use a forma compacta quando a carga útil da chave pública bruta tiver no máximo 255 bytes:

|Campo        |Largura|Valor ou significado|
| ------------ | --------------: | ------------------------ |
| `tag`        |          1 byte | `0x00`                   |
| `curve`      |          1 byte | `CurveId` valor do registro |
|`key_len` |1 byte |Comprimento da chave bruta |
| `public_key` | `key_len` bytes |Carga útil de chave pública bruta|

Chaves com mais de 255 bytes usam a forma estendida:

|Campo|Largura|Valor ou significado|
| ------------ | --------------: | ---------------------------- |
| `tag`        |          1 byte | `0x02`                       |
| `curve`      |          1 byte | `CurveId` valor do registro     |
| `key_len`    |         2 bytes |Comprimento da chave bruta, `big-endian`|
| `public_key` | `key_len` bytes |Carga útil de chave pública bruta|

Uma codificação estendida não é canônica para uma chave que se encaixa na forma compacta.

### Controlador multisig {#multisig-controller}

|Campo|Largura|Valor ou significado|
| ---------------- | -------: | ------------------------------ |
| `tag`            |   1 byte | `0x01`                         |
| `policy_version` |   1 byte |Valor atual `1`|
| `threshold`      |2 bytes|Peso total de aprovação necessário|
| `member_count`   |2 bytes|Número de membros a seguir|
| `members`        |Variável|Registros de membros repetidos|

Cada registro de membro é:

|Campo|Largura|Significado|
| ------------ | --------------: | ------------------------ |
| `curve`      |          1 byte | `CurveId` valor do registro |
| `weight`     |         2 bytes |Peso da aprovação do membro|
|`key_len` |2 bytes |Comprimento da chave bruta |
| `public_key` | `key_len` bytes |Carga útil de chave pública bruta|

Uma política válida tem pelo menos um membro, pesos positivos, nenhuma chave pública duplicada e um limite de `1` até a soma dos pesos dos membros.

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

A construção canônica classifica os membros pelo nome estável do algoritmo de assinatura, um byte separador zero e, em seguida, os bytes brutos da chave pública.

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

Um literal I105 não tem comprimento de caractere fixo porque controladores multisig e pós-quânticos podem ser grandes.

### `CurveId` registro {#curveid-registry}

A última coluna nomeia o recurso opcional `Cargo` necessário.

Um traço significa que a entrada do registro está disponível sem um recurso opcional do modelo de dados.

|ID|Algoritmo de assinatura|Recurso obrigatório `Cargo`|
| ---: | -------------------------------------------- | ------------------------ |
|  `1` | `Ed25519`                                    | —                        |
|  `2` | `ML-DSA`                                     | —                        |
|  `3` | `BLS12-381 normal`                           | `bls`                    |
|  `4` | `secp256k1`                                  | —                        |
|  `5` | `BLS12-381 small`                            | `bls`                    |
| `10` | `GOST R 34.10-2012 256-bit, parameter set A` | `gost`                   |
| `11` | `GOST R 34.10-2012 256-bit, parameter set B` | `gost`                   |
| `12` | `GOST R 34.10-2012 256-bit, parameter set C` | `gost`                   |
| `13` | `GOST R 34.10-2012 512-bit, parameter set A` | `gost`                   |
| `14` | `GOST R 34.10-2012 512-bit, parameter set B` | `gost`                   |
| `15` | `SM2`                                        | `sm`                     |

IDs não atribuídos e algoritmos desativados na versão receptora são rejeitados.

A carga útil da chave também deve ser estruturalmente válida para o algoritmo selecionado pelo `CurveId` declarado.

## Validação estrita AccountId e canonicidade {#strict-accountid-validation-and-canonicality}

Após configurar o SDK com o discriminante de cadeia esperado, faça o parsing em um `AccountId` e compare a renderização canônica retornada com a entrada aparada.

A comparação é significativa porque o analisador sintático pode normalizar o material de controlador decodificável enquanto constrói o `AccountId`.

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

Para uma string não confiável, um aplicativo conforme deve:

1. Apare apenas os espaços em branco de transporte permitidos ao redor do valor completo.
2. Leia o sentinela e exija o discriminante de cadeia esperado.
3. Mapeie cada símbolo `Unicode` restante através do alfabeto exato de 105 símbolos.
4. Separe os seis dígitos da soma de verificação.
5. Converta os dígitos da carga útil de volta para bytes canônicos.
6. Verifique a soma de verificação sobre esses bytes canônicos.
7. Analise o cabeçalho e o controlador, exigindo:
   - comprimentos exatos de campo
   - um `CurveId` suportado
   - uma chave pública válida
   - sem bytes finais
   - uma política multisig válida quando aplicável
8. Construa um `AccountId`.
9. Renderize o `AccountId` canonicamente para o discriminante esperado.
10. Exigir igualdade de `byte-for-byte` com a entrada aparada.

A etapa final explícita `render-and-compare` do aplicativo rejeita sentinelas numéricos não mínimos, layouts de controlador não canônicos, material de política reordenado e qualquer outra grafia que seja decodificada mas não seja a saída atual V1 do codificador.

Um checksum bem-sucedido ou análise de baixo nível `AccountAddress` não é um substituto para essa verificação.

Não aceite esses valores em um campo de ID de conta estrito:

- um apelido de conta como `alice@wonderland.universal`
- um literal I105 com um sufixo `@domain` anexado
- uma chave pública `multihash` como `ed0120...`
- hexadecimal de carga útil canônica, como `0x02000120...`
- um endereço para o discriminante de cadeia errado
- uma string com letras maiúsculas ou minúsculas alteradas, larguras de caractere, `kana`, carga útil ou soma de verificação

Resolva aliases na fronteira do aplicativo e mantenha o ID canônico I105 retornado para autorização, assinatura, permissões e registros de auditoria.

### Códigos de erro estáveis comuns {#common-stable-error-codes}

|Código                             |Significado|
| -------------------------------- | ------------------------------------------------------------------- |
| `ERR_UNEXPECTED_NETWORK_PREFIX`  |O discriminante decodificado não corresponde à rede exigida|
| `ERR_CHECKSUM_MISMATCH`          |Os seis símbolos de verificação não correspondem à carga|
| `ERR_INVALID_I105_CHAR`          |Um símbolo está fora do alfabeto exato|
| `ERR_MISSING_I105_SENTINEL`      |Nenhum sentinel nomeado ou numérico canônico foi encontrado|
| `ERR_I105_TOO_SHORT`             |O corpo não pode conter tanto o payload quanto o checksum|
| `ERR_INVALID_LENGTH`             |Um campo de controlador está truncado ou usa uma forma de comprimento não canônica|
| `ERR_UNKNOWN_CURVE`              |O controlador declara um `CurveId` não atribuído ou indisponível|
| `ERR_INVALID_PUBLIC_KEY`         |A chave é inválida para o algoritmo selecionado pelo seu `CurveId`|
| `ERR_UNSUPPORTED_ADDRESS_FORMAT` |A entrada não é uma forma canônica I105 aceita|

## API, regras de armazenamento e exibição {#api-storage-and-display-rules}

- Envie a string exata I105 UTF-8 nos campos de conta JSON.
- `Percent-encode` o ID completo da conta antes de colocá-lo em um segmento de caminho URL.
- Nunca use um alias de conta no lugar de um I105 ID.
- Armazene a string canônica retornada pelo codec com semântica de comparação `byte-preserving`.
- Use uma colação que preserve maiúsculas e minúsculas e a largura dos caracteres.
- Mantenha o discriminante da cadeia ou o perfil de rede nomeado com dados da conta exportados e backups.
- Reutilize um endereço apenas com seu contexto de rede.
- Exiba o endereço completo e forneça uma ação de cópia.
- Preserve exatamente cada caractere `kana`.
- Mantenha o endereço completo disponível quando uma exibição compacta encurtar a parte central.
- Use o ID canônico armazenado em vez de reconstruí-lo a partir de um alias.

A exibição de `AccountId` e sua representação JSON usam I105 canônico.

A exibição/representação de nível inferior `AccountAddress`/JSON usa hexadecimal canônico para contextos internos e de depuração.

Chame o codificador explícito `AccountAddress` I105 quando um ID de conta externo for necessário.

Para fluxos de trabalho de criação de conta e resolução de alias, continue com [Contas e apelidos](/pt/cookbook/accounts-and-aliases.md).

Para o modelo de dados da conta, veja [Contas](/pt/blockchain/accounts.md).
