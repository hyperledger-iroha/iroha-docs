# I105 հաշիվի հասցեային ձեւաչափ {#i105-account-address-format}

I105 է կանոնական արտաքին տեքստային ձեւաչափի համար Iroha 3 `AccountId`.

Նրա օգտակար բեռը ներկայացնում է հաշիվի վերահսկողությունը:

Նշանակված ցանցը նույնականացնում է նրա պահապանով շղթայի տարբերակիչի միջոցով:

Օգտագործեք այն ցանկացած վայրում, որտեղ API, գործարքը, թույլտվությունը կամ հարցումը պահանջում է կանոնիկ հաշիվ ID.

I105 հաշիվը ID ՝ առանց տիրույթի:

Նման արժեքը `treasury@payments.universal` հաշիվի alias-ն է, այլ ոչ թե I105 ID տառապանքի այլ ուղղագրություն:

I105 ID բաժնետոմսերը չեն գրանցվում եւ չեն ֆինանսավորվում հաշվին:

::: warning Կանոնները, որոնք կանխում են ինտեգրման մեծամասնության ձախողումները

- Ընտրեք ցանցի պրոֆիլը նախքան հասցեի կոդավորման կամ հավաստագրման համար:
- Պահպանեք եւ համեմատեք քանոնիկ UTF-8 շերտը ճշգրիտ:
- Պահպանեք տառերի մեծատառ/փոքրատառ ձևը և մի կիրառեք `Unicode` նորմալացում։
- I105 ID տեքստում չպետք է լինի `@domain` կամ `@domain.dataspace` հաջորդականությունը:
- Օգտագործեք Iroha SDK կամ `iroha tools address`
- Պարբերական արտահայտությունը չի նշանակում I105 վավերացնող:

:::

## Գրական անատոմիա {#literal-anatomy}

I105 բառապաշարը ունի երեք հարեւան մասեր եւ ոչ մի բաժանորդ:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

|Մաս |Նպատակ |Չեկային գումարի ապահովագրություն |
| ---------------- | ------------------------------------------------------------------ | ----------------- |
|Համացանցի հսկողություն |Նկարագրում է տեքստը մեկ `u16` շղթայի խտրականություն |Ոչ ընդգրկված |
|Օգտակար բեռը|`base-105` կանոնիկ հաշվի վերահսկիչի բայթերի կոդավորումը |Ընդգրկված |
|Չեկային գումարը |Վեց `Bech32m` ոճի `5-bit` արժեքներ, որոնք ներկայացված են I105 այբուբենով |N/A |

Օգտակար բեռը եւ ստուգման գումարը բացահայտում են հաշիվի վերահսկողին:

Sentinel-ը ընտրում է ցանցի համատեքստը:

Նույն վերահսկիչը ունի նույն օգտակար բեռն ու ստուգման գումարը Taira եւ Minamoto, բայց յուրաքանչյուր ցանց օգտագործում է տարբեր առաջատար պահապան:

Դեկոդերը պետք է ուժի մեջ դնի ակնկալվող խտրականությունը:

Չեկսումը չի կարող հայտնաբերել Sentinel փոխարինման.

### Համացանցային պահապաններ {#network-sentinels}

|ցանց կամ համատեքստ |Շղթաների խտրական |Hex |Canonical Sentinel |
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
|Taira հանրային փորձարկման ցանց |                            `369` |`0x0171` |`test` |
|Minamoto հանրային ցանց |                            `753` |`0x02f1` |`sora` |
|զարգացման համատեքստը |                              `0` |`0x0000` |`dev` |
|Ցանկացած այլ `u16` արժեք |Բոլորը, բացառությամբ `0`, `369` եւ `753` |        — |`n` գումարած նվազագույն տասնամավորը, օրինակ `n42` |

Նշված արժեքները միշտ օգտագործում են իրենց անվանած հսկողությունը:

Նման ձեւեր, ինչպիսիք են `n00042`, `n369`, `n753` եւ `n0`՝ ոչ թե կանոնիկ են:

Գործարքի շղթայի ID եւ I105 շղթայի տարբերակիչները առանձին արժեքներ են:

ID վերջային կետի կամ շղթայի ընտրությունը անուղղակիորեն չի ընտրում հասցեային պրոֆիլը:

## Օրենսդրական միակի բանալի օրինակ {#normative-single-key-example}

Օգտակար բեռը եւ Minamoto ձեւը ստորեւ բերված են SDK խաչմերուկային SDK-ների համապատասխանության թեստային տվյալներից:

Taira ձեւը կիրառվում է Taira-ի հսկողության վրա նույն օգտակար բեռնվածքի վրա.

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

Քանոնիկ օգտակար բեռը սկսվում է `02 00 01 20`: գլխավորություն `0x02`, կոմպակտ միակի փաթեթ `0x00`, `Ed25519` կուրծք ID `0x01`, եւ 32-բայթանոց բանալի երկարություն `0x20`.

`multihash` նախադրյալը մուտքագրված մետադատա է եւ չի կրկնօրինակվում վերահսկիչի օգտակար բեռում:

## Ստեղծեք եւ ստուգեք IDs ՝ օգտագործելով CLI {#create-and-inspect-ids-with-the-cli}

Հրապարակային ցանցի համար նախընտրում է անունով պրոֆիլ:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

Նորմալացրեք եւ համեմատեք I105 մուտքագրությունը հասցե-կոդեկի վարքի ախտորոշման ժամանակ.

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

Ստուգեք հայտնաբերված ձեւաչափը, քանոնիկ վեցկողմը եւ ընտրված ցանցի համատեքստը՝ որպես JSON:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

Փորձեք վերանայել նոր գծով բաժանված ֆայլի հասցե-կոդեկ կառուցվածքը ՝ առանց լռորեն ընդունելու պարբերականության ձախողումներ.

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution CLI վավերացման սահմանը

`convert`, `normalize` եւ`audit` հրամանները գործում են ցածր մակարդակի `AccountAddress` կոդեկով:

Դրանք ստուգում են sentinel-ը, այբուբենը, ստուգիչ գումարը, բայթերի երկարությունները, `CurveId`-ի/բանալու ձևը և հասցեի շերտի ճշգրիտ վերակոդավորումը։

Դրանք չեն կազմում `AccountId`

Նրանք ինքնուրույն չեն հաստատում բոլոր բազմակողմանի քաղաքականության սեմանտիկաները:

Նրանք չեն ապացուցում, որ գլուխների դասը համապատասխանում է վերահսկիչին:

Օգտագործեք `AccountId`-ի խիստ վավերացում նախքան թույլտվումը կամ պահպանումը։

:::

Մասնավոր ցանցի համար օգտագործեք դրա կոնֆիրգուրացված տարբերակիչը բացարձակապես `--network-prefix`:

Գոյություն ունեցող հասցեն բացասական համատեքստների միջեւ փոխակերպելիս նաեւ աղբյուրը լրացրեք `--expect-prefix`:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

Կրկին կոդավորումը փոխում է միայն ցանցի համատեքստը:

Այն չի գրանցում հաշիվը թիրախային ցանցում կամ ապացուցում, որ նույն վերահսկիչը պետք է օգտագործվի այնտեղ:

## Կոդավորման ալգորիթմ {#encoding-algorithm}

Canonical կոդավորիչները կատարում են հետեւյալ գործողությունները.

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

Առաջնորդ զրոյական բայթները պահպանվում են որպես զրոյական արժեք ունեցող `base-105` թվեր:

Փորձաքննության համար օգտագործվում են `Bech32` `polymod` գեներատորները եւ կոշտը `0x2bc830a3`.

Միայն ստուգման գումարը HRP-ն է ASCII շղթան `snx`.

Միայն ստուգման գումարը HRP տպագրված չէ հասցեում:

Վեց ստուգման գումարի արժեքները գտնվում են `0..31` շրջանակում եւ ներկայացվում են նույն I105 այբուբենով, ինչ օգնական բեռնվածքը:

### I105 այբուեն {#i105-alphabet}

105 խորհրդանիշները ինդեքսավորվում են հենց այս կարգով:

Առաջին շարքը `Bitcoin Base58` այբուբենն է եւ պարունակում է `0..57` թվեր:

Երկրորդ շարքը պարունակում է `58..104` թվեր:

Կոնկատենտացրեք շարքերը կոդեկի իրականացման ժամանակ.

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

Ալֆաբեթը զգայուն է `Unicode` - ի համար:

Ճշգրիտ հաջորդականությունը օգտագործում է `compatibility-width` ճապոնական `kana` խորհրդանիշները, գումարած `ヰ` եւ `ヱ` համար ցուցադրված կոդային կետերը:

Մի կիրառեք NFC, NFKC, լայնության փոխակերպում, տառերի ռեգիստրի միավորում կամ նման տեսք ունեցող նիշերով փոխարինում։

ASCII `0`, `O`, `I` եւ `l` չեն համարվում այբուբենային խորհրդանիշներ:

## Կանոնական հաշվի օգտակար բեռը {#canonical-account-payload}

`base-105` մարմինը կոդավորում է բինար հաշիվի օգտակար լիցքավորումը, ոչ թե հանրային բանալիների շղթան եւ ոչ էլ Norito JSON օբյեկտ:

```text
header:u8 || controller:variable
```

Ստորեւ ներկայացված բոլոր բազմաբայթային ամբողջական թվերը չեն ստորագրվել եւ `big-endian`:

Դոմեյնը, տվյալների տարածքը, կեղծանունները, UAID, եւ հաշիվի մետադատա բայթերը ներկա չեն:

### Գլխավորների բայթ {#header-byte}

|Փոքրիկներ|Լայնություն |Ներկայումս կոդավորման արտադրանքը |Նշում |
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |հասցեների ձեւաչափի տարբերակի դաշտ |
| `4..3` |     2 |`0` միավոր բանալին, `1` բազմաբնույթ |Գլխավոր դասարան |
| `2..1` |     2 |                          `1` |Normalization տարբերակի դաշտը |
| `0`    |     1 |                          `0` | Պահուստավորված `extension flag` |

Ներկայումս V1 կոդավորիչները թողարկում են մեկ առանցքային վերահսկողության համար գլխագիր `0x02` եւ բազմանշանակային վերահսկիչի համար `0x0a`:

`2` եւ `3` հասցեային դասերը նշանակված չեն:

`extension flag` բաժնի `1` մի մասը մերժվում է:

Ցածր մակարդակի դեկոդերը կարող է պահպանել այլ տարբերակների եւ կարգավորումների բիթ արժեքները, եւ չի ինքնուրույն խաչմերուկով ստուգում դասը վերահսկիչի տեգի հետ:

Փոխակերպելով `AccountId` եւ համեմատելով դրա քանոնիկ արտացոլումը, ապացուցում է ներկայիս V1 քանոնականությունը:

### Մեկ կոճակային վերահսկիչ {#single-key-controller}

Օգտագործեք համապարփակ ձեւը, երբ հանրային բանալին օգտագործման բեռը առավելագույնս 255 բայթ է:

|դաշտ |Լայնություն |Գոյություն կամ իմաստ |
| ------------ | --------------: | ------------------------ |
|`tag` |1 բայթ |`0x00` |
|`curve` |1 բայթ |`CurveId` գրանցման արժեքը |
|`key_len` |1 բայթ |Հում բանալու երկարությունը |
|`public_key` |`key_len` բայթեր |Հում հանրային բանալու օգտակար բեռը |

255 բայթից ավելի երկար բանալիները օգտագործում են ընդլայնված ձեւը.

|դաշտ |Լայնություն |Գոյություն կամ իմաստ |
| ------------ | --------------: | ---------------------------- |
|`tag` |1 բայթ |`0x02` |
|`curve` |1 բայթ |`CurveId` գրանցման արժեքը |
|`key_len` |2 բայթ |Հում բանալու երկարությունը, `big-endian` |
|`public_key` |`key_len` բայթեր |Հում հանրային բանալու օգտակար բեռը |

Լայնացված կոդավորումը ոչ թե կանոնիկ է այն բանալիների համար, որոնք համապատասխանում են համապարփակ ձեւի:

### Բազմաստորագրության վերահսկիչ {#multisig-controller}

|դաշտ |Լայնություն |Գոյություն կամ իմաստ |
| ---------------- | -------: | ------------------------------ |
|`tag` |1 բայթ |`0x01` |
|`policy_version` |1 բայթ |Առկա արժեքը `1` |
|`threshold` |2 բայտ |Սահմանված ընդհանուր հավանության քաշը |
|`member_count` |2 բայտ |Հետեւյալ անդամների թիվ |
|`members` |Փոփոխական |Կրկնվող անդամների գրառումներ |

Յուրաքանչյուր անդամի արձանագրությունը հետեւյալն է.

|դաշտ |Լայնություն |Նշում |
| ------------ | --------------: | ------------------------ |
|`curve` |1 բայթ |`CurveId` գրանցման արժեքը |
|`weight` |2 բայտ |Անդամների հավանության քաշ |
|`key_len` |2 բայթ |Հում բանալու երկարությունը |
|`public_key` |`key_len` բայթեր |Հում հանրային բանալու օգտակար բեռը |

Վավերական քաղաքականությունը ունի առնվազն մեկ անդամ, դրական քաշեր, ոչ մի կրկնօրինակ հանրային բանալիներ եւ սահմանված է `1` մինչեւ անդամների քաշերի գումար:

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

Կանոնիկ կառուցումը անդամներին դասակարգում է ըստ ստորագրման ալգորիթմի կայուն անվան, զրոյական բաժանարար բայթի, ապա՝ հանրային բանալու հում բայթերի։

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

I105 գրականությունը չունի ֆիքսված տառերի երկարություն, քանի որ բազմակողմանի եւ քվանտային վերահսկիչները կարող են մեծ լինել:

Վերջին սյունակում նշված է պահանջվող ընտրական `Cargo` հատկանիշը:

Նշանակում է, որ գրանցման մուտքը հասանելի է առանց ընտրական տվյալների մոդելի հատկանիշի:

| ---: | -------------------------------------------- | ------------------------ |
|  `1` |`Ed25519` | —                        |
|  `2` |`ML-DSA` | —                        |
|  `3` |`BLS12-381 normal` |`bls` |

Անբաժանված IDs եւ ընդունող կառուցվածքում անջատված ալգորիթմները մերժվում են:

Բացահայտված `CurveId` ալգորիթմի համար հիմնական օգտակար բեռը պետք է կառուցվածքայինորեն հավասար լինի:

## Հստակ AccountId վավերացում եւ կանոնականություն {#strict-accountid-validation-and-canonicality}

SDK-ը կոմպիգուրացելուց հետո սպասվող շղթայի տարբերակիչով, վերլուծեք `AccountId` եւ համեմատեք վերադարձված քանոնիկ ռենդերինգը կտրված մուտքի հետ:

Համեմատությունը նշանակալի է, քանի որ զննարկիչը կարող է նորմալացնել `AccountId` կառուցման ընթացքում դեկոդելի վերահսկողության նյութը:

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

Վստահելի չլինող շղթայի համար համապատասխան դիմում պետք է

1. Trim- ը թույլ է տվել միայն ամբողջական արժեքի շուրջ փոխանցել սպիտակ տարածք:
2. Կարդացեք Sentinel- ը եւ պահանջեք ակնկալվող շղթայի խտրականությունը:
3. Նկարագրեք մնացած բոլոր `Unicode` խորհրդանիշները 105 խորհրդանիշի այբուբենով:
4. Առանձնացրեք ստուգիչ գումարի վեց թվանշանները։
5. Փոխակերպեք օգտակար բեռի թվերը Canonical bytes- ների.
6. Ստուգեք այդ կանոնիկ բայթերի ստուգիչ գումարը։
7. Վերլուծել գլխավորիչը եւ վերահսկողությունը, պահանջելով:
   - ճշգրիտ դաշտի երկարությունները
   - աջակցվող `CurveId`
   - վավերացված հանրային բանալին
   - ոչ մի հետագա բայթներ
   - վավերացված բազմակողմանի քաղաքականություն, երբ կիրառելի է
8. Կառուցեք `AccountId`
9. `AccountId` կանոնիկ կերպով ներկայացրեք սպասվող խտրականության համար:
10. Պահանջվում է `byte-for-byte` հավասարություն կտրված մուտքի հետ:

Հավելվածի հստակ վերջնական `render-and-compare` քայլը մերժում է ոչ նվազագույն թվային sentinel-ները, վերահսկիչի ոչ կանոնիկ դասավորությունները, վերադասավորված քաղաքականության նյութը և ցանկացած այլ գրառում, որը ապակոդավորվում է, բայց չի համապատասխանում կոդավորիչի ընթացիկ V1 ելքին։

Հաջողակ ստուգման գումար կամ ցածր մակարդակի `AccountAddress` վերլուծությունը չի փոխարինում այս ստուգմանը:

Մի ընդունեք հետեւյալ արժեքները խիստ հաշվառման ID դաշտում.

- հաշվառման alias, ինչպիսիք են `alice@wonderland.universal`
- I105 բառակապակցությամբ, հավելվածով `@domain` հաջորդականությամբ
- հանրային բանալին `multihash`, ինչպես օրինակ, `ed0120...`
- կանոնիկ օգտակար բեռի հեքստեր, ինչպիսիք են `0x02000120...`
- սխալ շղթայական խտրականության հասցեն
- շղթան, որը փոխվել է մեծ կամ փոքր տառերով, բնութագրերի լայնությամբ, `kana`, շահագործման բեռով կամ ստուգողական գումարով

Բացահայտել կեղծանունները դիմման սահմանին եւ պահպանել վերադարձված կանոնիկ I105 ID՝ թույլտվության, ստորագրման, թույլտվությունների եւ աուդիտների համար:

## API, պահեստավորման եւ ցուցադրման կանոններ {#api-storage-and-display-rules}

- Տեղադրել I105 UTF-8 հստակ շղթան JSON հաշիվի դաշտերում:
- `Percent-encode` ամբողջական հաշիվը ID, նախքան այն տեղադրելը URL ճանապարհի հատվածում:
- Երբեք I105 ID-ն մի փոխարինեք հաշվի alias-ով։
- Կոդեկը վերադարձած կանոնիկական շղթան պահեք `byte-preserving` համեմատական սեմանտիկայի հետ:
- Օգտագործեք համադրում, որը պահպանում է տառերի մեծատառ/փոքրատառ ձևը և նիշերի լայնությունը։
- Պահպանեք շղթայի խտրական կամ անվանված ցանցային պրոֆիլը արտահանված հաշիվների տվյալներով եւ կրկնօրինակումներով։
- Վերաօգտագործել հասցեն միայն նրա ցանցային համատեքստով:
- Ցուցադրեք ամբողջ հասցեն եւ ներկայացրեք պատճենային գործողություն:
- Պահպանեք յուրաքանչյուր `kana` տառը ճշգրիտ:
- Պահպանեք ամբողջ հասցեն, երբ կոմպակտ էկրանը կարճացնում է դրա միջին մասը:
- Օգտագործեք պահված քանոնիկ ID ՝ փոխարենը այն վերակառուցելու մեկ կեղծ անունից:

`AccountId`-ի ցուցադրումը և JSON ներկայացումը օգտագործում են կանոնիկ I105։

Ցածր մակարդակի `AccountAddress`-ի ցուցադրումը/JSON ներկայացումը ներքին և վրիպազերծման համատեքստերում օգտագործում է կանոնիկ տասնվեցական ձևը։

Բացառիկ `AccountAddress` I105 կոդավորիչին զանգահարեք, երբ պահանջվում է արտաքին հաշիվ ID:

Հաշվեի ստեղծման եւ կեղծ անունների լուծման աշխատանքային հոսքերի համար շարունակեք [Հաշվերի եւ կեղծանունների հետ](/hy/cookbook/accounts-and-aliases.md).

Հաշվեի տվյալների մոդելի համար տես [Հաշվեներ](/hy/blockchain/accounts.md).
