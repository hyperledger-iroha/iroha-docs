# Torii Վերջնական կետեր {#torii-endpoints}

Torii է HTTP, SSE, եւ WebSocket դարպասային Iroha 3. Այն սպասարկում է երկու ledger-ն ուղղված APIs եւ օպերատորի վերջային կետերը:

Գործող արձանագրության կանոնները հետեւյալն են.

- քանոնական երկկողմ ձեւաչափը Norito
- շատ վերջնական կետեր նույնպես աջակցում են JSON, երբ ուղարկում եք `Accept: application/json`
- չափանիշները ներկայացված են Prometheus ձեւաչափով

Ֆորմատի մանրամասների, բովանդակության բանակցությունների, դասակարգման դրոշների, սխեմայի շիշերի եւ Norito RPC ուղեցույցի համար տես [Norito հղումը](/hy/reference/norito.md):

## Համանախագահական կետեր {#common-endpoints}

|Վերջնական կետը|ձեւաչափ |Նպատակ|
| -------------------------------- | -------------- | ---------------------------------------------------------------- |
|`POST /v1/pipeline/transactions` |Norito |Ներկայացրեք ստորագրված գործարք |
|`POST /v1/query` |Norito |Ներկայացնել ստորագրված հարցում |
|`GET /v1/events/ws` |WebSocket |Գրանցվեք իրադարձությունների հոսքերին |
|`GET /v1/events/sse` |SSE |Գրանցվեք SSE-ից ավելի իրադարձությունների հոսքներին|
|`GET /v1/blocks/stream` |WebSocket |Պայմանավորված բլոկների հոսք|
|`GET /v1/peers` |JSON |Torii կողմից բացված հանգույցների ցուցակ |
|`GET /livez` |Տեքստ |Միայն գործընթացային կենսունակություն. դա չի նշանակում արձանագրության պատրաստակամություն |
|`GET /readyz` |JSON |Լիարժեք բջիջների պատրաստությունը, ներառյալ պարտադիր առցանց կանխիկ ստուգումները|
|`GET /health` |JSON |Պատրաստության հետաքննություն նույն անփոխարինելի առցանց կանխիկով |
|`GET /v1/api/version` |Տեքստ |Բլոկային վերնագրերի ներկայիս տարբերակը |
|`GET /status` |Norito կամ JSON |Բարձր մակարդակի ախտորոշման կարգավիճակ; հստակ պահանջ JSON |
|`GET /metrics` |Պրոմետեոս |Պրոմետեուսի սրբման վերջակետը |
|`GET /v1/schema` |JSON |Տվյալների մոդելային սխեմանայի ակնթարթային նկարը , որը մատուցվում է հանգույցի կողմից , երբ ակտիվացված է |
|`GET /openapi.json` |JSON |OpenAPI փաստաթուղթ ակտիվ Torii HTTP երթեւեկության համար |
|`GET /v1/parameters` |JSON |Նոդի պարամետրերի ակնթարթային նկար|
|`GET /v1/node/capabilities` |JSON |Նոդի կարողությունը եւ տվյալների մոդելի մետադատները |
|`GET /v1/time/now` |JSON |Հանգույցի wall-clock snapshot |
|`GET /v1/time/status` |JSON |Ժամանակային համաժամեցման վիճակը |

SSE պահանջի համար գովազդեք բնային հոսքը գումարած տիպված հետընթացը.

```http
Accept: text/event-stream, application/json
```

Torii-ը նախ բանակցում է խնդրանքային շերտում JSON կամ Norito ներկայացումը, այնուհետեւ հավաստիացնում է ներկառուցված `text/event-stream` պատասխանը: Հետեւաբար միայն `text/event-stream` ուղարկելը մերժվում է `406`-ով; [-stream իրադարձությունների բաղադրատոմսը](/hy/cookbook/stream-events.md) օգտագործում է ամբողջական գլուխը:

`/openapi.json` սխեմայում ներկայացված երթուղիների համար ստեղծված պայմանագիրն է, այլ ոչ թե ամբողջական շահագործման հետաքննության ինվենտարի: Ներկայումս փաստաթղթում բացակայում են `/livez` եւ `/readyz`, եւ դրա `/health` նկարագրությունը կարող է ուշանալ պատրաստության կառավարիչին: Ստեղծեք երթուղային հաճախորդներ կենդանի փաստաթղթից, բայց հավաստիացրեք ակտիվությունը եւ պատրաստվածությունը անմիջապես գործող հանգույցի եւ փակված հյուրերի դեմ: Ճշգրիտ մակերեւույթը դեռ կախված է կառուցման առանձնահատկություններից եւ վազման ժամանակի կարգավորումից: Օգտագործեք [Torii API կոնսոլը ](/hy/reference/torii-api-console.md) ՝ այդ կենդանի փաստաթղթը բեռնելու, փորձարկելու JSON երթուղիները, կոպիացնել curl պահանջները եւ ներկայիս սխեմանից հաճախորդի կոդ ստեղծելու համար:

Յուրաքանչյուր կատալոգային աջակցված OpenAPI գործողություն ներառում է `x-iroha-route-auth` օբյեկտ: Կատալոգական աջակցված MCP գործիքները բացահայտում են նույն պայմանագիրը, ինչպես `_meta["iroha/routeAuth"]`: Երկու նախագծերը կրում են `schemaVersion`, `stableRouteId`, `authentication` եւ `admission`: Վերաբերեք `1` տարբերակը որպես ճշգրիտ պայմանագիր. մերժեք չաջակցված `schemaVersion` ՝ փոխարենը գուշակելու, թե ինչպես պետք է մեկնաբանել դրա հավատարմագրման կամ ընդունման մակնիշերը: Ճանապարհային մետադատները նկարագրում են խնդրանքային սահմանը եւ չեն փոխարինում այդ սահմանի պահանջվող վավերական հատկանիշներին:

## Փորձեք կենդանի Taira երթուղիներ {#try-live-taira-routes}

Հասարակական Taira փորձարկման ցանցը բացահայտում է նույն Torii JSON մակերեսը, որը կիրառման հաճախորդները օգտագործում են միայն ընթերցման համար: Այս հրամանները չեն պահանջում բանալիներ.

```bash
TAIRA_ROOT=https://taira.sora.org

curl -fsS -H 'Accept: application/json' "$TAIRA_ROOT/status" \
  | jq '{blocks, txs_approved, txs_rejected, queue_size, peers}'

curl -fsS "$TAIRA_ROOT/openapi.json" \
  | jq -r '.paths | keys[]' \
  | grep '^/v1/' \
  | head -n 20

curl -fsS -H 'Accept: application/json' \
  "$TAIRA_ROOT/v1/node/capabilities" \
  | jq '{abi_version, data_model_version, query: .query.aggregate.supported_resources}'
```

Փորձեք ռեսուրսների ընթերցումը ներկայիս համաշխարհային վիճակի վերաբերյալ.

```bash
curl -fsS "$TAIRA_ROOT/v1/domains?limit=5" \
  | jq -r '.items[].id'

curl -fsS "$TAIRA_ROOT/v1/assets/definitions?limit=5" \
  | jq -r '.items[] | [.id, .name, .total_quantity] | @tsv'
```

Եթե հանրային փորձարկման ցանցի երթուղին վերադարձնում է `502`, ժամանակներ դուրս, կամ հայտնում է հագեցած հերթը, դա վերաբերվում է որպես վերջնական կետերի մատչելիության խնդիր եւ կրկին փորձել հետագայում նախքան debugging ձեր հաճախորդի կոդը:

## Համաձայնություն եւ վազման ժամանակահատվածի ավարտական կետեր {#consensus-and-runtime-endpoints}

Ստորեւ բերված յուրաքանչյուր Sumeragi երթուղին պահանջում է օպերատորի խնդրանքային ստորագրությունը: Ստատուսը, ախտորոշումը, հոսքը, առաջնորդը, բանալին, QC եւ պարամետրային երթուղիները նույնպես պահանջում են հեռաչափության հնարավորություն ունեցող շինարարություն:

| ----------------------------------------- | -------------- | ------------------------------------------------------- |

|`GET /v1/sumeragi/diagnostics` |JSON |Ոչ հավատարմագրական մշակման շղթայի, հերթի եւ երթուղի ախտորոշման |
|`GET /v1/sumeragi/status/sse` |SSE |Շարունակական հեղինակավոր համակարծիքային վիճակի հոսք |
|`GET /v1/sumeragi/leader` |JSON |Ժամանակակից առաջնորդի տեղեկատվություն |
|`GET /v1/sumeragi/qc` |Norito կամ JSON |Ամենաբարձր եւ փակ քվորումի վկայականի ակնթարթային պատճեններ |
|`GET /v1/sumeragi/consensus-keys` |JSON |Ակտիվ կոնսենսուսի բանալիները |
|`GET /v1/sumeragi/bls-keys` |JSON |Ակտիվ BLS համաձայնության բանալիներ |
|`GET /v1/sumeragi/params` |JSON |Ներկայիս շղթայի վրա Sumeragi պարամետրեր |
|`GET /v1/sumeragi/evidence` |JSON |Բացադրիչների արձանագրությունները, ընտրանքային կերպով ֆիլտրված հարցման շղթայով |
|`GET /v1/sumeragi/evidence/count` |JSON |Բացադրիչների թիվը:|
|`GET /v1/runtime/abi/active` |JSON |Ակտիվ կատարման միջավայրի ABI-ի նկարագրություն |
|`GET /v1/runtime/abi/hash` |JSON |Ակտիվ կատարման միջավայրի ABI-ի հեշ |
|`GET /v1/runtime/metrics` |JSON |Runtime metrics snapshot |
|`GET /v1/runtime/upgrades` |JSON |Գործընթացային ժամանակի թարմացման ցուցակը |

## App եւ SORA երթուղի ընտանիքները {#app-and-sora-route-families}

Երբ Torii-ը կառուցվում է հավելվածի դեմ ուղղված առանձնահատկությունների հավաքածուով, այն բացահայտում է լրացուցիչ JSON ընտանիքներ հետազոտողների համար, SORA ծառայություններ, կամուրջային հոսքներ, ապացույցներ եւ պահեստավորում: Այս ընտանիքները չեն կարողացված յուրաքանչյուր ցանցի պրոֆիլում.

`/openapi.json` նկարագրում է ստեղծված app-API կատալոգում գրանցված երթուղիները. այն հավատարիմ է այն պարունակող գրառումների համար, այլ ոչ թե տեղադրված յուրաքանչյուր երթուղու համար մասնավորապես, հանրային տեղական SoraFS CID եւ հայտնի երթուղիները տեղադրվում են ստեղծված փաստաթղթի սահմաններից դուրս եւ պետք է ուղղակիորեն ուսումնասիրվեն:

|Ճանապարհային ընտանիք |Նպատակ|
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
|`/v1/accounts/*`, `/v1/domains/*`, `/v1/assets/*` |JSON ընթերցում, հարցման օգնականներ, ներբեռնումի օգնականներ եւ պորտֆելի կամ տիրողների դիտումներ |
|`/v1/nfts/*`, `/v1/rwas/*`, `/v1/confidential/*` |NFT, իրական աշխարհի ակտիվները եւ գաղտնի ակտիվների տեսանկյունից |
|`/v1/aliases/*`, `/v1/assets/aliases/*`, `/v1/sns/*`, `/v1/identifiers/*` |Անունը, կեղծանունները եւ նույնականացողի լուծումը|

## Հաշվի հավաստագրման, տեսանելիության եւ Explorer- ի կուրսերները {#account-authentication-visibility-and-explorer-cursors}

### App հաշիվի խնդրանքային արձանագրություն {#app-account-request-protocol}

Օգտագործման առնչվող երթուղիները կամ չեն ընդունում հստակեցման գլուխներ, մեկ ուղիղ միակողմանի ապացույց կամ մի քանի նշանների վկայություն: Յուրաքանչյուր հստակագրման գլուխ պետք է հայտնվի առավելագույնս մեկ անգամ:

Ուղիղ ապացույցի համար ուղարկեք բոլոր չորս գլխավորությունները միասին.

- `X-Iroha-Account`: ճշգրիտ քանոնիկ փոքր տառով `0x` հաշիվի հասցեային հեքիաթը կամ ակտիվ քանոնիկական ASCII հաշիվի անանունը: I105 տեքստը անվտանգ չէ որպես HTTP դաշտի արժեք, օգտագործեք այդ հաշիվի համար քանոնական հեքիետի ուղղագրությունը:
- `X-Iroha-Signature`: հստակ padded-base64 ստորագրության օգտակար բեռը:
- `X-Iroha-Timestamp-Ms`: կոնֆիգուրացված խախտումային պատուհանի ներսում միլիսիկունդներով կանոնիկական չստորագրված տասնամյակային Unix ժամանակաբանում:
- `X-Iroha-Nonce`: 1-ից մինչեւ 256 տպագրելի ASCII բայթներ (`0x21`-ից մինչեւ `0x7e`), որոնք եզակի են կրկնօրինակման պատուհանի մեջ:

Գրանցված միակի ստուգիչը ստորագրում է այս ճշգրիտ բայթները.

```text
iroha.app.request.network.v1\0 || <genesis-derived network_id[32]> ||
<UPPERCASE_METHOD>\n
<exact request path>\n
<canonical query>\n
<lowercase hex SHA-256 of the raw body>\n
<canonical timestamp_ms>\n
<nonce>
```

Քանոնիկ հարցման կառուցվածքը վերլուծում է կաթվածային հարցումը որպես `application/x-www-form-urlencoded` (`+` նշանակում է տարածք), տոկոս-դեկոդավորում է իր զույգերը, դասակարգում է դրանք `(key, value)` եւ ձեւ-կոդավորում նրանց կրկին: Պրոտոկոլը թույլ է տալիս առավելագույնս 64 կոդավորված զույգեր եւ 64 KiB չոր հարցման տեքստ: Հիշեք մարմնի բայթները ճիշտ այնպես, ինչպես փոխանցվում է: Մի տեղադրեք բաժանորդfix 32-բայտային ցանցի միջեւ ID եւ մեծ տառերի մեթոդը:

V1 ստուգիչը նաեւ նախքան զննումը սահմանում է մեթոդի տոկենը՝ 32 բայտ, տոկոսային կոդավորված խնդրանքային ուղին՝ 64 KiB, եւ անմիջական հաշիվի ինքնությունը՝ 36 KiB: Հաշվետու կեղծանունները ունեն երեք անվանումի հատվածների առավել խիստ կառուցվածքային սահմանը գումարած դրանց բաժանորդների: Կապը գերազանցելը չի կարող ստուգվել ստորագրության հաստատման կամ աղբյուրի չափերի բաժնումից առաջ:

Մուլտիսիգային վերահսկիչը պետք է փոխանցի `X-Iroha-Witness` որպես խիստ padded-base64 կանոնական Norito եւ բաց թողնել `X-Iroha-Signature`, `X-Iroha-Timestamp-Ms`, եւ `X-Iroha-Nonce`. `X-Iroha-Account` ընտրական է այս ձեւով. ներկայության դեպքում այն պետք է հավասար լինի վկա: `subject_account`. Գլխավոր էջ `CanonicalRequestWitnessV1` պարունակում է `schema_version`, `subject_account`, `timestamp_ms`, `nonce`, մի Iroha `Hash` ճշգրիտ ցանցի խնդրանք բայթների միջոցով մարմնի digest բայց առանց Թարմության դաշտեր, եւ առավելագույնը 64 անդամ ստորագրություններ: Յուրաքանչյուր անդամ ստորագրում է քանոնական Norito Նույն օգտակար բեռի կոդավորման առանց ստորագրությունների շարքի: պետք է բավարարել հաշիվի ընթացիկ բազմազանության քաղաքականությունը: Կոդավորված վկանը սահմանափակվում է 1 MiB.

Անվավերացման գլուխներ չտալը ընտրում է անանուն մուտքը: Ցանկացած մասնակի, խառնված, կրկնվող, սխալ ձեւակերպված, հնացած կամ վերարտադրված ապացույցի տրամադրումը ձախողում է նույնականացումը. այն երբեք չի վերադառնում անանուն տեսանելիության:

### Օպերատորի խնդրանքային արձանագրություն {#operator-request-protocol}

Օպերատորի կողմից հավաստագրված երթուղիների համար պահանջվում են բոլոր չորս սինգլետոնային գլխավորությունները.

- `x-iroha-operator-public-key`: քանոնիկ Iroha բազմազան հանրային բանալին:
- `x-iroha-operator-timestamp-ms`: Կանոնիկ անստորագրված տասնամյակային Unix ժամանակի նշանը միլիսեդկոնդներով:
- `x-iroha-operator-nonce`: 1-ից 256 տպագրելի ASCII բայթներ, որոնք բացառիկ են կրկնօրինակման պատուհանի մեջ գտնվող այդ կոճակի համար:
- `x-iroha-operator-signature`: հստակ padded-base64 ստորագրության օգտակար բեռը:

Գլխավորների արժեքները չպետք է պարունակեն շրջապատող սպիտակ տարածք: Օպերատորի հիմնական նշաններն են.

```text
iroha.operator.http-request.network.v1\0 || <genesis-derived network_id[32]> ||
<UPPERCASE_METHOD>\n
<exact request path>\n
<canonical query>\n
<lowercase hex SHA-256 of the raw body>\n
<canonical timestamp_ms>\n
<nonce>
```

Ճանապարհը, հարցումը, մարմինը, ժամանակային նշանը եւ nonce կանոնները նույն կանոնիկական կանոններն են, որոնք օգտագործվում են հավելվածի արձանագրության կողմից: Գալիկը պետք է մուտք գործվի նաեւ `[torii.operator_signatures]`: ցուցադրել այն `allowed_public_keys`-ում կամ բացարձակապես հնարավորություն տալ `allow_node_key`-ին կոդի բանկի օգտագործման ժամանակ: Replay-cache saturation- ը չի կարող փակվել `503 Service Unavailable` -ով:

Հայցի ճշգրիտ ստորագրությունը միշտ պարտադիր է: Երբ `[torii.operator_auth].enabled = true`, յուրաքանչյուր սովորական օպերատոր երթուղին նույնպես պահանջում է վավեր `x-iroha-operator-session`; երբ `require_mtls = true`, այն լրացուցիչ պահանջում է `x-forwarded-client-cert` վստահելի մուտքից: Ոչ մի գործոն չի փոխարինում խնդրագրի ստորագրությանը:

WebAuthn գրանցման եւ մուտքագրման համար օգտագործեք հետեւյալ չորս JSON վերջային կետերը.

|`POST /v1/operator/auth/registration/options` |Սկսեք WebAuthn վավերագրական գրանցումը |
|`POST /v1/operator/auth/registration/verify` |Փորձեք ստուգել եւ հաստատել վավերագրությունը |
|`POST /v1/operator/auth/login/options` |Սկսեք WebAuthn հավաստագրումը |
|`POST /v1/operator/auth/login/verify` |Ստուգեք պնդումը եւ թողարկեք նստաշրջան |

Կոնֆigurել `torii.operator_auth.tokens` հատուկ bootstrap արժեքներով: Նախքան որեւէ հավաստագիր գոյություն ունենա, ուղարկեք մեկը որպես `x-iroha-operator-token` ՝ առաջին գրանցումը սկսելու համար: Այդ տոքերը երբեք թույլ չի տալիս սովորական օպերատորի երթուղին, եւ լսող `x-api-token` արժեքները երբեք չեն օգտագործվում այս հոսքի համար: Երբ վավերագրությունը գոյություն ունի, մեկ այլ վավերագրություն գրանցելը պահանջում է հավաստիացված նստաշրջան: Մուտքագրման ստուգումը վերադարձնում է նստաշրջանի տոկենը յուրաքանչյուր նոր ճշգրիտ ցանցային օպերատորի խնդրանքների ստորագրության հետ միասին ուղարկելու համար: Վավերագրությունները մնում են `<torii.data_dir>/operator_auth/operator_webauthn.json`:

ISO 20022 երթուղիները կատարում են երկու անկախ ստուգումներ: Հայցը պետք է նախ անցնի այս օպերատորի թույլտվության եւ ստորագրման արձանագրությունը. ISO վարորդը ապա պահանջում է նույն բանալին, որպեսզի զբաղեցնի ստորեւ նկարագրված ճշգրիտ մասնակից կամ աուդիտի դերը:

### Ռեեստրի տեսանելիությունը և Explorer-ի կուրսորները {#ledger-visibility-and-explorer-cursors}

App- ի դեմ ուղղված գրառման ընթերցումները օգտագործում են վերեւում գտնվող ընտրական հավելվածի հաշիվի սահմանը: Ոչ ստորագրված դիմումը ստանում է միայն հանրային կարգավորված տվյալների տիրույթներ: Գոյություն ունեցող ստորագրված խնդրանք ավելացնում է տվյալների տարածքներ, որոնք կապված են զանգահարողի ընթացիկ UAID հետ, յուրաքանչյուր սահմանափակ տվյալների տարածք, որը կոչվում է ճշգրիտ `CanReadRestrictedDataspace { dataspace }` թույլտվությամբ կամ բոլոր երթուղիները, երբ հաշիվը ունի `CanReadAllLedgerData`:

Օգտագործեք ուղին, որը համապատասխանում է զանգահարողի լիազորությանը.

|Մեթոդ եւ վերջնական կետ |Վավերացում եւ տեսանելիություն |
| ------------------------------------- | --------------------------------------------------------------- |
|`POST /v1/transactions/visible/query` |Քանոնիկ հաշիվի ստորագրություն. կիրառվում է զանգահարողի տեսանելիությունը |
|`POST /v1/transactions/query` |Օպերատորի դիմում ստորագրություն; թույլ է տալիս գլոբալ օպերատորը դիտել |
|`GET /v1/triggers/completed` |Օպերատորի խնդրանքային ստորագրություն: Կարդում է բջիջների տեղական ավարտման գրառումները |

Նույն տեսանելիության օբյեկտները ֆիլտրում են հաշիվը, տիրույթը, ակտիվի սահմանումը, ակտիվը, NFT, RWA, պահողը եւ Explorer- ը կարդում է: Գոյություն չունեցող առարկա եւ օբյեկտ, որը գտնվում է զանգահարողի տեսանելի երթուղներից դուրս, միտումնավոր անհնար է տարբերել. Գործարքի կատարման եւ հրահանգների պատմությունը ցուցադրվում է միայն այն դեպքում, երբ գործարքի համար գրանցված յուրաքանչյուր երթուղի հատակ տեսանելի է: Միավորված տվյալների տարածքի գործարքը հետեւաբար թաքնված է, երբ նույնիսկ մեկ մասնակիցի հատված հեռանում է զանգահարողի շրջանակից. բացակայում, հնացած կամ սխալ ձեւավորված երթուղային համատեքստը տեսանելի է միայն գլոբալ ընթերցողին:

Աշխարհի աջակցությամբ վեց Explorer հավաքածուներում օգտագործվում են անբացատրելի կանոնիկ base64url բանալիրների դասիչներ: Նախնական էջի սահմանը 25 է, առավելագույնը 100 եւ մեկ էջը ստուգում է առավելագույնը 512 թեկնածու բանալիներ: Յուրաքանչյուր կուրսոր կապված է իր հավաքածուի, ֆիլտրների, քանոնիկ վերջին բանալիների եւ զանգահարողի տեսանելի երթուղային դիջեսի հետ, այնպես որ այն չի կարող կրկնվել մեկ այլ հարցում կամ զանգահարողի երեւակայության փոփոխություններից հետո:

Բլոկի, գործարքի, վերջին գործարքների, հրահանգների եւ վերջին հրահանգների պատմության կուրսորները լրացուցիչ ամրագրում են հաստատված snapshot-ի բարձրությունն ու բլոկի hash-ը։ Պատասխանները բացահայտում են `pagination.limit`, `pagination.snapshot_height`, `pagination.snapshot_hash`, `pagination.next_cursor` եւ `pagination.has_more`։ Այլ route-ի կամ filter set-ի cursor-ը, փոփոխված visibility digest-ը կամ snapshot-ը, որը հանգույցն այլեւս չի կարող վավերացնել, փակ կերպով մերժվում է։ Պատմության սկանավորումը մնում է Torii-ի query-admission permit-ի ներսում, մինչ blocking worker-ը աշխատում է։

Explorer WebSocket հոսքերը արտանետում են ֆիլտրված ամփոփումներ եւ վերաքննում են տեսանելիությունը, երբ փոփոխվում են գրախանութի թույլտվությունները: Տարօրինակ `GET /v1/blocks/stream` երթուղը տարբեր է. այն արտանետել է ամբողջական ստորագրված բլոկներ, պահանջում է `CanReadAllLedgerData` ձեռքի սեղմման ընթացքում, եւ փակվում է, եթե այդ թույլտվությունը հետագայում չեղյալ է հայտարարվել: Մի օգտագործեք տվյալների տարածք-սկանդվող հետազոտողի համար ներկառուցված հոսքը:

## ISO 20022 կամուրջ {#iso-20022-bridge}

Torii-ը բաց է թողնում ISO 20022 կամուրջը `/v1/iso20022/*`-ի տակ, երբ հավելվածին ուղղված API եւ կամրջի գործնական ժամանակը ակտիվ են: կամուրջը դիտավորյալ նպատակային է. այն ոչ թե ընդհանուր նպատակով ISO 20022 հաշվարկային մուտք է գործում, այլ աջակցվող ենթակազմ, որը ընտրված վճարային հաղորդագրությունները վերածում է ստորագրված Iroha փոխանցումների եւ դրանց գլխավոր գրքի կարգավիճակի հետապնդման համար:

Կազմեք կայուն տեղական `torii.iso_bridge.store_dir` նախքան ցանկացած ներկայացում ընդունելը: Կազմակերպման դաշտը ընտրանքային է միայն այնպես, որ հանգույցը կարող է մեկնարկել միայն կարդալու կամ ախտորոշիչ օգտագործման համար. յուրաքանչյուր հավաստագրված ISO ներկայացումը պահանջում է ցուցակ, եւ վերադարձնում է կրկնօրինակելի `503 Service Unavailable`, երբ պեսսպերանսը բացակայում է կամ վերանայող կրկնակի ուղարկումը կանխող նշիչ կամ հարուստ ձայնագրության գրելը ձախողվում է:

|`GET /v1/iso20022/messages/{msg_id}/sese024` |Հաշվարկի ընթացիկ կարգավիճակը վերադարձնել `sese.024` XML |
|`GET /v1/iso20022/messages/{msg_id}/sese025` |Գործնական կարգավորման հաստատումը ներկայացրեք որպես `sese.025` XML |

`pacs.008` ներկայացումները պետք է պարունակեն հաղորդագրությունը ID, բանկային փոխհատուցման գումարը, արժույթը, կարգավորման ամսաթիվը, պարտավորն ու վարկատուին IBANs, եւ պարտավորին եւ վարկատուին՝ BICs. Հաշվետու տվյալների կազմաձեւման ժամանակ կամուրջը նաեւ ստուգում է BIC, IBAN եւ ISO 4217 արժույթի անցումները, նախքան ստեղծված գործարքը մուտք է գործում մշակման շղթայի:

`pacs.009` ներկայացումները պետք է պարունակեն բիզնես հաղորդագրությունը ID, հաղորդագրության սահմանումը ID, ստեղծման ժամանակը, բանկային փոխհատուցման գումարը, արժույթը, հաշվարկման ամսաթիվը, հանձնարարականներ տրամադրող գործակալ BICs, պարտավոր եւ վարկատու IBANs: Եթե հաղորդագրությունը ներառում է `Purp`, կամուրջը ներկայումս ընդունում է միայն արժեթղթերի նպատակով ֆինանսավորում. `Purp=SECU`

`pacs.008` եւ `pacs.009` ներկայացման վերջային կետերը ընդունում են XML ISO փաթեթները կամ կամուրջի փորձարկումների ժամանակ օգտագործվող հարթ դաշտի ձեւաչափը: Ընտրական`SplmtryData` դաշտերը կարող են տեղադրել նպատակային Iroha գլխավոր գրքում, աղբյուրի եւ թիրախային հաշիվ IDs կամ հասցեներ, ինչպես նաեւ ակտիվների սահմանումը ID: Պատասխանը `202 Accepted` է ՝ `message_id`, `transaction_hash`, `status`, `pacs002_code`, եւ լուծված գլխավոր / հաշիվ / ակտիվի համատեքստով:

### Մասնակիցների թույլտվություն եւ կյանքի շրջանի սեփականությունը {#participant-authorization-and-lifecycle-ownership}

Յուրաքանչյուր ակտիվացված կամուրջ ունի մասնակիցների կատալոգ: Յուրաքանչյուր մասնակիցի մուտք ունեն եզակի մասնակից ID, մեկ կամ ավելի օպերատորների հանրային բանալիներ, մեկ կամ մի քանի ֆինանսական նույնականացումներ, թույլատրված պրոֆիլների հավաքածու եւ `originator`, `counterparty` կամ երկուսն էլ դերակատարներ: Օպերատորի բանալիները եւ ֆինանսական նույնականացումները չեն կարող պատկանել ավելի քան մեկ մասնակիցին: Կազմակերպեք `audit_admin_keys` առանձին. Audit-admin բանալին չի կարող լինել նաեւ մասնակիցների մուտացիոն բանալին:

Բոլոր ISO երթուղիները պահանջում են նոր օպերատորի ստորագրություն: Առաջին `pacs.008`, `pacs.009`, `sese.023` կամ `colr.012` ներկայացման համար հավատարմագրված օպերտորը պետք է պատկանի հայտի գլխավոր `From` ֆինանսական ինքնության մեջ հայտնաբերված մասնակիցին: `To` ինքնությունը պետք է լուծվի կոնֆիգուրացված մասնակիցին, ով ունի `counterparty` դերը, եւ ընտրված պրոֆիլը պետք է թույլատրվի երկու կողմերի համար: Հավերժական մուտքագրությունը արձանագրում է հեղինակը, հակառակորդը, ընդունող մասնակիցը եւ օպերատորի բանալին, ինչպես նաեւ բնօրինակ պրոֆիլն ու ներմուծված ստորագրության քաղաքականությունը:

Կյանքի շրջանի թույլտվությունը բխում է այդ անփոփոխ արձանագրությունից, այլ ոչ թե զանգահարողի կողմից ընտրված արժեքներից.

|Կյանքի շրջանի հաղորդագրություն |Պահանջվող մասնակից |
| ---------------------------------------------- | -------------------------------------------------- |
|`pacs.002`, `pacs.004`, `sese.024`, `sese.025` |`counterparty` դերակատարության օրիգինալ հակառակորդը |
|`camt.056` |Օրիգինալ հեղինակ՝ `originator` դերի հետ |

Օրիգինալ պրոֆիլը եւ ստորագրության քաղաքականությունը մնացել է փակ ամբողջ կյանքի ցիկլով, այնպես որ զանգահարողը չի կարող ընտրել ավելի թույլ պրոֆիլի թարմացման համար: A `pacs.002` կոդ, որը ներկայացնում է կարգավորումը (`ACSC`, `ACCP`, `SETT` կամ `SETTLED`) փոխում է սկզբնական արձանագրությունը կարգավորվելով միայն այն դեպքում, երբ Torii-ը հաստատված է գործարքի ապացույցներ:

Հաշվարկի վերջային կետը վերադարձնում է միայն այն գրառումները, որոնցում վավերացված մասնակիցն է հեղինակ կամ հակամարտող։ Հատկապես կոմֆիգուրացված աուդիտորային կառավարիչը ստանում է գլոբալ միայն ընթերցվող աուդիտի տեսանկյուն եւ չի կարող ուղարկել կամ փոխել հաղորդագրություններ: Անհայտ մասնակիցները եւ անկապակցված հաղորդագրությունների նույնականացողները չեն բացահայտվում:

### Հավերժական կրկնօրինակման ինքնությունը եւ ստորագրված արտահերթ տուփային փաստաթղթերը {#durable-replay-identity-and-signed-outbox-documents}

Կրկնակի ուղարկումը կանխող նշիչները- ը ընդունման խիստ սահմանն է: Torii արհեստավորում է անլսելի, չափազանց մեծ, սխալ ձեւավորված, սխալ անվանումներով, հակասություններով կամ բացարձակապես անհամատեղելի կրկնակի ուղարկումը կանխող նշիչների համար: Այն նաեւ բացարձակապես անհամատեղելի սխեմայի տարբերակի, ներգրավվածի, պրոֆիլի կամ ստորագրության քաղաքականության հետ հարուստ ձայնագրություն է ստեղծում, որը բացակայում է ընթացիկ կոնֆիգուրացիայից, կամ բացակայում կամ անհամապատասխան կենդանի կրկնակի ուղարկումը կանխող նշիչ:

Այլ հարուստ գրառումների վնասները այլ կերպ են լուծվում. Անկարդելի կամ չափազանց մեծ ֆայլեր, անվավեր JSON, անվավեր ընթացիկ սխեմայի արձանագրություններ, ոչ կանոնիկ ֆայլերի անուններ եւ հակասական կրկնօրինակման նույնականությունները գրանցվում են կամ բաց թողնում են: Պահպանված գրառումներից վերականգնվում է ընթերցելի կամ անվավեր ընթացիկ տարբերակի աուդիտային ինդեքս, միայն բացարձակապես անհամատեղելի աուդիտական ինդեքսի տարբերակը վերսկսում է աշխատանքը: Ուսումնասիրեք սկիզբի օրագրերը եւ համատեղեք վերականգնված աուդիտի մանիֆեսը, այլ ոչ թե ենթադրեք, որ ամեն կոռուպցիոն հարուստ գրառումների ֆայլը խանգարում է նոդին ծառայել:

Յուրաքանչյուր պահպանված հարուստ արձանագրություն պահում է մասնակիցների անփոխարինելի ծագումը: Հատուկ մշտական կրկնակի ուղարկումը կանխող նշիչները պահում են հաղորդագրությունը ID, օգտակար բեռը, բիզնես ուղերձը ID եւ UETR ՝ ամբողջական կրճատման համար TTL նույնիսկ հարստ արձանագրության մանրամասները կտրելուց հետո։

Torii շարունակվում է կրկնօրինակման ընդունումը, նախքան այն ստորագրում կամ մշակում է կյանքի շրջանի հաղորդագրություն: Այն երբեք չի հեռացնում չավարտված կրկնապատկման ինքնությունը: Եթե կոմֆիգուրացված հզորությունը ամբողջությամբ զբաղված է պաշտպանված արձանագրություններով կամ չավարտվող կրկնօրինակման նույնականություններով, ներկայացումները ստանում են վերականգնվող `503 Service Unavailable` ՝ առանց կյանքի ցիկլի կամ հաշվապահական վիճակի մուտացիայի.

Յուրաքանչյուր ստեղծված `pacs.002`, `pacs.004`, `camt.029`, `sese.024`, կամ `sese.025` փաստաթուղթը վերադարձվում է որպես `application/xml` այս պատասխանների գլխավորագրերով.

|Գլխավոր |Նշում |
| ------------------------------ | ----------------------------------------------------- |
|`X-Iroha-Iso-Signature-Domain` |Միշտ `iroha.iso20022.outbound.v2` |
|`X-Iroha-Iso-Signer` |Կոնոնիկ հանրային բանալին կոնֆիգուրացված կամուրջի ստորագրման համար |
|`X-Iroha-Iso-Signature` |Base64 ստորագրությունը XML բայթների վրա, որոնք բաժանված են տիրույթից |

Ստուգեք ստորագրությունը UTF-8 բայթերի հաջորդականության վրա `iroha.iso20022.outbound.v2`, մեկ զրոյական բայտ եւ ճշգրիտ արձագանքային մարմինը: Նախքան ստուգումը մի վերֆորմատացրեք կամ կարգավորեք XML:

### Վերլուծիչի և քարտեզագրման լրացուցիչ աջակցություն {#additional-parser-and-mapping-support}

IVM ISO օգնականը հավաստիացնում է եւ իրականացնում է նաեւ հետեւյալ հաղորդագրությունների ընտանիքները փաթեթների հավաստիացման, կարգավորման քարտեզավորման կամ իջեցող հաշտեցման համար: Նրանք չունեն ինքնուրույն Torii երթուղիներ:

|Հաղորդագրության ընտանիք |Գործնական աջակցություն |

|`head.001` |ISO փաթեթների համար բիզնես հայտերի գլխավորագրի վավերացում, ներառյալ `BizMsgIdr`, `MsgDefIdr` դաշտերը, ստեղծման ժամանակը եւ ընտրանքային ուղարկող/ընդունող BIC դաշտները |
|`pacs.007`, `pacs.028`, `pacs.029` |Վճարման հետադարձ փոփոխություն, վիճակագրության խնդրանք եւ քննության լուծում / վիճակի վերլուծություն |
|`pain.001`, `pain.002` |Հաճախորդի վճարման սկիզբը եւ վճարման վիճակագրության զեկույցի վավերացումը |
|`camt.052`, `camt.053`, `camt.054` |Հաշվի հաշվետվություն, հայտարարություն եւ ծանուցման հաստատում |

## Kaigi Հանդիպումներ {#kaigi-sessions}

Kaigi ապահովում է վճարված, իրական ժամանակի աուդիո / տեսահոլովակի սենյակներ SORA Nexus: Օգտագործեք այն, երբ ծրագիրը պահանջում է գրասենյակի աջակցությամբ նստաշրջանների ստեղծումը, ցուցակային փոփոխությունները, ռելեյի մանիֆեսները, կոդավորված ազդանշանը եւ օգտագործման հաշվարկը, փոխարենը պահելով բոլոր կոնֆերենցիաների վիճակը հեռու շղթայից:

Գլխավոր գրասենյակային կյանքի ցիկլը հետեւյալն է.

- `CreateKaigi`: ստեղծել զանգի տիրույթի ներքո եւ պահել դրա քաղաքականությունը, ժամանակացույցը, մետադատները եւ ընտրանքային ռեալի մանիֆեսը:
- `JoinKaigi`: թարմացնել զանգերի ցուցակը: `zk-roster-v1` ռեժիմում, հանրային զանգի տեսանկյունից բացատրում են պարտավորությունների եւ չեղյալ հայտարարողների հաշիվները մասնակիցների հաշվին փոխարեն IDs.
- `LeaveKaigi`: հեռացրեք մասնակիցը թափանցիկ զանգից: Անձնական ռեժիմով մեկնումն անջատված է առաջին թողարկման արձանագրության մեջ:
- `RecordKaigiUsage`: ավելացրեք հաշվարկված տեւողությունը եւ գազի ընդհանուր թիվը:
- `EndKaigi`: փակել է նստաշրջանը եւ գրանցել վերջնական ժամադրությունը:

Torii բացատրում է հետեւյալ հավելվածի ուղղությամբ ընթերցումները.

|Ճանապարհ |Վավերացում |Նպատակ|
| ----------------------------------- | --------------------------------------- | ------------------------------------------ |
|`/v1/kaigi/calls/{call_id}` |հանրություն |ընթացիկ զանգերի արձանագրություն |
|`/v1/kaigi/calls/{call_id}/signals` |վավերական ճշգրիտ ցանցային հաշիվների պահանջ |paginated հաստատված ազդանշանային մետադատա |
|`/v1/kaigi/calls/{call_id}/events` |վավերական ճշգրիտ ցանցային հաշիվների պահանջ |զանգահարել կյանքի շրջանակային հոսքը |
|`/v1/kaigi/relays` |թույլատրված ցուցակային օպերատորի խնդրանք |Relay ամփոփում |
|`/v1/kaigi/relays/{relay_id}` |թույլատրված ցուցակային օպերատորի խնդրանք |մեկ ռելեյի գրանցման եւ առողջության մանրամասները |
|`/v1/kaigi/relays/health` |թույլատրված ցուցակային օպերատորի խնդրանք |համախմբված ռեալի առողջություն |
|`/v1/kaigi/relays/events` |վավերական ճշգրիտ ցանցային հաշիվների պահանջ |Relay գրանցման եւ առողջապահական միջոցառումների հոսք |

Հավելվածը API պետք է ակտիվացվի: Relay ամփոփում եւ առողջության երթուղիները օպերատորի մակերեսներ են, չնայած դրանք միայն ընթերցման համար են: Ոչ ստորագրված խնդրանք `curl` ոչ վավերացված մատչելիության հետաքննություն: Հանդիպման վիճակը արտացոլվում է նաեւ Kaigi տիրույթի իրադարձությունների միջոցով, ինչպիսիք են `KaigiRosterSummary`, `KaigiRelayManifestUpdated`, `KaigiRelayHealthUpdated` եւ `KaigiUsageSummary`:

### CLI Ծխի փորձարկում {#cli-smoke-test}

Սկսեք `iroha app kaigi` CLI-ից, երբ ցանկանում եք ստուգել, որ Torii վերջնական կետը ընդունում է Kaigi գործարքները, նախքան միացնել UI: Quickstart հրամանը ստեղծում է սենյակ կոնֆիգուրացված վերջային կետի դեմ եւ տպագրում է իր զանգի նույնականացողը եւ միացնում մետադատա.

```bash
iroha app kaigi quickstart \
  --domain kaigi.universal \
  --summary-out kaigi-summary.json
```

Սկրիպտային հոսքերի համար բացարձակապես կառավարեք սենյակի կյանքի ցիկլը.

```bash
iroha app kaigi create \
  --domain kaigi.universal \
  --call-name daily \
  --host <i105-account-id> \
  --privacy-mode transparent \
  --room-policy authenticated

iroha app kaigi join \
  --domain kaigi.universal \
  --call-name daily \
  --participant <i105-account-id>

iroha app kaigi leave \
  --domain kaigi.universal \
  --call-name daily \
  --participant <i105-account-id>

iroha app kaigi record-usage \
  --domain kaigi.universal \
  --call-name daily \
  --duration-ms 120000 \
  --billed-gas 1500

iroha app kaigi end --domain kaigi.universal --call-name daily
```

Օգտագործեք `--room-policy public` այն սենյակների համար, որոնք ռելեյները կարող են բաց թողնել առանց դիտորդի տոմսերի կամ `--room-policy authenticated`, երբ ելքերը պետք է պահանջեն դիտորդի հավաստագրումը: Օգտագործիր `--privacy-mode zk-roster-v1` միայն հետո ցանցում կազմված է Kaigi ցուցակի եւ օգտագործման ստուգման բանալիները. հակառակ դեպքում միացումները, թերթերը եւ անձնական օգտագործման արձանագրությունները ձախողվում են դետերմինիստիկ ստուգման ընթացքում:

### JavaScript ինտեգրումը {#javascript-integration}

Ներկայիս [Iroha-ի JavaScript ցուցադրություն](https://github.com/soramitsu/iroha-demo-javascript) իրականացնում է թափանցիկ, հավաստագրված մեկ-մեկ հանդիպման պրոֆիլ: Այն չի բացահայտում պրոտոկոլի `zk-roster-v1` ապացույցային հոսքը: Դրա ռենդերերը ստեղծում է WebRTC առաջարկներ եւ պատասխաններ, մինչդեռ արտոնյալ կամուրջը օգտագործում է տեղական [`@iroha/iroha-js`](https://github.com/hyperledger-iroha/iroha/tree/0010c5a70039eac101a4846499ba9ceaf43eb65c/javascript/iroha_js) ստուգումը ՝ վճարի գնառաջարկ, ստորագրելու, ներկայացնելու եւ սպասելու ավարտված Kaigi գործարքների համար:

Դիտեք [Embed Kaigi-ը JavaScript App-ում](/hy/guide/tutorials/kaigi.md) ճշգրիտ երթեւեկության հավաստագրման, հրավիրման ձեւաչափի, կամուրջի սահմանների եւ ընթացիկ ապացուցման փորձարկման հրամանների համար:

## Պաշտոն եւ չափանիշներ {#status-and-metrics}

Ստատուսի եւ չափանիշների վերջային կետերը առաջին բանն են, որոնք ներմուծվում են դաշբորդերում.

- `/status` բացահայտում է բարձր մակարդակի հանգույցների, բլոկների, հերթի եւ համաձայնության դաշտերը
- `/metrics` բացահայտում է Prometheus հաշվիչները, չափիչները եւ հիստոգրամները

Nexus օժտված հանգույցներում, վիճակի արտադրանքը ներառում է նաեւ երթուղի եւ տվյալների տարածքի գիտակցող հատվածներ: Երբ `nexus.enabled = false`, այդ հատվածները բաց թողնվում են:

## JSON-ն ընդդեմ Norito-ի {#json-vs-norito}

Բազմաթիվ օպերատորների վերջնական կետերը վերադարձնում են Norito որպես նախապայման: Երբ վերջային կետը աջակցում է JSON, ուղարկեք՝

```http
Accept: application/json
```

Սա հատկապես օգտակար է հետեւյալ դեպքերում.

- `/v1/sumeragi/status`
- `/v1/sumeragi/qc`

Երբ վերջնական կետը ընդունում է կամ ուղղակիորեն վերադարձնում է Norito տիպի, օգտագործեք `application/x-norito` որպես բովանդակության տեսակ կամ նախընտրված `Accept` արժեք: Գտեք [Norito](/hy/reference/norito.md#torii-and-norito-rpc) փոխադրման մանրամասները.

## Հեռաչափության պրոֆիլներ {#telemetry-profiles}

Վերջնական կետի տեսանելիությունը կախված է հանգույցի `telemetry.profile` կարգավորումից: Ներկայիս կազմաձեւումը բացահայտում է հինգ պրոֆիլ մակարդակ.

|Պրոֆիլ |`/status` |`/metrics` |Գործարարների ուղիները |
| ----------- | --------- | ---------- | ---------------- |
|`disabled` |Ոչ, ոչ|Ոչ, ոչ|Ոչ, ոչ|
|`operator` |Այո.|Ոչ, ոչ|Ոչ, ոչ|
|`extended` |Այո.|Այո.|Ոչ, ոչ|
|`developer` |Այո.|Ոչ, ոչ|Այո.|

## CLI Փակ ճանապարհներ {#cli-shortcuts}

`iroha` CLI-ը արդեն ներառում է հետեւյալ վերջային կետերի շատերը.

```bash
export IROHA_OPERATOR_KEY_FILE=/run/secrets/iroha/operator.key

iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  --output-format text ops sumeragi status
iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  --output-format text ops sumeragi diagnostics
iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  ops sumeragi params
iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  --output-format text ops sumeragi evidence count
```
