# Ստեղծման խնդիրների լուծում {#troubleshooting-configuration-issues}

Այս բաժինը առաջարկում է խնդիրների լուծման խորհուրդներ Iroha 3 կոնֆիգուրացիայի համար: Համոզվեք, որ դուք [ նախ ստուգել եք ](./overview.md#check-the-keys) բանալիները, քանի որ դա ամենատարածված խնդրի աղբյուրն է Iroha:

Եթե ձեր խնդիրն այստեղ չի նկարագրվել, կապվեք մեզ հետ [Telegram](https://t.me/hyperledgeriroha) միջոցով:

## Docker Compose կարգավորման ժամանակակից գենեզը {#outdated-genesis-on-a-docker-compose-setup}

Երբ դուք օգտագործում եք Docker Compose տարբերակը Iroha, դուք կարող եք հանդիպել խնդրի մի զուգահեռ կոնտեյներները ձախողում է `Failed to deserialize raw genesis block` սխալ. Սա սովորաբար նշանակում է, որ հանգույցային, ստորագրված գենեզի գործարքը եւ ստեղծված կարգավորումը արտադրվել են տարբեր Iroha վերանայմաններ կամ պրոֆիլներ:

Հավաքածուի գրացուցակից գործարկեք `python3 poc.py logs`՝ վավերացնող հանգույցների մատյանները դիտելու համար։ Docker-ում նույն վերանայման գործարկվող ֆայլերով չորս վավերացնող հանգույց կառուցելու և գործարկելու համար հետևեք [Լանչում Iroha 3](/hy/get-started/launch-iroha.md) ուղեցույցին։

Նույն ցանցը վերագործարկելու համար գործարկեք `python3 poc.py down` և ապա `python3 poc.py up`։ `state/` գրացուցակը պահեք իր չորս Docker հատորների հետ միասին։

::: info

Հեռուստային ցանցում գենեզի փոխարինման համար չկա ընդհանուր ավտոմատ վերանորոգման ուղին: Սա դիտարկեք որպես համակարգված միգրացիա. պահպանեք հին վիճակը, բերեք համատեղելի հանգույցներ եւ վավերացողները տեղափոխեք նոր կոնֆիգուրացիա միայն այն բանից հետո, երբ օպերատորը համաձայնվի միգրացիայի պլանի հետ:

:::

## Գլխավոր եւ հանրային բանալիների բազմակողմանի ձեւաչափ {#multihash-format-of-private-and-public-keys}

Եթե նայեք [հաճախորդի կազմավորմանը](/hy/guide/configure/client-configuration.md), դուք կտեսնեք, որ այնտեղ գտնվող բանալիները տրված են [ բազմազան ձեւաչափով ](https://github.com/multiformats/multihash):

Եթե դուք նախկինում երբեք չեք աշխատել բազմա-հիշի հետ, բնական է ենթադրել, որ աջ կողմը առանցքային բայթների (երկու խորհրդանիշ մեկ բայթի համար) վեցամյակային ներկայացումն չէ, այլ ավելի շուտ ASCII (կամ UTF-8) կոդավորված բայտները, եւ զանգահարեք `from_hex` շղթայական բառապաշարի վրա ինչպես `public_key`, այնպես էլ `private_key` օրինակով:

Բնական է նաեւ ենթադրել, որ `PrivateKey::try_from_str` զանգահարելը շղթայական բառարանում կստանա միայն ճիշտ բանալին: Այսպիսով, եթե դուք սխալ եք ստանում ստեղնաշարի բիթների թիվը, օրինակ, 32 բայթներ vs 64, դա կհանգեցնի սխալ հաղորդագրության:

Այս երկու ենթադրությունները սխալ են: Ցավոք, սխալների հաղորդագրությունները չեն օգնում լուծել այս հատուկ տեսակի ձախողումները:

Ինչպես շտկել. օգտագործեք `hex_literal`։ Դա նաեւ տգեղ նիշերի տողը կվերածի գեղեցիկ փոքր աղյուսակի՝ ակնհայտ hexadecimal թվերով։

::: warning

Նույնիսկ `try_from_str` իրականացումը չի կարող ստուգել, թե արդյոք տրված շղթան է վավերական `PrivateKey` եւ նախազգուշացնել ձեզ, եթե այն չէ.

Այն կբացահայտի որոշ ակնհայտ սխալներ, օրինակ, եթե շղթան պարունակում է անվավեր խորհրդանիշ: Այնուամենայնիվ, քանի որ մենք նպատակ ունենք աջակցել բազմաթիվ բանալիր ձեւաչափերին, այն շատ բան չի կարող անել: Այն չի կարող ասել, թե արդյոք բանալին ճիշտ մասնավոր բանալիր է տվյալ հաշիվի համար, քանի դեռ դուք չեք ներկայացրել հրահանգ:

:::

Այս տեսակի մանր սխալները կարելի է խուսափել, օրինակ, ուղղակիորեն դեզերիալացնելով շղթայական բառերից կամ նոր բանալիների զույգը ստեղծելով այն վայրերում, որտեղ դա իմաստ ունի:
