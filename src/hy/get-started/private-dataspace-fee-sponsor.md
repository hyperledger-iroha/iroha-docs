# Հովանավորել մասնավոր տվյալների տարածքի վճարները {#sponsor-fees-for-a-private-data-space}

SORA Nexus վճարների հովանավորման ծրագիրը կարող է վճարել մասնավոր տվյալների տարածք երթուղավորված համապատասխան գործարքների համընդհանուր կատարման վճարները։ Օգտատերը շարունակում է ստորագրել ամբողջ գործարքը։ Դրա տիպավորված `FeePaymentIntent`-ն ընտրում է ճշգրիտ հովանավոր ծրագիրը և անփոփոխ տարբերակը, պահանջված դեպքում՝ կատարման գազի սահմանը, և առավելագույն գանձումները։

Տվյալների տարածքի կատալոգի գրառումը չի ստեղծում անկախ ստորագրված արմատ։ Անկախ տվյալների տարածքի արմատն ունի իր հաստատված վճարային արժույթն ու քաղաքականությունը․ հանրային հովանավոր պահոցները չեն կարող լիազորել դրա մասնավոր արմատի վճարները։ Հովանավորումը նախագծելուց առաջ հաստատեք կատարման արմատը։

## 1. Հաստատել ընդունված վճարային քաղաքականությունը {#_1-establish-the-committed-fee-policy}

Ստորագրված ծագման վիճակը ստեղծում է մեկ `root_fees_v1` հատուկ պարամետր, որը պարունակում է `RootFeePolicy`։ Այն կապում է վճարային արժույթը, վճար ստացող հաշիվը, հովանավորի պահպանության հաշիվը, պահանջների ազատումները և սակագները։ Յուրաքանչյուր սովորական բլոկ և գնառաջարկ օգտագործում է իր ամրագրված հաստատված քաղաքականությունը։ Սակագների, վճար ստացող հաշվի և պահանջների ազատումների լիազորված փոփոխությունները կիրառվում են հաջորդ բլոկից. վճարային արժույթը և հովանավորի պահպանության հաշիվը չեն կարող փոխվել առաջին բլոկից հետո։

Համընդհանուր կատարման համար բնիկ վճարն այրում է ստորագրված ցանցի ճշգրիտ XOR արժույթը։ Այդ արժույթը տրամադրում է հովանավորի ծրագրային պահոցը։ Հանգույցի կարգավորումներն ու գործարքի մետատվյալները չեն ընտրում վճարող և չեն ակտիվացնում հովանավորումը։

Օգտագործեք ցանցի կանոնական արժույթը և հաշիվների նույնությունները։ Այլանվան լուծումը չպետք է վերաուղղորդի հաստատված արժույթի, պահպանության կամ վճար ստացող հաշվի նույնությունները։

## 2. Ստեղծել և ֆինանսավորել հովանավոր ծրագիր {#_2-create-and-fund-a-sponsor-program}

Ծրագրի ID-ն ունի `<canonical-sponsor-account>/<program-name>` ձևը։ Այն պատրաստեք ընթացիկ SDK-ի և տվյալների մոդելի տրամադրած տիպավորված հրահանգներով․

| Հրահանգ | Նպատակ |
| --- | --- |
| `CreateFeeSponsorProgram` | Ստեղծել նախապատրաստված ծրագիրը՝ պարտադիր վճարման հաշվով։ |
| `StageFeeSponsorProgramRevision` | Սահմանել համապատասխանության, գործողությունների և բյուջեի մեկ անփոփոխ քաղաքականություն։ |
| `EnrollFeeSponsorBeneficiary` | Շղթայի վրա գրանցել համապատասխան շահառուին։ |
| `FundFeeSponsorProgram` | Ակտիվները փոխանցել պահպանության և մուտքագրել ճշգրիտ ծրագրային պահոցին։ |
| `ActivateFeeSponsorProgramRevision` | Պլանավորել նախապատրաստված տարբերակի ակտիվացման ամենավաղ բարձրությունը։ |

Ծրագրի կառավարումը լիազորում է հովանավորը կամ ճշգրիտ լիազորված կառավարիչը։ Միջոցների դուրսբերումը պահանջում է հենց հովանավորին և գումարը վերադարձնում է միայն ծրագրի գրանցված վճարման հաշվին՝ երբ ծրագիրը դադարեցված է կամ փակման փուլում։

Յուրաքանչյուր տարբերակ սահմանում է՝

- բացահայտ գրանցում կամ գրանցում՝ թույլատրված լռելյայն երթուղու համապատասխանության հետ միասին,
- թույլտվության և արգելքի կանոններ՝ բնիկ հրահանգների ճշգրիտ փոխանցման ID-ների կամ պայմանագրի հասցեների, կոդի հեշերի և մուտքի կետերի նկատմամբ,
- յուրաքանչյուր ակտիվի համար գործարքի, բլոկի, ծրագրի դարաշրջանի և շահառուի դարաշրջանի սահմաններ,
- պահուստի նվազագույն մակարդակ և դարաշրջանի դետերմինիստական երկարություն։

Արգելքի կանոնը գերակայում է թույլտվության կանոնին։ Տվյալների տարածքի `fee_sponsor_program_id`-ը լռելյայն երթուղու համապատասխանություն է տալիս միայն այն դեպքում, երբ ակտիվ տարբերակն այն թույլ է տալիս․ գործարքը միևնույն է պետք է նշի իր ճշգրիտ ծրագիրն ու տարբերակը։ Ակտիվացումը կարող է հետաձգվել, մինչև նախորդ տարբերակի չավարտված հատկացումների ժամկետը լրանա։

Հովանավոր պահոցի ակտիվները պետք է օգտագործեն `Global` մնացորդի քաղաքականությունը։ Միայն հովանավորի սովորական հաշվի ֆինանսավորումը չի ֆինանսավորում մեկուսացված ծրագրային պահոցը, և մի ծրագիր չի կարող ծախսել մյուսի մնացորդը։

## 3. Ստանալ գնառաջարկ, ստորագրել և ուղարկել ճշգրիտ գործարքը {#_3-quote-sign-and-submit-the-exact-transaction}

SDK ինտեգրումը կատարում է հետևյալ քայլերը․

1. Կառուցեք չստորագրված `TransactionPayload`՝ լիազորված սուբյեկտով, կատարվող բովանդակությամբ, ժամանակային նշումներով, nonce-ով, մետատվյալներով, հովանավոր ծրագրի ճշգրիտ տարբերակով և անհրաժեշտ գազի սահմանով։ Գանձումների առավելագույնները սկզբում կարող են դատարկ լինել։
2. Հաշվով ստորագրեք `POST /v1/fees/quote` հարցումը՝ `{"payload": <payload>}` բովանդակությամբ։ Հարցման ստորագրողը պետք է լինի գործարքի լիազորված սուբյեկտը։
3. Ուսումնասիրեք դիտարկված բարձրությունը, որոշված տվյալների տարածքի երթուղին, վճարի բաղադրիչները, գանձման աղբյուրը և հովանավորի կարողությունը։ Ստուգեք, որ պատասխանը պահպանում է ընտրված վճարողին, տարբերակը և գազի սահմանը։
4. Միայն `payload.fee_payment`-ը փոխարինեք առաջարկվող մտադրությամբ, ապա ստորագրեք և ուղարկեք ճշգրիտ այդ բովանդակությունը։
5. Հետևեք գործարքին մինչև վիճակից որոշված `Applied` վերջնականացումը և պահեք դրա անդորրագիրը՝ ներառյալ իրական հովանավոր ծրագիրը, տարբերակը և գանձումը։

Գնառաջարկը դիտարկում է գրանցամատյանը, այն կարողություն չի ամրագրում։ Հերթի ընդունումը կրկին ստուգում է համապատասխանությունը և ամրագրում ստորագրված առավելագույնները։ Հովանավորի մերժումը մերժում է գործարքը՝ առանց օգտատիրոջից գանձման անցնելու։

CLI-ն բացահայտ նշում է նույն վճարի աղբյուրը։ Օրինակ՝ երբ ծրագիրը թույլ է տալիս ակտիվի հենց այս փոխանցումը, իսկ հաշիվը համապատասխանում է պահանջներին․

```bash
iroha --config ./user.client.toml \
  --fee-payer sponsor \
  --fee-program '<SPONSOR_CANONICAL_I105>/team-payments' \
  --fee-program-revision 1 \
  ledger asset transfer \
  --definition '<ASSET_DEFINITION_BASE58>' \
  --account '<USER_CANONICAL_I105>' \
  --to '<RECIPIENT_CANONICAL_I105>' \
  --quantity 1
```

Օգտագործեք ձեր ցանցի ակտիվ տարբերակը և ճշգրիտ նույնացուցիչները։ Օգտատիրոջ կարգավորումը պարունակում է միայն այդ օգտատիրոջ ստորագրողը․ համապատասխան հովանավորվող գործարք ուղարկելու համար հովանավորի մասնավոր բանալին անհրաժեշտ չէ։

## 4. Որոշել՝ արդյոք օգտատերը վճարում է հավելվածային վճար {#_4-decide-whether-the-user-pays-an-application-fee}

Հովանավորը կարող է վճարել համընդհանուր վճարները, մինչ հավելվածը օգտատիրոջից ոչինչ չի գանձում։ Եթե հավելվածը հավաքում է տեղային տոկեն, այդ փոխանցումը կամ պայմանագրի կանոնը բացահայտ գրեք օգտատիրոջ ստորագրած կատարվող բովանդակությունում։ Յուրաքանչյուր գործողություն ներառեք հովանավորի տարբերակի քաղաքականության մեջ և ստուգեք ամբողջ բովանդակության գնառաջարկը։ Ցանցային վճարի մտադրությունից մի՛ ենթադրեք հավելվածի տոկենի փոխանցում։

## Ախտորոշել մերժումը {#diagnose-a-refusal}

Օգտագործեք հանգույցի վերադարձած կայուն վճարային կոդը և շտկման մանրամասները․

| Կոդ | Ստուգում |
| --- | --- |
| `program_not_found` | Ծրագրի ճշգրիտ կանոնական նույնությունը։ |
| `revision_not_active`, `program_not_active` | Տարբերակի ակտիվացումը և ծրագրի կյանքի ցիկլը։ |
| `beneficiary_not_eligible` | Գրանցումը կամ թույլատրված լռելյայն երթուղու համապատասխանությունը։ |
| `operation_not_allowed`, `operation_denied` | Յուրաքանչյուր ճշգրիտ ստորագրված գործողությունը և արգելքի կանոնը։ |
| `invalid_gas_limit`, `signed_limit_exceeded` | Գազի սահմանը և ստորագրված առավելագույնները՝ նոր գնառաջարկի նկատմամբ։ |
| `vault_insufficient` | Այս ծրագրի ճշգրիտ արժութային պահոցի ֆինանսավորված մնացորդը։ |
| Բյուջեի սպառման կոդեր | Գործարքի, բլոկի, ծրագրի դարաշրջանի և շահառուի դարաշրջանի կարողությունը։ |

Անորոշ արդյունքով ուղարկումը հետաքննելիս պահեք սկզբնական գործարքի հեշը և վճարի մերժման մանրամասները։ Փոխարինող գործարք կառուցելուց առաջ հաստատեք դրա վիճակը։
