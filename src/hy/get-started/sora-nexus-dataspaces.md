# Մշակում SORA Nexus-ում՝ Taira-ի և Minamoto-ի միջոցով {#build-on-sora-3-taira-and-minamoto}

SORA Nexus-ն աշխատում է Iroha 3-ի հիման վրա։ Նախ մշակեք և փորձարկեք հավելվածը Taira-ում։ Հաճախորդի նույն կարգավորումը Minamoto տեղափոխեք միայն այն ժամանակ, երբ ունենաք հիմնական ցանցի առանձին բանալիներ, վճարները մարելու համար իրական XOR և արտադրական միջավայրում աշխատելու թույլտվություն։

Այս ուղեցույցը ցույց է տալիս, թե ինչպես կարգավորել Iroha հաճախորդը SORA Nexus-ի երկու հանրային ցանցերի համար։

- Taira փորձարկման ցանցը՝ `https://taira.sora.org`
- Minamoto գլխավոր ցանց՝ `https://minamoto.sora.org`

Օգտագործեք Taira-ն ինտեգրման փորձարկումների, faucet-ի միջոցներով գրելու ստուգումների և տեղակայման փորձերի համար։ Minamoto-ն օգտագործեք միայն արտադրությանը պատրաստ հիմնական ցանցի գործունեության համար։ Երկու ցանցերն էլ վճարներ են գանձում XOR-ով։

- Taira-ն օգտագործում է հանրային faucet-ից ստացված testnet XOR-ը։
- Minamoto-ն օգտագործում է իրական XOR։ Minamoto-ի համար faucet չկա։

## Շինարարների ճանապարհը {#builder-path}

Գործնական հոսքը հետեւյալն է.

1. Կառուցեք Taira-ին միացող հաճախորդը և օգտագործեք հանրային `universal` տվյալների տարածքը։
2. Ավելացրեք ստորագրող եւ ֆինանսավորեք այն Taira faucet:
3. Օգտագործեք ձեր հավելվածի տրամաբանությունը Taira - ի դեմ, մինչեւ ձանձրալի եւ դիտարկելի չլինեն սխալները:
4. Ստեղծեք առանձին Minamoto ստորագրող, ֆինանսավորել այն իրական XOR եւ տեղափոխել միայն նույն ապացուցված գործառույթները mainnet:

## 1. Հասկացեք, թե ինչ եք նախապատրաստում {#_1-understand-what-you-are-setting-up}

SORA Nexus-ում տվյալների տարածքների կատալոգը սահմանում է տվյալների տարածքները։ Գոտիների կատալոգը գոտիները սահմանում է առանձին․ յուրաքանչյուր գոտի հղվում է մեկ տվյալների տարածքի, իսկ մեկ տվյալների տարածքը կարող է ունենալ մի քանի գոտի։ Հաճախորդը չի ստեղծում նոր հանրային տվյալների տարածք՝ պարզապես փոխելով `client.toml`-ը։ Հաճախորդի կարգավորումն անում է երկու բան․

1. հյուրին ուղղում է աջ Torii վերջային կետ
2. ընտրում է ցանցային համատեքստը և իր կանոնական հաշվի ստորագրման բանալին

`AccountId`-ն միշտ կանոնական է և դոմեն չի պարունակում, իսկ `client.toml`-ը դոմենի կարգավորում չունի․ `[account].profile`-ն ընտրում է միայն ցանցի I105 նախածանցը։ Դոմենի համատեքստը պատկանում է այլանուններին և դոմենին պատկանող օբյեկտներին։ Հավելվածների մեծ մասի համար սկսեք հանրային `universal` տվյալների տարածքից։ Դոմենի համատեքստն ունի `domain.dataspace` ձևը, օրինակ՝

```text
wonderland.universal
```

Եթե ձեզ պետք է նոր կազմակերպական տվյալների տարածք, պատրաստեք կատալոգի և երթուղավորման առաջարկ՝ սովորական հաճախորդի հաշվից այն գրանցելու փորձի փոխարեն։ Ստորև տես [Նոր տվյալների տարածքի տրամադրում](#_8-provision-a-new-data-space) բաժինը։

## 2. Ստուգեք հանրային Torii վերջնական կետը {#_2-check-the-public-torii-endpoint}

Ստուգեք Taira փորձնական ցանցի վիճակը `curl` և `jq` գործիքներով։ Ստուգման համար բանալիներ կամ տեղային հանգույց անհրաժեշտ չեն։

```bash
curl -fsS https://taira.sora.org/status \
  -H 'Accept: application/json' \
  | jq '{peers, blocks, txs_approved, queue_size}'
```

Ստուգեք հանգույցի տրամադրած տվյալների տարածքների և գոտիների տեսքը․

```bash
curl -fsS https://taira.sora.org/status \
  -H 'Accept: application/json' \
  | jq '.teu_lane_commit[] | {lane_id, alias, dataspace_id, dataspace_alias, visibility}'
```

Նախքան Minamoto-ն օգտագործելը՝ օպերատորի հետ ճշտեք հիմնական ցանցի ծառայության հասցեն և ստուգեք, որ TLS վկայագիրը համապատասխանում է հոսթի անվանը։

## Taira MCP գործակալների համար {#taira-mcp-for-agents}

Taira նաեւ բացահայտում է Torii- ի ներկառուցված մոդելի համատեքստային պրոտոկոլ (MCP) կամուրջը գործակալների վազման ժամանակների համար: Օգտագործեք այն, երբ գործակալին անհրաժեշտ է կենդանի թեստնետի ընթերցումներ, սցենտային ախտորոշում կամ սերտորեն վերանայված գրքի փորձարկումներ ՝ առանց նախ կառուցելու հարմարվողական Torii հաճախորդ.

|Կարգավորումը|Գինը |
| --- | --- |
|MCP վերջնական կետը |`https://taira.sora.org/v1/mcp` |
|ցանցի արմատը |`https://taira.sora.org` |
|Նախատեսված օգտագործումը |Taira թեստային ցանցի ընթերցումներ եւ գազանի կողմից ֆինանսավորվող գրելու փորձեր |
|Արտադրանքի համարժեք |Մի ուղղեք այս գրառումը Minamoto հասցեին, եթե հիմնական ցանցի MCP վերջային կետը եւ արտանետման վերահսկողությունները բացարձակապես հաստատված չեն: |

Կամուրջն ընդունում է միայն վիճակ չպահող JSON-RPC `POST` հարցումներ։ Նախքան ստորագրման նյութ ավելացնելը ստուգեք դրա հայտնաբերման մետատվյալները․

```bash
curl -fsS https://taira.sora.org/v1/mcp \
  -H 'Accept: application/json' \
  -H 'Content-Type: application/json' \
  -H 'MCP-Protocol-Version: 2026-07-28' \
  -H 'Mcp-Method: server/discover' \
  -d '{"jsonrpc":"2.0","id":1,"method":"server/discover","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{}}}}' \
  | jq '{versions: .result.supportedVersions, server: .result._meta["io.modelcontextprotocol/serverInfo"].name, toolset: .result.capabilities.extensions["org.hyperledger.iroha/tools"].toolsetVersion}'
```

Կոնֆigurել URL որպես օգտագործողի տեղական MCP սերվեր գործակալի վազման ժամանակ. Մի commit գործակալի MCP կոնֆիգը, API տոքերները, փոխանցված նույնականացման վերնագրերը, `authority`, կամ `private_key` արժեքները այս փաստաթղթերի repo կամ ծրագրի repo:

Գործակալ prompt կանոններ, որոնք աշխատում են լավ Taira:

- Բացահայտեք MCP սերվերի գործիքները, նախքան նրանց զանգելը; կրկին բացահայտեք, եթե սերվերը հաղորդում է `listChanged`:
- Նախընտրում են կուրացված `iroha.*` գործիքները 'փոխարինված `torii.*` աշխատանքային գործիքներին:
- Սկսեք կարդալ միայն. ստուգեք վիճակը, հաշիվները, ակտիվները, կեղծանունները, բլոկերը, կառավարման վիճակը եւ գործարքի կարգավիճակը նախքան գրելու առաջարկը:
- Պահանջել է հստակ մարդկային հրահանգներ կենդանի թեստային ցանցի մուտացիաներից առաջ: Նախապես ստորագրված գործարքի փաթեթների համար օգտագործեք `iroha.transactions.submit_and_wait`, որպեսզի գործակալը սպասի արդյունքին, այլ ոչ թե միայն ներկայացնի:
- Գործակալի արձագանքում ամփոփեք գործարքի շիշերը, վերջնական վիճակը եւ սերվերի հավաստագրման սխալները:

### Գործակալների հետ մշակման աշխատանքային ընթացքը {#development-workflow-with-agents}

Օգտագործեք գործակալներ որպես մշակման օգնական Iroha հաճախորդների, փոխանցումների ստեղծողների, ախտորոշիչ սցենարների եւ թեստնետի վազքի գրքերի համար: Պահպանեք գործակալի լիազորությունները սահմանափակ. Այն կարող է ստուգել կոդը, կարդալ Taira վիճակը, առաջարկել փոփոխություններ եւ իրականացնել տեղական փորձարկումներ, բայց այն չպետք է փոխի կենդանի ցանցը, քանի դեռ մարդը հաստատում է ճշգրիտ գործողությունը:

Գործնական աշխատանքային ընթացքը հետեւյալն է.

1. Խնդրեք գործակալին ստուգել համապատասխան փաստաթղթերը, SDK կոդը, CLI հրամանը կամ MCP գործիքային սխեման, նախքան կոդը գրելը:
2. Խնդրեք գործակալին նախ գրել հաճախորդի ամենափոքր ուղին. վիճակի ստուգում, հաշիվների որոնում, alias լուծումը կամ մնացորդի որոնում:
3. Գործարքի կառուցման կոդը ավելացնել միայն այն բանից հետո, երբ միայն ընթերցված զանգերը աշխատում են Taira դեմ:
4. Պահպանեք կենդանի ցանցի փորձարկումների ընտրությունը, օրինակ՝ `TAIRA_LIVE=1` ետեւում, այնպես որ սովորական միավորային փորձարկման ընթացքը երբեք չի ծախսում փորձարկման ցանցի միջոցներ կամ կախված է ցանցի առկայությունից:
5. Պահանջում է գործակալին զեկուցել ցանցի արմատը, շղթան, լիազոր հաշվի հաշիվը, հրահանգների ամփոփումը, վճարային ակտիվը եւ սպասվող վիճակի փոփոխությունը նախքան ցանկացած գործարք ներկայացնելուց:
6. Վերանայեք ստեղծված կոդը գաղտնի կառավարման, կրկին փորձելու վարքագծի, idempotency- ի եւ մերժման կառավարման համար ՝ այն առաջադրելուց առաջ CI կամ հիմնական ցանցի աշխատանքային հոսքերի վրա:

Մշակման ընթացքում MCP-ի միայն ընթերցման հրամաններով կարելի է գտնել հաշվի ակտիվները, որոշել այլանվանը համապատասխանող գրառումը, գտնել բլոկ կամ գործարք, ստանալ գործարքների ցանկը և ստուգել մշակման ընթացքի վիճակը։ Կատարեք այս ստուգումները նախքան ստորագրված տվյալներ ուղարկելը։

```text
Use Taira MCP as a read-only inspector while developing this Iroha feature.
Inspect available iroha.* tools, verify the target account and asset state,
then update the client code. Do not submit transactions unless I explicitly
say "submit this transaction".
```

### Գործարքի աշխատանքային հոսքը գործակալների միջոցով {#transaction-workflow-through-agents}

MCP կամուրջը կարող է ներկայացնել ստորագրված Iroha գործարք, բայց այն չի վերացնում գործարքի սովորական պահանջները: Գործարքի համար դեռ պետք է ճիշտ լիազոր հաշիվ, թույլտվություններ, վճարային ֆինանսավորում, շղթա ID, մեթադատա եւ ստորագրություն:

Հատուկ Iroha գործարքների համար նախ ստեղծեք եւ ստորագրեք գործարքի փաթեթը SDK կամ CLI անունով, այնուհետեւ ներկայացրեք գործակալին միայն կանոնական ստորագրված գործարքի բայտներ, որոնք կոդավորված են `body_base64`։ Գործակալը կարող է փաթեթը ներկայացնել `iroha.transactions.submit_and_wait` կամ `iroha.transactions.submit` եւ հարցազրույց՝ `iroha.transactions.wait` անունով:

Մի տեղադրեք մասնավոր բանալիները գործակալի հրահանգի մեջ: Եթե գործակալը պետք է կառուցի գործարք, ուղղեք այն տեղական կոդին, որը բեռնում է գաղտնիքները օգտագործողի վազման ժամանակ Շրջակա միջավայրի, ստեղնաշարի, սարքավորումների ստորագրող կամ անտեսված testnet կոնֆիգ ֆայլը. գործակալը երբեք չպետք է գրի հիմնական նյութը Markdown-ում, թեստային տվյալներում, օրագրերում կամ հանձնարարություններում։

Առեւտրի ներկայացնելուց առաջ գործակալը պետք է պատրաստի կարճ գործարքի ծրագիր.

- `network`: Taira փորձարկման ցանցի արմատը եւ շղթան ID
- `authority`: հաշիվ, որը ստորագրում է եւ վճարում է վճարներ
- `instructions`: գրանցում, մինետ, այրում, փոխանցում, մետադատա, թույլտվություն կամ պայմանագրի զանգի ամփոփում:
- `fee asset`: այն ակտիվը, որը կվճարվի Taira:
- `preflight reads`: հաշիվ, ակտիվների մնացորդ, թույլտվություններ, անանուններ կամ արդեն կատարված բլոկային ստուգումներ
- `expected result`: այն վիճակը, որը պետք է տեսանելի լինի հաստատումից հետո
- `idempotency`: ինչ է տեղի ունենում, եթե նույն խնդրանքը կրկին փորձարկվի

Ներկայացումից հետո գործակալին ստիպեք սպասել վերջնական կարգավիճակի, ապա ստուգեք վիճակի փոփոխությունը ընթերցման հարցումներով: Օգտակար ավարտի զեկույցը ներառում է.

- գործարքային շիշ
- վերջնական կարգավիճակը, ինչպիսիք են `Committed`, `Applied`, `Rejected` կամ `Expired`:
- բլոկի կամ հետազոտողի մանրամասները, երբ դրանք մատչելի են
- ստուգման ընթերցման արդյունքները
- մերժման հաղորդագրությունը եւ արդյոք ձախողումը նման է թույլտվությունների, վճարների, հավաստիացման, հնացած վիճակի կամ վերջնական կետերի մատչելիության

Օրինակ պահված արագություն.

```text
Prepare a Taira transaction plan, but do not submit yet. Use MCP reads to
verify the authority account, fee balance, target asset or alias, and current
transaction status if a hash already exists. Show the exact instructions and
expected post-state. Wait for my explicit "submit" message before calling
iroha.transactions.submit_and_wait.
```

Եթե ստորագրված փաթեթը արդեն պատրաստված է.

```text
Submit this pre-signed Taira transaction envelope with
iroha.transactions.submit_and_wait. Use the provided body_base64 only; do not
ask for private keys. Wait for a terminal status, then verify the resulting
state with read-only iroha.* tools and report the hash, status, and
verification result.
```

Taira MCP-ը վերաբերվում է որպես հանրային փորձարկման ցանցի վերահսկողության մակերես: Taira բանալիները, փորձարկման համակարգը XOR, faucet հաշիվները եւ կանարի ստորագրիչները մեկ անգամ օգտագործելի են եւ պետք է առանձին մնան Minamoto բանալիցներից եւ արտադրական ազատման աշխատանքային հոսքերից։

## Խաղալի օրինակներ, որոնք կարող եք փորձել հիմա {#toy-examples-you-can-try-now}

Այս օրինակներում Taira-ի տվյալները կարդացվում են առանց հաշվի բանալիների։

Ցուցադրեք Taira-ի տրամադրած հանրային տվյալների տարածքի գոտիները․

```bash
curl -fsS https://taira.sora.org/status \
  -H 'Accept: application/json' \
  | jq -r '.teu_lane_commit[]
    | select(.visibility == "public")
    | [.lane_id, .alias, .dataspace_alias, .visibility, .storage_profile, .block_height]
    | @tsv'
```

Ստեղծեք փոքրիկ Node.js վիճակային հետաքննություն վահանակի, բոտի կամ տեղակայման ստուգման համար.

```bash
node --input-type=module <<'EOF'
const response = await fetch('https://taira.sora.org/status', {
  headers: { Accept: 'application/json' },
});
if (!response.ok) throw new Error(`Taira HTTP ${response.status}`);
const status = await response.json();
const publicLanes = status.teu_lane_commit
  .filter((lane) => lane.visibility === 'public')
  .map((lane) => `${lane.alias}@${lane.dataspace_alias}:${lane.block_height}`)
  .join(', ');
console.log(`Taira: ${status.blocks} blocks, ${status.queue_size} queued, public lanes ${publicLanes}`);
EOF
```

Առաջին գրելու կողմի խաղալիքը պետք է լինի Taira faucet պնդում: Այն օգտագործում է փորձարկման ցանց XOR եւ երբեք չպետք է ուղղվի Minamoto հասցեին.

## 3. Ստեղծեք Taira հաճախորդի կարգավորումը {#_3-create-a-taira-client-config}

Ստեղծեք կոճակային զույգ, եթե դուք արդեն չունեք մեկը:

```bash
kagami keys --algorithm ed25519 --out-dir ./taira-client-key
```

Ստեղծեք `taira.client.toml`:

```toml
chain = "fc56984b-2be7-431d-840e-21514d1883f0"
# The exact `network_id` from https://taira.sora.org/v1/accounts/capabilities
network_id = "hash:4978D0BD15FC32B834672B27BBD8A03653B1DF060A1EEE7E9374D29AF3886D91#6774"
torii_url = "https://taira.sora.org/"

[account]
profile = "taira"
public_key = "<ED25519_PUBLIC_KEY_HEX>"
private_key = "<ED25519_PRIVATE_KEY_HEX>"

[transaction]
time_to_live_ms = 100000
status_timeout_ms = 15000
nonce = false
```

Վերին մակարդակի `chain`-ը Taira-ի գործարքների շղթայի ճշգրիտ ID-ն է, իսկ `network_id`-ն ցանցի ճշգրիտ նույնությունն է, որին կապվում է յուրաքանչյուր ստորագրություն։ Կարգավորեք `network_id`-ից կամ `network_id_file`-ից ճիշտ մեկը։ `[account].profile = "taira"` կարգավորումն առանձին ընտրում է Taira-ի I105 շղթայի տարբերակիչը։ Շղթայի ID-ն չի ընտրում հաշվի պրոֆիլը։

Կատարեք միայն ընթերցման ստուգում.

```bash
iroha --config ./taira.client.toml --output-format text ops sumeragi status
```

Նախքան գրելու թեստերը կատարեք հանրային Taira ախտորոշումը.

```bash
iroha taira doctor --public-root https://taira.sora.org --json
```

Մինչ վճարովի գրառման գործողություններ կատարելը համալրեք Taira հաշիվը փորձնական միջոցների տրամադրման ծառայության միջոցով։ Դրա նախապատրաստված ընթացքը նկարագրված է [Ստանալ փորձնական ցանցի XOR Taira-ում](#_4-get-testnet-xor-on-taira) բաժնում։

Հաշվի համալրումից հետո ստորագրված գրանցամատյանային հաղորդագրության հրահանգը կարող է ծառայել որպես գրառման կամընտիր պարզ ստուգում։ Յուրաքանչյուր ուղարկվող գործարք նշում է իր վճարողին, իսկ CLI-ն ստորագրելուց առաջ հաշվարկում է վճարի ճշգրիտ գնառաջարկը․

```bash
iroha --config ./taira.client.toml --fee-payer authority \
  tx ping --msg "taira smoke test"
```

Հրամանը սպասում է հաստատմանը։ Taira-ն հանրային փորձնական ցանց է, ուստի հերթի հագեցումը կարող է ձախողել կապի փորձնական գրառումը, նույնիսկ երբ միջոցների տրամադրման ծառայությունն աշխատում է։ Եթե `taira doctor`-ը հայտնում է հագեցած հերթի մասին, կամ փորձնական գրառումը վերադարձնում է `PRTRY:NEXUS_FEE_ADMISSION_REJECTED`, սպասեք և կրկին փորձեք՝ նախքան դա հաճախորդի կարգավորման սխալ համարելը։

Առանց հսկողության պարզ ստուգումների համար կապի փորձնական գրառումը տեղադրեք սահմանափակ կրկնափորձերի ցիկլում․

```bash
ok=false
for attempt in 1 2 3 4 5; do
  iroha --config ./taira.client.toml --fee-payer authority \
    tx ping --msg "taira smoke test" && ok=true && break

  sleep 60
done

test "$ok" = true
```

Դադարեցրեք կրկնակի փորձարկումը, եթե `iroha taira doctor` ցույց է տալիս ծանր ձախողումներ: Սյունիքի հագեցածությունը եւ վճարների ընդունման մերժումները անցումային հանրային թեստային ցանցի պայմաններ են. DNS, TLS կամ `status = "fail"` ախտորոշումները չեն:

## Ստեղծեք SORA Nexus հաշիվ ID {#generate-a-sora-nexus-account-id}

SORA Nexus հաշվի ID-ն կանոնական I105 հասցե է՝ ստացված հաշվի բաց բանալիից և նպատակային ցանցի նախածանցից։ Նույն բաց բանալին Taira-ում և Minamoto-ում կոդավորվում է տարբեր ID-ներով, իսկ արտադրական օգտագործողները պետք է Minamoto-ի համար ստեղծեն առանձին բանալիների զույգ։

Ստեղծել կամ բեռնել Ed25519 կոճակային զույգը, որը վերահսկում է հաշիվը:

```bash
kagami keys --algorithm ed25519 --out-dir ./nexus-account-key
```

Հասարակական բանալին Taira հաշիվի ID մեջ փոխակերպել

```bash
iroha tools address convert --profile taira <ED25519_PUBLIC_KEY_HEX>
```

Փոխակերպել Minamoto հանրային բանալին' հիմնական ցանցի նախադրյալով.

```bash
iroha tools address convert --profile minamoto <ED25519_PUBLIC_KEY_HEX>
```

Ստացված հաշվի ID-ն օգտագործեք ամենուր, որտեղ SORA Nexus API-ն կամ CLI հրամանը պահանջում է կանոնական հաշվի ID, օրինակ՝ մնացորդի հարցումներում, հաշվի խիստ դաշտերում կամ այլանվան կապումներում։ Համապատասխան փակ բանալին պահեք հաճախորդի կարգավորումներում և ընտրեք նույն հանրային ցանցը՝ `[account].profile = "taira"` կամ `[account].profile = "minamoto"`։

ID ստեղծելը ինքնուրույն չի ստեղծում ֆինանսավորվող շղթայի վրա հաշիվ: Taira -ի վրա faucet կարող է ստեղծել եւ ֆինանսավորել թեստային ցանցի գրառումների համար հաշիվը: Minamoto -ին, օգտագործեք հաստատված հիմնական ցանցի ներմուծում կամ գանձարանի հոսք:

### Գլխավորների պահեստավորում եւ կրկնօրինակում {#key-storage-and-backup}

Հաշիվը ID եւ հանրային բանալին կարող են կիսվել: Համատեղելի մասնավոր բանալին, գաղտնաբառը, սերմերը եւ վերականգնման նյութը պետք է պահվեն որպես գաղտնի:

Օգտագործեք SORA Nexus հաշիվների համար հետեւյալ վարքագիծը.

- Գաղտնի բանալիները պահեք կոդավորված գաղտնաբառերի կառավարիչում, սարքավորումների աջակցությամբ հիմնախնդիրների խանութում կամ նվիրված ստորագրման ծառայության մեջ: Մի commit բանալիները աղբյուրի վերահսկողությանը կամ թողեք արտադրական բանալիներ շելի պատմության մեջ, օրենսգրքում, զրույցում, տոմսերում կամ չկոդավորված կրկնօրինակումներ.
- Օգտագործեք յուրահատուկ բարձր էնդրոպիկ գաղտնաբառ յուրաքանչյուր պահեստի կամ արտադրության ստորագրողի համար: Պահպանեք գաղտնաբերերը գաղտնաբերի կառավարիչում կամ բաժանված պահեստավորման գործընթացում, այլ ոչ թե նույն ֆայլում կամ կրկնօրինակի փաթեթում, ինչպես կոդավորված մասնավոր բանալին:
- Պահպանեք Taira եւ Minamoto բանալիները առանձին: Բարեւեք Taira բանալիներին որպես մեկ անգամ օգտագործվող փորձարկման ցանցի նյութ, իսկ Minamoto բանալիններին՝ որպես արտադրական միջոցների մարմին:
- Պահպանեք մասնավոր բանալին, հանրային բանալը, հաշիվը ID, հաշիվի պրոֆիլը եւ ցանկացած հաշիվի վերականգնման կամ պահեստային գրառում, որոնք անհրաժեշտ են ստորագրողի վերականգնելու համար: Բացառական բանալին առանց ցանցի համատեքստի հեշտ է չարաշահմանել վերականգնման ընթացքում:
- Պահպանեք առնվազն մեկ կոդավորված օֆլայն պահեստ եւ մեկ աշխարհագրական առանձին կոդավորված պահեստ արտադրության ստորագրողների համար: Փորձեք վերականգնումը միայն ընթերցման փոքր գործողությամբ ՝ նախքան պատուհանի վրա կախված լինելը:
- Շրջեք կամ փոխարինեք ստորագրողին, եթե գաղտնի բանալին, գաղտնաբառը, պահեստային մեդիան կամ ստորագրող հյուրընկալողը կարող են հայտնվել:

Ավելի մանրամասն տեղեկություններ ստանալու համար դիտեք [Սպառման կրիպտոգրաֆիկ բանալիները](/hy/guide/security/storing-cryptographic-keys.md) եւ [Խաղանձի անվտանգությունը](/hy/guide/security/password-security.md).

## 4. Ստացեք թեստային XOR Taira-ից {#_4-get-testnet-xor-on-taira}

Պահանջեք փորձնական ցանցի XOR՝ CLI-ի միջոցների տրամադրման նախապատրաստված ընթացքով։ Ծառայությունը համալրում է `taira.client.toml`-ում կարգավորված հաշիվը և նախ գրանցում է այն, եթե հաշիվը դեռ գոյություն չունի։ Ընթացքը հետևյալն է․

1. Կարդացեք միջոցների տրամադրման հանրային քաղաքականությունը՝ ծառայության լիազորված սուբյեկտը, վճարի ակտիվը և գումարը։
2. Նախապատրաստեք պահանջը։ CLI-ն լուծում է աշխատանքի ապացույցի խնդիրը, ստուգում է Torii-ի պատրաստած ու ստորագրած ճշգրիտ գործարքը և այն պահում է մասնավոր մատյանի պանակում՝ առանց ուղարկելու։
3. Պահված գործարքն ուղարկեք մեկ անգամ։
4. Վճարովի գրառման գործողություններ ուղարկելուց առաջ սպասեք, մինչև ակտիվի մնացորդը տեսանելի դառնա։

Կարդացեք քաղաքականությունը․

```bash
curl -fsS https://taira.sora.org/v1/accounts/faucet/policy \
  -H 'Accept: application/json' \
  | tee ./taira-faucet-policy.json \
  | jq .
```

Պատասխանն ունի հետեւյալ ձեւը.

```json
{
  "schema_version": 1,
  "network_id": "hash:4978D0BD15FC32B834672B27BBD8A03653B1DF060A1EEE7E9374D29AF3886D91#6774",
  "network_prefix": 369,
  "authority": "<TAIRA_FAUCET_AUTHORITY_I105>",
  "asset_definition_id": "6TEAJqbb8oEPmLncoNiMRbLEK6tw",
  "amount": "25000"
}
```

Քաղաքականությունը չստորագրված հայտնաբերման տվյալներ է։ Ավտոմատացումը պետք է նախապես ամրագրի ակնկալվող լիազորված սուբյեկտը, ակտիվի սահմանումը և գումարը՝ յուրաքանչյուր պատասխանին վստահելու փոխարեն։ `prepare`-ը մերժում է նախապատրաստված գործարքը, եթե այն տարբերվում է ձեր փոխանցած արժեքներից։

Նախապատրաստեք և ուղարկեք պահանջը․

```bash
export TAIRA_FEE_ASSET="$(
  jq -er '.asset_definition_id' ./taira-faucet-policy.json
)"

iroha --config ./taira.client.toml --fee-payer authority \
  taira account faucet prepare \
  --journal ./taira-faucet \
  --issuer "$(jq -er '.authority' ./taira-faucet-policy.json)" \
  --asset-definition "$TAIRA_FEE_ASSET" \
  --amount "$(jq -er '.amount' ./taira-faucet-policy.json)"

iroha --config ./taira.client.toml \
  taira account faucet submit --journal ./taira-faucet
```

`prepare`-ը մատյանի պանակը ստեղծում է մասնավոր հասանելիությամբ և հրաժարվում է փոխարինել արդեն գոյություն ունեցողը, ուստի յուրաքանչյուր պահանջի համար օգտագործեք նոր պանակ։ Միջոցների տրամադրումը հանրային փորձնական ցանցի ծառայություն է։ Եթե `submit`-ը հայտնում է `Pending`, սպառում է սպասման ժամանակը կամ ստանում է `502`, գործարկեք `taira account faucet resume` նույն կարգավորումներով և մատյանով՝ մեկ այլ պահանջ պատրաստելու փոխարեն։ Աշխատանքի ապացույցի հնացած հենակետը ձախողում է `prepare`-ը․ նորից նախապատրաստեք նոր մատյանի պանակում։

Այնուհետեւ հարցում անցկացրեք ֆինանսավորվող ակտիվի վերաբերյալ, նախքան վճարովի գործարքները ներկայացնելուց:

```bash
iroha --config ./taira.client.toml ledger asset get \
  --definition "$TAIRA_FEE_ASSET" \
  --account <TAIRA_I105_ACCOUNT_ID>
```

Եթե պահանջը կատարվել է, բայց ակտիվը դեռ տեսանելի չէ, սպասեք և կրկնեք ընթերցումը՝ գրառումներ ուղարկելուց առաջ։

Փլաները նախատեսված են միայն Taira թեստնետային միջոցների համար: Չօգտագործեք XOR փորձնետային ցանցը, փլաների հաշիվները կամ Taira կանարի ստորագրիչները Minamoto հոսքներում.

## 5. Ստեղծեք Minamoto հաճախորդի կարգավորումը {#_5-create-a-minamoto-client-config}

Նախքան Minamoto-ն օգտագործելը՝ օպերատորի հետ ճշտեք հիմնական ցանցի ծառայության հասցեն և ստուգեք, որ TLS վկայագիրը համապատասխանում է հոսթի անվանը։

Օգտագործեք Minamoto համար առանձին կոճակային զույգ, իսկ հիմնական ցանցի համար մի օգտագործեք Taira կոճակները.

Ստեղծեք `minamoto.client.toml`:

```toml
chain = "00000000-0000-0000-0000-000000000753"
# The exact `network_id` from https://minamoto.sora.org/v1/accounts/capabilities
network_id = "<MINAMOTO_NETWORK_ID>"
torii_url = "https://minamoto.sora.org/"

[account]
profile = "minamoto"
public_key = "<ED25519_PUBLIC_KEY_HEX>"
private_key = "<ED25519_PRIVATE_KEY_HEX>"

[transaction]
time_to_live_ms = 100000
status_timeout_ms = 15000
nonce = false
```

Վերին մակարդակի `chain`-ը ընթացիկ SORA Nexus հիմնական ցանցի շղթայի ID-ն է, իսկ `network_id`-ն Minamoto-ի ցանցի ճշգրիտ նույնությունն է․ կարդացեք այն հնարավորությունների վերջնակետից՝ առաջին ստորագրված գործողությունից առաջ։ `[account].profile = "minamoto"`-ն ընտրում է Minamoto-ի I105 շղթայի տարբերակիչը․ վերջնակետի հոսթի անունը և շղթայի ID-ն այն անուղղակիորեն չեն ընտրում։

Փոխակերպել Minamoto հանրային բանալին իր կանոնիկ I105 հաշիվի մեջ ID ՝ հիմնական ցանցի նախադրյալով.

```bash
iroha tools address convert --profile minamoto <ED25519_PUBLIC_KEY_HEX>
```

Կատարեք միայն ընթերցված կողմի ստուգումներ, մինչեւ հաշիվը ապահովվի եւ ֆինանսավորվի հիմնական ցանցի ներբեռնման կամ կառավարման հոսքի միջոցով.

```bash
iroha --config ./minamoto.client.toml --output-format text ops sumeragi status
```

Minamoto-ի դեմ մի գործարկեք Taira-ի փորձնական միջոցների տրամադրման կամ պարզ ստուգման հրամանները։

## 6. Ֆինանսավորել Minamoto հաշիվ XOR: {#_6-fund-a-minamoto-account-with-xor}

Minamoto-ի վճարները վճարվում են արտադրական XOR-ով, և Minamoto-ն հանրային ծորակ չունի: Ֆինանսավորեք կազմաձևված հաշիվը հիմնական ցանցի հաստատված գրանցման կամ գանձապետարանի փոխանցման միջոցով, կամ XOR ստացեք արդեն ֆինանսավորված Minamoto հաշվից:

Նախքան գրառումը ներկայացնելը ստուգեք քանոնիկ հաշիվը ID եւ ֆինանսավորումը միայն ընթերցման միջոցով: Բարեւ Minamoto XOR-ին որպես արտադրական միջոցներ վերաբերվեք. նախ փորձեք նույն գործողությունը Taira- ում, պահեք առանձին արտադրական բանալիները եւ մի ենթադրեք, որ հիմնական ցանցի գործարքը կարող է վերսկսվել:

Taira XOR-ը չի կարող վճարել Minamoto տուրքերը: Testnet մնացորդը եւ գազի պահանջները չեն փոխանցվում Minamoto-ին:

## 7. Աշխատել գոյություն ունեցող տվյալների տարածքի ներսում {#_7-work-inside-an-existing-data-space}

Տվյալների տարածքի ներսում գտնվող գրանցամատյանի օբյեկտների համար օգտագործեք ամբողջությամբ որակավորված դոմենային անուններ։ Օրինակ՝ հանրային տվյալների տարածքում նախագծի դոմենը պետք է օգտագործի՝

```text
apps.universal
```

Այն բանից հետո, երբ ձեր հաշիվը ունենա պահանջվող թույլտվությունները, ստեղծեք գաղտնի `AliasSetupPlanRequestV1` մտադրություն դոմենի համար եւ օգտագործեք հայտարարական պլանավորիչը.

```bash
iroha --config ./taira.client.toml \
  app alias setup plan \
  --intent-file ./taira-apps-domain.intent.json \
  --plan-file ./taira-apps-domain.plan.json

iroha --config ./taira.client.toml --fee-payer authority \
  app alias setup apply --plan-file ./taira-apps-domain.plan.json
```

Minamoto համար պետք է ստեղծել եւ հաստատել առանձին հիմնական ցանցի մտադրություն եւ ծրագիր: Ծրագրերը կապված են իրենց շղթայի, լիազոր հաշվի, կենդանի վիճակի կապակցությամբ եւ ժամկետի հետ, այնպես որ Taira ծրագիրը չի կարող առաջխաղացվել կամ կրկնվել.

```bash
iroha --config ./minamoto.client.toml \
  app alias setup plan \
  --intent-file ./minamoto-apps-domain.intent.json \
  --plan-file ./minamoto-apps-domain.plan.json

iroha --config ./minamoto.client.toml --fee-payer authority \
  app alias setup apply --plan-file ./minamoto-apps-domain.plan.json
```

Հաշվի այլանուններն օգտագործում են տվյալների տարածքի նույն վերջածանցը․

```text
alice@apps.universal
alice@universal
```

Հստակ հաշվառման դաշտերը դեռեւս օգտագործում են կանոնական I105 հաշիվը IDs: Բարեւեք կեղծանունները որպես մարդկային ընթերցելի կապեր, որոնք լուծվում են կանոնային հաշվին IDs.

## 8. Տրամադրել նոր տվյալների տարածք {#_8-provision-a-new-data-space}

Նոր տվյալների տարածքը օպերատորական և կառավարման փոփոխություն է։ Հանրային Torii վերջնակետը կարող է երթևեկությունը ուղղել դեպի կարգավորված տվյալների տարածքներ, բայց կմերժի տվյալների տարածքների անհայտ այլանունները։

Նախքան փոփոխություն պատրաստելը, գրեք գործող կենդանի կատալոգը.

```bash
curl -fsS https://taira.sora.org/status \
  -H 'Accept: application/json' \
  | jq '.teu_lane_commit[] | {lane_id, alias, dataspace_id, dataspace_alias, visibility}'
```

Օպերատորի հաշիվի համար նաեւ ստուգեք երթուղու ցուցակային դիրքը.

```bash
iroha --config ./operator.client.toml app nexus lane-report --summary
```

Մի առաջադրեք նոր այլանուն, քանի դեռ գոտու ID-ն, տվյալների տարածքի ID-ն, վավերացնողների կազմը, խափանադիմացկունությունը, մանիֆեստը, երթուղավորման կանոններն ու գործառնական պատասխանատուն միասին չեն վերանայվել։ Պահանջվող թույլտվություններն ունեցող սովորական օգտատիրոջ հաշիվը կարող է այլանունների պլանավորիչի միջոցով ձեռք բերել դոմեն և դրա SNS վարձակալությունը գոյություն ունեցող տվյալների տարածքում․ այն չի կարող անվտանգ ավելացնել նոր հանրային տվյալների տարածք։

Մասնավոր կամ կազմակերպական տվյալների տարածքի համար պատրաստեք կատալոգի փոփոխություն՝ ներառելով՝

- տվյալների տարածքի եզակի այլանուն և թվային `id`
- համապատասխանող երթուղային մուտք կամ գոյություն ունեցող երթուղի նշանակում
- տվյալների տարածքի `fault_tolerance`-ը
- երթուղային կանոններ հանձնարարականների կամ հաշիվի շրջանակների համար, որոնք պետք է վայրէջք կատարեն այնտեղ
- Տարածքների գրացուցակի մանիֆեստ կամ տեղակայման համարժեք ապացույցներ, երբ տվյալների տարածքը տրամադրում է UAID հնարավորություններ
- Վավերացողի, համապատասխանության, կարգավորման եւ վերահսկողության քաղաքականության կառավարման հաստատումը

Վերանայելի կոնֆիգերի կտորը նման է հետեւյալին.

```toml
[[nexus.lane_catalog]]
index = 5
alias = "payments"
description = "Payments lane"
dataspace = "payments"
visibility = "public"
metadata = {}

[[nexus.dataspace_catalog]]
alias = "payments"
id = 20
description = "Payments dataspace"
fault_tolerance = 1

[[nexus.routing_policy.rules]]
lane = 5
dataspace = "payments"
[nexus.routing_policy.rules.matcher]
instruction = "transfer::asset"
description = "Route asset transfers to the payments dataspace"
```

Օպերատորի ընդունումը պետք է ներառում լինի հետեւյալ դռները.

- `iroha3d --sora --config <config.toml> --trace-config` փոխանցում է լուծված հանգույցի կարգավորումը
- ստեղծված կամ վերանայված մանիֆեսը արխիվավորվում է շեշերով եւ ստորագրություններով
- ծխի փորձարկումները անցնում են Taira նախքան ցանկացած Minamoto առաջխաղացում:
- փոփոխությունից հետո `/status` կատալոգը ցույց է տալիս նախատեսված գոտին և տվյալների տարածքը
- `iroha app nexus lane-report --summary` չի հայտնում բացակայության մասին պահանջվող մանիֆեսները

```bash
curl -fsS https://taira.sora.org/status \
  -H 'Accept: application/json' \
  | jq '.teu_lane_commit[] | select(.dataspace_alias == "payments")'
```

Նույն տվյալների տարածքը տեղափոխեք Minamoto միայն Taira-ի տեղակայման, պարզ ստուգումների, մոնիթորինգի և կառավարման ապացույցների ամբողջացումից հետո։
