# Արդյունավետություն եւ չափանիշներ {#performance-and-metrics}

Iroha կատարումը կախված է աշխատանքային բեռնվածությունից, վավերացողի տոպոլոգիայից, ցանցի պայմաններից եւ կոնսենսուսային կարգավորումներից: Հետեւաբար, մեկ TPS թիվը օգտակար է միայն այն դեպքում, երբ կապվում է ֆիքսված կոֆիգուրացիայի հետ ստանդարտ ցուցանիշի գործարկման հետ:

Հզորության պլանավորման համար կատարողականը դիտարկել որպես շահագործման առումով.

- ցանցը ընդունում է պահանջված գործարքի տոկոսադրույքը
- commit հետաձգման ժամանակահատվածի մնալը նպատակային բյուջեի մեջ
- գործարքային հերթերը սահմանափակվում են
- կոնսենսուսը չի հիմնվում կրկնվող դիտման փոփոխությունների կամ վերականգնման ուղիների վրա:

Օգտագործեք այս էջը ՝ գնահատելու համար, թե արդյոք տեղակայումը բարձր, միջին կամ ցածր կատարողական վիճակում է տվյալ բջիջների քանակության, ցանցի լատենցիայի շեմի եւ նպատակային TPS համար:

## Ինչ պետք է չափել {#what-to-measure}

Սկսեք հանրային բջիջի ակնթարթից եւ Prometheus- ի հետ, այնուհետեւ օգտագործեք CLI օպերատորի կողմից հավաստագրված համաձայնության վիճակի համար: Օպերատորը պետք է թույլատրվի նպատակային բջջիջով եւ լցվում է միայն վազման ժամանակ:

```bash
export TORII=http://127.0.0.1:8180
export OPERATOR_KEY_FILE=./secrets/operator.key

curl -s -H 'Accept: application/json' "$TORII/status" | jq .
curl -s "$TORII/metrics" > metrics.prom

iroha --config ./localnet/client.toml \
  --operator-private-key-file "$OPERATOR_KEY_FILE" \
  --output-format json ops sumeragi status
iroha --config ./localnet/client.toml \
  --operator-private-key-file "$OPERATOR_KEY_FILE" \
  --output-format json ops sumeragi diagnostics
iroha --config ./localnet/client.toml \
  --operator-private-key-file "$OPERATOR_KEY_FILE" \
  --output-format json ops sumeragi qc
iroha --config ./localnet/client.toml \
  --operator-private-key-file "$OPERATOR_KEY_FILE" \
  --output-format json ops sumeragi params
```

Հասարակական Taira օգտակար է անանուն բջիջների ակնթարթային ակնթարթային պատճենների ձեւը սովորելու համար: Նրա օպերատորի ախտորոշումը դիտավորաբար հասանելի չէ առանց Taira օպերտորի բանալին.

```bash
TAIRA=https://taira.sora.org

curl -fsS -H 'Accept: application/json' "$TAIRA/status" \
  | jq '{blocks, txs_approved, txs_rejected, queue_size, peers}'

curl -fsS "$TAIRA/v1/time/now" \
  | jq '{now_ms, offset_ms}'
```

Մի օգտագործեք հանրային փորձարկման ցանցի դիտարկումները որպես արտադրական կարողությունների թվեր ձեր սեփական տեղակայման համար:

Հեռաչափության տեսանելիությունը կախված է կազմավորված պրոֆիլից: `operator` հնարավորություն է տալիս ստատուսի եւ ախտորոշման ակնթարթային ակնթարթային պատճենները: `extended` ավելացնում է `/metrics` եւ թանկ ժամանակացույցներ. մինչդեռ `developer`-ը ավելացնում է զարգացնող սանապշոտներ, ինչպիսիք են առաջնորդը, QC, պարամետրերը եւ ապացույցները ՝ առանց հնարավորություն տալու `/metrics`: Օգտագործեք `full`-ը, երբ մեկ գործողության համար անհրաժեշտ են երկու հավաքածուները: `telemetry_profile`-ն առաջին թողարկման միակ հեռաչափական կոշտաժն է.

```toml
telemetry_profile = "full"
```

## Պերֆորմացիայի ժապավեններ {#performance-bands}

Օգտագործեք այս տերեւները դիտարկված երթեւեկության համար թիրախային անցում `Y` TPS եւ ուշացման բյուջետ `L` միլիսիկունտներում: Շարունակեք աշխատանքային բեռը բավականաչափ երկար, որպեսզի ներառեք ջերմացում, կայուն վիճակ եւ առնվազն մեկ ժամանակահատված ակնկալվող առավելագույն բեռնվածությունը:

|Գավաթ |Պայմաններ |Նշում |
| --- | --- | --- |
|Բարձր |Ընդունված ներթափանցումը հասնում է կամ գերազանցում `Y`, p95 հանձնարարականի հետաձգման ժամկետը ցածր է `0.8 * L`, հերթերը մնում են հզորության 10%-ից ցածր, եւ տեսանկյունի փոփոխություն/վերականգնման հաշվիչները հարթ են:|Բնակչության տեղակայման համար անհրաժեշտ աշխատանքային բեռնվածություն է: |
|միջին |Ընդունված ներուժը մոտ է `Y`, p95 հանձնարարականի հետաձգումը ցածր է `L`, հերթերը կայուն են 50%-ից ցածր եւ տեսողական փոփոխությունները հազվադեպ են լինում:|Գործարկումը գործում է, բայց պայթյունի հանդուրժողականությունը սահմանափակ է:|
|ցածր |Ընդունված թափանցիկությունը `Y` -ից ցածր է, p95 commit հետաձգումը գերազանցում է `L`-ը, երթեւեկության ընթացքում հերթերը աճում են կամ հեռանկարային փոփոխության/հակառակ ճնշման հաշվիչները շարունակաբար աճում են:|Աշխատանքի պահանջվող բեռը գերազանցում է առնվազն մեկ շշնջուղի խոչընդոտը |

Գլխավոր կանոնն է հերթի ուղղությունը: Եթե ներկայացված TPS մեծ է, քան հաստատված է TPS եւ հերթը շարունակում է աճել, տեղակայումը գերբեռնված է նույնիսկ եթե կարճ նմուշները առողջ են թվում:

## Նոթների թիվը եւ քվորումը {#node-count-and-quorum}

Ավելի շատ վավերացողները բարելավում են սխալների հանդուրժողականությունը, բայց ավելացնում են համակարգման, ստորագրության եւ ցանցի դուրս գալու ծախսերը: Առաջին թողարկման Sumeragi պրոտոկոլը պահանջում է:

- հստակ `n = 3f + 1` քվեարկության կոմիտեն
- `4 <= n <= 31`, այնպես որ գործող չափերը 4, 7, 10 եւ այլն են:
- `2f + 1` կոմիտեային քվորում
- դիտորդների հանգույցները համաժամեցնում են բլոկերը, բայց չեն քվեարկում, առաջարկում կամ հավաքում

|Փաստաբաններ |Սխալ բյուջե |Կատարեք քվորում:|Հասունակության ծանուցում |
| --- | --- | --- | --- |
| 4 | 1 | 3 |Միավոր սխալների հանդուրժողականության համար ընդհանուր նվազագույն |
| 7 | 2 | 5 |Ավելի դիմացկուն, ավելի շատ քվեարկության եւ տարածման երթեւեկությամբ |
| 10 | 3 | 7 |Կոորդինացիայի ավելի բարձր ծախսերը. ցանցի եւ ներթափանցման կարգավորումը ավելի կարեւոր է |
| 31 | 10 | 21 |Մաքսիմալ առաջին թողարկման կոմիտե: Համեմատական ցուցանիշների համակարգում եւ ստորագրության ծախսերը զգույշորեն |

Genesis- ի սերունդը եւ սկիզբի հաստատումը մերժում են ոչ համապատասխան հանձնաժողովների չափերը. Մի համեմատեք այն տոպոլոգիաների հետ, որոնք թողարկման մեջ չեն կարող ընդունել:

"X հանգույցները" գնահատելիս քվեարկության վավերացողները բաժանվում են դիտորդներից: դիտորդների ավելացումը սովորաբար ավելի ցածր է ծախսում, քան հաստատիչների ավելացումը, բայց դիտորդները դեռ սպառում են բլոկ գովազդներ, բլոկ սինկորացիա, սկավառակ եւ ցանցային թողունակություն:

## Տարբեր գործոններ, որոնք ազդում են կատարման վրա {#factors-that-influence-performance}

### Աշխատանքային բեռի ձեւը {#workload-shape}

Նույն TPS կարող է լինել ցածր կամ թանկ, կախված այն բանից, թե ինչ է կատարվում յուրաքանչյուր գործարքի հետ:

- յուրաքանչյուր գործարքի վերաբերյալ հրահանգների թիվը
- ստորագրության հաշման եւ ստորագրման ալգորիթմները
- գործարքի բայթերի չափը եւ դեկոմպրեսացված օգտակար լիցքավորման չափը
- ընթերցման/գրելու հարաբերակցությունը
- Մետադատային տվյալների չափը եւ ակտիվների գործողությունները
- խելացի պայմանագիր, գործարկիչ եւ կատարման ծախսեր IVM
- հարցման ծանրաբեռնվածությունը նույն հանգույցների դեմ

Փոքր տրանսֆերային գործարքները պայմանագրերով ծանր կամ մետադատա ծանր աշխատանքային բեռնվածքների փոխարինող չեն:

### Համաձայնություն Կադենս {#consensus-cadence}

Գործնական Sumeragi պարամետրի արձանագրությունը պարունակում է ստորագրված անփոխարինելի բլոկային կադենսիան եւ ժամացույցի հետ կապված սահմանը.

- `block_cadence_ms`
- `max_clock_drift_ms`

Նրանց ստուգեք հետեւյալ կերպ.

```bash
iroha --config ./localnet/client.toml \
  --operator-private-key-file "$OPERATOR_KEY_FILE" \
  --output-format json ops sumeragi params
```

`block_cadence_ms` -ը կատարվում է ստորագրված գենեզի միջոցով եւ սառեցվել է մեկնարկից հետո, դա կենդանի կարգավորման կոճակ չէ: Համեմատեք ցանցերը տարբեր ստորագրված Գենեզի մուտքներով միայն որպես առանձին ստանդարտ սցենարներ: Երբ դիտվում են փոփոխություններ, բացակայում է շահագործման բեռը կամ առաջանում է հակասական ճնշում, ավելի կարճ ժամանակահատվածը սովորաբար դարձնում է գերբեռնվածությունը ավելի տեսանելի, այլ ոչ թե ավելացնում է կայուն ներուժը:

### Առաջնորդների եւ մուտքի սահմանները {#candidate-and-ingress-bounds}

Node-lokal Sumeragi սահմանները որոշում են, թե որքան հավակնորդ եւ վերականգնման աշխատանք կարող է պահել վավերացողը.

- `sumeragi.block.max_transactions`
- `sumeragi.block.max_payload_bytes`
- `sumeragi.block.proposal_queue_scan_multiplier`
- `sumeragi.queues.commands`
- `sumeragi.queues.bodies` եւ `sumeragi.queues.body_bytes`
- `sumeragi.queues.body_source_bytes`, `sumeragi.queues.chunks`, եւ `sumeragi.queues.ready_bodies`

Չափազանց փոքր սահմանները ստեղծում են հերթի կամ օգտակար բեռների վերականգնման ճնշում: Չափից մեծ սահմանները ավելացնում են պահպանված հիշողությունը եւ չարաշահող հանգույցի համար մատչելի աշխատանքային քանակը: Համեմատեք ախտորոշման ակնթարթը գործընթացային հիշողության, հաղորդագրությունների կառավարման եւ բացակայում է մարմնի չափանիշների հետ մեկ անգամ փոխելուց առաջ.

```bash
iroha --config ./localnet/client.toml \
  --operator-private-key-file "$OPERATOR_KEY_FILE" \
  --output-format json ops sumeragi diagnostics
```

### Համացանցի պայմանները {#network-conditions}

Համաձայնության կատարումը զգայուն է հետեւյալը.

- RTT վավերացնողների միջեւ
- զյարդայնություն եւ փաթեթի կորուստ
- բլոկային օգտակար ծանրաբեռնվածքների եւ ստորագրված RS16 մասերի թողունակության լայնությունը
- տարածաշրջանների միջեւ անհամաչափ կապեր
- NAT, կրակի պատ, կամ ռեալի վարքագիծ, որը հետաձգում է հանգույցների կապը

Որպես պլանավորման կանոն, սահմանեք լատենցիայի բյուջեն բավականաչափ բարձր, որպեսզի կարողանա ընդգրկել մի քանի վավերացողի շրջադարձային ուղեւորություններ, գումարած կատարման եւ սկավառակի commit ժամանակ: Եթե p95 ցանցը RTT արդեն մոտ է ցանկալի p95 commit հետաձգմանը, նպատակն իրական չէ:

### Թերթեր եւ մուտքի սահմանափակումներ {#queues-and-admission-limits}

Թողարկման եւ հերթի կարգավորումները սահմանում են, թե որքան պայթյունային ճնշում կարող է ընկալել հանգույց:

- `queue.capacity`
- `queue.capacity_per_user`
- `queue.max_retained_bytes`
- `queue.transaction_time_to_live_ms`
- genesis գործարքի սահմանները, ինչպիսիք են առավելագույն ստորագրությունները, հրահանգները, բայթերը եւ կոմպրեսացված բայթները
- p2p հերթի ծայրերը եւ կոնսենսուսային մուտքի սահմանները

Բարձր հերթի հզորությունը կարող է մի ժամանակով թաքցնել գերբեռնվածությունը, բայց դա չի մեծացնում կայուն արտադրանքը: Կայուն հերթը առողջ է; աճող հերթը հետապնդում է:

### Հարդքորներ եւ պահեստավորում {#hardware-and-storage}

Քննեք յուրաքանչյուր վավերացնող, ոչ միայն առաջնորդը.

- CPU վավերացման, ստորագրության ստուգման եւ կատարման ընթացքում լցվածությունը
- հիշողության ճնշումը շարքերից, ակնթարթային պատճեններից եւ շահագործման բեռների վերականգնման զամբյուղերից
- բլոկային պահեստավորման եւ ակնթարթային պատճենի համար սկավառակի գրման ուշացում
- ցանցի փոխանցման/ընդունման լցվածությունը
- աշխատանքային ծանրաբեռնվածության ժամանակ գործնական սարքավորումների արագացման ընտրանքային կարգավորումները

Քվեարկության ամենադանդաղ վավերացնողը կարող է որոշել ցանցի հետագա ուշացումը:

## Պրոմետեոսի ազդանշանները {#prometheus-signals}

Մետրիկ անունները գալիս են ստուգված հեռաչափության կատալոգից: Սերիայի մատչելիությունը եւ նմուշակազմը դեռ կախված են կառուցման առանձնահատկություններից եւ `telemetry_profile`, այնպես որ նախքան դաշբորդի կառուցումը ստուգեք `/metrics` թիրախային հանգույցի վրա:

Սովորական ազդանշանները ներառում են.

|Սիմգալ |Պրոմետեուսի օրինակներ |Ի՞նչ դիտել:|
| --- | --- | --- |
|Ընդունված արտահոսք |`sum(rate(txs{type="accepted"}[5m]))` |Կպահպանել կամ գերազանցել նպատակային TPS մակարդակը: |
|Հրաժարականներ |`sum(rate(txs{type="rejected"}[5m]))` |Հարկ է բացատրել փորձաքննության պլանը:|
|Պատվիրել ուշացում |`histogram_quantile(0.95, sum(rate(commit_time_ms_bucket[5m])) by (le))` |Համեմատեք p95/p99-ը հետաձգման բյուջեի հետ |
|Էջի խորությունը |`queue_size`, `sumeragi_tx_queue_depth` |Պետք է պահպանել սահմանը բեռնման բարձրության ժամանակ:|
|Էջի հագեցածություն |`sumeragi_tx_queue_saturated` |Պահպանվող ոչ զրոյական արժեքները միջին գերբեռնվածություն |
|Նայեք փոփոխությունները |`view_changes`, `sumeragi_view_change_suggest_total`, `sumeragi_view_change_install_total` |Բարձրացվող արժեքները ցույց են տալիս ժամանակի, տոպոլոգիայի, օգտակար բեռնվածության կամ ցանցի խնդիրների |
|Թողված հաղորդագրություններ |`dropped_messages`, `sumeragi_consensus_message_handling_total` |Լիցքավորման ընթացքում նվազումները սովորաբար բացատրում են լատենցիայի բարձրացումը |
|Օգտակար բեռնվածք եւ DA վերականգնում |`sumeragi_missing_block_requests`, `sumeragi_missing_block_oldest_ms`, `sumeragi_missing_block_fetch_total`, `sumeragi_da_gate_block_total`, `sumeragi_da_gate_satisfied_total` |Պարբերական պահանջները, տարիքի աճը կամ կրկնվող DA դռները ցույց են տալիս մարմնի կամ մասերի ձեռքբերման խնդիր |
|Կատարեք քվորում:|`sumeragi_commit_signatures_counted`, `sumeragi_commit_signatures_required` |Հաշվարկված ստորագրությունները պետք է արագ հասնեն պահանջվող քվորումին:|

Երբ մետրիկան գոյություն ունի միայն `/v1/sumeragi/status`, նկարագրեք JSON ակնթարթային ակնթարթային պատճենը Prometheus- ի խեղդման նույն ընթացքի արվեստի գործիքների մեջ:

## Գործընթացների գնահատականներ {#estimation-workflow}

1. Պարզեք սցենարը.
   - վավերացնողների եւ դիտորդների թիվը
   - կոնսենսուսի ռեժիմ
   - նպատակային TPS
   - p95 եւ p99 commit հետաձգման բյուջեները
   - գործարքային խառնուրդ
   - սպասվող ցանց RTT, jitter եւ թողունակություն
2. Գրիր արդյունավետ կարգավորումը.

   ```bash
   iroha --config ./localnet/client.toml \
     --operator-private-key-file "$OPERATOR_KEY_FILE" \
     --output-format json ops sumeragi params \
     > artifacts/sumeragi-params.json
   iroha --config ./localnet/client.toml \
     --operator-private-key-file "$OPERATOR_KEY_FILE" \
     --output-format json ops sumeragi status \
     > artifacts/sumeragi-status.json
   iroha --config ./localnet/client.toml \
     --operator-private-key-file "$OPERATOR_KEY_FILE" \
     --output-format json ops sumeragi diagnostics \
     > artifacts/sumeragi-diagnostics.json
   ```

3. Աշխատանքային ծանրաբեռնվածությունը գործարկեք թիրախի վրա TPS։
4. Գտեք ընթացքի սկզբում, միջին եւ վերջում ստացված վիճակը եւ չափանիշները:
5. Գործընթացը դասակարգեք կատարողական տերեւի սեղանի միջոցով:
6. Եթե ժապավենը միջին կամ ցածր է, միաժամանակ փոխեք մեկ գործոն եւ կրկնեք:

## Համացանցային զեկույցի ձեւանմուշ {#benchmark-report-template}

Հրապարակել կատարողական թվերը միայն բավարար համատեքստով, որպեսզի դրանք վերարտադրվեն.

- Iroha commit, ազատման եւ առանձնահատկությունների դրոշներ
- վավերացողի եւ դիտորդի հաշվարկը
- համաձայնության ռեժիմը, ստորագրված բլոկային քանդենցիան եւ DA դասակարգումը:
- ճշգրիտ `3f + 1` կոմիտե, քվորում եւ դիտորդների ցուցակ
- `sumeragi.block`, `sumeragi.queues`, `sumeragi.limits` ցանցային մուտքի եւ գործարքների հերթի սահմանները
- հեռաչափության պրոֆիլ
- Hardware, պահեստավորման եւ OS մանրամասներ
- ցանց RTT, jitter, կորուստ եւ թողունակության ենթադրությունները
- գործարքի խառնուրդը եւ շահագործման բեռի չափերը
- առաջարկված TPS եւ ընթացքի տեւողությունը
- ընդունված / մերժված TPS
- p50/p95/p99 հանձնարարականի հետաձգում
- հերթի խորությունը եւ լցվածությունը
- դիտել փոփոխություններ, բաց թողնված հաղորդագրությունները, բացակայող բլոկների հավաքումը եւ DA դարպասային հաշվիչները:
- CPU, հիշողություն, սկավառակ եւ ցանցի օգտագործումը մեկ վավերացողի համար

Առանց այդ մանրամասների, TPS թիվը պետք է դիտարկվի որպես անեկդոտիկ:
