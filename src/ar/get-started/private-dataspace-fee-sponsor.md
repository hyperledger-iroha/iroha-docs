# رعاية رسوم مساحة بيانات خاصة {#sponsor-fees-for-a-private-data-space}

يمكن لبرنامج رعاية رسوم في SORA Nexus دفع رسوم التنفيذ الشامل للمعاملات المؤهلة الموجّهة إلى مساحة بيانات خاصة. يظل المستخدم يوقّع المعاملة كاملة. وتختار نية `FeePaymentIntent` ذات النوع المحدد برنامج رعاية دقيقًا ومراجعة غير قابلة للتغيير وحدًا للغاز حيثما يلزم وقيم الرسوم القصوى.

لا ينشئ إدخال كتالوج مساحة البيانات جذرًا موقّعًا بصورة مستقلة. لجذر مساحة البيانات المستقل عملة رسوم وسياسة مثبتتان خاصتان به؛ ولا تستطيع خزائن الرعاية العامة تفويض رسوم جذره الخاص. حدد جذر التنفيذ قبل تصميم الرعاية.

## 1. تحديد سياسة الرسوم المثبتة {#_1-establish-the-committed-fee-policy}

يعرّف التكوين الأولي الموقّع معاملًا مخصصًا واحدًا `root_fees_v1` يحتوي `RootFeePolicy`. يربط هذا المعامل عملة الرسوم ووجهتها وحساب حفظ أموال الراعي وإعفاءات المطالبات ومعدلات الرسوم. تستخدم كل كتلة عادية وكل عملية تسعير السياسة المثبتة التي التقطتها. وتسري التغييرات المصرح بها على المعدلات ووجهة الرسوم وإعفاءات المطالبات بدءًا من الكتلة التالية؛ ولا يمكن تغيير عملة الرسوم وحساب حفظ أموال الراعي بعد الكتلة الأولى.

في التنفيذ الشامل، تحرق الرسوم الأصلية عملة XOR المحددة بدقة في الشبكة الموقّعة. توفر خزينة برنامج الراعي تلك العملة. لا تختار إعدادات العقدة أو البيانات الوصفية للمعاملة دافعًا للرسوم ولا تفعّل الرعاية.

استخدم هويات العملة والحسابات المعيارية للشبكة. يجب ألا يعيد حل الأسماء المستعارة توجيه هويات العملة أو الحفظ أو وجهة الرسوم المثبتة.

## 2. إنشاء برنامج رعاية وتمويله {#_2-create-and-fund-a-sponsor-program}

يأخذ معرّف البرنامج الشكل `<canonical-sponsor-account>/<program-name>`. أنشئه عبر التعليمات ذات الأنواع المحددة التي يتيحها SDK ونموذج البيانات الحاليان:

| التعليمة | الغرض |
| --- | --- |
| `CreateFeeSponsorProgram` | إنشاء البرنامج قيد الإعداد مع حساب الصرف الإلزامي له. |
| `StageFeeSponsorProgramRevision` | تعريف سياسة واحدة غير قابلة للتغيير للأهلية والعمليات والميزانية. |
| `EnrollFeeSponsorBeneficiary` |سجّل مستفيدًا مؤهلاً على السلسلة.|
| `FundFeeSponsorProgram` | نقل الأصول إلى الحفظ وإضافة الرصيد إلى خزينة البرنامج المحددة بدقة. |
| `ActivateFeeSponsorProgramRevision` | جدولة أبكر ارتفاع يمكن عنده تفعيل المراجعة قيد الإعداد. |

يفوّض الراعي أو مدير مفوّض محدد بدقة إدارة البرنامج. تتطلب السحوبات الراعي نفسه، ولا تعيد الأموال إلا إلى حساب الصرف المسجّل للبرنامج أثناء توقفه المؤقت أو عملية إغلاقه.

كل مراجعة تحدد:

- تسجيلًا صريحًا، أو تسجيلًا إضافة إلى الأهلية المسموح بها عبر المسار الافتراضي؛
- قواعد سماح ورفض على معرّفات التعليمات الأصلية الدقيقة في تنسيق النقل، أو على عناوين العقود وتجزئات الكود ونقاط الدخول؛
- حدودًا لكل أصل على مستوى المعاملة والكتلة وحقبة البرنامج وحقبة المستفيد؛
- حدًا أدنى للاحتياطي وطول حقبة حتميًا.

تسبق قاعدة الرفض قاعدة السماح. يمنح `fee_sponsor_program_id` لمساحة البيانات الأهلية عبر المسار الافتراضي فقط إذا سمحت المراجعة النشطة بذلك؛ وتظل المعاملة ملزمة بتسمية البرنامج والمراجعة المحددين بدقة. يمكن تأجيل التفعيل حتى تنتهي التخصيصات المعلقة من المراجعة السابقة.

يجب أن تستخدم أصول خزنة الراعي سياسة الرصيد `Global`. تمويل الحساب العادي للراعي وحده لا يمول خزنة البرنامج المعزولة، ولا يمكن لبرنامج واحد استهلاك رصيد برنامج آخر.

## 3. تسعير المعاملة الدقيقة وتوقيعها وإرسالها {#_3-quote-sign-and-submit-the-exact-transaction}

يقوم تكامل SDK بتنفيذ هذه الخطوات:

1. أنشئ `TransactionPayload` غير الموقّع مع جهة التفويض والمحتوى التنفيذي والطوابع الزمنية وnonce والبيانات الوصفية ومراجعة برنامج الرعاية الدقيقة وأي حد غاز مطلوب. يمكن ترك قيم الرسوم القصوى فارغة في البداية.
2. وقّع طلب `POST /v1/fees/quote` بالحساب مع `{"payload": <payload>}`. يجب أن يكون موقّع الطلب جهة تفويض المعاملة.
3. افحص الارتفاع المرصود ومسار مساحة البيانات المستخلص ومكونات الرسوم ومصدر الخصم وسعة الراعي. تحقق من أن الاستجابة تحتفظ بدافع الرسوم والمراجعة وحد الغاز المختارين.
4. استبدل `payload.fee_payment` فقط بالنية الموصى بها، ثم وقّع تلك الحمولة الدقيقة وأرسلها.
5. تابع المعاملة حتى النهائية `Applied` التي تحسمها الحالة، واحتفظ بإيصالها متضمنًا برنامج الرعاية والمراجعة والرسوم الفعلية.

يراقب عرض الرسوم دفتر السجل ولا يحجز سعة. يعيد القبول في الطابور التحقق من الأهلية ويحجز القيم القصوى الموقّعة. يؤدي رفض الراعي إلى رفض المعاملة دون الرجوع إلى تحميل الرسوم للمستخدم.

تحدد CLI مصدر الرسوم نفسه صراحة. مثلًا، بعد أن يسمح البرنامج بنقل الأصل المحدد بدقة ويكون الحساب مؤهلًا:

```bash
iroha --config ./user.client.toml \
  --fee-payer sponsor \
  --fee-program '<SPONSOR_CANONICAL_I105>/team-payments' \
  --fee-program-revision 1 \
  ledger asset transfer \
  --definition '<ASSET_DEFINITION_BASE58>' \
  --account '<USER_CANONICAL_I105>' \
  --to '<RECIPIENT_CANONICAL_I105>' \
  --quantity 1
```

استخدم المراجعة النشطة والمعرّفات الدقيقة من شبكتك. يحتوي إعداد المستخدم فقط على موقّعه هو؛ ولا يلزم المفتاح الخاص للراعي لإرسال معاملة مؤهلة للرعاية.

## 4. تحديد ما إذا كان المستخدم يدفع رسوم التطبيق {#_4-decide-whether-the-user-pays-an-application-fee}

يمكن للراعي تغطية الرسوم الشاملة مع عدم فرض التطبيق أي رسوم على المستخدم. إذا حصّل التطبيق رمزًا محليًا، فعرّف التحويل أو قاعدة العقد صراحة داخل المحتوى التنفيذي الموقّع من المستخدم. ضمّن كل عملية في سياسة مراجعة الراعي وافحص عرض الرسوم للحمولة كاملة. لا تستنتج نقل رمز خاص بالتطبيق من نية دفع رسوم الشبكة.

## تشخيص الرفض {#diagnose-a-refusal}

استخدم رمز الرسوم الثابت وتفاصيل المعالجة التي تعيدها العقدة:

| الرمز | ما يجب فحصه |
| --- | --- |
| `program_not_found` | الهوية المعيارية الدقيقة للبرنامج. |
| `revision_not_active`، `program_not_active` |تفعيل المراجعة ودورة حياة البرنامج.|
| `beneficiary_not_eligible` | التسجيل أو الأهلية المسموح بها عبر المسار الافتراضي. |
| `operation_not_allowed`, `operation_denied` | كل عملية موقّعة محددة بدقة وكل قاعدة رفض. |
| `invalid_gas_limit`, `signed_limit_exceeded` | حد الغاز والقيم القصوى الموقّعة مقارنة بعرض رسوم جديد. |
| `vault_insufficient` | الرصيد الممول لخزينة العملة المحددة بدقة لهذا البرنامج. |
| رموز استنفاد الميزانية | السعة على مستوى المعاملة والكتلة وحقبة البرنامج وحقبة المستفيد. |

احتفظ بتجزئة المعاملة الأصلية وتفاصيل رفض الرسوم عند التحقيق في إرسال ذي نتيجة ملتبسة. تأكد من حالته قبل إنشاء بديل.
