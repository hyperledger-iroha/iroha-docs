# اختبار الفوضى مع Izanami {#chaos-testing-with-izanami}

أيزانامي هو الموسيقي الفوضوي في النهر Iroha مساحة العمل
يبدأ محلية تنفذية Iroha المجموعة، تقدم عبء عمل قابلة للتكوين،
ويحقق الأخطاء في أقرانهم المختارين حتى يتمكن المشغلون من التحقق مما إذا كانت
الشبكة تستمر في التقدم تحت الفشل المسيطر عليه

استخدام Izanami للتحقق من مقاومة قبل الإنتاج، وتكاثر التراجع،
لا تستهدف شبكة إنتاج: الأداة هي
المصممة لامتلاك الأقران التي تبدأها، بما في ذلك إعادة تشغيل الأقران، التخزين
المكياسات، فقدان الحزم الاصطناعية، والمقامي CPU أو ضغط القرص

## الشروط المسبقة {#prerequisites}

إدارة Izanami من
[Iroha مخزن المصدر](https://github.com/hyperledger-iroha/iroha),
ليس من هذا مخزن الوثائق:

```bash
git clone https://github.com/hyperledger-iroha/iroha.git
cd iroha
cargo build -p izanami
```

يجب السماح صراحة للجهاز الثنائي بإنشاء وتلاعب الشبكات
أقرانهم `--allow-net` لكل شخص غيرTUI تشغيل أو تمكين `allow_net` في
الموقع TUI.

```bash
cargo run -p izanami -- --allow-net --peers 4 --faulty 1 --duration 120s
```

للتشغيل التفاعلي تكوين:

```bash
cargo run -p izanami -- --tui --allow-net
```

يزازامي يستمر TUI و CLI الإعدادات تحت دليل تشكيل المستخدم، لذلك
مراجعة الإعدادات المعروضة قبل إعادة استخدام الملف الشخصي السابق.

## التشغيل الأساسي {#baseline-run}

ابدأ مع خط أساس واحد قابل للتكرار قبل إضافة الأخطاء الخطيرة:

```bash
cargo run -p izanami -- \
  --allow-net \
  --peers 4 \
  --faulty 1 \
  --duration 5m \
  --target-blocks 100 \
  --progress-interval 15s \
  --progress-timeout 120s \
  --latency-p95-threshold 2s \
  --tps 15 \
  --max-inflight 32 \
  --submitters 1 \
  --seed 42
```

هذه الجولة تنجح فقط إذا بلغ الكluster الهدف المطلوب من الكتلة،
يستمر في التقدم خلال فترة الإنتظار، ويبقى تحت p95 الاختياري
عتبة فترة الحظر.

اكتب القيادة يا سيل Iroha الالتزام، عدد الأقران، حساب الأقران الخاطئ،
ملف عبء العمل، الهدف TPS, وفرق التأخير مع السجلات
هذه القيم، لا يمكن لمشغل آخر إعادة تشغيل نفس نمط الفشل.

## ملفات تعريف الحملة {#workload-profiles}

يحتوي Izanami على اثنين من ملفات تعريف حمولة العمل:

| الملف الشخصي  | استخدمها                                         | ملاحظات                                  |
| -------- | -------------------------------------------------- | -------------------------------------- |
| `stable` | التدريبات الطويلة والتحقق من الأداء القابلة للتكرار | يفضل الوصفات الآمنة من التنفيذ          |
| `chaos`  | تغطية مسار الفشل                              | يتضمن وصفات غير صالحة عمداً |

استخدم الملف المستقر أولاً:

```bash
cargo run -p izanami -- --allow-net --workload-profile stable --seed 42
```

الانتقال إلى مستوى الفوضى عندما يتم فهم خط الأساس بالفعل

```bash
cargo run -p izanami -- --allow-net --workload-profile chaos --seed 42
```

يتم تعطيل وصفات تنفيذ العقود في عمليات ثابتة ما لم يكن صراحة
مسموح:

```bash
cargo run -p izanami -- \
  --allow-net \
  --workload-profile stable \
  --allow-contract-deploy-in-stable
```

الاستخدام `--nexus` عندما يجب على الركض أن يستخدم الجهاز المدمج SORA Nexus الاخطاء من
مساحة العمل في الأعلى.

## مكافحة الأخطاء {#fault-controls}

عندما `--faulty` هو أكبر من الصفر، على الأقل سيناريو خطأ واحد يجب أن يكون
تمكين. التبديل الخاطئ لتشغيل الافتراضي، والعلامات البولية يمكن أن تكون
معاقين `=false`.

| الخطأ                    | CLI العلم                                   | ما يمارس                          |
| ------------------------ | ------------------------------------------ | ------------------------------------------ |
| تحطم وإعادة تشغيل        | `--fault-enable-crash-restart`             | فقدان وعودة العمليات المتساوية             |
| مسح التخزين وإعادة تشغيل | `--fault-enable-wipe-storage`              | التعافي من حالة المفقودة المحلية          |
| رسائل غير صالحة للمعاملات | `--fault-enable-spam-invalid-transactions` | مسارات القبول والرفض              |
| تأخر الشبكة          | `--fault-enable-network-latency`           | الثرثرة البطيئة والرسائل المتأخرة للتوافق |
| قسم الشبكة        | `--fault-enable-network-partition`         | الانزلاق المؤقت بين الأقران الموثوقين           |
| P2P فقدان الحزمة          | `--fault-enable-network-packet-loss`       | انقطاع حركة المرور في الإطار التطبيقي          |
| CPU الإجهاد               | `--fault-enable-cpu-stress`                | ضغط التحقق من المصادقة المحلية والجدول المقرر   |
| تثبيت القرص          | `--fault-enable-disk-saturation`           | ضغط التخزين المحلي                     |

بالنسبة لرحلة خسارة الحزمة فقط:

```bash
cargo run -p izanami -- \
  --allow-net \
  --peers 20 \
  --faulty 5 \
  --duration 800s \
  --fault-window-start 133s \
  --fault-window-end 266s \
  --tps 200 \
  --submitters 20 \
  --max-inflight 512 \
  --fault-enable-crash-restart=false \
  --fault-enable-wipe-storage=false \
  --fault-enable-spam-invalid-transactions=false \
  --fault-enable-network-latency=false \
  --fault-enable-network-partition=false \
  --fault-enable-network-packet-loss=true \
  --fault-enable-cpu-stress=false \
  --fault-enable-disk-saturation=false \
  --fault-network-packet-loss-percent 75 \
  --seed 42
```

الاستخدام `--fault-window-start` و `--fault-window-end` للحفاظ على السيطرة
فترة حالة ثابتة قبل وبعد فشل الحقن.
من الأسهل تمييز ضجيج البدء عن تأثير الخطأ.

## أشكال السيناريو {#scenario-shapes}

خرائط الكتالوجية الصعودية Izanami تقرير فشل الاتصالات الشائعة
أشكال CLI يمكنك أن تقوم بتصميمها بنفس العلامات

| السيناريو              | الشكل النموذجي                                                                                                            |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| الحمل المستهدف         | `--faulty 0`, عالية `--tps`, أحد المقدمين، مرتفع `--max-inflight`                                                         |
| فشل مؤقت     | تمكين الإصطدام/إعادة تشغيل فقط داخل نافذة خطأ محددة                                                                  |
| فقدان الحزمة           | تمكين فقدان الحزم فقط، عادة مع معدل الخسارة الافتراضي 75%                                                          |
| التوقف والاسترداد | استخدام عدد كبير من الأقارب الخاطئة مع حادث / إعادة البدء                                                                    |
| عزل القائد      | استخدم بالضبط نظير واحد خاطئ مع فقط الشبكة التقسيم أو خسارة الحزمات الأخطاء؛ Izanami يلي Sumeragi قيادة التلفونية |

حافظ على متغير واحد ثابت في كل مرة. إذا قمت بتغيير عدد الأقران، عبء العمل
الملف الشخصي، نافذة الخطأ، و TPS في نفس الوقت، النتيجة صعبة
المترجم

## ما يجب مشاهدته {#what-to-watch}

أثناء الجري، مراقبة نفس الإشارات المستخدمة للتحقق من الأداء:

- تقدم في ارتفاع الكتلة عبر كل أقرة ركوب
- المعاملات المقدمة والمتقبلة والرفضة والمؤقتة
- عمق الصف ، وملء الصف ، والضغط الخلفي في النقطة النهائية
- تغييرات الرؤية، مسارات الاسترداد، كتلة مفقودة، والحكم المفقود
  الشهادات
- RBC الاحتمالات المتأخرة، الجلسات المنتظرة، وانخفاض أو تأخير حركة المرور بالإجماع
- CPU, الذاكرة، القرص، وتشبع الشبكة على المضيف تشغيل الأقران

لتحليل تأخير التحقق، قم بتشغيل سجلات إزالة الأخطاء في الحلقة الرئيسية:

```bash
RUST_LOG=iroha_core::sumeragi::main_loop=debug \
  cargo run -p izanami -- --allow-net --seed 42
```

كل كتلة يجب أن تنبعث `block validation timings` مع `stateless_ms`,
`execution_ms`, و `total_ms`. مقارنة تلك التوقيتات مع p95 حجر
فترات، وعدادات تغيير الرؤية، وضغط الصف قبل التغيير
توقيتات الإجماع.

## تفسير النتائج {#interpreting-results}

تعامل الجري صحياً عندما يستمر جميع الأقران المختارون في الالتزام بالبلوك
لا ينمو التخلفات بدون قيود ، وتوقف الأخطاء عن تسبب تعافي جديد
النشاط بعد انتهاء النافذة المثبتة.

اعتبر الجري فشلاً عندما:

- الحدود تقدم الموقف أطول من `--progress-timeout`
- ارتفاعات الأقران تختلف ولا تتحول مرة أخرى
- تتجاوز تأخير p95 `--latency-p95-threshold`
- الصفوف تنمو لبقية السباق بعد إغلاق نافذة الفشل
- المعاملات التي تم رفضها أو انتهت في الوقت المناسب لا يتم تفسيرها بواسطة المختارين
  عبء العمل
- إعادة تشغيل الأقران، مسح التخزين، أو استرداد فقدان الحزمة يتطلب يدوي
  التنظيف

بعد فشل، إعادة التشغيل بنفس البذور ونوع أخطاء أقل.
يبقي عبء العمل والتوقيت قابلاً للتكرار مع تقليل الفشل
سطح.
