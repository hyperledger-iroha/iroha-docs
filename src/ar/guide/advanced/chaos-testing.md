# اختبار الفوضى مع إيزانامي {#chaos-testing-with-izanami}

إيزانامي هو منسق الفوضى في مساحة العمل العليا Iroha. يقوم ببدء عنقود محلي Iroha مؤقت، ويقدم عبء عمل قابل للتكوين، ويحقن الأخطاء في الأقران المختارين في الشبكة لكي يتمكن المشغلون من التحقق مما إذا كانت الشبكة تواصل التقدم تحت الفشل المسيطر عليه.

استخدم Izanami لفحوصات المرونة قبل الإنتاج، وإعادة إنتاج الانحدار، وضبط الإجماع. لا توجهه نحو شبكة الإنتاج: الأداة مصممة لامتلاك أقران الشبكة التي يبدأها، بما في ذلك إعادة تشغيل أقران الشبكة، مسح التخزين، تقسيمات الأقران الموثوقين المؤقتة، والضغط المحلي على CPU أو القرص.

## المتطلبات الأساسية {#prerequisites}

قم بتشغيل Izanami من [Iroha مستودع المصدر](https://github.com/hyperledger-iroha/iroha)، وليس من مستودع الوثائق هذا:

```bash
git clone https://github.com/hyperledger-iroha/iroha.git
cd iroha
cargo build -p izanami
```

يجب السماح للملف الثنائي صراحةً بإنشاء والتعامل مع نظائر الشبكة المتصلة. مرر `--allow-net` لكل تشغيل غير TUI، أو قم بتمكين `allow_net` في TUI.

```bash
cargo run -p izanami -- --allow-net --peers 4 --faulty 1 --duration 120s
```

لإعداد تشغيل تفاعلي:

```bash
cargo run -p izanami -- --tui --allow-net
```

يستمر Izanami في الاحتفاظ بإعدادات TUI و CLI تحت دليل تكوين المستخدم. يحتوي ملف الإصدار الأول على بايت تخطيط V1 واحد صريح؛ ويتم رفض الإعدادات ما قبل الإصدار أو غير المرقمة بالإصدار ويجب إعادة إنشائها بدلاً من نقلها. راجع الإعدادات المعروضة قبل إعادة استخدام ملف تعريف حالي.

## تشغيل أساسي {#baseline-run}

ابدأ بخط أساس واحد يمكن إعادة إنتاجه قبل إضافة الأعطال الشديدة:

```bash
cargo run -p izanami -- \
  --allow-net \
  --peers 4 \
  --faulty 1 \
  --duration 5m \
  --target-blocks 100 \
  --progress-interval 15s \
  --progress-timeout 120s \
  --latency-p95-threshold 2s \
  --tps 15 \
  --max-inflight 32 \
  --submitters 1 \
  --seed 42
```

ينجح هذا التشغيل فقط إذا وصلت المجموعة إلى هدف الكتلة المطلوب، واستمرت في تحقيق التقدم ضمن فترة الانتظار، وظلت تحت عتبة فترة الكتلة اختيارية p95.

سجّل الأمر، البذرة، إنهاء بروتوكول Iroha، عدد نظراء الشبكة، عدد النظراء المعطوبين، ملف تعريف عبء العمل، الهدف TPS، وعَتبة الكمون مع السجلات. بدون هذه القيم، لا يمكن لمشغل آخر إعادة تشغيل نفس نمط الفشل.

## ملفات تعريف عبء العمل {#workload-profiles}

إيزانامي لديها ملفان تعبوين:

|الملف الشخصي|استخدمه لـ|ملاحظات|
| -------- | -------------------------------------------------- | -------------------------------------- |
| `stable` |تشغيلات غمر طويلة وفحوصات أداء قابلة للتكرار|يفضل الوصفات الآمنة للتنفيذ|
|`chaos`|تغطية مسار الفشل|يشمل وصفات غير صالحة عن قصد|

استخدم الملف الشخصي المستقر أولاً:

```bash
cargo run -p izanami -- --allow-net --workload-profile stable --seed 42
```

تحوّل إلى ملف الفوضى عندما يكون الأساس مفهوماً بالفعل:

```bash
cargo run -p izanami -- --allow-net --workload-profile chaos --seed 42
```

وصفات نشر العقود معطلة في النسخ المستقرة ما لم يُسمح بها صراحة:

```bash
cargo run -p izanami -- \
  --allow-net \
  --workload-profile stable \
  --allow-contract-deploy-in-stable
```

استخدم `--nexus` عندما يجب أن يستخدم التشغيل القيم الافتراضية المدمجة SORA Nexus من مساحة العمل العلوية.

## ضوابط الأعطال {#fault-controls}

عندما يكون `--faulty` أكبر من صفر، يجب تمكين سيناريو خطأ واحد على الأقل. يتم تعيين حالات التبديل للأخطاء لتكون مُمكَّنة افتراضيًا، ويمكن تعطيل العلامات المنطقية باستخدام `=false`.

|خطأ|علم CLI|ما الذي يمارسه|
| ------------------------ | ------------------------------------------ | ------------------------------------------ |
|تعطل وأعد التشغيل| `--fault-enable-crash-restart`             |فقدان واستعادة عملية النظراء في الشبكة|
|مسح التخزين وإعادة التشغيل| `--fault-enable-wipe-storage`              |الاسترداد من فقدان الحالة المحلية|
|معاملة غير صالحة مزعجة| `--fault-enable-spam-invalid-transactions` |مسارات القبول والرفض|
|زمن تأخر الشبكة| `--fault-enable-network-latency`           |الثرثرة البطيئة ورسائل التوافق المؤجلة|
|قسمة الشبكة| `--fault-enable-network-partition`         |عزل النظراء الموثوقين مؤقتًا|
| CPU ضغط| `--fault-enable-cpu-stress`                |التحقق المحلي وضغط الجدولة|
|تشبع القرص| `--fault-enable-disk-saturation`           |ضغط التخزين المحلي|

لتشغيل يقتصر على تقسيم الشبكة:

```bash
cargo run -p izanami -- \
  --allow-net \
  --peers 4 \
  --faulty 1 \
  --duration 5m \
  --fault-window-start 60s \
  --fault-window-end 180s \
  --tps 15 \
  --submitters 1 \
  --max-inflight 32 \
  --fault-enable-crash-restart=false \
  --fault-enable-wipe-storage=false \
  --fault-enable-spam-invalid-transactions=false \
  --fault-enable-network-latency=false \
  --fault-enable-network-partition=true \
  --fault-enable-cpu-stress=false \
  --fault-enable-disk-saturation=false \
  --seed 42
```

استخدم `--fault-window-start` و `--fault-window-end` للحفاظ على فترة حالة مستقرة مضبوطة قبل وبعد حدوث الفشل المحقون. هذا يجعل من الأسهل تمييز ضوضاء بدء التشغيل عن تأثير العطل.

## أشكال السيناريو {#scenario-shapes}

يقوم كتالوج إيزانامي العلوي برسم أشكال فشل الاتصال الشائعة في البلوكشين إلى ملفات تعريف CLI. يمكنك نمذجتها بنفس العلامات:

|سيناريو|الشكل النمطي|
| --------------------- | ------------------------------------------------------------------------------------------------------------------------ |
|الحمولة المستهدفة| `--faulty 0`، مرتفع `--tps`، مقدم واحد، مرتفع `--max-inflight`|
|فشل مؤقت|تمكين التعطل/إعادة التشغيل فقط داخل نافذة خطأ محدودة|
|التوقف والتعافي|استخدم عددًا كبيرًا من الأقران المعيبة مع التعطل/إعادة التشغيل|
|عزلة القائد|استخدم نظير شبكة واحد خاطئ بالضبط مع عطل تقسيم الشبكة فقط؛ يتبع إيزانامي جهاز تتبع القائد Sumeragi|

احتفظ بمتغير واحد ثابتًا في كل مرة. إذا قمت بتغيير عدد نظراء الشبكة، أو ملف تعريف عبء العمل، أو فترة العطل، و TPS في نفس التجربة، سيكون من الصعب تفسير النتيجة.

## ماذا تشاهد {#what-to-watch}

أثناء التشغيل، راقب نفس الإشارات المستخدمة للتحقق من الأداء:

- تقدم ارتفاع الكتلة عبر كل ند للشبكة يعمل
- المعاملات المقدمة، المقبولة، المرفوضة، والمنتهية بالمهلة
- عمق الطابور، تشبع الطابور، و API ضغط العودة للنقطة النهائية
- عرض التغييرات، مسارات الاسترداد، الكتل المفقودة، وشهادات النصاب المفقودة
- تم توقيع RS16 تراكم توفر، الجلسات المعلقة، وحركة المرور المتأخرة للموافقة
- CPU، الذاكرة، القرص، وتشبع الشبكة على المضيف الذي يشغّل نظراء الشبكة

لتحليل زمن الاستجابة للتحقق، قم بتمكين سجلات تصحيح الحلقة الرئيسية:

```bash
RUST_LOG=iroha_core::sumeragi::main_loop=debug \
  cargo run -p izanami -- --allow-net --seed 42
```

يجب أن يصدر كل كتلة `block validation timings` مع `stateless_ms` و`execution_ms` و`total_ms`. قارن تلك التوقيتات مع فترات كتلة p95، وأعداد تغييرات العرض، وضغط الطابور قبل تغيير مؤقتات الإجماع.

## تفسير النتائج {#interpreting-results}

اعتبر التشغيل صحيًا عندما يستمر جميع الأقران الشبكيين المحددين في إنهاء الكتل، ولا ينمو التراكم بشكل غير محدود، وتتوقف الأخطاء عن التسبب في نشاط استرداد جديد بعد انتهاء النافذة المحددة.

اعتبر الجري فشلاً عندما:

- توقف تقدم الحظر لفترة أطول من `--progress-timeout`
- ارتفاعات نظراء الشبكة تتباعد ولا تتقارب مرة أخرى
- تجاوز الكمون عند P95 `--latency-p95-threshold`
- تنمو الطوابير لبقية التشغيل بعد إغلاق نافذة الخطأ
- المعاملات المرفوضة أو التي انتهت مهلة تنفيذها لا تُفسر بالعبء العملي المحدد
- إعادة تشغيل نظير الشبكة، مسح التخزين، أو استعادة القسم تتطلب تنظيفًا يدويًا

بعد الفشل، أعد التشغيل باستخدام نفس البذرة ونوع خطأ واحد أقل. هذا يحافظ على قابلية إعادة إنشاء عبء العمل والتوقيت مع تضييق سطح الفشل.
