# صيغة عنوان الحساب I105 {#i105-account-address-format}

I105 هو تنسيق النص الخارجي القنوني ل Iroha 3 `AccountId`.

تحمله المفيد يمثل مدير الحساب.

تحدّد علامة الشبكة الشبكة المقصودة باستخدام مميّز السلسلة.

استخدمه في أي مكان يطلب فيه API المعاملة أو الإذن أو الاستفسار للحساب القنوني ID.

معرّف الحساب I105 ID بلا نطاق.

قيمة مثل `treasury@payments.universal` هي اسم مستعار للحساب، وليس أي كتابة أخرى لـ I105 ID.

لا يؤدي اشتقاق I105 ID إلى تسجيل الحساب أو تمويله.

::: warning القواعد التي تمنع معظم فشل التكامل

- اختر ملف تعريف الشبكة قبل تشفير العنوان أو التحقق منه.
- تخزين ومقارنة السلسلة الكانونية UTF-8 بالضبط.
- حافظ على حالة الأحرف (الكبيرة والصغيرة) كما هي، ولا تطبّق تسوية `Unicode`.
- يجب ألا يكون لـ I105 ID لاحقة `@domain` أو `@domain.dataspace`.
- استخدم Iroha SDK أو `iroha tools address`.
- التعبير النمطي ليس أداة تحقق من I105.

:::

## التشريح الحرفي {#literal-anatomy}

حرف I105 يحتوي على ثلاثة أجزاء مجاورة ولا يوجد منفصل:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

|الجزء|الغرض|تغطية مبلغ الشيك |
| ---------------- | ------------------------------------------------------------------ | ----------------- |
| علامة الشبكة |خرائط النص إلى واحد `u16` سلسلة التمييز |لا تغطية|
|الحمولة المفيدة|`base-105` تشفير البايتات القانونية للمراقب الحساب |تغطية|
|رقم التحقق|ستة قيم في `Bech32m` النمط `5-bit` تمثيلها بألفبي I105 |ن/أ |

الحمل المفيد ومبلغ التحقق يحدد مدير حساب.

الحارس يختار سياق الشبكة.

يحتوي نفس جهاز التحكم على نفس الحمل المفيد ومبلغ التحقق من Taira و Minamoto، ولكن كل شبكة تستخدم حارسًا قياديًا مختلفًا.

يجب أن تفرض وحدة فك الترميز مميّز السلسلة المتوقع.

لا يستطيع المجموع الاختباري اكتشاف استبدال علامة الشبكة.

### علامات الشبكة {#network-sentinels}

|شبكة أو سياق |التمييز في السلسلة|هيكس | علامة الشبكة المعيارية                          |
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
|Taira شبكة اختبار عامة |                            `369` |`0x0171` |`test` |
|Minamoto شبكة عامة|                            `753` |`0x02f1` |`sora` |
|السياق التنموي |                              `0` |`0x0000` |`dev` |
|أي قيمة أخرى `u16` |جميعها باستثناء `0`، `369`، و `753` |        — |`n` زائد الحد الأدنى من العشريات، على سبيل المثال `n42` |

القيم المسماة تستخدم دائمًا حارسها المسمى.

الأشكال مثل `n00042` و`n369` و`n753` و`n0` ليست تمثيلات معيارية.

قيمة ID لسلسلة المعاملات ومميّز سلسلة I105 قيمتان منفصلتان.

اختيار نقطة نهاية أو سلسلة ID لا يشير بشكل ضمني إلى اختيار ملف تعريف العنوان.

## المثال القياسي لمفتاح واحد {#normative-single-key-example}

الحمولة المفيدة والنموذج Minamoto أدناه يأتي من جهاز الامتثال المتقاطع-SDK.

النموذج Taira يطبق حارس Taira على نفس الحملة المفيدة:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

الحمل المفيد القنوني يبدأ مع `02 00 01 20`: العنوان `0x02`, علامة مفاتيح بسيطة `0x00`, `Ed25519` منحنى ID `0x01`, ومدة مفتاح 32 بايت `0x20`.

المقبل `multihash` هو البيانات الأساسية المدخلة ولا يتم نسخها في حمولة التحكم.

## إعداد ومفتشة IDs مع CLI {#create-and-inspect-ids-with-the-cli}

تفضل الملف الشخصي المسمى لشبكة عامة:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

تقييم ومقارنة مدخل I105 أثناء تشخيص سلوك العنوان-كوديك:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

تفتيش النموذج المكتشف، السبعية القانونية، والسياق الشبكي المحدد ك JSON:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

مراجعة هيكل كودك العنوان في ملف منفصل عن الخط الجديد دون قبول أخطاء التحليل بصمت:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution CLI حدود التحقق من المصادقة

تعمل الأوامر `convert` ، `normalize`، و `audit` على كوديك المستوى السفلي `AccountAddress`.

تتحقق هذه الأوامر من علامة الشبكة، والأبجدية، والمجموع الاختباري، وأطوال البايتات، وبنية `CurveId`/المفتاح، ومن إعادة الترميز الدقيقة على مستوى العنوان.

لا تنشئ هذه الأوامر كائن `AccountId`.

لا تتحقق هذه الأوامر بمفردها من جميع دلالات سياسة التوقيع المتعدد.

لا يثبتون أن فئة الرأس تتطابق مع جهاز التحكم.

استخدم التحقق الصارم من `AccountId` قبل التفويض أو التخزين الدائم.

:::

بالنسبة للشبكة الخاصة، استخدم تمييزها المكوّن صراحة مع `--network-prefix`.

عند تحويل عنوان موجود بين سياقات صريحة، أضف أيضاً المصدر `--expect-prefix`:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

إعادة تشفير تغير فقط سياق الشبكة.

فإنه لا يسجل الحساب على الشبكة المستهدفة أو يثبت أنه ينبغي إعادة استخدام نفس المعالج هناك.

## خوارزمية تشفير {#encoding-algorithm}

يقوم مرموزات القنونيكية بتلك العمليات:

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

يتم الحفاظ على البايتات الصفرية الرائدة بأرقام `base-105` ذات قيمة صفرية.

يستخدم المجموع الاختباري مولدات `Bech32` `polymod` والثابت `0x2bc830a3`.

إن HRP المستخدم حصريًا للمجموع الاختباري هو سلسلة ASCII `snx`.

لا يُدرج HRP المستخدم حصريًا للمجموع الاختباري في العنوان.

القيم الستة من مجموعات التحقق تقع في نطاق `0..31` ويتم عرضها عبر نفس الأبجدية I105 مثل الحمولة المفيدة.

### I105 الأبجدية {#i105-alphabet}

الرموز الـ105 يتم تحديدها بهذه الترتيب المحدد

الصف الأول هو `Bitcoin Base58` الأبجدية ويحتوي على الأرقام `0..57`.

الصف الثاني يحتوي على الأرقام `58..104`.

قم بتجميع الصفوف عند تنفيذ الكوديك.

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

الأبجدية حساسة `Unicode`.

يستخدم التسلسل الدقيق رموز `compatibility-width` اليابانية `kana` بالإضافة إلى نقاط الرمز المعروضة ل`ヰ` و `ヱ`.

لا تطبّق NFC أو NFKC، ولا تحوّل عرض الأحرف، ولا توحّد حالة الأحرف، ولا تستبدل الأحرف بأخرى متشابهة بصريًا.

ASCII `0` ، `O`، `I`، و `l` ليست رموز الأبجدية.

## الحملة المفيدة للحسابات القانونية {#canonical-account-payload}

جسم `base-105` يرمز حمولة مفيدة للحسابات الثنائية، وليس سلسلة مفتاح عامة ولا كائن Norito JSON:

```text
header:u8 || controller:variable
```

جميع أرقام كاملة متعددة البايت أدناه غير مؤهلة و `big-endian`.

النطاق ومساحة البيانات والاسم المستعار وUAID وبايتات البيانات الوصفية للحساب غير موجودة.

### بايت الرأس {#header-byte}

|قطرات |العرض|الناتج الحالي للكودر |المعنى|
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |حقل إصدار شكل العنوان |
| `4..3` |     2 |`0` مفتاح واحد، `1` متعددة الإشارات |فئة العناوين|
| `2..1` |     2 |                          `1` |حقل نسخة التطبيع |
| `0`    |     1 |                          `0` |الاحتياطي `extension flag` |

الحالي V1 الترميزات تنبعث عن رأس `0x02` لجهاز التحكم بمفتاح واحد و `0x0a` لسيطرة متعددة السجلات.

لا يتم تعيين فئات العناوين `2` و `3`.

يتم رفض `extension flag` من `1`.

يمكن لفكّر المستوى المنخفض الحفاظ على القيم البيتية الأخرى للنسخة والطبيعية ولا يتحقق بشكل مستقل من الفصل مقابل علامة التحكم.

تحويل إلى `AccountId` ومقارنة إظهارها القنوني يثبت القنونيية الحالية V1.

### جهاز تحكم مفاتيح واحد {#single-key-controller}

استخدم الصيغة المدمجة عندما لا يتجاوز طول الحمولة الخام للمفتاح العام 255 بايتًا:

|الحقل|العرض|قيمة أو معنى|
| ------------ | --------------: | ------------------------ |
|`tag` |1 بايت |`0x00` |
|`curve` |1 بايت |`CurveId` قيمة السجل |
|`key_len` |1 بايت |طول المفتاح الخام|
|`public_key` |`key_len` بايت |الحمولة الخام المفيدة للمفتاح العام|

مفاتيح أطول من 255 بايت تستخدم النموذج الممتد:

|الحقل|العرض|قيمة أو معنى|
| ------------ | --------------: | ---------------------------- |
|`tag` |1 بايت |`0x02` |
|`curve` |1 بايت |`CurveId` قيمة السجل |
|`key_len` |2 بايت |طول مفتاح الخام، `big-endian` |
|`public_key` |`key_len` بايت |الحمل المفيد الخام للمفتاح العام |

لا يكون الترميز الممتد معياريًا لمفتاح يمكن تمثيله بالصيغة المدمجة.

### وحدة تحكم متعددة التوقيعات {#multisig-controller}

|الحقل|العرض|قيمة أو معنى|
| ---------------- | -------: | ------------------------------ |
|`tag` |1 بايت |`0x01` |
|`policy_version` |1 بايت |القيمة الحالية `1` |
|`threshold` |2 بايت |الوزن الإجمالي المطلوب للموافقة |
|`member_count` |2 بايت |عدد الأعضاء التالية |
|`members` |متغير |سجلات أعضاء متكررة |

كل سجل عضو هو:

|الحقل|العرض|المعنى|
| ------------ | --------------: | ------------------------ |
|`curve` |1 بايت |`CurveId` قيمة السجل |
|`weight` |2 بايت |وزن الموافقة للعضو |
|`key_len` |2 بايت |طول المفتاح الخام|
|`public_key` |`key_len` بايت |الحمولة الخام المفيدة للمفتاح العام|

سياسة صالحة لديها عضو واحد على الأقل، ووزن إيجابي، لا يوجد مفاتيح عامة مزدوجة، وعلى عتبة من `1` إلى مجموع وزنات الأعضاء.

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

تصنف البناء القنوني الأعضاء من خلال الاسم المستقر لخوارزمة التوقيع ، وبايت الفصل الصفر ، ومن ثم البايتات العامة الخام.

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

حرف I105 لا يملك طولًا ثابتًا لأن وحدات التحكم متعددة الألواح ولاحقة الكم يمكن أن تكون كبيرة.

### سجل `CurveId` {#curveid-registry}

في العمود الأخير، يتم تحديد الميزة الاختيارية `Cargo` المطلوبة.

علامة التقاطع تعني أن إدخال السجل متاح دون ميزة نموذج بيانات اختيارية.

|ID |تخطيط التوقيع |ميزة `Cargo` مطلوبة |
| ---: | -------------------------------------------- | ------------------------ |
|  `1` |`Ed25519` | —                        |
|  `2` |`ML-DSA` | —                        |
|  `3` |`BLS12-381 normal` |`bls` |
|  `4` |`secp256k1` | —                        |
|  `5` |`BLS12-381 small` |`bls` |
| `10` |`GOST R 34.10-2012 256-bit, parameter set A` |`gost` |
| `11` |`GOST R 34.10-2012 256-bit, parameter set B` |`gost` |
| `12` |`GOST R 34.10-2012 256-bit, parameter set C` |`gost` |
| `13` |`GOST R 34.10-2012 512-bit, parameter set A` |`gost` |
| `14` |`GOST R 34.10-2012 512-bit, parameter set B` |`gost` |
| `15` |`SM2` |`sm` |

يتم رفض IDs غير المخصصة والخوارزميات التي تم تعطيلها في البناء المتلقي.

يجب أن يكون الحمل المفيد الرئيسي صالحًا من الناحية الهيكلية أيضًا للخوارزمية التي يختارها `CurveId` المعلنة.

## التحقق الصارم من AccountId والقدسية {#strict-accountid-validation-and-canonicality}

بعد تشكيل SDK مع التمييز المتوقع للسلسلة ، قم بتحليلها إلى `AccountId` ومقارنة التصوير القنوني المرجع مع المدخل المحل.

إن المقارنة مهمة لأن المصفح يمكنه تطبيع مادة التحكم القابلة للكشف أثناء بناء `AccountId`.

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

بالنسبة لسلسلة غير موثوق بها، يجب أن يكون التطبيق المتوافق:

1. أزِل فقط محارف المسافات البيضاء المسموح بها أثناء النقل من حول القيمة كاملةً.
2. اقرأ علامة الشبكة واشترط مميّز السلسلة المتوقع.
3. خريط كل رمز `Unicode` المتبقي من خلال الأبجدية الدقيقة لـ 105 رمز.
4. افصل أرقام المجموع الاختباري الستة.
5. قم بتحويل أرقام الحمولة المفيدة إلى البايتات القانونية.
6. تحقّق من المجموع الاختباري المحسوب على تلك البايتات المعيارية.
7. تحليل الرأس والتحكم، يتطلب:
   - طولات المجال الدقيقة
   - a مدعوم `CurveId`
   - مفتاح عام صالح
   - عدم وجود بايتات زائدة في النهاية
   - سياسة توقيع متعدد صالحة عند الاقتضاء
8. بناء `AccountId`.
9. أنشئ التمثيل المعياري لـ `AccountId` باستخدام المميّز المتوقع.
10. اشترط التطابق `byte-for-byte` مع الإدخال بعد إزالة المسافات المحيطة به.

ترفض خطوة `render-and-compare` النهائية والصريحة في التطبيق علامات الشبكة الرقمية غير ذات التمثيل الأدنى، وتخطيطات المتحكّم غير المعيارية، ومواد السياسة المعاد ترتيبها، وأي صياغة أخرى يمكن فك ترميزها لكنها لا تطابق ناتج V1 الحالي للمُرمِّز.

لا يمكن استبدال هذا التحقق بمبلغ الفحص الناجح أو دراسة منخفضة المستوى `AccountAddress`.

لا تقبل هذه القيم في حقل حساب صارم - ID:

- اسم مستعار لحساب مثل `alice@wonderland.universal`
- قيمة I105 أُلحقت بها لاحقة `@domain`
- مفتاح عام `multihash` مثل `ed0120...`
- الهيكس القائم على الحمل المفيد مثل `0x02000120...`
- عنوان لتمييز السلسلة الخطأ
- سلسلة ذات الأحرف الكبرى أو الصغيرة المتغيرة، وعرض الحروف، `kana`، والحمولة المفيدة، أو مجموعات التحقق.

حل أسماء مستعار عند حدود التطبيقات والاحتفاظ بالنسخة القنونية المرجعة I105 ID للحصول على الترخيص والتوقيع والإذن وسجلات التحقيق.

### رموز الخطأ المستقرة الشائعة {#common-stable-error-codes}

|الرمز |المعنى|
| -------------------------------- | ------------------------------------------------------------------- |
|`ERR_UNEXPECTED_NETWORK_PREFIX` | المميّز المفكوك لا يطابق الشبكة المطلوبة        |
|`ERR_CHECKSUM_MISMATCH` |الرموز الستة لم تتماشى مع الحمولة|
|`ERR_INVALID_I105_CHAR` |الرمز خارج الأبجدية الدقيقة|
|`ERR_MISSING_I105_SENTINEL` | لم يُعثر على علامة شبكة معيارية مسمّاة أو رقمية                    |
|`ERR_I105_TOO_SHORT` |الجسم لا يمكن أن يحتوي على كل من الحمولة المفيدة والرقم التحقق|
|`ERR_INVALID_LENGTH` | أحد حقول المتحكّم مبتور أو يستخدم صيغة طول غير معيارية |
|`ERR_UNKNOWN_CURVE` |يعلن مدير المعالجة عن `CurveId` غير المخصص أو غير متاح |
|`ERR_INVALID_PUBLIC_KEY` |المفتاح غير صالح للخوارزمية التي اختارتها `CurveId` |
|`ERR_UNSUPPORTED_ADDRESS_FORMAT` | الإدخال ليس صيغة I105 معيارية مقبولة                    |

## API، قواعد التخزين والظهور {#api-storage-and-display-rules}

- أرسل السلسلة الدقيقة I105 UTF-8 في حقول الحسابات JSON.
- `Percent-encode` الحساب الكامل ID قبل وضعها في قطاع مسار URL.
- لا تستخدم اسمًا مستعارًا للحساب بدلًا من I105 ID مطلقًا.
- تخزين السلسلة القانونية التي يعيدها الكوديك مع `byte-preserving` النطقية المقارنة.
- استخدم قواعد ترتيب ومقارنة للنصوص تحافظ على حالة الأحرف وعرض المحارف.
- احتفظ بمميّز السلسلة أو ملف تعريف الشبكة المسمّى مع بيانات الحساب المصدّرة والنسخ الاحتياطية.
- إعادة استخدام عنوان فقط مع سياق شبكتها.
- عرض العنوان الكامل وإعطاء عمل نسخة.
- حافظ على كل شخصية `kana` بالضبط.
- إبق العنوان الكامل متاحًا عندما تكون الشاشة الصغيرة قصيرة من منتصفها.
- استخدم الكانونيكال المخزن ID بدلاً من إعادة بناءه من اسم مستعار.

يستخدم عرض `AccountId` وتمثيله بصيغة JSON الشكل المعياري I105.

تستخدم عرض `AccountAddress` المستوى السفلي / تمثيل JSON الهيكس القنوني للسياقات الداخلية والتحريف.

استدعِ مُرمِّز I105 الصريح الخاص بـ `AccountAddress` عند الحاجة إلى ID حساب خارجي.

لتنفيذ عمليات إنشاء الحسابات وتحديد الأسماء التلقائية، استمر في [الحسابات والتلقائيات التلقائية ](/ar/cookbook/accounts-and-aliases.md).

لمعرفة نموذج بيانات الحساب، انظر [الحسابات](/ar/blockchain/accounts.md).
