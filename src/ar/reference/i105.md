# I105 صيغة عنوان الحساب {#i105-account-address-format}

I105 هو تنسيق النص الخارجي القياسي للبروتوكول الواحد لـ Iroha 3 `AccountId`.

تمثل حمولة البيانات الخاصة به وحدة التحكم في الحساب.

تحدّد علامة الشبكة الشبكة المقصودة باستخدام مميّز السلسلة.

استخدمه في أي مكان يطلب فيه API، أو معاملة، أو إذن، أو استعلام معرف حساب موحد وفقاً للبروتوكول.

معرّف الحساب I105 ID بلا نطاق.

قيمة مثل `treasury@payments.universal` هي اسم مستعار للحساب، وليست تهجئة أخرى للمعرّف I105.

لا يؤدي اشتقاق I105 ID إلى تسجيل الحساب أو تمويله.

::: warning القواعد التي تمنع معظم حالات فشل التكامل

- اختر ملف الشبكة قبل ترميز أو التحقق من عنوان.
- قم بتخزين ومقارنة سلسلة بروتوكول المعيار الفردي UTF-8 بالضبط.
- حافظ على حالة الأحرف (الكبيرة والصغيرة) كما هي، ولا تطبّق تسوية `Unicode`.
- يجب ألا يكون لـ I105 ID لاحقة `@domain` أو `@domain.dataspace`.
- استخدم Iroha SDK أو `iroha tools address`.
- التعبير النمطي ليس أداة تحقق من I105.

:::

## تشريح حرفي {#literal-anatomy}

للكود الحرفي I105 ثلاثة أجزاء متجاورة ولا يحتوي على فاصل:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

|جزء|الغرض|تغطية مجموع التحقق|
| ---------------- | ------------------------------------------------------------------ | ----------------- |
| علامة الشبكة |يحوّل النص إلى مميز سلسلة `u16` واحد|غير مغطى|
|حمولة|`base-105` ترميز بايتات وحدة التحكم في الحساب القياسية للبروتوكول الفردي|مغطى|
|مجموع التحقق|ستة قيم `5-bit`-أسلوب `Bech32m` تم عرضها بالأبجدية I105|غير متوفر|

تحدد الحمولة ومجموع التحقق وحدة التحكم في الحساب.

يختار الحارس سياق الشبكة.

لدى نفس وحدة التحكم نفس الحمولة ومجموع الاختبار على Taira و Minamoto، لكن كل شبكة تستخدم علامة بداية مختلفة.

يجب أن تفرض وحدة فك الترميز مميّز السلسلة المتوقع.

لا يستطيع المجموع الاختباري اكتشاف استبدال علامة الشبكة.

### علامات الشبكة {#network-sentinels}

|الشبكة أو السياق|مميز السلسلة|هيكس| علامة الشبكة المعيارية                          |
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
| Taira الشبكة التجريبية العامة |                            `369` | `0x0171` | `test`                                      |
| Minamoto الشبكة العامة |                            `753` | `0x02f1` | `sora`                                      |
|سياق التنمية|                              `0` | `0x0000` | `dev`                                       |
|أي قيمة `u16` أخرى|الجميع باستثناء `0` و `369` و `753`|        — | `n` زائد الحد الأدنى من الكسور العشرية، على سبيل المثال `n42` |

تستخدم القيم المسماة دائما الحارس المسمي الخاص بها.

الأشكال مثل `n00042` و`n369` و`n753` و`n0` ليست تمثيلات معيارية.

قيمة ID لسلسلة المعاملات ومميّز سلسلة I105 قيمتان منفصلتان.

اختيار نقطة نهاية أو معرف سلسلة API لا يختار ضمنيًا ملف تعريف العنوان.

## مثال قياسي بمفتاح واحد {#normative-single-key-example}

تأتي الحمولة وصيغة Minamoto أدناه من بيانات اختبار الامتثال المشتركة بين حزم SDK.

نموذج Taira يطبق حارس Taira على نفس الحمولة:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

يبدأ حمولة معيار البروتوكول الفردي بـ `02 00 01 20`: الرأس `0x02`، ووسم مفرد مضغوط `0x00`، ومعرف المنحنى `Ed25519` `0x01`، وطول المفتاح 32 بايت `0x20`.

اللاحقة `multihash` هي بيانات وصفية للإدخال وليست مضمَّنة في حمولة وحدة التحكم.

## إنشاء وفحص المعرفات باستخدام CLI {#create-and-inspect-ids-with-the-cli}

فضل ملفًا شخصيًا مسمى لشبكة عامة:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

تطبيع ومقارنة إدخال I105 أثناء تشخيص سلوك رمز العنوان:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

افحص التنسيق المكتشف، السادس عشري القياسي للبروتوكول الواحد، وسياق الشبكة المحدد كما يلي JSON:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

تدقيق هيكل العنوان-الترميز في ملف مفصول بأسطر جديدة دون قبول إخفاقات التحليل بصمت:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution CLI حد التحقق

تعمل أوامر `convert` و`normalize` و`audit` على برنامج الترميز `AccountAddress` منخفض المستوى.

تتحقق هذه الأوامر من علامة الشبكة، والأبجدية، والمجموع الاختباري، وأطوال البايتات، وبنية `CurveId`/المفتاح، ومن إعادة الترميز الدقيقة على مستوى العنوان.

لا تنشئ هذه الأوامر كائن `AccountId`.

لا تتحقق هذه الأوامر بمفردها من جميع دلالات سياسة التوقيع المتعدد.

هم لا يثبتون أن فئة العنوان تطابق وحدة التحكم.

استخدم التحقق الصارم من `AccountId` قبل التفويض أو التخزين الدائم.

:::

بالنسبة لشبكة خاصة، استخدم ميزة التمييز المكونة لها صراحة مع `--network-prefix`.

عند تحويل عنوان موجود بين السياقات الصريحة، زود المصدر أيضًا بـ `--expect-prefix`:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

إعادة الترميز تغير سياق الشبكة فقط.

لا يقوم بتسجيل الحساب على الشبكة المستهدفة أو إثبات أن نفس المتحكم يجب إعادة استخدامه هناك.

## خوارزمية الترميز {#encoding-algorithm}

تقوم المشفرات التي تتبع بروتوكولًا واحدًا قياسيًا بهذه العمليات:

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

يتم الاحتفاظ بالبايتات الصفرية الرائدة كأرقام `base-105` ذات قيمة صفرية.

يستخدم المجموع الاختباري مولدات `Bech32` `polymod` والثابت `0x2bc830a3`.

إن HRP المستخدم حصريًا للمجموع الاختباري هو سلسلة ASCII `snx`.

لا يُدرج HRP المستخدم حصريًا للمجموع الاختباري في العنوان.

قيم الجمع الاختباري الستة تقع في المدى `0..31` ويتم عرضها من خلال نفس أبجدية I105 مثل الحمولة.

### I105 الأبجدية {#i105-alphabet}

تم فهرسة الرموز الـ 105 بهذا الترتيب بالضبط.

الصف الأول هو الأبجدية `Bitcoin Base58` ويحتوي على الأرقام `0..57`.

الصف الثاني يحتوي على الأرقام `58..104`.

قم بدمج الصفوف عند تنفيذ برنامج الترميز.

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

الأبجدية حساسة لـ `Unicode`.

التسلسل الدقيق يستخدم رموز يابانية `compatibility-width` `kana` بالإضافة إلى نقاط الشفرة الموضحة لـ `ヰ` و `ヱ`.

لا تطبّق NFC أو NFKC، ولا تحوّل عرض الأحرف، ولا توحّد حالة الأحرف، ولا تستبدل الأحرف بأخرى متشابهة بصريًا.

ASCII `0` و`O` و`I` و`l` ليست رموز أبجدية.

## حمولة حساب قياسية لبروتوكول واحد {#canonical-account-payload}

الجسم `base-105` يشفر حمولة حساب ثنائية، وليس سلسلة مفتاح عام وليس كائن Norito JSON:

```text
header:u8 || controller:variable
```

جميع الأعداد الصحيحة متعددة البايت أدناه غير موقعة و`big-endian`.

النطاق ومساحة البيانات والاسم المستعار وUAID وبايتات البيانات الوصفية للحساب غير موجودة.

### بايت الرأس {#header-byte}

|بتات|العرض|مخرجات الترميز الحالية|المعنى|
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |حقل إصدار تنسيق العنوان|
| `4..3` |     2 |`0` مفتاح فردي، `1` توقيع متعدد|فئة العنوان|
| `2..1` |     2 |                          `1` |حقل إصدار التطبيع|
| `0`    |     1 |                          `0` |محجوز `extension flag`|

المشفّرات الحالية V1 تصدر العنوان `0x02` لمتحكم بمفتاح واحد و `0x0a` لمتحكم متعدد التواقيع.

فئات العناوين `2` و `3` غير مخصصة.

تم رفض `extension flag` من `1`.

يمكن للمُفكك منخفض المستوى الحفاظ على قيم البت للإصدار الآخر والتطبيع ولا يقوم بالتحقق من صحة الفئة بشكل مستقل مقابل علامة وحدة التحكم.

التحويل إلى `AccountId` ومقارنة عرضه وفق معيار البروتوكول الواحد يثبت امتثال V1 الحالي لصيغة معيار البروتوكول الواحد.

### جهاز تحكم بمفتاح واحد {#single-key-controller}

استخدم الصيغة المدمجة عندما لا يتجاوز طول الحمولة الخام للمفتاح العام 255 بايتًا:

|حقل|العرض|القيمة أو المعنى|
| ------------ | --------------: | ------------------------ |
|`tag`|1 بايت| `0x00`                   |
|`curve`|1 بايت|قيمة التسجيل `CurveId`|
|`key_len`|1 بايت|طول المفتاح الخام|
| `public_key` | `key_len` بايت |حمولة المفتاح العام الخام|

المفاتيح الأطول من ٢٥٥ بايت تستخدم الشكل الموسع:

|حقل|العرض|القيمة أو المعنى|
| ------------ | --------------: | ---------------------------- |
| `tag`        |1 بايت| `0x02`                       |
| `curve`      |1 بايت|قيمة سجل `CurveId`|
| `key_len`    |2 بايت|طول المفتاح الخام، `big-endian`|
| `public_key` | `key_len` بايت |حمولة المفتاح العام الخام|

لا يكون الترميز الممتد معياريًا لمفتاح يمكن تمثيله بالصيغة المدمجة.

### وحدة تحكم متعددة التوقيعات {#multisig-controller}

|حقل|العرض|القيمة أو المعنى|
| ---------------- | -------: | ------------------------------ |
| `tag`            |1 بايت| `0x01`                         |
| `policy_version` |1 بايت|القيمة الحالية `1`|
| `threshold`      |2 بايت|الوزن الإجمالي للموافقة المطلوبة|
|`member_count`|2 بايت|عدد الأعضاء التاليين|
| `members`        |متغير|سجلات الأعضاء المكررة|

كل سجل عضو هو:

|حقل|العرض|المعنى|
| ------------ | --------------: | ------------------------ |
| `curve`      |1 بايت|قيمة التسجيل `CurveId`|
| `weight`     |2 بايت|وزن موافقة العضو|
|`key_len`|2 بايت|طول المفتاح الخام|
| `public_key` |`key_len` بايت|حمولة المفتاح العام الخام|

السياسة الصالحة لها عضو واحد على الأقل، وأوزان موجبة، ولا توجد مفاتيح عامة مكررة، وعَتَبة من `1` حتى مجموع أوزان الأعضاء.

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

يقوم بروتوكول واحد قياسي بترتيب الأعضاء وفقًا للاسم المستقر لخوارزمية التوقيع، ثم بايت الفاصل الصفري، ثم بايتات المفتاح العام الخام.

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

يُعتبر الحرف الحرفي I105 بلا طول محدد لأن وحدات التحكم متعددة التوقيعات وما بعد الكم يمكن أن تكون كبيرة.

### `CurveId` سجل {#curveid-registry}

العمود الأخير يذكر الميزة الاختيارية المطلوبة `Cargo`.

الشرطة تعني أن إدخال السجل متاح بدون ميزة اختيارية في نموذج البيانات.

|معرّف|خوارزمية التوقيع|الميزة المطلوبة `Cargo`|
| ---: | -------------------------------------------- | ------------------------ |
|  `1` | `Ed25519`                                    | —                        |
|  `2` | `ML-DSA`                                     | —                        |
|  `3` | `BLS12-381 normal`                           | `bls`                    |
|  `4` | `secp256k1`                                  | —                        |
|  `5` | `BLS12-381 small`                            | `bls`                    |
| `10` | `GOST R 34.10-2012 256-bit, parameter set A` |`gost`|
| `11` | `GOST R 34.10-2012 256-bit, parameter set B` | `gost`                   |
| `12` | `GOST R 34.10-2012 256-bit, parameter set C` |`gost`|
| `13` | `GOST R 34.10-2012 512-bit, parameter set A` | `gost`                   |
| `14` | `GOST R 34.10-2012 512-bit, parameter set B` | `gost`                   |
| `15` | `SM2`                                        | `sm`                     |

يتم رفض المعرفات غير المخصصة والخوارزميات المعطلة في النسخة المستقبلة.

يجب أن تكون الحمولة الرئيسية صالحة من الناحية الهيكلية أيضًا للخوارزمية التي تم اختيارها بواسطة `CurveId` المعلن.

## التحقق الصارم AccountId والامتثال لنموذج البروتوكول الموحد المعياري {#strict-accountid-validation-and-canonicality}

بعد تكوين SDK بالمميز المتوقع للسلسلة، قم بتحليله إلى `AccountId` وقارن العرض القياسي للبروتوكول المفرد الذي تم إرجاعه مع الإدخال المقتطع.

المقارنة مهمة لأن المحلل يمكنه تطبيع المواد القابلة للفك المترابط أثناء بناء `AccountId`.

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

بالنسبة لسلسلة غير موثوق بها، يجب على التطبيق المتوافق أن:

1. أزِل فقط محارف المسافات البيضاء المسموح بها أثناء النقل من حول القيمة كاملةً.
2. اقرأ علامة الشبكة واشترط مميّز السلسلة المتوقع.
3. ارسم كل رمز `Unicode` المتبقي من خلال الأبجدية المكونة من 105 رمزًا بالضبط.
4. افصل أرقام المجموع الاختباري الستة.
5. حوّل أرقام الحمولة مرة أخرى إلى بايتات قياسية مفردة للبروتوكول.
6. تحقّق من المجموع الاختباري المحسوب على تلك البايتات المعيارية.
7. حلل الرأس والمتحكم، مع الاحتياج إلى:
   - أطوال الحقول الدقيقة
   - مدعوم `CurveId`
   - مفتاح عام صالح
   - عدم وجود بايتات زائدة في النهاية
   - سياسة توقيع متعدد صالحة عند الاقتضاء
8. قم ببناء `AccountId`.
9. أنشئ التمثيل المعياري لـ `AccountId` باستخدام المميّز المتوقع.
10. اشترط التطابق `byte-for-byte` مع الإدخال بعد إزالة المسافات المحيطة به.

ترفض خطوة `render-and-compare` النهائية والصريحة في التطبيق علامات الشبكة الرقمية غير ذات التمثيل الأدنى، وتخطيطات المتحكّم غير المعيارية، ومواد السياسة المعاد ترتيبها، وأي صياغة أخرى يمكن فك ترميزها لكنها لا تطابق ناتج V1 الحالي للمُرمِّز.

نجاح فحص المجموع أو تحليل `AccountAddress` منخفض المستوى لا يعد بديلاً عن هذا الفحص.

لا تقبل هذه القيم في حقل معرف الحساب الصارم:

- اسم مستعار للحساب مثل `alice@wonderland.universal`
- قيمة I105 أُلحقت بها لاحقة `@domain`
- مفتاح عام `multihash` مثل `ed0120...`
- حمولة قياسية لبروتوكول واحد بصيغة هيكس مثل `0x02000120...`
- عنوان لسلسلة التمييز الخاطئة
- سلسلة بأحرف كبيرة أو صغيرة معدلة، عرض الأحرف، `kana`، الحمولة، أو مجموع التحقق

قم بحل الأسماء المستعارة عند حدود التطبيق واحتفظ بمعرّف I105 الموحد وفق معيار البروتوكول الذي تم إرجاعه للتفويض والتوقيع والصلاحيات وسجلات التدقيق.

## API، قواعد التخزين والعرض {#api-storage-and-display-rules}

- أرسل السلسلة الدقيقة I105 UTF-8 في حقول حساب JSON.
- `Percent-encode` الحساب الكامل قبل وضعه في مقطع مسار URL.
- لا تستخدم اسمًا مستعارًا للحساب بدلًا من I105 ID مطلقًا.
- خزّن السلسلة المعيارية التي يعيدها المُرمِّز باستخدام دلالات مقارنة `byte-preserving`.
- استخدم قواعد ترتيب ومقارنة للنصوص تحافظ على حالة الأحرف وعرض المحارف.
- احتفظ بمميّز السلسلة أو ملف تعريف الشبكة المسمّى مع بيانات الحساب المصدّرة والنسخ الاحتياطية.
- أعد استخدام العنوان فقط في سياق شبكته.
- عرض العنوان الكامل وتوفير إجراء النسخ.
- حافظ على كل حرف `kana` بالضبط.
- احتفظ بالعنوان الكامل متاحًا عندما يقوم العرض المدمج بتقصير الجزء الأوسط منه.
- استخدم معرّف البروتوكول القياسي المخزن بدلاً من إعادة إنشائه من اسم مستعار.

يستخدم عرض `AccountId` وتمثيله بصيغة JSON الشكل المعياري I105.

يستخدم العرض/التمثيل `AccountAddress`/JSON على المستوى الأدنى صيغة سداسية عشرية موحدة وفق البروتوكول للسياقات الداخلية وتصحيح الأخطاء.

استدعِ مُرمِّز I105 الصريح الخاص بـ `AccountAddress` عند الحاجة إلى ID حساب خارجي.

لإنشاء الحساب وسير العمل الخاص بحل الأسماء المستعارة، تابع مع [الحسابات والأسماء المستعارة](/ar/cookbook/accounts-and-aliases.md).

للحصول على نموذج بيانات الحساب، راجع [الحسابات](/ar/blockchain/accounts.md).
