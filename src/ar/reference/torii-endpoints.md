# Torii API نقاط النهاية {#torii-endpoints}

Torii هو بوابة HTTP و SSE و WebSocket لـ Iroha 3. وهو يخدم كل من التفاعل مع دفتر سلسلة الكتل APIs ونقاط نهاية المشغل API.

قواعد البروتوكول الحالية هي:

- تنسيق الباينري الموحد للبروتوكول هو Norito
- العديد من نقاط النهاية API تدعم أيضًا JSON عند إرسال `Accept: application/json`
- يتم عرض المقاييس بتنسيق بروميثيوس

للحصول على تفاصيل التنسيق، والتفاوض على المحتوى، وأعلام التخطيط، وتجميعات التشفير للمخطط، وإرشادات Norito RPC، راجع [Norito مرجع](/ar/reference/norito.md).

## نقاط النهاية الشائعة API {#common-endpoints}

| API نقطة النهاية                         |تنسيق|الغرض|
| -------------------------------- | -------------- | ---------------------------------------------------------------- |
| `POST /v1/pipeline/transactions` | Norito         |إرسال معاملة موقعة|
| `POST /v1/query`                 | Norito         |قدّم استفسارًا موقعًا|
|`GET /v1/events/ws`|WebSocket|الاشتراك في تدفقات الأحداث|
| `GET /v1/events/sse`             | SSE            |اشترك في تدفقات الأحداث عبر SSE|
| `GET /v1/blocks/stream`          | WebSocket      |بث الكتل النهائية|
| `GET /v1/peers`                  | JSON           |قائمة نظراء الشبكة التي كشف عنها Torii|
| `GET /livez`                     |نص|الحيوية الخاصة بالعملية فقط؛ لا يعني الاستعداد للبروتوكول|
| `GET /readyz`                    | JSON           |إكمال جاهزية العقدة، بما في ذلك فحوصات النقد غير المتصل الإلزامية|
| `GET /health`                    | JSON           |مسح الجاهزية بنفس الثابت بدون اتصال|
| `GET /v1/api/version`            |نص|إصدار رأس الكتلة الحالي|
| `GET /status`                    | Norito أو JSON |حالة تشخيصية عالية المستوى؛ طلب JSON صراحة|
| `GET /metrics`                   |بروميثيوس|نقطة النهاية Prometheus scrape API|
| `GET /v1/schema`                 | JSON           |عرض بيانات نقطة الوقت في مخطط نموذج البيانات يتم تقديمه بواسطة العقدة عند تمكينه|
| `GET /openapi.json`              | JSON           | OpenAPI مستند للمسارات النشطة Torii HTTP|
| `GET /v1/parameters`             | JSON           |عرض بيانات نقطة في الزمن لمعلمة العقدة|
| `GET /v1/node/capabilities`      | JSON           |قدرة العقدة وبيانات وصف نموذج البيانات|
|`GET /v1/time/now`| JSON           |عرض بيانات توقيت النظام المحلي للنود|
|`GET /v1/time/status`| JSON           |حالة تزامن الوقت|

للطلب SSE، قم بالإعلان عن البث الأصلي بالإضافة إلى بديل مكتوب:

```http
Accept: text/event-stream, application/json
```

Torii يتفاوض أولاً على تمثيل JSON أو Norito في طبقة الطلب، ثم يتحقق من استجابة `text/event-stream` الأصلية. لذلك، يتم رفض إرسال `text/event-stream` فقط مع `406`؛ يستخدم [وصفة أحداث البث](/ar/cookbook/stream-events.md) الرأس الكامل.

`/openapi.json` هو العقد المُولَّد للمسارات الممثلة في المخطط، وليس جردًا تشغيلياً كاملاً لأجهزة الفحص. المستند الحالي يحذف `/livez` و `/readyz`، ويمكن أن يتأخر وصف `/health` الخاص به عن معالج الجاهزية. توليد عملاء الطريق من الوثيقة الحية، لكن تحقق من الحيوية والاستعداد مباشرة مقابل العقدة الجارية والمعالجات المثبتة. السطح الدقيق لا يزال يعتمد على ميزات البناء و تكوين بيئة تنفيذ البرامج. استخدم [Torii API وحدة التحكم](/ar/reference/torii-api-console.md) لتحميل ذلك المستند الحي، اختبر مسارات JSON، انسخ طلبات curl، وولد كود العميل من المخطط الحالي.

كل عملية مدعومة من الكتالوج OpenAPI تشمل كائن `x-iroha-route-auth`. الأدوات المدعومة من الكتالوج MCP تكشف نفس العقدة مثل `_meta["iroha/routeAuth"]`. كلا الإسقاطين يحملان `schemaVersion` و `stableRouteId` و `authentication` و `admission`. عامل الإصدار `1` كعقد دقيق: ارفض `schemaVersion` غير المدعوم بدلاً من التخمين حول كيفية تفسير علامات المصادقة أو القبول الخاصة به. تصف بيانات تعريف المسار حد الطلب؛ فهي لا تحل محل بيانات الاعتماد المطلوبة لذلك الحد.

## جرّب المسارات الحية Taira {#try-live-taira-routes}

شبكة الاختبار العامة Taira تعرض نفس واجهة Torii JSON التي يستخدمها عملاء التطبيق للاستكشاف للقراءة فقط. هذه الأوامر لا تتطلب مفاتيح:

```bash
TAIRA_ROOT=https://taira.sora.org

curl -fsS -H 'Accept: application/json' "$TAIRA_ROOT/status" \
  | jq '{blocks, txs_approved, txs_rejected, queue_size, peers}'

curl -fsS "$TAIRA_ROOT/openapi.json" \
  | jq -r '.paths | keys[]' \
  | grep '^/v1/' \
  | head -n 20

curl -fsS -H 'Accept: application/json' \
  "$TAIRA_ROOT/v1/node/capabilities" \
  | jq '{abi_version, data_model_version, query: .query.aggregate.supported_resources}'
```

جرّب قراءة الموارد مقابل حالة العالم الحالية:

```bash
curl -fsS "$TAIRA_ROOT/v1/domains?limit=5" \
  | jq -r '.items[].id'

curl -fsS "$TAIRA_ROOT/v1/assets/definitions?limit=5" \
  | jq -r '.items[] | [.id, .name, .total_quantity] | @tsv'
```

إذا أعاد مسار الشبكة التجريبية العامة `502`، أو انتهت مهلة الاتصال، أو أبلغ عن طابور مشبع، اعتبره مشكلة في توفر نقطة النهاية API وحاول مرة أخرى لاحقًا قبل تصحيح شفرة العميل الخاصة بك.

## التطبيق وعائلات مسارات SORA {#app-and-sora-route-families}

## مصادقة الحساب، الرؤية، ومؤشرات المستعرض {#account-authentication-visibility-and-explorer-cursors}

### بروتوكول طلب حساب التطبيق {#app-account-request-protocol}

طرق الواجهة للتطبيق تقبل إما عدم وجود رؤوس مصادقة، أو دليل مفتاح واحد مباشر، أو شاهد متعدد التوقيع واحد. يجب أن يظهر كل رأس مصادقة مرة واحدة على الأكثر.

لإثبات مباشر، أرسل جميع العناوين الأربعة معًا:

- `X-Iroha-Account`: بروتوكول واحد بالضبط قياسي، أحرف صغيرة `0x` عنوان الحساب الست عشري أو اسم مستعار لحساب واحد نشط حسب بروتوكول قياسي ASCII. النص I105 غير آمن كقيمة لحقل HTTP؛ استخدم التهجئة الست عشرية الموحدة وفق البروتوكول لذلك الحساب.
- `X-Iroha-Signature`: الحمولة الخاصة بالتوقيع المشدد المشفر بقاعدة 64 مع الحشو.
- `X-Iroha-Timestamp-Ms`: طابع زمني عشري غير موقع حسب معيار Unix بوحدة الميلي ثانية، ضمن نافذة الانحراف المكوَّنة.
- `X-Iroha-Nonce`: من 1 إلى 256 بايت قابل للطباعة ASCII (`0x21` إلى `0x7e`)، فريد ضمن نافذة الإعادة.

يقوم متحكم المفتاح الواحد المسجل بتوقيع هذه البايتات بالضبط:

```text
iroha.app.request.network.v1\0 || <genesis-derived network_id[32]> ||
<UPPERCASE_METHOD>\n
<exact request path>\n
<canonical query>\n
<lowercase hex SHA-256 of the raw body>\n
<canonical timestamp_ms>\n
<nonce>
```

إنشاء استعلام قياسي بالبروتوكول الفردي يقوم بتحليل الاستعلام الخام على أنه `application/x-www-form-urlencoded` (`+` يعني فراغ)، ويقوم بفك ترميز الأزواج المئوية، وترتيبها حسب `(key, value)`، ثم يعيد ترميزها في النموذج. يقبل البروتوكول بحد أقصى 64 زوجًا مفككًا و 64 KiB من نص الاستعلام الخام. قم بتجزئة تشفيرية لبايتات الجسم تمامًا كما تم إرسالها. لا تقم بإدراج فاصل بين معرف الشبكة الثابت الذي يبلغ 32 بايت والطريقة بالأحرف الكبيرة.

يقوم المدقق V1 أيضًا بتحديد حد رمزية الطريقة عند 32 بايت، ومسار الطلب المشفر بالنسب المئوية عند 64 KiB، وهوية الحساب المباشر عند 36 KiB قبل التحليل. أسماء الحساب البديلة لها حد هيكلي أكثر صرامة يتألف من ثلاثة أجزاء من الاسم بالإضافة إلى الفواصل الخاصة بها. تجاوز هذا الحد يؤدي إلى فشل المصادقة قبل التحقق من التوقيع أو تخصيص حجمه المصدر.

يجب على وحدة التحكم متعددة التوقيع بدلاً من ذلك إرسال `X-Iroha-Witness` كـ base64 ممتلئ بدقة وفقًا لبروتوكول واحد قياسي Norito وتجاوز `X-Iroha-Signature`، `X-Iroha-Timestamp-Ms`، و`X-Iroha-Nonce`. `X-Iroha-Account` اختياري في هذا النموذج؛ وعند وجوده، يجب أن يساوي الشاهد `subject_account`. يحتوي `CanonicalRequestWitnessV1` على `schema_version`، `subject_account`، `timestamp_ms`، `nonce`، و Iroha `Hash` لبايتات طلب الشبكة الدقيقة من خلال قيمة ملخص التشفير للجسم ولكن بدون حقول الحداثة، وبحد أقصى 64 توقيعًا للأعضاء. يقوم كل عضو بتوقيع الترميز القياسي للبروتوكول الفردي Norito لنفس الحمولة دون مصفوفة التوقيعات. يجب أن يستوفي الأعضاء الذين تم التحقق منهم سياسة التعددية الحالية للحساب. الحد الأقصى للشاهد المشفر هو 1 MiB.

توفير رؤوس مصادقة غير موجودة يختار الوصول المجهول. فشل تقديم أي دليل جزئي، مختلط، مكرر، مشوه، قديم، أو معاد تشغيله في المصادقة؛ فهو لا يعود أبدًا إلى الرؤية المجهولة.

### بروتوكول طلب المشغل {#operator-request-protocol}

المسارات الموسومة بأنها معتمدة من قبل المشغل تتطلب جميع رؤوس المفرد الأربعة:

- `x-iroha-operator-public-key`: مفتاح عام متعدد التجزئة القياسي للبروتوكول الفردي Iroha.
- `x-iroha-operator-timestamp-ms`: الطابع الزمني العشري غير الموقع في وحدات الميلي ثانية وفقًا لبروتوكول اليونكس القياسي.
- `x-iroha-operator-nonce`: من 1 إلى 256 بايت قابل للطباعة ASCII، فريد لذلك المفتاح داخل نافذة الإعادة.
- `x-iroha-operator-signature`: الحمولة الخاصة بالتوقيع المشفر باستخدام base64 مع تبطين صارم.

يجب ألا تحتوي قيم العنوان على مسافات بيضاء محيطة. علامات مفتاح العامل:

```text
iroha.operator.http-request.network.v1\0 || <genesis-derived network_id[32]> ||
<UPPERCASE_METHOD>\n
<exact request path>\n
<canonical query>\n
<lowercase hex SHA-256 of the raw body>\n
<canonical timestamp_ms>\n
<nonce>
```

قواعد المسار والاستعلام والجسم والطابع الزمني وقيمة nonce هي القواعد المعيارية نفسها التي يستخدمها بروتوكول التطبيق. ويجب أيضًا قبول المفتاح في `[torii.operator_signatures]`: أدرجه في `allowed_public_keys`، أو فعّل `allow_node_key` صراحة عند استخدام مفتاح العقدة. عند امتلاء ذاكرة منع إعادة التشغيل، يفشل النظام في وضع مغلق ويعيد `503 Service Unavailable`.

التوقيع الدقيق للطلب دائمًا إلزامي. عندما يكون `[torii.operator_auth].enabled = true`، كل مسار عامل عادي يتطلب أيضًا `x-iroha-operator-session` صالح؛ عندما يكون `require_mtls = true`، فإنه يتطلب بالإضافة إلى ذلك `x-forwarded-client-cert` من مصدر موثوق. لا يحل أي عامل محل توقيع الطلب.

WebAuthn التسجيل وتسجيل الدخول استخدام هذه الأربع JSON API نقاط النهاية:

|الطريقة ونقطة النهاية API|الغرض|
| --------------------------------------------- | ---------------------------------------- |
| `POST /v1/operator/auth/registration/options` |ابدأ تسجيل بيانات الاعتماد WebAuthn|
|`POST /v1/operator/auth/registration/verify`|تحقق من بيانات الاعتماد واحتفظ بها|
| `POST /v1/operator/auth/login/options`        |ابدأ مصادقة WebAuthn|
| `POST /v1/operator/auth/login/verify`         |تحقق من التأكيد وأصدر جلسة|

قم بتكوين `torii.operator_auth.tokens` بقيم التمهيد المخصصة. قبل أن توجد أي بيانات اعتماد، أرسل واحدة كـ `x-iroha-operator-token` لبدء التسجيل الأول. لا يسمح هذا الرمز أبداً لمسار المشغل العادي، ولا يتم إعادة استخدام قيم المستمع `x-api-token` لهذا التدفق. بمجرد وجود بيانات اعتماد، يتطلب تسجيل بيانات اعتماد أخرى جلسة مصادقة. تُرجع عملية التحقق من تسجيل الدخول رمز الجلسة ليتم إرساله مع كل توقيع طلب لمشغل الشبكة الدقيق الجديد. تبقى بيانات الاعتماد موجودة تحت `<torii.data_dir>/operator_auth/operator_webauthn.json`.

ISO ٢٠٠٢٢ المسارات تطبق فحصين مستقلين. يجب على الطلب أولاً اجتياز قائمة السماح للمشغل وبروتوكول التوقيع هذا؛ ثم يتطلب المعالج ISO نفس المفتاح لتشغل الدور المشار إليه أدناه سواء كان دور مشارك أو تدقيق.

### رؤية سجل البلوكشين ومؤشرات المستكشف {#ledger-visibility-and-explorer-cursors}

تستخدم قراءة دفتر الأستاذ الخاص بسلسلة الكتل الموجهة للتطبيق حد حساب التطبيق الاختياري أعلاه. تتلقى الطلبات غير الموقعة فقط مساحات البيانات المكونة كعامة. الطلب الموقَّع الصالح يضيف مساحات البيانات المرتبطة بـ UAID الحالي للمتصل، كل مساحة بيانات مقيدة يُسمى كل منها بإذن `CanReadRestrictedDataspace { dataspace }` المحدد، أو جميع المسارات عندما يكون للحساب `CanReadAllLedgerData`.

استخدم المسار الذي يطابق مبدأ تفويض المتصل:

|الطريقة ونقطة النهاية API|المصادقة والرؤية|
| ------------------------------------- | --------------------------------------------------------------- |
| `POST /v1/transactions/visible/query` |توقيع حساب قياسي لبروتوكول واحد؛ يطبق رؤية المتصل|
| `POST /v1/transactions/query`         |توقيع طلب المشغل؛ يسمح بعرض المشغل العالمي|
| `GET /v1/triggers/completed`          |توقيع طلب المشغل؛ يقرأ سجلات الإكمال المحلية للعقدة|

يقوم نفس كائن الرؤية بتصفية الحساب، النطاق، تعريف الأصل، الأصل، NFT، RWA، الحامل، وقراءات المستكشف. الكائن الغائب والكائن الذي يقع خارج المسارات المرئية للمتصل متعمد أن يكونا غير قابلين للتمييز. يتم عرض سجل المعاملات والتعليمات النهائي فقط عندما تكون كل جزء من أجزاء التحويل المالي للمسار المسجل للمعاملة مرئيًا. المعاملة المختلطة لفضاء البيانات هي لذلك يكون مخفيًا عندما يكون جزء واحد من تحويل مالي لمشارك خارج نطاق المتصل؛ السياق التوجيهي المفقود أو القديم أو المشوه يكون مرئيًا فقط للقارئ العالمي.

تستخدم مجموعات المستكشف الست المدعومة عالميًا مؤشرات مجموعة مفاتيح base64url بمعيار بروتوكول واحد غير شفافة. الحد الافتراضي للصفحة هو 25، والحد الأقصى هو 100، وتفحص الصفحة الواحدة ما يصل إلى 512 مفتاحًا مرشحًا كحد أقصى. كل مؤشر مرتبط بمجموعته، الفلاتر، مفتاح البروتوكول الموحد الأخير، وقيمة هضم تشفير مجموعة المسارات المرئية للمتصل، لذلك لا يمكن إعادة تشغيله على استعلام آخر أو بعد تغير رؤية المتصل.

مؤشرات التاريخ للكتل والمعاملات وأحدث المعاملات والتعليمات وأحدث التعليمات تثبت أيضًا ارتفاع عرض البيانات في نقطة زمنية نهائية والهاش التشفيري للكتلة. تعرض الاستجابات `pagination.limit`، `pagination.snapshot_height`، `pagination.snapshot_hash`، `pagination.next_cursor`، و `pagination.has_more`. مؤشر لمسار آخر أو مجموعة مرشحات، قيمة ملخص تشفيرية للرؤية تم تغييرها، أو عرض بيانات لحظة زمنية لم يعد بإمكان العقدة التحقق منه يفشل مغلقًا. يظل فحص التاريخ داخل تصريح قبول الاستعلام Torii بينما يعمل العامل المانِع.

تقوم تدفقات المستكشف WebSocket بإصدار ملخصات مفلترة وإعادة حساب الرؤية مع تغير أذونات دفتر الأستاذ البلوكشين. المسار الأصلي `GET /v1/blocks/stream` مختلف: يصدر كتلًا موقعة كاملة، ويتطلب `CanReadAllLedgerData` أثناء المصافحة، ويغلق إذا تم إلغاء ذلك الإذن لاحقًا. لا تستخدم التدفق الأصلي لمستكشف بنطاق مساحة البيانات.

## ISO جسر 20022 {#iso-20022-bridge}

Torii يكشف عن جسر ISO 20022 تحت `/v1/iso20022/*` عندما يكون واجهة التطبيق API وبيئة تنفيذ برنامج الجسر مفعلتين. الجسر محدد عن قصد: إنه ليس بوابة تسوية للأغراض العامة ISO 20022، بل هو مجموعة فرعية مدعومة لتحويل رسائل الدفع المختارة إلى تحويلات موقعة Iroha ولتتبع حالة سجلها في البلوكشين.

اضبط دليلًا محليًا دائمًا في `torii.iso_bridge.store_dir` قبل قبول أي إرسال. حقل التكوين اختياري فقط للسماح للعقدة ببدء التشغيل في وضع القراءة فقط أو لأغراض التشخيص: تتطلب كل عملية إرسال ISO موثّقة هذا الدليل، وتعيد الخطأ القابل لإعادة المحاولة `503 Service Unavailable` عند غياب التخزين الدائم أو فشل كتابة سجل منع إعادة التشغيل أو السجل الغني.

### Torii ISO 20022 API نقاط النهاية {#torii-iso-20022-endpoints}

|الطريقة ونقطة النهاية API|الغرض|
| -------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `POST /v1/iso20022/pacs008`                  |قدّم تحويل ائتماني للعميل من FI إلى FI وابنِ تحويل الأصل المطابق Iroha|
| `POST /v1/iso20022/pacs009`                  |قدّم تحويل ائتماني من FI إلى FI يُستخدم للتمويل النقدي المتعلق بـ PvP أو الأوراق المالية|
|`POST /v1/iso20022/pacs002`|قدّم تقرير حالة الدفع المملوك للطرف المقابل؛ تحتاج تسوية المعاملة المالية إلى دليل على المعاملة النهائية|
| `POST /v1/iso20022/pacs004`                  |تقديم إرجاع الدفع المملوك للطرف المقابل|
| `POST /v1/iso20022/camt056`                  |قدم طلب إلغاء الدفع المملوك للمنشئ|
| `POST /v1/iso20022/sese023`                  |تقديم تعليمات تسوية معاملة مالية للأوراق المالية|
| `POST /v1/iso20022/sese024`                  |إرسال رسالة حالة تسوية معاملة مالية لأوراق مالية مملوكة للطرف المقابل|
| `POST /v1/iso20022/sese025`                  |تقديم تأكيد تسوية معاملة مالية لأوراق مالية مملوكة للطرف المقابل|
| `POST /v1/iso20022/colr012`                  |إرسال رسالة استبدال الضمان|
| `GET /v1/iso20022/messages/{msg_id}`         |اقرأ سجل الجسر الموحد للبروتوكول لرسالة واحدة|
| `GET /v1/iso20022/audit/messages`            |اقرأ البيان الفني لتدقيق الرسائل التي تظهر عبثها|
| `GET /v1/iso20022/messages/{msg_id}/pacs002` |عرض حالة الدفع الحالية كـ `pacs.002` XML|
| `GET /v1/iso20022/messages/{msg_id}/pacs004` |عرض الإرجاع الحالي للدفع كـ `pacs.004` XML|
| `GET /v1/iso20022/messages/{msg_id}/camt029` |عرض قرار الإلغاء الحالي كـ `camt.029` XML|
| `GET /v1/iso20022/messages/{msg_id}/sese024` |عرض حالة تسوية المعاملة المالية الحالية كـ `sese.024` XML|
| `GET /v1/iso20022/messages/{msg_id}/sese025` |عرض تأكيد تسوية المعاملة المالية الحالية كـ `sese.025` XML|

يجب أن تتضمن الإرساليات `pacs.008` معرف الرسالة، ومبلغ تسوية المعاملة المالية بين البنوك، والعمله، وتاريخ تسوية المعاملة المالية، والمدين والدائن IBANs، والمدين والدائن BICs. عند تكوين بيانات المرجع، يقوم الجسر أيضًا بالتحقق من جداول تحويل العملات BIC و IBAN و ISO 4217 قبل أن تدخل المعاملة المولدة في سير عمل معالجة البرنامج.

`pacs.009` يجب أن تتضمن الإرسالات معرف رسالة العمل، معرف تعريف الرسالة، وقت الإنشاء، مبلغ تسوية المعاملات المالية بين البنوك، العملة, تاريخ تسوية المعاملة المالية، والوكيل الموجه والوكيل المتلقي BICs، والمدين والدائن IBANs. إذا كانت الرسالة تتضمن `Purp`، فإن الجسر يقبل حاليًا التمويل لأغراض الأوراق المالية فقط: `Purp=SECU`.

نقاط نهاية الإرسال `pacs.008` و `pacs.009` API تقبل حاويات بيانات XML ISO أو تنسيق الحقول المسطحة المستخدم في اختبارات الجسر. يمكن للحقول الاختيارية `SplmtryData` تثبيت دفتر الأستاذ الخاص بسلسلة الكتل الهدف Iroha، ومعرفات الحسابات المصدر والهدف أو عناوينها، ومعرّف تعريف الأصل. الاستجابة هي `202 Accepted` مع `message_id`، `transaction_hash`، `status`، `pacs002_code`، وسياق دفتر الأستاذ/الحساب/الأصل المحلّل.

### تفويض المشارك وامتلاك دورة الحياة {#participant-authorization-and-lifecycle-ownership}

كل جسر ممكن لديه فهرس للمشاركين. كل مدخل للمشارك يحتوي على معرف مشارك فريد، ومفتاح عام واحد أو أكثر للمشغل، ومعرف مالي واحد أو أكثر، ومجموعة ملف تعريف مسموح به، وأدوار `originator` و`counterparty` أو كلاهما. مفاتيح المشغل والمعرفات المالية لا يمكن أن تنتمي لأكثر من مشارك واحد. قم بتكوين `audit_admin_keys` بشكل منفصل؛ لا يمكن لمفتاح مسؤول التدقيق أن يكون أيضًا مفتاح تعديل مشارك.

جميع مسارات ISO تتطلب توقيع مشغل جديد. بالنسبة لتقديم `pacs.008` أو `pacs.009` أو `sese.023` أو `colr.012` لأول مرة، يجب أن يكون المشغل المصادق عليه تابعًا للمشارك المحدد بهوية مالية في رأس التطبيق `From`. يجب أن تتطابق هوية `To` مع مشارك مكوَّن له الدور `counterparty`، ويجب أن يكون الملف الشخصي المحدد مسموحًا به لكلا الطرفين. تسجل السجلات الدائمة الإدخالي المبدع والطرف المقابل والمشارك القبولي ومفتاح المشغل، وكذلك الملف الشخصي الأصلي وسياسة التوقيع المضمنة.

يتم اشتقاق تفويض دورة الحياة من هذا السجل الثابت بدلاً من القيم التي يختارها المتصل:

|رسالة دورة الحياة|المشارك المطلوب|
| ---------------------------------------------- | -------------------------------------------------- |
| `pacs.002`، `pacs.004`، `sese.024`، `sese.025` |الطرف الأصلي بالعقد بدور `counterparty`|
| `camt.056`                                     |المُنشئ الأصلي مع دور `originator`|

تظل سياسة الملف الشخصي والتوقيع الأصلية مثبتة طوال دورة الحياة بالكامل، بحيث لا يمكن للمستدعي اختيار ملف شخصي أضعف للتحديث. رمز `pacs.002` الذي يمثل تسوية المعاملة المالية (`ACSC`، `ACCP`، `SETT`، أو `SETTLED`) تغير السجل الأصلي إلى مُسوى فقط عندما يكون Torii قد أتم دليل المعاملة.

يمكن لأي طرف أصلي قراءة سجل رسائله والمستندات الصادرة التي تم إنشاؤها. تُرجع نقطة النهاية الخاصة بالتدقيق API فقط السجلات التي يكون فيها المشارك المصادق عليه هو المصدر أو الطرف المقابل. يتلقى مسؤول التدقيق الذي تم تكوينه بشكل منفصل عرض تدقيق عالمي للقراءة فقط ولا يمكنه إرسال الرسائل أو تغييرها. لا يتم الكشف عن المشاركين غير المعروفين ومعرفات الرسائل غير ذات الصلة.

### هوية إعادة التشغيل الدائمة ومستندات الصندوق الصادر الموقعة {#durable-replay-identity-and-signed-outbox-documents}

Markers الحذف الدائم لإعادة التشغيل هي الحد الصارم للقبول. Torii يوقف التشغيل لوجود Marker حذف دائم غير قابل للقراءة أو كبير الحجم أو مشوه أو مسمى خطأ أو متعارض أو غير متوافق صراحة. كما أنه يوقف العملية أيضًا في حالة وجود سجل غني بإصدار مخطط غير متوافق صريح، أو مشارك، أو ملف تعريف، أو سياسة توقيع غائبة عن التكوين الحالي، أو علامة حذف دائمة مباشرة مفقودة أو غير متطابقة.

يتم التعامل مع الأضرار الأخرى المسجلة للغنى بشكل مختلف: الملفات غير المقروءة أو الكبيرة الحجم، JSON غير الصالح، سجلات المخطط الحالي غير الصالحة، أسماء الملفات التي لا تتبع بروتوكولًا واحدًا، والهويات المتضاربة لإعادة التشغيل يتم تسجيلها أو تخطيها. يتم إعادة إنشاء فهرس التدقيق الحالي غير القابل للقراءة أو غير الصالح من السجلات المحتفظ بها؛ فقط نسخة فهرس تدقيق غير متوافقة صراحةً تؤدي إلى إيقاف التشغيل. راقب سجلات بدء التشغيل وقم بمطابقة البيان الفني المولد للمراجعة بدلاً من افتراض أن كل ملف سجل غني تالف يمنع العقدة من الخدمة.

كل سجل غني محتفظ به يحتفظ بأصل المشاركين الذي لا يمكن تغييره. يحتفظ مؤشر الحذف المتين والمستقل بمعرّف الرسالة، وهاش التشفير للمحتوى، ومعرّف رسالة العمل، و UETR للتكرار الكامل TTL حتى بعد تقليم تفاصيل السجل الغني.

Torii يواصل إعادة تشغيل القبول قبل أن يوقع أو يعالج رسالة دورة الحياة. لا يقوم أبدًا بإزالة هوية إعادة التشغيل غير المنتهية الصلاحية. إذا كانت السعة المكونة يشغل بالكامل سجلات محمية أو هويات إعادة تشغيل غير منتهية الصلاحية، تتلقى الإرسالات `503 Service Unavailable` قابلة لإعادة المحاولة دون تغيير حالة دورة الحياة أو المحاسبة.

يتم إرجاع كل مستند مُولَّد `pacs.002`، `pacs.004`، `camt.029`، `sese.024`، أو `sese.025` كـ `application/xml` مع رؤوس الاستجابة هذه:

|رأس الصفحة|المعنى|
| ------------------------------ | ----------------------------------------------------- |
| `X-Iroha-Iso-Signature-Domain` |دائماً `iroha.iso20022.outbound.v2`|
| `X-Iroha-Iso-Signer`           |مفتاح عام واحد وفق معايير البروتوكول لمُوقّع التشفير للجسر المُكوّن|
| `X-Iroha-Iso-Signature`        |توقيع Base64 على البايتات XML المفصولة بالنطاق|

تحقق من التوقيع فوق تسلسل البايت UTF-8 `iroha.iso20022.outbound.v2`، بايت واحد صفري، وجسم الاستجابة بالضبط. لا تقم بإعادة تنسيق أو تطبيع XML قبل التحقق.

### دعم إضافي للمحلل والخرائط {#additional-parser-and-mapping-support}

يقوم مساعد IVM ISO أيضًا بالتحقق من صحة وتفعيل عائلات الرسائل التالية للتحقق من صحة حاويات البيانات، أو تعيين تسوية المعاملات المالية، أو التسوية اللاحقة. ليس لديهم مسارات Torii مستقلة.

|رسالة إلى العائلة|الدعم الحالي|
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `head.001`                         |التحقق من رأس تطبيق الأعمال لحاويات البيانات ISO، بما في ذلك `BizMsgIdr`، `MsgDefIdr`، وقت الإنشاء، وحقول BIC الاختيارية للمرسل/المستقبل|
| `pacs.007`، `pacs.028`، `pacs.029` |عكس الدفع، طلب الحالة، وحل التحقيق / تحليل الحالة|
| `pain.001`, `pain.002`             |بدء دفع العميل والتحقق من تقرير حالة الدفع|
| `camt.052`, `camt.053`, `camt.054` |التحقق من تقرير الحساب والبيان والإشعارات|

## Kaigi الجلسات {#kaigi-sessions}

Kaigi يوفر غرف صوتية/مرئية مدفوعة وفورية على SORA Nexus. استخدمه عندما يحتاج التطبيق إلى إنشاء جلسات مدعومة بسجل البلوكشين، تغييرات القوائم، نقل البيانات التقنية، الإشارة المشفرة، وقياس الاستخدام بدلاً من الاحتفاظ بكل حالة المؤتمرات خارج السلسلة.

التفاعل مع دورة حياة دفتر السجلات للبلوكشين هو:

- `CreateKaigi`: إنشاء مكالمة تحت نطاق وتخزين سياستها، وجدولها، وبياناتها الوصفية، وملف التعريف الفني الاختياري للترحيل.
- `JoinKaigi`: تحديث قائمة المكالمات. في وضع `zk-roster-v1`، يعرض عرض المكالمات العامة قيمة الالتزام التشفيري وعدد المعرفات الباطلة بدلاً من معرفات حسابات المشاركين.
- `LeaveKaigi`: إزالة مشارك من مكالمة شفافة. المغادرة في الوضع الخاص تتم خارج السلسلة في بروتوكول الإصدار الأول.
- `RecordKaigiUsage`: أضف إجماليات مدة القياس وتكلفة تنفيذ المعاملة.
- `EndKaigi`: أغلق الجلسة وسجل الطابع الزمني النهائي.

Torii يكشف عن قراءات مواجهة للتطبيق التالية:

|مسار|المصادقة|الغرض|
| ----------------------------------- | --------------------------------------- | ------------------------------------------ |
| `/v1/kaigi/calls/{call_id}`         |عام|سجل المكالمات الحالي|
| `/v1/kaigi/calls/{call_id}/signals` |طلب حساب شبكة دقيق بمعيار بروتوكول واحد|البيانات الوصفية للإشارة النهائية المفصّلة|
|`/v1/kaigi/calls/{call_id}/events`|طلب حساب لشبكة محددة وفق معيار بروتوكول واحد|تدفق دورة حياة المكالمة|
| `/v1/kaigi/relays`                  |طلب المشغل المدرج في القائمة المسموح بها|ملخص التتابع|
| `/v1/kaigi/relays/{relay_id}`       |طلب المشغل المدرج في القائمة المسموح بها|تفاصيل تسجيل وصحة المرحل الواحد|
| `/v1/kaigi/relays/health`           |طلب المشغل المدرج في القائمة المسموح بها|صحة المرحل الإجمالية|
| `/v1/kaigi/relays/events`           |طلب حساب لشبكة محددة وفق معيار بروتوكول واحد|تسجيل الترحيل وتدفق أحداث الصحة|

يجب تمكين التطبيق API. ملخص الترحيل ومسارات الصحة هي واجهات تشغيلية على الرغم من أنها للقراءة فقط؛ طلب غير موقع `curl` هو ليست فحص توافر صالح. يتم أيضًا عكس حالة الجلسة من خلال أحداث النطاق Kaigi مثل `KaigiRosterSummary`، `KaigiRelayManifestUpdated`، `KaigiRelayHealthUpdated`، و`KaigiUsageSummary`.

### CLI اختبار الدخان {#cli-smoke-test}

ابدأ بـ `iroha app kaigi` CLI عندما تريد التحقق من أن نقطة النهاية Torii API تقبل معاملات Kaigi قبل توصيل UI. ينشئ أمر البدء السريع غرفة مقابل نقطة النهاية API المُكوَّنة ويطبع معرف المكالمة وبيانات الانضمام الخاصة بها:

```bash
iroha app kaigi quickstart \
  --domain kaigi.universal \
  --summary-out kaigi-summary.json
```

للتدفقات المبرمجة، قم بإدارة دورة حياة الغرفة بشكل صريح:

```bash
iroha app kaigi create \
  --domain kaigi.universal \
  --call-name daily \
  --host <i105-account-id> \
  --privacy-mode transparent \
  --room-policy authenticated

iroha app kaigi join \
  --domain kaigi.universal \
  --call-name daily \
  --participant <i105-account-id>

iroha app kaigi leave \
  --domain kaigi.universal \
  --call-name daily \
  --participant <i105-account-id>

iroha app kaigi record-usage \
  --domain kaigi.universal \
  --call-name daily \
  --duration-ms 120000 \
  --billed-gas 1500

iroha app kaigi end --domain kaigi.universal --call-name daily
```

استخدم `--room-policy public` للغرف التي قد تكشفها المكررات بدون تذاكر المشاهد، أو `--room-policy authenticated` عندما يجب أن تتطلب المخارج مصادقة المشاهد. استخدم `--privacy-mode zk-roster-v1` فقط بعد الشبكة تحتوي على قائمة المفاتيح المخصصة للتحقق من الاستخدام Kaigi؛ وإلا فإن عمليات الانضمام والمغادرة والسجلات الخاصة بالاستخدام ستفشل أثناء التحقق الحتمي.

### JavaScript دمج {#javascript-integration}

ينفذ [عرض Iroha التوضيحي بلغة JavaScript](https://github.com/soramitsu/iroha-demo-javascript) الحالي ملف تعريف اجتماع شفافًا وموثّقًا بين طرفين. وهو لا يتيح تدفق إثبات `zk-roster-v1` الخاص بالبروتوكول. ينشئ العارض عروض WebRTC وإجاباتها، بينما يستخدم جسر ذو صلاحيات نسخة العمل المحلية من [`@iroha/iroha-js`](https://github.com/hyperledger-iroha/iroha/tree/0010c5a70039eac101a4846499ba9ceaf43eb65c/javascript/iroha_js) لتحديد الرسوم والتوقيع والإرسال وانتظار بلوغ معاملات Kaigi حالة النهائية.

انظر [تضمين Kaigi في تطبيق JavaScript](/ar/guide/tutorials/kaigi.md) للمصادقة الدقيقة للمسار، ونمط الدعوة، وحدود الجسر، وأوامر اختبار العرض التوضيحي الحالية.

## الحالة والمؤشرات {#status-and-metrics}

نقاط النهاية للحالة والقياسات API هي أول الأشياء التي يتم توصيلها إلى لوحات المعلومات:

- `/status` يكشف عن الحقول العليا للنظير الشبكي، والكتلة، والطابور، والتوافق
- `/metrics` يكشف عدادات Prometheus، ومقاييسه، ورسومه البيانية

على العقد المُمكَّنة بـ Nexus، يتضمن مخرَج الحالة أيضًا أقسام مسار التنفيذ وأقسام الوعي بمساحة البيانات. عند `nexus.enabled = false`، يتم حذف تلك الأقسام.

## JSON مقابل Norito {#json-vs-norito}

عدة نقاط النهاية للمشغل API تُرجع Norito بشكل افتراضي. عندما تدعم نقطة النهاية API JSON، أرسل:

```http
Accept: application/json
```

هذا مفيد بشكل خاص لـ:

- `/v1/sumeragi/status`
- `/v1/sumeragi/qc`

عندما يقبل أو يعيد نقطة النهاية API بيانات Norito مكتوبة مباشرة، استخدم `application/x-norito` كنوع المحتوى أو القيمة المفضلة لـ `Accept`. انظر [Norito](/ar/reference/norito.md#torii-and-norito-rpc) لتفاصيل النقل.

## ملفات التعقب عن بعد {#telemetry-profiles}

API تعتمد وضوحية نقطة النهاية على إعداد `telemetry.profile` للعقدة. يعرّض التكوين الحالي خمسة مستويات للملف الشخصي:

|الملف الشخصي| `/status` | `/metrics` |مسارات المطور|
| ----------- | --------- | ---------- | ---------------- |
|`disabled`|لا|لا|لا|
|`operator`|نعم|لا|لا|
|`extended`|نعم|نعم|لا|
| `developer` |نعم|لا|نعم|
| `full`      |نعم|نعم|نعم|

## CLI الاختصارات {#cli-shortcuts}

يقوم `iroha` CLI بالفعل بتغليف العديد من هذه النقاط النهائية API:

```bash
export IROHA_OPERATOR_KEY_FILE=/run/secrets/iroha/operator.key

iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  --output-format text ops sumeragi status
iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  --output-format text ops sumeragi diagnostics
iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  ops sumeragi params
iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  --output-format text ops sumeragi evidence count
```
