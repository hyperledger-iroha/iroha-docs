# I105 Account Address Format

I105 is the canonical external text format for an Iroha 3 `AccountId`.

Its payload represents the account controller.

Its sentinel identifies the intended network with a chain discriminant.

Use it anywhere an API, transaction, permission, or query asks for a
canonical account ID.

An I105 account ID is domainless.

A value such as `treasury@payments.universal` is an account alias, not
another spelling of the I105 ID.

Deriving an I105 ID does not register or fund the account.

::: warning The rules that prevent most integration failures

- Select the network profile before encoding or validating an address.
- Store and compare the canonical UTF-8 string exactly.
- Preserve letter case and do not apply `Unicode` normalization.
- An I105 ID must not have an `@domain` or `@domain.dataspace` suffix.
- Use an Iroha SDK or `iroha tools address`.
- A regular expression is not an I105 validator.

:::

## Literal anatomy

An I105 literal has three adjacent parts and no separator:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

| Part             | Purpose                                                            | Checksum coverage |
| ---------------- | ------------------------------------------------------------------ | ----------------- |
| Network sentinel | Maps the text to one `u16` chain discriminant                      | Not covered       |
| Payload          | `base-105` encoding of the canonical account-controller bytes      | Covered           |
| Checksum         | Six `Bech32m`-style `5-bit` values rendered with the I105 alphabet | N/A               |

The payload and checksum identify the account controller.

The sentinel selects the network context.

The same controller has the same payload and checksum on Taira and
Minamoto, but each network uses a different leading sentinel.

A decoder must enforce the expected discriminant.

The checksum cannot detect a sentinel substitution.

### Network sentinels

| Network or context      |               Chain discriminant |      Hex | Canonical sentinel                          |
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
| Taira public testnet    |                            `369` | `0x0171` | `test`                                      |
| Minamoto public network |                            `753` | `0x02f1` | `sora`                                      |
| Development context     |                              `0` | `0x0000` | `dev`                                       |
| Any other `u16` value   | All except `0`, `369`, and `753` |        — | `n` plus minimal decimal, for example `n42` |

The named values always use their named sentinel.

Forms such as `n00042`, `n369`, `n753`, and `n0` are not canonical.

The transaction-chain ID and the I105 chain discriminant are separate
values.

Choosing an endpoint or chain ID does not implicitly choose the address
profile.

## Normative single-key example

The payload and Minamoto form below come from the cross-SDK compliance
fixture.

The Taira form applies Taira's sentinel to the same payload:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

The canonical payload starts with `02 00 01 20`: header `0x02`, compact
single-key tag `0x00`, `Ed25519` curve ID `0x01`, and a 32-byte key length
`0x20`.

The `multihash` prefix is input metadata and is not copied into the
controller payload.

## Create and inspect IDs with the CLI

Prefer a named profile for a public network:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

Normalize and compare an I105 input while diagnosing address-codec
behavior:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

Inspect the detected format, canonical hex, and selected network context as
JSON:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

Audit the address-codec structure of a newline-separated file without
silently accepting parse failures:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution CLI validation boundary

The `convert`, `normalize`, and `audit` commands operate on the lower-level
`AccountAddress` codec.

They verify the sentinel, alphabet, checksum, byte lengths, `CurveId`/key
shape, and exact address-layer re-encoding.

They do not materialize an `AccountId`.

They do not by themselves validate all multisig policy semantics.

They do not prove that the header class matches the controller.

Use strict `AccountId` validation before authorization or persistence.

:::

For a private network, use its configured discriminant explicitly with
`--network-prefix`.

When converting an existing address between explicit contexts, also supply
the source with `--expect-prefix`:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

Re-encoding changes only the network context.

It does not register the account on the target network or prove that the
same controller should be reused there.

## Encoding algorithm

Canonical encoders perform these operations:

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

Leading zero bytes are preserved as zero-valued `base-105` digits.

The checksum uses the `Bech32` `polymod` generators and constant
`0x2bc830a3`.

The checksum-only HRP is the ASCII string `snx`.

The checksum-only HRP is not printed in the address.

The six checksum values are in the range `0..31` and are rendered through
the same I105 alphabet as the payload.

### I105 alphabet

The 105 symbols are indexed in this exact order.

The first row is the `Bitcoin Base58` alphabet and contains digits `0..57`.

The second row contains digits `58..104`.

Concatenate the rows when implementing the codec.

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

The alphabet is `Unicode`-sensitive.

The exact sequence uses `compatibility-width` Japanese `kana` symbols plus
the code points shown for `ヰ` and `ヱ`.

Do not apply NFC, NFKC, width conversion, case folding, or look-alike
substitution.

ASCII `0`, `O`, `I`, and `l` are not alphabet symbols.

## Canonical account payload

The `base-105` body encodes a binary account payload, not a public-key
string and not a Norito JSON object:

```text
header:u8 || controller:variable
```

All multi-byte integers below are unsigned and `big-endian`.

Domain, dataspace, alias, UAID, and account metadata bytes are not present.

### Header byte

| Bits   | Width |       Current encoder output | Meaning                      |
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` | Address format version field |
| `4..3` |     2 | `0` single key, `1` multisig | Address class                |
| `2..1` |     2 |                          `1` | Normalization version field  |
| `0`    |     1 |                          `0` | Reserved `extension flag`    |

Current V1 encoders emit header `0x02` for a single-key controller and
`0x0a` for a multisig controller.

Address classes `2` and `3` are unassigned.

An `extension flag` of `1` is rejected.

The low-level decoder can preserve other version and normalization bit
values and does not independently cross-check the class against the
controller tag.

Converting to an `AccountId` and comparing its canonical rendering proves
current V1 canonicality.

### Single-key controller

Use the compact form when the raw public-key payload is at most 255 bytes:

| Field        |           Width | Value or meaning         |
| ------------ | --------------: | ------------------------ |
| `tag`        |          1 byte | `0x00`                   |
| `curve`      |          1 byte | `CurveId` registry value |
| `key_len`    |          1 byte | Raw key length           |
| `public_key` | `key_len` bytes | Raw public-key payload   |

Keys longer than 255 bytes use the extended form:

| Field        |           Width | Value or meaning             |
| ------------ | --------------: | ---------------------------- |
| `tag`        |          1 byte | `0x02`                       |
| `curve`      |          1 byte | `CurveId` registry value     |
| `key_len`    |         2 bytes | Raw key length, `big-endian` |
| `public_key` | `key_len` bytes | Raw public-key payload       |

An extended encoding is not canonical for a key that fits the compact form.

### Multisig controller

| Field            |    Width | Value or meaning               |
| ---------------- | -------: | ------------------------------ |
| `tag`            |   1 byte | `0x01`                         |
| `policy_version` |   1 byte | Current value `1`              |
| `threshold`      |  2 bytes | Required total approval weight |
| `member_count`   |  2 bytes | Number of following members    |
| `members`        | Variable | Repeated member records        |

Each member record is:

| Field        |           Width | Meaning                  |
| ------------ | --------------: | ------------------------ |
| `curve`      |          1 byte | `CurveId` registry value |
| `weight`     |         2 bytes | Member approval weight   |
| `key_len`    |         2 bytes | Raw key length           |
| `public_key` | `key_len` bytes | Raw public-key payload   |

A valid policy has at least one member, positive weights, no duplicate
public keys, and a threshold from `1` through the sum of member weights.

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

Canonical construction sorts members by the signing algorithm's stable
name, a zero separator byte, and then the raw public-key bytes.

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

An I105 literal has no fixed character length because multisig and
post-quantum controllers can be large.

### `CurveId` registry

The final column names the required optional `Cargo` feature.

A dash means that the registry entry is available without an optional
data-model feature.

|   ID | Signing algorithm                            | Required `Cargo` feature |
| ---: | -------------------------------------------- | ------------------------ |
|  `1` | `Ed25519`                                    | —                        |
|  `2` | `ML-DSA`                                     | —                        |
|  `3` | `BLS12-381 normal`                           | `bls`                    |
|  `4` | `secp256k1`                                  | —                        |
|  `5` | `BLS12-381 small`                            | `bls`                    |
| `10` | `GOST R 34.10-2012 256-bit, parameter set A` | `gost`                   |
| `11` | `GOST R 34.10-2012 256-bit, parameter set B` | `gost`                   |
| `12` | `GOST R 34.10-2012 256-bit, parameter set C` | `gost`                   |
| `13` | `GOST R 34.10-2012 512-bit, parameter set A` | `gost`                   |
| `14` | `GOST R 34.10-2012 512-bit, parameter set B` | `gost`                   |
| `15` | `SM2`                                        | `sm`                     |

Unassigned IDs and algorithms disabled in the receiving build are rejected.

The key payload must also be structurally valid for the algorithm selected
by the declared `CurveId`.

## Strict AccountId validation and canonicality

After configuring the SDK with the expected chain discriminant, parse into
an `AccountId` and compare the returned canonical rendering with the
trimmed input.

The comparison is significant because the parser can normalize decodable
controller material while constructing the `AccountId`.

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

For an untrusted string, a conforming application should:

1. Trim only permitted transport whitespace around the complete value.
2. Read the sentinel and require the expected chain discriminant.
3. Map every remaining `Unicode` symbol through the exact 105-symbol
   alphabet.
4. Split off the six checksum digits.
5. Convert the payload digits back to canonical bytes.
6. Verify the checksum over those canonical bytes.
7. Parse the header and controller, requiring:
   - exact field lengths
   - a supported `CurveId`
   - a valid public key
   - no trailing bytes
   - a valid multisig policy when applicable
8. Construct an `AccountId`.
9. Render the `AccountId` canonically for the expected discriminant.
10. Require `byte-for-byte` equality with the trimmed input.

The application's explicit final `render-and-compare` step rejects
non-minimal numeric sentinels, non-canonical controller layouts, reordered
policy material, and any other spelling that decodes but is not the
encoder's current V1 output.

A successful checksum or low-level `AccountAddress` parse is not a
substitute for this check.

Do not accept these values in a strict account-ID field:

- an account alias such as `alice@wonderland.universal`
- an I105 literal with an appended `@domain` suffix
- a public-key `multihash` such as `ed0120...`
- canonical payload hex such as `0x02000120...`
- an address for the wrong chain discriminant
- a string with changed uppercase or lowercase letters, character widths,
  `kana`, payload, or checksum

Resolve aliases at the application boundary and retain the returned
canonical I105 ID for authorization, signing, permissions, and audit
records.

### Common stable error codes

| Code                             | Meaning                                                             |
| -------------------------------- | ------------------------------------------------------------------- |
| `ERR_UNEXPECTED_NETWORK_PREFIX`  | The decoded discriminant does not match the required network        |
| `ERR_CHECKSUM_MISMATCH`          | The six checksum symbols do not match the payload                   |
| `ERR_INVALID_I105_CHAR`          | A symbol is outside the exact alphabet                              |
| `ERR_MISSING_I105_SENTINEL`      | No canonical named or numeric sentinel was found                    |
| `ERR_I105_TOO_SHORT`             | The body cannot contain both payload and checksum                   |
| `ERR_INVALID_LENGTH`             | A controller field is truncated or uses a non-canonical length form |
| `ERR_UNKNOWN_CURVE`              | The controller declares an unassigned or unavailable `CurveId`      |
| `ERR_INVALID_PUBLIC_KEY`         | The key is invalid for the algorithm selected by its `CurveId`      |
| `ERR_UNSUPPORTED_ADDRESS_FORMAT` | The input is not an accepted canonical I105 form                    |

## API, storage, and display rules

- Send the exact I105 UTF-8 string in JSON account fields.
- `Percent-encode` the complete account ID before placing it in a URL path
  segment.
- Never substitute an account alias for an I105 ID.
- Store the canonical string returned by the codec with `byte-preserving`
  comparison semantics.
- Use a collation that preserves letter case and character width.
- Keep the chain discriminant or named network profile with exported
  account data and backups.
- Reuse an address only with its network context.
- Display the complete address and provide a copy action.
- Preserve every `kana` character exactly.
- Keep the full address available when a compact display shortens its
  middle.
- Use the stored canonical ID instead of reconstructing it from an alias.

`AccountId` display and JSON use canonical I105.

The lower-level `AccountAddress` display/JSON representation uses canonical
hex for internal and debugging contexts.

Call the explicit `AccountAddress` I105 encoder when an external account ID
is required.

For account creation and alias resolution workflows, continue with
[Accounts and aliases](/cookbook/accounts-and-aliases.md).

For the account data model, see [Accounts](/blockchain/accounts.md).
