# I105 Formatos de direcciones de cuenta {#i105-account-address-format}

I105 es el formato de texto externo canónico para un Iroha 3 `AccountId`.

Su carga útil representa al controlador de la cuenta.

Su sentinela identifica la red prevista con un discriminante de cadena.

Utilice en cualquier lugar donde una API, transacción, permiso o consulta solicite una cuenta canónica ID.

Una cuenta de I105 ID no tiene dominio.

Un valor como `treasury@payments.universal` es un alias de la cuenta y no otra ortografía del I105 ID.

La derivación de un I105 ID no registra ni financia la cuenta.

::: warning Las reglas que evitan la mayoría de los fracasos de integración

- Seleccione el perfil de red antes de codificar o validar una dirección.
- Almacenar y comparar la cadena canónica UTF-8 exactamente.
- Conserve exactamente las mayúsculas y minúsculas, y no aplique la normalización de `Unicode`.
- Un I105 ID no debe tener un sufijo `@domain` o `@domain.dataspace`.
- Utilizar un Iroha SDK o `iroha tools address`.
- La expresión regular no es un validador I105.

:::

## La anatomía literal {#literal-anatomy}

Una letra I105 tiene tres partes adyacentes y no separación:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

|Parte |El propósito .|Cobertura del importe de los cheques |
| ---------------- | ------------------------------------------------------------------ | ----------------- |
|Sentinela de la red |Mapa del texto a un discriminante de la cadena `u16` |No está cubierto |
|Carga útil |`base-105` codificación de los bytes canónicos del controlador de cuentas |Cubierta |
|Sumario de los cheques|Seis valores del estilo `Bech32m` de `5-bit` representados con el alfabeto I105 |N/A |

La carga útil y la suma de cheques identifican al responsable del control de la cuenta.

El centinela selecciona el contexto de la red.

El mismo controlador tiene la misma carga útil y suma de control en Taira y Minamoto, pero cada red utiliza un centinela líder diferente.

Un decodificador debe hacer cumplir el discriminante esperado.

La suma de comprobación no puede detectar una sustitución de sentinela.

### Centinelas de red {#network-sentinels}

|Red o contexto |Discriminante de la cadena |Hex |Sentinela canónica .|
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
|Taira red de pruebas pública |                            `369` |`0x0171` |`test` |
|Minamoto red pública |                            `753` |`0x02f1` |`sora` |
|Contexto de desarrollo |                              `0` |`0x0000` |`dev` |
|Cualquier otro valor `u16` |Todos excepto `0`, `369`, y `753` |        — |`n` más un decimal mínimo, por ejemplo `n42` |

Los valores nombrados siempre utilizan su sentinela nombrada.

Los formularios tales como `n00042`, `n369`, `n753` y `n0` no son canónicos.

La cadena de transacciones ID y el elemento discriminante de la cadena I105 son valores separados.

La elección de un punto final o cadena ID no implica implícitamente la elección del perfil de dirección.

## Ejemplo normativo de llave única {#normative-single-key-example}

La carga útil y el formulario Minamoto a continuación provienen del dispositivo de cumplimiento transversal SDK.

El formulario Taira se aplica a la misma carga útil con el sentinela de Taira:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

La carga útil canónica comienza con: `02 00 01 20`: encabezado `0x02`, etiqueta compacta de llave única `0x00`, `Ed25519` de la curva ID `0x01`, y una longitud de tecla de 32 bytes `0x20`.

El prefijo `multihash` es un metadatos de entrada y no se copia en la carga útil del controlador.

## Crear e inspeccionar IDs con el CLI {#create-and-inspect-ids-with-the-cli}

Prefiere un perfil de nombre para una red pública:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

Normaliza y compara una entrada de I105 al diagnosticar el comportamiento del codec de dirección:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

Inspectar el formato detectado, el hexagonal canónico y el contexto de red seleccionado como JSON:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

Auditar la estructura del codec de direcciones de un archivo separado por líneas nuevas sin aceptar silenciosamente fallos en el análisis:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution límite de validación CLI

Los comandos `convert`, `normalize` y `audit` funcionan en el codec de nivel inferior `AccountAddress`.

Verifican la sentinela, el alfabeto, la suma de comprobación, las longitudes de byte, la forma `CurveId`/clave y la recodificación exacta de la capa de direcciones.

No se materializan en `AccountId`.

No validan por sí mismas todas las semánticas de la política multisig.

No demuestran que la clase de encabezado coincida con el controlador.

Utilice una validación estricta de `AccountId` antes de la autorización o persistencia.

:::

Para una red privada, utilice su discriminante configurado explícitamente con `--network-prefix`.

Cuando se convierta una dirección existente entre contextos explícitos, proporcione también a la fuente `--expect-prefix`:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

La recodificación cambia sólo el contexto de la red.

No registra la cuenta en la red de destino ni prueba que el mismo controlador debe ser reutilizado allí.

## Algoritmo de codificación {#encoding-algorithm}

Los codificadores canónicos realizan estas operaciones:

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

Los bytes de cero principales se conservan como dígitos de valor cero `base-105`.

La suma de comprobación utiliza los generadores `Bech32` `polymod` y la constante `0x2bc830a3`.

El HRP usado exclusivamente para la suma de comprobación es la cadena ASCII `snx`.

El HRP usado exclusivamente para la suma de comprobación no se incluye en la dirección.

Los seis valores de suma de comprobación se encuentran en el rango `0..31` y son representados por el mismo alfabeto I105 que la carga útil.

### Alfabeto I105 {#i105-alphabet}

Los 105 símbolos están indexados en este orden exacto.

La primera fila es el alfabeto `Bitcoin Base58` y contiene los dígitos `0..57`.

La segunda fila contiene los números `58..104`.

Concatenar las filas al implementar el codec.

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

El alfabeto es `Unicode` sensible.

La secuencia exacta utiliza los símbolos japoneses `kana` `compatibility-width` más los puntos de código indicados para `ヰ` y `ヱ`.

No aplique NFC ni NFKC, ni convierta el ancho de los caracteres, ni cambie las mayúsculas y minúsculas, ni sustituya caracteres por otros visualmente similares.

ASCII `0`, `O`, `I` y `l` no son símbolos del alfabeto.

## Carga útil de la cuenta canónica {#canonical-account-payload}

El cuerpo `base-105` codifica una carga útil de la cuenta binaria, no una cadena de llave pública y no un objeto Norito JSON:

```text
header:u8 || controller:variable
```

Todos los números enteros de varios bytes a continuación no están firmados y `big-endian`.

El dominio, el espacio de datos, el alias, el UAID y los bytes de metadatos de la cuenta no están presentes.

### Byte de encabezado {#header-byte}

|Un poco .|Ancho |Producción actual del codificador |El significado .|
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |Campo de la versión en formato de dirección |
| `4..3` |     2 |`0` llave única, `1` multisig |La clase de direcciones |
| `2..1` |     2 |                          `1` |Campo de versión de normalización |
| `0`    |     1 |                          `0` |Reservado `extension flag` |

Los codificadores de corriente V1 emiten encabezado `0x02` para un controlador de llave única y `0x0a` para un controller de signos múltiples.

Las clases de direcciones `2` y `3` no están asignadas.

Se rechazará una `extension flag` de `1`.

El decodificador de bajo nivel puede preservar otros valores de bits de versión y normalización y no verifica independientemente la clase contra la etiqueta del controlador.

La conversión a un `AccountId` y la comparación de su interpretación canónica demuestra la canonicalidad actual V1.

### Controlador de llave única {#single-key-controller}

Utilice el formulario compacto cuando la carga útil de clave pública en bruto sea como máximo 255 bytes:

|El campo |Ancho |Valor o significado |
| ------------ | --------------: | ------------------------ |
|`tag` |1 byte |`0x00` |
|`curve` |1 byte |`CurveId` valor del registro |
|`key_len` |1 byte |Longitud de la clave en bruto |
|`public_key` |`key_len` bytes |Carga útil de llave pública|

Las teclas de más de 255 bytes utilizan la forma extendida:

|El campo |Ancho |Valor o significado |
| ------------ | --------------: | ---------------------------- |
|`tag` |1 byte |`0x02` |
|`curve` |1 byte |`CurveId` valor del registro |
|`key_len` |2 bytes |Longitud de la clave en bruto, `big-endian` |
|`public_key` |`key_len` bytes |Carga útil de llave pública|

Una codificación extendida no es canónica para una clave que se ajusta a la forma compacta.

### Controlador multisig {#multisig-controller}

|El campo |Ancho |Valor o significado |
| ---------------- | -------: | ------------------------------ |
|`tag` |1 byte |`0x01` |
|`policy_version` |1 byte |Valor actual `1` |
|`threshold` |2 bytes |Peso total de aprobación requerido |
|`member_count` |2 bytes |Número de miembros siguientes |
|`members` |Variable |Registros de miembros repetidos |

Cada registro de miembro es:

|El campo |Ancho |El significado .|
| ------------ | --------------: | ------------------------ |
|`curve` |1 byte |`CurveId` valor del registro |
|`weight` |2 bytes |Peso de aprobación del miembro |
|`key_len` |2 bytes |Longitud de la clave en bruto |
|`public_key` |`key_len` bytes |Carga útil de llave pública|

Una póliza válida tiene al menos un miembro, pesos positivos, no duplicación de claves públicas y un umbral de `1` a través de la suma de pesos de los miembros.

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

La construcción canónica clasifica a los miembros por el nombre estable del algoritmo de firma, un byte separador cero y luego los bytes de clave pública en bruto.

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

Un I105 literal no tiene una longitud fija de caracteres porque los controladores multisig y post-quantum pueden ser grandes.

### Registro `CurveId` {#curveid-registry}

En la columna final se nombra la función `Cargo` opcional requerida.

Un dash significa que la entrada en el registro está disponible sin una función opcional de modelo de datos.

|ID |Algoritmo de firma |Función `Cargo` requerida |
| ---: | -------------------------------------------- | ------------------------ |
|  `1` |`Ed25519` | —                        |
|  `2` |`ML-DSA` | —                        |
|  `3` |`BLS12-381 normal` |`bls` |
|  `4` |`secp256k1` | —                        |
|  `5` |`BLS12-381 small` |`bls` |
| `10` |`GOST R 34.10-2012 256-bit, parameter set A` |`gost` |
| `11` |`GOST R 34.10-2012 256-bit, parameter set B` |`gost` |
| `12` |`GOST R 34.10-2012 256-bit, parameter set C` |`gost` |
| `13` |`GOST R 34.10-2012 512-bit, parameter set A` |`gost` |
| `14` |`GOST R 34.10-2012 512-bit, parameter set B` |`gost` |
| `15` |`SM2` |`sm` |

Se rechazan los IDs no asignados y los algoritmos desactivados en la configuración de recepción.

La carga útil de la clave también debe ser estructuralmente válida para el algoritmo seleccionado por el `CurveId` declarado.

## Validación y canonicidad estrictas AccountId {#strict-accountid-validation-and-canonicality}

Después de configurar el SDK con el discriminante de cadena esperado, analizar en un `AccountId` y comparar la representación canónica devuelta con la entrada recortada.

La comparación es significativa porque el parser puede normalizar el material del controlador descodificable mientras se construye la `AccountId`.

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

En el caso de una cadena no fiable, la aplicación conforme debe:

1. Trim sólo permitió el transporte de espacio blanco alrededor del valor completo.
2. Lea la sentinela y requiere el discriminante de cadena esperado.
3. Mapa todos los símbolos restantes `Unicode` a través del alfabeto exacto de 105 símbolos.
4. Separe los seis dígitos correspondientes a la suma de comprobación.
5. Convierta los dígitos de carga útil a bytes canónicos.
6. Verifique la suma de comprobación calculada sobre esos bytes canónicos.
7. Parsear el encabezado y el controlador, que requiere:
   - longitudes exactas de los campos
   - un `CurveId` respaldado
   - una clave pública válida
   - No hay bytes de seguimiento
   - una política de multisig válida cuando sea aplicable
8. Construir un `AccountId`.
9. Genere la representación canónica del `AccountId` para el discriminante esperado.
10. Requerir la igualdad `byte-for-byte` con la entrada recortada.

El paso final explícito de la aplicación `render-and-compare` rechaza las sentinelas numéricas no mínimas, los diseños del controlador no canónicos, el material de política reordenado y cualquier otra ortografía que decodifique pero que no sea la salida actual V1 del codificador.

Una suma de comprobación exitosa o un análisis de bajo nivel `AccountAddress` no sustituye a este control.

No acepte estos valores en un campo estricto de cuenta- ID:

- un alias de cuenta como `alice@wonderland.universal`
- una letra I105 con un sufijo adjunto de `@domain`
- una llave pública `multihash`, como la `ed0120...`
- Hex de carga útil canónica, como `0x02000120...`
- una dirección para el discriminante de la cadena equivocada
- una cadena en la que se hayan cambiado las letras mayúsculas o minúsculas, el ancho de los caracteres, los caracteres `kana`, la carga útil o la suma de comprobación

Resolver los alias en el límite de la aplicación y conservar el canónico devuelto I105 ID para la autorización, firma, permisos y registros de auditoría.

### Códigos de error estable comunes {#common-stable-error-codes}

|Código |El significado .|
| -------------------------------- | ------------------------------------------------------------------- |
|`ERR_UNEXPECTED_NETWORK_PREFIX` |El discriminante descifrado no coincide con la red requerida |
|`ERR_CHECKSUM_MISMATCH` |Los seis símbolos checksum no coinciden con la carga útil |
|`ERR_INVALID_I105_CHAR` |Un símbolo está fuera del alfabeto exacto .|
|`ERR_MISSING_I105_SENTINEL` |No se encontró ningún nombre canónico o centinela numérica .|
|`ERR_I105_TOO_SHORT` |El cuerpo no puede contener tanto la carga útil como el monto de los controles .|
|`ERR_INVALID_LENGTH` |Un campo del controlador es truncado o utiliza una forma de longitud no canónica |
|`ERR_UNKNOWN_CURVE` |El responsable del tratamiento declara una `CurveId` no asignada o no disponible. |
|`ERR_INVALID_PUBLIC_KEY` |La clave no es válida para el algoritmo seleccionado por su `CurveId` |
|`ERR_UNSUPPORTED_ADDRESS_FORMAT` |La entrada no es un formulario canónico aceptado I105 |

## API, reglas de almacenamiento y visualización {#api-storage-and-display-rules}

- Envíe la cadena exacta I105 UTF-8 en los campos de cuenta JSON.
- `Percent-encode` la cuenta completa ID antes de colocarla en un segmento de trayectoria URL.
- Nunca use un alias de cuenta en lugar de un I105 ID.
- Almacenar la cadena canónica devuelta por el codec con `byte-preserving` semántica de comparación.
- Use una intercalación que preserve las mayúsculas y minúsculas y el ancho de los caracteres.
- Mantenga el perfil de red denominado o discriminante en la cadena con datos y copias de seguridad de cuentas exportadas.
- Reutilizar una dirección sólo con su contexto de red.
- Muestre la dirección completa y proporcione una acción de copia.
- Preserva exactamente todos los caracteres `kana`.
- Mantenga la dirección completa disponible cuando una pantalla compacta acorte su centro.
- Utilice la canónica almacenada ID en lugar de reconstruirla a partir de un alias.

La visualización de `AccountId` y su representación JSON usan el formato I105 canónico.

La representación de nivel inferior `AccountAddress` muestra/JSON utiliza el hex canónico para contextos internos y de depuración.

Llame al codificador `AccountAddress` I105 explícito cuando se requiera una cuenta externa ID.

Para los flujos de trabajo de creación de cuentas y resolución de alias, continúe con [Cuentas y alias](/es/cookbook/accounts-and-aliases.md).

Para el modelo de datos sobre cuentas, véase [Cuentas](/es/blockchain/accounts.md).
