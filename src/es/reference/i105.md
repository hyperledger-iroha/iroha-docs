# I105 Formato de Dirección de la Cuenta {#i105-account-address-format}

I105 es el formato de texto externo canónico para un Iroha 3 `AccountId`.

Su carga representa el controlador de la cuenta.

Su centinela identifica la red deseada con un discriminador de cadena.

Úselo en cualquier lugar donde un API, transacción, permiso o consulta solicite un ID de cuenta canónico.

Un ID de cuenta I105 no tiene dominio.

Un valor como `treasury@payments.universal` es un alias de cuenta, no otra ortografía del ID I105.

Derivar un ID I105 no registra ni financia la cuenta.

::: warning Las reglas que previenen la mayoría de los fallos de integración

- Seleccione el perfil de red antes de codificar o validar una dirección.
- Almacene y compare la cadena canónica UTF-8 exactamente.
- Conserve exactamente las mayúsculas y minúsculas, y no aplique la normalización de `Unicode`.
- Un ID I105 no debe tener un sufijo `@domain` o `@domain.dataspace`.
- Usa un Iroha SDK o `iroha tools address`.
- Una expresión regular no es un validador de I105.

:::

## Anatomía literal {#literal-anatomy}

Un literal I105 tiene tres partes adyacentes y ningún separador:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

|Parte|Propósito|Cobertura de suma de verificación|
| ---------------- | ------------------------------------------------------------------ | ----------------- |
|Centinela de la red|Asigna el texto a un discriminante de cadena `u16`|No cubierto|
|Carga útil| `base-105` codificación de los bytes del controlador de cuenta canónica |Cubierto|
|Suma de comprobación|Seis valores `5-bit` al estilo `Bech32m` representados con el alfabeto I105|N/A|

La carga útil y la suma de verificación identifican al controlador de la cuenta.

El centinela selecciona el contexto de la red.

El mismo controlador tiene la misma carga útil y suma de verificación en Taira y Minamoto, pero cada red utiliza un centinela inicial diferente.

Un decodificador debe imponer el discriminante esperado.

La suma de verificación no puede detectar una sustitución de centinela.

### Centinelas de la red {#network-sentinels}

|Red o contexto|Discriminante de cadena|Hex|Centinela canónico|
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
| Taira red de prueba pública    |                            `369` | `0x0171` | `test`                                      |
| Minamoto red pública |                            `753` | `0x02f1` | `sora`                                      |
|Contexto de desarrollo|                              `0` | `0x0000` | `dev`                                       |
| Cualquier otro valor `u16` |Todos excepto `0`, `369` y `753`|        — | `n` más decimal mínimo, por ejemplo `n42` |

Los valores nombrados siempre usan su centinela nombrado.

Formas como `n00042`, `n369`, `n753` y `n0` no son canónicas.

El ID de la cadena de transacciones y el discriminante de cadena I105 son valores separados.

Elegir un endpoint o ID de cadena API no selecciona implícitamente el perfil de dirección.

## Ejemplo normativo de una sola tecla {#normative-single-key-example}

La carga útil y el formulario Minamoto a continuación provienen del vector de pruebas de conformidad entre SDK.

El formulario Taira aplica el centinela de Taira al mismo cargamento:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

La carga útil canónica comienza con `02 00 01 20`: encabezado `0x02`, etiqueta compacta de clave única `0x00`, ID de curva `Ed25519` `0x01`, y una longitud de clave de 32 bytes `0x20`.

El prefijo `multihash` es metadata de entrada y no se copia en la carga útil del controlador.

## Crea e inspecciona identificaciones con el CLI {#create-and-inspect-ids-with-the-cli}

Prefiera un perfil con nombre para una red pública:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

Normalizar y comparar una entrada I105 mientras se diagnostica el comportamiento del códec de direcciones:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

Inspeccione el formato detectado, el hexadecimal canónico y el contexto de red seleccionado como JSON:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

Audita la estructura de códec de direcciones de un archivo separado por nuevas líneas sin aceptar silenciosamente fallos de análisis:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution CLI límite de validación

Los comandos `convert`, `normalize` y `audit` funcionan sobre el códec `AccountAddress` de bajo nivel.

Verifican el centinela, alfabeto, suma de verificación, longitudes de bytes, `CurveId`/forma de clave y la re-codificación exacta de la capa de dirección.

No materializan un `AccountId`.

Por sí mismos no validan toda la semántica de la política multisig.

No demuestran que la clase del encabezado coincida con el controlador.

Utilice una validación estricta `AccountId` antes de la autorización o persistencia.

:::

Para una red privada, utilice su discriminante configurado explícitamente con `--network-prefix`.

Al convertir una dirección existente entre contextos explícitos, también proporcione la fuente con `--expect-prefix`:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

La re-codificación solo cambia el contexto de la red.

No registra la cuenta en la red de destino ni prueba que el mismo controlador deba reutilizarse allí.

## Algoritmo de codificación {#encoding-algorithm}

Los codificadores canónicos realizan estas operaciones:

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

Los bytes cero iniciales se conservan como dígitos `base-105` con valor cero.

La suma de verificación utiliza los generadores `Bech32` `polymod` y la constante `0x2bc830a3`.

El HRP usado exclusivamente para la suma de comprobación es la cadena ASCII `snx`.

El HRP usado exclusivamente para la suma de comprobación no se incluye en la dirección.

Los seis valores de suma de verificación están en el rango `0..31` y se representan a través del mismo alfabeto I105 que la carga útil.

### I105 alfabeto {#i105-alphabet}

Los 105 símbolos están indexados en este orden exacto.

La primera fila es el alfabeto `Bitcoin Base58` y contiene los dígitos `0..57`.

La segunda fila contiene los dígitos `58..104`.

Concatena las filas al implementar el códec.

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

El alfabeto es sensible a `Unicode`.

La secuencia exacta utiliza `compatibility-width` símbolos japoneses `kana` más los puntos de código mostrados para `ヰ` y `ヱ`.

No aplique NFC ni NFKC, ni convierta el ancho de los caracteres, ni cambie las mayúsculas y minúsculas, ni sustituya caracteres por otros visualmente similares.

ASCII `0`, `O`, `I` y `l` no son símbolos del alfabeto.

## Carga útil canónica {#canonical-account-payload}

El cuerpo `base-105` codifica una carga útil de cuenta binaria, no una cadena de clave pública y no un objeto Norito JSON:

```text
header:u8 || controller:variable
```

Todos los enteros multibyte a continuación son sin signo y `big-endian`.

El dominio, el espacio de datos, el alias, el UAID y los bytes de metadatos de la cuenta no están presentes.

### Byte de cabecera {#header-byte}

|Bits|Ancho|       Salida actual del codificador |Significado|
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |Campo de la versión del formato de dirección|
| `4..3` |     2 |`0` clave única, `1` multisig|Clase de dirección|
| `2..1` |     2 |                          `1` |Campo de versión de normalización|
| `0`    |     1 |                          `0` |Reservado `extension flag`|

Los codificadores actuales V1 emiten el encabezado `0x02` para un controlador de clave única y `0x0a` para un controlador multisig.

Las clases de dirección `2` y `3` no están asignadas.

Un `extension flag` de `1` es rechazado.

El decodificador de bajo nivel puede preservar otros valores de bits de versión y normalización y no verifica de forma independiente la clase contra la etiqueta del controlador.

Convertir a un `AccountId` y comparar su representación canónica demuestra la canonicidad actual de V1.

### Controlador de una sola tecla {#single-key-controller}

Use la forma compacta cuando la carga útil de la clave pública sin procesar tenga como máximo 255 bytes:

|Campo|Ancho|Valor o significado|
| ------------ | --------------: | ------------------------ |
| `tag`        |          1 byte | `0x00`                   |
| `curve`      |          1 byte |valor del registro `CurveId`|
|`key_len` |1 byte |Longitud de la clave en bruto |
| `public_key` | `key_len` bytes |Carga útil de clave pública sin procesar|

Las claves de más de 255 bytes usan la forma extendida:

|Campo|Ancho|Valor o significado|
| ------------ | --------------: | ---------------------------- |
| `tag`        |          1 byte |`0x02`                       |
| `curve`      |          1 byte | `CurveId` valor del registro     |
|`key_len` |2 bytes |Longitud de la clave en bruto, `big-endian` |
| `public_key` | `key_len` bytes |Carga útil de clave pública sin procesar|

Una codificación extendida no es canónica para una clave que encaja en la forma compacta.

### Controlador multisig {#multisig-controller}

|Campo|    Ancho |Valor o significado|
| ---------------- | -------: | ------------------------------ |
| `tag`            |1 byte| `0x01`                         |
| `policy_version` |   1 byte |Valor actual `1`|
| `threshold`      |2 bytes|Peso total de aprobación requerido|
| `member_count`   |2 bytes|Número de miembros que siguen|
| `members`        |Variable|Registros de miembros repetidos|

Cada registro de miembro es:

|Campo|Ancho|Significado|
| ------------ | --------------: | ------------------------ |
| `curve`      |          1 byte |valor del registro `CurveId`|
| `weight`     |         2 bytes |Peso de la aprobación del miembro|
|`key_len` |2 bytes |Longitud de la clave en bruto |
| `public_key` | `key_len` bytes |Carga útil de clave pública sin procesar|

Una política válida tiene al menos un miembro, ponderaciones positivas, sin claves públicas duplicadas y un umbral desde `1` hasta la suma de las ponderaciones de los miembros.

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

La construcción canónica clasifica a los miembros por el nombre estable del algoritmo de firma, un byte separador cero, y luego los bytes de clave pública en bruto.

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

Un literal I105 no tiene una longitud de carácter fija porque los controladores multisig y post-cuánticos pueden ser grandes.

### `CurveId` registro {#curveid-registry}

La columna final nombra la característica opcional requerida `Cargo`.

Un guion significa que la entrada del registro está disponible sin una característica opcional del modelo de datos.

|ID|Algoritmo de firma| Función requerida `Cargo` |
| ---: | -------------------------------------------- | ------------------------ |
|  `1` | `Ed25519`                                    | —                        |
|  `2` | `ML-DSA`                                     | —                        |
|  `3` | `BLS12-381 normal`                           | `bls`                    |
|  `4` | `secp256k1`                                  | —                        |
|  `5` | `BLS12-381 small`                            | `bls`                    |
| `10` | `GOST R 34.10-2012 256-bit, parameter set A` | `gost`                   |
| `11` | `GOST R 34.10-2012 256-bit, parameter set B` | `gost`                   |
| `12` | `GOST R 34.10-2012 256-bit, parameter set C` | `gost`                   |
| `13` | `GOST R 34.10-2012 512-bit, parameter set A` | `gost`                   |
| `14` | `GOST R 34.10-2012 512-bit, parameter set B` | `gost`                   |
| `15` | `SM2`                                        | `sm`                     |

Los ID no asignados y los algoritmos deshabilitados en la compilación receptora son rechazados.

La carga útil de la clave también debe ser estructuralmente válida para el algoritmo seleccionado por el `CurveId` declarado.

## Validación estricta AccountId y canonicidad {#strict-accountid-validation-and-canonicality}

Después de configurar el SDK con el discriminante de cadena esperado, analice en un `AccountId` y compare la representación canónica devuelta con la entrada recortada.

La comparación es significativa porque el analizador puede normalizar el material de controlador decodificable mientras construye el `AccountId`.

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

Para una cadena no confiable, una aplicación conforme debería:

1. Recorta solo los espacios de transporte permitidos alrededor del valor completo.
2. Lea el centinela y requiera el discriminante de cadena esperado.
3. Mapea cada símbolo `Unicode` restante a través del alfabeto exacto de 105 símbolos.
4. Separe los seis dígitos correspondientes a la suma de comprobación.
5. Convierte los dígitos de la carga útil de nuevo a bytes canónicos.
6. Verifique la suma de comprobación calculada sobre esos bytes canónicos.
7. Analiza el encabezado y el controlador, requiriendo:
   - longitudes de campo exactas
   - un `CurveId` compatible
   - una clave pública válida
   - sin bytes restantes
   - una política multisig válida cuando corresponda
8. Construye un `AccountId`.
9. Genere la representación canónica del `AccountId` para el discriminante esperado.
10. Requerir la igualdad de `byte-for-byte` con la entrada recortada.

El paso final explícito `render-and-compare` de la aplicación rechaza centinelas numéricos no mínimos, diseños de controladores no canónicos, material de políticas reordenado y cualquier otra ortografía que se decodifique pero que no sea la salida actual V1 del codificador.

Un checksum exitoso o un análisis de bajo nivel `AccountAddress` no son un sustituto de esta verificación.

No acepte estos valores en un campo de ID de cuenta estricto:

- un alias de cuenta como `alice@wonderland.universal`
- un I105 literal con un sufijo `@domain` añadido
- una clave pública `multihash` como `ed0120...`
- carga útil canónica en hexadecimal como `0x02000120...`
- una dirección para el discriminante de cadena incorrecto
- una cadena en la que se hayan cambiado las letras mayúsculas o minúsculas, el ancho de los caracteres, los caracteres `kana`, la carga útil o la suma de comprobación

Resuelva los alias en el límite de la aplicación y conserve el ID canónico I105 devuelto para autorización, firma, permisos y registros de auditoría.

### Códigos de error estables comunes {#common-stable-error-codes}

|Código|Significado|
| -------------------------------- | ------------------------------------------------------------------- |
|`ERR_UNEXPECTED_NETWORK_PREFIX`|El discriminante decodificado no coincide con la red requerida|
| `ERR_CHECKSUM_MISMATCH`          |Los seis símbolos de suma de verificación no coinciden con la carga útil|
| `ERR_INVALID_I105_CHAR`          |Un símbolo está fuera del alfabeto exacto|
| `ERR_MISSING_I105_SENTINEL`      |No se encontró ningún centinela nombrado o numérico canónico|
| `ERR_I105_TOO_SHORT`             |El cuerpo no puede contener tanto la carga útil como la suma de comprobación|
| `ERR_INVALID_LENGTH`             |Un campo del controlador está truncado o utiliza una forma de longitud no canónica|
| `ERR_UNKNOWN_CURVE`              |El controlador declara un `CurveId` no asignado o no disponible|
| `ERR_INVALID_PUBLIC_KEY`         |La clave no es válida para el algoritmo seleccionado por su `CurveId`|
| `ERR_UNSUPPORTED_ADDRESS_FORMAT` |La entrada no es una forma canónica I105 aceptada|

## API, almacenamiento y reglas de visualización {#api-storage-and-display-rules}

- Envía la cadena exacta I105 UTF-8 en los campos de cuenta JSON.
- `Percent-encode` la identificación completa de la cuenta antes de colocarla en un segmento de ruta URL.
- Nunca use un alias de cuenta en lugar de un I105 ID.
- Almacene la cadena canónica devuelta por el códec con semántica de comparación `byte-preserving`.
- Use una intercalación que preserve las mayúsculas y minúsculas y el ancho de los caracteres.
- Mantenga el discriminante de la cadena o el perfil de red nombrado con los datos de la cuenta exportados y las copias de seguridad.
- Reutilice una dirección solo con su contexto de red.
- Muestra la dirección completa y proporciona una acción de copiar.
- Preserva cada carácter `kana` exactamente.
- Mantenga la dirección completa disponible cuando una pantalla compacta acorte su parte central.
- Use el ID canónico almacenado en lugar de reconstruirlo a partir de un alias.

La visualización de `AccountId` y su representación JSON usan el formato I105 canónico.

La representación/visualización de nivel inferior `AccountAddress`/JSON utiliza hexagonal canónica para contextos internos y de depuración.

Llame al codificador explícito `AccountAddress` I105 cuando se requiera un ID de cuenta externa.

Para la creación de cuentas y los flujos de trabajo de resolución de alias, continúe con [Cuentas y alias](/es/cookbook/accounts-and-aliases.md).

Para el modelo de datos de la cuenta, consulte [Cuentas](/es/blockchain/accounts.md).
