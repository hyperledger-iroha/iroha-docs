# I105 Нягтлан бодох бүртгэлийн хаягийн хэлбэр {#i105-account-address-format}

I105 нь Canonical гадаад бичгийн хэлбэр Iroha 3 `AccountId`.

Үүнд ашигтай ачаалал нь дансны хяналтын ажилтанг илэрхийлдэг.

Түүний хяналтын зөөврийн тэмдэг нь зорилтот сүлжээг зангилын зөрчилтэй тодорхойлдог.

API, гүйлгээ, зөвшөөрөл, эсвэл хүсэлтээр ID санхүүгийн дансны талаар асуудаг хаана ч ашиглаарай.

I105 данс ID нь доменгүй.

`treasury@payments.universal` зэрэг утга нь I105 ID-ийн өөр бичлэг биш, дансны alias юм.

I105 ID-ийг олох нь дансыг бүртгэхгүй, санхүүжүүлэхгүй.

::: warning Нэвтрүүлгийн ихэнх алдааг урьдчилан сэргийлэх журам

- Хатуу хаягийг кодлож, баталгаажуулахын өмнө сүлжээний хувилбар сонгох.
- Canonical UTF-8 жиргийг үнэн зөв хадгалах, харьцуулах.
- Үсгийн том, жижиг хэлбэрийг хэвээр хадгалж, `Unicode` нормчлол бүү хэрэглэ.
- I105 ID нь `@domain` эсвэл `@domain.dataspace` дагавартай байж болохгүй.
- Iroha SDK эсвэл `iroha tools address` дугаарыг ашиглаж байна.
- Тогтмол илэрхийлэл нь I105 баталгаажуулагч биш.

:::

## Тодруулбал: {#literal-anatomy}

I105 утга нь гурван хөрш хэсэгтэй бөгөөд хуваагчгүй:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

|Дээрх хэсэг|Зорилго|Шэксний хэмжээг хамардаг |
| ---------------- | ------------------------------------------------------------------ | ----------------- |
|Сүлжээний хяналтын ажилтан |Текст нэг `u16` сүлжээний ялгаварч руу зураглана |Үүнд хамааралгүй .|
|Payload |`base-105` каноник дансны controller байтын кодлол |Хамрагдана |
|Хяналтын нийлбэр |I105 цагаан толгойгоор дүрслэгдсэн зургаан `Bech32m` маягийн `5-bit` утга |N/A |

Payload болон хяналтын нийлбэр нь дансны controller-ийг тодорхойлно.

Sentinel нь сүлжээний контекстийг сонгоно.

Нэг л хяналтын хэрэглэгч Taira болон Minamoto-д ижил үр ашигтай ачаалал, шалгалтын хэмжээтэй боловч тухайн сүлжээ нь өөр үндсэн хяналтчийн системийг ашигладаг.

Декодер нь хүлээгдэж буй дискриминантыг заавал шалган мөрдүүлэх ёстой.

Хяналтын нийлбэр нь sentinel-ийг сольсныг илрүүлэх боломжгүй.

### Тээврийн хяналтын тоног төхөөрөмж {#network-sentinels}

|Сүлжээ эсвэл хүрээнд |Сүлжээний ялгавар |Хекс |Canonical Sentinel |
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
|Taira олон нийтийн шалгалтын сүлжээ|                            `369` |`0x0171` |`test` |
|Minamoto нийтийн сүлжээ |                            `753` |`0x02f1` |`sora` |
|Хөгжлийн нөхцөл байдал |                              `0` |`0x0000` |`dev` |
|Бусад `u16` үнэ цэнэ |Бүх нь `0`, `369`, `753` бусад .|        — |`n` болон хамгийн бага арван тоот тоо, жишээ нь `n42` |

Нэрлэгдсэн үнэ цэнэүүд нь үргэлж өөрийн нэрэмжит хяналтын заалтыг ашигладаг.

`n00042`, `n369`, `n753` болон `n0` зэрэг хэлбэрүүд нь хуулиар батлагдаагүй.

Транзакцын сүлжээ ID болон I105 сүлжээний зөрүү нь бие даасан үнэ цэнэ юм.

ID төгсгөлийн цэг эсвэл зангилаа сонгох нь хаягийн хувилбарыг шууд ч сонгохгүй байна.

## Норматив нэг түлхүүгийн жишээ {#normative-single-key-example}

Доорх ашигтай ачаалл, Minamoto хэлбэр нь SDK-ийн хяналтын нийцүүлэлээс үүдэлтэй байна.

Taira бланк нь Taira-ийн хяналтын тоног төхөөрөмжийг ижил ашигтай ачаалалд ашигладаг:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

Каноникийн хэрэглээний ачаалл нь `02 00 01 20`: толгой `0x02`, компакт цорын ганц түлхүүр тэмдэг `0x00`, `Ed25519` дугуй ID `0x01`, 32 байтын товч урттай `0x20`.

`multihash` префикс нь өгөгдлийн метабарууд бөгөөд хяналтын тоног төхөөрөмжийн ашигтай ачаалалд оруулахгүй юм.

## IDs-ийг CLI -ийн хамт байгуулж, хяналт шалгана {#create-and-inspect-ids-with-the-cli}

Олон нийтийн сүлжээний хувьд нэр бүхий профилээр сонгох:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

I105 өгөгдлийг хаяг-кодек заншлыг оношилуулж харьцуулах:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

Мэдэгдсэн формат, Canonical hex, сонгогдсон сүлжээний хүрээг JSON гэж шалгана уу:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

Шинэ шугамгаар хуваагдсан файлын хаяг-кодекийн бүтцийг шинжилгээний алдаагүйгээр хянах:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution CLI баталгаажуулах хязгаар

`convert`, `normalize`, `audit` команд нь доод түвшний `AccountAddress` кодек дээр ажилладаг.

Эдгээр нь sentinel, цагаан толгой, хяналтын нийлбэр, байтын урт, `CurveId`/түлхүүрийн хэлбэр болон хаягийн түвшний яг ижил дахин кодлолтыг шалгана.

Эдгээр нь `AccountId` үүсгэдэггүй.

Тэд өөрсдөө бүх олон тамгын бодлогын утга зохиог баталгаажуулахгүй.

Эдгээр нь header-ийн ангилал controller-той тохирч байгааг нотлохгүй.

Зөвшөөрөл олгох эсвэл байнгын хадгалалт хийхээс өмнө `AccountId`-ийн хатуу баталгаажуулалт хэрэглэнэ.

:::

Хувийн сүлжээнд түүний тохируулсан дискриминантыг `--network-prefix`-ээр ил тод зааж хэрэглэнэ.

Орчин үеийн хаягийг тодорхой контекст хооронд өөрчлөх үед эх үүсвэрийг `--expect-prefix` гэж нэмнэ:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

Шинэчлэл нь зөвхөн сүлжээний хүрээг өөрчлөх болно.

Энэ нь зорилтот сүлжээнд дансыг бүртгэхгүй бөгөөд ижил controller-ийг тэнд дахин ашиглах ёстойг нотлохгүй.

## Кодируулсан алгоритм {#encoding-algorithm}

Canonical кодер нь дараах үйл ажиллагааг гүйцэтгэдэг:

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

Эхний тэг байтуудыг тэг утгатай `base-105` цифрүүд болгон хадгална.

Хяналтын дүн нь `Bech32` `polymod` генератор, тогтмол `0x2bc830a3` ашигладаг.

Зөвхөн хяналтын хэмжээний HRP нь ASCII шугам `snx` юм.

Зөвхөн хяналтын хэмжээ HRP нь хаягт хэвлэгддэггүй.

Хяналтын нийлбэрийн зургаан утга `0..31` мужид байх бөгөөд payload-тай адил I105 цагаан толгойгоор дүрслэгдэнэ.

### I105 албан бичиг {#i105-alphabet}

105 символ нь яг ийм жагсаалтад жагссан байна.

Эхний шугам нь `Bitcoin Base58` албан бичиг бөгөөд `0..57` тэмдэгтэй байна.

Хоёр дахь шугам нь `58..104` цифртай байна.

Codec-ийг хэрэгжүүлэхдээ шугамыг конкатент болгох.

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

Альфабет нь `Unicode` -ийн мэдрэмжтэй.

Тухайн цуврал нь `compatibility-width` Япон хэлний `kana` тэмдгийг болон `ヰ`, `ヱ` гэсэн код тоймдыг ашигладаг.

NFC, NFKC, өргөн хувиргалт, үсгийн том/жижиг хэлбэрийг нэгтгэх эсвэл төстэй дүрстэй тэмдэгтээр орлуулахыг бүү хэрэглэ.

ASCII `0`, `O`, `I` болон `l` нь албан бичгийн тэмдэг биш.

## Canonical бүртгэлийн ашигтай ачаалал {#canonical-account-payload}

`base-105` корпус нь олон нийтийн ач холбогдолтой шугам биш, Norito JSON объектыггүйгээр бинарны дансны ашиг ачааллыг кодлуулдаг:

```text
header:u8 || controller:variable
```

Доорх бүх олон байтын бүтэн тоог тэмдэглэхгүй бөгөөд `big-endian`.

Домен, өгөгдлийн орон зай, нууц нэр UAID, болон дансны метадангарын байт байхгүй.

### Header байт {#header-byte}

|Битүүд |Өргөн |Одоогийн кодлогчийн гаралт |Утга |
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |Хаягийн форматын хувилбарын талбар |
| `4..3` |     2 |`0` нэг түлхүүр, `1` multisig |Хаягийн ангилал |
| `2..1` |     2 |                          `1` |Нормализацын хувилбарын талбар |
| `0`    |     1 |                          `0` |Нөөцөлсөн `extension flag` |

Одоогийн V1 коджуулагч нь нэг түлхүүртэй хяналтын тоног төхөөрөмжийн `0x02` толгой, олон тамгын хяналт тавих тоног төмөрөөрөмжний `0x0a` үндсийг гаргаж байна.

`2` болон `3` хаягийн ангиллууд хуваарилдаггүй.

`extension flag` төвийг `1` нь татгалзах.

Төмөн түвшний декодер нь бусад хувилбар, нормализацийн бит-ийн үнэ цэнийг хадгалах боломжтой бөгөөд ангиг хяналтын хэсгээрээ бие дааж шалгаж чадахгүй.

`AccountId` руу хөрвүүлээд түүний каноник дүрслэлийг харьцуулах нь одоогийн V1 каноник хэлбэр мөн болохыг нотолно.

### Нэг түлхүүртэй хяналтын систем {#single-key-controller}

Түүхий нийтийн түлхүүрийн өгөгдөл хамгийн ихдээ 255 байт бол компакт хэлбэрийг ашиглана:

|Талбар |Өргөн |Утга |
| ------------ | --------------: | ------------------------ |
|`tag` |1 байт |`0x00` |
|`curve` |1 байт |`CurveId` бүртгэлийн үнэ цэнэ |
|`key_len` |1 байт |Түүхий түлхүүрийн урт |
|`public_key` |`key_len` байт |Түүхий нийтийн түлхүүрийн өгөгдөл |

255 байт илүү урт түлхүүр нь өргөжин тэлсэн хэлбэрээр ашигладаг:

|Талбар |Өргөн |Утга |
| ------------ | --------------: | ---------------------------- |
|`tag` |1 байт |`0x02` |
|`curve` |1 байт |`CurveId` бүртгэлийн үнэ цэнэ |
|`key_len` |2 байт |Түүхий түлхүүрийн урт, `big-endian` |
|`public_key` |`key_len` байт |Түүхий нийтийн түлхүүрийн өгөгдөл |

Компакт хэлбэрт багтах түлхүүрт өргөтгөсөн кодлол каноник биш.

### Multisig controller {#multisig-controller}

|Талбар |Өргөн |Утга |
| ---------------- | -------: | ------------------------------ |
|`tag` |1 байт |`0x01` |
|`policy_version` |1 байт |Одоогийн үнэ `1` |
|`threshold` |2 байт |Шаардлагатай нийт батлалын жин |
|`member_count` |2 байт |Дараах гишүүдийн тоо |
|`members` |Хувьсах |Давтагдах гишүүний бичлэгүүд |

Гишүүн бүрийн бичлэг:

|Талбар |Өргөн |Утга |
| ------------ | --------------: | ------------------------ |
|`curve` |1 байт |`CurveId` бүртгэлийн үнэ цэнэ |
|`weight` |2 байт |гишүүний зөвшөөрлийн жин |
|`key_len` |2 байт |Түүхий түлхүүрийн урт |
|`public_key` |`key_len` байт |Түүхий нийтийн түлхүүрийн өгөгдөл |

Хүчинтэй policy нь дор хаяж нэг гишүүнтэй, эерэг жинтэй, давхардсан нийтийн түлхүүргүй, threshold нь `1`-ээс гишүүдийн жингийн нийлбэр хүртэл байна.

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

Каноник үүсгэлт гишүүдийг гарын үсгийн алгоритмын тогтвортой нэр, тэг тусгаарлагч байт, дараа нь түүхий нийтийн түлхүүрийн байтаар эрэмбэлнэ.

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

I105 номонд тодорхой тэмдэгний урт байхгүй, учир нь мультисиг болон квантын дараах хяналтлагчид их байж болно.

Даш нь регистрийн бүртгэл нь сонголттой мэдээллийн загварын шинж чанаргүй байх боломжтой гэсэн үг юм.

| ---: | -------------------------------------------- | ------------------------ |
|  `1` |`Ed25519` | —                        |
|  `2` |`ML-DSA` | —                        |
|  `3` |`BLS12-381 normal` |`bls` |
|  `4` |`secp256k1` | —                        |

Үүнд зориулалтгүй IDs болон хүлээн авагч барилдаанд хүчингүй болгосон алгоритмүүд радлагдана.

Нүүрний ашигтай ачаалл нь `CurveId` дугуулсан алгоритмийн хувьд ч бүтэцээрээ хүчинтэй байх ёстой.

## AccountId-ийн хатуу баталгаажуулалт ба каноник байдал {#strict-accountid-validation-and-canonicality}

SDK-г хүлээгдэж буй сүлжээний дискриминантаар тохируулсны дараа `AccountId` болгон задлан шинжилж, буцаасан каноник дүрслэлийг захын зайг авсан оролттой харьцуулна.

Энэ харьцуулалт нь `AccountId` төхөөрөмжийг бүтээн байгуулахын зэрэгцээ дэкодлагдах хяналтын материалыг шинжилгээний систем хэвийн болгох боломжтой учраас чухал юм.

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

Итгэмжлэгдэхгүй жирний хувьд, нийцсэн хэрэгсэл:

1. Бүхэл утгын эргэн тойронд тээвэрлэлтийн зөвшөөрөгдсөн хоосон зайг л тайрна.
2. Sentinel-ийг уншиж, хүлээгдэж буй сүлжээний дискриминантыг шаард.
3. Үлдсэн `Unicode` тэмдэг бүрийг яг 105 тэмдэгтэй цагаан толгойгоор хөрвүүл.
4. Хяналтын нийлбэрийн зургаан цифрийг салга.
5. Payload-ийн цифрүүдийг каноник байт руу буцаан хөрвүүл.
6. Тэдгээр каноник байтын хяналтын нийлбэрийг шалга.
7. Header болон controller-ийг задлан, дараахыг шаард:
   - талбаруудын яг урт
   - дэмжигдсэн `CurveId`
   - хүчинтэй нийтийн түлхүүр
   - төгсгөлийн илүү байтгүй байх
   - хэрэглэх тохиолдолд хүчинтэй multisig policy
8. `AccountId` үүсгэ.
9. `AccountId`-ийг хүлээгдэж буй дискриминантад каноник байдлаар дүрсэл.
10. Захын зайг авсан оролттой `byte-for-byte` ижил байхыг шаард.

Хэрэглээний эцсийн тодорхой `render-and-compare` алхам нь хамгийн бага бус тоон sentinel-үүд, каноник бус controller байрлалууд, дахин эрэмбэлэгдсэн policy материал болон декодлогддог боловч encoder-ийн одоогийн V1 гаралт биш бусад бүх бичлэгийг няцаана.

Хяналтын нийлбэр амжилттай байх эсвэл доод түвшний `AccountAddress` задлалт энэ шалгалтыг орлохгүй.

Эдгээр үнэ цэнэүүдийг ID сангийн хатуу бүлэгт хүлээн зөвшөөрөхгүй:

- `alice@wonderland.universal` гэх мэт сангийн нууц нэр
- I105 нарийн бичгийн тэмдэг, хавсралтаар `@domain` хувилбар
- `ed0120...` гэх мэт олон нийтийн гол `multihash`
- Canonical payload hex `0x02000120...` гэх мэт
- буруу зангилагийн зөрчилтэй хүний хаяг
- Том эсвэл жижиг үсэг, тэмдэгтийн өргөн, `kana`, payload эсвэл хяналтын нийлбэр нь өөрчлөгдсөн тэмдэгт мөр

Хэрэглээний хязгаарт алиасыг шийдвэрлэх, зөвшөөрөл, гарын үсэг зурах, зөвшөөрөл олгох, аудитын бүртгэлийн хувьд эргүүлэн ирүүлсэн каноникийн I105 ID тэмдэгтийг хадгалах.

## API, хадгалах, дэлгэцийн дүрэм {#api-storage-and-display-rules}

- Тухайн I105 UTF-8 шугам нь JSON бүртгэлийн талбайд ирүүлнэ.
- `Percent-encode` бүрэн бүртгэл ID нь URL замын хэсгэнд байршуулахын өмнө.
- Хэзээ ч I105 ID-ийн оронд дансны нэрэмжит нэрийг солих хэрэггүй.
- Codec-ийн буцаасан Canonical string-ийг `byte-preserving` харьцуулах семантикатай хадгалах.
- Үсгийн том, жижиг хэлбэр болон тэмдэгтийн өргөнийг хадгалдаг эрэмбэлэлтийг ашигла.
- Экспортолсон дансны өгөгдөл болон нөөц хуулбарт chain discriminant эсвэл нэрлэсэн network profile-ийг хамт хадгал.
- Хаягийг зөвхөн өөрийнх нь сүлжээний контексттэй хамт дахин ашигла.
- Бүрэн хаягийг харуулж, хуулах үйлдэл өг.
- Бүх `kana` дүрүүдийг яг хадгалах.
- Тодорхой хаяг нь компакт дэлгэцийн дунд хэсгийг богино болгоход бэлэн байлгаарай.
- Alias-аас дахин бүтээхийн оронд хадгалсан каноник ID-г ашигла.

`AccountId`-ийн дэлгэц болон JSON дүрслэл каноник I105-г ашиглана.

Доод түвшний `AccountAddress` дэлгэц/JSON төлөөлөл нь дотоод болон дэбэглэмийн хүрээнд Canonical hex ашигладаг.

Гадаад данс ID шаардлагатай бол тодорхой `AccountAddress` I105 кодлогчийг дуудлаарай.

Ахуйн нэгжийн бүрэлдэхүүнтэй [Ахуйн нэгж, нууц нэр ](/mn/cookbook/accounts-and-aliases.md)-ээр үргэлжлүүлэн ажиллах.

Нягтлан бодох бүртгэлийн мэдээллийн загварын хувьд [Нээлттэй тооцоо](/mn/blockchain/accounts.md)-ийг үзнэ үү.
