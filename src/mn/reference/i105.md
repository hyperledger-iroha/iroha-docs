# I105 Дансны Хаягын Формат {#i105-account-address-format}

I105 нь Iroha 3 `AccountId`-ийн хувьд ганц протокол-стандарт гадаад текст формат юм.

Түүний ачаа нь дансны хянагчийг илэрхийлдэг.

Түүний анхааруулагч нь чиглэсэн сүлжээг гинжин ялгагч ашиглан тодорхойлдог.

Үүнийг хаана ч API, гүйлгээ, зөвшөөрөл, эсвэл лавлагаа нэг протокол-стандарт дансны ID-г шаардах үед ашиглана уу.

I105 дансны ID нь домэйнгүй байна.

`treasury@payments.universal` зэрэг утга нь I105 ID-ийн өөр бичлэг биш, дансны alias юм.

I105 ID үүсгэх нь дансыг бүртгэх буюу санхүүжүүлэхгүй.

::: warning Итгэлцлийн ихэнх алдаанаас урьдчилан сэргийлдэг дүрмүүд

- Хаягийг кодлох эсвэл баталгаажуулахаас өмнө сүлжээний профилыг сонгоно уу.
- Нэг протокол-стандарт UTF-8 мөрийг яг таг хадгалж, харьцуулна уу.
- Үсгийн том, жижиг хэлбэрийг хэвээр хадгалж, `Unicode` нормчлол бүү хэрэглэ.
- I105 ID нь `@domain` эсвэл `@domain.dataspace` дагавартай байж болохгүй.
- 1 ширхэг Iroha SDK эсвэл `iroha tools address` хэрэглэнэ үү.
- Тогтмол илэрхийлэл нь I105 баталгаажуулагч биш.

:::

## Буквал анатоми {#literal-anatomy}

I105 литерал нь гурван залгаа хэсэгтэй ба ямар ч тусгаарлагчгүй байна:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

|Хэсэг|Зорилго|Шалгалтын нийлбэрийн хураагдлыг хамрах|
| ---------------- | ------------------------------------------------------------------ | ----------------- |
|Сүлжээний харуул|Текстыг нэг `u16` гинжний ялгагчид зураглана|Хамаарахгүй|
|Payload |`base-105` каноник дансны controller байтын кодлол |Хамрагдана |
|Хяналтын нийлбэр |I105 цагаан толгойгоор дүрслэгдсэн зургаан `Bech32m` маягийн `5-bit` утга |N/A |

Payload болон хяналтын нийлбэр нь дансны controller-ийг тодорхойлно.

Sentinel нь сүлжээний контекстийг сонгоно.

Түүнтэй ижил удирдлагатай төхөөрөмж Taira болон Minamoto дээр ижил өгөгдөл ба шалгалтын нийлбэртэй байна, гэхдээ сүлжээ бүр өөр толгой тэмдэглэгээг хэрэглэдэг.

Декодер нь хүлээгдэж буй дискриминантыг заавал шалган мөрдүүлэх ёстой.

Хяналтын нийлбэр нь sentinel-ийг сольсныг илрүүлэх боломжгүй.

### Сүлжээний сэргэгчид {#network-sentinels}

|Сүлжээ эсвэл нөхцөл байдал|Гинжний ялгаглагч|      Шоо|нэг протокол стандартын хяналтын процесс|
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
| Taira нийтийн тест сүлжээ|                            `369` | `0x0171` | `test`                                      |
| Minamoto нийтэд зориулсан сүлжээ |                            `753` | `0x02f1` | `sora`                                      |
|Хөгжлийн хүрээ|                              `0` | `0x0000` | `dev`                                       |
| Бусад `u16` утга |Бүгдийг оруулаад `0`, `369`, ба `753` -г бусад нь|        — | `n` ба хамгийн бага утгатай аравтын орон, жишээлбэл `n42` |

Нэрлэсэн утгууд үргэлж өөрийн нэрлэсэн тусгай тэмдгийг ашигладаг.

`n00042`, `n369`, `n753`, `n0` гэсэн маягтууд нь ганц протоколын стандарт биш юм.

Гүйлгээний гинжийн ID болон I105 гинжийн ялгагчийг тусдаа утгууд юм.

API төгсгөлийн цэг эсвэл сүлжээний ID-ийг сонгосноор хаягийн профайлыг автоматаар сонгосон болохгүй.

## Стандартад нийцсэн ганц түлхүүрийн жишээ {#normative-single-key-example}

Доорх ачаалал болон Minamoto хэлбэр нь SDK-уудын хоорондын нийцлийн туршилтын өгөгдлөөс гаралтай.

Taira хэлбэр нь ижил ачаалалд Taira-ийн тусгай тэмдэгтийг хэрэглэнэ:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

Ганц протоколын стандарт ачаа нь `02 00 01 20`: гарчиг `0x02`, шахсан нэг түлхүүрийн шошго `0x00`, `Ed25519` муруй ID `0x01`, мөн 32-байт түлхүүрийн урт `0x20` -аар эхэлдэг.

`multihash` префикс нь оруулах метадата бөгөөд контроллерын өгөгдлийн багцад хуулбарлагдахгүй.

## CLI ашиглан ID-үүдийг үүсгэж, шалгана уу {#create-and-inspect-ids-with-the-cli}

Олон нийтийн сүлжээнд нэртэй профайлыг сонгох:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

Хаяг-кодекийн үйлдлийг оношлох үед I105 оруулгыг хэвийн болгож, харьцуулна:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

Илрүүлсэн форматыг, нэг протокол-стандартад нийцсэн хексийг, мөн сонгогдсон сүлжээний контекстыг JSON байдлаар шалга:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

Шинэ мөрөөр тусгаарлагдсан файлд хаяг-кодек бүтэцийг аудит хийж, задлах алдааг нам гүмээр хүлээн авахгүй:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution CLI баталгаажуулах хязгаар

`convert`, `normalize`, ба `audit` командууд доод түвшний `AccountAddress` кодек дээр ажилладаг.

Эдгээр нь sentinel, цагаан толгой, хяналтын нийлбэр, байтын урт, `CurveId`/түлхүүрийн хэлбэр болон хаягийн түвшний яг ижил дахин кодлолтыг шалгана.

Эдгээр нь `AccountId` үүсгэдэггүй.

Тэд өөрсдөө бүх олон гарын үсэг бүхий бодлогын утгыг баталгаажуулдаггүй.

Эдгээр нь header-ийн ангилал controller-той тохирч байгааг нотлохгүй.

Зөвшөөрөл олгох эсвэл байнгын хадгалалт хийхээс өмнө `AccountId`-ийн хатуу баталгаажуулалт хэрэглэнэ.

:::

Хувийн сүлжээнд түүний тохируулсан дискриминантыг `--network-prefix`-ээр ил тод зааж хэрэглэнэ.

Одоогийн хаягийг тодорхой контекстуудын хооронд хөрвүүлэхдээ эх сурвалжид `--expect-prefix` өгнө үү:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

Дахин кодлох нь зөвхөн сүлжээний нөхцөл байдлыг өөрчилдөг.

Энэ нь зорилтот сүлжээнд дансыг бүртгэхгүй бөгөөд ижил controller-ийг тэнд дахин ашиглах ёстойг нотлохгүй.

## Өгөгдөл кодлох алгоритм {#encoding-algorithm}

нэг протокол-стандарт кодлогчид эдгээр үйлдлүүдийг гүйцэтгэдэг:

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

Эхний тэг байтуудыг тэг утгатай `base-105` цифрүүд болгон хадгална.

Чексум нь `Bech32` `polymod` генераторууд болон тогтмол `0x2bc830a3`-г ашигладаг.

Зөвхөн шалгалтын нийлбэр HRP нь ASCII мөр `snx` юм.

Зөвхөн шалгалтын нийлбэр HRP хаяг дээр хэвлэгддэггүй.

Хяналтын нийлбэрийн зургаан утга `0..31` мужид байх бөгөөд payload-тай адил I105 цагаан толгойгоор дүрслэгдэнэ.

### I105 цагаан толгойн тэмдэгт {#i105-alphabet}

Эдгээр 105 тэмдэгтийг яг энэ дарааллаар индексэлсэн байна.

Эхний мөр нь `Bitcoin Base58` цагаан толгой ба `0..57` тоонуудыг агуулна.

Хоёр дахь мөр нь `58..104` тоонуудыг агуулна.

Кодекыг хэрэгжүүлэхдээ мөрүүдийг нийлүүл.

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

Цагаан толгой нь `Unicode`-т мэдрэг байдаг.

Яг таарч буй дараалал нь `compatibility-width` Япон `kana` тэмдэгтүүдийг ашигладаг ба `ヰ` ба `ヱ`-ийн кодын цэгүүдийг харуулсан байдаг.

NFC, NFKC, өргөн хувиргалт, үсгийн том/жижиг хэлбэрийг нэгтгэх эсвэл төстэй дүрстэй тэмдэгтээр орлуулахыг бүү хэрэглэ.

ASCII `0`, `O`, `I`, ба `l` нь цагаан толгойны тэмдэгтүүд биш юм.

## нэг протокол-стандарт дансны өгөгдөл {#canonical-account-payload}

`base-105` бие нь олон нийтийн түлхүүрийн мөр биш, мөн Norito JSON объект биш, харин хоёртын дансны агуулгыг кодлодог:

```text
header:u8 || controller:variable
```

Доорх бүх олон байтын бүхэл тоонууд утгагүй бөгөөд `big-endian` гэсэн болно.

Домэйн, өгөгдлийн орон зай, нэрийн хувилбар, UAID, болон дансны мета өгөгдлийн байт байхгүй байна.

### Толгойн байт {#header-byte}

|Битүүд |Өргөн |Одоогийн кодлогчийн гаралт |Утга |
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |Хаягийн форматын хувилбарын талбар |
| `4..3` |     2 |`0` нэг түлхүүр, `1` multisig |Хаягийн ангилал |
| `2..1` |     2 |                          `1` |Стандарчилалтын хувилбарын талбар|
| `0`    |     1 |                          `0` |Нөөцөлсөн `extension flag` |

Одоогийн V1 кодлогчид нэг түлхүүртэй контроллерт `0x02` ба олон гарын үсэг бүхий контроллерт `0x0a` гаргардаг.

Хаягийн ангиуд `2` ба `3` томилогдоогүй байна.

`1`-ийн `extension flag` нь үгүйсгэгдсэн.

Бага түвшний декодер нь өөр хувилбар болон стандартчиллын бит утгуудыг хадгалах боломжтой бөгөөд ангиллыг хянагчийн шошготой бие даан давхар шалгахгүй.

`AccountId` руу хөрвүүлээд түүний каноник дүрслэлийг харьцуулах нь одоогийн V1 каноник хэлбэр мөн болохыг нотолно.

### Нэг товчлууртай удирдлага {#single-key-controller}

Түүхий нийтийн түлхүүрийн өгөгдөл хамгийн ихдээ 255 байт бол компакт хэлбэрийг ашиглана:

|Талбар |Өргөн |Утга |
| ------------ | --------------: | ------------------------ |
| `tag`        |          1 байт | `0x00`                   |
| `curve`      |          1 байт | `CurveId` бүртгэлийн утга |
|`key_len` |1 байт |Түүхий түлхүүрийн урт |
|`public_key` |`key_len` байт |Түүхий нийтийн түлхүүрийн өгөгдөл |

255 байтаас урт түлхүүрүүд өргөтгөсөн хэлбэрийг ашиглана:

|Талбар |Өргөн |Утга |
| ------------ | --------------: | ---------------------------- |
| `tag`        |          1 байт | `0x02`                       |
| `curve`      |          1 байт | `CurveId` бүртгэлийн утга |
|`key_len` |2 байт |Түүхий түлхүүрийн урт, `big-endian` |
|`public_key` |`key_len` байт |Түүхий нийтийн түлхүүрийн өгөгдөл |

Компакт хэлбэрт багтах түлхүүрт өргөтгөсөн кодлол каноник биш.

### Олон гарын үсгийн хянагч {#multisig-controller}

|Талбар |Өргөн |Утга |
| ---------------- | -------: | ------------------------------ |
| `tag`            |1 байт| `0x01`                         |
| `policy_version` |1 байт|Одооны үнэ цэнэ `1`|
| `threshold`      |2 байт|Шаардлагатай нийт зөвшөөрлийн жин|
| `member_count`   |2 байт|Дараагийн гишүүдийн тоо|
|`members` |Хувьсах |Давтагдах гишүүний бичлэгүүд |

Гишүүн бүрийн бичлэг:

|Талбар |Өргөн |Утга |
| ------------ | --------------: | ------------------------ |
| `curve`      |          1 байт | `CurveId` бүртгэлийн утга |
| `weight`     |         2 байт |Гишүүний зөвшөөрлийн жин|
|`key_len` |2 байт |Түүхий түлхүүрийн урт |
|`public_key` |`key_len` байт |Түүхий нийтийн түлхүүрийн өгөгдөл |

Хүчинтэй policy нь дор хаяж нэг гишүүнтэй, эерэг жинтэй, давхардсан нийтийн түлхүүргүй, threshold нь `1`-ээс гишүүдийн жингийн нийлбэр хүртэл байна.

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

Каноник үүсгэлт гишүүдийг гарын үсгийн алгоритмын тогтвортой нэр, тэг тусгаарлагч байт, дараа нь түүхий нийтийн түлхүүрийн байтаар эрэмбэлнэ.

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

Нэг I105 литерал нь олон гарын үсэг болон пост-квант контроллерууд том байж болох тул тогтсон тэмдэгтийн уртгүй байдаг.

### `CurveId` бүртгэл {#curveid-registry}

Эцсийн багананд шаардлагатай сонголттой `Cargo` шинж чанарыг нэрлэдэг.

Тэмдэглэгээ нь бүртгэлийн бичлэг нь сонголттой өгөгдлийн загварын функцгүйгээр ашиглах боломжтой болохыг заана.

|ID|Гарын үсгийн алгоритм|Заавал шаардлагатай `Cargo` функц|
| ---: | -------------------------------------------- | ------------------------ |
|  `1` | `Ed25519`                                    | —                        |
|  `2` | `ML-DSA`                                     | —                        |
|  `3` | `BLS12-381 normal`                           | `bls`                    |
|  `4` | `secp256k1`                                  | —                        |
|  `5` | `BLS12-381 small`                            | `bls`                    |
| `10` | `GOST R 34.10-2012 256-bit, parameter set A` | `gost`                   |
| `11` | `GOST R 34.10-2012 256-bit, parameter set B` | `gost`                   |
| `12` | `GOST R 34.10-2012 256-bit, parameter set C` | `gost`                   |
| `13` | `GOST R 34.10-2012 512-bit, parameter set A` | `gost`                   |
| `14` | `GOST R 34.10-2012 512-bit, parameter set B` | `gost`                   |
| `15` | `SM2`                                        | `sm`                     |

Хүлээн авч буй хувилбарт оноогдоогүй ID болон идэвхгүй алгоритмуудыг татгалздаг.

Түлхүүрийн агуулга нь зарласан `CurveId`-ээр сонгогдсон алгоритмын хувьд бүтэцийн хувьд хүчин төгөлдөр байх ёстой.

## AccountId-ийн хатуу баталгаажуулалт ба каноник байдал {#strict-accountid-validation-and-canonicality}

SDK-г хүлээгдэж буй сүлжээний дискриминантаар тохируулсны дараа `AccountId` болгон задлан шинжилж, буцаасан каноник дүрслэлийг захын зайг авсан оролттой харьцуулна.

Энэ харьцуулалт нь чухал юм, учир нь парсер нь `AccountId`-ийг бүтээх явцад тайлагдах боломжтой хянагчийн материалыг хэвийн болгох боломжтой.

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

Найдвартай бус мөрийн хувьд тохирсон програм нь үүнийг хийх ёстой:

1. Бүхэл утгын эргэн тойронд тээвэрлэлтийн зөвшөөрөгдсөн хоосон зайг л тайрна.
2. Sentinel-ийг уншиж, хүлээгдэж буй сүлжээний дискриминантыг шаард.
3. Үлдсэн `Unicode` тэмдэг бүрийг яг 105 тэмдэгтэй цагаан толгойгоор хөрвүүл.
4. Хяналтын нийлбэрийн зургаан цифрийг салга.
5. Payload-ийн цифрүүдийг каноник байт руу буцаан хөрвүүл.
6. Тэдгээр каноник байтын хяналтын нийлбэрийг шалга.
7. Header болон controller-ийг задлан, дараахыг шаард:
   - талбаруудын яг урт
   - дэмжигдсэн `CurveId`
   - хүчинтэй нийтийн түлхүүр
   - төгсгөлийн илүү байтгүй байх
   - хэрэглэх тохиолдолд хүчинтэй multisig policy
8. `AccountId` үүсгэ.
9. `AccountId`-ийг хүлээгдэж буй дискриминантад каноник байдлаар дүрсэл.
10. Захын зайг авсан оролттой `byte-for-byte` ижил байхыг шаард.

Хэрэглээний эцсийн тодорхой `render-and-compare` алхам нь хамгийн бага бус тоон sentinel-үүд, каноник бус controller байрлалууд, дахин эрэмбэлэгдсэн policy материал болон декодлогддог боловч encoder-ийн одоогийн V1 гаралт биш бусад бүх бичлэгийг няцаана.

Хяналтын нийлбэр амжилттай байх эсвэл доод түвшний `AccountAddress` задлалт энэ шалгалтыг орлохгүй.

Эдгээр утгуудыг хатуу дансны ID талбарт хүлээн авбал зохилгүй:

- төлбөрийн дансны нэрийн орлуулга, жишээ нь `alice@wonderland.universal`
- нэг I105 үг бичлэг, ард нь `@domain` хаяг нэмэгдсэн
- нийтийн түлхүүр `multihash`, жишээ нь `ed0120...` шиг
- Нэг процессын стандартын дамжуулах өгөгдлийн хекс, жишээ нь `0x02000120...`
- зөв бус сүлжээний ялгагчийн хаяг
- Том эсвэл жижиг үсэг, тэмдэгтийн өргөн, `kana`, payload эсвэл хяналтын нийлбэр нь өөрчлөгдсөн тэмдэгт мөр

Программын хил дээр овог нэрийг шийдвэрлэн буцаасан ганц протоколын стандарт I105 ID-г зөвшөөрөл, гарын үсэг, эрх болон аудитын бичлэгт хадгалах.

### Ерөнхий тогтмол алдааны кодууд {#common-stable-error-codes}

| Код |Өгүүлэмж|
| -------------------------------- | ------------------------------------------------------------------- |
| `ERR_UNEXPECTED_NETWORK_PREFIX`  |Дешифрэгдсэн ялгааг шаардагдах сүлжээнд тохирохгүй байна|
| `ERR_CHECKSUM_MISMATCH`          |Тав зургаан шалгалтын нэгдлийн тэмдэгтүүд агуулгатай таарахгүй байна|
| `ERR_INVALID_I105_CHAR`          |Тэмдэг нь яг үсгийн сангаас гадна байна|
| `ERR_MISSING_I105_SENTINEL`      |Нэг ч протоколын стандарт нэртэй эсвэл тоон санж тэмдэг олдсонгүй|
| `ERR_I105_TOO_SHORT`             |Бие нь нийт агуулга ба шалгах дүнг зэрэг агуулж чадахгүй|
| `ERR_INVALID_LENGTH`             |Контроллерын талбар таслагдсан эсвэл нэг протоколын стандарт урт хэлбэрийг ашигладаггүй|
| `ERR_UNKNOWN_CURVE`              |Контроллер нь оноогдоогүй эсвэл ашиглах боломжгүй `CurveId` гэж зарлаж байна|
| `ERR_INVALID_PUBLIC_KEY`         |Тушаалыг сонгосон алгоритмд зориулагдсан түлхүүр хүчинтэй биш байна `CurveId`|
| `ERR_UNSUPPORTED_ADDRESS_FORMAT` |Оролт нь хүлээн зөвшөөрөгдсөн нэг протокол-стандарт I105 хэлбэр биш байна|

## API, хадгалах ба үзүүлэх дүрэм {#api-storage-and-display-rules}

- JSON дансны талбарт яг таг I105 UTF-8 тэмдэгт мөрийг илгээнэ үү.
- `Percent-encode` бүрэн дансны ID-г URL замын сегментэд байрлуулахын өмнө оруулна уу.
- Дансны нэрийг I105 ID-ийн оронд хэзээ ч ашиглаж болохгүй.
- Кодекээс буцсан ганц протокол-стандарт мөрийг `byte-preserving` харьцуулалтын утгатай хадгалаарай.
- Үсгийн том, жижиг хэлбэр болон тэмдэгтийн өргөнийг хадгалдаг эрэмбэлэлтийг ашигла.
- Экспортолсон дансны өгөгдөл болон нөөц хуулбарт сүлжээний ялгагч эсвэл нэрлэсэн сүлжээний профайлыг хамт хадгал.
- Хаягийг зөвхөн өөрийнх нь сүлжээний контексттэй хамт дахин ашигла.
- Бүрэн хаягийг харуулж, хуулах үйлдэл өг.
- Бүх `kana` тэмдгийг яг таг хадгалаарай.
- Дунд хэсэг нь багассан жижиг дэлгэцэнд хаягийг бүрэн хэмжээгээр нь хадгална уу.
- Alias-аас дахин бүтээхийн оронд хадгалсан каноник ID-г ашигла.

`AccountId`-ийн дэлгэц болон JSON дүрслэл каноник I105-г ашиглана.

Доод түвшний `AccountAddress` дэлгэц/JSON илэрхийлэлт нь дотоод болон алдааг оношлох нөхцөлд нэг протокол стандарт хэвтэж ашигладаг.

Гадаад дансны ID шаардагдахад тодорхой `AccountAddress` I105 кодлогчийг дуудах.

Данс үүсгэх ба овог нэрийг шийдвэрлэх ажлын урсгалын хувьд [Данс болон овгийн нэрүүд](/mn/cookbook/accounts-and-aliases.md) -оор үргэлжлүүлнэ үү.

Дансны өгөгдлийн загварыг үзэхийн тулд [Данс](/mn/blockchain/accounts.md) гэсэн хэсгийг харна уу.
