# Torii API төгсгөлийн цэгүүд {#torii-endpoints}

Torii нь Iroha 3-ын HTTP, SSE, болон WebSocket гарц юм. Энэ нь блокчэйн бүртгэлийн APIs болон операторын API төгсгөлүүдтэй харилцахад үйлчилдэг.

Одоогийн протоколын дүрэмүүд нь:

- Нэг процессын стандарт бинар формат нь Norito юм
- олон API төгсгөлүүд нь мөн та `Accept: application/json`-ийг илгээхэд JSON-ийг дэмждэг
- метрикүүд Prometheus хэлбэрээр илэрхийлэгдсэн байна

Форматыг дэлгэрэнгүй, агууламжийн тохиролцоо, зохион байгуулалтын далбаа, схемийн криптограф хэш болон Norito RPC удирдамжийн талаар [Norito лавлагаа](/mn/reference/norito.md)-ыг үзнэ үү.

## Ердийн API төгсгөлүүд {#common-endpoints}

| API төгсгөлийн цэг |Формат|Зорилго|
| -------------------------------- | -------------- | ---------------------------------------------------------------- |
| `POST /v1/pipeline/transactions` | Norito         |Гарын үсэг зурсан гүйлгээг илгээх|
| `POST /v1/query`                 | Norito         |Гарын үсэгтэй асуулга илгээх|
| `GET /v1/events/ws`              | WebSocket      |Үйл явдлын урсгалд захиалах|
| `GET /v1/events/sse`             | SSE            | SSE дээрх үйл явдлын урсгалд захиалга өгөх|
| `GET /v1/blocks/stream`          | WebSocket      |Дуусгасан блокыг урсгах|
| `GET /v1/peers`                  | JSON           |сүлжээний хамтрагчийн жагсаалт Torii-аар ил гарсан|
| `GET /livez`                     |Текст|Зөвхөн процессын амьд байдал; энэ нь протоколын бэлэн байдлыг заахгүй|
| `GET /readyz`                    | JSON           |Заавал оффлайн бэлэн мөнгө шалгалтыг оролцуулан, холбоосны бэлэн байдалд бүрэн бэлэн болох|
| `GET /health`                    | JSON           |Нэг л офлайн-налуут тогтмол утгатай бэлэн байдал шалгагч|
| `GET /v1/api/version`            |Текст|Одоогийн блок-гарчгийн хувилбар|
| `GET /status`                    | Norito эсвэл JSON |Өндөр түвшний оношлогооны төлөв байдал; JSON хүсэлтийг тодорхой зааварласан|
| `GET /metrics`                   |Прометей|Prometheus скрейп API цэг|
| `GET /v1/schema`                 | JSON           |Өгөгдлийн загварын схемийн тодорхой агшны өгөгдлийн харагдац нь идэвхжсэн үед зангилаагаар хүргэгддэг|
| `GET /openapi.json`              | JSON           | OpenAPI баримт бичиг идэвхтэй Torii HTTP чиглэлүүдэд|
| `GET /v1/parameters`             | JSON           |Нод параметр цэгийн цаг үеийн өгөгдөл харах|
| `GET /v1/node/capabilities`      | JSON           |Түгээмэл чадвар ба өгөгдлийн загварын мета мэдээлэл|
| `GET /v1/time/now`               | JSON           |Төлөвлөсөн цэгийн цагийн өгөгдлийн орон нутгийн системийн цагийн үзүүлэлт|
| `GET /v1/time/status`            | JSON           |Цагийн синхрончлолын төлөв|

SSE хүсэлтийн хувьд, үндэсний урсгалыг болон бичгийн нөөц хувилбарыг сурталчлаарай:

```http
Accept: text/event-stream, application/json
```

Torii эхлээд хүсэлтийн давхаргад JSON эсвэл Norito төлөөллийг хэлэлцээр хийдэг, дараа нь төрсөн `text/event-stream` хариуг баталгаажуулдаг. Зөвхөн `text/event-stream` илгээх нь `406`-гоор татгалзагддаг; [урсгалын үйл явдлын жор](/mn/cookbook/stream-events.md) бүрэн толгой хэсгийг ашигладаг.

`/openapi.json` нь схемд дүрслэгдсэн маршрутуудын үүсгэсэн гэрээ бөгөөд бүрэн хүчин чадлын туршилтын тооллогын жагсаалт биш юм. Одоогийн баримт бичгээс `/livez` болон `/readyz` орхигдсон ба түүний `/health` тайлбар нь бэлэн байдлын удирдагчийг хоцрогдуулж магадгүй. Амьд баримтаас маршрутын клиентүүдийг үүсгээрэй, гэхдээ амьдрал ба бэлэн байдлыг шууд ажиллаж байгаа нод болон тогтмол гүйцэтгэгчидтэй нь харьцуулан баталгаажуулаарай. Яг гадаргуу нь одоогоор барилгын боломжууд дээрээс хамаарах болно. программ хангамжийн гүйцэтгэлийн орчны тохиргоо. Тэрхүү амьд баримтыг ачааллахын тулд [Torii API консол](/mn/reference/torii-api-console.md) ашиглаж, JSON маршрутуудыг туршиж, curl хүсэлтийг хуулж, одоогийн схемээс клиент код үүсгээрэй.

Бүх каталогтой дэмжигдсэн OpenAPI ажиллагаанд `x-iroha-route-auth` объект агуулагдана. Каталогтой дэмжигдсэн MCP хэрэгслүүд `_meta["iroha/routeAuth"]`-тэй ижил гэрээг ил гаргах болно. Аль аль проекц нь `schemaVersion`, `stableRouteId`, `authentication`, болон `admission`-ыг агуулдаг. Хуулийн хувилбар `1`-ийг яг таг гэрээ гэж үзэж бай: дэмжигдээгүй `schemaVersion`-ийг таамаглахын оронд татгалз; ямар байдлаар баталгаажуулалт эсвэл зөвшөөрлийн шошгуудыг тайлбарлах ёстойг таах хэрэггүй. Шуудангийн мета өгөгдөл нь хүсэлтийн хил хязгаарыг тодорхойлдог; энэ хилээс шаардагдах итгэмжлэлийн орлуулалт биш.

## Taira-ийн амьд маршрутуудыг турших {#try-live-taira-routes}

Олон нийтийн Taira тест сүлжээ нь програмын клиентүүд унших зориулалттай судалгаанд ашигладаг ижил Torii JSON гадаргууг илчилдэг. Эдгээр командууд нь түлхүүр шаарддаггүй:

```bash
TAIRA_ROOT=https://taira.sora.org

curl -fsS -H 'Accept: application/json' "$TAIRA_ROOT/status" \
  | jq '{blocks, txs_approved, txs_rejected, queue_size, peers}'

curl -fsS "$TAIRA_ROOT/openapi.json" \
  | jq -r '.paths | keys[]' \
  | grep '^/v1/' \
  | head -n 20

curl -fsS -H 'Accept: application/json' \
  "$TAIRA_ROOT/v1/node/capabilities" \
  | jq '{abi_version, data_model_version, query: .query.aggregate.supported_resources}'
```

Одоогийн дэлхийн төлөвтэй харьцуулаад нөөцийн уншлагыг туршиж үзнэ үү:

```bash
curl -fsS "$TAIRA_ROOT/v1/domains?limit=5" \
  | jq -r '.items[].id'

curl -fsS "$TAIRA_ROOT/v1/assets/definitions?limit=5" \
  | jq -r '.items[] | [.id, .name, .total_quantity] | @tsv'
```

Хэрэв нийтийн тестнетийн маршрут `502` буцааж, хугацаа дууссан эсвэл дүүрсэн дараалалтай гэж мэдээлсэн бол үүнийг API төгсгөлийн боломжит асуудал гэж авч үзэж, клиентийн кодоо засахын өмнө дараа нь дахин оролдоно уу.

## Апп болон SORA маршрутын бүлгүүд {#app-and-sora-route-families}

## Дансны баталгаажуулалт, харагдац ба explorer курсор {#account-authentication-visibility-and-explorer-cursors}

### Аппликейшний дансны хүсэлтийн протокол {#app-account-request-protocol}

Апп-той нүүр тулах замууд нь ямар ч баталгаажуулах толгойгүй, нэг шууд нэг- түлхүүрийн баримт эсвэл нэг олон гарын үсгийн гэрчийг хүлээн авдаг. Бүрэн баталгаажуулах толгой нь хамгийн ихдээ нэг удаа гарч ирэх ёстой.

Шууд баталгаажуулалт хийхийн тулд бүх дөрвөн толгойг нэг дор илгээнэ үү:

- `X-Iroha-Account`: яг каноник, жижиг үсгийн `0x` дансны хаягийн hex эсвэл идэвхтэй каноник ASCII дансны alias. I105 текстийг HTTP талбарын утга болгон аюулгүй дамжуулах боломжгүй тул тухайн дансны каноник hex бичлэгийг ашиглана.
- `X-Iroha-Signature`: хатуу дүүргэгдсэн base64 гарын үсгийн өгөгдөл.
- `X-Iroha-Timestamp-Ms`: тохируулагдсан хазайлтын цонх доторх миллисекундэд хуваагдсан нэг протокол-стандартын тэмдэггүй арвантын Unix цаг хугацаа.
- `X-Iroha-Nonce`: 1-ийг 256 хүртэл хэвлэх боломжтой ASCII байт (`0x21`-ээс `0x7e` хүртэл), давталт цонх дотор өвөрмөц.

Бүртгэгдсэн ганц товчлууртай хянагч эдгээр яг ижил байтуудыг илэрхийлдэг:

```text
iroha.app.request.network.v1\0 || <genesis-derived network_id[32]> ||
<UPPERCASE_METHOD>\n
<exact request path>\n
<canonical query>\n
<lowercase hex SHA-256 of the raw body>\n
<canonical timestamp_ms>\n
<nonce>
```

нэг протокол-стандарт асуулга боловсруулах нь түүхий асуулгыг `application/x-www-form-urlencoded` (`+` нь зай гэсэн үг), хоёртын хослолуудаа хувьсгалын тэмдэгээр тайлбарладаг, `(key, value)` дагуу эрэмбэлдэг, мөн дахин форм-энкод хийдэг. Протокол хамгийн ихдээ 64 задласан хос болон 64 KiB түүхий асуултын текстийг хүлээн зөвшөөрдөг. Биеийн байтуудыг яг илгээсэн байдлаар криптографийн хэш хий. Тогтсон 32 байтны сети сүлжээний ID болон их үсгээр өгөгдсөн аргын хооронд салгагч оруулаарай.

V1 баталгаажуулагч нь мөн аргачлалын токены хэмжээг 32 байт, хувьссан кодлогдсон хүсэлтийн замыг 64 KiB, шууд дансны таних тэмдгийг 36 KiB байтад хүргэж, дараа нь шинжлэхээс өмнө хязгаарладаг. Дансны тодоорх нэрс нь гурван нэрийн хэсэг ба тэдний салгагчаас бүтэх хатуу бүтэцийн хязгаартай байдаг. Хязгаарыг давсан тохиолдолд гарын үсэг баталгаажуулах эсвэл эх үүсвэрийн хэмжээ хүртээхээс өмнө нэвтрэх эрх дутуу болно.

Олон гарын хяналтын хэрэгсэл нь үүний оронд `X-Iroha-Witness`-ыг хатуу нэмж-бэйс64 дан протоколын стандарт Norito хэлбэрээр илгээх ёстой бөгөөд `X-Iroha-Signature`, `X-Iroha-Timestamp-Ms`, ба `X-Iroha-Nonce`-ыг орхиж болно. `X-Iroha-Account` нь энэ хэлбэрт сонголттой; байвал, энэ нь гэрч `subject_account`-тай тэнцүү байх ёстой. `CanonicalRequestWitnessV1` нь `schema_version`, `subject_account`, `timestamp_ms`, `nonce`, биеийн криптографийн дижестийн утгаар дамжуулан яг сүлжээний хүсэлтийн байтны Iroha `Hash`-ийг агуулдаг боловч шинэлэг байдлын талбартай биш бөгөөд хамгийн ихдээ 64 гишүүний гарын үсэгтэй байж болно. Тус бүрийн гишүүн тухайн нэг payload-ийн гарын үсгийн массивгүй ганц протокол-стандарт Norito кодчиллыг гарын үсэг зурна. Баталгаажсан гишүүд нь тухайн дансны одоогийн олон гарын үсгийн бодлогыг хангах ёстой. Кодчилсон гэрч нь 1 MiB-ээр хязгаарлагдана.

Баталгаажуулах ямар ч толгойг нийлүүлэхгүй байх нь нэргүй хандалтыг сонгоно. Аль нэг хэсэг, холимог, давтагдсан, буруу бүтэцтэй, хуучирсан, эсвэл дахин тоглогдсон нотолгоог нийлүүлэх нь баталгаажуулалтонд бүтэлгүйтэнэ; энэ нь хэзээ ч нэргүй харагдах байдал руу буцдаггүй.

### Операторын хүсэлтийн протокол {#operator-request-protocol}

Оператороор баталгаажуулдаг маршрут дараах дөрвөн, тус бүр нэг удаа оролцох header-ийг шаардана:

- `x-iroha-operator-public-key`: каноник Iroha multihash нийтийн түлхүүр.
- `x-iroha-operator-timestamp-ms`: миллисекундээр илэрхийлсэн каноник, тэмдэггүй аравтын Unix timestamp.
- `x-iroha-operator-nonce`: хэвлэх боломжтой 1–256 ASCII байт; replay цонхны дотор тухайн түлхүүрт давтагдашгүй.
- `x-iroha-operator-signature`: хатуу дүүргэгдсэн base64 гарын үсгийн өгөгдөл.

Header-ийн утгын эхлэл, төгсгөлд хоосон зай байж болохгүй. Операторын түлхүүр дараах байтад гарын үсэг зурна:

```text
iroha.operator.http-request.network.v1\0 || <genesis-derived network_id[32]> ||
<UPPERCASE_METHOD>\n
<exact request path>\n
<canonical query>\n
<lowercase hex SHA-256 of the raw body>\n
<canonical timestamp_ms>\n
<nonce>
```

Зам, query, body, timestamp болон nonce-ийн дүрэм нь апп протоколын каноник дүрэмтэй адил. Түлхүүрийг `[torii.operator_signatures]` мөн зөвшөөрсөн байх ёстой: `allowed_public_keys`-д оруулах, эсвэл зангилааны түлхүүр ашиглаж байвал `allow_node_key`-г илэрхий идэвхжүүлнэ. Replay cache дүүрвэл `503 Service Unavailable` буцаан хаалттай горимоор татгалзана.

Яг хүсэлтийн гарын үсэг үргэлж заавал байна. `[torii.operator_auth].enabled = true` бол ердийн операторын маршрут бүр хүчинтэй `x-iroha-operator-session` мөн шаардана; `require_mtls = true` бол итгэмжлэгдсэн ingress-ээс `x-forwarded-client-cert` нэмж шаардана. Эдгээрийн аль нь ч хүсэлтийн гарын үсгийг орлохгүй.

WebAuthn бүртгүүлэх ба нэвтрэхэд эдгээр дөрвөн JSON API төгсгөл цэгийг ашиглана:

|Арга болон API төгсгөл|Зорилго|
| --------------------------------------------- | ---------------------------------------- |
| `POST /v1/operator/auth/registration/options` | WebAuthn баталгаажуулах бүртгэл эхлэх|
| `POST /v1/operator/auth/registration/verify`  |Мэдээллийг баталгаажуулж хадгалах|
| `POST /v1/operator/auth/login/options`        | WebAuthn-г баталгаажуулахыг эхлүүлэх|
| `POST /v1/operator/auth/login/verify`         |Магадлан баталгаажуулж, сесс үүсгээрэй|

`torii.operator_auth.tokens`-д зориулалтын bootstrap утгууд тохируулна. Итгэмжлэх мэдээлэл үүсээгүй үед анхны бүртгэлийг эхлүүлэхийн тулд нэг утгыг `x-iroha-operator-token` болгон илгээнэ. Энэ token ердийн операторын маршрутад эрх олгохгүй бөгөөд listener-ийн `x-api-token` утгыг энэ урсгалд дахин ашиглахгүй. Нэг итгэмжлэх мэдээлэл үүссэнээс хойш дараагийнхыг бүртгэхэд баталгаажуулсан session шаардлагатай. Нэвтрэлтийг шалгахад буцаасан session token-ийг тухайн сүлжээнд яг тааруулан шинээр үүсгэсэн операторын хүсэлтийн гарын үсэг бүртэй хамт илгээнэ. Итгэмжлэх мэдээллийг `<torii.data_dir>/operator_auth/operator_webauthn.json`-д хадгална.

ISO 20022 маршрут хоёр бие даасан шалгалт хийнэ. Хүсэлт эхлээд операторын энэ зөвшөөрөгдсөн жагсаалт ба гарын үсгийн протоколыг давах ёстой; дараа нь ISO handler ижил түлхүүрийг доор тайлбарласан яг оролцогчийн эсвэл аудитын үүрэгт тохируулсан байхыг шаардана.

### Бүртгэлийн харагдац ба explorer курсор {#ledger-visibility-and-explorer-cursors}

Аппликейшнд зориулсан бүртгэлийн уншилт дээрх сонголттой апп дансны хязгаарыг ашиглана. Гарын үсэггүй хүсэлт зөвхөн нийтэд нээлттэйгээр тохируулсан датаспейсийг харна. Хүчинтэй гарын үсэгтэй хүсэлт нь дуудагчийн одоогийн UAID-д холбосон датаспейс, яг `CanReadRestrictedDataspace { dataspace }` зөвшөөрөлд нэрлэсэн хязгаарлагдмал датаспейс, эсвэл данс `CanReadAllLedgerData`-тай бол бүх маршрутыг нэмж харна.

Дуудагчийн эрх олголтын голтой тохирох маршрутыг ашигла:

|Арга болон API төгсгөл|Нэвтрэлт болон үзэгдэх байдал|
| ------------------------------------- | --------------------------------------------------------------- |
| `POST /v1/transactions/visible/query` |Нэг протоколын стандарт дансны гарын үсэг; дуудах хүний харагдах байдлыг хэрэглэнэ|
| `POST /v1/transactions/query`         |Операторын хүсэлтийн гарын үсэг; дэлхийн операторын харах боломжийг зөвшөөрдөг|
| `GET /v1/triggers/completed`          |Операторын хүсэлт гарын үсэг; локал зангилааны дууссан бичлэгүүдийг уншина|

Ижил үзэгдэх байдалын объект нь данс, домэйн, хөрөнгийн тодорхойлолт, хөрөнгө, NFT, RWA, эзэмшигч, ба Explorer уншлагуудыг шүүхэд хэрэглэнэ. Байхгүй байгаа объект болон дуудлага хийж буй хүнд харагдах чиглэлтээс гадуур байгаа объект зориудаар ялгагдахгүй байна. Гүйцэтгэсэн гүйлгээ болон зааврын түүх нь тухайн гүйлгээнд бүртгэгдсэн санхүүгийн шилжүүлгийн бүх хэсэг харагдах үед л үзүүлэгдэх болно. Холимог өгөгдлийн сангийн гүйлгээ нь Иймээс нэг оролцогчийн санхүүгийн шилжүүлгийн хэсэг ч дуудсан хүний хүрээнээс гадуур байвал нууцлагддаг; алга болсон, хуучирсан эсвэл буруу замналын нөхцөл байдал нь зөвхөн дэлхийн уншигчид л харагддаг.

Дэлхийн зургаан дэмжигдсэн Explorer цуглуулгууд тунгалаг бус ганц протокол стандартад нийцсэн base64url түлхүүрийн курсоруудыг ашигладаг. Анхдагч хуудасны хязгаар нь 25, хамгийн их нь 100 бөгөөд нэг хуудас хамгийн ихдээ 512 нэр дэвшигч түлхүүрийг шалгана. Тус бүрийн курсор нь өөрийн цуглуулга, шүүлтүүрүүд, ганц протоколын стандарт сүүлчийн түлхүүр, дуудсан хүний үзэгдэх замын багцын криптографийн хураангуй утгатай холбогдсон байдаг тул үүнийг өөр асуулт дээр эсвэл дуудсан хүний үзэгдэх байдал өөрчлөгдсөний дараа дахин тоглуулах боломжгүй.

Блок, гүйлгээ, хамгийн сүүлийн гүйлгээ, заавар, болон хамгийн сүүлийн зааврын түүхийн курсорууд нэмэлтээр баталгаажсан хугацааны өгөгдлийн харагдах өндөр болон блокын криптографын хэшийг түгждэг. Хариулт нь `pagination.limit`, `pagination.snapshot_height`, `pagination.snapshot_hash`, `pagination.next_cursor`, болон `pagination.has_more`-ийг илэрхийлнэ. Өөр чиглэл эсвэл шүүлтүүрийн багцад зориулсан курсор, өөрчлөгдсөн харагдах байдалтай криптографийн хураангуй утга, эсвэл зангилаа дахин баталгаажуулах боломжгүй цаг мөчийн өгөгдлийн үзэгдэл хаалттай болох үед амжилтгүй болно. Түүхийн сканнер Torii-ийн асуултын зөвшөөрлийн дотор хэвээр байна, блоклох ажилтан ажиллаж буй үед.

Explorer WebSocket стримүүд шүүлтүүртэй дүгнэлтүүдийг цацаж, блокчейн дэвтийн зөвшөөрөл өөрчлөгдөхөд харагдах байдал шинэчилдэг. Уламжлалт `GET /v1/blocks/stream` маршрут нь өөр байдаг: энэ бүрэн гарын үсэг зурсан блокыг ялгаруулдаг, гарыг барих үед `CanReadAllLedgerData` шаарддаг, мөн энэ зөвшөөрлийг дараа нь цуцалбал хаагддаг. Dataspace-тэй хамааралтай судлаачийн хувьд энгийн урсгалыг битгий ашигла.

## ISO 20022 гүүр {#iso-20022-bridge}

Torii нь програмд чиглэсэн API болон гүүрний програм хангамжийн гүйцэтгэх орчин хүчинтэй болсон үед `/v1/iso20022/*` дор ISO 20022 гүүрийг илчилдэг. Гүүрийг зориудаар тодорхой хязгаарлалттайгаар бүтээдэг: энэ нь ерөнхий зориулалтын ISO 20022 цэвэрлэгээний гарц биш боловч сонгогдсон төлбөрийн мессежийг гарын үсэг зурсан Iroha шилжүүлэг рүү хөрвүүлэх болон тэдний блокчэйн бүртгэлийн төлөвийг хянахад зориулсан дэмжигдсэн хэсэг юм.

Аливаа илгээмжийг хүлээн авахын өмнө бат бөх локал `torii.iso_bridge.store_dir`-ийг тохируулна уу. Тохиргооны талбар нь зөвхөн зангилаа зөвхөн унших зориулалттай эсвэл оношлогооны зориулалтаар эхлэх боломжийг олгодог тул сонголттой байдаг: Бүртгэгдсэн ISO бүртгэл бүр каталогийг шаардаж, хадгалалт байхгүй эсвэл дахин тоглуулах-цогцослосон эсвэл баялаг-бичлэгийн бичих ажиллагаа амжилтгүй болсон үед дахин оролдож болох `503 Service Unavailable` буцаана.

|Арга болон API төгсгөл|Зорилго|
| -------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `POST /v1/iso20022/pacs008`                  | FI-аас FI хүртэлх хэрэглэгчийн зээлийн шилжүүлгийг илгээн, тохирох Iroha хөрөнгийн шилжүүлгийг үүсгээрэй|
| `POST /v1/iso20022/pacs009`                  | PvP эсвэл үнэт цаастай холбоотой бэлэн мөнгөний санхүүжилтэд ашиглагдсан FI-с FI кредит шилжүүлгийг илгээх|
| `POST /v1/iso20022/pacs002`                  |Гэрээний талын эзэмшлийн төлбөрийн төлөвлөлийн тайланг илгээх; санхүүгийн гүйлгээний гүйцэтгэлийг баталгаажуулах баримт шаардлагатай|
| `POST /v1/iso20022/pacs004`                  |Төстэй талын өмчлөлийн төлбөрийн буцаалтыг илгээх|

| `POST /v1/iso20022/sese024`                  |Нөгөө талын өмчлөлийн үнэт цаасны санхүүгийн гүйлгээний төлбөр тооцооны статусын мэдээг илгээх|

| `GET /v1/iso20022/messages/{msg_id}`         |Нэг мессежийн хувьд ганцхан протокол-стандарт гүүрний бүртгэлийг уншина уу|
| `GET /v1/iso20022/audit/messages`            |Нууцлалын эвдэгдээгүй мессежийн аудитын техникийн тодорхойлолтыг уншина уу|

`pacs.008` илгээмжүүд нь зурвасын ID, банкуудын хоорондын санхүүгийн гүйлгээний төлбөрийн дүн, валют, санхүүгийн гүйлгээний төлбөрийн огноо, өр төлбөртөй болон зээлдэгч IBANs, мөн өр төлбөртөй болон зээлдэгч BICs мэдээллийг заавал өгөх ёстой. Сэргээлийн өгөгдлийг конфигуруулбал, шугам нь програм хангамжийн боловсруулалтын ажлын урсгалд орж ирэхээс өмнө BIC, IBAN болон ISO 4217 валютын хилжилтийг хянах болно.

`pacs.009` илгээмжүүдэд бизнесийн зурвасын ID, зурвас тодорхойлолтын ID, үүсгэсэн цаг, банк хоорондын санхүүгийн гүйлгээний шийдвэрлэх дүн, валютыг заавал оруулах ёстой, санхүүгийн гүйлгээний тооцооны огноо, заавар өгсөн ба заавар авсан агент BICs, мөн өрийн болон өрийн үйлчилгээний тал IBANs. Хэрэв мессеж нь `Purp` агуулах юм бол, одоогоор гүүр зөвхөн үнэт цаасны зориулалтын санхүүжилтийг хүлээн авдаг: `Purp=SECU`.

`pacs.008` ба `pacs.009` илгээх API төгсгөлүүд нь XML ISO өгөгдлийн сав эсвэл гүүрний туршилтуудад ашигладаг шулуун талбарыг хүлээн авдаг. Сонголттой `SplmtryData` талбарууд нь зорилтот Iroha блокчэйн бүртгэл, эх сурвалж болон зорилтот дансны ID эсвэл хаяг, болон хөрөнгийн тодорхойлолтын ID-г тогтоож болно. Хариу нь `202 Accepted` бөгөөд үүнд `message_id`, `transaction_hash`, `status`, `pacs002_code`, ба шийдэгдсэн бүртгэл/данс/хөрөнгийн контекст орно.

### Оролцогчийн зөвшөөрөл ба амьдралын мөчлөгийн эзэмшил {#participant-authorization-and-lifecycle-ownership}

Бүх идэвхжсэн гүүрэнд оролцогчдын каталог байдаг. Тус бүрлэлийн бүртгэлд давтагдашгүй оролцогчийн ID, нэг буюу хэд хэдэн операторын олон нийтийн түлхүүр, нэг буюу хэд хэдэн санхүүгийн танигч, зөвшөөрөгдсөн профайлын багц, мөн `originator`, `counterparty`, эсвэл аль аль үүрэгт байрлал агуулагдана. Операторын түлхүүрүүд болон санхүүгийн танигчид нэгээс олон оролцогчтой байх боломжгүй. `audit_admin_keys`-ыг тусад нь тохируул; аудит-админ түлхүүр нь мөн оролцогчийн өөрчлөлтийн түлхүүр байж болохгүй.

Бүх ISO чиглэлд шинэ операторын гарын үсэг шаардлагатай. Анхны `pacs.008`, `pacs.009`, `sese.023`, эсвэл `colr.012` илгээгдсэн тохиолдолд баталгаажсан оператор нь өргөдлийн толгойн `From` санхүүгийн танилттай тодорхойлогдсон оролцогчдод хамаарах ёстой. `To` таних тэмдэг нь `counterparty` дүрэмтэй тохируулагдсан оролцогч дээр шийдэгдэх ёстой бөгөөд сонгосон профайл аль аль талд нь зөвшөөрөгдөх ёстой. Өндөр тэсвэртэй хүлээн авалтын тэмдэглэгээ нь эх үүсвэр, харилцагч тал, хүлээн авч буй оролцогч ба операторын түлхүүр, мөн анхны профайл ба оруулсан гарын үсгийн бодлогыг тэмдэглэдэг.

Амьдралын мөчлөгийн зөвшөөрлийг дуудсан этгээд сонгосон утгаас биш, тухайн өөрчлөгддөггүй бичиглэлээс гарган авдаг:

|Амьдралын мөчлөгийн мессеж|Шаардлагатай оролцогч|
| ---------------------------------------------- | -------------------------------------------------- |
| `pacs.002`, `pacs.004`, `sese.024`, `sese.025` |Анхны харилцагч `counterparty` үүрэгтэй|
| `camt.056`                                     | `originator` үүрэгтэй анхдагч үүсгэгч|

Эх хувийн профайл болон гарын үсгийн бодлого бүх амьдралын мөчлөгт наалттай хэвээр байна, иймд дуудах хүн шинэчлэлтэнд сул профайлыг сонгож чадахгүй. Төлөөлж буй `pacs.002` код нь санхүүгийн гүйлгээний төлбөрийг шийдвэрлэх (`ACSC`, `ACCP`, `SETT`, эсвэл `SETTLED`) зөвхөн Torii гүйлгээний нотолгоог эцэслэн баталгаажуулсаны дараа анхны бүртгэлийг шийдвэрлэгдсэн болгон өөрчилдөг.

Анхдагч аливаа тал өөрийн мэдээний бичлэгийг болон үүсгэсэн илгээмжийн баримтуудыг уншиж болно. Аудитын API төгсгөлийн цэг зөвхөн баталгаажсан оролцогч нь эхлэл эсвэл эсрэг талын талбар байх бичлэгүүдийг буцаана. Тусад нь тохируулсан аудитын админ дэлхийн унших-зуучлах аудитын үзэмжийг авдаг бөгөөд мессеж илгээх эсвэл өөрчлөх боломжгүй. Танихгүй оролцогчид болон холбоогүй мессежийн тодорхойлогчууд илчлэхгүй.

### Тогтвортой replay таних мэдээлэл ба гарын үсэгтэй outbox баримтууд {#durable-replay-identity-and-signed-outbox-documents}

Дахин тоглуулах бат бөх устгах тэмдэгүүд нь хатуу нэвтрэх хязгаар юм. Torii уншигдаж болохгүй, хэмжээ ихтэй, буруу бүтэцтэй, нэрээ буруу тавьсан, зөрчилтэй, эсвэл тодорхойгүй нийцэхгүй бат бөх устгах тэмдэгийн улмаас эхлэлийг зогсоодог. Мөн тодорхой зөрчилтэй схемийн хувилбар бүхий баялаг бичлэг, одоогийн тохиргоонд байхгүй оролцогч, профайл, эсвэл гарын үсгийн бодлого, эсвэл байхгүй эсвэл таарахгүй амьд удаан устгах тэмдгийн тохиолдолд зогсоодог.

Бусад баялаг бүртгэлийн гэмтлийг өөр аргаар боловсруулдаг: уншигдахгүй эсвэл хэт том файлууд, хүчингүй JSON, хүчингүй одоогийн схемийн бүртгэлүүд, нэг протоколын стандартад нийцээгүй файлын нэрс, маргаантай дахин тоглуулах танигчуудыг тэмдэглэж эсвэл үл тоомсорлодог. Уншигдахгүй эсвэл хүчин төгөлдөр бус одоогийн хувилбарын аудитын индекс хадгалагдсан бичлэгүүдээс дахин үүсгэнэ; зөвхөн илт зөрчилтэй аудитын индексийн хувилбар нь эхлүүлэх процессыг зогсооно. Эхлэх үед гарсан бүртгэлийн мэдээллийг хянаж, буцаан үүсгэсэн аудитын техникийн жагсаалтыг тааруул; бүх эвдэрсэн баялаг бичлэгийн файлууд нь нодны үйлчилгээг зогсоодог гэж таамаглах хэрэггүй.

Бүх хадгалагдсан баялаг бичлэг нь өөрчлөгдөшгүй оролцогчийн гарал үүсэлтийг хадгалдаг. Тусдаа бат бөх устгах тэмдэг нь баялаг бичлэгийн дэлгэрэнгүйг арилгасны дараа ч гэсэн мессежийн ID, ачааны криптографын хэш, бизнес мессежийн ID болон UETR-г бүрэн давхардлыг арилгахад TTL хадгалдаг.

Torii амьдралын мөчлөгийн мессежийг гарын үсэг зурж эсвэл боловсруулахын өмнө дахин тоглуулах нэвтрэлтийг хэвээр хадгалдаг. Энэ нь хүчинтэй хугацаа дуусаагүй дахин тоглуулах таних тэмдэгийг хэзээ ч хасдаггүй. Хэрэв тохируулах хүчин чадал нь бүрэн хамгаалагдсан бичлэгүүд эсвэл хүчинтэй хугацаа нь дуусаагүй дахин тоглуулах таних тэмдэглэгээгээр дүүрсэн бол илгээсэн зүйлс амьдралын мөчлөг эсвэл бүртгэлийн төлөвийг өөрчлөхгүйгээр дахин оролдох боломжтой `503 Service Unavailable` авдаг.

Үндсэн бүрдүүлсэн `pacs.002`, `pacs.004`, `camt.029`, `sese.024`, эсвэл `sese.025` баримт бичиг нь эдгээр хариулах гарчгууруудтайгаар `application/xml` болгон буцаагдана:

|Толгой|Өгүүлэмж|
| ------------------------------ | ----------------------------------------------------- |
| `X-Iroha-Iso-Signature-Domain` |Үргэлж `iroha.iso20022.outbound.v2`|
| `X-Iroha-Iso-Signer`           |тохируулагдсан гүүрний криптографийн гарын үсэг зурагчид зориулсан нэг протокол-стандарт олон нийтийн түлхүүр|
| `X-Iroha-Iso-Signature`        |Домайн тусгаарлагдсан XML байтын Base64 гарын үсэг|

Нэг нөгөө бичлэгийн дараа гарын үсгийг UTF-8 байт дараалал `iroha.iso20022.outbound.v2`, нэг тэг байт, болон яг хариу мөрийн биелэл дээр шалгана уу. Шалгахын өмнө XML-ийг дахин форматлах эсвэл хэвийн болгох хэрэггүй.

### Парсер ба зураглалын нэмэлт дэмжлэг {#additional-parser-and-mapping-support}

IVM ISO туслах нь мөн дараах мессежийн гэр бүлүүдийг өгөгдлийн савны баталгаажуулалт, санхүүгийн гүйлгээний тооцооллын зураглал эсвэл доод түвшний нийцлийг шалгах зориулалтаар баталгаажуулж, бодит болгодог. Эдгээр нь бие даасан Torii чиглэлүүдтэй биш.

|Гэр бүлд мессеж илгээх|Одоогийн дэмжлэг|
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `head.001`                         |ISO өгөгдлийн контейнеруудын бизнесийн програмын гарчиг шалгалт, үүнд `BizMsgIdr`, `MsgDefIdr`, үүсгэгдсэн цаг, мөн сонголттой илгээгч/хүлээн авагч BIC талбарууд орно|
| `pacs.007`, `pacs.028`, `pacs.029` |Төлбөр буцаалт, төлөвийн лавлагаа, болон мөрдлөгийн шийдвэр/төлвийн задлал|
| `pain.001`, `pain.002`             |Харилцагчийн төлбөр эхлүүлэх ба төлбөрийн төлөвлөгөөний тайлангийн баталгаажуулалт|
| `camt.052`, `camt.053`, `camt.054` |Дансны тайлан, мэдэгдэл, баталгаажуулалт|

## Kaigi сессүүд {#kaigi-sessions}

Kaigi нь SORA Nexus дээр төлбөртэй, бодит цагийн аудио/видео өрөөнүүдийг санал болгодог. Хэрэв програм нь бүх хуралдааны төлөвийг гадаадад хадгалахгүйгээр блокчэйн бүртгэлийн сессийг үүсгэх, бүртгэлийг өөрчлөх, дамжуулах техникийн үзүүлэлтүүдийг гаргах, криптографтай дохио дамжуулах, хэрэглээний хэмжилт хийх шаардлагатай бол үүнийг ашиглаарай.

Блокчэйн бүртгэлийн амьдралын мөчлөгтэй харилцах явц нь:

- `CreateKaigi`: домайн дор дуудлага үүсгэн түүний бодлого, хуваарь, мета өгөгдөл болон сонголттой дамжуулах техникийн manifest-г хадгалах.
- `JoinKaigi`: дуудлагын жагсаалтыг шинэчлэх. `zk-roster-v1` горимд олон нийтийн дуудлагын харагдац нь оролцогчийн дансны ID-ийн оронд криптографийн амлалт утга болон nullifier тоог харуулдаг.
- `LeaveKaigi`: Тунгалаг дуудлагаас оролцогчийг хасах. Хувийн горимд гарах нь анхны хувилбарын протоколд гинжнээс гадуурх болно.
- `RecordKaigiUsage`: хэмжигдсэн хугацаа ба гүйлгээний гүйцэтгэлийн зардлын нийлбэрийг нэмэх.
- `EndKaigi`: сессийг хааж, эцсийн цагийн тэмдгийг бичнэ үү.

Torii дараах апп-руу чиглэсэн уншлагуудыг ил болгодог:

|Зам|Нэвтрэлт баталгаажуулалт|Зорилго|
| ----------------------------------- | --------------------------------------- | ------------------------------------------ |
| `/v1/kaigi/calls/{call_id}`         |нийтийн|Одоогийн дуудлагын бичлэг|
| `/v1/kaigi/calls/{call_id}/signals` |нэг протокол-стандарт нарийн сүлжээний дансны хүсэлт|хуудастай эцсийн процесс бүхий дохионы мета өгөгдөл|
| `/v1/kaigi/calls/{call_id}/events`  |нэг протокол-стандарт нарийн сүлжээний дансны хүсэлт|дуудлагын амьдралын мөчлөгийн урсгал|
| `/v1/kaigi/relays`                  |зөвшөөрөгдсөн операторын хүсэлт|реле тойм|
| `/v1/kaigi/relays/{relay_id}`       |зөвшөөрөгдсөн операторын хүсэлт|нэг релейгийн бүртгэл ба эрүүл мэндийн дэлгэрэнгүй мэдээлэл|
| `/v1/kaigi/relays/health`           |зөвшөөрөгдсөн операторын хүсэлт|бүхэл сэлгэгчийн эрүүл мэнд|
| `/v1/kaigi/relays/events`           |нэг протокол-стандарт нарийн сүлжээний дансны хүсэлт|дамжуулах бүртгэл ба эрүүл мэндийн үйл явдлын урсгал|

Програм API идэвхжсэн байх ёстой. Релейн хураангуй ба эрүүл мэндийн замууд нь зөвхөн уншигддаг боловч операторын гадаргуу юм; гарын үсэггүй `curl` хүсэлт нь хүчин төгөлдөр бус боломжийн сорил. Сессийн төлөв нь мөн `KaigiRosterSummary`, `KaigiRelayManifestUpdated`, `KaigiRelayHealthUpdated`, болон `KaigiUsageSummary` зэрэг Kaigi домайн арга хэмжээгээр тусгагддаг.

### CLI шуурхай туршилт {#cli-smoke-test}

Хэрэв та Torii API төгсгөл Kaigi гүйлгээг хүлээн авч байгаа эсэхийг баталгаажуулахыг хүсвэл UI-тэй холбогдохоосоо өмнө `iroha app kaigi` CLI-оор эхлээрэй. Quickstart командыг тохируулах API төгсгөлд өрөө үүсгэж, дуудах таних тэмдэг болон нэгдэх метадатаг хэвлэнэ:

```bash
iroha app kaigi quickstart \
  --domain kaigi.universal \
  --summary-out kaigi-summary.json
```

Сценартаар процесс бүхий урсгалд өрөөний амьдралын мөчийг тодорхойгоор удирдана:

```bash
iroha app kaigi create \
  --domain kaigi.universal \
  --call-name daily \
  --host <i105-account-id> \
  --privacy-mode transparent \
  --room-policy authenticated

iroha app kaigi join \
  --domain kaigi.universal \
  --call-name daily \
  --participant <i105-account-id>

iroha app kaigi leave \
  --domain kaigi.universal \
  --call-name daily \
  --participant <i105-account-id>

iroha app kaigi record-usage \
  --domain kaigi.universal \
  --call-name daily \
  --duration-ms 120000 \
  --billed-gas 1500

iroha app kaigi end --domain kaigi.universal --call-name daily
```

Тасалгаа нь үзэгчийн тасалбаргүйгээр дамжуулах боломжтой өрөөний хувьд `--room-policy public`-ыг ашиглана уу, эсвэл гарц нь үзэгчийн баталгаажуулалт шаарддаг бол `--room-policy authenticated`-ийг ашиглана уу. Зөвхөн дараа нь `--privacy-mode zk-roster-v1`-ийг ашиглана уу сүлжээ нь Kaigi бүртгэл болон ашиглалтын баталгаажуулах түлхүүрүүдийг тохируулсан байна; үгүй бол нэгдэлт, гарэлт, болон хувийн ашиглалтын бүртгэлүүд тодорхой баталгаажуулалтын үед амжилтгүй болно.

### JavaScript интеграц {#javascript-integration}

Өнөөгийн [Iroha JavaScript демо](https://github.com/soramitsu/iroha-demo-javascript) ил тод, баталгаажсан нэгээс-нэг уулзалтын профайлыг хэрэгжүүлдэг. Энэ нь протоколыг ил болгодоггүй `zk-roster-v1` баримт үзүүлэх урсгал. Үүний рендерер үүсгэдэг WebRTC санал болон хариулт, харин давуу эрхтэй гүүр нь орон нутгийн ашигладаг [`@iroha/iroha-js`](https://github.com/hyperledger-iroha/iroha/tree/0010c5a70039eac101a4846499ba9ceaf43eb65c/javascript/iroha_js) санал авах, гарын үсэг зурах, илгээх, ба эцсийн байдлыг хүлээх Kaigi үйлдвэрлэлүүд.

Яг замын баталгаажуулалт, урилга оруулах хэлбэр, гүүрний хил болон одоогийн туршилтын командыг харахын тулд [Эмбед Kaigi-ийг JavaScript апп-д оруулах](/mn/guide/tutorials/kaigi.md)-ийг үзнэ үү.

## Төлөв ба хэмжүүр {#status-and-metrics}

Төлөв ба хэмжигдэхүүнүүд API гэсэн төгсгөлийн цэгүүд нь самбаруудад холбох анхны зүйлс юм:

- `/status` дээд түвшний сүлжээний түнш, блок, дараалал, санал нэгтэй байдлын талбаруудыг ил болгодог
- `/metrics` нь Prometheus-ийн тооллогч, хэмжүүлэгч, хистограммыг илрүүлж байна

Nexus идэвхжсэн зангилаанууд дээр, төлөв байдлын гаралт нь гүйцэтгэх эгнээ болон өгөгдлийн орон зайг ойлгосон хэсгүүдийг бас агуулна. `nexus.enabled = false` байх үед эдгээр хэсгүүдийг орхичихно.

## JSON ба Norito {#json-vs-norito}

Олон операторын API төгсгөлүүд анхдагчаар Norito буцаадаг. API төгсгөл JSON-ийг дэмждэг тохиолдолд дараахыг илгээнэ үү:

```http
Accept: application/json
```

Энэ нь ялангуяа дараах зүйлд ашигтай:

- `/v1/sumeragi/status`
- `/v1/sumeragi/qc`

Хэзээ нэгэн API төгсгөл Norito-ийг шууд хүлээн авдаг эсвэл буцаадаг бол, агуулгын төрөл эсвэл давамгай `Accept` утгаар `application/x-norito` ашигла. Тээврийн дэлгэрэнгүй мэдээллийг [Norito](/mn/reference/norito.md#torii-and-norito-rpc)-оос үзнэ үү.

## Телеметрийн профайлууд {#telemetry-profiles}

API төгсгөлийн цэгийн харагдах байдал нь зангины `telemetry.profile` тохиргооноос хамаарна. Одоогийн тохиргоо таван профайл түвшинг ил болгож байна:

|Профайл| `/status` | `/metrics` |Хөгжүүлэгчийн маршрутууд|
| ----------- | --------- | ---------- | ---------------- |
| `disabled`  |үгүй|үгүй|үгүй|
| `operator`  |тийм|үгүй|үгүй|
| `extended`  |тийм|тийм|үгүй|
| `developer` |тийм|үгүй|тийм|
| `full`      |тийм|тийм|тийм|

## CLI товчлолууд {#cli-shortcuts}

`iroha` CLI аль хэдийн эдгээр API олон төгсгөлүүдийг ороож байна:

```bash
export IROHA_OPERATOR_KEY_FILE=/run/secrets/iroha/operator.key

iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  --output-format text ops sumeragi status
iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  --output-format text ops sumeragi diagnostics
iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  ops sumeragi params
iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  --output-format text ops sumeragi evidence count
```
