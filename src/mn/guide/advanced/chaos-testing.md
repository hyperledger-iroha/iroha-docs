# Изанамитэй Хаос Туршилт {#chaos-testing-with-izanami}

Изанами нь дээд түвшний Iroha ажлын орчин дахь хэлцийн сүлжээний зохицуулагч юм. Энэ нь түр ашиглах зориулалттай локал Iroha бүлгийг эхлүүлж, тохируулах боломжтой ачааллыг илгээдэг бөгөөд операторууд сүлжээ контролдсон алдааны үед хэрхэн хөгжсөнийг шалгахын тулд тодорхой сүлжээний хамтрагчдад алдаа нэмж өгдөг.

Izanami-г урьдчилсан үйлдвэрлэлийн тэсвэр хатуужлын шалгалт, regression-ыг дахин сэргээх, болон consensus тохируулга хийхэд ашигла. Үүнийг үйлдвэрлэлийн сүлжээнд чиглүүлэх хэрэггүй: уг хэрэгсэл нь зориулсан юм сүлжээний хамтрагчдыг өөрийн болгох, үүнд сүлжээний хамтрагчдын дахин эхлүүлэлт, хадгалах сангийн арилгалт, түр итгэмжилсэн хамтрагчийн хэсгүүд, орон нутгийн CPU эсвэл дискний даралт орно.

## Өмнөх шаардлагууд {#prerequisites}

Энэ баримтжуулалтын хадгалах сангаас биш [Iroha эх сурвалжийн агуулах](https://github.com/hyperledger-iroha/iroha) -аас Izanami-г ажиллуулна уу:

```bash
git clone https://github.com/hyperledger-iroha/iroha.git
cd iroha
cargo build -p izanami
```

Сүлжээнд холбогдсон сүлжээний хэрэглэгчдийг үүсгэж, удирдахад хоёртын файл тодорхой зөвшөөрөгдсөн байх ёстой. Бүх TUI биш ажиллах үед `--allow-net`-ыг дамжуулах, эсвэл TUI-т `allow_net`-ийг идэвхжүүлнэ үү.

```bash
cargo run -p izanami -- --allow-net --peers 4 --faulty 1 --duration 120s
```

Интерактив ажиллуулах тохиргооны хувьд:

```bash
cargo run -p izanami -- --tui --allow-net
```

Изанами хэрэглэгчийн тохиргооны директорт TUI болон CLI тохиргоонуудыг хадгалдаг. Эхний хувилбарын файлд V1 зохион байгуулалтын нэг тодорхой байт байдаг; урьдчилсан хувилбар эсвэл хувилбаргүй тохиргоонуудыг татгалзан, шилжүүлэхийн оронд дахин үүсгэнэ үү. Одоогийн профайлыг дахин ашиглахаас өмнө дэлгэцэнд гарсан тохиргоог хянаарай.

## Үндсэн ажиллуулах {#baseline-run}

Хүнд гэмтлийг нэмэхийн өмнө нэг дахин бүтээж болох үндсэн талыг эхлүүлээрэй:

```bash
cargo run -p izanami -- \
  --allow-net \
  --peers 4 \
  --faulty 1 \
  --duration 5m \
  --target-blocks 100 \
  --progress-interval 15s \
  --progress-timeout 120s \
  --latency-p95-threshold 2s \
  --tps 15 \
  --max-inflight 32 \
  --submitters 1 \
  --seed 42
```

Энэ гүйлт зөвхөн кластер хүссэн блокын зорилтод хүрсэн, цагийн хязгаарт дотор ахиц дэвшил гаргасаар байгаа, мөн сонгосон p95 блокын интервалын хязгаараас доош байгаа тохиолдолд амжилттай болно.

Команд, үр, Iroha протоколын төгсгөл, сүлжээний хамтрагчдын тоо, алдаатай хамтрагчдын тоо, ажлын ачааллын профайл, зорилт TPS, болон хожуугийн хязгаартыг тэмдэглэлтэй хамт бичиж ав. Эдгээр утгуудгүйгээр, өөр оператор ижил алдааны хэв маягийг дахин тоглуулах боломжгүй.

## Ажлын ачааллын профайл {#workload-profiles}

Изанамид хоёр ачааллын профайл байдаг:

|Профайл|Үүнийг ашиглаарай|Тэмдэглэлүүд|
| -------- | -------------------------------------------------- | -------------------------------------- |
| `stable` |Урт хугацааны туршийн ажиллуулалт ба давтан гүйцэтгэлийн шалгалт|Гүйцэтгэл аюулгүй жоруудыг дэмждэг|
| `chaos`  |Амжилтгүй замын хамрах хүрээ|Урьдчилан зориудаар буруу жоруудыг агуулна|

Эхлээд тогтвортой профайлыг ашиглана уу:

```bash
cargo run -p izanami -- --allow-net --workload-profile stable --seed 42
```

Суурь ойлгогдсон үед замбараагүй байдлын профайл руу шилжнэ үү:

```bash
cargo run -p izanami -- --allow-net --workload-profile chaos --seed 42
```

Гэрээний байрлуулах жорууд нь тодорхой зөвшөөрөгдсөн тохиолдолыг ороогүй бол тогтвортой ажиллуулалтад идэвхгүй байна:

```bash
cargo run -p izanami -- \
  --allow-net \
  --workload-profile stable \
  --allow-contract-deploy-in-stable
```

Дээд түвшний ажлын орчноос оруулсан SORA Nexus анхдагч утгуудыг ашиглах үед `--nexus`-ыг ашигла.

## Гэрлийн хяналт {#fault-controls}

Хэрэв `--faulty` нь тэгээс их бол хамгийн багадаа нэг алдааны нөхцөл идэвхжсэн байх ёстой. Алдааны шилжүүлэгчүүд анхдагчаар идэвхжсэн байдаг бөгөөд boolean флагуудыг `=false`-ээр идэвхгүй болгох боломжтой.

|Гэмтэл| CLI туг|Юу дасгалжуулдаг вэ|
| ------------------------ | ------------------------------------------ | ------------------------------------------ |
|Унаж дахин эхлүүлэх| `--fault-enable-crash-restart`             |сүлжээний түнш процессийн алдагдал ба сэргээх|
|Хадгалах санг арчиж, дахин асаана уу| `--fault-enable-wipe-storage`              |Орон нутгийн төлөв алдагдсанаас сэргэлт|
|Буруу гүйлгээний спам| `--fault-enable-spam-invalid-transactions` |Оролт болон татгалзалтын замууд|
|Сүлжээний хойшилт| `--fault-enable-network-latency`           |Аажим цуурхал ба хожуу зөвшилцөлтийн мэдэгдэл|
|Сүлжээний салалт| `--fault-enable-network-partition`         | Түр зуурын итгэж болох түншээс тусгаарлалт |
|CPU стресс| `--fault-enable-cpu-stress`                |Орон нутгийн баталгаажуулалт ба хуваарийн дарамт|
|Дискний дүүргэлт| `--fault-enable-disk-saturation`           |Орон нутгийн хадгалах ачаалал|

Зөвхөн сүлжээний тасалдлын үед ажиллуулах:

```bash
cargo run -p izanami -- \
  --allow-net \
  --peers 4 \
  --faulty 1 \
  --duration 5m \
  --fault-window-start 60s \
  --fault-window-end 180s \
  --tps 15 \
  --submitters 1 \
  --max-inflight 32 \
  --fault-enable-crash-restart=false \
  --fault-enable-wipe-storage=false \
  --fault-enable-spam-invalid-transactions=false \
  --fault-enable-network-latency=false \
  --fault-enable-network-partition=true \
  --fault-enable-cpu-stress=false \
  --fault-enable-disk-saturation=false \
  --seed 42
```

Тарьсан алдаанаас өмнө болон дараа хяналттай тогтвортой үеийг хадгалахын тулд `--fault-window-start` болон `--fault-window-end`-ийг хэрэглэ. Энэ нь эхлүүлэх үеийн дуу чимээг алдааны нөлөөнөөс ялгаж салгахыг хялбар болгодог.

## Өнцөг байдалын хэлбэрүүд {#scenario-shapes}

Өмнөх Izanami каталог нь түгээмэл блокчэйн харилцаа-алдаа хэлбэрүүдийг CLI профайлд холбодог. Та үүнийг ижил далбаануудтайгаар загварчилж болно:

|Өнцөл байдал|Ерөнхий хэв маяг|
| --------------------- | ------------------------------------------------------------------------------------------------------------------------ |
|Тодорхой зорилтот ачаа| `--faulty 0`, өндөр `--tps`, нэг илгээгч, өндөр `--max-inflight`|
|Түр зуурын алдаа|Зөвхөн хязгаарлагдмал алдааны цонхны дотор осол/дахин ачаалалтыг идэвхжүүлэх|
|Зогсолт ба сэргэлт|Нас барсан/дахин ачаалагдах боломжтой алдаатай хорооны тоотой том бүлгийг ашиглана уу|
|Удирдагчийн тусгаарлалт|Зөвхөн сүлжээний тасалдлын алдаатай ганцхан сүлжээний хамтрагчийг яг ашигла; Izanami нь Sumeragi удирдагчийн телеметрийг дагана|

Нэг удаад нэг хувьсагчийг тогтвортой байлга. Хэрэв та нэгэндээ сүлжээний хамтрагчийн тоо, ажлын ачааллын профайл, алдааны цонх, ба TPS-г өөрчилбөл үр дүнг тайлбарлахад хэцүү болно.

## Юу үзэх вэ {#what-to-watch}

Гүйж байх үед гүйцэтгэлийг баталгаажуулахад ашигладаг ижил дохиог ажигла.

- бүх ажиллаж буй сүлжээний ижил тавцангийн оролцогчуудын блок өндрийн прогресс
- илгээсэн, хүлээн авсан, татгалзсан, хугацаа хэтэрсэн гүйлгээ
- оч эгнээний гүн, оч эгнээний дүүргэлт, болон API төгсгөлийн даралт
- өөрчлөлтүүдийг харах, сэргээх замууд, алга болсон блокууд, алга болсон кворумын гэрчилгээнүүд
- Гарын үсэг зурсан RS16 боломжуудын нөөц, хүлээгдэж буй хуралдаанууд, хоцорсон тохиролцооны урсгал
- CPU, сүлжээний хамтрагчийг ажиллуулж байгаа хост дээрх санах ой, диск, болон сүлжээний дүүргэлт

Баталгаажуулалтын хүлээлгийн анализ хийхийн тулд гол давталтын алдааны бүртгэлийг идэвхжүүлнэ үү:

```bash
RUST_LOG=iroha_core::sumeragi::main_loop=debug \
  cargo run -p izanami -- --allow-net --seed 42
```

Блок бүр `stateless_ms`, `execution_ms`, болон `total_ms` -тойгоор `block validation timings` -г гаргах ёстой. Эдгээр хугацааг p95 блокын интервалууд, view-change тоолуурууд, болон ээлж даралтын өмнөхтэй харьцуулж, зөвшилцөлт цаг хэмжигчийг солихоос өмнө.

## Үр дүнг тайлбарлах {#interpreting-results}

Бүх сонгосон сүлжээний хамтрагчид блокыг эцэслэхийг үргэлжлүүлж байвал, нөөц хуримтлалдаа хязгааргүй өсөхгүй байвал, тохируулагдсан цонх дууссаны дараа гэмтэл нь шинэ сэргээн засварлах үйл ажиллагааг зогсоодог бол гүйлтийг эрүүл гэж үзнэ.

Дараах тохиолдолд гүйхийг бүтэлгүйтэл гэж үзнэ:

- төлөвлөсөн прогресс `--progress-timeout`-аас илүү удаан саатна
- сүлжээний түншийн өндөрүүд ялгарч, дахин нийлдэггүй
- p95 хүлээлтийн хугацаа `--latency-p95-threshold`-аас давж байна
- алдааны цонх хаагдсаны дараа эцсийн байдлаар дараалал уртсдаг
- татгалзсан эсвэл хугацаа дууссан гүйлгээ нь сонгосон ажлын ачааллаар тайлбарлагдаагүй байна
- сүлжээний хөршийг дахин ачаалах, хадгалах зайг ариутгах, эсвэл хуваалтын сэргэлт нь гараар цэвэрлэх шаардлагатай

Ялагдлын дараа адил үржүүлгийн үрээр дахин ажиллуулж, нэг төрлийн алдааг багасгана. Энэ нь ажлын ачаалал ба цаг хугацааг давтагдахуйц байлгах боловч алдааны талбайг нарийсгана.
