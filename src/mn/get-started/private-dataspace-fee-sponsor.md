# Хувийн өгөгдлийн орон зайн шимтгэлийг ивээн тэтгэх {#sponsor-fees-for-a-private-data-space}

SORA Nexus шимтгэл ивээн тэтгэх хөтөлбөр нь хувийн өгөгдлийн орон зайд чиглүүлсэн шаардлага хангасан гүйлгээний глобал гүйцэтгэлийн шимтгэлийг төлж болно. Хэрэглэгч бүтэн гүйлгээнд гарын үсэг зурсан хэвээр байна. Түүний төрөлжсөн `FeePaymentIntent` нь яг ивээн тэтгэх хөтөлбөр, өөрчлөгдөхгүй хувилбар, шаардлагатай үед гүйцэтгэлийн зардлын хязгаар болон авах төлбөрийн дээд хэмжээг сонгоно.

Өгөгдлийн орон зайн каталогийн бичлэг бие даан гарын үсэгтэй үндэс үүсгэхгүй. Бие даасан өгөгдлийн орон зайн үндэс өөрийн батлагдсан шимтгэлийн валют, бодлоготой; нийтэд нээлттэй ивээн тэтгэгчийн сангууд түүний хувийн үндсийн шимтгэлд эрх олгож чадахгүй. Ивээн тэтгэлэг төлөвлөхөөс өмнө гүйцэтгэлийн үндсийг тодорхойлно.

## 1. Батлагдсан шимтгэлийн бодлогыг тогтоох {#_1-establish-the-committed-fee-policy}

Гарын үсэгтэй эхлэл төлөв `RootFeePolicy`-г агуулсан нэг `root_fees_v1` тусгай параметрийг тодорхойлно. Энэ нь шимтгэлийн валют, шимтгэл хүлээн авах данс, ивээн тэтгэгчийн хадгалалтын данс, нэхэмжлэлийн чөлөөлөлт болон тарифыг холбоно. Ердийн блок болон үнийн санал бүр өөрийн барьж авсан батлагдсан бодлогыг ашиглана. Тариф, шимтгэл хүлээн авах данс болон нэхэмжлэлийн чөлөөлөлтөд хийсэн зөвшөөрөгдсөн өөрчлөлтүүд дараагийн блокоос үйлчилнэ; шимтгэлийн валют болон ивээн тэтгэгчийн хадгалалтын дансыг эхний блокийн дараа өөрчлөх боломжгүй.

Глобал гүйцэтгэлийн үндсэн шимтгэл нь гарын үсэгтэй сүлжээний яг XOR валютыг шатаана. Ивээн тэтгэгчийн хөтөлбөрийн сан тэр валютыг гаргана. Зангилааны тохиргоо болон гүйлгээний метадата төлөгч сонгохгүй, ивээн тэтгэлэг идэвхжүүлэхгүй.

Сүлжээний каноник валют болон дансны таних тэмдгийг ашиглана. Өөр нэрийг тайлах ажиллагаа батлагдсан валют, хадгалалт эсвэл шимтгэл хүлээн авах дансны таних тэмдгийг өөр тийш чиглүүлэх ёсгүй.

## 2. Ивээн тэтгэх хөтөлбөр үүсгэж, санхүүжүүлэх {#_2-create-and-fund-a-sponsor-program}

Хөтөлбөрийн ID нь `<canonical-sponsor-account>/<program-name>` хэлбэртэй. Одоогийн SDK болон өгөгдлийн загварын гаргасан төрөлжсөн заавраар үүнийг үүсгэнэ:

| Заавар | Зорилго |
| --- | --- |
| `CreateFeeSponsorProgram` | Заавал байх буцаан төлөх данстай, бэлтгэсэн хөтөлбөр үүсгэх. |
| `StageFeeSponsorProgramRevision` | Шаардлага хангах нөхцөл, үйлдэл болон төсвийн нэг өөрчлөгдөхгүй бодлого тодорхойлох. |
| `EnrollFeeSponsorBeneficiary` | Шаардлага хангасан хүртэгчийг сүлжээнд бүртгэх. |
| `FundFeeSponsorProgram` | Хөрөнгийг хамгаалалттай хадгалалт руу шилжүүлж, яг хөтөлбөрийн санд нэмэх. |
| `ActivateFeeSponsorProgramRevision` | Бэлтгэсэн хувилбарын идэвхжих хамгийн эрт өндрийг товлох. |

Хөтөлбөрийн удирдлагыг ивээн тэтгэгч эсвэл яг эрх шилжүүлсэн менежер зөвшөөрнө. Хөрөнгө татахад ивээн тэтгэгч өөрөө шаардлагатай бөгөөд хөтөлбөр түр зогссон эсвэл хаагдаж байх үед л бүртгэсэн буцаан төлөх дансанд хөрөнгө буцаана.

Хувилбар бүр дараахыг тодорхойлно:

- илэрхий бүртгэл, эсвэл бүртгэл дээр нэмсэн зөвшөөрөгдсөн анхдагч маршрутын хамрагдах нөхцөл;
- үндсэн зааврын яг дамжуулах ID эсвэл гэрээний хаяг, кодын хэш, орох цэгээр зөвшөөрөх ба хориглох дүрэм;
- хөрөнгө тус бүрийн гүйлгээ, блок, хөтөлбөрийн эрин болон хүртэгчийн эриний хязгаар;
- нөөцийн доод хэмжээ болон детерминистик эриний урт.

Хориглох дүрэм зөвшөөрөх дүрмээс давуу. Өгөгдлийн орон зайн `fee_sponsor_program_id` нь идэвхтэй хувилбар зөвшөөрсөн үед л анхдагч маршрутаар хамрагдах эрх өгнө; гүйлгээ өөрийн яг хөтөлбөр, хувилбарыг заасан хэвээр байх ёстой. Өмнөх хувилбарын дуусаагүй хуваарилалтын хугацаа дуусах хүртэл идэвхжүүлэлтийг хойшлуулж болно.

Ивээн тэтгэгчийн сангийн хөрөнгө `Global` үлдэгдлийн бодлого ашиглах ёстой. Зөвхөн ивээн тэтгэгчийн ердийн дансыг санхүүжүүлэх нь тусгаарласан хөтөлбөрийн санг санхүүжүүлэхгүй; нэг хөтөлбөр нөгөөгийн үлдэгдлийг зарцуулж болохгүй.

## 3. Яг гүйлгээнд үнийн санал авч, гарын үсэг зурж, илгээх {#_3-quote-sign-and-submit-the-exact-transaction}

SDK интеграц дараах алхмуудыг хийнэ:

1. Эрх бүхий этгээд, гүйцэтгэх агуулга, цагийн тэмдэг, nonce, метадата, яг ивээн тэтгэх хөтөлбөрийн хувилбар болон шаардлагатай гүйцэтгэлийн зардлын хязгаартай гарын үсэггүй `TransactionPayload` үүсгэнэ. Төлбөрийн дээд хэмжээ эхэндээ хоосон байж болно.
2. `{"payload": <payload>}` бүхий `POST /v1/fees/quote` хүсэлтэд дансаар гарын үсэг зурна. Хүсэлтэд гарын үсэг зурагч нь гүйлгээний эрх бүхий этгээд байх ёстой.
3. Ажигласан өндөр, тодорхойлсон өгөгдлийн орон зайн маршрут, шимтгэлийн бүрэлдэхүүн, хөрөнгө хасах эх сурвалж болон ивээн тэтгэгчийн багтаамжийг шалгана. Хариу нь сонгосон төлөгч, хувилбар, гүйцэтгэлийн зардлын хязгаарыг хадгалсныг батална.
4. Зөвхөн `payload.fee_payment`-ийг санал болгосон зорилгоор сольж, дараа нь яг тэр агуулгад гарын үсэг зурж илгээнэ.
5. Гүйлгээг төлөвөөс тодорхойлсон `Applied` эцэслэлт хүртэл хянаж, бодит ивээн тэтгэх хөтөлбөр, хувилбар, төлбөрийг багтаасан баримтыг хадгална.

Үнийн санал бүртгэлийг ажиглахаас багтаамж нөөцлөхгүй. Дараалалд хүлээн авахдаа хамрагдах нөхцөлийг дахин шалгаж, гарын үсэгтэй дээд хэмжээг нөөцөлнө. Ивээн тэтгэгч татгалзвал гүйлгээг няцааж, хэрэглэгчээс төлбөр авах руу шилжихгүй.

CLI ижил шимтгэлийн эх сурвалжийг илэрхий нэрлэнэ. Жишээлбэл, хөтөлбөр яг энэ хөрөнгийн шилжүүлгийг зөвшөөрч, данс шаардлага хангасны дараа:

```bash
iroha --config ./user.client.toml \
  --fee-payer sponsor \
  --fee-program '<SPONSOR_CANONICAL_I105>/team-payments' \
  --fee-program-revision 1 \
  ledger asset transfer \
  --definition '<ASSET_DEFINITION_BASE58>' \
  --account '<USER_CANONICAL_I105>' \
  --to '<RECIPIENT_CANONICAL_I105>' \
  --quantity 1
```

Өөрийн сүлжээний идэвхтэй хувилбар болон яг танигчдыг ашиглана. Хэрэглэгчийн тохиргоонд зөвхөн тэр хэрэглэгчийн гарын үсгийн хэрэгсэл байна; шаардлага хангасан ивээн тэтгүүлсэн гүйлгээ илгээхэд ивээн тэтгэгчийн хувийн түлхүүр хэрэггүй.

## 4. Хэрэглэгч хэрэглээний шимтгэл төлөх эсэхийг шийдэх {#_4-decide-whether-the-user-pays-an-application-fee}

Хэрэглээ хэрэглэгчээс юу ч авахгүй байхад ивээн тэтгэгч глобал шимтгэлийг төлж болно. Хэрэглээ дотоод токен авдаг бол тэр шилжүүлэг эсвэл гэрээний дүрмийг хэрэглэгчийн гарын үсэгтэй гүйцэтгэх агуулгад илэрхий бичнэ. Үйлдэл бүрийг ивээн тэтгэх хувилбарын бодлогод оруулж, бүтэн агуулгын үнийн саналыг шалгана. Сүлжээний шимтгэлийн зорилгоос хэрэглээний токены шилжүүлгийг таамаглаж болохгүй.

## Татгалзсан шалтгааныг оношлох {#diagnose-a-refusal}

Зангилааны буцаасан тогтвортой шимтгэлийн код болон засах тайлбарыг ашиглана:

| Код | Шалгах зүйл |
| --- | --- |
| `program_not_found` | Яг каноник хөтөлбөрийн таних тэмдэг. |
| `revision_not_active`, `program_not_active` | Хувилбарын идэвхжил болон хөтөлбөрийн амьдралын мөчлөг. |
| `beneficiary_not_eligible` | Бүртгэл эсвэл зөвшөөрөгдсөн анхдагч маршрутын хамрагдах нөхцөл. |
| `operation_not_allowed`, `operation_denied` | Яг гарын үсэгтэй үйлдэл бүр болон хориглох дүрэм. |
| `invalid_gas_limit`, `signed_limit_exceeded` | Шинэ үнийн саналтай харьцуулсан гүйцэтгэлийн зардлын хязгаар болон гарын үсэгтэй дээд хэмжээ. |
| `vault_insufficient` | Энэ хөтөлбөрийн яг валютын сангийн санхүүжүүлсэн үлдэгдэл. |
| Төсөв дууссан кодууд | Гүйлгээ, блок, хөтөлбөрийн эрин болон хүртэгчийн эриний багтаамж. |

Үр дүн нь тодорхойгүй илгээлтийг шалгахдаа анхны гүйлгээний хэш болон шимтгэл няцаасан мэдээллийг хадгална. Орлуулах гүйлгээ үүсгэхийн өмнө төлөвийг нь батална.
