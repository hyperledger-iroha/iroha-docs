# アトミックなプライベートクロスデータスペースの金融取引決済を実行する {#run-atomic-private-cross-dataspace-settlement}

`AtomicPrivateSettlementV1` は、2 から 255 の SORA Nexus データスペースのそれぞれで1つの機密金融送金部分を調整し、すべての金融送金部分を1つのグローバルステートで完了させます取引。拒否された、期限切れの、または中止されたバンドルは、金銭的な移転部分を適用しません。透明ネイティブ AMX DvP/PvP は、別のプロトコル経路として残ります。

::: warning リリース状況
この機能は管理されており、デフォルトでは無効であり、まだ本番用には認定されていません。公開された機能が利用可能になるまでは、実際の CBDC 値には有効にしないでください。プライバシー、障害、パフォーマンス、再現可能ビルド、独立暗号レビュー、および成果物公開のゲートは、すべて正確なリリースに対して通過しました。
:::

## プロトコルが隠しているもの {#what-the-protocol-hides}

各金融送金パートは、固定された二入力三出力のプライベートノート証明を使用します。委員会の検証者は、証明と不透明な状態遷移を検証します; 彼らは平文の当事者、資産、金額、メモ、またはビジネス結果を受け取りません。認可された現地の監査人は、パディングされた監査カプセルを復号し、その内容を確認し、目的ごとに分離された承認に署名します。デフォルトのポリシーでは、管理対象の監査人セットからの1つの承認を受け入れます。

公開コンテナ取引およびプロトコル結果記録は、意図的に以下を明らかにする：

- ネットワークおよびバンドル識別子
- 参加者データスペースルートと参加者数
- タイミングと有効期限の高さ
- 安定した不透明なプロトコルデータグループ識別子、ルート、ヌリファイアー、暗号コミットメント値、および固定暗号文スロット
- 委員会の承認原則および正確な3分の4の可用性、準備、ならびにプロトコル確定証明書
- スポンサー、公共ネットワーク料金、端末の状態

これはコンテンツの機密性であり、トラフィックフローの匿名性ではありません。タイミング、参加者の数、データスペースの識別、および安定プールの活動は公開されたままです。1つの CBDC のみをホストするデータスペースも、リテラルな資産識別子が公開されていなくても、ルートから資産を推測できる場合があります。

## 展開要件 {#deployment-requirements}

起動前に、オペレーターは次のすべてを必要とします:

1. 各参加データスペースに対して正確に4つのバリデーターが存在し、異なる BLS コンセンサスキーと所有証明を持つ
2. すべての高さに対して必須 Sumeragi DA/RBC が有効
3. すべてのデータスペースにおける、管理された機密金融取引清算プロトコルデータグループおよび初期ルート
4. アクティブな V1 プライベートノート機能と、別個の金融取引決済証明プロファイル
5. 少なくとも1つの管理されているローカル`PrivateSettlementAuditPolicyV1`には、異なる監査人の署名やハイブリッド暗号鍵、鍵のエポック、高さの有効性、承認閾値が含まれます
6. 設定された保持期間のための十分なプライベート補助記録ストレージ
7. 最終的な公開コンテナ取引を提出できる中立的なスポンサーアカウント

監査人はバリデーターを操作することもできますが、別々のコンセンサス、監査人署名、および監査人暗号化キーを使用しなければなりません。廃止された復号キーは規制上の保存期間中保持するか、廃止する前にカプセルの再暗号化を管理・テストしてください。

四検証者認証の原則はクライアントによって提供されるのではなく、状態に依拠しています。技術マニフェストの`authority_context_height`において、各検証者はコンセンサス状態から正確な順序付きレーン/データスペースの名簿およびアクティブな実行レーンの化身を解決し、解決された高さが一致することを要求します。そして4つの BLS キーと所持証明を検証します。アップロード、準備、および最終プロトコル結果記録の承認はすべて、その同じ歴史的な認証原則を使用します。

## 入場を設定する {#configure-admission}

すべての生産動作はノードの設定から生じます。環境変数ではこのパスを有効化できません。出荷時のデフォルトは `enabled = false` です；機能を無効のままにするには、特定の処理区分の設定は不要です。

ガバナンスが必要な機能を登録し、十分な通知とともに有効化高さを選択した後、すべての関連ノードを一貫して設定します:

```toml
[nexus.atomic_private_settlement]
enabled = true
activation_height = 500000
minimum_activation_notice_blocks = 7200
proof_profile_version = 1
max_participants = 255
max_expiry_blocks = 7200
audit_timeout_blocks = 1200
prepare_timeout_blocks = 1200
commit_timeout_blocks = 1200
capsule_padding_classes_bytes = [4096, 16384, 65536, 262144]
max_proof_bytes = 8388608
max_capsule_bytes = 1048576
max_carrier_bytes = 4194304
sidecar_retention_blocks = 1000000
sidecar_max_records = 256
sidecar_max_total_bytes = 3221225472
default_min_auditor_approvals = 1
permitted_policy_versions = [1]
```

この例では、出荷された V1 の制限を使用しており、性能推奨ではありません。ストレージ、プルーフ、カプセル、コンテナトランザクション、およびレイテンシデータコンテナを測定します。動作範囲を選択する前に、意図したハードウェアを確認してください。三相のタイムアウトは`max_expiry_blocks`内に収まる必要があり、補助記録の保持期間は少なくともその有効期限の期間でなければなりません。

`max_capsule_bytes` は、全体の `PrivateSettlementAuditCapsuleV1` の正準的 Norito エンコーディングを制限します: AAD、暗号用ノンス値、暗号文、ベクターフレーミング、監査者の識別情報、およびすべてのラップされた DEK 行です。これは暗号文のみの制限ではありません。各構成済みパディングクラスは、少なくとも `default_min_auditor_approvals` 人の監査人向けの保守的な全カプセルデータコンテナに適合する必要があります。Torii は、`min_approvals` が規定された下限を下回る新規承認ポリシーも拒否し、完全な正準エンコーディングが大きすぎる実際のカプセルも拒否します。

`max_carrier_bytes` は、認定バンドルだけでなく、完全な正規スポンサー署名付きトランザクションを制限します。この件数には、登録済みの指示フレーミングも含まれます。取引承認の主体とメタデータ、手数料の意図、および署名。通常のネットワーク取引の制限は、独立した上限として引き続き適用されます。

統御される能力がアクティブであり、その状態と有効化高さが通知期間を満たし、コンパイルされた証明プロファイルが V1 と一致し、オンチェーンのプロトコルデータグループおよび監査記録が最新でない限り、アクティベーションはクローズ状態で失敗します。構成フラグを有効にするだけでは不十分です。

## 金融取引決済ワークフロー {#settlement-workflow}

クライアントは証明と暗号化カプセルをローカルで作成します。秘密の証人はネイティブウォレットまたはネイティブワーカー内に保持する必要があり、アプリケーションログ、Python オブジェクト、HTTP リクエスト、または永続的なコーディネーションレコードにシリアライズしてはいけません。

カプセルおよび監査人ごとの DEK-ラップ認証データには、正確な状態に基づく委員会および `authority_context_height` の暗号学的ダイジェスト値、ならびにネットワーク、ルート/インカーネーションが含まれます。バンドル、金融転送部分、ポリシー、重要な時代、平文の暗号コミットメント値。ラップされたキーは、異なる名簿や履歴的認可プリンシパルのコンテキストに移動することはできません。

各標準的な財務送金部分について、コーディネーターは次にこの手順を実行します：

1. 暫定的に暗号化された資料を4つのバリデータすべてにアップロードし、正確な3分の4の可用性証明書を取得してください。
2. 認可された監査人にカプセルを取得して復号化させ、公開バインディングを再計算し、ローカルポリシーを適用し、承認を提出させる。
3. 四人のバリデーターからの準備投票を要求する。各バリデーターは独立してデルタを検証し、投票前に確実にステージする。ステージされた各レスポンダーに、標準の3対4の準備証明書を永続化する。
4. すべての決済区間について Prepare 証明書がそろったら、変更不能な完全 Prepare バリアを構築します。標準形式の 3-of-4 Commit 証明書を要求して永続化します。コーディネーターが再起動した場合は、参加ノードにローカルで永続化された Prepare 証明書と Commit 証明書を照会し、標準形式でクォーラムと同等の証明書を選択して、処理を続行する前に再配布します。認証されていないローカルキャッシュから証明書を再構築してはいけません。
5. 技術マニフェストのスポンサーに署名させ、正確に1つのグローバルコンテナ取引を提出させてください。コンテナ取引には1つの `FinalizeAtomicPrivateSettlementV1` 指示と、完全に認定されたバンドルが含まれています。コーディネーターと WSV は、登録済みの指示フレーミングを含む、完全な型消去済み最終化指示を事前点検します。Torii とコアのワンショットコンテナトランザクションバインディングは、正確な標準的スポンサー署名トランザクションに対して`max_carrier_bytes`を強制します。承認主体、メタデータ、手数料意図、署名を含む。Torii は、承認主体のコンテキストの前、最終化に達する可能性のある最後の侵入高さ時点またはそれ以降、または規定された有効期限の範囲を超えて、コンテナ取引を拒否します。
6. グローバル最終性が得られるまで、公開バンドルの状態とプロトコル結果記録を照会してください。ローカル補助記録の状態は、その不変のグローバル最終記録と照合されるまで暫定的なものとして扱ってください。

Rust クライアントは、このフローを `certify_and_upload_private_settlement_legs_v1`、`prepare_private_settlement_bundle_v1`、`commit_private_settlement_bundle_v1`、および `submit_private_settlement_bundle_v1` を含むメソッドを通じて公開します。再起動に安全な調整には `recover_or_prepare_private_settlement_bundle_v1` および `recover_or_commit_private_settlement_bundle_v1` を使用します。委員会および監査人の技術的呼び出しには明示的な役割資格情報が必要であり、通常のアカウント暗号署名者を再利用することはありません。

## 監査ポリシーを安全にローテーションする {#rotate-an-auditor-policy-safely}

プライバシーガバナンス認可済み`RotatePrivateSettlementPoolPolicyV1`指示を使用してください。正確な現在のガバナンス暗号化ダイジェスト値を指定し、同じルート、プロトコルデータグループ、および資産バインディング暗号化コミットメント値を保持し、ガバナンスの改訂を1つ進める必要があります。厳密に新しいキーエポックと異なるポリシー／ガバナンス暗号ダイジェストを使用し、ローテーションを含むブロックで有効化します。プロトコルデータグループのフロンティア、ルート、ヌリファイア、出力、リプレイセットおよび確定されたプロトコル結果記録は保存されます。その回転の有効化高さで同じルート/プールに触れるプロトコル結果記録を含めないでください。その指示はその境界を拒否します。

公開プロトコルデータグループの投影は、完全な廃止されたポリシー改訂の系譜を保持します。したがって、回転前に確定されたプロトコル結果記録は再起動後も有効であり、その正確なプロトコル結果記録を再実行しても冪等性が保たれます。血統は未完成の作業を認可しません：アクティベーション境界を越える古いポリシーバンドルは、グローバル状態が変化する前に閉じて失敗します。保存されたカプセルを開くために必要な古いすべての復号キーを保持するか、破棄する前に管理されテストされたカプセルの再ラップを完了してください。

## Torii ルートファミリー {#torii-route-family}

これらのルートは標準の Norito リクエストおよびレスポンスオブジェクトを使用します。認証済みおよび制限付きのレスポンスはプライベートな`no-store`キャッシュ動作を使用します。

|操作|方法とパス|校長|
| ------------------ | -------------------------------------------------------------------------- | --------------------------- |
|財務転送部分をアップロード|`POST /v1/nexus/private-settlements/legs`|標準的なアカウント署名|
|利用可能性の共有| `POST /v1/nexus/private-settlements/legs/availability-shares`              |標準的なアカウント署名|
|投票の準備をする| `POST /v1/nexus/private-settlements/phases/prepare-votes`                  |標準的なアカウント署名|
|最終段階の投票| `POST /v1/nexus/private-settlements/phases/commit-votes`                   |標準的なアカウント署名|
|持続フェーズ QC|`POST /v1/nexus/private-settlements/phases/certificates`|標準的なアカウント署名|
|回復フェーズ QCs| `GET /v1/nexus/private-settlements/legs/{payload_digest}/phase-certificates` |技術的マニフェストスポンサー|
|財務送金部分の状況| `GET /v1/nexus/private-settlements/legs/{payload_digest}/status`           |標準的なアカウント署名|
|委員会の校正| `GET /v1/nexus/private-settlements/legs/{payload_digest}/committee-proof` |正確なロスター検証ツール|
|監査カプセル| `GET /v1/nexus/private-settlements/legs/{payload_digest}/audit-capsule`    |管理された監査人|
|監査人の承認| `POST /v1/nexus/private-settlements/legs/{payload_digest}/audit-approvals` |管理された監査人|
|最終送信／中止|`POST /v1/nexus/private-settlements/bundles`|技術的マニフェストスポンサー|
|バンドルのステータス| `GET /v1/nexus/private-settlements/bundles/{bundle_id}`                    |パブリック|
|プロトコル結果記録または中止| `GET /v1/nexus/private-settlements/bundles/{bundle_id}/receipt`            |公開|

公開ステータスおよびプロトコル結果記録 APIs は、文書化された公開フィールドのみを公開します。特に、通常の金融送金部分のステータスは、承認数や監査人の閾値を明らかにしません。制限付き読み取りは、欠落、不正アクセス、保持期限切れの資料を意図的に同じ利用不可応答クラスにまとめます。送信経路は、1つのスポンサー署名済みの完了または中止指示のみを正確に受け付けます。その`202`の応答には、バンドルID、観測された入場高さ、およびコンテナ取引の暗号ハッシュのみが含まれています。キューに入った中止がすでに確定していると主張するものではありません。この SDKs は、両方の識別子が正規化されたチェックサム付きの Norito`Hash`JSON リテラルであること、そして高さが正確な符号なし64ビット整数であることを要求します。欠落、追加、誤記、非正規、チェックサム無効、負、負のゼロ、小数、またはオーバーフローしたフィールドは閉じた状態で失敗します。権威ある端末状態にはバンドルステータスまたはプロトコル結果レコードを使用してください。ステータスコードも正確です：このコンテナの取引受け入れルートは`202`を必要としますが、その他のすべてのプライベート決済 V1 の成功応答には`200`が必要です。クライアントは、予期しないレスポンスボディをクライアントエラーで反映することなく、契約の逸脱として代替の成功した`2xx`コードを拒否します。彼らはサーバー拒否コードのみを公開しますそれが`[A-Za-z0-9_.:-]{1,128}`と一致したとき、応答パーサー/検証の原因を破棄し、ボディコンテンツや攻撃者が選んだ JSON フィールド名が原因認識ログを通じて再出現するのを防ぎます。

## 失敗と回復 {#failure-and-recovery}

監査人の承認が欠落しているか古いもの、3つ未満の検証者投票、誤ったルートやエポック、重複したヌリファイア、置き換えられた証明やカプセル、非標準の金融部品の注文の転送、期限切れのバンドル、および不一致の払い戻し条件はすべて、グローバル変異の前に失敗します。コンセンサス確定証明書は、決してプライベート状態を変異させません。

検証者は、補助レコード、ステージングされたデルタ、およびフェーズ証明書を確認する前に fsync します。再起動時には、正準耐久レコードから予約を再構築し、その後、不変のグローバルプロトコル結果レコード、中止マーカー、または有効期限を照合します。監督付きリコンシリエーターは、端末候補を調整する必要がない場合でも、同期的に観測された権威ある高さで端末保持の剪定を実行します。そして、それはプルーニングエラーで閉じて失敗します。権限のあるグローバル端末レコードだけがステージングされたロックを解放します。同一の最終プロトコル結果レコードを再生することは冪等です；競合する再生は決定的に失敗します。

予約識別子には完全なルートが含まれます。プロトコルデータグループのヘッダーは`(route, pool_id, epoch, root)`を使用し、ヌリファイアは`(route, pool_id, nullifier)`を使用し、出力は`(route, pool_id, commitment)`を使用します。別のルートでの等しい不透明値は独立しており、正確なルートの衝突は再起動後もロックされたままです。

運用アラートでは、不透明なバンドル、ルート、フェーズ、暗号ダイジェスト値、高さ、理由クラスのフィールドのみを使用する必要があります。復号されたカプセル、アカウントや資産の識別子、金額、メモ、ビューのデータ、証明の証人、またはパーサペイロードをログ、イベント、メトリクスラベル、またはトレーシングスパンに含めてはいけません。

## 実際の価値の前の資格 {#qualification-before-real-value}

展開する予定の正確なビルドと構成について、次の内容を網羅する証拠を記録してください:

- 対立証明、カプセル、ポリシー、キー回転、補償、およびリプレイのケース
- バリデータとコーディネーターの再起動、認証された5％、10％、20％のメッセージ損失、フェーズパーティション、回復、および永続境界クラッシュを含む、2、3、4、8、および16のデータスペースに対する実際の4バリデータプロセス
- Torii、P2P、ブロック、Kura、データスナップショット、クエリ、イベント、ログ、およびテレメトリにわたるカナリアおよび差分漏洩解析
- 実際のネットワーク参加者数ごとに少なくとも5回のウォームアップと30束の測定を行い、p50、p95、p99、信頼区間、リソース、トラフィック、証明およびプロトコル結果の記録サイズ、透明な AMX をコントロールとして使用する
- 厳格なワークスペーステスト、リンとフォーマットのチェック、ランダム化されたシード、ソークテスト、再現可能なビルド、SBOMs、および署名付きアーティファクトの暗号ハッシュ

プロデューサーは、ステージ済み、未ステージ、追跡されていない、またはマージされていないファイルや、キャプチャ中の任意のソース変更に失敗します。生のソースコードのリビジョンオブジェクト、標準化されたGitツリーインベントリ、正確なバイナリパスのリスト、決定論的なソースシール、および`Cargo.lock`を保持します；最終リリース技術マニフェストには、JSON の結果からのすべてのアーティファクト宣言を含めます。これは、最終的な DOI-バンドル検証者や外部リリースゲートを免除するものではありません。

ソースシールは携帯可能でフェイルクローズです：プロデューサーと最終検証者は、アーカイブされたシンボリックリンクの全グラフを解決するため、ルート内に現れるが別のリンクを通じて逃げるリンク、循環、`.git` トラバーサル、または Windows スタイルのターゲットは、リンクが作成される前に拒否されます。構造化されたソースおよびゲートレポートは、暗号学的ダイジェスト値と長さがリリース技術マニフェストと一致する境界付きの安定したファイルからのみ解析され、各ソースペイロードの種類は正確に一度だけ出現しなければなりません。

すべての生の故障ランおよび遅延サンプルは、完全リリースのソースコード改訂版、1つの構造化された固定ハードウェア記述の SHA-256、およびその正確な参加者数構成の SHA-256 にバインドする必要があります。N=2、3、4、8、16をカバーする1つの標準的な構成技術マニフェストをアーカイブしてください。各エントリは保持された構成バイトを参照し、各データスペースに対して正確に4人のバリデーター、3分の4クォーラム、および必須の署名 RS16 DA/RBC を主張する必要があります。リリース検証者は、異なるビルド、ハードウェアプロファイル、またはネットワーク構成で生成されたサマリーを拒否します。すべての個別の損失、フェーズカット、および永続クラッシュ行は、さらに SHA-256 に限定された中で、再利用できない正確な JSONL レコード参照を指定する必要があります。認証コントローラーおよび原子性キャプチャのアーティファクト。リリース検証者はそれらの暗号学的ダイジェストを解決し、行が実行の識別、試行インデックスおよびパラメータ、コントローラーの確認または回復結果、連続チェックのカウントと一致することを要求します。そして部分的な可視性や使用可能性の観測はゼロです。後でリリースされた p95/p99 の比較も、ハードウェア、構成、または測定要件が候補と異なる署名済みのベースラインを拒否します。最終検証者は、切り離されたベンチマークの要約を信頼するのではなく、アーカイブされた生サンプルから報告されたすべてのパーセンタイル、MADs、および決定的信頼区間を再生成します。それは同様にカナリアの技術マニフェストを再読み込みし、すべてのアーカイブされたプライバシーサーフェスを独立して再スキャンするため、レポートはファイルの暗号化ダイジェストを再バインドした後に仕込まれた秘密のヒットを抑制することはできません。各シークレット専用の実行は、所有者専用の未フィルタリングのループバックPCAP、未加工のtcpdump標準エラー出力とゼロドロップ統計、標準的なポート技術マニフェスト、パックされた制限付きソースアーカイブ、そしてすべてのピアのアトミシティ観測を保持しなければなりません。最終検証者は、公開された要約を信頼するのではなく、アーカイブされたバイトからポートに結び付けられたパケット分割、ソース投影、およびベースラインから端末までの原子性チェックを再実行します。

アーカイブには、すべての必要なプライバシーサーフェスについて、正確な左右のファイルパス、種類、バイト長、および SHA-256 暗号学的ダイジェストを結び付ける標準的なペアトラフィックカウントおよび差分ペア技術マニフェストも含める必要があります。その宣言されたルートは、正確にペアになったアーカイブのインベントリを含まなければなりません。検証者は、通常の表面に対して、等しい全ファイルサイズと JSON の公開形状を必要とします。エントロピーを含む生ループバックキャプチャおよびパックされた制限付きソースアーカイブは明示的なサイズ例外です；代わりにパケットリンクタイプとパケットごとの長さ、制限付きソースの識別、および固定形状の行長を比較します。すべての Torii リクエスト/レスポンス、公開/制限された P2P パケット、ブロック、クエリ、イベント、ログ、テレメトリトラフィックのカウントも一致する必要があります。パケット形状の変更、同サイズの構造的漏洩、偽の出所の主張、または、ペアになっていないファイルは、漏洩報告書とその暗号ハッシュを書き換えることで隠すことはできません。
