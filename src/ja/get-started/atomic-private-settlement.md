# データスペース間のアトミックなプライベート決済を実行する {#run-atomic-private-cross-dataspace-settlement}

`AtomicPrivateSettlementV1` は、2から255の SORA Nexus データスペースのそれぞれで一つの機密決済レッグを調整し、すべてのレッグをグローバル状態に対する一つのトランザクションで確定します。拒否、期限切れ、中止となったバンドルでは、どのレッグも適用されません。透過型のネイティブ AMX DvP/PvP は、別のプロトコル経路です。

::: warning リリース状況
この機能は管理されており、デフォルトでは無効であり、まだ本番用には認定されていません。公開された機能が利用可能になるまでは、実際の CBDC 値には有効にしないでください。プライバシー、障害、パフォーマンス、再現可能ビルド、独立暗号レビュー、および成果物公開のゲートは、すべて正確なリリースに対して通過しました。
:::

## プロトコルが隠しているもの {#what-the-protocol-hides}

各金融送金パートは、固定された二入力三出力のプライベートノート証明を使用します。委員会の検証者は、証明と不透明な状態遷移を検証します; 彼らは平文の当事者、資産、金額、メモ、またはビジネス結果を受け取りません。認可された現地の監査人は、パディングされた監査カプセルを復号し、その内容を確認し、目的ごとに分離された承認に署名します。デフォルトのポリシーでは、管理対象の監査人セットからの1つの承認を受け入れます。

公開コンテナ取引およびプロトコル結果記録は、意図的に以下を明らかにする：

- ネットワークおよびバンドル識別子
- 参加するデータスペースへの経路と参加者数
- タイミングと有効期限の高さ
- 安定した不透明なプロトコルデータグループ識別子、ルート、ヌリファイアー、暗号コミットメント値、および固定暗号文スロット
- 委員会の承認原則および正確な3分の4の可用性、準備、ならびにプロトコル確定証明書
- スポンサー、公共ネットワーク料金、端末の状態

ここで保護されるのは内容の機密性であり、通信の流れの匿名性ではありません。タイミング、参加者数、データスペースの識別子、安定したプールの活動は引き続き公開されます。一つの CBDC だけを扱うデータスペースでは、資産識別子そのものを公開しなくても、経路から資産を推測できる場合があります。

## 展開要件 {#deployment-requirements}

起動前に、オペレーターは次のすべてを必要とします:

1. 参加する各データスペースに、互いに異なる BLS 合意形成鍵と所有証明を持つ、ちょうど4台のバリデータがあること
2. すべての高さに対して必須 Sumeragi DA/RBC が有効
3. 各データスペースに、ガバナンスで管理された機密決済プールと初期ルートがあること
4. 利用可能なネイティブの `IrohaIvmPrivateNoteStarkV1` 実装、コミット済みのプライベート決済の上限、および V1 ポリシーの権限
5. 少なくとも1つの管理されているローカル`PrivateSettlementAuditPolicyV1`には、異なる監査人の署名やハイブリッド暗号鍵、鍵のエポック、高さの有効性、承認閾値が含まれます
6. コミット済みの保持期間に対応できる十分なプライベート補助記録ストレージ
7. 最終的な公開コンテナ取引を提出できる中立的なスポンサーアカウント

監査人はバリデーターを操作することもできますが、別々のコンセンサス、監査人署名、および監査人暗号化キーを使用しなければなりません。廃止された復号キーは規制上の保存期間中保持するか、廃止する前にカプセルの再暗号化を管理・テストしてください。

4台のバリデータによる権限は状態に結び付けられ、クライアントから供給されるものではありません。各バリデータは、マニフェストの `authority_context_height` における合意形成状態から、レーンとデータスペースの正確な順序付き名簿、および有効なレーンの世代を解決します。解決したブロック高の一致を要求し、4個の BLS 鍵と所有証明を検証します。アップロード、Prepare、最終受領記録の受け入れには、すべて同じ過去時点の権限を使います。

## 補助レコードの保管を設定する {#configure-sidecar-custody}

コミット済みのプライバシーポリシーは、証明、カプセル、コンテナ取引の上限、参加者数の上限、有効期限、保持期間、監査人の要件を定めます。受け入れには、プールポリシーのガバナンス通知期間と、現在のオンチェーンのプールおよび監査記録も必要です。ノードの有効化フラグやサービスの有効化高さはありません。

ノード設定が制御するのは、暗号化された補助レコードストアのローカル容量だけです。

```toml
[nexus.atomic_private_settlement]
sidecar_max_records = 256
sidecar_max_total_bytes = 3221225472
```

これらは提供されているストレージ上限です。ローカル容量を選ぶ前に、使用予定のハードウェアで、保持する記録数と正規形式のバイト数を測定してください。容量を設定するだけでは、決済を有効にしたり、コミット済みの妥当性ポリシーを変更したりできません。

コミット済みのカプセル上限は、`PrivateSettlementAuditCapsuleV1` の正規 Norito 符号化全体を対象とします。AAD、ノンス、暗号文、ベクトルのフレーム情報、監査人の識別子、ラップされた DEK の全行を含みます。コミット済みの搬送トランザクション上限は、スポンサーが署名したトランザクション全体を対象とし、命令のフレーム情報、権限主体、メタデータ、手数料インテント、署名を含みます。通常のネットワークのトランザクション上限も適用されます。

## 金融取引決済ワークフロー {#settlement-workflow}

クライアントは証明と暗号化カプセルをローカルで作成します。秘密の証人はネイティブウォレットまたはネイティブワーカー内に保持する必要があり、アプリケーションログ、Python オブジェクト、HTTP リクエスト、または永続的なコーディネーションレコードにシリアライズしてはいけません。

カプセルおよび監査人ごとの DEK-ラップ認証データには、正確な状態に基づく委員会および `authority_context_height` の暗号学的ダイジェスト値、ならびにネットワーク、ルート/インカーネーションが含まれます。バンドル、金融転送部分、ポリシー、重要な時代、平文の暗号コミットメント値。ラップされたキーは、異なる名簿や履歴的認可プリンシパルのコンテキストに移動することはできません。

各標準的な財務送金部分について、コーディネーターは次にこの手順を実行します：

1. 暫定的に暗号化された資料を4つのバリデータすべてにアップロードし、正確な3分の4の可用性証明書を取得してください。
2. 認可された監査人にカプセルを取得して復号化させ、公開バインディングを再計算し、ローカルポリシーを適用し、承認を提出させる。
3. 四人のバリデーターからの準備投票を要求する。各バリデーターは独立してデルタを検証し、投票前に確実にステージする。ステージされた各レスポンダーに、標準の3対4の準備証明書を永続化する。
4. すべての決済区間について Prepare 証明書がそろったら、変更不能な完全 Prepare バリアを構築します。マニフェストのスポンサーに、それを 1 つの `RegisterAtomicPrivateSettlementPrepareV1` 制御用コンテナ取引で提出させ、ファイナリティを待ちます。Commit の投票者は、その複製されたロックを参照します。その後、標準形式の 3-of-4 Commit 証明書を要求して永続化します。コーディネーターが再起動した場合は、参加ノードにローカルで永続化された Prepare 証明書と Commit 証明書を照会し、標準形式でクォーラムと同等の証明書を選択して、処理を続行する前に再配布します。認証されていないローカルキャッシュから証明書を再構築してはいけません。
5. マニフェストのスポンサーに、グローバルな最終化コンテナ取引へ署名させ、提出させてください。コンテナ取引には1つの `FinalizeAtomicPrivateSettlementV1` 指示と、完全に認定されたバンドルが含まれています。コーディネーターと WSV は、登録済みの指示フレーミングを含む、完全な型消去済み最終化指示を事前点検します。Torii とコアのワンショットコンテナトランザクションバインディングは、承認主体、メタデータ、手数料意図、署名を含む、正確な標準的スポンサー署名トランザクションに対して`max_carrier_bytes`を強制します。Torii は、承認主体のコンテキストの前、有効期限までに最終化に達し得る最後の受付高さの時点またはそれ以降、または規定された有効期限の範囲を超えて、コンテナ取引を拒否します。
6. グローバル最終性が得られるまで、公開バンドルの状態とプロトコル結果記録を照会してください。ローカル補助記録の状態は、その不変のグローバル最終記録と照合されるまで暫定的なものとして扱ってください。

Rust クライアントは、このフローを `certify_and_upload_private_settlement_legs_v1`、`prepare_private_settlement_bundle_v1`、`register_private_settlement_prepare_and_wait_v1`、`commit_private_settlement_bundle_v1`、および `submit_private_settlement_bundle_v1` を含むメソッドを通じて公開します。再起動に安全な調整には `recover_or_prepare_private_settlement_bundle_v1` および `recover_or_commit_private_settlement_bundle_v1` を使用します。委員会および監査人の技術的呼び出しには明示的な役割資格情報が必要であり、通常のアカウント暗号署名者を再利用することはありません。

## 監査ポリシーを安全にローテーションする {#rotate-an-auditor-policy-safely}

プライバシーガバナンス認可済み`RotatePrivateSettlementPoolPolicyV1`指示を使用してください。正確な現在のガバナンス暗号化ダイジェスト値を指定し、同じルート、プロトコルデータグループ、および資産バインディング暗号化コミットメント値を保持し、ガバナンスの改訂を1つ進める必要があります。厳密に新しいキーエポックと異なるポリシー／ガバナンス暗号ダイジェストを使用し、ローテーションを含むブロックで有効化します。プロトコルデータグループのフロンティア、ルート、ヌリファイア、出力、リプレイセットおよび確定されたプロトコル結果記録は保存されます。その回転の有効化高さで同じルート/プールに触れるプロトコル結果記録を含めないでください。その指示はその境界を拒否します。

公開プロトコルデータグループの投影は、完全な廃止されたポリシー改訂の系譜を保持します。したがって、ローテーション前に確定されたプロトコル結果記録は再起動後も有効であり、そのプロトコル結果記録をまったく同じ形で再実行しても、状態を変更せずに拒否されます。系譜は未完成の作業を認可しません：アクティベーション境界を越える古いポリシーバンドルは、グローバル状態が変化する前に閉じて失敗します。保存されたカプセルを開くために必要な古いすべての復号キーを保持するか、破棄する前に管理されテストされたカプセルの再ラップを完了してください。

## Torii ルートファミリー {#torii-route-family}

これらのルートは標準の Norito リクエストおよびレスポンスオブジェクトを使用します。認証済みおよび制限付きのレスポンスはプライベートな`no-store`キャッシュ動作を使用します。

|操作|方法とパス|校長|
| ------------------ | -------------------------------------------------------------------------- | --------------------------- |
| 承認主体のコンテキスト | `POST /v1/nexus/private-settlements/context/{height}` | 標準的なアカウント署名 |
|財務転送部分をアップロード|`POST /v1/nexus/private-settlements/legs`|標準的なアカウント署名|
|利用可能性の共有| `POST /v1/nexus/private-settlements/legs/availability-shares`              |標準的なアカウント署名|
|投票の準備をする| `POST /v1/nexus/private-settlements/phases/prepare-votes`                  |標準的なアカウント署名|
|最終段階の投票| `POST /v1/nexus/private-settlements/phases/commit-votes`                   |標準的なアカウント署名|
|持続フェーズ QC|`POST /v1/nexus/private-settlements/phases/certificates`|標準的なアカウント署名|
|回復フェーズ QCs| `GET /v1/nexus/private-settlements/legs/{payload_digest}/phase-certificates` |技術的マニフェストスポンサー|
|財務送金部分の状況| `GET /v1/nexus/private-settlements/legs/{payload_digest}/status`           |標準的なアカウント署名|
|委員会の校正| `GET /v1/nexus/private-settlements/legs/{payload_digest}/committee-proof` |正確なロスター検証ツール|
| 監査カプセル | `POST /v1/nexus/private-settlements/legs/{payload_digest}/audit-capsule` | ガバナンスで定めた監査人 |
|監査人の承認| `POST /v1/nexus/private-settlements/legs/{payload_digest}/audit-approvals` |管理された監査人|
|コンテナ取引の送信|`POST /v1/nexus/private-settlements/bundles`|技術的マニフェストスポンサー|
|バンドルのステータス| `GET /v1/nexus/private-settlements/bundles/{bundle_id}`                    |パブリック|
|プロトコル結果記録または中止| `GET /v1/nexus/private-settlements/bundles/{bundle_id}/receipt`            |公開|

公開ステータスおよびプロトコル結果記録 APIs は、文書化された公開フィールドのみを公開します。特に、通常の金融送金部分のステータスは、承認数やガバナンスで定めた監査人の閾値を明らかにしません。制限付き読み取りは、欠落、不正アクセス、保持期限切れの資料を意図的に同じ利用不可応答クラスにまとめます。送信経路は、スポンサーが直接署名した Prepare ロック登録、最終化、または中止の指示を正確に1つだけ受け付けます。その`202`の応答には、バンドルID、観測された受け入れ高さ、およびコンテナ取引のハッシュのみが含まれています。キューに入った中止がすでに確定していると主張するものではありません。この SDKs は、両方の識別子が正規化されたチェックサム付きの Norito`Hash`JSON リテラルであること、そして高さが正確な符号なし64ビット整数であることを要求します。欠落、追加、誤記、非正規、チェックサム無効、負、負のゼロ、小数、またはオーバーフローしたフィールドは閉じた状態で失敗します。権威ある最終状態にはバンドルステータスまたはプロトコル結果レコードを使用してください。ステータスコードも正確です：このコンテナの取引受け入れルートは`202`を必要としますが、その他のすべてのプライベート決済 V1 の成功応答には`200`が必要です。クライアントは、予期しないレスポンスボディをクライアントエラーで反映することなく、契約の逸脱として代替の成功した`2xx`コードを拒否します。クライアントは、サーバーの拒否コードが`[A-Za-z0-9_.:-]{1,128}`と一致する場合にのみそれを公開し、応答パーサー／検証の原因を破棄することで、ボディの内容や攻撃者が選んだ JSON フィールド名が原因を記録するログを通じて再び現れるのを防ぎます。

## 失敗と回復 {#failure-and-recovery}

監査人の承認が欠落しているか古いもの、3つ未満の検証者投票、誤ったルートやエポック、重複したヌリファイア、置き換えられた証明やカプセル、非標準の金融部品の注文の転送、期限切れのバンドル、および不一致の払い戻し条件はすべて、グローバル変異の前に失敗します。コンセンサス確定証明書は、決してプライベート状態を変異させません。

検証者は、補助レコード、ステージングされたデルタ、およびフェーズ証明書を確認する前に fsync します。再起動時には、正準耐久レコードから予約を再構築し、その後、不変のグローバルプロトコル結果レコード、中止マーカー、または有効期限を照合します。監督付きリコンシリエーターは、照合すべき終端候補がない場合でも、同期的に観測された権威ある高さで終端データの保持期間に基づく剪定を実行します。そして、剪定エラーが発生した場合はクローズドに失敗します。権威あるグローバル終端レコードだけがステージングされたロックを解放します。最終化されたプロトコル結果レコードをまったく同じ形で再生すると、状態を変更せずに拒否されます；競合する再生は決定的に失敗します。

予約識別子には完全なルートが含まれます。プロトコルデータグループのヘッダーは`(route, pool_id, epoch, root)`を使用し、ヌリファイアは`(route, pool_id, nullifier)`を使用し、出力は`(route, pool_id, commitment)`を使用します。別のルートでの等しい不透明値は独立しており、正確なルートの衝突は再起動後もロックされたままです。

運用アラートでは、不透明なバンドル、ルート、フェーズ、暗号ダイジェスト値、高さ、理由クラスのフィールドのみを使用する必要があります。復号されたカプセル、アカウントや資産の識別子、金額、メモ、ビューのデータ、証明の証人、またはパーサペイロードをログ、イベント、メトリクスラベル、またはトレーシングスパンに含めてはいけません。

## 実際の価値の前の資格 {#qualification-before-real-value}

展開する予定の正確なビルドと構成について、次の内容を網羅する証拠を記録してください:

- 対立証明、カプセル、ポリシー、キー回転、補償、およびリプレイのケース
- 2、3、4、8、16のデータスペースについて、それぞれ実際の4バリデータプロセスで検証すること。バリデータとコーディネーターの再起動、認証された5%、10%、20%のメッセージ損失、各フェーズでの分断、復旧、永続化の境界でのクラッシュを含む
- Torii、P2P、ブロック、Kura、データスナップショット、クエリ、イベント、ログ、およびテレメトリにわたるカナリアおよび差分漏洩解析
- 実際のネットワーク参加者数ごとに少なくとも5回のウォームアップと30束の測定を行い、p50、p95、p99、信頼区間、リソース、トラフィック、証明およびプロトコル結果の記録サイズ、透明な AMX をコントロールとして使用する
- 厳格なワークスペーステスト、リンとフォーマットのチェック、ランダム化されたシード、ソークテスト、再現可能なビルド、SBOMs、および署名付きアーティファクトの暗号ハッシュ
- 2 つの形式レイヤーの両方：3/255 区間の個数対称性チェックと、正確に 4 台のバリデータを使う委員会インデックス付き構成（N=2 のバリデータ重点構成と完全な有界障害構成、論文で主要対象とする N=3 障害構成、N=4 正常構成、N=3 有効期限切れ／リプレイ構成）。障害予算は委員会ごとに独立させます
- 証明関係、ダミースロットの選択、資産とカプセルの結び付き、払い戻し関係、暗号方式、データスペース間の状態機械について、独立したレビューを行うこと

生の証拠と整理済みの証拠、脅威モデル、プロトコルの議論、制限事項、ソースコードの改訂ID、ハードウェアの説明、および監査報告書を公開する不変の DOI バックのアーティファクト。リポジトリのテストだけでは、この機能を本番対応の CBDC 金融取引決済システムにすることはできません。

プロデューサーは、ステージ済み、未ステージ、追跡されていない、またはマージされていないファイルや、キャプチャ中の任意のソース変更に失敗します。生のソースコードのリビジョンオブジェクト、標準化されたGitツリーインベントリ、正確なバイナリパスのリスト、決定論的なソースシール、および`Cargo.lock`を保持します；最終リリース技術マニフェストには、JSON の結果からのすべてのアーティファクト宣言を含めます。これは、最終的な DOI-バンドル検証者や外部リリースゲートを免除するものではありません。

ソースシールは携帯可能でフェイルクローズです：プロデューサーと最終検証者は、アーカイブされたシンボリックリンクの全グラフを解決するため、ルート内に現れるが別のリンクを通じて逃げるリンク、循環、`.git` トラバーサル、または Windows スタイルのターゲットは、リンクが作成される前に拒否されます。構造化されたソースおよびゲートレポートは、暗号学的ダイジェスト値と長さがリリース技術マニフェストと一致する境界付きの安定したファイルからのみ解析され、各ソースペイロードの種類は正確に一度だけ出現しなければなりません。

すべての障害試験の生の実行記録とレイテンシーのサンプルは、リリースの完全なコミット識別子、固定したハードウェアを記述する一つの構造化文書の SHA-256、正確な参加者数設定の SHA-256 に結び付ける必要があります。N=2,3,4,8,16 を網羅する一つの正規設定マニフェストを保存してください。各項目は保存された設定バイト列を参照し、データスペースごとにちょうど4台のバリデータ、4台中3台の定足数、必須の署名付き RS16 DA/RBC を明示しなければなりません。リリース検証器は、異なるビルド、ハードウェアプロファイル、ネットワーク設定で作られた要約を拒否します。個々の損失、フェーズ分断、永続化境界のクラッシュを表す各行は、さらに、SHA-256 で結び付けられた認証済みコントローラー成果物と原子性キャプチャ成果物内の正確な JSONL レコードを、全体で再利用できない参照で指定する必要があります。リリース検証器はこれらのダイジェストを解決し、行が実行識別子、試行インデックスとパラメーター、コントローラーの確認応答または復旧結果、継続検査の回数と一致すること、そして部分的な可視性や支出可能性の観測がゼロであることを要求します。後続リリースでの p95/p99 比較でも、ハードウェア、設定、測定要件が候補と異なる署名済み基準値は拒否します。最終検証器は、切り離されたベンチマーク要約を信頼せず、保存された生サンプルから、報告されたすべてのパーセンタイル、MADs、決定論的な信頼区間を再計算します。同様に、カナリアのマニフェストを再読み込みし、保存されたすべてのプライバシー検査対象を独立して再走査するため、ファイルのダイジェストを再設定しても、仕込まれた秘密情報の検出結果をレポートから隠すことはできません。秘密情報のみを変える各実行では、所有者だけがアクセスできる、フィルターをかけていないループバックの pcap、tcpdump の生の標準エラー出力とドロップ数ゼロの統計、正規ポートマニフェスト、まとめられたアクセス制限付きソースアーカイブ、全ピアの原子性観測を保存する必要があります。最終検証器は公開された要約を信頼せず、保存されたバイト列から、ポートに結び付けたパケット分割、ソースの射影、基準状態から終了状態までの原子性検査を再実行します。

アーカイブには、すべての必要なプライバシーサーフェスについて、正確な左右のファイルパス、種類、バイト長、および SHA-256 暗号学的ダイジェストを結び付ける標準的なペアトラフィックカウントおよび差分ペア技術マニフェストも含める必要があります。その宣言されたルートは、正確にペアになったアーカイブのインベントリを含まなければなりません。検証者は、通常の表面に対して、等しい全ファイルサイズと JSON の公開形状を必要とします。エントロピーを含む生ループバックキャプチャおよびパックされた制限付きソースアーカイブは明示的なサイズ例外です；代わりにパケットリンクタイプとパケットごとの長さ、制限付きソースの識別、および固定形状の行長を比較します。すべての Torii リクエスト/レスポンス、公開/制限された P2P パケット、ブロック、クエリ、イベント、ログ、テレメトリトラフィックのカウントも一致する必要があります。パケット形状の変更、同サイズの構造的漏洩、偽の出所の主張、または、ペアになっていないファイルは、漏洩報告書とその暗号ハッシュを書き換えることで隠すことはできません。
