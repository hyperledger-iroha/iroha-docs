# 賢明な契約 {#smart-contracts}

Iroha 取引は, `Executable` の役に立たない負荷を実行する.現在のデータモデルでは:

- `Executable::Instructions`: Iroha 特別指示の順序付けされたセット
- `Executable::ContractCall`: 展開された契約インスタンスの副参照呼び出し
- `Executable::Ivm`: Iroha VM バイトコード
- `Executable::IvmProved`: Iroha VM バイトコードで,事前に計算された指示の重複と証明義務がある

Kotodama は Iroha の高水準スマートコントラクト言語です。`.ko` ソースファイルは決定論的な IVM バイトコードにコンパイルされ、通常はデプロイ用の `.to` アーティファクトとして保存されます。Kotodama の対象は IVM のみです。RISC-V や WebAssembly は対象ではありません。

最初のリリースでサポートされるのは ABI バージョン 1 のみです。syscall と pointer-ABI のポリシーはコントラクトの受け入れ時および実行時に無条件で適用され、実行時互換性を切り替える設定はありません。

## 賢明 な 契約 を いつ 使う か {#when-to-use-smart-contracts}

取引を直接表現できる場合,通常の指示を使用する.

- 登録または非登録物件
- ミント,バーン,または転送資産
- 更新されたメタデータ
- 許可を授与または撤回する
- トイガーを実行する
- チェーン上のパラメータを設定する

スマートコントラクトを使用すると,トランザクションがパケットされた論理を必要とし,静的な指示シーケンスとして表現するのが難しい場合,またはデプロイされた契約インスタンスを参照で呼び出す必要があるとき.

## IVM 実行可能 {#ivm-executables}

`Executable::Ivm`には原始の IVM バイトコードがあります.ノードは,そのバイトコードをチェーンに設定された実行時間制限内に実行します.バイトコードが小さく決定的に保持されます.契約はトランザクション実行の一部であり,したがって合意に影響を与える.

`Executable::IvmProved`は,防弾を運ぶ流れのために設計されている.

- IVM バイトコード
- 決定的な指示の重複
- 実行イベントのコミットメント
- ガス政策へのコミットメント

証明は,実行されたバイトコードにオーバーレイを結びつけます.パイプラインポリシーによって,検証者は追加の安全チェックとして証明を実行を確認し再演出することができます.

## 配備された契約電話 {#deployed-contract-calls}

`Executable::ContractCall` はアドレスでデプロイされた契約インスタンスを呼び出す.契約コードが別々に登録され,取引はバイトコードを毎回運ぶ代わりに参照で呼び出すべきである場合,これを使用します.

## 契約寿命と所有権 {#contract-lifecycle-and-ownership}

各部署されたアドレスは,契約が無効であるときも `ContractLifecycleControlV1` の記録を保持する.この記録には,最初の部署の源泉,現在のおよび待機中の所有者,撤回可能な議会代表団,アクティブコードハッシュ,ゼロ以外の比較・交換修正が含まれます.直接部署は,提出するアカウントを所有者として指定し,部署の起源として記録します.議会部署は議会を所有者として指定し,その提案者,提案内容 ID を登録します.ID での成功の治理試みは,出産のみである.

構成されている保護された名前の空間は,議会の展開のために確保されています. `CanRegisterSmartContractCode`保有者はアーティファクトの登録を許可しますが,直接に権限を与えるわけではありません保護された命名空間への部署または原始の活性化.そこで最初のライフサイクルの記録は,欧州議会が認定した部署経路によって作成されなければならない.

ライフサイクルの所有者は1つのアカウントまたは議会である.口座所有権変更は `OfferContractOwnership` を使用し,その後に待機している所有者の `AcceptContractOwnership` を使用する;現在の所有者は請求書を撤回することができる.`CancelContractOwnershipOffer`で受け入れられないオファー. 承認は,議会の代表団をクリアする.アカウントが契約を所有している間または未開設されたオファーを保有している間,口座移除は拒否される.

アカウントの所有者は,議会が契約をアップグレードしたり,アクティブ化したり,無効化したりして,その権限を取り消すことができる. 代表団は,議会に所有権を譲渡したり,代表団を変更したりすることは決して許さない. 議会が所有する変更と議会の承認は,認定された統治効果によって制定されます.

RAW `ActivateContractInstance`および `DeactivateContractInstance`の指示は,行動口座所有者にのみ提供される.それらは記録の正確な `expected_revision`を載せなければならない.古いまたはゼロ修正は閉じることができません.原発アクティベーションはライフサイクル記録を作成できず,登録されたアーテファクト,マニフェスト,および ABI を変更する前に有効化します `active_code_hash`.無効化 アクティブコードハッシュをクリアしますが,所有権と起源を維持します. ライフサイクルのすべての成功的な移行は修正を加速し,完全なポストステートを発行します.

緊急段階の議会提案は,完全な議会パイプラインを通じてのみ,最初の政策陪審員席のうち少なくとも三分の2の"Aye"票で停止を課すことができる.この停止は現在の修正,コードハッシュ,およびゼロでないインシデントダイジェストに結合し,最大3600ブロックまで持続する.呼び出しと触発実行のみを停止できます:拡張またはコード,所有権,代引きを変更することはできません.呼び出しおよび一致する触発実行は,課金高度から有効期限までブロックされています.Expiry は自動で実行を復元しますが,阻害を消さない.証明された `CompleteEmergencyHoldRetrospective` アクションは,記録がクリアされる前に正確な阻害 IDs を結合し,非ゼロの発見根を加えて消化する必要があります.その後期調査が完了するまで,別の阻害を課すことはできません.

アプリ API が有効になったとき,保存状態を `GET /v1/gov/contracts/{contract_address}` で読む.その `found` フィールドは,ライフサイクルの記録が存在することを意味し,アドレスには現在アクティブコードがあるわけではない.

## 運用ガイドライン {#operational-guidance}

- 契約を決定的に保つ.契約行動は,ローカルウォールクロック時間,ホストファイルシステム状態,ネットワーク通話,または他のピアローカル入力に依存してはならない.
- バイトコードが大きいので,トランザクションのサイズとブロック拡散コストは増加します.
- 簡単なレジャー変更のために入力された指示を好みます. 監査が容易で実行は安くです.
- 契約のアップグレードと登録許可をリスクの高い運用制御とみなす.
