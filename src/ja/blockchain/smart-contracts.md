# スマートコントラクト {#smart-contracts}

Iroha トランザクションは`Executable`ペイロードを実行します。現在のデータモデルは以下をサポートしています:

- `Executable::Instructions`：順序付けられた Iroha 命令操作の集合
- `Executable::ContractCall`: デプロイされたコントラクトインスタンスへの参照による技術的呼び出し
- `Executable::Ivm`: Iroha VM バイトコード
- `Executable::IvmProved`: Iroha VM 事前計算された命令オーバーレイと暗号学的コミットメント値を持つバイトコード

Kotodama は Iroha の高レベルスマートコントラクト言語です。`.ko`ソースファイルは決定論的な IVM バイトコードにコンパイルされ、通常はデプロイのために`.to`アーティファクトとして保存されます。Kotodama は IVM のみを対象としています。RISC-V や WebAssembly は対象としていません。

最初のリリースは ABI バージョン1 のみをサポートします。システムコールおよびポインタ-ABI ポリシーは、アドミッションと実行によって強制される1つの無条件の V1 契約であり、代替のソフトウェア実行モードはありません。

## スマートコントラクトを使用する時 {#when-to-use-smart-contracts}

取引を直接表現できる場合は、通常の指示を使用してください:

- オブジェクトを登録または登録解除する
- 資産を発行、破壊、または譲渡する
- メタデータを更新する
- 権限を付与または取り消す
- トリガーを実行する
- オンチェーンパラメータを設定する

取引に静的な命令列として表現するのが不便なパッケージ化されたロジックが必要な場合、またはデプロイされた契約インスタンスを参照によって呼び出す必要がある場合は、スマートコントラクトを使用してください。

## IVM 実行可能ファイル {#ivm-executables}

`Executable::Ivm` は生の IVM バイトコードを運びます。ノードはチェーンに設定されたソフトウェアの実行制限内でそのバイトコードを実行します。バイトコードは小さく決定論的に保つ必要があります；コントラクトはトランザクションの実行の一部であり、そのためコンセンサスに影響を与えます。

`Executable::IvmProved` は証明付きフロー向けに設計されています。これには以下が含まれます:

- IVM バイトコード
- 決定論的命令オーバーレイ
- 実行イベントの暗号コミットメント値
- ガスポリシー暗号化コミットメント値

その証明は、オーバーレイを実行されたバイトコードに結び付けます。ソフトウェア処理のワークフローポリシーに応じて、検証者は証明を検証し、追加の安全確認として実行を再現することができます。

## 展開されたコントラクトの呼び出し {#deployed-contract-calls}

`Executable::ContractCall` は、アドレスによってデプロイされたコントラクトのインスタンスを呼び出します。コントラクトコードが別途登録されており、トランザクションが毎回バイトコードを持ち運ぶのではなく、参照によって呼び出す必要がある場合に使用します。

## 契約のライフサイクルと所有権 {#contract-lifecycle-and-ownership}

すべてのデプロイ済みアドレスは、契約が非アクティブな場合でも、`ContractLifecycleControlV1` レコードを保持します。このレコードには、不変の初回デプロイの起源、現在および保留中の所有者、取り消し可能な議会委任、アクティブなコードの暗号ハッシュ、ゼロでない比較・交換リビジョンが含まれます。および保持されている緊急ホールド。直接のデプロイメントはデプロイするアカウントを記録します。議会によるデプロイメントは、その提案者、提案内容ID、および成功したガバナンス試行IDを記録します。

ライフサイクルのオーナーは、アカウントのいずれか一つ、または議会です。アカウント所有権の変更は別のオファーと承諾を使用します。オファーを受け入れると、議会の委任はすべて解除されます。アカウントの所有者は、議会に契約を有効化または無効化することを許可し、その後その委任を取り消すことができますが、委任によって議会が所有権を移転することは決してできません。議会所有の変更と議会の承認は、認証されたガバナンス効果を通じて実行されます。

生の `ActivateContractInstance` および `DeactivateContractInstance` の指示は、現在のアカウント所有者のみが利用できます。それらはレコードの正確な `expected_revision` を保持する必要があります。古いまたはゼロの改訂では閉じることに失敗します。生のアクティベーションではライフサイクルレコードを作成できず、`active_code_hash`を変更する前に登録されたアーティファクト、技術マニフェスト、ABI を検証します。無効化はアクティブなコードの暗号ハッシュをクリアしますが、所有権と出所は保持します。すべてのライフサイクル遷移が成功すると、リビジョンが進み、完全なポスト状態が出力されます。

アクティベーションは、ステージ1のマニフェストで宣言されたライフサイクルフックもステージングできます。技術マニフェストに `EntryPointKind::Hajimari` エントリポイント (`hajimari`/`始まり`) を含む最初のアクティベーションは、`Hajimari` をステージングします。技術マニフェストに `EntryPointKind::Kaizen` エントリポイント (`kaizen`/`改善`) を含むコードにアクティブなアドレスを再バインドすると、`Kaizen` ステージが発生します。バインディングは直ちに変更されますが、契約はまだ準備ができていません:正確なステージされたフックが成功するまで、すべての `Kotoage` および `View` の技術的呼び出しは拒否されます。フックが保留中の場合、別のアクティベーションも拒否されます。

同じ契約アドレスで `Executable::ContractCall` を使用してステージングされたフックを、新しいコードの暗号ハッシュとともに呼び出し、正確な `hajimari` または `kaizen` エントリーポイントと、その技術マニフェストで宣言された引数を使用してください。ソフトウェアランタイムはアドレスおよびセレクタのスコープを持つ`CanInvokeContractEntrypoint`権限を供給します。要求するクライアントはその権限を作成したり付与したりしてはなりません。保留中のマーカーにはランタイム生成の決定論的な`transition_id`と新しい`code_hash`が含まれます。`Kaizen`マーカーにも`previous_code_hash`が含まれます。クライアントは `transition_id` を計算も提出もしません。フックが成功するとマーカーは原子的に消費され、フックが失敗すると後で再試行できるように保留されたままになります。

緊急レベルの議会提案は、現在のリビジョン、コードの暗号ハッシュ、およびゼロでないインシデント暗号ダイジェスト値を拘束する場合、最大3,600ブロックのホールドを課すことができます。技術的な呼び出しは、課された高さから有効期限の高さまで（有効期限の高さを含まずに）ブロックされます。期限切れは実行を復元しますが、保留を消去することはありません。認定された`CompleteEmergencyHoldRetrospective`アクションは、記録がクリアされる前に、正確な保留IDと暗号学的ダイジェスト値に加えてゼロ以外の発見ルートを後で確定する必要があります。その回顧が未解決の間、別の保留を課すことはできません。

アプリ API が有効になっているとき、保持されている状態を `GET /v1/gov/contracts/{contract_address}` で読み取ります。その `found` フィールドは、ライフサイクルの記録が存在することを意味しており、アドレスに現在アクティブなコードがあることを意味するわけではありません。

## 運用ガイダンス {#operational-guidance}

- 契約を決定論的に保つこと。契約の挙動は、ローカルシステムの時計時間、ホストのファイルシステムの状態、ネットワークリクエスト、または他のピアローカルの入力に依存してはなりません。
- ペイロードはコンパクトに保つ。大きなバイトコードはトランザクションのサイズとブロックの伝播コストを増加させる。
- 簡単なブロックチェーン台帳の変更にはタイプされた指示を好む。それらは監査がしやすく、実行するのも安価である。
- 契約のアップグレードおよび登録権限を高リスクの運用管理として扱う。
