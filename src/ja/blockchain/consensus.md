# コンセンサス {#consensus}

トランザクションは、Sumeragi がそれらをブロックで提案する前にキューに入ります。バリデーターは独立して提案を検証および実行し、再現できる状態遷移にのみ署名します。必要なバリデーターの定足数がその結果に同意し、対応するペイロードが利用可能になった後、ブロックが確定されます。

すべての Iroha 3 ネットワークは、署名済みの RS16 データ可用性技術マニフェストとチャンク、さらに認定機関による回復を使用します。データの可用性は合意形成の要件であり、任意のデプロイメント機能ではありません。

## Sumeragi {#sumeragi}

Sumeragi は Iroha のビザンチン障害耐性コンセンサスエンジンです。キューからトランザクションを取得し、バリデータネットワークのピアが同意します順序付けられたブロックであり、十分な数のバリデーターが同じ結果を再現し、コンセンサス確定証明書に署名した後にのみ、そのブロックを確定します。

### 提案およびコンセンサスの最終化の経路 {#proposal-and-commit-path}

Sumeragi はブロックチェーン台帳を一度に1ブロックずつ進めます。各ブロック高さにおいて、1人のバリデーターが現在のビューの提案者として行動します。提案者はキューから適格なトランザクションを取り出し、候補ブロックを構築し、その提案をアクティブなバリデーターセットに通知します。

同じ Sumeragi ソフトウェア処理ワークフローは、許可型および指名証明付きステーク（NPoS）展開の両方で使用されます。

1. バリデーターはキューに入ったトランザクションからブロックを提案します。
2. バリデータは、同じワールドステートに対してトランザクションを実行することによって提案を検証します。
3. バリデーターは、現在の高さとビューに対して、投票とコンセンサスクォーラム証明書を交換します。
4. コンセンサスの最終確定の定足数に達すると、ネットワークのピアはブロックを確定し、ワールドステートを更新します。

バリデーターは、自分がローカルで再現できるデータにのみ署名します。投票する前に、バリデーターは提案が期待されるチェーン、高さ、ビューに属しているか、トランザクションの署名と制限がプロトコル規則を満たしているか、実行レーンのルーティングと実行者の検証が決定的であるかを確認します。そして、ペイロードを実行すると、期待された状態遷移が生じます。もしローカルの結果が異なる場合、バリデーターはそれに投票するのではなく、提案を拒否します。

投票は小さな署名付きのコンセンサスメッセージです。それらは提案されたブロック、高さ、ビュー、そしてバリデーターの身元を指します。検証された署名はコンセンサスの準備および確定の証明書を形成します。コンセンサス最終化証明書は、十分な数のバリデーターが同じブロックに対して同じ結果を観測したことの確実な証拠です。各バリデーターは自身の本会議への準備および最終化段階の投票；任意のバリデーターが必要な同等の票を集計し、得られた証明書をブロードキャストできます。

### 定足数とオブザーバー {#quorum-and-observers}

最初にリリースされたプロトコルでは、正確な `3f + 1` 投票委員会のみが認められ、検証者は4人から31人までです。したがって、有効なサイズは4、7、10など、31までです。`n = 3f + 1`の場合、ビザンチンフェイルト予算は`f`であり、プロトコルの最終化定足数は`2f + 1`です。ブロックチェーンのジェネシス生成と起動時の検証では、他の委員会構成はすべて拒否されます。

オブザーバーネットワークのピアは確定済みブロックを同期できますが、提案、投票、またはコンセンサス確定定足数へのカウントは行いません。ローカルでのクエリ能力、インデックス作成、監視が必要なデプロイメントではオブザーバーを使用してください。または、投票権を持つバリデーターの数を増やすことなく、地域ブロックの複製。

### 変更と復元の表示 {#view-changes-and-recovery}

ビューは、特定の提案者とタイミング計画で1つの高さを確定しようとする Sumeragi の試みです。提案、ペイロード、投票、またはコンセンサスの確定の進行が停滞した場合、コンセンサスのペースメーカーは高さを後のビューに移動させることができます。ビューの変更は、確定されたブロックを書き換えるものではありません。これは、検証者がまだ確定していない高さを完了しようとする方法を変更し、ネットワークのピアが矛盾するブロックを確定しないように、既知の最高の定足数またはコンセンサス確定の証拠を引き継ぎます。

ペイロードの回収は、最終決定とは別です。ネットワークのピアは、完全なブロックペイロードを受け取る前に、定足数またはコンセンサスの最終化証明書を受け取ることがあります。その場合、ネットワークピアは署名された RS16 ペイロードチャンクまたは認証済みボディを要求し、回復したバイトを公開された暗号ハッシュと照合して検証し、その後にのみブロックをワールドステートおよび Kura に適用します。

### コンセンサスモード {#consensus-modes}

選択したモードは、バリデーター集合の構成方法と運用方法を制御します。このモードは署名済みジェネシスの [`consensus_mode`](/ja/reference/genesis.md) で宣言され、各ブロック高のコンテキストに固定されます。ローカルの `[sumeragi]` 設定で選択できるのは、ノードの役割と、ブロック、キュー、ランタイム、ストレージ、キーポリシーに関する有限の上限だけです。モードやブロック生成間隔を上書きすることはできません。すべてのバリデーターで、同じ署名済みジェネシス、トポロジー、信頼済みピア情報、有効な Sumeragi パラメーターを使用する必要があります。

|モード|最適|バリデータセット|運用の焦点|
| ------------ | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
|許可された|プライベート、コンソーシアム、オペレーター管理ネットワーク|バリデータは、展開によって合意された信頼できるネットワークピアのトポロジーから来ます|すべてのバリデータを同じ署名されたブロックチェーンのジェネシス、信頼できるネットワークピア、ネットワークピアキー、および Sumeragi パラメータに保持してください|
|NPoS|公開または Nexus 指向のネットワークで、検証は指名とステークポリシーに従って行われる|バリデーターは通常エポックごとにNPoSプロファイルによって選ばれ、BLS キーと所有証明（Proofs-of-Possession）が必要です|ステークデータのスナップショット、署名済みエポックおよび選挙入力、バリデーター PoPs、およびネットワーク全体で整合した不変のブロックカデンツを保持する|

::: tip 許可制モード

バリデータの名簿が明示的な運用上の選択である場合は、許可モードを使用してください。これは、自身でホストする Iroha ネットワークの通常の出発点です。なぜなら、メンバーシップの変更は、意図的なガバナンスまたは管理者の行動だからです。重要な運用ルールは、すべてのバリデーターがブロックチェーンのジェネシス、信頼できるネットワークピア、BLS 所有権証明、そして Sumeragi パラメータを同じ見解で実行しなければならないということです。異なるトポロジーや署名付きブロックチェーンのジェネシスを持つ単一のネットワークピアが、ネットワークの確定を妨げる可能性があります。

:::

::: tip NPoSモード

デプロイメントプロファイルが指名およびステーク状態によるバリデータの参加を想定している場合は、NPoSモードを使用してください。パブリック SORA Nexus デプロイメントは NPoS を使用し、生成されたプロファイルには BLS バリデータの識別情報、所有証明、エポック設定が含まれます。および Sumeragi のNPoSパラメータは起動時に必要です。エポックの変更により、定義されたブロック高さでアクティブなバリデータセットを置き換えることができるため、オペレーターはコンセンサスの健全性と、次のロスタに反映されるステークまたは指名の状態の両方を監視する必要があります。

:::

## マルチレーン合意 {#multilane-consensus}

Iroha のマルチレーンコンセンサスパスは、Nexus の実行レーンとデータスペース構成を通じて実装されています。各実行レーンごとに別々のコンセンサスインスタンスを開始することはありません。 Sumeragi は依然として1つの注文されたブロックストリームを最終化します；実行レーンは、取引がそのストリーム内でどのようにルーティングされ、スケジュールされ、会計処理され、保存されるかを説明します。

ソフトウェアのランタイム構成は、3つの実行レーンの状態を構築します:

- `nexus.lane_catalog`：それぞれ数値の`LaneId`、エイリアス、データスペース、可視性、ストレージプロファイル、証明スキーム、およびメタデータを持つ、設定された実行レーン。
- `nexus.dataspace_catalog`：構成されたデータスペースで、それぞれに数値の`DataSpaceId`とリレイ委員会のサイズ決定に使用されるフォールトトレランス値があります。
- `nexus.routing_policy`：アカウントや命令経路と一致することができるデフォルトのレーン/データスペースのペアと順序付きルーティングルール。

取引がキューに入ると、実行レーンルーターはそれを次のものに解決します `RoutingDecision { lane_id, dataspace_id }`. 単一レーンモードでは、これは常に実行レーンです `0` そしてユニバーサルデータスペースで。 Nexus モードでは、設定されたルーターがデータスペースにスコープされたルール、金融取引決済ルーティング、アカウントルールを適用します。 明示的なルーティングルール、そして最後にデフォルトルート。解決された実行レーンとデータスペースは、それぞれのカタログに存在しなければなりません。 そして、実行レーンは解決されたデータスペースにバインドされなければなりません。さもなければ、トランザクションはキューに入る前に拒否されます。

キューは、このルーティングの決定をトランザクションの暗号ハッシュと一緒に保持するため、後の段階で再度推測する必要がありません。その後、プロポーザルの構築では、実行レーンのメタデータを2つの方法で使用します：

- それはトランザクションを実行レーンごとに交互に配置するので、ある実行レーンが単にそのトランザクションが先にキューに入れられたからといってブロックを支配することはありません。
- これは、各レーンのトランザクション実行ユニット（TEU）の制限を適用します。実行レーンの設定された容量を超えるトランザクションは保留され、再キューに入れられますが、デッドロックを回避するために、最初の過負荷トランザクションは実行レーンに受け入れられる場合があります。

候補準備の際、Sumeragi は提案されたペイロードを実行レーンとデータスペースごとに集約し、レーンローカルのデータ可用性の識別子を導出します。記録された合計には、トランザクション数、チャンク、ペイロードバイト、および TEU が含まれます。プロトコルの最終化後、それらの合計は認証済み Sumeragi 診断を通じて公開される実行レーンおよびデータ空間の暗号的コミットメント値データスナップショットとなる。もしブロックが実行レーンの金融取引清算プロトコル結果記録を含む場合、ブロック処理は実行レーンの金融取引清算暗号的コミットメント値およびリレーも作成しますブロックヘッダー、コンセンサス最終化証明書、バインディング値のデータ可用性暗号ハッシュ、金融取引決済証明、および実行レーンペイロードサイズを結合するデータコンテナ。

## データの可用性とペイロードの回収 {#data-availability-and-payload-recovery}

Sumeragi v2は、署名済みの RS16 `PayloadManifest`および`PayloadChunk`メッセージを通じて、グローバルなペイロードの可用性を提供します。リーダーは署名済みの技術マニフェストを全委員会に送信し、最初にSet Aに決定論的なチャンクを分配します。バリデータは、標準の本文を再構築し、技術的マニフェストとチャンクの暗号ハッシュを検証し、本文を耐久的に保存した後にのみ、投票の準備を行うことができます。そして決定的検証の完了。高速パスが停止した場合、リカバリはチャンク配信をセットBに拡張します。認証済み本体のリカバリとブロック同期は、ネットワークのピアが本体を受け取る前に最終性を学習した場合に、有限のリカバリパスを提供します。

マルチレーン実行はさらに、各実行レーン対象の決定論的ペイロード所有権暗号ハッシュおよびレーンローカル RBC インスタンス暗号ハッシュを導出します。これらのアイデンティティは、実行レーンの提案と証明書をグローバルコンテナ取引に結び付けます。それらは別のグローバルコンセンサスセッションではありません。ブロックは、ネットワークピアが有効なコンセンサス最終証明書と一致するペイロードをローカルに持っている場合にのみ、最終化されます。

別の RBC API エンドポイントではなく、認証済みのオペレーターサーフェスを使用してください:

- `iroha --operator-private-key-file <path> --output-format text ops sumeragi status` は、権威のある身長、視野、段階、証明書、および生存状態を報告します。
- `iroha --operator-private-key-file <path> --output-format text ops sumeragi diagnostics` は、非権威キュー、ソフトウェア処理ワークフロー、NPoS、実行レーン、および実行レーンのペイロード所有権を含むデータスペース診断を報告します。
- Prometheus のシグナルには `sumeragi_missing_block_requests`、`sumeragi_missing_block_oldest_ms`、`sumeragi_missing_block_fetch_total`、`sumeragi_da_gate_block_total`、`sumeragi_da_gate_satisfied_total` があり、欠落したボディの回復、データ可用性ゲート、およびメッセージ処理を区別します；詳細は [パフォーマンスと指標](/ja/guide/advanced/metrics.md) を参照してください。

Kura はストレージレイアウトのために派生された実行レーン構成を使用します。各実行レーンは `blocks/lane_000_core` や `merge_ledger/lane_000_core_merge.log` のような決定論的なストレージ名を受け取り、実行レーンのライフサイクルの変更によって、グローバルブロックの順序を変更することなく、これらのセグメントをプロビジョニング、廃止、またはラベル変更することができます。
