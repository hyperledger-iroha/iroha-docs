# コンセンサス {#consensus}

トランザクションは、Sumeragi がそれらをブロックで提案する前にキューに入ります。バリデーターは独立して提案を検証および実行し、再現できる状態遷移にのみ署名します。必要なバリデーターの定足数がその結果に同意し、対応するペイロードが利用可能になった後、ブロックが確定されます。

すべての Iroha 3 ネットワークは、署名済みの RS16 データ可用性技術マニフェストとチャンク、さらに認定機関による回復を使用します。データの可用性は合意形成の要件であり、任意のデプロイメント機能ではありません。

## Sumeragi {#sumeragi}

Sumeragi は Iroha のビザンチン障害耐性コンセンサスエンジンです。キューからトランザクションを取得し、バリデータネットワークのピアが同意します順序付けられたブロックであり、十分な数のバリデーターが同じ結果を再現し、コンセンサス確定証明書に署名した後にのみ、そのブロックを確定します。

### 提案およびコンセンサスの最終化の経路 {#proposal-and-commit-path}

Sumeragi は、ブロック高を一つずつ進めながら台帳を更新します。各高さでは、一つのバリデーターが現在のビューの提案者になります。提案者はキューから処理対象のトランザクションを取り出し、候補ブロックを構築して、稼働中のバリデーター集合に提案を通知します。処理待ちのトランザクションがないチェーンは空ブロックを生成しません。

同じ Sumeragi ソフトウェア処理ワークフローは、許可型および指名証明付きステーク（NPoS）展開の両方で使用されます。

1. バリデーターはキューに入ったトランザクションからブロックを提案します。
2. バリデータは、同じワールドステートに対してトランザクションを実行することによって提案を検証します。
3. バリデーターは、現在の高さとビューに対して、投票とコンセンサスクォーラム証明書を交換します。
4. コンセンサスの最終確定の定足数に達すると、ネットワークのピアはブロックを確定し、ワールドステートを更新します。

バリデーターは、自分がローカルで再現できるデータにのみ署名します。投票する前に、バリデーターは提案が期待されるチェーン、高さ、ビューに属しているか、トランザクションの署名と制限がプロトコル規則を満たしているか、実行レーンのルーティングと実行者の検証が決定的であるかを確認します。そして、ペイロードを実行すると、期待された状態遷移が生じます。もしローカルの結果が異なる場合、バリデーターはそれに投票するのではなく、提案を拒否します。

投票は小さな署名付きのコンセンサスメッセージです。それらは提案されたブロック、高さ、ビュー、そしてバリデーターの身元を指します。検証された署名は、準備段階と確定段階のクォーラム証明書を形成します。確定証明書は、十分な数のバリデーターが同じブロックに対して同じ結果を観測したことの永続的な証拠です。集合 A のバリデーターは通常、Prepare 投票と Commit 投票をそのラウンドのプロキシテールに送り、プロキシテールは必要な数の同等の票を過不足なく集約して証明書をブロードキャストします。証明書の到着が遅れている場合は、集合 B のバリデーターもプロキシテールに投票します。最後の手段として、すべてのバリデーターが自身の投票をブロードキャストし、任意のバリデーターが証明書を集約できます。

### 定足数とオブザーバー {#quorum-and-observers}

初回リリースのプロトコルでは、投票委員会のバリデーター数は4から31までの範囲で、厳密に `3f + 1` を満たす必要があります。有効な人数は4、7、10、…、31です。`n = 3f + 1` の場合、許容するビザンチン障害数は `f`、コミットの定足数は `2f + 1` です。ジェネシス生成時と起動時の検証は、それ以外の委員会構成を拒否します。PrepareQC、CommitQC、TimeoutCert はいずれも、等しい重みのバリデーター票を厳密に `q = n - f` 票含みます。それを超える署名者集合は拒否されます。

オブザーバーネットワークのピアは確定済みブロックを同期できますが、提案、投票、またはコンセンサス確定定足数へのカウントは行いません。ローカルでのクエリ能力、インデックス作成、監視が必要なデプロイメントではオブザーバーを使用してください。または、投票権を持つバリデーターの数を増やすことなく、地域ブロックの複製。

### 変更と復元の表示 {#view-changes-and-recovery}

ビューは、特定の提案者とタイミング計画で1つの高さを確定しようとする Sumeragi の試みです。提案、ペイロード、投票、またはコンセンサスの確定の進行が停滞した場合、コンセンサスのペースメーカーは高さを後のビューに移動させることができます。ビューの変更は、確定されたブロックを書き換えるものではありません。これは、検証者がまだ確定していない高さを完了しようとする方法を変更し、ネットワークのピアが矛盾するブロックを確定しないように、既知の最高の定足数またはコンセンサス確定の証拠を引き継ぎます。

ペイロードの回収は、最終決定とは別です。ネットワークのピアは、完全なブロックペイロードを受け取る前に、定足数またはコンセンサスの最終化証明書を受け取ることがあります。その場合、ネットワークピアは署名された RS16 ペイロードチャンクまたは認証済みボディを要求し、回復したバイトを公開された暗号ハッシュと照合して検証し、その後にのみブロックをワールドステートおよび Kura に適用します。

### コンセンサスモード {#consensus-modes}

選択したモードが、バリデーター集合の構成方法と運用方法を決めます。このモードは署名済みジェネシスの[`consensus_mode`](/ja/reference/genesis.md)で宣言され、各ブロック高の文脈に固定されます。ローカルの `[sumeragi]` 設定が指定するのは、ノードの役割、署名の保管・管理、安全性記録のパス、および文書化されたタイムアウトと同期設定の上書きです。ブロックとトランザクションの上限、合意モード、ブロックの間隔は、署名済みジェネシスとコミット済み状態から取得します。バリデーター間で、署名済みジェネシス、トポロジー、信頼するピアの情報、有効な Sumeragi パラメーターが一致している必要があります。

|モード|最適|バリデータセット|運用の焦点|
| ------------ | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
|許可された|プライベート、コンソーシアム、オペレーター管理ネットワーク|バリデータは、展開によって合意された信頼できるネットワークピアのトポロジーから来ます|すべてのバリデータを同じ署名されたブロックチェーンのジェネシス、信頼できるネットワークピア、ネットワークピアキー、および Sumeragi パラメータに保持してください|
| NPoS | 指名とステークのポリシーに従って検証する公開ネットワーク、または SORA Nexus 向けネットワーク | バリデーターは通常エポックごとに NPoS プロファイルで選ばれ、BLS 鍵と所有証明（Proofs-of-Possession）が必要 | ステークのスナップショット、署名済みのエポック・選出入力、バリデーターの PoPs、不変のブロック間隔をネットワーク全体で一致させる |

::: tip 許可制モード

バリデータの名簿が明示的な運用上の選択である場合は、許可モードを使用してください。これは、自身でホストする Iroha ネットワークの通常の出発点です。なぜなら、メンバーシップの変更は、意図的なガバナンスまたは管理者の行動だからです。重要な運用ルールは、すべてのバリデーターがブロックチェーンのジェネシス、信頼できるネットワークピア、BLS 所有権証明、そして Sumeragi パラメータを同じ見解で実行しなければならないということです。異なるトポロジーや署名付きブロックチェーンのジェネシスを持つ単一のネットワークピアが、ネットワークの確定を妨げる可能性があります。

:::

::: tip NPoSモード

デプロイメントプロファイルが指名およびステーク状態によるバリデータの参加を想定している場合は、NPoSモードを使用してください。パブリック SORA Nexus デプロイメントは NPoS を使用し、生成されたプロファイルには BLS バリデータの識別情報、所有証明、エポック設定が含まれます。および Sumeragi のNPoSパラメータは起動時に必要です。エポックの変更により、定義されたブロック高さでアクティブなバリデータセットを置き換えることができるため、オペレーターはコンセンサスの健全性と、次のロスタに反映されるステークまたは指名の状態の両方を監視する必要があります。

:::

## マルチレーン合意 {#multilane-consensus}

データスペースは、データ、権限、ポリシー、アプリケーションのための環境を定めます。そこに属するレーンが、データ配信と認証の処理能力を追加します。カタログは別々です。`nexus.dataspace_catalog` はデータスペースを定義し、`nexus.lane_catalog` はそれぞれ一つのデータスペースを参照するレーンを定義します。複数のレーンが同じデータスペースを共有できます。

公開のグローバル実行では、レーン `0` の順序付けをグローバル Sumeragi インスタンスが担います。それ以外の稼働中レーンでは、各世代が、固定された委員会と合意パラメーターを使って同じ Sumeragi コアの独立したインスタンスを実行します。その認証済みブロックには、コミット済みのグローバルアンカーに照らして受け入れ条件を検証した、順序付きのトランザクションバッチが含まれます。レーンの認証はグローバル State を変更しません。

グローバルチェーンは、各レーンから次の連続した認証済みブロックを取り込みます。その結果できたグローバルブロックの実行により、トランザクションが正規の順序で適用され、グローバル CommitQC がその実行を確定します。したがって、レーンの証明書だけでは、トランザクションがグローバル State を変更したと主張するには不十分です。復旧と実行の全過程で、レーンの識別子と世代、アンカーの鮮度、元データの保管責任、連続した取り込み境界の検証を維持します。

コミット済みの `sumeragi_lane_policy` が、固定レーン、経路、委員会、自動スケーリングを統制します。設定カタログだけでは合意に参加するレーンは有効になりません。具体的なデータスペースの対象は、受け入れ済みの適合するレーンに解決される必要があります。利用できないプライベート経路は、ユニバーサルの処理として実行せず拒否します。カタログ更新や有効化の遷移を進められるように、完全な制御プレーンのバッチはレーン `0` を経由します。

独立して署名されたデータスペースのルートは、独自の State とローカルなファイナリティを持つ、別個の実行境界です。データスペースのカタログ項目を登録するだけでは、そのルートは作られません。ルートをまたぐ原子性には、別の AMX プロトコルを使います。固定された候補では、この経路の金銭的な処理とネットワーク全体についての適格性検証がまだ完了していません。

固定されたソースの[レーン実装](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/crates/iroha_core/src/sumeragi/lanes/mod.rs)、[レーンの仕様](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/specs/sumeragi_lanes.md)、[独立したデータスペースの仕様](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/specs/sumeragi.md)、[適格性検証の状況](https://github.com/hyperledger-iroha/iroha/blob/c8c872461e92f04325c350cdd952f4276e96f9dc/specs/sumeragi_goals.md)を参照してください。

## データの可用性とペイロードの回収 {#data-availability-and-payload-recovery}

Sumeragi V1 は、署名付きの RS16 `PayloadManifest` メッセージと `PayloadChunk` メッセージによって、グローバルなペイロードの可用性を確保します。リーダーは署名済みマニフェストと署名済みのすべての行を、委員会の他のすべてのメンバーと、次の委員会に加わるメンバーに送ります。バリデーターが Prepare 投票を行えるのは、正規の本体を再構築し、マニフェストとチャンクのハッシュを検証し、本体を永続保存したうえで、決定論的な検証を完了した後だけです。行が欠けているピアは、`PayloadRequest` でそれらを要求します。ピアが本体の受信前にファイナリティを知った場合は、認証済み本体の復旧とブロック同期により、資源使用量を制限した復旧経路を確保します。

各レーンのインスタンスは、固有の認証済み可用性情報と証明書の文脈を使います。グローバルな取り込み検証は、認証済みバッチと元のペイロードを、期待する世代とアンカーに結び付けます。ピアがグローバルなファイナリティを適用するのは、一致するグローバルペイロードと有効な CommitQC をローカルに保持している場合だけです。

別の RBC API エンドポイントではなく、認証済みのオペレーターサーフェスを使用してください:

- `iroha --operator-private-key-file <path> --output-format text ops sumeragi status` は、権威のある身長、視野、段階、証明書、および生存状態を報告します。
- `iroha --operator-private-key-file <path> --output-format text ops sumeragi diagnostics` は、トランザクションキューの逼迫状況、NPoS の選出状態、レーンガバナンスのマニフェスト状態を表示します。これらの情報は権威あるものではありません。
- `sumeragi_fetch_requests_total`（欠落した本体には `kind="body"`、追いつき同期には `kind="sync"`）、`sumeragi_view_changes_total`、`sumeragi_round_stage`、`sumeragi_dropped_total` などのインスタンスごとの Prometheus 系列は `lane` ラベルを持ち、欠落した本体の回復、ビュー変更、上限付きキューでの破棄を区別します。詳細は [パフォーマンスと指標](/ja/guide/advanced/metrics.md) を参照してください。

レーンのブロックストアは、取り込みと復旧に必要な認証済みバッチと取得元の記録を保持します。そのライフサイクルはコミット済みのレーン世代に従います。ストレージディレクトリの名前だけで、新しいレーンや実行ルートが認可されることはありません。
