# I105 口座アドレスの形式 {#i105-account-address-format}

I105 は, Iroha 3 `AccountId` のカノニカルな外部テキストフォーマットである.

負荷は口座管理者を表す.

そのセンチネルは,意図されたネットワークをチェーン識別子で識別する.

API,トランザクション,許可,または查询がカノニカルアカウント ID を要求するどこでも使用します.

I105 アカウント ID はドメインなしです.

I105 ID の他の綴りではなく, `treasury@payments.universal` のような値はアカウントの別名です.

I105 ID を誘導することは,口座の登録や資金調達を行わない.

::: warning 統合の失敗を防ぐ規則

- アドレスをエンコードまたは検証する前に、ネットワークプロファイルを選択してください。
- UTF-8 文字列を正確に保存し比較する.
- 英字の大文字と小文字を保持し、`Unicode` 正規化を適用しないでください。
- I105 ID は, `@domain`または `@domain.dataspace`のサフィックスを持つことができません.
- 1 を使用する Iroha SDK または `iroha tools address`.
- 正規表現は I105 バリデーターではありません。

:::

## 文字通り解剖学 {#literal-anatomy}

I105 文字には,隣接する3つの部分があり,分離者はない.

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

| 部分 | 目的 | チェックサムの対象 |
| ---------------- | ------------------------------------------------------------------ | ----------------- |
| ネットワークセンチネル | テキストを 1 つの `u16` チェーン識別値に対応付ける | 対象外 |
|パイロード |`base-105` カノニカルアカウントコントローラバイトのエンコーディング |覆われている|
| チェックサム | I105 アルファベットで表現した `Bech32m` 形式の 6 個の `5-bit` 値 | N/A |

ペイロードとチェックサムはアカウントコントローラーを識別します。

Sentinelはネットワークコンテキストを選択します.

同じコントローラは Taira と Minamoto の有効負荷とチェックサムを同じものとするが,それぞれのネットワークは異なるリードセンチネルを使用する.

デコーダーは期待されるチェーン識別値を必ず検証しなければなりません。

チェックサムではセンチネルの置き換えを検出できません。

### ネットワーク・センチナー {#network-sentinels}

| ネットワークまたはコンテキスト | チェーン識別値 | Hex | 正規センチネル |
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
|Taira 公共テストネット |                            `369` |`0x0171`|`test`|
|Minamoto 公共ネットワーク |                            `753` |`0x02f1`|`sora`|
|開発状況|                              `0` |`0x0000`|`dev`|
|その他の `u16`値 |`0`,`369`,および `753`を除くすべて.|        — |`n`と最小の十数値,例えば `n42`|

名前付きの値には、常に対応する名前付きセンチネルを使用します。

`n00042`、`n369`、`n753`、`n0` のような形式は正規ではありません。

トランザクションチェーン ID と I105 チェーン識別子は,別々の値である.

エンドポイントまたはチェーン ID を選択することは,暗示的にアドレスのプロフィールを選択するものではありません.

## 標準的な単鍵例 {#normative-single-key-example}

SDK クロスコンプライアンスの固定装置から下記の役に立たない負荷と Minamoto フォームが作成されています.

Taira フォームは,同じ用荷に Taira のセンチネルが適用される.

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

`02 00 01 20`:ヘッダー `0x02`,コンパクトシングルキータグ `0x00`,曲線`Ed25519` ID `0x01`,および32バイトのキー長さ `0x20`から始まる.

`multihash`前尾は入力メタデータであり,コントローラ用荷にコピーされません.

## 作成および検査 IDs と CLI {#create-and-inspect-ids-with-the-cli}

公共ネットワークでは,名前付きプロフィールを好みます:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

I105 入力を標準化し,アドレスのコードック行動を診断する際に比較します:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

検出されたフォーマット,カノニカルヘックス,および選択したネットワークコンテキストを JSON として検査する.

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

Newline-separated file のアドレス・コデック構造を,解析障害を黙って受け入れずに監査する.

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution CLI 検証境界線

`convert`,`normalize`,および `audit`コマンドは,下層レベルの `AccountAddress` コデックで動作します.

センチネル,アルファベット,チェックサム,バイト長さ, `CurveId`/キー形,および正確なアドレスレイヤの再コーディングを検証します.

`AccountId`は実現しない.

複数のシグ政策のセマンティックを全て検証するわけではありません.

ヘッダークラスがコントローラと一致していることを証明しない.

認可または永続化の前に、厳格な `AccountId` 検証を行ってください。

:::

プライベートネットワークでは、設定済みのチェーン識別値を `--network-prefix` で明示的に指定してください。

既存のアドレスを明示的な文脈間で変換する際に,また `--expect-prefix` をソースに入力してください.

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

再コーディングはネットワークの文脈のみを変化させる.

ターゲットネットワーク上のアカウントを登録したり,同じコントローラがそこに再利用されるべきであることを証明したりしない.

## 暗号化アルゴリズム {#encoding-algorithm}

カノニカルエンコードは以下の操作を実行します.

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

リードする0バイトは,ゼロ値の `base-105`桁として保存されます.

チェックサムでは、`Bech32` の `polymod` 生成子と定数 `0x2bc830a3` を使用します。

チェックサムのみ HRP は, ASCII 文字列 `snx`です.

チェックサム専用の HRP はアドレスに出力されません。

チェックサムの6つの値は `0..31`範囲にあり,用荷と同じ I105 アルファベットで表示される.

### I105 アルファベット {#i105-alphabet}

この105つのシンボルはまさにこの順序で表記されています.

最初の行は `Bitcoin Base58`アルファベットで,数字 `0..57` を含んでいる.

第2行には `58..104` の数字が含まれています.

コデックを実行する際に行をコンカテネートします.

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

文字は `Unicode`に敏感です

正確な配列は, `compatibility-width` 日本語 `kana` シンボルと, `ヰ` と `ヱ` のコードポイントを使用します.

NFC, NFKC,幅変換,ケース折り畳み,または見た目の類似の置き換えを適用しないでください.

ASCII `0`,`O`, `I`,および `l`はアルファベットのシンボルではない.

## カノニカルアカウントの有用な負荷 {#canonical-account-payload}

`base-105` 本文はバイナリアカウントペイロードをエンコードするものであり、公開鍵文字列でも Norito JSON オブジェクトでもありません:

```text
header:u8 || controller:variable
```

以下の複数バイト整数はすべて符号なしで、`big-endian` です。

ドメイン,データスペース,アライアス, UAID,およびアカウントメタデータバイトは存在しません.

### ヘッダーバイト {#header-byte}

|ビット|幅|現在のエンコーダー出力|意味|
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |アドレスフォーマットバージョンフィールド |
| `4..3` |     2 |`0` 単鍵, `1` 多サイン|アドレスクラス |
| `2..1` |     2 |                          `1` |標準化バージョンのフィールド|
| `0`    |     1 |                          `0` |予約された `extension flag`|

現在の V1 エンコードは,単鍵コントローラのためのヘッダー `0x02` と,多シグコントローラ用の `0x0a` を発信する.

`2`と `3`のアドレスクラスは指定されていない.

`extension flag`の `1`は拒否される.

低レベルのデコーダーは他のバージョンと正常化ビット値を保存し,クラスをコントローラタグと比較して独立的にクロスチェックしません.

`AccountId` に変換し、その正規の表現と比較することで、現在の V1 正規性を確認できます。

### 単鍵制御器 {#single-key-controller}

生の公開鍵ペイロードが 255 バイト以下の場合は、コンパクト形式を使用します:

|フィールド|幅|価値や意味|
| ------------ | --------------: | ------------------------ |
|`tag`|1バイト|`0x00`|
|`curve`|1バイト|`CurveId`登録値 |
| `key_len` | 1 バイト | 生の鍵の長さ |
| `public_key` | `key_len` バイト | 生の公開鍵ペイロード |

255 バイトを超える鍵では拡張形式を使用します:

|フィールド|幅|価値や意味|
| ------------ | --------------: | ---------------------------- |
|`tag`|1バイト|`0x02`|
|`curve`|1バイト |`CurveId`登録値 |
| `key_len` | 2 バイト | 生の鍵の長さ、`big-endian` |
| `public_key` | `key_len` バイト | 生の公開鍵ペイロード |

コンパクト形式に収まる鍵に対して、拡張エンコードは正規ではありません。

### マルチシグコントローラ {#multisig-controller}

|フィールド|幅|価値や意味|
| ---------------- | -------: | ------------------------------ |
|`tag`|1バイト|`0x01`|
|`policy_version`|1バイト |現在の価値 `1` |
| `threshold` | 2 バイト | 必要な承認の重みの合計 |
|`member_count`|2バイト|次のメンバーの数 |
|`members`|変数|メンバーの記録を繰り返す|

各メンバーの記録は:

|フィールド|幅|意味|
| ------------ | --------------: | ------------------------ |
|`curve`|1バイト |`CurveId`登録値 |
| `weight` | 2 バイト | メンバーの承認の重み |
| `key_len` | 2 バイト | 生の鍵の長さ |
| `public_key` | `key_len` バイト | 生の公開鍵ペイロード |

有効なポリシーには少なくとも1人のメンバー,ポジティブな重量,複製の公開鍵がないし,メンバーの重量の合計を介して `1` からしきい値があります.

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

正規構築では、署名アルゴリズムの安定した名前、ゼロ区切りバイト、生の公開鍵バイトの順でメンバーを並べ替えます。

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

I105 文字は,マルチシグとポスト量子コントローラーが大きいため,固定文字長さがありません.

### `CurveId`登録 {#curveid-registry}

最後の列には,必要なオプション `Cargo` 機能が記載されている.

ダッシュは,レジストリエントリがオプションのデータモデル機能なしで利用可能であることを意味します.

|ID|署名アルゴリズム|必須の `Cargo`機能|
| ---: | -------------------------------------------- | ------------------------ |
|  `1` |`Ed25519`| —                        |
|  `2` |`ML-DSA`| —                        |
|  `3` |`BLS12-381 normal`|`bls`|
|  `4` |`secp256k1`| —                        |
|  `5` |`BLS12-381 small`|`bls`|
| `10` |`GOST R 34.10-2012 256-bit, parameter set A`|`gost`|
| `11` |`GOST R 34.10-2012 256-bit, parameter set B`|`gost`|
| `12` |`GOST R 34.10-2012 256-bit, parameter set C`|`gost`|
| `13` |`GOST R 34.10-2012 512-bit, parameter set A`|`gost`|
| `14` |`GOST R 34.10-2012 512-bit, parameter set B`|`gost`|
| `15` |`SM2`|`sm`|

配属されていない IDs および受信ビルドで無効化されたアルゴリズムは,拒否されます.

鍵の役に立たない負荷は,申告された `CurveId` によって選択されたアルゴリズムに対しても構造的に有効である.

## 厳格な AccountId 検証と法典性 {#strict-accountid-validation-and-canonicality}

SDK に期待されるチェーン識別値を設定した後、`AccountId` として解析し、返された正規の表現を前後の許可された空白を除去した入力と比較します。

`AccountId`を構築する際に,解析器が解読可能なコントローラー素材を正常化できるため,比較は重要である.

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

信頼性のない文字列の場合,適合したアプリケーションは:

1. 値全体の前後にある、許可された転送上の空白だけを除去します。
2. センチネルを読み,期待される鎖識別子を要求する.
3. `Unicode` の 残りのすべてのシンボルを 正確な105文字のアルファベットでマップします.
4. チェックサムの6桁を分割する
5. ペイロードの各桁を正規バイト列へ戻します。
6. その正規バイト列に対してチェックサムを検証します。
7. ヘッダとコントローラを解析し:
   - フィールドの正確な長さ
   - サポートされた `CurveId`
   - 有効な公開鍵
   - 末尾に余分なバイトがないこと
   - 適用可能な場合,有効なマルチシグポリシー
8. `AccountId` を作る.
9. 期待されるチェーン識別値に対して `AccountId` を正規形式で表現します。
10. 前後の許可された空白を除去した入力との `byte-for-byte` 一致を要求します。

アプリケーションの明示的な最終 `render-and-compare` ステップでは、最小形式でない数値センチネル、非正規のコントローラーレイアウト、並べ替えられたポリシー素材、およびデコードできてもエンコーダーの現在の V1 出力ではないその他の表記を拒否します。

成功したチェックサムまたは低レベルの `AccountAddress`解析は,このチェックを代替するものではありません.

厳格なアカウント-ID フィールドでこれらの値を受け入れない.

- `alice@wonderland.universal`のようなアカウントの偽名
- 末尾に `@domain` サフィックスを付加した I105 リテラル
- 公開鍵 `multihash` のような `ed0120...`
- `0x02000120...`などのカノニカル用荷 Hex
- 誤ったチェーン識別値のアドレス
- 字母大文字や小文字,文字幅, `kana`,使用負荷,またはチェックサムが変更された文字列

アプリケーションの境界線で異名詞を解決し,承認,署名,許可および監査記録のために返還された法典的な I105 ID を保持する. .

### 常識の安定エラーコード {#common-stable-error-codes}

|コード|意味|
| -------------------------------- | ------------------------------------------------------------------- |
|`ERR_UNEXPECTED_NETWORK_PREFIX`|解読された識別子は,要求されるネットワークと一致しない.|
|`ERR_CHECKSUM_MISMATCH`|6つのチェックサムシンボルは,用荷に一致しない|
|`ERR_INVALID_I105_CHAR`|符号は 正確なアルファベットの外にある|
|`ERR_MISSING_I105_SENTINEL`|カノニカル・ネームや数値の哨戒者は見つかりませんでした|
|`ERR_I105_TOO_SHORT`|ボディは 荷物とチェックスマムの両方を収めることはできません|
|`ERR_INVALID_LENGTH`|コントローラーフィールドは 短縮されたり,非定規長さの形式を使用する.|
|`ERR_UNKNOWN_CURVE`|管理者は,指定されていないまたは利用できない `CurveId` を宣言します.|
|`ERR_INVALID_PUBLIC_KEY`|`CurveId`によって選択されたアルゴリズムにとって鍵は無効です.|
|`ERR_UNSUPPORTED_ADDRESS_FORMAT`|入力は認められた法典的な I105 形式ではない.|

## API,貯蔵と表示の規則 {#api-storage-and-display-rules}

- JSON アカウントフィールドに正確な I105 UTF-8 文字列を送信する.
- 完全なアカウント ID を URL パスセグメントに配置する前に `Percent-encode` してください。
- I105 ID の代わりにアカウントエイリアスを使用しないでください。
- `byte-preserving`比較セマンティックでコーデックが返したカノニカル文字列を保存します.
- 英字の大文字と小文字、および文字幅を保持する照合順序を使用してください。
- 輸出されたアカウントデータとバックアップを含むチェーン差別化または命名されたネットワークプロフィールを保持する.
- ネットワークコンテキストのみでアドレスを再利用する.
- 完全なアドレスを表示し、コピー操作を提供してください。
- `kana` のすべての文字を正確に保存する.
- コンパクトディスプレイが真ん中を短縮する時,完全なアドレスを用意してください.
- ID の保存された法典を使用し,偽名から再構築する代わりに.

`AccountId`表示と JSON 使用カノニカル I105.

低レベルの `AccountAddress` ディスプレイ/JSON 表示は,内部およびデバッグコンテキストのためにカノニカルヘックスを使用しています.

外部アカウント ID が必要な場合は、明示的な `AccountAddress` I105 エンコーダーを呼び出してください。

口座作成とアライス解析作業の流れについては, [アカウントおよびアライス](/ja/cookbook/accounts-and-aliases.md) を続行してください.

口座データモデルについては, [会計](/ja/blockchain/accounts.md)を参照してください.
