# I105 アカウント住所形式 {#i105-account-address-format}

I105 は Iroha 3 `AccountId` の正規の外部テキスト形式です。

そのペイロードはアカウントコントローラーを表しています。

そのセンチネルはチェーン識別値を使って対象ネットワークを識別します。

それを、API、取引、許可、またはクエリが標準のアカウントIDを要求する場所で使用してください。

I105 アカウントIDはドメインがありません。

`treasury@payments.universal` のような値はアカウントの別名であり、I105 ID の別の綴りではありません。

I105 IDを取得しても、アカウントの登録や資金の投入は行われません。

::: warning ほとんどの統合失敗を防ぐルール

- アドレスをエンコードまたは検証する前に、ネットワークプロファイルを選択してください。
- 正確に標準的な UTF-8 文字列を保存して比較してください。
- 英字の大文字と小文字を保持し、`Unicode` 正規化を適用しないでください。
- I105 IDには`@domain`または`@domain.dataspace`のサフィックスを付けてはいけません。
- Iroha SDK または `iroha tools address` を使用してください。
- 正規表現は I105 バリデーターではありません。

:::

## 文字通りの解剖学 {#literal-anatomy}

「I105」リテラルは、3つの隣接する部分があり、区切り記号はありません。

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

| 部分 | 目的 | チェックサムの対象 |
| ---------------- | ------------------------------------------------------------------ | ----------------- |
| ネットワークセンチネル | テキストを 1 つの `u16` チェーン識別値に対応付ける | 対象外 |
|ペイロード| `base-105` 標準のアカウントコントローラーバイトのエンコーディング|覆われた|
| チェックサム | I105 アルファベットで表現した `Bech32m` 形式の 6 個の `5-bit` 値 | N/A |

ペイロードとチェックサムはアカウントコントローラーを識別します。

センチネルはネットワークコンテキストを選択します。

同じコントローラーは、Taira と Minamoto で同じペイロードとチェックサムを持っていますが、それぞれのネットワークは異なる先頭セントネルを使用します。

デコーダーは期待されるチェーン識別値を必ず検証しなければなりません。

チェックサムではセンチネルの置き換えを検出できません。

### ネットワークの哨兵 {#network-sentinels}

| ネットワークまたはコンテキスト | チェーン識別値 | Hex | 正規センチネル |
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
| Taira 公共テストネット |                            `369` | `0x0171` | `test`                                      |
| Minamoto 公共ネットワーク |                            `753` | `0x02f1` | `sora`                                      |
|開発環境|                              `0` | `0x0000` | `dev`                                       |
|他の`u16`の値|すべて `0`、`369`、および `753` を除く|        — | `n` プラス最小の小数、例えば `n42` |

名前付きの値には、常に対応する名前付きセンチネルを使用します。

`n00042`、`n369`、`n753`、`n0` のような形式は正規ではありません。

取引チェーンIDと I105 チェーン識別子は別々の値です。

API のエンドポイントまたはチェーンIDを選択しても、アドレスプロファイルが自動的に選択されるわけではありません。

## 規範的な単一キーの例 {#normative-single-key-example}

以下のペイロードと Minamoto 形式は、SDK 間の適合性テスト用フィクスチャに由来します。

Taira フォームは、同じペイロードに Taira のセンチネルを適用します。

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

標準的なペイロードは `02 00 01 20` で始まり、ヘッダー `0x02`、コンパクトな単一キータグ `0x00`、`Ed25519` 曲線ID `0x01`、および32バイトのキー長 `0x20` があります。

`multihash` プレフィックスは入力メタデータであり、コントローラのペイロードにはコピーされません。

## CLI でIDを作成および確認する {#create-and-inspect-ids-with-the-cli}

パブリックネットワークに対して名前付きプロファイルを指定する:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

アドレスコーデックの動作を診断する際に、I105 入力を正規化して比較します:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

検出された形式、正規の 16 進表現、選択したネットワークコンテキストを JSON で確認します:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

改行で区切られたファイルのアドレス-コーデック構造を、解析失敗を黙って受け入れることなく監査する:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution CLI 検証境界

`convert`、`normalize`、および`audit`コマンドは、より低レベルの`AccountAddress`コーデックで動作します。

彼らはセンチネル、アルファベット、チェックサム、バイト長、`CurveId`/キーの形状、および正確なアドレス層の再エンコードを検証します。

彼らは`AccountId`を具現化しない。

それらだけでは、すべてのマルチシグポリシーのセマンティクスを検証することはできません。

それらはヘッダークラスがコントローラーと一致することを証明するものではありません。

認可または永続化の前に、厳格な `AccountId` 検証を行ってください。

:::

プライベートネットワークでは、設定済みのチェーン識別値を `--network-prefix` で明示的に指定してください。

既存のアドレスを明示的なコンテキスト間で変換する場合は、ソースに `--expect-prefix` も提供してください:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

再エンコードはネットワークのコンテキストだけを変更します。

それはターゲットネットワーク上でアカウントを登録したり、同じコントローラーをそこでも再利用すべきであることを証明したりするものではありません。

## 符号化アルゴリズム {#encoding-algorithm}

標準エンコーダはこれらの操作を実行します:

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

先頭のゼロバイトは、ゼロ値の `base-105` 桁として保持されます。

チェックサムでは、`Bech32` の `polymod` 生成子と定数 `0x2bc830a3` を使用します。

チェックサムのみの HRP は ASCII 文字列 `snx` です。

チェックサム専用の HRP はアドレスに出力されません。

6つのチェックサム値は `0..31` の範囲にあり、ペイロードと同じ I105 アルファベットを通じて表されます。

### I105 アルファベット {#i105-alphabet}

105の記号は、この正確な順序で索引付けされています。

最初の行は `Bitcoin Base58` アルファベットで、数字 `0..57` が含まれています。

2行目には数字 `58..104` が含まれています。

コーデックを実装するときに行を連結してください。

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

アルファベットは`Unicode`に敏感です。

正確なシーケンスは、`compatibility-width` の日本語 `kana` 記号と、`ヰ` および `ヱ` に示されたコードポイントを使用します。

NFC、NFKC、幅の変換、大文字小文字の統一、または類似文字の置換は適用しないでください。

ASCII `0`、`O`、`I`、および `l` はアルファベットの記号ではありません。

## 標準的なアカウントペイロード {#canonical-account-payload}

`base-105` 本文はバイナリアカウントペイロードをエンコードするものであり、公開鍵文字列でも Norito JSON オブジェクトでもありません:

```text
header:u8 || controller:variable
```

以下の複数バイト整数はすべて符号なしで、`big-endian` です。

ドメイン、データスペース、エイリアス、UAID、およびアカウントメタデータのバイトが存在しません。

### ヘッダバイト {#header-byte}

|ビット|幅|現在のエンコーダ出力|意味|
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |住所形式バージョン欄|
| `4..3` |     2 |`0` 単一キー、`1` マルチシグ|住所クラス|
| `2..1` |     2 |                          `1` |正規化バージョンフィールド|
| `0`    |     1 |                          `0` |予約済み `extension flag`|

現在の V1 エンコーダは、シングルキーコントローラーにはヘッダー `0x02` を、マルチシグコントローラーにはヘッダー `0x0a` を出力します。

アドレスクラス `2` と `3` は未割り当てです。

`1`の`extension flag`は却下されました。

低レベルデコーダは他のバージョンおよび正規化ビット値を保持でき、クラスをコントローラーのタグと独立して照合することはありません。

`AccountId` に変換し、その正規の表現と比較することで、現在の V1 正規性を確認できます。

### シングルキーコントローラー {#single-key-controller}

生の公開鍵ペイロードが 255 バイト以下の場合は、コンパクト形式を使用します:

|フィールド|幅|価値または意味|
| ------------ | --------------: | ------------------------ |
| `tag`        |1バイト|`0x00`|
| `curve`      |1バイト| `CurveId` レジストリ値 |
| `key_len` | 1 バイト | 生の鍵の長さ |
| `public_key` | `key_len` バイト | 生の公開鍵ペイロード |

255 バイトを超える鍵では拡張形式を使用します:

|フィールド|幅|価値または意味|
| ------------ | --------------: | ---------------------------- |
| `tag`        |1バイト| `0x02`                       |
|`curve`|1バイト| `CurveId` レジストリ値|
| `key_len` | 2 バイト | 生の鍵の長さ、`big-endian` |
| `public_key` | `key_len` バイト | 生の公開鍵ペイロード |

コンパクト形式に収まる鍵に対して、拡張エンコードは正規ではありません。

### マルチシグコントローラー {#multisig-controller}

|フィールド|幅|価値または意味|
| ---------------- | -------: | ------------------------------ |
| `tag`            |1バイト|`0x01`|
| `policy_version` |1バイト|現在の値 `1`|
| `threshold` | 2 バイト | 必要な承認の重みの合計 |
| `member_count`   |2バイト|フォローしているメンバーの数|
| `members`        |変数|重複した会員記録|

各メンバーの記録は次の通りです:

|フィールド|幅|意味|
| ------------ | --------------: | ------------------------ |
|`curve`|1バイト| `CurveId` レジストリ値 |
| `weight` | 2 バイト | メンバーの承認の重み |
| `key_len` | 2 バイト | 生の鍵の長さ |
| `public_key` | `key_len` バイト | 生の公開鍵ペイロード |

有効なポリシーは、少なくとも1人のメンバーを持ち、重みが正で、重複する公開鍵がなく、閾値は`1`からメンバーの重みの合計までの範囲です。

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

正規構築では、署名アルゴリズムの安定した名前、ゼロ区切りバイト、生の公開鍵バイトの順でメンバーを並べ替えます。

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

一つの I105 リテラルは、マルチシグやポスト量子コントローラーが大きくなる可能性があるため、固定の文字長を持ちません。

### `CurveId` レジストリ {#curveid-registry}

最後の列は、必要なオプションの `Cargo` 機能の名前を示しています。

ダッシュは、そのレジストリ項目がオプションのデータモデル機能なしで利用可能であることを意味します。

|ID|署名アルゴリズム|必要な `Cargo` 機能|
| ---: | -------------------------------------------- | ------------------------ |
|  `1` |`Ed25519`| —                        |
|  `2` | `ML-DSA`                                     | —                        |
|  `3` | `BLS12-381 normal`                           |`bls`|
|  `4` | `secp256k1`                                  | —                        |
|  `5` |`BLS12-381 small`                            | `bls`                    |
| `10` | `GOST R 34.10-2012 256-bit, parameter set A` |`gost`|
| `11` | `GOST R 34.10-2012 256-bit, parameter set B` | `gost`                   |
| `12` | `GOST R 34.10-2012 256-bit, parameter set C` | `gost`                   |
| `13` | `GOST R 34.10-2012 512-bit, parameter set A` | `gost`                   |
| `14` | `GOST R 34.10-2012 512-bit, parameter set B` | `gost`                   |
| `15` |`SM2`| `sm`                     |

受信ビルドで割り当てられていないIDおよび無効化されたアルゴリズムは拒否されます。

キーのペイロードは、宣言された`CurveId`によって選択されたアルゴリズムに対しても構造的に有効でなければなりません。

## 厳密な AccountId 検証と正規性 {#strict-accountid-validation-and-canonicality}

SDK に期待されるチェーン識別値を設定した後、`AccountId` として解析し、返された正規の表現を前後の許可された空白を除去した入力と比較します。

この比較は重要です。なぜなら、パーサーは`AccountId`を構築する際にデコード可能なコントローラの素材を正規化できるからです。

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

信頼できない文字列の場合、準拠するアプリケーションは次のことを行うべきです:

1. 値全体の前後にある、許可された転送上の空白だけを除去します。
2. センチネルを読み取り、期待されるチェーン識別子を要求してください。
3. 残りのすべての `Unicode` 記号を正確な105記号のアルファベットを使ってマッピングします。
4. 6桁のチェックサムを分離してください。
5. ペイロードの各桁を正規バイト列へ戻します。
6. その正規バイト列に対してチェックサムを検証します。
7. ヘッダーとコントローラーを解析し、次を要求する：
   - 正確なフィールド長
   - サポートされた `CurveId`
   - 有効な公開鍵
   - 末尾に余分なバイトがないこと
   - 該当する場合の有効なマルチシグポリシー
8. `AccountId`を構築する。
9. 期待されるチェーン識別値に対して `AccountId` を正規形式で表現します。
10. 前後の許可された空白を除去した入力との `byte-for-byte` 一致を要求します。

アプリケーションの明示的な最終 `render-and-compare` ステップでは、最小形式でない数値センチネル、非正規のコントローラーレイアウト、並べ替えられたポリシー素材、およびデコードできてもエンコーダーの現在の V1 出力ではないその他の表記を拒否します。

成功したチェックサムまたは低レベルの`AccountAddress`解析は、このチェックの代わりにはなりません。

厳密なアカウントIDフィールドでは、これらの値を受け入れないでください:

- 例えば～のようなアカウント別名 `alice@wonderland.universal`
- 末尾に `@domain` サフィックスを付加した I105 リテラル
- 公開鍵 `multihash` 例えば `ed0120...` のような
- 例えば `0x02000120...` のような標準的なペイロードの16進数
- 誤ったチェーン識別値のアドレス
- 大文字と小文字の文字、文字幅、`kana`、ペイロード、またはチェックサムが変更された文字列

アプリケーション境界でエイリアスを解決し、認証、署名、権限、および監査記録のために返された正規の I105 ID を保持します。

|コード|意味|

## API、保管および表示ルール {#api-storage-and-display-rules}

- JSON アカウントのフィールドに正確な I105 UTF-8 文字列を送信してください。
- 完全なアカウント ID を URL パスセグメントに配置する前に `Percent-encode` してください。
- I105 ID の代わりにアカウントエイリアスを使用しないでください。
- コーデックによって返される標準文字列を `byte-preserving` 比較セマンティクスで保存します。
- 英字の大文字と小文字、および文字幅を保持する照合順序を使用してください。
- エクスポートしたアカウントデータとバックアップには、チェーン識別値または名前付きネットワークプロファイルを一緒に保存してください。
- アドレスは、そのネットワークのコンテキストとともにのみ再利用してください。
- 完全なアドレスを表示し、コピー操作を提供してください。
- すべての `kana` 文字を正確に保持してください。
- コンパクト表示が中間部分を短縮する場合でも、完全な住所を利用できるようにしておいてください。
- エイリアスから再構築するのではなく、保存されている正規のIDを使用してください。

`AccountId` を表示し、JSON は標準の I105 を使用します。

下位レベルの `AccountAddress` 表示/JSON 表現は、内部およびデバッグの文脈で標準の16進数を使用します。

外部アカウント ID が必要な場合は、明示的な `AccountAddress` I105 エンコーダーを呼び出してください。

アカウント作成およびエイリアス解決のワークフローについては、[アカウントとエイリアス](/ja/cookbook/accounts-and-aliases.md) を続行してください。

アカウントデータモデルについては、[アカウント](/ja/blockchain/accounts.md) を参照してください。
