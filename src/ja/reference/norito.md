# Norito {#norito}

Norito は Iroha の公式のシリアル化レイヤーです。ネットワークのピア、SDKs、CLI ツール、Torii、Kura、および生成されたアーティファクトがまったく同じペイロードに合意する必要がある場合に使用されるバイト形式です。

データがコンセンサス、署名、ハッシュ化、永続化、またはクロス-SDK の相互運用性の一部である場合は、Norito を使用してください。API エンドポイントがオペレーター、ダッシュボード、または迅速なデバッグのために人間が読み取れる投影を明示的に提供する場合は、JSON を使用してください。

## Norito が現れる場所 {#where-norito-appears}

|表面| Norito の使い方 |
| --- | --- |
|取引と照会|Torii を通じて送信された署名付きトランザクションおよびクエリペイロードは、Norito としてエンコードされます。|
|ブロックチェーンのジェネシス| `kagami genesis sign` は、ネットワークのピアが起動時に読み込む署名付きの `.nrt` ブロックを生成します。 |
| Torii タイプされた応答| API 型付きバイナリレスポンスをサポートするエンドポイントは `Accept: application/x-norito` を使用します。 |
| SDKs | Rust、Python、JavaScript、Kotlin/Java、Swift、および Android クライアントは、手作業で組み立てたバイトの代わりに Norito ビルダーまたはバインディングを使用します。|
|Kura ストレージ|ブロックのペイロード、回復補助レコード、名簿、ブロック最終化マーカーは、Norito フレーム付きデータとして保存されます。|
|技術的マニフェスト| Nexus、データの利用可能性、SoraFS、ストリーミング、およびアプリ向けの技術マニフェストは、技術マニフェストを署名またはハッシュする必要がある場合に Norito を使用します。|
|ストリーミング| Norito ストリーミングは、Norito の技術マニフェスト、セグメントヘッダー、制御フレーム、および適合性フィクスチャを使用します。|

Norito はスマートコントラクト言語ではありません。これは、取引、契約呼び出し、技術マニフェスト、および型付き API ペイロードを運ぶ決定論的データコンテナおよびコーデックです。

## ペイロードモデル {#payload-model}

プロトコル上のすべての送信やディスク上の Norito ペイロードは、ヘッダーに続いてエンコードされたペイロードバイトによってフレーミングされます。ヘッダーなし、またはベアペイロードは、内部ハッシュ計算、ベンチマーク、および結果を直ちにヘッダーでラップして送信する補助的な APIs 用に予約されています。

|ヘッダーフィールド|サイズ|目的|
| --- | ---: | --- |
|魔法|4バイト| ASCII `NRT0` は、非 Norito データを早期に拒否するために使用されます。|
|専攻|1バイト|フォーマットのメジャーバージョン。現在のペイロードは`0`を使用しています。|
|マイナー|1バイト|v1のヒントをデコードします。現在の値は`0x00`です。フラグはレイアウトを示します。|
|スキーマ暗号ハッシュ|16バイト|型付きデコーダーが予期しないペイロードを拒否するために使用する型識別子。|
|圧縮|1バイト| `0 = None`, `1 = Zstd`。不明な値は拒否されます。|
|ペイロード長|8バイト|リトルエンディアンでの非圧縮ペイロードの長さ `u64`。|
| CRC64 |8バイト| CRC64-XZ 未圧縮ペイロードのチェックサム。 |
|旗|1バイト|コンパクトな長さ、パックされたシーケンス、およびパックされた構造体のレイアウトフラグ。|

ヘッダーは40バイトです。デコーダーは、型付き値を再構築する前に、マジック、バージョン、サポートされているフラグマスク、ペイロードの長さ、チェックサム、スキーマの暗号ハッシュを検証します。

## レイアウトフラグ {#layout-flags}

Norito は最終ヘッダーバイトにレイアウトの選択を格納します。デフォルトの v1 ヘルパーは、コンパクトな値ごとの長さプレフィックスのために `COMPACT_LEN` (`0x02`) を出力します。明示的な固定幅の長さプレフィックスは、呼び出し側が `flags = 0x00` でエンコードすると引き続き読みやすいままです。

|旗|16進数|ステータス|効果|
| --- | ---: | --- | --- |
| `PACKED_SEQ` | `0x01` |サポートされている|オフセットテーブルと連続するデータブロックを使用して、可変サイズのコレクションをエンコードします。|
| `COMPACT_LEN` | `0x02` |デフォルト|値ごとの長さの接頭辞には標準の符号なし可変長整数を使用します。|
| `PACKED_STRUCT` | `0x04` |サポートされている|deriveで生成された構造体をパックされたフィールドペイロードとしてエンコードします。|
| `VARINT_OFFSETS` | `0x08` |予約済み|v1で拒否されました；パック済みシーケンスオフセットは固定幅です `u64`。|
| `COMPACT_SEQ_LEN` | `0x10` |予約済み|v1で拒否されました; トップレベルのシーケンス長ヘッダーは固定幅です `u64`。|
| `FIELD_BITSET` | `0x20` |要件に対応|パックされた構造体のためにビットセットを追加し、明示的なサイズを必要とするフィールドだけがサイズプレフィックスを持つようにします。`PACKED_STRUCT`および`COMPACT_LEN`が必要です。|

フラグは明示的です。デコーダーはペイロードの形状、マイナーバージョン、またはヒューリスティックからレイアウトを推測しません。不明または無効な組み合わせは拒否され、すべてのネットワークピアがペイロードを同じ方法で解釈するようにします。

## エンコーディング規則 {#encoding-rules}

Norito は、Iroha データモデルに現れる一般的なデータ形状に対して決定論的レイアウトを使用します。

- 文字列は `[len][utf8-bytes]` です；`len` は有効になると `COMPACT_LEN` に従います。
- `COMPACT_LEN` が設定されている場合、各値の長さはコンパクトな可変長整数を使用します。
- `COMPACT_LEN` が存在しない場合、各値の長さは 8 バイトのリトルエンディアン `u64` です。
- v1では、シーケンス長ヘッダーは固定8バイトのリトルエンディアン`u64`です。
- `Vec<u8>` は、1バイトごとの長さではなく `[len_u64][raw-bytes]` としてエンコードされます。
- パックされたシーケンスは、連結された要素ペイロードに続く`u64`単調`(len + 1)`オフセットを使用します。
- マップは固定された `u64` でエントリ数を符号化し、決定論的なキー順序を使用します。`HashMap` のエントリはエンコード前にキーでソートされます。`BTreeMap` は自然順序を使用します。
- `BigInt` は、リトルエンディアンの二の補数バイトを `u32` バイトの長さで使用し、512ビットの上限があります。
- `Numeric` は `(mantissa, scale)` として符号化され、ここで仮数部には整数値が格納され、スケールには小数桁数が格納されます。

これらのルールは署名と暗号ハッシュに重要です。同じ論理トランザクションを構築する2つの SDKs は、同じ正規バイトを生成しなければなりません。

## スキーマ暗号ハッシュ {#schema-hashes}

型付き Norito ペイロードは、ヘッダーに16バイトのスキーマ暗号ハッシュを持っています。デフォルトの暗号ハッシュは、完全修飾型名から導出されます。構造的スキーマハッシュを有効にするビルドでは、暗号ハッシュは代わりに標準的なスキーマから導出されます。

型付きデコーダはスキーマの不一致を拒否します。これにより、クライアントが有効な Norito フレームを誤った型として誤ってデコードするのを防ぎ、SDK テストアーティファクトバンドルがノードデータモデルからずれた場合の通常の障害モードとなります。

## 圧縮と加速 {#compression-and-acceleration}

Norito は、論理ペイロードを変更することなく、明示的および適応的な圧縮をサポートします:

|特徴|目的|
| --- | --- |
| `to_bytes` |ヘッダーをエンコードし、その後に未圧縮のペイロードを続けます。|
| `to_compressed_bytes` |Zstdでエンコードし、ヘッダーに圧縮タグを記録する。|
| `to_bytes_auto` |圧縮が有益かどうかを判断するために、決定的なヒューリスティックを適用する。|
|CRC64 加速度|どこでもポータブルな CRC64-XZ を使用し、x86_64では CLMUL を、aarch64では利用可能な場合に PMULL を使用します。|
| GPU CRC64 と圧縮 |オプションのMetalまたは CUDA ヘルパーは、大きなペイロードを加速させることができ、その後 CPU 経路に戻ることがあります。|

ハードウェアアクセラレーションはデコードされた内容を変更することはありません。CRC および JSON のアクセラレータは、ポータブル出力がビット単位で一致する必要があります。CPU と GPU のエンコーダ間で Zstd フレームのバイトは異なる場合がありますが、デコードされたペイロードおよび Norito ヘッダメタデータは検証のために決定論的に保持されます。

## JSON サポート {#json-support}

Norito は、Norito 型システムを離れることなく、JSON を必要とする API エンドポイントおよびツール向けのネイティブ JSON スタックを含みます。

| JSON 機能 |ユースケース|
| --- | --- |
| `norito::json::{to_json, from_json}` |決定論的型付き JSON エンコード/デコード。|
|かわいくて作家の助け手| CLI 出力、テスト成果物、そしてストリーミング `std::io` 統合。 |
|DOM 値| Norito の JSON 値モデルを通じたプログラムによる操作。|
|高速で入力された JSON|ホット DTO パスのための構造テープベースのデコード/エンコード。|
|ゼロコピーリーダー|可能な場合に入力から文字列を借用するトークンスキャニング。|
|ステージ1のアクセラレーター|オプション：AVX2、NEON、Metal、または CUDA の構造インデックス指定（スカラーのフォールバック付き）。|

Iroha コードは、型付き API ペイロードに対して `norito::json` ヘルパーを優先すべきです。プレーンな `serde_json` を本番パスに追加すると、SDKs および Torii エクストラクターが期待するスキーマやフィールド処理の動作から逸脱するリスクがあります。

## サポートを導き出す {#derive-support}

Rust のデータ型は、通常、手動でのコーデックコードではなく、deriveマクロを使用します。derive層は Norito バイナリコーデック、スキーマ、そして JSON ヘルパーを生成することができます。

一般的なフィールド属性は次の通りです：

|属性|効果|
| --- | --- |
| `#[norito(rename = "other")]` |スキーマおよび JSON の互換性のために安定したシリアライズされた名前を使用します。|
| `#[norito(skip)]` |エンコーダはフィールドを省略します。デコーダはその`Default`の値を提供します。|
| `#[norito(default)]` |デコードされたペイロードにフィールドが含まれていない場合、`Default` を使用します。|
| `#[norito(skip_serializing_if = "...")]` |述語が一致する場合に JSON からフィールドを省略し、決定論的デコーディングのデフォルトを保持します。|

派生型は、可能な場合にはエンコードされた長さのヒントや正確な長さの計算も公開します。エンコーダはそれらのヒントを使用してバッファを確保し、余分なコピーを回避します。

## ソフトウェアパッケージ機能ファミリー {#crate-feature-families}

ソースから Iroha または SDK のバインディングを構築する際、Norito の機能はどのヘルパーとアクセラレータが利用可能かを選択します:

|機能ファミリー|それが可能にするもの|
| --- | --- |
| `derive` |バイナリ、スキーマ、および JSON 派生のための手続きマクロを再エクスポートしました。|
| `compression` |ヘッダーフレーム化されたペイロードのZstdサポート。|
| `packed-seq` |オフセットテーブルを使用したパックされたコレクションのレイアウト。|
| `packed-struct` |パックされた derive 生成の構造体レイアウト。|
| `compact-len` |値ごとの可変長プリフィックス。|
| `columnar` | Norito カラムブロック、適応型 AoS/NCB 行コーデック、およびスキャンが多いパス用の借用ビュー；デフォルトに含まれています `node-codec` 機能セット。 |
| `strict-safe` |失敗する可能性のある経路でのデコードのパニックを構造化されたエラーに変換します。|
| `simd-accel` |利用可能な場合は CPU のアクセラレーションを使用し、決定論的なフォールバックを行います。|
| `json` |ネイティブ JSON パーサー、ライター、DOM、型付きデリブ、および高速パス。|
| `json-std-io` |リーダーとライターのヘルパーが JSON スタックに重ねられました。|
| `metal-stage1`、`cuda-stage1` |オプションの GPU JSON 構造インデックスバックエンド。|
| `metal-stage2` |JSON 構造用テープのオプションのメタルメタデータ分類。|
| `metal-crc64`、`cuda-crc64` |大きなペイロード用のオプションの GPU CRC64 ヘルパー。|
| `gpu-compression` |大きなペイロード向けのオプションの金属または CUDA Zstd アクセラレーション。|
| `stage1-validate` |加速された JSON 構造インデックスをスカラー出力と比較するデバッグ検証。|

機能の利用可能性は、SDKs とリリースプロファイルの間で異なる場合があります。ワイヤーフォーマットは、ローカルビルドフラグではなく、ヘッダーとスキーマによって管理されます。

## Torii と Norito RPC {#torii-and-norito-rpc}

Torii は多くのオペレータールートで JSON を公開しますが、型付きバイナリールートは Norito を使用します。現在の型付き Norito HTTP 本文のメディアタイプは `application/x-norito` です。

これらのヘッダーは、API エンドポイントが型付きの Norito を受け入れる場合または返す場合に使用してください:

```http
Content-Type: application/x-norito
Accept: application/x-norito
```

API エンドポイントが両方の表現をサポートしている場合、クライアントは明示的な優先リストを送信できます:

```http
Accept: application/x-norito, application/json
```

デコードの失敗は型付きの Torii エラーとして表示され、テレメトリによってカウントされます。一般的な原因には、無効なマジック、サポートされていないバージョン、サポートされていない機能フラグ、チェックサムの不一致、整形されていない UTF-8、無効な列挙タグ、スキーマの不一致が含まれます。

Norito RPC のトランスポートはトランスポート構成を通じて選択されます。オペレーターのダッシュボードは、リクエストのレイテンシ、失敗、アクティブ接続、応答バイト、および `torii_norito_decode_failures_total` を JSON トラフィックとは別に追跡する必要があります。

## Norito ストリーミング {#norito-streaming}

Norito ストリーミングは、メディアおよびリアルタイムトランスポートの領域にも同じ決定論的アプローチを拡張します。その主要な要素は次の通りです。

|ストリーミング機能|目的|
| --- | --- |
|技術マニフェスト|セグメントの暗号コミットメント値、プライバシールート、機能、コーデックプロファイル、暗号化スイート、およびコンテンツキーのメタデータを宣言します。|
|セグメントヘッダー|セグメント番号、期間、チャンク数、タイミング、エントロピーモード、オーディオの概要、およびマークルルートをバインドします。|
|チャンク暗号コミットメント値|視聴者とリレーが、提供またはデコードする前に、ペイロードのチャンクを技術マニフェストと照合するようにしてください。|
|制御フレーム|技術的マニフェストの発表、フィードバック、主要な更新、および能力交渉を行う。|
| HPKE キー更新 |交渉されたスイートと単調に増加するカウンターを使用して、輸送の秘密を回転させます。|
|機能交渉|サポートされている機能ビット、データグラムの制限、フィードバックの間隔、およびプライバシー要件に交差します。|
| FEC とフィードバック|損失のあるリアルタイム経路に対して、決定論的受信報告とパリティ判定を使用します。|
|適合ベクトル|クロスランゲージのテストアーティファクトは、SDKs が同じ技術的マニフェスト、セグメント、およびエントロピーストリームをデコードすることを証明します。|

ストリーミング専用のコーデックとエントロピープロファイルは、コアの Norito トランザクション／クエリ形式とは別ですが、それらの技術的マニフェストと制御データは引き続き Norito を使用するため、ルーティング、課金、リプレイ、および監査証跡は再現可能なままです。

## 運用ガイダンス {#operational-guidance}

- 手作りの Norito バイトよりも、SDK ビルダーと生成されたバインディングを優先してください。
- スキーマの不一致は一時的なネットワーク障害ではなく、バージョンやテストの問題として扱うべきです。
- リリースまたはそれらを生成したインシデントバンドル内のアーカイブ `.nrt`、`.norito` および技術マニフェストアーティファクト。
- 署名済み、ハッシュ済み、または永続化されたデータの信頼できる情報源として Norito を使用してください。ダッシュボードや手動検査のためには JSON のプロジェクションを使用してください。
- 新しい型付きの Torii API エンドポイントを追加する際には、JSON、Norito、またはその両方を受け入れるかどうかを文書化し、サポートされているコンテンツタイプを `/openapi.json` に公開してください。
- アクセラレータを有効にする前に、スカラ出力に対してパリティテストを実行してください。アクセラレータが失敗した場合は、決定論的なスカラフォールバックを使用してください。ペイロードのセマンティクスは変更されてはいけません。
