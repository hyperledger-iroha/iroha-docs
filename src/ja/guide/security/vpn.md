# 仮想プライベートネットワーク {#virtual-private-networks}

A <abbr title="Virtual Private Network">VPN</abbr>は、誰が Iroha サービスにアクセスできるかを制限するネットワーク制御です。これは、バリデータ、アプリケーションバックエンド、およびオペレーターが公開されたインターネット経路ではなくプライベートアドレスを通じて通信すべきプライベートおよびコンソーシアム展開に最も役立ちます。

A VPN は Iroha のネットワークピアキー、アカウントキー、権限、ファイアウォールルール、監視、または安全なキー保管を置き換えるものではありません。それを一つの層として扱ってください。展開境界: VPN はネットワーク到達性を狭め、Iroha の構成とガバナンスはどのネットワークピアとアカウントが信頼されるかを決定します。

## VPN を使用するタイミング {#when-to-use-a-vpn}

次の場合に VPN を使用します:

- バリデータは異なる組織によって、または異なるホスティング環境で運営されています
- Torii は、アプリケーションのバックエンド、オペレーター、または信頼できるクライアントのみが到達可能であるべきです
- メトリクス、ログ、SSH、またはその他の管理用 API エンドポイントは、プライベートなオペレーターネットワーク上にとどまる必要があります
- テストまたはステージングネットワークは、公共の API エンドポイントを公開することなく、本番のアクセス制御に似ているべきです

すべてのデプロイメントにおいて VPN は必ずしも必要ではありません。パブリックネットワークは、パブリックゲートウェイ、ロードバランサー、またはリバースプロキシを通じて Torii を意図的に公開する場合があります。その場合でも、バリデータのピアツーピアトラフィックおよび管理用 API エンドポイントは、可能な限り制限されたネットワーク内に保持してください。

::: tip

ブラウザ VPN は、そのブラウザからのトラフィックのみを保護します。`iroha3d`、CLI、SDK、SSH、メトリクス、バックアップトラフィックは、それらのプロセスが同じプライベートネットワークを通る場合を除き、保護されません。

:::

## 配置パターン {#deployment-pattern}

プライベートバリデータメッシュの場合、すべてのバリデータに安定した VPN アドレスまたはプライベート DNS 名を付与してください。ネットワークのピアを設定して、広告されるピアツーピアアドレスがそのネットワーク上の他のバリデータから到達可能であるようにしてください:

```toml
trusted_peers = [
  "PUBLIC_KEY_1@10.20.0.11:1337",
  "PUBLIC_KEY_2@10.20.0.12:1337",
  "PUBLIC_KEY_3@10.20.0.13:1337",
  "PUBLIC_KEY_4@10.20.0.14:1337",
]

[network]
address = "10.20.0.11:1337"
public_address = "10.20.0.11:1337"

[torii]
address = "10.20.0.11:8080"
```

現在のネットワークピアに割り当てられたアドレスを`network.address`および`network.public_address`で使用します。各ネットワークピアは、同じ信頼されたネットワークピアの識別子を一覧表示する必要がありますが、自身の VPN ルートテーブルから到達可能なアドレスを使用する必要があります。

クライアントおよび CLI の設定は、VPN を通じて、または制御された内部ゲートウェイを通じて到達可能な Torii API エンドポイントを指す必要があります:

```toml
torii_url = "http://10.20.0.11:8080"
```

もし Torii を VPN の外部で使用可能にする必要がある場合は、TLS、認証、レート制限、ログ記録を提供するリバースプロキシまたはロードバランサーの背後に配置してください。生のピアツーピアポートや管理用 API エンドポイントを直接パブリックインターネットに公開することは避けてください。

## ファイアウォールルール {#firewall-rules}

ホストおよびクラウドのファイアウォールルールは、VPN が存在する場合でも使用してください:

|サービス|推奨アクセス|
| --- | --- |
|ピアツーピアポート|他のバリデーター VPN は次のことのみを対象としています|
| Torii |アプリケーションバックエンド、オペレーター、または信頼されたクライアント VPN 範囲|
|メトリクスとヘルスチェック|オペレーターネットワーク上の監視システム|
| SSH および管理|バスティオンホスト、特権オペレーター VPN の範囲、または緊急時対応プロセス|
|バックアップとストレージの複製|プライベートネットワーク上のバックアップシステム|

デフォルトで拒否するルールは、広範な許可ルールよりも監査が簡単です。新しいネットワークピアがネットワークに参加する場合、VPN メンバーシップ、ファイアウォールの許可リスト、および Iroha 信頼されたネットワークピアの構成を1つの連携した変更として更新してください。

## 運用チェックリスト {#operational-checklist}

- 監査され、積極的に維持されている VPN の実装、例えば WireGuard、IPsec、または組織承認済みの管理されたプライベートネットワークを選択してください。
- 各ホストおよびオペレーターごとにユニークな VPN 認証情報を使用してください。VPN キーをバリデーター間で共有しないでください。
- VPN の認証情報は、Iroha の秘密鍵およびブロックチェーンのジェネシス署名資料と分けて保管してください。
- モニター VPN 遅延、パケット損失、再接続、およびルートの変更。コンセンサスは持続的なネットワークの不安定性に敏感です。
- 有効な MTU をテストします。パケットの断片化は、断続的なネットワークピアまたは Torii の障害のように見えることがあります。
- ピアツーピア、Torii、メトリクス、SSH、およびバックアップ API エンドポイントに到達できる VPN の範囲を記載したドキュメント。
- ホスト、オペレーターアカウント、または組織がネットワークを離れたときに、VPN の資格情報を回転させます。
- バリデーター間の唯一のルートとして単一の VPN ゲートウェイを避けてください。運用ネットワークのために、冗長なゲートウェイやサイト間ルートを計画してください。
- オペレーターがネットワーク分断と Iroha プロセスの障害を区別すべき時を理解できるように、インシデント対応演習に VPN の障害を含めてください。
