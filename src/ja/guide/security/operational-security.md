# 作戦上の安全保障 {#operational-security}

運用セキュリティは、Iroha の展開に関連する人員、ホスト、認証情報、および手順を保護します。ブロックチェーン台帳は、受け入れられた状態の変更を記録します。運用者は、自身のワークステーション、署名鍵、およびインシデント対応プロセスを別個に保護する必要があります。

以下のコントロールを展開の基準として使用してください。それらをリスクの大きさや組織の要件に合わせて調整してください。

## 運用の基準を確立する {#establish-an-operational-baseline}

- バリデータホスト、ネットワークピアの識別子、アカウント認可プリンシパル、署名デバイス、公開 API エンドポイント、および責任者の在庫を維持します。
- 開発、テスト、本番環境ごとに別々の認証情報を使用してください。各暗号署名者、ベアラートークン、および秘密鍵をそれぞれの環境に割り当ててください。
- 設定およびデプロイメントの自動化をレビュー可能なバージョン管理下に置きます。承認されたシークレットストアや署名デバイスから、ソフトウェア実行時にシークレットを注入します。
- リリース成果物の予想される暗号ハッシュや署名を記録します。展開前にそれらを確認してください。バイナリ、ブロックチェーンのジェネシスマテリアル、設定、またはサービス定義を置き換えられる人を制限します。
- オペレーティングシステムのアカウント、Iroha 権限、およびネットワーク管理に最小権限を適用してください。各役割には、その作業に必要な権限のみを付与してください。
- 本番稼働前に、バックアップ、リストア、キー交換、およびピアリカバリー手順をテストしてください。

ベースラインを定義する際に、[セキュリティの原則](./security-principles.md) と [リリース準備](../best-practices/release-readiness.md) を確認してください。

## キーと暗号署名者を保護する {#protect-keys-and-signers}

- プライベートキー、シード情報、ベアラートークン、認証ヘッダー、および回復用シークレットを、ソース管理、課題トラッカー、チャットの記録、スクリーンショット、公開ドキュメントに含めないでください。
- 高価値の認可プリンシパルには、ハードウェア対応または隔離された署名を使用してください。クライアントが署名を代理できる場合は、生のキー素材をブラウザや汎用アプリケーションプロセスの外に保持してください。
- 通常の取引、ガバナンス、デプロイメント、リカバリーには、それぞれ別々の認可プリンシパルを使用してください。
- 秘密のストレージとそのバックアップを暗号化します。ライブキーと同じアクセス制御を秘密鍵のバックアップにも適用します。
- テスト済みの交換または取り消し手順を維持してください。ポリシーで要求される場合や、キーが漏洩したと疑われる場合は、キーを交換してください。
- バリデータのメンバーシップ、特権のある役割、または高価値資産の変更には、独立したレビューを要求する。

キー固有のガイダンスについては、[暗号鍵の生成](./generating-cryptographic-keys.md) と [暗号鍵の保存](./storing-cryptographic-keys.md) を参照してください。

## ノードおよびオペレーターアクセスを強化する {#harden-nodes-and-operator-access}

- 現在ベンダーがサポートしているパッチ適用済みシステムで、ノードおよびオペレーターツールを実行します。不要なサービスは無効にしてください。
- 指名されたオペレーターに対しては、監査され暗号化されたチャネルを通じてのみ管理者アクセスを付与する。
- 非公開のインターフェースはプライベートネットワークまたは[VPN](./vpn.md)に置いてください。
- デプロイメントで必要な Torii、監視、およびアプリケーションルートのみを公開してください。
- すべての公共の入口を、環境に適したレート制限と通信セキュリティで保護します。
- 設定ファイルやサービスの認証情報を制限付きのファイル権限で保護してください。秘密情報をコマンドライン、プロセスリスト、シェルの履歴に含めないようにしてください。
- リスクモデルが独立した管理を必要とする場合、バリデーター、クライアント、モニタリング、およびバックアップの業務を分離してください。
- 信頼できるソースから時間を同期してください。調査のために十分なシステム、サービス、およびネットワークのログを保持してください。

## セキュアブラウザと管理者ワークフロー {#secure-browser-and-admin-workflows}

ウェブインターフェースを使用するオペレーターの場合：

- 管理されたワークステーションで、現在ベンダーがサポートしている完全に更新されたブラウザを使用してください。
- 必要な拡張機能のみを備えた専用のオペレーターのプロファイルまたはデバイスを使用してください。
- リクエストを承認する前に、出所と証明書を確認してください。
- 見た目が似ているドメイン、予期しないリダイレクト、そして生の鍵素材のリクエストは、インシデントとして扱う。
- アクティブなオペレーターセッションから関連のないサイトや拡張機能をブロックします。
- 短命なセッションを使用してください。特権操作には再認証を要求してください。
- 暗号署名者に取引の詳細を表示します。オペレーターは、承認前に承認主体、ネットワーク、指示、資産、および手数料を確認できる必要があります。

ブラウザの分離は露出を減らします。オペレーターはそれでも取引を確認し、安全な署名を使用する必要があります。

## 監視して対応する {#monitor-and-respond}

これらの信号を監視してください：

- バリデーターおよびネットワークピアのメンバーシップ変更
- 繰り返される認証失敗または異常な特権命令
- 予期しないソフトウェア、設定、またはルートの変更
- 通常の基準値を超えた署名、クエリ、およびトランザクションの失敗
- リソースの枯渇、合意の停滞、または期待されるネットワークピアの喪失
- 不正行為ルールに一致する資産、権限、およびアカウントの変更

影響を受けたホストとは独立してチャンネルにアラートを送信します。関連するログ、構成データのスナップショット、ブロックチェーンの台帳イベント、およびタイムスタンプ付きのトランザクション暗号化ハッシュを保存します。[不正監視](./fraud-monitoring.md)および[パフォーマンスと指標](../advanced/metrics.md)を参照してください。

## 回復計画 {#recovery-plan}

本番稼働前にリカバリ計画を準備してください。リカバリ計画には次の事項を明確にする必要があります:

- 誰がインシデントを宣言して調整できるか
- バリデーター、インフラ運営者、アプリケーションの所有者、および影響を受けるユーザーへの連絡方法
- どの認可プリンシパルが権限を取り消したり、キーを置き換えたり、ネットワークのピアのメンバーシップを変更したりできるか
- 信頼できるバイナリ、構成、ブロックチェーンのジェネシスレコード、バックアップ、キーの在庫が保存されている場所
- 復旧後にネットワークと依存アプリケーションを検証する方法

事故が発生した場合:

1. 影響を受けたホスト、認証情報、経路、または認可主体を隔離します。証拠を保全します。
2. ログとブロックチェーン台帳の参照を保存します。すべての復旧作業を記録します。
3. 承認されたガバナンスプロセスを通じて、露出した資格情報や権限を取り消すか、置き換えます。
4. 検証済みの成果物からソフトウェアと構成を復元する。
5. ネットワークピアのメンバーシップ、コンセンサスの健全性、パブリックルート、監視、およびアプリケーションの読み取りを確認します。これらのチェックが通過した後にのみ書き込みを再開します。
6. 根本原因を文書化する。コントロール、オートメーション、演習を更新する。

::: warning

取り消し不可能なブロックチェーン台帳の操作については、事前にレビューされた手順に従ってください。影響を受ける認可主体および資産に適切な承認を要求してください。

:::
