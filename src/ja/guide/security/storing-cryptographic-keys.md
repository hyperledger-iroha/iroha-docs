# 暗号鍵の保存 {#storing-cryptographic-keys}

秘密鍵は、その権限の主体に許可されたすべての操作を認可することができます。秘密鍵を共有しないでください。シード素材、回復秘密、ベアラートークン、およびエクスポートされた鍵ファイルを同じ注意を払って保護してください。

製品の立ち上げ前にカストディデザインを選択してください。デザインは、リスクにさらされる価値、アカウント管理ポリシー、および展開の復旧プロセスと一致している必要があります。

## カストディ境界を定義する {#define-the-custody-boundary}

- 各認証主体、公開鍵、アルゴリズム、環境、目的、管理者、保管場所、バックアップ、および交換手順の在庫を管理してください。
- 開発、テスト、本番、定期取引、ガバナンス、展開、および復旧のために別々のキーを使用してください。
- 人やプロセスには、役割に応じて必要な鍵だけアクセスを許可する。
- リスクモデルが必要とする場合、高額またはガバナンス関連の署名には独立した承認を要求する。
- 暗号署名者が使用できるネットワークおよび認可プリンシパルを記録してください。署名サービスは、その範囲外のリクエストを拒否しなければなりません。

## 適切な保管方法を選ぶ {#choose-an-appropriate-storage-method}

ローカル開発、制御されたテスト、または安全な保管の引き渡しのために、キーを権限制限されたファイルにエクスポートできます。対応するUnixプラットフォームでは、`kagami`を使用して新しいキー・ディレクトリを生成します:

```bash
cargo run --bin kagami -- keys --algorithm ed25519 --out-dir ./client-key
```

親ディレクトリは存在している必要があります。ターゲットは新規であるか、現在のユーザーが既に所有している必要があり、モード `0700` で、シンボリックリンクがなく、空である必要があります。Kagami 書き込み`public.key` および `private.key` をモード `0600` で設定します；`--pop` は `pop.hex` も書き込みます。コマンドは、Kagami が所有者専用のファイルシステム規則を強制できないプラットフォームでは失敗します。

秘密鍵ファイルは暗号化されていないエクスポートです。ソース管理、共有フォルダ、ログ、チケット、チャット、ビルド成果物には保存しないでください。運用用の鍵を承認された管理境界にインポートし、その後デプロイ手順に従ってエクスポートを削除してください。開発用キーを本番環境で再利用しないでください。

本番環境では、次のような監査済みのカストディ境界を推奨します:

- ハードウェアセキュリティモジュールまたはハードウェア対応キーストア
- オペレーティングシステムまたはモバイルキーストア
- 孤立した署名サービス
- 認可されたワークロードにのみキーを公開するシークレットマネージャー

選択した統合がそのプロパティをサポートしている場合、鍵素材を非輸出可能に保持してください。Iroha 認可プリンシパルによって要求されるアルゴリズムおよび署名操作をカストディシステムがサポートしていることを確認してください。

保存時の暗号化は、保存されたコピーを保護します。権限のないプロセスやオペレーターが復号済みのバイトを取得した場合、鍵を保護することはできません。ホストを強化し、ソフトウェアの実行時アクセスを制限し、署名活動を監視してください。

## 署名ワークフローを保護する {#protect-signing-workflows}

- 署名システムへのアクセスには、名前付きオペレーターの識別、強力な認証、および監査されたアクセスを使用してください。
- 生のキーをコマンドライン引数、シェル履歴、環境ダンプ、プロセス一覧、クラッシュレポート、アプリケーションログに含めないでください。
- 必要な操作のためだけに暗号署名者のロックを解除します。使用後はセッションを閉じるか期限切れにしてください。
- 承認前に、認可の主体、ネットワーク、指示、資産、および手数料を表示してください。
- 特権的または高額な取引には明示的な確認を要求してください。
- カスタムクライアント統合が署名を委任できる場合は、生のプライベートキーをブラウザページや汎用アプリケーションプロセスの外に保管してください。

プレーンテキストのクライアント構成は、ローカル開発や管理されたテストにのみ適しています。本番環境の統合では、承認された保管境界を通じて署名を取得する必要があります。株式 Iroha CLI はクライアントの設定から秘密鍵を読み込み、汎用の外部暗号署名サービスアダプターを提供しません。カスタムクライアントは、取引ペイロードの暗号ハッシュを生成し、外部暗号署名者によって作成された署名を添付することができます。

## キーのバックアップと復元 {#back-up-and-recover-keys}

- 回復ポリシーでバックアップが必要なキーのみをバックアップしてください。
- バックアップを暗号化し、実稼働の暗号署名者とは別に保管してください。
- バックアップにも、ライブキーと同じアクセスおよび承認の制御を適用します。
- 職務分離が必要な場合は、回復用認証情報を独立した管理下に置いてください。
- 本番用キー素材を公開せずに復元テストを行う。
- すべてのバックアップの作成、アクセス、復元、および破棄を記録して確認する。

無関係なウォレットのニーモニック形式が Iroha の秘密鍵を表すと仮定しないでください。選択したカストディシステムでサポートされ、テストされたリカバリ形式のみを使用してください。

## 露出したまたは使用停止になったキーを交換する {#replace-exposed-or-retired-keys}

事故の前に交換品を準備してください。手順には以下を明確にする必要があります:

1. 誰が鍵を露出または廃止と宣言できるか
2. 影響を受けた暗号署名者がどのように隔離されるか
3. 新しい鍵がどのように生成され、承認された管理下に置かれるか
4. アカウントの場合、承認されたコントローラーの交換またはソーシャルリカバリーがどのようにして交換用のカノニカル`AccountId`を作成し、リンクされた状態を移行するか
5. ノードまたはネットワークピアの場合、承認されたオンチェーンコンセンサスキーのローテーションまたは無効化が、BLS PoP、有効化および重複ポリシー、ローカルキー構成、`trusted_peers_pop`、およびデプロイトポロジーとどのように調整されるか
6. 依存する構成、アプリケーション、およびオペレーターが、新しい `AccountId`、公開鍵、またはネットワークピアの識別をどのように採用するか
7. 古い鍵の認可主体がどのように削除され、そのコピーがどのようにアーカイブまたは破棄されるか
8. その後、ネットワークおよび依存するアプリケーションがどのように検証されるか

::: warning

暗号化や新しいパスワードは、コピーされた秘密鍵を再び安全にすることはできません。漏洩が疑われる場合は、その鍵の使用を中止し、承認された交換または失効手順に従ってください。

:::
