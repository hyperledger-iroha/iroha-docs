# データモデリング {#data-modeling}

ブロックチェーン台帳データは、所有権、移転の挙動、許可の境界、およびクエリパターンを中心にモデル化する必要があります。監査可能性と決定論的実行をサポートできる最小のオンチェーン表現を選択してください。

## ドメインとアカウント {#domains-and-accounts}

- ドメインを使用して、管理上およびポリシー上の境界を表現します。アカウントや資産の識別子に表示されるため、ドメイン名は安定させておきます。
- 1つのアカウントに無関係な責任を過剰に割り当てないでください。ユーザー、サービス、トリガー、オペレーター、および手数料スポンサーには、別々のアカウントを使用してください。
- 設定とテストでは正規のアカウントおよびドメイン識別子を使用してください。Iroha の名前は正規解析後に大文字と小文字が区別されます。
- テスト環境と本番環境の識別情報は、名前、ドメイン、設定ファイルのパスで目に見えるように区別してください。

見る [ドメイン](/ja/blockchain/domains.md), [アカウント](/ja/blockchain/accounts.md), そして [命名](/ja/reference/naming.md).

## 資産および NFTs {#assets-and-nfts}

- 代替可能な残高や譲渡可能な数量には数値資産を使用してください。
- 一意に所有されるレコードには、NFTs またはドメイン固有のオブジェクトを使用してください。
- 価値を持つ状態をメタデータのみにエンコードすることは避けてください。アセットや NFTs は、メタデータにはないライフサイクルイベント、転送の意味論、および権限チェックを提供します。
- 資産をアプリケーションに公開する前に、精度、供給ポリシー、発行者の責任、およびバーン/ミント認可の原則を定義してください。

見る [資産](/ja/blockchain/assets.md), [NFTs](/ja/blockchain/nfts.md), そして [RWAs](/ja/blockchain/rwas.md).

## メタデータ {#metadata}

- ラベル、統合ID、ポリシーフラグ、暗号ハッシュ、URIs、またはコンテンツアドレス参照など、ブロックチェーン台帳オブジェクトのコンパクトな属性にはメタデータを使用します。
- メタデータのキーは安定したものにして、文書化しておくこと。クライアントがそれに依存した後でキー名を変更すると、移行の問題が発生する。
- 大きなドキュメント、ログ、個人ユーザーデータ、または高い変更頻度のアプリケーション状態をメタデータに直接保存しないでください。
- メタデータがオフチェーンデータを指す場合、コンテンツの暗号ハッシュ、URI、SoraFS パス、技術マニフェスト参照、またはコンパクトな暗号コミットメント値など、検証可能な参照を保存してください。

[メタデータとブロックチェーン台帳の保存方法の選択](/ja/guide/configure/metadata-and-store-assets.md) と [メタデータ](/ja/blockchain/metadata.md) を参照してください。

## モデルごとの権限 {#permissions-by-model}

- 役割は実装の便宜ではなく、ビジネスの運営を中心に設計してください。ジョブやサービスの名前を付けた役割は、広範な技術的能力の名前を付けた役割よりも監査が容易です。
- ワークフローを満たす最小のオブジェクトに権限トークンの範囲を制限します。
- 発行、破棄、ネットワークピア管理、実行者の変更、トリガー管理、メタデータの変更に関する権限は、影響の大きい権限として扱います。
- 一時的な権限に対する明示的な取り消しおよび更新手順を追加する。

[権限](/ja/blockchain/permissions.md) と [許可トークン](/ja/reference/permissions.md) を参照してください。

## クエリ形状 {#query-shape}

- アプリケーションが最も頻繁に必要とするクエリをサポートする識別子とメタデータキーを選択してください。
- 広範な結果セットをページ分けし、通常の操作でブロックチェーン台帳全体を無制限にスキャンすることを必要とするユーザーインターフェースを避けてください。
- 重要なアプリケーションの動作に使用される場合には、オフチェーンのインデックスがブロックチェーン台帳のデータやイベントから再構築可能な状態に保つこと。
