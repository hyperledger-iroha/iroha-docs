# I105 Hesab Ünvanının Formatı {#i105-account-address-format}

I105 Iroha 3 `AccountId` üçün yeganə protokol-standart xarici mətn formatıdır.

Onun yükü hesab nəzarətçisini təmsil edir.

Onun gözətçisi nəzərdə tutulmuş şəbəkəni zəncir diskriminantı ilə müəyyən edir.

Onu hər yerdə istifadə edin, harada ki, API, əməliyyat, icazə və ya sorğu tək protokol-standart hesab identifikatoru tələb edir.

Bir I105 hesab ID-si domainsizdir.

`treasury@payments.universal` kimi bir dəyər hesab aliasıdır, I105 ID-nin başqa yazılışı deyil.

I105 ID-nin əldə edilməsi hesabı qeydiyyatdan keçirmir və ya maliyyələşdirmir.

::: warning Əksər inteqrasiya uğursuzluqlarının qarşısını alan qaydalar

- Adres kodlaşdırılmadan və ya yoxlanılmadan əvvəl şəbəkə profilini seçin.
- Tək protokol-standart UTF-8 sətrini dəqiq saxlayın və müqayisə edin.
- Hərflərin böyük-kiçikliyini qoruyun və `Unicode` normallaşdırmasını tətbiq etməyin.
- I105 ID-də `@domain` və ya `@domain.dataspace` şəkilçisi olmamalıdır.
- Bir Iroha SDK və ya `iroha tools address` istifadə edin.
- Müntəzəm ifadə I105 doğrulayıcısı deyil.

:::

## Həqiqi anatomiya {#literal-anatomy}

Bir I105 literalı üç qonşu hissədən ibarətdir və heç bir ayırıcı yoxdur:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

|Hissə|Məqsəd|Yoxlama cəmi əhatəsi|
| ---------------- | ------------------------------------------------------------------ | ----------------- |
|Şəbəkə mühafizəçisi|Mətni bir `u16` zəncir diskriminantına xəritələyir|Əhatə olunmur|
|Faydalı yük|`base-105` kanonik hesab nəzarətçisi baytlarının kodlanması |Əhatə olunur |
|Yoxlama cəmi| I105 əlifbası ilə təqdim olunan altı `Bech32m`-stil `5-bit` dəyər|Y/Ə|

Yükləmə və yoxlama cəmi hesabın idarəedicisini müəyyən edir.

Mühafizəçi şəbəkə kontekstini seçir.

Eyni idarəedicinin Taira və Minamoto üzərində eyni yükü və yoxlama cəmi var, lakin hər şəbəkə fərqli başlanğıc sentinel istifadə edir.

Dekoder gözlənilən diskriminanti tətbiq etməlidir.

Yoxlama cəmi sentinel əvəzlənməsini aşkar edə bilmir.

### Şəbəkə mühafizəçiləri {#network-sentinels}

|Şəbəkə və ya kontekst|Zəncir diskriminant|Heks|tək protokol-standart sentinel|
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
| Taira ictimai test şəbəkəsi |                            `369` | `0x0171` | `test`                                      |
|Minamoto ümumi şəbəkə|                            `753` | `0x02f1` | `sora`                                      |
|İnkişaf konteksti|                              `0` | `0x0000` | `dev`                                       |
|Hər hansı digər `u16` dəyəri|Bütün `0`, `369` və `753` istisna olmaqla|        — | `n` plus minimal onluq, məsələn `n42` |

Adlandırılmış dəyərlər həmişə onların adlandırılmış sentineldən istifadə edirlər.

`n00042`, `n369`, `n753` və `n0` kimi formalar tək protokol-standart deyil.

Əməliyyat-zəncir ID-si və I105 zəncir fərqləndiricisi ayrı dəyərlərdir.

API son nöqtəsini və ya zəncir ID-ni seçmək ünvan profilini avtomatik seçmir.

## Normativ tək-açar nümunə {#normative-single-key-example}

Aşağıdakı faydalı yük və Minamoto forması SDK-lərarası uyğunluq test verilənlərindən götürülüb.

Taira forması Taira-in gözətçisini eyni yükə tətbiq edir:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

Tək protokol-standart yük `02 00 01 20` ilə başlayır: başlıq `0x02`, kompakt tək-açar etiketi `0x00`, `Ed25519` əyrisi ID `0x01` və 32 baytlıq açar uzunluğu `0x20`.

`multihash` prefiksi giriş metadata-sıdır və kontroller yükünə kopyalanmır.

## CLI ilə ID-ləri yaradın və yoxlayın {#create-and-inspect-ids-with-the-cli}

İctimai şəbəkə üçün adla profil üstünlük verin:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

Ünvan-kodek davranışını diaqnoz edərkən I105 girişini normallaşdırın və müqayisə edin:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

Aşkarlanmış formatı, tək protokol-standart heks və seçilmiş şəbəkə kontekstini JSON kimi yoxlayın:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

Yeni sətirlərlə ayrılmış faylın ünvan-kodek strukturunu analiz edin və təhlil səhvlərini səssizcə qəbul etməyin:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution CLI təsdiqləmə sərhəddi

`convert`, `normalize` və `audit` komandaları aşağı səviyyəli `AccountAddress` kodeki üzərində işləyir.

Onlar sentinel, əlifba, checksum, bayt uzunluqları, `CurveId`/açar forması və dəqiq ünvan təbəqəsinin yenidən kodlanmasını yoxlayırlar.

Onlar `AccountId`-u maddiləşdirmirlər.

Onlar özləri bütün çox imzalı siyasət semantikasını təsdiqləmirlər.

Onlar başlıq sinfinin kontrollerlə uyğun olduğunu sübut etmirlər.

Avtorizasiyadan və ya davamlı yaddaşa yazmadan əvvəl ciddi `AccountId` təsdiqləməsindən istifadə edin.

:::

Özəl şəbəkə üçün, onun təyin edilmiş fərqləndiricisini açıq şəkildə `--network-prefix` ilə istifadə edin.

Mövcud ünvanı açıq kontekstlər arasında çevirərkən, həmçinin mənbəyə `--expect-prefix` təqdim edin:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

Yenidən kodlaşdırma yalnız şəbəkə kontekstini dəyişir.

Bu, hesabı hədəf şəbəkədə qeyd etmir və ya eyni nəzarətçinin orada yenidən istifadə edilməli olduğunu sübut etmir.

## Kodlaşdırma alqoritmi {#encoding-algorithm}

tək protokol-standart kodlayıcılar bu əməliyyatları yerinə yetirir:

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

Öndəki sıfır baytlar sıfır dəyərli `base-105` rəqəmlər kimi qorunur.

Yoxlama cəmi `Bech32` `polymod` generatorlarından və `0x2bc830a3` sabitindən istifadə edir.

Yalnız yoxlama cəmi HRP ASCII sətir `snx`-dir.

Yalnız yoxlama cəmi HRP ünvanda çap edilmir.

Altı yoxlama cəmi dəyərləri `0..31` aralığındadır və yük kimi eyni I105 əlifbası ilə göstərilir.

### I105 əlifba {#i105-alphabet}

105 simvol bu dəqiq ardıcıllıqla indeksləşdirilib.

Birinci sıra `Bitcoin Base58` əlifbasıdır və `0..57` rəqəmləri ehtiva edir.

İkinci sətir `58..104` rəqəmlərini ehtiva edir.

Kodeki tətbiq edərkən sətirləri birləşdirin.

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

Əlifba `Unicode`-ə həssasdır.

Dəqiq ardıcıllıq `compatibility-width` Yapon `kana` simvollarından və `ヰ` və `ヱ` üçün göstərilən kod nöqtələrindən istifadə edir.

NFC, NFKC, simvol eninin çevrilməsi, hərf registrinin qatlanması və ya oxşar görünüşlü simvollarla əvəzləmə tətbiq etməyin.

ASCII `0`, `O`, `I` və `l` əlifba simvolları deyillər.

## tək protokol-standart hesab məlumatları {#canonical-account-payload}

`base-105` bədəni ikili hesab payloadunu kodlayır, açıq açar sətiri və Norito JSON obyekti deyil:

```text
header:u8 || controller:variable
```

Aşağıdakı bütün çoxbaytlı tam ədədlər işarəsizdir və `big-endian` dır.

Domain, dataspace, alias, UAID və hesab metadata baytları mövcud deyil.

### Başlıq baytı {#header-byte}

| Biti |En|Cari kodlayıcı çıxışı|Mənası|
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |Ünvan formatı versiyası sahəsi|
| `4..3` |     2 | `0` tək açar, `1` çox imzalı |Ünvan sinfi|
| `2..1` |     2 |                          `1` |Normallaşdırma versiyası sahəsi|
| `0`    |     1 |                          `0` |Rezerv edilmiş `extension flag` |

Hazırkı V1 kodlayıcılar tək açarlı nəzarətçi üçün başlıq `0x02` və çox imzalı nəzarətçi üçün `0x0a` yayırlar.

Ünvan sinifləri `2` və `3` təyin olunmayıb.

`1`-in `extension flag`-u rədd edildi.

Aşağı səviyyəli dekoder digər versiya və normallaşdırma bit dəyərlərini saxlayır və sinfi müstəqil olaraq kontroller teqi ilə qarşılıqlı yoxlamır.

`AccountId`-a çevirmək və onun tək protokol-standart şəklini müqayisə etmək, cari V1-in tək protokol-standart formasına uyğun olduğunu göstərir.

### Tək düyməli idarəedici {#single-key-controller}

Xam açıq açar yükü maksimum 255 bayt olduqda yığcam formadan istifadə edin:

|Sahə|En|Dəyər və ya mənası|
| ------------ | --------------: | ------------------------ |
| `tag`        |          1 bayt | `0x00`                   |
| `curve`      |          1 bayt | `CurveId` qeydiyyat dəyəri |
|`key_len` |1 bayt |Xam açarın uzunluğu |
|`public_key` |`key_len` baytlar |Xam ictimai açar yükü |

255 baytdan uzun açarlarda genişləndirilmiş forma istifadə olunur:

|Sahə|En|Dəyər və ya mənası|
| ------------ | --------------: | ---------------------------- |
| `tag`        |          1 bayt | `0x02`                       |
| `curve`      |          1 bayt | `CurveId` qeyd dəftəri dəyəri |
|`key_len` |2 bayt |Xam açarın uzunluğu, `big-endian` |
|`public_key` |`key_len` baytlar |Xam ictimai açar yükü |

Genişləndirilmiş kodlaşdırma, kompakt formaya uyğun gələn açar üçün tək protokol-standart deyil.

### Çox imzalı nəzarətçi {#multisig-controller}

|Sahə|En|Dəyər və ya mənası|
| ---------------- | -------: | ------------------------------ |
| `tag`            |1 bayt| `0x01`                         |
| `policy_version` |   1 bayt |Cari dəyər `1`|
| `threshold`      |  2 bayt |Tələb olunan ümumi təsdiq çəkisi|
| `member_count` |  2 bayt |Aşağıdakı üzvlərin sayı|
| `members`        |Dəyişən|Təkrarlanan üzv qeydləri|

Hər bir üzv qeydi belədir:

|Sahə|En|Mənası|
| ------------ | --------------: | ------------------------ |
| `curve`      |          1 bayt | `CurveId` qeydiyyat dəyəri |
| `weight`     |         2 bayt |Üzv təsdiqi çəkisi|
|`key_len` |2 bayt |Xam açarın uzunluğu |
|`public_key` |`key_len` baytlar |Xam ictimai açar yükü |

Etibarlı siyasətin ən azı bir üzvü və müsbət çəkiləri olmalı, təkrarlanan ictimai açarları olmamalı, həddi isə `1`-dən üzvlərin çəkilərinin cəminədək olmalıdır.

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

tək protokol-standart quruluş üzvləri imzalama alqoritminin sabit adına, sıfır ayırıcı bayta və sonra xam açıq açar baytlarına görə sıralayır.

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

Bir I105 literalı sabit simvol uzunluğuna malik deyil, çünki çox imzalı və kvant sonrası nəzarətçilər böyük ola bilər.

## Sərt AccountId yoxlama və vahid protokol-standart formasına uyğunluq {#strict-accountid-validation-and-canonicality}

SDK-i gözlənilən zəncir diskriminantı ilə konfiqurasiya etdikdən sonra, onu `AccountId`-ə ayrışdırın və qaytarılan tək protokol-standart təqdimatı kəsilmiş girişlə müqayisə edin.

Müqayisə əhəmiyyətlidir, çünki təhlilçi `AccountId` qurarkən deşifrə edilə bilən nəzarətçi materialını normallaşdıra bilər.

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

Etibarsız bir sətir üçün, uyğun bir tətbiq aşağıdakıları etməlidir:

1. Yalnız tam dəyərin ətrafında icazə verilmiş nəqliyyat boşluqlarını kəsin.
2. Növbəti qiyməti oxuyun və gözlənilən zəncir diskriminantını tələb edin.
3. Qalan hər `Unicode` simvolunu tam olaraq 105 simvolluq əlifba ilə xəritələndirin.
4. Yoxlama cəminin altı rəqəmini ayırın.
5. Yük məlumatlarının rəqəmlərini yenidən tək protokol-standart byte-lara çevirin.
6. O tək protokol-standart baytlar üzərində checksum-u təsdiqləyin.
7. Başlıq və kontrolleri analiz edin, tələb olunur:
   - dəqiq sahə uzunluqları
   - daşınan `CurveId`
   - etibarlı açıq açar
   - sonrakı baytlar yoxdur
   - tətbiq olunduğu halda etibarlı multisig siyasəti
8. `AccountId` inşa et.
9. Gözlənilən diskriminant üçün `AccountId`-i tək protokol-standart formada təqdim edin.
10. Kənar boşluqları kəsilmiş girişlə `byte-for-byte` bərabərlik tələb edin.

Tətbiqin açıq son `render-and-compare` mərhələsi minimal olmayan rəqəmsal sentinel-ləri, tək protokol-standart nəzarətçi yerləşdirmələrini, yenidən sıralanmış siyasət materialını və kodu deşifrə edən, lakin kodlayıcının hazırkı V1 çıxışı olmayan hər hansı digər yazımı rədd edir.

Uğurlu bir yoxlama cəmi və ya aşağı səviyyəli `AccountAddress` təhlil bu yoxlamanın əvəzi deyil.

Bu dəyərləri sərt hesab-ID sahəsində qəbul etməyin:

- bir hesab ləqəbi, məsələn `alice@wonderland.universal`
- əlavə edilmiş `@domain` şəkilçisi olan I105 mətn
- ictimai açar `multihash` kimi `ed0120...`
- tək protokol-standart faydalı yük hex kimi `0x02000120...`
- yanlış zəncir diskriminantı üçün ünvan
- böyük və ya kiçik hərfləri, simvol enləri, `kana`, yükləmə məlumatı və ya yoxlama cəmi dəyişmiş bir simli

Söhbət tətbiq sərhədində təxəllüsləri həll etməkdən gedir və icazə, imzalama, səlahiyyətlər və audit qeydləri üçün geri qaytarılan tək protokol-standart I105 identifikatorunu saxlamaq.

## API, saxlama və göstərmə qaydaları {#api-storage-and-display-rules}

- JSON hesab sahələrində dəqiq I105 UTF-8 sətirini göndərin.
- `Percent-encode` tam hesab ID-sini URL yol seqmentinə yerləşdirmədən əvvəl.
- Heç vaxt I105 ID-ni hesab aliası ilə əvəz etməyin.
- Kodek tərəfindən qaytarılan tək protokol-standart simli `byte-preserving` müqayisə semantikası ilə saxlayın.
- Hərflərin böyük-kiçikliyini və simvol enini qoruyan kollasiyadan istifadə edin.
- Zəncir diskriminantını və ya ixrac edilmiş hesab məlumatları və ehtiyat nüsxələri ilə adlandırılmış şəbəkə profilini saxlayın.
- Bir ünvandan yalnız onun şəbəkə konteksti ilə istifadə edin.
- Tam ünvanı göstərin və nüsxə əməliyyatı təmin edin.
- Hər `kana` simvolunu dəqiq qoruyun.
- Tam ünvanı əlçatan saxlayın, əgər kompakt göstərici onun ortasını qısaldırsa.
- Bunu bir laqeydlikdən yenidən qurmaq əvəzinə saxlanılan tək protokol-standart ID-dən istifadə edin.

`AccountId` ekranı və JSON təqdimatı kanonik I105-dən istifadə edir.

Aşağı səviyyəli `AccountAddress` ekran/JSON təsviri daxili və ayıklama kontekstlərində tək protokol-standart səkkizlikdən istifadə edir.

Xarici hesab ID-si tələb olunduqda açıq `AccountAddress` I105 kodlayıcısını çağırın.

Hesab yaradılması və təxəllüs həll etmə iş axınları üçün, [Hesablar və təxəllüslər](/az/cookbook/accounts-and-aliases.md) ilə davam edin.

Hesab məlumat modeli üçün baxın [Hesablar](/az/blockchain/accounts.md).
