# בדיקת כאוס עם איזאנאמי {#chaos-testing-with-izanami}

איזאנאמי הוא ארכיסטרטור הרעש במעלה הזרם. Iroha חלל עבודה.
פותח מקומי חד פעמי Iroha הקלאסטר מספק עומס עבודה מותאם,
ומדביקים שגיאות לתוך עמידים נבחרים כדי שהפעילים יוכלו לבדוק אם
הרשת ממשיכה להתקדם תחת כשלון מבוטל.

השתמש ביזאנאמי לבדיקות עמידות לפני הייצור, פירוש ריגרסיה,
לא לכוון את זה לרשת הייצור: הכלים הם
מיועדת להיות בעלת הדוגמאות שהיא מתחילה, כולל התחזית דוגמנית, אחסון
כביסה, אובדן ארגז מלאכותי, ומרחב מקומי CPU או לחץ דיסק.

## תנאים מוקדמים {#prerequisites}

לנהל Izanami מה
[Iroha מאגר המקור](https://github.com/hyperledger-iroha/iroha),
לא מתוך מאגר המסמכים הזה:

```bash
git clone https://github.com/hyperledger-iroha/iroha.git
cd iroha
cargo build -p izanami
```

יש לאפשר באופן מפורש ל-binary ליצור ולפעול ברשת
עמיתים. `--allow-net` עבור כל לא-TUI להפעיל או לאפשר `allow_net` ב
ה- TUI.

```bash
cargo run -p izanami -- --allow-net --peers 4 --faulty 1 --duration 120s
```

עבור תצוגה אינטראקטיבית:

```bash
cargo run -p izanami -- --tui --allow-net
```

Izanami מתעקש TUI ו CLI הגדרות תחת תיבת ההשפעה של המשתמש, כך
לבדוק את ההגדרות המוצגות לפני השימוש מחדש בפרופיל הקודם.

## תוצאת בסיס {#baseline-run}

תתחיל עם בסיס אחד שניתן להשיב לפני שתוסיף פגמים חמורים:

```bash
cargo run -p izanami -- \
  --allow-net \
  --peers 4 \
  --faulty 1 \
  --duration 5m \
  --target-blocks 100 \
  --progress-interval 15s \
  --progress-timeout 120s \
  --latency-p95-threshold 2s \
  --tps 15 \
  --max-inflight 32 \
  --submitters 1 \
  --seed 42
```

הפריסה הזו תצליח רק אם הקלאסטר יגיע למטרה המבוקשת,
ממשיך להתקדם תוך זמן הפסקה, ונשאר תחת p95 בחופשי.
סף מרחב חסיבות.

כותב את הפקודה, זרע. Iroha מחייב, ספירת שווים, ספירה כפויה של שווים,
פרופיל עומס העבודה, מטרה TPS, סף איחור עם היומן.
הערכים אלה, מפעיל אחר לא יכול לחזור על דפוס הפסלה אותו.

## פרופילים של עומס עבודה {#workload-profiles}

ביזאנאמי יש שני פרופילים של עומס עבודה:

| פרופיל  | השתמשו בו                                         | הערות                                  |
| -------- | -------------------------------------------------- | -------------------------------------- |
| `stable` | טיולים ארוכים ובדוקי ביצועים שניתנים לשחזר | מעדיפים מתכונים בטוחים בביצוע          |
| `chaos`  | כיסוי מסלול כשל                              | כולל מתכונים לא חוקיים בכוונה |

השתמש בפרופיל יציב קודם:

```bash
cargo run -p izanami -- --allow-net --workload-profile stable --seed 42
```

לעבור לפרופיל הוהוס כאשר הקו הבסיסי כבר ברור:

```bash
cargo run -p izanami -- --allow-net --workload-profile chaos --seed 42
```

המתכונים של הפעלת החוזים מופלמים במסלולים יציבים אלא אם כן מפורש
מותר:

```bash
cargo run -p izanami -- \
  --allow-net \
  --workload-profile stable \
  --allow-contract-deploy-in-stable
```

שימוש `--nexus` כאשר הפסקה צריכה להשתמש במערכת המשתולבת SORA Nexus דמיון
המרחב העבודה העליון.

## בקרת טעויות {#fault-controls}

מתי? `--faulty` הוא גדול יותר משני, לפחות סצנתר שגיאה אחד חייב להיות
פגמים בטעויות מופעלים באופן מקובל, וציגים בולניים יכולים להיות
פצועים עם `=false`.

| אשמה                    | CLI דגל                                   | מה הוא עושה                          |
| ------------------------ | ------------------------------------------ | ------------------------------------------ |
| להתמוטט ולהתחיל מחדש        | `--fault-enable-crash-restart`             | אובדן ושיקום של תהליך משותף             |
| לחיסול אחסון ולהתחיל מחדש | `--fault-enable-wipe-storage`              | התאוששות ממדינה מקומית חסרה          |
| ספאם של עסקאות לא חוקיות | `--fault-enable-spam-invalid-transactions` | מסלול הכניסה והרחיקה              |
| איחור רשת          | `--fault-enable-network-latency`           | בדיחות איטיות וודעות הסכמה מאוחרות |
| חלוקה רשת        | `--fault-enable-network-partition`         | בידוד זמני עם חברים אמינים           |
| P2P אובדן חבילה          | `--fault-enable-network-packet-loss`       | תנועת קישור יישומים נמוכה          |
| CPU לחץ               | `--fault-enable-cpu-stress`                | לחץ אישור מקומי ופעילות לוח הזמנים   |
| סיפוק דיסק          | `--fault-enable-disk-saturation`           | לחץ אחסון מקומי                     |

עבור תופעה עם אובדן רק של חבילות:

```bash
cargo run -p izanami -- \
  --allow-net \
  --peers 20 \
  --faulty 5 \
  --duration 800s \
  --fault-window-start 133s \
  --fault-window-end 266s \
  --tps 200 \
  --submitters 20 \
  --max-inflight 512 \
  --fault-enable-crash-restart=false \
  --fault-enable-wipe-storage=false \
  --fault-enable-spam-invalid-transactions=false \
  --fault-enable-network-latency=false \
  --fault-enable-network-partition=false \
  --fault-enable-network-packet-loss=true \
  --fault-enable-cpu-stress=false \
  --fault-enable-disk-saturation=false \
  --fault-network-packet-loss-percent 75 \
  --seed 42
```

שימוש `--fault-window-start` ו `--fault-window-end` כדי לשמור על
תקופה של מצב יציב לפני ואחרי הפסקה.
קל יותר להבחין בין רעש התחלה לתופעת הפגם.

## צורות הסצנה {#scenario-shapes}

הקלטוג של איזאנאמי מפה תקשורת blockchain נפוצה-כישלון
צורות ל CLI אתה יכול לדגם אותם עם אותם דגלים:

| תסריט              | צורה טיפוסית                                                                                                            |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| עומס ממוקד         | `--faulty 0`, גבוה `--tps`, אחד המגיש, גבוה `--max-inflight`                                                         |
| כשל חלקי     | אפשרת כנס/התחל מחדש רק בתוך חלון פגם מוגבל                                                                  |
| אובדן חבילה           | אפשר רק אובדן חבילות, בדרך כלל עם שיעור אובדן 75% כפויתי                                                          |
| עצירה ושיקום | השתמשו באוכלוסייה גדולה של דוגמאות פגמים עם קריסה/התחל מחדש                                                                    |
| בידוד מנהיג      | השתמשו בדיוק בקטן אחד שגוי עם טעויות רק בחלקת רשת או אובדן חבילות; Izanami עונה Sumeragi טלמטריה של המנהיג |

שמרו על משתנה אחד קבוע בכל פעם. אם תשנו את מספר השווים, עומס העבודה
פרופיל, חלון פגם, ו TPS באותה מידה, התוצאה היא קשה
תרגם.

## מה לצפות בו {#what-to-watch}

במהלך הריצה, צפו באותם אותים המשמשים לאישור הביצועים:

- התקדמות בגובה כביש בכל עוצמה
- עסקאות שהוגשו, התקבלו, נדחו ושלם
- עומק שורה, סיפוק שורה ולחץ אחראי של נקודת הסיום
- שינויים בתצוגה, דרכי התאוששות, בלוקים חסרים וקורום חסר
  תעודות
- RBC מאבקים, פגישות מחופשות, או תנועה קונצנזוס נמוכה או מאוחרת
- CPU, זיכרון, דיסק, ושמנת הרשת על המארח פועלת את העמיתים

עבור ניתוח של איחור אישור, להפעיל רישומי תיקון מעקב מרכזי:

```bash
RUST_LOG=iroha_core::sumeragi::main_loop=debug \
  cargo run -p izanami -- --allow-net --seed 42
```

כל חגורת צריכה לשחרר `block validation timings` עם `stateless_ms`,
`execution_ms`, ו `total_ms`. השווא את הזמנים האלה עם בלוק p95
מרחבים, מדדלי שינוי תצפית, לחץ בתור לפני השינוי
זמני הסכמה.

## תוצאות פירוש {#interpreting-results}

תתייחסו לרוץ כמו בריא כאשר כל השווים שנבחרים ממשיכים לבצע בלוקים,
מאבדים לא גדלים ללא קישור, ותשפעות מפסיקות לגרום להתאוששות חדשה
פעילות לאחר סיום החלון המוגדר.

להתייחס לרוץ ככישלון כאשר:

- חבילות התקדמות של בלוק ארוכות יותר `--progress-timeout`
- גבהים של עמידים משתלבים ואינם מתכנסים מחדש.
- איחור p95 עולה `--latency-p95-threshold`
- שורות גדלות לשארית ההופעה לאחר כיסוי חלון פגם
- עסקים נדחפים או שנעצרו בזמן לא מוסברים על ידי
  עומס עבודה
- התחלה מחדש של עמיתים, סחירת אחסון או התאוששות מאובדן חבילה דורשת ידנית
  ניקוי

לאחר כישלון, תחזור עם אותו זרם וטיפוס פגם אחד פחות.
שומר על עומס העבודה והזמן שניתנים לשחזר תוך צמצום ההפלה.
על פני השטח.
