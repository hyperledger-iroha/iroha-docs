# מימון עמלות עבור מרחב נתונים פרטי {#sponsor-fees-for-a-private-data-space}

תוכנית למימון עמלות של SORA Nexus יכולה לשלם את עמלות הביצוע הגלובלי של עסקאות זכאיות המנותבות למרחב נתונים פרטי. המשתמש עדיין חותם על העסקה המלאה. ה־`FeePaymentIntent` מטיפוס מוגדר בוחר תוכנית מימון מדויקת וגרסה בלתי ניתנת לשינוי, מגבלת גז היכן שנדרשת, וחיובים מרביים.

רשומה בקטלוג מרחבי הנתונים אינה יוצרת שורש בעל חתימה עצמאית. לשורש עצמאי של מרחב נתונים יש מטבע עמלות ומדיניות מאושרים משלו; כספות מימון ציבוריות אינן יכולות לאשר עמלות של השורש הפרטי שלו. הגדירו את שורש הביצוע לפני תכנון המימון.

## 1. הגדרת מדיניות העמלות המאושרת {#_1-establish-the-committed-fee-policy}

ה־genesis החתום מגדיר פרמטר מותאם אישית יחיד בשם `root_fees_v1`, המכיל את `RootFeePolicy`. הוא מקבע את מטבע העמלות, יעד העמלות, חשבון המשמורת של נותן החסות, הפטורים לתביעות ואת התעריפים. כל בלוק רגיל והצעת מחיר משתמשים במדיניות המאושרת שנלכדה עבורם. שינויים מורשים בתעריפים, ביעד העמלות ובפטורים לתביעות חלים מהבלוק הבא; לא ניתן לשנות את מטבע העמלות ואת חשבון המשמורת של נותן החסות לאחר הבלוק הראשון.

בביצוע גלובלי, העמלה הניטיבית שורפת את מטבע ה־XOR המדויק שהוגדר בחתימה עבור הרשת. כספת התוכנית של נותן החסות מספקת את המטבע הזה. הגדרות הצומת והמטא־נתונים של העסקה אינם בוחרים משלם ואינם מפעילים מימון.

השתמשו בזהויות המטבע והחשבונות הקנוניות של הרשת. פתרון כינויים אינו רשאי להפנות מחדש את זהויות המטבע, המשמורת או יעד העמלות המאושרות.

## 2. יצירה ומימון של תוכנית חסות {#_2-create-and-fund-a-sponsor-program}

מזהה התוכנית הוא מהצורה `<canonical-sponsor-account>/<program-name>`. הגדירו אותה באמצעות ההוראות מטיפוסים מוגדרים שה־SDK ומודל הנתונים הנוכחיים חושפים:

| הוראה | מטרה |
| --- | --- |
| `CreateFeeSponsorProgram` | יצירת התוכנית בהכנה עם חשבון התשלום היוצא הנדרש שלה. |
| `StageFeeSponsorProgramRevision` | הגדרת מדיניות אחת ובלתי ניתנת לשינוי של זכאות, פעולות ותקציב. |
| `EnrollFeeSponsorBeneficiary` | רישום מוטב זכאי בשרשרת. |
| `FundFeeSponsorProgram` | העברת נכסים למשמורת וזיכוי כספת התוכנית המדויקת. |
| `ActivateFeeSponsorProgramRevision` | קביעת גובה ההפעלה המוקדם ביותר של הגרסה שבהכנה. |

נותן החסות או מנהל מסוים שהוסמך לכך מאשרים את ניהול התוכנית. משיכות מחייבות את נותן החסות עצמו ומחזירות כספים רק לחשבון התשלום היוצא הרשום של התוכנית, כשהתוכנית מושהית או בתהליך סגירה.

כל גרסה מציינת:

- הרשמה מפורשת, או הרשמה בצירוף זכאות מותרת כברירת המחדל של המסלול;
- כללי התרה ודחייה עבור מזהי תעבורה מדויקים של הוראות ניטיביות או כתובות חוזים, גיבובי קוד ונקודות כניסה;
- מגבלות לכל נכס ברמת עסקה, בלוק, תקופת תוכנית ותקופת מוטב;
- סף עתודה מינימלי ואורך תקופה דטרמיניסטי.

כלל דחייה גובר על כלל התרה. `fee_sponsor_program_id` של מרחב נתונים מעניק זכאות כברירת המחדל של המסלול רק אם הגרסה הפעילה מתירה זאת; העסקה עדיין חייבת לציין את התוכנית והגרסה המדויקות שלה. אפשר לדחות את ההפעלה עד לפקיעת ההקצאות הפתוחות מהגרסה הקודמת.

נכסי כספת המימון חייבים להשתמש במדיניות היתרה `Global`. מימון החשבון הרגיל של נותן החסות לבדו אינו מממן את כספת התוכנית המבודדת, ותוכנית אחת אינה יכולה לצרוך את היתרה של תוכנית אחרת.

## 3. קבלת הצעת מחיר, חתימה והגשת העסקה המדויקת {#_3-quote-sign-and-submit-the-exact-transaction}

שילוב באמצעות SDK מבצע את השלבים הבאים:

1. בנו את `TransactionPayload` הלא חתום עם הסמכות, תוכן הביצוע, חותמות הזמן, הערך החד־פעמי, המטא־נתונים, הגרסה המדויקת של תוכנית המימון וכל מגבלת גז נדרשת. בתחילה אפשר להשאיר את החיובים המרביים ריקים.
2. חתמו באמצעות החשבון על `POST /v1/fees/quote` עם `{"payload": <payload>}`. חותם הבקשה חייב להיות סמכות העסקה.
3. בדקו את הגובה שנצפה, מסלול מרחב הנתונים שנפתר, רכיבי העמלה, מקור החיוב וקיבולת המימון. ודאו שהתשובה משמרת את המשלם, הגרסה ומגבלת הגז שנבחרו.
4. החליפו רק את `payload.fee_payment` בכוונה המומלצת, ולאחר מכן חתמו על המטען המדויק הזה והגישו אותו.
5. עקבו אחר העסקה עד לסופיות `Applied` שנקבעה לפי המצב, ושמרו את הקבלה שלה, לרבות תוכנית המימון, הגרסה והחיוב ששימשו בפועל.

הצעת מחיר צופה בספר החשבונות; היא אינה שומרת קיבולת. הקבלה לתור בודקת מחדש את הזכאות ושומרת את הסכומים המרביים החתומים. סירוב למימון דוחה את העסקה ואינו עובר לחיוב המשתמש כחלופה.

ה־CLI מציין במפורש את אותו מקור עמלה. למשל, לאחר שהתוכנית מתירה את העברת הנכס המדויקת הזאת והחשבון זכאי:

```bash
iroha --config ./user.client.toml \
  --fee-payer sponsor \
  --fee-program '<SPONSOR_CANONICAL_I105>/team-payments' \
  --fee-program-revision 1 \
  ledger asset transfer \
  --definition '<ASSET_DEFINITION_BASE58>' \
  --account '<USER_CANONICAL_I105>' \
  --to '<RECIPIENT_CANONICAL_I105>' \
  --quantity 1
```

השתמשו בגרסה הפעילה ובמזהים המדויקים מהרשת שלכם. תצורת המשתמש מכילה רק את החותם של אותו משתמש; אין צורך במפתח הפרטי של נותן החסות להגשת עסקה ממומנת זכאית.

## 4. קביעה אם המשתמש משלם עמלת יישום {#_4-decide-whether-the-user-pays-an-application-fee}

נותן חסות יכול לכסות עמלות גלובליות בעוד היישום אינו גובה דבר מהמשתמש. אם היישום גובה אסימון מקומי, הגדירו את ההעברה או כלל החוזה האלה במפורש בתוכן הביצוע שעליו המשתמש חותם. כללו כל פעולה במדיניות של גרסת תוכנית המימון ובדקו את הצעת המחיר עבור המטען המלא. אל תסיקו העברת אסימון של היישום מכוונת עמלת הרשת.

## אבחון סירוב {#diagnose-a-refusal}

השתמשו בקוד העמלה היציב ובפרטי התיקון שהצומת מחזיר:

| קוד | מה לבדוק |
| --- | --- |
| `program_not_found` | זהות התוכנית הקנונית המדויקת. |
| `revision_not_active`, `program_not_active` | הפעלת הגרסה ומחזור החיים של התוכנית. |
| `beneficiary_not_eligible` | הרשמה או זכאות מותרת כברירת המחדל של המסלול. |
| `operation_not_allowed`, `operation_denied` | כל פעולה חתומה מדויקת וכלל דחייה. |
| `invalid_gas_limit`, `signed_limit_exceeded` | מגבלת הגז והסכומים המרביים החתומים מול הצעת מחיר חדשה. |
| `vault_insufficient` | היתרה הממומנת בכספת המטבע המדויקת של התוכנית הזאת. |
| קודים של מיצוי תקציב | הקיבולת ברמת עסקה, בלוק, תקופת תוכנית ותקופת מוטב. |

שמרו את גיבוב העסקה המקורי ואת פרטי דחיית העמלה בעת חקירת הגשה שתוצאתה אינה ברורה. ודאו את מצבה לפני בניית עסקה חלופית.
