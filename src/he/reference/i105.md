# I105 צורת כתובת החשבון {#i105-account-address-format}

I105 הוא פורמט הטקסט החיצוני הקנוני עבור Iroha 3 `AccountId`.

מטען הנתונים שלו מייצג את מנהל החשבון.

הסנטינל שלו מזהה את הרשת המיועדת באמצעות מבחין השרשרת.

השתמשו בו בכל מקום שבו API, עסקאות, רשות או שאילתה מבקשת חשבון קנוני ID.

חשבון I105 ID הוא ללא דומיין.

ערך כגון `treasury@payments.universal` הוא כינוי חשבון, ולא איות אחר של ה־I105 ID.

גזירת I105 ID אינה רושמת את החשבון ואינה מממנת אותו.

::: warning החוקים שמונעים את רוב הכישלונות באינטגרציה

- בחר את פרופיל הרשת לפני הקודד או אישור כתובת.
- שמרו והשוו במדויק את מחרוזת ה־UTF-8 הקנונית.
- שמרו על רישיות האותיות ואל תחילו נרמול `Unicode`.
- ל־I105 ID אסור שתהיה סיומת `@domain` או `@domain.dataspace`.
- השתמשו ב- Iroha SDK או `iroha tools address`.
- ביטוי רגולרי אינו כלי אימות ל־I105.

:::

## אנטומיה מילולית {#literal-anatomy}

במילה I105 יש שלושה חלקים סמוכים ולא מפרידים:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

| חלק | מטרה | כיסוי סכום הביקורת |
| ---------------- | ------------------------------------------------------------------ | ----------------- |
| סנטינל רשת | ממפה את הטקסט למבחין שרשרת `u16` אחד | לא מכוסה |
| מטען | קידוד `base-105` של הבתים הקנוניים של בקר החשבון | מכוסה |
| סכום ביקורת | שישה ערכי `5-bit` בסגנון `Bech32m`, המיוצגים באלפבית I105 | N/A |

המטען וסכום הביקורת מזהים את בקר החשבון.

השומר בוחר את ההקשר של הרשת.

לאותו מנהל יש את אותו מטען ואת סכום הבדיקות על Taira ו Minamoto, אך כל רשת משתמשת בסנטינל מוביל שונה.

מפענח חייב לאכוף את מבחין השרשרת הצפוי.

סכום הביקורת אינו יכול לזהות החלפה של הסנטינל.

### משמרים ברשת {#network-sentinels}

| רשת או הקשר | מבחין שרשרת | Hex | סנטינל קנוני |
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
|Taira רשת מבחן ציבורית |                            `369` |`0x0171` |`test` |
|רשת ציבורית Minamoto|                            `753` |`0x02f1` |`sora` |
|היקף הפיתוח |                              `0` |`0x0000` |`dev` |
|כל ערך אחר `u16` |כל אלה מלבד `0`, `369`, ו `753` |        — |`n` ועוד דצימלית מינימלית, למשל `n42` |

ערכים בעלי שם משתמשים תמיד בסנטינל בעל השם המתאים להם.

טופסים כגון `n00042`, `n369`, `n753` ו `n0` אינם קנוניים.

ה־ID של שרשרת העסקאות ומבחין השרשרת של I105 הם ערכים נפרדים.

בחירת נקודת קצה או ID של שרשרת אינה בוחרת במשתמע את פרופיל הכתובת.

## דוגמה של מפתח אחד נורמטיבי {#normative-single-key-example}

המטען וטופס Minamoto שלהלן מגיעים מערכת בדיקות התאימות חוצת-SDK.

הטופס Taira מיישם את השומר של Taira על אותו מטען נתונים:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

מטען הנתונים הקנוני מתחיל עם `02 00 01 20`: כותרת `0x02`, קישור חד-מפתח קומפקטי `0x00`, עקומה `Ed25519` ID `0x01`, וגובה מפתח של 32 בייטים `0x20`.

הפריפיקס `multihash` הוא מטא-מדע הכניסה ואינו נעתק לטובת המובטח של השליטה.

## ליצור ולבדוק את IDs עם CLI {#create-and-inspect-ids-with-the-cli}

מעדיפים פרופיל עם שם עבור רשת ציבורית:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

נורמליזציה והשוואה של הכניסה I105 בעת אבחון התנהגות כתובת-קודק:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

לבחון את התבנית המובטחת, הקס קנוני וקשר הרשת הנבחר כ- JSON:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

לבחון את מבנה ה-codec של תיק נפרד בשורה חדשה ללא לקבלת כישלונות בניתוח בשקט:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution גבול אישור CLI

הפקודות `convert`, `normalize`, ו `audit` פועלות על הקודק של רמה נמוכה יותר `AccountAddress`.

הפקודות מאמתות את הסנטינל, האלפבית, סכום הביקורת, אורכי הבתים, המבנה של `CurveId`/המפתח, ואת הקידוד מחדש המדויק בשכבת הכתובת.

הן אינן יוצרות `AccountId`.

הם אינם מאשרים בעצמם את כל הסמנטיקה של מדיניות multisig.

הם לא מוכיחים שהכיתה של כותרת תואמת את המפעיל.

השתמשו באימות קפדני של `AccountId` לפני הרשאה או שמירה מתמשכת.

:::

ברשת פרטית, השתמשו במפורש במבחין שהוגדר לה באמצעות `--network-prefix`.

כאשר מתבנית כתובת קיימת בין קונקסטים מפורשים, גם למסור את המקור עם `--expect-prefix`:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

קידוד מחדש משנה רק את הקשר הרשת.

הוא לא רשום את החשבון ברשת היעד או מוכיח כי אותו מנהל צריך להיות בשימוש מחדש שם.

## אלגוריתם קוד {#encoding-algorithm}

מקודרים קאנוניקים מבצעים את הפעולות הבאות:

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

בייטים של אפס מובילים נשמרו כמספרים `base-105` בעלים ערך אפס.

סכום הבדיקה משתמש בגינרטורים `Bech32` `polymod` וקבוע `0x2bc830a3`.

ה־HRP המשמש רק לסכום הביקורת הוא מחרוזת ה־ASCII `snx`.

ה־HRP המשמש רק לסכום הביקורת אינו מופיע בכתובת.

שש הערכים של סכום הבדיקה נמצאים בטווח `0..31` ומוצגים באותם אלפבית I105 כמו מטען הנתונים.

### אלפבית I105 {#i105-alphabet}

105 הסימבלים מיועדים בסדר זה בדיוק.

השורה הראשונה היא האלפבית `Bitcoin Base58` ומכילה את המספרים `0..57`.

השורה השנייה מכילה את המספרים `58..104`.

קונקייטן את השורות בעת יישום הקודק.

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

האלפבית רגיש ל- `Unicode`.

רצף מדויק משתמש באותיות `compatibility-width` יפניות `kana` בתוספת נקודות הקוד המוצגות עבור `ヰ` ו`ヱ`.

אל תחילו NFC, NFKC, המרת רוחב, קיפול רישיות או החלפה בתו דומה למראה.

ASCII `0`, `O`, `I`, ו `l` אינם סמלים אלפבית.

## מטען שימושי של חשבון קאנוניקה {#canonical-account-payload}

גוף `base-105` מקודד עומס מועיל של חשבון בינארי, לא שרשרת מפתח ציבורי ולא אובייקט Norito JSON:

```text
header:u8 || controller:variable
```

כל המספרים השלמים מרובי־הבתים שלהלן הם ללא סימן ובסדר `big-endian`.

דומיין, חלל נתונים, כינוי, UAID, ובייטים של מטא-נתונים של חשבון אינם נוכחים.

### כותרת בייט {#header-byte}

|חלקים |רוחב |תוצאת ה-encoder הנוכחית |משמעות |
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |שדה גרסה של תיאור כתובת |
| `4..3` |     2 |`0` מפתח חד פעמי, `1` רב סיג |כיתה כתובת |
| `2..1` |     2 |                          `1` |שדה גרסה נורמליזציה |
| `0` | 1 | `0` | `extension flag` שמור |

הקודרים הנוכחיים V1 משדרים כותרת `0x02` עבור שליטה בעלת מפתח אחד, ו`0x0a` עבור שליטה עם מספר סיג'ים.

מחלקות הכתובת `2` ו־`3` אינן מוקצות.

דחייה `extension flag` של `1` נדחה.

המפענח ברמה הנמוכה יכול לשמר ערכי ביט אחרים של גרסה ונרמול, ואינו מבצע באופן עצמאי בדיקה צולבת של המחלקה מול תג הבקר.

המרה ל־`AccountId` והשוואה לייצוג הקנוני שלו מוכיחות קנוניות לפי V1 הנוכחי.

### בדיקת מפתח אחד {#single-key-controller}

השתמשו בצורת קומפקטית כאשר עומס הפועל של המפתח הציבורי הוא לא יותר מ-255 בייטים:

|שדה |רוחב |ערך או משמעות |
| ------------ | --------------: | ------------------------ |
|`tag` |1 בייט |`0x00` |
|`curve` |1 בייט |`CurveId` ערך רישום |
| `key_len` | בית אחד | אורך המפתח הגולמי |
| `public_key` | `key_len` בתים | מטען המפתח הציבורי הגולמי |

מפתחות ארוכות יותר מ -255 בייטים משתמשות בצורת המורחבה:

|שדה |רוחב |ערך או משמעות |
| ------------ | --------------: | ---------------------------- |
|`tag` |1 בייט |`0x02` |
|`curve` |1 בייט |`CurveId` ערך רישום |
| `key_len` | 2 בתים | אורך המפתח הגולמי, `big-endian` |
|`public_key` |`key_len` בייטים |מטען פוטנציאלי של מפתח ציבורי|

קוד ממושך אינו קנוני עבור מפתח שמתאים לצורת קומפקטית.

### פיקוח רב סיג {#multisig-controller}

|שדה |רוחב |ערך או משמעות |
| ---------------- | -------: | ------------------------------ |
|`tag` |1 בייט |`0x01` |
|`policy_version` |1 בייט |ערך זמני `1` |
|`threshold` |2 בייטים |משקל האישור הכולל הנדרש |
|`member_count` |2 בייטים |מספר חברי הבאים |
|`members` |משתנה |רישומי חברי חוזרים |

כל רישום חבר הוא:

|שדה |רוחב |משמעות |
| ------------ | --------------: | ------------------------ |
|`curve` |1 בייט |`CurveId` ערך רישום |
|`weight` |2 בייטים |משקל האישור של חבר |
| `key_len` | 2 בתים | אורך המפתח הגולמי |
| `public_key` | `key_len` בתים | מטען המפתח הציבורי הגולמי |

מדיניות תקפה יש לפחות חבר אחד, משקל חיובי, אין מפתחות ציבוריים כפולים, וסף של `1` דרך סכום משקלי חברי.

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

הבנייה הקנונית ממיינת את החברים לפי השם היציב של אלגוריתם החתימה, אחריו בית מפריד אפס, ולאחר מכן בתי המפתח הציבורי הגולמי.

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

במילה I105 אין אורך אותיות קבוע, כי המפעילים מולטי-סיג'ים ופוסט-קוואנטי יכולים להיות גדולים.

### רישום `CurveId` {#curveid-registry}

העמודה הסופית מכילה את התכונה הבלתי אפשרית `Cargo` הנדרשת.

סימן מחיצה אומר כי הכניסה לרשום זמינה ללא תכונה אופציונלית של דגם נתונים.

|ID |אלגוריתם חתימה |הדרישה `Cargo` תכונה |
| ---: | -------------------------------------------- | ------------------------ |
|  `1` |`Ed25519` | —                        |
|  `2` |`ML-DSA` | —                        |
|  `3` |`BLS12-381 normal` |`bls` |
|  `4` |`secp256k1` | —                        |
|  `5` |`BLS12-381 small` |`bls` |
| `10` |`GOST R 34.10-2012 256-bit, parameter set A` |`gost` |
| `11` |`GOST R 34.10-2012 256-bit, parameter set B` |`gost` |
| `12` |`GOST R 34.10-2012 256-bit, parameter set C` |`gost` |
| `13` |`GOST R 34.10-2012 512-bit, parameter set A` |`gost` |
| `14` |`GOST R 34.10-2012 512-bit, parameter set B` |`gost` |
| `15` |`SM2` |`sm` |

IDs ללא מיתוי ואלגוריתמים שאינם פעילים בבניית המתקבלים נדחו.

המטען החשוב של המפתח חייב להיות גם בעלת תקנה מבנית לאלגוריתם שנבחר על ידי `CurveId` המוצהר.

## אישור קפדני AccountId וקנוניקה {#strict-accountid-validation-and-canonicality}

לאחר הגדרת ה־SDK עם מבחין השרשרת הצפוי, נתחו ל־`AccountId` והשוו את הייצוג הקנוני שהוחזר לקלט לאחר הסרת הרווחים מקצותיו.

ההשוואה חשובה משום שהמנתח יכול לנרמל חומר בקר שניתן לפענוח בעת בניית ה־`AccountId`.

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

עבור שרשרת לא אמינה, יישום מתאים צריך:

1. הסירו רק רווחי תעבורה מותרים מסביב לערך המלא.
2. קראו את הסנטינל ודרשו את מבחין השרשרת הצפוי.
3. מפו כל סמל `Unicode` שנותר דרך האלפבית המדויק בן 105 הסמלים.
4. לחלק את שש המספרים של סכום המחאה.
5. הפוך את המספרים של המטען נתונים בחזרה באייטים קנוניים.
6. בדוק את סכום הבדיקה על האייטים הקנוניים האלה.
7. נתחו את הכותרת ואת הבקר, ודרשו:
   - אורך השדה המדויק
   - א תומך `CurveId`
   - מפתח ציבורי בתוקף
   - שלא יהיו בתים עודפים בסוף
   - מדיניות רב סיג תקפה, אם מתאימה.
8. לבנות `AccountId`.
9. הציגו את `AccountId` בצורה קנונית עבור המבחין הצפוי.
10. דרשו שוויון `byte-for-byte` לקלט לאחר הסרת הרווחים מקצותיו.

שלב ה־`render-and-compare` הסופי והמפורש של היישום דוחה סנטינלים מספריים שאינם מינימליים, פריסות בקר שאינן קנוניות, חומר מדיניות שסודר מחדש, וכל איות אחר שניתן לפענוח אך אינו הפלט הנוכחי של מקודד V1.

אימות מוצלח של סכום הביקורת או ניתוח מוצלח ברמה הנמוכה של `AccountAddress` אינם תחליף לבדיקה זו.

לא לקבל את הערכים הללו בשדה של חשבון קפדני- ID:

- כינוי חשבון כגון `alice@wonderland.universal`
- ליטרל I105 שבסופו נוספה סיומת `@domain`
- מפתח ציבורי `multihash` כגון `ed0120...`
- כמות המשאבים הפועלים הקנוניים כגון `0x02000120...`
- כתובת עבור מבחין שרשרת שגוי
- שרשרת עם אותיות גדולות או קטנות, רוחב אותיות, `kana`, מטען, או סכום בדיקה משתנים

לפתור כינויים בגבול היישום ולשמור את הקנוניק הוחזר I105 ID לאישור, חתימה, רשיונות ורשומות ביקורת .

## API, תקנות אחסון והצוגה {#api-storage-and-display-rules}

- שלחו את מחרוזת I105 UTF-8 המדויקת בשדות החשבון ב־JSON.
- לפני הצבת ID החשבון המלא במקטע נתיב של URL, בצעו לו `Percent-encode`.
- לעולם אל תשתמשו בכינוי חשבון במקום I105 ID.
- שמרו את המחרוזת הקנונית שה־codec מחזיר, עם סמנטיקת השוואה `byte-preserving`.
- השתמשו בקולציה המשמרת רישיות אותיות ורוחב תווים.
- שמרו את מבחין השרשרת או את פרופיל הרשת בעל השם יחד עם נתוני החשבון שיוצאו ועם הגיבויים.
- השתמשו מחדש בכתובת רק בהקשר הרשת שלה.
- הציגו את הכתובת המלאה וספקו פעולת העתקה.
- שמרו על כל אותיות `kana` בדיוק.
- שמרו את הכתובת המלאה זמינה כאשר מסך קומפקטי מקצר את מרכזו.
- השתמשו בקנוניקה המאוחסנת ID במקום לבנות אותה מחדש על ידי שם כינוי.

תצוגה של `AccountId` ושימוש של JSON קנוניקה I105.

תצוגה של רמה נמוכה יותר `AccountAddress` מציגה/JSON משתמשת ב- hex קנוני עבור מקשרים פנימיים ושל תיקון.

כאשר נדרש ID של חשבון חיצוני, הפעילו את מקודד I105 המפורש של `AccountAddress`.

עבור זרימת עבודה של יצירת חשבונות ופתרון שמהות, המשך עם [חשבות ושמהות ](/he/cookbook/accounts-and-aliases.md).

עבור מודל נתוני החשבון, ראה [החשבות ](/he/blockchain/accounts.md).
