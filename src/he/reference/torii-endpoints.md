# Torii נקודות סוף {#torii-endpoints}

Torii האם זה HTTP, SSE, ו WebSocket שער ל Iroha 3. זה משרת שניים מתבוננים בספר APIs ונקודות הסיום של המפעיל.

הכללים הנוכחיים של הפרוטוקול הם:

- פורמט בינארי קנוני הוא Norito
- הרבה נקודות קצה תומכות גם JSON כאשר אתה שולח `Accept: application/json`
- מדדים נחשפים בצורת Prometheus.

לפרטים על הפורמט, משא ומתן על תוכן, דגלי פריסה, גיבובי סכמה והנחיות Norito RPC, עיינו ב[הפניית Norito](/he/reference/norito.md).

## נקודות סוף משותפות {#common-endpoints}

|נקודת סוף.|פורמט |מטרה.|
| -------------------------------- | -------------- | ---------------------------------------------------------------- |
|`POST /v1/pipeline/transactions` |Norito |תגיש עסקה חתומה |
|`POST /v1/query` |Norito |תגיש בקשה חתומה |
|`GET /v1/events/ws` |WebSocket |לחתום על זרמי אירועים |
|`GET /v1/events/sse` |SSE |לחתום על זרמי אירועים מעל SSE |
|`GET /v1/blocks/stream` |WebSocket |זרם בלוקים commit |
|`GET /v1/peers` |JSON |רשימת צמתים שחשפו על ידי Torii |
|`GET /livez` |טקסט |חיות תהליך בלבד; זה לא מצביע על מוכנות פרוטוקול |
|`GET /readyz` |JSON |הכנות מלאה של קשרים, כולל בדיקות כספיות חיוביות מחוץ למערכת |
|`GET /health` |JSON |סופרת הכנות עם אותו אינפואריאנט מזומנים לא מקוונת |
|`GET /v1/api/version` |טקסט |גרסה הנוכחית של כותרת בלוק |
|`GET /status` |Norito או JSON |מצב דיאגנוסטי ברמה גבוהה; בקשת JSON מפורשת |
|`GET /metrics` |פרומטהיאוס |נקודת הסיום של Prometheus scrape.|
|`GET /v1/schema` |JSON |תמונת גיליון של מודל נתונים שמשרתת על ידי הערך כאשר היא פעילה. |
|`GET /openapi.json` |JSON |מסמך OpenAPI למסלולים פעילים Torii HTTP |
|`GET /v1/parameters` |JSON |תמונת מצב של פרמטרים הערך |
|`GET /v1/node/capabilities` |JSON |יכולת הערך ו- metadata של מודל הנתונים |
|`GET /v1/time/now` |JSON |תמונת מצב של שעון הקיר של Node|
|`GET /v1/time/status` |JSON |מצב סינכרון זמן |

עבור בקשה SSE, תפרסמו את הזרם המקומי בתוספת הפסקת הכתובת:

```http
Accept: text/event-stream, application/json
```

Torii המשא ומתן הראשון JSON או Norito ייצוג על שכבת הדרישה, ולאחר מכן מאשר את המקור `text/event-stream` תגובה. שולחת רק `text/event-stream` לפיכך הוא נדחף `406`; ה- [מתכון של אירועי הזרם](/he/cookbook/stream-events.md) משתמשת בראש שלם.

`/openapi.json` הוא החוזה שנוצר עבור מסלולים המוצגים בסקמה, ולא רשימה שלם של סנב מבצע. המסמך הנוכחי מפספס את `/livez` ו- `/readyz`, ותוארתו של `/health` עשויה לעמוד מאחור במפעיל הכנות. ליצור לקוחות מסלול מתוך המסמך חי, אך לאשר את החיות והכנות ישירות נגד הרכיב המפעיל ומעובדים מחוברים. פני השטח המדויק עדיין תלויים בתכונות הבנייה ובשינוי זמן הפעלה. השתמש בקונסולת [Torii API ](/he/reference/torii-api-console.md) כדי לטעון את המסמך החיה, לבחון את הדרכים של JSON , להעתיק את בקשות curl ולייצר קוד לקלינט מהשמעת הנוכחית.

כל פעולת OpenAPI שמגובה בקטלוג כוללת אובייקט `x-iroha-route-auth`. כלי MCP שמגובים בקטלוג חושפים את אותו חוזה בתור `_meta["iroha/routeAuth"]`. שתי ההטלות כוללות את `schemaVersion`, `stableRouteId`, `authentication` ו-`admission`. יש להתייחס לגרסה `1` כחוזה מדויק: דחו `schemaVersion` שאינו נתמך במקום לנחש כיצד לפרש את תוויות האימות או הקבלה שלו. מטא-נתוני הנתיב מתארים את גבול הבקשה; הם אינם מחליפים את האישורים שהגבול דורש.

## נסה לשרות Taira {#try-live-taira-routes}

רשת המבחן הציבורית Taira חושפת את אותה פני השטח Torii JSON שהלקוחות של יישומים משתמשים בהחקירה בקריאה בלבד. פקודות אלו לא דורשות מפתחות:

```bash
TAIRA_ROOT=https://taira.sora.org

curl -fsS -H 'Accept: application/json' "$TAIRA_ROOT/status" \
  | jq '{blocks, txs_approved, txs_rejected, queue_size, peers}'

curl -fsS "$TAIRA_ROOT/openapi.json" \
  | jq -r '.paths | keys[]' \
  | grep '^/v1/' \
  | head -n 20

curl -fsS -H 'Accept: application/json' \
  "$TAIRA_ROOT/v1/node/capabilities" \
  | jq '{abi_version, data_model_version, query: .query.aggregate.supported_resources}'
```

ניסיון מקור קורא נגד המצב העולמי הנוכחי:

```bash
curl -fsS "$TAIRA_ROOT/v1/domains?limit=5" \
  | jq -r '.items[].id'

curl -fsS "$TAIRA_ROOT/v1/assets/definitions?limit=5" \
  | jq -r '.items[] | [.id, .name, .total_quantity] | @tsv'
```

אם מסלול טסטנץ ציבורי חוזר `502`, מפסיק, או מדווח על זורה מלאה, לטפל בזה כבעיה של זמינות נקודת סוף ולנסות שוב מאוחר יותר לפני תיקון הקוד הלקוח שלך.

## אימות החשבונות, תצפיות וקרסורים של Explorer {#account-authentication-visibility-and-explorer-cursors}

### פרוטוקול בקשת חשבון אפליקציה {#app-account-request-protocol}

נתיבים הפונים לאפליקציות מקבלים אחת משלוש אפשרויות: ללא כותרות אימות, הוכחה ישירה אחת במפתח יחיד, או עד multisig אחד. כל כותרת אימות רשאית להופיע לכל היותר פעם אחת.

בשביל הוכחה ישירה, שלח את כל ארבעת הכותרות ביחד:

- `X-Iroha-Account`: ה-hex של כתובת החשבון הקנוניקה המדויקת `0x` או שם שמה של חשבון קנוניק פעיל ASCII. טקסט I105 אינו בטוח כערך שדה HTTP; השתמשו ב-hex האיות הקנוניקית עבור החשבון הזה .
- `X-Iroha-Signature`: המטען החשוב ביותר של בסיס 64 עם סימון.
- `X-Iroha-Timestamp-Ms`: חותמת זמן Unix דצימלית לא חתומה בקנוניקה במיליסעקונדים, במסגרת חלון ההפוך המוגדר.
- `X-Iroha-Nonce`: 1 עד 256 בייטים דפסים ASCII (`0x21` עד `0x7e`), ייחודיים בחלון ההשתלטות.

המפעיל בעל מפתח אחד רשום חותם על הבייטים הנכונים האלה:

```text
iroha.app.request.network.v1\0 || <genesis-derived network_id[32]> ||
<UPPERCASE_METHOD>\n
<exact request path>\n
<canonical query>\n
<lowercase hex SHA-256 of the raw body>\n
<canonical timestamp_ms>\n
<nonce>
```

בניית שאילתה קנונית מנתחת את השאילתה הגולמית כ־`application/x-www-form-urlencoded` (`+` פירושו רווח), מפענחת באחוזים את הזוגות, ממיינת אותם לפי `(key, value)` ומקודדת אותם שוב כטופס. הפרוטוקול מתיר לכל היותר 64 זוגות מפוענחים ו־64 KiB של טקסט שאילתה גולמי. חשבו hash לבתי הגוף בדיוק כפי שנשלחו. אל תוסיפו מפריד בין ה־network ID הקבוע בן 32 הבתים לבין השיטה באותיות רישיות.

בדיקת V1 מגבילת גם את סימן השיטה ב-32 בייטים, מסלול הדרישה הקודד בממוצע ב-64 KiB, ואת זהות החשבון ישירה ב-36 KiB לפני ניתוח. לכיסויים של חשבונות יש גבול מבנה חזק יותר של שלושה סגמנטים שמות ועוד הפרדים שלהם. מעבר לקשור נכשל אימות לפני אימת חתימה או מיזוג בגודל מקור.

בקר multisig חייב לשלוח במקום זאת את `X-Iroha-Witness` כ-Norito קנוני strict padded-base64, ולהשמיט את `X-Iroha-Signature`, `X-Iroha-Timestamp-Ms` ו-`X-Iroha-Nonce`. בצורה זו `X-Iroha-Account` אופציונלי; כאשר הוא קיים, עליו להיות שווה ל-`subject_account` של העד. `CanonicalRequestWitnessV1` מכיל `schema_version`, `subject_account`, `timestamp_ms`, `nonce`, `Hash` של Iroha לבתי הבקשה של הרשת המדויקת עד body digest אך ללא שדות freshness, ולכל היותר 64 חתימות חברים. כל חבר חותם על קידוד Norito הקנוני של אותו payload ללא מערך החתימות. החברים שאומתו חייבים לעמוד במדיניות ה-multisig הנוכחית של החשבון. גודל העד המקודד מוגבל ל-1 MiB.

אספקת ראשי אימות לא מבחרים גישה אנונימית. אספקת כל הוכחה חלקית, מעורבת, חוזרת, פגומה, מזדיינת או מופיעה מחדש נכשלת באותנטיקה; היא אף פעם לא נופלת חזרה לדיטור אנונימי.

### פרוטוקול בקשת המפעיל {#operator-request-protocol}

מסלולים המוצגים כאותנטיים על ידי מפעיל דורשים את כל ארבעת הכותרות החדשות:

- `x-iroha-operator-public-key`: המפתח הציבורי הקנוני של Iroha בפורמט multihash.
- `x-iroha-operator-timestamp-ms`: חותמת זמן יוניקס דצימלית לא חתומה בקנוניקה במיליסעקונדים.
- `x-iroha-operator-nonce`: 1 עד 256 בייטים מודפסים ASCII, ייחודיים עבור המפתח הזה בחלון ההשתתפות.
- `x-iroha-operator-signature`: המטען החשוב ביותר של בסיס 64 עם סימון.

ערכי הכותרות אינם יכולים להכיל רווח לבן מסביב. מפתח המפעיל חותם על:

```text
iroha.operator.http-request.network.v1\0 || <genesis-derived network_id[32]> ||
<UPPERCASE_METHOD>\n
<exact request path>\n
<canonical query>\n
<lowercase hex SHA-256 of the raw body>\n
<canonical timestamp_ms>\n
<nonce>
```

חוקי הנתיב, השאילתה, הגוף, סימן הזמן ו-nonce הם אותם הכללים הקנוניים המשמשים על ידי פרוטוקול האפליקציה. המפתח חייב להיות גם רשום על ידי `[torii.operator_signatures]`: לרשום אותו ב `allowed_public_keys`, או להפעיל באופן מפורש `allow_node_key` בעת שימוש במפתח הערך. כאשר מטמון ההפעלה החוזרת מתמלא, המערכת נכשלת באופן סגור עם `503 Service Unavailable`.

חתימת הבקשה המדויקת תמיד חובה. כאשר `[torii.operator_auth].enabled = true`, כל נתיב מפעיל רגיל דורש גם `x-iroha-operator-session` תקף; כאשר `require_mtls = true`, הוא דורש בנוסף `x-forwarded-client-cert` מ-ingress מהימן. אף אחד מהגורמים אינו מחליף את חתימת הבקשה.

WebAuthn ההרשמה והגישה משתמשים בארבע נקודות הסיום JSON:

|שיטה ונקודת סוף |מטרה.|
| --------------------------------------------- | ---------------------------------------- |
|`POST /v1/operator/auth/registration/options` |התחילו WebAuthn רישום תעודות ראיות |
|`POST /v1/operator/auth/registration/verify` |לאבד ולשמר את האישור |
|`POST /v1/operator/auth/login/options` |תתחיל אימות WebAuthn |
|`POST /v1/operator/auth/login/verify` |תבדקו את ההצהרה ותעשיו פגישה |

הקונפיגור `torii.operator_auth.tokens` עם ערכי בוטסטראפ מוקדמים. לפני שיש אישור, לשלוח אחד כמו `x-iroha-operator-token` כדי להתחיל את ההרשמה הראשונה. סימן זה אף פעם לא מאשר מסלול מפעיל רגיל, והערכים של האוזן `x-api-token` לעולם לא משמשים מחדש עבור זרימת זו. ברגע שיש אישור, ההרשמה של אישור אחר דורשת פגישה מאושרת. לאמת הכניסה חוזרת את סימן הפגישה כדי לשלוח לצד כל חתימה חדשה בקשה של מפעיל רשת מדויקת. אישור נותר תחת `<torii.data_dir>/operator_auth/operator_webauthn.json`.

מסלולים ISO 20022 מבצעים שני בדיקות עצמאיות. בקשה חייבת קודם לעבור את פרוטוקול הזכות של המפעיל והחתום הזה; מעבד ISO לאחר מכן דורש את אותו מפתח כדי לכבוש את תפקיד המשתתף המדויק או הבדיקה המתוארים בהמשך.

### תצפיות ספרים וקרסורים של Explorer {#ledger-visibility-and-explorer-cursors}

קריאות ledger הפונות לאפליקציה משתמשות בגבול חשבון האפליקציה האופציונלי שלעיל. בקשה לא חתומה מקבלת רק dataspaces שהוגדרו כציבוריים. בקשה חתומה תקפה מוסיפה dataspaces שקשורים ל-UAID הנוכחי של הקורא, כל dataspace מוגבל שנקוב בהרשאת `CanReadRestrictedDataspace { dataspace }` מדויקת, או את כל הנתיבים כאשר לחשבון יש `CanReadAllLedgerData`.

השתמשו בנתיב שמתאים לרשות המתקשר:

|שיטה ונקודת סוף |האותנטיקה והראות |
| ------------------------------------- | --------------------------------------------------------------- |
|`POST /v1/transactions/visible/query` |חתימת חשבון קאנוניקה; מתיישבת תצפית המתקשר |
|`POST /v1/transactions/query` |מבקשת חתימה של מפעיל; מאפשרת את התצוגה העולמית של מפעילה |
|`GET /v1/triggers/completed` |כתיבת בקשה של המפעיל; קורא רשומות סיום מקומיות של הערכיים |

האובייקטים הבולטים של חשיבות זהה הם חשבון, דומיין, הגדרת נכס, נכס, NFT, RWA, מחזיק ו-Explorer. אובייקט נעלם ואובייקט שהוא מחוץ למסלולים הראויים של המתקשר אינם ניתן להבחין במכוון. היסטוריית העסקאות וההנחיות הוצגו רק כאשר כל מקטע הנתיב שנקלט עבור העסקה נראית. העסקה עם מרחבי נתונים מעורבים היא לכן מוסתר כאשר אפילו מקטע אחת של המשתתף נמצאת מחוץ לתפקידו של המתקשר; מקשר הנתיב חסר, ישן או פגום נראה רק לקורא גלובלי.

שישה אוסף Explorer תומכים בעולם משתמשים בקורסורים קנוניים לא ברורים בסיס 64url. הגבול המקובל של דף הוא 25, מקסימום הוא 100, ודף אחד בודק לכל הפחות 512 מפתחות מועמדות. כל קורסר מחובר לאוסף, פילטרים, מפתח קנוני אחרון, ודיגסט המסלול הנראה של המתקשר, כך שהוא לא יכול להופיע שוב בשאילתה אחרת או לאחר שינויים בהראות של המתקשר.

בלוק, עסקאות, טרנזקציות אחרונות, הוראות וארכי ההיסטוריה של ההוראות האחרונים גם מצביעים את גובה הצילום המובטח ואת האש של הבלוק. תגובות חושפות `pagination.limit`, `pagination.snapshot_height`, `pagination.snapshot_hash`, `pagination.next_cursor`, ו `pagination.has_more`. קורסר עבור מסלול אחר או קבוצה של פילטר, צירוף זיהוי שונה, או תמונת מצב שנרגע שהנקודה כבר לא יכולה לאשר נכשלת נסגרת. סריקה ההיסטוריה נשארת בתוך רשות הכניסה לשאילתה של Torii בזמן שעובד חסימה פועל.

זרמי Explorer WebSocket פולטים תקצירים מסוננים ומחשבים מחדש את הנראות כאשר ההרשאות בספר החשבונות משתנות. הנתיב native `GET /v1/blocks/stream` שונה: הוא פולט בלוקים חתומים מלאים, דורש `CanReadAllLedgerData` במהלך ה־handshake ונסגר אם הרשאה זו מבוטלת לאחר מכן. אל תשתמשו בזרם native עבור explorer שמוגבל לפי dataspace.

## ISO גשר 20022 {#iso-20022-bridge}

Torii חושף את גשר ISO 20022 תחת `/v1/iso20022/*` כאשר ה־app API וסביבת הריצה של הגשר מופעלים. אין זה שער סליקה כללי של ISO 20022, אלא תת־קבוצה נתמכת הממפה הודעות תשלום נבחרות לעסקאות Iroha חתומות ועוקבת אחר מצבן בספר החשבונות.

להגדיר מקומי קבוע `torii.iso_bridge.store_dir` לפני הכניסה לכל הפרישה. שדה ההגדרות הוא אופציונלי רק כך הערך יכול להתחיל לשימוש בקריאה בלבד או באבחון: כל הודעה מאושרת ISO דורשת את התיקון, ומחזירה חוזרת `503 Service Unavailable` כאשר העמידות אינה קיימת או כתיבת סמן למניעת שידור חוזר או רשום עשיר נכשלת.

### Torii ISO 20022 נקודות סוף {#torii-iso-20022-endpoints}

|שיטה ונקודת סוף |מטרה.|
| -------------------------------------------- | -------------------------------------------------------------------------------------------------- |
|`POST /v1/iso20022/pacs008` |להגיש העברת אשראי FI ל FI לקוח ולבנות את העברה של נכסים Iroha המתאימה |
|`POST /v1/iso20022/pacs009` |להגיש העברת אשראי FI ל FI ששימשו עבור PvP או למימון במזומן הקשור לכספים |
|`POST /v1/iso20022/pacs002` |להגיש דו"ח מצב התשלומים בבעלות הצדדים האחרים; הצורך בהסדר הסדר ראיות למערכה commit |
|`POST /v1/iso20022/pacs004` |להגיש הצהרת תשלום בבעלות הצד השני |
|`POST /v1/iso20022/camt056` |להגיש בקשה לבטל תשלום בבעלות המקור |
|`POST /v1/iso20022/sese023` |להגיש הוראה לפיצוי ניירות ערך |
|`POST /v1/iso20022/sese024` |תשלח הודעה על מצב הסדר של ניירות ערך בבעלות הצד השני |
|`POST /v1/iso20022/sese025` |להגיש אישור על הסדר של ניירות ערך בבעלות הצד השני |
|`POST /v1/iso20022/colr012` |תשלח הודעה על תחליף ביטוח |
|`GET /v1/iso20022/messages/{msg_id}` |תקרא את תיעוד הגשר הקנוני עבור מסר אחד.|
|`GET /v1/iso20022/audit/messages` |תקרא את מסר הניתוח של הודעות המסתיימות.|
|`GET /v1/iso20022/messages/{msg_id}/pacs002` |להציג את מצב התשלום הנוכחי כ- `pacs.002` XML |
|`GET /v1/iso20022/messages/{msg_id}/pacs004` |להציג את הצהרת התשלום הנוכחית כ `pacs.004` XML |
|`GET /v1/iso20022/messages/{msg_id}/camt029` |להציג את החלטת ביטול הנוכחית כ- `camt.029` XML |
|`GET /v1/iso20022/messages/{msg_id}/sese024` |להשיב את מצב הסדר הנוכחי כ `sese.024` XML |
|`GET /v1/iso20022/messages/{msg_id}/sese025` |להציג את אישור הסדר הנוכחי כ- `sese.025` XML |

בהגשות `pacs.008` יש לספק את ID ההודעה, סכום ומטבע הסליקה הבין־בנקאית, תאריך הסליקה, ה־IBANs של החייב והנושה, וכן את ה־BICs של החייב והנושה. כאשר מוגדרים נתוני ייחוס, הגשר בודק גם את התאמות BIC, IBAN ומטבעות ISO 4217 לפני שהעסקה שנוצרה נכנסת לשרשרת העיבוד העיבוד.

הגשות `pacs.009` חייבות לספק את ה־business message ID, ה־message definition ID, זמן היצירה, סכום הסליקה הבין-בנקאית, המטבע, תאריך הסליקה, ה-BICs של הסוכן המורה והסוכן המקבל הוראה, ואת ה-IBANs של החייב והנושה. אם ההודעה כוללת `Purp`, הגשר מקבל כעת מימון למטרת ניירות ערך בלבד: `Purp=SECU`.

נקודות הקצה להגשת `pacs.008` ו־`pacs.009` מקבלות מעטפות XML ISO או את פורמט השדות השטוח שמשמש בבדיקות הגשר. שדות `SplmtryData` אופציונליים יכולים להצמיד את ספר החשבונות היעד של Iroha, את IDs או הכתובות של חשבון המקור והיעד ואת ID של הגדרת הנכס. התשובה היא `202 Accepted` עם `message_id`, `transaction_hash`, `status`, `pacs002_code` והקשר ספר־חשבונות/חשבון/נכס שנפתר.

### הסמכות של המשתתפים וניהול מעגל חיים {#participant-authorization-and-lifecycle-ownership}

לכל גשר מופעל יש קטלוג משתתפים. לכל רשומת משתתף יש מזהה משתתף ייחודי (participant ID), מפתח ציבורי אחד או יותר של מפעיל, מזהה פיננסי אחד או יותר, קבוצת פרופילים מותרים, ותפקיד `originator`, `counterparty` או שניהם. מפתחות מפעיל ומזהים פיננסיים אינם יכולים להשתייך ליותר ממשתתף אחד. הגדירו את `audit_admin_keys` בנפרד; מפתח audit-admin אינו יכול להיות גם מפתח לשינוי משתתף.

כל נתיבי ISO דורשים חתימת מפעיל חדשה. בהגשה ראשונית של `pacs.008`, `pacs.009`, `sese.023` או `colr.012`, המפעיל המאומת חייב להשתייך למשתתף שמזוהה באמצעות הזהות הפיננסית `From` שבכותרת היישום. הזהות `To` חייבת להיפתר למשתתף מוגדר בעל התפקיד `counterparty`, והפרופיל שנבחר חייב להיות מותר לשני הצדדים. רשומת הקבלה הקבועה מתעדת את ה-originator, ה-counterparty, המשתתף שקיבל את הבקשה ומפתח המפעיל, וכן את הפרופיל המקורי ואת מדיניות החתימה המוטמעת.

אישור מחזור חיים נובע מהרשימה הבלתי משתנה זו ולא מהערכים שנבחרו על ידי המתקשר:

|מסר מחזור החיים |משתתף נדרש |
| ---------------------------------------------- | -------------------------------------------------- |
|`pacs.002`, `pacs.004`, `sese.024`, `sese.025` |הצד השני המקורי עם תפקיד `counterparty` |
|`camt.056` |מקורית עם תפקיד `originator` |

מדיניות הפרופיל והחתום המקורי נשארות מחוברות לאורך כל מחזור החיים, כך שהתקשר לא יכול לבחור פרופיל חלש יותר לעדכון. קוד `pacs.002` הוא מייצג הסדר (`ACSC`, `ACCP`, `SETT` או `SETTLED`) משנה את הרשומה המקורית לסדר רק כאשר Torii מחייב ראיות על עסקאות.

כל צד מקורי יכול לקרוא את רישום ההודעות שלו ואת המסמכים המוצאים בקופסא הפתיחה. נקודת הסיום של הניתוח חוזרת רק על רשומות שבהן המשתתף האותנטי הוא מקורם או הצד השני. מנהל ביקורת מותאם בנפרד מקבל תצוגה ביקורת גלובלית רק קריאה ואינו יכול לשלוח או לשנות הודעות. משתתפים לא ידועים וזהים של הודעות שאינם קשורים אינם מוסברים.

### תעודת זהות משחזור יציבה ומסמכים חתומים של תיבת הפוסט {#durable-replay-identity-and-signed-outbox-documents}

סמן למניעת שידור חוזר שיחקו מחדש היא הגבול הקפדני של הכניסה. Torii מבטל את ההתחלה עבור סמן למניעת שידור חוזר שאינה ניתן לקרוא, גדולה מדי, מוטעה, שנקראת לא נכונה, מתנגדת או לא תואמת באופן מפורש. הוא גם מבטל עבור רשום עשיר עם גרסה של סכימה שאינה מתאימה באופן מפורש, משתתף, פרופיל או מדיניות חתימה נעלמת מהקונפיגורציה הנוכחית, או סמן למניעת שידור חוזר חי חסרה או לא הוגנת.

נזקים אחרים של רישומים עשירים מתמודדים באופן שונה: קבצים לא קריאים או גדולים מדי, תקליטים בלתי חוקיים JSON, תקליטים לא חוקיים של סכימות קרנט, שמות קבצים שאינם קנוניים, וזהויות שידור חוזר מנוגדות נרשמים או נמלטו. אינדיקס בדיקת הגרסה הנוכחית שאינו ניתן לקרוא או לא חוקי מתחדש מהרישומים שנשמרו; רק גרסה של אינדיקס הבדיקת שאינה תואמת במפורש מפסיקה את ההתחלה. תדאגי ללוגים של ההתחלה ותתאימו את מוניפסט הניתוח המחדל במקום להניח שכל קבוצה מושחתת עם רישום עשיר מונעת את העמוד מהעבודה.

כל רשומה עשירה שנשמרת שומרת את מקורות המשתתפים בלתי משתנים. סמן למניעת שידור חוזרה יציבה נפרדת שומרת את ההודעה ID, האש של מטען הנתונים, הודעת העסק ID, ו UETR לדידופליקציה מלאה TTL גם לאחר פרטי הרשומות עשירים ניתקו.

Torii ממשיכה לקבלת שיחזור לפני שהוא חותם או מעבד מסר מחזור חיים. זה אף פעם לא גורש זהות שיחזור לא נגמרה. אם הכוח המוגדר כביכול מעובד על ידי רשומות מוגנות או זהויות משקפות לא נגמרות, הודעות מקבלות `503 Service Unavailable` חוזרת ללא שינוי מחזור חיים או מצב חשבונאי.

כל יצור `pacs.002`, `pacs.004`, `camt.029`, `sese.024`, או `sese.025` המסמך חוזר כ `application/xml` עם כותרות תגובה אלה:

|כותרת |משמעות |
| ------------------------------ | ----------------------------------------------------- |
|`X-Iroha-Iso-Signature-Domain` |תמיד `iroha.iso20022.outbound.v2`|
|`X-Iroha-Iso-Signer` |מפתח ציבורי קאנוני עבור חותמת הגשר המוגדרת |
|`X-Iroha-Iso-Signature` |חתימה Base64 על XML בייטים נפרדים על ידי תחום |

אמתו את החתימה על רצף הבתים UTF-8 ‏`iroha.iso20022.outbound.v2`, אחריו בית אפס יחיד וגוף התגובה המדויק. אל תשנו את העיצוב ואל תנרמלו את ה־XML לפני האימות.

### תמיכה נוספת בניתוחים ומפונים {#additional-parser-and-mapping-support}

העוזר IVM ISO גם מאשר ומטייליז את משפחות ההודעות הבאות עבור אישור המעטפה, מאפיית ההתיישבות או התאמה במורד זרם. אין להם דרכים עצמאיות Torii:

|המשפחה של הודעות |תמיכה זמנית |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
|`head.001` |אישור כותרת היישום העסקי למעטפות ISO, כולל שדות `BizMsgIdr`, `MsgDefIdr`, זמן יצירה, ושלח/קבל בחופשי BIC |
|`pacs.007`, `pacs.028`, `pacs.029` |הפחתת תשלומים, בקשה לסטטוס ופתרון החקירה/נתח מצב |
|`pain.001`, `pain.002` |תחילת התשלום של הלקוח והעמידה של דו"ח מצב התשלום |
|`camt.052`, `camt.053`, `camt.054` |דו"ח חשבונות, הצהרה וחיסכון של הודעות |

## Kaigi הפגישות {#kaigi-sessions}

Kaigi מספקת חדרי אודיו/וידאו בזמן אמת ובתשלום על גבי SORA Nexus. השתמשו בה כאשר יישום זקוק ליצירת פגישה מגובה בספר החשבונות, שינויי רשימה, מניפסטים של חדרים, איתות מוצפן ומדידת שימוש, במקום לשמור את כל מצב החיוב מחוץ לשרשרת.

מחזור החיים המסתובב על הספר הוא:

- `CreateKaigi`: ליצור שיחה תחת דומיין ולשמר את מדיניותו, לוח הזמנים, מטא-מנתונים ומניסט ההחזקת בחופשי.
- `JoinKaigi`: מעדכן את רשימת ההזמנות. במצב `zk-roster-v1`, תצוגת ההזמנה הציבורית חושפת מחויבות ומספרים של ביטול במקום חשבון המשתתף IDs.
- `LeaveKaigi`: מסיר משתתף משיחה שקופה. יציאה במצב פרטי מתבצעת מחוץ לשרשרת בפרוטוקול של הגרסה הראשונה.
- `RecordKaigiUsage`: הוסף את משך הזמן הממוצע ואת סכום הגז.
- `EndKaigi`: סגור את הפגישה ולהקליט את סימן הזמן הסופי.

Torii חושף את הקריאות הבאות הפנות לאפליקציה:

|דרך.|אימות |מטרה.|
| ----------------------------------- | --------------------------------------- | ------------------------------------------ |
|`/v1/kaigi/calls/{call_id}` |ציבורי|רישום שיחות זמנית |
|`/v1/kaigi/calls/{call_id}/signals` |בקשת חשבון רשת מדויקת קנונית |מטא-נתונים של סיגנל commit.|
|`/v1/kaigi/calls/{call_id}/events` |בקשת חשבון רשת מדויקת קנונית |קראו לזרם מחזור החיים |
|`/v1/kaigi/relays` |בקשה של מפעיל רשום לרשימה |סיכום רלוף |
|`/v1/kaigi/relays/{relay_id}` |בקשה של מפעיל רשום לרשימה |רישום ופרטים רפואיים של מרחב אחד |
|`/v1/kaigi/relays/health` |בקשה של מפעיל רשום לרשימה |בריאות המשמרת המצטברת |
|`/v1/kaigi/relays/events` |בקשת חשבון רשת מדויקת קנונית |זרימת אירועים בריאותיים |

יש להפעיל את API האפליקציה. נתיבי סיכום ובריאות של relay הם משטחי מפעיל אף שהם לקריאה בלבד; בקשת `curl` לא חתומה אינה בדיקת זמינות תקפה. מצב ההפעלה משתקף גם באירועי דומיין של Kaigi, כגון `KaigiRosterSummary`, `KaigiRelayManifestUpdated`, `KaigiRelayHealthUpdated` ו-`KaigiUsageSummary`.

### CLI בדיקת עשן {#cli-smoke-test}

התחל עם `iroha app kaigi` CLI כאשר אתה רוצה לוודא כי נקודת קצה Torii מקבלת עסקאות Kaigi לפני חיבור UI. פקודה ההתחלה המהירה יוצרת חדר נגד נקודת הקצה המוגדרת ומדפסת את מזהה השיחה שלה ולהצטרף למעטא נתונים:

```bash
iroha app kaigi quickstart \
  --domain kaigi.universal \
  --summary-out kaigi-summary.json
```

בתהליכים מתוסרטים, נהלו במפורש את מחזור החיים של החדר:

```bash
iroha app kaigi create \
  --domain kaigi.universal \
  --call-name daily \
  --host <i105-account-id> \
  --privacy-mode transparent \
  --room-policy authenticated

iroha app kaigi join \
  --domain kaigi.universal \
  --call-name daily \
  --participant <i105-account-id>

iroha app kaigi leave \
  --domain kaigi.universal \
  --call-name daily \
  --participant <i105-account-id>

iroha app kaigi record-usage \
  --domain kaigi.universal \
  --call-name daily \
  --duration-ms 120000 \
  --billed-gas 1500

iroha app kaigi end --domain kaigi.universal --call-name daily
```

השתמש `--room-policy public` לחדרים שבהם משקיפים עשויים לחשוף ללא כרטיסי תצפית, או `--room-policy authenticated` כאשר היציאות צריכות לאותנטיזציה של התצפית. השתמשו `--privacy-mode zk-roster-v1` רק לאחר ברשת יש את Kaigi רשימה ושימוש בדיקת מפתחות מוגדרים; אחרת חיבורים, עמודים, ורשומות השימוש הפרטיים נכשלים במהלך הבדיקת דטרמיסטית.

### JavaScript שילוב {#javascript-integration}

הדמו הנוכחית [Iroha JavaScript ](https://github.com/soramitsu/iroha-demo-javascript) מיישמת פרופיל פגישה אחד לאחד שקוף, מאושר. היא אינה חושפת את זרימת ההוכחה של הפרוטוקול `zk-roster-v1`. המוצג שלו יוצר הצעות ותשובות WebRTC, בעוד גשר מובטח משתמש בנקודת הקבלה המקומית [ `@iroha/iroha-js` ](https://github.com/hyperledger-iroha/iroha/tree/0010c5a70039eac101a4846499ba9ceaf43eb65c/javascript/iroha_js) כדי לציין, לחתום, להגיש ולחכות למבצעים סופיים Kaigi.

ראו [Embed Kaigi באפליקציה JavaScript App](/he/guide/tutorials/kaigi.md) עבור האותנטיקה המדויקת של הנתיב, פורמט ההזמנה, גבול הגשר ופקודות הבדיקה הדמו הנוכחית.

## מצב ומטריקים {#status-and-metrics}

נקודות הסיום של הסטטוס והמטריקות הן הדברים הראשונים שנחברו לדהשבארדים:

- `/status` חושף את שדות הצמתים, הבלוקים, הקווים וההסכמה ברמה העליונה.
- `/metrics` חושף ספרי Prometheus, מדדים והיסטוגרמים.

בנקודות Nexus המאפשרות, יצירת מצב כוללת גם חלקי קו ומרחב נתונים מודעים. כאשר `nexus.enabled = false`, החלקים האלה נמנעים.

## JSON לעומת Norito {#json-vs-norito}

מספר נקודות הסיום של המפעיל חוזרות Norito באופן מקובל. כאשר נקודת הסיום תומכת JSON, לשלוח את:

```http
Accept: application/json
```

זה מועיל במיוחד עבור:

- `/v1/sumeragi/status`
- `/v1/sumeragi/qc`

כאשר נקודת סוף מקבלת או חוזרת בטופס Norito ישירות, השתמשו ב- `application/x-norito` כטיפוס התוכן או ערך מועדף `Accept`. ראה את פרטי התחבורה של [Norito ](/he/reference/norito.md#torii-and-norito-rpc).

## פרופיל טלמטריה {#telemetry-profiles}

נראה של נקודת הסיום תלוי בהגדרת `telemetry.profile` של הערך. הקונפיגורציה הנוכחית חושפת חמישה רמות פרופיל:

|פרופיל |`/status` |`/metrics` |מסלול פיתוח |
| ----------- | --------- | ---------- | ---------------- |
|`disabled` |לא.|לא.|לא.|
|`operator` |כן.|לא.|לא.|
|`extended` |כן.|כן.|לא.|
|`developer` |כן.|לא.|כן.|
|`full` |כן.|כן.|כן.|
