# Запуск Iroha 3 {#launch-iroha-3}

Запустите четыре валидатора Iroha 3 на одной виртуальной машине (VM) Linux для проверки интеграции в закрытой среде. Вы отправите подписанную транзакцию, остановите один валидатор и убедитесь, что остальные три подтверждают следующую транзакцию. В результате будет создан автономный реестр с ограниченным доступом. Для подключения его к SORA Nexus в качестве управляемого пространства данных требуется отдельная настройка.

## Подготовка VM {#prepare-the-vm}

Используйте Linux x86_64 с Docker Engine, Buildx, Compose v2, Python 3.8 или новее и утилитой `unzip`. Вашей учётной записи нужен доступ к Docker. При первой сборке потребуются исходящие HTTPS-соединения с GitHub, Docker Hub, зеркалами пакетов Debian и crates.io.

Мы собрали и проверили комплект на VM с шестью vCPU и 32 GiB RAM оперативной памяти, выполнив несколько тестовых транзакций. Подберите объём хранилища под вашу нагрузку и срок хранения данных. Используйте одну копию комплекта на экземпляр Docker Engine и оставьте свободными порты 18080–18083 на интерфейсе обратной петли.

[Скачайте комплект для четырёх валидаторов](/downloads/iroha-trade-poc.zip). В него входят сценарий запуска, список зависимостей с фиксированными версиями и исправления для сборки валидатора и клиента из одной и той же ревизии Iroha. В каталоге загрузки проверьте контрольную сумму архива и распакуйте его.

```sh
echo 'b12d450f9f15c0126dfe5eca83cdfad8bc420c779a78f916d374f433a2b3da0e  iroha-trade-poc.zip' | sha256sum --check
unzip iroha-trade-poc.zip
cd iroha-trade-poc
```

## Запуск и проверка всех четырёх валидаторов {#start-and-verify-all-four-validators}

```sh
python3 poc.py up
python3 poc.py verify
```

При первом запуске собирается образ, а на VM создаются идентификатор сети, ключи и подписанный начальный блок. Каждый валидатор использует собственный постоянный том. Сценарий проверки подписывает тестовую транзакцию и ждёт, пока все четыре валидатора сообщат о трёх подключённых узлах и одинаковом хеше нового блока. Начальный блок включает демонстрационные учётные записи. Используйте тестовые данные и ограничьте доступ к APIs интерфейсом обратной петли.

Чтобы получить состояние первого валидатора с VM, явно запросите ответ в формате JSON.

```sh
curl -fsS -H 'Accept: application/json' http://127.0.0.1:18080/status
```

## Проверка отказа одного валидатора {#test-a-validator-failure}

```sh
python3 poc.py failover
```

Сценарий останавливает один валидатор, отправляет новую транзакцию и проверяет хеш подтверждённого блока на трёх оставшихся валидаторах. Затем он перезапускает четвёртый и ждёт, пока тот получит тот же блок. При отказе VM остановятся все четыре валидатора. Для проверки отказа одного физического хоста разместите по одному валидатору на каждом из четырёх независимых хостов.

## Остановка и возобновление работы {#stop-and-resume}

```sh
python3 poc.py down
python3 poc.py up
```

Выполняйте обе команды из одного и того же каталога, в который распакован комплект. Сохраняйте каталог `state/` и все четыре тома Docker вместе, чтобы после перезапуска валидаторы могли открыть прежний реестр. Если запуск зависнет, выполните `python3 poc.py logs` в том же каталоге.

## Проверка публичного API {#try-the-public-endpoint}

Приложение может читать данные из универсального пространства данных SORA Nexus в сети Taira без собственной VM для реестра. С рабочей станции, где установлены `curl` и `jq`, отправьте следующий запрос на чтение к тестовой сети.

```sh
curl -fsS -H 'Accept: application/json' https://taira.sora.org/status \
  | jq '{peers, blocks, txs_approved, queue_size}'
```

В ответе указано, сколько узлов подключено к опрошенному узлу, сколько блоков подтверждено, сколько транзакций одобрено и сколько ожидает в очереди. Для планирования развёртывания см. раздел [Развёртывание сети](/ru/guide/best-practices/network-deployment.md).
