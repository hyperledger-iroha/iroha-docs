# Спонсирование комиссий приватного пространства данных {#sponsor-fees-for-a-private-data-space}

Программа спонсирования комиссий SORA Nexus может оплачивать комиссии глобального исполнения для подходящих транзакций, направленных в приватное пространство данных. Пользователь по-прежнему подписывает всю транзакцию. Её типизированное поле `FeePaymentIntent` выбирает точную программу спонсирования и неизменяемую ревизию, ограничение газа там, где оно требуется, и максимальные списания.

Запись в каталоге пространств данных не создаёт независимо подписываемый корень. Независимый корень пространства данных имеет собственные зафиксированные комиссионную валюту и политику; публичные спонсорские хранилища не могут разрешать оплату комиссий этого приватного корня. Определите корень исполнения перед проектированием спонсирования.

## 1. Определите зафиксированную комиссионную политику {#_1-establish-the-committed-fee-policy}

Подписанный генезис задаёт один пользовательский параметр `root_fees_v1`, содержащий `RootFeePolicy`. Он связывает комиссионную валюту, получателя комиссий, счёт хранения спонсорских средств, освобождения для запросов и ставки. Каждый обычный блок и расчёт комиссии используют зафиксированную политику, захваченную для них. Разрешённые обновления политики применяются со следующего блока.

При глобальном исполнении встроенная комиссия сжигает точную валюту XOR подписанной сети. Эту валюту предоставляет хранилище программы спонсора. Настройки узла и метаданные транзакции не выбирают плательщика и не активируют спонсирование.

Используйте канонические идентификаторы валюты и учётных записей сети. Разрешение псевдонимов не должно перенаправлять зафиксированные идентификаторы валюты, хранения или получателя комиссий.

## 2. Создайте и пополните программу спонсирования {#_2-create-and-fund-a-sponsor-program}

Идентификатор программы имеет форму `<canonical-sponsor-account>/<program-name>`. Создайте её через типизированные инструкции текущего SDK и модели данных:

| Инструкция | Назначение |
| --- | --- |
| `CreateFeeSponsorProgram` | Создать подготовленную программу с обязательным счётом выплат. |
| `StageFeeSponsorProgramRevision` | Определить одну неизменяемую политику допуска, операций и бюджета. |
| `EnrollFeeSponsorBeneficiary` | Записать подходящего получателя в блокчейн. |
| `FundFeeSponsorProgram` | Перевести активы на хранение и зачислить их в точное хранилище программы. |
| `ActivateFeeSponsorProgramRevision` | Назначить самую раннюю высоту активации подготовленной ревизии. |

Администрирование программы разрешает спонсор или конкретный делегированный управляющий. Вывод средств требует полномочий самого спонсора и возвращает средства только на записанный счёт выплат программы, пока программа приостановлена или закрывается.

Каждая ревизия задаёт:

- явное включение получателей либо включение вместе с разрешённым допуском по умолчанию для маршрута;
- разрешающие и запрещающие правила для точных идентификаторов встроенных инструкций в wire-формате либо адресов контрактов, хешей кода и точек входа;
- лимиты по каждому активу на транзакцию, блок, эпоху программы и эпоху получателя;
- минимальный резерв и детерминированную длину эпохи.

Запрещающее правило имеет приоритет над разрешающим. Поле `fee_sponsor_program_id` пространства данных даёт допуск по умолчанию для маршрута, только если активная ревизия это разрешает; транзакция всё равно должна указывать точные программу и ревизию. Активация может быть отложена до истечения непогашенных резервирований предыдущей ревизии.

Активы спонсорского хранилища должны использовать политику баланса `Global`. Пополнение только обычной учётной записи спонсора не пополняет изолированное хранилище программы, и одна программа не может расходовать баланс другой.

## 3. Получите расчёт комиссии, подпишите и отправьте точную транзакцию {#_3-quote-sign-and-submit-the-exact-transaction}

Интеграция через SDK выполняет следующие шаги:

1. Сформируйте неподписанный `TransactionPayload` с субъектом полномочий, исполняемым содержимым, временными метками, nonce, метаданными, точной ревизией программы спонсирования и необходимым лимитом газа. Максимальные списания первоначально могут быть пустыми.
2. Подпишите запрос `POST /v1/fees/quote` с `{"payload": <payload>}` ключом учётной записи. Подписант запроса должен быть субъектом полномочий транзакции.
3. Проверьте наблюдаемую высоту, разрешённый маршрут пространства данных, компоненты комиссии, источник списания и доступную ёмкость спонсора. Убедитесь, что ответ сохраняет выбранные плательщика, ревизию и ограничение газа.
4. Замените только `payload.fee_payment` рекомендованным намерением, затем подпишите и отправьте именно эту полезную нагрузку.
5. Отслеживайте транзакцию до финальности `Applied`, определённой состоянием, и сохраните квитанцию, включая фактические программу спонсирования, ревизию и списание.

Расчёт комиссии наблюдает состояние реестра и не резервирует ёмкость. При допуске в очередь право на спонсирование проверяется повторно и резервируются подписанные максимумы. Отказ спонсора отклоняет транзакцию без перехода к списанию с пользователя.

CLI явно указывает тот же источник комиссии. Например, после того как программа разрешила этот точный перевод актива и учётная запись получила право на участие:

```bash
iroha --config ./user.client.toml \
  --fee-payer sponsor \
  --fee-program '<SPONSOR_CANONICAL_I105>/team-payments' \
  --fee-program-revision 1 \
  ledger asset transfer \
  --definition '<ASSET_DEFINITION_BASE58>' \
  --account '<USER_CANONICAL_I105>' \
  --to '<RECIPIENT_CANONICAL_I105>' \
  --quantity 1
```

Используйте активную ревизию и точные идентификаторы своей сети. Конфигурация пользователя содержит только средства подписи этого пользователя; закрытый ключ спонсора не нужен для отправки подходящей спонсируемой транзакции.

## 4. Решите, платит ли пользователь комиссию приложения {#_4-decide-whether-the-user-pays-an-application-fee}

Спонсор может покрывать глобальные комиссии, а приложение — ничего не взимать с пользователя. Если приложение собирает локальный токен, явно задайте этот перевод или правило контракта в подписываемом пользователем исполняемом содержимом. Включите каждую операцию в политику ревизии спонсора и проверьте расчёт комиссии для всей полезной нагрузки. Не выводите перевод токена приложения из намерения оплаты сетевой комиссии.

## Диагностика отказа {#diagnose-a-refusal}

Используйте стабильный код комиссионной ошибки и рекомендации по устранению, возвращённые узлом:

| Код | Что проверить |
| --- | --- |
| `program_not_found` | Точный канонический идентификатор программы. |
| `revision_not_active`, `program_not_active` | Активацию ревизии и жизненный цикл программы. |
| `beneficiary_not_eligible` | Включение получателя или разрешённый допуск по умолчанию для маршрута. |
| `operation_not_allowed`, `operation_denied` | Каждую точную подписанную операцию и запрещающее правило. |
| `invalid_gas_limit`, `signed_limit_exceeded` | Ограничение газа и подписанные максимумы относительно свежего расчёта комиссии. |
| `vault_insufficient` | Пополненный баланс хранилища точной валюты этой программы. |
| Коды исчерпания бюджета | Доступную ёмкость транзакции, блока, эпохи программы и эпохи получателя. |

При расследовании отправки с неоднозначным результатом сохраняйте исходный хеш транзакции и подробности отказа по комиссии. Подтвердите её статус перед созданием замены.
