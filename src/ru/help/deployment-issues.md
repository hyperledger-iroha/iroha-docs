# Проблемы с развертыванием {#troubleshooting-deployment-issues}

В этом разделе предлагаются советы по устранению неполадок для развертывания Iroha 3. Если проблема, с которой вы столкнулись, не описана здесь, свяжитесь с нами по телефону [Telegram](https://t.me/hyperledgeriroha).

## Начните с генерируемых артефактов . {#start-with-generated-artifacts}

Для локальных и тестовых развертываний предпочтительнее артефакты, генерируемые Kagami, чем ручно написанные файлы-партнеры:

```bash
cargo run --bin kagami -- localnet --peers 4 --out-dir ./localnet
```

В генерируемом каталоге содержится конфигурация сверстников, материал по генезису, стартовые скрипты и README для строки строительства Iroha 3.

## Сверстник не начинается {#peer-does-not-start}

Сначала проверьте эти предметы:

- `iroha3d --config <path>` пунктов в собственном файле TOML.
- `public_key` и `private_key` в конфигурации сверстников относятся к одной и той же паре ключей.
- `genesis.public_key` совпадает с ключом, использованным для подписания сделки о генезисе.
- идентификаторы сверстников validator используют BLS-Normal keys, а `trusted_peers_pop` содержит записи подтверждения владения для локального ключа и доверенных сверстниц.
- порты для Torii и P2P уже не связаны другим процессом.
- Список магазинов Kura принадлежит к той же цепочке и не был скопирован из другого профиля сети.

Используйте конфигурационное отслеживание, когда дэймон читает более одного слоя TOML:

```bash
cargo run -p irohad --bin iroha3d -- --config ./config.toml --trace-config
```

## Docker и Композиция {#docker-and-compose}

Генерация Составлять из текущего выхода локальной сети Kagami, чтобы аргументы командной строки и файлы конфигурации соответствовали проверенному коду:

```bash
cargo run --bin kagami -- localnet --peers 4 --out-dir ./localnet
cargo run --bin kagami -- docker --peers 4 --config-dir ./localnet --image hyperledger/iroha:dev --out-file ./docker-compose.yml --force
docker compose -f ./docker-compose.yml up
```

Если развертывание композиции начинается, а затем останавливается, проверьте журналы демонов на:

- несовместимые `chain`
- один сверстник, использующий другую генезисную транзакцию или манифест
- рекламируемые адреса P2P, которые работают только в сети контейнеров;
- повторное использование местного объема после регенерации генезиса

При тестировании нового генезиса удалите старые Kura объемы перед перезагрузкой стека. Сохранение старого блока с новым генезисом приведет к неудаче воспроизведения.

## Кубернеты {#kubernetes}

Для Kubernetes, рассматривать каждый валидатор как состоятельная инфраструктура:

- дать каждому партнеру стабильный идентификационный ключ и стабильный постоянный объем
- раскрыть P2P адреса, которые другие коллеги могут решить изнутри кластера
- установка конфигурации и файлов генезиса как неизменная конфигурация для развертывания
- внедрять все изменения генезиса или топологии преднамеренно, а не как автоматическое обновление конфигурационной карты

Если капсула возобновляется неоднократно, сравнить представленную конфигурацию в капсуле с ожидаемым [`peer.template.toml`](/ru/reference/peer-config/index.md#template) и проверить, воспроизводит ли пир старые данные Kura.

## Профиль Соры {#sora-profile}

Iroha 3 развертывания, которые используют Nexus, SoraFS или многополосные потоки, должны запускать демона с включенным профилем Sora:

```bash
cargo run -p irohad --bin iroha3d -- --config ./config.toml --sora
```

Используйте один и тот же профиль последовательно для validators в той же сети.
