# I105 Формат адреса учетной записи {#i105-account-address-format}

I105 является каноническим внешним текстовым форматом для Iroha 3 `AccountId`.

Его полезная нагрузка представляет контроллер аккаунта.

Его страж определяет целевую сеть с помощью цепочного различителя.

Используйте это везде, где API, транзакция, разрешение или запрос запрашивают канонический идентификатор аккаунта.

Идентификатор аккаунта I105 не имеет домена.

Значение, такое как `treasury@payments.universal`, является псевдонимом учетной записи, а не другой записью идентификатора I105.

Получение идентификатора I105 не регистрирует и не пополняет аккаунт.

::: warning Правила, которые предотвращают большинство сбоев интеграции

- Выберите сетевой профиль перед кодированием или проверкой адреса.
- Сохраняйте и сравнивайте каноническую строку UTF-8 точно.
- Сохраняйте регистр букв и не применяйте нормализацию `Unicode`.
- Идентификатор I105 не должен иметь суффикс `@domain` или `@domain.dataspace`.
- Используйте Iroha SDK или `iroha tools address`.
- Регулярное выражение не является валидатором I105.

:::

## Буквальная анатомия {#literal-anatomy}

Литерал I105 имеет три смежные части и не имеет разделителя:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

|Часть|Цель|Покрытие контрольной суммы|
| ---------------- | ------------------------------------------------------------------ | ----------------- |
|Сетевой страж|Отображает текст на один дискриминант цепочки `u16`|Не покрыто|
|Полезная нагрузка| `base-105` кодирование байтов канонического контроллера учетной записи|Покрытый|
|Контрольная сумма|Шесть значений `5-bit` в стиле `Bech32m`, отображенных с помощью алфавита I105|Н/Д|

Полезная нагрузка и контрольная сумма идентифицируют контроллер учетной записи.

Смотритель выбирает сетевой контекст.

У одного и того же контроллера одинаковая полезная нагрузка и контрольная сумма на Taira и Minamoto, но каждая сеть использует разный ведущий сигнал.

Декодер должен обеспечивать соблюдение ожидаемого дискриминанта.

Контрольная сумма не может обнаружить замену сигнального значения.

### Сетевые стражи {#network-sentinels}

|Сеть или контекст|Цепной дискриминант|шестигранник|канонический страж|
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
| Taira публичная тестовая сеть |                            `369` | `0x0171` |`test`|
| Minamoto общественная сеть |                            `753` | `0x02f1` | `sora`                                      |
|Контекст развития|                              `0` | `0x0000` | `dev`                                       |
|Любое другое значение `u16`|Все, кроме `0`, `369` и `753`|        — | `n` плюс минимальная десятичная, например `n42` |

Именованные значения всегда используют своего именованного сигнального значения.

Формы, такие как `n00042`, `n369`, `n753` и `n0`, не являются каноническими.

ID цепочки транзакций и дискриминатор цепочки I105 — это разные значения.

Выбор конечной точки API или идентификатора цепочки не подразумевает выбор профиля адреса.

## Нормативный пример с одной клавишей {#normative-single-key-example}

Полезная нагрузка и форма Minamoto ниже поступают от приспособления для кросс-SDK соответствия.

Форма Taira применяет стража Taira к той же полезной нагрузке:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

Каноническая полезная нагрузка начинается с `02 00 01 20`: заголовок `0x02`, компактный тег с одним ключом `0x00`, идентификатор кривой `Ed25519` `0x01` и длина ключа 32 байта `0x20`.

Префикс `multihash` является входными метаданными и не копируется в полезную нагрузку контроллера.

## Создавайте и проверяйте идентификаторы с CLI {#create-and-inspect-ids-with-the-cli}

Предпочтительно использовать именованный профиль для публичной сети:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

Нормализуйте и сравните входной I105 при диагностике поведения адресного кодека:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

Проверьте обнаруженный формат, канонический шестнадцатеричный код и выбранный сетевой контекст как JSON:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

Аудит структуры адреса-кодека файла, разделенного переносами строк, без молчаливого принятия ошибок разбора:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution CLI граница проверки

Команды `convert`, `normalize` и `audit` работают с низкоуровневым кодеком `AccountAddress`.

Они проверяют сторожевой байт, алфавит, контрольную сумму, длину байтов, `CurveId`/форму ключа и точное повторное кодирование адресного уровня.

Эти команды не создают объект `AccountId`.

Эти команды сами по себе не проверяют всю семантику политики мультиподписи.

Они не доказывают, что класс заголовка соответствует контроллеру.

Используйте строгую проверку `AccountId` перед авторизацией или постоянным сохранением.

:::

Для частной сети явно используйте её настроенный дискриминант с `--network-prefix`.

При преобразовании существующего адреса между явными контекстами также укажите источник с `--expect-prefix`:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

Повторное кодирование изменяет только сетевой контекст.

Это не регистрирует аккаунт в целевой сети и не доказывает, что тот же контроллер следует использовать там снова.

## Алгоритм кодирования {#encoding-algorithm}

канонические кодировщики выполняют эти операции:

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

Ведущие нулевые байты сохраняются как цифры `base-105` с нулевым значением.

Контрольная сумма использует генераторы `Bech32` `polymod` и константу `0x2bc830a3`.

Контрольная сумма только HRP — это ASCII строка `snx`.

Контрольная сумма только HRP не выводится в адресе.

Шесть контрольных сумм находятся в диапазоне `0..31` и отображаются с использованием того же алфавита I105, что и полезная нагрузка.

### I105 алфавит {#i105-alphabet}

Эти 105 символов проиндексированы в этом точном порядке.

Первый ряд — это алфавит `Bitcoin Base58` и содержит цифры `0..57`.

Вторая строка содержит цифры `58..104`.

Объедините строки при реализации кодека.

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

Алфавит чувствителен к `Unicode`.

Точная последовательность использует `compatibility-width` японские `kana` символы плюс указанные кодовые точки для `ヰ` и `ヱ`.

Не применяйте NFC, NFKC, преобразование ширины символов, приведение регистра или замену визуально похожих символов.

ASCII `0`, `O`, `I` и `l` не являются буквенными символами.

## каноническая полезная нагрузка аккаунта {#canonical-account-payload}

Тело `base-105` кодирует бинарную полезную нагрузку учетной записи, а не строку открытого ключа и не объект Norito JSON:

```text
header:u8 || controller:variable
```

Все многобайтовые целые числа ниже являются беззнаковыми и `big-endian`.

Домен, пространство данных, псевдоним, UAID и байты метаданных учётной записи отсутствуют.

### Заголовочный байт {#header-byte}

|Биты|Ширина|Текущий выход кодировщика|Значение|
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |Поле версии формата адреса|
| `4..3` |     2 |`0` одинарный ключ, `1` мультиподпись|Класс адреса|
| `2..1` |     2 |                          `1` |Поле версии нормализации|
| `0`    |     1 |                          `0` |Зарезервировано `extension flag`|

Текущие энкодеры V1 излучают заголовок `0x02` для контроллера с одним ключом и `0x0a` для мультиподписного контроллера.

Классы адресов `2` и `3` не назначены.

«`extension flag` `1` отклонён.»

Низкоуровневый декодер может сохранять другие версии и значения битов нормализации и не выполняет независимую проверку класса относительно тега контроллера.

Преобразование в `AccountId` и сравнение его канонического отображения доказывает каноничность текущего V1.

### Однокнопочный контроллер {#single-key-controller}

Используйте компактную форму, когда исходная полезная нагрузка открытого ключа не превышает 255 байт:

|Поле|Ширина|Значение или смысл|
| ------------ | --------------: | ------------------------ |
| `tag`        |          1 байт |`0x00`|
|`curve`      |          1 байт | Значение из реестра `CurveId` |
| `key_len`    |          1 байт |Длина исходного ключа|
| `public_key` | `key_len` байт |Необработанный полезный нагрузка открытого ключа|

Ключи длиной более 255 байт используют расширенную форму:

|Поле|Ширина|Значение или смысл|
| ------------ | --------------: | ---------------------------- |
| `tag`        |          1 байт | `0x02`                       |
|`curve`      |          1 байт | Значение из реестра `CurveId`     |
| `key_len`    |         2 байта |Длина исходного ключа, `big-endian`|
| `public_key` | `key_len` байт |Необработанное содержимое открытого ключа|

Расширённое кодирование не является каноническим для ключа, который подходит компактной форме.

### Мультиподписной контроллер {#multisig-controller}

|Поле|Ширина|Значение или смысл|
| ---------------- | -------: | ------------------------------ |
|`tag`            |1 байт| `0x01`                         |
| `policy_version` |1 байт|Текущее значение `1`|
| `threshold`      |2 байта|Требуемый общий вес одобрения|
| `member_count`   |2 байта|Количество следующих участников|
| `members`        |Переменная|Повторяющиеся записи участников|

Каждая запись участника:

|Поле|Ширина|Значение|
| ------------ | --------------: | ------------------------ |
| `curve`      |          1 байт | Значение из реестра `CurveId` |
| `weight`     |         2 байта |Вес одобрения участника|
| `key_len`    |         2 байта |Длина исходного ключа|
| `public_key` | `key_len` байт |Необработанный полезный нагрузка открытого ключа|

Действительная политика имеет как минимум одного участника, положительные веса, отсутствие дублирующихся открытых ключей и порог от `1` до суммы весов участников.

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

каноническая конструкция сортирует элементы по стабильному имени алгоритма подписи, байту нулевого разделителя, а затем по необработанным байтам открытого ключа.

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

Литерал I105 не имеет фиксированной длины символов, потому что мультиподписи и постквантовые контроллеры могут быть большими.

### `CurveId` реестр {#curveid-registry}

Последний столбец указывает на необходимую необязательную функцию `Cargo`.

Тире означает, что запись в реестре доступна без дополнительной функции модели данных.

|ID|Алгоритм подписи|Требуется функция `Cargo`|
| ---: | -------------------------------------------- | ------------------------ |
|  `1` | `Ed25519`                                    | —                        |
|  `2` | `ML-DSA`                                     | —                        |
|  `3` | `BLS12-381 normal`                           |`bls`|
|  `4` | `secp256k1`                                  | —                        |
|  `5` |`BLS12-381 small`                            | `bls`                    |
| `10` | `GOST R 34.10-2012 256-bit, parameter set A` |`gost`|
| `11` | `GOST R 34.10-2012 256-bit, parameter set B` |`gost`|
| `12` | `GOST R 34.10-2012 256-bit, parameter set C` | `gost`                   |
| `13` | `GOST R 34.10-2012 512-bit, parameter set A` |`gost`|
| `14` | `GOST R 34.10-2012 512-bit, parameter set B` |`gost`|
| `15` | `SM2`                                        | `sm`                     |

Не назначенные идентификаторы и алгоритмы, отключенные в принимаемой сборке, отклоняются.

Основной полезный пакет также должен быть структурно допустимым для алгоритма, выбранного заявленным `CurveId`.

## Строгая проверка AccountId и каноничность {#strict-accountid-validation-and-canonicality}

После настройки SDK с ожидаемым цепным дискриминантом, разберите в `AccountId` и сравните возвращённое каноническое отображение с обрезанным вводом.

Сравнение имеет значение, потому что парсер может нормализовать декодируемый материал контроллера при построении `AccountId`.

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

Для ненадежной строки соответствующее приложение должно:

1. Удалите только разрешённые при передаче пробельные символы вокруг всего значения.
2. Прочитайте стража и потребуйте ожидаемый дискриминант цепочки.
3. Отобразите каждый оставшийся символ `Unicode` через точный 105-символьный алфавит.
4. Отделите шесть цифр контрольной суммы.
5. Преобразуйте цифры полезной нагрузки обратно в канонические байты.
6. Проверьте контрольную сумму для этих канонических байтов.
7. Разберите заголовок и контроллер, требуя:
   - точные длины полей
   - поддерживаемый `CurveId`
   - действительный публичный ключ
   - отсутствие лишних байтов в конце
   - допустимая политика мультиподписи, если применимо
8. Постройте `AccountId`.
9. Сформируйте каноническое представление `AccountId` для ожидаемого дискриминатора.
10. Требуйте равенства `byte-for-byte` со входной строкой после удаления пробелов по краям.

Явный финальный шаг `render-and-compare` приложения отклоняет неминимальные числовые сигналы, некатегориальные схемы контроллера, переупорядоченные материалы политики и любое другое написание, которое декодируется, но не является текущим V1 выходом кодировщика.

Успешная проверка контрольной суммы или низкоуровневый разбор `AccountAddress` не заменяет эту проверку.

Не принимайте эти значения в поле с строгим идентификатором аккаунта:

- псевдоним аккаунта, такой как `alice@wonderland.universal`
- литерал I105 с добавленным суффиксом `@domain`
- открытый ключ `multihash`, такой как `ed0120...`
- канонический шестнадцатеричный полезный объект, такой как `0x02000120...`
- адрес для неправильного дискриминатора цепочки
- строка с измененными заглавными или строчными буквами, шириной символов, `kana`, полезной нагрузкой или контрольной суммой

Разрешайте псевдонимы на границе приложения и сохраняйте возвращенный канонический I105 идентификатор для авторизации, подписи, разрешений и аудиторских записей.

## API, правила хранения и отображения {#api-storage-and-display-rules}

- Отправьте точную строку I105 UTF-8 в поля учетной записи JSON.
- `Percent-encode` полный идентификатор учетной записи перед его размещением в сегменте пути URL.
- Никогда не используйте псевдоним учётной записи вместо I105 ID.
- Храните каноническую строку, возвращаемую кодеком, с семантикой сравнения `byte-preserving`.
- Используйте правило сортировки и сравнения, сохраняющее регистр букв и ширину символов.
- Храните дискриминатор цепочки или именованный профиль сети вместе с экспортированными данными учётной записи и резервными копиями.
- Повторно используйте адрес только в его сетевом контексте.
- Отобразите полный адрес и предоставьте действие копирования.
- Сохраняйте каждый символ `kana` точно.
- Держите полный адрес под рукой, когда компактный экран сокращает его середину.
- Используйте сохранённый канонический идентификатор вместо того, чтобы восстанавливать его из псевдонима.

Для отображения `AccountId` и его представления в JSON используется канонический формат I105.

Низкоуровневое представление `AccountAddress` для отображения и JSON использует канонический шестнадцатеричный формат во внутренних контекстах и при отладке.
