# Формат адреса счета I105 {#i105-account-address-format}

I105 является каноническим внешним текстовым форматом для Iroha 3 `AccountId`.

Ее полезная нагрузка представляет собой контролера счета.

Его охранник идентифицирует намеченную сеть с помощью цепного дискриминатора.

Используйте его в любом месте, где API, транзакция, разрешение или запрос просит канонический счет ID.

Счет I105 ID не имеет доменов.

Такое значение, как `treasury@payments.universal`, является псевдонимом для учета, а не другой орфографией I105 ID.

Вывод I105 ID не регистрирует или не финансирует счет.

::: warning Правила, которые предотвращают большинство неудач в интеграции

- Выберите профиль сети перед кодированием или проверкой адреса.
- Сохранить и сравнивать каноническую строку UTF-8 точно.
- Сохраняйте регистр букв и не применяйте нормализацию `Unicode`.
- На I105 ID не должно быть зафиксировано `@domain` или `@domain.dataspace`.
- Используйте Iroha SDK или `iroha tools address`.
- Регулярное выражение не является валидатором I105.

:::

## Буквальная анатомия {#literal-anatomy}

Буквальный I105 имеет три соседних части и не имеет разделителя:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

|Часть |Цель .|Покрытие счетной суммы |
| ---------------- | ------------------------------------------------------------------ | ----------------- |
|Сетевой сторожевой |Карты текста на один `u16` цепный дискриминатор |Не охваченные|
|Нагрузка .|`base-105` кодирование байтов канонического контролера счетов |Покрыто|
|Счетная сумма|Шесть значений стиля `Bech32m` `5-bit`, сделанных на алфавите I105 |N/A |

Пользовательная нагрузка и сумма проверки идентифицируют оператора счета.

Охранитель выбирает контекст сети.

Тот же контроллер имеет одинаковую полезную нагрузку и сумму проверки на Taira и Minamoto, но каждая сеть использует другой ведущий охранник.

Декодер должен задействовать ожидаемый дискриминатор.

Счетная сумма не может обнаружить замещение Sentinel.

### Сетевые охранники {#network-sentinels}

|Сеть или контекст |Дискриминатор цепочки |Хекс .|Канонический сторожевой |
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
|Taira общественная тестовая сеть |                            `369` |`0x0171` |`test` |
|Minamoto общественная сеть |                            `753` |`0x02f1` |`sora` |
|Контекст развития |                              `0` |`0x0000` |`dev` |
|Любое другое значение `u16` |Все, кроме `0`, `369` и `753` |        — |`n` плюс минимальная десятичная цифра, например, `n42` |

У именных значений всегда используется их именный сторожевой.

Формы, такие как `n00042`, `n369`, `n753` и `n0` не являются каноническими.

ID цепочки транзакций и дискриминатор цепочки I105 — это разные значения.

Выбор конечного пункта или цепочки ID не означает подразумеваемого выбора профиля адреса.

## Нормативный пример с одним ключом {#normative-single-key-example}

Ниже приведенная полезная нагрузка и форму Minamoto поступают из кросс-SDK фиксации соответствия.

Форма Taira применяется к одной и той же полезной нагрузке сопроводитель Taira:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

Каноническая полезная нагрузка начинается с `02 00 01 20`: заголовка `0x02`, компактный одноключевой тег `0x00`, кривая `Ed25519` ID `0x01` и длина ключа в 32 байта `0x20`.

Префикс `multihash` представляет собой входящие метаданные и не копируется в полезную нагрузку контроллера.

## Создание и инспекция IDs с помощью CLI {#create-and-inspect-ids-with-the-cli}

Предпочитаю именный профиль для публичной сети:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

Нормализация и сравнение ввода I105 при диагностике поведения адреса-кодека:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

Проверьте обнаруженный формат, канонический шестерник и выбранный контекст сети как JSON:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

Провести аудит структуры адреса-кодека файла, разделенного на новые строки, не принимая молчание ошибок анализа:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution Граница проверки CLI

Команды `convert`, `normalize` и `audit` работают на кодеке более низкого уровня `AccountAddress`.

Они проверяют сторожевую строку, алфавит, чекс-сумму, длину байтов, форму `CurveId`/ключа и точное перекодирование адресового слоя.

Эти команды не создают объект `AccountId`.

Эти команды сами по себе не проверяют всю семантику политики мультиподписи.

Они не доказывают, что класс заголовка соответствует контроллеру.

Используйте строгую проверку `AccountId` перед авторизацией или постоянным сохранением.

:::

Для частной сети используйте ее конфигурированный дискриминатор явно с `--network-prefix`.

При конвертации существующего адреса между ясными контекстами также укажите источник `--expect-prefix`:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

Перекодирование меняет только контекст сети.

Он не регистрирует учетную запись в целевой сети и не доказывает, что тот же контроллер должен быть повторно использован там.

## Алгоритм кодирования {#encoding-algorithm}

Канонические кодировки выполняют следующие операции:

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

Ведущие нулевые байты сохраняются в виде нулевых цифр `base-105`.

В контрольной сумме используются генераторы `Bech32` `polymod` и постоянная `0x2bc830a3`.

Лишь сумма проверки HRP представляет собой строку ASCII `snx`.

Только чековая сумма HRP не печатается в адресе.

Шесть значений контрольной суммы находятся в диапазоне `0..31` и отображаются с помощью того же алфавита I105, что и полезная нагрузка.

### Алфавит I105 {#i105-alphabet}

Все 105 символов перечислены в таком же порядке.

Первый ряд - алфавит `Bitcoin Base58` и содержит цифры `0..57`.

Второй ряд содержит цифры `58..104`.

Конкатенируйте строки при выполнении кодека.

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

Алфавит чувствительный к `Unicode`.

Точная последовательность использует символы `compatibility-width` японского языка `kana` плюс кодовые точки, указанные для `ヰ` и `ヱ`.

Не применяйте NFC, NFKC, преобразование ширины символов, приведение регистра или замену визуально похожих символов.

ASCII `0`, `O`, `I` и `l` не являются символами алфавита.

## Пользовательная нагрузка канонического счета {#canonical-account-payload}

Тело `base-105` кодирует полезную нагрузку бинарного счета, а не строку публичного ключа и не объект Norito JSON:

```text
header:u8 || controller:variable
```

Все нижеперечисленные многобайтные целые числа не подписаны и `big-endian`.

Домен, пространство данных, псевдоним, UAID и байты метаданных учётной записи отсутствуют.

### Заголовок байт {#header-byte}

|Биты |Ширина |Выход текущего кодера |Значение .|
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |Поле версии формата адреса |
| `4..3` |     2 |`0` один ключ, `1` многозначный |Адресный класс |
| `2..1` |     2 |                          `1` |Поле версии нормализации |
| `0`    |     1 |                          `0` |Резервированные `extension flag` |

Текущие кодировщики V1 выпускают заголовок `0x02` для одноключного контроллера и `0x0a` для многозначного контроллера.

Адресные классы `2` и `3` не присваиваются.

`extension flag` от `1` отклоняется.

Декодер низкого уровня может сохранить другие значения бит версии и нормализации и не самостоятельно перекрестит класс с тегом контроллера.

Преобразование в `AccountId` и сравнение его канонического отражания свидетельствует о текущей каноничности V1.

### Одноключевый контроллер {#single-key-controller}

Используйте компактную форму, когда полезная нагрузка сырого общественного ключа составляет не более 255 байтов:

|Поле |Ширина |Значение или значение |
| ------------ | --------------: | ------------------------ |
|`tag` |1 байт |`0x00` |
|`curve` |1 байт | Значение из реестра `CurveId` |
|`key_len` |1 байт |Длина сырой клавиши |
|`public_key` |`key_len` байты |Суровая полезная нагрузка общественного ключа |

Ключи длиннее 255 байтов используют расширенную форму:

|Поле |Ширина |Значение или значение |
| ------------ | --------------: | ---------------------------- |
|`tag` |1 байт |`0x02` |
|`curve` |1 байт | Значение из реестра `CurveId`     |
|`key_len` |2 байта |Длина сырого ключа, `big-endian` |
|`public_key` |`key_len` байты |Суровая полезная нагрузка общественного ключа |

Расширенное кодирование не является каноническим для ключа, который подходит к компактной форме.

### Мультисигный контроллер {#multisig-controller}

|Поле |Ширина |Значение или значение |
| ---------------- | -------: | ------------------------------ |
|`tag` |1 байт |`0x01` |
|`policy_version` |1 байт |Текущая стоимость `1` |
|`threshold` |2 байта |Необходимая общая масса одобрения |
|`member_count` |2 байта |Число следующих членов |
|`members` |Переменный |Повторные записи членов |

Каждый запись членов:

|Поле |Ширина |Значение .|
| ------------ | --------------: | ------------------------ |
|`curve` |1 байт | Значение из реестра `CurveId` |
|`weight` |2 байта |Веса одобрения члена |
|`key_len` |2 байта |Длина сырой клавиши |
|`public_key` |`key_len` байты |Суровая полезная нагрузка общественного ключа |

Действующая политика имеет по меньшей мере одного члена, положительные весы, отсутствие двойных государственных ключей и порог от `1` до суммы весов членов.

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

Каноническая конструкция сортирует членов по стабильному названию алгоритма подписания, нулевому байту разделителя, а затем чистым байтам общественного ключа.

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

Буквальный I105 не имеет фиксированной длины символов, потому что мультисигные и постквантовые контроллеры могут быть большими.

### Регистр `CurveId` {#curveid-registry}

В последней колонке указана требуемая опциональная функция `Cargo`.

Датши означают, что запись в регистре доступна без дополнительной функции модели данных.

|ID |Подписание алгоритма |Необходимость `Cargo` |
| ---: | -------------------------------------------- | ------------------------ |
|  `1` |`Ed25519` | —                        |
|  `2` |`ML-DSA` | —                        |
|  `3` |`BLS12-381 normal` |`bls` |
|  `4` |`secp256k1` | —                        |
|  `5` |`BLS12-381 small` |`bls` |
| `10` |`GOST R 34.10-2012 256-bit, parameter set A` |`gost` |
| `11` |`GOST R 34.10-2012 256-bit, parameter set B` |`gost` |
| `12` |`GOST R 34.10-2012 256-bit, parameter set C` |`gost` |

Нераспределенные IDs и алгоритмы, отключенные в приемной сборке, отвергаются.

Ключевая полезная нагрузка также должна быть структурно действительной для алгоритма, выбранного декларируемым `CurveId`.

## Строгая валидация и каноничность AccountId {#strict-accountid-validation-and-canonicality}

После конфигурации SDK с ожидаемым цепным дискриминатором, проанализируйте в `AccountId` и сравнивайте возвращенное каноническое отображение с отрезанным вводом.

Сравнение имеет значение, поскольку анализатор может нормализовать декодируемый контроллер при строительстве `AccountId`.

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

Для неуверенной струны, соответствующее применение должно:

1. Удалите только разрешённые при передаче пробельные символы вокруг всего значения.
2. Прочитайте сторожевой и требуйте ожидаемого цепного дискриминатора.
3. Карта каждого оставшегося символа `Unicode` по точному алфавиту на 105 символов.
4. Отделите шесть цифр контрольной суммы.
5. Преобразовать цифр полезной нагрузки обратно в канонические байты.
6. Проверьте контрольную сумму для этих канонических байтов.
7. Проанализировать заголовок и контроллер, требуя:
   - точные длины поля
   - поддерживаемый `CurveId`
   - действительный общественный ключ
   - отсутствие лишних байтов в конце
   - допустимая политика мультиподписи, если применимо
8. Создать `AccountId`.
9. Сформируйте каноническое представление `AccountId` для ожидаемого дискриминатора.
10. Требуйте равенства `byte-for-byte` со входной строкой после удаления пробелов по краям.

Определенный окончательный шаг приложения `render-and-compare` отклоняет не минимальные числовые сторожевые элементы, неканонические макеты контроллеров, перепорядоченные политические материалы и любое другое правописание, которое декодирует, но не является текущим выходом кодера V1.

Успешная проверка суммы или анализ низкого уровня `AccountAddress` не является заменой этой проверки.

Не принимать эти значения в строгом поле счета-ID:

- псевдоним для счета, например `alice@wonderland.universal`
- буквальный I105 с приложенным суфиксом `@domain`
- общедоступный ключ `multihash`, например, `ed0120...`
- каноническая полная нагрузка hex, например `0x02000120...`
- адрес неправильного дискриминатора цепочки
- строка с измененными большими или малыми буквами, ширинами символов, `kana`, полезной нагрузкой или суммой проверки

Решение псевдонимов на границе приложения и сохранение возвращенной канонической I105 ID для разрешений, подписания, разрешений и аудиторских записей.

## API, правила хранения и отображения {#api-storage-and-display-rules}

- Отправьте точную строку I105 UTF-8 в полях учетной записи JSON.
- `Percent-encode` полный счет ID перед его размещением в сегменте пути URL.
- Никогда не используйте псевдоним учётной записи вместо I105 ID.
- Сохранить канонический строк, возвращенный кодеком с семантикой сравнения `byte-preserving`.
- Используйте правило сортировки и сравнения, сохраняющее регистр букв и ширину символов.
- Храните дискриминатор цепочки или именованный профиль сети вместе с экспортированными данными учётной записи и резервными копиями.
- Повторное использование адреса только в контексте сети.
- Показать полный адрес и указать копию действия.
- Сохранить каждый `kana` персонаж точно.
- Сохраняйте полный адрес, когда компактный дисплей сокращает его середину.
- Используйте сохраненный канонический ID вместо того, чтобы восстанавливать его из псевдонима.

Для отображения `AccountId` и его представления в JSON используется канонический формат I105.

Низкоуровневое представление `AccountAddress` для отображения и JSON использует канонический шестнадцатеричный формат во внутренних контекстах и при отладке.

Если требуется внешний счет ID, обращайтесь к кодирующему модулю `AccountAddress` I105.

Для процессов создания учетных записей и разрешения псевдонимов продолжать с помощью [Счетные записи и псевдоним](/ru/cookbook/accounts-and-aliases.md).

Для модели данных о счетах см. [Счетные отчеты](/ru/blockchain/accounts.md).
