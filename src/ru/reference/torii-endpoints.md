# Torii API конечные точки {#torii-endpoints}

Torii является шлюзом HTTP, SSE и WebSocket для Iroha 3. Он служит как для взаимодействия с распределённым реестром блокчейна APIs, так и с конечными точками оператора API.

Текущие правила протокола следующие:

- канонический бинарный формат — Norito
- многие API конечные точки также поддерживают JSON, когда вы отправляете `Accept: application/json`
- метрики представлены в формате Prometheus

Для подробностей о формате, согласовании содержимого, флагах макета, криптографических хэшах схемы и руководстве Norito RPC см. [Norito справка](/ru/reference/norito.md).

## Общие API конечные точки {#common-endpoints}

| API конечная точка                         |Формат|Цель|
| -------------------------------- | -------------- | ---------------------------------------------------------------- |
| `POST /v1/pipeline/transactions` |Norito|Отправить подписанную транзакцию|
|`POST /v1/query`| Norito         |Отправьте подписанный запрос|
| `GET /v1/events/ws`              |WebSocket      |Подписаться на потоки событий|
| `GET /v1/events/sse`             |SSE            |Подписаться на потоки событий через SSE|
| `GET /v1/blocks/stream`          | WebSocket      |Поток готовых блоков|
|`GET /v1/peers`| JSON           |список сетевых узлов, раскрытый Torii|
| `GET /livez`                     |Текст|Только живость процесса; это не означает готовность протокола|
|`GET /readyz`| JSON           |Полная готовность узла, включая обязательные проверки автономной наличности|
| `GET /health`                    | JSON           |Проба готовности с тем же инвариантом оффлайн-кэша|
|`GET /v1/api/version`            |Текст|Текущая версия заголовка блока|
| `GET /status`                    | Norito или JSON |Высокий уровень диагностического состояния; запрос JSON явно|
|`GET /metrics`|Прометей|Сбор данных Prometheus с эндпоинта API|
| `GET /v1/schema`                 | JSON           |Снимок данных схемы модели данных, предоставляемый узлом при включении|
| `GET /openapi.json`              |JSON           | OpenAPI документ для активных Torii HTTP маршрутов                |
| `GET /v1/parameters`             |JSON           |Снимок данных параметров узла|
|`GET /v1/node/capabilities`      | JSON           |Возможности узла и метаданные модели данных|
| `GET /v1/time/now`               |JSON           |Снимок данных локальных системных часов узла|
|`GET /v1/time/status`            | JSON           |Статус синхронизации времени|

Для запроса SSE рекламируйте нативный поток плюс типизированную резервную версию:

```http
Accept: text/event-stream, application/json
```

Torii сначала ведет переговоры о представлении JSON или Norito на уровне запроса, затем проверяет нативный ответ `text/event-stream`. Отправка только `text/event-stream` поэтому отклоняется с `406`; [рецепт потоковых событий](/ru/cookbook/stream-events.md) использует полный заголовок.

`/openapi.json` — это сгенерированный контракт для маршрутов, представленных в схеме, а не полный инвентарь эксплуатационных проб. Текущий документ опускает `/livez` и `/readyz`, а его описание `/health` может отставать от обработчика готовности. Генерируйте маршруты клиентов из рабочего документа, но проверяйте активность и готовность напрямую через запущенный узел и закрепленные обработчики. Точная поверхность все еще зависит от сборки функции и конфигурация выполнения программного обеспечения. Используйте [Torii API консоль](/ru/reference/torii-api-console.md), чтобы загрузить этот живой документ, протестировать маршруты JSON, скопировать запросы curl и сгенерировать клиентский код из текущей схемы.

Каждая операция с поддержкой каталога OpenAPI включает объект `x-iroha-route-auth`. Инструменты с поддержкой каталога MCP предоставляют тот же контракт, что и `_meta["iroha/routeAuth"]`. Обе проекции несут `schemaVersion`, `stableRouteId`, `authentication` и `admission`. Обращайтесь с версией `1` как с точным контрактом: отклоняйте неподдерживаемый `schemaVersion`, вместо того чтобы догадываться, как следует интерпретировать его метки аутентификации или допуска. Метаданные маршрута описывают границы запроса; они не заменяют учетные данные, требуемые этой границей.

## Попробуйте живые маршруты Taira {#try-live-taira-routes}

Публичная тестовая сеть Taira предоставляет тот же интерфейс Torii JSON, который клиенты приложений используют для просмотра только для чтения. Для выполнения этих команд ключи не требуются:

```bash
TAIRA_ROOT=https://taira.sora.org

curl -fsS -H 'Accept: application/json' "$TAIRA_ROOT/status" \
  | jq '{blocks, txs_approved, txs_rejected, queue_size, peers}'

curl -fsS "$TAIRA_ROOT/openapi.json" \
  | jq -r '.paths | keys[]' \
  | grep '^/v1/' \
  | head -n 20

curl -fsS -H 'Accept: application/json' \
  "$TAIRA_ROOT/v1/node/capabilities" \
  | jq '{abi_version, data_model_version, query: .query.aggregate.supported_resources}'
```

Попробуйте чтение ресурсов в соответствии с текущим состоянием мира:

```bash
curl -fsS "$TAIRA_ROOT/v1/domains?limit=5" \
  | jq -r '.items[].id'

curl -fsS "$TAIRA_ROOT/v1/assets/definitions?limit=5" \
  | jq -r '.items[] | [.id, .name, .total_quantity] | @tsv'
```

Если публичный тестнет-маршрут возвращает `502`, истекает по времени или сообщает о перегруженной очереди, рассматривайте это как проблему доступности конечной точки API и повторите попытку позже перед отладкой вашего клиентского кода.

## Приложение и семейства маршрутов SORA {#app-and-sora-route-families}

## Аутентификация аккаунта, видимость и курсоры обозревателя {#account-authentication-visibility-and-explorer-cursors}

### Протокол запроса учетной записи приложения {#app-account-request-protocol}

Маршруты, доступные приложению, принимают либо отсутствие заголовков аутентификации, либо одно прямое доказательство с одним ключом, либо один мультиподписанный свидетель. Каждый заголовок аутентификации должен появляться не более одного раза.

Для прямого доказательства отправьте все четыре заголовка вместе:

- `X-Iroha-Account`: точный канонический адрес счета в нижнем регистре `0x` в формате hex или активный канонический псевдоним счета ASCII. Текст I105 небезопасен как значение поля HTTP; используйте каноническое написание в hex для этого счета.
- `X-Iroha-Signature`: строгая полезная нагрузка подписи с дополнением base64.
- `X-Iroha-Timestamp-Ms`: канонический беззнаковый десятичный Unix-временной штамп в миллисекундах, в пределах настроенного окна сдвига.
- `X-Iroha-Nonce`: от 1 до 256 печатных байт ASCII (`0x21` до `0x7e`), уникальны в пределах окна повтора.

Зарегистрированный однокнопочный контроллер посылает именно эти байты:

```text
iroha.app.request.network.v1\0 || <genesis-derived network_id[32]> ||
<UPPERCASE_METHOD>\n
<exact request path>\n
<canonical query>\n
<lowercase hex SHA-256 of the raw body>\n
<canonical timestamp_ms>\n
<nonce>
```

каноническое построение запроса анализирует исходный запрос как `application/x-www-form-urlencoded` (`+` означает пробел), выполняет процентное декодирование его пар, сортирует их по `(key, value)` и снова кодирует в форме. Протокол допускает не более 64 декодированных пар и 64 KiB текста необработанного запроса. Выполните криптографическое хеширование байтов тела точно так, как они были переданы. Не вставляйте разделитель между фиксированным 32-байтовым идентификатором сети и методом в верхнем регистре.

Проверяющий V1 также ограничивает маркер метода до 32 байт, путь запроса в процентном кодировании до 64 KiB и прямую идентификацию учетной записи до 36 KiB перед разбором. Псевдонимы аккаунтов имеют более жесткое структурное ограничение: три сегмента имени плюс их разделители. Превышение этого ограничения приводит к сбою аутентификации до проверки подписи или выделения памяти под исходный размер.

Мультиподписной контроллер должен вместо этого отправлять `X-Iroha-Witness` в виде строго дополненной base64 канонической формы Norito и опускать `X-Iroha-Signature`, `X-Iroha-Timestamp-Ms` и `X-Iroha-Nonce`. `X-Iroha-Account` является необязательным в этой форме; если присутствует, оно должно быть равно свидетелю `subject_account`. `CanonicalRequestWitnessV1` содержит `schema_version`, `subject_account`, `timestamp_ms`, `nonce`, Iroha `Hash` точных сетевых байтов запроса через значение криптографического дайджеста тела, но без полей свежести, и не более 64 подписей участников. Каждый участник подписывает каноническое Norito кодирование той же полезной нагрузки без массива подписей. Проверенные участники должны соответствовать текущей политике мультиподписи аккаунта. Кодированный свидетель ограничен 1 MiB.

Отсутствие заголовков аутентификации означает анонимный доступ. Любое частичное, смешанное, повторяющееся, неверно сформированное, устаревшее или повторное подтверждение приводит к сбою аутентификации; оно никогда не приводит к возврату к анонимной видимости.

### Протокол запроса оператора {#operator-request-protocol}

Маршруты, отмеченные как аутентифицированные оператором, требуют все четыре одиночных заголовка:

- `x-iroha-operator-public-key`: канонический Iroha мультихеш открытый ключ.
- `x-iroha-operator-timestamp-ms`: каноническая беззнаковая десятичная метка времени Unix в миллисекундах.
- `x-iroha-operator-nonce`: 1–256 печатаемых ASCII байт, уникальных для этого ключа в пределах окна повторного воспроизведения.
- `x-iroha-operator-signature`: строгое полезное нагрузка подписи с дополнением base64.

Значения заголовков не должны содержать окружающие пробелы. Знаки ключей оператора:

```text
iroha.operator.http-request.network.v1\0 || <genesis-derived network_id[32]> ||
<UPPERCASE_METHOD>\n
<exact request path>\n
<canonical query>\n
<lowercase hex SHA-256 of the raw body>\n
<canonical timestamp_ms>\n
<nonce>
```

Правила для пути, запроса, тела, временной метки и криптографического числа nonce такие же, как и канонические правила, используемые протоколом приложения. Ключ также должен быть допущен `[torii.operator_signatures]`: укажите его в `allowed_public_keys` или явно включите `allow_node_key` при использовании ключа узла. Насыщение кеша повторов приводит к срабатыванию защищённого закрытия с `503 Service Unavailable`.

Точная подпись запроса всегда обязательна. Когда `[torii.operator_auth].enabled = true`, для каждого обычного маршрута оператора также требуется действительный `x-iroha-operator-session`; когда `require_mtls = true`, дополнительно требуется `x-forwarded-client-cert` от доверенного входа. Ни один из факторов не заменяет подпись запроса.

WebAuthn регистрация и вход используют эти четыре JSON API конечные точки:

|Метод и API конечная точка|Цель|
| --------------------------------------------- | ---------------------------------------- |
| `POST /v1/operator/auth/registration/options` |Начать регистрацию учетных данных WebAuthn|
| `POST /v1/operator/auth/registration/verify`  |Проверьте и сохраните учетные данные|
|`POST /v1/operator/auth/login/options`        |Начать аутентификацию WebAuthn|
| `POST /v1/operator/auth/login/verify`         |Проверьте утверждение и выдайте сеанс|

Настройте `torii.operator_auth.tokens` с выделенными значениями загрузки. До появления любых учетных данных отправьте один как `x-iroha-operator-token`, чтобы начать первую регистрацию. Этот токен никогда не авторизует обычный маршрут оператора, а значения слушателя `x-api-token` никогда не используются повторно для этого потока. Как только учетные данные существуют, регистрация другой учетной записи требует аутентифицированной сессии. Проверка входа возвращает токен сессии, который необходимо отправлять вместе с каждой новой подписью запроса оператора точной сети. Учетные данные сохраняются в `<torii.data_dir>/operator_auth/operator_webauthn.json`.

ISO 20022 маршруты проходят две независимые проверки. Запрос должен сначала пройти этот белый список операторов и протокол подписи; затем обработчик ISO требует, чтобы тот же ключ занимал точно ту же роль участника или аудитора, описанную ниже.

### распределённый блокчейн-реестр, видимость и указатели обозревателя {#ledger-visibility-and-explorer-cursors}

Запросы на чтение распределенного реестра блокчейна с стороны приложения используют вышеуказанную необязательную границу учетной записи приложения. Несigned-запрос получает только пространства данных, настроенные как публичные. Действительный подписанный запрос добавляет области данных, привязанные к текущему UAID вызывающего, каждая ограниченная область данных именуется по точному разрешению `CanReadRestrictedDataspace { dataspace }`, или все маршруты, когда аккаунт имеет `CanReadAllLedgerData`.

Используйте маршрут, который соответствует основному пользователю запроса:

|Метод и конечная точка API|Аутентификация и видимость|
| ------------------------------------- | --------------------------------------------------------------- |
| `POST /v1/transactions/visible/query` |каноническая подпись аккаунта; применяет видимость вызывающего|
|`POST /v1/transactions/query`|Подпись запроса оператора; разрешает глобальный просмотр оператора|
| `GET /v1/triggers/completed`          |Подпись запроса оператора; читает локальные на узле записи о завершении|

Один и тот же объект видимости фильтрует учетную запись, домен, определение актива, актив, NFT, RWA, владельца и чтения Explorer. Отсутствующий объект и объект, находящийся за пределами видимых маршрутов вызывающего, намеренно неразличимы. Окончательно завершённая транзакция и история инструкций отображаются только тогда, когда видна каждая часть финансового перевода по маршруту, записанная для транзакции. Транзакция с смешанным пространством данных — поэтому скрыто, когда даже одна часть финансового перевода участника находится за пределами области вызова; отсутствующий, устаревший или неверно сформированный контекст маршрутизации виден только глобальному читателю.

Шесть коллекций Explorer, поддерживаемых миром, используют непрозрачные канонические курсоры ключей base64url. Лимит страницы по умолчанию составляет 25, максимум — 100, а одна страница проверяет не более 512 кандидатных ключей. Каждый курсор привязан к своей коллекции, фильтрам, каноническому последнему ключу и криптографическому дайджесту видимого набора маршрутов вызывающего, поэтому его нельзя воспроизвести в другом запросе или после изменения видимости вызывающего.

Курсоры истории блока, транзакции, последней транзакции, инструкции и последней инструкции дополнительно фиксируют высоту завершённого снимка данных и криптографический хеш блока. Ответы показывают `pagination.limit`, `pagination.snapshot_height`, `pagination.snapshot_hash`, `pagination.next_cursor` и `pagination.has_more`. Курсор для другого маршрута или набора фильтров, изменённое значение криптографического дайджеста видимости или снимок данных, который узел больше не может проверить, закрывается с ошибкой. Сканирование истории остаётся внутри разрешения на приём запросов Torii, пока выполняется блокирующий рабочий процесс.

Потоки Explorer WebSocket передают отфильтрованные сводки и перерассчитывают видимость по мере изменения разрешений распределенного реестра блокчейна. Родной маршрут `GET /v1/blocks/stream` отличается: он излучает полностью подписанные блоки, требует `CanReadAllLedgerData` во время рукопожатия и закрывается, если это разрешение позже отзывается. Не используйте нативный поток для обозревателя с областью данных.

## ISO Мост 20022 {#iso-20022-bridge}

Torii раскрывает мост ISO 20022 под `/v1/iso20022/*`, когда включены программное обеспечение моста и среда выполнения API, обращенная к приложению. Мост намеренно ограничен: это не универсальный шлюз клиринга ISO 20022, а поддерживаемый поднабор для преобразования выбранных платежных сообщений в подписанные переводы Iroha и для отслеживания их состояния в распределенном реестре блокчейна.

Настройте надежный локальный `torii.iso_bridge.store_dir` перед принятием любых отправок. Поле конфигурации является необязательным только для того, чтобы узел мог запускаться в режиме только для чтения или для диагностического использования: каждая аутентифицированная ISO отправка требует каталог и возвращает `503 Service Unavailable`, подлежащий повтору, когда отсутствует сохранение или когда запись replay-tombstone или rich-record не удается.

|Метод и конечная точка API|Цель|
| -------------------------------------------- | -------------------------------------------------------------------------------------------------- |

|`GET /v1/iso20022/audit/messages`            |Прочитайте технический манифест аудита сообщений с защищённой от подделки маркировкой|
| `GET /v1/iso20022/messages/{msg_id}/pacs002` |Отобразите текущий статус оплаты как `pacs.002` XML|

Поданные `pacs.008` материалы должны содержать идентификатор сообщения, сумму расчета по межбанковской финансовой транзакции, валюту, дату расчета финансовой транзакции, а также IBANs должника и кредитора и BICs должника и кредитора. Когда настроены эталонные данные, мост также проверяет перекрестные таблицы валют BIC, IBAN и ISO 4217 перед тем, как сгенерированная транзакция войдет в процесс обработки программного обеспечения.

`pacs.009` представленные материалы должны содержать идентификатор бизнес-сообщения, идентификатор определения сообщения, время создания, сумму расчета по межбанковской финансовой транзакции, валюту, дата расчета финансовой операции, агент, дающий указания, и агент, получающий указания BICs, а также должник и кредитор IBANs. Если сообщение включает `Purp`, мост в настоящее время принимает финансирование только для целей ценных бумаг: `Purp=SECU`.

Этот `pacs.008` и `pacs.009` подача API конечные точки принимают XML ISO контейнеры данных или плоский формат поля, используемый в тестах моста. Необязательно `SplmtryData` поля могут закреплять цель Iroha распределенный реестр блокчейна, идентификаторы или адреса исходного и целевого аккаунтов, а также идентификатор определения актива. Ответ `202 Accepted` с `message_id`, `transaction_hash`, `status`, `pacs002_code`, и разрешённый контекст реестра/счёта/актива.

### Авторизация участника и жизненный цикл владения {#participant-authorization-and-lifecycle-ownership}

Каждый включённый мост имеет каталог участников. Каждая запись участника содержит уникальный идентификатор участника, один или несколько открытых ключей оператора, один или несколько финансовых идентификаторов, набор разрешённых профилей и роли `originator`, `counterparty` или обе. Ключи оператора и финансовые идентификаторы не могут принадлежать более чем одному участнику. Настройте `audit_admin_keys` отдельно; ключ администратора аудита не может одновременно быть ключом мутации участника.

Все маршруты ISO требуют новой подписи оператора. Для первоначальной подачи `pacs.008`, `pacs.009`, `sese.023` или `colr.012` аутентифицированный оператор должен принадлежать участнику, указанному в заголовке приложения `From` с финансовой идентичностью. Идентификатор `To` должен соответствовать настроенному участнику с ролью `counterparty`, и выбранный профиль должен быть разрешен для обеих сторон. Надежная запись о приеме фиксирует инициатора, контрагента, участника, принимающего участие, и ключ оператора, а также исходный профиль и встроенную политику подписи.

Авторизация жизненного цикла получается из этой неизменяемой записи, а не из выбранных вызывающим значений:

|Сообщение жизненного цикла|Требуется участник|
| ---------------------------------------------- | -------------------------------------------------- |
| `pacs.002`, `pacs.004`, `sese.024`, `sese.025` |Оригинальная контрагент с ролью `counterparty`|
| `camt.056`                                     |Оригинальный инициатор с ролью `originator`|

Исходная политика профиля и подписи остается закрепленной на протяжении всего жизненного цикла, поэтому вызывающий не может выбрать более слабый профиль для обновления. Код `pacs.002`, который представляет финансовое урегулирование транзакции (`ACSC`, `ACCP`, `SETT` или `SETTLED`) изменяет исходную запись на «урегулировано» только тогда, когда Torii предоставил окончательные доказательства транзакции.

Любая из исходных сторон может читать свою запись сообщений и созданные исходящие документы. Конечная точка аудита API возвращает только записи, в которых аутентифицированный участник является инициатором или контрагентом. Отдельно настроенный администратор аудита получает глобальный режим только для чтения аудита и не может отправлять или изменять сообщения. Неизвестные участники и несвязанные идентификаторы сообщений не раскрываются.

### Надёжная идентичность воспроизведения и подписанные документы исходящей почты {#durable-replay-identity-and-signed-outbox-documents}

Маркировки постоянного удаления воспроизведения являются строгой границей допуска. Torii прерывает запуск при наличии нечитаемой, слишком большой, неправильно сформированной, неправильно названной, конфликтующей или явно несовместимой маркировки постоянного удаления. Это также прерывается для богатой записи с явно несовместимой версией схемы, участника, профиля или политики подписи, отсутствующих в текущей конфигурации, или при отсутствии или несоответствии маркера долговременного удаления.

Другие повреждения записей с богатой структурой обрабатываются иначе: нечитаемые или слишком большие файлы, недопустимые JSON, недопустимые записи текущей схемы, некорректные имена файлов и конфликтующие идентичности повторов записываются в журнал или пропускаются. Нечитаемый или недопустимый индекс аудита текущей версии восстанавливается из сохранённых записей; только явно несовместимая версия индекса аудита прерывает запуск. Отслеживайте журналы запуска и сверяйте восстановленный технический манифест аудита, вместо того чтобы предполагать, что каждый поврежденный файл rich-record препятствует работе узла.

Каждая сохранённая полная запись сохраняет неизменяемое происхождение участника. Отдельный долговечный маркер удаления хранит идентификатор сообщения, криптографический хэш полезной нагрузки, бизнес-идентификатор сообщения и UETR для полной дедупликации TTL даже после того, как детали полной записи будут удалены.

Torii сохраняет повторное воспроизведение подтверждения до того, как оно подпишет или обработает сообщение жизненного цикла. Оно никогда не удаляет неистекший идентификатор повторного воспроизведения. Если настроенная емкость полностью занято защищёнными записями или неистёкшими идентификаторами воспроизведения, отправки получают повторяемый `503 Service Unavailable` без изменения состояния жизненного цикла или учётного состояния.

Каждый сгенерированный документ `pacs.002`, `pacs.004`, `camt.029`, `sese.024` или `sese.025` возвращается как `application/xml` с этими заголовками ответа:

|Заголовок|Значение|
| ------------------------------ | ----------------------------------------------------- |
| `X-Iroha-Iso-Signature-Domain` |Всегда `iroha.iso20022.outbound.v2`|
|`X-Iroha-Iso-Signer`           |канонический открытый ключ для настроенного криптографического подписанта моста|
|`X-Iroha-Iso-Signature`        |Подпись Base64 для доменно-разделённых XML байт|

Проверьте подпись над последовательностью байтов UTF-8 `iroha.iso20022.outbound.v2`, одним нулевым байтом и точным телом ответа. Не форматируйте и не нормализуйте XML перед проверкой.

## Kaigi Сессии {#kaigi-sessions}

Kaigi предоставляет платные аудио-/видео-комнаты в реальном времени на SORA Nexus. Используйте это, когда приложению требуется создание сессий, изменения в списке участников, передача технических манифестов и зашифрованная сигнализация, поддерживаемые распределенным реестром блокчейна. и измерение использования вместо хранения всех состояний конференций вне цепочки.

Взаимодействие с жизненным циклом распределенного реестра блокчейна состоит в следующем:

- `CreateKaigi`: создать звонок в домене и сохранить его политику, расписание, метаданные и необязательный технический манифест ретрансляции.
- `JoinKaigi`: обновите список вызовов. В режиме `zk-roster-v1` публичный просмотр вызовов отображает значение криптографического обязательства и количество нулификаторов вместо идентификаторов учетных записей участников.
- `LeaveKaigi`: удалить участника из прозрачного звонка. Выход в приватном режиме осуществляется вне цепочки в протоколе первой версии.
- `RecordKaigiUsage`: добавить итоги с измеренной продолжительностью и стоимостью выполнения транзакции.
- `EndKaigi`: закройте сессию и зафиксируйте конечную временную метку.

Torii предоставляет следующий доступ приложений к чтению:

|Маршрут|Аутентификация|Цель|
| ----------------------------------- | --------------------------------------- | ------------------------------------------ |
|`/v1/kaigi/calls/{call_id}`|публичный|текущая запись звонка|
| `/v1/kaigi/calls/{call_id}/signals` |канонический запрос учетной записи точной сети|странично оформленные окончательные метаданные сигнализации|
| `/v1/kaigi/calls/{call_id}/events`  |канонический запрос учетной записи точной сети|поток жизненного цикла вызова|
|`/v1/kaigi/relays`                  |запрос оператора из разрешённого списка|резюме эстафеты|
| `/v1/kaigi/relays/{relay_id}`       |запрос оператора из разрешённого списка|регистрационные и данные о состоянии одного реле|
| `/v1/kaigi/relays/health`           |запрос оператора из разрешённого списка|сводное состояние реле|
| `/v1/kaigi/relays/events`           |канонический запрос учетной записи точной сети|регистрация ретранслятора и поток событий здоровья|

Приложение API должно быть включено. Сводка реле и маршруты состояния являются поверхностями оператора, даже если они только для чтения; неподписанный запрос `curl` является недопустимая проверка доступности. Состояние сеанса также отражается через события домена Kaigi, такие как `KaigiRosterSummary`, `KaigiRelayManifestUpdated`, `KaigiRelayHealthUpdated` и `KaigiUsageSummary`.

### CLI Тест на дым {#cli-smoke-test}

Начните с `iroha app kaigi` CLI, когда хотите проверить, что Torii API конечная точка принимает Kaigi транзакции перед подключением UI. Команда quickstart создает комнату на настроенной API конечной точке и выводит ее идентификатор вызова и метаданные для присоединения:

```bash
iroha app kaigi quickstart \
  --domain kaigi.universal \
  --summary-out kaigi-summary.json
```

Для скриптовых потоков управляйте жизненным циклом комнаты явно:

```bash
iroha app kaigi create \
  --domain kaigi.universal \
  --call-name daily \
  --host <i105-account-id> \
  --privacy-mode transparent \
  --room-policy authenticated

iroha app kaigi join \
  --domain kaigi.universal \
  --call-name daily \
  --participant <i105-account-id>

iroha app kaigi leave \
  --domain kaigi.universal \
  --call-name daily \
  --participant <i105-account-id>

iroha app kaigi record-usage \
  --domain kaigi.universal \
  --call-name daily \
  --duration-ms 120000 \
  --billed-gas 1500

iroha app kaigi end --domain kaigi.universal --call-name daily
```

Используйте `--room-policy public` для комнат, которые реле могут открывать без билетов зрителей, или `--room-policy authenticated`, когда для выхода требуется аутентификация зрителя. Используйте `--privacy-mode zk-roster-v1` только после сеть имеет настроенные ключи проверки списка участников и использования Kaigi; в противном случае присоединения, выходы и приватные записи использования не пройдут детерминированную проверку.

### JavaScript Интеграция {#javascript-integration}

Текущий [Iroha JavaScript демо](https://github.com/soramitsu/iroha-demo-javascript) реализует прозрачный, аутентифицированный профиль встречи один на один. Он не раскрывает протокол `zk-roster-v1` поток доказательства. Его рендерер создает WebRTC предложения и ответы, в то время как привилегированный мост использует локальный [`@iroha/iroha-js`](https://github.com/hyperledger-iroha/iroha/tree/0010c5a70039eac101a4846499ba9ceaf43eb65c/javascript/iroha_js) оформите заказ для получения предложения, подписи, отправки и ожидания окончательного варианта Kaigi транзакции.

Смотрите [Встроить Kaigi в приложение JavaScript](/ru/guide/tutorials/kaigi.md) для точной аутентификации маршрута, формата приглашения, границ моста и текущих команд тестового демо.

## Статус и Метрики {#status-and-metrics}

Эндпоинты статуса и метрик API — это первые вещи, которые нужно подключить к панелям мониторинга:

- `/status` раскрывает поля верхнего уровня для сетевых узлов, блока, очереди и консенсуса
- `/metrics` показывает счетчики, индикаторы и гистограммы Prometheus

На узлах с поддержкой Nexus вывод статуса также включает разделы, учитывающие линию выполнения и пространство данных. Когда `nexus.enabled = false`, эти разделы опускаются.

## JSON против Norito {#json-vs-norito}

Несколько конечных точек оператора API по умолчанию возвращают Norito. Когда конечная точка API поддерживает JSON, отправьте:

```http
Accept: application/json
```

Это особенно полезно для:

- `/v1/sumeragi/status`
- `/v1/sumeragi/qc`

Когда конечная точка API принимает или возвращает типизированный Norito напрямую, используйте `application/x-norito` в качестве типа содержимого или предпочтительного значения `Accept`. Дополнительные сведения о транспортировке см. в [Norito](/ru/reference/norito.md#torii-and-norito-rpc).

## Телеметрические профили {#telemetry-profiles}

API видимость конечной точки зависит от настройки `telemetry.profile` узла. Текущая конфигурация отображает пять уровней профиля:

|Профиль| `/status` | `/metrics` |Маршруты разработчика|
| ----------- | --------- | ---------- | ---------------- |
| `disabled`  |нет|нет|нет|
| `operator`  |да|нет|нет|
| `extended`  |да|да|нет|
| `developer` |да|нет|да|
|`full`      |да|да|да|

## CLI Ярлыки {#cli-shortcuts}

`iroha` CLI уже оборачивает многие из этих API конечных точек:

```bash
export IROHA_OPERATOR_KEY_FILE=/run/secrets/iroha/operator.key

iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  --output-format text ops sumeragi status
iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  --output-format text ops sumeragi diagnostics
iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  ops sumeragi params
iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  --output-format text ops sumeragi evidence count
```
