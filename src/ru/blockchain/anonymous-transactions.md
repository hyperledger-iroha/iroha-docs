# Анонимные транзакции {#anonymous-transactions}

Анонимные транзакции в Iroha создаются из конфиденциальных операций с активами. Вместо того чтобы записывать публичные переводы с одного счета на другой с открытыми суммами, кошелек перемещает стоимость в защищенный распределенный реестр блокчейна, а затем расходует непрозрачные ноты с доказательствами с нулевым разглашением.

Публичный распределённый реестр блокчейна всё равно фиксирует факт конфиденциальной операции. Он записывает криптографические обязательства, нулификаторы, хеши доказательств и события, но не раскрывает владельца ноты, получателя или сумму при защищённом переводе. Обычный контейнер транзакции всё ещё может раскрывать аккаунт отправителя, поэтому «анонимный» здесь означает анонимное перемещение активов, а не автоматическую анонимность на уровне сети или аккаунта.

## Строительные блоки {#building-blocks}

|Концепция|распределённое представление реестра блокчейна|
| ------------------ | ------------------------------------------------------------------------------------------------------------------ |
| Защищённая нота | Приватная запись кошелька, содержащая актив, сумму, сведения о владельце и случайное значение. |
| Криптографическое обязательство | 32-байтовое публичное значение, которое связывает ноту, не раскрывая её поля. |
| Нулификатор | 32-байтовое публичное значение, выводимое при расходовании ноты. Iroha отклоняет повторный нулификатор, предотвращая двойное расходование. |
| Корень Меркле | Недавний корень дерева обязательств актива. Доказательство использует его, чтобы подтвердить существование расходуемой ноты. |
| Вложение доказательства | Объект `ProofAttachment`, содержащий байты доказательства и ссылку на ключ проверки либо встроенный ключ проверки. |
| Конфиденциальное событие | Событие распределённого реестра, например `ConfidentialEvent::Shielded`, `Transferred` или `Unshielded`. |

Основные инструкции следующие:

- `RegisterZkAsset`: регистрирует актив как совместимый с ZK и связывает проверочные ключи для передачи, защиты и снятия защиты.
- `Shield`: списывает открытый баланс и добавляет зашифрованное обязательство ноты.
- `ZkTransfer`: расходует защищённые ноты и создаёт новые защищённые ноты с криптографическими обязательствами.
- `Unshield`: расходует защищённые ноты и зачисляет средства на баланс публичного аккаунта.
- `ScheduleConfidentialPolicyTransition` и `CancelConfidentialPolicyTransition`: изменить политику конфиденциальности актива через управление.

Определение актива также несет [`AssetConfidentialPolicy`](/ru/reference/data-model-schema.md). Режим политики управляет тем, какие потоки являются допустимыми:

|Режим|Значение|
| ----------------- | ---------------------------------------------------------------- |
| `TransparentOnly` |Принимаются только обычные публичные балансы и переводы.|
| `Convertible`     |Пользователи могут перемещать средства между публичными балансами и защищёнными записями.|
| `ShieldedOnly`    |Выпуск и передача активов должны оставаться в защищённом распределённом реестре блокчейна.|

## Как их использовать {#how-to-use-them}

1. Включите конфиденциальную поддержку на узлах валидаторов. Валидаторы должны согласовать бэкенд проверяющего, активные проверяющие ключи, идентификаторы параметров Poseidon/Pedersen и версию правил конфиденциальности. Узлы отклоняют сетевых партнеров или блоки с несовпадающими криптографическими дайджестами функций конфиденциальности.
2. Опубликуйте или зарегистрируйте проверочные ключи и наборы параметров, используемые схемами. Кошельки и операторы должны ссылаться на ключи как `VerifyingKeyId`, например `halo2/ipa:vk_transfer`.
3. Зарегистрируйте актив как совместимый с ZK с `RegisterZkAsset`, или проведите переход политики с `TransparentOnly` на `Convertible` или `ShieldedOnly`.
4. Защитите средства из открытого баланса с помощью `Shield`. Перед отправкой транзакции кошелёк создаёт криптографическое обязательство ноты и зашифрованную полезную нагрузку для получателя.
5. Переводите конфиденциально с помощью `ZkTransfer`. Кошелек создает доказательство того, что он владеет входными нотами, что входные и выходные значения сбалансированы, и что каждая потраченная нота закреплена в недавно созданном дереве значений криптографических обязательств.
6. Снимайте защиту только тогда, когда это разрешено политикой актива. `Unshield` раскрывает публичную сумму и аккаунт получателя, расходует приватный нулификатор ноты и может создавать приватные выходы сдачи.
7. Проводите аудит, читая конфиденциальные события, записи доказательств, состояние нулификаторов и записи анонимного эскроу через типизированные запросы и эндпоинты Torii API.

## CLI Примеры {#cli-examples}

Команды ZK CLI предназначены для операторских и тестовых потоков. Производственные кошельки должны генерировать криптографические значения обязательств, зашифрованные полезные данные и доказательства с помощью библиотеки кошелька/доказателя перед отправкой полученных инструкций.

Зарегистрируйте актив с поддержкой гибридного ZK:

```bash
iroha app zk register-asset \
  --asset <asset-definition-id> \
  --allow-shield true \
  --allow-unshield true \
  --vk-transfer halo2/ipa:vk_transfer \
  --vk-unshield halo2/ipa:vk_unshield \
  --vk-shield halo2/ipa:vk_shield
```

Создайте версионированный зашифрованный контейнер полезной нагрузки для защищённой ноты:

```bash
iroha app zk envelope \
  --ephemeral-pubkey 0101010101010101010101010101010101010101010101010101010101010101 \
  --nonce-hex 020202020202020202020202020202020202020202020202 \
  --ciphertext-b64 AQIDBA== \
  --print-json \
  --output note-envelope.bin
```

CLI подготавливает политику активов, проверяющие ссылки и контейнер зашифрованных заметок. Он не раскрывает подкоманды транзакции `shield` или `unshield`. Создавайте эти инструкции с помощью SDK и отправляйте их как обычную подписанную транзакцию с оценкой комиссии.

Несколько защищённое прикрепление имеет следующую форму:

```bash
cat > unshield-proof.json <<'JSON'
{
  "backend": "halo2/ipa",
  "proof_b64": "BASE64_PROOF_BYTES",
  "vk_ref": {
    "backend": "halo2/ipa",
    "name": "vk_unshield"
  }
}
JSON
```

## SDK Пример {#sdk-example}

Точные байты доказательства поступают от настроенного бэкенда доказательств. Полезная нагрузка транзакции требует только публичных входных данных и вложения доказательства:

```rust
use iroha_data_model::{
    isi::zk::{Unshield, ZkTransfer},
    prelude::{AccountId, AssetDefinitionId, InstructionBox},
    proof::{ProofAttachment, ProofBox, VerifyingKeyId},
};

fn transfer_instruction(
    asset: AssetDefinitionId,
    input_nullifier: [u8; 32],
    output_commitment: [u8; 32],
    anchor_root: [u8; 32],
    proof_bytes: Vec<u8>,
) -> InstructionBox {
    let backend = "halo2/ipa".into();
    let proof = ProofBox::new(backend, proof_bytes);
    let vk = VerifyingKeyId::new("halo2/ipa", "vk_transfer");
    let attachment = ProofAttachment::new_ref("halo2/ipa".into(), proof, vk);

    ZkTransfer::new(
        asset,
        vec![input_nullifier],
        vec![output_commitment],
        attachment,
        Some(anchor_root),
    )
    .into()
}

fn unshield_instruction(
    asset: AssetDefinitionId,
    recipient: AccountId,
    amount: u128,
    input_nullifier: [u8; 32],
    anchor_root: [u8; 32],
    proof_bytes: Vec<u8>,
) -> InstructionBox {
    let backend = "halo2/ipa".into();
    let proof = ProofBox::new(backend, proof_bytes);
    let vk = VerifyingKeyId::new("halo2/ipa", "vk_unshield");
    let attachment = ProofAttachment::new_ref("halo2/ipa".into(), proof, vk);

    Unshield::new(
        asset,
        recipient,
        amount,
        vec![input_nullifier],
        attachment,
        Some(anchor_root),
    )
    .into()
}
```

## Анонимный эскроу для активов {#anonymous-asset-escrow}

Анонимный эскроу-актив использует ту же защищённую систему перевода для эскроу-средств. Стороны и состояние эскроу всё ещё записываются в запись эскроу, но финансирование, выпуск, отмена, и разрешение финансовых переводов частей использует защищённые нулификаторы и значения криптографических обязательств выхода.

Для подробного поведения и примеров эскроу ISI см. [Эскроу для родных активов](/ru/blockchain/escrow.md#anonymous-escrow).

Жизненный цикл:

1. `OpenAnonymousAssetEscrow` расходует защищённые финансовые записи и создаёт одно криптографическое обязательство эскроу.
2. `AcceptAnonymousAssetEscrow` записывает покупателя.
3. `MarkAnonymousEscrowPaymentSent` фиксирует, что покупатель отправил платеж вне цепочки.
4. `ReleaseAnonymousAssetEscrow` расходует значение криптографической привязки условного депонирования на значения криптографической привязки выхода покупателя.
5. `CancelAnonymousAssetEscrow` возвращает значение криптографического обязательства условного депонирования обратно на выходные криптографические обязательства продавца, когда оплата не была отмечена.
6. `OpenAnonymousEscrowDispute` и `ResolveAnonymousEscrowDispute` обрабатывают спорные эскроу с использованием криптографических хэшей доказательств и разделения, контролируемого разрешающей стороной.

Используйте анонимные запросы эскроу, указанные в [Запросы](/ru/reference/queries.md#escrow-and-proof-records), чтобы проверять записи и статусы эскроу.

## Математика {#math}

Ниже приведённая нотация описывает поток конфиденциальных активов. Реализации используют активную схему и идентификаторы параметров из политики активов и реестра проверяющих, поэтому клиенты должны рассматривать значения криптографических обязательств, нулификаторов и байтов доказательства как непрозрачные выходные данные кошелька/доказывающей стороны.

Защищённую ноту можно описать так:

$$
n = (\mathsf{asset}, \mathsf{amount}, \mathsf{owner}, \rho)
$$

где `owner` выводится из материала просмотра или расходования получателя, а `rho` — случайное значение ноты.

Криптографическое значение обязательства ноты является скрывающим криптографическим значением обязательства:

$$
C = \mathsf{Commit}(\mathsf{asset}, \mathsf{amount}, \mathsf{owner}, \rho)
$$

Для текущих конфиденциальных схем передачи публичные входные данные включают значения криптографических обязательств нот, нулификаторы, корень Меркле, метку актива и метку цепочки. Схема обеспечивает соблюдение отношения значения криптографического обязательства следующей формы:

$$
C = H_c(\mathsf{amount}, \rho, \mathsf{owner\_tag}, \mathsf{asset\_tag})
$$

Когда нота расходуется, кошелёк выводит нулификатор:

$$
N = H_n(\mathsf{spend\_key}, \rho, \mathsf{asset\_tag}, \mathsf{chain\_tag})
$$

`N` является публичным. Он не раскрывает ноту, но остаётся стабильным для этой ноты и цепочки, поэтому Iroha может отклонить повторное расходование с тем же нулификатором.

Дерево криптографических значений обязательств доказывает существование записи. Если кошелек тратит криптографическое значение обязательства `C_i`, доказательство включает приватный путь Меркл от `C_i` до недавно созданного публичного корня:

$$
\mathsf{MerkleRoot}(C_i, \mathsf{path}) = R
$$

Для перевода с защищённого на защищённый доказательство также обеспечивает сохранение значения:

$$
\sum \mathsf{inputs} = \sum \mathsf{outputs}
$$

Для некрытого суммы публичной включены:

$$
\sum \mathsf{inputs} = \mathsf{public\_amount} + \sum \mathsf{private\_change}
$$

Представленное доказательство можно резюмировать следующим образом:

$$
\mathsf{Verify}(\mathsf{vk}, \mathsf{public\_inputs}, \pi) = \mathsf{true}
$$

где `public_inputs` являются значениями криптографического обязательства, нулификаторами, корнем, тегом актива, тегом цепочки и любой публичной незащищённой суммой. Свидетель содержит суммы заметок, случайные значения, расходные материалы и пути Меркле. Валидаторы проверяют доказательство, а затем изменяют состояние распределённого реестра блокчейна, добавляя выходные значения криптографического обязательства и помечая входные нулификаторы как использованные.

## Что такое общественное {#what-is-public}

Анонимные транзакции не делают каждый наблюдаемый факт приватным. Следующие данные всё ещё могут быть публичными:

- криптографический хэш транзакции, высота блока и порядок
- основной субъект авторизации отправляемой транзакции, если только приложение не использует приватную точку входа или шаблон ретранслятора
- используемое определение актива
- аннулирующие значения и выходные криптографические обязательства
- доказательство криптографических хешей, ссылки на проверочные ключи и криптографические хеши необязательных контейнеров данных
- публичная сумма и счет получателя для `Unshield`
- анонимный эскроу-продавец, покупатель, статус, временные метки и криптографические хэши доказательств

Разрабатывайте приложения так, чтобы эти общедоступные метаданные не раскрывали деловые отношения, которые вы пытаетесь защитить.
