# Транзакции {#transactions}

Транзакция — это подписанный запрос на выполнение работы в блокчейне. Исполняемая нагрузка может быть упорядоченной последовательностью [инструкции](./instructions.md), техническим вызовом контракта, IVM байткодом или доказанным IVM исполнением. См. [Умные контракты](./smart-contracts.md) для текущей модели выполнения контрактов.

Транзакции выполняют работу, изменяющую состояние или требующую выполнения. Только для чтения используется проверка с помощью подписанных запросов или публичных конечных точек для чтения API и не создаёт транзакцию.

Транзакция, принятная в финализированный блок, сохраняется вместе с результатом её выполнения, включая отказ в исполнении. Запросы, отклонённые до принятия в блок, такие как недопустимый контейнер данных или транзакция, отвергнутая очередью, не сохраняются в блоке.

Для перемещения активов с сохранением конфиденциальности см. [Анонимные транзакции](./anonymous-transactions.md). Анонимные транзакции используют защищённые активные ноты, криптографические значения обязательств, нулификаторы и доказательства с нулевым разглашением вместо изменения балансов между публичными аккаунтами.

Для доказательства воздействия выбранного прозрачного выполнения см. [FastPQ](./fastpq.md). FastPQ использует свидетелей выполнения после обычного исполнения транзакции и создаёт детерминированные пакеты доказательств для поддерживаемых переходов состояния.

## Запустите этот рабочий процесс на Taira {#try-it-on-taira}

Используйте маршруты обозревателя, чтобы проверить последние публичные блоки Taira и статусы транзакций без учетной записи для подписи:

```bash
curl -fsS 'https://taira.sora.org/v1/explorer/blocks?page=1&per_page=3' \
  | jq '{pagination, blocks: [.items[] | {height, hash, transactions_total, transactions_rejected}]}'

curl -fsS 'https://taira.sora.org/v1/explorer/transactions?page=1&per_page=5' \
  | jq '{pagination, txs: [.items[] | {hash, block, status, executable}]}'
```

Чтобы отследить транзакцию, которую ваше приложение отправило ранее, скопируйте `hash` из списка и проверьте маршрут деталей в обозревателе:

```bash
TX_HASH='<transaction-hash>'

curl -fsS "https://taira.sora.org/v1/explorer/transactions/$TX_HASH" \
  | jq '{hash, block, status, authority, executable}'
```

Это все еще только для чтения. Для отправки транзакции требуется подписанный контейнер данных Norito, правильный идентификатор цепочки, метаданные комиссии и аккаунт Taira, финансируемый тестовой сетью.

Для примеров с оплатой на Taira сохраните помощника службы финансирования тестовой сети с [Получить тестовую сеть XOR на Taira](/ru/get-started/sora-nexus-dataspaces.md#_4-get-testnet-xor-on-taira) как `taira_faucet_claim.py`, затем сначала профинансируйте криптографического подписанта через публичную службу финансирования тестовой сети:

```bash
export TAIRA_ACCOUNT_ID='<TAIRA_I105_ACCOUNT_ID>'
export TAIRA_FEE_ASSET=6TEAJqbb8oEPmLncoNiMRbLEK6tw

curl -fsS https://taira.sora.org/v1/accounts/faucet/puzzle | jq .
python3 taira_faucet_claim.py "$TAIRA_ACCOUNT_ID"

iroha --config ./taira.client.toml ledger asset get \
  --definition "$TAIRA_FEE_ASSET" \
  --account "$TAIRA_ACCOUNT_ID"
```

Если головоломка сервиса финансирования тестовой сети или маршрут запроса возвращает `502`, подождите и повторите попытку перед отладкой самой транзакции.

Затем прикрепите метаданные платёжного актива Taira при отправке транзакции:

```bash
printf '{"gas_asset_id":"%s"}\n' "$TAIRA_FEE_ASSET" > taira.tx-metadata.json

iroha --config ./taira.client.toml \
  --metadata ./taira.tx-metadata.json \
  ledger transaction ping --msg "faucet-funded taira transaction"
```

## Офлайн-транзакции {#offline-transactions}

Iroha имеет два рабочих процесса для офлайн-транзакций:

- Офлайн-подписание создает обычную подписанную транзакцию, пока устройство для подписи отключено. Транзакция не обрабатывается до тех пор, пока онлайн-клиент не отправит подписанный контейнер данных в Torii, поэтому ей по-прежнему необходимы правильный идентификатор цепочки, полномочия, разрешения, комиссии, и продолжительность транзакции.
- Kagemusha пополняет кошелёк офлайн-наличными, пока тот находится в сети, поддерживает передачу от кошелька к кошельку, когда оба устройства не в сети, и погашает полученное состояние ноты после возвращения получателя в сеть.

Torii раскрывает полный жизненный цикл Kagemusha под `/v1/offline/*`:

|Метод и конечная точка API|Цель|
| --- | --- |
| `GET /v1/offline/readiness` |Оцените готовность Кагемуши для одного `asset_definition_id`|
| `POST /v1/offline/receiver-lineage` |Разрешить проверку происхождения активной регистрации с доказательством для подписанного запроса получателя|
| `POST /v1/offline/top-up` |Отправить подписанную операцию пополнения с онлайн на офлайн|
| `POST /v1/offline/redeem` |Отправить подписанную офлайн-операцию выкупа|
| `GET /v1/offline/operations/{operation_id}` |Прочитайте канонический статус пополнения или погашения|

Проверьте готовность актива перед началом оффлайн-операции:

```bash
curl -fsS --get https://taira.sora.org/v1/offline/readiness \
  --data-urlencode 'asset_definition_id=<canonical_asset_definition_id>' \
  | jq '{ready, blockers, artifact_set}'
```

Готовность связывает кошелек с активным мостом ABI 21 и аутентифицированным V4 набором артефактов. Запросы на происхождение, пополнение и погашение используют типизированные `application/x-norito` архивы. Пополнение и возврат выкупа `202 Accepted` с заголовком `Location`, указывающим на ресурс операции; встроенный ненулевой идентификатор операции предоставляет ключ идемпотентности.

Типичный процесс выглядит следующим образом:

1. Проверьте готовность и остановитесь, если `ready` ложен или применяются любые блокирующие факторы.
2. Используйте типизированный кошелёк Swift или JVM, чтобы создать канонический архив пополнения и отправить его. Сохраняйте состояние входной ноты и ID операции, пока операция не достигнет окончательного состояния цепочки.
3. При необходимости установите происхождение регистрации получателя, локально создавайте и проверяйте каждую одноранговую передачу и сохраняйте зашифрованное состояние ноты до подтверждения передачи.
4. Когда получатель в сети, создайте канонический архив выкупа, отправьте его и опрашивайте его ресурс операции до завершения.

Распределённый реестр не может обнаружить конфликтующую офлайн-передачу, пока состояние ноты не вернётся через сетевой этап жизненного цикла. Поэтому политика кошелька и оператора должна обеспечивать ограничения суммы, срок действия, список принимаемых эмитентов, надёжное локальное хранение и интервалы сверки.

Вот пример создания новой транзакции с инструкцией `Grant`. В этой транзакции Mouse предоставляет Alice указанную роль (`role_id`). Проверьте [полный пример](./permissions.md#register-a-new-role).

```rust
let grant_role = Grant::account_role(role_id, alice_id);
let grant_role_tx = TransactionBuilder::new(chain_id, mouse_id)
    .with_instructions([grant_role])
    .sign(mouse_private_key);
```
