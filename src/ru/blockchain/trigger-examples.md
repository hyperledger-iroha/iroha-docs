# Пример срабатывания события {#event-trigger-example}

Этот пример использует канонические идентификаторы аккаунтов без домена и ожидаемые определения активов в модели данных Iroha 3.

Предположим, что сеть имеет:

- канонический аккаунт, контролируемый ключом Alice
- канонический аккаунт, контролируемый ключом Mad Hatter
- определение актива с прогнозом как `tea` по `wonderland.universal`
- баланс этого актива на каждом счёте

Цель состоит в том, чтобы зарегистрировать триггер, который отслеживает баланс чая у Alice и выполняет перевод с аккаунта Mad Hatter, когда возникает соответствующее событие данных.

## 1. Подготовьте счета и активы {#_1-prepare-accounts-and-assets}

Сначала зарегистрируйте участвующие аккаунты и определение активов. В текущем Iroha идентификаторы аккаунтов поступают от контроллеров аккаунтов, тогда как проецируемые домены используют форму `domain.dataspace`:

```text
domain: wonderland.universal
asset definition projection: tea in wonderland.universal
holder accounts: AccountId(controller=alice_key), AccountId(controller=mad_hatter_key)
```

Определение актива по-прежнему имеет канонический непрозрачный адрес. Сохраните или запросите этот адрес после регистрации и используйте его в действии триггера.

## 2. Выберите принципиальный элемент авторизации триггера {#_2-choose-the-trigger-authority}

Установите техническую учетную запись триггера на выделенную учетную запись, если это возможно. Выделенная учетная запись ясно показывает, какие разрешения необходимы для выполнения триггера, и предотвращает привязку триггера к персональному ключу подписи оператора.

Технический аккаунт должен уже существовать и должен иметь разрешение на отправку инструкций в исполняемом файле триггера.

## 3. Определите исполняемый файл {#_3-define-the-executable}

Исполняемый файл — это последовательность инструкций, которую триггер отправляет, когда фильтр событий совпадает. В этом примере он содержит одну передачу:

```text
Transfer(
  source = AssetId(tea_definition, mad_hatter_account),
  value = Numeric(1),
  destination = AssetId(tea_definition, alice_account)
)
```

Используйте текущие типизированные билдеры SDK для финального полезного содержимого транзакции. Избегайте жесткого кодирования старых текстовых идентификаторов в коде триггера; разбирайте или запрашивайте канонические идентификаторы перед созданием исполняемого кода.

## 4. Определите фильтр событий {#_4-define-the-event-filter}

Используйте фильтр data-event, который сужает события до объекта, который вас интересует:

```text
EventFilterBox::Data(
  DataEventFilter for asset changes involving
  AssetId(tea_definition, alice_account)
)
```

Держите фильтры максимально специфичными. Фильтр `AcceptAll` полезен для отладки, но он заставляет каждое совпадающее событие нести затраты на оценку триггера.

## 5. Зарегистрируйте триггер {#_5-register-the-trigger}

Зарегистрируйте триггер с:

- стойкий `TriggerId`
- последовательность исполняемых инструкций
- `Repeats::Indefinitely` или `Repeats::Exactly(n)`
- технический аккаунт
- фильтр событий
- необязательные метаданные

Сама регистрация триггера является обычной транзакцией, поэтому аккаунту, который регистрирует триггеры, нужны права на регистрацию триггеров. Техническому аккаунту нужны права, требуемые выполняемым триггером.

## Порядок выполнения {#execution-order}

Когда блок выполняется:

1. Сначала выполняются обычные инструкции по транзакциям.
2. Данные события, создаваемые этими инструкциями, собираются.
3. Триггеры, фильтры которых соответствуют этим событиям, запланированы.
4. Эффекты, вызванные триггером, обрабатываются в рабочем процессе программного обеспечения выполнения блока без допуска неограниченного рекурсивного выполнения триггеров.

Если триггер использует `Repeats::Exactly(n)`, зарегистрируйте новый триггер, когда счет исчерпан, и если требуется повторить то же самое поведение.
