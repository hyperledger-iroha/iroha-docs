# Пример вызова событий {#event-trigger-example}

В этом примере используется канонический бездоменный учет IDs и прогнозируемый актив
определения в Iroha 3 модель данных.

Предположим, что сеть имеет:

- канонический отчет, контролируемый ключом Алисы
- Канонический отчет, управляемый ключем безумного шляпщика.
- определение активов, прогнозируемое как `tea` под `wonderland.universal`
- баланс этого актива, находящегося на каждом счете

Цель состоит в том, чтобы зарегистрировать триггер, который наблюдает баланс чая Алисы и
представляет перевод с учетной записи Mad Hatter, когда событие совпадающих данных
выделяется.

## 1. Подготовка счетов и активов {#_1-prepare-accounts-and-assets}

Регистрация учетных записей и определения активов.
текущий Iroha, учетный счет IDs приходят от контролеров счетов, в то время как прогнозируется
использование доменов `domain.dataspace` Форма:

```text
domain: wonderland.universal
asset definition projection: tea in wonderland.universal
holder accounts: AccountId(controller=alice_key), AccountId(controller=mad_hatter_key)
```

Определение актива все еще имеет канонический непрозрачный адрес.
адрес после регистрации и использовать его в процессе запуска.

## 2. Выберите авторитет запуска {#_2-choose-the-trigger-authority}

Если это возможно, установить технический счет запуска на специальный счет.
Dedicated account ясно указывает, какие разрешения требуются для запуска
выполнение и избегает соединения триггера с личным подписью оператора
Ключ.

Технический учет должен уже существовать и иметь разрешение на представление
инструкции в запускающем устройстве.

## 3. Определить исполняемое {#_3-define-the-executable}

Исполняемая последовательность инструкций , которую подает триггер при выполнении события
Для этого примера он содержит одну передачу:

```text
Transfer(
  source = AssetId(tea_definition, mad_hatter_account),
  value = Numeric(1),
  destination = AssetId(tea_definition, alice_account)
)
```

Используйте SDK"Сегодняшние строящиеся для последней транзакции.
Старый текстовый код IDs в коде запуска; анализ или запрос канонический IDs
до создания исполняемого.

## 4. Определить фильтр событий {#_4-define-the-event-filter}

Используйте фильтр событий данных , который сужает события на объект , о котором вы заботитесь:

```text
EventFilterBox::Data(
  DataEventFilter for asset changes involving
  AssetId(tea_definition, alice_account)
)
```

Сохраняйте фильтры так же конкретными, как и практичными. `AcceptAll` фильтр полезен для
Дебгугирование, но это заставляет каждое совпадение платить стоимость запуска
оценка.

## 5. Зарегистрируйте спусковую установку {#_5-register-the-trigger}

Зарегистрируйте триггер:

- Ставка `TriggerId`
- последовательность выполняемой инструкции
- `Repeats::Indefinitely` или `Repeats::Exactly(n)`
- технический отчет
- фильтр событий
- необязательные метаданные

Регистрация триггера сама по себе является обычной транзакцией, поэтому регистрация
Учебное расчетное средство требует разрешения на регистрацию триггеров.
разрешения, необходимые для выполнения аккумулятора.

## Приказ исполнения {#execution-order}

При выполнении блока:

1. Обычные инструкции о транзакциях работают первыми.
2. Собираются данные о событиях, вызванных указанными инструкциями.
3. Запускаются триггеры, фильтры которых совпадают с этими мероприятиями.
4. Эффекты, вызванные триггером, обрабатываются в трубопроводе выполнения блока без
   позволяет осуществлять неограниченный рекурсивный запуск.

Если выключатель использует `Repeats::Exactly(n)`, зарегистрировать новую зарядку, когда подсчет
Вы исчерпаны, и вам нужно снова вести себя так же.
