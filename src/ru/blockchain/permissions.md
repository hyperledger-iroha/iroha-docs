# Разрешения {#permissions}

Аккаунтам необходимы токены разрешений для различных действий в блокчейне, например, для выпуска или уничтожения активов.

Существует разница между публичным и частным блокчейном с точки зрения прав доступа, предоставленных пользователям. В публичном блокчейне большинство аккаунтов имеют одинаковый набор прав. В частной блокчейн-сети предполагается, что большинство учетных записей не могут выполнять действия за пределами полномочий, предоставленных им, если им явно не предоставлено соответствующее разрешение.

Наличие разрешения на что-либо означает, что аккаунт имеет соответствующее `Permission`. Разрешения могут предоставляться непосредственно или через [`Role`](#permission-groups-roles), который группирует набор разрешений. Разрешения предоставляются с помощью `Grant` инструкция. Разрешения и роли не истекают; удалите их с помощью `Revoke` инструкция.

## Токены разрешений {#permission-tokens}

Токены разрешений — это типизированные объекты, определяемые активным исполнителем. Некоторые токены являются глобальными, такие как `CanManagePeers`, а другие ограничены конкретным распределённым объектом реестра блокчейна, таким как аккаунт, актив, определение актива, домен, NFT, роль или триггер.

Вот несколько примеров параметров, используемых для различных токенов разрешений:

- Токен, который предоставляет разрешение на изменение метаданных для конкретного аккаунта, содержит поле `account`:

  ```json
  {
    "account": "<AccountId>"
  }
  ```

- Токен, предоставляющий разрешение на передачу активов для конкретного определения актива, содержит поле `asset_definition`:

  ```json
  {
    "asset_definition": "<AssetDefinitionId>"
  }
  ```

- Глобальный токен, такой как `CanManagePeers`, не имеет полей:

  ```json
  {}
  ```

## Группы разрешений (Роли) {#permission-groups-roles}

Набор разрешений называется ролью. Подобно токенам разрешений, роли могут быть предоставлены с помощью инструкции `Grant` и отозваны с помощью инструкции `Revoke`.

Прежде чем предоставить учетной записи роль, роль должна быть сначала зарегистрирована.

Роли полезны, когда нескольким учетным записям необходимо предоставить один и тот же набор разрешений. Зарегистрируйте роль один раз, предоставьте роли разрешения, а затем предоставляйте или отзывайте роль для отдельных учетных записей.

### Зарегистрировать новую роль {#register-a-new-role}

Давайте зарегистрируем новую роль, которая, при предоставлении, позволит другой учетной записи получить доступ к [метаданные](/ru/blockchain/metadata.md) в учетной записи Mouse:

```rust
let role_id = RoleId::from_str("ACCESS_TO_MOUSE_METADATA")?;
let role = iroha_data_model::role::Role::new(role_id.clone(), mouse_id.clone())
    .add_permission(CanModifyAccountMetadata {
        account: mouse_id.clone(),
    });
let register_role = Register::role(role);
```

### Предоставить роль {#grant-a-role}

После того как роль зарегистрирована, Mouse может предоставить её Alice:

```rust
let grant_role = Grant::account_role(role_id, alice_id);
let grant_role_tx = TransactionBuilder::new(chain_id, mouse_id)
    .with_instructions([grant_role])
    .sign(mouse_private_key);
```

## Проверки разрешений {#permission-validators}

Разрешения существуют для того, чтобы только учетные записи с требуемым токеном разрешений могли выполнять защищенное действие. Исполнитель по умолчанию проверяет разрешения во время выполнения инструкций, запросов и выражений.

Поверхность валидатора по умолчанию сгруппирована по зонам распределённого реестра блокчейна:

- управление сетевыми узлами
- домены и аккаунты
- активы, NFTs и эскроу
- триггеры
- роли и разрешения
- исполнитель/время выполнения, доказательства, мосты и модули SORA/Nexus

Точный список токенов поддерживается источником в [Справочник по токенам разрешений](/ru/reference/permissions.md).

### программные средства выполнения Проверки {#runtime-validators}

Проверки разрешений выполняются активным исполнителем. Исполнитель по умолчанию предоставляет встроенные валидаторы разрешений и определения токенов, и сеть может изменить политику, обновив используемого исполнителя.

Валидаторы возвращают вердикт валидации. Валидатор может разрешить операцию, отклонить её с указанием причины или пропустить, если операция выходит за пределы области действия данного валидатора. Выбранный судья объединяет эти вердикты, чтобы определить, может ли инструкция, запрос или выражение быть выполнено.
