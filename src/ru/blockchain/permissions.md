# Разрешения {#permissions}

Счеты нуждаются в знаках разрешения для различных действий на блокчейне, например.
для заготовки или сжигания активов.

Существует разница между публичным и частным блокчейн в том, что касается
В публичной блокчейне большинство аккаунтов имеют
В частном блокчейн большинство аккаунтов
считают, что они не могут делать ничего за пределами предоставленных им полномочий
если только соответствующее разрешение не было прямо предоставлено.

Разрешение на что-то означает, что счет имеет
соответствующие `Permission`. Разрешения могут быть предоставлены непосредственно или через
[`Role`](#permission-groups-roles), которые объединяют набор разрешений.
Разрешения выдаются с `Grant` Разрешения и роли
не истекают срока действия; удалить их с `Revoke` - Инструкция.

## Токены разрешения {#permission-tokens}

Токены разрешения - это типные объекты, определенные активным исполнителем.
токены являются глобальными, например: `CanManagePeers`, и другие направлены на
конкретный объект бухгалтерского учета, такой как счет, актив, определение активов, домен;
NFT, роль или триггер.

Вот несколько примеров параметров, используемых для различных токенов разрешений:

- Токен , который дает разрешение на изменение метаданных для конкретной учетной записи
  несет `account` поле:

  ```json
  {
    "account": "<AccountId>"
  }
  ```

- Токен, предоставляющий разрешение на передачу активов для конкретного актива
  определение имеет значение `asset_definition` поле:

  ```json
  {
    "asset_definition": "<AssetDefinitionId>"
  }
  ```

- Глобальный токен, такой как `CanManagePeers` не имеет полей:

  ```json
  {}
  ```

## Группы разрешений (роли) {#permission-groups-roles}

Набор разрешений называется **роль**. Точно так же, как и разрешение на токены.
роль может быть предоставлена с использованием `Grant` указания и отзывы с использованием
`Revoke` - Инструкция.

Перед тем, как предоставлять роль счету, должна быть зарегистрирована роль.

Роли полезны , когда несколько счетов должны получить одно и то же разрешение
Зарегистрировать роль один раз, предоставить разрешения на роль, а затем предоставить или
отменить роль отдельных счетов.

### Зарегистрируйте новую роль {#register-a-new-role}

Давайте зарегистрируем новую роль, которая, когда будет предоставлена, позволит другой счет
доступ к [метаданные](/ru/blockchain/metadata.md) В отчете мыши:

```rust
let role_id = RoleId::from_str("ACCESS_TO_MOUSE_METADATA")?;
let role = iroha_data_model::role::Role::new(role_id.clone(), mouse_id.clone())
    .add_permission(CanModifyAccountMetadata {
        account: mouse_id.clone(),
    });
let register_role = Register::role(role);
```

### Подарите роль {#grant-a-role}

После того, как роль будет зарегистрирована, Мыша может предоставить ее Алисе:

```rust
let grant_role = Grant::account_role(role_id, alice_id);
let grant_role_tx = TransactionBuilder::new(chain_id, mouse_id)
    .with_instructions([grant_role])
    .sign(mouse_private_key);
```

## Валидаторы разрешений {#permission-validators}

Разрешения существуют таким образом , что только учетные записи с необходимым токеном разрешений
может выполнять защищенное действие. По умолчанию исполнитель проверяет разрешения
во время выполнения инструкций, запросов и выражений.

Поверхность проверщика по умолчанию группируется по площади реестра:

- Управление сверстниками
- домены и учетные записи
- активы, NFTs, и сбережения
- триггеры
- роли и разрешения
- исполнитель/время работы, доказательства, мосты и SORA/Nexus модули

Точный список символов поддерживается источником в
[Ссылка на Tokens разрешения](/ru/reference/permissions.md).

### Валидаторы времени запуска {#runtime-validators}

Проверка разрешений осуществляется активным исполнителем.
Исполнитель предоставляет встроенные валидаторы разрешений и определения токенов,
и сеть может изменить политику путем обновления исполнителя, который она использует.

Валидаторы возвращают **вердикт о подтверждении**. Валидатор может позволить
операции, отрицать ее по уважительной причине или пропустить ее, если операция находится вне
Выбранный судья объединяет эти приговоры в
принимать решение о том, может ли продолжать действие инструкции, запроса или выражения.
