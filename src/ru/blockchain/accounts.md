# Счета {#accounts}

Аккаунт — это принципал авторизации, который может подписывать транзакции и владеть состоянием распределенного реестра блокчейна. В текущей модели данных Iroha 3, `AccountId` является каноническим и не имеет домена: он выведен из контроллера учетной записи и кодируется канонически как [I105](/ru/reference/i105.md). Читаемый человеком контекст домена и пространства данных относится к отдельным связываниям псевдонима учетной записи.

## Структура {#structure}

Зарегистрированный `Account` содержит:

- `id`: канонический `AccountId`
- `metadata`: произвольные метаданные учетной записи
- `label`: необязательный стабильный псевдоним
- `uaid`: необязательный универсальный идентификатор учетной записи, используемый потоками Nexus
- `opaque_ids`: непрозрачные идентификаторы, привязанные к UAID аккаунта

Полезная нагрузка транзакции, используемая для создания аккаунта, — `NewAccount`. Она содержит те же поля идентичности, метаданных, метки, UAID и непрозрачного идентификатора, которые используются зарегистрированным аккаунтом.

`uaid` дополняет канонический `AccountId`; он его не заменяет. Используйте его, когда Nexus сервисам необходим стабильный идентификатор пользователя или организации через пространства данных, регистрация с сохранением конфиденциальности или поиск возможностей сервиса. Время выполнения программного обеспечения поддерживает один к одному индекс UAID-к-аккаунту, требует, чтобы непрозрачные идентификаторы были прикреплены через UAID, и отклоняет дублирующиеся или конфликтующие непрозрачные идентификаторы. См. [FHE и UAID](/ru/blockchain/sora-nexus-services.md#fhe-and-uaid) для потока уровня сервиса Nexus.

## Контролёры счетов {#account-controllers}

Контроллер определяет, как аккаунт авторизует действия. Стандартный клиентский поток использует пару ключей Ed25519, но модель данных также поддерживает более сложные контроллеры, такие как контроллеры с политикой мультиподписей.

Конфигурация клиента хранит основной объект авторизации подписи отдельно от конфигурации сетевого узла:

```toml
[account]
public_key = "ed0120..."
private_key = { digest_function = "ed25519", payload = "..." }
```

См. [конфигурация клиента](/ru/guide/configure/client-configuration.md) и [генерация ключей](/ru/guide/security/generating-cryptographic-keys.md) для текущих форматов ключей.

## Запустите этот рабочий процесс на Taira {#try-it-on-taira}

Перечислите несколько канонических идентификаторов аккаунтов из публичной тестовой сети Taira:

```bash
curl -fsS 'https://taira.sora.org/v1/accounts?limit=5' \
  | jq -r '.items[] | [.id, (.primary_alias // "-")] | @tsv'
```

Чтобы проверить активы счета, скопируйте идентификатор счета из первого технического вызова и закодируйте его в формате URL перед тем, как вставить в путь. Этот фрагмент Python делает это для первого указанного счета:

```bash
python3 - <<'PY'
import json
import urllib.parse
import urllib.request

root = "https://taira.sora.org"
accounts = json.load(urllib.request.urlopen(f"{root}/v1/accounts?limit=1"))["items"]
account_id = accounts[0]["id"]
encoded = urllib.parse.quote(account_id, safe="")
assets = json.load(
    urllib.request.urlopen(f"{root}/v1/accounts/{encoded}/assets?limit=5")
)

print(json.dumps({"account_id": account_id, "assets": assets["items"]}, indent=2))
PY
```

Это публичные чтения. Создание или обновление аккаунта является подписанной транзакцией и требует настройки с финансированием из тестовой сети Taira, описанной в [Подключиться к SORA Nexus Dataspaces](/ru/get-started/sora-nexus-dataspaces.md).

## Регистрация и разрешения {#registration-and-permissions}

Аккаунты регистрируются и аннулируются с использованием общего [`Register` и `Unregister`](/ru/blockchain/instructions.md#un-register) инструкции. Активный программный валидатор времени выполнения решает, кто может создавать учетные записи и какие токены разрешений или роли требуются.

После регистрации аккаунт может:

- подписывать транзакции
- держать активы
- собственные домены
- получать роли и токены разрешений
- сохранять метаданные
- участвовать в процессах псевдонима, переназначения ключа, восстановления и идентификации Nexus, когда эти функции включены

## Устранение проблем с идентификацией {#troubleshooting-identity-issues}

Если транзакция неожиданно отклонена, проверьте, что:

- открытый ключ клиента соответствует закрытому ключу, использованному для подписи
- учетная запись была зарегистрирована в генезисе блокчейна или с помощью завершенной транзакции
- у субъекта авторизации есть разрешения, требуемые инструкцией
- строгие поля аккаунта используют канонический идентификатор аккаунта I105, тогда как читаемые имена определяются через активное связывание псевдонима аккаунта
