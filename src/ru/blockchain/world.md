# Мир {#world}

`World` — это глобальная сущность, которая содержит другие сущности. `World` состоит из:

- Iroha [параметры конфигурации](/ru/guide/configure/client-configuration.md)
- зарегистрированные сетевые узлы
- зарегистрированные домены
- зарегистрирован [триггеры](/ru/blockchain/triggers.md)
- зарегистрирован [роли](/ru/blockchain/permissions.md#permission-groups-roles)
- зарегистрирован [определения токенов разрешений](/ru/blockchain/permissions.md#permission-tokens)
- токены разрешений для всех аккаунтов
- [цепочка валидаторов времени выполнения программного обеспечения](/ru/blockchain/permissions.md#runtime-validators)

Когда домены, сетевые узлы или роли регистрируются или снимаются с регистрации, `World` является целью (анти)регистрации [инструкция](/ru/blockchain/instructions.md).

## Вид мирового состояния (WSV) {#world-state-view-wsv}

Представление состояния мира — это представление текущего состояния блокчейна в памяти. Оно включает `World`, криптографические хэши финализированных блоков, индексы транзакций и сетевых участников, избранных для текущей эпохи. Полные полезные нагрузки блока предоставляются с Kura, а не дублируются как изменяемые данные WSV.

WSV — это состояние, которое запрашивается для чтения и которое изменяется блокировкой выполнения. Оно само по себе не является надежным источником истины. Надежная история хранится в [Kura](#kura-storage). и WSV можно восстановить из блоков Kura или загрузить из снимка данных состояния, а затем догнать, воспроизводя более новые блоки Kura.

### Какие WSV треки {#what-the-wsv-tracks}

WSV шире, чем объект `World`. На практике он содержит:

- `World`: параметры, сетевые узлы, домены, учётные записи, активы, NFTs, роли, разрешения, триггеры, данные исполнителя и другие зарегистрированные объекты модели данных
- финализированные криптографические хэши блоков и последняя финализированная высота
- индексы транзакция-к-блоку, используемые запросами и записями результатов протокола
- текущая и предыдущая топология завершения протокола, используемая консенсусом
- индексы в оперативной памяти, полученные из завершённых блоков, такие как значения криптографических обязательств доступности данных, курсоры записей результатов протокола, намерения закрепления и маркеры проекции запросов
- снимки данных конфигурации времени выполнения программного обеспечения, необходимые для детерминированного выполнения блоков, такие как криптография, управление, рабочий процесс обработки программного обеспечения, контент, расчет финансовых транзакций и настройки Nexus

Запросы обычно получают только для чтения `StateView` над этими структурами. Представление является согласованным снимком данных для выполнения запроса; оно не позволяет прямое изменение WSV.

### Как меняется WSV {#how-the-wsv-changes}

Изменения WSV ставятся в очередь перед их окончательной фиксацией. Выполнение блока создает наложение состояния с областью видимости блока, и каждая принятая транзакция применяет свои инструкции в накладывание, ограниченное транзакцией. Триггеры данных, вызванные этими транзакциями, выполняются в том же контексте блока. Временные триггеры оцениваются после эффектов транзакций для блока.

После того как консенсус завершает блок, сетевой узел сначала помещает финализированный блок в очередь Kura. Если этот шаг постановки в очередь не удается, WSV не продвигается, и цикл консенсуса повторяет попытку или возвращает полезную нагрузку блока в очередь. Когда блок принимается в очередь Kura, Iroha применяет эффекты блока после выполнения, обновляет производные индексы и завершает подготовленные изменения WSV под блокировкой просмотра состояния. Это предотвращает возможность для читателей наблюдать частично завершенный блок.

Критически важное правило консенсуса заключается в том, что узлы сети должны получать одинаковый WSV из одинаковых финализированных блоков. Прямые локальные изменения данных WSV обходят инструкции и приведут к расхождению узлов сети во время проверки или воспроизведения.

### Запуск и повтор {#startup-and-replay}

При запуске Iroha сначала инициализирует Kura и узнаёт сохранённую высоту блока. Затем он пытается загрузить снимок состояния. Если снимок данных недоступен, или если снимок данных отклоняется как восстанавливаемый, Iroha создаёт начальное состояние и воспроизводит завершённые блоки из Kura. Если снимок данных действителен, но отстаёт от Kura, воспроизводится только отсутствующий диапазон высот.

Повторная проверка валидирует каждый сохранённый блок, восстанавливает реестр завершения протокола для этой высоты, применяет эффекты блока к WSV и завершает результирующее состояние. Это означает, что Kura является путем восстановления для WSV, в то время как снимки данных являются оптимизацией, которая позволяет избежать воспроизведения всей цепочки.

## Kura Хранилище {#kura-storage}

Kura является постоянным блочным хранилищем Iroha. Оно хранит подписанные блоки и метаданные восстановления. Оно не хранит вторую изменяемую копию WSV.

Kura хранилище расположено в [`kura.store_dir`](/ru/reference/peer-config/params.md#param-kura-store-dir). В этом корне данные блоков разделяются по исполнительной линии или сегменту. Основные файлы для сегмента следующие:

|Путь|Цель|
| --- | --- |
| `blocks/<segment>/blocks.data` |Смежные Norito-оформленные подписанные полезные нагрузки блоков.|
| `blocks/<segment>/blocks.index` |Записи фиксированного размера `(start, length)`, которые отображают высоту блока в байтах в `blocks.data`.|
| `blocks/<segment>/blocks.hashes` |Блокировать криптографические хэши по высоте для быстрого поиска и проверки при запуске.|
| `blocks/<segment>/blocks.count.norito` |Надёжный маркер завершения блока, фиксирующий, сколько записей индекса блока можно безопасно использовать.|
| `blocks/<segment>/da_blocks/` |Выгруженные полезные данные блоков хранятся вне `blocks.data`, когда контроль бюджета диска перемещает старые тела из горячего файла.|
| `blocks/<segment>/pipeline/sidecars.norito` и `sidecars.index` |Вспомогательные записи восстановления рабочего процесса обработки программного обеспечения, индексируемые по высоте блока.|
| `blocks/<segment>/pipeline/roster_sidecars.norito` и `roster_sidecars.index` |Недавнее завершение протокола — вспомогательные записи реестра, используемые для синхронизации блоков и воспроизведения.|
| `merge_ledger/<segment>.log` |записи журнала слияния блокчейна согласованы с финализированными блоками.|
| `commit-rosters.norito` |Сохранены сертификаты окончательного консенсуса и контрольные точки валидатора для недавних блоков.|

Kura сохраняет компактный в памяти вектор для цепочки: для каждой высоты есть криптографический хэш блока и, при необходимости, тело блока. Генезис-блок блокчейна остается в кэше, а самый новый [`kura.blocks_in_memory`](/ru/reference/peer-config/params.md#param-kura-blocks-in-memory) не-генезисные блоки хранят свои тела в памяти. Более старые тела блоков удаляются из памяти и перезагружаются из Kura файлы по мере необходимости.

Во время инициализации режим `strict` проверяет сохранённые блоки из полезных данных блоков и при необходимости переписывает файл криптографического хэша. Режим `fast` начинается с сохранённых метаданные хэша/индекса и возвращается к строгой инициализации, если эти метаданные неконсистентны. Если Kura обнаруживает поврежденный хвост, он обрезает хранилище до последнего проверенного блока.

Kura записывает новые блоки с помощью фонового записывающего процесса. Записывающий процесс добавляет полезные данные блоков, криптографические хэши и записи индекса, затем продвигает маркер надежного подсчета в соответствии с настроенной политикой fsync. Когда контроль бюджета диска активен, Kura может удалять выведенные из эксплуатации сегменты или выгружать более старые блоки в `da_blocks/`, сохраняя при этом криптографические хэши и записи индекса доступными для проверки и поиска.
