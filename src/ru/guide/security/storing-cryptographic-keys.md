# Сохранение криптографических ключей {#storing-cryptographic-keys}

Ваши конфиденциальные данные остаются частными только в том случае, если вы принимаете <abbr title="Operational Security">OPSEC</abbr> При этом, как и в случае с другими пользователями, вы можете использовать криптологический ключ для защиты ключей.

Для получения дополнительной информации о <abbr title="Operational Security">OPSEC</abbr> и его лучшие практики, см. [Операционная безопасность](./operational-security).

## Цифровое хранение криптографических ключей {#storing-cryptographic-keys-digitally}

Когда дело доходит до цифровой защиты криптографических ключей, в основном только два подхода[SSH](https://www.ssh.com/) и [GPG](https://www.gnupg.org/)Эти методы обеспечивают слои безопасности для предотвращения несанкционированного доступа к вашим криптографическим ключам.

Многие Iroha На архитектурные решения влияют принципы **Безопасная оболочка** (`SSH`Протокол, поэтому данный раздел в первую очередь фокусируется на `SSH` подход, предлагая инструкции о том, как эффективно реализовать протокол для хранения ваших криптографических ключей в Iroha экосистемы.

### Использование SSH и SSH Агент . {#using-ssh-and-ssh-agent}

**Протокол защищенной оболочки** (`SSH`) является криптографическим сетевым протоколом, который служит виртуальным шлюзом, позволяющим безопасный доступ к удаленным машинам через потенциально менее SSH Ключи к доступу. Он обеспечивает эффективный способ удаленного взаимодействия с системами без необходимости физического присутствия. `SSH` предлагает два основных механизма аутентификации: традиционный подход на основе пароля и более безопасный метод пары ключей государственно-частного сектора.

Для получения дополнительной информации о `SSH`, Смотрите [сопутствующие SSH Тема Академии](https://www.ssh.com/academy/ssh).

Чтобы упростить процесс входа и обойти необходимость повторного ввода, можно соединить `SSH` ключи с **SSH Агент .** (`ssh-agent`Программа помощников, которая запоминает ваши `SSH` Ключи и/или пароль для длительности сеанса. `SSH` шлюз для беспрепятственного доступа к ключам, когда он подключается к другим машинам.

Рабочий процесс здесь следующий: вы храните свой публичный ключ на удаленной системе и держите свой частный ключ в безопасности. `ssh-agent` шаги в общении с вами _общественность_ Затем удаленная система отправляет обратно [вызов](https://en.wikipedia.org/wiki/Challenge%E2%80%93response_authentication) что только твой _частные_ Ключ может правильно ответить. `ssh-agent` решает эту задачу, используя _частные_ Если ответ соответствует ожиданиям системы, вам предоставляется доступ.

Красота `ssh-agent` что он сохраняет ваш частный ключ во время сеанса, так что нет необходимости вводить пароль или пароль для частного ключа каждый раз, когда вы подключаетесь к удаленной системе.

Для получения дополнительной информации о `ssh-agent`, Смотрите [сопутствующие SSH Тема Академии](https://www.ssh.com/academy/ssh/agent).

::: info Примечание

Для подробного обзора `SSH` Протокол и `ssh-agent` инструмент, см. следующее [SSH Академия](https://www.ssh.com/academy) Темы:

  - [Что это? SSH (Secure Shell)?](https://www.ssh.com/academy/ssh)
  - [ssh-agent: как настроить ssh-агента, пересылки агента и протокол агента](https://www.ssh.com/academy/ssh/agent)

:::

### Добавление программы управления паролями {#adding-a-password-manager-program}

Рекомендуется повысить безопасность `SSH` ключи, защищая их паролем, который служит дополнительным препятствием для вредоносных лиц, стремящихся получить вашу конфиденциальную информацию.

Для хранения паролей пользователей и `SSH` Ключи временно. [KeePass](https://keepass.info/) используется в качестве примера менеджера паролей, в частности, [KeePassXC](https://keepassxc.org/) порты, работающие на операционных системах Linux.

Для инструкций по установке KeePassXC См. [Конфигурация KeePassXC](#configuring-keepassxc) раздел ниже.

KeePassXC Он обеспечивает повышенную безопасность, гибкость и контроль. `SSH` При использовании для хранения ключей этот менеджер паролей обеспечивает `ssh-agent` с сохраненными ключами, которые затем незамедлительно удаляются из его памяти после KeePassXC Окно закрыто.

#### Конфигурация KeePassXC {#configuring-keepassxc}

Для конфигурации KeePassXC, выполнять следующие шаги:

1. Запуск KeePassXC, Тогда иди к **Инструменты** > **Настройки**, или выберите **Устройство** кнопка сверху UI панель.

2. В **Настройки приложения** отметка, которая появляется, выберите **SSH Агент .** из левого меню, а затем выберите **Включить SSH Интеграция агентов** Счетчик.

   ::: info Показывать ссылочный скриншот

   ![KeePassXC `SSH Agent` Вкладка: Определить SSH Агент .](../../../img/keepassxc_ssh_agent.png)

3. Создайте новый KeePassXC База данных. [KeePassXC Руководство для пользователей > Создание первой базы данных](https://keepassxc.org/docs/KeePassXC_UserGuide#_creating_your_first_database).

4. Для каждого ключа, который вы хотели бы хранить в KeePassXC База данных, которую вы создали, выполните следующие шаги:

   - Добавить новый ввод в базу данных. [KeePassXC Руководство для пользователей > Создание первой базы данных](https://keepassxc.org/docs/KeePassXC_UserGuide#_creating_your_first_database).

   - При добавлении нового входа прикрепите файл, содержащий ключ, выполняя следующее: **Продвинутые** из левого меню, затем выберите **Добавить** в **Прикрепления** раздел, выберите требуемый файл в **Выберите файлы** окно, которое появляется.

   - При добавлении нового входа выберите **SSH Агент .** из левого меню, затем выберите файл ключа, который вы добавили из **Прикрепление** меню в **Частный ключ** раздел; затем выберите следующие окна:

      - **Добавить ключ к агенту при открытии/отключении базы данных**

      - **Удалить ключ от агента, когда база данных закрыта/заперта**

      - **Требуется подтверждение пользователя при использовании этого ключа**

   - При необходимости внесите другие изменения в запись.

   - При подготовке выберите **OK** Чтобы сохранить вход.

- Криптовалюты и `shh` Ключи хранятся в виде записей в KeePassXC База данных, к которой можно получить доступ во время KeePassXC Окно открыто.

- Криптовалюты `ssh` Ключи могут быть использованы, когда они требуются для получения разрешения.

- Криптовалюты `ssh` ключи удаляются из `ssh-agent` когда-то KeePassXC Окно закрыто.

Не позволяя **Требуется подтверждение пользователя при использовании этого ключа** В качестве альтернативы `ssh-agent` может не контролировать процесс, который предоставил ему ключ. `SIGKILL` С другой стороны, если вы не получите сигнал, ключ, вероятно, останется в `ssh-agent`, как программы системы Unix не могут перехватывать `SIGKILL`.

## Физическое хранение криптографических ключей {#storing-cryptographic-keys-physically}

Для тех, кто стремится к наивысшему уровню офлайн-безопасности, возможность хранения криптографических ключей физически гарантирует, что ключи остаются полностью отключены от цифровых сетей, таким образом минимизируя риск несанкционированного доступа.

### Используя аппаратный ключ {#using-a-hardware-key}

Наша команда считает, что аппаратные ключи являются одной из лучших мер безопасности. USB Порт и имеет размеры типичного флеш-накопителятолько обрабатывает события, связанные с безопасностью, когда он подключен к машине.

Тем не менее, поскольку существует много брендов аппаратных ключей, каждый из которых имеет свой уникальный APIs необходимо исследовать рынок, чтобы найти ключ, наиболее подходящий для ваших потребностей.

До сих пор наша команда провела внутренние испытания [YubiKey 5С](https://www.yubico.com/il/product/yubikey-5c/) аппаратный ключ, который оказался обладает многими положительными характеристиками, в том числе универсальным API функциональность.

Однако есть потенциальный недостаток, который следует учитывать. [HMAC аутентификация вызова-ответа](https://en.wikipedia.org/wiki/Challenge%E2%80%93response_authentication) и хранение соответствующего _частные_ Ключ к этому ответу может создать уязвимость. YubiKey Память 5C, что нарушает безопасность.

К счастью, эта уязвимость может быть смягчена путем принятия альтернативного подхода к использованию YubiKey 5С. Идея состоит в том, чтобы использовать YubiKey 5C для безопасного доступа к KeePassXC база данных , хранящая ваши криптографические и `SSH` Этот метод может даже считаться полезным, поскольку он превосходит безопасность большинства паролей и делает необходимым для вредоносной стороны быть в распоряжении вашего аппаратного ключа в случае KeePassXC База данных утечка.

Чтобы узнать больше о _метод выше_, см. ответ одного из KeePassXC разработчики[Янек Бевендорф](https://github.com/phoerious) к следующим StackExchange Вопрос:
