# Виртуальные частные сети {#virtual-private-networks}

Сетевой контроль <abbr title="Virtual Private Network">VPN</abbr> — это механизм, который ограничивает, кто может обращаться к сервисам Iroha. Он наиболее полезен для частных и консорциумных развертываний, где валидаторы, серверная часть приложений и операторы должны общаться через приватные адреса вместо открытых интернет-маршрутов.

VPN не заменяет ключи сетевого пира Iroha, ключи учетной записи, разрешения, правила брандмауэра, мониторинг или безопасное хранение ключей. Рассматривайте это как один уровень в граница развертывания: VPN ограничивает доступность сети, в то время как конфигурация и управление Iroha определяют, какие сетевые узлы и учетные записи считаются доверенными.

## Когда использовать VPN {#when-to-use-a-vpn}

Используйте VPN, когда:

- валидаторы управляются разными организациями или в разных хостинг-средах
- Torii должен быть доступен только для серверной части приложения, операторов или доверенных клиентов
- метрики, журналы, SSH или другие административные API конечные точки должны оставаться в частной сети оператора
- тестовая или промежуточная сеть должна имитировать контроль доступа в производственной среде, не открывая публичные API конечные точки

Для каждого развертывания VPN не требуется. Публичные сети могут намеренно открывать Torii через публичный шлюз, балансировщик нагрузки или обратный прокси. Даже в этом случае сохраняйте трафик между валидаторами и административные API конечные точки в ограниченной сети, когда это возможно.

::: tip

Браузер VPN защищает трафик только этого браузера. Он не защищает `iroha3d`, CLI, SDK, SSH, метрики или резервный трафик, если только эти процессы не направляются через ту же приватную сеть.

:::

## Шаблон развертывания {#deployment-pattern}

Для частной сети валидаторов присвойте каждому валидатору стабильный адрес VPN или приватное имя DNS. Настройте сетевых пиров так, чтобы их рекламируемые одноранговые адреса были доступны другим валидаторам через эту сеть:

```toml
trusted_peers = [
  "PUBLIC_KEY_1@10.20.0.11:1337",
  "PUBLIC_KEY_2@10.20.0.12:1337",
  "PUBLIC_KEY_3@10.20.0.13:1337",
  "PUBLIC_KEY_4@10.20.0.14:1337",
]

[network]
address = "10.20.0.11:1337"
public_address = "10.20.0.11:1337"

[torii]
address = "10.20.0.11:8080"
```

Используйте адрес, назначенный текущему сетевому узлу, в `network.address` и `network.public_address`. Каждый сетевой узел должен перечислять одни и те же доверенные идентификаторы сетевых узлов, но с адресами, доступными из собственной таблицы маршрутов VPN.

Конфигурации клиента и CLI должны указывать на конечную точку Torii API, доступную через VPN или через контролируемый внутренний шлюз:

```toml
torii_url = "http://10.20.0.11:8080"
```

Если Torii должен быть доступен за пределами VPN, разместите его за обратным прокси или балансировщиком нагрузки, который обеспечивает TLS, аутентификацию, ограничение скорости и ведение журналов. Избегайте прямого открытия необработанных peer-to-peer портов или административных API конечных точек для публичного интернета.

## Правила брандмауэра {#firewall-rules}

Используйте правила брандмауэра хоста и облака, даже когда присутствует VPN:

|Сервис|Рекомендуемый доступ|
| --- | --- |
|Пиринговый порт|Другой валидатор VPN адресует только|
| Torii |Фоновые приложения, операторы или доверенные клиентские диапазоны VPN|
|Метрики и проверки состояния|Системы мониторинга в сети оператора|
| SSH и администрация|Бастионный хост, привилегированный оператор VPN диапазон или процесс экстренного доступа|
|Резервное копирование и репликация хранилища|Резервные системы в частной сети|

Правила с запретом по умолчанию легче проверять, чем широкие правила разрешения. Когда новый сетевой узел присоединяется к сети, обновите членство VPN, список разрешений брандмауэра и конфигурацию доверенного сетевого узла Iroha в рамках одного согласованного изменения.

## Операционный контрольный список {#operational-checklist}

- Выберите проверенную и активно поддерживаемую реализацию VPN, такую как WireGuard, IPsec или управляемую частную сеть, одобренную организацией.
- Используйте уникальные учетные данные VPN для каждого хоста и оператора. Не делитесь ключами VPN между валидаторами.
- Храните учетные данные VPN отдельно от приватных ключей Iroha и материалов для подписи генезиса блокчейна.
- Мониторьте задержку VPN, потерю пакетов, повторные подключения и изменения маршрута. Консенсус чувствителен к продолжительной нестабильности сети.
- Проверьте эффективность MTU. Фрагментация пакетов может выглядеть как прерывистые сбои сети с узлом или Torii.
- Документ, в котором указаны диапазоны VPN, которые разрешено достигать через одноранговые соединения, Torii, метрики, SSH и резервные API конечные точки.
- Меняйте учетные данные VPN, когда хост, аккаунт оператора или организация покидает сеть.
- Избегайте использования одного VPN шлюза в качестве единственного маршрута между валидаторами. Планируйте резервные шлюзы или маршруты между площадками для производственных сетей.
- Включите отказы VPN в учения по реагированию на инциденты, чтобы операторы знали, когда отличать разделение сети от отказа процесса Iroha.
