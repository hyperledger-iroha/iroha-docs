# Разработка приложений {#application-development}

Iroha приложения должны сделать поведение транзакции ясным, продолжать подписывать
содержимого, и использовать запросы и события способами, которые легко
наблюдать при производстве.

## Настройка клиента {#client-setup}

- Сохранить конфигурацию клиента за пределами исходного кода приложения.
  цепь ID, Torii URL, подписывающий счет и настройки транзакций от
  Конфигурация, специфическая для окружающей среды.
- Держи . `client.toml` отдельные файлы для localnet, Taira, Minamoto, и
  Копируемый подписитель тестовой сети никогда не должен стать основной сетью
  Подпись.
- Сознательно устанавливают сроки действия транзакций и временные сроки.
  жизнь может истечь при нормальном сетевом нерве, в то время как очень длинный
  может затруднить размышление о дублированных заявлениях.
- Использование `nonce = true` только в тех случаях, когда повторяющиеся сделки должны иметь разные
  Для бескорыстных бизнес-операций, хранение и повторное использование
  запрос на подачу заявления ID так что повторные попытки прослеживаются.

Посмотрите. [Конфигурация клиента](/ru/guide/configure/client-configuration.md) для
текущий TOML полей.

## Транзакции {#transactions}

- Создать транзакции из типовых SDK инструкции, если это возможно, вместо
  сырой JSON или полезные нагрузки, смонтированные по струнам.
- "Префлиг" пишет с вопросами только для чтения.
  балансы активов, состояние разрешения, доступность актива по счетам и целевая ставка
  состояние объекта.
- Зарегистрируйте хэш транзакции, авторитетную учетную запись, резюме инструкций и
  ожидаемые изменения состояния до подачи.
- Лечить `Rejected`, `Expired`, И результаты отсрочки будут отличаться.
  означает, что клиент не соблюдал окончательный статус; это не доказывает, что
  сеть проигнорировала транзакцию.
- После успешной записи проверьте полученное состояние с помощью запроса или
  контрольно-пропускный пункт событий, соответствующий деятельности бизнеса.

Для механики транзакций см. [Транзакции](/ru/blockchain/transactions.md).

## Вопросы и события {#queries-and-events}

- Используйте запросы по текущему состоянию и потокам событий для уведомлений о изменениях.
  Избегайте замены обработки событий повторяющимися широкими запросами.
- Опубликовать широкие итерационные запросы, такие как счет, актив и блок
  Списки.
- Для подписей и триггеров предпочитаются узкие фильтры.
  полезно для диагностики, но может добавить ненужное выполнение и клиентская сторона
  обработки.
- Держите проверки дыма только для чтения отдельно от подписанных тестов транзакции так
  доступность конечных пунктов легче диагностировать.

Посмотрите. [Вопросы](/ru/blockchain/queries.md), [События](/ru/blockchain/events.md), и
[Фильтрации](/ru/blockchain/filters.md).

## Развитие с помощью агентов {#agent-assisted-development}

- Пусть агенты осматривают врачей, SDK код, и только для чтения сетевого состояния до
  просить их написать код транзакции.
- Сохраняйте тесты в живой сети, выбирая за флагом окружающей среды, например:
  `TAIRA_LIVE=1`.
- Не вставляйте частные ключи, материалы для восстановления счета. API токены, или
  Пересылают заголовки авторов в запросы.
- Требуйте план транзакции, прежде чем какой-либо агент представит живую тестовую сеть
  План должен назвать сеть, орган, инструкции.
  стоимость, предлетные показатели, ожидаемый результат и повторное поведение.

Для Taira MCP рабочий процесс, см.
[Построиться на SORA 3: Taira и Minamoto](/ru/get-started/sora-nexus-dataspaces.md#taira-mcp-for-agents).

## SDK Гигиена {#sdk-hygiene}

- Пин SDK и бинарных версий вместе с использованием
  [Матрица совместимости](/ru/reference/compatibility-matrix.md).
- Сохраняйте генерируемый код клиента, фрагменты и примеры синхронизированы с
  пересмотр рабочего пространства вверх потоком.
- Добавьте единичные тесты для создания кода транзакций и тесты интеграции для
  наименьшие способы чтения и письма, от которых зависит ваше заявление.
