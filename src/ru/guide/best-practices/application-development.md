# Разработка приложений {#application-development}

Приложения Iroha должны делать поведение транзакций явным, держать состояние подписей изолированным и использовать запросы и события таким образом, чтобы их было легко наблюдать в работе.

## Настройка клиента {#client-setup}

- Храните конфигурацию клиента вне исходного кода приложения. Загружайте идентификатор цепочки, Torii URL, учетную запись для подписи и настройки транзакций из конфигурации, специфичной для среды.
- Держите файлы `client.toml` отдельно для localnet, Taira, Minamoto и частных сетей. Скопированный криптографический подписант тестовой сети никогда не должен становиться криптографическим подписантом основной сети.
- Устанавливайте сроки жизни транзакций и тайм-ауты статусов намеренно. Очень короткий срок может истечь при обычных колебаниях сети, в то время как очень длинный может затруднить понимание повторных отправок.
- Используйте `nonce = true` только тогда, когда повторяющиеся транзакции должны иметь различные криптографические хэши. Для идемпотентных бизнес-операций храните и повторно используйте идентификатор запроса приложения, чтобы повторы были отслеживаемыми.

Смотрите [Конфигурация клиента](/ru/guide/configure/client-configuration.md) для текущих полей TOML.

## Транзакции {#transactions}

- Формируйте транзакции из типизированных инструкций SDK, где это возможно, вместо использования сырьевых JSON или собранных из строк полезных нагрузок.
- Предварительная проверка важных операций с использованием запросов только для чтения: существование аккаунта, балансы активов, состояние разрешений, доступность активов для комиссий и состояние целевого объекта.
- Запишите криптографический хеш транзакции, аккаунт авторизующего лица, краткое описание инструкции и ожидаемое изменение состояния перед отправкой.
- Обращайтесь с результатами `Rejected`, `Expired` и истечением времени по-разному. Истечение времени означает, что клиент не получил окончательный статус; это не доказывает, что сеть проигнорировала транзакцию.
- После успешной записи проверьте полученное состояние с помощью запроса или контрольной точки события, которая соответствует бизнес-операции.

Для механики транзакций см. [Транзакции](/ru/blockchain/transactions.md).

## Запросы и события {#queries-and-events}

- Используйте запросы для текущего состояния и потоки событий для уведомлений об изменениях. Избегайте замены обработки событий повторяющимися широкими запросами.
- Разбивайте на страницы широкие итерируемые запросы, такие как списки аккаунтов, активов и блоков.
- Предпочитайте узкие фильтры для подписок и триггеров. Широкие фильтры полезны для диагностики, но могут приводить к ненужному выполнению и обработке на стороне клиента.
- Держите проверки только для чтения отдельно от тестов подписанных транзакций, чтобы было проще диагностировать доступность конечной точки API.

См. [Запросы](/ru/blockchain/queries.md), [События](/ru/blockchain/events.md) и [Фильтры](/ru/blockchain/filters.md).

## Разработка с помощью агента {#agent-assisted-development}

- Позвольте агентам проверять документы, код SDK и состояние сети только для чтения перед тем, как просить их писать код транзакции.
- Оставьте тесты в живой сети с участием по желанию за флагом окружения, таким как `TAIRA_LIVE=1`.
- Не вставляйте приватные ключи, материалы для восстановления аккаунта, токены API или пересылаемые заголовки аутентификации в подсказки.
- Требуется план транзакции перед тем, как любой агент отправит транзакцию в тестовую сеть. План должен указывать сеть, основное лицо для авторизации, инструкции, актив для оплаты комиссии, предварительное чтение, ожидаемый результат и поведение при повторной попытке.

Для рабочего процесса Taira MCP см. [Построить на SORA 3: Taira и Minamoto](/ru/get-started/sora-nexus-dataspaces.md#taira-mcp-for-agents).

## SDK Гигиена {#sdk-hygiene}

- Закрепите SDK и бинарные версии вместе с помощью [Матрица совместимости](/ru/reference/compatibility-matrix.md).
- Держите сгенерированный клиентский код, фрагменты и примеры синхронизированными с закрепленной ревизией рабочего пространства upstream.
- Добавьте модульные тесты для кода построения транзакций и интеграционные тесты для самых маленьких путей чтения и записи, от которых зависит ваше приложение.
