# Ключи для развертывания сети {#keys-for-network-deployment}

Каждая сеть требует различного ключевого материала для клиентов, сетевых узлов, подписания генезиса блокчейна и, для NPoS или профилей Nexus, идентификаторов валидаторов BLS.

## Где используются ключи {#where-keys-are-used}

- Клиентские подписи хранятся в `client.toml` под `[account]`.
- Ключи идентификации сетевых узлов хранятся в каждом сетевом узле `config.toml` как `public_key` и `private_key`.
- Обнаружение сетевых узлов использует открытый ключ каждого сетевого узла в `trusted_peers`.
- BLS доказательства владения валидатора хранятся в `trusted_peers_pop` для профилей NPoS.
- Подпись генезиса блокчейна использует `[genesis].public_key` в конфигурации сетевого узла и соответствующий закрытый ключ при подписании технического манифеста.

Для локальных или тестовых развертываний позвольте Kagami сгенерировать все эти файлы вместе:

```bash
cargo run --bin kagami -- localnet --peers 4 --out-dir ./localnet
```

Для существующей сети или профиля используйте пошаговую инструкцию:

```bash
cargo run --bin kagami -- wizard
```

## Создать индивидуальные пары ключей {#generate-individual-key-pairs}

Используйте `kagami keys` для отдельного ключевого материала:

```bash
cargo run --bin kagami -- keys --algorithm ed25519 \
  --out-dir ./client-key
```

Для материала валидатора BLS включите доказательство владения:

```bash
cargo run --bin kagami -- keys --algorithm bls_normal --pop \
  --out-dir ./validator-key
```

Используйте `--seed-hex` только с точной 32-байтовой шестнадцатеричной секретной строкой для воспроизводимых фикстур разработки. Для развертывания в производственной среде пропустите его, чтобы Kagami использовал случайность операционной системы, затем поместите нешифрованный экспорт приватного ключа в утвержденную зону хранения. Эта команда никогда не выводит приватные ключи.

## Согласованность сетевых узлов {#peer-consistency}

Все валидаторы должны согласовать одну и ту же транзакцию генезиса блокчейна, топологию, публичные ключи доверенных узлов сети и валидатора PoPs. Отсутствие или несоответствие хотя бы одного ключа узла сети может помешать запуску сети или достижению консенсуса.

Для минимального развертывания, устойчивого к византийским отказам, используйте как минимум четыре сетевых узла. Каждый сетевой узел должен иметь собственный приватный ключ, но конфигурация каждого сетевого узла должна содержать один и тот же набор доверенных сетевых узлов.

## Клиентские счета {#client-accounts}

Клиентский аккаунт в `client.toml` должен уже существовать в цепочке. Он может быть зарегистрирован техническим манифестом генезиса блокчейна или более поздней транзакцией. Избегайте использования идентификационной подписи блокчейна на этапе создания (genesis) в качестве долговременного аккаунта приложения; привилегии при создании блокчейна применяются только в раунде создания блокчейна, и рабочие клиенты должны использовать свои собственные аккаунты и роли.
