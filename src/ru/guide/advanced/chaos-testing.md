# Тестирование хаоса с Izanami {#chaos-testing-with-izanami}

Идзанами — это оркестратор chaosnet в upstream Iroha рабочем пространстве. Он запускает одноразовый локальный кластер Iroha, отправляет настраиваемую нагрузку и внедряет сбои в выбранные сетевые узлы, чтобы операторы могли проверить, продолжает ли сеть успешно функционировать при контролируемых сбоях.

Используйте Izanami для проверок стойкости на этапе предпроизводства, воспроизведения регрессий и настройки консенсуса. Не направляйте его на производственную сеть: инструмент предназначен владеть сетевыми узлами, которые он запускает, включая перезапуски сетевых узлов, очистку хранилища, временные разделы доверенных узлов и локальное CPU или нагрузку на диск.

## Предварительные требования {#prerequisites}

Запускайте Izanami из [Iroha исходный репозиторий](https://github.com/hyperledger-iroha/iroha), а не из этого репозитория документации:

```bash
git clone https://github.com/hyperledger-iroha/iroha.git
cd iroha
cargo build -p izanami
```

Двоичный файл должен быть явно разрешен для создания и управления сетевыми узлами. Передайте `--allow-net` для каждого запуска, не являющегося TUI, или включите `allow_net` в TUI.

```bash
cargo run -p izanami -- --allow-net --peers 4 --faulty 1 --duration 120s
```

Для интерактивной конфигурации запуска:

```bash
cargo run -p izanami -- --tui --allow-net
```

Izanami сохраняет настройки TUI и CLI в каталоге конфигурации пользователя. Файл первой версии содержит один явный байт макета V1; предварительная версия или иные настройки без версии отклоняются и должны быть воссозданы, а не перенесены. Проверьте отображаемые настройки перед повторным использованием текущего профиля.

## Базовый запуск {#baseline-run}

Начните с одной воспроизводимой исходной точки перед добавлением серьёзных ошибок:

```bash
cargo run -p izanami -- \
  --allow-net \
  --peers 4 \
  --faulty 1 \
  --duration 5m \
  --target-blocks 100 \
  --progress-interval 15s \
  --progress-timeout 120s \
  --latency-p95-threshold 2s \
  --tps 15 \
  --max-inflight 32 \
  --submitters 1 \
  --seed 42
```

Этот запуск успешен только в том случае, если кластер достигает запрошенной цели по блокам, продолжает прогрессировать в течение времени ожидания и остаётся ниже необязательного порога интервала блоков p95.

Запишите команду, seed, Iroha завершение протокола, количество сетевых узлов, количество неисправных узлов, профиль нагрузки, целевой TPS и порог задержки вместе с журналами. Без этих значений другой оператор не сможет воспроизвести ту же схему отказа.

## Профили нагрузки {#workload-profiles}

У Изанами два профиля нагрузки:

|Профиль|Используйте это для|Заметки|
| -------- | -------------------------------------------------- | -------------------------------------- |
| `stable` |Длительные пробежки на выносливость и проверяемые тесты производительности|Предпочитает рецепты с безопасным выполнением|
|`chaos`|Покрытие путей отказа|Включает намеренно недействительные рецепты|

Сначала используйте стабильный профиль:

```bash
cargo run -p izanami -- --allow-net --workload-profile stable --seed 42
```

Переключитесь на профиль хаоса, когда базовый уровень уже понятен:

```bash
cargo run -p izanami -- --allow-net --workload-profile chaos --seed 42
```

Рецепты развертывания контрактов отключены в стабильных версиях, если это явно не разрешено:

```bash
cargo run -p izanami -- \
  --allow-net \
  --workload-profile stable \
  --allow-contract-deploy-in-stable
```

Используйте `--nexus`, когда выполнение должно использовать встроенные значения по умолчанию SORA Nexus из вышестоящего рабочего пространства.

## Контроль отказов {#fault-controls}

Когда `--faulty` больше нуля, должен быть включен как минимум один сценарий отказа. Переключатели отказов по умолчанию включены, а логические флаги можно отключить с помощью `=false`.

|Ошибка| CLI флаг                                   |Что это упражняет|
| ------------------------ | ------------------------------------------ | ------------------------------------------ |
|Сбой и перезапуск| `--fault-enable-crash-restart`             |потеря и восстановление процесса сетевого узла|
|Стереть хранилище и перезагрузить|`--fault-enable-wipe-storage`|Восстановление отсутствующего локального состояния|
|Неверная транзакция спам| `--fault-enable-spam-invalid-transactions` |Пути принятия и отклонения|
|Сетевые задержки|`--fault-enable-network-latency`           |Медленные слухи и задержанные сообщения о консенсусе|
|Сетевой разрыв|`--fault-enable-network-partition`|Временная изоляция доверенного узла|
| CPU стресс               | `--fault-enable-cpu-stress`                |Местная проверка и давление сроков|
|Насыщение диска|`--fault-enable-disk-saturation`           |Локальное давление хранения|

Для запуска только с разделением сети:

```bash
cargo run -p izanami -- \
  --allow-net \
  --peers 4 \
  --faulty 1 \
  --duration 5m \
  --fault-window-start 60s \
  --fault-window-end 180s \
  --tps 15 \
  --submitters 1 \
  --max-inflight 32 \
  --fault-enable-crash-restart=false \
  --fault-enable-wipe-storage=false \
  --fault-enable-spam-invalid-transactions=false \
  --fault-enable-network-latency=false \
  --fault-enable-network-partition=true \
  --fault-enable-cpu-stress=false \
  --fault-enable-disk-saturation=false \
  --seed 42
```

Используйте `--fault-window-start` и `--fault-window-end`, чтобы поддерживать контролируемый установившийся режим до и после введённого сбоя. Это облегчает различение шумов при запуске от влияния ошибки.

## Формы сценариев {#scenario-shapes}

Верхнеуровневый каталог Izanami сопоставляет распространённые формы сбоев связи в блокчейне с профилями CLI. Вы можете моделировать их с использованием тех же флагов:

|Сценарий|Типичная форма|
| --------------------- | ------------------------------------------------------------------------------------------------------------------------ |
|Целевая нагрузка| `--faulty 0`, высокий `--tps`, один отправитель, высокий `--max-inflight`|
|Временный сбой|Включить сбой/перезапуск только внутри ограниченного окна сбоев|
|Остановка и восстановление|Используйте большую популяцию неисправных узлов с сбоем/перезапуском|
|Изоляция лидера|Используйте ровно одного неисправного сетевого узла только с ошибкой разделения сети; Изанами следует телеметрии лидера Sumeragi|

Держите одну переменную фиксированной за раз. Если вы измените количество сетевых узлов, профиль рабочей нагрузки, окно отказа и TPS в одном запуске, результат будет сложно интерпретировать.

## Что смотреть {#what-to-watch}

Во время запуска следите за теми же сигналами, которые используются для проверки производительности:

- прогресс высоты блока на каждом запущенном сетевом узле
- отправленные, принятые, отклонённые и завершившиеся по тайм-ауту транзакции
- глубина очереди, насыщение очереди и API обратное давление конца точки
- просмотр изменений, путей восстановления, отсутствующих блоков и отсутствующих сертификатов кворума
- подписанный RS16 отставание доступности, ожидающие сеансы и задержанный трафик консенсуса
- CPU, насыщение памяти, диска и сети на хосте, на котором работают сетевые узлы

Для анализа задержки проверки включите отладочные журналы основного цикла:

```bash
RUST_LOG=iroha_core::sumeragi::main_loop=debug \
  cargo run -p izanami -- --allow-net --seed 42
```

Каждый блок должен испускать `block validation timings` с `stateless_ms`, `execution_ms` и `total_ms`. Сравните эти показатели времени с интервалами блоков p95, счетчиками изменения представления и давлением в очереди перед изменением таймеров консенсуса.

## Интерпретация результатов {#interpreting-results}

Считайте запуск здоровым, когда все выбранные сетевые узлы продолжают завершать блоки, очередность не растет бесконтрольно, и сбои перестают вызывать новую активность восстановления после окончания настроенного окна.

Считайте пробег неудачным, когда:

- прогресс блока задерживается более чем на `--progress-timeout`
- высоты узлов сети расходятся и не сойдутся снова
- задержка p95 превышает `--latency-p95-threshold`
- очереди растут в течение оставшегося времени работы после закрытия окна сбоев
- отклонённые или истёкшие по времени транзакции не объясняются выбранной рабочей нагрузкой
- перезапуск сетевого узла, очистка хранилища или восстановление раздела требует ручной очистки

После сбоя перезапустите с тем же начальным значением и на один тип ошибки меньше. Это позволяет сохранять воспроизводимость рабочей нагрузки и времени, одновременно сужая область возможных сбоев.
