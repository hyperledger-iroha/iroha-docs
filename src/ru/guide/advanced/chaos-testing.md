# Тестирование хаоса с Изанами {#chaos-testing-with-izanami}

Изанами - оркестратор хаоса в верхнем потоке. Iroha рабочее пространство.
запускает одноразовый локальный Iroha кластер, представляет конфигурируемую рабочую нагрузку;
и вводит ошибки в выбранные сверстники, чтобы операторы могли проверить,
сеть продолжает добиваться прогресса при контролируемой неудаче.

Используйте Izanami для проверки устойчивости до производства, регрессионного воспроизводства,
Не указывайте на производственную сеть: инструмент
предназначен для владельца сверстников, включая перезагрузку сверстника, хранение
стереотипы, искусственная потеря упаковки и местные CPU или давление диска.

## Предусмотренные условия {#prerequisites}

Запустить Izanami из
[Iroha источник хранилища](https://github.com/hyperledger-iroha/iroha),
не из данного хранилища документации:

```bash
git clone https://github.com/hyperledger-iroha/iroha.git
cd iroha
cargo build -p izanami
```

Бинарным должен быть прямо разрешено создавать и управлять сетевыми
Сверстники, проходите. `--allow-net` для каждого не-TUI запустить или включить `allow_net` в
в) TUI.

```bash
cargo run -p izanami -- --allow-net --peers 4 --faulty 1 --duration 120s
```

Для интерактивной конфигурации выполнения:

```bash
cargo run -p izanami -- --tui --allow-net
```

Изанами настаивает . TUI и CLI настройки в каталоге конфигурации пользователя, так что
пересмотреть отображаемые настройки перед повторным использованием предыдущего профиля.

## Исходный показатель {#baseline-run}

Начните с одного воспроизводимого исходного показателя, прежде чем добавить серьезные ошибки:

```bash
cargo run -p izanami -- \
  --allow-net \
  --peers 4 \
  --faulty 1 \
  --duration 5m \
  --target-blocks 100 \
  --progress-interval 15s \
  --progress-timeout 120s \
  --latency-p95-threshold 2s \
  --tps 15 \
  --max-inflight 32 \
  --submitters 1 \
  --seed 42
```

Эта попытка будет успешной только в том случае, если кластер достигнет требуемой цели блока.
продолжает добиваться прогресса в течение срока, и остается под дополнительным p95
порог интервала блокировки.

Запиши приказ, семя. Iroha совершать ошибки, считать сверстников, считать несоответствующими сверстникам,
профиль рабочей нагрузки, цель TPS, и порог задержки с журналом.
если эти значения, другой оператор не может воспроизвести тот же шаблон сбоев.

## Профили загрузки {#workload-profiles}

Izanami имеет два профиля рабочей нагрузки:

| Профиль  | Используйте его для                                         | Примечания                                  |
| -------- | -------------------------------------------------- | -------------------------------------- |
| `stable` | Длинные пробеги на погружении и воспроизводимые проверки производительности | Рецепты, безопасные для исполнения          |
| `chaos`  | Покрытие пути неудачи                              | Включает намеренно недействительные рецепты |

Сначала используйте стабильный профиль:

```bash
cargo run -p izanami -- --allow-net --workload-profile stable --seed 42
```

Перейти к профилю хаоса, когда базовая линия уже понята:

```bash
cargo run -p izanami -- --allow-net --workload-profile chaos --seed 42
```

Рецепты контрактного развертывания отключаются в стационарных режимах, если только это не явно
разрешено:

```bash
cargo run -p izanami -- \
  --allow-net \
  --workload-profile stable \
  --allow-contract-deploy-in-stable
```

Использование `--nexus` когда на пробеге следует использовать встроенный SORA Nexus неисправности
рабочее пространство вверх по течению.

## Контроль ошибок {#fault-controls}

Когда `--faulty` является более чем нулевым, по крайней мере один сценарий ошибки должен быть
Ошибка переключается по умолчанию на включенный, и булевые флаги могут быть
инвалиды с `=false`.

| Ошибка                    | CLI флаг                                   | Что он делает                          |
| ------------------------ | ------------------------------------------ | ------------------------------------------ |
| Сбой и перезапуск        | `--fault-enable-crash-restart`             | Потеря и восстановление процесса сверстников             |
| Стирать хранилище и перезагрузить | `--fault-enable-wipe-storage`              | Восстановление после исчезновения местного государства          |
| Недействительный спам транзакций | `--fault-enable-spam-invalid-transactions` | Пути приема и отказа              |
| Задержка сети          | `--fault-enable-network-latency`           | Медленные сплетни и задержанные сообщения консенсуса |
| Сетевая разделка        | `--fault-enable-network-partition`         | Временная изоляция доверенных лиц           |
| P2P потеря пакета          | `--fault-enable-network-packet-loss`       | Сброшенный трафик в рамках приложений          |
| CPU стресс               | `--fault-enable-cpu-stress`                | Местное давление на валидацию и планирование   |
| Насыщение диска          | `--fault-enable-disk-saturation`           | Местное давление хранения                     |

Для поезда только с пакетной потерей:

```bash
cargo run -p izanami -- \
  --allow-net \
  --peers 20 \
  --faulty 5 \
  --duration 800s \
  --fault-window-start 133s \
  --fault-window-end 266s \
  --tps 200 \
  --submitters 20 \
  --max-inflight 512 \
  --fault-enable-crash-restart=false \
  --fault-enable-wipe-storage=false \
  --fault-enable-spam-invalid-transactions=false \
  --fault-enable-network-latency=false \
  --fault-enable-network-partition=false \
  --fault-enable-network-packet-loss=true \
  --fault-enable-cpu-stress=false \
  --fault-enable-disk-saturation=false \
  --fault-network-packet-loss-percent 75 \
  --seed 42
```

Использование `--fault-window-start` и `--fault-window-end` для поддержания контролируемой
Период стабильного состояния до и после инъекции.
легче отличить шум запуска от эффекта ошибки.

## Формы сценария {#scenario-shapes}

Каталог Izanami вверх по течению отображает общие неисправности блокчейн-коммуникации
формы к CLI Профили. Вы можете моделировать их с теми же флагами:

| Сценарий              | Типичная форма                                                                                                            |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Целевая нагрузка         | `--faulty 0`, высокая `--tps`, один подающий, высокий `--max-inflight`                                                         |
| Временная неисправность     | Включить отказ/перезагрузку только в окне с ограниченной погрешностью                                                                  |
| Потеря пакета           | Включить только потерю пакетов, обычно с дефолтным уровнем потерь 75%                                                          |
| Прекращение и восстановление | Используйте большую популяцию неисправностей с отказом/перезагрузкой                                                                    |
| Изоляция лидеров      | Используйте точно один неисправный партнер с только сетевой разделения или пакетной потери ошибок; Izanami следует Sumeragi телеметрия лидера |

Если вы измените количество сверстников, рабочая нагрузка
профиль, окно ошибок и TPS В то же время, результат трудно
интерпретировать.

## Что нужно смотреть {#what-to-watch}

Во время бега следите за теми же сигналами, которые используются для проверки производительности:

- прогресс по высоте блока на каждом бегущем уровне
- представленные, принятые, отклоненные и истекшие сроки операции
- глубина очереди, насыщенность очереди и обратное давление конечного пункта
- просмотр изменений, пути восстановления, отсутствие блоков и отсутствие кворума
  сертификаты
- RBC задержка, ожидающие сессии и снижение или замедление консенсусного трафика
- CPU, память, диск и насыщение сети на хостере, работающем сверстниками

Для анализа задержки проверки, включить журналы дебъюга основного цикла:

```bash
RUST_LOG=iroha_core::sumeragi::main_loop=debug \
  cargo run -p izanami -- --allow-net --seed 42
```

Каждый блок должен выделять `block validation timings` с `stateless_ms`,
`execution_ms`, и `total_ms`. Сравните эти сроки с блоком p95
интервалы, счетчики смены просмотра и давление в очереди перед изменением
Консенсусные таймеры.

## Результаты интерпретации {#interpreting-results}

Относитесь к бегу как к здоровому, когда все выбранные сверстники продолжают совершать блокировки.
задержка не растет без ограничений, а ошибки перестают вызывать новое восстановление
активность после окончания конфигурированного окна.

Оценить бег как неудачу, если:

- прогресс блокируются дольше, чем `--progress-timeout`
- Высота однородников расходятся и не пересходят
- превышает пропускную способность p95 `--latency-p95-threshold`
- очереди растут в течение остальной части пробега после закрытия окна с ошибкой
- отклоненные или отсроченные сделки не объясняются выбранными
  нагрузка
- для перезагрузки с помощью параметров, стирания хранилища или восстановления пакетной потери требуется руководство
  уборка

После неудачи, перезапустите с тем же семя и одним меньшим типом дефекта.
сохраняет воспроизводимость рабочей нагрузки и времени, уменьшая сбои
поверхность.
