# Torii API የመጨረሻ ነጥቦች {#torii-endpoints}

Torii የ Iroha 3 HTTP፣ SSE እና WebSocket ጌትዌይ ነው። ከመዝገቡ ጋር የሚገናኙ APIs እና የኦፕሬተር መጨረሻ ነጥቦችን ያቀርባል።

አሁን ያሉት የፕሮቶኮል ህጎች -

- ነጠላ ፕሮቶኮል-መደበኛ ሁለትዮሽ ቅርጸት Norito ነው።
- ብዙ API የመጨረሻ ነጥቦችም ይደግፋሉ JSON ሲልኩ `Accept: application/json`
- መለኪያዎች በፕሮሜቲየስ ቅርጸት ይጋለጣሉ

ለቅርጸት ዝርዝሮች፣ የይዘት ድርድር፣ የአቀማመጥ ባንዲራዎች፣ የመርሃግብር ምስጠራ ሃሽ እና Norito RPC መመሪያ [Norito ማጣቀሻ](/am/reference/norito.md) ይመልከቱ።

| -------------------------------- | -------------- | ---------------------------------------------------------------- |
|`POST /v1/pipeline/transactions`|Norito|የተፈረመ ግብይት ያስገቡ|

|`GET /readyz`|JSON|የግዴታ ከመስመር ውጭ የገንዘብ ቼኮችን ጨምሮ የተሟላ የኖድ ዝግጁነት|

|`GET /v1/node/capabilities`|JSON|የኖድ ችሎታ እና የውሂብ-ሞዴል ሜታዳታ|

|`GET /v1/time/status`|JSON|የጊዜ ማመሳሰል ሁኔታ|

ለ SSE ጥያቄ፣ ቤተኛ ዥረቱን እና የተተየበ ተተኪ አማራጩን ያስተዋውቁ -

```http
Accept: text/event-stream, application/json
```

Torii በመጀመሪያ በጥያቄው ንብርብር ላይ የ JSON ወይም Norito ውክልና ይደራደራል፣ ከዚያም ቤተኛ `text/event-stream` ምላሽን ያረጋግጣል። ስለዚህ `text/event-stream` ብቻ መላክ በ `406` ውድቅ ይደረጋል; [የዥረት-ክስተቶች የተግባር መመሪያ](/am/cookbook/stream-events.md) ሙሉውን ራስጌ ይጠቀማል.

`/openapi.json` በመርሃግብሩ ውስጥ ለተወከሉት መንገዶች የመነጨ ውል እንጂ የተሟላ የአሠራር-መመርመሪያ ክምችት አይደለም።. አሁን ያለው ሰነድ `/livez` እና `/readyz`ን ይተዋል፣ እና የእሱ `/health` መግለጫው የዝግጁነት ተቆጣጣሪውን ሊዘገይ ይችላል። የመስመር ደንበኞችን ከቀጥታ ሰነዱ ያመነጩ፣ ነገር ግን ሕያውነትን እና ዝግጁነትን በቀጥታ በሩጫ ኖድ እና በተሰኩ ተቆጣጣሪዎች ላይ ያረጋግጡ። ትክክለኛው ወለል አሁንም በግንባታ ባህሪያት ላይ የተመሰረተ ነው እና የሶፍትዌር ማስፈጸሚያ አካባቢ ውቅር። ያንን የቀጥታ ሰነድ ለመጫን፣ JSON መንገዶችን ለመፈተሽ፣ curl ጥያቄዎችን ለመቅዳት እና የደንበኛ ኮድ አሁን ካለው እቅድ ለማመንጨት [Torii API ኮንሶል](/am/reference/torii-api-console.md)ን ይጠቀሙ።

እያንዳንዱ በካታሎግ የተደገፈ OpenAPI ክዋኔ `x-iroha-route-auth` ነገርን ያካትታል። በካታሎግ የተደገፉ MCP መሳሪያዎች ከ `_meta["iroha/routeAuth"]` ጋር ተመሳሳይ ውል ያጋልጣሉ። ሁለቱም ትንበያዎች `schemaVersion`፣ `stableRouteId`፣ `authentication` እና `admission` ይይዛሉ። ስሪት `1`ን እንደ ትክክለኛ ውል ይያዙት የማረጋገጫ ወይም የመግቢያ መለያዎቹ እንዴት መተርጎም እንዳለባቸው ከመገመት ይልቅ የማይደገፍ `schemaVersion` ውድቅ ያድርጉ። የመንገዱ ሜታዳታ የጥያቄውን ወሰን ይገልጻል; በዚያ ድንበር የሚፈለጉትን ምስክርነቶች አይተካም.

## የቀጥታ Taira መንገዶችን ይሞክሩ {#try-live-taira-routes}

ይፋዊው Taira testnet የመተግበሪያ ደንበኞች ለተነባቢ-ብቻ አሰሳ የሚጠቀሙበትን ተመሳሳይ Torii JSON ገጽ ያጋልጣል። እነዚህ ትዕዛዞች ቁልፎችን አያስፈልጋቸውም -

```bash
TAIRA_ROOT=https://taira.sora.org

curl -fsS -H 'Accept: application/json' "$TAIRA_ROOT/status" \
  | jq '{blocks, txs_approved, txs_rejected, queue_size, peers}'

curl -fsS "$TAIRA_ROOT/openapi.json" \
  | jq -r '.paths | keys[]' \
  | grep '^/v1/' \
  | head -n 20

curl -fsS -H 'Accept: application/json' \
  "$TAIRA_ROOT/v1/node/capabilities" \
  | jq '{abi_version, data_model_version, query: .query.aggregate.supported_resources}'
```

አሁን ካለው የአለም ሁኔታ አንጻር የግብአት ንባቦችን ይሞክሩ -

```bash
curl -fsS "$TAIRA_ROOT/v1/domains?limit=5" \
  | jq -r '.items[].id'

curl -fsS "$TAIRA_ROOT/v1/assets/definitions?limit=5" \
  | jq -r '.items[] | [.id, .name, .total_quantity] | @tsv'
```

ይፋዊ የቴስትኔት መስመር `502` ከተመለሰ፣ ጊዜው ካለፈ ወይም የሳቹሬትድ ወረፋን ሪፖርት ካደረገ፣ እንደ API የመጨረሻ ነጥብ ተገኝነት ችግር አድርገው ይያዙት እና የደንበኛ ኮድዎን ከማረምዎ በፊት በኋላ እንደገና ይሞክሩ።

## መተግበሪያ እና SORA የመንገድ ቤተሰቦች {#app-and-sora-route-families}

## የመለያ ማረጋገጫ፣ ታይነት እና አሳሽ ጠቋሚዎች {#account-authentication-visibility-and-explorer-cursors}

### የመተግበሪያ መለያ ጥያቄ ፕሮቶኮል {#app-account-request-protocol}

መተግበሪያን የሚመለከቱ መንገዶች ምንም የማረጋገጫ ራስጌዎችን፣ ነጠላ ቀጥተኛ ቁልፍ ማረጋገጫ ወይም ነጠላ ባለብዙ ሲግ ምስክርነትን ይቀበላሉ። እያንዳንዱ የማረጋገጫ ራስጌ ቢበዛ አንድ ጊዜ መታየት አለበት።

ለቀጥታ ማረጋገጫ፣ አራቱንም ራስጌዎች አንድ ላይ ይላኩ -

- `X-Iroha-Account` ትክክለኛው ነጠላ ፕሮቶኮል-መደበኛ ንዑስ ሆሄያት `0x` የመለያ-አድራሻ ሄክስ ወይም ገባሪ ነጠላ ፕሮቶኮል-መደበኛ ASCII መለያ ተለዋጭ ስም። I105 ጽሑፍ እንደ HTTP የመስክ እሴት ደህንነቱ የተጠበቀ አይደለም; ለዚያ መለያ ነጠላ ፕሮቶኮል-መደበኛ የሄክስ አጻጻፍ ይጠቀሙ።
- `X-Iroha-Signature` ጥብቅ የታሸገ-ቤዝ64 ፊርማ ጭነት።
- `X-Iroha-Timestamp-Ms` አንድ ፕሮቶኮል-መደበኛ ያልተፈረመ የአስርዮሽ ዩኒክስ የጊዜ ማህተም በሚሊሰከንዶች ውስጥ፣ በተዋቀረው የተዛባ መስኮት ውስጥ።
- `X-Iroha-Nonce` ከ1 እስከ 256 ሊታተም የሚችል ASCII ባይት (`0x21` እስከ `0x7e`)፣ በድጋሚ ማጫወት መስኮቱ ውስጥ ልዩ።

የተመዘገበው ነጠላ-ቁልፍ መቆጣጠሪያ እነዚህን ትክክለኛ ባይቶች ይፈርማል -

```text
iroha.app.request.network.v1\0 || <genesis-derived network_id[32]> ||
<UPPERCASE_METHOD>\n
<exact request path>\n
<canonical query>\n
<lowercase hex SHA-256 of the raw body>\n
<canonical timestamp_ms>\n
<nonce>
```

ነጠላ ፕሮቶኮል-መደበኛ መጠይቅ ግንባታ ጥሬውን መጠይቅ እንደ `application/x-www-form-urlencoded` (`+` ማለት ቦታ ማለት ነው፣ ጥንዶቹን በመቶኛ ይፈታቸዋል፣ በ `(key, value)` ይለያያል እና እንደገና ኮድ ያደርጋቸዋል። ፕሮቶኮሉ ቢበዛ 64 ዲኮድ የተደረገ ጥንድ እና 64 KiB ጥሬ መጠይቅ ጽሑፍን ይቀበላል። ልክ እንደተላለፈው የውሂብ አካል ባይት በምስጠራ ይሃሽ። በቋሚው ባለ 32-ባይት አውታረ መረብ መታወቂያ እና በአቢይ ሆሄያት ዘዴ መካከል መለያየት አያስገቡ።

የ V1 አረጋጋጩ ከመተንተን በፊት የስልቱን ማስታወሻ በ32 ባይት፣ በመቶኛ የተመሰጠረ የጥያቄ ዱካ በ64 KiB እና ቀጥተኛ መለያ መታወቂያውን በ36 KiB ይሸፍናል። የመለያ ተለዋጭ ስሞች የሶስት የስም ክፍሎች እና መለያዎቻቸው ጥብቅ መዋቅራዊ ገደብ አላቸው። ከዚህ ገደብ ማለፍ የፊርማ ማረጋገጫ ወይም የምንጭ መጠን ከመመደብ በፊት ማረጋገጫው እንዳይሳካ ያደርገዋል።

የመልቲሲግ ተቆጣጣሪ በምትኩ `X-Iroha-Witness`ን እንደ ጥብቅ የታሸገ-ቤዝ64 ነጠላ ፕሮቶኮል-ስታንዳርድ Norito መላክ እና `X-Iroha-Signature`፣ `X-Iroha-Timestamp-Ms` እና `X-Iroha-Nonce` መተው አለበት። `X-Iroha-Account` በዚህ ቅጽ አማራጭ ነው; በሚገኝበት ጊዜ ከምስክሩ ጋር እኩል መሆን አለበት `subject_account`። `CanonicalRequestWitnessV1` `schema_version`፣ `subject_account`፣ `timestamp_ms`፣ `nonce`፣ Iroha `Hash` ትክክለኛ የአውታረ መረብ ጥያቄ ባይት በውሂብ አካል ክሪፕቶግራፊያዊ ዳይጀስት በኩል ግን ያለ ትኩስነት መስኮች እና ቢበዛ 64 አባላት ፊርማዎችን ይዟል። እያንዳንዱ አባል ያለ ፊርማ ድርድር ተመሳሳይ ጭነት ነጠላ ፕሮቶኮል-ስታንዳርድ Norito ኢንኮዲንግ ይፈርማል። የተረጋገጡ አባላት የመለያውን የአሁኑን የብዝሃ ፖሊሲ ማሟላት አለባቸው። የተመሰጠረው ምስክር በ1 MiB ተይዟል።

ምንም የማረጋገጫ ራስጌዎችን ማቅረብ ስም-አልባ መዳረሻን ይመርጣል። ማንኛውንም ከፊል፣ የተደባለቀ፣ የተደጋገመ፣ የተደጋገመ፣ የተበላሸ፣ ያረጀ ወይም በድጋሚ የተጫወተ ማረጋገጫ ማቅረብ ማረጋገጫውን አይሳካም። ወደ ማንነቱ ያልታወቀ ታይነት በጭራሽ አይወድቅም።

### የኦፕሬተር ጥያቄ ፕሮቶኮል {#operator-request-protocol}

በኦፕሬተር የተረጋገጠ ምልክት የተደረገባቸው መንገዶች አራቱንም ነጠላ ራስጌዎች ያስፈልጋቸዋል -

- `x-iroha-operator-public-key` ነጠላ ፕሮቶኮል-መደበኛ Iroha ባለብዙ ሃሽ የህዝብ ቁልፍ።
- `x-iroha-operator-timestamp-ms` ነጠላ ፕሮቶኮል-መደበኛ ያልተፈረመ የአስርዮሽ ዩኒክስ የጊዜ ማህተም በሚሊሰከንዶች ውስጥ።
- `x-iroha-operator-nonce`: ከ 1 እስከ 256 ሊታተም የሚችል ASCII ባይት፣ በድጋሚ ማጫወት መስኮቱ ውስጥ ለዚያ ቁልፍ ልዩ።
- `x-iroha-operator-signature` ጥብቅ የታሸገ-ቤዝ64 ፊርማ ጭነት።

የራስጌ ዋጋዎች በዙሪያው ያለ ነጭ ቦታ መያዝ የለባቸውም። የ ኦፕሬተር ቁልፍ ምልክቶች

```text
iroha.operator.http-request.network.v1\0 || <genesis-derived network_id[32]> ||
<UPPERCASE_METHOD>\n
<exact request path>\n
<canonical query>\n
<lowercase hex SHA-256 of the raw body>\n
<canonical timestamp_ms>\n
<nonce>
```

መንገዱ፣ መጠይቁ፣ አካል፣ የጊዜ ማህተም እና ምስጠራ ኖስ እሴት ህጎች በመተግበሪያው ፕሮቶኮል የሚጠቀሙባቸው ተመሳሳይ ነጠላ ፕሮቶኮል-መደበኛ ህጎች ናቸው። ቁልፉ እንዲሁ አለበት በ `[torii.operator_signatures]` ይቀበሉ በ `allowed_public_keys` ውስጥ ይዘርዝሩት፣ ወይም የኖድ ቁልፉን ሲጠቀሙ `allow_node_key`ን በግልፅ ያንቁ። የድጋሚ አጫውት-መሸጎጫ ሙሌት በ`503 Service Unavailable` በአስተማማኝ ሁኔታ ውድቅ ይሆናል።

ትክክለኛው የጥያቄ ፊርማ ሁል ጊዜ ግዴታ ነው። `[torii.operator_auth].enabled = true`፣ እያንዳንዱ ተራ ኦፕሬተር መንገድ እንዲሁ ትክክለኛ `x-iroha-operator-session` ያስፈልገዋል። `require_mtls = true` ሲሆን፣ ከታመነ መግቢያ `x-forwarded-client-cert` ያስፈልገዋል። ሁለቱም ምክንያቶች የጥያቄ ፊርማውን አይተኩም።

WebAuthn ምዝገባ እና መግቢያ እነዚህን አራት JSON API የመጨረሻ ነጥቦችን ይጠቀሙ -

|ዘዴ እና API የመጨረሻ ነጥብ|ዓላማ|
| --------------------------------------------- | ---------------------------------------- |
|`POST /v1/operator/auth/registration/options`|WebAuthn የምስክር ወረቀት ምዝገባ ጀምር|
|`POST /v1/operator/auth/registration/verify`|ምስክርነቱን ያረጋግጡ እና ያስቀምጡ|
|`POST /v1/operator/auth/login/options`|WebAuthn ማረጋገጫን ጀምር|
|`POST /v1/operator/auth/login/verify`|ማረጋገጫውን ያረጋግጡ እና ክፍለ ጊዜ ያውጡ|

`torii.operator_auth.tokens`ን በወሰኑ የማስነሻ እሴቶች ያዋቅሩ። ማንኛውም ምስክርነት ከመኖሩ በፊት የመጀመሪያውን ምዝገባ ለመጀመር አንዱን እንደ `x-iroha-operator-token` ይላኩ። ያ ቶከን ተራ የኦፕሬተር መንገድን ፈጽሞ አይፈቅድም፣ እና የአድማጭ `x-api-token` እሴቶች ለዚህ ፍሰት በጭራሽ ጥቅም ላይ አይውሉም። አንዴ ምስክርነት ከተፈጠረ፣ ሌላ ምስክርነት መመዝገብ የተረጋገጠ ክፍለ ጊዜ ያስፈልገዋል። የመግቢያ ማረጋገጫ ከእያንዳንዱ አዲስ ትክክለኛ የአውታረ መረብ ኦፕሬተር ጥያቄ ፊርማ ጋር ለመላክ የክፍለ-ጊዜ ቶከኑን ይመልሳል። ምስክርነቶች በ`<torii.data_dir>/operator_auth/operator_webauthn.json` ስር ይቀጥላሉ።

ISO የ20022 መንገዶች ሁለት ገለልተኛ ቼኮችን ይተገብራሉ። ጥያቄው በመጀመሪያ ይህንን ኦፕሬተር የተፈቀደ ዝርዝር እና የፊርማ ፕሮቶኮል ማለፍ አለበት; የ ISO ተቆጣጣሪው ከዚህ በታች የተገለጸውን ትክክለኛ ተሳታፊ ወይም የኦዲት ሚና ለመያዝ ተመሳሳይ ቁልፍ ይፈልጋል።

### የብሎክቼይን መዝገብ ታይነት እና ኤክስፕሎረር ጠቋሚዎች {#ledger-visibility-and-explorer-cursors}

መተግበሪያን የሚመለከት የብሎክቼይን መዝገብ ያነባል ከላይ ያለውን አማራጭ የመተግበሪያ መለያ ድንበር ይጠቀሙ። ያልተፈረመ ጥያቄ እንደ ይፋዊ የተዋቀሩ የውሂብ ቦታዎችን ብቻ ይቀበላል። ትክክለኛ የተፈረመ ጥያቄ ከደዋዩ የአሁኑ UAID፣ እያንዳንዱ የተገደበ የውሂብ ቦታ በትክክለኛው `CanReadRestrictedDataspace { dataspace }` ፍቃድ የተሰየመ ወይም መለያው `CanReadAllLedgerData` ሲኖረው ሁሉንም መንገዶች ያክላል።

## ISO 20022 ድልድይ {#iso-20022-bridge}

Torii የመተግበሪያው ፊት ለፊት ያለው API እና የድልድይ ሶፍትዌር ማስፈጸሚያ አካባቢ ሲነቃ የ ISO 20022 ድልድይ በ`/v1/iso20022/*` ስር ያጋልጣል። ድልድዩ ሆን ተብሎ ወሰን አለው - እሱ አጠቃላይ ዓላማ ISO 20022 የማጽዳት መግቢያ በር አይደለም፣ ነገር ግን የተመረጡ የክፍያ መልዕክቶችን ወደ የተፈረሙ Iroha ዝውውሮች ለመቀየር እና የብሎክቼይን መዝገብ ሁኔታቸውን ለመከታተል የሚደገፍ ንዑስ ስብስብ ነው።

ማንኛውንም ግቤት ከመቀበልዎ በፊት የሚበረክት አካባቢያዊ `torii.iso_bridge.store_dir` ያዋቅሩ። የውቅረት መስኩ አማራጭ ብቻ ነው ስለዚህ ኖድ ለተነባቢ-ብቻ ወይም ለምርመራ አገልግሎት መጀመር ይችላል - እያንዳንዱ የተረጋገጠ ISO ማቅረቢያ ማውጫውን ይፈልጋል፣ እና ጽናት በማይኖርበት ጊዜ ወይም የድጋሚ አጫውት የዘላቂ ስረዛ ምልክት ወይም የበለፀገ ሪከርድ መፃፍ ሳይሳካ ሲቀር እንደገና ሊሞከር የሚችል `503 Service Unavailable` ይመልሳል።

### የተሳታፊ ፈቃድ እና የሕይወት ዑደት ባለቤትነት {#participant-authorization-and-lifecycle-ownership}

## Kaigi ክፍለ-ጊዜዎች {#kaigi-sessions}

Kaigi የሚከፈልበት፣ የእውነተኛ ጊዜ ኦዲዮ/ቪዲዮ ክፍሎችን በ SORA Nexus ያቀርባል። አንድ መተግበሪያ በብሎክቼይን የተደገፈ የክፍለ ጊዜ መፍጠር፣ የስም ዝርዝር ለውጦች፣ ቴክኒካል ማኒፌስቶችን ማስተላለፍ፣ ኢንክሪፕት የተደረገ ምልክት እና የአጠቃቀም መለኪያ ሲፈልግ ይጠቀሙበት።

ከብሎክቼይን መዝገብ የሕይወት ዑደት ጋር ያለው መስተጋብር -

- `CreateKaigi` በጎራ ስር ጥሪ ይፍጠሩ እና ፖሊሲውን፣ መርሃ ግብሩን፣ ሜታዳታውን እና አማራጭ ቅብብሎሽ ቴክኒካል ማኒፌስት ያከማቹ።
- `JoinKaigi` የጥሪ ዝርዝሩን ያዘምኑ። በ`zk-roster-v1` ሁነታ፣ የህዝብ ጥሪ እይታ ከተሳታፊ መለያ መታወቂያዎች ይልቅ ክሪፕቶግራፊያዊ ኮሚትመንቶችን እና የዋጋ ቆጠራዎችን ያሳያል።
- `LeaveKaigi` ተሳታፊን ከግልፅ ጥሪ ያስወግዱ። የግል ሁነታ መነሳት በመጀመሪያ የተለቀቀው ፕሮቶኮል ውስጥ ከሰንሰለት ውጪ ነው።
- `RecordKaigiUsage` የሚለካውን የቆይታ ጊዜ እና የግብይት ማስፈጸሚያ ወጪ ድምርን ያክሉ።
- `EndKaigi` ክፍለ-ጊዜውን ይዝጉ እና የመጨረሻውን የጊዜ ማህተም ይመዝግቡ።

Torii የሚከተሉትን የመተግበሪያ ፊት ለፊት ያጋልጣል

|መንገድ|ማረጋገጫ|ዓላማ|
| ----------------------------------- | --------------------------------------- | ------------------------------------------ |
|`/v1/kaigi/calls/{call_id}`|የህዝብ|የአሁኑ የጥሪ መዝገብ|
|`/v1/kaigi/calls/{call_id}/signals`|ነጠላ ፕሮቶኮል-መደበኛ ትክክለኛ-አውታረ መረብ መለያ ጥያቄ|ገፆች የተጠናቀቀ የምልክት ሜታዳታ|
|`/v1/kaigi/calls/{call_id}/events`|ነጠላ ፕሮቶኮል-መደበኛ ትክክለኛ-አውታረ መረብ መለያ ጥያቄ|የሕይወት ዑደት ዥረት ይደውሉ|

መተግበሪያው API መንቃት አለበት። የማስተላለፊያ ማጠቃለያ እና የጤና መስመሮች ምንም እንኳን ተነባቢ ብቻ ቢሆኑም የኦፕሬተር ገጽታዎች ናቸው። ያልተፈረመ `curl` ጥያቄ ነው። ትክክለኛ ተገኝነት ምርመራ አይደለም። የክፍለ-ጊዜ ሁኔታ እንደ `KaigiRosterSummary`፣ `KaigiRelayManifestUpdated`፣ `KaigiRelayHealthUpdated` እና `KaigiUsageSummary` ባሉ Kaigi ጎራ ክስተቶች ይንጸባረቃል።

### CLI የየመጀመሪያ የስራ ሙከራ {#cli-smoke-test}

UI ከማገናኘትዎ በፊት የ Torii API የመጨረሻ ነጥብ Kaigi ግብይቶችን መቀበሉን ማረጋገጥ ሲፈልጉ በ`iroha app kaigi` CLI ይጀምሩ። የፈጣን ጅምር ትዕዛዙ ከተዋቀረው API የመጨረሻ ነጥብ ጋር አንድ ክፍል ይፈጥራል እና የጥሪ መለያውን ያትማል እና ሜታዳታን ይቀላቀሉ -

```bash
iroha app kaigi quickstart \
  --domain kaigi.universal \
  --summary-out kaigi-summary.json
```

ለስክሪፕት ፍሰቶች የክፍሉን የሕይወት ዑደት በግልፅ ያስተዳድሩ -

```bash
iroha app kaigi create \
  --domain kaigi.universal \
  --call-name daily \
  --host <i105-account-id> \
  --privacy-mode transparent \
  --room-policy authenticated

iroha app kaigi join \
  --domain kaigi.universal \
  --call-name daily \
  --participant <i105-account-id>

iroha app kaigi leave \
  --domain kaigi.universal \
  --call-name daily \
  --participant <i105-account-id>

iroha app kaigi record-usage \
  --domain kaigi.universal \
  --call-name daily \
  --duration-ms 120000 \
  --billed-gas 1500

iroha app kaigi end --domain kaigi.universal --call-name daily
```

ማስተላለፊያዎች ያለ ተመልካች ትኬቶች ሊያጋልጡ ለሚችሉ ክፍሎች `--room-policy public`ን ይጠቀሙ፣ ወይም `--room-policy authenticated` መውጫዎች የተመልካች ማረጋገጫ ሲፈልጉ ነው። `--privacy-mode zk-roster-v1`ን ከ በኋላ ብቻ ይጠቀሙ አውታረ መረብ የ Kaigi ዝርዝር እና የአጠቃቀም ማረጋገጫ ቁልፎች የተዋቀሩ አሉት። ያለበለዚያ በዲተርሚኒስቲክ ማረጋገጫ ወቅት ይቀላቀላሉ፣ ቅጠሎች እና የግል አጠቃቀም መዝገቦች አይሳኩም።

### JavaScript ማስተባበር {#javascript-integration}

የአሁኑ [Iroha JavaScript ቅንጭብ ማሳያ](https://github.com/soramitsu/iroha-demo-javascript) ግልጽ እና የተረጋገጠ የአንድ ለአንድ ስብሰባ መገለጫ ተግባራዊ ያደርጋል። ፕሮቶኮሉን አያጋልጥም `zk-roster-v1` የማረጋገጫ ፍሰት. የእሱ አቅራቢ ይፈጥራል WebRTC አቅርቦቶች እና መልሶች, የአካባቢውን ልዩ ድልድይ ሲጠቀሙ [`@iroha/iroha-js`](https://github.com/hyperledger-iroha/iroha/tree/0010c5a70039eac101a4846499ba9ceaf43eb65c/javascript/iroha_js) ለመጥቀስ፣ ለመፈረም፣ ለማስገባት እና እስኪጠናቀቅ ድረስ ይጠብቁ Kaigi ግብይቶች.

ለትክክለኛው የመንገድ ማረጋገጫ፣ የግብዣ ቅርጸት፣ የድልድይ ድንበር እና የአሁኑን የማሳያ ሙከራ ትዕዛዞች [በ JavaScript መተግበሪያ ውስጥ Kaigi ን መክተት](/am/guide/tutorials/kaigi.md)ን ይመልከቱ።

የሁኔታው እና መለኪያዎች API የመጨረሻ ነጥቦች ወደ ዳሽቦርዶች ለመገናኘት የመጀመሪያዎቹ ነገሮች ናቸው -

- `/status` ከፍተኛ ደረጃ የአውታረ መረብ አቻ፣ ብሎክ፣ ወረፋ እና የጋራ መግባባት መስኮችን ያጋልጣል
- `/metrics` የፕሮሜቲየስ ቆጣሪዎችን፣ መለኪያዎችን እና ሂስቶግራሞችን ያጋልጣል

በ Nexus የነቁ አንጓዎች ላይ፣ የሁኔታ ውፅዓት የማስፈጸሚያ መስመር እና የውሂብ-ቦታን የሚያውቁ ክፍሎችንም ያካትታል። `nexus.enabled = false` ሲሆኑ እነዚያ ክፍሎች ይተዋሉ።

## JSON ከ Norito {#json-vs-norito}

በርካታ ኦፕሬተር API የመጨረሻ ነጥቦች በነባሪነት Norito ይመለሳሉ። API የመጨረሻ ነጥብ JSON ን ሲደግፍ ላክ

```http
Accept: application/json
```

ይህ በተለይ ለሚከተሉት ጠቃሚ ነው-

- `/v1/sumeragi/status`
- `/v1/sumeragi/qc`

የ API የመጨረሻ ነጥብ የተተየበውን Norito በቀጥታ ሲቀበል ወይም ሲመልስ፣ `application/x-norito`ን እንደ የይዘት አይነት ወይም ተመራጭ `Accept` እሴት ይጠቀሙ። ለማጓጓዣ ዝርዝሮች [Norito](/am/reference/norito.md#torii-and-norito-rpc)ን ይመልከቱ።

## የቴሌሜትሪ መገለጫዎች {#telemetry-profiles}

API የመጨረሻ ነጥብ ታይነት በኖድ `telemetry.profile` ቅንብር ላይ የተመሰረተ ነው።. የአሁኑ ውቅር አምስት ያጋልጣል ደረጃዎች -

|ባንድ በኩል የሆነ መልክ|`/status`|`/metrics`|የገንቢ መንገዶች|
| ----------- | --------- | ---------- | ---------------- |
|`disabled`|አይ|አይ|አይ|
|`operator`|አዎ|አይ|አይ|
|`extended`|አዎ|አዎ|አይ|
|`developer`|አዎ|አይ|አዎ|
|`full`|አዎ|አዎ|አዎ|

## CLI አቋራጮች {#cli-shortcuts}

`iroha` CLI ከእነዚህ API የመጨረሻ ነጥቦች ውስጥ ብዙዎቹን ጠቅልሏል -

```bash
export IROHA_OPERATOR_KEY_FILE=/run/secrets/iroha/operator.key

iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  --output-format text ops sumeragi status
iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  --output-format text ops sumeragi diagnostics
iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  ops sumeragi params
iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  --output-format text ops sumeragi evidence count
```
