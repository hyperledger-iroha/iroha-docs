# I105 የሂሳብ አድራሻ ቅርጸት {#i105-account-address-format}

I105 ነው የ Canonical ውጫዊ ጽሑፍ ቅርጸት አንድ Iroha 3 `AccountId`.

የእሱ ተጠቃሚ ጭነት የሂሳብ መቆጣጠሪያውን ይወክላል.

የእሱ ጠባቂ የተፈለገውን አውታረመረብ ሰንሰለት ልዩነት ጋር ይለያል.

API፣ ግብይት፣ ፈቃድ ወይም ጥያቄ ለካኖኒካል መለያ ID በሚጠይቅበት ቦታ ሁሉ ይጠቀሙበት።

የ I105 መለያ ID ጎራ የሌለው ነው።

እንደ `treasury@payments.universal` ያለ እሴት የሂሳብ ስያሜ ነው ፣ የ I105 ID ሌላ ፊደል ሳይሆን ።

I105 ID መውሰድ መለያውን አይመዘገብም ወይም አያስተዳድርም።

::: warning አብዛኛዎቹን የውህደት ውድቀቶች የሚከላከሉ ህጎች

- አንድን አድራሻ ከማስመሰል ወይም ከማረጋገጫ በፊት የኔትወርክ መገለጫውን ይምረጡ።
- የ UTF-8 ቀመርን በትክክል ያስቀምጡ እና ያነፃፅሩ.
- የፊደሎችን አቢይና ንዑስ ሆሄ ሁኔታ ይጠብቁ እና የ `Unicode` መደበኛነትን አይተግብሩ።
- አንድ I105 ID የ `@domain` ወይም `@domain.dataspace` ፊደል ሊኖረው አይገባም።
- Iroha SDK ወይም `iroha tools address` የሚለውን ይጠቀሙ።
- መደበኛ መግለጫ I105 ማረጋገጫ አይደለም.

:::

## የፊደል አናቶሚ {#literal-anatomy}

የ I105 ፊደላት ሶስት ተጓዳኝ ክፍሎች እና ምንም መለዋወጫ የላቸውም:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

|ክፍል |ዓላማ|የቼክ መጠን ሽፋን |
| ---------------- | ------------------------------------------------------------------ | ----------------- |
|የአውታረ መረብ ጠባቂ |ጽሑፉን ወደ አንድ `u16` ሰንሰለት ልዩነት ያቀርባል |አልተሸፈነም|
|የዋጋ ጭነት|`base-105` የካኖኒካዊ የሂሳብ መቆጣጠሪያ ባይት ኮድ ማድረግ |የተሸፈነ|
|የቼክ መጠን |ስድስት `Bech32m` ቅርጸት ያላቸው `5-bit` እሴቶች በ I105 ፊደል የተገለጹ ናቸው |N/A |

የፍጆታ ጭነት እና የቁጥጥር መጠን የሂሳብ አስተዳዳሪን ያመለክታል።

ጠባቂው የአውታረ መረቡን አውድ ይመርጣል።

ተመሳሳይ መቆጣጠሪያ Taira እና Minamoto ላይ አንድ ዓይነት ጥቅማጥቅም ጭነት እና ቁጥጥር መጠን አለው ፣ ግን እያንዳንዱ አውታረመረብ የተለየ መሪ ጠባቂን ይጠቀማል ።

አንድ ዲኮደር የሚጠበቀው ልዩነት ማስፈፀም አለበት.

የቼክ አኃዝ የ Sentinel ምትክ መፈለግ አይችሉም.

### የአውታረ መረብ ጠባቂዎች {#network-sentinels}

|የአውታረ መረብ ወይም አውድ |ሰንሰለት መለያየት | ሄክስ|የካኖኒካል ጠባቂ|
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
|Taira የህዝብ ፈተና ኔት |                            `369` |`0x0171` |`test` |
|Minamoto የህዝብ አውታረመረብ |                            `753` |`0x02f1` |`sora` |
|የልማት አውድ |                              `0` |`0x0000` |`dev` |
|ሌላ ማንኛውም `u16` ዋጋ |ሁሉም `0` ፣ `369` እና `753` በስተቀር |        — |`n` እና አነስተኛ አሥረኛ, ለምሳሌ `n42` |

የተሰየሙት እሴቶች ሁል ጊዜም የተሰየመውን ጠባቂ ይጠቀማሉ ።

እንደ `n00042`, `n369`, `n753` እና `n0` ያሉ ቅጾች ቀኖናዊ አይደሉም ።

የግብይት ሰንሰለት ID እና I105 ሰንሰለት ልዩነት የተለያዩ እሴቶች ናቸው ።

የመጨረሻ ነጥብ ወይም ሰንሰለት ID መምረጥ የአድራሻውን መገለጫ በግልጽ አይመርጥም።

## የአንድ ቁልፍ ደንብ ምሳሌ {#normative-single-key-example}

ከዚህ በታች ያለው የዋጋ ጭነት እና Minamoto ቅጽ ከ SDK መስቀለኛ ማሟያ ቅንብር የተገኙ ናቸው ።

የ Taira ቅጽ የ Taira ጠባቂን በተመሳሳይ አጠቃቀም ጭነት ላይ ይተግብራል:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

የካኖኒክ ጥቅማጥቅሞች በ `02 00 01 20`: አርዕስት `0x02`, የታመቀ ነጠላ ቁልፍ መለያ `0x00`, `Ed25519` አዙሪት ID `0x01`, እና የ 32 ባይት ቁልፍ ርዝመት `0x20`.

የ `multihash` ቅድመ-ጽሑፍ የመግቢያ ሜታዳታ ነው እና ወደ ተቆጣጣሪ ጥቅማጥቅሞች ውስጥ አይገለብጥም.

## በ CLI አማካኝነት IDs ይፍጠሩ እና ይፈትሹ። {#create-and-inspect-ids-with-the-cli}

ለህዝብ አውታረመረብ የተሰየመ መገለጫን ይመርጣሉ

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

የአድራሻ-ኮዴክ ባህሪን በሚመረምሩበት ጊዜ የ I105 ግብዓት መደበኛ እና አወዳድር:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

የተፈለገውን ቅርጸት፣ ካኖኒካል ሄክስ እና የተመረጠውን የአውታረ መረብ አውድ እንደ JSON ይፈትሹ:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

በአዲስ መስመር የተለዩ ፋይሎች አድራሻ-ኮዴክ መዋቅርን ያለ ትንታኔ ስህተቶች በዝምታ መቀበል:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution CLI የማረጋገጫ ገደብ

`convert`, `normalize`, እና `audit` ትዕዛዞች በዝቅተኛ ደረጃ `AccountAddress` ኮዴክ ላይ ይሰራሉ.

እነሱ ጠባቂ ፣ ፊደል ፣ የቼክ አኃዝ ፣ የባይት ርዝመቶች ፣ `CurveId` / ቁልፍ ቅርፅ እና ትክክለኛ የአድራሻ ንብርብሮች ዳግም ምስጠራን ያረጋግጣሉ ።

እነሱ `AccountId` አይሆኑም.

እነዚህ በራሳቸው ሁሉንም ባለብዙ ምልክት ፖሊሲ ትርጓሜዎችን አያረጋግጡም ።

የራስጌው ክፍል ከመቆጣጠሪያው ጋር መዛመዱን አያረጋግጡም።

ከፈቃድ መስጠት ወይም ከማከማቸት በፊት ጥብቅ `AccountId` ማረጋገጫ ይጠቀሙ።

:::

ለግል አውታረመረብ በ `--network-prefix` ላይ በግልጽ የተዋቀረውን ልዩነቱን ይጠቀሙ።

አንድ ነባር አድራሻ ከገለጹ አውድሮች መካከል ሲቀየር ምንጩን `--expect-prefix` ጋር ያቅርቡ

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

ዳግም ኮድ ማድረግ የአውታረ መረብ አውድ ብቻ ይለውጣል።

በዒላማው አውታረመረብ ላይ ያለውን ሂሳብ አይመዘገብም ወይም በዚያ ተመሳሳይ ተቆጣጣሪ እንደገና ጥቅም ላይ መዋል እንዳለበት አያረጋግጥም ።

## የኮዲንግ ስልተ ቀመር {#encoding-algorithm}

የካኖኒካል ኮዴሮች የሚከተሉትን ተግባራት ያከናውናሉ።

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

ቀዳሚ ዜሮ ባይቶች እንደ ዜሮ ዋጋ ያላቸው `base-105` አሃዞች ይጠብቃሉ።

የቼክ አኃዝ `Bech32` `polymod` ማመንጫዎችን እና ቋሚ `0x2bc830a3` ይጠቀማል.

የቁጥጥር መጠን ብቻ HRP የ ASCII ሰንጠረዥ `snx` ነው።

የቼክ ቁጥር ብቻ HRP በአድራሻው ላይ አይታተምም።

ስድስቱ የቼክ አሃዝ እሴቶች በ `0..31` ክልል ውስጥ የሚገኙ ሲሆን ከጠቅላላው ጭነት ጋር ተመሳሳይ በሆነው I105 ፊደል አማካኝነት ይሰጣሉ።

### I105 ፊደል {#i105-alphabet}

105ቱ ምልክቶች በዚህ ቅደም ተከተል ተዘርዝረዋል።

የመጀመሪያው ረድፍ `Bitcoin Base58` ፊደል ሲሆን `0..57` ቁጥሮችን ይ containsል።

በሁለተኛው ረድፍ ላይ `58..104` ቁጥሮች ይገኛሉ።

ኮዴክን በሚተገበሩበት ጊዜ ረድፎቹን ያገናኙ።

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

ፊደሉ ለ `Unicode` የተጋለጠ ነው።

ትክክለኛው ቅደም ተከተል `compatibility-width` የጃፓንኛ `kana` ምልክቶችን እና ለ `ヰ` እና `ヱ` የቀረቡትን ኮድ ነጥቦች ይጠቀማል ።

NFC፣ NFKC፣ የስፋት ልወጣ፣ የአቢይ/ንዑስ ፊደል ማጠፍ ወይም ተመሳሳይ መልክ ባለው ቁምፊ መተካት አይተግብሩ።

ASCII `0`, `O`, `I` እና `l` ፊደል ምልክቶች አይደሉም.

## የካኖኒካል ሂሳብ አጠቃቀም {#canonical-account-payload}

የ `base-105` አካሉ ለሁለትዮሽ ሂሳብ ጥቅማጥቅሞች ኮድ ይሰጣል ፣ የህዝብ ቁልፍ ገመድ አይደለም እና የ Norito JSON ነገር አይደለም።

```text
header:u8 || controller:variable
```

ከዚህ በታች ያሉት ሁሉም ባለብዙ ባይት ሙሉ ቁጥሮች ያልተፈረሙ እና `big-endian` ናቸው።

ጎራ, የውሂብ ቦታ, ቅጽል ስሞች, UAID, እና የመለያ ሜታዳታ ባይቶች አይገኙም.

### የርዕስ ባይት {#header-byte}

|ቁርጥራጮች |ስፋት |የአሁኑ ኢንኮደር ውፅዓት |ትርጉም|
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |የአድራሻ ቅርጸት ስሪት መስክ |
| `4..3` |     2 |`0` ነጠላ ቁልፍ፣ `1` ባለብዙ ምልክት |የአድራሻ ክፍል |
| `2..1` |     2 |                          `1` |መደበኛነት ስሪት መስክ |
| `0`    |     1 |                          `0` |የተያዙት `extension flag` |

የአሁኑ V1 ኢንኮደሮች ለአንድ ቁልፍ መቆጣጠሪያ ራስጌ `0x02` እና ለብዙ ምልክት መቆጣጠሪያዎች `0x0a` አርዕስት ያወጣሉ ።

አድራሻ ክፍሎች `2` እና `3` አልተመደቡም ።

`extension flag` የ `1` ተቀባይነት አይኖረውም።

ዝቅተኛ-ደረጃ ዲኮደር ሌሎች ስሪት እና መደበኛነት ቢት እሴቶች መጠበቅ ይችላሉ, እና በራስ-ሰር መቆጣጠሪያ መለያ ጋር ክላሲክ ማጣራት አይደለም.

ወደ `AccountId` መለወጥ እና የካኖኒክ ትርጓሜውን ማወዳደር የአሁኑን V1 ካኖኒካዊነት ያረጋግጣል.

### የአንድ ቁልፍ መቆጣጠሪያ {#single-key-controller}

ጥሬ የህዝብ ቁልፍ ጥቅማጥቅሞች 255 ባይት ላይ ሲሆኑ የታመቀ ቅርጸት ይጠቀሙ:

|`tag` |1 ባይት |`0x00` |
|`curve` |1 ባይት |`CurveId` የምዝገባ ዋጋ |
|`key_len` |1 ባይት |ጥሬ ቁልፍ ርዝመት |
|`public_key` |`key_len` ባይት |ጥሬ የሕዝብ ቁልፍ አጠቃቀም ጭነት |

ከ 255 ባይት በላይ የሆኑ ቁልፎች የተራዘመውን ቅጽ ይጠቀማሉ-

|መስክ |ስፋት |ዋጋ ወይም ትርጉም |
| ------------ | --------------: | ---------------------------- |
|`tag` |1 ባይት |`0x02` |
|`curve` |1 ባይት |`CurveId` የምዝገባ ዋጋ |
|`key_len` |2 ባይት |ጥሬ ቁልፍ ርዝመት, `big-endian` |
|`public_key` |`key_len` ባይት |ጥሬ የሕዝብ ቁልፍ አጠቃቀም ጭነት |

የተራዘመ ኮዲንግ ለኮምፓክ ቅርጸት የሚስማማ ቁልፍ መደበኛ አይደለም ።

### ባለብዙ ተቆጣጣሪ {#multisig-controller}

|መስክ |ስፋት |ዋጋ ወይም ትርጉም |
| ---------------- | -------: | ------------------------------ |
|`tag` |1 ባይት |`0x01` |
|`policy_version` |1 ባይት |የአሁኑ ዋጋ `1` |
|`threshold` |2 ባይት |የሚያስፈልገው አጠቃላይ የፀደቅ ክብደት |
|`member_count` |2 ባይት |የሚከተሉትን አባላት ቁጥር |
|`members` |ተለዋዋጭ |ተደጋጋሚ የአባላት መዝገቦች |

እያንዳንዱ አባል መዝገብ የሚከተለው ነው:

|መስክ |ስፋት |ትርጉም|
| ------------ | --------------: | ------------------------ |
|`curve` |1 ባይት |`CurveId` የምዝገባ ዋጋ |
|`weight` |2 ባይት |የአባልነት ማረጋገጫ ክብደት |
|`key_len` |2 ባይት |ጥሬ ቁልፍ ርዝመት |
|`public_key` |`key_len` ባይት |ጥሬ የሕዝብ ቁልፍ አጠቃቀም ጭነት |

ትክክለኛ ፖሊሲ ቢያንስ አንድ አባል፣ አዎንታዊ ክብደቶች፣ ያልተደጋገሙ የሕዝብ ቁልፎች እና ከ `1` እስከ የአባላት ክብደት ድምር ያለ ገደብ አለው።

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

የካኖኒካል ኮንስትራክሽን አባላት በፊርማ ስልተ ቀመር የተረጋጋ ስም ፣ ዜሮ ተለቃባይት እና ከዚያ ጥሬ የህዝብ ቁልፍ ባይቶች ይለያያሉ ።

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

አንድ I105 ፊደላት ቋሚ ቁምፊ ርዝመት የለውም ምክንያቱም ባለብዙ ምልክት እና የፖስት-ኳንቲም ተቆጣጣሪዎች ትልቅ ሊሆኑ ይችላሉ.

አሻራ ማለት የምዝገባው መግቢያ ያለ አማራጭ የመረጃ ሞዴል ባህሪ ይገኛል ማለት ነው።

ቁልፉ ጥቅም ላይ የሚውለው ጭነትም በ `CurveId` የተገለጸው ስልተ ቀመር ለሚመረጠው ስልተ ቀመሩ መዋቅራዊ ትክክለኛ መሆን አለበት ።

## ጥብቅ AccountId ማረጋገጫ እና ካኖኒካዊነት {#strict-accountid-validation-and-canonicality}

SDK ከተጠበቀው ሰንሰለት መለያ ጋር ከተዋቀረ በኋላ ወደ `AccountId` ይገመግሙ እና የተመለሰውን የካኖኒካል ማቅረቢያ ከታነሰ ግብዓት ጋር ያወዳድሩ ።

ማነፃፀሩ አስፈላጊ ነው ምክንያቱም መርማሪው `AccountId` ን በሚገነባበት ጊዜ ሊፈታ የሚችል መቆጣጠሪያ ቁሳቁስ መደበኛ ማድረግ ይችላል ።

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

ለማይታመን ገመድ ተስማሚ የሆነ አፕሊኬሽን የሚከተለውን ማድረግ አለበት

1. ትሪም ሙሉውን ዋጋ ዙሪያ ብቻ ነጭ ቦታን ለማጓጓዝ ፈቀደ።
2. ጠባቂውን ያንብቡ እና የሚጠበቀው ሰንሰለት ልዩነት ያስፈልግዎታል.
3. የቀሩትን `Unicode` ምልክቶች በሙሉ በትክክል በ105 ምልክት ፊደላት ውስጥ ካስቀመጡ በኋላ ያግኙ።
4. ስድስቱ የቼክ አኃዝ ቁጥሮች ይከፋፍሉ.
5. የጠቅላላ ጭነት ቁጥሮችን ወደ ቀኖናዊ ባይት ይለውጡ.
6. በካኖኒካል ባይቶች ላይ ያለውን የቼክ አኃዝ ያረጋግጡ ።
7. ራስጌውን እና መቆጣጠሪያውን ይገመግሙ፣ የሚከተሉትን ይጠይቃሉ፦
   - ትክክለኛ የመስክ ርዝመት
   - የተደገፈ `CurveId`
   - ትክክለኛ የሕዝብ ቁልፍ
   - ምንም የኋላ ባይት የለም
   - ተፈጻሚነት ያለው ባለብዙ ፊርማ ፖሊሲ
8. አንድ `AccountId` ይገንቡ.
9. `AccountId` የሚጠበቅበትን ልዩነት በካኖኒካዊ መንገድ ያቅርቡ ።
10. ከተከረከመው ግብዓት ጋር `byte-for-byte` እኩልነትን ይጠይቁ።

የማመልከቻው ግልፅ የመጨረሻ ደረጃ `render-and-compare` ዝቅተኛ ያልሆኑ የቁጥር ጠባቂዎችን ፣ ቀኖናዊ ያልሆኑ ተቆጣጣሪ አቀማመጦችን ፣ እንደገና የተደራጁ ፖሊሲ ቁሳቁሶችን እና ማንኛውንም ሌላ የአጻጻፍ አጻጻፍ ውድቅ ያደርጋል ፣ ነገር ግን የኮዲንግ ወቅታዊ V1 ውጽዓት አይደለም ።

ስኬታማ የሆነ የቼክ አኃዝ ወይም ዝቅተኛ ደረጃ `AccountAddress` ትንታኔ የዚህን ፍተሻ አይተካም።

እነዚህን እሴቶች በጥብቅ የሂሳብ- ID መስክ ውስጥ አይቀበሉ:

- እንደ `alice@wonderland.universal` ያለ የሂሳብ ስያሜ
- አንድ I105 ፊደላት እና ተያይዘው የገቡት `@domain` ቅደም ተከተል
- የህዝብ ቁልፍ `multihash` እንደ `ed0120...`
- እንደ `0x02000120...` ያሉ የካኖኒክ የፍጆታ ጭነት hex
- የተሳሳተ ሰንሰለት ልዩነት አድራሻ
- አቢይ ወይም ንዑስ ፊደሎች፣ የቁምፊ ስፋቶች፣ `kana`፣ የፍጆታ ጭነት ወይም የቼክ ድምር የተቀየረበት ሕብረቁምፊ

በመተግበሪያው ወሰን ላይ ቅጽል ስሞችን መፍታት እና ለተፈቀደላቸው, ለመፈረም, ለፍቃዶች እና ለኦዲት መዝገቦች የተመለሰውን የካኖኒካል I105 ID መያዝ.

## API፣ የማከማቻ እና የማሳያ ደንቦች {#api-storage-and-display-rules}

- በ JSON የሂሳብ መስኮች ውስጥ ትክክለኛውን I105 UTF-8 ሰንጠረዥ ይላኩ.
- `Percent-encode` በ URL መንገድ ክፍል ውስጥ ከማስቀመጥዎ በፊት የተሟላውን ሂሳብ ID።
- የሂሳብ ስያሜ በ I105 ID ምትክ በጭራሽ አይጠቀሙ።
- በኮዴክ የተመለሰውን የካኖኒካል ገመድ ከ `byte-preserving` ማወዳደር ትርጓሜ ጋር ያከማቹ።
- የፊደላትን አቢይ/ንዑስ ሁኔታ እና የቁምፊዎችን ስፋት የሚጠብቅ የማነጻጸሪያ ደንብ ይጠቀሙ።
- የውጭ ሂሳብ ውሂብ እና ምትኬዎች ጋር ሰንሰለት ልዩነት ወይም የተሰየመ አውታረ መረብ መገለጫ ይያዙ.
- አንድ አድራሻ ከኔትወርክ አውድ ጋር ብቻ እንደገና ይጠቀሙ።
- የተሟላውን አድራሻ ማሳየት እና የቅጂ እርምጃን መስጠት።
- እያንዳንዱን `kana` ቁምፊ በትክክል ይጠብቁ.
- የታመቀ ማሳያ መካከለኛውን ክፍል ሲያሳጥር ሙሉውን አድራሻ እንዲገኝ ያድርጉ።
- ከቅጽል ስም እንደገና ከመገንባት ይልቅ የተከማቸውን ካኖኒካል ID ይጠቀሙ።

የ `AccountId` ማሳያ እና JSON ካኖኒካል I105 ይጠቀማሉ።

የዝቅተኛ ደረጃ `AccountAddress` ማሳያ/JSON ውክልና ለውስጣዊ እና debugging አውድ ቀኖናዊ hex ይጠቀማል.

ውጫዊ መለያ ID ሲያስፈልግ ግልፅ የሆነውን `AccountAddress` I105 ኢንኮደር ይደውሉ።

የሂሳብ መፍጠር እና የማጠራቀሚያ አፈፃፀም የሥራ ፍሰቶች በ [ሂሳቦች እና ማጠራቀሚያዎች ](/am/cookbook/accounts-and-aliases.md) ይቀጥሉ.

የሂሳብ መረጃ ሞዴል ለማግኘት [ሂሳብ](/am/blockchain/accounts.md) ይመልከቱ።
