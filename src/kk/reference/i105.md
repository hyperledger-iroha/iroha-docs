# I105 Есепті мекенжайдың форматы {#i105-account-address-format}

I105 - Iroha 3 `AccountId` үшін каноникалық сыртқы мәтін форматы.

Оның пайдалы жүктемесі есептік жазбаны басқарушы болып табылады.

Оның күзетшісі жоспарланған желіді тізбекті ажыратушымен анықтайды.

Оны API, транзакция, рұқсат немесе сұрау салу ID үшін каноникалық шотты сұраған кез-келген жерде қолдану.

I105 тіркелгісі ID доменсіз.

`treasury@payments.universal` сияқты мән — I105 ID-дің басқа жазылуы емес, тіркелгі бүркеншік аты.

I105 ID түсімін алу тіркелмейді немесе шотты қаржыландырмайды.

::: warning Интеграцияның көпшілік сәтсіздіктерін болдырмайтын ережелер

- Адресті кодтау немесе бекітуден бұрын желі профилін таңдаңыз.
- Қаноникалық UTF-8 жіпті дәл сақтау және салыстыру.
- Әріптердің үлкен-кішілігін сақтаңыз және `Unicode` қалыпқа келтіруін қолданбаңыз.
- Қалған I105 ID болуы тиіс емес `@domain` немесе `@domain.dataspace` жұрнақ.
- Iroha SDK немесе `iroha tools address` белгілерін қолдану.
- Тұрақты өрнек I105 валидаторы емес.

:::

## Жазу анатомиясы {#literal-anatomy}

I105 сөз тіркесінің үш жапсарлас бөлігі бар және бөлектеуші жоқ:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

|Бөліні |Мақсаты |Тексеру сомасының қамтуы |
| ---------------- | ------------------------------------------------------------------ | ----------------- |
|Желілік күзетші |Мәтінді `u16` тізбектік айырмашылыққа орнату |Қапталмаған |
|Пайдалы жүк|`base-105` каноникалық есеп жүргізуші байттерін кодтау |Қапталған |
|Тексеру сомасы |I105 әліпбиімен берілген алты `Bech32m` стильдегі `5-bit` мәндер |N/A |

Пайдалы жүктеме мен тексеру сомасы шот бақылаушысын анықтайды.

Күзетші желілік контекстті таңдайды.

Бір контроллер Taira және Minamoto желілерінде бірдей пайдалы жүктеме мен бақылау сомасына ие, бірақ әрбір желі әртүрлі жетекші күзетшіді пайдаланады.

Декодер күтілетін дискриминанттың сәйкестігін міндетті түрде қамтамасыз етуі тиіс.

Тексеру жиынтығы күзетші алмастыруын анықтамайды.

### Желідегі күзетшілер {#network-sentinels}

|Желі немесе контекст |Желілік айырмашылық |Гекс |Canonical Sentinel |
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
|Taira мемлекеттік тест желісі |                            `369` |`0x0171` |`test` |
|Minamoto қоғамдық желі |                            `753` |`0x02f1` |`sora` |
|Дамуындағы жағдай |                              `0` |`0x0000` |`dev` |
|Басқа кез келген `u16` мәні |Олардың барлығы `0`, `369` және `753` қоспағанда|        — |`n` қосылған ең төменгі ондық, мысалы `n42` |

Аталған мәндер әрдайым өздерінің аталатын күзетшісін пайдаланады.

`n00042`, `n369`, `n753` және `n0` сияқты нысандар каноникалық емес.

Транзакция тізбекінің ID және I105 тізбектің айырмашылығы бөлек мәндер болып табылады.

Аяқ нүктесін немесе тізбекті ID таңдау адрестік профильді жасырын түрде таңдамайды.

## Нормативтiк бiр кілт мысалы {#normative-single-key-example}

Төмендегі пайдалы жүктеме және Minamoto нысаны SDK көлденең сәйкестік белгісінен келеді.

Taira нысанында Taira нөкері сол жүкке қолданылады:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

Қаноникалық пайдалы жүктеме `02 00 01 20`: баған `0x02`, компактты бір кілті тегі `0x00`, `Ed25519` қиылысы ID `0x01` және 32-байттық кілттің ұзындығы `0x20` арқылы басталады.

`multihash` префиксі кіріс метамәліметтері болып табылады және бақылаушының пайдалы жүктемесіне көшірілмейді.

## IDs түрін CLI түрінде жасау және тексеру {#create-and-inspect-ids-with-the-cli}

Қоғамдық желі үшін аталмыш профильді артық көремін:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

Адрес-кодек мінез-құлқын диагностикалай отырып, I105 кірісін қалыпқа келтіру және салыстыру:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

Белгіленген форматты, каноникалық шегін және таңдалған желілік контекстті JSON ретінде тексеріңіз:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

Жаңа сызықпен бөлінген файлдың адрестік-кодек құрылымын үнсіз талдау қателерін қабылдамай тексеру:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution CLI жарамдылық шегі

`convert`, `normalize` және `audit` командалары төменгі деңгейдегі `AccountAddress` кодекпен жұмыс істейді.

Олар күзетшінің, әліпбидің, чексумның, байт ұзындығының, `CurveId` / кілттің пішінінің және адрестік қабаттың нақты қайта кодтауын тексереді.

Олар `AccountId` нысанын жасамайды.

Олар өздері барлық көп қолтаңбалы саясаттың семантикасын растамайды.

Олар басқыштың класы контроллермен сәйкес келетінін дәлелдей алмайды.

Авторизациялау немесе тұрақты сақтауға жазу алдында `AccountId` қатаң тексеруін қолданыңыз.

:::

Жеке желі үшін оның конфигурацияланған айырмашылығын `--network-prefix` белгісімен айқын пайдалану.

Қолданыстағы мекен-жайларды айқын контексттер арасында аудару кезінде `--expect-prefix` дегенді де келтіріңіз:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

Қайта кодтау желілік контекстті ғана өзгертеді.

Ол мақсатты желідегі шотты тіркемейді немесе сол бақылаушыны қайта пайдалану керектігін дәлелдей алмайды.

## Шифрлау алгоритмі {#encoding-algorithm}

Canonical кодерлері мынадай операцияларды орындайды:

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

Алдыңғы нөлдік байттар нөлдік `base-105` цифрлар ретінде сақталады.

Тексеру сомасына `Bech32` `polymod` генераторлары мен тұрақты `0x2bc830a3` қолданылады.

Тек тексеру сомасы HRP - ASCII тізбекті `snx`.

Тек тексеру сомасы HRP мекенжайда басып шығарылмаған.

Алты бақылау сомасы `0..31` диапазонында болады және пайдалы жүкпен бірдей I105 әліпбимен көрсетіледі.

### I105 әліпбиі {#i105-alphabet}

105 символ дәл осы ретпен индекстеледі.

Бірінші жол - `Bitcoin Base58` әліпбиі және онда `0..57` цифрлары бар.

Екінші қатарда `58..104` сандары бар.

Кодекті іске асыру кезінде қатарларды конкатенаттайтыңыз.

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

Әліпби `Unicode` -ға тән.

Нақты реттілік `compatibility-width` жапондық `kana` символдарын және `ヰ` және `ヱ` код нүктелерін пайдаланады.

NFC, NFKC, енді түрлендіруді, әріп регистрін бүктеуді немесе ұқсас таңбамен алмастыруды қолданбаңыз.

ASCII `0`, `O`, `I` және `l` - бұл әліпбилік символдар емес.

## Каноникалық шоттың пайдалы жүктемесі {#canonical-account-payload}

`base-105` тетігі бинарлық шоттың пайдалы жүктемесін кодтайды, ол мемлекеттік кілтті жіп емес және Norito JSON объектісі емес:

```text
header:u8 || controller:variable
```

Төмендегі барлық көп байтты бүтін сандар қолтаңбаланбаған және `big-endian`.

Домен, деректер кеңістігі, псевдонимы, UAID және шот метамәдени байттар жоқ.

### Бапшықтың байты {#header-byte}

|Беттер |Кеңісі |Ағымдағы кодтаушы шығысы |Мағынасы |
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |Адрес пішімінің нұсқасы |
| `4..3` |     2 |`0` бір кілт, `1` көпбелгілі |Адрес класы |
| `2..1` |     2 |                          `1` |Стандарттау нұсқасы өрісі |
| `0`    |     1 |                          `0` | Резервтелген `extension flag` |

Ағымдағы V1 кодтаушылар бір кілтілік бақылаушы үшін `0x02` және көп белгілі басқарушы үшін `0x0a` бағанды шығарады.

`2` және `3` адрестік сыныптар тағайындалмаған.

`extension flag` сомасының `1` мөлшерлемесі қабылданбайды.

Төмен деңгейдегі декодер басқа нұсқалар мен нормализация біт мәндерін сақтай алады және класты контроллер тегімен тәуелсіз аралай тексеруді жүзеге асырмайды.

`AccountId` түріне айналдыру және оның каноникалық нұсқасын салыстыру қазіргі V1 каноникалдықты дәлелдеді.

### Бір кілтті басқарушы {#single-key-controller}

Қоғамдық кілттің пайдалы жүктемесі ең көп дегенде 255 байт болған кезде компактты нысанды қолдану:

|Өрісте |Кеңісі |Құндылығы немесе мәні |
| ------------ | --------------: | ------------------------ |
|`tag` |1 байт |`0x00` |
|`curve` |1 байт |`CurveId` тіркелгі мәні |
|`key_len` |1 байт |Шикі кілттің ұзындығы |
|`public_key` |`key_len` байттар |Жалпыға ортақ кілті жүк|

255 байттан асатын кілттер кеңейтілген нысанды пайдаланады:

|Өрісте |Кеңісі |Құндылығы немесе мәні |
| ------------ | --------------: | ---------------------------- |
|`tag` |1 байт |`0x02` |
|`curve` |1 байт |`CurveId` тіркелгі мәні |
|`key_len` |2 байт |Шикі кілттің ұзындығы: `big-endian` |
|`public_key` |`key_len` байттар |Жалпыға ортақ кілті жүк|

Ұзартылған кодтау компакт формаға сәйкес келетін кілттің каноникалық емес.

### Multisig контроллері {#multisig-controller}

|Өрісте |Кеңісі |Құндылығы немесе мәні |
| ---------------- | -------: | ------------------------------ |
|`tag` |1 байт |`0x01` |
|`policy_version` |1 байт |Ағымдағы құны `1` |
|`threshold` |2 байт |Қажетті жалпы бекіту салмағы |
|`member_count` |2 байт |Төмендегі мүшелердің саны |
|`members` |Айнымалы |Қауым мүшелерінің қайталанған жазбалары |

Әрбір мүшелік жазбасы:

|Өрісте |Кеңісі |Мағынасы |
| ------------ | --------------: | ------------------------ |
|`curve` |1 байт |`CurveId` тіркелгі мәні |
|`weight` |2 байт |Қауым мүшелерінің рұқсат беру салмағы |
|`key_len` |2 байт |Шикі кілттің ұзындығы |
|`public_key` |`key_len` байттар |Жалпыға ортақ кілті жүк|

Жарамды саясатта кемінде бір мүше, оң салмақтар болуы, қайталанатын ашық кілттер болмауы және шек `1`-ден мүшелер салмақтарының қосындысына дейін болуы тиіс.

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

Каноникалық құрылыс мүшелерді қолтаңбалау алгоритмінің тұрақты атауы, нөлдік бөлгіш байты және одан кейін шикі қоғамдық кілті байттары бойынша жіктейді.

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

I105 сөз тіркесінің белгіленген таңба ұзындығы жоқ, өйткені мультисиг және посткванттық бақылаушылар үлкен болуы мүмкін.

### `CurveId` тіркелімі {#curveid-registry}

Соңғы бағанда талап етілетін `Cargo` параметрі көрсетіледі.

Тасбелгісі реестр жазуы параметрлі дерек үлгісі функциясысыз қол жетімді екенін білдіреді.

|ID |Қолтаңбалау алгоритмі |Қажетті `Cargo` белгісі |
| ---: | -------------------------------------------- | ------------------------ |
|  `1` |`Ed25519` | —                        |
|  `2` |`ML-DSA` | —                        |
|  `3` |`BLS12-381 normal` |`bls` |
|  `4` |`secp256k1` | —                        |
|  `5` |`BLS12-381 small` |`bls` |
| `10` |`GOST R 34.10-2012 256-bit, parameter set A` |`gost` |
| `11` |`GOST R 34.10-2012 256-bit, parameter set B` |`gost` |
| `12` |`GOST R 34.10-2012 256-bit, parameter set C` |`gost` |
| `13` |`GOST R 34.10-2012 512-bit, parameter set A` |`gost` |
| `14` |`GOST R 34.10-2012 512-bit, parameter set B` |`gost` |
| `15` |`SM2` |`sm` |

Белгісі жоқ IDs және қабылдау құрамында рұқсат етілмеген алгоритмдер қабылданбайды.

Кілттің пайдалы жүктемесі де `CurveId` мәлімделген алгоритм үшін құрылымдық жарамды болуы тиіс.

## Қатаң AccountId растау және каноникалдық {#strict-accountid-validation-and-canonicality}

SDK тізбекті таңбалаушы элементпен конфигурациялағаннан кейін, `AccountId` түріне талдау жасап, қайтарылған каноникалық рендерлеуді қысқартылған кіріспен салыстыру керек.

Салыстыру маңызды, өйткені талдаушы `AccountId` конструкциясын жасау кезінде декодируға болатын контроллер материалдарын қалыпқа келтіре алады.

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

Сенімсіз жиек үшін сәйкесті қосымша:

1. Трим тек толық құнның айналасында ғана тасымалдауға рұқсат берді.
2. Сентинелді оқып, күтілетін тізбек дискриминантын талап етіңіз.
3. Қалған әрбір `Unicode` таңбасын 105 таңбалы әліпби арқылы картаға түсіріңіз.
4. Бақылау сомасының алты цифрын бөліп алыңыз.
5. Пайдалы жүктеме цифрларын қаноникалық байтқа қайтару.
6. Қаноникалық байттар бойынша тексеру сомасын тексеріңіз.
7. Басымды және басқарушыны талдау, мыналар қажет:
   - өрістердің дәл ұзындықтары
   - қолдау көрсетілетін `CurveId`
   - жарамды ашық кілт
   - артта қалған байттар жоқ
   - тиiстi жағдайда жарамды көпбелгi саясаты
8. `AccountId` құрастыру.
9. `AccountId` мәнін күтілетін дискриминант үшін канондық түрде көрсетіңіз.
10. Қырқылған кіріспен `byte-for-byte` теңдікті талап етіңіз.

Қолданбаның нақты соңғы `render-and-compare` қадамы минималды емес сандық сентинелдерді, канондық емес контроллер орналасуларын, қайта реттелген саясат материалын және декодталатын, бірақ кодтаушының ағымдағы V1 шығысына жатпайтын кез келген басқа жазылымды қабылдамайды.

Тексерудің табыстылығы немесе төмен деңгейдегі `AccountAddress` талдау осы тексеруді алмастыруға болмайды.

Осы мәндерді ID деген қатаң есеп өрісінде қабылдамаңыз:

- Есепшоттың `alice@wonderland.universal` деген атаулы аты
- I105 әріпті, оған қоса берілген `@domain` жұрнағы
- `ed0120...` сияқты ашық кілті бар `multihash`
- `0x02000120...` сияқты каноникалық пайдалы жүк шегі
- дұрыс емес тізбектік айырмашылыққа арналған адрес
- үлкен немесе кіші әріптері, таңбаларының ендері, `kana`, пайдалы жүктеме немесе тексеру сомасы өзгерген жіп.

Қолданба шекарасында бүркеншік аттарды шешіп, авторизациялау, қол қою, рұқсаттар және аудит жазбалары үшін қайтарылған канондық I105 ID мәнін сақтаңыз.

## API, сақтау және көрсетілу қағидалары {#api-storage-and-display-rules}

- JSON тіркелгі өрістеріне нақты I105 UTF-8 тізбекті жіберіңіз.
- `Percent-encode` толық есеп ID оны URL жол сегментіне орналастырудан бұрын.
- Ешқашан I105 ID орнына тіркелгі бүркеншік атын қолданбаңыз.
- Кодек қайтарған каноникалық жиынды `byte-preserving` салыстыру семантикасымен сақтау.
- Әріптердің үлкен-кішілігі мен таңба енін сақтайтын салыстыру ережесін қолданыңыз.
- Шығарылған шот деректері мен резервті көшірмелерімен тізбектің айырмашылығын немесе аталатын желі профилін сақтау.
- Адресті тек оның желілік контексімен қайта пайдалану.
- Толық адресті көрсетіңіз және көшірме әрекетін келтіріңіз.
- Әр `kana` таңбасын дәл сақтаңыз.
- Жіктес дисплей ортасын қысқартқан кезде толық адресті қолжетімді сақтаңыз.
- Сақталған каноникалық ID псевдонимнен қайта құрудың орнына қолданылсын.

`AccountId` дисплейі мен JSON көрсетілімі канондық I105 пішімін пайдаланады.

Төменгі деңгейдегі `AccountAddress` дисплейі/JSON көрсетілімі ішкі және жөндеу контекстерінде канондық он алтылық пішімді пайдаланады.

Сыртқы тіркелгі ID қажет болған жағдайда, нақты `AccountAddress` I105 кодтаушысына хабарлаңыз.

Тіркелгілерді құру және аты-жөндерді шешу жұмыс тетіктері үшін [Тіркелгілер мен аты-жөнімен жалғастырыңыз](/kk/cookbook/accounts-and-aliases.md).

Есептік деректер үлгісі үшін [Сандар](/kk/blockchain/accounts.md) дегенді қараңыз.
