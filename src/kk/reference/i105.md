# I105 Есеп шотының мекенжай форматы {#i105-account-address-format}

I105 — бұл Iroha 3 `AccountId` үшін бірегей протокол-стандарт сыртқы мәтін форматы.

Оның жүктемесі есеп шотының басқарушысын білдіреді.

Оның күзетшісі тізбек айырғышымен көзделген желіні анықтайды.

Оны API, транзакция, рұқсат немесе сұрау бір протокол-стандартты есептік жазба идентификаторын сұраған кез келген жерде пайдаланыңыз.

I105 аккаунт идентификаторы доменсіз.

`treasury@payments.universal` сияқты мән — I105 ID-дің басқа жазылуы емес, тіркелгі бүркеншік аты.

I105 идентификаторын алу есепшотты тіркемейді немесе қаржыландырмайды.

::: warning Көптеген интеграция сәтсіздіктерін болдырмайтын ережелер

- Мекенжайды кодтау немесе тексеру алдында желі профилін таңдаңыз.
- Бір протокол-стандарт UTF-8 жолын дәл сақтау және салыстыру.
- Әріптердің үлкен-кішілігін сақтаңыз және `Unicode` қалыпқа келтіруін қолданбаңыз.
- I105 идентификаторында `@domain` немесе `@domain.dataspace` қосымшасы болмауы керек.
- Iroha SDK немесе `iroha tools address` қолданыңыз.
- Тұрақты өрнек I105 валидаторы емес.

:::

## Литеральді анатомия {#literal-anatomy}

Бір I105 литералы үш қатарлас бөліктен тұрады және бөлгіш жоқ:

```text
<network sentinel><base-105 canonical payload><six checksum symbols>
```

|Бөлім|Мақсат|Чексума қамтуы|
| ---------------- | ------------------------------------------------------------------ | ----------------- |
|Желілік күзетші|Мәтінді бір `u16` тізбекті дискриминантқа бейнелейді|Қамтамасыз етілмеген|
|Жүк| `base-105` бір протокол-стандартты есеп-шот контроллері байттарын кодтау|Қапталған|
|Тексеру сомасы| I105 әліпбиімен көрсетілген алты `Bech32m`-стильді `5-bit` мәні |Қолданылмайды|

Жүктеме мен тексеру сомасы тіркелгі контроллерін анықтайды.

Сақшы желі контекстін таңдайды.

Бірдей контроллерде Taira және Minamoto нүктелерінде бірдей жүктеме және тексеру сомасы бар, бірақ әрбір желі әртүрлі бастапқы sentinel қолданады.

Декодер күтілетін дискриминанттың сәйкестігін міндетті түрде қамтамасыз етуі тиіс.

Чексум сенсортты ауыстыруды анықтай алмайды.

### Желі күзетшілері {#network-sentinels}

|Желі немесе контекст|Тізбекті дискриминант|      Гекс |бірінші хаттама-стандартты күзетші|
| ----------------------- | -------------------------------: | -------: | ------------------------------------------- |
| Taira ашық тест желісі    |                            `369` | `0x0171` | `test`                                      |
| Minamoto қоғамдық желі |                            `753` | `0x02f1` | `sora`                                      |
|Дамудың контексті|                              `0` | `0x0000` | `dev`                                       |
|Кез келген басқа `u16` мәні|Барлығы `0`, `369`, және `753` қоспағанда|        — | `n` плюс минималды ондық, мысалы `n42` |

Атауылған мәндер әрқашан өздерінің атаулы сигналына қолданылады.

`n00042`, `n369`, `n753` және `n0` сияқты формалар бір протокол-стандарт емес.

Транзакция тізбегі идентификаторы мен I105 тізбек дискриминанты бөлек мәндер болып табылады.

API соңғы нүктесін немесе тізбек идентификаторын таңдау мекенжай профилін тікелей таңдау емес.

## Нормативтік біртүйінді мысал {#normative-single-key-example}

Төмендегі payload және Minamoto формасы кросс-SDK сәйкестік құралына жатады.

Taira формасы Taira сақшысын бірдей жүктемеге қолданады:

```text
Public-key payload:
3B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Public-key multihash accepted by tooling:
ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29

Canonical account payload:
0x020001203b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29

Minamoto I105, discriminant 753:
sorauﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE

Taira I105, discriminant 369:
testuﾛ1NﾗhBUd2BﾂｦﾄiﾔﾆﾂﾇKSﾃaﾘﾒﾓQﾗrﾒoﾘﾅnｳﾘbQｳQJﾆLJ5HSE
```

Бірегей протокол-стандарт жүктемесі `02 00 01 20` бастап шығады: тақырып `0x02`, ықшам бірлешікті кілт белгілері `0x00`, `Ed25519` қисық идентификаторы `0x01`, және 32-байттық кілт ұзындығы `0x20`.

`multihash` префиксі енгізу метадеректері болып саналады және контроллердің жүктемесіне көшірілмейді.

## CLI арқылы идентификаторларды жасау және тексеру {#create-and-inspect-ids-with-the-cli}

Қоғамдық желі үшін атаулы профильді таңдаңыз:

```bash
PUBLIC_KEY='ed01203B6A27BCCEB6A42D62A3A8D02A6F0D73653215771DE243A63AC048A18B59DA29'

TAIRA_ACCOUNT_ID="$(
  iroha tools address convert --profile taira "$PUBLIC_KEY"
)"

MINAMOTO_ACCOUNT_ID="$(
  iroha tools address convert --profile minamoto "$PUBLIC_KEY"
)"
```

Мекенжай-кодек мінез-құлқын диагностикалау кезінде I105 енгізуді қалыпқа келтіріп, салыстырыңыз:

```bash
NORMALIZED_ACCOUNT_ID="$(
  printf '%s\n' "$TAIRA_ACCOUNT_ID" \
    | iroha tools address normalize --profile taira
)"

test "$NORMALIZED_ACCOUNT_ID" = "$TAIRA_ACCOUNT_ID"
```

Табылған форматты, бір протоколдық стандартты он алтылықты және таңдалған желілік контексті JSON ретінде тексеріңіз:

```bash
iroha tools address convert \
  --profile taira \
  --format json \
  "$TAIRA_ACCOUNT_ID"
```

Жаңа жолмен бөлінген файлдың мекенжай-кодек құрылымын талдауда талдау қателіктерін үндеместен қабылдамау:

```bash
iroha tools address audit \
  --profile taira \
  --input account-ids.txt \
  --format json
```

::: caution CLI тексеру шегі

`convert`, `normalize` және `audit` командалары төменгі деңгейдегі `AccountAddress` кодектерінде жұмыс істейді.

Олар сторожды, алфавитті, чексумманы, байт ұзындықтарын, `CurveId`/кілт пішінін және нақты адрес-қабат қайта кодтауды тексереді.

Олар `AccountId` нысанын жасамайды.

Олар өздері барлық мультисиг саясат семантикасын растамайды.

Олар тақырып сыныбы контроллерге сәйкес келетінін дәлелдемейді.

Авторизациялау немесе тұрақты сақтауға жазу алдында `AccountId` қатаң тексеруін қолданыңыз.

:::

Жеке желі үшін оның конфигурацияланған айырғышын `--network-prefix` арқылы нақты көрсетіңіз.

Қолданыстағы мекенжайды ашық контексттер арасында ауыстырғанда, сонымен қатар бастапқы мекенжайға `--expect-prefix` көрсетіңіз:

```bash
iroha tools address convert \
  --expect-prefix 369 \
  --network-prefix 753 \
  "$TAIRA_ACCOUNT_ID"
```

Қайта кодтау тек желілік контексті өзгертеді.

Бұл мақсатты желіде есепшотты тіркемейді немесе сол жерде бірдей контроллерді қайта пайдалану керек екенін дәлелдемейді.

## Шифрлау алгоритмі {#encoding-algorithm}

бір ғана протокол-стандартты кодерлер осы операцияларды орындайды:

```text
canonical = header || controller
payload_digits = base_convert(canonical, base_256, base_105)
checksum_digits = bech32m_6(hrp = "snx", convert_8_to_5(canonical, pad = true))
literal = sentinel(discriminant) || alphabet[payload_digits || checksum_digits]
```

Алдыңғы нөлдік байттар нөлдік мәндегі `base-105` сандары ретінде сақталады.

Тексеру сомасы `Bech32` `polymod` генераторларын және `0x2bc830a3` тұрақтысын қолданады.

Тек тексеру сомасы HRP — бұл ASCII жолы `snx`.

Тек тексеру сомасы HRP мекен-жайда басылмайды.

Алты тексеру сомасы мәндері `0..31` диапазонында орналасқан және олар жүктеме сияқты I105 алфавиті арқылы көрсетіледі.

### I105 әліпбе {#i105-alphabet}

105 символ дәл осы реттілікте индекстеледі.

Бірінші жол - `Bitcoin Base58` әліпбиі және сандық белгілерді `0..57` қамтиды.

Екінші қатарда сандықтар `58..104` бар.

Кодекті іске асыру кезінде жолдарды біріктіріңіз.

```text
123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz
ｲﾛﾊﾆﾎﾍﾄﾁﾘﾇﾙｦﾜｶﾖﾀﾚｿﾂﾈﾅﾗﾑｳヰﾉｵｸﾔﾏｹﾌｺｴﾃｱｻｷﾕﾒﾐｼヱﾋﾓｾｽ
```

Алфавит `Unicode`-сезімтал.

Дәл реттілік `compatibility-width` жапон `kana` символдарын және `ヰ` мен `ヱ` көрсетілген код ұпайларын қолданады.

NFC, NFKC, енді түрлендіруді, әріп регистрін бүктеуді немесе ұқсас таңбамен алмастыруды қолданбаңыз.

ASCII `0`, `O`, `I` және `l` әліппе символдары емес.

## бір протокол-стандарт есептік жазба деректер пакеті {#canonical-account-payload}

`base-105` денесі екілік есептік деректерді кодтайды, қоғамдық кілт жолын немесе Norito JSON объектісін кодтамайды:

```text
header:u8 || controller:variable
```

Төмендегі барлық көп байттық бүтін сандар таңбасыз және `big-endian`.

Домен, деректер алаңы, жарлық, UAID, және есептік жазба метадеректер байттары жоқ.

### Тақырып байты {#header-byte}

|Биттер|Ені|Ағымдағы кодтағыш шығысы|Мағына|
| ------ | ----: | ---------------------------: | ---------------------------- |
| `7..5` |     3 |                          `0` |Мекенжай форматының нұсқасы өрісі|
| `4..3` |     2 | `0` бір кілт, `1` мультиөлшем |Мекенжай класы|
| `2..1` |     2 |                          `1` |Нормализация нұсқасы өрісі|
| `0`    |     1 |                          `0` | Резервтелген `extension flag` |

Қазіргі V1 энкодерлер бір кілттік контроллер үшін тақырып `0x02` шығарады және мультисиг контроллер үшін `0x0a` шығарады.

Мекенжай кластар `2` және `3` тағайындалмаған.

`1`-нің `extension flag`-і қабылданбады.

Төмен деңгейлі декодер басқа нұсқаларды және нормалау бит мәндерін сақтай алады және класты контроллер тегіне қатысты тәуелсіз тексермейді.

`AccountId`-ге ауыстыру және оның бір протокол-стандарт нұсқасын салыстыру қазіргі V1 бір протокол-стандарт формасына сәйкестігін дәлелдейді.

### Бір батырмалы контроллер {#single-key-controller}

Қарапайым ашық кілттің деректері ең көп дегенде 255 байт болғанда ықшам нұсқасын пайдаланыңыз:

|Егістік|Ені|Мәні немесе мағынасы|
| ------------ | --------------: | ------------------------ |
| `tag`        |1 байт| `0x00`                   |
| `curve`      |1 байт| `CurveId` тіркеу мәні |
| `key_len`    |1 байт|Шикі кілт ұзындығы|
| `public_key` | `key_len` байт |Жай ашық кілттік мәлімет|

255 байттан ұзын кілттер кеңейтілген формада қолданылады:

|Өсеу алаңы|Ені|Мәні немесе мағынасы|
| ------------ | --------------: | ---------------------------- |
| `tag`        |1 байт| `0x02`                       |
| `curve`      |1 байт| `CurveId` тіркеу мәні|
| `key_len`    |         2 байт |Шикі кілт ұзындығы, `big-endian`|
| `public_key` | `key_len` байт |Жай ашық кілттік жүктеме|

Кеңейтілген кодтау – ықшам нысанына сәйкес келетін кілт үшін бір ғана протокол-стандарт емес.

### Көпқол қою контроллері {#multisig-controller}

|Өсеу алаңы|Ені|Мәні немесе мағынасы|
| ---------------- | -------: | ------------------------------ |
| `tag`            |1 байт| `0x01`                         |
| `policy_version` |1 байт|Ағымдағы мән `1`|
| `threshold`      |  2 байт |Қажетті жалпы мақұлдау салмағы|
| `member_count`   |2 байт|Келесі мүшелер саны|
| `members`        |Айнымалы|Қайталанған мүшелер жазбалары|

Әрбір мүше жазбасы:

|Өсеу алаңы|Ені|Мағына|
| ------------ | --------------: | ------------------------ |
| `curve`      |1 байт| `CurveId` тіркеу мәні |
| `weight`     |         2 байт |Мүшелердің мақұлдау салмағы|
| `key_len`    |         2 байт |Шикі кілт ұзындығы|
| `public_key` | `key_len` байт |Жай ашық кілттік мәлімет|

Жарамды саясатта кемінде бір мүше, оң салмақтар болуы, қайталанатын ашық кілттер болмауы және шек `1`-ден мүшелер салмақтарының қосындысына дейін болуы тиіс.

```text
member_count >= 1
all(member.weight > 0)
1 <= threshold <= sum(member.weight)
all_unique(member.public_key)
```

Жеке хаттама-стандарт құрылыс мүшелерді қол қою алгоритмінің тұрақты атауы бойынша, нөлдік бөлгіш байт арқылы, содан кейін ашық кілттің шикі байттары арқылы сұрыптайды.

```text
member_sort_key = stable_algorithm_name || 0x00 || raw_public_key
```

Мәтіндік I105 тұрақты таңба ұзындығына ие емес, өйткені көпқолдық және посткванттық контроллерлер үлкен бола алады.

### `CurveId` тіркеу {#curveid-registry}

Соңғы бағанда қажет опционалды `Cargo` функция көрсетілген.

Сызықша тіркеу жазбасы қосымша деректер үлгісі ерекшелігісіз қолжетімді екенін білдіреді.

|ID|Қол қою алгоритмі|Қажетті `Cargo` функция|
| ---: | -------------------------------------------- | ------------------------ |
|  `1` | `Ed25519`                                    | —                        |
|  `2` | `ML-DSA`                                     | —                        |
|  `3` | `BLS12-381 normal`                           | `bls`                    |
|  `4` | `secp256k1`                                  | —                        |
|  `5` | `BLS12-381 small`                            | `bls`                    |
| `10` | `GOST R 34.10-2012 256-bit, parameter set A` | `gost`                   |
| `11` | `GOST R 34.10-2012 256-bit, parameter set B` | `gost`                   |
| `12` | `GOST R 34.10-2012 256-bit, parameter set C` | `gost`                   |
| `13` | `GOST R 34.10-2012 512-bit, parameter set A` | `gost`                   |
| `14` | `GOST R 34.10-2012 512-bit, parameter set B` | `gost`                   |
| `15` | `SM2`                                        | `sm`                     |

Қабылдаушы құрастыруда тағайындалмаған идентификаторлар мен алгоритмдер жоққа шығарылады.

Негізгі жүктеме сондай-ақ жарияланған `CurveId` таңдаған алгоритмге құрылымдық тұрғыдан жарамды болуы керек.

## Қатаң AccountId тексеру және біртұтас протокол-стандартты формаға сәйкестік {#strict-accountid-validation-and-canonicality}

Күтілетін тізбек дискриминантымен SDK-ді конфигурациялағаннан кейін, оны `AccountId`-ке талдап, қайтарылған бір протокол-стандартты көріністі қысқартылған кіріспемен салыстырыңыз.

Салыстыру маңызды, өйткені парсер декодталатын контроллер материалын `AccountId` құрастырған кезде қалыпқа келтіре алады.

```rust
use eyre::{ensure, Result};
use iroha::data_model::prelude::AccountId;

fn parse_canonical_account_id(input: &str) -> Result<AccountId> {
    let input = input.trim();
    let parsed = AccountId::parse_encoded(input)?;

    ensure!(
        parsed.canonical() == input,
        "account ID is valid but not in its current canonical I105 form"
    );

    Ok(parsed.into_account_id())
}
```

Сенімсіз жол үшін сәйкесті қолданба келесі әрекеттерді орындауы керек:

1. Тек рұқсат етілген тасымалдау бос орындарын толық мәннің айналасынан кесіңіз.
2. Сентинелді оқып, күтілетін тізбек дискриминантын талап етіңіз.
3. Қалған барлық `Unicode` символдарын дәл 105-символдық әліпби арқылы сәйкестендіріңіз.
4. Бақылау сомасының алты цифрын бөліп алыңыз.
5. Payload цифрларын қайтадан бір протокол стандартты байттарға түрлендіріңіз.
6. Осы бір протоколдық стандарт байттар бойынша тексеру сомасын растаңыз.
7. Тақырыпты және контроллерді талдаңыз, мынаны талап етеді:
   - өрістердің дәл ұзындықтары
   - қолдау көрсетілетін `CurveId`
   - жарамды ашық кілт
   - артық байттар жоқ
   - қолдануға болатын жарамды мультисиғар саясаты
8. `AccountId` құру.
9. `AccountId` мәнін күтілетін дискриминант үшін канондық түрде көрсетіңіз.
10. Қырқылған кіріспен `byte-for-byte` теңдікті талап етіңіз.

Қолданбаның нақты соңғы `render-and-compare` қадамы минималды емес сандық сентинелдерді, канондық емес контроллер орналасуларын, қайта реттелген саясат материалын және декодталатын, бірақ кодтаушының ағымдағы V1 шығысына жатпайтын кез келген басқа жазылымды қабылдамайды.

Сәтті чексум немесе төмен деңгейлі `AccountAddress` талдауы осы тексеру үшін алмастыра алмайды.

Бұл мәндерді қатал есеп тіркелгісі идентификаторы өрісінде қабылдамаңыз:

- мысалы, `alice@wonderland.universal` тіркелгі атауы
- қосымша `@domain` аффиксі бар I105 мәтіндік мән
- қоғамдық кілт `multihash` мысалы `ed0120...` сияқты
- жалғыз протокол-стандартты жүктеме hex мысалы `0x02000120...`
- қате тізбек ерекшелендіргішіне арналған мекенжай
- үлкен немесе кіші әріптер, таңба ендері, `kana`, мазмұны немесе тексеру сомасы өзгертілген жол

Қолданба шекарасында бүркеншік аттарды шешіп, авторизациялау, қол қою, рұқсаттар және аудит жазбалары үшін қайтарылған канондық I105 ID мәнін сақтаңыз.

### Жиі кездесетін тұрақты қате кодтары {#common-stable-error-codes}

|Код|Мағына|
| -------------------------------- | ------------------------------------------------------------------- |
| `ERR_UNEXPECTED_NETWORK_PREFIX`  |Шифрланған дискриминант қажет желімен сәйкес келмейді|
| `ERR_CHECKSUM_MISMATCH`          |Алты тексеру сомасы символы жүктемеге сәйкес келмейді|
| `ERR_INVALID_I105_CHAR`          |Символ дәл әліпбиден тыс|
| `ERR_MISSING_I105_SENTINEL`      |Бірде-бір атаулы немесе сандармен көрсетілген протокол стандарты табылған жоқ|
| `ERR_I105_TOO_SHORT`             |Дене бір уақытта жүктеме мен тексеру сомасын ұстай алмайды|
| `ERR_INVALID_LENGTH`             |Басқару өрісі қысқарған немесе бірдей протокол стандартты ұзындық формасын қолданбайды|
| `ERR_UNKNOWN_CURVE`              |Басқару құралы тағайындалмаған немесе қол жетімсіз `CurveId` екенін көрсетеді|
| `ERR_INVALID_PUBLIC_KEY`         |Таңдалған алгоритм үшін кілт жарамсыз `CurveId`|
| `ERR_UNSUPPORTED_ADDRESS_FORMAT` |Енгізу қабылданған бір протокол-стандарт I105 формасы емес|

## API, сақтау және көрсету ережелері {#api-storage-and-display-rules}

- JSON есептік жазба өрістерінде дәл I105 UTF-8 жолын жіберіңіз.
- `Percent-encode` оны URL жол сегментіне қоюдан бұрын толық есепшот идентификаторын енгізіңіз.
- Ешқашан I105 ID орнына тіркелгі бүркеншік атын қолданбаңыз.
- Кодектен қайтарылған бір протокол-стандартты жолды `byte-preserving` салыстыру семантикасымен сақтаңыз.
- Әріптердің үлкен-кішілігі мен таңба енін сақтайтын салыстыру ережесін қолданыңыз.
- Шынжыр дискриминантын немесе экспортталған есептік деректер мен резервтік көшірмелері бар аталған желі профилін сақтаңыз.
- Мекенжайды тек оның желілік контекстімен қайта пайдаланыңыз.
- Толық мекенжайды көрсетіп, көшіру әрекетін орындаңыз.
- Әрбір `kana` таңбаны дәл сақтаңыз.
- Ортаң қысқарып кеткен кезде толық мекен-жайды қолжетімді ұстаңыз.
- Оны тіркелген бір протокол-стандартты идентификатордан ала отырып, оны лақап аттан қалпына келтірмеңіз.

`AccountId` дисплейі мен JSON көрсетілімі канондық I105 пішімін пайдаланады.

Төменгі деңгейдегі `AccountAddress` дисплейі/JSON көрсетілімі ішкі және жөндеу контекстерінде канондық он алтылық пішімді пайдаланады.

Сыртқы есептік жазба идентификаторы қажет болған кезде нақты `AccountAddress` I105 кодтағышты шақырыңыз.

Шотты құру және лақап атыңызды шешу жұмыс үрдістері үшін, [Есепшоттар және лақап аттар](/kk/cookbook/accounts-and-aliases.md) арқылы жалғастырыңыз.

Есептік жазба деректер моделін көру үшін, [Шоттар](/kk/blockchain/accounts.md) қараңыз.
