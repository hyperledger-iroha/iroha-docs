# Torii API ұш нүктелер {#torii-endpoints}

Torii — бұл Iroha 3 үшін HTTP, SSE және WebSocket шлюзі. Ол блокчейн тізілімі APIs және оператор API соңғы нүктелерімен әрекеттесуге қызмет етеді.

Ағымдағы хаттама ережелері мыналар:

- жалғыз протокол-стандартты бинарлық формат Norito
- көптеген API соңғы нүктелері сіз `Accept: application/json` жіберген кезде JSON қолдайды
- метрикалар Prometheus форматында көрсетіледі

Форматтың егжей-тегжейлері, мазмұнды келісу, орналасу белгілері, схема криптографиялық хэштері және Norito RPC нұсқауларына қатысты мәліметтерді [Norito сілтеме](/kk/reference/norito.md) қараңыз.

## Жиі қолданылатын API соңғы нүктелері {#common-endpoints}

| API соңғы нүкте |Формат|Мақсат|
| -------------------------------- | -------------- | ---------------------------------------------------------------- |
| `POST /v1/pipeline/transactions` | Norito         |Қол қойылған транзакцияны жіберу|
| `POST /v1/query`                 | Norito         |Қол қойылған сұрауды жіберу|
| `GET /v1/events/ws`              | WebSocket      |Оқиғалар ағындарына жазылу|
| `GET /v1/events/sse`             | SSE            |SSE арқылы оқиға ағындарына жазылыңыз|
| `GET /v1/blocks/stream`          | WebSocket      |Ағындық аяқталған блоктар|
| `GET /v1/peers`                  | JSON           |Torii арқылы ашылған желі әріптес тізімі|
| `GET /livez`                     |Мәтін|Тек процесс өміршеңдігі; бұл протоколдың дайын екенін білдірмейді|
| `GET /readyz`                    | JSON           |Төлемсіз кеш тексерулерін қоса алғанда, түйіннің дайындылығын толық тексеру|
| `GET /health`                    | JSON           |Офлайн-касса инвариантымен бірдей дайындық зондын тексеру|
| `GET /v1/api/version`            |Мәтін|Ағымдағы блок тақырыбының нұсқасы|
| `GET /status`                    | Norito немесе JSON |Жоғары деңгейлі диагностикалық күй; JSON сұранысын нақты көрсету|
| `GET /metrics`                   |Прометей|Prometheus скраптау API нүктесі|
| `GET /v1/schema`                 | JSON           |Қосылған кезде түйін арқылы берілетін деректер моделі схемасының уақыт бойынша деректер көрінісі|
| `GET /openapi.json`              | JSON           | OpenAPI құжаты белсенді Torii HTTP маршруттар үшін|
| `GET /v1/parameters`             | JSON           |Түйін параметрі уақыт бойынша деректер көрінісі|
| `GET /v1/node/capabilities`      | JSON           |Түйін мүмкіндігі және деректер үлгісі метадеректері|
| `GET /v1/time/now`               | JSON           |Түйін жергілікті жүйелік сағат нүкте-мезгіл деректер көрінісі|
| `GET /v1/time/status`            | JSON           |Уақытты синхрондау күйі|

SSE сұрауы үшін, жергілікті ағынды жарнамалаңыз және терілген сақтық көшірмесін қосыңыз:

```http
Accept: text/event-stream, application/json
```

Torii бірінші сұрау қабатында JSON немесе Norito өкілдігін келіссөз жүргізеді, содан кейін жергілікті `text/event-stream` жауабын тексереді. Тек `text/event-stream` жіберу сондықтан `406` арқылы қабылданбайды; [ағыстар оқиғалары рецепті](/kk/cookbook/stream-events.md) толық тақырыпты қолданады.

`/openapi.json` – схемада көрсетілген маршруттар үшін жасалған келісімшарт, толық операциялық-зондтық тізім емес. Ағымдағы құжат `/livez` және `/readyz`-ні қамтымайды, ал оның `/health` сипаттамасы дайындық өңдегішінен кейін қалуы мүмкін. Тірі құжаттан маршрут клиенттерін тудыру, бірақ тірі болуын және дайын болуын тікелей іске қосылып тұрған түйін мен бекітілген өңдегіштерге қарсы тексеру. Нақты интерфейс әлі де құрылыс мүмкіндіктеріне байланысты бағдарламалық қамтамасыз етуді орындау ортасын конфигурациялау. Сол тірі құжатты жүктеу үшін [Torii API консоль](/kk/reference/torii-api-console.md) пайдаланыңыз, JSON маршруттарды тексеріңіз, curl сұрауларды көшіріңіз және ағымдағы схемадан клиент коды жасаңыз.

Әрбір каталогқа негізделген OpenAPI операциясы `x-iroha-route-auth` объектісін қамтиды. Каталогқа негізделген MCP құралдары `_meta["iroha/routeAuth"]` сияқты келісімді көрсетеді. Екі проекцияда да `schemaVersion`, `stableRouteId`, `authentication` және `admission` бар. Нұсқаны `1` нақты келісімшарт ретінде қарастырыңыз: аутентификация немесе қабылдау белгілері қалай түсіндірілуі керектігін болжаудың орнына, қолдау көрсетілмеген `schemaVersion` қабылдамаңыз. Бағыт метадеректері сұрау шегін сипаттайды; ол сол шек үшін қажет куәліктерді алмастырамайды.

## Тікелей Taira бағыттарын сынап көріңіз {#try-live-taira-routes}

Қоғамдық Taira тест желісі қолданбалы клиенттер оқу үшін ғана зерттеу жүргізетін сол Torii JSON беткейін ашады. Бұл командалар кілттерді қажет етпейді:

```bash
TAIRA_ROOT=https://taira.sora.org

curl -fsS -H 'Accept: application/json' "$TAIRA_ROOT/status" \
  | jq '{blocks, txs_approved, txs_rejected, queue_size, peers}'

curl -fsS "$TAIRA_ROOT/openapi.json" \
  | jq -r '.paths | keys[]' \
  | grep '^/v1/' \
  | head -n 20

curl -fsS -H 'Accept: application/json' \
  "$TAIRA_ROOT/v1/node/capabilities" \
  | jq '{abi_version, data_model_version, query: .query.aggregate.supported_resources}'
```

Ресурстарды ағымдағы әлем күйіне қарсы оқуды байқап көріңіз:

```bash
curl -fsS "$TAIRA_ROOT/v1/domains?limit=5" \
  | jq -r '.items[].id'

curl -fsS "$TAIRA_ROOT/v1/assets/definitions?limit=5" \
  | jq -r '.items[] | [.id, .name, .total_quantity] | @tsv'
```

Егер қоғамдық тестнет маршруты `502` қайтаратын болса, уақытынан асып кетсе немесе қаныққан кезек туралы хабарласса, оны API соңғы нүктесінің қолжетімділігі мәселесі деп қарастырып, клиент кодыңызды жөндеуден бұрын кейінірек қайта көріңіз.

## Қосымша және SORA Бағыт Отбасы {#app-and-sora-route-families}

Torii қосымшаға бағытталған функциялар жиынтығымен құрылған кезде, ол шолушылар, SORA қызметтер, көпір ағындары, дәлелдер және сақтау үшін қосымша JSON отбасыларын ашады. Бұл отбасылардың бәрі әр желі профилінде белсендірілмейді.

`/openapi.json` генерацияланған app-API каталогында тіркелген маршруттарды сипаттайды; ол тек өзінде бар жазбалар үшін беделді, қосылған әр маршрут үшін емес жүйе арқылы. Әсіресе, қоғамдық жергілікті SoraFS CID және танымал маршруттар сол жасалған құжаттан тыс орналастырылған және тікелей тексерілуі керек.

| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `/v1/accounts/*`, `/v1/domains/*`, `/v1/assets/*`                         | JSON оқу, сұрау көмекшілері, кіріспе көмекшілері және портфолио немесе иелер көріністері|

## Есептік жазбаны растау, Көріну және Шолу курсорлары {#account-authentication-visibility-and-explorer-cursors}

### Қосымша есептік жазбаға сұрау протоколы {#app-account-request-protocol}

Қолданбаға бағытталған маршруттар ешқандай аутентификация тақырыптарын қабылдамауы мүмкін, немесе бір тікелей бір кілттік дәлелді, немесе бір көпқолтық куәгерді қабылдауы мүмкін. Әрбір аутентификация тақырыбы ең көп бір рет пайда болуы керек.

Тікелей дәлел үшін, барлық төрт тақырыпты бірге жіберіңіз:

- `X-Iroha-Account`: дәл бір протокол-стандартты кіші әріппен жазылған `0x` есеп-шот мекенжайының hex немесе белсенді бір протокол-стандартты ASCII есеп-шот лақап аты. I105 мәтін HTTP өріс мәні ретінде қауіпсіз емес; сол есеп-шот үшін бір протокол-стандартты hex жазылуын пайдаланыңыз.
- `X-Iroha-Signature`: қатаң толтырылған base64 қолтаңба деректер жиынтығы.
- `X-Iroha-Timestamp-Ms`: бапталған ауытқу терезесі ішінде, бір ғана протокол стандартына сәйкес келетін, таңбасыз ондық Unix уақыт белгісі миллисекундта.
- `X-Iroha-Nonce`: 1-ден 256-ға дейін басып шығартылатын ASCII байт (`0x21` бастап `0x7e` дейін), қайта ойнату терезесінде бірегей.

Тіркелген бір түймелі контроллер осы нақты байттарды белгілейді:

```text
iroha.app.request.network.v1\0 || <genesis-derived network_id[32]> ||
<UPPERCASE_METHOD>\n
<exact request path>\n
<canonical query>\n
<lowercase hex SHA-256 of the raw body>\n
<canonical timestamp_ms>\n
<nonce>
```

жеке протокол-стандарт сұрау құрастыру шикі сұрауды `application/x-www-form-urlencoded` ретінде талдайды (`+` бос орынды білдіреді), жұптарын пайыздық түрде декодтайды, оларды `(key, value)` бойынша сұрыптайды және қайтадан формада кодтайды. Протокол ең көп дегенде 64 декодталған жұп пен 64 KiB шикі сұрау мәтінін қабылдайды. Дене байттарын дәл жіберілген күйінде криптографиялық хэштер арқылы өңдеңіз. Тұрақты 32 байттық желі идентификаторы мен үлкен әріппен жазылған әдістің арасында бөлгіш қоймаңыз.

V1 тексерушісі әдіс маркерін 32 байтқа, пайызбен кодталған сұраныс жолын 64 KiB-ке және тікелей есептік жазбаның идентификаторын 36 KiB-ге дейін шектейді, содан кейін талдайды. Есептік жазбалардың лақап аттары үш атау сегменті мен олардың бөлгіштерінен тұратын қатаң құрылымдық шектеуге ие. Шектен асу автентификацияның қолтаңбаны тексеруден немесе дереккөз мөлшерін бөлуден бұрын сәтсіз болуына әкеледі.

Көп қателікке төзімді контроллер оның орнына жіберуі керек `X-Iroha-Witness` қатаң толтырылған-base64 бір протокол-стандарт Norito және өткізіп жіберу `X-Iroha-Signature`, `X-Iroha-Timestamp-Ms`, және `X-Iroha-Nonce`. `X-Iroha-Account` осы формада міндетті емес; бар болған жағдайда, ол куәгермен бірдей болуы керек `subject_account`. Бұл `CanonicalRequestWitnessV1` қамтиды `schema_version`, `subject_account`, `timestamp_ms`, `nonce`, бір Iroha `Hash` нақты желі сұрау байттарын дене криптографиялық дайджест мәні арқылы, бірақ жаңалық өрістерісіз, және ең көп дегенде 64 мүше қолы. Әрбір мүше бір протокол стандартын қол қояды Norito сол сол payload-тың тіркелімдер массивісіз кодталуы. Расталған мүшелер есептік жазбаның ағымдағы мультиподпистік саясатына сай болуы керек. Шифрланған куәгер 1-ге дейін шектелген MiB.

Аутентификация тақырыптары берілмесе, бұл анонимді кіруді таңдауды білдіреді. Кез келген жартылай, аралас, қайталанған, бұзылған, ескі немесе қайталанған дәлелдерді беру аутентификацияны сәтсіз етеді; ол ешқашан анонимді көрінуге ауыспайды.

### Оператор сұрау хаттамасы {#operator-request-protocol}

Оператордың рұқсатымен белгіленген маршруттар барлық төрт жеке тақырыпты қажет етеді:

- `x-iroha-operator-public-key`: бір протокол-стандартты Iroha көпхэштік ашық кілт.
- `x-iroha-operator-timestamp-ms`: миллисекундпен көрсетілген бір ғана протокол-стандартты таңбаланбаған ондық Unix уақыт белгісі.
- `x-iroha-operator-nonce`: 1 ден 256-ға дейінгі басып шығарылатын ASCII байт, қайта ойнату терезесі ішінде сол кілт үшін бірегей.
- `x-iroha-operator-signature`: қатаң толтырылған base64 қолтаңба жүктемесі.

Тақырып мәндерінде айналадағы бос орын болмауы керек. Оператор кілтінің белгілері:

```text
iroha.operator.http-request.network.v1\0 || <genesis-derived network_id[32]> ||
<UPPERCASE_METHOD>\n
<exact request path>\n
<canonical query>\n
<lowercase hex SHA-256 of the raw body>\n
<canonical timestamp_ms>\n
<nonce>
```

Жол, сұрау, дене, уақыт белгісі және криптографиялық nonce мәніне қойылатын ережелер қосымша хаттама қолданатын бірдей бір стандартталған хаттама ережелері болып табылады. Кілт те `[torii.operator_signatures]` арқылы қабылдансын: оны `allowed_public_keys` тізімінде көрсетіңіз немесе түйін кілтін қолданған кезде `allow_node_key` мүмкіндігін нақты түрде қосыңыз. Replay-cache қанығуы `503 Service Unavailable` кезінде жабық күйде сәтсіз болады.

Нақты сұрау қолтаңбасы әрқашан міндетті болып табылады. `[torii.operator_auth].enabled = true` болған кезде, әрбір кәдімгі оператор маршруты да жарамды `x-iroha-operator-session` талап етеді; `require_mtls = true` болған кезде, ол сондай-ақ сенімді кірістен `x-forwarded-client-cert` қажет етеді. Екі фактор да сұрау қолтаңбасын алмастыра алмайды.

WebAuthn тіркелу және кіру үшін осы төрт JSON API соңғы нүктелерін пайдаланыңыз:

|Әдіс және API тіркелу нүктесі|Мақсат|
| --------------------------------------------- | ---------------------------------------- |
| `POST /v1/operator/auth/registration/options` | WebAuthn куәлікке тіркелуді бастаңыз |
| `POST /v1/operator/auth/registration/verify`  |Куәлікті тексеріп, сақтаңыз|
| `POST /v1/operator/auth/login/options`        | WebAuthn аутентификациясын бастау|
| `POST /v1/operator/auth/login/verify`         |Дәлірек екенін тексеріп, сессияны шығарыңыз|

`torii.operator_auth.tokens` арнайы бастауыш мәндермен баптаңыз. Кез келген куәлік пайда болғанға дейін, бірінші тіркеуді бастау үшін біреуін `x-iroha-operator-token` ретінде жіберіңіз. Сол токен әдеттегі оператор маршрутын ешқашан авторизацияламайды, және тыңдаушы `x-api-token` мәндері бұл ағын үшін ешқашан қайта қолданылмайды. Бір рет куәлiк бар болса, басқа куәлiкке тіркелу үшін аутентификацияланған сессия қажет. Кіру тексерісі әр жаңа дәл-ақ желілік оператор сұранысы қолтаңбасымен бірге жіберілетін сессия токенін қайтарады. Куәлiктер `<torii.data_dir>/operator_auth/operator_webauthn.json` астында сақталады.

ISO 20022 бағыттары екі тәуелсіз тексеруден өтуді талап етеді. Сұраныс алдымен осы оператордың рұқсат тізімінен және қолтаңба протоколынан өтуі керек; содан кейін ISO өңдеуші дәл төменде сипатталған қатысушы немесе аудит рөлін алу үшін сол кілтті талап етеді.

### блокчейн тіркеу тізілімінің Көрінуі және Шолушы Көрсеткіштері {#ledger-visibility-and-explorer-cursors}

Қосымшаға арналған блокчейн тізілімін оқу үшін жоғарыдағы опционалды қосымша есептік шекараны пайдаланады. Қолтаңбасыз сұраным тек жария ретінде бапталған деректер кеңістіктерін алады. Дұрыс қолтаңбаланған сұраным қоңырау шалушының ағымдағы UAID байланған деректер кеңістіктерін қосады, әрбір шектелген деректер кеңістігі нақты `CanReadRestrictedDataspace { dataspace }` рұқсатымен аталады, немесе егер есептік жазбада `CanReadAllLedgerData` болса, барлық маршруттар.

Шақырған адамның уәкілетті субъектіге сәйкес келетін маршрутты пайдаланыңыз:

|Әдіс және API тіркелу нүктесі|Растау және көріну|
| ------------------------------------- | --------------------------------------------------------------- |
| `POST /v1/transactions/visible/query` |бір протокол-стандарт тіркелгі қолтаңбасы; шақырушының көрінуін қолданады|
| `POST /v1/transactions/query`         |Оператордың сұрау қолтаңбасы; жаһандық оператор көрінісіне мүмкіндік береді|
| `GET /v1/triggers/completed`          |Оператор сұранысының қолтаңбасы; түйінге жергілікті аяқтау жазбаларын оқиды|

Сол көрінетін объект есептік жазбаны, доменді, активтердің анықтамасын, активті, NFT, RWA, ұстаушыны және Explorer оқуын сүзеді. Жоқ объект және шақырушының көрінетін маршрутынан тыс объект қасақана ажыратып болмайды. соңына дейін аяқталған транзакция және нұсқау тарихы тек транзакция үшін жазылған барлық маршруттық қаржылық аударым бөліктері көрінгенде көрсетіледі. Аралас-мәліметтер кеңістігі транзакциясы — сондықтан бір қатысушының қаржылық аударым бөлімі қоңырау шалушының ауқымынан тыс болған кезде жасырылған; жоқ, ескірген немесе дұрыс құрылмаған бағыттау контексті тек жаһандық оқырманға көрінеді.

Алты әлемдік қолдауға ие Explorer жинақтары мөлдір емес бір протокол-стандартты base64url кілт жиынтық курсорларын қолданады. Әдепкі бет шегі 25, ең көп дегенде 100, және бір бетте ең көп 512 кандидат кілт тексеріледі. Әр курсор өзінің жинағына, сүзгілеріне, бір протокол стандартты соңғы кілтке және шақырушының көрінетін маршрут жиынтығы криптографиялық дайджест мәніне байланған, сондықтан оны басқа сұрауда немесе шақырушының көрінісі өзгергеннен кейін қайта ойнату мүмкін емес.

Блок, транзакция, соңғы транзакция, нұсқаулық және соңғы нұсқаулық тарих курсорлары қосымша түрде аяқталған уақытша нүкте деректер көрінісінің биіктігін және блок криптографиялық хэшін бекітеді. Жауаптар `pagination.limit`, `pagination.snapshot_height`, `pagination.snapshot_hash`, `pagination.next_cursor`, және `pagination.has_more` мәндерін көрсетеді. Басқа маршрут немесе сүзгі жиынтығы үшін курсор, өзгерген көріну криптографиялық дайджест мәні немесе түйін енді тексере алмайтын уақыт-нүктесі деректер көрінісі жабық күйде сәтсіз аяқталады. Тарихты сканерлеу блоктайтын жұмысшы іске қосылған кезде Torii сұрау-кіру рұқсатында қалады.

Explorer WebSocket ағындары сүзілген қорытындыларды шығарады және блокчейн тізілімінің рұқсаттары өзгерген сайын көрінуін қайта есептейді. Туынды `GET /v1/blocks/stream` маршруты әр түрлі: ол толық қол қойылған блоктарды шығарады, қол алысы кезінде `CanReadAllLedgerData` талап етеді және сол рұқсат кейін жойылған жағдайда жабылады. Деректер кеңістігіне қатысты шолушы үшін жергілікті ағынды қолданбаңыз.

## ISO 20022 Көпір {#iso-20022-bridge}

Torii қосымшалық беттегі API және көпір бағдарламалық қамтамасыз ету орындау ортасы қосылған кезде `/v1/iso20022/*` астында ISO 20022 көпірін көрсетеді. Көпір әдейі шектелген: Бұл жалпы мақсаттағы ISO 20022 есеп айырысу шлюзі емес, бірақ таңдалған төлем хабарламаларын қол қойылған Iroha аударымдарға айналдыру және олардың блокчейн тізілімі күйін бақылау үшін қолдау көрсетілетін ішкі жиынтық болып табылады.

Кез келген тапсырманы қабылдамас бұрын орнықты жергілікті `torii.iso_bridge.store_dir` орнатыңыз. Конфигурация өрісі тек түйіннің тек оқу немесе диагностикалық қолдану үшін іске қосылуы мүмкін болғандықтан ғана міндетті емес: әрбір аутентификацияланған ISO тапсырыс каталогты қажет етеді және сақтау жоқ болған жағдайда немесе қайта ойнату-мәрмәр немесе бай жазба жазу сәтсіз болғанда қайта әрекет етуге болатын `503 Service Unavailable` қайтарады.

| `GET /v1/iso20022/messages/{msg_id}/sese024` |Қазіргі қаржылық операцияны есеп айырысу жағдайын `sese.024` XML ретінде көрсетіңіз|
| `GET /v1/iso20022/messages/{msg_id}/sese025` |Қазіргі қаржылық операцияны есеп айырысу туралы растауды `sese.025` XML ретінде көрсетіңіз|

`pacs.008` тапсырмалар хабарлама идентификаторын, банктер арасындағы қаржылық операцияларды есептеу сомасын, валютаны, қаржылық операцияларды есептеу күнін, борышкер мен кредиторды IBANs, және борышкер мен кредиторды BICs көрсетуі тиіс. Сілтеме деректері конфигурацияланған кезде, көпір жасалған транзакция бағдарламалық өңдеу жұмыс ағымына кірмей тұрып, сондай-ақ BIC, IBAN және ISO 4217 валюта кроссвоктарын тексереді.

`pacs.009` жіберілімдерде бизнес хабарлама идентификаторы, хабарлама анықтамасы идентификаторы, құрылу уақыты, банктер арасындағы қаржылық транзакцияны есептеу сомасы, валюта көрсетілуі тиіс, қаржылық операцияны есептеу күні, нұсқаушы және нұсқаулық алған агент BICs, сондай-ақ қарызгер мен несие беруші IBANs. Егер хабарламада `Purp` болса, қазіргі уақытта көпір тек бағалы қағаздарды қаржыландыру мақсатында қабылдайды: `Purp=SECU`.

`pacs.008` және `pacs.009` жіберу API соңғы нүктелері XML ISO деректер контейнерлерін немесе көпірлеп тестерде қолданылатын тегіс өріс форматтарын қабылдайды. Міндетті емес `SplmtryData` өрістер мақсатты Iroha блокчейн есеп тізілімі, бастапқы және мақсатты есепшот идентификаторлары немесе мекенжайлары, және актив анықтамасының идентификаторын бекіте алады. Жауап `202 Accepted` болып табылады, оған `message_id`, `transaction_hash`, `status`, `pacs002_code`, және шешімін тапқан тізілім/есепшот/актив контексті кіреді.

### Қатысушының рұқсат беруі және өмірлік кезеңді иеленуі {#participant-authorization-and-lifecycle-ownership}

Әр қосылған көпірде қатысушылар каталоги болады. Әр қатысушы жазбасында бірегей қатысушы идентификаторы, бір немесе бірнеше оператордың ашық кілттері, бір немесе бірнеше қаржылық идентификаторлары, рұқсат етілген профильдер жиынтығы және `originator`, `counterparty` немесе екеуі де рөлдері болады. Оператор кілттері мен қаржылық идентификаторлар бір қатысушыға ғана тиесілі болуы мүмкін. `audit_admin_keys` жеке конфигурациялаңыз; аудит-әкімші кілті сондай-ақ қатысушы мутация кілті бола алмайды.

Барлық ISO маршруттар жаңа оператордың қолын талап етеді. Бастапқы `pacs.008`, `pacs.009`, `sese.023` немесе `colr.012` тапсырмасы үшін расталған оператор `From` қаржылық тұлғаның қосымшасының тақырыбымен көрсетілген қатысушыға тиесілі болуы тиіс. `To` жеке басы `counterparty` рөлі бар конфигурацияланған қатысушыға сәйкес келуі керек, ал таңдалған профиль екі тарапқа да рұқсат етілуі керек. Төзімді қабылдау жазбалары бастапқы жіберушіні, қарсы тарапты, қабылдаушы қатысушы мен оператор кілтін, сондай-ақ бастапқы профиль мен кірістірілген қолтаңба саясатын тіркейді.

Өмірлік кезеңді авторизациялау шақыртушы таңдаған мәндерден емес, сол өзгермейтін жазбадан алынады:

|Өмірлік цикл туралы хабарлама|Қажетті қатысушы|
| ---------------------------------------------- | -------------------------------------------------- |
| `pacs.002`, `pacs.004`, `sese.024`, `sese.025` | `counterparty` рөліндегі бастапқы қарсы тарап |
| `camt.056`                                     | `originator` рөліндегі түпнұсқа бастамашы|

Бастапқы профиль мен қолтаңба саясаты бүкіл өмірлік цикл бойы бекітіліп тұрады, сондықтан қоңырау шалушы жаңарту үшін әлсіз профильді таңдай алмайды. Өкілейтін `pacs.002` коды қаржылық транзакцияны есеп айырысу (`ACSC`, `ACCP`, `SETT`, немесе `SETTLED`) бастапқы жазбаны тек Torii транзакцияның дәлелін аяқтаған кезде ғана есеп айырысқан деп өзгертеді.

Кез келген бастапқы тарап өз хабарлама жазбасын және жасалған жіберу құжаттарын оқи алады. Тексеру API соңғы нүктесі тек аутентификацияланған қатысушы бастаушы немесе қарсы тарап болып табылатын жазбаларды қайтарады. Бөлек бапталған аудит әкімшісі ғаламдық тек оқуға арналған аудиттік көріністі алады және хабарламаларды жіберуге немесе өзгертуге мүмкіндік жоқ. Белгісіз қатысушылар мен байланыссыз хабарлама идентификаторлары жарияланбайды.

### Төзімді Ойнату Бұлтты Жеке Тұлға және Қол қойылған Шығарылатын Құжаттар {#durable-replay-identity-and-signed-outbox-documents}

Қайта ойнату үшін тұрақты жою маркерлері қатаң қабылдау шегін білдіреді. Torii оқу мүмкін емес, тым үлкен, бұзылған, дұрыс аталмаған, қайшылықты немесе айқын үйлеспейтін тұрақты жою маркері үшін іске қосылуды тоқтатады. Сонымен қатар ол қазіргі конфигурациядан жоқ немесе сәйкес келмейтін схема нұсқасы бар бай жазба, қатысушы, профиль немесе қолтаңба саясаты, немесе жоқ немесе сәйкес келмейтін тікелей тұрақты жою маркері үшін де тоқтатылады.

Басқа бай тізімдегі зақымдар әртүрлі өңделеді: оқылмайтын немесе үлкен файлдар, жарамсыз JSON, жарамсыз ағымдағы схема жазбалары, бір протокол стандартында емес файл атаулары және қайшы келетін ойнату идентификаторлары тіркеледі немесе өткізіледі. Оқылмайтын немесе жарамсыз ағымдағы нұсқадағы аудит индексі сақталған жазбалардан қайта генерацияланады; тек айқын үйлеспейтін аудит индекс нұсқасы ғана іске қосылуды тоқтатады. Бастапқы журналдарды бақылап, әрбір бүлінген бай жазба файлы түйінді қызмет көрсетуден тоқтатады деп есептемей, қайта жасалған аудиттік техникалық манифесті салыстырыңыз.

Әрбір сақталған бай жазба өзгермейтін қатысушының шығу тегін сақтайды. Жеке тұрақты жою белгісі хабардың ID-сін, жүктеме криптографиялық хэшін, бизнес хабар ID-сін және бай жазба мәліметтері тазаланғаннан кейін де толық қайталануды TTL сақтау үшін UETR сақтайды.

Torii өмірлік циклдік хабарламаға қол қояр немесе өңдегенге дейін қайта ойнатуды қабылдауды сақтайды. Ол ешқашан уақытылы өшпеген қайта ойнату идентификаторын шығармайды. Егер конфигурацияланған сыйымдылық толықтай қорғалатын жазбалармен немесе мерзімі өткен жоқ қайта ойнату сәйкестіктерімен толтырылған жағдайда, жіберулер өмірлік циклді немесе есепке алу күйін өзгертпей қайта талпынуға болатын `503 Service Unavailable` алады.

Әрбір жасалған `pacs.002`, `pacs.004`, `camt.029`, `sese.024` немесе `sese.025` құжат `application/xml` ретінде қайтарылады, осы жауап тақырыптарымен:

|Тақырып|Мағына|
| ------------------------------ | ----------------------------------------------------- |
| `X-Iroha-Iso-Signature-Domain` |Әрдайым `iroha.iso20022.outbound.v2`|
| `X-Iroha-Iso-Signer`           |конфигурацияланған көпір криптографиялық қолтаңбасына арналған бір стандартты протоколдық ашық кілт|
| `X-Iroha-Iso-Signature`        |Доменге бөлінген XML байттар үстіндегі Base64 қолтаңбасы|

UTF-8 байттық тізбегі `iroha.iso20022.outbound.v2`, бір нөлдік байт және дәл жауап денесі үстіндегі қолтаңбаны растаңыз. Растамас бұрын XML-ны қайта форматтамай немесе қалыпқа келтірмеңіз.

### Қосымша парсер және сәйкестендіру қолдауы {#additional-parser-and-mapping-support}

IVM ISO көмекші сонымен қатар деректер контейнерін тексеру, қаржылық транзакцияларды есептеу немесе кейінгі сәйкестендіру үшін келесі хабарлама отбасыларын тексеріп, нақтылайды. Олардың жеке Torii бағыттары жоқ.

|Отбасына хабарлама|Ағымдағы қолдау|
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `head.001`                         |ISO деректер контейнерлері үшін бизнес-қосымша тақырыбын тексеру, оның ішінде `BizMsgIdr`, `MsgDefIdr`, жасау уақыты және опционалды жіберуші/қабылдаушы BIC өрістері|
| `pacs.007`, `pacs.028`, `pacs.029` |Төлемді қайтару, мәртебесін сұрау және зерттеу шешімі/мәртебесін талдау|
| `pain.001`, `pain.002`             |Тұтынушының төлем бастамасы және төлем мәртебесін есепті тексеру|
| `camt.052`, `camt.053`, `camt.054` |Есеп шоты туралы есеп, мәлімдеме және хабарландыруларды тексеру|

## Kaigi Сессиялар {#kaigi-sessions}

Kaigi SORA Nexus платформасында ақылы, нақты уақыттағы аудио/видео бөлмелерді ұсынады. Қолданбаға блокчейн тізілімі арқылы сессия жасау, қатысушылар тізіміндегі өзгерістер, релелік техникалық сипаттамалар, шифрланған сигнализация және пайдалану есептеу қажет болғанда, барлық конференц-жағдайды off-chain сақтау орнына оны пайдаланыңыз.

Блокчейн есеп шотының өмірлік циклімен өзара әрекеттесу мынадай:

- `CreateKaigi`: доменнің аясында қоңырау жасап, оның саясатын, кестесін, метадеректерін және таңдаулы релейлік техникалық manifest-ін сақтаңыз.
- `JoinKaigi`: қоңырау тізімін жаңартыңыз. `zk-roster-v1` режимінде қоғамдық қоңырау көрінісі қатысушылардың есептік жазба идентификаторларының орнына криптографиялық міндеттемелер мәнін және нөлдендіру есептерін көрсетеді.
- `LeaveKaigi`: қатысушыны мөлдір қоңыраудан шығару. Жеке режимдегі шығу бірінші нұсқалық протоколда off-chain жүргізіледі.
- `RecordKaigiUsage`: өлшенген ұзақтығы мен транзакцияны орындау шығындарының жалпы сомасын қосыңыз.
- `EndKaigi`: сессияны жабыңыз және соңғы уақыт таңбасын жазып қойыңыз.

Torii келесі қолданбаға бағытталған оқу операцияларын көрсетеді:

|Маршрут|Аутентификация|Мақсат|
| ----------------------------------- | --------------------------------------- | ------------------------------------------ |
| `/v1/kaigi/calls/{call_id}`         |қоғамдық|ағымдағы қоңырау жазбасы|
| `/v1/kaigi/calls/{call_id}/signals` |бір ғана протокол-стандарт дәл желілік есеп тіркелім сұранысы| беттелген аяқталған сигнал беру метадеректері|
| `/v1/kaigi/calls/{call_id}/events`  |бір ғана протокол-стандарт дәл желілік есеп тіркелім сұранысы|қоңырау өмірлік цикл ағыны|
| `/v1/kaigi/relays`                  |рұқсат етілген оператордың сұрауы|өршіктеу қорытындысы|
| `/v1/kaigi/relays/{relay_id}`       |рұқсат етілген оператордың сұрауы|бір реленің тіркеу және денсаулық деректері|
| `/v1/kaigi/relays/health`           |рұқсат етілген оператордың сұрауы|релелердің жалпы жағдайы|
| `/v1/kaigi/relays/events`           |жалғыз протокол-стандарт дәл желілік есеп тіркелім сұранысы|реттеу тіркелімі және денсаулық оқиғалары ағыны|

Қосымша API қосулы болуы керек. Релейдің жиынтық және күй жолдары оператор беттері болып табылады, тіпті олар тек оқу үшін болса да; қол қойылмаған `curl` сұраныс жарамды қолжетімділік сынағы емес. Сессия күйі сондай-ақ Kaigi домендік оқиғалары арқылы көрсетіледі, мысалы, `KaigiRosterSummary`, `KaigiRelayManifestUpdated`, `KaigiRelayHealthUpdated`, және `KaigiUsageSummary`.

### CLI Шылымнан сынақ {#cli-smoke-test}

Сіз UI-ті қосар алдында Torii API соңғы нүктесі Kaigi транзакцияларын қабылдайтынын тексергіңіз келгенде `iroha app kaigi` CLI-пен бастаңыз. Quickstart командасы конфигурацияланған API соңғы нүктеге қарсы бөлме жасайды және оның шақыру идентификаторы мен қосылу метадеректерін шығарады:

```bash
iroha app kaigi quickstart \
  --domain kaigi.universal \
  --summary-out kaigi-summary.json
```

Сценарийленген ағындар үшін бөлменің өмірлік циклін нақты басқару:

```bash
iroha app kaigi create \
  --domain kaigi.universal \
  --call-name daily \
  --host <i105-account-id> \
  --privacy-mode transparent \
  --room-policy authenticated

iroha app kaigi join \
  --domain kaigi.universal \
  --call-name daily \
  --participant <i105-account-id>

iroha app kaigi leave \
  --domain kaigi.universal \
  --call-name daily \
  --participant <i105-account-id>

iroha app kaigi record-usage \
  --domain kaigi.universal \
  --call-name daily \
  --duration-ms 120000 \
  --billed-gas 1500

iroha app kaigi end --domain kaigi.universal --call-name daily
```

`--room-policy public` көрермен билеттерінсіз көрсетілуі мүмкін бөлмелер үшін немесе шығулар көрерменнің аутентификациясын талап етуі тиіс болғанда `--room-policy authenticated` пайдаланыңыз. `--privacy-mode zk-roster-v1` тек кейін ғана пайдаланыңыз Желіде Kaigi тізімі және пайдалану тексеру кілттері конфигурацияланған; әйтпесе қосылулар, шығулар және жеке пайдалану жазбалары детерминистік тексеру кезінде сәтсіз болады.

### JavaScript Интеграция {#javascript-integration}

Ағымдағы [Iroha JavaScript демо](https://github.com/soramitsu/iroha-demo-javascript) транспарентті, аутентификацияланған бір-бірімен кездесетін профильді іске асырады. Ол протоколдың ашылуына жол бермейді `zk-roster-v1` дәлел ағыны. Оның рендерері жасайды WebRTC ұсыныстар мен жауаптар, ал артықшылықты көпір жергілікті қолданады [`@iroha/iroha-js`](https://github.com/hyperledger-iroha/iroha/tree/0010c5a70039eac101a4846499ba9ceaf43eb65c/javascript/iroha_js) дәйексөз алу, қол қою, жіберу және соңғы нұсқасын күту үшін тексеру Kaigi транзакциялар.

Дәл маршрут аутентификациясы, шақыру форматы, көпір шекарасы және ағымдағы демонстрациялық тест командалары үшін [JavaScript қосымшасында Kaigi кірістіру](/kk/guide/tutorials/kaigi.md) қараңыз.

## Күй және өлшемдер {#status-and-metrics}

Статус пен метрикалар API соңғы нүктелерін бақылау панелдеріне қосатын алғашқы заттар:

- `/status` жоғарғы деңгейдегі желілік әріптес, блок, кезек және консенсус өрістерін көрсетеді
- `/metrics` Prometheus есептегіштерін, өлшегіштерін және гистограммаларын көрсетеді

Nexus-қолдау көрсетілген түйінде статус шығару сонымен қатар орындалу жолы мен деректер кеңістігін ескеретін бөлімдерді қамтиды. `nexus.enabled = false` кезінде, сол бөлімдер шығарылмайды.

## JSON мен Norito салыстыруы {#json-vs-norito}

Бірнеше оператор API соңғы нүктелері әдепкі бойынша Norito қайтарады. API соңғы нүктесі JSON қолдаған кезде, жіберіңіз:

```http
Accept: application/json
```

Бұл әсіресе мына үшін пайдалы:

- `/v1/sumeragi/status`
- `/v1/sumeragi/qc`

API соңғы нүктесі типтелген Norito-ті тікелей қабылдаған немесе қайтарған кезде, мазмұн түрі немесе таңдаулы `Accept` мәні ретінде `application/x-norito` пайдаланыңыз. Көлік мәліметтері үшін [Norito](/kk/reference/norito.md#torii-and-norito-rpc)-ге қараңыз.

## Телеметрия профильдері {#telemetry-profiles}

API соңғы нүктенің көрінуі түйіннің `telemetry.profile` баптауына байланысты. Қазіргі конфигурация бес профиль деңгейін көрсетеді:

|Профиль| `/status` | `/metrics` |Әзірлеуші бағыттары|
| ----------- | --------- | ---------- | ---------------- |
| `disabled`  |жоқ|жоқ|жоқ|
| `operator`  |иә|жоқ|жоқ|
| `extended`  |иә|иә|жоқ|
| `developer` |иә|жоқ|иә|
| `full`      |иә|иә|иә|

## CLI Қысқартулар {#cli-shortcuts}

`iroha` CLI бұған дейін осы көптеген API соңғы нүктелерін орап алған:

```bash
export IROHA_OPERATOR_KEY_FILE=/run/secrets/iroha/operator.key

iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  --output-format text ops sumeragi status
iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  --output-format text ops sumeragi diagnostics
iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  ops sumeragi params
iroha --config ./localnet/client.toml --operator-private-key-file "$IROHA_OPERATOR_KEY_FILE" \
  --output-format text ops sumeragi evidence count
```
