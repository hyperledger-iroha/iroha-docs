# Изанами арқылы хаос тестілеу {#chaos-testing-with-izanami}

Izanami – бұл жоғарғы Iroha жұмыс алаңындағы хаостық желі ұйымдастырушысы. Ол уақытша жергілікті Iroha кластерін іске қосады, бапталатын жұмыс жүктемесін береді және таңдалған желі әріптестеріне ақаулар енгізеді, осылайша операторлар желінің басқарылатын ақау кезінде де алға жылжуын тексере алады.

Izanami-ні алдын ала өндірістік төзімділік тексерістері, регрессияны қайталау және консенсус баптауы үшін пайдаланыңыз. Оны өндірістік желіге бағыттамаңыз: құрал сол үшін жасалған желідегі әріптестерді басқарып алу үшін, оларға желі әріптестерін қайта іске қосу, сақтау жадын өшіру, уақытша сенімді әріптес бөлімшелерін жасау және жергілікті CPU немесе диск қысымын қосқанда әрекет етеді.

## Алдын ала шарттар {#prerequisites}

Осы құжаттама репозиторийінен емес, [Iroha бастапқы репозиторий](https://github.com/hyperledger-iroha/iroha) ішінен Izanami іске қосыңыз:

```bash
git clone https://github.com/hyperledger-iroha/iroha.git
cd iroha
cargo build -p izanami
```

Бинарлық файл желілік желілік құрылымдар жасауға және олармен жұмыс істеуге ашық түрде рұқсат етілуі керек. Әрбір TUI емес іске қосу үшін `--allow-net` жіберіңіз немесе TUI ішіндегі `allow_net`-ді қосыңыз.

```bash
cargo run -p izanami -- --allow-net --peers 4 --faulty 1 --duration 120s
```

Интерактивті іске қосу конфигурациясы үшін:

```bash
cargo run -p izanami -- --tui --allow-net
```

Izanami пайдаланушы конфигурация каталогында TUI және CLI баптауларын сақтайды. Бірінші шығарылым файлы бір нақты V1 орналасу байтын қамтиды; алдын ала шығарылым немесе басқа нұсқаланбаған баптаулар қабылданбайды және оларды көшірудің орнына қайта жасау қажет. Ағымдағы профильді қайта пайдалану алдында көрсетілген параметрлерді қарап шығыңыз.

## Базалық іске қосу {#baseline-run}

Ауыр ақауларды қоспас бұрын бір қайталанатын базалық деңгейден бастаңыз:

```bash
cargo run -p izanami -- \
  --allow-net \
  --peers 4 \
  --faulty 1 \
  --duration 5m \
  --target-blocks 100 \
  --progress-interval 15s \
  --progress-timeout 120s \
  --latency-p95-threshold 2s \
  --tps 15 \
  --max-inflight 32 \
  --submitters 1 \
  --seed 42
```

Бұл іске қосу тек кластер сұралған блок мақсатына жетсе, уақыт шегінде прогресті жалғастырса және кез келген p95 блок интервалы шегінен аспаса ғана сәтті болады.

Команданы, тұқымды, Iroha протоколын аяқтауды, желідегі түйіндер санын, ақаулы түйіндер санын, жұмыс жүктемесі профилін, мақсатты TPS және кешігу шегін журналдармен бірге жазып алыңыз. Бұл мәндерсіз басқа оператор бірдей ақау үлгісін қайтала алмайды.

## Жұмыс жүктемесінің профильдері {#workload-profiles}

Идзанамида екі жүктеме профилі бар:

|Профиль|Оны пайдаланыңыз|Ескертпелер|
| -------- | -------------------------------------------------- | -------------------------------------- |
| `stable` |Ұзақ жүктеме жүгірістері және қайталанатын өнімділік тексерулері|Орындалуға қауіпсіз рецептерді қолдайды|
| `chaos`  |Сәтсіздік жолын қамту|Қасақана дұрыс емес рецепттерді қамтиды|

Алдымен тұрақты профильді пайдаланыңыз:

```bash
cargo run -p izanami -- --allow-net --workload-profile stable --seed 42
```

Негізгі жағдай түсінікті болғанда хаос профиліне ауысыңыз:

```bash
cargo run -p izanami -- --allow-net --workload-profile chaos --seed 42
```

Келісімшартты орналастыру рецепттері тұрақты іске қосуларда нақты рұқсат етілмеген жағдайда өшірілген:

```bash
cargo run -p izanami -- \
  --allow-net \
  --workload-profile stable \
  --allow-contract-deploy-in-stable
```

Жүгіру кезінде жоғарғы деңгейдегі жұмыс орнынан кіріктірілген SORA Nexus әдепкі мәндерді пайдалану қажет болса, `--nexus` пайдаланыңыз.

## Қатеге бақылау {#fault-controls}

`--faulty` нөлден үлкен болғанда, кем дегенде бір ақау сценарийі қосулы болуы тиіс. Ақау ауыстырғыштары әдепкі бойынша қосулы болады және логикалық белгілер `=false` арқылы өшіруге болады.

|Қате| CLI ту                                  |Ол қандай жаттығулар жасайды|
| ------------------------ | ------------------------------------------ | ------------------------------------------ |
|Құлау және қайта жүктеу| `--fault-enable-crash-restart`             | желі әріптес процесінің жоғалуы және қалпына келуі |
|Жадты сүртіңіз және қайта қосыңыз| `--fault-enable-wipe-storage`              |Жергілікті күйдің жоғалуынан қалпына келтіру|
|Жарамсыз транзакция спам| `--fault-enable-spam-invalid-transactions` |Қабылдау және бас тарту жолдары|
|Желінің кідіріуі| `--fault-enable-network-latency`           |Баяу өсек және кешіктірілген келісім хабарлары|
|Желілік бөлу| `--fault-enable-network-partition`         |Уақытша сенімді әріптесті оқшаулау|
| CPU стресс| `--fault-enable-cpu-stress`                |Жергілікті тексеру және кестелеу қысымы|
|Диск қанығуы| `--fault-enable-disk-saturation`           |Жергілікті сақтау қымысы|

Тек желіні бөлуден тұратын іске қосу үшін:

```bash
cargo run -p izanami -- \
  --allow-net \
  --peers 4 \
  --faulty 1 \
  --duration 5m \
  --fault-window-start 60s \
  --fault-window-end 180s \
  --tps 15 \
  --submitters 1 \
  --max-inflight 32 \
  --fault-enable-crash-restart=false \
  --fault-enable-wipe-storage=false \
  --fault-enable-spam-invalid-transactions=false \
  --fault-enable-network-latency=false \
  --fault-enable-network-partition=true \
  --fault-enable-cpu-stress=false \
  --fault-enable-disk-saturation=false \
  --seed 42
```

`--fault-window-start` және `--fault-window-end` пайдаланып, енгізілген қателіктен бұрын және кейін бақылаулы тұрақты күй мерзімін сақтау қажет. Бұл іске қосу кезінде пайда болатын шуды қателіктің әсерінен ажыратуды жеңілдетеді.

## Сценарий пішіндері {#scenario-shapes}

Жоғары деңгейлі Izanami каталогы жалпы блокчейн байланыс-қатесі пішіндерін CLI профильдеріне сәйкестендіреді. Оларды дәл сол ту жалауларымен модельдеуге болады:

|Сценарий|Дәстүрлі пішін|
| --------------------- | ------------------------------------------------------------------------------------------------------------------------ |
|Мақсатты жүктеме| `--faulty 0`, жоғары `--tps`, бір жіберуші, жоғары `--max-inflight` |
|Уақытша сәтсіздік|Қатенің шектелген терезесінде ғана апат/қайта іске қосуды қосу|
|Тоқтау және қалпына келу|Үлкен ақаулы әріптес популяциясын апат/қайта жүктеу үшін пайдаланыңыз|
|Көшбасшының оқшаулануы|Тек бір ғана ақаулы желілік серіктесті пайдаланыңыз, тек желіні бөлісу ақауымен; Изанами Sumeragi жетекші телеметриясын бақылайды|

Бір уақытта бір айнымалыны ғана тұрақты ұстаңыз. Егер сіз сол бір орында желі қатысушыларының санын, жүктеме профилін, ақау терезесін және TPS өзгертсеңіз, нәтиже түсіндіру қиын болады.

## Не көру керек {#what-to-watch}

Жүгіру кезінде өнімділікті тексеру үшін қолданылатын сол сигналдарды бақылаңыз:

- әрбір жұмыс істеп тұрған желі теңсарпымен блок биіктігінің прогресі
- жүктелген, қабылданған, қабылданбаған және уақытынан өткен транзакциялар
- кезектің тереңдігі, кезек қанықтығы және API соңғы нүктедегі артқы қысым
- өзгерістерді қарау, қалпына келтіру жолдары, жетіспейтін блоктар және жетіспейтін кворум сертификаттары
- қол қойылған RS16 қолжетімділік тапшылығы, күтіліп тұрған сессиялар және кешіктірілген консенсус трафигі
- CPU, желілік әріптестерді іске қосатын хосттағы жады, диск және желі қанықтығы

Растау-қўршау кешіктіруін талдау үшін негізгі циклдің баптау журналдарын қосыңыз:

```bash
RUST_LOG=iroha_core::sumeragi::main_loop=debug \
  cargo run -p izanami -- --allow-net --seed 42
```

Әр блок `block validation timings` шығарып, `stateless_ms`, `execution_ms`, және `total_ms` қосуы керек. Сол уақыттарды өзгертпей тұрып p95 блок интервалдары, көріністі өзгерту есептегіштері және кезек қысымымен салыстырыңыз.

## Нәтижелерді талдау {#interpreting-results}

Барлық таңдалған желі әріптестері блоктарды аяқтауды жалғастыруда, артта қалу шектеусіз өсіп кетпейді және ақаулар орнатылған терезе аяқталғаннан кейін жаңа қалпына келтіру әрекеттерін тудырмайтыны жағдайда іске қосылуды сау деп есептеңіз.

Жүгірісті сәтсіздік деп қарастыру жағдайлары:

- прогрестің тоқтауы `--progress-timeout`-дан ұзаққа созылады
- желі серіктестерінің биіктіктері айырмашылыққа түседі және қайта қосылмайды
- p95 кідіруі `--latency-p95-threshold`-дан асып кетті
- қате терезесі жабылғаннан кейін кезектер қалған процесс барысында өседі
- бас тартылған немесе уақытынан кешіктірілген транзакциялар таңдалған жүктеме арқылы түсіндірілмейді
- желі әріптесін қайта іске қосу, сақтау орнын тазалау немесе бөлімді қалпына келтіру қолмен тазалауды қажет етеді

Сәтсіздіктен кейін, сол тұқыммен және бір кем қате түрімен қайта іске қосыңыз. Бұл жұмыс көлемі мен уақытты қайта өндіруге мүмкіндік береді, сонымен қатар сәтсіздік беткейін тарылтады.
