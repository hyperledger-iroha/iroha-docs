# Конфигурация мәселелерін түзету {#troubleshooting-configuration-issues}

Бұл бөлімде Iroha 3 конфигурациясы үшін ақауды түзету бойынша кеңестер ұсынылған. Алдымен [пернелерді тексерді](./overview.md#check-the-keys) орындағаныңызға көз жеткізіңіз, өйткені бұл Iroha-тегі мәселелердің ең жиі кездесетін себебі болып табылады.

Егер сіз кездесіп отырған мәселе мұнда сипатталмаған болса, бізбен [Телеграм](https://t.me/hyperledgeriroha) арқылы байланысыңыз.

## Docker Compose орнатуда ескірген блокчейн негізі {#outdated-genesis-on-a-docker-compose-setup}

Iroha бағдарламасының Docker Compose нұсқасын пайдаланған кезде, желідегі бір әріптес контейнерінің `Failed to deserialize raw genesis block` қатесімен істен шығуы мәселесіне тап болуыңыз мүмкін. Бұл әдетте желідегі серіктес, қол қойылған блокчейн генезис транзакциясы және жасалған конфигурация әртүрлі Iroha нұсқалары немесе профилдері арқылы жасалғанын білдіреді.

Мынандай қадамдар арқылы ақауды тексеріңіз:

1. Қазіргі контейнерлерді тексеру үшін `docker ps` қолданыңыз. Жасалған профильге байланысты, әдетте сіз `hyperledger/iroha:dev` контейнерлерін көресіз. Әдепкі Docker Compose профилінде төрт желілік теңсерік контейнер бар, бірақ сіздің жасалған `docker-compose.yml` басқа болуы мүмкін.

2. Журналдарды тексеріп, `Failed to deserialize raw genesis block` қатесін іздеңіз. Егер сіз `docker compose up -d` арқылы Iroha-ті демон режимінде бастасаңыз, `docker compose logs` пәрменін пайдаланыңыз.

Мұндай мәселені шешу тәсілі Iroha пайдалануына байланысты. Егер бұл негізгі демонстрация болса және сізге желілік әріптес деректерін сақтау қажет болмаса, сәйкес localnet немесе Docker Compose пакетін Kagami арқылы қайта жасау керек:

```bash
cargo run --bin kagami -- localnet --peers 4 --out-dir ./localnet
cargo run --bin kagami -- docker --peers 4 --config-dir ./localnet --image hyperledger/iroha:dev --out-file ./docker-compose.yml
```

Содан кейін ескі контейнер күйін жойып, қайта жасалған `genesis.signed.nrt`, желідегі серіктес `config.toml` файлдарынан және `client.toml` бастап қайта іске қосыңыз.

Егер сізге Iroha мысал деректерін қалпына келтіру қажет болса, келесі әрекеттерді орындаңыз:

1. Бірінші (жұмыс істемейтін) желі әріптесінен деректерді көшіретін екінші Iroha желі әріптесін қосыңыз.
2. Жаңа желі әріптесі деректерді бірінші желі әріптесімен синхрондауын күтіңіз.
3. Жаңа желілік түйінді белсенді қалдырыңыз.
4. Біріккен көшіру аясында тек бірінші желі серіктесінің блокчейн генезисі мен конфигурация файлдарын жаңартыңыз.

::: info

Тірі желіде блокчейннің бастауышын ауыстыру үшін жалпы автоматты қайта жазу жолы жоқ. Мұны үйлестірілген көші-қон ретінде қарастырыңыз: ескі күйді сақтаңыз, үйлесімді желі теңдерін іске қосыңыз және тек операторлар көші-қон жоспарына келіскеннен кейін валидаторларды жаңа конфигурацияға ауыстырыңыз.

:::

## Жеке және Қоғамдық Кілттердің Көпөлшемді Хеш Форматы {#multihash-format-of-private-and-public-keys}

Егер сіз [клиент конфигурациясы](/kk/guide/configure/client-configuration.md)-ге қарасаңыз, онда ондағы пернелер [көп хэш пішімі](https://github.com/multiformats/multihash)-де берілгенін байқайсыз.

Егер сіз бұрын көп хэшпен жұмыс істемеген болсаңыз, оң жақтағы бөліктің кілт байттарының он алтылық көрінісі емес деп ойлау табиғи нәрсе (екі символ бір) байт), бірақ ASCII (немесе UTF-8) ретінде кодталған байттар, және `public_key` және `private_key` инстанциялау кезінде жолдық литералға `from_hex` шақыру.

Сондай-ақ, жолдық литералға `PrivateKey::try_from_str` қосу тек дұрыс кілтті беретінін болжау табиғи деп саналады. Сондықтан егер сіз кілттегі биттердің санын дұрыс есептемесеңіз, мысалы, 32 байт орнына 64, онда бұл қате туралы хабарламаны шығарады.

Бұл екі болжам да қате. Өкінішке орай, қате хабарламалары осы типтегі бұзылысты түзетуде көмектеспейді.

Қалай түзетуге болады: `hex_literal` пайдаланыңыз. Бұл сонымен қатар жағымсыз символдар тізбегін айқын он алтылық сандардан тұратын кішігірім кестеге айналдырады.

::: warning

Тіпті `try_from_str` жүзеге асыру берілген жолдың жарамды `PrivateKey` екеніне көз жеткізе алмайды және егер ол жарамсыз болса, сізге ескерте алмайды.

Бұл кейбір айқын қателіктерді анықтай алады, мысалы, егер жолда жарамсыз символ болса. Дегенмен, біз көптеген кілт форматтарын қолдауды мақсат етіп отырғандықтан, ол басқаны көп істей алмайды. Сондай-ақ, егер сіз нұсқаулық жібермесеңіз, кілттің берілген есептік жазбаға дұрыс жеке кілт екенін айта алмайды.

:::

Мұндай нәзік қателіктер, мысалы, тікелей жолдық литералдардан десериализациялау арқылы немесе мағынасы бар жерлерде жаңадан кілт жұбын жасау арқылы болдырмауға болады.
